## 1. 出发点

### 1.1 两种使用场景

| | 工作模式 | 远程模式 |
|---|---|---|
| 场景 | 在电脑前 | 不在电脑前 |
| 入口 | 控制台的新界面，其次是命令行 | 飞书 |
| 用法 | 几个任务并行，每个任务一段能随时切换、隔几天还能接着说的对话；新事先建任务再在里面说；临时的事交给主管家 | 收通知、回关卡和确认、发短指令、看状态（晨报、`/todo`、`/status`、提醒）、交待一件临时的事；不在飞书里并行处理多个任务 |

目标：在电脑前用 Looper 处理几件事，要和同时开几个编码 CLI 会话一样顺手，同时保留 Looper 的后台执行、评审和记忆。

### 1.2 一个任务的两种做法

- **直接模式（默认）：** 每个任务有自己的助手。它和操作者对话，自己在任务的目录里读、改、跑，像在编码 CLI 里一样；操作者一句纠正马上生效。
- **编排模式：** 同一个助手把活拆成步骤交给后台的执行者，评审者把关，它根据结果做决定、在对话里汇报。用在时间长、能并行、要独立评审的活，或者操作者要离开的时候。
- **同一个任务里切换：** 说「交给后台」就切到编排；后台在跑时操作者回来说话，答的还是这个助手；操作者也可以把活拿回来，回到直接模式。

**不变的规则：** 在任务里，操作者只和这一个助手说话；消息直接进任务对话，不经过主管家，也不转述；停止、开始、接手这类控制由代码立刻执行，不排在模型后面。

### 1.3 优先级和范围

1. 工作模式的最小第一步最先做：控制台里新建任务、进对话、助手直接在任务目录里干活、过程看得见、能打断、全部任务看得见能切换（第 10 节）。编排模式是第 2 步。
2. 「飞书里一个任务一个话题」排到最后，并重新评估要不要；远程模式也许只要「回复任务的通知就是对这个任务说话」这一层（第 14 节）。
3. 远程模式已经上线的能力（投递层、晨报、「需要你处理」、状态卡、台账）照原计划做完，本文不改它们的角色。
4. 两种场景之间的衔接：飞书里关于某个任务的一句话落进那个任务的对话（第 14 节）。
5. 不在范围：主管家自己的改进（系统提示词用 append 模式、给管家装 skill）；桌面外壳（以后的待办，本文不设计，只要求新界面只用现有的 HTTP API 和流式通道、每个任务对话有自己的网址、在单独窗口里也能用）；另造「工作会话」对象；拆分主管家的那一条对话；用模型猜「说的是哪个任务」；把操作者的 CLI 会话记录交给 Looper；OS 级隔离。

## 3. 任务助手是什么

### 3.1 三种做法

| | a. 规划者的会话加一个直接模式（采用） | b. 新角色「任务助手」，编排时调用规划和派发的机制 | c. 直接模式是一个类执行者的会话，编排模式是规划者，共享对话记录 |
|---|---|---|---|
| 谁拿着上下文 | 一条会话（`planner-<task_id>`）贯穿两种模式 | 任务助手一条；编排时规划者另一条，任务助手把操作者的话转给它 | 两条，各模式各一条 |
| 切换时上下文怎么过去 | 同一份对话记录；按模式重启进程、换契约和权限，用同一个会话 id 续上（用不同工具集续同一会话有先例：会诊，`consult.py:19-21`） | 直接 → 编排：需求和交接给规划者；编排 → 直接：规划者的结果回到任务助手 | 两个方向都要交接 |
| 操作者的感受 | 一个助手 | 一个助手，但编排时它的话要转给规划者，纠正到下一个规划者回合才生效 | 切换时能感觉到换了人 |
| 契约 | 两份：直接模式（自由文本加工具）和编排模式（今天的 JSON），按模式换；切换时有一个类型化的回合说明 | 新角色一份，规划者不变 | 类执行者一份（今天的执行者契约是按步骤的），规划者不变 |
| 规划者要改多少 | 加模式、直接模式的回合循环、按模式启动、切换；编排的部分不改 | 不改规划者；新角色要从头做常驻会话、流式、停止、续接 | 执行者今天每步一次运行，要改成能长期对话的常驻会话 |
| 花费 | 编排回合带着直接模式的历史，上下文更长；切换时先压缩一次（3.3） | 两份上下文，加上转话的回合 | 两份上下文，加上两个方向的交接 |

**采用 a。** 只有 a 让操作者面对的真的是一个助手、一份上下文：b 在编排时又回到了把话转给规划者，c 每次切换都要交接、都会丢细节。a 的代价集中在规划者模块里，而且大部分能复用：常驻进程、续接、只读启动、`[CHAT]`、规划和派发都已经在那里，直接模式要的中断、回合中并入、部分输出 Claude Code 的常驻会话也已经有（第 2 节）。

### 3.2 一个任务一条会话

- 任务助手的会话就是 `agent_sessions` 里的 `planner-<task_id>`，任务对话的地址仍是 `task:<task_id>`。
- 任务在直接模式、就绪和已结束时，助手由 TaskRouter 的新表 `_agents` 管（按需起，闲置回收，第 8 节）；编排模式时，照今天由运行中的规划者（`_planners`，`tiers/task.py:417`）管。同一时刻一个任务只在其中一张表里；切换时前一个停掉进程（会话 id 留着），后一个用同一个 id 续上。
- 角色和 Profile：两种模式都用这个任务的规划者角色解析出的 Agent Profile，所以切换时运行时和 provider 不变，会话续得上。直接模式只能在支持它的运行时上跑（5.6）。

### 3.3 和既有决定的关系

- **规划者只读 RFC 的修订：** 那篇定了规划者不改文件、由工具强制。本文在编排模式下保留这一条；直接模式下，同一个助手用全部工具（启动时显式给 `Access.FULL`，显式权限优先于角色默认，`agent_settings.py:1024-1031`），读改都在任务的工作区里。编排模式下改文件的仍只有执行者。
- **角色提示词：** 规划者角色推荐的提示词写着「不要亲自修改文件」。直接模式不带规划者的角色提示词层，用代码定义的直接模式契约；编排模式照今天带。
- **工作区 RFC 的 W2：** worktree 原来在任务第一次开始时建。直接模式的任务第一次让助手干活时就要有工作区，所以改成在第一个直接模式的回合之前建（5.4）。
- **上下文：** 切换到编排之前，先对这条会话做一次无头压缩（Claude Code 支持，`runtimes/__init__.py:208`；规划者已经在用，`tiers/planner.py:5415`），让编排回合不必带着直接模式里所有的工具输出。

## 5. 直接模式

### 5.1 回合

- 操作者的一句话就是一个回合：`operator_chat.send` 的目标 `kind: task`（10.2 卡 1.4）把它交给这个任务的助手，不经过主管家。助手按需起（第 8 节），用 `--resume` 续上会话，在任务的工作区里跑。
- **契约**（新的模型可见内容，英文，公开）：你是这个任务的助手，在这个目录里直接干活；只读的查证和小改动自己做；任务的需求可能还没写，先和操作者谈清楚，需要时用 `task_requirement_set` 写下来；要交给后台时用 `task_handoff_propose` 提议，等操作者确认；不要假装做了没做的事。系统提示词里有任务一节（需求、项目、工作区方式和分支、有没有没提交的改动）、项目知识和操作者为这个目录记的笔记（W6），和规划者今天的一样；不带规划者的角色提示词（3.3）。
- **任务工具**（经 Looper 的 MCP 服务，凭据绑定这个任务，服务端逐次校验）：`task_requirement_set(text)` 写一版需求（`edit_requirement` 的同一条路径）；`task_title_set(text)`；`task_handoff_propose(summary, next)` 在对话里出一张「交给后台」的卡片（第 6 节，第 2 步）；`task_review_request()`（5.5，第 2 步）。助手不能开始、交接、结束或重新打开任务，这些都是操作者的动作。
- **排队：** 回合进行中操作者又发来的话，界面显示「排队中」，到下一个回合边界送达（第 6 步再接入回合中并入，Claude Code 已支持，`runtimes/claude_code.py:157`）。直接模式没有决策回合，不会排在 `DECISION` 后面。

### 5.2 过程看得见

- 回答是自由文本，部分输出按 delta 转发给提问的一方，网页渠道照今天转成 `answer.delta`（`channels/web.py:327-331`）。不用从 JSON 里抽，所以没有半截 JSON 的问题。
- 工具调用：从流里的工具调用和工具结果事件，代码生成一行记录（工具名、参数摘要、结果摘要，各有长度上限，不放原始输出），作为新的流事件 `agent.tool` 发出，界面上可以展开。
- 结束时一条代码写的小结：这一轮改了哪些文件、提交到哪里（5.4）。

### 5.3 停止和控制

- **停止：** 输入框的 Stop、Esc 或 `/stop`，由 Looper 处理，调用常驻会话的中断（`claude_cli.py:1562`，Claude Code 的 `interrupt` 控制请求）。已经做了的改动留在工作区，小结照样写。排队的消息一起撤回。
- **其他控制**（按钮或固定命令，由代码执行，不交给模型）：`/done` 把任务记为完成；`/background` 交给后台（第 2 步）；`/takeover` 接手（第 2 步，编排模式下）；`/start` 开始一个就绪的任务。命令只认整句（去掉首尾空白、不分大小写），同关卡的 `END_WORDS`（`gate_routing.py:45`）。

### 5.4 工作区、落点和租约

- **工作区在第一个直接回合之前准备好：** 原地任务就是 `work_dir`；worktree 任务调用 `task_workspaces.prepare`（`task_workspaces.py:324-385`）建任务 worktree 和分支 T，之后一直在里面。草稿阶段就建，删草稿时照删除的规则收尾；T 上没有任何提交时连分支一起删，不留空分支。
- **落点：**
  - worktree 任务：每个改了文件的直接回合结束时，Looper 把改动提交到 T（Looper 的身份、不跑钩子、尾注 `Looper-Task` 和 `Looper-Turn`，用 `step_workspaces.commit_pending`，`step_workspaces.py:690`）。每一轮是一个提交，操作者可以点「撤回上一轮」：只能撤最后一轮，而且之后没有新的未提交改动，代码执行 `git reset --keep` 到上一轮的提交。
  - 原地任务：Looper 不提交，因为那是操作者自己的检出。每轮开始和结束各记一次 `git status`，小结里列出这一轮改了哪些文件；撤回由操作者自己用 git 做。
- **租约：** 每个直接回合开始时，非阻塞地拿这个 checkout 的共享锁（16.1），持有到回合结束；操作者在命令行用 `looper task enter --mode work` 持有排他锁时，这一轮不跑，回答「操作者正在命令行里改这个目录」。同一个任务的直接模式和编排模式不会同时存在（第 7 节），所以和自己的后台执行者不会撞上。

### 5.5 评审

直接模式不强制评审。操作者点「请评审者看一下」，或助手用 `task_review_request` 提议、操作者确认后，Looper 跑一次评审者（现有的评审角色和契约），看的是从上次评审（没有就是工作区的基点）到现在的改动，加上需求和助手写的小结；结论贴进对话，不阻挡任何东西，花费算在任务上。放在第 2 步。

### 5.6 运行时

直接模式要四样：常驻会话、写文件的工具、随时能中断、部分输出。

| 运行时 | 现状 | v0 |
|---|---|---|
| Claude Code | 常驻的 stream-json 会话、全部工具、`can_interrupt = True`、回合中并入已验证、部分输出（`runtimes/claude_code.py:157-169`、`:410-430`） | 支持 |
| Codex | 常驻会话按回合起进程（默认 `resident_transport = PER_TURN`，`runtimes/__init__.py:534`），没有设 `can_interrupt`（默认 False，`:538`）：停止会被拒绝，不会变成杀进程；运行中的引导只对执行者的运行（`codex_steer.py`） | 不支持 |
| DSH | 普通的 DSH 按回合起进程（`runtimes/dsh.py:302`、`:310`），不能中断；经 runner 跑时声明能中断（`runtimes/dsh_runner.py:69`），但 runner 上的常驻会话还没验证 | 不支持；runner 验证后再开 |
| Grok | ACP 的 `session/cancel` 能中断（`runtimes/grok.py:151-152`） | 以后评估 |

任务的规划者 Profile 不支持直接模式时，任务对话写明原因（`runtime_cannot_direct`），并给两条路：给这个任务换一个 Claude Code 的 Profile，或者直接交给后台（编排模式照今天在所有运行时上跑）。

## 6. 编排模式和切换协议（第 2 步）

### 6.1 直接 → 编排：`hand_off`

- **触发：** 操作者点「交给后台」或发 `/background`；或者助手用 `task_handoff_propose` 出卡片、操作者确认。
- **前提：** 没有直接回合在跑（有就先排在它后面，或者操作者先停掉它）；任务有确认过的需求。没有时，Looper 让助手跑一轮只写需求的回合，任务进入就绪（`init`），对话里出一张需求卡片，操作者点「开始」或改一句；在这张卡片之前说「直接交给后台」就跳过确认（21.2）。
- **执行：**
  1. 工作区：worktree 任务把剩下的改动提交到 T；原地任务记下 HEAD 和没提交的文件。
  2. 写一行 `task_handoffs`：方向、需求的版本、助手写的小结（做了什么、现在的状态、接下来做什么，至多 3000 字，由助手在一个交接回合里写，同今天的 `[HANDOFF]`，`tiers/planner.py:5986`）、工作区的 HEAD 和没提交的文件。小结也存成一条 `via = handoff` 的补充说明，所以之后的执行者和评审者都看得到。
  3. 对这条会话做一次无头压缩（3.3）。
  4. 状态 → `pending`，TaskRouter 照今天起规划者，用同一个会话 id 续上，编排模式的启动（只读）。`[PLAN]` 不再开新会话（`tiers/planner.py:1324-1328` 那一段改成：任务有助手会话时接着用），消息里带上第 2 条的交接；计划的 `start_commit` 是现在的 HEAD。
  5. 任务以前有过计划（例如结束后又回到直接模式），走第 12 节 `reopen` 的控制流：保留已验收的步骤，规划者拿到一轮带续接说明的回合。

### 6.2 编排 → 直接：`take_over`

- **触发：** 操作者点「我来接手」或发 `/takeover`，由代码执行。
- **两种方式：**
  - `finish`（默认）：不再派新步骤，正在跑的步骤做完并按今天的规则验收；这期间任务的状态是 `handing_back`，计划状态记为停止派发（同今天到上限时的 `stopping`，但不记失败）。最后一个步骤结束后，状态 → `direct`。
  - `stop`：立刻停掉正在跑的执行者和评审者（今天停任务的那条路径），没做完的步骤回到未开始，状态 → `direct`。
- **之后：** 规划者停掉进程（会话 id 留着），任务助手用同一个 id、直接模式的启动续上；第一轮前带一段代码写的说明：这次编排跑了什么、结果如何、工作区现在的状态。计划保留，下次 `hand_off` 接着它做。
- **编排中操作者说话：** 交给运行中的规划者，走今天的 `[CHAT]`，排队到它的下一个回合边界，界面显示它在做什么、这句话排第几。`[CHAT]` 的回答分段出现：契约要求 `"reply"` 是 JSON 的第一个键，规划者看到 `{"reply": "` 之后才转发字符串里已经完整解码的字符；键的顺序不对、JSON 不完整或流中途出错时一个字也不先显示，等整条回答到齐、解析成功后再显示 `reply`；解析失败时显示一行类型化的错误，从不显示半截 JSON。

## 7. 状态机

### 7.1 状态

| 状态 | 存的值 | 谁答 | 改文件的是谁 | 占执行并发 |
|---|---|---|---|---|
| 直接模式（含还没写需求的草稿） | `direct`（新，组 `TaskGroup.DIRECT`） | 任务助手（直接模式） | 任务助手 | 否 |
| 就绪 | `init`（复用） | 任务助手（直接模式） | 任务助手 | 否 |
| 编排中、等你 | 今天的那些 | 运行中的规划者（`[CHAT]`） | 执行者 | 是 |
| 交回中 | `handing_back`（新，组 `IN_PROGRESS`） | 运行中的规划者 | 正在跑的执行者，做完为止 | 是 |
| 已结束 | `completed`、`failed`、`stopped`、`cancelled` | 任务助手（只读回答） | 没有 | 否 |

`init` 能复用：它今天的意思就是「有需求、没开始、只能由用户开始」（`db/tasks.py:21-23`）；用旧路径（`tasks.create`、管家建任务）建的任务也是它。`direct` 不进 `ACTIVE_STATUSES`。

### 7.2 转换

```
新建（控制台、转成任务、管家建草稿）                       → direct
direct ──hand_off（需求已确认，或「直接交给后台」）──→ pending → 编排中 …
direct ──hand_off（需求没确认）──→ init ──开始──→ pending
init   ──操作者在对话里说话──→ direct（回到直接模式）
编排中 ──take_over finish──→ handing_back ──步骤做完──→ direct
编排中 ──take_over stop──→ direct
编排中 ──结束──→ 已结束                                        （不变）
direct ──/done──→ completed                                    （收尾同完成）
已结束 ──接着问──→ 已结束（只读回答，状态不变）
已结束 ──重新打开──→ direct（默认）                            （第 12 节）
direct、init ──删除──→ （删除）
```

- 一行：**`direct ⇄ 编排（init 确认 → pending … ；handing_back 回到 direct）→ 已结束 →（重新打开）direct`**。
- 开始、交接、接手、完成、重新打开都只由操作者触发（按钮或 5.3 的固定命令）；助手只能提议。
- `direct` 和 `init` 下操作者的话不当补充说明（今天 `init` 不收补充说明，`ops/tasks.py:549-551`），直接进对话。

## 8. 并发、预算与资源

- **任务助手的上限：** 新设置 `tasks.agents.max_resident`，默认 6：全机同时活着的任务助手（直接模式和结束后的只读回答）最多 6 个。编排中的规划者不在里面，照今天的生命周期。这个上限和管家会话的常驻上限是两个设置，后者归能力范围 RFC。
- **满了怎么办：** 新消息要起一个助手而已经有 6 个时，先停掉最久没说话的那个空闲助手（会话 id 留着，下一句话续上）；6 个都在回合中时，新消息排队，对话里显示「排队中：已有 6 个任务的助手在工作」，有一个结束就轮到它。
- **闲置回收：** 30 分钟没有回合就停进程（`tasks.agents.idle_seconds`），做法同规划者等关卡时停进程（`tiers/planner.py:287`、`:2620-2640`）。
- **内存：** 每个常驻进程空闲约 240 MB，带子进程树约 310 MB（助理层 RFC 第 4.2 节），6 个约 1.5–1.9 GB。按需恢复到第一次回答只比常驻慢 1–2 秒，所以不值得多留进程；内存紧的机器调到 4。
- **花费：** 直接模式的回合和结束后的回答都是这个任务的运行，记在 `llm_records` 上，算进任务的上限（任务自己的 `budget_usd`，没有就用项目的）。每轮之前用和 `_within_budget` 同一个谓词（抽成共用函数）算一次；到了上限不跑这一轮，回答「这个任务已到花费上限，提高上限后再说」，任务状态不变，不像编排中那样停掉任务、记为失败（`tiers/planner.py:6851-6887`）。费用拦截（`planner_budget.within`）照样生效，但不改直接模式和就绪任务的状态（7.3）。
- **执行并发：** 直接模式不派步骤，不占执行者和评审者的并发。

## 9. 续接和工作区的转换

- **能续上：** 同一个工作区路径、同一个运行时和 provider、会话记录还在时，`--resume` 原会话。
- **续不上：** 走现有的退路（开新会话，第一轮带 `[RESUME]` 简报，`tiers/planner.py:5523-5526`），并在任务对话里插一行类型化的事件 `session_fresh`：「原会话续不上，已用摘要重开」，带原因（运行时或 provider 变了、会话找不到、工作区路径变了）。不悄悄换会话。实际部署里重启后有一部分续接落到了这一路。
- **完成的 worktree 任务**（worktree 在完成时删了，`task_workspaces.py:402-440`），操作者回来说话时：

| 情况 | 转换 |
|---|---|
| 分支 T 还在 | `rebuild`：按 T 在原路径建回（`prepare` 的 `:353` 那一支），`task_worktrees.state` 记成新值 `kept`，助手在里面续原会话 |
| 分支 T 没了 | `read_only_open`：助手在工作区 W 里只读回答（新会话带简报，插 `session_fresh` 事件），不能重新打开（`branch_gone`） |
| T 正检出在别处 | 同上只读打开，说明 T 检出在哪 |

- **`kept` 要改的地方：** `task_worktrees.state` 的 CHECK（`schema.sql:509`）和 `WorktreeState`（`task_workspaces.py:63-65`）加 `kept`；启动清扫只认 `list_active`（`db/task_worktrees.py:40-47`），改成也认 `kept`：干净的 `kept` 目录在启动时照完成的做法删掉，有未提交改动的留着；清扫删任何目录之前先非阻塞地试 checkout 的排他锁，拿不到就跳过；`finish` 对不是 `active` 的行直接返回（`:413`），加一条删除任务的分支，`kept` 照 `active` 的做法先提交再删；助手闲置回收时，干净的 `kept` 目录一起删掉；重新打开时 `kept` 改回 `active`。
- 需要验证：Claude Code 换了工作目录后 `--resume` 能不能找到原会话；Claude Code 自己会不会清理很久以前的会话记录。两者都只决定走「续上」还是「退路」。

→ {items: [{task_id, title, requirement_head, project_id, project_name, status, group, mode,

## 11. 第 4 步：命令行

### 11.1 命令

```
looper task enter  [<选择>] [--all] [--mode observe|work] [--new] [--claude PATH]
looper task ask    [--task <选择>] <text> [--timeout SECONDS]
looper task brief  [<选择>] [--all] [--full] [--hook]
looper task sessions [<task_id>]
looper task reopen <选择> [<text>] [--budget-usd N] [--yes]                       # 第 3 步
looper task register --dir PATH [--requirement TEXT] [--handoff-file FILE] [--session ID] ...   # 第 7 步
```

- 都带 `--runtime-root`、`--config`，`--claude` 的默认值同 `looper claude-code`（`cli.py:122`）。退出码是这组命令自己的：0 完成，2 用法，3 列出了候选、什么都没做，4 拒绝，5 没有这个任务，6 数据库不可用，7 找不到 Claude Code（和 `looper ledger` 不同，那里的 3 是「台账没开」，`ledger_commands.py:8`）。在 Looper 启动的 agent 里一律拒绝（同 `ledger_commands.py:152-161`）；调服务时用本机的操作者令牌。

### 11.2 `looper task enter`

在任务目录里打开操作者自己的 Claude Code 会话，带任务简报；离开再进来续上同一条会话。这是操作者亲自动手的入口，和任务助手是两回事；在里面用 `looper task ask` 对任务助手说话，问答写进同一段任务对话。

- **方式：** 编排中的任务默认 `observe`（`--permission-mode plan`）；其他状态默认 `work`。`work` 要先拿 checkout 的排他锁（16.1）：编排中的任务持有共享锁，所以被拒绝并说明持有者；直接模式的任务只在助手的回合进行中持有共享锁，回合之间操作者可以进来动手，助手的下一轮会因为锁被占而等操作者退出（5.4）。完成的 worktree 任务用 `work` 进入时按第 9 节建回（`kept`）。
- **会话：** 第一次 `claude --session-id <新 uuid> --name "<标题> · <task_id>" --settings <钩子>`；以后 `--resume`；续不上提示 `--new`。会话 id 存在新表 `task_operator_sessions`（只在本机，`looper task sessions` 列出来）。父进程不 `exec`，退出后推进「上次离开以后」的游标；租约的描述符由 Claude Code 继承（16.1）。
- **简报：** `task_brief.compose(task_id)` 由代码拼出（头、需求、补充说明、计划或最近的直接模式小结、等你的关卡、上次离开以后、怎么用 `ask`）；别人写的内容由 `untrusted.fence()` 围起来，总是打开；总长上限 6000 字符，`--full` 打印全文。经 `--settings` 传一个只属于这次启动的 SessionStart 钩子注入（`looper task brief <id> --hook`），不写用户设置；`--hook` 时失败不写 stderr、退出 0，在 agent 里不输出（同 `claude_code_entry.py:69-73`），不带 `--hook` 时原因打到 stderr（`:74-78`）。需要验证：`--settings` 里的钩子和用户设置里的钩子是否都执行、`source` 的取值、`additionalContext` 的上限；不行就退回 `--append-system-prompt-file`。

### 11.3 `looper task ask`

把一句话发进任务对话（`kind: task`），等回答打印出来（默认 300 秒，超时只说还没答），消息记入口 `cli`。在 `enter` 打开的会话里（环境变量 `LOOPER_TASK_SESSION`）不用指明任务，也只接受这一个任务。

### 11.4 不用任务 id 找到任务

`enter`、`ask --task`、`brief` 和控制台的快速切换用同一个确定性的解析（服务端的 `tasks.select`，第 1 步的 1.5），结果是一个任务、一张候选表或没找到，从不调用模型：

| 选择 | 规则 |
|---|---|
| 任务 id（`task-` 加 12 位十六进制，`projects.py:619`） | 就是这个任务 |
| 省略 | 先看 `LOOPER_TASK_SESSION`；否则取 `cwd` 的真实路径，找 `work_dir`、`workspace_dir`、活着的或 `kept` 的任务 worktree 等于它或包含它的任务，只留最深的一层；剩一个就是它，几个时恰好一个没结束就取它，否则列出来；都没有就列出最近 14 天有动态的任务，最多 20 个 |
| 一个 MR | 整个选择是一个 MR：`/pull/<N>` 或 `/merge_requests/<N>` 的链接（带仓库），或 `!N`、`#N`、`MR N`、`PR N`、1 到 7 位纯数字；和任务等待步骤的 `github_pr` 检查（`waits.py:228-244`）以及标题、需求、原话、补充说明里认出的引用比较；任务文本里的纯数字不算引用 |
| 别的文字 | NFKC、转小写、空白合一、去两头的引号；按空格切词，每个词都要是标题或最新需求的字面子串（同 `db/tasks.py:690-691`） |

范围最近 90 天（`--all` 全部）；排序先看匹配的档次，再看是否没结束，再按最近动态；只有恰好一个匹配才直接进入，几个就列出（最多 10 行），没有就明说查了什么。

**粗估** 4–6 人日。**验证：** 方式和租约的每种组合；租约的先后顺序、子目录和符号链接、父进程被杀；钩子的几种 `source`；开工前用真实 Claude Code 验证标了「需要验证」的几件事。

## 12. 第 3 步：结束后接着做

### 12.1 接着问、接着做

- 结束后操作者在任务对话里说话：任务助手只读地回答（用规划者的只读启动，`[AFTER]` 回合，自由文本），状态不变。
- 要接着做：操作者点「重新打开」、发 `/reopen`，或助手用 `task_reopen_propose(text)` 提议、操作者确认。重新打开默认回到直接模式；以后再交给后台时，计划从原来的接着做（12.3）。

### 12.2 转换

`reopen` 由 `check_task_control(task_id, "reopen")` 检查：

| 当前状态或条件 | 结果 |
|---|---|
| 直接模式、就绪 | 拒绝 `not_ended`，直接说就行 |
| 编排中、等你、交回中 | 拒绝 `still_running` |
| 失败、停止、取消、完成 | 允许 |
| 没有目录 | 拒绝 `no_directory`（`projects.py:1257-1258`） |
| 定时任务产生的任务 | 拒绝 `scheduled_task`：它的规划者用的是定时任务共用的会话（`tiers/planner.py:7111-7138`），重新打开会写进下一次定时运行还要接着用的会话；要追问，改定时任务的需求或立即运行一次 |
| 绑了意图规则的任务 | 拒绝 `rule_bound`：开始路径处理规则执行的租约（`projects.py:1214-1238`），重置不碰那些行 |
| 完成的 worktree 任务、分支 T 没了 | 拒绝 `branch_gone`（第 9 节的只读打开） |
| checkout 的排他锁在操作者手里 | 拒绝 `lease_held`，说明持有者 |
| 已经到上限、没给新上限 | 拒绝 `budget_exhausted` |
| 任务有上限、花费读不到 | 拒绝 `budget_unavailable` |

**执行：** 检查都过才写；给了新上限就写进这个任务的 `tasks.budget_usd`（从不写项目的上限，不像 `tasks.continue` 在任务没有自己的上限时提高项目的，`v1_domains/task_configuration.py:61-70`；确认文案说的是这个任务）；续接说明存成补充说明（`via = reopen`）；一个事务里 `run_no` 加一（`reset_task_for_restart(keep_steps=True)`）、清掉 `completed_at`、写 `task_runs` 的一行、状态 → `direct`；工作区按第 9 节（`kept` 改回 `active`）；台账有条目时写一条 `note`（`actor_kind = user`；入口是 CLI 时 `session_label` 必填，`schema.sql:1831-1832`，在 `enter` 的会话里是 `task-session:<task_id>`，否则是 `cli:task-reopen`；写失败只记日志和计数，不中止）。

### 12.3 以后交给后台时

重新打开过的任务再 `hand_off` 时，规划者走 `_restart_plan`（`tiers/planner.py:4392-4492`）的续接，`REOPEN` 改三处：等待中的关卡那一段（`:4439-4451`）原样保留；`:4458-4460` 在计划已完成时直接 `_complete_plan` 并返回，这一句只对 `continue` 生效，否则规划者看不到续接说明；回合答 `none` 时先标送达，计划仍完成就再完成，这一轮失败时以 `reopen_turn_failed` 失败、续接说明不标送达。开头对完成的任务用自己的一句，不复用 `_ended`（`:4496-4500` 只有三种说法）。消息里带上直接模式在这期间做了什么（`task_handoffs` 的最新一行）和代码算出的目录变化。

### 12.4 预算、通知、`task_runs`

- 上限按任务累计，重新打开不重置；预检和 `_within_budget` 同一个谓词，在写任何东西之前做；到上限要在命令里给新上限；花费读不到时拒绝（重新打开是「再花钱」的决定）。
- 重新打开之后的结束只通知发起它的地方；原来的来源聊天默认不再收到（21.5）。
- 新表 `task_runs(task_id, run_no >= 2, reason ∈ {restart, start_over, at_cap, reopen}, via, ended_status, supplement_id, reply_route, created_at)`，在重置的事务里写，和 `task_outcomes` 按运行号对上；现有的 `restart` 不写 `reply_route`，通知照今天。

**粗估** 4–6 人日。**验证：** 上表每行一个测试；结束后的回答不改状态、不能写文件；`[REOPEN]` 收得到续接说明；关卡的「still waits」；`task_runs` 和 `task_outcomes` 对得上；`[AFTER]` 和 `[REOPEN]` 跑真实评测；一次性 serve 上「完成 → 接着问 → 重新打开 → 直接改 → 交给后台 → 完成」。

## 13. 第 2 步：编排模式

## 14. 第 5 步：两种场景之间的衔接

## 16. 并发与安全

### 16.1 checkout 租约

- **保证：** 同一个 checkout 上，操作者的一次 `looper task enter --mode work` 和任何任务的写入（直接模式的回合、编排中的执行者）不会同时发生。两个任务之间照 W5 只提醒。同一个任务的直接模式和编排模式由状态机互斥。`observe` 退出 plan 模式后写文件不在保证之内。
- **单位：** 目录所在 checkout 的真实路径（`git rev-parse --show-toplevel` 再取 `realpath`；不在 git 里就是目录本身）；worktree 任务用任务 worktree 的路径。子目录和符号链接都落在同一把锁上。`others_active_in`（`db/tasks.py:96-102`）只做字面相等，仍只用于 W5 的提醒。
- **锁：** 每个 checkout 一个锁文件（键的 sha256 前 16 位），放在用户级状态目录 `${XDG_STATE_HOME:-~/.local/state}/looper/checkout-leases/`，不放在 runtime root 下，CLI 和服务用不同的 runtime root 也碰得到；测试用 `LOOPER_LEASE_DIR`；不在本地文件系统上时拒绝（`lease_unsupported`）。任务的写入方持共享锁：编排中的运行从写 `pending` 之前拿到 `_teardown_task` 写完最终状态；直接模式的回合只在回合进行中持有。操作者的 `work` 持排他锁。持有者写进旁边的说明文件，被拒的一方据此说明是谁；互斥只看锁。
- **顺序：** 任务开始（开始、交接、重启、重新打开之后的第一轮、服务启动时的 `resume_tasks` 和 `start_tasks`，`tiers/task.py:270-300`）在写状态之前非阻塞地拿共享锁，拿不到就不开始（服务启动时恢复的任务记成 stopped，原因 `operator_session_open`）。操作者的 `work` 先拿排他锁，再写行，再启动 Claude Code。清扫删目录之前也试排他锁。
- **进程：** 操作者会话的锁描述符不设 close-on-exec，由 Claude Code 继承，父进程被杀而 Claude Code 还在写时锁仍在。脱离进程树又没继承描述符的后台进程不在保证内。
- **没有强行接管。** 被拒的一方只能等对方放开。

### 16.2 只有操作者

- 任务对话只有操作者能进：`kind: task` 的发送、新建直接模式的任务、交接、接手、完成、重新打开、`tasks.work_list`、`tasks.mark_seen`、`tasks.changes`、`tasks.select` 都是 `operator_only`；API 客户端调用答 `operator_only`。直接模式（能写文件的助手）只给操作者。群里的人通过场景管家接触任务，走能力范围 RFC 的规则。
- 管家的 `looper_task_draft` 只在操作者的回合里能用，`ops/tasks.py` 在调用时用 `operator_call(call.turn)`（`ops/service.py:1474`，只调用、签名不变）判断。
- 飞书里回复任务通知只认操作者本人；`looper task *` 在 Looper 启动的 agent 里拒绝。

### 16.3 注入和私有内容

- 简报、转成任务的开场、交接说明、`[REOPEN]` 里别人写的内容由 `untrusted.fence()` 围起来，这几处总是打开。
- 不给任务助手注入操作者画像：助手的话会写进需求、交接、步骤说明和 room，被执行者、评审者看到；它的输入只有这个任务的内容。要用画像里的偏好，操作者在对话里说。
- Looper 从不读操作者的 Claude Code 会话记录，也不写操作者的 Claude Code 文件；会话 id 只在本机。

## 21. 已定的问题

各项默认值以后都可以改。

### 21.1 每个任务默认直接模式，助手是规划者的会话

**决定：** 每个任务有一个助手，默认直接模式，需要时交给后台编排；助手就是这个任务规划者的会话加一个直接模式（3.1 的 a）。**理由：** 只有一个助手、一份上下文，操作者不会碰到转话；规划者已经有常驻进程、续接、规划和派发，直接模式要的中断和部分输出 Claude Code 已经有。**以后可以改：** 编排中的排队如果太长，再评估 3.1 的 b。

### 21.2 需求只在交给后台时确认一次，可以跳过

**决定：** 直接模式不要求需求；交给后台时，助手把对话整理成需求，任务停在就绪，操作者点「开始」或改一句；说「直接交给后台」跳过。**理由：** 后台执行和评审要一份明确的依据；直接模式里操作者就在旁边，不需要。**以后可以改：** 例如按项目设成默认跳过。

### 21.3 新界面先并存，以后替换

**决定：** `#work` 和 Chat 页并存，默认入口不变。**理由：** 改动面大，并存可以随时退回。**以后可以改：** 用顺了再替换。

### 21.4 任务助手有自己的上限

**决定：** 默认 6，闲置 30 分钟回收；满了先回收最久没用的空闲助手，都在忙时新消息排队并显示（第 8 节）。**理由：** 管家会话的上限归能力范围 RFC，规划者不在里面；回收空闲的比让操作者等更顺手，只有都在忙时才排队。**以后可以改。**

### 21.5 其他

- 重新打开之后只通知发起的地方，不通知原来的来源聊天（12.4）。
- 命令行动手：编排中默认只看，动手先拿 checkout 的排他锁，拿不到就说明持有者，不能强行接管（11.2、16.1）。
- 完成的 worktree 任务只在分支还在时建回，否则只读打开、不能重新打开（第 9 节）。
- 上限按任务累计，到了上限重新打开要给新上限；花费读不到时拒绝（12.4）。
- 登记已有目录默认原地（第 15 节）。
- 不用任务 id 也能找到任务，解析是确定性的代码（11.4）。
- 不给任务助手注入操作者画像（16.3）。
- 把 CLI 会话分叉给助手不做，列为以后的探索。
- 飞书话题待定（第 15 节）。

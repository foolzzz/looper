## 1. 背景与目标

有一类工作要周期性地做：每半小时看一次新告警并分析，每天早上检查依赖更新，每周整理一次测试失败。现在只能在
Looper 之外用 cron 或 launchd 写脚本，再自己调 agent。一个典型的例子是本机的告警监控，做法如下：

- launchd 每 30 分钟跑一次脚本；
- 脚本先拉告警、提取新增，有新增才调 agent 分析，分析有超时；
- 已处理过的告警记在一个索引文件里。

这类脚本反复踩到同一批坑，每个项目都得自己再写一遍：

- 电脑休眠时 cron 不跑，也不补跑；
- 进程卡死会带着锁一直挂着；
- 上一轮没退出时，下一轮的处理要么挡住、要么并发；
- 登录看着正常，实际已经失效；
- 失败被悄悄吞掉，要靠「连续 N 轮没成功」才能发现。

**目标：**

- 定时任务属于项目，按时间规则自动触发，每次触发是该项目里的一个普通任务，计划、执行、评审、花费、记录全部复用；
- 休眠和重启后的补跑、重叠、超时、连续失败告警，由平台统一处理；
- 一次运行能看到前几次运行的结果，不用每个项目自己造索引；
- 在项目页和管家聊天里都能创建和管理。

**不做：**

- 只跑命令、不跑 agent 的定时任务（D3）；
- 定时任务之间的依赖编排；
- 唤醒休眠中的电脑（只在醒来后补跑）。

## 2. 概念

| 概念 | 定义 |
|---|---|
| 定时任务 | 属于一个项目：一条时间规则（cron 表达式加时区）、每次要做的事（任务需求），以及运行策略 |
| 一次运行 | 定时任务的一次触发：按时触发、补跑或手动「立即运行」。它要么建出一个任务，要么记下为什么跳过 |
| 前置检查 | 可选的一条命令，在建任务之前执行，用来判断这次值不值得跑：没有新内容就跳过，省下一整个任务的花费 |
| 补跑 | 服务停了或电脑睡了，醒来后发现错过了若干次触发，按策略补跑一次或者跳过 |
| 重叠 | 到点时上一次运行建出的任务还没结束 |

### 2.1 边界：平台、项目、任务各管什么（2026-10-15 定）

- **平台（Looper）**：任何周期性的 agent 工作都需要的通用机制，不认识具体领域。把「告警」换成「每天检查依赖更新」，这些机制一个字不用改。
- **项目**：项目仓库和它在 Looper 里的项目配置。负责领域知识、脚本、工具和凭据，以及对平台机制的取值。
- **任务**：定时任务的需求。规定一轮具体做什么、这一轮的输入是什么、怎样算做完。

| 层 | 负责 |
|---|---|
| 平台 | 调度（时间规则、补跑、重叠、超时、立即运行、运行历史）；前置检查的**机制**（执行项目给的命令，按输出决定跑不跑，并把输出交给任务）；跨轮次连续性（前几次运行的结果、漏跑信息、**失败那一轮的输入交给下一轮**）；执行模型（规划、步骤并行、评审策略、并发和花费上限）；Agent Profile 与按角色、按项目选择的机制；项目说明对**所有运行时**可见；可靠性（进程树清理、卡死检测、重启恢复）；观测与告警（连续失败、长时间没有成功、发到渠道、总览页） |
| 项目 | 领域知识（排查流程、级别规则、归属、报告格式），放在项目背景和项目知识里；脚本（拉取、提取新增、自己的去重索引、标记已处理、上传和推送）；不进 agent 流程的确定性工作（例如需要秒级送达的转发，继续用脚本或 cron）；工具和凭据（本机 CLI 的登录）；在 Looper 里的取值（各角色的 Agent Profile、评审策略、并发、预算、通知发到哪里、测试期用的环境变量） |
| 任务 | 一轮做什么（例如「对前置检查给出的每条新增项各拆一个步骤，按流程处理；最后一步标记已处理并汇总」）；本轮输入（前置检查的输出，加平台注入的上一轮未完成项和漏跑信息）；验收标准 |

判断一项能力放哪一层：它对别的项目也成立，而且不需要领域知识，就放平台；需要领域知识或项目自己的状态，就放项目；只描述这一类运行做什么，就写进任务。

**例子：处理新增项时不能因为某一轮失败而漏掉。** 两层各管一半：

- 平台保证失败那一轮的前置检查输出会作为「上一轮未完成」交给下一轮（第 7 节）；
- 项目决定自己的索引什么时候推进：前置检查只列出未处理的项，不做标记；任务最后一步调用项目的标记脚本。

## 3. 现状可复用的部分

- **任务**：#88 之后任务可以「建好不跑」（`init`），再由 `TASK_START` 启动；启动受项目并发上限约束（#81）。
- **花费**：项目有单个任务的花费上限 `task_budget_usd` 及到达上限时的处理；运行记录按花费来源区分真钱和订阅等价。
- **任务级 Profile 覆盖**：`task_profile_overrides`，可以让定时任务用更便宜的代理配置。
- **渠道**：飞书、Telegram 已能向指定会话发消息。
- **管家**：已有「确认项目 → 代码生成配置块 → 问是否开始」的流程（#88），可以照搬到「是否启用」。
- **总览页**：已有按分组的任务计数和「需要处理」（#89）。

## 4. 决策

| # | 决策 | 理由 |
|---|---|---|
| **D1** | **每次触发都是一个完整任务**（规划者拆步骤、执行者执行、按需评审），不做「单个 agent」的轻量形态 | 维护者选定：复用全部任务能力，界面和记录统一；轻量形态以后真有需要再加 |
| **D2** | **漏掉的触发默认只补一次**，并把漏了几次、从何时起告诉这次运行；每个定时任务可改成「跳过」 | 维护者选定：休眠或重启后不至于一下子补跑一堆，又不会悄悄漏掉；需要回捞的任务自己根据漏跑信息回捞 |
| **D3** | **不做只跑命令的定时任务** | 维护者选定：纯脚本的周期拉取继续用 launchd；「先跑脚本再决定要不要叫 agent」由前置检查覆盖 |
| **D4** | **入口是项目页和管家** | 维护者选定 |
| D5 | **调度器在 `looper serve` 进程内**，到点从数据库读出到期的定时任务 | 配置、记录、界面都在数据库里，只有一处事实；服务本身由 launchd 守护。每个定时任务写一个 launchd 配置的方案，配置分散在两处，不采用 |
| D6 | **启用定时任务就是批准**：触发建出的任务直接开始，不停在「未开始」 | 无人值守是定时任务的本意；批准发生在创建和启用时（管家流程里明确问「要启用吗」） |
| D7 | **重叠时默认跳过这一次**，可改成「排队」（最多排一个）或「并行」（可重入，最多 `max_parallel_runs` 个，前置检查不并发） | 与 launchd 单实例的行为一致，防止任务越堆越多；并行留给增量、按认领分工的场景 |
| D8 | **cron 表达式自己解析**（标准 5 段：分 时 日 月 周，支持 `*`、列表、范围、步长），时区用标准库 `zoneinfo` | 项目运行时只依赖两个库，一个小解析器加表驱动测试足够；不支持秒和 `L`、`W`、`#` 这类扩展 |

## 5. 数据模型

```
schedules
  id                  'sched-<12 位十六进制>'
  project_id          → projects，项目删除前要先删除或移走它的定时任务
  name                项目内唯一
  cron, timezone      例：'0 9 * * 1-5'，'America/Los_Angeles'；默认服务器的本地时区
  requirement         每次运行的任务需求
  work_dir            为空时用项目默认目录
  gate_command        前置检查命令（S2），可空；gate_timeout_seconds
  overlap             'skip' | 'queue' | 'parallel'，默认 'skip'
  max_parallel_runs   overlap 为 'parallel' 时最多同时进行的运行数，1–10，默认 3
  catch_up            'once' | 'skip'，默认 'once'
  run_timeout_seconds 一次运行（任务）的最长墙钟时间，可空
  run_budget_usd      覆盖项目的单任务花费上限，可空
  daily_budget_usd    这个定时任务每天的花费上限，可空（S2）
  notify              'failures' | 'always' | 'never'，默认 'failures'（S2）
  notify_target       渠道和会话；为空时发到创建它的渠道会话（S2）
  profile_overrides   按角色的代理配置覆盖，写进每次建出的任务（存为表 schedule_profile_overrides，
                      外键指向 agent_profiles：定时任务选中的 Profile 不能删除）
  enabled             新建时为 false，由用户启用
  next_fire_at, last_fired_at, last_success_at, consecutive_failures
  created_via         'dashboard' | 'manager'

schedule_runs
  id, schedule_id, scheduled_for（应触发的时刻）, fired_at
  trigger             'scheduled' | 'catch_up' | 'manual'
  missed              这次补跑前漏掉的触发次数
  status              'queued'（排队等上一次的任务结束）| 'running'
                      | 'completed' | 'failed' | 'stopped' | 'cancelled' | 'timed_out'
                      | 'skipped_overlap' | 'skipped_missed'（补跑策略为跳过时错过的触发）
                      | 'skipped_gate' | 'skipped_budget' | 'gate_failed'（S2）
  task_id             → tasks，可空（跳过时没有任务）
  gate_output         截断保存（S2）
  summary, cost_usd, error, finished_at

tasks.schedule_id     可空，任务列表据此显示「定时」标记；定时任务删除后置空
tasks.budget_usd      任务自己的花费上限，覆盖项目的单任务上限（触发时从 run_budget_usd 复制）
```

状态只在一处推进：`schedule_runs` 的终态由任务结束时的回调写入，`schedules` 上的计数和时间戳同时更新。

## 6. 触发流程

调度器每 15 秒检查一次 `enabled AND next_fire_at <= now()` 的定时任务（`FOR UPDATE SKIP LOCKED`，即使误开了两个服务也不会重复触发），对每个到期的定时任务：

1. **算漏跑**：从 `next_fire_at` 到现在，按时间规则应触发几次（启用和改规则时 `next_fire_at` 从当时算起，所以不会回补）。只有一次且距现在不超过 2 分钟（正常到点）时，`trigger='scheduled'`；不止一次，或唯一的一次已过去 2 分钟以上（休眠醒来），都算漏跑，按 `catch_up` 处理：
   - `once`：只跑一次，`trigger='catch_up'`，`missed` 记录漏掉的次数；
   - `skip`：最近一次应触发的时刻距现在不超过 2 分钟时照常跑，否则记一条 `skipped_missed`，等下一个时间点。
2. **重叠**：上一次运行的任务还在进行中或排队，`skip` 记 `skipped_overlap`；`queue` 记下待跑，上一个结束后立刻跑，最多排一个；`parallel`（可重入，2026-10-15 加入，用于每分钟增量检查而一次运行较长的场景）在进行中的运行旁边再起一个，最多 `max_parallel_runs` 个同时进行，超过就记 `skipped_overlap`。前置检查任何时候都不并发：有运行在前置检查中时，这次触发记 `skipped_overlap`，只有任务阶段重叠。前置检查的环境里有 `LOOPER_SCHEDULE_ID`、`LOOPER_SCHEDULE_RUN_ID`、`LOOPER_SCHEDULE_SCHEDULED_FOR` 和 `LOOPER_SCHEDULE_RUN_TIMEOUT_SECONDS`，便于它为这次运行认领条目、按运行超时释放；失败那一轮的输入只交给下一次运行；每日花费上限按所有运行合计；在项目 Planner 并发上限下排队的运行，运行超时照样计时，`max_parallel_runs` 超过这个上限时保存会给出提醒。
3. **每日花费**（S2）：这个定时任务今天的运行花费已达 `daily_budget_usd`，记 `skipped_budget`。
4. **前置检查**（S2）：在工作目录里执行，有超时；超时（或服务停止）时按停止 agent 的方式结束它的整个进程树（`proc_tree`：先发终止信号，宽限期后强杀）。
   - 输出为空：记 `skipped_gate`；
   - 有输出：带进任务；
   - 失败：记 `gate_failed`，算一次失败。
5. **建任务并开始**：需求是定时任务的 `requirement`，后面附一节「定时运行上下文」（第 7 节），`schedule_id` 记在任务上，按任务覆盖写入 `profile_overrides`，然后直接走启动流程，受项目并发上限约束（D6）。
6. **推进时间**：`last_fired_at` 设为这次应触发的时刻，`next_fire_at` 设为现在之后的下一个时刻。

**手动「立即运行」**：`trigger='manual'`，同样经过重叠检查和前置检查，不改 `next_fire_at`。

**任务结束**：写入运行的终态、花费和摘要（任务结果）；成功时清零 `consecutive_failures` 并更新 `last_success_at`，失败时加一；按 `notify` 发通知。

**超时**：运行超过 `run_timeout_seconds` 时，按现有的停止流程停掉任务，记 `timed_out`，算一次失败。

## 7. 跨轮次上下文

每次运行的任务需求后面附上，由代码生成：

- 定时任务名称、时间规则（附人话描述），以及这次应触发的时刻（本地时区）；
- 是否补跑；漏了几次、从何时起（D2）；
- 前置检查的输出（S2）；
- 最近 3 次运行的结果：时刻、状态、任务摘要（截断）；
- 上一轮没有成功时，它的前置检查输出，标为「上一轮未完成」（S2）；
- 一句约定：这是无人值守的运行，不要等用户回答，需要假设时做出合理选择并写进结果。

再长期的经验照常进项目知识（M7b），由规划者在任务完成时沉淀。

## 8. 可靠性与监控

| 风险 | 处理 |
|---|---|
| 电脑休眠、服务重启 | 醒来后按 D2 补跑；补跑的运行里写明漏了几次 |
| 运行卡死 | 墙钟超时停任务；前置检查超时后强杀整个进程组 |
| 重叠堆积 | D7：默认跳过，排队最多一个 |
| 连续失败 | `consecutive_failures` 达到 3 时通知一次，恢复成功后再通知一次（S2） |
| 长时间没有成功 | 超过「3 个周期」（至少 15 分钟、至多 24 小时）仍没有成功，通知一次（S2）；运行进行中不算 |
| 花费失控 | 单次运行用任务花费上限；每日上限（S2）；时间规则的最小间隔为 5 分钟，有前置检查的为 1 分钟（没有新内容时停在前置检查，不建任务、不花钱） |
| 重复触发 | 每次触发的读改写在一个事务里完成，用 `FOR UPDATE SKIP LOCKED` 锁住到期的那几行 |

总览页（S2）新增「定时任务」一栏：接下来 5 次触发、正在失败的定时任务，以及今天被跳过的运行次数，每项可点。

## 9. 入口

## 10. 时间规则

- 标准 5 段 cron，分、时、日、月、周。周日写 0 或 7；日和周都限定时按 cron 惯例取「或」；
- 时区存 IANA 名称，按当地墙钟时间计算：
  - 夏令时跳过的时刻（如 02:30 不存在）顺延到当天下一个有效时刻；
  - 重复的时刻（回拨）只触发一次，取第一次；
- 两次触发的最小间隔为 5 分钟，有前置检查命令的定时任务为 1 分钟，保存时按接下来 24 小时内的触发时刻检查；去掉每分钟触发的定时任务的前置检查会被拒绝；重复的跳过（同一原因、同一天）记在最近那一次运行上（`firings`），不每分钟新增一行；
- 界面和管家都显示人话描述，以及接下来几次触发的时刻。

## 11. 评测与验收

- **单元测试**：时间规则解析与「下一次」计算用注入的时钟，覆盖步长、列表、范围、日和周取或、月末、夏令时前后两个方向；补跑判断（无漏跑、漏 1 次、漏多次、`skip` 的 2 分钟窗口）。

| S3 | **并入[管家平台工具 RFC](manager-platform-tools-v0.zh-CN.md) 的 T3**（2026-10-15）：管家入口改用平台工具实现，导出与导入一起做 | S2、管家平台工具 T2 |

S1 实现与上文的出入：

- 唯一一次到期的触发若已过去 2 分钟以上，也按漏跑处理（`once` 补跑并写明漏了 1 次，`skip` 记 `skipped_missed`），休眠醒来时不会把几小时前的触发当作准点；
- 运行状态补了 `queued`、`cancelled` 和 `skipped_missed`；用户停止或取消的运行不计失败也不计成功；运行的终态只写一次；
- 重叠判断看这个定时任务建出的任务里有没有仍在进行（排队、运行，或刚建好待开始）的，所以超时被停、还在收尾的任务也算重叠；
- 建出的任务先以 `init` 写入，同一事务提交后立即发 `TASK_START`，走 TaskRouter 原有的启动路径（受项目并发上限约束）；若服务恰好在两者之间停止，调度器在任务停在 `init` 超过 1 分钟后重发；
- 名称重复、项目还有定时任务时删除项目，按现有接口的惯例返回 409（其余校验错误返回 400）；
- `profile_overrides` 存为表、`run_budget_usd` 落到任务的 `budget_usd` 上，见第 5 节；任务在自己的上限处失败后「提高上限继续」只提高这个任务的上限。

S2 实现与上文的出入：

- 前置检查在事务之外后台执行，期间运行记为 `gating`（算作进行中，这时的触发按重叠处理）；服务停止时被打断的记 `gate_failed`。宽限期沿用停止 agent 的（`proc_tree`，3 秒），不是 10 秒；它退出后留在自己进程组里的进程一并结束。
- 「上一轮未完成」只看上一次真正跑了东西的运行（跳过的不算），它失败、超时、被停止或取消、或前置检查失败，且有前置检查输出时才交给下一轮；这时即使这次前置检查没有输出，也照样建任务。上下文里写明前置检查的输出就是这一轮的输入，只处理这些。
- 每日花费按服务器本地零点起「这一天触发的运行」计：已结束的按记录的花费，进行中的按它的任务到目前为止的花费；跨零点的运行算在触发那天。
- `notify`：`failures` 只发失败（`failed`、`timed_out`、`gate_failed`）的运行，`always` 发每次跑了东西的运行，`never` 什么都不发（告警也只留在总览页）；跳过的运行从不发。目标是渠道发送者白名单里已有的聊天（Telegram 用户 ID、飞书 open_id），不填只在总览页显示（Q2 改为这样：项目页还不知道「创建它的渠道会话」）。每条消息都记在 `schedule_notifications` 里，发送失败也记下原因。
- 「长时间没有成功」从上次成功（完成，或前置检查没有新内容）、最近一次启用（`enabled_at`，创建时也记一次）和最近一次改规则或时区（`rule_changed_at`）三者中最晚的那个之后的第一次触发算起，取 3 个周期，但不少于 15 分钟（每分钟触发的有前置检查的定时任务，3 个周期只有 3 分钟，没有意义）、不多于 24 小时；还没运行过的不告警；有运行正在进行（排队、前置检查中，或任务在运行超时内运行）时不告警，它造成的「上一次还在跑」跳过也不算。停用期间不算：停用很久后再启用，不会一启用就告警，停用的定时任务也从不告警。前置检查没有新内容算健康，不会因此告警。

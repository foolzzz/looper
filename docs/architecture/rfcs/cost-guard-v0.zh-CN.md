# RFC：花费守卫 v0（运行前准入、按天和按角色的上限、没人回的推送）

- **状态：** 决策已定案（2026-11-22），本文仅为文档，不包含实现。维护者对第 17 节 Q1–Q10 全部采用推荐答复，记录在第 18 节（D15–D24）；后续实现按第 15 节的 PR 顺序另行交付。
- **需求：** 花费由代码守住，而且在超出之前就守住，不是花完了才发现：
  - 任务、定时任务、后台角色、整个 Looper 每天各有上限；
  - 运行开始之前先算一笔预留，在跑的运行也算进去；
  - 到了上限，按事情的性质处理：你发起的事先问你，后台的事停掉并告诉你，从不悄悄换模型；
  - 订阅登录没有逐次的价格，它的「等价花费」和真花的钱分开算，订阅的用量窗口另外看；
  - 一个定时推送连着几天没人回，先问你一次，再没人回就自动暂停。
- **里程碑命名：** 按维护者的产品设计，本 RFC 是第 4 期的 P4.7（花费守卫，产品设计第 14.7.8 节）。它同时落实第 14.7.9 节模型接入层里的 G3（按角色的每日预算），以及第 14.8 节「成本上涨」一行的「每日花费告警」。第 14.7.9 节的 G2（用量和限流信号）、G4（降级规则类型化）和 P4.3（全局准入和公平队列）不在本文，本文只用到它们已有的信号。
- **相关：**
  - #1502（用量和限流信号，`provider_limit_windows`）、#1514（失败分型，`llm_records.failure_class`）：本文读它们的信号，不重复记录。
  - #1523（度量与评测底座）：花费指标的口径（真钱和等价花费分开）。
  - #1506 和 #1543（管家的会话预算、单轮上限）：本文第 12 节说明两者怎么配合。
  - [对外动作审查 RFC](outbound-review-v0.zh-CN.md)：审查分类器的花费，第 12 节。
  - [Advisor RFC](advisor-v0.zh-CN.md)：`advisor_daily_alert_usd` 和请教的预算。
  - [助理层 RFC](assistant-layer-v0.zh-CN.md)：「需要你处理」、送达层、`proactive_deliveries`。
- **核对基线：** `main` `2cfe4f00a`；用量信号和失败分型尚未在 `main`，另核对了未合入的 #1502（`1fd2e8987`）、#1514（`ee0a633c5`）及 #1543。第 4 节的现状是读代码得出的，每项标了出处。本文没有启动服务，也没有调用模型。
- **术语：**
  - **真钱：** 用 API key、按供应商价格计费的运行的花费（`spend_since` 的 `provider_priced_usd`）。
  - **等价花费：** 订阅登录的运行按 API 价格折算的数字（`equivalent_usd`），不是真花的钱，是订阅用量的近似。
  - **用量窗口：** 订阅账号自己的限额，例如 5 小时窗口、每周窗口，由 #1502 记录（`provider_limit_windows`：状态、利用率、重置时间）。
  - **预留：** 一个运行开始之前，按它可能花的钱先占住的额度；运行结束、花费已知时换成实际花费。
  - **准入：** 运行开始之前问一次「还能不能花」；回答只有放行、不放行、先问你三种。
  - **范围：** 上限作用的对象：一次运行、一个任务、一个定时任务的一天、一个后台角色的一天、整个 Looper 的一天。

## 1. 背景与目标

Looper 现在已经有好几种上限（第 4 节），但它们有几个共同的缺口：

1. **大多是事后的。** 任务上限只加总已有 `cost_usd` 的记录，没有给仍在跑且花费未知的运行预留，并行的几个 Worker 加起来能超出好几倍；processor、room consult、advisor、对外审查的上限都在运行结束后才检查，钱已经花了，只是丢掉输出。
2. **订阅登录没有事中的估算。** Claude Code 订阅登录的运行只靠 CLI 的 `--max-budget-usd`，它会多出一次请求，而且常驻进程按整个进程的寿命累计；Grok、Cursor、Coco 的运行根本没有逐次的上限。
3. **没有按天的总上限。** 唯一的全局数字是 `advisor_daily_alert_usd`，只告警，不拦。
4. **两种钱混在一起。** 任务上限和定时任务的每日预算把等价花费和真钱加成一个数。
5. **到了上限只有一种做法。** 任务直接失败；定时任务悄悄跳过（`skipped_budget` 不发任何消息）；没有「先问你」这一步。
6. **没人看的推送一直推。** 定时推送不会因为没人回而停下，也不会问你还要不要。

**目标：**

- 所有运行在开始前过一次准入，在跑的运行按预留计入，上限在超出之前就起作用。
- 真钱、等价花费、订阅用量窗口三者分开：前两者各有自己的上限，第三者由用量信号决定是否暂缓。
- 到上限的动作是类型化的、按范围定的：问你、停掉这个角色到明天、跳过这一次、等用量窗口重置；都会通知你。
- 实现产品设计 P4.7 的「没人回的推送」规则：先问一次，再自动暂停；被暂停的出现在「需要你处理」里，能一键恢复。
- 默认关闭，关闭时行为、命令行、提示词、工具列表逐字节不变。

**不做：**

- 不做多账号轮换来绕开限额（产品设计第 14.7.9 节明确不做）。
- 不做按供应商、按账号的全局并发槽位和公平队列（P4.3）。本文只在用量窗口被拒时暂缓后台角色。
- 不悄悄降级模型。降级只用于你明确配置了备用 Profile 的后台角色（D7）。
- 不改现有的单次运行上限、任务上限的默认值。

## 2. 用户入口的变化

| 入口 | 变化 |
|---|---|
| 控制台 | Settings 多一个「花费」页：每日上限（真钱、等价花费分开）、各后台角色的每日上限、到上限的动作、没人回的推送规则；首页「今天的花费」旁边显示离上限还有多少；「需要你处理」多一类「花费」（等你决定继续还是停下的事，被暂停的定时推送） |
| 飞书、Telegram | 打开后：到上限时的提问和告警发给你（每个范围每天最多一条，第 10 节）；回「继续」「停」处理提问 |
| CLI | `loopercli cost_guard get/update`、`loopercli cost_holds list/decide`（由 v1 目录生成） |
| Agent | 没有新工具；被拦下的运行会收到类型化的拒绝（不是模型可见的提示词改动，第 14 节） |

## 3. 决定

| 编号 | 决定 | 理由 |
|---|---|---|
| D1 | **三种量分开：** 真钱、等价花费各有上限；订阅用量窗口不换算成钱，由 #1502 的信号决定暂缓 | 混在一起会让订阅登录的数字吓人或者被忽略；用量窗口才是订阅真正的限制 |
| D2 | **运行前准入：** 所有运行在开始之前都调用同一个函数 `cost_guard.admit`，回答是 `ADMIT`、`DENY`、`ASK` 三种之一（第 6 节） | 只有这样才能在超出之前拦住；分散的检查会漏 |
| D3 | **预留：** 准入通过时，按这个运行的预估金额占住额度，写在它的运行记录 `metadata.reservation`（金额和币种）里；运行结束、花费已知时释放，换成实际花费 | 在跑的运行也算进去，并行的 Worker 不会一起冲过上限；预留落在运行记录上，重启后能算回来，不用另建表 |
| D4 | **预估的口径：** 有单次上限的用单次上限；没有的，用这个角色近 30 天单次花费的 P95，但不低于下限；订阅登录的运行按模型目录的价格（`pricer`）在事中软限（照 #1543 的做法） | 不预估就没法事前判断；P95 让少数大运行也被兜住 |
| D5 | **范围：** 一次运行（已有）、一个任务（已有，加上预留）、一个定时任务的一天（已有的每日预算，加上预留，两种钱分开）、一个后台角色的一天（新，产品设计的 G3）、整个 Looper 的一天（新）。每个范围是枚举 `BudgetScope` 的一个值 | 每一层都有人会问「这一层花了多少」；整个 Looper 的一天是最后一道 |
| D6 | **到上限的动作按范围定，是枚举 `LimitAction`：** 你发起的事（任务、管家的回合）是 `ASK`；后台角色是 `STOP_ROLE`（停到第二天，告诉你）；定时任务是 `SKIP`（跳过这一次，告诉你）；用量窗口被拒是 `HOLD`（暂缓到窗口重置）。动作可以在 Settings 里按范围改，但只能在这几个值里选 | 你发起的事应该由你决定；后台的事不值得每次都问；所有动作都通知你 |
| D7 | **不悄悄降级模型。** 后台角色在 Settings 里配置了备用 Profile 时，到上限可以选 `FALLBACK`（换到备用 Profile，告诉你）；管家、Planner、Worker、Reviewer（包括收尾回合）不提供这个动作；切换 Profile 后必须重新准入（第 7 节） | 产品设计第 14.7.9 节 G4：管家和 Planner 换模型之前先告诉你，不悄悄换 |
| D8 | **「先问你」是一条类型化的记录（`cost_holds`）：** 进「需要你处理」的「花费」一类，你可以在控制台、私聊或 CLI 回答「继续（这一层上限提高到 X）」或「停」；24 小时没回答，按「停」处理 | 提问要能被追踪、能在任何入口回答，也要有终点 |
| D9 | **没人回的推送（产品设计 P4.7）：** 一个定时任务或订阅在 3 天里推送不少于 15 条、你一条都没回，就问你一次；再过 3 天还没回，自动暂停，暂停原因记为 `unanswered`；被暂停的出现在「需要你处理」里，可以一键恢复 | 产品设计的原规则 |
| D10 | **暂停有原因：** `schedules` 加 `pause_reason`（`operator`、`unanswered`、`budget`、`quota`）和 `paused_at`；`enabled = false` 仍然是生效的那个开关 | 没有原因就分不清是你停的还是 Looper 停的，也没法在「需要你处理」里解释 |
| D11 | **只有操作者能改上限和规则：** v1 操作 `cost_guard.get`、`cost_guard.update`（`operator_only`，提高上限要确认）；管家的 `looper_settings` 不列它们 | 上限是对 agent 的约束，agent 不能自己放宽 |
| D12 | **分阶段打开：** 开关 `cost_guard.mode` 取 `off`（默认）、`observe`、`enforce`。`observe` 只记录「本来会怎样处理」，不拦也不问；先 `observe` 一周，看过记录再改成 `enforce` | 上限设错的代价很大（任务被拦下、推送被停）；先看一周数据 |
| D13 | **守卫自己出错时允许继续原执行路径（fail-open），并告警；不绕过审查。** 对外动作的放行只表示分类器照常运行，仍须得到允许结论且写入审计；审查路径异常、预留失败或 `cost_holds` 写失败仍拦截动作（第 12 节） | 普通运行保留现有单次和任务上限；审查保留 `review()` 的异常即拦截边界 |
| D14 | **关闭时逐字节不变。** `mode = off` 时 `admit` 只检查已加载的配置，直接返回 `ADMIT`，不做任何读写 I/O；没人回的推送规则有自己的开关 `cost_guard.unanswered_pushes.enabled`，默认关 | 每项新行为一个开关，默认关 |

## 5. 三种量和预估

### 5.1 三种量

| 量 | 来源 | 上限的单位 | 到上限 |
|---|---|---|---|
| 真钱 | 运行记录的 `cost_usd`，计费方式不是订阅等价（`EQUIVALENT` 为假） | 美元 | 第 7 节按范围的动作 |
| 等价花费 | 运行记录的 `cost_usd`，`EQUIVALENT` 为真 | 美元（等价） | 同上，阈值单独设 |
| 用量窗口 | #1502 的 `provider_limit_windows`（`status`、`utilization`、`resets_at`）；#1514 的 `failure_class = quota` | 窗口状态 | `HOLD`（第 9 节） |

每个运行属于哪一种钱，在准入时就能确定：它的 Profile 的供应商认证方式（`oauth` 是订阅）和运行时的计价方式（`CostSource`）。准入和预留都按这个币种记。

### 5.2 预估（预留的金额）

按顺序取第一个有的：

1. 这个运行的单次上限（`run_budget_usd`、管家的单轮上限、processor 的上限、请教和审查各自的上限）；
2. 没有单次上限时，取 `max(这个角色近 30 天单次花费的 P95, 下限)`（同一币种）；启动时先从运行记录重算 P95，之后每天刷新一次，缓存放内存；
3. 同一角色、币种没有可用样本时才直接用下限：$0.50（Planner、Worker、Reviewer、管家）、$0.05（processor、判别、审查）。`observe` 记录注明 `estimate_source = floor_no_samples`，便于发现冷启动低估；不能仅因重启清空了缓存就跳过历史重算。

- **常驻会话：** 管家、Planner 的常驻进程跨多个回合。预留按**回合**算：每个回合开始前准入一次，用单轮上限或这个角色单个回合的 P95。
- **事中软限（仅 `enforce`）：** 订阅登录的运行在事中也按模型目录的价格估算花费（`runtimes.pricing.pricer`，#1543 已经这样做）；有价格就建 `RunSpend`，到了预留就按现有的软上限路径结束。没有价格的（Coco 等），只在开始前把关。
- **运行结束：** 运行记录关闭时，预留换成实际花费；实际比预留多，差额照实记入，下一次准入就会看到。

## 6. 准入

### 6.1 调用点

| 运行 | 调用点 | 范围链（从小到大） |
|---|---|---|
| Worker | `PlannerAgent._dispatch_step` | 任务 → 全局的一天 |
| Reviewer | `PlannerAgent._dispatch_review` 等三种评审的派发 | 任务 → 全局的一天 |
| Planner 回合 | Planner 每个回合开始前（`_within_budget` 所在的位置） | 任务 → 全局的一天 |
| 管家回合 | 管家的用户回合、收尾回合开始前 | 全局的一天（管家没有任务；单轮上限仍按 #1543） |
| 定时任务触发 | 调度器触发前（每日预算检查的位置） | 定时任务的一天 → 全局的一天 |
| processor、线索核对、判别、审查分类器、advisor | `processor.run`、`spawn.run_child` 开始前 | 角色的一天 → 全局的一天（定时任务的运行再加定时任务的一天） |
| room consult | `consult` 开始前 | 任务 → 全局的一天 |

- **一个函数：** `cost_guard.admit(run_kind, scopes, currency, estimate) -> Admission`。`Admission` 是 `ADMIT`、`DENY(scope, action)`、`ASK(hold_id)` 之一。调用方只按这个类型化的结果分支，不读文字。
- **怎么判：** 对范围链上的每一层：已结束运行的实际花费 + 在跑运行的预留 + 这次的预估，超过这一层的上限，就按这一层的 `LimitAction` 处理；最先触发的那一层说了算。
- **计数在内存里：** 每层的「已花 + 已预留」由内存里的计数器维护，启动时从运行记录算一次（今天的已结束运行，加上在跑运行的 `metadata.reservation`），之后在运行记录开始和关闭时增减。准入不查大表。
- **天的边界：** v0 复用 `Scheduler.day_start`，守卫、定时任务每日预算和订阅的 `SubscriptionRuns.day_start` 使用同一日界线。`main` 的调度器默认按服务器本地时区（构造时可指定 `day_zone`），尚未读取 `user.timezone`；不能声称两者已经一致。v0 不单独把守卫切到用户时区；若以后采用 `user.timezone`，必须一起迁移调度器、订阅与守卫，并重算当日计数。

### 6.2 调用方怎么处理结果

| 结果 | Worker、Reviewer | Planner 回合 | 管家回合 | 定时任务 | 后台角色 |
|---|---|---|---|---|---|
| `ADMIT` | 照常 | 照常 | 照常 | 照常 | 照常 |
| `ASK` | 这一步不派出，任务进入「等你决定」（新的任务状态，第 13 节），已经在跑的不停 | 回合不开始，任务同上 | 见第 12 节 | — | — |
| `DENY`（`SKIP`） | — | — | — | 跳过这次触发，记 `skipped_budget`，并告诉你（第 10 节） | — |
| `DENY`（`STOP_ROLE`） | — | — | — | — | 这个角色今天不再运行；调用方按各自已有的失败处理（例如线索核对失败放行、审查失败即拦截） |
| `DENY`（`HOLD`） | 这一步等到用量窗口重置再派出 | 回合等到重置 | 见第 12 节 | 推迟到重置之后 | 推迟到重置之后 |

- **被拒的运行对 agent 来说是一个类型化的结果：** 例如 Planner 收到的是「这一步因为花费上限暂停，等操作者决定」，和现在等关卡一样的状态，不是提示词里的新内容。
- **已经在跑的运行不被打断。** 守卫只管开始；在跑的运行由它自己的单次上限和事中软限管。

## 7. 范围与上限

| 范围 | 设置 | 默认 | 到上限的默认动作 | 可选的动作 |
|---|---|---|---|---|
| 一次运行 | 现有的 `run_budget_usd` 等 | 不变（内置默认仍是不限） | 现有行为（软上限、CLI 的上限） | — |
| 一个任务 | 现有的 `task_budget_usd`，现在把在跑运行的预留算进去 | 不变 | 现有的 `task_budget_action`（`fail`） | 新增 `ask`：不失败，进「等你决定」 |
| 一个定时任务的一天 | 现有的 `daily_budget_usd`，加上 `daily_budget_equivalent_usd`；都把预留算进去 | 不变（不设就不限） | `SKIP`，并告诉你 | `SKIP` |
| 一个后台角色的一天 | 新：`cost_guard.roles.<role>.daily_usd` 和 `daily_equivalent_usd`；角色是 processor、`leads_check`、`advice_check`、`outbound_check`、`advisor` | 不设（不限） | `STOP_ROLE` | `STOP_ROLE`、`FALLBACK`（配置了备用 Profile 时） |
| 整个 Looper 的一天 | 新：`cost_guard.daily_usd`、`cost_guard.daily_equivalent_usd` | 不设（不限） | 你发起的事 `ASK`；后台角色 `STOP_ROLE`；定时任务 `SKIP` | 按事情的种类分别选 |

- **默认都不设：** 打开守卫本身不会拦任何东西，直到你设了上限。打开前建议用 `observe` 模式看一周（D12），再按近 30 天的分布定数字（第 17 节 Q1）。
- **80% 提醒：** 每一层到 80% 时提醒一次（第 10 节），给你时间提前调整。
- **收尾回合不提供 `FALLBACK`：** 管家和 Planner 的收尾仍属于各自角色；到上限不能借「后台」身份自动换模型，准入被拒时按第 12 节退回代码通知或原结束路径。
- **Profile 切换后重新准入：** 无论是操作者手动切换，还是允许的后台 `FALLBACK`，都按新 Profile 的认证方式、币种、单次上限或同币种 P95 重算预留，检查完整范围链和用量窗口。旧的未启动预留先释放，新的预留成功才运行；不得复用旧 Profile 的 `ADMIT`，也不得借切换清零同币种角色/全局累计。备用 Profile 仍被拒时停止，不循环切换；后台备用不得用于绕过第 9 节的账号限额。

## 8. 没人回的推送（产品设计 P4.7）

**开关：** `cost_guard.unanswered_pushes.enabled`，默认关。它读 `proactive_deliveries`，所以打开时要求 `manager.metrics.enabled` 已经打开；没打开就拒绝，并说明原因。

| 阶段 | 条件 | 动作 |
|---|---|---|
| 提问 | 一个定时任务（含订阅）在最近 3 天里推送不少于 15 条，而且这些推送你一条都没回（`replied_at` 全为空） | 问你一次：「『<名字>』3 天推了 N 条，你都没回。还要继续推吗？」选项：继续（30 天内不再问）、暂停；这个提问是一条 `cost_holds`（D8），进「需要你处理」 |
| 暂停 | 提问之后又过了 3 天，你没回答，期间也没回过它的任何推送 | 自动暂停：`enabled = false`、`pause_reason = unanswered`、`paused_at`；告诉你一次，「需要你处理」的「定时任务」一类里显示它和「恢复」按钮 |
| 恢复 | 你在控制台、私聊或 CLI 点「恢复」 | `enabled = true`，清掉暂停原因，30 天内不再问 |

- **「回过」的口径：** 用 P0.1 的 `replied_at`：推送发出后 30 分钟内你在同一个会话里说过话。这比「看过」严格，所以先问一次再暂停，不直接停。
- **只统计推给你本人的：** 推到群里的推送不算（群里的回复不代表你）。
- **测试：** 暂停和恢复各有测试；被暂停的定时任务出现在「需要你处理」里有测试（产品设计 P4.7 的验收）。

## 9. 用量窗口

准入顺序：先检查金额范围链（②），保留其 `ASK` / `DENY`；金额放行后再执行本节的 `HOLD`（⑤）。操作者管家回合的全局金额例外不豁免被拒窗口。窗口到期后重新准入，仍按此顺序检查。

依赖 #1502 和 #1514。两者没合入或没打开时，这一节不起作用。

| 信号 | 判定 | 动作 |
|---|---|---|
| 某个账号的某个窗口 `status = rejected`，且有未来的 `resets_at` | 这个账号被拒到该时刻 | 用这个账号的 Profile 的运行：后台角色和定时任务 `HOLD` 到 `resets_at`；你发起的事也 `HOLD`，任务页和管家回复说明「等用量窗口重置（约 HH:MM）」，你可以在任务页换一个 Profile，重新准入后继续 |
| `utilization >= 0.95`，且有未来的 `resets_at` | 快到了；列值是 0–1，95% 对应 `0.95` | 只暂缓后台角色和定时任务到 `resets_at`，你发起的事照常 |
| 运行失败，`failure_class = quota`（`failure_cause = usage_limit` 或 `rate_limit`） | 重置时间取可选的 `metadata.failure.resets_at`；`rate_limit` 不保证有时间 | 有未来重置时间按 `rejected` 处理；缺失时按下面的有限冷却处理。失败步骤不进入普通失败重试 |

- **未知重置时间：** `resets_at = null` 的拒绝或高利用率信号不能永久 `HOLD`。没有可用重置时间时，从信号的 `observed_at`（失败记录用结束时间）起最多冷却 5 分钟，显示「重置时间未知」并通知你；同一信号不会因每次准入或进程重启而延长冷却。已过期的重置时间不再暂缓。
- **no-retry 由守卫负责：** #1514 只分类和记录，不改变重试。守卫在 `enforce` 下接线失败处理，阻止已知 `quota` 失败走普通失败重试；冷却到期不自动重试已经失败的步骤。未开始、只因准入被暂缓的运行，到期后按原顺序重新准入；失败步骤由操作者明确继续后重新准入。`observe` 只记录本来会怎样，保留原失败处理。
- **不换账号：** 守卫不会自动换到另一个账号的 Profile（不做多账号轮换）。换不换由你决定；切换后按第 7 节重新准入。
- **窗口重置或冷却到期以后：** 过期信号不再暂缓，重新检查最新窗口和完整预算范围链，不能直接复用之前的准入结果。

## 10. 告警

| 事件 | 发给谁 | 频率 |
|---|---|---|
| 某一层到 80% | 你的私聊（或控制台的告警会话，沿用 Advisor 告警的目标） | 每层每天一次 |
| 某一层到上限，触发了 `SKIP`、`STOP_ROLE`、`FALLBACK`、`HOLD` | 同上 | 每层每天一次；同一天里后续的同类事件只计数，第二天的消息里汇总 |

## 11. 操作者的控制

- **v1 操作**（`operator_only`，独立于 `chat_settings` 视图和 `chat_settings.update`；不向 agent 开放）：
  - `cost_guard.get`、`cost_guard.update`：模式、各层上限、各层动作、没人回的推送规则；提高上限、改成更宽松的动作要确认。
  - `cost_holds.list`、`cost_holds.decide`：列出等你决定的事，回答 `continue`（带新的上限）或 `stop`。
  - 定时任务的「恢复」沿用 `schedule_admin.update`，恢复时清掉暂停原因。
- **动作级别：** `cost_guard.get/update`、`cost_holds.list/decide` 均显式声明 `Operation.level = ActionLevel.INSIDE`：只读写 Looper 自身的设置和等待状态。操作描述以不超过 120 字符的 summary 开头；这里不新增 agent 工具，后续若新增必须在 `TOOL_LEVELS` 单独声明级别和理由。
- **Settings 的「花费」页：** 上面这些的表单；每一层显示今天已花、已预留、上限（两种钱分开）；`observe` 模式下显示「本来会拦下的」最近 20 条。
- **私聊：** 「需要你处理」的提问可以直接回「继续」「停」，和账本的确认一样只认你本人（说话人是操作者，1.1 的判断）。
- **首页：** 「今天的花费」旁边加离全局上限还有多少；有等你决定的事时显示数量。

## 12. 和其他上限的关系

- **管家的单轮上限（#1506、#1543）：** 单轮上限照旧，是事中的软限。守卫在每个回合开始前准入一次，预留就是单轮上限。全局一天到上限时：
  - 你本人的回合（控制台、你的私聊）**照常放行**，回复的末尾由代码加一行「今天的花费已经到了上限（$X），后台任务已暂停」，每天只加一次；
  - 别人的回合按全局的动作处理；管家收尾回合被拒时退回代码通知，Planner 收尾回合被拒时继续原结束路径。两种收尾都不提供 `FALLBACK`，不能自动切换 Profile；操作者明确切换 Profile 后也必须按第 7 节重新准入。
- **会话预算的压缩、换新：** 压缩和交接摘要本身也是运行，按管家的回合准入；被拒时跳过这次维护，下一轮再检查，不影响回复。
- **对外审查的花费：** 审查分类器是后台角色 `outbound_check`，有自己的每日上限。到上限时守卫拒绝运行，动作被拦下（失败即拦截），并写一条 `cost_holds`：「审查的预算用完了，要提高上限吗？」。`cost_holds` 写失败仍拦截，不得把创建提问失败解释为放行动作。D13 的 fail-open 只允许在守卫计数/判定出错时继续运行分类器，绝不直接允许对外动作：审查路径的异常（包括预留失败）仍由 `review()` 的异常即拦截路径处理，分类器必须成功给出允许结论且审计写成功，动作才能发出。`main` 的 `outbound.review()` 捕获分类异常为 `BLOCK`，`_record()` 在审计写失败时也返回 `BLOCK`；接入守卫后保留这两道边界。
- **advisor：** 请教是后台角色 `advisor` 的运行；`advisor_daily_alert_usd` 保留为告警，守卫打开并给 advisor 设了每日上限时，以守卫为准。
- **任务上限：** 现有的 `_within_budget` 保留；守卫在同一位置把在跑运行的预留加进去，所以两者判的是同一个数。任务的「继续」沿用现有的 `tasks.continue`。

## 14. 关闭时不变、模型可见性

- **`mode = off`：** 模式由正常的启动/配置刷新路径加载并缓存；`admit` 只看已加载配置后直接返回 `ADMIT`，不为判断开关再查数据库，也不做任何读写 I/O。运行记录不写 `reservation`；告警、提问都不发；`skipped_budget` 和调度器日界线保持现状。测试：配置加载后，`admit` 的读写调用数为 0；同一任务、定时任务、processor 的命令行、提示词、工具列表及模型可见工具结果与 `main` 一致，没有守卫新增的数据库行或字段。
- **`mode = observe`：** 只多写内部 `reservation` 和「本来会怎样」的记录（日志和仅操作者可读的 Settings 页最近 20 条），不拦、不问、不发消息，也不增加事中软限或改变重试。命令行、提示词、工具列表及模型可见工具结果保持一致；`metadata.reservation`、预估来源、模拟拒绝等守卫内部字段不得进入 agent 的工具返回或运行记录的模型可见投影，不能只验证工具 schema 没变。
- **模型可见：** 守卫不改提示词、契约、工具描述。被拒的派发对 Planner 是一个已有形式的状态（像等关卡），不是新的文字；管家回复末尾的那一行由代码加在回复后面，不进模型的上下文。这一点在 ② 号 PR 里用测试确认；如果实现时发现 Planner 需要看到一句新的说明，那就是模型可见的改动，要跑真实评测。

## 16. 验收（出口标准）

1. `off`：配置加载后 `admit` 的读写调用数为 0；命令行、提示词、工具列表及模型可见工具结果与 `main` 一致，没有守卫新增的数据库行或字段。
2. `observe`：并行派出 3 个 Worker、每个单次上限 $1、任务上限 $2 时，记录显示第 3 个「本来会被拦下」；运行结束后预留换成实际花费，计数和 `task_costs` 一致（两种钱分开）。重启先重算历史 P95，无样本才用下限并注明来源；模拟预留及观察记录不进入模型可见工具结果，不改变事中软限或重试。
3. `enforce`：同样的任务，第 3 个 Worker 不派出，任务进入 `awaiting_budget`，「需要你处理」里出现一条；回「继续」并提高上限后派出；回「停」或 24 小时不回，任务按 `stopped` 结束。
4. 全局一天到上限：你本人的管家回合照常回复，末尾多一行（一天一次）；别人的回合和收尾回合按设置处理；后台角色停到第二天。管家和 Planner 收尾均不能 `FALLBACK`；手动切换或后台备用 Profile 均重新计算币种、预留并检查完整范围链。服务器时区与 `user.timezone` 不同时，守卫和调度器（含订阅）仍复用 `Scheduler.day_start` 的日界线，覆盖跨午夜，`off` 保持原行为。
5. 后台角色到每日上限：线索核对按它的失败语义放行；审查分类器被拒时对外动作被拦，并出现「审查预算用完」的提问。守卫判定异常可继续分类，但审查路径异常、预留失败、`cost_holds` 或审计写失败均拦截动作，不能出现分类器未运行却发出动作。80% 和到上限各告警一次，同一天不重复。
6. 没人回的推送：合成 3 天 15 条没人回的推送，问一次；再过 3 天没回答，暂停，`pause_reason = unanswered`，出现在「需要你处理」里；恢复后 30 天内不再问。推到群里的不计入。
7. 用量窗口：`utilization = 0.95` 命中后台暂缓，低于阈值不命中；`rejected` 暂缓到有效的 `resets_at`。无重置时间的窗口/`rate_limit` 只有限冷却，重启不延长；过期信号不继续拦。验证从 `metadata.failure.resets_at` 取时间，且守卫实际阻断 `quota` 失败的普通重试；到期重新准入不会自动重试已失败步骤，`observe` 保持原行为。

# RFC：卡片按钮 v0（高风险确认和关卡一键作答）

- **状态：** 实现中（本 PR）。默认关闭，开关是系统设置 `cards.actions.enabled`。
- **需求：** 需要你确认的操作，现在都靠打字：高风险动作回「确认」，关卡用 `/gate N <回答>` 或回复消息。助理层第 2 期要把它们变成卡片上的按钮：点一下就办完，重放同一次点击不会办两次，别人点无效。高风险确认现在只在内存里，重启就丢；借这次落库，打字确认和按钮确认走同一条记录。
- **范围：** 关卡回复、高风险确认、意图的「建 / 驳回」和账本决定的确认，共用本文的表和回调。渠道是飞书自建应用（bot token 的长连接，`lark_bot`）和 Telegram（内联按钮）。lark-cli 渠道和网页聊天不发按钮，照旧打字。
- **相关：** [Manager 平台工具 RFC](manager-platform-tools-v0.zh-CN.md)（风险分级、确认）、[用户关卡 RFC](user-gate-v0.zh-CN.md)、[飞书 bot token 渠道 RFC](lark-bot-token-channel-v0.zh-CN.md)、[Agent 系统架构](../agent-system.md)。

## 1. 前提：卡片回调走同一条长连接

飞书的新版卡片回调（`card.action.trigger`）在开发者后台「事件与回调 → 回调配置」里打开后，和消息事件走同一条长连接，不需要另配 HTTP 地址。帧的类型头是 `event`，不是旧的 `card`；用哪个事件看载荷里的 `header.event_type`。这一点对照了官方 Go SDK（v3.7.2）的 `ws/client.go`：`MessageTypeEvent` 交给事件分发器处理，卡片回调的返回值（`CardActionTriggerResponse`：`toast`、`card`）放进确认帧的 `data` 字段（JSON 再 base64，`{"code":200,"headers":null,"data":"…"}`）；`MessageTypeCard` 直接返回，不回确认。

所以长连接的做法是：

- 消息事件照旧：先回 `{"code":200}`，再处理。
- 卡片回调（`event` 帧，`event_type` 是 `card.action.trigger`）先交给渠道处理，拿到答复后再回确认，答复放进 `data`；平台等 3 秒，Looper 自己限 2.8 秒，超时就回普通确认。同一个 `event_id` 只处理一次（平台重投时回普通确认）。按钮的值里没有 `looper` 键的（这个应用的别的发送方做的卡片），照旧回普通确认后忽略。开关关闭时渠道不答复，回的是和以前一样的普通确认（`{"code":200}`）。
- 旧式的 `card` 帧照旧回 `{"code":200}` 后忽略，每条连接只记一行 INFO 日志。

本 PR 没有真实测试会话，按钮在本地假的长连接服务器上验证（`tests/lark_platform_fake.py` 的 `push_card_action`）。

## 2. 数据：`card_actions`

一张卡片一行（迁移 `card_actions`，新表，在线安全）：

| 列 | 说明 |
|---|---|
| `token` | 不透明 token，主键。按钮里只带 `<token>:<choice>`，`choice` 是按钮自己的键（`confirm`、`cancel`、选项编号、`end`），不带任何参数 |
| `kind` | `confirmation`（Manager 的高风险确认）、`gate`（用户关卡）、`intent`（意图处理）、`ledger`（转述决定确认） |
| `subject` | 绑定的对象：确认的 `confirmation_id`，关卡的 step id |
| `digest` | 绑定参数的摘要（sha256）：确认是工具名、参数和确认时记下的状态；关卡是题目和还开着的问题及其选项。参数变了，旧按钮失效 |
| `payload` | 办这件事要用的东西：卡片本身（文字和按钮）、关卡的任务和选项答案；确认还有发起的回合和调用参数（见下） |
| `allowed` | 允许点的人（飞书 open_id、Telegram 用户 id）。确认是发起的人；关卡是私聊的用户或群里的发起人；没有发起人的 Telegram 群为空，即这个 bot 在这个群准入的人 |
| `chat`、`message_id` | 卡片所在的会话（确认：发起消息所在的会话；关卡：关卡的目标，飞书私聊先是用户的 open_id），和它发出后成为的那条渠道消息。渠道发送后记下消息 id 和发送答复里的会话（飞书发给 open_id 的卡片这时换成私聊的 chat id），只写一次 |
| `expires_at` | 过期时间：确认 10 分钟（和打字确认一样），关卡 7 天 |
| `handled_at`、`handled_by`、`handled_via`、`choice`、`outcome` | 处理时间、谁、怎么处理的（`button`、`typed`、`lapsed`）、点了哪个、结果（`running`、`ok`、`error`、`cancelled`、`lapsed`、`answered`、`stale`） |

一行只处理一次：`claim` 在一个事务里先锁住这一行（单独一条 `SELECT … FOR UPDATE`），再用 `UPDATE … WHERE handled_at IS NULL AND expires_at > clock_timestamp()` 处理它。两次点击、或者一次点击和一次打字确认，只有一个能成功；一个等锁等到过期的 `claim` 按拿到锁之后的时钟判断，不会在过期后成功。

参数里有像密钥的字段（`manager_actions.masked` 会遮住的）时，不把参数落库；这样的确认重启后不恢复，直接标为 `lapsed`，用户重新让管家问一次。

## 3. 点击的处理

渠道收到点击后调用 `card_actions.respond`，由代码答复，不经过模型：

1. 按钮的值解析不出来、开关关了（「按钮已关闭，请打字回复」）、找不到这一行或它不是这个 bot 发的，都不执行。
2. 点击要来自卡片所在的地方：同一个会话，记下了消息 id 的还要是同一条消息（转发出去的副本不算）。会话和消息一起比：Telegram 的消息 id 只在一个会话内唯一；飞书的消息 id 本身就是消息的唯一标识，也一样比会话。飞书发给用户 open_id 的卡片，如果发送后没来得及记下私聊的 chat id（服务刚发完就停了），点击要来自平台确认为私聊（`chat_mode` 为 `p2p`）的会话，且点的人就是这个用户，群里点无效。不是的回「这张卡片只能在发出它的会话里操作」，不 `claim`，这一行不变。
3. 点的人先要过渠道的准入，规则和这个会话里的消息相同（飞书：bot 的发送者名单、这个会话绑定的额外发送者，或绑定为 `sender_policy` `chat` 的群里的人；私聊里只有对方能点），再要在 `allowed` 里；不是的回「只有发起人能确认」（关卡回「只有发起人能回答」）。
4. 已处理或已过期的回「已处理」；参数变了的回「已失效，请看最新的消息」。
5. 第 1–4 步的核对（开关、卡片、会话和消息、平台的会话类型查询、点击人）从渠道收到点击起必须在 1.5 秒内做完（`AUTHORIZE_SECONDS`）；超时或出错就取消核对，回「没能及时核对这次点击，没有处理，请再点一次」，不 `claim`，之后核对自己结束了也不会再执行。只有通过核对的点击，它的动作才可能在答复之后继续执行。
6. 否则 `claim` 这一行，按 `kind` 交给处理者。答复（提示和卡片现在的样子）在 2.5 秒内给出；动作 2.5 秒内办完的，卡片直接显示结果，否则先显示「⏳ 已确认，正在执行…」，办完后再更新一次卡片（飞书 `PATCH /open-apis/im/v1/messages/{id}`，卡片是共享卡片；Telegram `edit_message_text`）。

**关卡**（`card_actions.press_gate`）：选项按钮把「问题：选项」作为用户的消息交给关卡，带上 `agenda_item` 和 `option`；「按现在的结论结束」等同 `/gate N end`。都走 `gate_service.post_message`，`via` 是 `button:<渠道>`，回执和 `/gate` 一样由代码写。

**确认**（`ManagerOps.press`）：只在这次确认还在等（内存里这个会话的待确认就是它，摘要一致）时有效。「确认」在一个和发起回合相同的回合里执行这次调用（同样的会话、发起人、原消息），和打字确认走同一段代码（`_run_confirmed`：重新检查权限、执行、写 `manager_actions`），工具在回合里加的内容（比如新任务的配置）显示在卡片上。「取消」直接作废。

## 4. 高风险确认落库

开关打开时，每个需要确认的调用都写一行 `card_actions`（网页聊天和 lark-cli 也写，只是不发按钮）：

- **打字确认**：`looper_confirm` 在执行前也要 `claim` 这一行；已经被按钮处理过的，返回 `conflict`，告诉模型这次确认已经用卡片答复过、不会再执行。`claim` 成功之后才把它从内存里拿掉：同时按下的按钮仍然看到它在等，于是输在 `claim` 上，而不会把它当成已作废（那样两边都不执行）。
- **作废**：内存里的待确认被丢掉时（下一条消息没确认、被新的确认替换、停止、`/new`、超过 50 个会话被挤掉），这一行标为 `lapsed`，之后点按钮回「已处理」。
- **重启**：Manager 启动时（`ManagerFleet.load` 和启用一个场景 Manager 时）读回这个 Manager 还在等、没过期、保存了参数的确认，放回内存。用户的下一条消息照旧带着 `[Looper]` 提示，打字确认和按钮都能用。

内存仍然是判断「这次确认是否还在等」的依据（`begin_turn` 等方法是同步的）；数据库是两条路径共同认的处理记录和重启后的来源。

## 5. 卡片怎么发

- **确认**：Manager 回复里的确认块（「需要你确认：…回复「确认」就执行；回复别的就不执行。」）原样保留在回复里；渠道有按钮时，回复的 `metadata.cards` 带上这张卡片，渠道把这段文字从回复里拿掉，回复发完后把它作为一条带「确认 / 取消」的卡片发到同一个地方（群里回复在那条消息下面）。卡片发不出去时，把这段文字作为普通消息补发，用户仍然可以打字确认。群聊回复被线索检查替换时，回复里没有这段文字，也就不发卡片。
- **关卡**：`GateCourier` 发需要作答的消息（打开、更新、提醒、任务继续）时，渠道有按钮就发卡片：原来的文字，加上还开着的问题的选项（最多 3 个问题、每个 5 个选项），再加「按现在的结论结束」。卡片的消息 id 照旧记进 `task_user_gate_posts`，回复卡片也算回复这个关卡。
- 飞书卡片的发送、回复和更新都经过渠道里的一个对象（`lark.CardWrites`）。出站 gateway（另一个 PR，未合入）合入后，把 gateway 和它的开关传给这个对象（一行），卡片写就和文字写一样走 gateway 的限速、熔断和重试；gateway 的持久化 outbox 不含卡片。
- 飞书用卡片 JSON 2.0（`update_multi: true`，按钮的 `behaviors` 是 `callback`，值是 `{"looper": "<token>:<choice>"}`），群卡片 @ 发起人；Telegram 用一条纯文本消息加内联键盘（`callback_data` 是 `<token>:<choice>`，不超过 64 字节）。

## 6. 开关关闭时

`cards.actions.enabled` 没有这一行或不是 `true`：不写 `card_actions`，回复不带 `cards`，关卡消息照旧发文字，确认只在内存里；飞书长连接对卡片点击回普通确认，Telegram 的点击不答复，都和以前一样（帧级测试比较了确认帧）。提示词、工具列表、命令行不变；开关打开时模型看到的确认提示、工具返回和下一轮的 `[Looper]` 提示也和关闭时逐字节相同（测试比较了两种情况）。唯一新增的模型可见文字是上面打字确认撞上已用按钮处理过的确认时的 `conflict` 说明，只在开关打开且按钮先被点的情况下出现。

Dashboard 上还没有按钮开关，`cards.actions.enabled` 仍通过系统设置配置；账本自己的 `ledger.enabled` 已有 Settings → Chat 入口。

## 7. 风险与监控

- **按钮执行时管家不知道。** 按钮执行后，管家的会话里最后看到的仍是「需要确认」；用户问起时，管家要像看待 Dashboard 上做的改动一样去查状态。之后可以在下一轮的提示里补一句（模型可见，需要评测）。
- **点击方能控制的文字不进模型上下文。** 点击事件里只用平台给的 id（飞书 open_id、Telegram 用户 id）和按钮值；按钮值只用来查 `card_actions`，从不显示给模型。关卡收到的是 Planner 自己写的问题和选项（`question：option`、`agenda_item`、`option`），群里的 `author` 是点击者的 id 而不是显示名，`via` 是代码写的 `button:<渠道>`；打字确认撞上按钮时的 `conflict` 说明只含代码生成的确认 id。点击者的显示名不读取、不保存。
- **作废写库是异步的。** 作废先改内存再写库；写库前进程退出，重启可能把一个已作废的确认读回来。它仍要用户的下一条消息确认（或点按钮）才会执行。
- **表只增不减。** 一张卡片一行，量很小；清理以后再做。
- **日志：** 被拒的点击记 INFO（只有渠道和发送者 id），点击处理失败、卡片发送失败记 WARNING；旧式卡片帧每条连接一行 INFO。
- **验收：** 四类操作都能一键完成；重放同一次点击不会执行两次；别人点无效；重启后确认还在。

## 8. 意图和账本的后续接入

- 意图推送保留原文字，加「建 / 驳回」；按钮和「建 I-xxxx / 驳回 I-xxxx」共用业务服务。意图行锁、卡片 claim 和状态转换在一个事务内；失败回滚卡片 claim，缺项目或目录仍可走原有的编号回复或意图页。成功的打字操作也结算同一批卡片。卡片摘要绑定标题、摘要、来源和项目配置，内容变化的旧卡失效。意图的终态编辑保留卡片类型并移除按钮。
- 账本里本人新增的决定已经确认，不再问一次；本人在私聊通过 `looper_ledger_update` 的 get/list 查看尚未确认的转述决定时，代码附上「确认」卡片。群聊、其他发送者不发这种卡片。按钮重新核对当前 operator 身份和账本开关，再走 `db.ledger.apply`；账本行锁保护摘要检查、确认事件和卡片结算。CLI 和工具里的打字确认结算同一记录，修改或撤销使旧卡失效。
- 两类按钮都复用会话/消息绑定，以及从收到点击起 1.5 秒的授权期限；各自当前身份和功能状态的核对也在期限内。没有新增工具、设置或 v1 操作。开关关闭时不写卡片记录，原消息、调用参数、模型工具和启动命令保持不变。
- Needs-you 的待操作确认由 `card_actions.pending_confirmations` 读取：开关打开时读持久化的 confirmation，内存只补未能持久化的确认；关闭时沿用内存。意图和账本仍列在自己的分类，不重复计入操作确认。

## 9. 不在本 PR

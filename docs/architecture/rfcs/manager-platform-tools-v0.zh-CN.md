## 1. 背景与目标

维护者希望**能在界面上做的事，尽量都能通过和管家聊天完成**：开始、停止任务，新增、修改 Agent Profile，聊天过程中调整任务的内容，等等。

现状：

- 管家只有两个动作，建任务（`task_request`）和开始任务（`task_start`）。管家在回复里写一段 JSON，代码解析后执行（#88）。
- 平台的 HTTP 接口约 65 个，管家都碰不到。
- 管家要做别的事，只能自己在 shell 里 curl 接口。没有类型，没有确认，也没有留痕。

**目标：**

- 平台和管家之间有一份明确的交互协议：有哪些操作、各自的输入输出、风险分档、确认规则、身份和留痕；
- 管家通过 MCP 工具调用这些操作。三种运行时（Claude Code、Codex、OMP）都能用；
- 高影响操作由代码强制确认，不靠提示词约束；
- 现有的 JSON 动作迁到同一套机制里，最后只剩一种方式。

**不做：**

- 密钥不经过聊天：管家可以登记 LLM 提供方，但 API key 只在界面里填；
- 文件上传类操作（上传 skill 包、导入配置文件）留在界面；
- 执行者、评审者不拿平台工具。规划者只拿三个限定在本任务的工具（两个选 Agent Profile，D9；一个改本任务的并发上限，D10），按补充说明或需求修改重新规划仍走它的回复约定（第 8.2 节）。

## 2. 概念

| 概念 | 定义 |
|---|---|
| 操作 | 平台能做的一件事，例如「停止任务」。有名称、输入输出结构、错误码和风险档 |
| 操作目录 | 所有操作的唯一定义。管家工具、管家专用接口和文档都从它生成 |
| 工具 | 管家看到的 MCP 工具，一个工具可以覆盖同一资源上的几个操作 |
| 风险档 | `read` 只读；`write` 普通修改；`high` 高影响，需要用户确认 |
| 待确认 | 高影响操作的第一步：平台只登记、不执行，把影响说明直接发给用户 |
| 补充说明 | 任务开始后用户追加的话：经管家转达的，以及在聊天页直接发给规划者的。类型化存储（任务日志的 `supplement` 条目），只追加不修改；列在需求后面，规划者、之后的每个执行者和评审者都看得到，任务页显示为「补充说明」 |
| 需求版本 | 任务的需求原文可以随时修改（未开始和运行中都可以）；每次修改存一个新版本，旧文本保留，任务页显示当前文本和历史 |
| 任务变更 | 一条补充说明或一次需求修改。每一条都必定以一轮规划者回合送达，规划者正忙时排到下一轮，重启后也不丢（第 8.1 节） |
| 可选 Agent Profile | 项目设置里的一个列表：规划者只能从中为本任务的执行者、评审者选 Agent Profile。默认为空，即规划者不能换 |

## 3. 决策

| # | 决策 | 理由 |
|---|---|---|
| **D1** | **用 MCP 工具**，不扩展 JSON 动作，也不让管家 curl | 维护者选定。MCP 的参数有结构并在调用时校验，一轮里能连续调用、看结果再决定下一步，三种运行时都原生支持 |
| **D2** | **分档确认**：只读直接执行；普通修改在用户提出后执行；高影响操作两步确认 | 维护者选定。开始、停止这类日常操作不用多问一句；删除、取消、改共用默认、提高花费上限这类，代码先列出影响面 |
| **D3** | **任务随时可以编辑调整，计划由规划者来改**：补充说明（管家转达、聊天页直接发给规划者）和需求修改（管家、任务页）都是任务变更，每一条都以一轮回合送达规划者，由它决定不动、加步骤、转给运行中的执行者，还是重新规划（第 8 节） | 维护者选定。维护者的目标：「让 task 是可以编辑调整，并且会让 planner 感知并决定是否要重新编排规划」。计划只有一个人在改，不会冲突 |
| **D4** | **排在定时任务 S2 之后、S3 之前**；S3 的管家入口并入 T3 | 维护者选定。S3 不必先做一套 JSON 动作再迁移 |
| D5 | **MCP 进程只做转发**：校验、分档、确认、执行、留痕都在 `looper serve` 里，通过一个只给管家用、要带令牌的接口完成 | MCP 进程由管家的运行时拉起，每种运行时管理它的方式不同（Codex 每轮重新拉起）。逻辑放在平台里，只有一处事实 |
| D6 | **不另做 skill**。工具的用法写进管家提示词里由代码维护的一节，和现有的回复约定放在一起 | Looper 关掉了 Codex 的原生 skill 列表。写在提示词里，三种运行时都看得到 |
| D7 | **代码生成的关键信息由平台直接发到聊天**，包括任务配置块、确认说明，不经模型转述 | 用户看到的是代码保证的原文；模型只需说明「见上」 |
| D8 | **原生 tool 不单做**。等 SDK 运行时（M9d）上线时，从同一份操作目录生成 | 避免两套定义 |
| **D9** | **规划者用 MCP 工具选 Agent Profile**：一个只服务本任务规划者的 MCP 条目，按任务发令牌；工具可查允许的 Profile 和价格，可为本任务剩下的步骤或指定的步骤设定、清除某个角色的 Profile（第 8.3 节） | 维护者选定（2026-10-15，没有采用 v1 初稿推荐的回复约定方案）。和管家用同一套 MCP 服务和操作目录 |
| **D10** | **规划者只在本任务内行事**：只能从项目允许的列表里为本任务的执行者、评审者选 Profile，不能选规划者自己的 Profile，不能改角色和共用默认的设置；可以改本任务的 Worker、Reviewer 并发上限，直接生效、不需确认，每次都记入任务日志（任务页可见），并经任务的通知渠道告诉用户；令牌只认本任务 | 维护者选定（2026-10-15；改并发一项 2026-10-16 修订；2026-10-17 再修订：并发只按任务算，项目没有上限，改项目上限的工具删除）。项目的可选列表是维护者事先的授权，默认为空；改并发和管家的 `looper_concurrency` 走同一条代码，只是范围检查和确认不同 |

## 4. 架构

```
用户（网页 / 飞书 / Telegram）
   │ 聊天
   ▼
looper serve ──── 管家专用接口 POST /api/agent/v1/ops/<操作>（需令牌）
   │ 交给管家                   ▲
   ▼                            │ 本机 HTTP
管家进程（Claude Code / Codex / OMP）
   │ stdin / stdout，JSON-RPC
   ▼
looper mcp-server（子进程，薄客户端）
```

- **操作目录**：放在 `looper/agents/ops/`，每个操作是「名称、说明、输入结构（JSON Schema）、风险档、处理函数」。处理函数调用现有的服务代码，和界面接口共用校验。
- **MCP 服务**：`looper mcp-server` 子命令，走标准输入输出。自己实现 MCP 的 `initialize`、`tools/list`、`tools/call`，不加依赖。工具列表从操作目录生成，每次调用转发给管家专用接口。
- **注入**：内置的 MCP 条目只装给管家角色，始终启用，不能卸载；沿用现有 MCP 的注入路径（Claude Code `--mcp-config`，Codex 的 `config.toml`，OMP 的 `mcpServers`）。平台地址和令牌经这个条目的环境变量传入。

## 5. 交互流程

**启动**：管家进程拉起 `looper mcp-server`，发 `initialize` 交换版本，再发 `tools/list` 取得工具列表，放进模型的上下文。

**普通调用**（「把斗地主任务停掉」）：

1. 模型调用 `looper_tasks`，参数是 `{"action": "list", "query": "斗地主"}`，拿到任务编号；
2. 同一轮里调用 `looper_task_control`，参数是 `{"task_id": "…", "action": "stop"}`；
3. 平台确认这是 `write` 档、调用发生在用户的这一轮里，于是执行，记一条留痕，返回结果；
4. 模型回复用户。

**高影响调用**（「把 doudizhu 项目删了」）：

1. 模型调用 `looper_projects`，参数是 `{"action": "delete", …}`；
2. 平台不执行，登记一条待确认，返回 `{"status": "needs_confirmation", "confirmation_id": "c-…", "expires_in_seconds": 600}`，同时把代码生成的影响说明直接发到这个聊天；
3. 用户回复。平台把消息交给管家时附一句提示，说明上一轮有待确认的操作；
4. 模型调用 `looper_confirm`，参数是 `{"confirmation_id": "c-…"}`。平台核对三件事：同一个聊天、正是用户紧接着的下一条消息、没有过期。三条都满足才执行，否则作废并返回原因。

## 6. 协议

**返回结构**：

| 字段 | 含义 |
|---|---|
| `status` | `ok`、`needs_confirmation` 或 `error` |
| `result` | `ok` 时的结果，结构由操作定义 |
| `confirmation_id`、`expires_in_seconds` | `needs_confirmation` 时给出 |
| `error.code` | `not_found`、`invalid`、`needs_user_turn`、`forbidden`、`conflict`、`expired` |
| `error.message` | 给模型看的原因，写明怎么改 |

**确认规则**：

- 每个聊天同时只有一条待确认，新的一条取代旧的；
- 有效期 10 分钟；
- 只认用户紧接着的下一条消息之后的那一轮；
- 确认后按登记时的参数执行，不接受改参数。

**身份与范围**：

- `looper serve` 每次启动生成一个随机令牌，只交给管家的 MCP 条目；
- 平台知道管家当前正在处理哪个聊天、哪个渠道的哪条消息，每次调用都挂到这一轮上；
- 管家自己发起的一轮（后台工作结束时，#26）只能调用 `read` 档；
- 规划者范围的令牌（T2）按任务发、只认本任务的三个工具（两个 Profile 工具和 `looper_task_concurrency`），见第 8.3 节。

**留痕**：新表 `manager_actions` 记录时间、聊天、渠道、操作、参数（密钥打码）、风险档、结果、确认编号。任务页、设置页上，管家做过的改动标「由管家操作」。

## 7. 工具清单（约 15 个，按资源合并）

| 工具 | 操作 | 风险档 | 期 |
|---|---|---|---|
| `looper_overview` | 总览：进行中的任务、正在跑的 agent、今天的花费 | read | T1 |
| `looper_tasks` | 列出、查看（含计划、步骤、花费）、搜索 | read | T1 |
| `looper_task_create` | 建任务（未开始），返回配置块（平台直接发到聊天）；项目不存在时走确认 | write；新项目 high | T1 |
| `looper_task_control` | 开始、停止、恢复、重启；取消 | write；取消 high | T1 |
| `looper_task_instruct` | 给运行中的任务加补充说明：存为 `supplement` 条目，作为任务变更送达规划者（D3，第 8.1 节）；未开始的任务没有规划者，请用 `looper_task_update` 改需求 | write | T1 |
| `looper_task_update` | 修改需求（任何未结束的任务；存新版本，运行中的作为任务变更送达规划者，第 8.1 节）；未开始的任务还可以改目录；按角色的 Agent Profile（运行中的：执行者、评审者下一步开始生效，规划者按会话切换规则，第 8.4 节） | write | T1 |
| `looper_confirm` | 确认执行一条待确认的操作 | — | T1 |
| `looper_projects` | 列出、查看、新建、改名和背景；删除 | write；删除 high | T2 |
| `looper_agent_profiles` | 列出、新建、修改；删除 | write；删除 high | T2 |
| `looper_providers` | 列出、登记（不含密钥，提醒去界面填） | write | T2 |
| `looper_settings` | 查看和修改角色层、项目层的设置，含项目的可选 Agent Profile 列表；改共用默认 | write；共用默认 high | T2 |
| `looper_catalog` | 列出技能和 MCP，按项目、角色安装或卸载 | write | T2 |
| `looper_costs` | 按任务、项目、时间段查花费 | read | T2 |
| `looper_schedules` | 列出、查看（含最近的运行）、启用、停用、删除（looper #160）；新建（停用）、修改、立即运行（第 7.1 节） | 列出、查看 read；write；启用、立即运行、删除、提高或取消花费上限的修改 high | T3 |
| `looper_config_export` | 把配置导出成文件，放在 Looper 自己的目录里，不含密钥（第 7.1 节） | read | T3 |

提高花费上限（项目的单任务上限、定时任务的每日上限）一律算 high。T2 里还有：`looper_settings` 改并发上限（Worker、Reviewer 角色层，即每个任务的默认值；2026-10-17 起项目和项目里的角色没有并发上限）、提高或取消每次运行的花费上限（按各层解析后、该层任一角色的运行会拿到更高的上限或没有上限）算 high。一个工具里只列出、查看的动作（`list`、`get`、`view`）算 read，自主轮里也能调用。任何工具都不接受名字像密钥的参数（key、token、secret、password、credential），返回 `forbidden` 并说明去界面填。

### 7.1 T3：定时任务的新建、修改、立即运行和配置导出

T3 的剩余部分（looper #160 已做列出、查看、启用、停用、删除）：管家能新建、修改定时任务，能立即运行一次；有一个导出配置的工具；定时任务随项目进入配置文件，导入后一律停用。

**`looper_schedules` 新增三个动作**，都调用界面接口用的代码（`agents.schedules` 的 `create_schedule`、`update_schedule`、`run_now`），校验和拒绝的提示与界面相同：

| 动作 | 参数 | 做什么 | 风险档 |
|---|---|---|---|
| `create` | `project`（已有项目的名字）、`fields` | 新建定时任务，**一律停用**（`created_via` 为 `manager`）。Looper 在回复后附上代码写的配置块，最后问「要启用吗」 | write |
| `update` | `schedule`（id 或名字，同 #160）、`fields` | 只改给出的字段，`null` 清除可清除的字段；`fields.profiles`、`fields.task_limits` 整份替换 | write；提高或取消每次运行、每日花费上限时为 high |
| `run` | `schedule` | 等于界面的 Run now：照样经过重叠检查，`next_fire_at` 不变，停用的也能跑；答复给出这次运行的状态（运行中、前置检查中、排队、跳过及原因） | write |

`fields` 是一个对象，字段与 `POST /api/projects/:id/schedules` 相同：`name`、`cron`、`timezone`、`requirement`、`work_dir`、`overlap`、`max_parallel_runs`、`catch_up`、`run_timeout_seconds`、`run_budget_usd`、`gate_command`、`gate_timeout_seconds`、`daily_budget_usd`、`notify`、`notify_target`，外加 `profiles`（按角色的 Agent Profile，id 或名字，即接口的 `profile_overrides`）和 `task_limits`（#173：每次运行建出的任务自己的 Worker、Reviewer 上限）。放进一个对象而不是摊在顶层，是为了不和 `schedule`、`project`、`enabled`（列表的筛选）混淆，也让工具定义更短（第 11 节）。

**确认规则**：

- **新建为 write，代码不另加确认，管家也不先复述**：项目、时间规则和每次运行做什么都清楚了就直接调用工具（回复约定写明，管家评测验证）。新建的定时任务是停用的，不会运行，删掉就没了。真正开始花钱、无人值守的时刻是启用（定时任务 RFC 的 D6：启用就是批准），所以确认放在启用上：新建之后，代码写的配置块（项目、目录、规则的人话描述、接下来 3 次触发的本地时刻、重叠策略、前置检查、花费上限、通知、Agent Profile、任务并发上限）直接发到聊天，最后问「要启用吗？回复「启用」就启用」；用户回复「启用」后，管家调用 `enable`，代码返回 `needs_confirmation` 并写出要启用的内容，用户下一条消息确认后才启用（见下一条）。
- **启用、立即运行为 high（2026-10-18 维护者定，改变 #160 已交付的启用：原为 write）**：和取消任务一样由代码执行——第一次调用返回 `needs_confirmation`、什么都不做，用户在下一条消息里确认（`looper_confirm`）才启用或运行，没有在下一条消息确认的作废。确认说明写出规则、接下来 3 次触发（启用）、需求和花费上限。已经启用的再启用不需要确认。管家不用自己的话先问这两件事：评测里 opus xhigh 在回复约定要求先问时只在文字里问、不调用工具，对话里用户说「现在立即运行一次」后没有运行（`schedule_run` 0/2），所以回复约定改为直接调用，确认由代码问。
- **同一轮新建的定时任务，这一轮里不能启用，也不能立即运行**（`conflict`）。这一条由代码执行（轮次记下自己新建的定时任务），不靠提示词：用户还没看到配置块，管家不能替他批准。
- **修改为 write**，只有提高或取消花费上限（`run_budget_usd`、`daily_budget_usd` 变高或变成 `null`）为 high，沿用第 7 节「提高花费上限一律算 high」。修改之后（或 high 时在确认说明里），代码写出每个改动的字段「改前 → 改后」，规则或时区变了时附上接下来 3 次触发的时刻。
- **立即运行**等于界面的 Run now 按钮，一次运行受它自己的花费上限和每日上限约束；档位见上，为 high。
- 只能建在已有项目里；项目不存在时返回 `not_found`，提示先用 `looper_projects` 按用户给的目录建项目。定时任务 RFC 第 9 节原写「新项目由代码确认」，那是 #88 建任务时的做法；`looper_projects` 的 `create` 在 T2 已是 write，不必为定时任务再做一套新项目确认。
- **通知默认发到发起的聊天**：在 Telegram 或飞书里新建、且没有给 `notify_target` 时，目标是发消息的人（发送者白名单允许时；不允许就只在控制台），即定时任务 RFC 的 Q2 原定做法。网页聊天里新建的只在控制台。
- **重名时问用户**：工具拒绝有歧义的名字并列出候选（#160）；回复约定还要求管家问用户是哪个项目的，不自己挑（haiku 实测里有一次先列出、再自己挑了一个运行）。
- **导出用工具**：回复约定把 `looper_config_export` 列进读取类工具（haiku 实测里有两次没用它，自己读了项目和定时任务、自己写了一个文件，还说已经导出）。

**考虑过、没有采用的做法**：

| 做法 | 为什么不用 |
|---|---|
| 新建为 high（代码在下一条消息确认后才建） | 管家已经先复述、等用户确认；代码再确认一次，用户要在复述、确认说明和启用问题上回复三次，确认挡的还是不花钱的一步。代码写的事实（规则的人话描述、接下来几次触发）放在启用之前，挡住的才是真正有风险的那一步 |
| 新建为 high，确认后直接启用 | 用户想先建好、暂不启用时还得另外处理；和「新建的定时任务一律停用」的接口规则相反 |
| 启用、立即运行保持 write，只靠回复约定让管家先问 | 约定不是代码：opus xhigh 只在文字里问、不调用工具（`schedule_run` 0/2），且问了之后没有代码保证确认来自用户的下一条消息；改为 high 后确认由代码执行，和取消任务一致（2026-10-18 维护者定） |

**`looper_config_export`**：参数只有 `include_projects`（默认 `false`，同 `looper config export --include-projects`；为 `true` 时含每个项目的设置层、知识、技能和定时任务）。**从不含密钥**：没有对应参数，密钥一律是占位符（要带密钥，在本机用 `looper config export --include-secrets`）。文件写到 Looper 运行目录的 `exports/looper-config-<UTC 时间>-<短 id>.json`，读权限按 umask，答复给出路径、大小、各部分条数、留作占位符的密钥数、要重新指向的路径文档数，以及怎么导入（`looper config import <文件>`，或界面的 Settings → Import / Export）。风险档 read：它不改平台的任何状态，自主轮里也能用。不接受用户指定路径：从聊天里往任意路径写文件，等于让管家能覆盖本机任意文件；不只给一个下载链接：飞书、Telegram 里的用户不一定能打开控制台。

**定时任务的导出与导入**（`looper config export --include-projects`、界面的导出、管家的导出都一样）：

- 定时任务放在所属项目的 `schedules` 里（只在含项目时导出）：上面 `fields` 的各项，Agent Profile 按名字，`task_limits` 按角色。**不导出**：是否启用（导入后一律停用）、运行记录和通知记录、计数和告警状态，以及定时任务自己的目录：目录是本机路径，和项目目录一样不导出；有自己目录的，条目里带 `repoint: true`。
- 导入按（项目，名字，不区分大小写）匹配，新的部分是 `project.schedules`：
  - 文件里有、这里没有：**新建，停用**（`created_via` 为 `import`），用项目的目录；
  - 两边都有、字段不同：**按文件改写并停用**，目录保留这里的；
  - 两边都有、字段相同：不动（保持原来的启用状态），所以同一个文件再导入一次什么也不改；
  - 校验不过（规则无效或太密、Agent Profile 这里没有、超出范围的值）：跳过并写明原因，和其他条目一样。
- `notify_target` 只有在这台机器（含这次导入的渠道配置）的发送者白名单允许时才保留，否则去掉、改为只在控制台，并记一条说明。
- 预览和导入的结果里，每个新建或改写的定时任务都记一条说明：已停用，检查它的目录和前置检查之后再启用。
- 停用而不是保留启用状态，是因为启用就是批准（定时任务 RFC 的 D6）：换了机器、改了规则，都没有人在这里批准过。考虑过「已有的保持启用、只改字段」，没有采用：导入会让一个改过规则的定时任务在没人看过的情况下继续无人值守地跑。

## 8. 调整运行中的任务

目标：任务随时可以编辑调整，规划者每次都会知道，并决定要不要重新编排（D3）。

### 8.1 任务变更：补充说明和需求修改

**两种变更**：

| 变更 | 来源 | 存储 |
|---|---|---|
| 补充说明 | 管家 `looper_task_instruct`（用户原话和管家的一句概括）；聊天页直接发给规划者的消息 | 任务日志的 `supplement` 条目：原文、概括（可空）、时间、经由（管家及其渠道和聊天，或聊天页）。只追加，不修改、不撤回，后一条和前一条冲突时以后一条为准 |
| 需求修改 | 管家 `looper_task_update`；任务页编辑需求 | 新表 `task_requirement_versions`：任务、版本号（从 1 起，建任务时的原文是 1）、全文、时间、经由。`tasks.requirement` 始终是当前版本 |

`supplement` 取代现在的 `user_instruction`：聊天页发给规划者的每条消息都记为补充说明。一次性迁移把已有的 `user_instruction` 条目改为 `supplement`，此后代码只写 `supplement`。

**送达保证**：每一条变更都必定以一轮规划者回合送达，不会丢。

- 变更先存进数据库，带「尚未送达规划者」的标记，再通知规划者；
- 规划者空闲时立即做一轮变更回合；正在跑一轮（规划、决策、聊天、巡检）时，这一轮结束后紧接着做；
- 同时攒下的多条变更合成一轮：补充说明逐条列出，需求修改给出旧版本到新版本的差异（按行的 diff，过长时给出新全文和改动的段落）；
- 这一轮的回复被代码解析、执行之后，才把这些变更标为已送达。回合失败、进程退出或服务重启时，变更仍是未送达，下一次规划者起来（恢复的任务、重启的任务）先做这一轮；
- 还在排队（`pending`，规划者还没起来）的任务，变更在 PLAN 轮里一并交给规划者并标为已送达；已经结束的任务不接受变更（`conflict`），重启时按新的需求规划；
- 变更回合沿用 CHAT 的形状（第 8.2 节），消息开头写明这是任务变更、来自哪里。规划者的 `reply` 发回变更来自的聊天（管家所在的聊天、聊天页）；来自任务页的，记进任务动态。

**之后的每一轮都看得到**：

- 规划者：PLAN 和之后每一轮的消息里单列「补充说明」，全部、按时间先后，预算单独计（同现在 `user_instruction` 的做法）；规划者 system prompt 的任务一节始终是当前版本的需求，需求修改后它的进程在下一轮按现有规则（system prompt 变了）以 `--resume` 重起；
- 执行者、评审者：之后开始的每一步，任务一节里是当前版本的需求，后面列出全部补充说明。评审者也看得到，否则执行者照补充说明做了，评审却按原需求判不通过（开发计划第 5.2 节已记的同类缺口）；
- 任务页：需求一栏显示当前文本，可以展开历史版本（版本号、时间、经由）；下面一栏「补充说明」，按时间先后；
- 未开始的任务：没有规划者，管家和任务页直接改需求（同样存版本），不产生变更回合；补充说明只给已开始的任务。

### 8.2 规划者的 CHAT 新增 `replan`

CHAT（包括变更回合）的动作从 none、forward、add_steps 增加到四个，由规划者选：

| 动作 | 做什么 |
|---|---|
| `none` | 只回答 |
| `forward` | 把一段话转给某个运行中的执行者，作为它的下一轮（Codex、OMP 的执行者不能在运行中插话，留给该步的决策轮） |
| `add_steps` | 在计划末尾加步骤 |
| `replan` | `"steps"`（PLAN 的步骤形状）替换所有还没开始的步骤；已经开始的步骤不变；可选 `"stop": ["s2"]` 停掉指定的运行中步骤 |

运行中的步骤遇到 `replan` 默认保留（维护者 2026-10-15 认可）：

- 保留：它跑完后照常进入决策轮，规划者那时已经看得到变更，可以接受、带反馈重试或再规划。不浪费已经做完的部分，也不引入新的中断路径。
- 停止（`stop` 里列出的）：沿用 SUPERVISE 的 kill 路径结束它的执行者，该步记为放弃（`skipped`），日志记一条「因任务变更停止」。它已经写进工作目录的改动留在原处，新的步骤要说明怎么处理；并行步骤的目录隔离落地后，隔离运行的步骤被停止时，它的工作区按[目录隔离 RFC](step-workdir-isolation-v0.zh-CN.md) 第 7 节「改计划」一行标为 `discarded` 并清理，任务目录不受影响。用于变更让正在做的事白做的情况，例如「数据库改用 PostgreSQL」时正在写 SQLite 的那一步。

`replan` 的校验和 DECISION 的 `replan` 相同（步骤编号、依赖、无环；步骤数不设上限），`stop` 只能列出运行中的步骤，新步骤可以依赖保留下来的运行中步骤。

### 8.3 规划者选 Agent Profile：本任务的 MCP 工具（D9、D10）

**能力**：规划者可以为本任务的执行者、评审者选 Agent Profile，为剩下的步骤，或为指定的某一步，例如难的一步换更强的模型。只能从项目的可选列表里选，不能改规划者自己的 Profile，也不能改角色、共用默认的设置。它还可以改本任务的并发上限（D10）。

**MCP 条目**：同一个 `looper mcp-server`，以「规划者」范围启动。`looper serve` 在规划者启动时为该任务生成一个令牌（以 `planner.` 开头，只存哈希，不进日志），经条目的环境变量交给它；规划者停止（任务结束，或换了新的规划者）时作废，任务结束后也不再接受；平台只接受这个令牌对本任务的调用，调用其他任务、其他操作（包括管家的工具）一律 `forbidden`，管家的令牌也调用不了规划者的工具。工具有四个：

| 工具 | 做什么 | 风险档 |
|---|---|---|
| `looper_task_profiles` | 列出项目允许的 Profile（编号、名字、运行时、模型、强度、每百万 token 的输入输出价格）、本任务当前对执行者和评审者生效的选择及其来源、各步骤的选择 | read |
| `looper_task_profile_set` | `{"role": "worker" \| "reviewer", "profile_id": "…" \| null, "step": "<步骤编号，可空>"}`：为剩下的步骤（不给 `step`）或指定的一步设定这个角色的 Profile；`null` 清除 | write |
| `looper_task_concurrency` | `{"limits": {"worker"?, "reviewer"?}, "reason": "…"}`：本任务的 Worker、Reviewer 上限（同任务页） | write |

并发工具和管家的 `looper_concurrency` 走同一条代码，直接生效；调高后排队的立即开始，调低不停止正在运行的。它只列它接受的角色：真实运行里 OMP 上的 GPT 模型会把参数结构里列出的每个角色都填上。2026-10-17 前另有改项目上限的 `looper_project_concurrency`，并发只按任务算后删除。

**生效时机**：选择在执行者、评审者的运行开始时读取（和用户给任务选的 Profile 一样）。调用返回之后才派发的执行者或评审者用新的选择，包括同一轮里先调用、再回复 `retry` 或 `replan` 的情况（回复被解析之后才派发）；已经开始运行的不受影响，保留它开始时的 Profile；派发后还在等并发名额的，开始时用那时的选择。为某一步设定的选择，对它此后的每次尝试（重试）都有效；那一步已经结束、或不存在时返回 `invalid`。选择只在 Profile 还在任务所属项目的可选列表里时有效：从列表里去掉一个 Profile，项目里规划者对它的选择一并删除；任务换到别的项目后，只认新项目列表里的。按「从头再来」重启任务时，规划者的选择一并清除；接着做时保留。

**校验**：Profile 在项目的可选列表里，并且能跑该角色（和界面选 Profile 用同一个检查）；用户给本任务明确选过这个角色时一律拒绝（`forbidden`，说明是用户选的）；只在代码发起的规划者回合里接受，规划者自己发起的一轮（后台工作结束后）只能调用 `read` 档。

**优先级**（从高到低）：用户给本任务的选择（建任务时或 `looper_task_update`）→ 规划者为这一步的选择 → 规划者为剩下步骤的选择 → 各设置层。

**留痕与显示**：每次 `looper_task_profile_set` 记一条任务日志（新类型 `profile_choice`：角色、Profile、范围、理由由工具参数可选的 `reason` 给出）和一条动态；每次改并发记一条 `concurrency_change`（各角色改前改后的上限和理由）和一条动态，任务来自 Telegram 或飞书时还经任务的通知对象（`NotifyTarget`）发一条消息，来自网页聊天的只记日志；运行记录的 Profile 来源多两层（规划者为本步 `planner_step`、规划者为剩下步骤 `planner_task`）；任务页的 Agents 一栏显示执行者、评审者当前用的 Profile 及其来源，Findings 列出规划者的选择和改并发的记录。

**代价**：规划者多注入一个 MCP 条目，三种运行时都要：Claude Code 常驻进程里 MCP 子进程随它常驻；Codex、OMP 的规划者每轮重起进程，MCP 子进程每轮重新拉起，约多 0.3–1 秒；四个工具的定义和 system prompt 里的用法一节常驻规划者上下文，实测约 5.5 KB（定义约 3.6 KB，用法约 1.9 KB）。另需按任务发、收令牌，平台多一条按任务限定范围的入口。（v1 初稿比较过把选择写进规划者回复约定的做法，维护者选了 MCP 工具：和管家同一套机制，规划者可以自己查询可选列表和价格。）

**项目设置**：新增「规划者可选的 Agent Profile」列表（新表 `project_allowed_profiles`：项目、Profile；删项目时一起删，Profile 被列表引用时不能删并说明在哪），在项目设置页编辑，管家在 T2 用 `looper_settings` 改。**默认为空**：维护者放开之前，规划者的 `looper_task_profile_set` 一律返回 `forbidden`，行为和现在一样。一份列表管整个项目，选的时候再检查能不能跑该角色（Q6）。

**确认**：规划者换 Profile 不需要确认，包括换成更贵的（维护者 2026-10-15 认可）：没有人在线等确认，列表本身就是事先授权，单任务花费上限兜底。

### 8.4 运行中的任务换 Agent Profile（管家）

管家用 `looper_task_update` 改运行中任务的按角色 Profile：执行者、评审者从下一步开始生效；规划者换不换会话按现有规则（多运行时 RFC 的 P5，先交接再开新会话）。这是用户本人的选择，不受项目可选列表限制，也是规划者不能推翻的那一层。

## 9. 迁移现有的 JSON 动作

- `task_request` → `looper_task_create`，`task_start` → `looper_task_control(start)`；
- 新项目确认（#88 的 `new_project`）改走第 6 节的确认规则；
- 配置块和开始提问由平台直接发到聊天；
- 迁完后删掉回复里的 JSON 解析和提示词里对应的约定；仍为旧默认提示词的 manager 行迁到新默认，改过的保留。

## 10. 运行时

| 运行时 | 注入 | 说明 |
|---|---|---|
| Claude Code | `--mcp-config`，配合 `--strict-mcp-config` | 常驻进程，MCP 子进程随它常驻 |
| Codex | 隔离目录 `config.toml` 的 `[mcp_servers.looper]` | 每轮起一个进程，MCP 子进程每轮重新拉起，约多 0.3–1 秒 |
| OMP | 家目录里生成的插件 `looper` 的 `mcpServers` | 同 Codex，逐轮续接 |

规划者（T2）用同样的三种注入方式，条目以规划者范围启动、带本任务的令牌（第 8.3 节）。

## 11. 上下文开销

T2 之后管家有 14 个工具，定义实测 12.6 KB（`tools/list` 的 JSON），用法一节（`TOOLS_CONTRACT`）2.7 KB；T1 时是 8 个工具 6.8 KB、用法 2.4 KB。T2 的六个工具共 5.8 KB，说明已经压短。T3 的 `looper_schedules` 先有列出、查看、启用、停用、删除时是 15 个工具 13.4 KB（这个工具 0.84 KB），用法 2.8 KB。T3 完成后是 16 个工具 15.0 KB（14,988 字节；`looper_schedules` 2.0 KB，`looper_config_export` 0.35 KB），用法 3.3 KB，正好压在 15 KB 的线内：定时任务的设置放进一个 `fields` 对象，各字段只留必要的说明，导出工具的说明也压短了。以后再加工具或动作，先合并工具或精简已有的说明。规划者（T2）只多四个工具和一节用法，实测约 5.5 KB。

## 12. 评测与验收

- **管家评测（新增）**：现有评测只覆盖规划者、执行者、评审者。新增一组对话脚本，每段对话断言工具调用和平台状态。用例：
  - 没说项目时先问项目；
  - 停止和恢复任务；
  - 给运行中的任务加补充说明、改需求：平台存下 `supplement` 或新的需求版本，规划者在一轮变更回合里收到并选择动作；
  - 删除时确认，以及拒绝确认；
  - 给角色换 Agent Profile；
  - 自主轮里的写操作被拒。
  
  真实模式用 haiku，每次评测不超过 $0.50。
- **规划者评测（在现有一组上新增）**：
  - 补充说明触发重新规划：任务进行中加一条改变后续步骤的补充说明（例如输出格式从 JSON 改为 CSV），断言规划者选了 `replan` 或 `add_steps`，最终文件符合补充说明，评审者按补充说明判断；
  - 修改需求触发重新规划：同样的改动以需求修改的方式给出，断言规划者收到差异并改了计划；
  - 补充说明不需要改计划时选 `none`；
  - （T2）选 Agent Profile 只在允许的列表内：项目放开两个 Profile，断言规划者的 `looper_task_profile_set` 都在列表里、被拒的调用没有生效；列表为空时调用一律被拒。
- **单元和数据库测试**：操作目录的结构校验、风险档、确认规则（同聊天、下一条、过期、作废）、令牌、自主轮只读、留痕；`supplement` 的存储（含 `user_instruction` 的迁移）和在规划者、执行者、评审者、任务页的出现；需求版本；变更的送达保证（规划者忙时排到下一轮、多条合成一轮、回合失败和重启后仍未送达、排队中的任务在 PLAN 里送达）；CHAT `replan` 的校验和 `stop`；（T2）规划者范围的令牌只认本任务，Profile 选择不在列表、用户已选、不能跑该角色时都拒绝，生效时机、优先级和留痕。
- **真实路径**：
  - 本分支在新库、非 8767 端口上起服务；
  - 用真实模型（haiku）走一遍上面的对话，网页聊天和替身渠道各一次；
  - 核对平台状态和留痕；
  - 三种运行时各做一次工具调用。

|---|---|---|
| Q1 | 普通接口没有令牌，任何本机 agent 都能 curl | 本次只给管家专用接口加令牌；普通接口加令牌另列待办，界面通过同源会话获得令牌 |
| Q2 | 网页聊天里给确认加一个按钮 | 先用「下一条消息」规则，三个渠道通用；按钮作为界面优化（非核心待办） |

| Q5 | 飞书、Telegram 上的确认说明格式 | 纯文本；平台直接发，按渠道的长度上限截断并给出完整说明的链接 |
| Q6 | 可选 Profile 列表按项目一份，还是按角色各一份 | **已定（维护者 2026-10-15）**：按项目一份，选的时候再检查能不能跑该角色 |

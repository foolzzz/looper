# RFC：管家的平台工具（v0）

- **状态：** 方向已定（第 3 节 D1–D4 由维护者在 2026-10-15 拍板；v1 修订加入维护者同日的两项决定：规划者可以在本任务内选执行者、评审者的 Agent Profile，管家给运行中的任务加补充说明），其余为设计提案；待决问题见第 13 节。
- **开发计划：** [长程 Agent 上下文体系开发计划](../../plans/2026-10-13-long-horizon-agent-context.zh-CN.md) 第 5.0 节的 T1–T3。
- **最近更新：** 2026-10-15（v1）

## 1. 背景与目标

维护者希望**能在界面上做的事，尽量都能通过和管家聊天完成**：开始、停止任务，新增、修改 Agent Profile，聊天过程中调整任务的内容，等等。

现状：

- 管家只有两个动作，建任务（`task_request`）和开始任务（`task_start`）。管家在回复里写一段 JSON，代码解析后执行（#88）。
- 平台的 HTTP 接口约 65 个，管家都碰不到。
- 管家要做别的事，只能自己在 shell 里 curl 接口。没有类型，没有确认，也没有留痕。

**目标：**

- 平台和管家之间有一份明确的交互协议：有哪些操作、各自的输入输出、风险分档、确认规则、身份和留痕；
- 管家通过 MCP 工具调用这些操作。三种运行时（Claude Code、Codex、OMP）都能用；
- 高影响操作由代码强制确认，不靠提示词约束；
- 现有的 JSON 动作迁到同一套机制里，最后只剩一种方式。

**不做：**

- 密钥不经过聊天：管家可以登记 LLM 提供方，但 API key 只在界面里填；
- 文件上传类操作（上传 skill 包、导入配置文件）留在界面；
- 规划者、执行者、评审者不拿平台工具，它们各有自己的回复约定。规划者需要的新能力（选 Agent Profile、按补充说明重新规划）加进它的回复约定，由代码校验（D9）。

## 2. 概念

| 概念 | 定义 |
|---|---|
| 操作 | 平台能做的一件事，例如「停止任务」。有名称、输入输出结构、错误码和风险档 |
| 操作目录 | 所有操作的唯一定义。管家工具、管家专用接口和文档都从它生成 |
| 工具 | 管家看到的 MCP 工具，一个工具可以覆盖同一资源上的几个操作 |
| 风险档 | `read` 只读；`write` 普通修改；`high` 高影响，需要用户确认 |
| 待确认 | 高影响操作的第一步：平台只登记、不执行，把影响说明直接发给用户 |
| 补充说明 | 任务开始后用户追加的要求，类型化存储（任务日志的 `supplement` 条目）。需求原文不改，补充说明列在它后面，规划者、之后的每个执行者和评审者都看得到，任务页显示为「补充说明」 |
| 可选 Agent Profile | 项目设置里的一个列表：规划者只能从中为本任务的执行者、评审者选 Agent Profile。默认为空，即规划者不能换 |

## 3. 决策

| # | 决策 | 理由 |
|---|---|---|
| **D1** | **用 MCP 工具**，不扩展 JSON 动作，也不让管家 curl | 维护者选定。MCP 的参数有结构并在调用时校验，一轮里能连续调用、看结果再决定下一步，三种运行时都原生支持 |
| **D2** | **分档确认**：只读直接执行；普通修改在用户提出后执行；高影响操作两步确认 | 维护者选定。开始、停止这类日常操作不用多问一句；删除、取消、改共用默认、提高花费上限这类，代码先列出影响面 |
| **D3** | **调整运行中的任务由规划者来改计划**：管家把用户的要求存为任务的补充说明并转给该任务的规划者，规划者在一轮 CHAT 里决定不动、加步骤、转给运行中的执行者，还是重新规划（第 8 节） | 维护者选定（v1 补充：补充说明类型化、所有后续 agent 可见，CHAT 新增 `replan`）。计划只有一个人在改，不会冲突 |
| **D4** | **排在定时任务 S2 之后、S3 之前**；S3 的管家入口并入 T3 | 维护者选定。S3 不必先做一套 JSON 动作再迁移 |
| D5 | **MCP 进程只做转发**：校验、分档、确认、执行、留痕都在 `looper serve` 里，通过一个只给管家用、要带令牌的接口完成 | MCP 进程由管家的运行时拉起，每种运行时管理它的方式不同（Codex 每轮重新拉起）。逻辑放在平台里，只有一处事实 |
| D6 | **不另做 skill**。工具的用法写进管家提示词里由代码维护的一节，和现有的回复约定放在一起 | Looper 关掉了 Codex 的原生 skill 列表。写在提示词里，三种运行时都看得到 |
| D7 | **代码生成的关键信息由平台直接发到聊天**，包括任务配置块、确认说明，不经模型转述 | 用户看到的是代码保证的原文；模型只需说明「见上」 |
| D8 | **原生 tool 不单做**。等 SDK 运行时（M9d）上线时，从同一份操作目录生成 | 避免两套定义 |
| **D9** | **规划者选 Agent Profile 走它的回复约定**（方案 b），不给规划者 MCP 工具：步骤、重试和本任务默认值上可选填 Agent Profile，代码按项目的可选列表校验（第 8.3 节） | 维护者决定给规划者这项能力（2026-10-15）。规划者每一轮本来就交代码校验的 JSON，选择和它所属的决定在同一个回复里，原子、可复现，三种运行时一样；对比见第 8.3 节 |
| **D10** | **规划者只能在本任务内、从项目允许的列表里选**；不能改项目、角色和共用默认的设置，也不能改自己的 Profile | 维护者选定。项目的可选列表是维护者事先的授权，默认为空 |

## 4. 架构

```
用户（网页 / 飞书 / Telegram）
   │ 聊天
   ▼
looper serve ──── 管家专用接口 POST /api/agent/v1/ops/<操作>（需令牌）
   │ 交给管家                   ▲
   ▼                            │ 本机 HTTP
管家进程（Claude Code / Codex / OMP）
   │ stdin / stdout，JSON-RPC
   ▼
looper mcp-server（子进程，薄客户端）
```

- **操作目录**：放在 `looper/agents/ops/`，每个操作是「名称、说明、输入结构（JSON Schema）、风险档、处理函数」。处理函数调用现有的服务代码，和界面接口共用校验。
- **MCP 服务**：`looper mcp-server` 子命令，走标准输入输出。自己实现 MCP 的 `initialize`、`tools/list`、`tools/call`，不加依赖。工具列表从操作目录生成，每次调用转发给管家专用接口。
- **注入**：内置的 MCP 条目只装给管家角色，始终启用，不能卸载；沿用现有 MCP 的注入路径（Claude Code `--mcp-config`，Codex 的 `config.toml`，OMP 的 `mcpServers`）。平台地址和令牌经这个条目的环境变量传入。

## 5. 交互流程

**启动**：管家进程拉起 `looper mcp-server`，发 `initialize` 交换版本，再发 `tools/list` 取得工具列表，放进模型的上下文。

**普通调用**（「把斗地主任务停掉」）：

1. 模型调用 `looper_tasks`，参数是 `{"action": "list", "query": "斗地主"}`，拿到任务编号；
2. 同一轮里调用 `looper_task_control`，参数是 `{"task_id": "…", "action": "stop"}`；
3. 平台确认这是 `write` 档、调用发生在用户的这一轮里，于是执行，记一条留痕，返回结果；
4. 模型回复用户。

**高影响调用**（「把 doudizhu 项目删了」）：

1. 模型调用 `looper_projects`，参数是 `{"action": "delete", …}`；
2. 平台不执行，登记一条待确认，返回 `{"status": "needs_confirmation", "confirmation_id": "c-…", "expires_in_seconds": 600}`，同时把代码生成的影响说明直接发到这个聊天；
3. 用户回复。平台把消息交给管家时附一句提示，说明上一轮有待确认的操作；
4. 模型调用 `looper_confirm`，参数是 `{"confirmation_id": "c-…"}`。平台核对三件事：同一个聊天、正是用户紧接着的下一条消息、没有过期。三条都满足才执行，否则作废并返回原因。

## 6. 协议

**返回结构**：

| 字段 | 含义 |
|---|---|
| `status` | `ok`、`needs_confirmation` 或 `error` |
| `result` | `ok` 时的结果，结构由操作定义 |
| `confirmation_id`、`expires_in_seconds` | `needs_confirmation` 时给出 |
| `error.code` | `not_found`、`invalid`、`needs_user_turn`、`forbidden`、`conflict`、`expired` |
| `error.message` | 给模型看的原因，写明怎么改 |

**确认规则**：

- 每个聊天同时只有一条待确认，新的一条取代旧的；
- 有效期 10 分钟；
- 只认用户紧接着的下一条消息之后的那一轮；
- 确认后按登记时的参数执行，不接受改参数。

**身份与范围**：

- `looper serve` 每次启动生成一个随机令牌，只交给管家的 MCP 条目；
- 平台知道管家当前正在处理哪个聊天、哪个渠道的哪条消息，每次调用都挂到这一轮上；
- 管家自己发起的一轮（后台工作结束时，#26）只能调用 `read` 档。

**留痕**：新表 `manager_actions` 记录时间、聊天、渠道、操作、参数（密钥打码）、风险档、结果、确认编号。任务页、设置页上，管家做过的改动标「由管家操作」。

## 8. 调整运行中的任务

### 8.1 补充说明（`looper_task_instruct`）

1. 管家调用 `looper_task_instruct`，参数 `{"task_id": "…", "text": "<用户的原话>", "summary": "<管家的一句概括，可空>"}`。平台只接受运行中的任务（`pending`、`running`、`executing`），未开始的任务返回 `invalid` 并提示改用 `looper_task_update`，已结束的任务返回 `conflict`。
2. 平台把它写成任务日志里一条 `supplement` 条目（新的类型，和 `user_instruction` 并列）：原话、概括、时间、经由（管家，渠道和聊天）。直接在规划者聊天里发的消息仍记为 `user_instruction`，不算补充说明：那里常常只是提问。
3. 平台把补充说明作为一条消息交给该任务的规划者，规划者做一轮 CHAT（第 8.2 节）。规划者的回答由平台发回管家所在的聊天，管家不再转述（D7）。还在排队（`pending`，规划者还没起来）或正在制定计划的任务，补充说明先存下：还没开始规划的，规划者在 PLAN 轮里看到；正在规划的，计划定下后紧接着一轮 CHAT 交给规划者。
4. 补充说明从此跟着需求一起出现：
   - 规划者：PLAN 消息和每一轮 DECISION、SUPERVISE、CHAT 的消息里，在用户指令之前单列「补充说明」，全部、按时间先后，预算单独计（同 `user_instruction` 的做法）；
   - 执行者：之后开始的每一步，它的任务一节里，需求原文后面列出全部补充说明；
   - 评审者：同执行者。评审按补充说明之后的要求判断，否则执行者照补充说明做了，评审却按原需求判不通过（开发计划第 5.2 节已记的同类缺口：重试时的补充说明评审者看不到）；
   - 任务页：需求下面一栏「补充说明」，按时间先后，每条写明时间和经由；
   - 补充说明只追加、不修改；后一条和前一条冲突时以后一条为准，提示词里写明。
5. 未开始的任务没有规划者：管家用 `looper_task_update` 直接改需求原文，不产生补充说明。

### 8.2 规划者的 CHAT 新增 `replan`

CHAT 的动作从 none、forward、add_steps 增加到四个，由规划者选：

| 动作 | 做什么 |
|---|---|
| `none` | 只回答 |
| `forward` | 把一段话转给某个运行中的执行者，作为它的下一轮（Codex、OMP 的执行者不能在运行中插话，留给该步的决策轮） |
| `add_steps` | 在计划末尾加步骤 |
| `replan` | `"steps"`（PLAN 的步骤形状）替换所有还没开始的步骤；已经开始的步骤不变；可选 `"stop": ["s2"]` 停掉指定的运行中步骤 |

运行中的步骤遇到 `replan`，**默认保留**，建议如此：

- 保留：它跑完后照常进入决策轮，规划者那时已经看得到补充说明，可以接受、带反馈重试或再规划。不浪费已经做完的部分，也不引入新的中断路径。
- 停止（`stop` 里列出的）：沿用 SUPERVISE 的 kill 路径结束它的执行者，该步记为放弃（`skipped`），日志记一条「因补充说明停止」。它已经写进工作目录的改动留在原处，新的步骤要说明怎么处理；并行步骤的目录隔离（开发计划第 5.0 节第 11 项）落地后，停止的步骤连同它的工作目录一起丢弃。用于补充说明让正在做的事白做的情况，例如「数据库改用 PostgreSQL」时正在写 SQLite 的那一步。

`replan` 的校验和 DECISION 的 `replan` 相同（步骤编号、依赖、上限 8 步、无环），`stop` 只能列出运行中的步骤，新步骤可以依赖保留下来的运行中步骤。

### 8.3 规划者选 Agent Profile（D9、D10）

**能力**：规划者可以为本任务的执行者、评审者选 Agent Profile，按步骤，或作为本任务剩下步骤的默认值，例如难的一步换更强的模型。只能从项目的可选列表里选，选择在下一个执行者或评审者开始时生效，不影响正在运行的，也不能改规划者自己的 Profile。

**两种机制的比较**：

| | (a) MCP 工具，按任务发令牌 | (b) 规划者的回复约定（推荐） |
|---|---|---|
| 和决定的关系 | 工具调用和 DECISION 回复分开：先调工具换 Profile，再回复 retry，两者的先后、失败一半时怎么办都要另外定 | 选择就在它所属的决定里，例如 `retry` 带上这一步的 Profile，一个回复、一次校验、一起生效 |
| 校验和出错 | 工具返回错误，模型可能不理会，照样回复 | 不在列表里就是违反约定，进入现有的修复轮，模型必须改正 |
| 运行时 | 规划者要多挂一个 MCP 子进程，Codex、OMP 每轮重新拉起；要按任务发令牌、限定范围 | 不需要新进程和令牌，三种运行时一样 |
| 可复现与评测 | 依赖模型是否调用工具 | 回复是结构化 JSON，评测直接断言 |
| 能做的事 | 还能自己查询可选列表 | 可选列表和每个 Profile 的模型、强度、运行时、价格由代码写进消息，不需要查询 |

结论：选 (b)。它提供同样的能力（按步骤或本任务默认，在允许的列表内），又少一个进程、一种令牌和一条失败路径。维护者说的「开放给管家和规划者」由此兑现：管家用 MCP 工具，规划者用它本来就交给代码校验的回复约定，两者共用操作目录里的同一段校验（Profile 存在、能跑该角色、在项目列表里）。以后规划者若需要只读查询（例如查花费），再按 (a) 给它开只读工具。

**约定**（加进 `REPLY_CONTRACT`）：

- PLAN 和 `replan`、`add_steps` 的步骤形状加可选 `"profiles": {"worker": "<profile id>", "reviewer": "<profile id>"}`：只对这一步生效；
- DECISION 的 `retry` 加可选 `"profiles"`：只对重试的这一步生效；
- PLAN、DECISION、CHAT 的回复加可选 `"task_profiles": {"worker": …, "reviewer": …}`：本任务之后开始、没有自己选择的步骤都用它；值为 `null` 时取消；
- 消息里列出项目允许的 Profile（编号、名字、运行时、模型、强度、价格）和当前生效的选择；列表为空时不出现这些字段的说明，出现了即违反约定。

**校验**：Profile 在项目的可选列表里，并且能跑对应角色（和界面选 Profile 用同一个检查）；否则违反约定，进入修复轮，错误信息列出允许的 Profile。

**优先级**（从高到低）：用户给本任务的选择（建任务时或 `looper_task_update`）→ 这一步的选择 → 规划者的本任务默认 → 各设置层。用户给本任务明确选过某个角色的 Profile 时，规划者对该角色的选择一律拒绝（违反约定，错误信息说明是用户选的，消息里也不列这个角色），即用户的选择不被规划者推翻。

**存储与显示**：步骤记下它的执行者、评审者 Profile 和来源（`step`、`planner_task`），规划者的本任务默认存在计划行上；运行记录的 Profile 来源多一层「规划者为本步选择」；任务日志记一条决定；任务页每一步显示它用的 Profile。

**项目设置**：新增「规划者可选的 Agent Profile」列表（新表 `project_allowed_profiles`：项目、Profile；删项目时一起删，Profile 被列表引用时不能删并说明在哪），在项目设置页编辑，管家在 T2 用 `looper_settings` 改。**默认为空**，建议如此：维护者明确放开之前，规划者不能换，行为和现在一样。

**确认**：规划者换 Profile 不需要确认，包括换成更贵的：没有人在线等确认，列表本身就是事先授权，单任务花费上限兜底。每次选择都记日志并显示在任务页。

### 8.4 运行中的任务换 Agent Profile（管家）

管家用 `looper_task_update` 改运行中任务的按角色 Profile：执行者、评审者从下一步开始生效；规划者换不换会话按现有规则（多运行时 RFC 的 P5，先交接再开新会话）。这是用户本人的选择，不受项目可选列表限制，也是规划者不能推翻的那一层。

## 9. 迁移现有的 JSON 动作

- `task_request` → `looper_task_create`，`task_start` → `looper_task_control(start)`；
- 新项目确认（#88 的 `new_project`）改走第 6 节的确认规则；
- 配置块和开始提问由平台直接发到聊天；
- 迁完后删掉回复里的 JSON 解析和提示词里对应的约定；仍为旧默认提示词的 manager 行迁到新默认，改过的保留。

## 11. 上下文开销

约 15 个工具的定义常驻管家上下文，预计 10 KB 左右。实现后实测；超过 15 KB 就合并工具或精简说明。

## 12. 评测与验收

- **管家评测（新增）**：现有评测只覆盖规划者、执行者、评审者。新增一组对话脚本，每段对话断言工具调用和平台状态。用例：
  - 没说项目时先问项目；
  - 停止和恢复任务；
  - 给运行中的任务加补充说明：平台存下 `supplement`，规划者收到并选择动作；
  - 删除时确认，以及拒绝确认；
  - 给角色换 Agent Profile；
  - 自主轮里的写操作被拒。
  
  真实模式用 haiku，每次评测不超过 $0.50。
- **规划者评测（在现有一组上新增）**：
  - 补充说明触发重新规划：任务进行中加一条改变后续步骤的补充说明（例如输出格式从 JSON 改为 CSV），断言规划者选了 `replan` 或 `add_steps`，最终文件符合补充说明，评审者按补充说明判断；
  - 补充说明不需要改计划时选 `none`；
  - 选 Agent Profile 只在允许的列表内：项目放开两个 Profile，断言规划者的选择都在列表里、违反约定次数为 0；列表为空时回复里不出现 `profiles`。
- **单元和数据库测试**：操作目录的结构校验、风险档、确认规则（同聊天、下一条、过期、作废）、令牌、自主轮只读、留痕；`supplement` 的存储和在规划者、执行者、评审者、任务页的出现；CHAT `replan` 的校验和 `stop`；规划者的 Profile 选择（不在列表、用户已选、不能跑该角色时都拒绝）、优先级和存储。
- **真实路径**：
  - 本分支在新库、非 8767 端口上起服务；
  - 用真实模型（haiku）走一遍上面的对话，网页聊天和替身渠道各一次；
  - 核对平台状态和留痕；
  - 三种运行时各做一次工具调用。

## 13. 待决问题与风险

| # | 问题 | 建议 |
|---|---|---|
| Q1 | 普通接口没有令牌，任何本机 agent 都能 curl | 本次只给管家专用接口加令牌；普通接口加令牌另列待办，界面通过同源会话获得令牌 |
| Q2 | 网页聊天里给确认加一个按钮 | 先用「下一条消息」规则，三个渠道通用；按钮作为界面优化（非核心待办） |
| Q3 | 管家误操作 | 有分档确认和留痕；`write` 档的操作都可以撤回或再改，`high` 档要确认 |
| Q4 | 工具太多占上下文 | 按资源合并，实测控制在 15 KB 内 |
| Q5 | 飞书、Telegram 上的确认说明格式 | 纯文本；平台直接发，按渠道的长度上限截断并给出完整说明的链接 |
| Q6 | 可选 Profile 列表按项目一份，还是按角色各一份 | 按项目一份，选的时候再检查能不能跑该角色；以后真有需要再拆 |
| Q7 | 用户已给本任务选过 Profile 时，规划者能否在个别步骤上换 | 不能，用户的选择优先；用户想放开就清掉本任务的选择 |
| Q8 | 规划者换成更贵的 Profile 要不要确认 | 不要（第 8.3 节）；管家改运行中任务的 Profile 也只算 `write`，不另加确认 |
| Q9 | 补充说明能否修改、撤回 | 只追加；要改就再加一条，以后一条为准 |
| Q10 | 直接在规划者聊天里说的话是否也算补充说明 | 不算，仍记 `user_instruction`（只给规划者和执行者，不进任务页的补充说明栏）；以后可在任务页加「加补充说明」输入框，和管家走同一个操作 |

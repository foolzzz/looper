# Looper v2.14.58

This is the patch release v2.14.58, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.57: `looper service upgrade` (and `looper service restart --drain`) now starts a service that exited during the drain, instead of leaving the unit down ([#1030](https://github.com/foolzzz/looper/pull/1030)).

## Release Decision

**Who should upgrade:** Anyone who runs `looper service upgrade` or `looper service restart --drain`, in particular on hosts where the service can be killed or run out of memory while it drains.

**What this release solves:** The service process may exit during the drain (a crash, an out-of-memory kill, or `kill`; systemd's `Restart=on-failure` does not restart a SIGTERM exit). The next drain-status poll then failed, and recovery only cancelled the drain, because it started the unit only after it had attempted a stop. The unit stayed down until someone ran `looper service restart`. [#1030](https://github.com/foolzzz/looper/pull/1030) makes recovery start the unit when the saved PID is gone, the service manager reports nothing running and nothing listens on the port. Nothing has been installed at that point, so it starts the code that was running. When something runs or listens, recovery starts nothing and only cancels the drain.

**Breaking changes:** No. No API shape or migration changes. An upgrade whose service exited during the drain now ends with the service running instead of down.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#1030](https://github.com/foolzzz/looper/pull/1030); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.58
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.57 upgrades directly. This release adds no migration.

## Behavior changes

- **Recovery starts a service that exited during the drain ([#1030](https://github.com/foolzzz/looper/pull/1030)).** When the drain-status poll fails, no stop has been attempted, and the saved PID is no longer alive, recovery starts the unit if the service manager reports nothing running and nothing listens on the port. It starts the code that was running, because nothing has been installed yet. This also applies if the service was stopped explicitly during the drain.
- **Wait for a closing process.** If the port is already closed but the old PID is still alive (shutdown closes HTTP before the process exits), recovery waits for it to exit, without renewing the drain, and then starts the unit. If the process is still alive when the wait ends, `recovery_error` says so and tells the user to start it with `looper service restart` once it exits. This message now names the PID.
- **Nothing started when something else runs or listens.** If the old PID is gone and another process holds the port while the service manager reports nothing running, recovery raises a port-conflict error ("port N is served by another process (pid P); not starting a second server"; the PID is shown when known) and only cancels the drain. If the service manager already restarted the unit, the upgrade starts nothing and waits up to `--timeout` for it to answer before it reports whether the service is serving.
- **Unchanged.** When the saved PID is still alive, the behavior is unchanged. Retrying the upgrade after recovery and the stop-timeout and start-failure recovery paths are out of scope and unchanged. The text of the existing port-conflict error was reworded (it now comes from one shared helper).
- **Model-visible changes:** No. No prompt, tool description, tool schema or Manager confirmation text changes.
- **Documentation and tests.** `docs/architecture/agent-system.md` describes the recovery. Tests cover it in `tests/test_service_upgrade_execution.py`. The change is in `looper/agents/service.py`.

## 中文摘要

本版本是 patch release v2.14.58（热修线，每个合并的改动立即发布）。自 v2.14.57 以来只合并了一项改动：`looper service upgrade`（以及 `looper service restart --drain`）现在会启动在排空期间退出的服务，而不是让 unit 一直停着（[#1030](https://github.com/foolzzz/looper/pull/1030)）。

### 升级决策

**谁需要升级：**运行 `looper service upgrade` 或 `looper service restart --drain` 的用户，尤其是服务在排空期间可能被杀或内存不足退出的主机。

**解决了什么：**服务进程可能在排空期间退出（崩溃、OOM 被杀或 `kill`；systemd 的 `Restart=on-failure` 不会重启 SIGTERM 退出）。之后的排空状态轮询失败，而恢复逻辑只取消排空，因为它只在尝试过停止之后才启动 unit，于是 unit 一直停着，直到有人运行 `looper service restart`。[#1030](https://github.com/foolzzz/looper/pull/1030) 让恢复在保存的 PID 已不存在、服务管理器报告没有进程运行且端口无人监听时启动 unit。此时尚未安装任何内容，所以启动的是原来运行的代码。若有进程在运行或监听，恢复不启动任何东西，只取消排空。

**是否有破坏性变更：**否。API 形态和迁移不变。排空期间服务退出的升级，现在结束时服务在运行，而不是停着。

**如何验证：**运行 `looper --version` 核对版本为 2.14.58。

**贡献者：**维护者 @foolzzz 提交 [#1030](https://github.com/foolzzz/looper/pull/1030)；本版本无社区贡献。

```bash
looper --version   # looper 2.14.58
```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.57 上的安装可直接升级。本版本没有新迁移。

### 行为变化与入口

- **恢复会启动排空期间退出的服务（[#1030](https://github.com/foolzzz/looper/pull/1030)）。**排空状态轮询失败、尚未尝试停止且保存的 PID 已不存在时，如果服务管理器报告没有进程运行且端口无人监听，恢复会启动 unit。由于尚未安装任何内容，启动的是原来运行的代码。排空期间被显式停止的服务也适用。
- **等待正在关闭的进程。**如果端口已关闭但旧 PID 仍存活（关闭时先关 HTTP 再退出进程），恢复会在不续期排空的情况下等待其退出，然后启动 unit。等待结束时进程仍存活，则 `recovery_error` 会说明，并提示其退出后用 `looper service restart` 启动；该消息现在带有 PID。
- **有其他进程运行或监听时不启动。**旧 PID 已不存在、另一个进程占用端口且服务管理器报告没有运行时，恢复抛出端口冲突错误（“port N is served by another process (pid P); not starting a second server”，已知时显示 PID），只取消排空。如果服务管理器已重启 unit，升级不启动任何东西，并最多等待 `--timeout` 让其响应，然后报告是否在服务。
- **不变。**保存的 PID 仍存活时行为不变。恢复后重试升级，以及停止超时和启动失败的恢复路径不在范围内，保持不变。原有端口冲突错误的文字已改写（现由同一个辅助函数生成）。
- **面向模型的变化：**无。不改变提示、工具描述、工具 schema 或 Manager 的确认文字。
- **文档与测试。**`docs/architecture/agent-system.md` 描述了该恢复逻辑，测试位于 `tests/test_service_upgrade_execution.py`，改动在 `looper/agents/service.py`。

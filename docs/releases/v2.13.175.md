# Looper v2.13.175

## Release Decision

**Who should upgrade:** Operators who use schedules with a gate command and rename a schedule or change its notifications while a gate runs. It is a hotfix that ships the change merged since v2.13.174.

**What this release solves:** [#777](https://github.com/foolzzz/looper/pull/777) separates a schedule's execution identity from its presentation settings, so a rename or a notification change no longer discards the output of a gate that is running. A real execution change still does, and the original execution snapshot stays recoverable.

**Breaking changes:** No. No command, API route or configuration format changed. The schema gains one nullable column, added with `ADD COLUMN IF NOT EXISTS`.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#777](https://github.com/foolzzz/looper/pull/777); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.175
```

## Behavior changes

- **Execution fingerprint ([#777](https://github.com/foolzzz/looper/pull/777)):** `fingerprint` in `looper/agents/schedule_templates.py` no longer hashes every schedule field. It hashes an explicit list of execution settings: manager, project, requirement, work dir, template key and inputs, profile overrides, task limits, gate command and timeout, run timeout mode and seconds, run and daily budgets, cron, timezone, overlap, max parallel runs and catch-up. Presentation settings such as the name and notifications, and the `enabled` flag, are outside it. The resolved template's `updated_at` is dropped, so restoring the same settings matches the earlier fingerprint.
- **Enabled state ([#777](https://github.com/foolzzz/looper/pull/777)):** since `enabled` left the fingerprint, `Scheduler._gate` takes the `enabled` value seen when the gate run was created and fails the run if the schedule was enabled or disabled before the gate started or while it ran.
- **Gate output kept ([#777](https://github.com/foolzzz/looper/pull/777)):** `_gate` now stores the gate's stdout in `gate_output` as soon as the gate finishes, before the configuration check. Before, it was stored only after the check passed, and a configuration change cleared it. A run that fails because the configuration changed now keeps its output.
- **Execution snapshot ([#777](https://github.com/foolzzz/looper/pull/777)):** a gating run records its fingerprint as the new `schedule_runs.execution_snapshot` JSONB column (schema `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`) when it is created. The run view returned by the schedules API gains an `execution_snapshot` field. Runs from before have `NULL`.
- **Carried input ([#777](https://github.com/foolzzz/looper/pull/777)):** `Scheduler._carried` now takes the schedule and skips an earlier unhanded run whose snapshot differs from the current execution fingerprint. Runs without a snapshot are still carried. The ownership and duplicate-consumption checks are unchanged. `_create_run` now computes the carried input inside its savepoint, and no longer clears `gate_output` on a configuration change.
- **Storage ([#777](https://github.com/foolzzz/looper/pull/777)):** `looper/db/schedules.py` serializes and parses `execution_snapshot` in `update_run`, `get_run`, `list_runs`, `latest_runs` and `unhanded_runs`.
- **Model-visible changes:** no prompt text, tool description or tool schema changed. The input a scheduled task receives can differ: gate output from a run made under a different execution configuration is no longer carried into the next task, and output saved before a rename now is.

## Upgrade and rollback

Re-run `install.sh` once v2.13.175 is published. The new column is added when the schema is applied. Rolling back to v2.13.174 leaves the column in place and unused.

## 中文摘要

### 升级决策

**谁需要升级：**使用带 gate 命令的 schedule，并在 gate 运行期间重命名 schedule 或修改通知设置的运维人员。本版本是随合并即发布的 hotfix。

**解决了什么：**[#777](https://github.com/foolzzz/looper/pull/777) 把 schedule 的执行身份与展示设置分开，重命名或修改通知不再丢弃正在运行的 gate 的输出；真正的执行配置变更仍会丢弃，且原始执行快照可恢复。

**是否有破坏性变更：**无。命令、API 路由和配置格式均未改变。数据库 schema 新增一个可空列（`ADD COLUMN IF NOT EXISTS`）。

**如何验证：**运行 `looper --version` 核对版本为 2.13.175。

**贡献者：**维护者 @foolzzz 提交 [#777](https://github.com/foolzzz/looper/pull/777)；本次 patch release 无社区贡献。

```bash
looper --version   # looper 2.13.175
```

### 行为变化与入口

- **执行指纹（#777）：**`schedule_templates.py` 的 `fingerprint` 不再哈希所有字段，只哈希明确列出的执行设置（manager、project、requirement、work dir、模板 key 与输入、profile 覆盖、任务限制、gate 命令与超时、运行超时、运行与每日预算、cron、时区、overlap、最大并行数、catch-up）。名称、通知等展示设置以及 `enabled` 不在其中；已解析模板的 `updated_at` 被忽略，恢复相同设置时指纹一致。
- **启用状态（#777）：**`enabled` 不再属于指纹，`Scheduler._gate` 记录 gate 运行创建时的 `enabled`，若在 gate 启动前或运行中被启用或停用，则该运行失败。
- **保留 gate 输出（#777）：**`_gate` 在 gate 结束后、配置检查之前就把 stdout 存入 `gate_output`。此前只在检查通过后才存，配置变更会清空它。因配置变更而失败的运行现在保留其输出。
- **执行快照（#777）：**gating 运行创建时把指纹记录到新列 `schedule_runs.execution_snapshot`（JSONB）。schedules API 的运行视图新增 `execution_snapshot` 字段。旧运行为 `NULL`。
- **携带输入（#777）：**`Scheduler._carried` 现在接收 schedule，跳过快照与当前执行指纹不同的未传递运行；没有快照的运行仍被携带。归属与重复消费检查不变。`_create_run` 在其 savepoint 内计算携带输入，配置变更时不再清空 `gate_output`。
- **存储（#777）：**`looper/db/schedules.py` 在 `update_run`、`get_run`、`list_runs`、`latest_runs`、`unhanded_runs` 中序列化并解析 `execution_snapshot`。
- **面向模型的变化：**没有 prompt 文本、工具描述或工具 schema 改动。定时任务收到的输入可能不同：在不同执行配置下产生的 gate 输出不再被带入下一个任务，而重命名之前保存的输出现在会被带入。

### 升级与回退

v2.13.175 发布后重新运行 `install.sh`，应用 schema 时会添加新列。回退到 v2.13.174 时该列保留但不再使用。

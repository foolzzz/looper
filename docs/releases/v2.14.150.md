# Looper v2.14.150

This is the patch release v2.14.150, a hotfix line in which each merged change ships at once. It documents one change: [#1267](https://github.com/foolzzz/looper/pull/1267) (a schedule can notify a group chat bound to a Manager).

## Release Decision

**Who should upgrade:** Operators who use scheduled tasks with notifications and want a schedule to tell a group chat that is bound to a Manager on the built-in Telegram or Lark bot, not only an allowlisted sender's direct chat. Everyone else gets no change except the two effects listed under Behavior changes.

**What this release solves:** [#1267](https://github.com/foolzzz/looper/pull/1267) makes chats explicitly bound to a Manager on a built-in channel valid schedule notify targets, sends notices to them through the binding's bot, and shows a saved target whose allowlist entry or binding was removed as unavailable instead of rerouting it.

**Breaking changes:** No. There is no migration and no API removal. One behavior is stricter: a saved notify target that is no longer offered now fails delivery (see Behavior changes). The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.14.150
```

**Contributors:** Maintainer @foolzzz authored [#1267](https://github.com/foolzzz/looper/pull/1267); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.149 upgrades directly. There is no schema change.

## Behavior changes

- **Bound chats are notify targets** ([#1267](https://github.com/foolzzz/looper/pull/1267), `looper/agents/schedules.py`, `looper/db/chat_bindings.py`, `docs/architecture/agent-system.md`). `notify_targets` now offers, besides allowlisted senders' direct chats, every chat explicitly bound to a non-deleted Manager on a built-in channel. Its label reads "<Telegram|Lark> · <chat name or id> (bound to <Manager name>)". A chat already offered as an allowlisted sender appears once. Creating or updating a schedule with such a chat is accepted; the "not one the channel allows" refusal now also says to bind the chat to a Manager.
- **Delivery through the binding's bot** (`looper/agents/channels/lark.py`, `looper/agents/gate_service.py`). A Lark notice to a native chat id (starting `oc_`) is sent to the chat; other Lark ids are still sent as direct messages. Gate prompts follow the same rule.
- **Removed target is unavailable, not rerouted** (`looper/agents/schedule_notify.py`, `looper/agents/schedules.py`). When a notice is due, the target is checked against the current offer. If its allowlist entry or binding was removed, the notice is recorded as failed ("the notification target is unavailable: its allowlist entry or chat binding was removed") and nothing is sent; the saved target is kept. This check also applies to allowlisted direct chats, which were not checked at delivery before. Every schedule view carries a new boolean `notify_target_available` (true when no target is set); the v1 schedule schema declares it, and the dashboard shows "(unavailable)" and a warning on the schedule and in the target picker.
- **Manager scope** (`looper/agents/ops/schedules.py`). A Manager whose scope is limited (scoped, or read-only on `looper_projects`) may select only chats bound to itself for create and update; any other target is refused with a forbidden error ("this Manager may notify only chats explicitly bound to itself"). A schedule a Manager creates from a chat message defaults its target to that chat only when it is among the targets that Manager may select. The dashboard and operator API may select any offered target. The comment in the code notes that tasks-only Managers cannot write schedules today.
- **Config import** (`looper/agents/config_transfer.py`). An imported schedule keeps its `notify_target` when the chat is allowlisted or bound on a built-in bot of the destination; otherwise it is dropped with a note, now pointing to binding the chat in Settings → Channels.
- **Unchanged:** the notice text, the `notify` modes, custom (added) bots, which are still never targets, and the handling of allowlisted senders' direct chats apart from the delivery check above.
- **Model-visible changes:** Yes, small. A Manager's schedule tools return the schedule view with the new `notify_target_available` field, the new refusal text for a target outside its own chats, and the changed validation message above; the target list a Manager can choose from includes bound chats with the labels above (chat and Manager names). The notice sent to the chat is not model input.

## 中文摘要

本版本是 patch release v2.14.150（热修线，每个合并的改动立即发布），说明一项改动：[#1267](https://github.com/foolzzz/looper/pull/1267)（定时任务可以通知绑定了 Manager 的群聊）。

### 升级决策

**谁需要升级：**使用带通知的定时任务，并希望通知发到内置 Telegram 或飞书机器人上绑定了 Manager 的群聊（而不只是白名单发送者的私聊）的运维者。其他人除“行为变化”中的两点外没有变化。

**解决了什么：**[#1267](https://github.com/foolzzz/looper/pull/1267) 让在内置通道上明确绑定了 Manager 的聊天成为有效的定时任务通知目标，经绑定所用的机器人发送，并把白名单条目或绑定已被移除的已存目标显示为不可用，而不是改投别处。

**是否有破坏性变更：**否。没有迁移，没有移除 API。有一处更严格：已存的通知目标不再被提供时，投递会失败（见行为变化）。桥接边界不变：早于 v2.13.165 的安装须先升级到 v2.13.165。

**如何验证：**核对版本为 2.14.150。

**贡献者：**维护者 @foolzzz 提交 [#1267](https://github.com/foolzzz/looper/pull/1267)；本版本无社区贡献。

```bash
looper --version   # looper 2.14.150
```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.149 上的安装可直接升级。没有结构变更。

### 行为变化与入口

- **绑定的聊天成为通知目标**（[#1267](https://github.com/foolzzz/looper/pull/1267)，`looper/agents/schedules.py`、`looper/db/chat_bindings.py`、`docs/architecture/agent-system.md`）。`notify_targets` 除白名单发送者的私聊外，现在还提供内置通道上明确绑定到未删除 Manager 的聊天，标签为“<Telegram|Lark> · <聊天名或 id>（bound to <Manager 名>）”。已作为白名单发送者出现的聊天只出现一次。用这类聊天创建或更新定时任务会被接受；“通道不允许该聊天”的拒绝信息现在也提示可把聊天绑定到 Manager。
- **经绑定的机器人投递**（`looper/agents/channels/lark.py`、`looper/agents/gate_service.py`）。飞书通知若发往原生聊天 id（以 `oc_` 开头）则发到该聊天，其他飞书 id 仍按私聊发送；Gate 提示遵循同一规则。
- **被移除的目标显示为不可用，不改投**（`looper/agents/schedule_notify.py`、`looper/agents/schedules.py`）。通知到点时，会按当前可选目标核对。若其白名单条目或绑定已被移除，该通知记为失败（“the notification target is unavailable: its allowlist entry or chat binding was removed”），不发送；已存目标保留。此检查也适用于白名单私聊（此前投递时不检查）。每个定时任务视图新增布尔字段 `notify_target_available`（未设目标时为 true），v1 schema 已声明；控制台在任务详情和目标选择器中显示“(unavailable)”和警告。
- **Manager 范围**（`looper/agents/ops/schedules.py`）。范围受限的 Manager（scoped，或对 `looper_projects` 只读）创建和更新时只能选择绑定到自己的聊天，其他目标被以 forbidden 错误拒绝（“this Manager may notify only chats explicitly bound to itself”）。Manager 在聊天中创建定时任务时，仅当来源聊天在其可选目标中才默认作为通知目标。控制台和运维 API 可选任何被提供的目标。代码注释说明仅任务范围的 Manager 目前不能写定时任务。
- **配置导入**（`looper/agents/config_transfer.py`）。导入的定时任务在聊天已在目标机器内置通道白名单中或已绑定时保留 `notify_target`，否则丢弃并附说明，说明现在提示到设置 → 通道中绑定聊天。
- **不变：**通知文本、`notify` 模式、自定义（新增）机器人仍不能作为目标，以及除上述投递检查外对白名单私聊的处理。
- **面向模型的变化：**有，较小。Manager 的定时任务工具返回的视图带新字段 `notify_target_available`，目标超出自身聊天时有新的拒绝文本，校验信息有变化；Manager 可选的目标列表包含带上述标签（聊天名和 Manager 名）的绑定聊天。发到聊天的通知不是模型输入。

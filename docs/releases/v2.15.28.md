# Looper v2.15.28

This release documents the changes merged since the v2.15.27 tag. That tag is on its release commit (`d14f14bcf`), so this range also contains pulls that merged after the v2.15.27 scope freeze (`6613380fa`) but are not on that tag ([#1531](https://github.com/foolzzz/looper/pull/1531), [#1549](https://github.com/foolzzz/looper/pull/1549), [#1575](https://github.com/foolzzz/looper/pull/1575), [#1583](https://github.com/foolzzz/looper/pull/1583), [#1585](https://github.com/foolzzz/looper/pull/1585), [#1588](https://github.com/foolzzz/looper/pull/1588), [#1591](https://github.com/foolzzz/looper/pull/1591)). They ship here, with full notes. The v2.15.27 release pull request ([#1601](https://github.com/foolzzz/looper/pull/1601)) is not a change in this release. The headline is a confirmed memory write into the vault ([#1531](https://github.com/foolzzz/looper/pull/1531), `memory_write`, still absent until saved) and operator direct-chat pushes of those candidates ([#1583](https://github.com/foolzzz/looper/pull/1583), the same object, and only when `enabled` is true and `push_channel` is set). A weekday morning brief can go to the operator's direct chat ([#1549](https://github.com/foolzzz/looper/pull/1549), `morning_brief.enabled`, default off). An event-triage subscription can run and store message outcomes ([#1575](https://github.com/foolzzz/looper/pull/1575), `subscriptions.triage.enabled`, still off). A pending intent whose pushes failed now expires, and its final notice is retried ([#1585](https://github.com/foolzzz/looper/pull/1585), `intents.enabled` unchanged). Tests and CI only: [#1588](https://github.com/foolzzz/looper/pull/1588), [#1591](https://github.com/foolzzz/looper/pull/1591), [#1593](https://github.com/foolzzz/looper/pull/1593), [#1603](https://github.com/foolzzz/looper/pull/1603), [#1604](https://github.com/foolzzz/looper/pull/1604), [#1606](https://github.com/foolzzz/looper/pull/1606), [#1607](https://github.com/foolzzz/looper/pull/1607), [#1608](https://github.com/foolzzz/looper/pull/1608), [#1619](https://github.com/foolzzz/looper/pull/1619). This release is frozen at `1a9c4285e`. Pull requests merged into main after that commit are not in this release.

No new switch in this release defaults to on. With every new switch left off, startup still applies three additive migrations and no new online step, starts the memory-writer loop (10 seconds), the memory-push loop (10 seconds) and the morning-brief loop (30 seconds), and each of those returns after reading its switch. Housekeeping deletes `proactive_deliveries` older than 90 days even while metrics are off. An existing triage subscription still ends `skipped_gate` and does not move its cursor. Creating one is refused. While `intents.enabled` is not the string `true`, stuck intents do not expire, and the new `intent_final_notices` table stays empty. Nothing new is added to configuration export. No code in this release drafts a memory candidate.

## Release Decision

**Who should upgrade:** Anyone who will turn on memory writing, memory pushes, the morning brief or event-triage runs, and anyone who already has `intents.enabled` set to the string `true` or who already stores triage subscriptions. An installation that turns none of the new switches on still applies three additive migrations at startup, starts three idle loops, and deletes proactive-delivery rows older than 90 days even while metrics are off. `web/` changed, so the dashboard bundle is rebuilt by the release workflow as usual.

**What this release solves:** A memory candidate the operator has already confirmed can be committed into the knowledge vault, and, once a push channel is set, pushed to that operator's direct chat for `记`, `驳回` or `重试`. A weekday morning brief can collect what is waiting, that day's reminders, and messages already held for the digest. An event-triage subscription can store per-message outcomes while its switch is on. A pending intent no longer stays pending forever after a failed push: it expires 24 hours after creation, and the final notice is retried. None of the new switches turns itself on.

**Breaking changes:** No. No existing API drops a field that a caller must send. There are three additive PostgreSQL migrations and no new online step. While `intents.enabled` is already the string `true`, a pending intent with a null `expires_at` expires on the next expiry pass from its creation time, and the operator may receive one delayed expiry reply. The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older. New operator operations include `memory.list`, `memory.get`, `memory.confirm`, `memory.confirm_many`, `memory.reject`, `memory.edit`, `memory.retry`, `memory.revive`, `memory.delete`, `memory.settings_get`, `memory.settings_put`, `memory.check`, `morning_brief.get` and `morning_brief.update`.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.15.28
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.15.27 upgrades directly. Restart the service after upgrading, as for every release. `web/` changed (the project-schedules triage preset), so the release workflow rebuilds the dashboard bundle from `web/` into the wheel, as usual. This pull request does not commit that bundle. The wheel now depends on PyYAML 6.x, used when a memory write parses note frontmatter. The off path does not import it.

On an upgrade from v2.15.27, startup applies three new migrations, once, inside the schema transaction, in `(order, name)` order. None of them defines an online step, so this release adds none. A step whose marker is already recorded is skipped: v2.15.27's online steps do not run again once their markers exist. A database that has not yet finished an earlier online step still runs that step. `gateway_aliases` is still absent from admission probes. A fresh database creates the same objects from `schema.sql` plus each module's `fresh_ddl` and does not record a separate migration for a table that DDL already created. `schema.sql` itself changes only the comment on `intents.expires_at`. No migration rewrites a row. No new seed row is inserted.

The three that run, in apply order:

- `intent_final_notices` ([#1585](https://github.com/foolzzz/looper/pull/1585)), order 700. Pending when its marker is absent and `intent_final_notices` does not exist. `apply` runs the DDL and inserts the marker. The table is `push_id` (primary key, references `intent_posts` on delete cascade), `handled_at`, `final_post_id` (references `intent_posts` on delete set null), `state` default `pending` and checked in `pending`, `sent`, `failed`, `attempts` default 0, `next_attempt_at`, `failure_reason` checked in `final_notice_retry_exhausted` and required exactly when `state` is `failed`, and `updated_at`. Index `idx_intent_final_notices_failed` is on `updated_at` where `state` is `failed`, created in the same transaction, not as an online step. No online step.
- `morning_brief_kind` ([#1549](https://github.com/foolzzz/looper/pull/1549)), order 720. Pending when `proactive_deliveries` exists and the single-column check on `source` does not contain `morning_brief`. If that table is absent, this module is not pending (the earlier migration creates the table). `apply` drops that check when its name is a plain identifier, adds `proactive_deliveries_source_check` as `NOT VALID`, then `VALIDATE CONSTRAINT` in the same schema transaction. That validation is not an online step. The allowed sources are `task_notice`, `completion`, `progress`, `gate`, `gate_reminder`, `subscription`, `intent`, `schedule`, `advisor_alert`, `autonomous`, `user_reminder` and `morning_brief`. The marker is recorded only when the database state is not empty. No row rewrite. No online step.
- `morning_briefs` ([#1549](https://github.com/foolzzz/looper/pull/1549)), order 730. Pending when `morning_briefs` is absent and the marker is absent, or when the table exists but `consumed_until`, `read_ids` or `morning_brief_consumed` is missing. A marker without the table is left alone. `apply` creates `morning_briefs` (primary key `local_date`, `channel_id`, `chat`; `status` in `sending`, `sent`, `skipped`, `uncertain`, `failed`; `attempts` at least 0; `detail` null or at most 500 characters; `consumed_until`; `read_ids` `BIGINT[]` not null default `'{}'`) and `morning_brief_consumed` (`delivery_id` primary key, references `proactive_deliveries` on delete cascade). No online step.

[#1531](https://github.com/foolzzz/looper/pull/1531), [#1583](https://github.com/foolzzz/looper/pull/1583) and [#1575](https://github.com/foolzzz/looper/pull/1575) add no schema. [#1588](https://github.com/foolzzz/looper/pull/1588), [#1591](https://github.com/foolzzz/looper/pull/1591), [#1593](https://github.com/foolzzz/looper/pull/1593), [#1603](https://github.com/foolzzz/looper/pull/1603), [#1604](https://github.com/foolzzz/looper/pull/1604), [#1606](https://github.com/foolzzz/looper/pull/1606), [#1607](https://github.com/foolzzz/looper/pull/1607), [#1608](https://github.com/foolzzz/looper/pull/1608) and [#1619](https://github.com/foolzzz/looper/pull/1619) add no schema.

What is visible while every new switch stays off: those three migrations still run, and no new online step runs; the memory writer, the memory push and the morning brief each start a loop and stop after reading an off switch; housekeeping deletes `proactive_deliveries` rows older than 90 days whether or not metrics are on; a triage subscription that already exists ends `skipped_gate` with the error `subscriptions.triage.enabled is off` and does not move its cursor; creating a triage subscription is HTTP 400 with `cannot create a triage subscription: subscriptions.triage.enabled is off`; `intent_final_notices` exists and stays empty, and intents do not expire, while `intents.enabled` is not the string `true`; configuration export still carries `settings.system` as `manager.persona` only and `settings.chat` as `metrics_enabled` only. `memory_write`, `morning_brief.enabled` and `morning_brief.time` are not exported.

## Behavior changes

### Memory write, off, and nothing is drafted ([#1531](https://github.com/foolzzz/looper/pull/1531))

v2.15.26 stored `memory_write` and did not write a candidate. This release commits a vault candidate that is already `confirmed`. No code path in this release inserts a candidate. Saving `sources` does not start drafting from the Manager, from tasks or from leads.

- **`memory_write` is absent until set, and absent means off.** It is one JSON object. `enabled` defaults to false and must be a real boolean, not the string `true`. `root` is required: a folder relative to the knowledge vault, or `''` for the vault itself. It must not overlap a writable folder. `rules_files` defaults to none and holds at most 3 vault-relative Markdown paths. `targets` defaults to none. `required_frontmatter` defaults to none and holds at most 20 plain names. `sources` defaults to `manager`, `tasks` and `leads` all false. `branch` is optional; when set it must be the main checkout's current branch, and a save stores that branch. `worktree_root`, when set, is an absolute path outside the vault. `commit_prefix` is at most 40 characters and is derived when omitted. `push_channel` is null until set: one line, 1 to 200 characters, an enabled Lark or Telegram bot whose operator target is a direct chat. `pending_days` defaults to 7, a whole number from 1 to 90. `draft_budget_usd` defaults to 0.15, above 0 and at most 10. `daily_budget_usd` defaults to 1.00, above 0 and at most 100. Unknown keys are refused. An unreadable stored value is treated as off (`enabled` is not true).
- **Clearing deletes the row.** `memory.settings_put` with a body that is only `{"root": null}` deletes the `memory_write` row. Any other body is checked against the vault, git and the push channel before it is stored. Only the operator can call `memory.settings_get`, `memory.settings_put` and `memory.check`. Configuration export leaves the key out. It is not a new export key.
- **While it is off,** the service still constructs `MemoryWriteService` and starts it. Every 10 seconds `run_once` reads `memory_write` and returns before the advisory lock. There is no filesystem inspection, no git, no cleanup and no candidate transition. `memory.check` and every write action refuse with `memory writing is not enabled` (code `disabled`) and do not open the vault or write a candidate row. `looper memory list`, `show` and `check` still read; `reject`, `retry` and `delete` refuse while the switch is off.
- **While `enabled` is true,** the writer claims one `confirmed` vault candidate, commits it, and cleans up memory branches and worktrees that this writer owns. An interrupted `writing` row is recovered: a matching commit finishes as `written`; otherwise, while `attempts` is below 3, it returns to `confirmed`; at 3 it becomes `blocked` with reason `interrupted`. A conflict clears the confirmation and queues at most one system redraft. `blocked` keeps the confirmation and waits for `retry`. This release still does not draft a new candidate, so an empty candidate table writes nothing.
- **Delete leaves a tombstone and keeps the vault note.** `memory.delete`, and `looper memory delete`, are dashboard or CLI only. The candidate's revisions, events, posts and sources go with it. `memory_tombstones` keeps `fingerprint`, `kind`, `destination` and `deleted_via`. A candidate in `writing` or `in_effect` is refused (code `state`). A later seed of the same fingerprint is refused with `the operator deleted this memory before` (code `tombstoned`), unless the seed's source class is the operator's own, which deletes that tombstone instead. `clear_tombstones` deletes every tombstone. There is no direct-chat delete command.
- **Operator operations.** `memory.list`, `get`, `confirm`, `confirm_many`, `reject`, `edit`, `retry`, `revive`, `delete`, `settings_get`, `settings_put` and `check` are operator-only. `confirm`, `confirm_many` and `edit` are not on the generated CLI (`looper memory` has `list`, `show`, `check`, `reject`, `retry` and `delete`). `edit` and `revive` are dashboard only. A reject reason is at most 300 characters. Confirmation binds the displayed content hash. Save-and-confirm is one transaction. An API client token cannot call these operations. `web/` does not add a memory page in this release.

### Memory push and direct-chat replies, off until a channel is set ([#1583](https://github.com/foolzzz/looper/pull/1583))

Same `memory_write` object. Pushes call the channel registry directly. They do not go through proactive delivery, and this pull request does not add a memory source to `proactive_deliveries`.

- **Inactive unless `enabled` is true and `push_channel` is set.** No row, unreadable JSON, `enabled` not the boolean true, or a missing `push_channel`, leaves both the push loop and the reply router inactive. The service still starts `MemoryPushService`. Every 10 seconds `run_once` reads the setting through `target_for` and returns before a candidate query or a channel call. `route` returns after that same read and does not load the vault or inspect the message, a post or a channel. A memory command is therefore an ordinary message while the pair is unset, and the model sees it.
- **While both are set,** a `pending` vault candidate can be pushed to that bot's operator direct chat. The Manager calls the router before the model, so a matching command is not shown to the model. Commands are `记 M-…` (one or more ids), `驳回 M-…` with an optional reason of 1 to 300 characters, and `重试 M-…`. An id is `M-` or `m-` plus 1 to 18 digits. Quoting a push and replying exactly `记` confirms that candidate. Quoting it and replying `驳回`, with an optional reason, rejects it. There is no delete command.
- **Replies, as the code sends them.** A non-operator, a group, an unsupported channel, a Lark chat whose type is not `p2p`, a missing chat or message id, or a quoted post whose chat is not the operator chat: `记忆候选只能由你本人在私聊或记忆页处理`. Text that claims the grammar and does not fully match: `请回复「记 M-0042」「驳回 M-0042 [理由]」或「重试 M-0042」`. No such candidate: `没有 {label} 这条记忆候选`. Already written: `{label} 已写入`. Already rejected: `{label} 已驳回`. Already confirmed or writing: `{label} 已确认，写入后通知你`. Confirming an expired candidate: `{label} 已过期，请到记忆页恢复：` plus the dashboard link. A push whose hash or revision no longer matches: `{label} 在推送后改过，请看最新的推送`. Before confirm, the problem is one of `尚未在此私聊推送`, `推送送达情况不明`, `推送失败`, `推送尚未完成` or `内容较长`, then `，请到记忆页确认：` plus the link. Any other refusal: `{label} 当前不能处理，请到记忆页查看：` plus the link. After confirm or retry the router waits 20 seconds. If the candidate is not yet in a finished state, the reply is again `{label} 已确认，写入后通知你`. Finished replies use the push module's text: written is `✅ {label} 已写入 {path}（commit {sha}）` (the path or `记忆区`, the sha's first 8 characters); blocked is `⚠️ {label} 写入受阻：{reason}。处理后回「重试 {label}」`; a redraft is `⚠️ {label} 已重新起草，请看最新推送并重新确认`; conflict or drafting is `⚠️ {label} {reason}，请查看新版本并重新确认`; rejected is `❌ {label} 已驳回`; expired is `⌛ {label} 已过期`; dropped is `❌ {label} 未写入，请到记忆页查看：` plus the link. The link is the service dashboard origin plus `/#/memory?candidate={label}`. This release does not add that page.
- **The push text** tells a complete candidate to reply `记` or `记 {label}` to write, and `驳回 {label}` to reject, and names `pending_days`. An incomplete push says `内容较长，请到记忆页确认` and still offers reject. Warnings that can appear are `来自飞书消息，未经确认`, `来源里有要求助手做事的话`, `会删掉这篇笔记 N 行`, and `这条像是每次都要遵守的硬规则：可能还要写进全局指令（Looper 不写）`.

### Morning brief, off ([#1549](https://github.com/foolzzz/looper/pull/1549))

- **`morning_brief.enabled` defaults off.** Only the stored string `true` turns it on. No row, the string `false`, or any other value, is off. A failed read stays off. `morning_brief.time` defaults to `09:15` and must match `HH:MM` (00:00 through 23:59). An unreadable stored time falls back to `09:15` at load. Only the operator can call `morning_brief.get` and `morning_brief.update` (level inside; the update is high risk and confirms). `null` for `enabled` deletes that key and restores off. `null` for `time` deletes that key and restores `09:15`. A field left out of the body keeps its stored value. An empty body is refused. An unknown key is refused. The two keys are not part of the chat-settings payload clients see, are not listed as a new export key, and are not written by configuration import. `false` stores the string `false`.
- **While it is off,** `MorningBriefService` still starts. Every 30 seconds `run_once` reads the in-memory switch and returns before it acquires a database connection. No skip row is written, and no channel is called. The two migrations still apply, and the widened source check still names `morning_brief`.
- **While it is on,** one post goes to each enabled `telegram`, `lark` or `lark_bot` that has an operator direct chat, on a workday (Monday to Friday; a weekday holiday still sends; Saturday and Sunday send nothing), at or after `morning_brief.time` in `user.timezone` when that zone is set, otherwise the server zone. A skipped clock minute is due on the first tick after the gap. A repeated hour is the same local date, so the row sends once. Monday's first window also includes Saturday and Sunday. The title is `晨报 · {mm-dd}（周{一二三四五六日}）`. Sections are the needs-you summary (the sentence `现在没有需要你处理的事。` is not a section; a section that could not be read is), reminders due that local day, and proactive deliveries whose decision is `digest`. Every section empty stores a skip `nothing to say` and sends nothing. No operator direct chat stores a skip `no operator direct chat` and sends nothing. Another server holding advisory lock `(741926, 1)` makes the tick return. The switch, the channel and the operator are read again after the summary and immediately before the post, and the switch once more after the operator query. A fresh claim that then fails is deleted, so turning the brief back on can still send that day. A claim that continued a refusal is put back as that refusal. Three refusals (`failed`) are left failed. `uncertain` is not retried. `delivery.enabled` must be the string `true` before a `proactive_deliveries` row is written, under the key `morning_brief:{local date}:{channel_id}:{chat}`, decision `send`. The post itself is sent uncounted: quiet hours and the daily cap do not hold it. If that decision write throws, the brief still sends. A sent or uncertain settle records the digest ids it read into `morning_brief_consumed` and sets `consumed_until` to the check time, which is not a watermark. A refusal records none of those ids. A crash before settle marks the row `uncertain` and consumes exactly the stored ids. This brief does not consume triage digest events. There is no dashboard page, no Telegram command and no CLI hand command for it.
- **Housekeeping, whether or not the brief or metrics are on.** The 90-day purge of `proactive_deliveries` no longer waits for `manager.metrics.enabled`. It loops until a purge returns 0. With every switch off the table may be empty; the step still runs.

### Event triage runs, off until the existing switch is on ([#1575](https://github.com/foolzzz/looper/pull/1575))

v2.15.27 added the tables and the switch and did not run a processor. This release runs one. The architecture section "Event triage foundation" still describes that tables-only state, including "execution is not available". The run is the RFC section linked under Optional Capability Activation. No new setting and no new migration. No real-model eval was run for this release.

- **`subscriptions.triage.enabled` is unchanged and stays off.** Only the string `true` turns it on. No row, or any other value, leaves it off. `triage_settings.update` with `null` deletes the row. Only the operator can call `triage_settings.get` and `triage_settings.update`. It is not a new export key.
- **While it is off,** `extraction.plan` returns `subscriptions.triage.enabled is off` before it reads a window. The firing is `skipped_gate` with that error and does not move the cursor. No processor starts and no `triage_events` row is written. Creating a subscription whose `output_kind` is `triage` raises `cannot create a triage subscription: subscriptions.triage.enabled is off`, returned as HTTP 400. The dashboard hides the `事件分流` preset unless `triage_settings.get` reports the switch on. An existing triage subscription can still be renamed or reconfigured; the create-time check is the one that refuses a new one.
- **While it is on,** a subscription runs only while its confirmation still holds (`target_confirmed_at` set and `target_confirmed_version` equal to the current config version). Otherwise the firing is `skipped_gate` with `not confirmed: confirm the subscription to start extracting`, and the cursor stays. An empty window advances the cursor and is `skipped_gate` with no processor. A window that stays unreadable, or that a prompt hook blocks, is skipped and the cursor advances; a skipped triage window also stores the selected seqs. Losing the confirmation, or a processor failure, leaves the cursor where it was. Uncited messages have no event row; they count as ignore. A parsed `NONE` records the whole window as ignored, writes no individual rows, and reports uncited as 0. Important events keep a null `manager_event_id`. This run writes no `manager_events` and does not enqueue work. Digest events are stored and are not read by the morning brief in this release. The dashboard confirmation copy says the result is stored and not sent.

### Intent expiry after a failed push, not a new switch ([#1585](https://github.com/foolzzz/looper/pull/1585))

- **`intents.enabled` is unchanged.** Only the string `true` turns intents on. No row leaves them off. No new setting, no prompt change and no model-contract change. While intents are off, `IntentPushService.run_once` and `expire` return immediately. The migration still creates the empty `intent_final_notices` table. Stuck intents do not expire and no final notice is sent.
- **While intents are on,** a pending intent is due when `expires_at`, or `created_at` plus 24 hours when `expires_at` is null, is at or before now. The expiry pass runs every 300 seconds (the push loop still ticks every 10 seconds). On the way through a pending intent whose `expires_at` is null, the service sets `expires_at` to `created_at` plus 24 hours. A successful push or progress, while the intent is still pending, sets `expires_at` to 24 hours after that send. A pending intent that never had a successful push therefore expires 24 hours after it was created. On an upgrade, previously stuck pending intents expire on the next pass. There is no manual backfill and no row rewrite inside the migration. The operator may receive one delayed expiry reply. The final card text for that state is `⌛ {id} 已过期（没有处理） · {name}`.
- **Final notices are retried on their own table.** For a `tasked`, `rejected` or `expired` intent that has a sent push to the current confirmed operator direct chat, the service owns a bounded retry. Three delivery attempts. The delay is 30 seconds, doubled, and capped at 300 seconds (30, then 60, then the cap). The attempt count is stored before the send. An invalid target defers `next_attempt_at` and does not spend an attempt. Exhaustion sets `state` to `failed` and `failure_reason` to `final_notice_retry_exhausted`. An uncertain delivery is not resent; retrying the idempotent edit can still repair the notice. The edit of the original push is tried first; on failure a `kind` `final` post is inserted and delivered. An `expired` to `tasked` transition starts a new notice (attempts back to 0). An older failed expiry reply cannot replace that new task status. A legacy row that set `edited_at` even on failure is adopted once, including one whose earlier retries were already exhausted, into a fresh budget of 3. A legacy final that already succeeded is left completed. Groups stay refused. The target stays the currently confirmed operator direct chat.

### Tests and CI only

## Optional Capability Activation & Use

### Memory write

**Activation:** Off until the operator stores `memory_write` with `enabled` true. The value is one JSON object, not the string `true`. `root` is required (`''` is the whole vault). Defaults inside that object: `pending_days` 7, `draft_budget_usd` 0.15, `daily_budget_usd` 1.00, and `sources.manager`, `sources.tasks` and `sources.leads` false. Set it as the operator through `POST /api/v1/memory/settings_put`. A body that is only `{"root": null}` deletes the row. Saving it does not draft a candidate. The writer commits a candidate that is already confirmed. An API client token gets 403.

**Validation:** With the row absent, `POST /api/v1/memory/settings_get` reports `configured` false and `enabled` false, and `POST /api/v1/memory/check` does not touch the vault. With `enabled` true, `looper memory check` reports the git and worktree checks, and a confirmed vault candidate is claimed by the writer. With `enabled` false, a write action returns `memory writing is not enabled`.

**Disable / rollback:** `POST /api/v1/memory/settings_put` with `{"root": null}` deletes the setting. The next writer pass reads the absent row and does not commit. Notes already written stay in the vault. Deleting a candidate (`POST /api/v1/memory/delete` or `looper memory delete M-0042`) removes the candidate and leaves its fingerprint tombstone; it does not delete the vault note, and it is refused while the candidate is `writing` or `in_effect`.

**Authority boundary:** Operator only. `memory.confirm`, `memory.edit` and `memory.revive` are dashboard only. Direct chat can confirm, reject and retry once Memory push is active, and cannot delete. `looper memory` can list, show, check, reject, retry and delete, and cannot confirm. Disabled actions do not open the vault.

**Docs:** https://github.com/foolzzz/looper/blob/v2.15.28/docs/architecture/agent-system.md#memory-candidates-what-looper-may-write-to-the-vault-once-confirmed

```bash
looper memory check
```

### Memory push

**Activation:** Off until `memory_write.enabled` is true and `memory_write.push_channel` is a non-empty line of at most 200 characters naming an enabled Lark or Telegram bot whose operator target is a direct chat. Set both through `POST /api/v1/memory/settings_put` as the operator. There is no separate system key. Pushes do not go through proactive delivery.

**Validation:** While `push_channel` is null, a direct-chat `记 M-0042` is an ordinary message. While both are set, that reply is handled before the model. A complete push says to reply `记` or `驳回`. A candidate that does not exist gets `没有 M-0042 这条记忆候选` (the id in the reply is the one that was named). A group or another sender gets `记忆候选只能由你本人在私聊或记忆页处理`.

**Disable / rollback:** Set `push_channel` to null in `memory.settings_put`, or delete the whole setting with `{"root": null}`. The next push pass and the next message both stop after one settings read. Candidates already `confirmed` can still be written while `enabled` stays true; clearing `enabled` stops the writer too.

**Authority boundary:** The verified operator, in that bot's direct chat only. A Lark chat whose type is not `p2p` is refused. Delete, edit and revive are not direct-chat commands. An API client token cannot call the memory operations.

**Docs:** https://github.com/foolzzz/looper/blob/v2.15.28/docs/architecture/rfcs/memory-write-path-v0.zh-CN.md#53-私聊推送和回复

```bash
looper memory list --state open
```

### Morning brief

**Activation:** Off until the system setting `morning_brief.enabled` is the string `true`. No row, or any other value, leaves it off. `morning_brief.time` defaults to `09:15`. Set them as the operator through `POST /api/v1/morning_brief/update` with `enabled` true and an optional `time` of `HH:MM`. `null` restores that field's default. The update confirms. An API client token gets 403. The keys are not in the chat-settings payload and are not in configuration export.

**Validation:** While off, a workday at 09:15 sends nothing and writes no `morning_briefs` row. While on, one enabled bot with an operator direct chat gets one brief per local workday, titled `晨报 · {mm-dd}（周…）`, or a skip `nothing to say` when every section is empty. Saturday and Sunday send nothing. A second server does not send a second copy.

**Disable / rollback:** `POST /api/v1/morning_brief/update` with `enabled` null, or `enabled` false. `null` deletes the key and restores off. `false` stores the string `false`. The next tick reads the in-memory switch and does not open a database connection. Rows already sent stay sent. `time` null restores `09:15`.

**Authority boundary:** Operator only. `morning_brief.get` is read, level inside. `morning_brief.update` is high risk and confirms. There is no dashboard switch, no Telegram command and no CLI hand command. The post goes only to an enabled bot's operator direct chat.

**Docs:** https://github.com/foolzzz/looper/blob/v2.15.28/docs/architecture/agent-system.md#morning-brief

```bash
looper --version
```

### Event triage runs

**Activation:** Off until the existing system setting `subscriptions.triage.enabled` is the string `true`. No row, or any other value, leaves it off. Set it as the operator through `POST /api/v1/triage_settings/update` with `enabled` true. `null` deletes the row. Then create a subscription with `output_kind` `triage` and confirm it. The dashboard shows `事件分流` only while the switch is on. An API client token gets 403 on the settings operations.

**Validation:** While off, creating a triage subscription returns HTTP 400 `cannot create a triage subscription: subscriptions.triage.enabled is off`. An existing one fires as `skipped_gate` with `subscriptions.triage.enabled is off` and does not move its cursor. While on, an unconfirmed subscription fires as `skipped_gate` with `not confirmed: confirm the subscription to start extracting` and does not move its cursor. A confirmed run stores `triage_events` for cited messages and does not send them.

**Disable / rollback:** `POST /api/v1/triage_settings/update` with `enabled` null, or `enabled` false. `null` deletes the row. The next firing is `skipped_gate`, the cursor stays, and no new event row is written. Events already stored remain. Creating a new triage subscription is refused again.

**Authority boundary:** Operator only for `triage_settings.get` and `triage_settings.update`. A run uses the subscription the operator confirmed. It does not enqueue a Manager event and it does not post to a chat. Scope is the subscription's own window: private chats, mentions, the operator's messages and registered alert bots, with no second model check in this release.

### 行为变化

#### 记忆写入，默认关闭，本版本不起草候选（[#1531](https://github.com/foolzzz/looper/pull/1531)）

v2.15.26 只保存 `memory_write`，不写入候选。本版本提交已经处于 `confirmed` 的知识库候选。本版本没有任何代码插入一条候选。保存 `sources` 不会从管家、任务或线索开始起草。

- **没有 `memory_write` 这一行就是关。** 它是一个 JSON 对象。`enabled` 默认 false，必须是布尔值，字符串 `true` 不算。`root` 必填：知识库内的相对目录，或 `''` 表示整个知识库，并且不能和可写目录重叠。`rules_files` 默认没有，最多 3 个知识库内的 Markdown 路径。`targets` 默认没有。`required_frontmatter` 默认没有，最多 20 个普通名字。`sources` 的 `manager`、`tasks`、`leads` 默认都是 false。`branch` 可选；设置时必须是主检出当前分支，保存时记下这个分支。`worktree_root` 若设置，必须是知识库之外的绝对路径。`commit_prefix` 最多 40 字，不给就派生。`push_channel` 在设置之前是 null：一行，1 到 200 字，一个已启用、操作者目标是私聊的 Lark 或 Telegram 机器人。`pending_days` 默认 7，1 到 90 的整数。`draft_budget_usd` 默认 0.15，大于 0 且最多 10。`daily_budget_usd` 默认 1.00，大于 0 且最多 100。未知键被拒绝。存下来的 JSON 读不出来就当作关（`enabled` 不是 true）。
- **清空会删掉这一行。** `memory.settings_put` 的正文若正好是 `{"root": null}`，就删除 `memory_write`。其他正文要先通过知识库、Git 和推送通道的检查才保存。只有操作者能调用 `memory.settings_get`、`memory.settings_put` 和 `memory.check`。配置导出不含这个键。它不是新的导出键。
- **关闭时，** 服务仍会构造并启动 `MemoryWriteService`。每 10 秒 `run_once` 读一次 `memory_write`，在咨询锁之前返回。不检查文件系统，不跑 Git，不做清理，也不改候选状态。`memory.check` 和每个写动作都拒绝，正文是 `memory writing is not enabled`（代码 `disabled`），并且不开知识库、不写候选行。`looper memory list`、`show`、`check` 仍能读；`reject`、`retry`、`delete` 在关闭时拒绝。
- **`enabled` 为 true 时，** 写入器领取一条 `confirmed` 的知识库候选并提交，并清理这个写入器自己的记忆分支和工作目录。被中断的 `writing` 行会恢复：找到对应提交就记为 `written`；否则在 `attempts` 小于 3 时回到 `confirmed`；到 3 次则成为 `blocked`，原因 `interrupted`。冲突会清掉确认，并最多排队一次系统重起草。`blocked` 保留确认，等 `retry`。本版本仍然不起草新候选，所以候选表是空的时候什么都不写。
- **删除留下墓碑，知识库里的笔记还在。** `memory.delete` 和 `looper memory delete` 只在仪表盘或命令行。候选的修订、事件、帖子和来源一起删掉。`memory_tombstones` 留下 `fingerprint`、`kind`、`destination` 和 `deleted_via`。状态是 `writing` 或 `in_effect` 的候选被拒绝（代码 `state`）。之后同样指纹的种子被拒绝，正文是 `the operator deleted this memory before`（代码 `tombstoned`）；来源类别是操作者自己的种子则改为删掉那条墓碑。`clear_tombstones` 删掉全部墓碑。私聊没有删除命令。
- **操作者操作。** `memory.list`、`get`、`confirm`、`confirm_many`、`reject`、`edit`、`retry`、`revive`、`delete`、`settings_get`、`settings_put` 和 `check` 只给操作者。`confirm`、`confirm_many` 和 `edit` 不在生成的命令行上（`looper memory` 有 `list`、`show`、`check`、`reject`、`retry`、`delete`）。`edit` 和 `revive` 只在仪表盘。驳回理由最多 300 字。确认绑定当时展示的内容哈希。保存并确认是同一个事务。API 客户端令牌不能调用这些操作。本版本的 `web/` 不加记忆页。

#### 记忆推送和私聊回复，要等通道设上（[#1583](https://github.com/foolzzz/looper/pull/1583)）

还是同一个 `memory_write` 对象。推送直接调通道注册表，不走主动投递，本拉取请求也不给 `proactive_deliveries` 加记忆来源。

- **`enabled` 不是 true，或没有 `push_channel`，就不活动。** 没有这一行、JSON 读不出来、`enabled` 不是布尔 true，或没有 `push_channel`，推送循环和回复路由都不活动。服务仍会启动 `MemoryPushService`。每 10 秒 `run_once` 经 `target_for` 读设置，在查询候选或调用通道之前返回。`route` 同一次读取之后就返回，不加载知识库，也不看消息、帖子或通道。这时一条记忆口令只是普通消息，模型看得到。
- **两者都设上之后，** `pending` 的知识库候选可以推到该机器人的操作者私聊。管家在模型之前调用路由，匹配的口令不会交给模型。口令是 `记 M-…`（一个或多个编号）、`驳回 M-…`（理由可选，1 到 300 字）和 `重试 M-…`。编号是 `M-` 或 `m-` 加 1 到 18 位数字。引用一条推送并只回 `记`，就是确认那一条。引用并回 `驳回`，理由可选，就是驳回。没有删除口令。
- **回复按代码原样发送。** 非操作者、群、不支持的通道、Lark 聊天类型不是 `p2p`、缺少聊天或消息编号，或引用的帖子不属于操作者的聊天：`记忆候选只能由你本人在私聊或记忆页处理`。口令像记忆命令但没有完全匹配：`请回复「记 M-0042」「驳回 M-0042 [理由]」或「重试 M-0042」`。没有这条候选：`没有 {label} 这条记忆候选`。已经写入：`{label} 已写入`。已经驳回：`{label} 已驳回`。已经确认或正在写入：`{label} 已确认，写入后通知你`。确认一条已过期的：`{label} 已过期，请到记忆页恢复：` 再加仪表盘链接。推送的哈希或修订已经对不上：`{label} 在推送后改过，请看最新的推送`。确认之前的问题是 `尚未在此私聊推送`、`推送送达情况不明`、`推送失败`、`推送尚未完成` 或 `内容较长` 之一，然后是 `，请到记忆页确认：` 再加链接。其他拒绝：`{label} 当前不能处理，请到记忆页查看：` 再加链接。确认或重试之后路由等待 20 秒。还没进入结束状态时，回复仍是 `{label} 已确认，写入后通知你`。结束回复使用推送模块的文本：写入是 `✅ {label} 已写入 {路径}（commit {sha}）`（路径或 `记忆区`，sha 前 8 位）；受阻是 `⚠️ {label} 写入受阻：{原因}。处理后回「重试 {label}」`；重新起草是 `⚠️ {label} 已重新起草，请看最新推送并重新确认`；冲突或起草中是 `⚠️ {label} {原因}，请查看新版本并重新确认`；驳回是 `❌ {label} 已驳回`；过期是 `⌛ {label} 已过期`；放弃是 `❌ {label} 未写入，请到记忆页查看：` 再加链接。链接是服务的仪表盘来源加上 `/#/memory?candidate={label}`。本版本不加这个页面。
- **推送正文** 对完整候选说回复 `记` 或 `记 {label}` 写入，回复 `驳回 {label}` 驳回，并写出 `pending_days`。不完整的推送说 `内容较长，请到记忆页确认`，同时仍可以驳回。可能出现的警告是 `来自飞书消息，未经确认`、`来源里有要求助手做事的话`、`会删掉这篇笔记 N 行`，以及 `这条像是每次都要遵守的硬规则：可能还要写进全局指令（Looper 不写）`。

#### 晨报，默认关闭（[#1549](https://github.com/foolzzz/looper/pull/1549)）

- **`morning_brief.enabled` 默认关闭。** 只有存下的字符串 `true` 才打开。没有这一行、字符串 `false` 或其他值都是关。读失败也保持关闭。`morning_brief.time` 默认 `09:15`，必须是 `HH:MM`（00:00 到 23:59）。存下来的时间读不出来，加载时退回 `09:15`。只有操作者能调用 `morning_brief.get` 和 `morning_brief.update`（级别 inside；更新是高风险，要确认）。`enabled` 为 null 就删掉这个键并恢复关闭。`time` 为 null 就删掉这个键并恢复 `09:15`。正文里没给的字段保持原值。空正文被拒绝。未知键被拒绝。这两个键不在客户端看到的聊天设置里，不是新的导出键，配置导入也不写它们。`false` 存下字符串 `false`。
- **关闭时，** `MorningBriefService` 仍会启动。每 30 秒 `run_once` 读内存里的开关，在取得数据库连接之前返回。不写跳过行，也不调用通道。两条迁移仍会执行，放宽后的 source 检查仍包含 `morning_brief`。
- **打开后，** 每个已启用、有操作者私聊的 `telegram`、`lark` 或 `lark_bot`，在工作日（周一到周五；工作日的假日仍会发；周六和周日不发）当地时间达到 `morning_brief.time` 时发一条。时区是已设置的 `user.timezone`，否则是服务器时区。被跳过的那一分钟在缺口后的第一次滴答补上。重复的那一小时仍是同一个本地日期，所以只发一次。周一的第一扇窗口还包括周六和周日。标题是 `晨报 · {mm-dd}（周{一二三四五六日}）`。各节是需要你处理的摘要（句子 `现在没有需要你处理的事。` 不算一节；没能读到的一节算）、当天到期的提醒，以及决定为 `digest` 的主动投递。每一节都空就记下跳过 `nothing to say`，不发送。没有操作者私聊就记下跳过 `no operator direct chat`，不发送。另一个服务器持有咨询锁 `(741926, 1)` 时这次滴答返回。摘要之后、发送之前会再读开关、通道和操作者，操作者查询返回后再读一次开关。这时检查失败的新领取会被删掉，所以当天重新打开仍能发。延续一次拒绝的领取会放回那次拒绝。三次拒绝（`failed`）就留在失败。`uncertain` 不重试。只有 `delivery.enabled` 是字符串 `true` 时才写 `proactive_deliveries` 行，键是 `morning_brief:{本地日期}:{channel_id}:{chat}`，决定是 `send`。帖子本身不计次：免打扰和每日上限都不拦住它。那次决定写入抛错时，晨报仍发送。送达或不确定的结算把读到的摘要编号记入 `morning_brief_consumed`，并把 `consumed_until` 设为检查时间，它不是水位。拒绝不记这些编号。结算前崩溃把行标成 `uncertain`，并且只消费当时存下的编号。这份晨报不消费分流的摘要事件。没有仪表盘页面，没有 Telegram 命令，也没有命令行手动发送。
- **清理与晨报或度量是否打开无关。** `proactive_deliveries` 超过 90 天的清除不再等 `manager.metrics.enabled`。它一直删到某次返回 0。开关都关闭时这张表可以是空的；这一步仍会跑。

#### 事件分流运行，既有开关仍默认关闭（[#1575](https://github.com/foolzzz/looper/pull/1575)）

v2.15.27 加了表和开关，不跑处理器。本版本会跑。架构文档里的「Event triage foundation」仍写着只有表、执行还不可用。运行的说明是下面可选能力一节链到的 RFC。没有新设置，没有新迁移。本版本没有做真实模型评测。

- **`subscriptions.triage.enabled` 不变，仍默认关闭。** 只有字符串 `true` 才打开。没有这一行或其他值都是关。`triage_settings.update` 传 `null` 就删掉这一行。只有操作者能调用 `triage_settings.get` 和 `triage_settings.update`。它不是新的导出键。
- **关闭时，** `extraction.plan` 在读窗口之前返回 `subscriptions.triage.enabled is off`。这次触发是 `skipped_gate`，错误就是这句，游标不动。不启动处理器，也不写 `triage_events` 行。创建 `output_kind` 为 `triage` 的订阅会抛出 `cannot create a triage subscription: subscriptions.triage.enabled is off`，作为 HTTP 400 返回。仪表盘在 `triage_settings.get` 报告开关打开之前不显示「事件分流」预设。已经存在的分流订阅仍可改名或改配置；拒绝新建的是创建时的那次检查。
- **打开后，** 只有确认仍然有效才运行（`target_confirmed_at` 已设，且 `target_confirmed_version` 等于当前配置版本）。否则这次触发是 `skipped_gate`，错误是 `not confirmed: confirm the subscription to start extracting`，游标不动。空窗口会推进游标，并记为 `skipped_gate`，不启动处理器。两次都读不出来、或被提示词钩子拦住的窗口会跳过并推进游标；跳过的分流窗口还会存下选中的 seq。确认丢失或处理器失败时游标留在原地。未被引用的消息没有事件行，按忽略计数。解析出的 `NONE` 把整个窗口记为忽略，不写单行，未引用计数为 0。重要事件的 `manager_event_id` 保持 null。这次运行不写 `manager_events`，也不把工作排进队列。摘要事件只存储，本版本的晨报不读它们。仪表盘的确认文案写明结果只存储、不发送。

#### 推送失败之后的意图过期，不是新开关（[#1585](https://github.com/foolzzz/looper/pull/1585)）

- **`intents.enabled` 不变。** 只有字符串 `true` 才打开意图。没有这一行就是关。没有新设置，没有提示词变化，也没有模型契约变化。意图关闭时，`IntentPushService.run_once` 和 `expire` 立刻返回。迁移仍会建空的 `intent_final_notices` 表。卡住的意图不会过期，也不发终态通知。
- **意图打开时，** 待处理意图在 `expires_at` 已到时过期；`expires_at` 为空则用创建时间加 24 小时。过期检查每 300 秒一次（推送循环仍每 10 秒一次）。处理一条 `expires_at` 为空的待处理意图时，服务把它设为创建时间加 24 小时。推送或进展发送成功且意图仍是 pending 时，把 `expires_at` 设为那次发送之后 24 小时。因此从未成功推送的待处理意图在创建 24 小时后过期。升级后，以前卡住的待处理意图在下一次检查时过期。没有手工回填，迁移里也不改写行。操作者可能收到一条推迟的过期回复。该状态的终态卡片文本是 `⌛ {编号} 已过期（没有处理） · {名称}`。
- **终态通知在自己的表上重试。** 对已经 `tasked`、`rejected` 或 `expired`、并且有一条发到当前已确认操作者私聊的成功推送的意图，服务做有界重试。三次投递。间隔 30 秒，翻倍，上限 300 秒（30，然后 60，然后顶到上限）。次数在发送之前写入。目标无效时推迟 `next_attempt_at`，不消耗一次尝试。用尽后 `state` 为 `failed`，`failure_reason` 为 `final_notice_retry_exhausted`。不确定的投递不重发；重试幂等的编辑仍可能补上通知。先尝试编辑原来的推送；失败再插入并投递一条 `kind` 为 `final` 的帖子。`expired` 转到 `tasked` 会开始一条新通知（次数回到 0）。更早的失败过期回复不能取代这个新的任务状态。即使失败也写了 `edited_at` 的旧行会被采纳一次，包括以前的重试已经用尽的，进入新的 3 次预算。已经成功的旧终态通知保持完成。群仍然拒绝。目标仍是当前已确认的操作者私聊。

### 可选能力启用与使用

#### Memory write

**启用：** 操作者保存 `memory_write` 且 `enabled` 为 true 之前是关。值是一个 JSON 对象，不是字符串 `true`。`root` 必填（`''` 表示整个知识库）。对象内的默认是 `pending_days` 7、`draft_budget_usd` 0.15、`daily_budget_usd` 1.00，以及 `sources.manager`、`sources.tasks`、`sources.leads` 都为 false。操作者用 `POST /api/v1/memory/settings_put` 保存。正文正好是 `{"root": null}` 就删掉这一行。保存不会起草候选。写入器提交的是已经确认的候选。API 客户端令牌得到 403。

**验证：** 没有这一行时，`POST /api/v1/memory/settings_get` 的 `configured` 和 `enabled` 都是 false，`POST /api/v1/memory/check` 不碰知识库。`enabled` 为 true 时，`looper memory check` 报告 Git 和工作目录检查，已确认的知识库候选会被写入器领取。`enabled` 为 false 时，写动作返回 `memory writing is not enabled`。

**停用 / 回退：** `POST /api/v1/memory/settings_put` 正文 `{"root": null}` 删除设置。下一次写入读取到没有这一行，就不再提交。已经写进知识库的笔记留在原地。删除候选（`POST /api/v1/memory/delete` 或 `looper memory delete M-0042`）去掉候选并留下指纹墓碑；不删除知识库笔记；候选处于 `writing` 或 `in_effect` 时拒绝。

**权限边界：** 只给操作者。`memory.confirm`、`memory.edit` 和 `memory.revive` 只在仪表盘。私聊在 Memory push 活动之后可以确认、驳回和重试，不能删除。`looper memory` 可以 list、show、check、reject、retry 和 delete，不能确认。关闭时的动作不开知识库。

**文档：** https://github.com/foolzzz/looper/blob/v2.15.28/docs/architecture/agent-system.md#memory-candidates-what-looper-may-write-to-the-vault-once-confirmed

#### Memory push

**启用：** `memory_write.enabled` 为 true，且 `memory_write.push_channel` 是一行最多 200 字、指向已启用的 Lark 或 Telegram 机器人、其操作者目标是私聊之前，都是关。操作者用 `POST /api/v1/memory/settings_put` 一起设置。没有单独的系统键。推送不走主动投递。

**验证：** `push_channel` 为 null 时，私聊里的 `记 M-0042` 是普通消息。两者都设上之后，这条回复在模型之前处理。完整推送会说回复 `记` 或 `驳回`。不存在的候选得到 `没有 M-0042 这条记忆候选`（回复里的编号就是对方写出的那个）。群或其他发送者得到 `记忆候选只能由你本人在私聊或记忆页处理`。

**停用 / 回退：** 在 `memory.settings_put` 里把 `push_channel` 设为 null，或用 `{"root": null}` 删掉整个设置。下一次推送和下一条消息都在读完一次设置后停止。`enabled` 仍为 true 时，已经 `confirmed` 的候选仍会被写入；清掉 `enabled` 也会停掉写入器。

**权限边界：** 已核验的操作者，且只在该机器人的私聊里。Lark 聊天类型不是 `p2p` 会被拒绝。删除、编辑和恢复不是私聊口令。API 客户端令牌不能调用记忆操作。

**文档：** https://github.com/foolzzz/looper/blob/v2.15.28/docs/architecture/rfcs/memory-write-path-v0.zh-CN.md#53-私聊推送和回复

```bash
looper memory list --state open
```

#### Morning brief

**启用：** 系统设置 `morning_brief.enabled` 成为字符串 `true` 之前是关。没有这一行或其他值都是关。`morning_brief.time` 默认 `09:15`。操作者用 `POST /api/v1/morning_brief/update` 设置，`enabled` 为 true，`time` 可选，格式 `HH:MM`。null 恢复该字段的默认。更新要确认。API 客户端令牌得到 403。这两个键不在聊天设置载荷里，也不在配置导出里。

**验证：** 关闭时，工作日 09:15 不发送，也不写 `morning_briefs` 行。打开后，每个有操作者私聊的已启用机器人每个本地工作日收到一条，标题为 `晨报 · {mm-dd}（周…）`；每一节都空则跳过，详情是 `nothing to say`。周六和周日不发送。第二个服务器不会再发一份。

**停用 / 回退：** `POST /api/v1/morning_brief/update` 的 `enabled` 为 null 或 false。null 删掉这个键并恢复关闭。false 存下字符串 `false`。下一次滴答读内存里的开关，不开数据库连接。已经发出的行保持已发送。`time` 为 null 恢复 `09:15`。

**权限边界：** 只给操作者。`morning_brief.get` 是读，级别 inside。`morning_brief.update` 是高风险，要确认。没有仪表盘开关，没有 Telegram 命令，也没有命令行手动发送。帖子只发到已启用机器人的操作者私聊。

**文档：** https://github.com/foolzzz/looper/blob/v2.15.28/docs/architecture/agent-system.md#morning-brief

```bash
looper --version
```

#### Event triage runs

**启用：** 既有系统设置 `subscriptions.triage.enabled` 成为字符串 `true` 之前是关。没有这一行或其他值都是关。操作者用 `POST /api/v1/triage_settings/update` 把 `enabled` 设为 true。null 删掉这一行。然后创建 `output_kind` 为 `triage` 的订阅并确认。仪表盘只在开关打开时显示「事件分流」。设置操作对 API 客户端令牌返回 403。

**验证：** 关闭时，创建分流订阅返回 HTTP 400，正文是 `cannot create a triage subscription: subscriptions.triage.enabled is off`。已经存在的一条以 `skipped_gate` 结束，错误是 `subscriptions.triage.enabled is off`，游标不动。打开后，未确认的订阅以 `skipped_gate` 结束，错误是 `not confirmed: confirm the subscription to start extracting`，游标不动。已确认的运行为被引用的消息写入 `triage_events`，并且不发送它们。

**停用 / 回退：** `POST /api/v1/triage_settings/update` 的 `enabled` 为 null 或 false。null 删掉这一行。下一次触发是 `skipped_gate`，游标不动，也不再写新的事件行。已经存下的事件还在。再次创建分流订阅会被拒绝。

**权限边界：** `triage_settings.get` 和 `triage_settings.update` 只给操作者。一次运行使用操作者确认过的订阅。它不排入管家事件，也不往聊天里发帖。范围是订阅自己的窗口：私聊、提及、操作者自己的消息和已登记的告警机器人；本版本没有第二次模型检查。

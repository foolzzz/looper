# Looper v2.14.78

This is the patch release v2.14.78, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.77: the Tasks page's Running filter now lists tasks whose Planner is working ([#1088](https://github.com/foolzzz/looper/pull/1088)).

## Release Decision

**Who should upgrade:** Operators who use the Tasks page's Running filter, or `status=running` in the task list API, to see what is in flight. Everyone else can stay.

**What this release solves:** The Running filter showed nothing for tasks whose Planner is working, because those tasks hold the Planner's own status (`planning`, `executing`, `verifying`, `stopping`; badge "Executing") and the filter matched `running` exactly. Its chip had no count either. [#1088](https://github.com/foolzzz/looper/pull/1088) makes the filter cover them.

**Breaking changes:** No. No setting, schema or operation is added or removed; only the set of tasks that `status=running` selects and counts grows.

**How to verify:** Check the installed version. With a task in `planning` or `executing`, Tasks → Running lists it and the chip shows its count.

**Contributors:** Maintainer @foolzzz authored [#1088](https://github.com/foolzzz/looper/pull/1088); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.78
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.77 upgrades directly. This release has no schema change.

## Behavior changes

- **Running covers the Planner's phases** (`looper/db/tasks.py`). A new `STATUS_FILTERS` maps the filter `running` to `assigned`, `running`, `planning`, `executing`, `verifying` and `stopping` (the in-progress group minus `waiting` and `pending`, which keep their own filters); every other filter covers only itself, and an unknown filter still matches exactly. `list_tasks` (and `status=running` of the task list operation) and `count_by_status` use it.
- **Counts are by filter.** `count_by_status` folds each status into the filter that covers it, so the Running count sums its statuses, each task is counted once and the total is unchanged; unknown statuses keep their own keys. The `counts` field of the task list result is described accordingly in the operation schema (`looper/agents/v1_domains/task_views.py`) and in `web/src/lib/api.ts`.
- **Tasks page** (`web/src/pages/tasks.tsx`). The page no longer filters the loaded tasks by exact status in the browser; it lists what the server returns for the filter and reads the Running count from the API. Badges are unchanged.
- **Documentation and tests.** The Tasks paragraph of the architecture doc says what Running covers. Tests added in `tests/test_task_list_db.py`, `tests/test_overview.py` and `web/src/pages/tasks.test.tsx`.
- **Model-visible changes:** None to prompts, role text or agent tool descriptions. The only change in a model-facing schema is the description of the `counts` property in the `tasks.list` operation schema, which now reads "Counts by status filter; each task counted once. Unknown statuses keep their keys.", and the `running` filter and its count now include more tasks.

## 中文摘要

本版本是 patch release v2.14.78（热修线，每个合并的改动立即发布）。自 v2.14.77 以来只合并了一项改动：任务页的 Running 过滤器现在会列出 Planner 正在工作的任务（[#1088](https://github.com/foolzzz/looper/pull/1088)）。

### 升级决策

**谁需要升级：**使用任务页 Running 过滤器或任务列表 API 的 `status=running` 查看进行中任务的运维人员。其他人可不升级。

**解决了什么：**Planner 正在工作的任务持有 Planner 自己的状态（`planning`、`executing`、`verifying`、`stopping`；徽标 "Executing"），而过滤器只精确匹配 `running`，因此 Running 下什么也看不到，其标签也没有计数。[#1088](https://github.com/foolzzz/looper/pull/1088) 让过滤器覆盖这些任务。

**是否有破坏性变更：**否。没有新增或移除设置、数据库结构或操作；只是 `status=running` 选中并计数的任务范围变大。

**如何验证：**核对版本为 2.14.78。有任务处于 `planning` 或 `executing` 时，任务 → Running 会列出它，标签显示其计数。

**贡献者：**维护者 @foolzzz 提交 [#1088](https://github.com/foolzzz/looper/pull/1088)；本版本无社区贡献。

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.77 上的安装可直接升级。本版本没有数据库结构变更。

### 行为变化与入口

- **Running 覆盖 Planner 的各阶段**（`looper/db/tasks.py`）。新的 `STATUS_FILTERS` 把过滤器 `running` 映射到 `assigned`、`running`、`planning`、`executing`、`verifying` 和 `stopping`（进行中分组去掉保留各自过滤器的 `waiting` 和 `pending`）；其他过滤器只覆盖自身，未知过滤器仍按精确匹配。`list_tasks`（以及任务列表操作的 `status=running`）和 `count_by_status` 都使用它。
- **按过滤器计数。**`count_by_status` 把每个状态归入覆盖它的过滤器，因此 Running 的计数是其各状态之和，每个任务只计一次，总数不变；未知状态保留自己的键。任务列表结果的 `counts` 字段在操作 schema（`looper/agents/v1_domains/task_views.py`）和 `web/src/lib/api.ts` 中相应更新了说明。
- **任务页**（`web/src/pages/tasks.tsx`）。页面不再在浏览器里按精确状态过滤已加载的任务，而是列出服务器针对该过滤器返回的任务，并从 API 读取 Running 计数。徽标不变。
- **文档与测试。**架构文档的任务页段落说明了 Running 覆盖的范围。测试新增于 `tests/test_task_list_db.py`、`tests/test_overview.py` 和 `web/src/pages/tasks.test.tsx`。
- **面向模型的变化：**提示词、角色文本和 agent 工具说明均无变化。面向模型的 schema 只有 `tasks.list` 操作 schema 中 `counts` 属性的说明变为 "Counts by status filter; each task counted once. Unknown statuses keep their keys."，且 `running` 过滤器及其计数包含更多任务。

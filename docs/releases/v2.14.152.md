# Looper v2.14.152

This is the patch release v2.14.152, a hotfix line in which each merged change ships at once. It documents one change: [#1274](https://github.com/foolzzz/looper/pull/1274) (a slow start during a service upgrade is waited for, not reported as a failure).

## Release Decision

**Who should upgrade:** Operators who run `looper service upgrade` on a loaded host, where the restarted service can need more than 120 s to answer. Everyone else gets no change in normal use.

**What this release solves:** [#1274](https://github.com/foolzzz/looper/pull/1274) makes the upgrade wait up to `--start-timeout` (default 300 s, was a fixed 120 s) for the restarted service to answer, fails at once when the new process has exited, and, when the deadline passes with the process still alive, reports it as still starting (`starting: true`) instead of as a stopped service, leaving it running.

**Breaking changes:** No. There is no migration and no API removal. `--timeout` stays as an alias of `--start-timeout`. The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.14.152
```

**Contributors:** Maintainer @foolzzz authored [#1274](https://github.com/foolzzz/looper/pull/1274); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.151 upgrades directly. There is no schema change.

## Behavior changes

- **Longer start wait for the upgrade** ([#1274](https://github.com/foolzzz/looper/pull/1274), `looper/cli.py`, `looper/agents/service.py`). `looper service upgrade --start-timeout SECONDS` (alias `--timeout`) now defaults to 300 s instead of 120 s. A live process is allowed the whole interval; the last sleep is cut to the deadline. The positive-finite check on the timeouts now names `--start-timeout (--timeout)`.
- **A process that exited fails immediately** (`looper/agents/service.py`). While waiting, the start check polls the service state and raises "the service exited before answering on port N" with the state and log tail as soon as the process is gone, instead of waiting out the timeout. This applies to every caller of the start wait, so `looper service install` and `looper service restart` (default still 120 s) also fail early on an exited process.
- **Still starting is not a failure of the service** (`looper/agents/service.py`). At the deadline with the process alive, the wait raises a new `ServiceStarting` error naming the last logged startup step (or "no startup step logged yet") and saying not to restart it. The upgrade report then has `status: "starting"`, `starting: true`, `serving: false` and `last_startup_step` (null before any step was logged), carries no restart hint, and does not cancel the drain. The CLI still exits nonzero, because readiness is unverified, with the message "starting: yes; still starting; do not restart it". Other failures keep `serving: yes/no` and the restart hint.
- **Startup steps are logged before they run** (`looper/agents/serve.py`). The serve log gets a `startup step: <name>` line at the start of each step, so an unfinished step can be named. Only entries after the log offset of the current start count, and a truncated log is read from its start.
- **Unchanged:** no frontend change; the upgrade plan, drain and install steps are as before.
- **Model-visible changes:** None. The change touches the service CLI, its report and the serve log only; no prompt, tool, tool result or Manager scope text changed.

## 中文摘要

本版本是 patch release v2.14.152（热修线，每个合并的改动立即发布），说明一项改动：[#1274](https://github.com/foolzzz/looper/pull/1274)（服务升级时启动较慢会被等待，而不是报告为失败）。

### 升级决策

**谁需要升级：**在高负载主机上运行 `looper service upgrade`、重启后的服务可能需要超过 120 秒才响应的运维者。其他人在正常使用中没有变化。

**解决了什么：**[#1274](https://github.com/foolzzz/looper/pull/1274) 让升级最多等待 `--start-timeout`（默认 300 秒，原为固定 120 秒）；新进程已退出则立即失败；到期时进程仍存活则报告为仍在启动（`starting: true`），而不是服务已停止，并保持其运行。

**是否有破坏性变更：**否。没有迁移，没有移除 API。`--timeout` 保留为 `--start-timeout` 的别名。桥接边界不变：早于 v2.13.165 的安装须先升级到 v2.13.165。

**如何验证：**核对版本为 2.14.152。

**贡献者：**维护者 @foolzzz 提交 [#1274](https://github.com/foolzzz/looper/pull/1274)；本版本无社区贡献。

```bash
looper --version   # looper 2.14.152
```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.151 上的安装可直接升级。没有结构变更。

### 行为变化与入口

- **升级的启动等待更长**（[#1274](https://github.com/foolzzz/looper/pull/1274)，`looper/cli.py`、`looper/agents/service.py`）。`looper service upgrade --start-timeout SECONDS`（别名 `--timeout`）默认由 120 秒改为 300 秒。存活的进程可使用整个等待时间；最后一次休眠截止到期限。对超时参数的正有限数检查现在写作 `--start-timeout (--timeout)`。
- **进程已退出则立即失败**（`looper/agents/service.py`）。等待期间启动检查会轮询服务状态，进程一旦退出就立即报错“the service exited before answering on port N”，附状态和日志尾部，而不是等到超时。所有使用该启动等待的调用方都适用，因此 `looper service install` 和 `looper service restart`（默认仍为 120 秒）对已退出的进程也会提前失败。
- **仍在启动不等于服务失败**（`looper/agents/service.py`）。到期时进程仍存活，则抛出新的 `ServiceStarting`，指出最后记录的启动步骤（或“尚无启动步骤记录”）并提示不要重启。升级报告随之为 `status: "starting"`、`starting: true`、`serving: false` 和 `last_startup_step`（尚无步骤时为 null），不带重启提示，也不取消排空。CLI 因就绪未确认仍以非零退出，信息为“starting: yes; still starting; do not restart it”。其他失败仍为 `serving: yes/no` 并带重启提示。
- **启动步骤在执行前记录**（`looper/agents/serve.py`）。serve 日志在每个步骤开始时写入 `startup step: <name>`，以便指出未完成的步骤。只统计本次启动日志偏移之后的条目，日志被截断时从头读取。
- **不变：**前端无改动；升级计划、排空和安装步骤同前。
- **面向模型的变化：**无。改动只涉及服务 CLI、其报告和 serve 日志；没有改动提示词、工具、工具结果或 Manager 范围文本。

# Looper v2.13.27

## Release Decision

**Who should upgrade:** Everyone who streams Manager replies to the dashboard, Telegram or Lark. The fix matters most for long replies.

**What this release solves:** [#371](https://github.com/foolzzz/looper/pull/371) stops a long streamed Manager reply from stalling the server. The message bus journaled every `STATUS_UPDATE` message (streamed deltas, phases), and each journaled message cost a synchronous `fsync` on the event loop (about 20 ms measured locally). A reply streams hundreds of deltas, so the dashboard got no deltas and other requests, a stop included, waited for seconds.

**Breaking changes:** No. No CLI command, configuration key, API or database schema changed. One behavior change is listed below.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#371](https://github.com/foolzzz/looper/pull/371); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.27
```

## Behavior changes

- **Status updates are not journaled:** `MessageBus.publish` (`looper/agents/bus.py`) skips the journal append for `STATUS_UPDATE` messages and still delivers them to subscribers. The delivery loop does not mark them delivered in the journal either, since they were never written.
- **No replay after a restart:** status updates from before a restart are no longer replayed, so a stale "thinking" line no longer shows up in Telegram or Lark. Replies and every other message type are journaled and replayed as before.
- **Model-visible changes:** None. No prompt text, tool schema or tool result changed.

## Upgrade and rollback

Re-run `install.sh` once v2.13.27 is published. There is no schema or configuration change. Rolling back to v2.13.26 is safe; the only difference is that streamed replies are slow again and status updates are replayed after a restart. An existing journal needs no migration.

## Optional Capability Activation & Use

No new optional capability activation is introduced in this release.

## 中文摘要

### 升级决策

**谁需要升级：**把 Manager 回复流式推送到 dashboard、Telegram 或 Lark 的用户；回复越长，收益越明显。

**解决了什么：**[#371](https://github.com/foolzzz/looper/pull/371) 修复长的流式 Manager 回复卡住服务的问题。消息总线会把每条 `STATUS_UPDATE`（流式增量、阶段）写入 journal，每条在事件循环上同步 `fsync`，本机实测约 20 ms；一次回复会流出数百个增量，导致 dashboard 收不到增量，其他请求（包括停止）要等数秒。

**是否有破坏性变更：**无。CLI、配置项、API、数据库 schema 均未变化，仅有下文列出的一项行为变化。

**如何验证：**运行 `looper --version` 核对版本为 2.13.27。

**贡献者：**维护者 @foolzzz 提交 [#371](https://github.com/foolzzz/looper/pull/371)；本次 patch release 无社区贡献。

```bash
looper --version   # looper 2.13.27
```

### 行为变化与入口

- 状态更新不再写 journal：`MessageBus.publish`（`looper/agents/bus.py`）对 `STATUS_UPDATE` 跳过 journal 追加，仍照常投递给订阅者；投递循环也不再为其标记已投递，因为它们从未写入。
- 重启后不再重放：重启前的状态更新不再被重放，Telegram 或 Lark 不会再出现过期的“思考中”行。回复和其他所有消息类型照旧写 journal 并重放。
- 面向模型的变化：无。提示词文本、工具 schema、工具结果均无变化。

### 升级与回退

发布后重跑 `install.sh`。无 schema 或配置变更。回退到 v2.13.26 安全；区别仅是流式回复会重新变慢，且重启后会重放状态更新。已有 journal 无需迁移。

### 可选能力启用与使用

本版本未新增可选能力启用入口。

# Looper v2.15.45

Contains everything merged to main after [v2.15.44](v2.15.44.md)'s scope freeze `448632f1f` (the merge of [#1874](https://github.com/foolzzz/looper/pull/1874)), up to and including `98703b682` (the merge of [#1891](https://github.com/foolzzz/looper/pull/1891)): twenty-six pull requests, each its own first-parent merge. Release pull request [#1877](https://github.com/foolzzz/looper/pull/1877) is not a change. If main has moved beyond this freeze when the release pull request merges, the tag belongs on that pull request's own head, as described in [the release procedure](README.md). PENDING: the freeze moves again when the open pull requests listed under Pending pull requests merge; every sentence marked `PENDING #<n>` is written from the pull request text and is rewritten from the merged code before the release.

This is an audit and hardening release. The Manager's action trail now records who started each call, for the dashboard operator, chat senders and API clients alike. The task Manager's direct session (off by default) runs inside Claude Code's Bash sandbox with a fixed tool list. Smaller fixes close a git call in the leads export that could run repository-configured code, an unvalidated @-mention in Lark cards, an unbounded scan of very long Lark text, an ACP preflight probe that could import from its working directory, and API responses that left MIME sniffing to the browser. The task Manager sandbox also gets a per-project network allowlist (empty by default) with explanations of denied commands and a process environment classified name by name, and a runner that answered its health probe is no longer reclaimed after a host stall. The release adds three migrations (2160, 2170, 2180), no runtime dependency and no switch. Everything takes effect without a switch except the task Manager changes, which apply only while `tasks.conversations.manager_answers` is on. Details, including every behavior change, are under Behavior changes.

## Release Decision

**Who should upgrade:** Every installation that uses the Manager's action trail, the Lark channel or `looper leads eval-export`, and every installation that has turned `tasks.conversations.manager_answers` on (read Before you upgrade first: its direct session loses tools and refuses some launches). PENDING #1901 (not merged yet): installations that run the DSH or pi runtime, or omp with a work directory outside a repository, should take the release that contains it. Other installations can take the release at their next upgrade; nothing here is urgent without those. From v2.15.38 or earlier, upgrade straight to v2.15.45 and read [v2.15.44](v2.15.44.md), [v2.15.43](v2.15.43.md), [v2.15.42](v2.15.42.md), [v2.15.41](v2.15.41.md), [v2.15.40](v2.15.40.md) and [v2.15.39](v2.15.39.md).

**What this release solves:** An audit of the Manager's calls can tell an operator's call from a group member's or an API client's: each row records the turn's trusted sender and audience class, and a confirmed call records both who asked and who confirmed (#1876, #1885). The task Manager's direct session starts only inside Claude Code's Bash sandbox with every key that could loosen it pinned by code, a built-in tool allowlist of `Bash`, no project or local settings layer, a read deny list for credentials, and every MCP server started from a private directory outside the task directory (#1871). `looper leads eval-export` asks git through the hardened git helper (#1881). A Lark card @-mentions only a well-formed open_id (#1883), and Lark text longer than 64 Ki characters is neutralized in one linear pass instead of parsed (#1875). The ACP sandbox preflight runs its probe isolated, and JSON and event-stream API responses carry `X-Content-Type-Options: nosniff` (#1884). Three tests are fixed: one flaky timing test, one that failed on a transient `busy` answer, and one whose fake lacked members the launch path calls (#1875, #1880, #1882). A direct in-place task Manager turn now records the task's branches and tags before and after, reports each change with a restore command and refuses a turn whose `HEAD` has left the recorded task branch (#1878). `looper profile show` and the SessionStart profile hook no longer print nothing on a slow machine (#1889). The documentation and the `confirm` operation's text say that a REST confirmation is the client confirming its own request (#1892). A direct task Manager session now starts only in a checked, unshared in-place directory (#1872), and a change to another branch or tag waits in needs-you until the operator marks it handled (#1879). A direct session's process environment is classified name by name: other runtimes' homes and credentials and any profile `env` name the Claude CLI does not need are dropped, and the read deny list adds the Copilot login directory (#1886). The operator can allow external domains per project (none by default), and a command the sandbox denies gets a code-generated explanation in the task thread (#1873). A runner that answered its health probe is no longer reclaimed after a host stall that ends while the loop-lag sampler sleeps (#1888). Nine test-only or plan-only changes remove clock and ordering dependence, make the serve smoke test print its cause when it fails, tighten two contract scanners and sync the development plan (#1887, #1891, #1893, #1895, #1896, #1897, #1898, #1899, #1902). PENDING #1870, #1894, #1868, #1890: the rest of the task Manager sandbox stack (readback, the ref report follow-up, instructions, directory admission hardening) is in review and is described under Pending pull requests; PENDING #1900: a task stop survives a failing cleanup step and a late Planner status no longer overwrites a stopped or cancelled task; PENDING #1901: project instruction files that Looper reads itself are read only from inside the repository; PENDING #1903: a stop that arrives as a lark-cli call finishes is no longer lost on Python 3.11.

**Breaking changes:** Yes, only for an installation with `tasks.conversations.manager_answers` on: a direct task Manager session no longer has any built-in tool except `Bash`, no longer loads project or local settings, project `CLAUDE.md`, skills, commands or agents, refuses to start on a platform other than macOS (`sandbox_unavailable`), and refuses an allowed MCP server whose launcher can run code from the working directory (`mcp_launcher_unsafe`), and refuses a turn whose `HEAD` is not on the task branch Looper recorded (`head_detached`, `head_moved`), and starts only for an in-place task at the root of its own non-bare git repository that is not the home or a system directory, not an ancestor of trusted configuration and not shared with another live direct session (`worktree_unsupported`, `workspace_is_home`, `workspace_in_system_dir`, `workspace_contains_trusted_config`, `workspace_not_repo_root`, `workspace_overlaps_session`), and starts without the profile `env` names and other runtimes' variables the Claude CLI does not need (item 5 of Before you upgrade); see Behavior changes. Without that switch no operation or setting is removed, and the behavior changes are small: a Lark card drops a malformed @-mention, Lark text over 64 Ki characters loses its images and tag openers, `looper leads eval-export` can refuse where it asked git directly before, two response headers are added, and a runner health probe now counts a host stall that ends while its sampler sleeps. The first upgrade to this release still uses the upgrade order of the version being replaced (see Upgrading). Upgrades from v2.15.43 or earlier also inherit v2.15.44's migration and behavior changes. Installations older than the bridge must upgrade to v2.13.165 first and start once.

**How to verify:** Check the version and that the service starts and applies `manager_action_sender` (2170). Call a Manager tool from the dashboard or a chat, then read the task's detail (`tasks.detail`): the new row in `manager_actions` has `sender_kind` set (`operator` for you) and, for a confirmed call, `initiator_kind`. Request any JSON API answer and confirm the response carries `X-Content-Type-Options: nosniff`. If you turned `manager_answers` on, send a message to a direct task and confirm the task thread shows a reply or a refusal reason and that no built-in tool other than `Bash` was used; the checks run for this document are listed under Validation.

```bash
looper --version   # looper 2.15.45
```

## Included changes

### Audit: who started each Manager action

- **[#1876](https://github.com/foolzzz/looper/pull/1876), the action trail records the sender.** An audit of `manager_actions` could not tell an operator's call from a group member's: rows did not record who started the turn. Affected: installations that read the Manager's action trail, which includes every installation that runs the Manager. Fix: upgrade. Migration `manager_action_sender` (2170) adds four nullable columns without defaults to `manager_actions`, `sender_id`, `sender_kind`, `initiator_sender_id` and `initiator_kind`, so no row is rewritten and history keeps NULLs. Two checks are added `NOT VALID` and validated after commit by an online step (`manager_action_sender_online`), so no scan holds the schema lock. New rows take the values from Looper's own classification of the turn (the turn's sender, speaker, API client and origin), never from model text. `sender_kind` is `operator`, `allowed`, `member`, `client` or `autonomous` (a turn no user started, which has no sender id); `initiator_kind` takes the first four. For a confirmed call, `sender_*` is the confirming turn, or the person who pressed a confirmation button, and `initiator_*` is the asking turn; the asker's class is kept in the confirmation's stored turn, so a button pressed after a restart still names it. A button presser is given the asker's class only when the presser is the asker. `sender_kind` stays NULL where nothing classified the turn. Refusal rows (a tool outside the allowed scope, a tool refused in an API client session) and the API client path record the same columns. `manager_actions.for_task`, and so the `manager_actions` items of `tasks.detail` and the task page's data, return the four fields; `sender_id` and `initiator_sender_id` (chat user ids) are returned only to the operator and are null for any other caller, such as an API client. No dashboard change shows the new fields. The previous release's insert and read statements name their columns, so it ignores the new ones.
- **[#1885](https://github.com/foolzzz/looper/pull/1885), operator REST calls are attributed.** A call an operator made through an audited `/api/v1` operation with the operator token was recorded with `sender_kind` NULL, the same as a turn nothing classified. It now records `operator`. The two writes that bypass the Manager's call path, `manager_sessions.assign_task` and the `manager_cleanup.preview` audit row, record `operator` too (the cleanup row only for the operator principal). This is audit attribution only: the fields authorization reads (speaker, principal, client id, channel) are unchanged, and a test pins that for an operator and a client turn. The `tasks.detail` schema documents the four fields as nullable strings.

### Hardening

- **[#1881](https://github.com/foolzzz/looper/pull/1881), `looper leads eval-export` asks git through the hardened helper.** The check that the output path could not be committed ran `git rev-parse` and `git check-ignore` with a bare subprocess call, so a repository configuration that names a program (for example `core.fsmonitor`) could run code. Affected: installations that run `looper leads eval-export` with an output path inside a git work tree. Fix: upgrade. Both calls now go through the helper of [#1861](https://github.com/foolzzz/looper/pull/1861) (`git_safe`), with the same arguments, timeouts and results, and the file leaves the helper's direct-git allowlist. A refusal by the helper is caught like a timeout and reported as "cannot ask git whether <path> could be committed", which refuses the export with the existing refusal exit code.
- **[#1883](https://github.com/foolzzz/looper/pull/1883), Lark card @-mentions are validated; the neutralizer boundary is pinned.** A card's @-mention was interpolated into the card's Markdown after the text was neutralized. A `Card` now accepts a mention only when it matches `ou_` plus letters and digits, checked when the card is built, restored from its stored form or settled; any other value is dropped, the card is sent without the @-mention, and a warning that does not carry the value is logged. Well-formed open_ids are unchanged. A new test drives every send, reply, edit and card entry point of both Lark transports with remote-image Markdown and scans `looper/` so that a new Lark message write that skips the neutralizer fails CI. Affected: installations using the Lark channel; the mention values Looper itself produces are the sender's open_id and match.
- **[#1875](https://github.com/foolzzz/looper/pull/1875), very long Lark text is neutralized in one linear pass.** The Lark image and tag neutralizer ([#1867](https://github.com/foolzzz/looper/pull/1867)) runs synchronously on the event loop and had no length limit. Text longer than 64 Ki characters now takes one pass that writes every `![` as `&#33;[` and every tag opener (`<` plus a letter, `</` plus a letter, `<!`, `<?`) as `&#60;`, with nothing parsed, so images, code, links and Lark's own tags are not preserved above that length; shorter text is unchanged. Chat replies are far shorter (Telegram caps a message at 4096 characters). The same pull request cuts the neutralizer's retained per-line state on a huge paragraph (output unchanged) and replaces its flaky wall-clock timing test with a size-ratio test.
- **[#1884](https://github.com/foolzzz/looper/pull/1884), the ACP preflight runs isolated; API responses state `nosniff`.** The macOS sandbox preflight of Grok over ACP started its probe interpreter without `-I`, so a module in the working directory could shadow a standard-library import of the probe; it now runs `python -I -c ...` with the same absolute interpreter, and the probe's behavior is unchanged. `_json_response`, which answers every JSON API response including static 404s, and the four hand-written response heads (the configuration export, the chat stream, the task activity stream and the operator chat stream) now carry `X-Content-Type-Options: nosniff`. Browsers do not treat JSON or an event stream as a document, so nothing visible changes; the dashboard's Content-Security-Policy and the other headers are unchanged, and API responses still carry no Content-Security-Policy.

### Task Manager, off by default

- **[#1871](https://github.com/foolzzz/looper/pull/1871), the direct session runs inside Claude Code's Bash sandbox.** A direct-mode task Manager session ran with the operator's Claude Code configuration and its full built-in tool set, and a task's directory is not trusted. The direct session now starts with fixed flags and a fixed `--settings` file written by code (`looper/agents/task_manager_sandbox.py`): `--setting-sources user` (the task directory's project and local settings, hooks, `env`, `.mcp.json`, skills, commands, agents and `CLAUDE.md` do not load), `--strict-mcp-config` and `--tools Bash`. `EndConversation` and `WaitForMcpServers` may still appear and are tolerated. The settings file pins the keys that could widen the boundary: the sandbox on and required, unsandboxed commands off, an empty excluded-commands list, a strict network allowlist, empty write, Unix-socket and Mach-lookup lists, the weaker-isolation and Apple-event options off, skill shell execution off, inbound messages from other sessions refused, and tool search off so allowed MCP tools load without it. The sandbox's write scope is the task directory and its temporary directory, and `.git/hooks`, `.git/config`, `.git/info` and `.git/modules` of the task directory are write-denied. A read deny list covers the operator's credential directories and files (SSH, cloud, GPG, container and cluster logins, git credential stores, shell history, browser profiles, the login keychain), Claude Code's configuration directory and `.claude.json`, other agent runtimes' login directories and Looper's runtime root; it is a blacklist and cannot say "read only the task directory". A direct session carries no outbound-review hook (the sandbox is its boundary), so a user-level `disableAllHooks` setting no longer refuses a direct launch; the Claude Code version check still runs on every launch and resume. The MCP servers of a direct session (Looper's own and the ones allowed by `manager_mcp`) are all started through a wrapper that changes into a private directory under the runtime root, outside every task directory, and refuses an allowed server whose launcher can run code from the working directory or starts another program (`npx`, `uvx`, `bunx`, `uv run`, `npm exec`, `pnpm` and `yarn` `dlx`/`exec`, `deno run`, `bundle exec`, `go run`, `cargo run`, `python -m` without `-I`, `env` and the shells, a relative command, script or `cwd`, any `cwd`, and a code-loading `env` variable such as `PYTHONPATH` or `NODE_OPTIONS`) with the new reason `mcp_launcher_unsafe`. The generated MCP configuration, which can hold server secrets, now lives under the task Manager's own directory in the runtime root and the service removes leftovers from a crash at startup. The direct session's process environment no longer carries proxy variables (either case), `SSH_AUTH_SOCK` or the credential variables of non-Anthropic model providers (#1886 below classifies the rest); the Anthropic API key variable stays visible to the sandboxed Bash (a residual risk recorded in the RFC). A platform other than macOS refuses with `sandbox_unavailable` before any process starts. The 14 refusal reasons of the sandbox design are added to the task event schema, the launch-refusal metric (`task_manager_launch_refusals_total`, whose `phase` also accepts `turn`) and the dashboard's list; code on main raises eleven of them today: `sandbox_unavailable`, `mcp_launcher_unsafe`, the six directory reasons of #1872, `head_detached` and `head_moved` of #1878 and `network_policy_invalid` of #1873; the other three (`readback_unavailable`, `launch_setting_mismatch`, `mcp_set_mismatch`) are for PENDING #1870. The orchestrated read-only session is unchanged. This applies only while `tasks.conversations.manager_answers` is on. The boundary was verified against Claude Code 2.1.332, the version the code already pins, with a probe suite that runs the real command against the real CLI and a scripted local Messages API; it is opt-in and CI does not run it.
- **[#1878](https://github.com/foolzzz/looper/pull/1878), ref reports for an in-place direct session.** In an in-place direct session the model's sandboxed Bash writes the real `.git`, so a turn can move a branch, delete a tag or switch `HEAD`. Affected: installations with `tasks.conversations.manager_answers` on. Fix: upgrade. Before every direct in-place turn Looper records `refs/heads`, `refs/tags` and `HEAD` in the running turn's memory (values, not files, so packed refs, `gc` and reflog removal show no change; `refs/remotes` is never read) and compares them after the turn (`looper/agents/task_manager_refs.py`). A change is reported in the task conversation as a `ref_report` event with one restore command per ref (`git update-ref --no-deref`, or `git symbolic-ref` for a symbolic ref); nothing is restored automatically and no alert is raised, because a ref change is not an invariant violation. A fast-forward of the task branch is the Manager's own commits and is not listed; a reset, rewrite or delete of it is listed. Whether a move is a fast-forward is decided from the raw commit objects (grafts and replace refs are not honoured) in a bounded walk (20000 commits, 1 MiB per object); a walk that cannot decide is reported as a rewrite. A change to any other branch or tag is stored with `needs_you` set, except under `refs/heads/looper/<other task>/` while that task exists and is unfinished, which is `info` only. The needs-you list and the way to mark them handled are #1879, below. The task branch is recorded once, at the first enablement, with a `sandbox_notice` event that the real checkout is edited directly; a detached `HEAD` then refuses the first turn (`head_detached`) and every later turn refuses while `HEAD` is not on that branch (`head_moved`), until it is checked out again or the operator runs the new operator-only operation `tasks.task_manager_branch_set`. A ref listing Looper cannot read safely (a name with a line break, a repeated name, a failed read) refuses the turn at its start and, at its end, gives a `sandbox_notice` with notice `refs_unreadable` instead of a report. Migration `task_manager_refs` (2180) adds two tables, `task_manager_branches` and `task_manager_ref_reports`; existing rows are untouched. The dashboard renders both events. A direct turn in a directory that is not the root of a git repository is refused before the turn by the directory checks of #1872 (`workspace_not_repo_root`). Git is always asked through `git_safe`, with `GIT_OPTIONAL_LOCKS=0`.
- **[#1872](https://github.com/foolzzz/looper/pull/1872), a direct session starts only in a checked, unshared in-place directory.** A direct session ran in whatever directory its task named. Affected: installations with `tasks.conversations.manager_answers` on. Fix: upgrade, and read Before you upgrade. `looper/agents/task_manager_dirs.py` checks the directory before the process starts, in this order: a worktree task is refused as `worktree_unsupported` (kind `workspace_mode`), because v1 has no direct mode for it and the commit-per-turn of [#1848](https://github.com/foolzzz/looper/pull/1848) is not reached in direct mode; the operator's home is `workspace_is_home`; a system directory (`/`, `/System`, `/Library`, `/usr`, `/bin`, `/sbin`, `/etc`, `/private/etc`, `/dev`, `/Applications`, `/cores` and anything under them) is `workspace_in_system_dir`; a directory that is, or contains, trusted configuration (the sandbox's read deny list plus the whole Claude configuration directory, the configuration home and the ops file) is `workspace_contains_trusted_config`; a linked worktree or submodule (`.git` is a file or a symlink) is `worktree_unsupported` (kind `linked_worktree`); a bare repository, a subdirectory of a repository and a directory that is not a git repository are `workspace_not_repo_root`; a directory equal to, inside or containing another live direct session's directory is `workspace_overlaps_session`. Directories are compared by device and inode, so two spellings of one directory, including case variants on a case-insensitive filesystem, are one directory. One direct session holds a directory: a lock file `task-manager-locks/<device>-<inode>.lock` under the runtime root (directory mode 0700, file mode 0600, never deleted, close-on-exec) is taken at admission and the overlap check runs again after it, so a parent and a child that both passed the early check cannot both start. If the Looper process dies while the Claude process is alive, the kernel releases the lock at Looper's exit; that early release is accepted for v1. The refusals reach the task event stream, the launch-refusal metric and the dashboard's list like the other reasons; the refused event payload stays `{kind, reason}`. The orchestrated session is unchanged. No migration, setting or operation is added.
- **[#1879](https://github.com/foolzzz/looper/pull/1879), a change to another branch or tag waits in needs-you.** The reports of #1878 with `needs_you` set are now one needs-you item each, in the new section `task_manager_refs` (key `tm_refs:<id>`, the task's name as context, a link to the task page, the changed ref names and their count). The needs-you page has a "标为已处理" button, and the new operator-only operation `tasks.task_manager_ref_report_resolve` marks a report handled; a second call keeps the first time, an unknown report is `NOT_FOUND`. Info-only reports never appear. Resolving changes nothing in git and restores nothing. The section also appears in the work attention list, the idle checks (with no model-visible context) and the status card. Affected: installations with `manager_answers` on that have stored a report; with none stored the section is absent. Fix: upgrade.
- **[#1886](https://github.com/foolzzz/looper/pull/1886), the direct session's environment is classified, and the read deny list grows.** Affected: installations with `tasks.conversations.manager_answers` on. Fix: upgrade, and read Before you upgrade. Every variable name the runtime environment helper (`child_env`) can pass is classified in `RUNTIME_ENV_CLASS` (`looper/agents/task_manager_sandbox.py:73`) as `keep` (the Claude CLI needs it: its configuration directory, the Anthropic variables and the Claude Code OAuth token) or `drop` (another runtime's home or credential: the Trae, Codex, Grok and Copilot homes and the Codex and xAI/Grok keys and tokens); a test fails when a name is added without a decision. A direct session's process environment drops proxy variables (both cases), `SSH_AUTH_SOCK` and every `drop` name. It also drops each name an Agent Profile's `env` adds unless the name starts with `ANTHROPIC_`, `CLAUDE_`, `ENABLE_TOOL_SEARCH`, `DISABLE_`, `MAX_THINKING_TOKENS` or `API_TIMEOUT_MS`, is set by the profile's provider binding, or is one the server inherits by allowlist (`profile_env_dropped`, `:90`): a profile's `GH_TOKEN` or cloud key no longer reaches the sandboxed Bash, which could print it. The Anthropic API key and the other Anthropic variables stay visible to the sandboxed Bash, and when the session's environment holds a long-lived key or token of that class the launch logs one warning that names the variables and never a value (`credential_warning`, `:107`). v1 supports the Anthropic API and the Claude login only: a profile on a cloud-provider backend (Bedrock, Vertex) gets no region, profile or credentials from its `env`, and its credential files are on the read deny list, so a direct session on such a profile cannot authenticate. The read deny list adds `~/.copilot` and the directory `COPILOT_HOME` names (`:216-218`). The comment and the architecture document now say that the direct session keeps the operator's user-level settings and memory (the global instructions) and that `Skill` is not an allowlisted tool, so a user skill is not something the model can call. No migration, setting or operation is added.
- **[#1873](https://github.com/foolzzz/looper/pull/1873), a per-project network allowlist and explanations of sandbox denials.** A direct session reached no external host, and a denied command only failed. Affected: installations with `manager_answers` on that want a task's Bash to reach a domain, and anyone who reads such a task's thread. Fix: upgrade. *Allowlist.* The operator-only operations `projects.task_manager_sandbox_get` and `projects.task_manager_sandbox_update` (`looper/agents/v1_domains/task_manager_sandbox.py:18,25`) read and replace a project's list of external domains; the default is the empty list (revision 0), which reaches nothing. An entry is accepted only when it is an external name (`looper/agents/task_manager_network.py:86`): at most 50 entries, unique (a duplicate is an error and is never dropped), lower-cased with one trailing dot removed, no IP literal (including `127.1` and `0x7f.1` forms), no port, path, user information or whitespace, `*` only as a leading `*.`, no single-label name and nothing under `localhost`, `local`, `internal`, `home.arpa` or `lan`. Any other value returns the new error code `network_policy_invalid` (HTTP 400) and writes nothing; `expected_revision`, when given, must match or the call returns `conflict`. Each change writes one audit row with the old and new list. Every launch and resume reads the stored list again and validates it, and an entry this version refuses refuses the launch with `network_policy_invalid`. The list is the sandbox's `allowedDomains` in the settings file, so a change restarts the process on its next turn and resumes the same session. Scope: only commands that go through the sandbox's HTTP(S) proxy are affected (`curl`, `npm`, `pip`, ordinary Python HTTP clients); Go command-line tools such as `gh` fail certificate verification inside the sandbox even for a listed domain, Node command-line tools do not use the proxy by default and are not guaranteed to work, and a listed domain can itself carry data out, so choosing entries is the operator's responsibility (`SCOPE_TEXT`, `:121`). Validation cannot catch a name that resolves to a private address; the sandbox still refuses loopback and private destinations. *Denials.* When a Bash result ends in the CLI's `<sandbox_violations>` block and the CLI itself marked that result as a sandbox violation in its result metadata (a block a command prints is ignored, and a CLI version without the marker explains nothing), Looper reads its `deny network-outbound <host>:<port>` lines (`looper/agents/task_manager_denials.py:215`) and classifies each denial: not on the project's list (`not_allowed`), on the list but from a client the sandbox cannot support (`unsupported_client`, for now a Go TLS client recognized by the executable name `gh`, `gcloud` or `terraform`), a destination that can never be allowed such as an IP literal or a local name (`not_allowable`), or `unknown`, which names no host and does not suggest that allowing one helps. Any other `deny` line is category `other` with no target; the observed CLI reports no path for a denied write, so category `write` is reachable only through a future CLI format. Each denial writes an activity row of kind `sandbox_denial` (typed fields and a SHA-256 prefix of the command, never its text), adds one count to the new metric `task_manager_sandbox_denials_total` of `manager_metrics.get` (category and project; the host is never a dimension) and, for the first denial of each category and target in a turn, sends a `sandbox_denial` task event that the dashboard turns into text from its fields. These records are left out of the model's brief. A failure to record never fails the turn. The task page shows the project's effective list read-only; an older server without the operation shows nothing. Migration `task_manager_sandbox_policy` (2160) creates `task_manager_sandbox_policies` and `task_manager_sandbox_policy_audit`; no existing row changes.

### Fixes

- **[#1889](https://github.com/foolzzz/looper/pull/1889), the profile reader no longer times out on a cold import.** `looper profile show` and the SessionStart profile hook (`looper claude-code profile --hook`) ran the reader child under a 1-second wall clock that also had to cover its Python imports (2-3.5 s on a cold bytecode cache), so on a slow machine they printed nothing. Affected: installations that use the profile injection or the hook. Fix: upgrade. The child now bounds its own database and settings work to 0.7 s after its imports, and the parent waits at most 4.5 s for the child to exit (`looper/agents/profile_commands.py`); the hook itself is cut off at 5 s, so in the worst case it can still end first. Missing settings, an unavailable database, an invalid profile or a timeout still print nothing and exit 0. Help text and docs say 4.5 s.
- **[#1888](https://github.com/foolzzz/looper/pull/1888), a runner that answered its health probe is no longer reclaimed after a host stall.** The health probe measured how long the event loop had been stalled with a sampler task that sleeps one tick at a time; the probe cancelled it when the stall ended while it was parked in that sleep, so the stall was never counted, the probe was not retried and the timeout counted against the runner (`runner_health_failed reason=timeout`). Affected: installations that run runner-based runtimes on a host that can stall longer than the health limit. Fix: upgrade. One class, `HostLag` (`looper/agents/runtimes/runner/bridge.py:167`), replaces the two copies of the sampler, and its `settle()` counts the pending tick synchronously before the sampler is cancelled and before a late reply is judged against the deadline (`bridge.py:269,355`, `supervisor.py:500,519`). A stall longer than the lag limit that ends mid-sleep is now counted, so the probe retries, and a reply that arrived inside the stall is judged against the deadline minus that lag. Stalls shorter than the limit and a runner that is really silent behave as before.

## Before you upgrade

Check these before you upgrade if the task Manager is on; with `tasks.conversations.manager_answers` off, none of them applies.


1. **A direct task Manager needs macOS and sandbox-safe MCP servers.** On another platform a direct session refuses with `sandbox_unavailable`. For each name in `tasks.conversations.manager_mcp`, check that its user-scope definition uses an absolute command to an installed executable: a server started through `npx`, `uvx`, `bunx`, `uv run` or a shell, a relative command or script, a `cwd`, or a code-loading `env` variable is refused with `mcp_launcher_unsafe` (#1871).
2. **A direct session has `Bash` only.** The model reads and writes files through the sandboxed Bash; it has no Read, Write, Edit, search or web tools, cannot read images, PDFs or notebooks, and does not load the task directory's project instruction files. A workflow that relied on those needs the follow-up work under Pending pull requests (#1871, PENDING #1868).
3. **A direct session's Bash reaches only the domains you allow.** The project's network allowlist is empty by default and strict, and proxy variables are not passed on, so a command that needs the network (a package install, a fetch) fails and the task thread says which host was denied. Allow domains with the operator-only `projects.task_manager_sandbox_update`; only commands through the sandbox's HTTP(S) proxy are affected (`gh` and other Go tools do not work even for a listed domain, Node tools are not guaranteed), and a listed domain can carry data out (#1871, #1873).
4. **A direct session needs its own repository root.** Each task that uses a direct session must be an in-place task whose directory is the root of its own non-bare git repository, not your home or a system directory, not a directory that contains your credential or Claude configuration, and not nested in, or containing, another task's direct session. A worktree task, a linked worktree and a submodule are refused with `worktree_unsupported`, and a subdirectory or a non-git directory with `workspace_not_repo_root` (#1872).
5. **A direct session's environment is the Claude CLI's own.** Other runtimes' homes and credentials are not passed, and neither is any name an Agent Profile's `env` adds unless it is the CLI's own (names starting `ANTHROPIC_`, `CLAUDE_`, `ENABLE_TOOL_SEARCH`, `DISABLE_`, `MAX_THINKING_TOKENS`, `API_TIMEOUT_MS`) or set by the profile's provider binding. A profile that relied on another variable (a token for a command-line tool, a cloud region or credential) loses it in the direct session; a profile on a cloud-provider backend (Bedrock, Vertex) cannot authenticate there. The Anthropic credentials stay visible to the sandboxed Bash, so prefer a subscription login or a short-lived token to a long-lived key in the service environment or the profile; the launch logs a warning that names such variables (#1886).

**Dependency note.** The runtime dependencies and the `test` extra are unchanged from v2.15.44: `pyproject.toml` is identical at the freeze. A source-checkout upgrade (`looper service upgrade`) still syncs with `--extra test`, so the machine needs the packages v2.15.44 already required, from the package index or a warm uv cache. Because the upgrade that installs v2.15.45 runs the code of the version being replaced, read the upgrade-order note under Upgrading.

## Behavior changes

### Without a new switch

- **Manager action trail (#1876, #1885).** New rows in `manager_actions` carry `sender_kind` (and `sender_id` where a user sent the turn) and, for a confirmed call, `initiator_kind` and `initiator_sender_id`; old rows keep NULLs. `tasks.detail` lists the four fields in each `manager_actions` item; the two id fields are null unless the caller is the operator. No authorization input, prompt, tool list or setting changes.
- **Lark (#1883, #1875).** A card whose mention is not an `ou_` open_id is sent without the @-mention. Text longer than 64 Ki characters (not a chat reply's size) has every `![` written as `&#33;[` and every tag opener as `&#60;`, so its code, links, image keys and Lark tags no longer render as such; text up to that length is neutralized as before.
- **Leads export (#1881).** `looper leads eval-export` no longer lets a repository's own configuration run a program while checking the output path. A repository the helper refuses (for example one whose `info/attributes` assigns a driver) makes the check report "cannot ask git ..." and refuses the export; before, the same repository would have been asked directly.
- **API responses (#1884).** Every JSON answer and the four event-stream or export heads carry `X-Content-Type-Options: nosniff`. The ACP preflight probe starts with `-I`.
- **Profile reader (#1889).** `looper profile show` and the SessionStart profile hook wait up to 4.5 s for their reader child instead of 1 s; nothing is printed on failure, as before.
- **Needs-you (#1879).** A new section `task_manager_refs` appears in needs-you only while a stored ref report needs you, with a "标为已处理" button; the new operator-only operation `tasks.task_manager_ref_report_resolve` marks one handled and changes nothing in git.
- **REST confirmation (#1892).** No behavior changes; the `confirm` operation's summary and description and the 202 response text now say that the client confirms its own request.
- **Runner health (#1888).** A host stall that ends while the health probe's sampler sleeps is counted, so the probe retries instead of reclaiming a runner that answered; stalls shorter than the lag limit and silent runners behave as before.
- **Migrations (#1876, #1878, #1873).** Startup applies `task_manager_sandbox_policy` (2160), `manager_action_sender` (2170) and `task_manager_refs` (2180), also with every optional feature off.

### Task Manager network allowlist

**Activation:** The list is empty by default, so a direct session's Bash reaches no external domain. As the operator, read the project's list and revision with `projects.task_manager_sandbox_get` (`{"project": "<name or id>"}`), then call `projects.task_manager_sandbox_update` with the whole new `network_allowed_domains` list (external names only, at most 50, `*.` only as a leading prefix) and, optionally, the `expected_revision` you read. It matters only while `tasks.conversations.enabled` and `tasks.conversations.manager_answers` are on; the next turn of each affected session restarts it with the new list and resumes the same session.

**Validation:** Read the list and revision back. An IP literal, a name with a port or a bare `*` returns `network_policy_invalid` and the stored list stays as read. In a direct task session of a throwaway project, a `curl` to a listed test domain goes through the sandbox's proxy, and the same command to an unlisted domain fails and shows a `sandbox_denial` explanation in the task thread and adds one count to `task_manager_sandbox_denials_total` of `manager_metrics.get`; the task page shows the effective list. Do not point this at a production task or domain.

**Disable / rollback:** Update with `[]` (optionally with `expected_revision`): the next turn restarts the session with no reachable domain. Every change stays in the audit table. This does not turn the task Manager off; `manager_answers` does that.

**Authority boundary:** Both operations are operator-only and write only Looper's own policy and audit rows. Everything the sandboxed Bash runs can reach a listed domain, including a command the task's own files lead the model to run, and a listed domain can carry data out; the list gives no other sender a new tool and does not widen the write scope, the read deny list or the environment.

## 中文摘要

包含 [v2.15.44](v2.15.44.md) 范围冻结点 `448632f1f`（#1874 的合并）之后、至 `98703b682`（#1891 的合并）为止合入 main 的全部改动：26 个 PR，各自一个第一父链合并。发布 PR #1877 不算改动。若发布 PR 合入时 main 已越过冻结点，tag 应打在发布 PR 自己的 head 上。PENDING：「待合入的 PR」一节里的 PR 合入后冻结点会再次移动；每个标了 `PENDING #<n>` 的句子都是按 PR 文字写的，发布前要按合入后的代码重写。

这是一个审计与加固版本。管家的操作记录现在会记下每次调用是谁发起的，仪表盘操作者、聊天发送者和 API 客户端都一样。任务管家的直连会话（默认关闭）运行在 Claude Code 的 Bash 沙箱里，工具列表固定。较小的修复关闭了这些问题：leads 导出里一次可能执行仓库配置程序的 git 调用、Lark 卡片里未校验的 @ 提及、对超长 Lark 文本的无上限扫描、ACP 预检探针可能从工作目录导入模块、以及 API 响应把 MIME 嗅探留给浏览器。任务管家沙箱另外得到按项目的网络白名单（默认为空）和对被拒命令的解释，进程环境也按名字逐个分类；已经回答了健康探测的 runner 不再在宿主停顿之后被回收。本版新增三项迁移（2160、2170、2180），没有运行时依赖，也没有开关。除任务管家的改动（仅在 `tasks.conversations.manager_answers` 开启时生效）外，全部无需开关即生效，详见「行为变化」。

### 升级决策

**谁需要升级：** 使用管家操作记录、Lark 渠道或 `looper leads eval-export` 的安装，以及已经开启 `tasks.conversations.manager_answers` 的安装（请先读「升级前请检查」：直连会话会失去工具，部分启动会被拒绝）。PENDING #1901（尚未合入）：使用 DSH 或 pi 运行时、或在仓库之外的工作目录里使用 omp 的安装，应升级到包含它的版本。其他安装可以在下次升级时一并升级，没有这些就没有紧迫性。从 v2.15.38 或更早版本直接升级到 v2.15.45，并阅读 [v2.15.44](v2.15.44.md)、[v2.15.43](v2.15.43.md)、[v2.15.42](v2.15.42.md)、[v2.15.41](v2.15.41.md)、[v2.15.40](v2.15.40.md)、[v2.15.39](v2.15.39.md)。

**解决了什么：** 管家调用的审计现在能区分操作者、群成员和 API 客户端：每一行记录该轮可信的发送者和受众类别，已确认的调用同时记录谁提出、谁确认（#1876、#1885）。任务管家直连会话只在 Claude Code 的 Bash 沙箱里启动，所有可能放宽边界的键都由代码固定，内置工具白名单只有 `Bash`，不加载项目或本地设置层，有凭据读取黑名单，每个 MCP 服务都从任务目录之外的私有目录启动（#1871）。`looper leads eval-export` 通过加固后的 git 辅助模块询问 git（#1881）。Lark 卡片只 @ 格式正确的 open_id（#1883），超过 64 Ki 字符的 Lark 文本用一次线性扫描中和，不再解析（#1875）。ACP 沙箱预检以隔离模式运行探针，JSON 与事件流 API 响应带 `X-Content-Type-Options: nosniff`（#1884）。修复了三个测试：一个不稳定的计时测试、一个因瞬时 `busy` 回答失败的测试、一个假对象缺少启动路径所调用成员的测试（#1875、#1880、#1882）。直连的原地任务管家一轮现在会记录任务的分支和 tag 的前后状态，给出每处变化和恢复命令，并拒绝 `HEAD` 已离开所记录任务分支的一轮（#1878）。`looper profile show` 和 SessionStart profile hook 不再在慢机器上什么都不打印（#1889）。文档和 `confirm` 操作的说明写明 REST 确认是客户端对自己请求的确认（#1892）。直连会话现在只在检查过的、不被共享的原地目录里启动（#1872），对其他分支或 tag 的改动会留在“需要你处理”里，直到操作者标为已处理（#1879）。直连会话的进程环境按名字逐个分类：其他运行时的主目录和凭据、以及 profile `env` 里 Claude CLI 用不到的名字都不再传入，读取黑名单增加 Copilot 的登录目录（#1886）。操作者可以按项目放行外部域名（默认没有），沙箱拒绝的命令会在任务线程里得到代码生成的解释（#1873）。已经回答了健康探测的 runner，不再因为在循环滞后采样器睡眠期间结束的宿主停顿而被回收（#1888）。另有九个只改测试或计划的改动，去掉对时钟和执行顺序的依赖、让 serve 冒烟测试失败时打印原因、收紧两个契约扫描器、同步开发计划（#1887、#1891、#1893、#1895、#1896、#1897、#1898、#1899、#1902）。PENDING #1870、#1894、#1868、#1890：任务管家沙箱的其余部分（回读、引用报告的后续、指令、目录准入加固）仍在评审，见「待合入的 PR」；PENDING #1900：任务停止在清理步骤失败时仍然完成，迟到的 Planner 状态不再覆盖已停止或已取消的任务；PENDING #1901：Looper 自己读取的项目指令文件只从仓库内部读取；PENDING #1903：与 lark-cli 调用同时到达的停止在 Python 3.11 上不再丢失。

**是否有破坏性变更：** 是，仅对开启了 `tasks.conversations.manager_answers` 的安装：直连任务管家会话除 `Bash` 外没有任何内置工具，不再加载项目或本地设置、项目 `CLAUDE.md`、skills、commands 或 agents，在 macOS 以外的平台拒绝启动（`sandbox_unavailable`），并拒绝启动器能从工作目录运行代码的被允许 MCP 服务（`mcp_launcher_unsafe`），并拒绝 `HEAD` 不在 Looper 所记录任务分支上的一轮（`head_detached`、`head_moved`），并且只为位于自己的非裸 git 仓库根目录的原地任务启动，该目录不能是主目录、系统目录、受信配置的祖先，也不能与另一个存活的直连会话共享（`worktree_unsupported`、`workspace_is_home`、`workspace_in_system_dir`、`workspace_contains_trusted_config`、`workspace_not_repo_root`、`workspace_overlaps_session`），并且启动时不带 profile `env` 里和其他运行时的、Claude CLI 用不到的变量（「升级前请检查」第 5 项），见「行为变化」。不开这个开关时没有删除任何操作或设置，行为变化很小：Lark 卡片丢掉格式错误的 @ 提及，超过 64 Ki 字符的 Lark 文本失去图片和标签开头，`looper leads eval-export` 在原来直接询问 git 的地方可能拒绝，多两个响应头，runner 健康探测也会计入在采样器睡眠期间结束的宿主停顿。升级到本版的那一次升级仍使用被替换版本的升级顺序（见升级一节）。从 v2.15.43 或更早升级还会继承 v2.15.44 的迁移和行为变化。早于桥接版本的安装需先升级到 v2.13.165 并启动一次。

### 包含的改动

**审计：每个管家操作是谁发起的**

- **[#1876](https://github.com/foolzzz/looper/pull/1876)，操作记录带发送者。** `manager_actions` 的审计分不清操作者和群成员的调用，因为行里没有记录是谁发起了这一轮。影响：读管家操作记录的安装，即所有运行管家的安装。修复：升级。迁移 `manager_action_sender`（2170）给 `manager_actions` 加四个可空、无默认值的列 `sender_id`、`sender_kind`、`initiator_sender_id`、`initiator_kind`，不重写任何行，历史保持 NULL。两个检查以 `NOT VALID` 创建，由在线步骤 `manager_action_sender_online` 在提交之后校验，不会因扫描表而持有 schema 锁。新行的值来自 Looper 自己对该轮的判定（该轮的发送者、说话人、API 客户端和来源），不取模型文本。`sender_kind` 取 `operator`、`allowed`、`member`、`client` 或 `autonomous`（没有用户发起的一轮，没有发送者 id）；`initiator_kind` 取前四个。已确认的调用里，`sender_*` 是确认的那一轮，或点按钮的人，`initiator_*` 是提出请求的那一轮；提出者的类别保存在待确认项保存的那一轮里，所以重启之后点按钮仍能记下它。点按钮的人只有本人就是提出者时才被记为提出者的类别。没有任何东西判定过那一轮时，`sender_kind` 保持 NULL。拒绝行（超出允许范围的工具、API 客户端会话里被拒绝的工具）和 API 客户端路径写入同样的列。`manager_actions.for_task`，也就是 `tasks.detail` 的 `manager_actions` 项和任务页的数据，返回这四个字段；`sender_id` 和 `initiator_sender_id`（聊天用户 id）只返回给操作者，对其他调用方（如 API 客户端）为 null。仪表盘没有改动，不显示新字段。上一版的插入和读取语句都写明列名，所以旧版本会忽略新列。
- **[#1885](https://github.com/foolzzz/looper/pull/1885)，操作者 REST 调用有归属。** 操作者用操作者 token 调用受审计的 `/api/v1` 操作时，`sender_kind` 记为 NULL，和没有判定过的一轮无法区分；现在记为 `operator`。绕过管家调用路径的两处直接写入，`manager_sessions.assign_task` 和 `manager_cleanup.preview` 审计行，也记为 `operator`（清理行只对操作者主体这样记）。这只是审计归属：授权读取的字段（说话人、主体、客户端 id、渠道）不变，测试对操作者和客户端两种轮次都钉住了这一点。`tasks.detail` 的 schema 把这四个字段写为可空字符串。

**加固**

- **[#1881](https://github.com/foolzzz/looper/pull/1881)，`looper leads eval-export` 通过加固后的辅助模块询问 git。** 检查输出路径能否被提交时，`git rev-parse` 和 `git check-ignore` 用裸子进程调用，仓库配置里指定程序的项（例如 `core.fsmonitor`）可以执行代码。影响：在 git 工作树内的路径上运行 `looper leads eval-export` 的安装。修复：升级。两处调用现在都经过 [#1861](https://github.com/foolzzz/looper/pull/1861) 的辅助模块（`git_safe`），参数、超时和返回值不变，该文件也从辅助模块的直接 git 白名单中移除。辅助模块的拒绝和超时一样被捕获，报告为「cannot ask git whether <path> could be committed」，用现有的拒绝退出码拒绝导出。
- **[#1883](https://github.com/foolzzz/looper/pull/1883)，校验 Lark 卡片的 @ 提及，钉住中和边界。** 卡片的 @ 提及在文本中和之后才被拼进卡片的 Markdown。现在 `Card` 只接受匹配 `ou_` 加字母数字的提及，在构建、从保存形式恢复或定稿时检查；其他值被丢弃，卡片不带 @ 发送，并记一条不含该值的警告。格式正确的 open_id 不变。新增测试用带远程图片的 Markdown 驱动两个 Lark 传输的每个发送、回复、编辑和卡片入口，并扫描 `looper/`，让新增的、绕过中和的 Lark 消息写入在 CI 中失败。影响：使用 Lark 渠道的安装；Looper 自己产生的提及值是发送者的 open_id，符合格式。
- **[#1875](https://github.com/foolzzz/looper/pull/1875)，超长 Lark 文本用一次线性扫描中和。** Lark 图片和标签中和器（[#1867](https://github.com/foolzzz/looper/pull/1867)）在事件循环上同步运行，之前没有长度上限。超过 64 Ki 字符的文本现在走一次扫描：每个 `![` 写成 `&#33;[`，每个标签开头（`<` 加字母、`</` 加字母、`<!`、`<?`）写成 `&#60;`，不做任何解析，所以超过该长度后图片、代码、链接和 Lark 自己的标签都不保留；更短的文本不变。聊天回复远小于这个长度（Telegram 单条上限 4096 字符）。同一个 PR 还减少了中和器在超大段落上保留的逐行状态（输出不变），并把不稳定的墙钟计时测试改成按输入规模比值判断的测试。
- **[#1884](https://github.com/foolzzz/looper/pull/1884)，ACP 预检隔离运行；API 响应声明 `nosniff`。** Grok over ACP 的 macOS 沙箱预检启动探针解释器时没有 `-I`，工作目录里的模块可以遮蔽探针对标准库的导入；现在运行 `python -I -c ...`，仍是同一个绝对解释器路径，探针行为不变。`_json_response`（回答每一个 JSON API 响应，包括静态 404）和四处手写的响应头（配置导出、聊天流、任务活动流、操作者聊天流）现在带 `X-Content-Type-Options: nosniff`。浏览器不会把 JSON 或事件流当作文档，所以没有可见变化；仪表盘的 Content-Security-Policy 和其他响应头不变，API 响应仍不带 Content-Security-Policy。

**任务管家，默认关闭**

文件启动（`looper/agents/task_manager_sandbox.py`）：`--setting-sources user`（任务目录的项目和本地设置、hooks、`env`、`.mcp.json`、skills、commands、agents 和 `CLAUDE.md` 都不加载）、`--strict-mcp-config` 和 `--tools Bash`。`EndConversation` 和 `WaitForMcpServers` 仍可能出现，予以容忍。设置文件固定了所有可能放宽边界的键：沙箱开启且必须可用、不沙箱命令关闭、排除命令列表为空、严格网络白名单、写入/Unix socket/Mach lookup 列表为空、弱隔离与 Apple 事件选项关闭、skill 内联 shell 关闭、拒绝其他会话的入站消息，以及关闭工具搜索，使被允许的 MCP 工具无需它就能加载。沙箱的写范围是任务目录和它的临时目录，任务目录的 `.git/hooks`、`.git/config`、`.git/info` 和 `.git/modules` 禁止写入。读取黑名单覆盖操作者的凭据目录和文件（SSH、云、GPG、容器和集群登录、git 凭据存储、shell 历史、浏览器配置、登录钥匙串）、Claude Code 的配置目录和 `.claude.json`、其他 agent 运行时的登录目录以及 Looper 的运行时根目录；它是黑名单，不能表达「只读任务目录」。直连会话不带出站审查 hook（沙箱就是它的边界），所以用户级 `disableAllHooks` 设置不再拒绝直连启动；Claude Code 版本检查在每次启动和恢复时仍会运行。直连会话的 MCP 服务（Looper 自己的和 `manager_mcp` 允许的）都通过一个包装器启动，包装器先切到运行时根目录下的私有目录，该目录在所有任务目录之外；被允许的服务如果启动器能从工作目录运行代码或会再启动别的程序（`npx`、`uvx`、`bunx`、`uv run`、`npm exec`、`pnpm`/`yarn` 的 `dlx`/`exec`、`deno run`、`bundle exec`、`go run`、`cargo run`、不带 `-I` 的 `python -m`、`env` 和各种 shell、相对的命令/脚本/`cwd`、任何 `cwd`，以及 `PYTHONPATH`、`NODE_OPTIONS` 之类加载代码的 `env` 变量），以新的原因 `mcp_launcher_unsafe` 拒绝。可能含服务密钥的生成 MCP 配置现在放在运行时根目录下任务管家自己的目录里，服务启动时会清掉崩溃遗留的文件。直连会话的进程环境不再带代理变量（大小写两种）、`SSH_AUTH_SOCK` 和非 Anthropic 模型服务商的凭据变量（其余的由下面的 #1886 分类）；Anthropic API key 变量对沙箱内的 Bash 仍然可见（RFC 里记录的残余风险）。在 macOS 以外的平台，直连会话在启动任何进程之前以 `sandbox_unavailable` 拒绝。沙箱设计里的 14 个拒绝原因被加进任务事件 schema、启动拒绝指标（`task_manager_launch_refusals_total`，其 `phase` 也接受 `turn`）和仪表盘的列表；main 上的代码目前会产生其中十一个：`sandbox_unavailable`、`mcp_launcher_unsafe`、#1872 ### 升级前请检查

如果任务管家是开着的，升级前请检查这五项；`tasks.conversations.manager_answers` 关闭时，都不适用。

1. **直连任务管家需要 macOS 和沙箱安全的 MCP 服务。** 在其他平台，直连会话以 `sandbox_unavailable` 拒绝。对 `tasks.conversations.manager_mcp` 里的每个名字，确认它的用户级定义使用指向已安装可执行文件的绝对命令：通过 `npx`、`uvx`、`bunx`、`uv run` 或 shell 启动、相对命令或脚本、带 `cwd`、或带加载代码的 `env` 变量的服务，都会以 `mcp_launcher_unsafe` 被拒绝（#1871）。
2. **直连会话只有 `Bash`。** 模型通过沙箱里的 Bash 读写文件；没有读、写、编辑、搜索或网页工具，不能读图片、PDF 或 notebook，也不加载任务目录里的项目指令文件。依赖这些的工作流需要「待合入的 PR」里的后续工作（#1871、PENDING #1868）。
3. **直连会话的 Bash 只能访问你放行的域名。** 项目的网络白名单默认为空且严格，代理变量也不传入，所以需要网络的命令（装包、抓取）会失败，任务线程会说明哪个主机被拒绝。用仅操作者可用的 `projects.task_manager_sandbox_update` 放行域名；只有经沙箱 HTTP(S) 代理的命令受影响（`gh` 等 Go 工具即使域名在列表里也不能用，Node 工具不保证可用），列表里的域名也可能把数据传出去（#1871、#1873）。
4. **直连会话需要自己的仓库根目录。** 每个使用直连会话的任务必须是原地任务，目录是自己非裸 git 仓库的根目录，不是你的主目录或系统目录，不包含你的凭据或 Claude 配置，也不嵌套在另一个任务的直连会话里或包含它。worktree 任务、链接的 worktree 和子模块以 `worktree_unsupported` 拒绝，子目录或非 git 目录以 `workspace_not_repo_root` 拒绝（#1872）。
5. **直连会话的环境只有 Claude CLI 自己的变量。** 其他运行时的主目录和凭据不传入，Agent Profile 的 `env` 加入的名字也不传入，除非它是 CLI 自己的（以 `ANTHROPIC_`、`CLAUDE_`、`ENABLE_TOOL_SEARCH`、`DISABLE_`、`MAX_THINKING_TOKENS`、`API_TIMEOUT_MS` 开头）或由 profile 的服务商绑定设置。依赖其他变量（命令行工具的 token、云区域或凭据）的 profile 在直连会话里会失去它们；云厂商后端（Bedrock、Vertex）的 profile 在那里无法认证。Anthropic 的凭据对沙箱内的 Bash 仍然可见，所以服务环境或 profile 里请优先用订阅登录或短期 token，而不是长期 key；启动时会记一条点名这类变量的警告（#1886）。

**依赖说明：** 运行时依赖和 `test` extra 与 v2.15.44 相同：冻结点上的 `pyproject.toml` 一致。源码目录升级（`looper service upgrade`）仍带 `--extra test` 同步，所以机器需要 v2.15.44 已经要求的那些包，来自包索引或已预热的 uv 缓存。因为安装 v2.15.45 的那次升级运行的是被替换版本的代码，请阅读「升级」里的升级顺序说明。

### 可选能力启用与使用

本版一个面：任务管家按项目的网络白名单，只在直连会话开启时才有意义。示例只做读取，需替换示例站点并提供操作者 cookie，不会改任何东西。继承能力见 [v2.15.44](v2.15.44.md#optional-capability-activation--use)、[v2.15.43](v2.15.43.md#optional-capability-activation--use)、[v2.15.42](v2.15.42.md#optional-capability-activation--use)、[v2.15.41](v2.15.41.md#optional-capability-activation--use) 和 [v2.15.39](v2.15.39.md#optional-capability-activation--use)。任务管家的沙箱没有自己的设置：它是 `tasks.conversations.manager_answers` 打开的直连会话的一部分。

#### Task Manager network allowlist

**启用：** 默认为空，所以直连会话的 Bash 访问不了任何外部域名。操作者先用 `projects.task_manager_sandbox_get`（`{"project": "<名称或 id>"}`）读项目的列表和版本号，再用 `projects.task_manager_sandbox_update` 提交整个新的 `network_allowed_domains` 列表（只能是外部名字，最多 50 条，`*.` 只能作开头前缀），也可附上读到的 `expected_revision`。它只在 `tasks.conversations.enabled` 和 `tasks.conversations.manager_answers` 都开启时才有意义；每个受影响会话的下一轮会带着新列表重启并恢复同一个会话。

**验证：** 读回列表和版本号。IP 字面量、带端口的名字或单独的 `*` 返回 `network_policy_invalid`，已存的列表保持读到的样子。在一次性项目的直连任务会话里，对列表内的测试域名运行 `curl` 会经沙箱代理通过，对不在列表里的域名运行同样的命令会失败，并在任务线程里出现 `sandbox_denial` 解释，`manager_metrics.get` 的 `task_manager_sandbox_denials_total` 加一；任务页显示当前生效的列表。不要对生产任务或生产域名做这个检查。

**权限边界：** 两个操作都仅限操作者，只写 Looper 自己的策略和审计行。沙箱里的 Bash 运行的任何东西都能访问列表里的域名，包括任务自己的文件引导模型运行的命令，列表里的域名本身也可能把数据传出去；该列表不给其他发送者任何新工具，也不放宽写范围、读取黑名单或环境。

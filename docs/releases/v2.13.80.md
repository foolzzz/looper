# Looper v2.13.80

## Release Decision

**Who should upgrade:** Anyone who deletes tasks or discards step workspaces from the dashboard, or who calls `POST /api/tasks/delete`, `POST /api/tasks/{id}/workspaces/{n}/discard` or `GET /api/workspaces/check` from a script. Everyone else gets no change.

**What this release solves:** [#516](https://github.com/foolzzz/looper/pull/516) moves task deletion, step-workspace discard and the pre-creation workspace check onto three typed operations in the versioned API, with explicit confirmation for the two destructive ones and the existing cleanup order kept, and removes the three legacy routes.

**Breaking changes:** Yes. `POST /api/tasks/delete`, `POST /api/tasks/{id}/workspaces/{n}/discard` and `GET /api/workspaces/check` are removed; a script that calls them must use `POST /api/v1/tasks/delete`, `POST /api/v1/workspaces/discard` and `POST /api/v1/workspaces/check`. The dashboard shipped in this release already does.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#516](https://github.com/foolzzz/looper/pull/516); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.80
```

## Behavior changes

- **Three operations on v1 ([#516](https://github.com/foolzzz/looper/pull/516)):** the new `looper/agents/v1_domains/workspaces.py` registers `tasks.delete` (risk `high`), `workspaces.discard` (risk `high`) and `workspaces.check` (risk `read`), all `POST`. Requests are closed objects; `task_id` must be non-blank and `workspace_id` an integer from 1 to 10^18 − 1. `workspaces.check` takes the former query fields (`dir`, `project_id`, `mode`, `base`) in the body, all optional.
- **Destructive calls confirm:** `tasks.delete` and `workspaces.discard` are declared `confirms=True`, so a call can answer `needs_confirmation` first (HTTP 202) with an impact text: for delete, the task, its step worktrees, task checkout, saved sessions and database records, with the result branch kept; for discard, the workspace's directory and branch. The impact step answers not-found for an unknown task, or for a workspace that is not in that task. The operations are not marked operator-only, so an API client can call them through the confirmation flow; this draft did not run that flow.
- **Cleanup behavior kept:** the delete body moved from `_handle_task_delete` into `AgentHTTPServer._delete_task` in `looper/agents/http_server.py` with the same checks: unknown task 404, a task in an active status 400 ("stop the task before deleting"), a task-worktree failure 409 with the worktree kept, then session removal and the database delete. The result is `{deleted: <task_id>}`; discard returns `{workspace}`.
- **Response shape:** results are wrapped in the v1 `OpOk.result` envelope, and errors follow the v1 error shape rather than the legacy `{"error": ...}` bodies.
- **Removed routes:** the three legacy routes and the `_RE_TASK_WORKSPACE_DISCARD` dispatch are removed from the HTTP dispatch table in `looper/agents/http_server.py`.
- **Dashboard:** `deleteTask`, `discardStepWorkspace` and `checkWorkspace` in `web/src/lib/api.ts` call the new operations; a confirmation answer is surfaced as an error to the caller by these functions.
- **Tests:** the new `tests/test_api_v1_task_workspaces.py` and `..._db.py` cover the CLI shape, id bounds, confirmation and pending-state handling, active-task refusal, a worktree-finish failure keeping state, ordered deletion, discard refusals, check defaults and warnings, and the legacy routes retired; several existing workspace, overview, wait-status and dashboard tests were updated.
- **Model-visible changes:** None. The operations declare no Tool, so no Manager, Worker, Planner or Reviewer prompt and no Manager Tool changed. They do appear in the v1 operation catalog that API clients read.
- **Not confirmed in code:** this draft did not run any test; claims about confirmation and error answers come from the code and the pull request's tests.

## Upgrade and rollback

Re-run `install.sh` once v2.13.80 is published. No data migration. Update any script that used the removed routes. Rolling back to v2.13.79 restores them together with the old dashboard.

### 行为变化与入口

- **三个 v1 操作（[#516](https://github.com/foolzzz/looper/pull/516)）：**新增 `looper/agents/v1_domains/workspaces.py`，注册 `tasks.delete`（风险 `high`）、`workspaces.discard`（风险 `high`）和 `workspaces.check`（风险 `read`），均为 `POST`。请求为封闭对象；`task_id` 不能为空白，`workspace_id` 为 1 到 10^18 − 1 的整数。`workspaces.check` 把原来的查询参数（`dir`、`project_id`、`mode`、`base`，均可选）放进请求体。
- **破坏性调用需确认：**`tasks.delete` 与 `workspaces.discard` 声明为 `confirms=True`，调用可能先返回 `needs_confirmation`（HTTP 202）和影响说明：删除会说明任务、步骤 worktree、任务检出、已保存会话和数据库记录，结果分支保留；丢弃会说明工作区目录与分支。任务不存在或工作区不属于该任务时，影响检查返回 not found。这些操作未标记为仅限操作员，API 客户端可通过确认流程调用；本草稿未运行该流程。
- **清理行为不变：**删除逻辑从 `_handle_task_delete` 移入 `looper/agents/http_server.py` 的 `AgentHTTPServer._delete_task`，检查相同：任务不存在 404，处于活动状态 400（“stop the task before deleting”），任务 worktree 失败 409 且 worktree 保留，然后移除会话并删除数据库记录。结果为 `{deleted: <task_id>}`；丢弃返回 `{workspace}`。
- **响应形态：**结果包在 v1 的 `OpOk.result` 中，错误采用 v1 错误格式，不再是旧的 `{"error": ...}`。
- **移除的路由：**三条旧路由及 `_RE_TASK_WORKSPACE_DISCARD` 分派已从 `looper/agents/http_server.py` 的 HTTP 分派表中移除。
- **仪表盘：**`web/src/lib/api.ts` 中的 `deleteTask`、`discardStepWorkspace`、`checkWorkspace` 调用新操作；这些函数会把确认应答作为错误抛给调用方。
- **测试：**新增 `tests/test_api_v1_task_workspaces.py` 与 `..._db.py`，覆盖 CLI 形态、id 边界、确认与待处理状态、活动任务拒绝、worktree 收尾失败时保留状态、按序删除、丢弃拒绝场景、检查默认值与警告，以及旧路由已下线；并更新了若干现有的工作区、概览、等待状态和仪表盘测试。
- **面向模型的变化：**无。这些操作未声明 Tool，因此 Manager、Worker、Planner、Reviewer 的 prompt 和 Manager Tool 均未改动。它们会出现在 API 客户端读取的 v1 操作目录中。
- **代码中未确认：**本草稿未运行任何测试；关于确认流程和错误应答的说法来自代码以及该 PR 的测试。

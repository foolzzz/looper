# Looper v2.14.112

This is the patch release v2.14.112, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.111: the dashboard Pipeline view now draws AND/OR dependency conditions ([#1177](https://github.com/foolzzz/looper/pull/1177)).

## Release Decision

**Who should upgrade:** Operators who turned on the per-project `dependency_conditions` switch from v2.14.111 and want the Pipeline tab to show what a step waits for. Plans without conditions, and projects with the switch off, are drawn as before.

**What this release solves:** [#1177](https://github.com/foolzzz/looper/pull/1177). In v2.14.111 the Pipeline view drew only the flat `depends_on` list, so an `any_of` or `k_of` condition looked like an AND. Now a plain AND stays a straight edge, while any other condition gets a join node labelled all, any or k of n, edges labelled completed or passed where the leaf asks for that, and its state shown as text and icon, not color alone.

**Breaking changes:** No. Dashboard-only change: no API, schema, server or dependency change.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.14.112
```

**Contributors:** Maintainer @foolzzz authored [#1177](https://github.com/foolzzz/looper/pull/1177); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.111 upgrades directly. There is no schema change.

## Behavior changes

- **Pipeline graph** (`web/src/lib/pipeline-layout.ts`, `web/src/pages/task-detail.tsx`). A step whose `ready_when` is a step id or a nested `all_of` of step ids (a plain AND) keeps its edges from `depends_on` unchanged. Any other `ready_when` on a work, gate or wait step adds one join node per group, placed in the layout row between the dependencies and the step. The node shows the group's label (all, any, or `k/n`) and a state icon with text (satisfied, pending, unsatisfiable). Edges from a leaf that waits for `completed` or `passed` carry that word as a label. The root node uses the API's `ready_state`; nested groups are evaluated in the browser with the same rules (`conditionState`), because the API reports only the root state. Edges and node placement are derived from one shared edge list, so layering and drawing agree. The labels on the graph are in Chinese, as is the rest of the Pipeline view.
- **Step cards** (`web/src/lib/node-cards.ts`). For a non-plain condition, the "Depends on" section of work, gate and wait cards is a text rendering of the condition (for example `全部（a，b）`, `任一（...）`, `k/n（...）`); otherwise it lists the dependency steps as before.
- **Interaction** (`web/src/components/pipeline-node-card.tsx`). Pointer handling for the detail card now ignores graph nodes that have no card, so a join node opens none; join nodes are focusable and carry an accessible label (step, group, state). After data refreshes the graph re-measures node handles so edges stay attached.
- **API types** (`web/src/lib/api.ts`). Types for `Condition`, `ConditionState` and the optional `ready_when` and `ready_state` fields on steps, gates and waits; the server already sends them since v2.14.111.
- **Documentation.** One line added to `docs/plans/2026-10-13-long-horizon-agent-context.zh-CN.md`. New browser test `tests/test_pipeline_conditions_browser.py`; unit tests for the layout and cards extended.
- **Unchanged:** the server, scheduling, the Planner and Manager protocols, the database, the API payloads, Worker and Reviewer behavior, channels (Telegram and Lark), dependencies and billing.
- **Model-visible changes:** None. No prompt, tool schema or tool result changes; the change is in the dashboard only.

### 行为变化与入口

- **流水线图**（`web/src/lib/pipeline-layout.ts`、`web/src/pages/task-detail.tsx`）。`ready_when` 为步骤 id 或仅由步骤 id 组成的嵌套 `all_of`（普通 AND）时，边仍来自 `depends_on`，不变。工作、门禁或等待步骤的其他 `ready_when` 会为每个分组增加一个汇合节点，位于依赖与该步骤之间的布局行。节点显示分组标签（全部、任一或 `k/n`）以及状态图标和文字（已满足、等待中、无法满足）。叶子等待 `completed` 或 `passed` 时，边上带该标签。根节点使用 API 的 `ready_state`；嵌套分组由浏览器按相同规则求值（`conditionState`），因为 API 只报告根状态。布局分层与绘制使用同一份边列表。图上的标签为中文，与流水线视图其余部分一致。
- **步骤卡片**（`web/src/lib/node-cards.ts`）。对非普通条件，工作、门禁和等待卡片的 “Depends on” 部分显示条件的文字形式（如 `全部（a，b）`、`任一（...）`、`k/n（...）`）；否则仍列出依赖步骤。
- **交互**（`web/src/components/pipeline-node-card.tsx`）。详情卡片的指针处理现在忽略没有卡片的图节点，因此汇合节点不会打开卡片；汇合节点可获得焦点，并带有无障碍标签（步骤、分组、状态）。数据刷新后图会重新测量节点连接点，使边保持连接。
- **API 类型**（`web/src/lib/api.ts`）。新增 `Condition`、`ConditionState` 类型，以及步骤、门禁和等待上可选的 `ready_when`、`ready_state` 字段；服务端自 v2.14.111 起已发送这些字段。
- **文档。**`docs/plans/2026-10-13-long-horizon-agent-context.zh-CN.md` 增加一行。新增浏览器测试 `tests/test_pipeline_conditions_browser.py`；布局和卡片的单元测试有扩展。
- **不变：**服务端、调度、Planner 与 Manager 协议、数据库、API 负载、Worker 与 Reviewer 行为、渠道（Telegram 和 Lark）、依赖和计费。
- **面向模型的变化：**无。提示、工具 schema 和工具结果均未改变；改动仅在仪表盘。

# Looper v2.13.154

## Release Decision

**Who should upgrade:** Operators who run Managers on the `api` runtime, or who delete scenario Managers while the service runs. Everyone else can stay on v2.13.153.

**What this release solves:** [#715](https://github.com/foolzzz/looper/pull/715) keeps api Manager sessions consistent across a service restart and a scenario Manager deletion: the context size is restored after a restart so the handoff threshold still applies, a deleted Manager's api session rows go in the same transaction, and an in-flight reply can no longer recreate a deleted session. It covers #710.

**Breaking changes:** No. The new `api_sessions.context_tokens` column is additive and nullable.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#715](https://github.com/foolzzz/looper/pull/715); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.154
```

## Behavior changes

- **Restored context size (#715):** `api_sessions` gains a nullable `context_tokens` column. Each completed request saves the prompt size (a request with unknown usage keeps the earlier value). When a resident api session is resumed, `ApiSession.start` reads the saved value, and the Manager now starts the api session before deciding on a context-full handoff, so a restarted Manager applies the handoff threshold instead of treating the context as empty. A one-time migration (`api_sessions_context_tokens_backfill`) fills existing rows from the latest `llm_records.context_tokens` of the same session.
- **Session creation (#715):** the `api_sessions` row is now created before a new session's first request (`api_sessions.create`) rather than by the first append. If that first request is interrupted or fails before any turn is stored, the row is deleted. `append` refuses a session that no longer exists ("the API session no longer exists") instead of recreating it, and `save_context_tokens` only updates an existing row.
- **Manager deletion (#715):** `ManagerFleet.delete_manager` is new and `managers.delete` (v1) now goes through it. After the refusal checks (tasks, schedules, bots, chat bindings) and under the Manager row lock, it stops the resident Manager and waits for its current turn (`stop_agent(..., strict=True)`), then deletes the session pointer and the api history in the same transaction. Bus messages are settled only after the commit. If the stop fails or the delete rolls back, supervision is restored, the interrupted turn is replayed before the queue without journaling it again, and an enabled Manager keeps running. `stop_agent` gains the keyword `strict`; its default behavior is unchanged.
- **Model-visible changes:** none to prompts, tool descriptions or schemas. A restarted api Manager whose restored context is over the threshold now runs the existing handoff, which sends the existing handoff prompt; before this release it did not. CLI Managers are unchanged.
- **Docs (#715):** the long-horizon agent context plan (Chinese) describes step ⑤ with the saved context size and the delete ordering.
- **Tests (#715):** adds cases to `tests/test_api_session.py`, `tests/test_api_sessions_db.py`, `tests/test_api_context_switch_db.py`, `tests/test_manager_fleet_db.py`, `tests/test_api_transcript_db.py`, `tests/test_api_v1_managers_templates_db.py` and `tests/test_config_transfer_db.py`.

## Upgrade and rollback

Re-run `install.sh` once v2.13.154 is published. Startup adds the `context_tokens` column and runs the one-time backfill. Rolling back to v2.13.153 leaves the column unused; restarted api Managers then lose the restored context size as before.

### 升级决策

**谁需要升级：**在 `api` 运行时上跑 Manager、或在服务运行中删除场景 Manager 的运维者。其他人可留在 v2.13.153。

**解决了什么：**[#715](https://github.com/foolzzz/looper/pull/715) 让 api Manager 会话在服务重启和场景 Manager 删除后保持一致：重启后恢复上下文规模，交接阈值仍然生效；删除 Manager 时在同一事务内删除其 api 会话行；进行中的回复不会再重建已删除的会话。对应 #710。

**是否有破坏性变更：**否。新增的 `api_sessions.context_tokens` 列是增量且可空的。

**如何验证：**运行 `looper --version` 核对版本为 2.13.154。

**贡献者：**维护者 @foolzzz 提交 [#715](https://github.com/foolzzz/looper/pull/715)；本次 patch release 无社区贡献。

```bash
looper --version   # looper 2.13.154
```

### 行为变化与入口

- **恢复上下文规模（#715）：**`api_sessions` 新增可空列 `context_tokens`。每个完成的请求保存提示规模（用量未知时保留之前的值）。恢复驻留 api 会话时 `ApiSession.start` 读取保存值，Manager 现在先启动 api 会话再判断是否需要上下文已满的交接，因此重启后的 Manager 会应用交接阈值，而不是把上下文当作空。一次性迁移（`api_sessions_context_tokens_backfill`）用同一会话最新的 `llm_records.context_tokens` 回填已有行。
- **会话创建（#715）：**新会话首次请求前先创建 `api_sessions` 行（`api_sessions.create`），不再由首次追加创建。若首次请求在存下任何一轮前被中断或失败，该行会被删除。`append` 对已不存在的会话报错（“the API session no longer exists”），不再重建；`save_context_tokens` 只更新已存在的行。
- **删除 Manager（#715）：**新增 `ManagerFleet.delete_manager`，v1 的 `managers.delete` 改走它。在拒绝检查（任务、定时任务、bot、聊天绑定）之后、持有 Manager 行锁时，先停止驻留 Manager 并等待其当前轮结束（`stop_agent(..., strict=True)`），再在同一事务中删除会话指针和 api 历史。总线消息在提交后才结算。若停止失败或删除回滚，会恢复监督，把被中断的轮次排在队列之前重放（不重复写日志），已启用的 Manager 继续运行。`stop_agent` 新增关键字 `strict`，默认行为不变。
- **面向模型的变化：**提示词、工具描述和 schema 均无变化。重启后恢复的上下文超过阈值的 api Manager 现在会执行现有交接，发送现有的交接提示词；此前不会。CLI Manager 不变。
- **文档（#715）：**长程智能体上下文计划（中文）的第 ⑤ 步补充了保存的上下文规模和删除顺序。
- **测试（#715）：**在 `tests/test_api_session.py`、`tests/test_api_sessions_db.py`、`tests/test_api_context_switch_db.py`、`tests/test_manager_fleet_db.py`、`tests/test_api_transcript_db.py`、`tests/test_api_v1_managers_templates_db.py`、`tests/test_config_transfer_db.py` 中新增用例。

### 升级与回退

v2.13.154 发布后重跑 `install.sh`。启动时会添加 `context_tokens` 列并执行一次性回填。回退到 v2.13.153 后该列不再使用，重启的 api Manager 与以前一样不再恢复上下文规模。

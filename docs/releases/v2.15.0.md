# Looper v2.15.0

This is the minor release v2.15.0, not a patch release. It marks the 2.14 series. No pull request was merged after v2.14.193, so this release changes no code: its tree is that of v2.14.193, and only the version number, the changelog entry and this body are new. The sections below summarize what changed across the 2.14 series since v2.14.0, grouped by theme, for an operator who is moving from v2.14.0 (or from the bridge) to the current line. They are the changes a user notices, not every patch; each patch's own release body (`docs/releases/v2.14.N.md`) has the detail.

## What changed in the 2.14 series since v2.14.0

- **Agent rooms and message delivery.** A message in a task's room reaches a running Claude Code run with its text, not as a reminder to poll (v2.14.155), and steers a running Codex run (v2.14.158); runs get room guidance that matches how they receive messages (v2.14.157). Runtimes without deliveries, such as Cursor Agent, still read their inbox. Images and files sent in the dashboard chat or in Lark reach the Manager as attachments (v2.14.154, v2.14.156).
- **Chat channels and Lark.** Lark rich-text posts reach the Manager as text (v2.14.149). A chat binding can admit extra senders (v2.14.82); a bound Lark chat can be opened to everyone in it (`sender_policy: chat`), and bots that @-mention the bot are answered through the `lark-cli` channel's polling (v2.14.175, v2.14.190, v2.14.193). Schedules can notify a group chat bound to a Manager (v2.14.150). Telegram and Lark messages sent while the service restarts or upgrades are delivered afterwards (v2.14.38, v2.14.165, v2.14.169), and Lark catch-up reads a bounded set of threads (v2.14.174).
- **Workflows and the Planner.** Workflow presets fix a task's roles and Agent Profiles, review panels, adjudication of review findings, read-only verification rounds and AND/OR step dependency conditions, and end the result with a process record (v2.14.111 to v2.14.144). They are managed in the dashboard, by the Manager, as project defaults and through config transfer (v2.14.115). A schedule can opt its tasks into user gates (v2.14.13). Planner turns carry plan changes instead of the whole plan (v2.14.138), a Planner's empty reply gets the repair turn an invalid one gets (v2.14.22), and Workers wait without spending (v2.14.137). A profile can name a fallback that takes over when a run fails to launch or exits before any model output (v2.14.110, v2.14.142, v2.14.145).
- **Runtimes and providers.** Cursor Agent (v2.14.77, v2.14.79), Coco (TRAE CLI) (v2.14.128, v2.14.129) and Codex, Cursor Agent or Coco through TTADK (v2.14.28, v2.14.81, v2.14.133) are runtimes of their own, with the built-in `cursor-login` and `coco login` providers. Pi and DSH profiles run on their SDK runners by default, with runners pooled per SDK and startup failures that no longer stop `looper serve` (v2.14.15, v2.14.21, v2.14.23). A provider can be disabled and re-enabled, its model list fetched, and a Custom provider is described by an API format and one base URL (v2.14.88, v2.14.89, v2.14.94). Grok runs can turn off web search per Agent Profile (v2.14.172).
- **The local gateway and request recording.** Claude Code roles can run OpenAI Chat Completions models through Looper's loopback gateway (v2.14.103, v2.14.105), and other Anthropic clients on the machine can use them through the optional local gateway endpoint (v2.14.107), which the Manager can view and change with confirmation (v2.14.178). Request recording keeps the model requests of Claude Code and Model API runs (v2.14.97, v2.14.100), with a dashboard viewer, JSONL export and cache hit rates (v2.14.98, v2.14.106). It is on by default, bounded by age and size (v2.14.104).
- **Command schedules.** A schedule can run a shell command with no agent or model spend. The scheduler runs them and adopts their runs after a restart, and they keep firing while the service drains for an upgrade (v2.14.31, v2.14.33). They are in the schedule API, config transfer, the dashboard (create, edit and run history) and the Manager's schedule tool, with per-schedule alert thresholds and bounded run history (v2.14.35 to v2.14.45).
- **Upgrades and keepers.** `looper service upgrade` executes its plan (`--dry-run` previews it, `--to` names a git ref or wheel), `looper service restart --drain` drains first, and a health probe can be installed (v2.14.28, v2.14.30, v2.14.36). With the opt-in keeper mode (`[agent_host] keeper = "on"`), running Claude Code Workers and Reviewers are held by keeper processes, and a planned control-plane restart detaches and adopts them (v2.14.48 to v2.14.70). Later patches harden the upgrade: it waits for a slow start and for non-keepable runs, reports its blockers, and survives a reused pid (v2.14.152, v2.14.153, v2.14.181).
- **Projects.** An optional `[projects] root` gives every new project its own directory (v2.14.73); a project's directory can be moved together with its files (v2.14.75); a project can be deleted together with its tasks and schedules after confirmation (v2.14.16); a scenario Manager can own a set of projects (v2.14.85, v2.14.95).
- **Dashboard and `loopercli`.** The dashboard home shows the agents running now (v2.14.170), the Tasks page's Running filter lists tasks whose Planner is working (v2.14.78), and Chat lists `loopercli` conversations as their own group (v2.14.80). `loopercli` creates, starts, stops and deletes tasks with short commands (v2.14.109) and prints a command schedule's log (v2.14.39).
- **Performance and stability.** Journal and inbox writes, directory removal, knowledge hashing, the code manifest and process-table reads moved off the event loop (v2.14.183, v2.14.188 to v2.14.192). `system.status` answers from cached check state so every API operation stays under 2 seconds, `runs.list` returns summaries, and API latency is observable (v2.14.177, v2.14.180, v2.14.184). `looper serve` logs each startup step's time and listens sooner (v2.14.83, v2.14.102). Key-shaped values are redacted from run errors (v2.14.146).

## Release Decision

**Who should upgrade:** Operators on any 2.14 release who want the current line, and operators on v2.13.165 or a later 2.13 release who want everything above. An installation older than v2.13.165 must upgrade to v2.13.165 first (see Upgrading).

**What this release solves:** It marks the 2.14 series with a minor version and gives the series one summary. It contains no change that v2.14.193 did not already ship.

**Breaking changes:** No. This release adds no code, schema or interface change over v2.14.193. The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older. For an installation coming from an earlier 2.14 release, the changes that alter a default are listed under Behavior changes.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.15.0
```

**Contributors:** Maintainer @foolzzz authored the changes of the series; no community contribution was included in this release.

## Upgrading

**Bridge boundary, unchanged.** An installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; v2.13.165 contains every historical migration and is the fixed bridge. See the Upgrading section of the v2.14.0 release for the steps and the rollback. An installation on v2.13.165 or a later 2.13 release that has started once, or on any 2.14 release, upgrades directly.

**What the first start changes and backs up.**

- From v2.14.193 to v2.15.0: nothing. The code is identical, so there is no schema change, no new setting and no backup. Run `install.sh` again (it installs the wheel of the latest release) and restart the service. Nothing else is required.
- From an earlier 2.14 release: the 2.14 patches added columns, tables and constraints to the registry (for example workflows, gateway aliases, project activity, a provider's enabled flag and the schedule fields of command schedules), applied by `looper serve` at start. When the start is about to change the schema, `serve` first writes a `pg_dump` backup into the runtime root's `backups/` (newest 5 per database kept) and checks that it can be read. A new, empty database needs none. If there is no usable `pg_dump` or the backup fails, `serve` exits before it changes anything. Having `pg_dump` available, or `[backup]` set in the ops file, is the one thing to check beforehand; `looper doctor` reports it.
- From v2.13.165 or a later 2.13 release: the registry is converted once to schema 4 after a verified full custom-format backup, as in v2.14.0, and the 2.14 additions are applied too.
- Defaults that differ from what an old installation did: Pi and DSH profiles run on their SDK runners (Node 22.19+); set `[runtimes] pi = "cli"` or `[runtimes] dsh = "cli"` in the ops file to keep the CLI, and restart. Request recording is on by default, including after an upgrade when the operator never set it; an explicitly stored off stays off. Keeper mode stays off unless `[agent_host] keeper = "on"` is set. The local gateway, `[projects] root` and workflow presets stay off until an operator sets them up.

**What is refused.** An installation older than v2.13.165, with "upgrade to v2.13.165 or a later 2.13 release first"; any other database; a schema version above 4; a backup that fails or cannot be verified, which stops the start before any change; `looper serve --skip-backup` for the bridge conversion (a later schema change that is not the bridge conversion may still proceed with a warning, which is not advised); a configuration file that is not `looper-config/v4`, and retired fields in it, before anything is written.

**Rollback.** The upgraded schema must not be opened by an older binary. Stop the new service, leave the upgraded database unchanged, restore the verified full backup into a separate database and point the older release at it. Writes made after the backup stay only in the upgraded database. A schema-only dump or a configuration export cannot restore history.

## Behavior changes

No code changed in this release, so it introduces no behavior change of its own. For an installation coming from an earlier 2.14 release, the behavior changes that matter at upgrade are these:

- Pi and DSH profiles use their SDK runners by default (v2.14.21), with an ops-file opt-out to the CLI.
- Model request recording is on by default and bounded by age (1 to 90 days, default 7) and size (256 to 65536 MiB, default 2048) (v2.14.104). Claude subscription runs are recorded only with the separate `include_oauth` setting.
- Pooling, drain and upgrade behavior of runners, keepers and schedules described above.

**Model-visible changes.** None in this release. Within the series, a few patches changed text a model sees (room guidance, how Planner turns carry plan changes, the Planner's adjudication message); each is recorded in its own release body and changelog entry.

## Optional Capability Activation & Use

No new optional capability activation is introduced in this release.

The optional capabilities that the 2.14 series introduced are activated as their own release bodies describe; each is off until an operator sets it up, except request recording, which is on by default since v2.14.104. They are the TTADK Codex runtime and the service health probe and upgrade dry run (v2.14.28, v2.14.30), keeper mode (v2.14.49), the projects root and project directory move (v2.14.73, v2.14.75), the Cursor login provider and Cursor Agent runtime (v2.14.74, v2.14.77), request recording, its viewer and its proxy hardening (v2.14.97 to v2.14.100), the local gateway endpoint (v2.14.107), workflow presets (v2.14.113) and the Coco runtime (v2.14.128, v2.14.129).

**如何验证：**核对版本为 2.15.0。

### 升级

**桥接边界不变。**早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（先升级到 v2.13.165）；v2.13.165 包含全部历史迁移，是固定的桥接版本。步骤与回退见 v2.14.0 发布说明的升级一节。已在 v2.13.165 或更晚 2.13 版本上启动过一次的安装，或任何 2.14 版本，可直接升级。

**首次启动会改变和备份什么。**

- 从 v2.14.193 到 v2.15.0：什么都不变。代码相同，因此没有 schema 变更、没有新设置、没有备份。再次运行 `install.sh`（它安装最新发布的 wheel）并重启服务即可，无需其他操作。
- 从更早的 2.14 版本：2.14 的补丁向 registry 增加了列、表和约束（例如工作流、网关别名、项目活动、提供方的启用标志和命令定时任务的字段），由 `looper serve` 在启动时应用。启动将要改变 schema 时，`serve` 先把 `pg_dump` 备份写入运行时根目录的 `backups/`（每个数据库保留最新 5 份）并检查其可读。全新的空数据库不需要备份。没有可用的 `pg_dump` 或备份失败时，`serve` 在改动任何内容之前退出。需要事先确认的只有一件事：可用的 `pg_dump`，或运维文件中设置了 `[backup]`；`looper doctor` 会报告。
- 从 v2.13.165 或更晚的 2.13 版本：registry 在经过验证的完整自定义格式备份后一次性转换为 schema 4（与 v2.14.0 相同），并同时应用 2.14 的新增内容。
- 与旧安装行为不同的默认值：Pi 和 DSH profile 运行在各自的 SDK runner 上（Node 22.19+）；要保留 CLI，在运维文件中设置 `[runtimes] pi = "cli"` 或 `[runtimes] dsh = "cli"` 并重启。请求记录默认开启，运维人员从未设置过时升级后也是如此；显式保存的关闭状态保持关闭。除非设置 `[agent_host] keeper = "on"`，keeper 模式保持关闭。本地网关、`[projects] root` 和工作流预设在运维人员设置之前保持关闭。

**会被拒绝的情况。**早于 v2.13.165 的安装，提示“upgrade to v2.13.165 or a later 2.13 release first”；任何其他数据库；高于 4 的 schema 版本；失败或无法验证的备份，会在改动前终止启动；桥接转换使用 `looper serve --skip-backup`（非桥接转换的后续 schema 变更仍可带警告继续，但不建议）；不是 `looper-config/v4` 的配置文件及其中的已退役字段，在写入任何内容之前被拒绝。

**回退。**升级后的 schema 不得被旧版本二进制打开。停止新服务，保持升级后的数据库不变，把验证过的完整备份恢复到单独的数据库，并让旧版本指向它。备份之后写入的内容只保留在升级后的数据库中。仅含 schema 的转储或配置导出无法恢复历史。

### 行为变化与入口

本版本不改代码，因此自身没有行为变化。对从更早 2.14 版本升级的安装，升级时值得注意的行为变化是：

- Pi 和 DSH profile 默认使用 SDK runner（v2.14.21），可在运维文件中选择退回 CLI。
- 模型请求记录默认开启，按时长（1 至 90 天，默认 7）和大小（256 至 65536 MiB，默认 2048）限制（v2.14.104）。Claude 订阅 run 仅在单独的 `include_oauth` 设置下才被记录。
- 上文所述 runner、keeper 和定时任务的池化、排空与升级行为。

**面向模型的变化：**本版本没有。系列内少数补丁改动过模型可见的文本（房间指引、Planner 回合携带计划变更的方式、Planner 的裁决消息）；各自记录在对应的发布说明和 changelog 条目中。

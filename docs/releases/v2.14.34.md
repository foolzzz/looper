# Looper v2.14.34

This is the patch release v2.14.34, a hotfix line in which each merged change ships at once. It ships the two changes merged since v2.14.33: command runs survive a failed `ps` and keep their catch-up details through the overlap queue ([#958](https://github.com/foolzzz/looper/pull/958)), and the probe service install checks the port the service really uses and keeps its unit across a failed reinstall ([#961](https://github.com/foolzzz/looper/pull/961)).

## Release Decision

**Who should upgrade:** Anyone who runs command schedules (a failed `ps` could kill a live run), anyone who relies on `LOOPER_SCHEDULE_MISSED_SINCE` for catch-up fires that wait in the overlap queue, and anyone who installs `looper service` with `[probe]` notifications configured.

**What this release solves:** [#958](https://github.com/foolzzz/looper/pull/958) stops a failed, timed-out or empty `ps` from turning a live command runner into a lost run, declares a runner lost at once when its recorded process is confirmed gone, and keeps `missed_since` on queued catch-up fires. [#961](https://github.com/foolzzz/looper/pull/961) makes the probe check the service's real port, and makes install, restart and uninstall keep the probe unit consistent with the service.

**Breaking changes:** No. No API, default or configuration is removed. One additive database migration runs on first start (see Upgrading). The behavior changes are listed below.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#958](https://github.com/foolzzz/looper/pull/958) and [#961](https://github.com/foolzzz/looper/pull/961); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.34
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.33 upgrades directly. This release adds one migration, applied once on the first start of an existing database and recorded in `schema_migrations`; a new database gets it from `schema.sql`:

- `schedule_missed_since` ([#958](https://github.com/foolzzz/looper/pull/958)) adds the nullable column `schedule_runs.missed_since` (`TIMESTAMPTZ`).

It only adds; existing runs read as having no `missed_since`.

## Behavior changes

- **Command runs survive a failed `ps` ([#958](https://github.com/foolzzz/looper/pull/958)).** In `looper/agents/command_runs.py`, the supervisor lists its runners with `ps`.
  - **Observation failure.** A non-zero exit, a timeout, an OS error, or empty output is now an `Unknown` observation. The scheduler leaves such a run unchanged and retries on the next tick, with a logged warning. Before, the run could be judged lost, its command group killed with SIGKILL and the run recorded as `interrupted`. The query always includes the supervisor's own PID, so empty output means `ps` failed even when every runner has ended.
  - **Runner gone.** A run whose recorded runner PID is confirmed gone, or has a different start time, and that has no exit record, is `Lost` at once ("its runner (pid N) ended without recording an exit code"), instead of waiting out the 60-second start grace.
- **Catch-up details through the overlap queue ([#958](https://github.com/foolzzz/looper/pull/958)).** A catch-up fire that waits in the overlap queue keeps its `missed_since`, now stored in `schedule_runs.missed_since` and restored when the queued run starts, so `LOOPER_SCHEDULE_MISSED_SINCE` is set for it. Before, it was empty for such runs.
- **Probe checks the real port ([#961](https://github.com/foolzzz/looper/pull/961)).** In `looper/agents/service.py`, `looper service install` uses an explicit `--port`, else the installed unit's explicit port, else the ops file's port; the ops file's port no longer overrides the installed unit's explicit port. The readiness wait after install and restart connects to the configured host (`::` is checked through `::1`, an empty host, `localhost` and `0.0.0.0` through `127.0.0.1`). `looper service status` still asks `127.0.0.1`.
- **Probe unit across reinstall, restart and uninstall ([#961](https://github.com/foolzzz/looper/pull/961)).**
  - **Install.** The probe unit is no longer deleted before the replacement starts. It is synchronized before the server starts, so a failed start leaves the probe consistent with the new unit. If the ops file has no `[probe]`, install removes any existing probe units.
  - **Restart.** `looper service restart` recreates the probe unit when `[probe]` is configured and the installed probe is missing or does not match the ops file, runtime root and port; the result line then reports the probe. The old in-place port rewrite of the probe is removed.
  - **Uninstall.** Uninstall stops the probe (the timer and the running service on Linux) and waits until it is inactive before removing the units; if that cannot be confirmed within the stop wait it fails and keeps the units. It does nothing for the probe when no probe unit exists.
  - **Docs.** `docs/architecture/agent-system.md` describes the port rule.
- **Model-visible changes:** None for the models' prompts or tools. The only text a model might see is the environment variable `LOOPER_SCHEDULE_MISSED_SINCE` of a command run, now set for queued catch-up fires; no prompt, tool or message text changes.

## 中文摘要

本版本是 patch release v2.14.34（热修线，每个合并的改动立即发布）。自 v2.14.33 以来合并了两项改动：命令运行在 `ps` 失败时不再被误杀，且排队的补跑保留其补跑信息（[#958](https://github.com/foolzzz/looper/pull/958)）；probe 服务安装检查服务真正使用的端口，并在重装失败时保留 probe 单元（[#961](https://github.com/foolzzz/looper/pull/961)）。

### 升级决策

**谁需要升级：**运行命令类定时任务的人（`ps` 失败可能杀掉存活的运行）、依赖 `LOOPER_SCHEDULE_MISSED_SINCE` 的排队补跑的人，以及配置了 `[probe]` 通知并安装 `looper service` 的人。

**解决了什么：**[#958](https://github.com/foolzzz/looper/pull/958) 让失败、超时或为空的 `ps` 不再把存活的命令 runner 判为丢失；runner 进程确认已消失时立即判为丢失；排队的补跑保留 `missed_since`。[#961](https://github.com/foolzzz/looper/pull/961) 让 probe 检查服务的真实端口，并让安装、重启和卸载保持 probe 单元与服务一致。

**是否有破坏性变更：**否。不移除任何 API、默认值或配置；首次启动会执行一项增量数据库迁移（见升级一节）。行为变化见下。

**如何验证：**运行 `looper --version` 核对版本为 2.14.34。

**贡献者：**维护者 @foolzzz 提交 [#958](https://github.com/foolzzz/looper/pull/958) 和 [#961](https://github.com/foolzzz/looper/pull/961)；本版本无社区贡献。

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.33 上的安装可直接升级。本版本新增一项迁移，在已有数据库首次启动时执行一次并记入 `schema_migrations`，新数据库由 `schema.sql` 创建：

- `schedule_missed_since`（[#958](https://github.com/foolzzz/looper/pull/958)）新增可为空的列 `schedule_runs.missed_since`（`TIMESTAMPTZ`）。

迁移只新增；已有的运行读作没有 `missed_since`。

### 行为变化与入口

- **命令运行在 `ps` 失败时不再被误杀（[#958](https://github.com/foolzzz/looper/pull/958)）。**`looper/agents/command_runs.py` 用 `ps` 列出 runner。
  - **观测失败。**非零退出、超时、OS 错误或空输出现在是 `Unknown` 观测。调度器保持该运行不变，下一个 tick 重试并记录警告。此前该运行可能被判为丢失、命令组被 SIGKILL，并记为 `interrupted`。查询总是带上监督进程自己的 PID，所以即使所有 runner 都已结束，空输出也表示 `ps` 失败。
  - **runner 已消失。**记录的 runner PID 确认已消失或启动时间不符、且没有退出记录的运行，立即判为 `Lost`（“its runner (pid N) ended without recording an exit code”），不再等 60 秒启动宽限期。
- **排队补跑保留补跑信息（[#958](https://github.com/foolzzz/looper/pull/958)）。**在重叠队列中等待的补跑保留其 `missed_since`，现存于 `schedule_runs.missed_since`，排队的运行启动时恢复，因此 `LOOPER_SCHEDULE_MISSED_SINCE` 会被设置；此前这类运行为空。
- **probe 检查真实端口（[#961](https://github.com/foolzzz/looper/pull/961)）。**`looper/agents/service.py` 中，`looper service install` 使用显式 `--port`，否则用已安装单元的显式端口，再否则用 ops 文件的端口；ops 文件的端口不再覆盖已安装单元的显式端口。安装和重启后的就绪等待连接配置的主机（`::` 通过 `::1` 检查，空主机、`localhost` 和 `0.0.0.0` 通过 `127.0.0.1`）。`looper service status` 仍询问 `127.0.0.1`。
- **重装、重启和卸载时的 probe 单元（[#961](https://github.com/foolzzz/looper/pull/961)）。**
  - **安装。**不再在替换服务启动前删除 probe 单元，而是在服务启动前同步，因此启动失败时 probe 仍与新单元一致。ops 文件没有 `[probe]` 时，安装会移除已有的 probe 单元。
  - **重启。**配置了 `[probe]` 且已安装的 probe 缺失或与 ops 文件、运行时根目录和端口不符时，`looper service restart` 重建 probe 单元，结果行会报告 probe。原先就地改写 probe 端口的逻辑已移除。
  - **卸载。**卸载先停止 probe（Linux 上包括 timer 和运行中的 service）并等到其不活动后再移除单元；若在停止等待时间内无法确认，则失败并保留这些单元。没有 probe 单元时不对 probe 做任何事。
  - **文档。**`docs/architecture/agent-system.md` 描述了端口规则。
- **面向模型的变化：**模型的提示词和工具无变化。模型唯一可能看到的是命令运行的环境变量 `LOOPER_SCHEDULE_MISSED_SINCE`，它现在会为排队的补跑设置；提示词、工具或消息文本都不变。

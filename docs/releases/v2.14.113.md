# Looper v2.14.113

This is the patch release v2.14.113, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.112: operator-defined workflow presets that are snapshotted into tasks ([#1176](https://github.com/foolzzz/looper/pull/1176)).

## Release Decision

**Who should upgrade:** Operators who want to define named workflows (fixed work and review roles, per-task execution rules, Planner instructions) and start tasks from them through the API or `loopercli`. Everyone else can stay on v2.14.112: a task created without a workflow, in a project with no default workflow, is planned and run as before.

**What this release solves:** [#1176](https://github.com/foolzzz/looper/pull/1176). Until now the only reusable task shape was a task template. An operator can now store a workflow, pick it when a task is created, and the task keeps its own snapshot: later edits or deletion of the workflow do not change running or past tasks. The workflow's roles become task roles that the Planner cannot redefine, its execution rules apply to that task, and the Planner is told about it.

**Breaking changes:** No. Additive: new operator-only operations, an optional `workflow` field on task creation, and an automatic additive database migration. Tasks and plans without a workflow behave as before.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.14.113
```

**Contributors:** Maintainer @foolzzz authored [#1176](https://github.com/foolzzz/looper/pull/1176); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.112 upgrades directly.

This release changes the database schema. On first start it creates the `workflows` table, adds `projects.default_workflow` and `tasks.workflow`, and widens the `task_roles` origin check to accept `workflow`. The migration runs once and is recorded; existing rows are untouched. Do not roll back to an earlier release after creating a task from a workflow: that earlier release does not know the new role origin, and this was not tested.

## Behavior changes

- **Workflow definitions** (`looper/agents/workflows.py`, `looper/db/workflows.py`). A workflow has a key (lowercase, at most 32 characters, not `none`), a unique name (at most 60 characters, one line), a description, Planner instructions (at most 8,000 characters), Agent Profile ids for the planner, worker and reviewer, up to 8 fixed roles (work or review, each with a prompt, optional harness and optional profile), a default work role, a retry limit (0 to 20), review-all, dependency conditions, a task budget, user gates on exhaustion and other fields. A definition is validated before it is stored, including that referenced roles exist and that Agent Profiles are usable and compatible.
- **API and CLI** (`looper/agents/v1_domains/workflows.py`). Four operator-only operations: `workflows.list`, `workflows.get`, `workflows.put` (create or replace) and `workflows.delete` (high risk, asks for confirmation), reachable as `loopercli workflows <action>`. Replacing or deleting a workflow never alters existing task snapshots; deleting also clears project defaults that name it.
- **Task creation** (`looper/agents/projects.py`, `looper/agents/v1_domains/task_create.py`). Task creation accepts `workflow` (a key, or `none`); `loopercli create --workflow <key>` sets it, and the channel task-creation tools take the same field. Without it, the project's `default_workflow` is used, except for scheduled tasks and tasks created from a template. A workflow and a template cannot be selected together (rejected as invalid). The workflow's Agent Profiles are applied to the task; a conflicting profile chosen for the same role is refused. The workflow's budget becomes the task's budget. The creation confirmation and the configuration summary name the workflow and show the effective review, retry, dependency-condition and budget settings. The full definition is stored on the task (`tasks.workflow`) and returned as `workflow` in the task list and detail views.
- **Execution** (`looper/agents/project_execution.py`, `looper/agents/tiers/planner.py`). For a task with a workflow, its snapshot overlays the project's settings: review policy (all steps when `review_all`, otherwise the Planner's choice), dependency conditions on or off, the retry limit when set, and user gates when `escalate_on_exhaustion` is set. A work step with no role uses the workflow's default work role; gates and waits never get one.
- **Task roles** (`looper/agents/task_roles.py`, `looper/agents/ops/planner.py`, `looper/db/tasks.py`). Workflow roles are written as version 1 task roles with origin `workflow`, and are restored from the snapshot when a task is planned anew. The Planner's role tool refuses to redefine one. A task with a workflow roles list can use only those roles, even where the project does not let Planners define roles. Roles from a workflow are exempt from the project's Agent Profile allow-list.
- **Schema** (`looper/db/connection.py`, `looper/db/schema.sql`). Described under Upgrading.
- **Stored but not yet acted on.** A definition can also carry a review panel, adjudication, verification, phase notices and a distinct-reviewer-runtime requirement. These are validated and stored, and the runtime-distinctness requirement is checked when the definition is saved and when a task is created. Nothing at run time executes a review panel, adjudication, verification or phase notices yet: the validation document lists review-panel execution and verification enforcement as later stages. Do not rely on them in this release.
- **Not included.** No dashboard controls, no Manager workflow discovery, no configuration transfer, and no API to set a project's default workflow (the column exists and is honoured when set). No frontend assets changed.
- **Unchanged:** tasks without a workflow, scheduling, channels (Telegram and Lark), the Worker and Reviewer prompts, dependencies and billing. Existing tests pin the Planner, Worker and Reviewer prompts without a workflow.
- **Model-visible changes:** Only for a task that has a workflow, plus tool schemas for everyone. (1) The Planner's task section gains a "Workflow:" line, the rules code enforces (retry limit, review policy, dependency conditions, spending cap, user gates, fixed roles, default work role) and the operator's Planner instructions under "Workflow instructions". (2) For a task with workflow roles, the Planner's reply contract carries a role section for fixed workflow roles instead of the project role section. (3) The Planner's role views mark workflow roles `from_workflow`, and the refusal to redefine a role reads "the workflow defines role ..." (the wording for user-edited roles changes slightly too). (4) The task-creation tool gains an optional `workflow` property, in the Manager's tool and in the client tools; its description says "An operator workflow key, or none to run without the project's default; cannot be combined with a template." Worker and Reviewer prompts are not changed. The prompts and tools of tasks without a workflow differ only by that tool property.

## Optional Capability Activation & Use

### Workflow presets

**Activation:** Opt-in and operator-only. Nothing changes until an operator stores a workflow with `workflows put` and selects it for a task with `--workflow` (or sets a project's `default_workflow` in the database; no API does that yet).

**Validation:** `loopercli workflows get --key <key>` reads a definition back; the created task's detail view shows its `workflow` snapshot and the configuration summary names it. See the validation document for what the change was checked against.

**Disable / rollback:** Create tasks with `--workflow none`, or delete the workflow (`workflows delete` clears project defaults; existing tasks keep their snapshot). Rolling back to an earlier release after creating a workflow task is not supported (see Upgrading).

**Authority boundary:** The operations are operator-only; client tokens and the Planner cannot create, change or delete workflows. A workflow can fix Agent Profiles and role prompts for a task and set its budget and review rules, so it carries the operator's authority into every task that uses it. The Planner cannot redefine its roles.

**Docs:** https://github.com/foolzzz/looper/blob/v2.14.113/docs/validation/workflow-presets-entity.md

```bash
loopercli workflows put --body workflow.json
loopercli workflows list
loopercli create --requirement "Build" --project Example --workflow reviewed
  # Disable:
loopercli workflows delete --key reviewed
```

## 中文摘要

本版本是 patch release v2.14.113（热修线，每个合并的改动立即发布）。自 v2.14.112 以来只合并了一项改动：运维人员定义的工作流预设，并在创建任务时快照进任务（[#1176](https://github.com/foolzzz/looper/pull/1176)）。

### 升级决策

**谁需要升级：**想定义命名工作流（固定的工作与评审角色、任务级执行规则、Planner 指令），并通过 API 或 `loopercli` 用它启动任务的运维人员。其他人可留在 v2.14.112：不带工作流、且项目没有默认工作流的任务，规划与运行方式不变。

**解决了什么：**[#1176](https://github.com/foolzzz/looper/pull/1176)。此前可复用的任务形态只有任务模板。现在运维人员可以保存工作流、在创建任务时选用，任务保留自己的快照：之后修改或删除工作流不影响运行中和已有的任务。工作流的角色成为 Planner 不能重新定义的任务角色，其执行规则作用于该任务，Planner 也会被告知。

**是否有破坏性变更：**否。纯新增：新的仅运维人员可用的操作、任务创建上可选的 `workflow` 字段，以及自动执行的增量数据库迁移。不带工作流的任务和计划行为不变。

**如何验证：**核对版本为 2.14.113。

**贡献者：**维护者 @foolzzz 提交 [#1176](https://github.com/foolzzz/looper/pull/1176)；本版本无社区贡献。

```bash
looper --version   # looper 2.14.113
```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.112 上的安装可直接升级。

本版本变更数据库结构。首次启动时创建 `workflows` 表，新增 `projects.default_workflow` 和 `tasks.workflow`，并放宽 `task_roles` 的来源检查以接受 `workflow`。迁移只执行一次并被记录，现有数据不变。创建过基于工作流的任务之后，不要回退到更早的版本：更早的版本不认识新的角色来源，且此点未经测试。

### 行为变化与入口

- **工作流定义**（`looper/agents/workflows.py`、`looper/db/workflows.py`）。工作流包含 key（小写，最长 32 字符，不能是 `none`）、唯一的名称（最长 60 字符，单行）、描述、Planner 指令（最长 8000 字符）、planner/worker/reviewer 的 Agent Profile id、最多 8 个固定角色（工作或评审，各有提示词、可选 harness 和可选 profile）、默认工作角色、重试上限（0 到 20）、全部评审、依赖条件、任务预算、耗尽时开启用户门禁等字段。定义在保存前校验，包括所引用的角色存在、Agent Profile 可用且兼容。
- **API 与 CLI**（`looper/agents/v1_domains/workflows.py`）。四个仅运维人员可用的操作：`workflows.list`、`workflows.get`、`workflows.put`（创建或替换）和 `workflows.delete`（高风险，需确认），可通过 `loopercli workflows <action>` 调用。替换或删除工作流不会改变已有任务的快照；删除还会清除指向它的项目默认值。
- **任务创建**（`looper/agents/projects.py`、`looper/agents/v1_domains/task_create.py`）。任务创建接受 `workflow`（key 或 `none`）；`loopercli create --workflow <key>` 设置它，渠道的任务创建工具也接受同一字段。未指定时使用项目的 `default_workflow`，但定时任务和来自模板的任务除外。工作流与模板不能同时选择（按无效请求拒绝）。工作流的 Agent Profile 会应用到任务；为同一角色另选冲突的 profile 会被拒绝。工作流的预算成为任务预算。创建确认和配置摘要会写出工作流，并显示生效的评审、重试、依赖条件和预算设置。完整定义存入任务（`tasks.workflow`），并在任务列表和详情中以 `workflow` 返回。
- **执行**（`looper/agents/project_execution.py`、`looper/agents/tiers/planner.py`）。对带工作流的任务，其快照覆盖项目设置：评审策略（`review_all` 时每一步评审，否则由 Planner 决定）、依赖条件开关、设置了则覆盖重试上限、设置了 `escalate_on_exhaustion` 则开启用户门禁。没有指定角色的工作步骤使用工作流的默认工作角色；门禁和等待步骤不会有角色。
- **任务角色**（`looper/agents/task_roles.py`、`looper/agents/ops/planner.py`、`looper/db/tasks.py`）。工作流角色以来源 `workflow` 写成第 1 版任务角色，任务重新规划时从快照恢复。Planner 的角色工具拒绝重新定义它们。带工作流角色列表的任务只能使用这些角色，即使项目不允许 Planner 定义角色。工作流角色不受项目 Agent Profile 允许列表限制。
- **数据库结构**（`looper/db/connection.py`、`looper/db/schema.sql`）。见“升级”。
- **已保存但尚未生效。**定义还可携带评审小组、仲裁、验证、阶段通知和“评审运行时须不同”要求。这些会校验并保存，其中运行时不同的要求在保存定义和创建任务时检查。运行时尚不会执行评审小组、仲裁、验证和阶段通知：验证文档把评审小组执行和验证强制列为后续阶段。本版本不要依赖它们。
- **未包含。**没有仪表盘控件，没有 Manager 的工作流发现，没有配置迁移，也没有设置项目默认工作流的 API（该列已存在，设置后会生效）。前端资源未改。
- **不变：**不带工作流的任务、调度、渠道（Telegram 和 Lark）、Worker 与 Reviewer 提示词、依赖和计费。现有测试固定了无工作流时 Planner、Worker 和 Reviewer 的提示词。
- **面向模型的变化：**仅对带工作流的任务，外加所有人的工具 schema。（1）Planner 的任务部分增加“Workflow:”行、由代码强制的规则（重试上限、评审策略、依赖条件、花费上限、用户门禁、固定角色、默认工作角色）以及“Workflow instructions”下运维人员的 Planner 指令。（2）对有工作流角色的任务，Planner 的回复契约用固定工作流角色的说明代替项目角色说明。（3）Planner 的角色视图把工作流角色标为 `from_workflow`，拒绝重新定义时的文字为 “the workflow defines role ...”（用户编辑角色的拒绝文字也略有变化）。（4）任务创建工具新增可选的 `workflow` 属性，位于 Manager 的工具和客户端工具中，其描述为 “An operator workflow key, or none to run without the project's default; cannot be combined with a template.”。Worker 和 Reviewer 提示词未改。不带工作流的任务，其提示词和工具仅相差该工具属性。

### 可选能力启用与使用

#### Workflow presets

**启用：**需主动启用，且仅限运维人员。在运维人员用 `workflows put` 保存工作流并在任务上用 `--workflow` 选用它（或在数据库里设置项目的 `default_workflow`；暂无 API 可设置）之前，一切不变。

**验证：**`loopercli workflows get --key <key>` 读回定义；创建出的任务详情显示其 `workflow` 快照，配置摘要会写出它。该改动的检查范围见验证文档。

**停用 / 回退：**用 `--workflow none` 创建任务，或删除工作流（`workflows delete` 会清除项目默认值；已有任务保留快照）。创建过工作流任务后不支持回退到更早版本（见“升级”）。

**权限边界：**这些操作仅限运维人员；客户端令牌和 Planner 不能创建、修改或删除工作流。工作流可以为任务固定 Agent Profile 与角色提示词，并设定预算和评审规则，因此它把运维人员的权限带入每个使用它的任务。Planner 不能重新定义其角色。

**文档：**https://github.com/foolzzz/looper/blob/v2.14.113/docs/validation/workflow-presets-entity.md

```bash
loopercli workflows delete --key reviewed
```

# Looper v2.13.157

## Release Decision

**Who should upgrade:** Operators who want to permanently remove the stored history of Managers they deleted long ago. Everyone else can stay on v2.13.156.

**What this release solves:** [#728](https://github.com/foolzzz/looper/pull/728) adds an operator-only preview and irreversible purge of a deleted Manager's chat message bodies, run records with their events, and action records, once a retention window has passed. The Manager and its thread ownership rows are kept as identity tombstones.

**Breaking changes:** No. Nothing is removed automatically, and the new operations are opt-in. There is no schema migration.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#728](https://github.com/foolzzz/looper/pull/728); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.157
```

## Behavior changes

- **Two operator-only operations (#728):** `manager_cleanup.preview` (risk `read`) and `manager_cleanup.purge` (risk `high`, needs a confirmation) are served at `/api/v1/manager_cleanup/preview` and `/api/v1/manager_cleanup/purge` (`looper/agents/v1_domains/manager_cleanup.py`) and appear in the generated OpenAPI document and the generated `loopercli manager-cleanup`. They take `manager_id` and `retention_days` (integer 30 to 3650, default 30) and return eligibility, blockers, counts and whether the purge ran. The confirmation text states the counts and that the loss is irreversible.
- **Eligibility (#728):** the target must be a deleted, disabled, non-default Manager whose deletion is at least `retention_days` old, judged by the database transaction time (`looper/db/manager_cleanup.py`). Any task, bot (channel config), chat binding or schedule of the Manager, or a run record still `running`, blocks it. The default Manager and unknown ids are refused with a conflict.
- **Runtime retirement (#728):** the preview and the purge also ask the fleet (`cleanup_blockers` in `looper/agents/managers.py`) and block while the Manager has a live agent or turn (a suspended idle process still counts as live), is retiring, has pending synchronization or retries, pending bus messages, or undelivered outbound messages. Purge holds the fleet lock (`cleanup_guard`) and the Manager row lock, and rechecks both before deleting.
- **What is deleted (#728):** in one transaction, which commits entirely or rolls back: chat messages of threads owned by exactly this Manager, its run records (`llm_records.agent_id`) with their events through the existing cascade, and its action records (`manager_actions.manager_id`). The `managers` row and the `chat_threads` rows stay, so the key cannot be reused and old sessions cannot be reassigned; `counts.threads` reports these retained rows, not rows to delete. Repeating a purge deletes zero rows. Run files, channel discovery and rejection records, and projects, tasks and Planner data are not touched.
- **Audit (#728):** the preview records a read action (target and retention days only, no content) in the default operator action stream. The purge's own record is written the same way by the existing operation path and not under the purged Manager.
- **Dashboard (#728):** Settings → Managers has a collapsed "清理已删除 Manager 的历史（仅操作员）" control (`web/src/components/manager-cleanup.tsx`). The operator enters a Manager id and retention days, previews, and confirms the purge in a dialog. Changing an input discards the preview, and a failed request requires a new preview.
- **Docs (#728):** the Chinese scenario-Managers RFC and the long-horizon plan describe the feature and drop the old "no cleanup tool" to-do.
- **Model-visible changes:** none. The operations are operator-only and are not Manager tools or channel capabilities; no prompts, tool descriptions or tool schemas change. The `/api/v1` OpenAPI document gains the two operations.

## Upgrade and rollback

Re-run `install.sh`. No migration runs and no data changes until an operator confirms a purge. Rolling back to v2.13.156 removes the operations; purged history is not restored.

## Optional Capability Activation & Use

### Manager history cleanup

**Activation:** Off until used. In Settings → Managers open the cleanup control, or call `manager_cleanup.preview` and `manager_cleanup.purge` through `/api/v1` or `loopercli manager-cleanup`.

**Validation:** Delete a scenario Manager, then preview it with the minimum 30-day retention and check that it is reported as not yet eligible with the retention blocker. Use a Manager deleted at least 30 days ago to see the counts and a purge.

**Disable / rollback:** Do not run a purge; there is no background cleaner to switch off. A completed purge cannot be undone.

**Authority boundary:** Operator-only; client tokens and Manager tools cannot reach it. It deletes only history owned by the one named deleted Manager and keeps the Manager and thread ownership rows. It adds no tools and no permissions.

**Docs:** [Agent system](https://github.com/foolzzz/looper/blob/v2.13.157/docs/architecture/agent-system.md).

### 行为变化与入口

- **两个仅限操作员的操作（#728）：**`manager_cleanup.preview`（风险 `read`）和 `manager_cleanup.purge`（风险 `high`，需确认）位于 `/api/v1/manager_cleanup/preview` 与 `/api/v1/manager_cleanup/purge`（`looper/agents/v1_domains/manager_cleanup.py`），出现在生成的 OpenAPI 文档和生成的 `loopercli manager-cleanup` 中。参数为 `manager_id` 和 `retention_days`（整数 30 至 3650，默认 30），返回资格、阻止原因、数量及是否已清理。确认文案写明数量和不可恢复。
- **资格（#728）：**目标必须是已删除、已停用的非默认管家，且删除时间已满 `retention_days`，以数据库事务时间判断（`looper/db/manager_cleanup.py`）。管家仍有任务、机器人（渠道配置）、聊天绑定或定时任务，或有状态仍为 `running` 的运行记录，都会阻止。默认管家和未知 id 会以冲突拒绝。
- **运行时退役（#728）：**预览和清理还会询问 fleet（`looper/agents/managers.py` 的 `cleanup_blockers`），在管家仍有存活 agent 或回合（已挂起的空闲进程也算存活）、正在退役、有待处理的同步或重试、总线待处理消息或未送达的出站消息时阻止。清理持有 fleet 锁（`cleanup_guard`）和管家行锁，并在删除前重新检查。
- **删除内容（#728）：**在一个事务中全部提交或全部回滚：由该管家精确拥有的线程的聊天消息、其运行记录（`llm_records.agent_id`）及经现有级联删除的事件、其操作记录（`manager_actions.manager_id`）。`managers` 行和 `chat_threads` 行保留，因此 key 不能重用、旧会话不能被重新分配；`counts.threads` 表示保留的行数，而非待删除行数。重复清理删除零行。运行文件、渠道发现和拒绝记录，以及项目、任务和 Planner 数据均不触及。
- **审计（#728）：**预览在默认操作员操作流中记录一条读取操作（只含目标和保留天数，不含内容）。清理自身的记录由现有操作路径以同样方式写入，不写在被清理的管家名下。
- **控制台（#728）：**设置 → 管家有一个折叠的“清理已删除 Manager 的历史（仅操作员）”控件（`web/src/components/manager-cleanup.tsx`）。操作员填写管家 id 和保留天数，预览后在对话框中确认清理。修改输入会丢弃预览，请求失败后需重新预览。
- **文档（#728）：**中文的场景管家 RFC 和长程计划描述了该功能，并去掉“没有清理工具”的旧待办。
- **面向模型的变化：**无。这些操作仅限操作员，不是管家工具或渠道能力；提示词、工具描述和工具 schema 均未变化。`/api/v1` 的 OpenAPI 文档新增这两个操作。

### 升级与回退

重新运行 `install.sh`。不执行迁移，操作员确认清理前不会改动任何数据。回退到 v2.13.156 会移除这些操作；已清理的历史不会恢复。

### 可选能力启用与使用

#### Manager history cleanup

**启用：**使用前保持关闭。在设置 → 管家中打开清理控件，或通过 `/api/v1` 或 `loopercli manager-cleanup` 调用 `manager_cleanup.preview` 与 `manager_cleanup.purge`。

**验证：**删除一个场景管家，以最短 30 天保留期预览，确认它被报告为尚不符合条件并带有保留期阻止原因。用一个删除已满 30 天的管家查看数量并执行清理。

**停用 / 回退：**不执行清理即可；没有需要关闭的后台清理器。已完成的清理无法撤销。

**权限边界：**仅限操作员；客户端令牌和管家工具无法访问。只删除被点名的已删管家自己的历史，并保留管家和会话归属记录。不新增工具和权限。

**文档：**[Agent system](https://github.com/foolzzz/looper/blob/v2.13.157/docs/architecture/agent-system.md)。

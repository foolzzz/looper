# Looper v2.12.2

## Release Decision

**Who should upgrade:** Operators using recurring schedules who want the Planner to remember earlier runs' requirements and work, and operators needing explicit session reset and safe fallback when a stored conversation cannot be reused.

**What this release solves:** Non-parallel schedules (`skip` or `queue`) continue one stored Planner session across runs. Each trigger still creates a separate task; run records, budgets, timeouts and activity remain per run. Each run's requirement, including its run context and gate output, is also placed in the conversation for later runs to remember. Session ownership, reset and restore checks prevent two live Planners from using the same session. See [#249](https://github.com/foolzzz/looper/pull/249).

**Breaking changes:** No. Existing schedule settings remain compatible. There is a deliberate default-behavior change: after upgrade, every non-parallel schedule continues its Planner from its second run onward, without an activation switch. Failure, requirement edits, timing edits and gate edits do not reset the stored session. Reset makes the next run fresh; subsequent runs continue again.

**How to verify:** Re-run `install.sh`, restart with the existing configuration and runtime root, and check the version below. On a disposable server, run a non-parallel schedule whose first requirement contains a code word. Remove the word from its next requirement and ask the second run to recall it; check the continuation activity and task badge. Confirm Reset Planner session, read back that no session is stored, then run again and check that it starts fresh. Check parallel and unavailable-session fallbacks separately.

**Contributors:** Release maintainer @foolzzz; no community contribution in [#249](https://github.com/foolzzz/looper/pull/249).

```bash
looper --version   # looper 2.12.2
looper doctor
```

## Changes

- **A schedule keeps its Planner conversation.** Non-parallel runs claim the stored session while preserving independent tasks, run accounting, budgets and timeouts. The continued run is told to treat earlier plans and step identifiers as history and plan the current task with new step identifiers. Its requirement is kept in the PLAN user message, subject to the same clipping limit as the Task section, so subsequent runs can remember inputs that were previously only in the changing system prompt. Ordinary tasks and parallel runs keep their existing PLAN message.
- **Reset is explicit.** The dashboard's Reset Planner session button and `POST /api/schedules/<id>/reset-planner-session` clear the stored session and its holder. The Manager's `looper_schedules` action `reset_planner_session` requires user confirmation. An in-progress run keeps its own session until it finishes and cannot write it back after reset. Session state is runtime state: configuration export does not include it and import does not restore it. Unresumable sessions can be replaced through fallback without performing a user reset.
- **Storage and ownership survive reset and restart.** Restore checks both the schedule holder and other live tasks using the session. Failed checks refuse shared-session resume and writeback. A run starting a fresh session after giving up the shared conversation uses its own task storage label, persisted before launch; a stale saved label cannot send a fresh session into another run's storage after reset or restart. A holder replacing an unusable session saves the replacement back for the next run, including after a server restart.

## Optional Capability Activation & Use

### Schedule Planner session

**Activation:** No new switch. Existing and new schedules with overlap `skip` or `queue` retain a Planner session automatically; the first run after upgrade establishes it and the second can continue it. Parallel schedules do not read or write the stored conversation. The dashboard shows Planner session status and a continuation badge on tasks that actually resumed it; the API exposes status without exposing the session identifier.

**Validation:** Check the version, then use a disposable schedule for the code-word and reset sequence above. Read back session status from `GET /api/schedules/<id>` and `continues_schedule_session` from `GET /api/tasks/<id>`. A successful resume records `Continuing the schedule's Planner session`. Check the fallback activity below when a session cannot safely be used.

```bash
looper --version
looper doctor
```

**Disable / rollback:** Reset Planner session clears the conversation for the next run; it is not a persistent opt-out. Pause the schedule to stop future runs, or reinstall v2.12.1 to restore a fresh Planner conversation per run. Changing overlap to `parallel` bypasses session sharing but also changes concurrency semantics; it is not an equivalent disable switch.

**Authority boundary:** The dashboard reset asks for confirmation. The HTTP reset uses the same caller checks as schedule updates and deletion; it returns HTTP 404 for an unknown schedule, otherwise `{"cleared": true}` or `{"cleared": false}`. Telegram and Lark reach reset through the Manager's schedules tool and its user-confirmation step, without separate channel commands. There is no new CLI command because the shared scheduler and Planner implement continuity. Reset does not cancel an active task, erase earlier tasks or merge their budgets.

**Docs:** [Schedule Planner session design](https://github.com/foolzzz/looper/blob/main/docs/architecture/rfcs/schedule-planner-session-v0.zh-CN.md).

## Fallback activity

Fallback does not invoke user reset. If the current holder replaces an unusable session, the replacement is saved for later runs; parallel runs and runs refused ownership leave the stored session alone.

| Situation | Activity and behavior |
|---|---|
| Parallel overlap | `Schedule Planner session left as stored: this run overlaps (parallel) and starts fresh`; no claim or writeback. |
| Runtime/provider cannot resume, or the stored session is missing or unresumable | `Schedule Planner session replaced: the stored session cannot be resumed (...)` or `Schedule Planner session replaced: the stored session could not be resumed (...)`, followed by `this run starts fresh`; the holder saves its replacement. Existing new-session and resume-error activity also remains. |
| Another live run holds it | `Schedule Planner session not claimed: another active task holds it; this run starts fresh`; restore also refuses a session now held or used by another task and records the new-session reason. |
| A claim or safety check fails | A claim error records `Schedule Planner session not claimed: ...; this run starts fresh`. Restore records the failed holder/occupancy check in its new-session reason, or `Schedule Planner session not resumed: ...` when there is no saved session to drop. Shared-session resume and writeback are refused; the run uses its own storage. |

## Validation

The following are the reported implementation validations for #249, not runtime tests rerun while drafting this release:

- **Four Codex review rounds:** All findings were fixed, with regression tests demonstrated to fail without each fix. These cover two Planners using one session after reset/restore, storage labels across reset and restart, a run retaining its own label after giving up the shared session, occupancy checks failing closed and the holder's replacement session being written back.
- **Real disposable-server run with a sonnet Planner:** Run 2 continued run 1's session and stated a code word present only in run 1's requirement. Reset cleared the stored session; run 3 started fresh. Dashboard screenshots were checked. Reported usage costs are subscription-equivalent dollars, not subscription invoices or a guarantee of future savings.
- **CI:** Green for #249. Cross-run resume on Codex, Grok and OMP is covered by stand-in tests only, not real-runtime validation.

## Remaining limits

- Prompt caching mainly helps when runs are close together. A long-lived conversation can cost more per run as its history grows or its cache expires; continuity does not promise lower costs.
- There is no automatic handoff at a context threshold and no automatic reset for session length. Context compaction belongs to the runtime: Claude Code compacts automatically; long-session compaction on the other runtimes needs verification. An unusable session follows the replacement fallback above.
- Cross-run resume on Codex, Grok and OMP still needs real-runtime verification.
- Changing overlap to `parallel` during a run can leave a stale cost baseline for the next run.

## 中文摘要

### 升级决策

**谁需要升级：**使用重复定时任务、希望 Planner 记住更早运行的需求和工作，以及需要明确重置入口和安全回退的操作者。

**解决了什么：**非并行定时任务（`skip`、`queue`）跨运行续接同一条 Planner 会话；每次触发仍创建独立任务，运行记录、预算、超时和活动按次计算。每轮需求连同运行上下文、前置检查输出也写进对话，让后续运行能记住早先输入。认领、重置和恢复检查避免两个活跃 Planner 使用同一会话。见 [#249](https://github.com/foolzzz/looper/pull/249)。

**是否有破坏性变更：**无。已有定时任务设置兼容，但默认行为改变：升级后所有非并行定时任务从第二轮起续接 Planner，无需开关。失败以及修改需求、时间规则或前置检查均不自动重置；用户重置后下一轮全新，再往后的运行恢复续接。

**如何验证：**重跑 `install.sh`，使用原配置和 runtime root 重启，检查版本。在一次性服务中让首轮需求包含一个暗号，第二轮需求删去暗号再要求回忆，核对续接活动和任务标记；确认重置后读回无会话状态，第三轮应从全新会话开始。另行检查并行和会话不可用时的回退。

**贡献者：**发布维护者 @foolzzz；[#249](https://github.com/foolzzz/looper/pull/249) 无社区贡献。

### 可选能力启用与使用

#### Schedule Planner session

**启用：**无新增开关。已有和新建定时任务只要 overlap 为 `skip` 或 `queue` 就自动保留会话；升级后的首轮建立会话，第二轮可以续接。`parallel` 不读写已存会话。Dashboard 显示会话状态，实际续接的任务显示标记；API 返回状态，不返回会话 id。续接消息要求把旧计划与步骤当作历史，本轮使用新的步骤编号；需求原文按 Task 节的相同上限截断后写入 PLAN 用户消息。普通任务和并行运行的 PLAN 消息不变。

**验证：**检查版本后，在一次性定时任务上完成暗号回忆和重置流程。通过 `GET /api/schedules/<id>` 读回会话状态，通过 `GET /api/tasks/<id>` 检查 `continues_schedule_session`；成功续接记录 `Continuing the schedule's Planner session`。

```bash
looper --version
looper doctor
```

**停用 / 回退：**Reset Planner session 只清空下一轮要接的会话，不是持续关闭开关。暂停定时任务可停止后续运行；回装 v2.12.1 可恢复每轮使用全新 Planner。改为 `parallel` 虽然绕过会话共享，也会改变并发语义，不能视为等价停用方式。

**权限边界：**Dashboard 的 Reset Planner session 按钮需要确认。`POST /api/schedules/<id>/reset-planner-session` 使用与修改、删除定时任务相同的调用者检查，未知任务返回 404，否则返回 `{"cleared": true}` 或 `{"cleared": false}`。飞书与 Telegram 经 Manager 的 `looper_schedules` 动作 `reset_planner_session`，由用户确认后执行；无需新增渠道命令或 CLI 命令。进行中的运行保留自己的会话直到结束，重置后不能写回；重置不取消任务、不删除历史、不合并预算。会话属于运行状态，不随配置导出或导入。

**文档：**[定时任务共用 Planner 会话设计](https://github.com/foolzzz/looper/blob/main/docs/architecture/rfcs/schedule-planner-session-v0.zh-CN.md)。

### 回退活动

- 并行运行全新开始、不认领也不写回，活动为 `Schedule Planner session left as stored: this run overlaps (parallel) and starts fresh`。
- 运行时或 provider 不兼容、会话丢失或无法续接，活动为 `Schedule Planner session replaced: the stored session cannot be resumed (...)` 或 `could not be resumed (...)`，并说明 `this run starts fresh`；仍持有会话的运行把替代会话写回，下一轮接替代会话，不调用用户重置。原有的新会话及续接错误活动保留。
- 其他活跃运行占用会话时，认领记录 `Schedule Planner session not claimed: another active task holds it; this run starts fresh`；恢复时也检查 holder 和其他活跃任务，拒绝重复续接并记录换会话原因。
- 认领失败记录 `Schedule Planner session not claimed: ...; this run starts fresh`；恢复检查失败时，换会话原因说明 holder 或占用查询失败，无会话可丢弃时记录 `Schedule Planner session not resumed: ...`。检查失败即拒绝共享会话续接和写回，避免错误清掉已存会话。
- 放弃共享会话后启动全新会话，使用并先保存本轮任务自己的存储标签；重置或重启后残留的标签不能把新会话带进其他运行的存储。仍持有会话的运行更换不可用会话时，重启后也会写回替代会话。

### 验证与剩余限制

- 以下为 #249 已报告的实现验证，本次起草发布说明未重跑运行时验证。四轮 Codex 评审发现均已修复，回归测试已验证去掉修复会失败：覆盖重置及恢复后两个 Planner 共用会话、重置加重启后的存储标签、放弃共享会话后保留自己的标签、占用检查出错时拒绝共享续接，以及 holder 写回替代会话。
- 一次性服务使用 sonnet Planner：第二轮续接首轮会话，说出仅在首轮需求中出现的暗号；重置清空会话，第三轮全新开始，Dashboard 截图已检查。报告中的花费按订阅等价美元口径，不是订阅账单，也不代表后续必然省钱。#249 的 CI 全绿。
- 提示词缓存主要帮助间隔较近的运行；会话历史增长或缓存过期后，长期会话的单轮花费可能上升。不做上下文阈值自动交接，也不因长度自动重置；由运行时自己压缩。Claude Code 会自动压缩，其他运行时的长会话压缩需要验证。
- Codex、Grok、OMP 的跨轮续接只有运行时替身测试，真实运行仍待验证。运行中把 overlap 改为 `parallel`，可能给下一轮留下过期的花费基线。

# Looper v2.13.53

## Release Decision

**Who should upgrade:** Operators who run Telegram or Lark channels on `looper serve`, in particular those whose startup checks are slow or whose channels receive messages while the server starts. Nobody else needs to act.

**What this release solves:** [#434](https://github.com/foolzzz/looper/pull/434) fixes the open review follow-ups of the channels, serve startup and delivery (#404.1, #404.10, #377): channel bots start receiving only after every enabled Manager is known, they poll before the advisory startup checks, a message queued during startup is no longer delivered twice after the journal replay, and configuration export and import preview read channels on a database that has not yet run the Manager migration.

**Breaking changes:** No. No existing API, configuration or stored data changed.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#434](https://github.com/foolzzz/looper/pull/434); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.53
```

## Behavior changes

- **Channel bots register after the fleet (`looper/agents/serve.py`):** the Telegram bots, then the Lark and Lark bot channels, are registered after the Manager fleet is created, with `fleet.is_running` as the check for a Manager. Before, Telegram bots were registered first with a check that answered "running" for every Manager until the fleet existed. Receiving now starts only once every enabled Manager is known, so backlog is neither lost nor handed to a disabled Manager.
- **Polling before the startup checks (`looper/agents/serve.py`):** the advisory self checks (database, Claude, Codex and Grok login, Lark CLI, git) now run after the channels are registered instead of before. Telegram drops pending updates when polling starts, so messages sent during a slow check are now received. The checks still only warn, in the log and on `/api/status`.
- **No double delivery after replay (`looper/agents/bus.py`):** a journaled message that was queued before `MessageBus.start()` (a channel can receive during the startup checks) is remembered and skipped by the journal replay, so it stays durable but is not delivered a second time. The remembered set is cleared when `start()` finishes.
- **Old status messages are settled at replay (`looper/agents/bus.py`):** an undelivered journal entry that is no longer journaled by the current rules (statuses written by older versions, whose turns ended at the restart) is marked delivered and not replayed.
- **Config export and import preview (`looper/db/config_transfer.py`):** the channel query no longer selects `manager_id`, so `config.export` and `config.import_preview` work on a database whose `channel_configs` table has not yet got that column (before the Manager migration). The exported channel fields are `channel_id`, `channel_type`, `display_name`, `enabled` and `config`.
- **Model-visible changes:** None. No prompt, tool result, channel text or OpenAPI operation changed.
- **Tests added:** The pull request reports added lines: tests 167, production 8 (fixtures excluded). New tests cover the bus replay (`tests/test_agent_bus.py`), serve startup order and channel delivery (`tests/test_serve_channel_bots_db.py`) and export and preview before the Manager migration (`tests/test_config_transfer_channel_bots_db.py`).

## Upgrade and rollback

Re-run `install.sh` once v2.13.53 is published. No data migration. Rolling back to v2.13.52 restores the earlier startup order and replay; nothing is stored differently.

No new optional capability activation is introduced in this release.

### 行为变化与入口

- 渠道机器人在 fleet 之后注册：Telegram 机器人，随后 Lark 与 Lark bot 渠道，在 Manager fleet 创建之后注册，并以 `fleet.is_running` 判断 Manager 是否运行。此前 Telegram 机器人先注册，且在 fleet 存在之前对所有 Manager 都回答“运行中”。现在只有所有已启用的 Manager 都确定后才开始接收，积压消息不会丢失，也不会交给已停用的 Manager。
- 先轮询再自检：建议性自检（数据库、Claude、Codex 与 Grok 登录、Lark CLI、git）现在在渠道注册之后运行，而非之前。Telegram 在开始轮询时会丢弃待处理更新，因此自检较慢期间发送的消息现在能被收到。自检仍只在日志和 `/api/status` 中告警。
- 重放后不再重复投递：在 `MessageBus.start()` 之前已入队的日志消息（渠道可在启动自检期间接收）会被记住，并被日志重放跳过，因此保持持久化但不会被再次投递。`start()` 结束时清空该记录。
- 旧状态消息在重放时结算：按当前规则不再写入日志的未投递条目（旧版本写入的状态消息，其轮次在重启时已结束）会被标记为已投递而不重放。
- 配置导出与导入预览：渠道查询不再选取 `manager_id`，因此 `config.export` 与 `config.import_preview` 可在 `channel_configs` 表尚无该列（Manager 迁移之前）的数据库上工作。导出的渠道字段为 `channel_id`、`channel_type`、`display_name`、`enabled` 和 `config`。
- 面向模型的变化：无。提示词、工具结果、渠道文案和 OpenAPI 操作均未改动。
- 新增测试：PR 报告新增测试 167 行、生产代码 8 行（不含 fixture）。新测试覆盖总线重放（`tests/test_agent_bus.py`）、serve 启动顺序与渠道投递（`tests/test_serve_channel_bots_db.py`）以及 Manager 迁移前的导出与预览（`tests/test_config_transfer_channel_bots_db.py`）。

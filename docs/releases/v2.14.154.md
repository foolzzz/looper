# Looper v2.14.154

This is the patch release v2.14.154, a hotfix line in which each merged change ships at once. It documents one change: [#1278](https://github.com/foolzzz/looper/pull/1278) (a dashboard chat message to a Manager can carry attachments that Looper saves, checks and shows to the Manager).

## Release Decision

**Who should upgrade:** Clients of the dashboard API's `operator_chat.send` that send `attachments`, and operators who want the Manager to read files sent with a chat message. Everyone else gets no change in normal use.

**What this release solves:** [#1278](https://github.com/foolzzz/looper/pull/1278) turns `attachments` from a list of arbitrary objects that was passed through and never read into at most 10 `{filename, content_base64}` files that Looper saves, checks by content and lists in the Manager's turn, so a Manager can open an image, a PDF, an Office file or a text file sent with a message.

**Breaking changes:** Yes, for `operator_chat.send` callers that sent arbitrary `attachments` objects: any item that is not `{filename, content_base64}` is now refused `invalid`, as is a request with more than 10 items or more than 6,000,000 decoded bytes. The PR calls this an intended maintainer decision. There is no migration and no schema change. The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.14.154
```

**Contributors:** Maintainer @foolzzz authored [#1278](https://github.com/foolzzz/looper/pull/1278); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.153 upgrades directly. There is no schema change.

## Behavior changes

- **Attachment input** ([#1278](https://github.com/foolzzz/looper/pull/1278), `looper/agents/v1_domains/operator_chat_streams.py`). The `attachments` argument of `operator_chat.send` is a closed list of at most 10 objects `{filename, content_base64}` (`filename` 1 to 255 characters). The decoded total may not exceed 6,000,000 bytes; invalid base64 or an excess total is refused `invalid`, naming the file. Attachments with a Planner target are refused `invalid` ("attachments go only to a Manager"), and so are attachments when no runtime root is available.
- **Content check** (`looper/agents/chat_attachments.py`). Each file is saved and classified by its content, not its name: an image (PNG, JPEG, GIF or WEBP), a PDF, a docx, xlsx or pptx (a zip is accepted only with one of those three extensions), or UTF-8 text; executables and binary data are not accepted. The per-file cap is 20 MB, which the 6,000,000-byte request total makes the lower limit on this route. A file that fails refuses the whole send with `invalid`, naming the file and the reason, and its saved directory is removed. A file name is reduced to a safe name (no directories, control characters or leading dots, at most 100 characters), and a name without an extension gets one from the type.
- **Storage and cleanup** (`looper/agents/chat_attachments.py`, `looper/agents/housekeeping.py`). Files are kept in `chat-attachments/<source>/<message>/` under the runtime root, with directories 0700 and files 0600; symlinked storage directories are refused. The hourly housekeeping deletes message directories older than 7 days; its log line and report gain a `chat_attachments` count. A replay of a message after cleanup shows the file as "no longer available". The dashboard sends the files through this API only; this release has no frontend change.
- **Runtime hint** (`looper/agents/runtimes/__init__.py`, `looper/agents/runtimes/claude_code.py`). Runtimes gain `image_input` (`none` by default); Claude Code is `read_tool`.
- **Evals and docs.** The prompt-regression suite gains the `attachment_read` dialog (61 dialogs now) and `docs/architecture/agent-system.md` describes the feature.
- **Model-visible changes:** Yes, for a Manager turn whose message carries attachments (`looper/agents/tiers/manager.py`, `chat_attachments.section`). After the user's message the turn text gets an "Attachments sent with this message (kept on this machine for 7 days; never put their paths in a reply)" section. It lists each file's number, kind, name, MIME type, size and local path, or "not received" with the reason (larger than 20 MB, more than 10 attachments, or another reason; "the user was told" if so). It ends with an instruction: a Claude Code Manager is told to open a file with its file-reading tool; other runtimes are told to do so for files but that they cannot view images, and to say so if asked what an image shows. A turn without attachments is unchanged; no system prompt, tool or tool result changed.

### 升级决策

**谁需要升级：**在 `operator_chat.send` 中传 `attachments` 的控制台 API 客户端，以及希望 Manager 读取随聊天消息发送的文件的运维者。其他人在正常使用中没有变化。

**解决了什么：**[#1278](https://github.com/foolzzz/looper/pull/1278) 把 `attachments` 从“原样传递、从不读取的任意对象列表”改为最多 10 个 `{filename, content_base64}` 文件，由 Looper 保存、按内容检查并列在 Manager 的回合中，使 Manager 能打开随消息发送的图片、PDF、Office 文件或文本文件。

**是否有破坏性变更：**是，对发送任意 `attachments` 对象的 `operator_chat.send` 调用方：不是 `{filename, content_base64}` 的项、超过 10 项或解码后超过 6,000,000 字节的请求都会被以 `invalid` 拒绝。PR 称这是有意的维护者决定。没有迁移，没有结构变更。桥接边界不变：早于 v2.13.165 的安装须先升级到 v2.13.165。

**如何验证：**核对版本为 2.14.154。

**贡献者：**维护者 @foolzzz 提交 [#1278](https://github.com/foolzzz/looper/pull/1278)；本版本无社区贡献。

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.153 上的安装可直接升级。没有结构变更。

### 行为变化与入口

- **附件输入**（[#1278](https://github.com/foolzzz/looper/pull/1278)，`looper/agents/v1_domains/operator_chat_streams.py`）。`operator_chat.send` 的 `attachments` 是最多 10 个 `{filename, content_base64}` 对象的封闭列表（`filename` 1 至 255 字符）。解码后总量不得超过 6,000,000 字节；base64 无效或总量超限以 `invalid` 拒绝并指出文件名。发给 Planner 的附件以 `invalid` 拒绝（“attachments go only to a Manager”），没有运行时根目录时同样拒绝。
- **按内容检查**（`looper/agents/chat_attachments.py`）。每个文件按内容而非文件名分类并保存：图片（PNG、JPEG、GIF、WEBP）、PDF、docx/xlsx/pptx（zip 仅在扩展名为这三种之一时接受）或 UTF-8 文本；可执行文件和二进制数据不接受。单文件上限 20 MB，在此路由上受 6,000,000 字节总量限制而更低。任何文件未通过检查，整条消息以 `invalid` 拒绝，指出文件名和原因，并删除已保存的目录。文件名会被规整为安全名称（无目录、控制字符和前导点，最长 100 字符），无扩展名时按类型补上。
- **存储与清理**（`looper/agents/chat_attachments.py`、`looper/agents/housekeeping.py`）。文件保存在运行时根目录下的 `chat-attachments/<source>/<message>/`，目录 0700、文件 0600；符号链接的存储目录会被拒绝。每小时的 housekeeping 删除超过 7 天的消息目录，其日志行和报告新增 `chat_attachments` 计数。清理后重放消息，该文件显示为“no longer available”。控制台仅通过此 API 发送文件；本版本无前端改动。
- **运行时提示**（`looper/agents/runtimes/__init__.py`、`looper/agents/runtimes/claude_code.py`）。运行时新增 `image_input`（默认 `none`）；Claude Code 为 `read_tool`。
- **评测与文档。**提示词回归套件新增 `attachment_read` 对话（现为 61 个），`docs/architecture/agent-system.md` 说明了该功能。
- **面向模型的变化：**有，针对带附件消息的 Manager 回合（`looper/agents/tiers/manager.py`、`chat_attachments.section`）。回合文本在用户消息之后增加“Attachments sent with this message (kept on this machine for 7 days; never put their paths in a reply)”一节，列出每个文件的序号、类型、名称、MIME 类型、大小和本地路径，或“not received”及原因（超过 20 MB、超过 10 个附件或其他原因；若已告知用户则注明“the user was told”）。末尾附一条指令：Claude Code 的 Manager 被告知用文件读取工具打开文件；其他运行时同样被告知用该工具打开文件，但无法查看图片，被问到图片内容时应说明看不到。无附件的回合不变；系统提示词、工具和工具结果均未改动。

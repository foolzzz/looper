# Looper v2.14.102

This is the patch release v2.14.102, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.101: `looper serve` now records how long each startup step takes, logs it once the server listens and reports it in the status and the upgrade report ([#1149](https://github.com/foolzzz/looper/pull/1149)). It is observability only.

## Release Decision

**Who should upgrade:** Operators who want to see which startup step makes the gap of a `looper service upgrade` or a restart slow. Everyone else can stay.

**What this release solves:** [#1149](https://github.com/foolzzz/looper/pull/1149). A slow deploy gap could not be attributed to a startup step. The server now measures each step and logs the seconds in one INFO line right after "HTTP server listening"; the upgrade report carries the same numbers.

**Breaking changes:** No. No database change, no new dependency, no new setting, no new command or dashboard control. Startup order and behavior are unchanged; the status response and the upgrade report each gain one optional field.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.14.102
```

**Contributors:** Maintainer @foolzzz authored [#1149](https://github.com/foolzzz/looper/pull/1149); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.101 upgrades directly. There is no database change.

## Behavior changes

- **Startup step timings** (`looper/agents/serve.py`). The startup of `looper serve` is wrapped in timing contexts. Each step that is entered records its elapsed seconds in execution order, starting with `imports` (from process start until the first log) and including, among others, `operator_token`, `database_check`, `lease`, `pool`, `schema`, `kept_scan`, `llmrec` (request recording), `step_worktrees`, `task_worktrees`, the login inspections, `reclaim_unused`, `run_sessions`, one `channel:<id>` per configured channel and `http`. After the HTTP server starts, one INFO line `startup steps: name=seconds ...` is logged, ending with `total`. Steps that are skipped are not recorded. The order of the steps and their error handling are not changed; the channel start code was only re-indented into its timing context.
- **Status** (`looper/agents/http_server.py`, `looper/agents/v1_domains/status.py`). The server status gains an optional `startup_steps` object (step name to non-negative seconds), present when the server was started by `looper serve`. The status schema accepts it. The pull request description does not mention this field.
- **Upgrade report** (`looper/agents/service.py`). After the restarted service answers, `looper service upgrade` copies `startup_steps` from its status into the report when it is present; otherwise the report has no such field.
- **Documentation and tests.** `tests/test_startup_steps.py` is new, `tests/test_service_upgrade_execution.py` covers the report with and without the field, and `tests/test_room_consult.py` now also looks through timing contexts when it checks the startup order.
- **Unchanged:** the database schema, the dependencies, settings, commands and their options, the dashboard, the Manager's tools, channels (Telegram and Lark).
- **Model-visible changes:** None. No prompt, tool description or agent environment changes.

## 中文摘要

本版本是 patch release v2.14.102（热修线，每个合并的改动立即发布）。自 v2.14.101 以来只合并了一项改动：`looper serve` 现在记录每个启动步骤的耗时，在服务开始监听后写一行日志，并在状态和升级报告中给出（[#1149](https://github.com/foolzzz/looper/pull/1149)）。仅为可观测性改动。

### 升级决策

**谁需要升级：**想知道 `looper service upgrade` 或重启的间隙慢在哪个启动步骤的运维人员。其他人可不升级。

**解决了什么：**[#1149](https://github.com/foolzzz/looper/pull/1149)。此前无法把变慢的部署间隙归因到某个启动步骤。现在服务会测量每个步骤，并在 "HTTP server listening" 之后用一行 INFO 日志给出各步骤秒数；升级报告带有同样的数据。

**是否有破坏性变更：**否。无数据库变更、无新依赖、无新设置、无新命令或仪表盘控件。启动顺序与行为不变；状态响应和升级报告各新增一个可选字段。

**如何验证：**核对版本为 2.14.102。

**贡献者：**维护者 @foolzzz 提交 [#1149](https://github.com/foolzzz/looper/pull/1149)；本版本无社区贡献。

```bash
looper --version   # looper 2.14.102
```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.101 上的安装可直接升级。无数据库变更。

### 行为变化与入口

- **启动步骤耗时**（`looper/agents/serve.py`）。`looper serve` 的启动被包在计时上下文中。每个被执行的步骤按执行顺序记录耗时秒数，首项为 `imports`（从进程启动到第一条日志），其余包括 `operator_token`、`database_check`、`lease`、`pool`、`schema`、`kept_scan`、`llmrec`（请求记录）、`step_worktrees`、`task_worktrees`、登录检查、`reclaim_unused`、`run_sessions`、每个已配置渠道一项 `channel:<id>` 以及 `http`。HTTP 服务启动后写一行 INFO 日志 `startup steps: name=seconds ...`，以 `total` 结尾。被跳过的步骤不记录。步骤顺序和错误处理不变；渠道启动代码只是缩进进了计时上下文。
- **状态**（`looper/agents/http_server.py`、`looper/agents/v1_domains/status.py`）。服务状态新增可选的 `startup_steps` 对象（步骤名到非负秒数），由 `looper serve` 启动时存在。状态 schema 接受该字段。PR 描述未提及此字段。
- **升级报告**（`looper/agents/service.py`）。重启后的服务应答后，`looper service upgrade` 在其状态含 `startup_steps` 时将其复制进报告；否则报告不含该字段。
- **文档与测试。**新增 `tests/test_startup_steps.py`；`tests/test_service_upgrade_execution.py` 覆盖报告有无该字段两种情况；`tests/test_room_consult.py` 检查启动顺序时现在也会穿过计时上下文。
- **不变：**数据库结构、依赖、设置、命令及选项、仪表盘、Manager 工具、渠道（Telegram 和 Lark）。
- **面向模型的变化：**无。提示、工具描述和 agent 环境均无变化。

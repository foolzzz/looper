# Looper v2.14.69

This is the patch release v2.14.69, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.68: `looper service upgrade` now plans and reports control-plane upgrades that keep running agents ([#1063](https://github.com/foolzzz/looper/pull/1063)).

## Release Decision

**Who should upgrade:** Installations that run with the keeper on and upgrade the service with `looper service upgrade`. Others see no change.

**What this release solves:** v2.14.68 adopts detached kept runs at startup, but the upgrade command still planned `FULL` for every control-plane change. [#1063](https://github.com/foolzzz/looper/pull/1063) lets it plan `CONTROL_PLANE` when it is safe to keep runs, and report what was kept, adopted and interrupted.

**Breaking changes:** No. The only API change is the optional `keepers.failed_after_start` field of `system.status`, and there is no migration.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#1063](https://github.com/foolzzz/looper/pull/1063); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.69
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.68 upgrades directly. This release adds no migration. The upgrade that installs this release is planned by the older code, so the new planning applies from the next upgrade.

## Behavior changes

- **Plan.** `looper service upgrade` (`looper/agents/service.py`) reads `system.status.keepers` from the running service and plans `CONTROL_PLANE` for a control-plane change only when keeper mode is on, the service manager preserves keepers (launchd always; systemd only with `KillMode=process`), every live keeper offers at least one protocol version the target supports, and the adoption contract is unchanged. Otherwise it plans `FULL`; for an older systemd unit the reasons say to reinstall the service. With keeper mode off the behavior is unchanged. `scan_keepers` (`looper/upgrade.py`) now discovers live keepers and reads their `protocol_versions`; if liveness cannot be checked, the upgrade refuses. The preview prints `keepers    on (N live)`.
- **Tiered drain for `CONTROL_PLANE`.** While any run is not keepable, `--drain-timeout` applies; once only turns block, `--turns-timeout` applies, measured from the start of the drain. `--no-force` cancels deployment at the applicable deadline. Only non-keepable runs interrupted at the deadline are listed in `interrupted`, with reason `not_keepable`; full drains keep reason `deadline`.
- **Report.** `kept_before` counts keepable runs in the last drain status. After the restart the CLI waits up to 330 seconds for pending adoptions and reports `adopted` (from `keepers.adopted_at_start`) and `failed_after_start` reason counts. If fewer runs were adopted than kept, or an adoption failed, it adds a P1 alert and prints a `warning` line; a serving upgrade still exits successfully.
- **`system.status`.** `keepers` gains `failed_after_start` (adoption failures by reason, counted by `WorkerPool`). `checks` gains `kept_runs` warnings: P1 when adoption is incomplete or failed, P2 when live keepers outside this pool have had no controller for over ten minutes. The orphan check scans lazily and caches for 30 seconds. Keepers now record `controller_disconnected_at` in their state file. The dashboard shows these through its existing checks list; Telegram, Lark and the CLI status are unchanged, and notifying the Manager about P1 warnings is a separate follow-up.
- **Housekeeping.** `docs/architecture/agent-system.md` and the hot-upgrade plan entry describe the flow.
- **Size:** per the pull request description, 120 added lines of production code and 578 of tests (fixtures excluded).
- **Model-visible changes:** None. No prompt, tool description or tool result text changed.

### 升级决策

**谁需要升级：**开启 keeper 并使用 `looper service upgrade` 升级服务的安装。其他安装没有变化。

**解决了什么：**v2.14.68 在启动时接管脱离的托管运行，但升级命令对每次控制面变更仍规划 `FULL`。[#1063](https://github.com/foolzzz/looper/pull/1063) 让它在可以安全保留运行时规划 `CONTROL_PLANE`，并报告保留、接管和中断的情况。

**是否有破坏性变更：**否。唯一的 API 变化是 `system.status` 可选的 `keepers.failed_after_start` 字段，没有迁移。

**如何验证：**运行 `looper --version` 核对版本为 2.14.69。

**贡献者：**维护者 @foolzzz 提交 [#1063](https://github.com/foolzzz/looper/pull/1063)；本版本无社区贡献。

```bash

```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.68 上的安装可直接升级。本版本没有迁移。安装本版本的升级仍由旧代码规划，新的规划从下一次升级起生效。

### 行为变化与入口

- **规划。**`looper service upgrade`（`looper/agents/service.py`）从运行中的服务读取 `system.status.keepers`，仅当 keeper 开启、服务管理器保留 keeper（launchd 始终保留；systemd 仅在 `KillMode=process` 时）、每个存活 keeper 至少提供一个目标支持的协议版本、且接管契约未变时，才为控制面变更规划 `CONTROL_PLANE`；否则规划 `FULL`，旧版 systemd 单元的原因会提示重新安装服务。keeper 关闭时行为不变。`scan_keepers`（`looper/upgrade.py`）现在发现存活 keeper 并读取其 `protocol_versions`；无法检查存活状态时升级拒绝执行。预览会打印 `keepers    on (N live)`。
- **`CONTROL_PLANE` 的分级排空。**只要有运行不可保留，就使用 `--drain-timeout`；仅剩 turns 阻塞后使用 `--turns-timeout`，从排空开始计时。`--no-force` 在对应期限到达时取消部署。只有期限到达时被中断的不可保留运行会列入 `interrupted`，原因为 `not_keepable`；完整排空仍用 `deadline`。
- **报告。**`kept_before` 统计最后一次排空状态中可保留的运行。重启后 CLI 最多等待 330 秒让待定接管完成，并报告 `adopted`（来自 `keepers.adopted_at_start`）和 `failed_after_start` 按原因的计数。接管数少于保留数或有接管失败时，添加 P1 告警并打印 `warning` 行；升级仍以成功退出。
- **`system.status`。**`keepers` 新增 `failed_after_start`（`WorkerPool` 按原因统计的接管失败）。`checks` 新增 `kept_runs` 警告：接管不完整或失败为 P1；不属于本连接池的存活 keeper 超过十分钟无控制器为 P2。孤儿检查惰性扫描并缓存 30 秒。keeper 在状态文件中记录 `controller_disconnected_at`。仪表盘通过已有的检查列表显示；Telegram、Lark 和 CLI 状态不变，向 Manager 通知 P1 警告是另行的后续工作。
- **其他。**`docs/architecture/agent-system.md` 和热升级计划条目描述了该流程。
- **规模：**据 PR 描述，生产代码新增 120 行，测试新增 578 行（不含 fixture）。
- **面向模型的变化：**无。没有提示、工具说明或工具结果文字变化。

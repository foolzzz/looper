# Looper v2.15.1

This is the patch release v2.15.1, a hotfix line in which each merged change ships at once. It documents one change: [#1369](https://github.com/foolzzz/looper/pull/1369) (room push for SDK-runner runs, the Pi and DSH default path).

## Release Decision

**Who should upgrade:** Operators who run Pi or DSH Workers or Reviewers on the hosted runner path (the default for those runtimes) and use the task room, so that room messages reach the run while it works instead of waiting to be pulled.

**What this release solves:** [#1369](https://github.com/foolzzz/looper/pull/1369) delivers room messages to hosted Pi and DSH runs by steering them into the running turn. Before, these runs only pulled room messages through the room tools. A message is marked read only when the runner reports that the steer joined a model request.

**Breaking changes:** No. The CLI, the API and the dashboard are unchanged, no new command or control is added and there is no PostgreSQL schema change. The PR states a behavior change (maintainer decision, intended: steering is preferred wherever the runtime supports it), listed below. The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.15.1
```

**Contributors:** Maintainer @foolzzz authored [#1369](https://github.com/foolzzz/looper/pull/1369); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.15.0 upgrades directly. There is no PostgreSQL schema change. Restart the service after upgrading, as for every release.

## Behavior changes

Read in the diff of the PR, which states: behavior change (maintainer decision, intended).

### #1369: Room push for SDK-runner runs (Pi and DSH default path)

- **Push mode.** A new `RoomPush.RUNNER` mode is set on the hosted Pi and DSH runner runtimes (`PiRunnerRuntime`, `DshRunnerRuntime`). `room_push(launch)` returns it when the runtime hosts its runs, independent of the CLI steering capability. Runs that do not use the hosted runner, and runtimes such as Cursor, are unchanged and keep pulling.
- **Delivery.** The Worker pool sends room deliveries to these runs with `steer`, with the delivery uuid as the steer's `message_id`. A delivery is marked read only when a `steer_applied` event names that `message_id`, after the steer joins a model request; acceptance alone marks nothing read, and there is no fallback timer. The room cursor stays cumulative, so a later receipt never confirms an earlier unseen delivery.
- **Dropped steers.** A `steer_dropped` for a room delivery leaves its messages unread and closes room confirmation for the rest of that run, because confirming a later delivery would also mark the dropped one read. The drop is recorded in the run's activity as a room delivery ("Room delivery dropped (...); its messages stay unread") and is never reported to the Planner as `missed_input`. Planner steers are unchanged.
- **Runner channel.** `RunnerChannel.send` remembers a steer's text for `dropped_input()` only when it has no uuid, so room deliveries are not returned as dropped Planner input.
- **Other runtimes.** The Claude Code user-turn confirmation (replayed user messages and result `user_message_uuids`) and the Codex item-history confirmation are skipped for runner runs; they keep their own paths.
- **Docs.** `docs/architecture/agent-system.md` describes the mode and the receipt rules.

### Model-visible changes

Yes, for hosted Pi and DSH runs. `room_input` now gives them the pushed room guidance (`PUSHED`) instead of the pull guidance (`PULL`), so the room section of their Worker and Reviewer prompts changes: the run is told that messages are delivered to it and does not wait for them as a timer. The room message bodies themselves now arrive as steered input in the run's turn (addressed or interface-post messages in full, others in an oldest-first prefix, as documented for the other pushed runtimes). Other runtimes' prompts are unchanged. No tool schema was changed by this PR.

### 行为变化与入口

以下在该 PR 的差异中可见，PR 声明：有行为变化（维护者决定，有意为之）。

**#1369：SDK runner 运行的房间推送（Pi 和 DSH 默认路径）**

- **推送模式。**托管的 Pi 和 DSH runner 运行时（`PiRunnerRuntime`、`DshRunnerRuntime`）新增 `RoomPush.RUNNER` 模式。运行时托管其运行时，`room_push(launch)` 返回该模式，与 CLI 的 steer 能力无关。不使用托管 runner 的运行以及 Cursor 等运行时不变，仍然拉取。
- **投递。**Worker 池用 `steer` 向这些运行投递房间消息，以投递 uuid 作为 steer 的 `message_id`。只有 `steer_applied` 事件点名该 `message_id`（即 steer 已进入一次模型请求）后才标记已读；仅被接受不会标记任何已读，也没有兜底计时器。房间游标仍是累积的，后到的回执不会确认更早未见的投递。
- **被丢弃的 steer。**房间投递的 `steer_dropped` 会让其消息保持未读，并在该运行剩余时间内关闭房间确认，因为确认之后的投递会把被丢弃的投递一并标为已读。丢弃会记录到运行活动中（“Room delivery dropped (...); its messages stay unread”），不会作为 Planner 的 `missed_input` 上报。Planner 的 steer 不变。
- **Runner 通道。**`RunnerChannel.send` 仅在没有 uuid 时记住 steer 文本供 `dropped_input()` 返回，因此房间投递不会被当作被丢弃的 Planner 输入返回。
- **其他运行时。**Claude Code 的用户轮次确认（回放的用户消息和结果的 `user_message_uuids`）与 Codex 的 item 历史确认对 runner 运行跳过，各自保持原有路径。
- **文档。**`docs/architecture/agent-system.md` 说明了该模式和回执规则。

**面向模型的变化：**有，针对托管的 Pi 和 DSH 运行。`room_input` 现在为它们给出推送式房间指引（`PUSHED`）而不是拉取式（`PULL`），因此其 Worker 和 Reviewer 提示词中的房间部分会变化：运行被告知消息会送达，不再把等待当作定时器。房间消息正文现在作为 steer 输入进入运行的当前轮次（被点名或界面发帖的消息给出全文，其余按最早优先的前缀，与其他推送运行时的文档一致）。其他运行时的提示词不变。该 PR 未改动工具 schema。

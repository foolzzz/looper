# Looper v2.13.205

## Release Decision

**Who should upgrade:** Operators who run the opt-in Pi runner with a run or task budget cap. A Planner turn there could be stopped as `budget_unverifiable` when the model provider reported token usage whose totals or detail counts disagree. It ships the change merged since v2.13.204.

**What this release solves:** [#854](https://github.com/foolzzz/looper/pull/854) makes the Pi runner keep usage that a compatible provider reports inconsistently, so the turn is priced and its budget caps are checked instead of being stopped. It also logs which value made a budget unverifiable.

**Breaking changes:** No. Commands, settings, the database schema and the admitted upgrade path are unchanged.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#854](https://github.com/foolzzz/looper/pull/854); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.205
```

## Behavior changes

- **Usage accepted from the provider (`runners/pi/src/provider.ts`):** `responseUsage` no longer discards a response's usage when `total_tokens` differs from input plus output, when cached plus cache-write tokens exceed the input tokens, or when reasoning tokens exceed the output tokens. It still discards usage when a count is not a non-negative safe integer or is missing. Billable buckets are now `input - cacheRead - cacheWrite` (never below zero), `output`, `cacheRead`, `cacheWrite`; reasoning is treated as part of output. `totalTokens` is input plus output. The same function serves the chat-completions path, so those usage shapes are accepted too.
- **Budget effect (`looper/agents/runtimes/runner/turn.py`):** previously discarded usage marked the turn's usage incomplete, and with a run or task cap set the request-end check returned `budget_unverifiable`, which capped the turn and failed the task. Such turns are now priced from the accepted buckets and finish without a cap reason. Usage that is truly missing or invalid is still capped as `budget_unverifiable`.
- **Where the refusal happens:** the title and description of #854 speak of the first request being refused. In the code the first request is admitted; the refusal came when the request ended with unusable usage. The test added for the first request asserts one admitted request and that the cap arises at `request_end`.
- **New diagnostic log:** when a capped turn finds its budget unverifiable, one warning is logged with the session id, trace id, phase (`authorize`, `request_end` or `finish`), the first failing cause (`usage_incomplete`, `run_cost`, `estimate`, `pending_estimate` or `task_spent`) and request counts. It contains no prompts, credentials or provider errors. Nothing is logged when the budget is verifiable or no cap is set. The decision logic itself is unchanged.
- **Tests:** new `tests/test_runner_budget_db.py` (needs a test database; checks first-request admission with known task spend and unpriced history), new cases in `tests/test_pi_runner_turns.py`, `tests/test_pi_runner_serve_db.py` and `tests/test_runner_turn.py`. Cases that expected usage with mismatched totals to be rejected now expect it to be priced.
- **Model-visible changes:** None. No prompt, tool or message text changed; the model sees the same requests.

## Upgrade and rollback

Re-run `install.sh` once v2.13.205 is published. No data or schema change is involved, so a rollback to v2.13.204 needs no database restore.

## 中文摘要

### 升级决策

**谁需要升级：**使用可选 Pi runner 并设置了运行或任务预算上限的运维者。当模型 provider 报告的 token 用量总数或明细互相不一致时，Planner 回合可能被以 `budget_unverifiable` 终止。包含 v2.13.204 之后合并的改动。

**解决了什么：**[#854](https://github.com/foolzzz/looper/pull/854) 让 Pi runner 保留兼容 provider 报告得不一致的用量，从而该回合会被计价并检查预算上限，而不是被终止。它还会记录是哪个值导致预算无法验证。

**是否有破坏性变更：**否。命令、设置、数据库 schema 和允许的升级路径均不变。

**如何验证：**运行 `looper --version` 核对版本为 2.13.205。

**贡献者：**维护者 @foolzzz 提交 [#854](https://github.com/foolzzz/looper/pull/854)；本次 patch release 无社区贡献。

```bash
looper --version   # looper 2.13.205
```

### 行为变化与入口

- **接受的 provider 用量（`runners/pi/src/provider.ts`）：**当 `total_tokens` 与输入加输出不等、缓存读加缓存写超过输入、或推理 token 超过输出时，`responseUsage` 不再丢弃该响应的用量。计数不是非负安全整数或缺失时仍会丢弃。计费分项为 `input - cacheRead - cacheWrite`（不小于零）、`output`、`cacheRead`、`cacheWrite`；推理 token 视为已包含在输出中。`totalTokens` 为输入加输出。chat-completions 路径共用该函数，因此同样接受这些用量形态。
- **预算影响（`looper/agents/runtimes/runner/turn.py`）：**此前被丢弃的用量使该回合用量标记为不完整，设置了运行或任务上限时，请求结束检查返回 `budget_unverifiable`，回合被截止并使任务失败。现在这类回合按接受的分项计价，结束时没有截止原因。真正缺失或无效的用量仍会以 `budget_unverifiable` 截止。
- **拒绝发生的位置：**#854 的标题和描述说第一次请求被拒绝。代码中第一次请求是被放行的；拒绝发生在请求结束、用量不可用时。新增的首次请求测试断言放行一次请求，并在 `request_end` 阶段产生截止。
- **新增诊断日志：**设置了上限的回合发现预算无法验证时，记录一条警告，含会话 id、trace id、阶段（`authorize`、`request_end` 或 `finish`）、第一个失败原因（`usage_incomplete`、`run_cost`、`estimate`、`pending_estimate` 或 `task_spent`）以及请求计数，不含提示词、凭据或 provider 错误。预算可验证或未设上限时不记录。判定逻辑本身不变。
- **测试：**新增 `tests/test_runner_budget_db.py`（需要测试数据库；检查已知任务花费与未计价历史下的首次请求放行），并在 `tests/test_pi_runner_turns.py`、`tests/test_pi_runner_serve_db.py`、`tests/test_runner_turn.py` 增加用例。原先期望总数不一致的用量被拒绝的用例，现在期望其被计价。
- **面向模型的变化：**无。提示词、工具和消息文本均未改变，模型看到的请求相同。

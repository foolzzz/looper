# Looper v2.13.201

## Release Decision

**Who should upgrade:** Operators who start `looper serve` against an existing database, and anyone who keeps a database older than v2.13.165. A fresh install sees no difference. It is a hotfix that ships the change merged since v2.13.200.

**What this release solves:** [#808](https://github.com/foolzzz/looper/pull/808) enforces a bridge-only database upgrade boundary. Looper now upgrades in one guarded step only a database that a completed v2.13.165 or later release left at schema 3, and refuses every other older database with a message that names the bridge release. The many historical migrations are gone, so a fresh and an upgraded database end with the same final schema (version 4).

**Breaking changes:** Yes. A database older than v2.13.165 (or schema 3 with an unrecognised `schema.sql` fingerprint) no longer starts: upgrade it with v2.13.165 or a later 2.13 release first, start that once, then upgrade to this version. Command names and settings did not change.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#808](https://github.com/foolzzz/looper/pull/808); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.201
```

## Behavior changes

- **Admission (`looper/db/connection.py`, `_classify_schema`):** under the schema advisory lock, read-only, a database is `empty` (no Looper tables), `current` (`registry_schema_version` is 4 and the `post_bridge_baseline` marker is in `schema_migrations`), or `bridge`. `bridge` means version 3 with a `schema_fingerprint` equal to one of two recorded values (`BRIDGE_ERA_FINGERPRINTS`, v2.13.165–174 and v2.13.175–192) and with every table and column that the conversion reads present. Any other state raises `RegistrySchemaVersionError` ("unsupported Looper database; upgrade to v2.13.165 or a later 2.13 release first, start it once, then upgrade to this version"), as does a version 4 database without the marker, a missing version row, or Looper tables spread over more than one schema namespace. `REGISTRY_SCHEMA_VERSION` is now 4.
- **Startup (`ensure_schema`):** the historical legacy-registry, layer-effort and task-concurrency migrations are no longer run. A `current` database only re-applies the builtin phase on each start (missing builtins are filled without resetting saved choices). An `empty` or `bridge` database runs the schema phases, then `final_constraints`, and for a bridge database `upgrade_from_bridge`, all in the one schema transaction, and then records version 4. `final_constraints` drops `agent_setting_layers.effort` and the `task_user_gate_posts` `UNIQUE (channel, chat, external_id)` constraint and records the four migration names, including `post_bridge_baseline`.
- **Bridge conversion (`looper/db/bridge_upgrade.py`):** it rewrites task `config` to a JSON object (as the bridge reader saw it, with `{}` when unreadable, logged); sets `projects.task_workspaces` to `in_place` when null; fills the runtime `claude-code` and provider `prov-claude-subscription` on sessions and schedule planner sessions only when it can be proven; normalises channel sender allowlists and drops `app_id_env`/`app_secret_env` from Lark configs; replaces the old builtin harness prompt with the current default; copies `metadata.agent` to `metadata.profile` and marks records without provider auth `subscription_equivalent`; and sets `channel_id` on gate posts and messages of builtin channels, and `channel` on posts of an existing custom bot. Rows whose bot cannot be recovered are kept and logged. Non-object metadata and invalid allowlists are kept unchanged.
- **Backup (`looper/agents/serve.py`):** `schema_change_pending` is true only for a `bridge` database, so only that upgrade takes the backup (it may not be skipped with `--skip-backup`). A `current` database whose `schema.sql` text changed no longer triggers a backup. The backup failure message now includes the cause, and the restore hint is logged for registry upgrades as well.
- **Config import (`looper/agents/config_transfer.py`):** an unsupported database makes `import_config --apply` fail as "schema change pending" with the admission message, instead of a version error.
- **Gate posts (`looper/db/user_gates.py`, `schema.sql`):** `record_post` now stores `channel` as given, not only for builtin bots, because the old binary's unique constraint is gone. The unique key is `(channel_id, chat, external_id)`.
- **CI:** the Python and installed-test workflows fetch the pinned v2.13.165 tag and check its commit, and a new `bridge-schema-pg18` job runs `tests/test_bridge_schema_db.py` on PostgreSQL 18. About 40 historical database acceptance test files and helpers were deleted; new bridge fixtures and tests replace them.
- **Scope:** 58 files, 1102 added and 3352 deleted lines. The description reports "tests 555, production 199 (fixtures excluded)".
- **Model-visible changes:** None for prompts, tools and messages in normal operation. The only prompt-related data change: a stored builtin harness prompt that equals the old text is replaced by the current default during the bridge conversion.

## Upgrade and rollback

Re-run `install.sh` once v2.13.201 is published. Run it first on v2.13.165 or later if the database is older. The first start on a bridge database takes a verified `pg_dump` backup (needs `pg_dump`) and then converts the schema. Rolling back to v2.13.200 after the conversion is not supported on that database: restore the backup into a new isolated database instead.

## 中文摘要

### 升级决策

**谁需要升级：**对已有数据库启动 `looper serve` 的运维者，以及数据库早于 v2.13.165 的用户；全新安装无差别。本版本是随合并即发布的 hotfix，包含 v2.13.200 之后合并的改动。

**解决了什么：**[#808](https://github.com/foolzzz/looper/pull/808) 确立仅经桥接版本的数据库升级边界。Looper 现在只对已由完整的 v2.13.165 或更高版本留在 schema 3 的数据库做一次受保护的升级，其他较旧数据库一律拒绝并提示桥接版本。历史迁移已移除，新建与升级后的数据库得到相同的最终 schema（版本 4）。

**是否有破坏性变更：**是。早于 v2.13.165 的数据库（或 `schema.sql` 指纹不被识别的 schema 3）不再能启动：须先用 v2.13.165 或更高的 2.13 版本升级并启动一次，再升级到本版本。命令名和设置未改变。

**如何验证：**运行 `looper --version` 核对版本为 2.13.201。

**贡献者：**维护者 @foolzzz 提交 [#808](https://github.com/foolzzz/looper/pull/808)；本次 patch release 无社区贡献。

```bash
looper --version   # looper 2.13.201
```

### 行为变化与入口

- **准入（`looper/db/connection.py`，`_classify_schema`）：**在 schema 咨询锁下只读判定数据库为 `empty`（无 Looper 表）、`current`（`registry_schema_version` 为 4 且 `schema_migrations` 含 `post_bridge_baseline`）或 `bridge`。`bridge` 指版本为 3、`schema_fingerprint` 等于两个记录值之一（`BRIDGE_ERA_FINGERPRINTS`，v2.13.165–174 与 v2.13.175–192），且转换所读的表和列都存在。其他状态抛出 `RegistrySchemaVersionError`（“unsupported Looper database; upgrade to v2.13.165 or a later 2.13 release first…”），缺少标记的版本 4、缺失版本行、Looper 表分散在多个 schema 命名空间同样拒绝。`REGISTRY_SCHEMA_VERSION` 现为 4。
- **启动（`ensure_schema`）：**不再运行历史的旧注册表、layer-effort 和 task-concurrency 迁移。`current` 数据库每次启动只重新应用 builtin 阶段（补齐缺失内置项，不重置已保存的选择）。`empty` 或 `bridge` 数据库运行 schema 各阶段，再运行 `final_constraints`，bridge 数据库还运行 `upgrade_from_bridge`，全部在同一个 schema 事务内，然后记录版本 4。`final_constraints` 删除 `agent_setting_layers.effort` 和 `task_user_gate_posts` 的 `UNIQUE (channel, chat, external_id)` 约束，并记录四个迁移名（含 `post_bridge_baseline`）。
- **桥接转换（`looper/db/bridge_upgrade.py`）：**把任务 `config` 改写为 JSON 对象（与桥接版本读取一致，不可读时为 `{}` 并记录日志）；`projects.task_workspaces` 为空时设为 `in_place`；仅在可证明时为会话和计划调度的规划会话补 `claude-code` 运行时和 `prov-claude-subscription` 提供方；规范化渠道发送者白名单并移除 Lark 配置的 `app_id_env`/`app_secret_env`；把旧的内置 harness 提示词替换为当前默认；把 `metadata.agent` 复制为 `metadata.profile`，并把无提供方认证的记录标为 `subscription_equivalent`；为内置渠道的 gate 帖子和消息补 `channel_id`，为现存自定义 bot 的帖子补 `channel`。无法恢复 bot 的行保留并记录日志；非对象 metadata 和无效白名单保持不变。
- **备份（`looper/agents/serve.py`）：**`schema_change_pending` 仅对 `bridge` 数据库为真，所以只有该升级会备份（不可用 `--skip-backup` 跳过）。`schema.sql` 文本变化的 `current` 数据库不再触发备份。备份失败消息现在包含原因，注册表升级也会记录还原提示。
- **配置导入（`looper/agents/config_transfer.py`）：**数据库不受支持时，`import_config --apply` 以“schema change pending”失败并给出准入消息，而不是版本错误。
- **Gate 帖子（`looper/db/user_gates.py`、`schema.sql`）：**`record_post` 现在原样存储 `channel`，不再只限内置 bot，因为旧二进制的唯一约束已移除。唯一键为 `(channel_id, chat, external_id)`。
- **CI：**Python 与 installed 测试工作流拉取固定的 v2.13.165 标签并校验其提交，新增 `bridge-schema-pg18` 任务在 PostgreSQL 18 上运行 `tests/test_bridge_schema_db.py`。约 40 个历史数据库验收测试文件和辅助文件被删除，由新的桥接夹具和测试取代。
- **范围：**58 个文件，新增 1102 行、删除 3352 行。描述写的是“测试 555 行、生产代码 199 行（不含 fixtures）”。
- **面向模型的变化：**正常运行时提示词、工具和消息无变化。唯一与提示词相关的数据变化：存储的内置 harness 提示词若等于旧文本，会在桥接转换时替换为当前默认。

### 升级与回退

v2.13.201 发布后重新运行 `install.sh`。数据库更旧时，先在 v2.13.165 或更高版本上运行一次。bridge 数据库首次启动会做经校验的 `pg_dump` 备份（需要 `pg_dump`），然后转换 schema。转换后不支持在该数据库上回退到 v2.13.200：请把备份还原到新的隔离数据库。

本版本未新增可选能力启用入口。

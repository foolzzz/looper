# Looper v2.15.23

This release documents the changes merged since v2.15.22. The default Manager can send its resident sections as one stable block ([#1471](https://github.com/foolzzz/looper/pull/1471), `manager.stable_context`, default off) and can be told where to look before it asks ([#1468](https://github.com/foolzzz/looper/pull/1468), `manager.research_order`, default off). On the operator's own turns it can read the knowledge vault ([#1477](https://github.com/foolzzz/looper/pull/1477), `manager_read`, default off). Task ends can gather into one completion turn, delivered by a completion service with typed delivery ([#1463](https://github.com/foolzzz/looper/pull/1463)); `manager.completion_turns` stays off. A leads or intents subscription can run a second check before it stores ([#1472](https://github.com/foolzzz/looper/pull/1472), `check_items`, default off). A task's dispatch and step decisions can be recorded ([#1484](https://github.com/foolzzz/looper/pull/1484), `decision_snapshots.enabled`, default off). Settings → Chat can turn the Manager ledger on ([#1492](https://github.com/foolzzz/looper/pull/1492)); `ledger.enabled` stays off until it is exactly `true`. A schedule that already keeps a persistent Planner session now bounds that session before the next resume ([#1473](https://github.com/foolzzz/looper/pull/1473)); that is a default change for those schedules. A Manager or API client that changes where a provider connects, or that installs an MCP server, now waits for confirmation ([#1478](https://github.com/foolzzz/looper/pull/1478)). The tool-less `outbound_check` role and its audit table are added ([#1479](https://github.com/foolzzz/looper/pull/1479)); nothing calls the review, and `outbound_review.enabled` is not in this release. An assistant-experience eval can be run on demand ([#1490](https://github.com/foolzzz/looper/pull/1490)); it does not change the product. The drain/restart test no longer depends on which Worker starts, and the agent-system jobs allow 20 minutes ([#1475](https://github.com/foolzzz/looper/pull/1475)). Docs only: the outbound-review RFC ([#1469](https://github.com/foolzzz/looper/pull/1469)), the memory-write-path RFC ([#1476](https://github.com/foolzzz/looper/pull/1476)), the assistant-layer RFC ([#1481](https://github.com/foolzzz/looper/pull/1481), [#1494](https://github.com/foolzzz/looper/pull/1494)), the memory-tiers RFC ([#1480](https://github.com/foolzzz/looper/pull/1480)) and the engine-reliability RFC ([#1483](https://github.com/foolzzz/looper/pull/1483)). The repository ignores a root `references/` checkout ([#1474](https://github.com/foolzzz/looper/pull/1474)). Skipping a window a prompt hook blocks, or whose reply cannot be read ([#1482](https://github.com/foolzzz/looper/pull/1482)), is not in this release.

## Release Decision

**Who should upgrade:** Anyone whose schedules keep a persistent Planner session, whose Manager or API client changes a provider's endpoints or environment or installs an MCP server, or who will turn on the stable context block, the research order, completion turns, a subscription's second check, the Manager's vault reads, decision snapshots, or the ledger from Settings → Chat. An installation that turns none of these on still applies the additive migrations at startup. With those switches left off, the Manager's prompts and tool lists stay as in v2.15.22, apart from the persistent-session maintenance and the new confirmations, both described under Behavior changes. `chat_settings.get` also answers `ledger_enabled`, false when the row is absent, and that read writes nothing. `web/` changed, so the dashboard bundle is rebuilt by the release workflow as usual.

**What this release solves:** A Manager session can keep one cached copy of its resident state, and can be told to look in its own records, leads, installed tools and the web before it asks the user. The operator can let that Manager read their notes on their own turns. Several task ends in one minute can be told in one message, and a message that tells an end has a typed delivery. A second model can drop or fix a lead or an intent before it is stored. What the engine saw when it dispatched or decided can be replayed later. A persistent Planner session is compacted or rotated before it spends the task budget on context that is already too large. Changing what agents connect to, or installing a server they will run, asks first. The ledger, still off until `ledger.enabled` is exactly `true`, can be turned on from Settings → Chat, which then names enabled Telegram and Lark bots that have no My ID.

**Breaking changes:** No. No existing API drops a field that a caller must send. A schedule that already keeps a persistent Planner session can compact or rotate that session before the next resume. A Manager or API client that changes a provider's endpoints or environment, or that installs an MCP server or enables that install again, now waits for confirmation and can receive HTTP 202; the dashboard still applies those calls at once. Both are under Behavior changes. There are additive PostgreSQL migrations (see Upgrading). The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.15.23
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.15.22 upgrades directly. Restart the service after upgrading, as for every release. `web/` changed, so the release workflow rebuilds the dashboard bundle from `web/` into the wheel, as usual. This pull request does not commit that bundle.

This release has additive PostgreSQL migrations, applied once at startup. They write no lead, intent, completion or snapshot row. A database that has not yet finished `run_tree_online` or `step_difficulty_online` still runs those steps, unchanged from v2.15.22. The new online steps run after the schema transaction commits, validate `NOT VALID` constraints, and build one index concurrently (`idx_schedule_notifications_manager_event`). `decision_snapshots` and `outbound_reviews` create their indexes with the new empty tables and have no other index step.

A database upgraded from v2.15.22 already has that profile; it is no longer the built-in `advice_check` judge, and this release uses it for the second check when the role layer selects none.

## Behavior changes

### Manager stable context, off ([#1471](https://github.com/foolzzz/looper/pull/1471))

- **`manager.stable_context` defaults off.** Absent, or any value other than `true`, leaves it off. There is no dashboard, CLI or HTTP control. While it is off, the Manager's user turns, composed prompt, tool list and process signature are as in v2.15.22. One more system-settings read per turn is the only difference.
- **While it is on,** the resident sections (projects, task templates, workflows, ready tasks, open gates, active goals) are one block, `Looper state (rev R)`, R a hash of the lines. The whole block is sent on a new session (`/new`, a session switch such as a context-full handoff, or no saved session), on a new process (a server restart or an idle close), after a reported compaction (`compact_boundary`) or a turn the session ran on its own, after a turn that did not go through, and on every turn of a runtime that does not declare `resident_compaction_events`. Only Claude Code declares that. Other runtimes get the whole block every turn, never an unchanged line or a note. A compaction, or a turn the session ran on its own, moves a context generation on: a turn rendered before that is rendered whole again just before its message is written, and a turn keeps its block only for the generation it was rendered for. Any other turn starts with `Looper state: unchanged since rev R`, or with the lines added and removed since the last whole block, never since the previous note. A note that changes more than 30 percent of the non-blank lines (a replaced line counts twice), or is longer than 40 percent of the new block, is a new whole block. Exactly 30 percent or 40 percent is still a note. An open gate's line says when it opened, in UTC to the minute, instead of how long it has been open. The contract ends with `STABLE_CONTEXT_CONTRACT`. Each turn's record can carry `metadata.looper_state`. Turning the switch on or off changes the system prompt, so the process restarts once and resumes its session. The switch applies to the default Manager and to scenario Managers, in every channel.

### Research order, off ([#1468](https://github.com/foolzzz/looper/pull/1468))

- **`manager.research_order` defaults off.** `chat_settings.get` and `chat_settings.update` carry `research_order`, false unless it is true. The architecture note names Settings → Chat. This release's page saves `stop_enabled`, `completion_turns` and the ledger checkbox, and does not save `research_order`, so there is no dashboard switch for the research order. While it is off, no prompt text, tool or signature element is added.
- **While it is on,** only the default Manager's contract gains a `## Looking things up` section (`+RESEARCH_ORDER`), before `STABLE_CONTEXT_CONTRACT`. It names the sources that turn really has, in order: the knowledge vault when the turn lists both vault reads, Looper's own records, message leads when the turn lists `looper_leads_search`, the tools the runtime loads for this launch (up to 12, Looper's own server left out), then the web when that launch has web tools. A scenario Manager never gets the section. A group turn is not told to search leads. The section is composed per turn, so a group turn after a dashboard turn restarts the resident process, which the tool listing already did.

### Manager vault reads, off ([#1477](https://github.com/foolzzz/looper/pull/1477))

- **`manager_read` defaults off.** It is stored only when true. With it absent or false, the vault setting is byte-identical to before, and the Manager's tool list, prompt and signature are unchanged. `knowledge_vault.get` and `update` answer the field. There is no dashboard switch. Saving it is confirmed like any vault change; the confirmation says the default Manager reads the notes in the dashboard and the user's own direct chats only.
- **While it is on,** and the vault setting holds, the default Manager lists `looper_vault_search` and `looper_vault_read` on the operator's own turns: the dashboard chat with no API client, or a direct chat whose sender is that bot's My ID. A group, another sender, an API client, a turn the model runs on its own, a bot with no My ID, and a scenario Manager do not list them, and a call is `forbidden`. There is never a vault write from the Manager. A search returns paths and snippets. A read returns the note's text, the first 64 KiB, without a sha256. Each answer starts with a notice that the notes are the user's and are not to be quoted in a group. A group reply that shares 16 letters and digits with text returned in the last 24 hours is replaced and not sent. The research-order section names the vault only on a turn that lists both reads.

### Completion turns, still off ([#1463](https://github.com/foolzzz/looper/pull/1463))

- **`manager.completion_turns` stays `off` by default.** With it off, nothing a chat sees changes and no event stays pending. What is new with the switch off: `manager_events.summary` and `system.health` answer more fields (`pending`, `oldest_pending_seconds`, `failing`, `turn_cost_usd`; health's `completion` is null until the first pass); the nullable outbox column `schedule_notifications.manager_event_id`; and a completion-service pass about every 5 seconds that reads `manager_events`. Settings → Chat shows "When a task ends" ("Send the task notice" or "The Manager tells the chat") and the last 24 hours of ends.
- **While it is `dm_only`.** A chat's first task end opens a 60-second window. Ends before it closes are told in one turn, at most 10 events a batch. The completion service (`completion_service`, one per `looper serve`) queues `COMPLETION_DUE` when the oldest pending event is due, at most one queue per chat per 30 seconds, and at once when an end is recorded. A pending event that waited 15 minutes falls back (`queue_deadline`). A Manager that does not run gets the notice (`manager_off`). On service start, `running` events of Managers that do not run fall back with `restart`. A schedule run's message to an allowlisted direct chat is `pending` for the default Manager when the task ended and `notify` sends that run (`failures`: only a failed run). A chat bound to a Manager is `skipped` / `group_chat` and keeps the code notice. A Lark task with no reply route uses the direct chat that person's latest task with that bot recorded; with none, the end is `skipped` / `no_chat`. A batch whose schedule moved is `target_changed`.
- **Typed delivery.** The reply or the code notice moves `pending` to `sending` (committed before the channel is asked), then `sent`, `failed` (retried with backoff, 8 tries) or `uncertain` (never sent again). A stale `sending` becomes `uncertain`, not a resend. `schedule_notifications.manager_event_id` names the event for a run message and is null while the switch is off.

### Leads check, off per subscription ([#1472](https://github.com/foolzzz/looper/pull/1472))

- **`check_items` defaults false,** including the presets. While it is false, extraction prompts, command lines, stored rows, `extract_counts` and confirmation versions are as before. A push subscription cannot set it, and a push subscription's confirmation version is unchanged. Turning it on, or changing the check's profile, clears the confirmation; the version then binds the check and the profile's facts.
- **While it is on,** after parse and before the storing transaction, the tool-less `leads_check` role checks each item against the messages it cites. The built-in profile is `claude-code/haiku-5-5` (`claude-haiku-5-5`) unless Settings → Roles selects another. A verdict is `keep`, `drop` or `fix`. A drop stores the item as `dropped` (a lead merges into nothing and supersedes nothing; an intent is handled by the system at once and is never pushed). A failed check stores every item unchecked and the run still succeeds. `subscription_runs.check_status` is `skipped`, `checked` or `failed`. As many `failed` runs in a row as the schedule's failure alert waits for (3 by default) send one `check_alert`; a `skipped` run neither ends nor adds to that streak; the next `checked` run sends `check_recovered`. The leads backfill does not run the check.
- **Visible with the check off.** Settings → Roles lists Leads check. `dropped` is a lead and intent state; the default search excludes it, and `all` lists it last, labelled 已被复核丢弃. Marking a dropped lead inaccurate is refused. `looper leads eval-export` writes JSONL outside a git work tree (or to a path git ignores) and exits 4 before reading the database otherwise. `intents.stats` counts `dropped` apart from `recognized`.

### Decision snapshots, off ([#1484](https://github.com/foolzzz/looper/pull/1484))

- **`decision_snapshots.enabled` defaults off.** Absent, or any value other than `true`, leaves it off. A failed or timed-out read counts as off. There is no dashboard switch. While it is off, no row is written, and prompts, tool lists and command lines are unchanged. What still happens with the switch off: one indexed system-settings read, bounded to 1 second, before each dispatch pass (outside the project's dispatch lock), before each applied step decision, and in each hourly housekeeping pass; the housekeeping log line gains `decision_snapshots_deleted=0`; `looper decisions replay` exists and exits 1 when a task has no rows.
- **While it is on,** one dispatch snapshot is written per dispatch pass, before its work steps start, and one step-decision snapshot per applied `accept`, `review`, `retry`, `replan` or `fail` (`advise` and a checkpoint's `proceed` are not recorded). A pass whose inputs and decision equal the task's last one is not written again. No message text is stored. Nothing flows back into a prompt, a tool or a channel. A write that fails is logged and the decision goes on. Each snapshot's database work, connection-pool waits included, has 1 second; past that the snapshot is dropped. Rows go with their task. Hourly housekeeping deletes rows older than 30 days only while the switch is on.
- **Replay.** `looper decisions replay TASK_ID` reads the database directly, including while the service is stopped. Exit 0 means every stored snapshot replays the same, 1 means none were recorded, 3 means some differ, and 6 means the database cannot be used. The dashboard, Telegram and Lark have nothing to show.

### Manager ledger, still off ([#1492](https://github.com/foolzzz/looper/pull/1492))

- **`ledger.enabled` stays off until it is exactly `true`.** No row, or any other value, leaves it off. With the row absent, `chat_settings.get` reports `ledger_enabled` false and writes nothing. While it is off, prompts, tool lists and command lines do not mention the ledger, `looper ledger` exits 3, and the two reads answer `conflict`, as in v2.15.22.
- **Settings → Chat** has a checkbox below "When a task ends", with one line of help. Checking it stores `ledger.enabled` as `true`. Unchecking stores `false`. The operator's dashboard call applies at once. There is no confirmation dialog. Turning it on returns `missing_operator_ids`: every enabled `telegram`, `lark` and `lark_bot` whose `operator_sender_id` is absent or blank. A bot with a blank display name is listed by its channel id. A non-empty list is an inline notice of those names, and the words Settings → Channels link to the channels page. An empty list shows no notice. The list does not re-check the id and does not match channel ids by substring. Channel transports are unchanged. `false` omits the list. `null` deletes the row, and the ledger is off again. `chat_settings.get` never includes `missing_operator_ids`.
- **Only the operator can set `ledger_enabled`.** A client token that includes the field gets 403, including when the same body also sets another chat setting, and nothing in that body is stored. The other fields of `chat_settings.update` stay available to a client, with the existing confirmation. The generated client command `loopercli chat-settings update` has `--ledger-enabled`; a client that sends the field is refused.
- **While it is on,** the default Manager's ledger tools and registration stay as in v2.15.22. This release does not add the To-do page, the ledger contract in the Manager's system prompt, or HTTP writes of ledger items. `research_order` stays off this page. No schema change.

### Persistent Planner sessions, bounded by default ([#1473](https://github.com/foolzzz/looper/pull/1473))

This changes default behavior for a schedule that already keeps a persistent Planner session (`skip` or `queue`). Schedules without a stored session, parallel runs and ordinary tasks keep their prompts, tools and launch commands.

- Before resume, context strictly above `scheduler.session_context_max_tokens` (default 100,000; allowed 40,000 to 100,000,000) triggers maintenance. Cost also triggers it when context is at least half that threshold and the previous run's Planner cost is strictly above half the effective task budget. Equality at either upper limit does not. A small context does not rotate only because the previous run was expensive.
- Unknown context is recovered from the old holder's last Planner record when that measurement exists. If it stays unknown, Claude Code, OMP, Pi and the Model API rotate; Codex, Cursor, Grok, Coco and DSH keep resuming. An unknown cost rotates when the cost rule's context floor applies.
- Claude Code, which declares `headless_compaction`, compacts a measured session when maintenance is required and the context is at most three times the threshold. Looper requires a `compact_boundary`. Above three times the threshold, or when the frozen launch price estimates uncached input above half the task budget, the session rotates. Native Claude Code reports its own cost and has no launch price, so it may compact up to three times the threshold even with a budget. A failed compaction rotates.
- The run records `planner_session_action` (`compacted` or `rotated`), `planner_session_reason` (`context` or `cost`), and the before and after sizes. `failure_kind` is published only for a failed run, and only as `task_budget`. The redundant history setting is removed from HTTP, Manager settings and configuration transfer. Reset stays `POST /api/v1/schedule_admin/reset_planner_session`, the schedule row's Reset Planner session button, or the Manager's `reset_planner_session` action.

### Provider routes and MCP installs ask first ([#1478](https://github.com/foolzzz/looper/pull/1478))

This changes default behavior. There is no new switch.

- A Manager `looper_providers` update that sets `endpoints` or `env` waits for confirmation. The confirmation names the account, how many Agent Profiles use it, the new endpoints, and the environment variables' names. Values are never shown. The confirmed call is frozen to that account. A change the registry would refuse (a credential in `env`, a bad endpoint) is refused before anyone is asked. A rename, `max_concurrency` and `enabled` still apply at once. Registering a new account still applies at once.
- Installing an MCP server, or enabling an install of one again, waits for confirmation, from the Manager's `looper_catalog` and from an API client's `installs.create` and `installs.update`. Those two operations can return HTTP 202. The impact shows the command line and the variables' names, or the URL of a remote server. An install already in that place is still a conflict, before anyone is asked. A skill or a plugin still installs at once. Disabling an install, or changing its roles, needs no confirmation.
- The operator's own dashboard calls still apply at once. No schema change.

### Outbound check, not called yet ([#1479](https://github.com/foolzzz/looper/pull/1479))

The tool-less role `outbound_check` is seeded (Outbound check, 30 seconds, built-in profile `claude-code/sonnet-5-5` when the role layer selects none). Settings → Roles API and configuration transfer accept the role. `outbound.review()` can allow or block one proposed action and writes an `outbound_reviews` row, but no tool, hook or HTTP route calls it. The switch `outbound_review.enabled` is not in this release. Prompts, tool lists and command lines of running agents are unchanged. A non-operator turn would be blocked by code without a run; that path is not reached. The dashboard has no role row and no audit list for it yet.

### Manager stable context

**Activation:** Off until the system setting `manager.stable_context` is `true`. No row, or any other value, leaves it off. This release has no dashboard, CLI or HTTP write for that setting. **Validation:** With the setting absent, a user turn matches v2.15.22. With it `true`, the first turn of a new session starts with `Looper state (rev R)`, an unchanged state starts with `Looper state: unchanged since rev R`, and a runtime that does not declare `resident_compaction_events` gets the whole block on every turn. **Disable / rollback:** Delete `manager.stable_context`, or set it to any value other than `true`. The next turn is rendered as in v2.15.22, and the process restarts once. Nothing was stored that has to be deleted. No table is dropped.

**Authority boundary:** The setting is a system-settings row. There is no channel command and no Manager tool that turns it on. The block is the same sections the Manager already rendered. It is not a new tool and it does not read the vault, leads or the web.

### 升级决策

**谁需要升级：**定时任务保留了规划者会话的安装，Manager 或 API 客户端会改 provider 的端点或环境、或会安装 MCP 服务器的安装，以及要打开稳定内容块、查找顺序、完成回合、订阅的第二次核对、Manager 知识库只读、决策快照，或要从 Settings → Chat 打开账本的安装。这些都不打开的安装，启动时仍会执行可加的迁移。开关保持关闭时，Manager 的提示词和工具列表与 v2.15.22 相同，除了下面行为变化里的规划者会话维护，以及新的确认。`chat_settings.get` 也会回答 `ledger_enabled`，没有这一行时为 false，这次读取什么都不写。`web/` 有改动，仪表盘包由发布流程照常重新构建。

**解决了什么：**Manager 会话可以只缓存一份常驻状态，并在问用户之前先查自己的记录、线索、装上的工具和网页。操作者可以让这个 Manager 在自己的回合里读笔记。同一分钟里的多次任务结束可以合成一条消息，告诉结束的那条消息有类型化的投递。第二个模型可以在线索或意图写入之前丢掉或改它。引擎分发或做决定时看见的内容，之后可以重放。过大的常驻规划者会话会在花掉任务预算之前被压缩或换掉。改 agent 要连接的地方，或安装它们要跑的服务器，会先问一声。账本在 `ledger.enabled` 正好是 `true` 之前仍关闭，可以从 Settings → Chat 打开；打开时会列出没有填 My ID 的已启用 Telegram 和 Lark 机器人。

**是否有破坏性变更：**无。已有 API 没有去掉调用方必须发送的字段。已经保留规划者会话的定时任务，下一次恢复之前可能会压缩或轮换这个会话。Manager 或 API 客户端更改 provider 的端点或环境，或安装、重新启用 MCP 服务器时，现在要等确认，并可能收到 HTTP 202；仪表盘仍立刻执行。这两项见行为变化。有可加的 PostgreSQL 迁移（见升级）。桥接边界不变：早于 v2.13.165 的安装须先升级到 v2.13.165。

- `manager_event_reasons`（[#1463](https://github.com/foolzzz/looper/pull/1463)）：替换 `manager_events_reason_check`，`NOT VALID`，使 `reason` 可以是 `off`、`group_chat`、`manager_off`、`turn_failed`、`turn_timeout`、`turn_stopped`、`empty_reply`、`send_failed`、`queue_deadline`、`restart`、`no_chat` 或 `target_changed`。在线步骤 `manager_event_reasons_online` 校验 `manager_events_reason_check`。约束从本 schema 的 `manager_events` 表读取。
- `manager_event_delivery`（[#1463](https://github.com/foolzzz/looper/pull/1463)）：给 `manager_events` 增加 `delivery`、`delivery_attempts`（整数，非空，默认 0）、`delivery_at`、`delivery_error` 和 `delivery_claim`，以及 `manager_events_delivery_check`（`pending`、`sending`、`sent`、`failed` 或 `uncertain`），`NOT VALID`。在线步骤 `manager_event_delivery_online` 校验 `manager_events_delivery_check`。
- `leads_check`（[#1472](https://github.com/foolzzz/looper/pull/1472)）：给 `subscriptions` 增加 `check_items`（布尔，非空，默认 false）和 `check_alert_at`；给 `subscription_runs` 增加 `check_status`；给 `message_leads` 和 `intents` 增加 `check_verdict`、`check_reason` 和 `check_record_id`。列本身不带检查。每条约束都以 `NOT VALID` 加上：`agent_setting_layers_role_check`（也接受 `leads_check`）、`subscription_runs_check_status_check`（`skipped`、`checked` 或 `failed`）、`schedule_notifications_kind_check`（也接受 `check_alert` 和 `check_recovered`），以及 `message_leads` 和 `intents` 上的状态检查（也接受 `dropped`）、`check_verdict`（`keep`、`fix` 或 `drop`）、`check_reason`（最多 200 个字符）、`check_record_id` 指向 `llm_records(id)` 且 `ON DELETE SET NULL`，还有 `dropped`（`state` 为 `dropped` 当且仅当 `check_verdict` 为 `drop`）。在线步骤 `leads_check_online` 校验这些约束。新库在自己的事务里校验它们，仍然只记录基线。
- `decision_snapshots`（[#1484](https://github.com/foolzzz/looper/pull/1484)）：创建空表 `decision_snapshots`（`kind` 为 `dispatch` 或 `step_decision`，`inputs` 和 `decision` 为对象，`inputs_sha256`，可空的 `step_id` 和 `record_id`，`created_at`），以及索引 `idx_decision_snapshots_task` 和 `idx_decision_snapshots_created`。`task_id` 指向 `tasks(id)`，`ON DELETE CASCADE`。`record_id` 没有外键，所以不会锁 `llm_records`。`kind` 为 `step_decision` 时 `step_id` 必须有值，否则必须为空。不改写已有行。这次迁移没有在线步骤。
- `outbound_reviews`（[#1479](https://github.com/foolzzz/looper/pull/1479)）：创建空表 `outbound_reviews`，以及索引 `idx_outbound_reviews_created`、`idx_outbound_reviews_task`（`task_id` 非空）和 `idx_outbound_reviews_blocked`（`verdict` 为 `block`）。`task_id` 指向 `tasks(id)`，`ON DELETE CASCADE`。`record_id` 和 `parent_record_id` 没有外键。当 `llm_records_run_kind_check` 或 `agent_setting_layers_role_check` 还没有列出 `outbound_check` 时，那条约束以 `NOT VALID` 替换，不改写已有行。角色检查这时也列出 `outbound_check`，以及 `leads_check`。在线步骤 `outbound_reviews_online` 校验 `llm_records_run_kind_check` 和 `agent_setting_layers_role_check`。新表自己的检查随表创建。这次迁移不写复核行。

启动时若还没有，会插入模型 `claude-haiku-5-5` 和内置 Profile `claude-code/haiku-5-5`（给 `leads_check`）。同名 id 的已有 Profile 保持原样。从 v2.15.22 升级的库已经有这个 Profile；它不再是内置的 `advice_check` 判别，本版本在角色层没有另选时用它做第二次核对。

### 行为变化

**Manager 稳定内容块，默认关闭（[#1471](https://github.com/foolzzz/looper/pull/1471)）**

- **`manager.stable_context` 默认关闭。**没有这一行，或取值不是 `true`，都算关闭。没有仪表盘、CLI 或 HTTP 开关。关闭时，Manager 的用户回合、拼好的提示词、工具列表和进程签名与 v2.15.22 相同。每回合多读一次系统设置，是唯一的差别。
- **打开之后，**常驻各节（项目、任务模板、工作流、就绪任务、未关闭的关卡、进行中的目标）合成一块 `Looper state (rev R)`，R 是这些行的哈希。整块在这些时候发出：新会话（`/new`、会话切换例如上下文满了之后的交接、或没有保存的会话）、新进程（服务重启或空闲关闭）、会话报告了压缩（`compact_boundary`）或自己跑了一回合之后、没有走完的回合之后，以及没有声明 `resident_compaction_events` 的运行时的每一回合。只有 Claude Code 声明了这一点。其他运行时每一回合都拿到整块，不会是「未变」一行，也不会是差异说明。压缩或会话自己跑的回合会推进上下文代次：在那之前渲染的回合，会在消息写入前再整块渲染一次，一个回合只保留它渲染时所在代次的那一块。其余回合以 `Looper state: unchanged since rev R` 开头，或列出相对上一整块增加和删掉的行，不会相对上一条差异说明。非空行变化超过 30%（被替换的一行算两次），或说明长过新块的 40%，就再发一整块。刚好 30% 或 40% 仍然是说明。未关闭关卡的一行写打开时间，UTC 到分钟，不再写已经开了多久。契约以 `STABLE_CONTEXT_CONTRACT` 结束。每回合的记录可以带 `metadata.looper_state`。打开或关掉都会改系统提示词，进程重启一次并恢复会话。这个开关对默认 Manager 和场景 Manager、所有渠道都生效。

**查找顺序，默认关闭（[#1468](https://github.com/foolzzz/looper/pull/1468)）**

- **`manager.research_order` 默认关闭。**`chat_settings.get` 和 `chat_settings.update` 带 `research_order`，不是 true 就是关。架构说明写了 Settings → Chat。本版本的这一页保存 `stop_enabled`、`completion_turns` 和账本复选框，不保存 `research_order`，所以查找顺序没有仪表盘开关。关闭时不增加提示词、工具或签名里的内容。
- **打开之后，**只有默认 Manager 的契约多一节 `## Looking things up`（契约层里的 `+RESEARCH_ORDER`），位于 `STABLE_CONTEXT_CONTRACT` 之前。它按顺序列出这一回合真正有的来源：这一回合列出了两个知识库读工具时才有知识库，然后是 Looper 自己的记录，列出了 `looper_leads_search` 时才有消息线索，然后是这次启动真正装上的工具（最多 12 个，不含 Looper 自己的服务），然后是这次启动有网页工具时的网页。场景 Manager 没有这一节。群回合不会被要求去查线索。这一节按回合拼，所以仪表盘回合之后的群回合会重启常驻进程；工具列表本来就会这样重启。

**Manager 只读知识库，默认关闭（[#1477](https://github.com/foolzzz/looper/pull/1477)）**

- **`manager_read` 默认关闭。**只有为 true 时才写入。没有或为 false 时，知识库设置与以前逐字节相同，Manager 的工具列表、提示词和签名不变。`knowledge_vault.get` 和 `update` 会返回这个字段。没有仪表盘开关。保存时像其他知识库变更一样要确认；确认文案写明默认 Manager 只在仪表盘和用户自己的私聊里读这些笔记。
- **打开并且知识库设置成立时，**默认 Manager 在操作者本人的回合列出 `looper_vault_search` 和 `looper_vault_read`：没有 API 客户端的仪表盘会话，或发送者是该机器人 My ID 的私聊。群、别人、API 客户端、模型自己跑的回合、没有 My ID 的机器人，以及场景 Manager，都不列出，调用是 `forbidden`。Manager 永远没有知识库写入。检索返回路径和片段。阅读返回笔记正文的前 64 KiB，不带 sha256。每条回答开头说明这些是用户自己的笔记，不要在群里引用。群回复若与过去 24 小时内返回的文本有连续 16 个字母或数字，会被换掉并且不发送。查找顺序只有在这一回合列出了两个读工具时才写知识库。

**完成回合，仍然默认关闭（[#1463](https://github.com/foolzzz/looper/pull/1463)）**

- **`manager.completion_turns` 默认仍是 `off`。**关闭时，会话里看见的不变，也没有事件停在待处理。关闭时仍能看见的变化：`manager_events.summary` 和 `system.health` 多了字段（`pending`、`oldest_pending_seconds`、`failing`、`turn_cost_usd`；健康检查里的 `completion` 在第一次扫描之前是 null）；可空的发件箱列 `schedule_notifications.manager_event_id`；完成服务大约每 5 秒扫一次 `manager_events`。Settings → Chat 有「When a task ends」（「Send the task notice」或「The Manager tells the chat」），以及最近 24 小时的结束。
- **设为 `dm_only` 之后。**一个会话的第一次任务结束打开 60 秒窗口。窗口关掉之前的结束在同一回合里说，一批最多 10 条。完成服务（`completion_service`，每个 `looper serve` 一个）在最早的待处理事件到期时把 `COMPLETION_DUE` 放进队列，同一会话 30 秒内最多一次，记下结束时也会立刻看一眼。等了 15 分钟的待处理事件回退（`queue_deadline`）。没有在跑的 Manager 得到代码通知（`manager_off`）。服务启动时，没在跑的 Manager 的 `running` 事件以 `restart` 回退。定时任务发到允许名单里的私聊、任务已结束并且 `notify` 要发这条运行消息时（`failures` 只发失败的），对默认 Manager 是 `pending`。绑到某个 Manager 的会话是 `skipped` / `group_chat`，仍发代码通知。没有回复路由的飞书任务，用这个人最近一次用该机器人记下的私聊；都没有时，这次结束是 `skipped` / `no_chat`。定时任务在检查前改了目标的一批是 `target_changed`。
- **有类型的投递。**回复或代码通知从 `pending` 到 `sending`（问渠道之前先提交），再到 `sent`、`failed`（退避重试，8 次）或 `uncertain`（不再发送）。过期的 `sending` 变成 `uncertain`，不会再发一次。`schedule_notifications.manager_event_id` 标出告诉这条运行消息的事件；开关关闭时它是 null。

**线索第二次核对，按订阅默认关闭（[#1472](https://github.com/foolzzz/looper/pull/1472)）**

- **`check_items` 默认 false，**预设也是。为 false 时，抽取的提示词、命令行、写入的行、`extract_counts` 和确认版本都与以前相同。推送订阅不能设置它，推送订阅的确认版本不变。打开它，或改核对用的 Profile，会清掉确认；之后的版本绑上核对和 Profile 的事实。
- **打开之后，**在解析之后、写入事务之前，不带工具的 `leads_check` 角色按引用的消息核对每一条。内置 Profile 是 `claude-code/haiku-5-5`（`claude-haiku-5-5`），除非 Settings → Roles 另选。结论是 `keep`、`drop` 或 `fix`。丢掉的存成 `dropped`（线索不并入任何一条，也不覆盖任何一条；意图立刻由系统处理，并且永不推送）。核对失败时每条都不经核对就存下，这次运行仍然成功。`subscription_runs.check_status` 为 `skipped`、`checked` 或 `failed`。连续 `failed` 的次数达到定时任务失败告警所等的次数（默认 3）时发一次 `check_alert`；`skipped` 既不结束也不增加这段连续次数；下一次 `checked` 发 `check_recovered`。线索回填不跑这次核对。
- **核对关闭时仍能看见的变化。**Settings → Roles 列出 Leads check。`dropped` 是线索和意图的一种状态；默认检索排除它，`all` 把它列在最后，标签是「已被复核丢弃」。把已丢弃的线索标为不准确会被拒绝。`looper leads eval-export` 把 JSONL 写到 git 工作树之外（或 git 忽略的路径），否则在读库之前以退出码 4 结束。`intents.stats` 把 `dropped` 单独计数，不算进 `recognized`。

**决策快照，默认关闭（[#1484](https://github.com/foolzzz/looper/pull/1484)）**

- **`decision_snapshots.enabled` 默认关闭。**没有这一行，或取值不是 `true`，都算关闭。读失败或超时也算关闭。没有仪表盘开关。关闭时不写行，提示词、工具列表和命令行不变。关闭时仍会发生的事：每次分发之前（在项目的分发锁之外）、每次已应用的步骤决定之前，以及每小时的管家扫描里，有一次最多 1 秒的系统设置读取；管家日志多一项 `decision_snapshots_deleted=0`；`looper decisions replay` 存在，任务没有行时退出码为 1。
- **打开之后，**每次分发在工作步骤开始前写一条分发快照，每个已应用的 `accept`、`review`、`retry`、`replan` 或 `fail` 写一条步骤决定快照（`advise` 和检查点的 `proceed` 不记）。输入和决定都与该任务上一条相同的分发不再写。不存消息正文。不会流回提示词、工具或渠道。写入失败只记日志，决定照常进行。每条快照的数据库工作，含连接池等待，一共 1 秒；超过就丢掉这条快照。行随任务删除。只有开关打开时，每小时的管家才删除超过 30 天的行。
- **重放。**`looper decisions replay TASK_ID` 直接读库，服务停着也能用。退出码 0 表示每条已存快照重放结果相同，1 表示没有记录，3 表示有的不同，6 表示数据库不能用。仪表盘、Telegram 和 Lark 没有可看的内容。

**Manager 账本，仍然默认关闭（[#1492](https://github.com/foolzzz/looper/pull/1492)）**

- **`ledger.enabled` 在正好是 `true` 之前保持关闭。**没有这一行，或其他取值，都算关。没有这一行时，`chat_settings.get` 报告 `ledger_enabled` 为 false，并且什么都不写。关闭时，提示词、工具列表和命令行都不提账本，`looper ledger` 退出码为 3，两个读取操作返回 `conflict`，与 v2.15.22 相同。
- **Settings → Chat** 在「When a task ends」下面有一个复选框，附一行说明。勾上就把 `ledger.enabled` 存成 `true`。取消勾选就存成 `false`。操作者在仪表盘上的调用立刻生效。没有确认框。打开时返回 `missing_operator_ids`：每一个已启用、且 `operator_sender_id` 空着或空白的 `telegram`、`lark` 和 `lark_bot`。没有显示名的机器人用它的 channel id 列出。名单非空时，页面上有一行提示这些名字，其中的 Settings → Channels 链到频道页。名单为空时不提示。这份名单不重新核对 id，也不按子串去比 channel id。渠道传输不变。`false` 不带这份名单。`null` 删掉这一行，账本再次关闭。`chat_settings.get` 从不包含 `missing_operator_ids`。
- **只有操作者能设置 `ledger_enabled`。**客户端令牌只要带上这个字段就得到 403，哪怕同一请求还设置了别的聊天项，这一次请求什么都不存。`chat_settings.update` 的其他字段仍可由客户端修改，并走原有的确认。生成的客户端命令 `loopercli chat-settings update` 有 `--ledger-enabled`；客户端发送这个字段会被拒绝。
- **打开之后，**默认 Manager 的账本工具和登记与 v2.15.22 相同。本版本没有待办页，没有 Manager 系统提示词里的账本契约，也没有写账本条目的 HTTP。`research_order` 仍不在这一页。没有 schema 变化。

**常驻规划者会话，默认有界（[#1473](https://github.com/foolzzz/looper/pull/1473)）****

这是已经保留规划者会话的定时任务（`skip` 或 `queue`）的默认行为变化。没有保存会话的定时任务、并行运行和普通任务的提示词、工具和启动命令不变。

- 恢复之前，上下文严格大于 `scheduler.session_context_max_tokens`（默认 100,000；允许 40,000 到 100,000,000）就做维护。上下文至少达到该阈值的一半，并且上一次运行的规划者花费严格大于有效任务预算的一半时，花费也会触发维护。任一上限刚好相等都不触发。上下文不大时，不会只因为上一次很贵就轮换。
- 未知的上下文会从旧持有者最后一条规划者记录里找回，如果那次测量还在。仍然未知时，Claude Code、OMP、Pi 和 Model API 会轮换；Codex、Cursor、Grok、Coco 和 DSH 继续恢复。花费未知、且上下文已经达到花费规则的下限时，也会轮换。
- 声明了 `headless_compaction` 的 Claude Code，在需要维护且上下文不超过阈值三倍时压缩已测量的会话。Looper 要求有 `compact_boundary`。超过三倍，或按冻结的启动价格估计的未缓存输入超过任务预算的一半时，会话轮换。原生 Claude Code 自己报告花费，没有启动价格，所以即使有任务预算，也可以在三倍阈值以内压缩。压缩失败则轮换。
- 运行记下 `planner_session_action`（`compacted` 或 `rotated`）、`planner_session_reason`（`context` 或 `cost`），以及前后的大小。`failure_kind` 只在失败的运行上出现，并且只为 `task_budget`。多余的历史设置从 HTTP、Manager 设置和配置传输里去掉。重置仍是 `POST /api/v1/schedule_admin/reset_planner_session`、定时任务行上的 Reset Planner session 按钮，或 Manager 的 `reset_planner_session` 操作。

**改 provider 连接和安装 MCP 要先确认（[#1478](https://github.com/foolzzz/looper/pull/1478)）**

这是默认行为变化。没有新开关。

- Manager 的 `looper_providers` 更新若设置了 `endpoints` 或 `env`，要等确认。确认文案写出账号、有多少 Agent Profile 在用它、新的端点，以及环境变量的名字。值从不展示。确认后的调用钉在那个账号上。注册表会拒绝的变更（`env` 里有凭据、端点不合法）在询问之前就拒绝。改名、`max_concurrency` 和 `enabled` 仍然立刻生效。登记一个新账号仍然立刻生效。
- 安装 MCP 服务器，或重新启用一个已有安装，要等确认。Manager 的 `looper_catalog`，以及 API 客户端的 `installs.create` 和 `installs.update`，都是这样。后两个操作可以返回 HTTP 202。影响说明写出命令行和变量名，远程服务器则写出 URL。那个位置已经有安装时，仍是冲突，并且在询问之前。技能和插件仍然立刻安装。停用安装，或改它的角色，不用确认。
- 操作者自己在仪表盘上的调用仍然立刻生效。没有 schema 变化。

**出站核对角色，还没有调用方（[#1479](https://github.com/foolzzz/looper/pull/1479)）**

不带工具的角色 `outbound_check` 已种下（Outbound check，30 秒，角色层没有另选时用内置 Profile `claude-code/sonnet-5-5`）。Settings → Roles 的 API 和配置传输接受这个角色。`outbound.review()` 可以对一个提议的动作允许或拦住，并写一行 `outbound_reviews`，但没有工具、hook 或 HTTP 路由调用它。开关 `outbound_review.enabled` 不在本版本。正在跑的 agent 的提示词、工具列表和命令行不变。不是操作者的回合会由代码拦住并且不启动运行；这条路径现在到不了。仪表盘还没有这个角色的一行，也没有审计列表。

### 可选能力启用与使用

#### Manager stable context

**启用：**系统设置 `manager.stable_context` 为 `true` 之前是关的。没有这一行，或其他取值，都算关。本版本没有仪表盘、CLI 或写这个设置的 HTTP。把系统设置 `manager.stable_context` 写成 `true` 即可。之后对每个 Manager 的下一回合生效。打开或关掉都会让常驻进程重启一次。

**验证：**没有这个设置时，用户回合与 v2.15.22 相同。为 `true` 时，新会话的第一回合以 `Looper state (rev R)` 开头，状态未变时以 `Looper state: unchanged since rev R` 开头，没有声明 `resident_compaction_events` 的运行时每一回合都拿到整块。只有设置打开时，契约才以稳定内容那一节结束。

**停用 / 回退：**删掉 `manager.stable_context`，或把它设成 `true` 以外的值。下一回合按 v2.15.22 渲染，进程重启一次。没有要删的已存数据。没有表被删掉。

**权限边界：**这是一行系统设置。没有渠道命令，也没有 Manager 工具能打开它。这一块就是 Manager 本来就会渲染的那些节。它不是新工具，也不读知识库、线索或网页。

**文档：**https://github.com/foolzzz/looper/blob/v2.15.23/docs/architecture/agent-system.md#manager-looperagentstiersmanagerpy

```bash
looper --version
```

#### Research order

**启用：**`chat_settings.update` 把 `research_order` 设为 true 之前是关的。false 或 null 都是关。本版本的 Settings → Chat 页不保存这个字段。只有默认 Manager 受影响，而且只在设置变为 true 之后的回合。

**验证：**设置为 false 时，拼好的提示词没有 `## Looking things up`，工具列表不变。为 true 时，仪表盘回合列出这一回合有的来源，群回合不提 `looper_leads_search`，场景 Manager 的提示词不变。

**停用 / 回退：**经 `chat_settings.update` 把 `research_order` 设回 false 或 null。这一节会离开默认 Manager 的契约。线索和任务的行不变。没有表被删掉。

**权限边界：**这一节是说明。它不会给这一回合的工具列表里没有的工具。群回合不会被要求去查线索。知识库一步只在这一回合列出了两个读工具时出现。

**文档：**https://github.com/foolzzz/looper/blob/v2.15.23/docs/architecture/agent-system.md#manager-looperagentstiersmanagerpy

```bash
looper --version
```

#### Completion turns

**启用：**`manager.completion_turns` 为 `dm_only` 之前是关的。默认仍是 `off`。在 Settings → Chat 的「When a task ends」里设置，或经 `chat_settings.update`。对下一次任务结束生效。关闭时，会话仍收到代码通知。

**验证：**开关关闭时，一次任务结束是 `skipped`、原因 `off`，通知与以前一样发出。`dm_only` 时，一个会话在 60 秒窗口里的结束合成一条 Manager 消息，大约在第一次结束的一分钟之后。群仍走代码通知。发到允许名单里的私聊的定时任务运行，由默认 Manager 来说。Settings → Chat 显示最近 24 小时，`system.health` 带 `completion`。

**停用 / 回退：**把 `manager.completion_turns` 设回 `off`。之后的结束再次发代码通知。已经存下的事件留到管家清理删掉超过 30 天的行。投递列和 `schedule_notifications.manager_event_id` 留着，不会被删掉。

**权限边界：**完成回合对产品是只读的：它告诉会话，不确认操作。群得不到这个回合。回合没有跑时，服务发送已经记下的通知。定时任务的消息发到事件记下的那个会话，走与运行消息相同的发送路径。

**文档：**https://github.com/foolzzz/looper/blob/v2.15.23/docs/architecture/agent-system.md#task-reports

```bash
looper --version
```

#### Leads check

**启用：**线索或意图订阅把 `check_items` 设为 true 之前是关的。预设保持 false，推送订阅不能设置。创建或更新订阅时带上 `check_items` true，然后重新确认：打开它会清掉确认。核对角色是 `leads_check`，Profile 为 `claude-code/haiku-5-5`，除非 Settings → Roles 另选。v2.15.22 的线索和意图开关仍须打开，订阅仍须确认，否则不会抽取。

**验证：**`check_items` 为 false 时，一次触发只有一次 processor 调用，确认版本不变。为 true 时，写入了行的一次触发记下 `check_status`，丢掉的条目存成 `dropped`，意图则不会被推送。`looper leads eval-export --out leads.jsonl` 在 git 工作树之外写出 JSONL，在工作树之内以退出码 4 结束，并且在读库之前。

**停用 / 回退：**把 `check_items` 设回 false 并再次确认。之后的运行不再核对。已经存下的行，包括 `dropped`，留到操作员删除。`leads_check` 的列和种子 Profile 留着，不会被删掉。

**权限边界：**核对运行不带工具，只看抽取已经解析出的条目和引用的消息。只有它的有类型结论会改一条。它写的东西不会被执行或发送。丢掉的意图永不推送。`looper leads eval-export` 与其他 `looper leads` 命令一样，在 agent 进程里会被拒绝。

**文档：**https://github.com/foolzzz/looper/blob/v2.15.23/docs/architecture/agent-system.md#extraction-subscriptions

```bash
looper leads eval-export --out leads.jsonl
```

#### Manager vault reads

**启用：**知识库设置成立并且 `manager_read` 为 true 之前是关的。这个字段只有为 true 时才写入。经 `knowledge_vault.update` 设置。这次变更像其他知识库变更一样要确认。本版本没有仪表盘开关。之后默认 Manager 只在操作者本人的回合列出这两个读工具。先设置 My ID（Settings → Channels，允许名单里的一个发送者），私聊发送者才会被认成操作者。

**验证：**没有 `manager_read` 时，工具列表与目录一致，提示词没有知识库契约。为 true 时，仪表盘回合和操作者的私聊列出 `looper_vault_search` 和 `looper_vault_read`，检索返回路径和片段，阅读返回笔记正文且不带 sha256。群回合两个都不列，引用了返回笔记的群回复不会发出。

**停用 / 回退：**把 `manager_read` 设为 false，或清掉知识库设置。工具在下一次列出时消失。已经放行的调用在设置关掉后回答 `conflict`。知识库里的笔记不变：Manager 从不写入。没有表被删掉。

**权限边界：**只有默认 Manager，只有操作者本人的回合，只有这两个读。写入调用会被拒绝，并且什么都不写。返回的文本记住 24 小时，复述它的群回复会被扣下。审计结果不留笔记正文。任务里的 agent 仍用它们自己的知识库工具，没有改。

**文档：**https://github.com/foolzzz/looper/blob/v2.15.23/docs/architecture/agent-system.md#the-knowledge-vault-the-operators-notes-read-and-written-through-looper

#### Decision snapshots

**启用：**系统设置 `decision_snapshots.enabled` 为 `true` 之前是关的。没有这一行，或其他取值，都算关。读失败或超时也算关。本版本没有仪表盘开关。把这个系统设置写成 `true`。之后的分发和已应用的步骤决定会被记下。提示词、工具列表和命令行不变。

**验证：**没有这个设置时，完成的任务没有行，`looper decisions replay TASK_ID` 退出码为 1。为 `true` 时，该任务有 `dispatch` 和 `step_decision` 行，每条重放相同则同一命令退出码为 0。管家日志里有 `decision_snapshots_deleted`。不存提示词正文。

**停用 / 回退：**删掉 `decision_snapshots.enabled`，或设成 `true` 以外的值。之后的分发不再写。已经存下的行留到它们的任务被删除。只有开关打开时，管家才删除超过 30 天的行，所以关掉之后这些行还在。表不会被删掉。

**权限边界：**快照是记录。不给模型看，也不改变决定。重放命令读库，什么都不写。服务停着也能用。不发渠道消息。

**文档：**https://github.com/foolzzz/looper/blob/v2.15.23/docs/architecture/agent-system.md#decision-snapshots

```bash
looper decisions replay TASK_ID
```

#### Manager ledger

**启用：**系统设置 `ledger.enabled` 正好为 `true` 之前是关的。没有这一行，或其他取值，都算关。在 Settings → Chat、「When a task ends」下面的复选框打开，或由操作者经 `chat_settings.update` 把 `ledger_enabled` 设为 true。操作者的调用立刻生效。客户端令牌带上 `ledger_enabled` 得到 403，这一次请求什么都不存。先设置 My ID（Settings → Channels，允许名单里的一个发送者），私聊发送者才会被认成用户。设置变成 `true` 之前，默认 Manager 不会列出 `looper_ledger_add` 或 `looper_ledger_update`，`looper ledger` 退出码为 3。

**验证：**没有这个设置时，`chat_settings.get` 报告 `ledger_enabled` 为 false 且什么都不写，`looper ledger list` 退出码为 3。为 `true` 时，默认 Manager 列出这两个工具，仪表盘回合可以新增一条，`looper ledger list` 在有条目时退出码为 0，打开的列表为空时为 1。打开时会列出每一个已启用、且操作者 id 空着的 `telegram`、`lark` 和 `lark_bot`。名单为空时不提示。

**停用 / 回退：**取消勾选，或把 `ledger_enabled` 设为 false 或 null。false 存成 `false`。null 删掉这一行。工具在默认 Manager 下一次列出时消失，命令再次以退出码 3 结束。已经存下的条目留着。账本的表来自 v2.15.19，不会被删掉。

**权限边界：**只有操作者能设置 `ledger_enabled`。客户端仍可改其他聊天设置，并走原有的确认。账本的唯一写入者仍是 `db.ledger.apply`。命令行写入记为用户，并且必须带 `--session`。`LOOPER_AGENT_RUN` 已设置时拒绝。本版本没有待办页，没有 Manager 系统提示词里的账本契约，也没有写账本条目的 HTTP。

**文档：**https://github.com/foolzzz/looper/blob/v2.15.23/docs/architecture/agent-system.md#the-ledger

```bash
looper ledger list
```

# Looper v2.14.42

This is the patch release v2.14.42, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.41: the Manager's `looper_schedules` tool can create, modify and view command schedules ([#981](https://github.com/foolzzz/looper/pull/981)).

## Release Decision

**Who should upgrade:** Anyone who uses the Manager to manage schedules and wants it to handle command schedules (a shell command on a time rule, with no agent) instead of only agent schedules.

**What this release solves:** [#981](https://github.com/foolzzz/looper/pull/981) adds `kind`, `command`, `env`, `env_file`, `success_deadline` and three alert thresholds to the `looper_schedules` parameters. For a command schedule, the configuration block, the before-and-after diff and the confirmation text for enabling and for run-now show the command verbatim and say that it does not use model quota. The list and run summaries include the schedule type and the exit code. A confirmed enable or run-now is also bound to the configuration the user was shown, so an edit made between the question and the answer cannot change what runs.

**Breaking changes:** No. No API or configuration is removed, and there is no new migration or setting. The tool results gain fields: see "Behavior changes".

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#981](https://github.com/foolzzz/looper/pull/981); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.42
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.41 upgrades directly. This release adds no migration and no new setting.

## Behavior changes

- **Command schedules in `looper_schedules` ([#981](https://github.com/foolzzz/looper/pull/981)).** The tool parameters gain `kind` (`agent` or `command`, create only, default `agent`), `command`, `env`, `env_file`, `success_deadline`, `alert_failures_after`, `alert_stale_after_seconds` and `alert_overlap_after`. The tool description now says a schedule can be a shell command with `kind` command.
- **Create.** A new command schedule is created disabled, as before. Its configuration block lists the type, rule, next fires, directory, command, the names of the `env` variables (not their values), the env file path, overlap and catch-up rules, run timeout, success deadline, alert thresholds and notification target.
- **Enable and run-now confirmation.** For a command schedule the question shows the command verbatim, the rule and the directory (and the next fires when enabling), and says the command runs without an agent and without model quota. Agent schedules keep their existing text.
- **Diff on update.** The `command` line appears whenever the command text differs. For `env`, the diff shows variable names only; a changed value is reported by name ("值已修改") without its value.
- **Confirmed actions are bound to what was shown.** When the confirmation is composed, the schedule id and a version hash of its settings (including `env` values, excluding counters and fire times) are stored with the pending confirmation, not in the tool arguments. On confirm, enable, disable and run-now resolve the schedule by that id, even if another schedule has taken its name, and refuse if the settings changed since: the API answers 409 "the schedule configuration changed; run the tool again to ask for confirmation". `Scheduler.run_now`, `schedules.run_now` and `schedules.update_schedule` take an optional `expected_version`; without it, behavior is unchanged.
- **Results.** Each item of the list result gains `kind`, and each run summary gains `exit_code` (null for agent runs); the Manager's result schemas (`LISTED_SCHEDULE`, `LISTED_RUN`) declare both.
- **Model-visible changes:** Yes. The `looper_schedules` tool description and its parameter schema change, its list and run results gain `kind` and `exit_code`, and the confirmation and diff text the Manager relays changes for command schedules. The PR adds an eval dialog for creating a command schedule disabled (the eval README counts 49 dialogs instead of 48) and adjusts the existing agent-schedule dialog to require an agent schedule.

本版本是 patch release v2.14.42（热修线，每个合并的改动立即发布）。自 v2.14.41 以来合并了一项改动：Manager 的 `looper_schedules` 工具可以创建、修改和查看命令定时任务（[#981](https://github.com/foolzzz/looper/pull/981)）。

### 升级决策

**谁需要升级：**用 Manager 管理定时任务，并希望它能处理命令定时任务（按时间规则执行 shell 命令、不经过 agent）而不只是 agent 定时任务的人。

**解决了什么：**[#981](https://github.com/foolzzz/looper/pull/981) 为 `looper_schedules` 增加 `kind`、`command`、`env`、`env_file`、`success_deadline` 和三个告警阈值参数。对命令定时任务，配置块、修改前后对比，以及启用和立即运行的确认文字都会原样显示命令，并说明不花模型额度。列表和运行摘要包含任务类型和退出码。已确认的启用或立即运行还绑定到用户看到的配置，确认前被修改的配置不会改变实际执行的内容。

**是否有破坏性变更：**否。不移除任何 API 或配置，也没有新的迁移或设置。工具结果新增字段，见“行为变化与入口”。

**如何验证：**运行 `looper --version` 核对版本为 2.14.42。

**贡献者：**维护者 @foolzzz 提交 [#981](https://github.com/foolzzz/looper/pull/981)；本版本无社区贡献。

```bash
looper --version   # looper 2.14.42
```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.41 上的安装可直接升级。本版本没有新迁移，也没有新设置。

### 行为变化与入口

- **`looper_schedules` 中的命令定时任务（[#981](https://github.com/foolzzz/looper/pull/981)）。**工具参数新增 `kind`（`agent` 或 `command`，仅创建时可用，默认 `agent`）、`command`、`env`、`env_file`、`success_deadline`、`alert_failures_after`、`alert_stale_after_seconds` 和 `alert_overlap_after`。工具描述说明定时任务也可以是 `kind` 为 command 的 shell 命令。
- **创建。**新的命令定时任务仍然以禁用状态创建。配置块列出类型、规则、接下来的触发时间、目录、命令、`env` 变量名（不含值）、环境文件路径、重叠与错过触发规则、运行超时、最晚成功时间、告警阈值和通知目标。
- **启用与立即运行的确认。**对命令定时任务，提问原样显示命令、规则和目录（启用时还有接下来的触发时间），并说明命令不经过 agent、不花模型额度。agent 定时任务的文字不变。
- **更新时的对比。**命令文字不同时总会显示 `command` 一行。`env` 的对比只显示变量名；值被修改时只按名称报告（“值已修改”），不显示值。
- **确认的操作绑定到所展示的内容。**生成确认时，定时任务 id 和其设置（含 `env` 值，不含计数器和触发时间）的版本哈希与待确认项一起保存，不放在工具参数里。确认时，启用、停用和立即运行按该 id 找到定时任务（即使别的任务占用了它的名称），若设置已变化则拒绝：API 返回 409 “the schedule configuration changed; run the tool again to ask for confirmation”。`Scheduler.run_now`、`schedules.run_now` 和 `schedules.update_schedule` 新增可选的 `expected_version`；不传时行为不变。
- **结果。**列表结果的每一项新增 `kind`，每条运行摘要新增 `exit_code`（agent 运行为 null）；Manager 的结果 schema（`LISTED_SCHEDULE`、`LISTED_RUN`）声明了这两个字段。
- **面向模型的变化：**有。`looper_schedules` 的工具描述和参数 schema 变化，列表与运行结果新增 `kind` 和 `exit_code`，Manager 转述的命令定时任务确认与对比文字也有变化。该 PR 新增一个“创建禁用的命令定时任务”的评测对话（评测 README 的对话数由 48 变为 49），并让原有 agent 定时任务对话要求其类型为 agent。

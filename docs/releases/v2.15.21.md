# Looper v2.15.21

This release documents the changes merged since v2.15.20. A subscription can now select the way an hourly digest does ([#1446](https://github.com/foolzzz/looper/pull/1446)) and cover a rolling day at most once ([#1447](https://github.com/foolzzz/looper/pull/1447)), so those jobs can move onto Looper. Nothing about either runs until such a subscription is created and its push target is confirmed. A subscription with no rules that reads only groups and topics keeps the same input, byte for byte. Schema-change backups keep the `source_events` schema and leave out its rows, and a daily copy of that table is off unless the ops file asks for it ([#1454](https://github.com/foolzzz/looper/pull/1454)). Online schema steps are serialized across processes ([#1453](https://github.com/foolzzz/looper/pull/1453)). Advisor phase 1 has its tables, roles and checks ([#1436](https://github.com/foolzzz/looper/pull/1436), [#1438](https://github.com/foolzzz/looper/pull/1438)); the project switch `advisor` and the Planner side are not in this release. A Manager completion turn is off unless `manager.completion_turns` is `dm_only` ([#1455](https://github.com/foolzzz/looper/pull/1455)). Message leads and intents have their tables and one search function ([#1450](https://github.com/foolzzz/looper/pull/1450), [#1452](https://github.com/foolzzz/looper/pull/1452), [#1459](https://github.com/foolzzz/looper/pull/1459)); nothing extracts, and there is no tool and no page yet.

## Release Decision

**Who should upgrade:** Anyone who will create a digest or daily subscription, turn on daily message backups, or turn on the Manager completion turn. An installation that does none of these keeps its schedules, chats and prompts. Startup applies additive migrations. Two changes apply with no new setting: a schema-change backup made with pg_dump keeps the source_events schema and leaves out its rows, and a provider-priced Claude run bills a one-hour cache write at twice the input price.

**What this release solves:** An operator can express an hourly digest and a rolling daily digest as subscriptions, and can keep seven daily copies of message text. Advisor roles, lead tables and a read-only completion turn are present and do nothing until a later release, or until the completion setting is turned on.

**Breaking changes:** No. No API or schedule that exists today changes its result. A subscription with no rules that reads only groups and topics is unchanged, including its input. There are additive PostgreSQL migrations (see Upgrading). The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.15.21
```

**Contributors:** Maintainer @foolzzz authored [#1446](https://github.com/foolzzz/looper/pull/1446), [#1447](https://github.com/foolzzz/looper/pull/1447), [#1455](https://github.com/foolzzz/looper/pull/1455), [#1459](https://github.com/foolzzz/looper/pull/1459), [#1454](https://github.com/foolzzz/looper/pull/1454), [#1450](https://github.com/foolzzz/looper/pull/1450), [#1452](https://github.com/foolzzz/looper/pull/1452), [#1453](https://github.com/foolzzz/looper/pull/1453), [#1438](https://github.com/foolzzz/looper/pull/1438) and [#1436](https://github.com/foolzzz/looper/pull/1436); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.15.20 upgrades directly. Restart the service after upgrading, as for every release.

This release has additive PostgreSQL migrations, applied once at startup. They write no subscription, lead or consult row.

- `subscription_rules`: adds `subscriptions.rules` (JSONB array, default `[]`) and `subscriptions.config_epoch` (bigint, default 0); adds `subscription_runs.config`, `subscription_runs.config_epoch` and `subscription_runs.match_timeouts` (integer, default 0); widens `subscriptions_render_check` so `render` accepts `lines_v1` and `lines_v2`.
- `subscription_lookback`: adds `subscriptions.window` (`cursor` or `lookback`, default `cursor`) and `subscriptions.delivery_policy` (`per_run` or `daily`, default `per_run`); adds `subscription_runs.window_mode` (default `cursor`) and `subscription_runs.daily_date`; creates `subscription_daily_claims` (`schedule_id`, `local_date`).
- `run_tree`: adds `llm_records.parent_record_id` and `llm_records.run_kind`, with `NOT VALID` constraints. No older row is rewritten; a missing `run_kind` is still read from the agent id. After the schema transaction commits, the online marker `run_tree_online` validates `llm_records_run_kind_check` and `llm_records_parent_record_id_fkey` and builds `idx_llm_records_parent` concurrently.
- `step_difficulty`: adds `task_steps.difficulty` (`routine`, `hard` or `critical`) as `NOT VALID`. The online marker `step_difficulty_online` validates `task_steps_difficulty_check`. Nothing writes the column yet.
- `agent_spawns`: creates `agent_spawns` and `advisor_advice`, with their indexes and constraints. The tables stay empty.
- `advisor_roles`: widens `agent_setting_layers_role_check` so it also accepts `advisor` and `advice_check`. No saved layer is rewritten.
- `message_leads`: adds `source_chats.extraction` (default `included`) and `source_chats.extraction_excluded_at`; widens `subscriptions.output_kind` so it also accepts `leads` and `intents` (the write API still accepts only `push`); widens `subscription_runs.outcome` with `extracted` and adds `subscription_runs.extract_counts`; creates `message_leads`, `message_lead_sources`, `message_lead_people`, `intent_types`, `intent_type_versions` (three built-in types at version 1: `dev_task`, `bug_triage`, `alert_triage`), `intent_type_projects`, `message_chat_projects`, `intent_alert_senders`, `intents`, `intent_sources` and `intent_posts`. Deleting a source message deletes the leads and intents made from it.
- `intent_merges`: replaces a cascading `intents.merged_into` key with `NO ACTION`, and adds the `AFTER DELETE` trigger `A_intents_detach_merged`. Deleting an intent sets every intent merged into it back to `pending`. An intent whose own message is deleted is still deleted.

Online steps (`run_tree_online`, `step_difficulty_online`) take one database-wide session advisory lock after the schema transaction commits. A waiter holds no transaction. After five seconds the start continues and leaves the unmarked steps for the owner or the next start. A caller that is already inside a transaction defers them. A stopped index build is dropped and rebuilt. ([#1453](https://github.com/foolzzz/looper/pull/1453))

Startup also inserts, if they are absent, the models `claude-fable-5-2` and `claude-haiku-5-5` and the built-in profiles `claude-code/fable-5-2` (effort `high`) and `claude-code/haiku-5-5`. An existing profile of the same name is left as it is.

The next schema-changing start takes its usual verified backup first. That dump now keeps the `source_events` schema and leaves out its rows.

## Behavior changes

### Subscription rules, off until one is created and confirmed ([#1446](https://github.com/foolzzz/looper/pull/1446))

- **Until a subscription is created with rules, nothing about them changes.** `rules` defaults to `[]`. With no rules the subscription's own filter applies, and `lines_v1` reads exactly as before. A subscription with no rules that reads only `group` and `topic` is byte-identical, and its `config_version` is unchanged. Existing agent and command schedules, prompts, tool lists and the Manager's commands are unchanged.
- Up to 20 rules. A message is kept when any rule takes it, and the first that does names it. A rule has `name`, `label`, `chat_kinds`, `include_chats`, `exclude_chats`, `sender_kinds`, `exclude_self`, `mentions_me` (`any`, `only` or `exclude`), `text_match`, `never_quiet` and `areas`. `lines_v2` writes `[time] 【label·area】《chat》 sender: text`.
- `output_header` may hold `{count}` and `{count:RULE NAME}`. They are filled only when `rules` is nonempty. Without rules they stay as written.
- `text_match` is operator data, at most 500 characters, checked on Python's own parse tree when it is saved. A repeat whose body holds a repeat or a branch is refused, including as `{,n}` or under a verbose flag. At most 2 repeats may run long (unbounded, or a maximum over 10), at most 8 repeats of any kind, and at most 8 alternations. It runs on the first 1,000 characters of a message, in a separate process killed after 5 seconds, inside the firing transaction. Past that deadline no pattern takes anything in the window and the run records `match_timeouts`.
- **`never_quiet`:** when the processor says the quiet word but the window holds such a message, code writes the list of those messages (per label, at most 30, 200 characters each, the same @ stripping) and that list is pushed like processor output.
- **Private content.** A subscription that can select a direct chat, a chat of unknown kind, `mentions_me: only`, or `never_quiet` may push only to the operator's own direct chat: a Lark chat with the user its source is bound to. A group, a colleague's chat, Telegram and a source with no bound user are refused on create, on an update that changes the stream or the target, on confirm, and before every message. Disabling and renaming still work. Being private is part of `config_version` only when it is true. A subscription with no rules whose `chat_kinds` includes `p2p` or `unknown` counts as private. One that reads only groups and topics does not.
- A run selects with the configuration it started with (`subscription_runs.config`) and pins `config_epoch`. That counter moves on every change of the stream, rules, target, rule, zone, notify, enabled state, Profile choice and every confirmation, so a change and its undoing both stop the push. An in-place edit of the processor's Agent Profile does not bump `config_epoch`; `config_version`, compared before every message and against the Profile the run launched with, covers that edit.
- Rules are set through the API. The dashboard shows that they exist. Creating a subscription may fill `chat_kinds` and `sender_kinds`; an update that adds rules does not fill them.

### Lookback and a daily claim, off until selected ([#1447](https://github.com/foolzzz/looper/pull/1447))

- **Existing subscriptions stay on `window: cursor` and `delivery_policy: per_run`.** Their input, order, headers, cursor and confirmation version are unchanged. The new modes have to be set explicitly. Creating one does not push until the target is confirmed.
- `lookback` ignores the cursor. It selects committed events sent from the firing time minus `max_age_minutes` through the firing time, keeps the newest `max_events`, and renders them oldest first. It never initializes or advances the cursor. Cursor reset is refused. Empty windows, quiet output, failures and restart recovery leave the cursor alone. Age is required on creation. Switching back to `cursor` starts at the source's current end.
- `{date}` in `output_header` is the scheduled fire's local date, `YYYY-MM-DD`, in the schedule's timezone. A manual run uses its request time. Catch-up across midnight keeps the latest missed firing's date. `{date}` works with or without rules. Count placeholders still need nonempty rules.
- `delivery_policy: daily` reserves `(schedule_id, local_date)` in `subscription_daily_claims` before the processor starts, inside the firing transaction. Manual, queued and catch-up fires reserve too. A retained claim blocks that date and any earlier local date, including after the timezone moves backwards. The claimed date is stored on `subscription_runs.daily_date` and is not recomputed when the run ends.
- Quiet output, dashboard-only output, and any sent or uncertain message keep the claim. A failed run, or an interrupted run, with nothing sent or uncertain releases that exact claim in the same transaction, so the same local day can be tried again. A repeated attempt is `skipped_gate`. It does not clear a failure streak and does not update `last_ok_at`. A genuinely empty window is a healthy skip and reserves nothing.
- Changing the window or the policy clears the confirmation and is refused while a run is open. Both are part of `config_version`. The dashboard form is unchanged; these fields are set through the API. Lark and Telegram keep their existing bot delivery.

### Message backups ([#1454](https://github.com/foolzzz/looper/pull/1454))

- **Every schema-change dump made with `pg_dump` now leaves out `source_events` rows.** The table's schema stays. `event_sources`, `source_chats`, `source_threads`, `source_people` and `source_runs` keep their rows. Delivered subscription output stays. Looper appends `--exclude-table-data=source_events` to its own `pg_dump` and to a `backup.command` whose program is `pg_dump`, including one run through `docker exec`. A command that is not `pg_dump` is unchanged and must exclude that data itself. The startup log says the dump keeps the schema and leaves out the rows. A restore of that dump has the chats and not the message text.
- **The daily copy is off.** `[backup] messages = "daily"` writes `looper-<database>-<UTC stamp>.messages.dump` in the runtime root's `backups/` directory, schema and rows, at most once a day, and keeps the newest 7. The name ends in `.messages.dump`, so rotating it cannot delete a schema-change dump, and the other way around. Omit `messages`, or set `"off"`, and serve does not write or delete one. A failed attempt is not retried until a day later, or at the next start when the newest copy is already a day old. Stopping the service stops that `pg_dump`. Restore a message backup into a database that already has the source's chats. Two servers can each write a copy; there is no lock between them.

### Online schema steps ([#1453](https://github.com/foolzzz/looper/pull/1453))

Validating a `NOT VALID` constraint and building an index concurrently used to deadlock when two processes started together. Those steps now take one session advisory lock, distinct from the schema transaction's lock. The waiter does not hold a transaction. After five seconds the start continues and the unmarked steps wait for the owner or the next start. A start that is already inside a transaction defers them. Prompts, tools and defaults are unchanged.

### Advisor phase 1 groundwork, unused ([#1436](https://github.com/foolzzz/looper/pull/1436), [#1438](https://github.com/foolzzz/looper/pull/1438))

- **No task can open a consult.** The project switch `advisor` and the Planner side are not in this release. Those pull requests are still open. Nothing in a Planner prompt, a Worker prompt or a command line names the advisor.
- **What is present.** `Launch.access` is `full`, `read_only`, `consult` or `advisor`. `None` is still the role's own level: `read_only` for a Planner, `full` for every other role. `spawn` can run one tool-less child and record it on `agent_spawns`. The request and the answer are parsed and checked (format, a code lint, then an `advice_check` judge), and an advisor round can be run. Nothing calls that path from a task.
- **Settings.** Settings → Agent Profiles lists two more built-in profiles: `claude-code/fable-5-2` (`claude-fable-5-2`, effort `high`) for `advisor`, and `claude-code/haiku-5-5` for `advice_check`. The agent-settings API lists both roles. Settings → Roles does not list them yet. If a profile of either name already exists, the seed skips it and that role does not run until one is chosen. The Claude login catalog gains the two models under their full ids.
- **Prices.** `claude-fable-5-2` is 8, 40, 0.20 and 10 USD per million tokens for input, output, cache read and a five-minute cache write, and 16 for a one-hour cache write. The `fable` alias resolves to it. Anthropic models in the built-in table bill a one-hour cache write at twice the input price. A write whose duration is unknown is billed at that rate, so the figure is not below what was spent. A run priced from the runtime's own report is unchanged. A spawned run priced from a provider, whose writes do not say how long they last, gives no output.
- New run records store `run_kind`. Older rows are not rewritten.

### Manager completion turn, off ([#1455](https://github.com/foolzzz/looper/pull/1455))

- **`manager.completion_turns` defaults to `off`.** A task end is still the code notice. A user's turn has the same command, tool list, turn text and system prompt. `chat_settings.get` and `chat_settings.update` gain the field. An update may send one field. A missing or invalid stored value is `off`.
- **`dm_only`**, set with `chat_settings.update`, applies to the next task end. The end of a task asked for in a dashboard chat or a Telegram or Lark direct chat is told by the Manager in one read-only `[COMPLETION]` turn, instead of the notice. A group stays on the notice (`skipped`, `group_chat`). A schedule's run message stays on the notice (`skipped`, `off`). A report that did not reach the task's own Manager is `skipped` with `manager_off`.
- The turn claims up to 10 pending events of that chat, does not stream, and is the chat's live turn, so `/stop` there stops it. A write answers `needs_user_turn` and does not consume a confirmation waiting in the chat. The reply goes where the notice would, and code appends each task's link line. If the turn fails, times out (120 seconds), is stopped, is empty, or cannot be sent, the recorded notice is sent unchanged. A restart sends notices left unsent and wakes chats that still have pending events.

### Message leads and intents, off ([#1450](https://github.com/foolzzz/looper/pull/1450), [#1452](https://github.com/foolzzz/looper/pull/1452), [#1459](https://github.com/foolzzz/looper/pull/1459))

- **Default off.** The tables are empty of extracted rows. No subscription is created. The write API still accepts only `output_kind` `push`. No prompt, tool or command line mentions leads. There is no extraction run, no `looper leads` command, no Manager tool and no page. The search function and the operator check exist for later slices and have no caller on this release.
- Deleting an intent does not delete intents that were merged into it. Those become `pending` again (`intent_merges`). An intent whose own source message is deleted is still deleted. Nothing writes an intent yet, so this changes no stored row today.
- [#1450](https://github.com/foolzzz/looper/pull/1450) is the RFC only.

## Optional Capability Activation & Use

### Digest and daily subscriptions

**Activation:** Off until an operator creates a schedule of kind `subscription` that sets `rules`, `window: lookback` or `delivery_policy: daily`, and then confirms its push target. There is no setting that turns these modes on. A subscription with no rules, `window` `cursor` and `delivery_policy` `per_run` behaves as in v2.15.20. A new subscription is disabled, and in cursor mode its cursor starts at the source's committed sequence. `target_confirmed_at` is unset, so the output stays on the dashboard. The same confirmation as v2.15.20 applies: the dashboard's "Confirm push target…" shows the target and calls `schedule_admin.confirm_target` with the `config_version` just shown. A private subscription (direct chats, chats of unknown kind, `mentions_me: only`, or `never_quiet`) can be confirmed only for the operator's own Lark direct chat. Set the daily fields through `schedule_admin.create` or `schedule_admin.update`: `window` `lookback`, `max_age_minutes` 1440, `delivery_policy` `daily`, `render` `lines_v2`, and `output_header` with `{date}` and, when rules are nonempty, `{count}`.

**Validation:** Before confirmation, a run with output ends `dashboard_only` and the channel is not asked. After `confirm_target` accepts the version the schedule has now, a firing with selected events runs the processor and posts to the confirmed direct chat or bound group. A `text_match` with a nested repeat is refused. A second daily firing on a claimed local date does not start the processor. A failed daily run that sent nothing releases that date, and a later firing the same local day can run. A subscription with no rules that reads only groups and topics still renders `lines_v1`.

**Disable / rollback:** Disable the schedule, or delete it. Set `rules` back to `[]`, `window` back to `cursor` and `delivery_policy` back to `per_run`; changing the window or the policy clears the confirmation. The new columns and `subscription_daily_claims` are additive. With no such subscription they are unused. The tables are not dropped by turning the modes off.

**Authority boundary:** An operator or an API client manages the subscription through `schedule_admin`, and a high-risk write waits for confirmation. The push goes out as the bot, only to an allowlisted direct chat or a bound group, and only while the confirmed `config_version` and the pinned `config_epoch` are still the schedule's. Private content may go only to the operator's own direct chat. The Manager cannot create or change one and sees state and counts only. The processor runs with no tools. Logs of a push carry error types and ids, not message text.

**Docs:** https://github.com/foolzzz/looper/blob/v2.15.21/docs/architecture/agent-system.md#subscriptions-a-message-stream-on-a-time-rule

```bash
loopercli schedule-admin confirm-target --schedule-id SCHEDULE_ID --config-version CONFIG_VERSION
```

### Message backups

**Activation:** The daily backup of `source_events` is off until the ops file sets `[backup] messages` to `"daily"`. There is no environment variable and no dashboard switch. Omit the key, or set `"off"`, and serve does not write or delete a message backup. The schema-change exclusion is not optional: the next schema-changing start, using built-in `pg_dump` or a `backup.command` whose program is `pg_dump`, keeps the `source_events` schema and leaves out its rows. Restart the service after editing the ops file.

**Validation:** With `messages` unset, the `backups/` directory gains no file whose name ends in `.messages.dump`. With `messages = "daily"`, one such file appears, at most once a day, and a sixth older copy is removed when a seventh new one is written. A schema-change dump made with `pg_dump` lists the `source_events` table and not its rows. `looper doctor` still reports the verifier used for a schema-change dump.

**Disable / rollback:** Set `[backup] messages` to `"off"`, or remove the key, and restart. Serve then neither writes nor deletes a message backup. Copies already written stay until an operator removes them. The schema-change exclusion stays: a dump from this release does not hold message rows. To roll back the service, stop it, leave the upgraded database unchanged, and restore a verified backup into a separate database. Restore a `.messages.dump` only into a database that already has the source's chats.

**Authority boundary:** Only the operator's ops file turns the daily backup on. The files are mode 0600 in the runtime root's `backups/` directory and hold message text. No agent, prompt or tool reads or writes them. A schema-change dump no longer holds that text. Two servers sharing one database can each write a daily copy; there is no lock between them.

**Docs:** https://github.com/foolzzz/looper/blob/v2.15.21/docs/architecture/agent-system.md#message-stream

```bash
looper service restart
```

## 中文摘要

本版本说明自 v2.15.20 以来合并的改动。订阅可以按小时摘要那样筛选（[#1446](https://github.com/foolzzz/looper/pull/1446)），也可以用回看窗口做每天至多一次的日报（[#1447](https://github.com/foolzzz/looper/pull/1447)），因此这两类任务可以迁到 Looper。不创建并确认这种订阅，就没有这项行为。没有规则、只读群和话题的订阅，输入逐字节不变。schema 变更时的备份保留 `source_events` 的表结构、不保留它的行；每天一份消息备份默认关闭，除非运维文件要求（[#1454](https://github.com/foolzzz/looper/pull/1454)）。在线 schema 步骤改为跨进程串行（[#1453](https://github.com/foolzzz/looper/pull/1453)）。Advisor 第一期有了表、角色和检查（[#1436](https://github.com/foolzzz/looper/pull/1436)、[#1438](https://github.com/foolzzz/looper/pull/1438)）；项目开关 `advisor` 和规划者一侧不在本版本。Manager 的收尾回合默认关闭，除非 `manager.completion_turns` 设为 `dm_only`（[#1455](https://github.com/foolzzz/looper/pull/1455)）。消息线索和意图有了表和一个查询函数（[#1450](https://github.com/foolzzz/looper/pull/1450)、[#1452](https://github.com/foolzzz/looper/pull/1452)、[#1459](https://github.com/foolzzz/looper/pull/1459)）；还没有抽取，也没有工具和页面。

### 升级决策

**谁需要升级：**要创建摘要或日报订阅、打开每日消息备份、或打开 Manager 收尾回合的安装。三者都不做的安装，其定时任务、聊天和提示词保持原样。启动时会执行可加的迁移。没有新开关也会变的有两处：用 pg_dump 做的 schema 变更备份保留 source_events 的表结构、不保留行；按服务商价格计费的 Claude 运行，把一小时缓存写入按输入价格的两倍计算。

**解决了什么：**操作员可以把小时摘要和滚动日报写成订阅，并保留七份消息原文的每日备份。Advisor 角色、线索表和只读的收尾回合已经在，但在后续版本之前、或在打开收尾设置之前，不会做事。

**是否有破坏性变更：**无。今天已有的 API 和定时任务的结果不变。没有规则、只读群和话题的订阅不变，包括它的输入。有可加的 PostgreSQL 迁移（见升级）。桥接边界不变：早于 v2.13.165 的安装须先升级到 v2.13.165。

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.15.20 上的安装可直接升级。升级后照常重启服务。

本版本有可加的 PostgreSQL 迁移，启动时执行一次。它们不写订阅行、线索行或请教行。

- `subscription_rules`：增加 `subscriptions.rules`（JSONB 数组，默认 `[]`）和 `subscriptions.config_epoch`（bigint，默认 0）；给 `subscription_runs` 增加 `config`、`config_epoch` 和 `match_timeouts`（整数，默认 0）；放宽 `subscriptions_render_check`，使 `render` 接受 `lines_v1` 和 `lines_v2`。
- `subscription_lookback`：增加 `subscriptions.window`（`cursor` 或 `lookback`，默认 `cursor`）和 `subscriptions.delivery_policy`（`per_run` 或 `daily`，默认 `per_run`）；给 `subscription_runs` 增加 `window_mode`（默认 `cursor`）和 `daily_date`；创建 `subscription_daily_claims`（`schedule_id`、`local_date`）。
- `run_tree`：给 `llm_records` 增加 `parent_record_id` 和 `run_kind`，约束为 `NOT VALID`。不改写旧行；没有 `run_kind` 时仍按 agent id 读取。schema 事务提交之后，在线标记 `run_tree_online` 校验 `llm_records_run_kind_check` 和 `llm_records_parent_record_id_fkey`，并用并发方式建立 `idx_llm_records_parent`。
- `step_difficulty`：给 `task_steps` 增加 `difficulty`（`routine`、`hard` 或 `critical`），约束为 `NOT VALID`。在线标记 `step_difficulty_online` 校验 `task_steps_difficulty_check`。现在还没有代码写这一列。
- `agent_spawns`：创建 `agent_spawns` 和 `advisor_advice` 及其索引和约束。表保持为空。
- `advisor_roles`：放宽 `agent_setting_layers_role_check`，使它也接受 `advisor` 和 `advice_check`。不改写已保存的层。
- `message_leads`：给 `source_chats` 增加 `extraction`（默认 `included`）和 `extraction_excluded_at`；放宽 `subscriptions.output_kind`，使它也接受 `leads` 和 `intents`（写入 API 仍只接受 `push`）；`subscription_runs.outcome` 增加 `extracted`，并增加 `extract_counts`；创建 `message_leads`、`message_lead_sources`、`message_lead_people`、`intent_types`、`intent_type_versions`（三个内置类型的第 1 版：`dev_task`、`bug_triage`、`alert_triage`）、`intent_type_projects`、`message_chat_projects`、`intent_alert_senders`、`intents`、`intent_sources` 和 `intent_posts`。删掉一条来源消息，会删掉由它生成的线索和意图。
- `intent_merges`：把级联删除的 `intents.merged_into` 外键换成 `NO ACTION`，并增加 `AFTER DELETE` 触发器 `A_intents_detach_merged`。删掉一条意图时，合并进它的意图回到 `pending`。一条意图自己的来源消息被删时，它仍会被删掉。

在线步骤（`run_tree_online`、`step_difficulty_online`）在 schema 事务提交之后获取一把全库的会话咨询锁。等待的一方不持有事务。五秒之后本次启动继续，未完成的步骤留给持锁的一方或下一次启动。调用方已经在事务里时也会推迟。建到一半的无效索引会先删掉再重建。（[#1453](https://github.com/foolzzz/looper/pull/1453)）

启动时若还没有，会插入模型 `claude-fable-5-2`、`claude-haiku-5-5`，以及内置 Profile `claude-code/fable-5-2`（effort 为 `high`）和 `claude-code/haiku-5-5`。同名的已有 Profile 保持原样。

下一次会改 schema 的启动仍会先做经过校验的备份。这份转储现在保留 `source_events` 的表结构，不保留它的行。

### 行为变化与入口

**订阅规则，创建并确认之前关闭（[#1446](https://github.com/foolzzz/looper/pull/1446)）**

- **不带规则创建订阅，就没有这项行为。**`rules` 默认为 `[]`。没有规则时仍用订阅自己的筛选，`lines_v1` 的读法与以前逐字相同。没有规则、只读 `group` 和 `topic` 的订阅逐字节不变，`config_version` 也不变。已有的 agent 和命令定时任务、提示词、工具列表和 Manager 的命令都不变。
- 最多 20 条规则。任一规则选中即保留，第一条选中的规则为它命名。一条规则有 `name`、`label`、`chat_kinds`、`include_chats`、`exclude_chats`、`sender_kinds`、`exclude_self`、`mentions_me`（`any`、`only` 或 `exclude`）、`text_match`、`never_quiet` 和 `areas`。`lines_v2` 写成 `[time] 【label·area】《chat》 sender: text`。
- `output_header` 可以含 `{count}` 和 `{count:RULE NAME}`。只有 `rules` 非空时才填上。没有规则时它们保持原文。
- `text_match` 是操作员提供的数据，最长 500 字符，保存时按 Python 自己的语法树检查。重复的内容里再含重复或分支则拒绝，包括写成 `{,n}` 或放在详细模式标志下。最多 2 个可能跑很久的重复（无上界，或上界超过 10），任意重复最多 8 个，分支最多 8 个。它只看一条消息的前 1,000 个字符，在单独的进程里跑，5 秒后杀掉，并且发生在这次触发的事务里。超过时限则本窗口没有任何模式选中消息，运行记下 `match_timeouts`。
- **`never_quiet`：**processor 说了静默词，但窗口里有这类消息时，由代码写出这些消息的列表（每个标签最多 30 条、每条 200 字，同样去掉 @），并像 processor 的输出一样推送。
- **私密内容。**能选中私聊、未知类型的会话、`mentions_me: only` 或 `never_quiet` 的订阅，只能推到操作员自己的私聊：来源所绑定用户的飞书私聊。群、同事的私聊、Telegram，以及没有绑定用户的来源，在创建、改变读取或目标的更新、确认，以及每一条消息发送前都会拒绝。停用和改名仍然可以。只有在它确实私密时，这一点才进入 `config_version`。没有规则但 `chat_kinds` 含 `p2p` 或 `unknown` 的订阅算私密。只读群和话题的不算。
- 一次运行用它开始时的配置选择（`subscription_runs.config`），并钉住 `config_epoch`。读取配置、规则、目标、时间规则、时区、通知、是否启用、Profile 选择和每一次确认都会让这个计数前进，因此改了再改回去也会停掉推送。就地修改 processor 的 Agent Profile 不会增加 `config_epoch`；每次发送前比对的 `config_version`，以及和这次运行实际启动的 Profile 的比对，覆盖这种修改。
- 规则经 API 设置。仪表盘只显示有规则。创建订阅时可以补上 `chat_kinds` 和 `sender_kinds`；更新时加上规则不会补这些字段。

**回看窗口和按日占位，选定之前关闭（[#1447](https://github.com/foolzzz/looper/pull/1447)）**

- **已有订阅保持 `window: cursor` 和 `delivery_policy: per_run`。**它们的输入、顺序、标题、游标和确认版本都不变。新模式必须显式设置。创建之后，目标确认之前不推送。
- `lookback` 忽略游标。它选取发送时间在触发时刻减去 `max_age_minutes` 到触发时刻之间、且已提交的事件，保留最新的 `max_events` 条，再按从旧到新渲染。它从不初始化或推进游标。游标重置会被拒绝。空窗口、静默、失败和重启恢复都不动游标。创建时必须给时间范围。切回 `cursor` 时从该来源的当前末尾开始。
- `output_header` 里的 `{date}` 是计划触发的本地日期，`YYYY-MM-DD`，用该定时任务的时区。手动运行用请求时间。跨过午夜的补跑保留最近一次错过的触发的日期。有没有规则都可以用 `{date}`。计数字段仍要 `rules` 非空。
- `delivery_policy: daily` 在 processor 启动前、在这次触发的事务里，于 `subscription_daily_claims` 占用 `(schedule_id, local_date)`。手动、排队和补跑也会占用。已占用的日期会挡住这一天以及任何更早的本地日期，时区往回拨也一样。占用的日期存在 `subscription_runs.daily_date`，运行结束时不按当前时区重算。
- 静默、只留在仪表盘，以及任一已发送或 `uncertain` 的消息，都保留占用。失败的运行，或被打断的运行，在什么都没发出去、也没有 `uncertain` 时，在结束它的同一事务里释放这一天，因此同一个本地日可以再试。重复的一次是 `skipped_gate`。它不清失败连续计数，也不更新 `last_ok_at`。真正的空窗口是健康的跳过，不占用。
- 改窗口或投递策略会清掉确认，运行未结束时拒绝修改。两者都在 `config_version` 里。仪表盘表单不变；这些字段经 API 设置。Lark 和 Telegram 仍走原来的机器人投递。

**消息备份（[#1454](https://github.com/foolzzz/looper/pull/1454)）**

- **凡是用 `pg_dump` 做的 schema 变更转储，现在都不含 `source_events` 的行。**表结构保留。`event_sources`、`source_chats`、`source_threads`、`source_people` 和 `source_runs` 保留行。已投递的订阅输出也保留。Looper 给自己的 `pg_dump`，以及程序是 `pg_dump` 的 `backup.command`（含经 `docker exec` 运行的），加上 `--exclude-table-data=source_events`。程序不是 `pg_dump` 的命令保持原样，必须自己排除这些数据。启动日志会写明转储保留表结构、不含行。恢复这份转储后有会话、没有消息正文。
- **每日副本默认关闭。**`[backup] messages = "daily"` 时，在运行根目录的 `backups/` 里写 `looper-<database>-<UTC stamp>.messages.dump`，含表结构和行，每天至多一次，保留最新的 7 份。文件名以 `.messages.dump` 结尾，因此轮转它不会删掉 schema 变更转储，反过来也不会。省略 `messages` 或设为 `"off"`，服务既不写也不删。失败的一次要到一天之后，或到下一次启动时最新的一份已经超过一天，才会再试。停止服务会停掉这次 `pg_dump`。把消息备份恢复到已经有该来源会话的数据库里。两台服务可以各写一份；它们之间没有锁。

**在线 schema 步骤（[#1453](https://github.com/foolzzz/looper/pull/1453)）**

两个进程一起启动时，校验 `NOT VALID` 约束和并发建索引以前会死锁。这些步骤现在获取一把会话咨询锁，与 schema 事务的锁分开。等待的一方不持有事务。五秒之后本次启动继续，未完成的步骤留给持锁的一方或下一次启动。启动时已经在事务里也会推迟。提示词、工具和默认值都不变。

**Advisor 第一期的地基，尚未使用（[#1436](https://github.com/foolzzz/looper/pull/1436)、[#1438](https://github.com/foolzzz/looper/pull/1438)）**

- **没有任务能发起请教。**项目开关 `advisor` 和规划者一侧不在本版本，对应的拉取请求仍开着。规划者提示词、Worker 提示词和命令行都不提 advisor。
- **已经有的。**`Launch.access` 为 `full`、`read_only`、`consult` 或 `advisor`。不填时仍是角色自己的级别：规划者是 `read_only`，其他角色是 `full`。`spawn` 可以跑一个不带工具的子运行并记到 `agent_spawns`。请教包和回答会经过解析和检查（格式、代码检查，然后 `advice_check` 判别），也可以跑一轮 advisor。任务路径上还没有调用。
- **设置。**Settings → Agent Profiles 多两个内置 Profile：`advisor` 用 `claude-code/fable-5-2`（`claude-fable-5-2`，effort 为 `high`），`advice_check` 用 `claude-code/haiku-5-5`。agent-settings API 会列出这两个角色。Settings → Roles 页面还不会列出它们。若已有同名 Profile，种子会跳过，该角色在设置里选定之前不会运行。Claude 登录的模型目录增加这两个完整 id。
- **价格。**`claude-fable-5-2` 为每百万 token 输入 8、输出 40、缓存读 0.20、五分钟缓存写 10 美元，一小时缓存写 16 美元。别名 `fable` 解析到它。内置价格表里的 Anthropic 模型，一小时缓存写入按输入价格的两倍计。说不清时长的写入也按这个价格计，因此不会低于实际花费。花费来自运行时自己报告的运行不变。按服务商价格计费的子运行，如果写入时长说不清，则不给出输出。
- 新的运行记录会存 `run_kind`。旧行不改写。

**Manager 收尾回合，默认关闭（[#1455](https://github.com/foolzzz/looper/pull/1455)）**

- **`manager.completion_turns` 默认为 `off`。**任务结束仍是代码通知。用户回合的命令、工具列表、回合正文和系统提示词都不变。`chat_settings.get` 和 `chat_settings.update` 多这个字段。更新可以只带一个字段。存下来的值缺失或非法时是 `off`。
- **`dm_only`** 用 `chat_settings.update` 设置，对下一次任务结束生效。在仪表盘会话或 Telegram、Lark 私聊里提出的任务结束时，由 Manager 用一个只读的 `[COMPLETION]` 回合告诉该聊天，而不再发代码通知。群仍是通知（`skipped`，`group_chat`）。定时任务的运行消息仍是通知（`skipped`，`off`）。报告没有到达任务自己的 Manager 时为 `skipped`、原因 `manager_off`。
- 这一回合认领该聊天最多 10 条待处理事件，不流式输出，并且是该聊天当前的回合，因此在那里发 `/stop` 会停掉它。写入会得到 `needs_user_turn`，不会消耗聊天里正在等的确认。回复发到原来通知要去的地方，代码再附上每个任务的链接行。回合失败、超时（120 秒）、被停止、回复为空或发不出去时，改为发送记录里的那条通知。重启会补发还没发出去的通知，并唤醒仍有待处理事件的聊天。

**消息线索和意图，默认关闭（[#1450](https://github.com/foolzzz/looper/pull/1450)、[#1452](https://github.com/foolzzz/looper/pull/1452)、[#1459](https://github.com/foolzzz/looper/pull/1459)）**

- **默认关闭。**这些表里没有抽取出来的行。不会创建订阅。写入 API 仍只接受 `output_kind` 为 `push`。提示词、工具和命令行都不提线索。还没有抽取运行、没有 `looper leads` 命令、没有 Manager 工具、也没有页面。查询函数和操作者判断留给后面的切片，本版本没有调用方。
- 删掉一条意图，不会删掉合并进它的意图。那些回到 `pending`（`intent_merges`）。一条意图自己的来源消息被删时，它仍会被删掉。现在还没有代码写意图，所以今天没有已存的行会变。
- [#1450](https://github.com/foolzzz/looper/pull/1450) 只是 RFC。

### 可选能力启用与使用

#### Digest and daily subscriptions

**启用：**操作员创建 `kind` 为 `subscription` 的定时任务，并设置 `rules`、`window: lookback` 或 `delivery_policy: daily`，然后确认推送目标之前，这项能力是关的。没有单独的开关。没有规则、`window` 为 `cursor`、`delivery_policy` 为 `per_run` 的订阅与 v2.15.20 相同。新建的订阅是停用的；游标模式下，游标从来源已提交的序号起。`target_confirmed_at` 为空，因此输出留在仪表盘。确认方式与 v2.15.20 相同：仪表盘的「Confirm push target…」显示目标，并带上刚显示的 `config_version` 调用 `schedule_admin.confirm_target`。私密订阅（私聊、未知类型的会话、`mentions_me: only` 或 `never_quiet`）只能确认为操作员自己的飞书私聊。日报字段经 `schedule_admin.create` 或 `schedule_admin.update` 设置：`window` 为 `lookback`，`max_age_minutes` 为 1440，`delivery_policy` 为 `daily`，`render` 为 `lines_v2`，`output_header` 含 `{date}`，规则非空时再加 `{count}`。

**验证：**确认之前，有输出的运行以 `dashboard_only` 结束，不会去问渠道。`confirm_target` 接受定时任务当前的版本之后，选中了事件的一次触发会运行 processor，并推送到已确认的私聊或已绑定的群。带嵌套重复的 `text_match` 会被拒绝。同一个本地日上，已经占用过的第二次日报触发不会启动 processor。什么都没发出去的失败日报会释放这一天，同一本地日稍后的触发可以再跑。没有规则、只读群和话题的订阅仍渲染 `lines_v1`。

**停用 / 回退：**停用该定时任务，或删除它。把 `rules` 设回 `[]`，`window` 设回 `cursor`，`delivery_policy` 设回 `per_run`；改窗口或投递策略会清掉确认。新列和 `subscription_daily_claims` 是可加的。没有这种订阅时不被使用。关掉这些模式不会删表。

**权限边界：**操作员或 API 客户端经 `schedule_admin` 管理订阅，高风险写入要等确认。推送以机器人身份发出，只发到已允许的私聊或已绑定的群，并且只在已确认的 `config_version` 和钉住的 `config_epoch` 仍是该定时任务的当前值时发出。私密内容只能发到操作员自己的私聊。Manager 不能创建或修改订阅，只看到状态和计数。processor 运行时不带工具。推送的日志只有错误类型和 id，没有消息正文。

#### Message backups

**启用：**`source_events` 的每日备份在运维文件把 `[backup] messages` 设为 `"daily"` 之前是关的。没有环境变量，也没有仪表盘开关。省略该键或设为 `"off"`，服务既不写也不删消息备份。schema 变更时排除行不是可选项：下一次会改 schema 的启动，若用内置 `pg_dump` 或程序为 `pg_dump` 的 `backup.command`，会保留 `source_events` 的表结构、不保留行。改完运维文件后重启服务。

**验证：**未设置 `messages` 时，`backups/` 里不会多出以 `.messages.dump` 结尾的文件。设为 `messages = "daily"` 后会出现一份，每天至多一次；写到第七份新的时会删掉更旧的、超出 7 份的那一份。用 `pg_dump` 做的 schema 变更转储会列出 `source_events` 这张表，但没有它的行。`looper doctor` 仍会报告 schema 变更转储用的校验程序。

**停用 / 回退：**把 `[backup] messages` 设为 `"off"`，或删掉该键，然后重启。服务此后既不写也不删消息备份。已经写下的副本留着，直到操作员自己删。schema 变更时排除行仍然保留：本版本的转储不含消息行。要回退服务，先停掉它，升级后的库保持不动，把经过校验的备份恢复到另一个数据库。`.messages.dump` 只恢复到已经有该来源会话的数据库。

**权限边界：**只有操作员的运维文件能打开每日备份。文件在运行根目录的 `backups/` 里，权限为 0600，里面是消息正文。没有 agent、提示词或工具会读写它们。schema 变更转储不再含这段正文。两台服务共用一个数据库时可以各写一份每日副本；它们之间没有锁。

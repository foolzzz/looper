# Looper v2.14.180

This is the patch release v2.14.180, a hotfix line in which each merged change ships at once. It documents one change: [#1332](https://github.com/foolzzz/looper/pull/1332) (API latency observability: loop-lag stacks, slow-call warnings, periodic per-operation summaries).

## Release Decision

**Who should upgrade:** Operators who run `looper serve` and want to find out why an API call is slow, and anyone who reads the server log for API timing.

**What this release solves:** [#1332](https://github.com/foolzzz/looper/pull/1332) adds diagnostics to the existing server log so a slow API operation or a blocked event loop leaves evidence: a warning with the time split, the stacks of a blocked loop, and a periodic latency summary per operation. It does not change how any operation behaves.

**Breaking changes:** No. API responses, the Telegram and Lark channel protocols, the dashboard and the CLI are unchanged, and there is no database change. Log consumers see new lines (`api slow`, `api summary`, `loop summary`, watchdog warnings) and a changed `api client=...` line (see Behavior changes). The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.14.180
```

**Contributors:** Maintainer @foolzzz authored [#1332](https://github.com/foolzzz/looper/pull/1332); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.179 upgrades directly. There is no database change.

## Behavior changes

Read in the diff of [#1332](https://github.com/foolzzz/looper/pull/1332) (the PR description itself only says "behavior changes as described in the card"):

- **Slow-call warning** (`looper/agents/http_server.py`, `looper/db/timing.py`, `looper/db/connection.py`). Each `/api/v1/` operation runs with a request-local timing record. The pool now registers an asyncpg query logger on every new connection that adds each query's elapsed time and count to the request's record. A non-stream operation that takes more than 2 s logs a WARNING `api slow` with `ms`, `db_ms`, `db_queries`, `other_ms` (total minus accumulated DB time, which can be negative when queries ran concurrently) and `awaiting`, the chain of up to six looper frames the request was suspended in, captured at the 2 s mark.
- **Per-operation summary** (`looper/agents/http_server.py`). Every 600 s the server logs, for each operation seen in the window, `api summary` with count, nearest-rank p50, p95, p99, maximum and the number above 2 s, then a `loop summary` line (stalls, maximum stall, process stalls). Percentiles use at most the first 20,000 samples per operation, counts and maxima cover all requests, and an `api summary samples` line reports dropped samples. A window with no requests and no stalls logs nothing. Streams are excluded from summaries and slow warnings.
- **Changed completion line.** The INFO line `api client=... op=... status=... ms=...` is now written for every dispatched operation, including a request that raised or was cancelled (`status=error:internal` or `cancelled`), where before it was written only after an answer was built. A stream's line also carries `first_byte_ms` (the first response write, `None` if nothing was written). `openapi` still logs no line.
- **Event-loop watchdog** (`looper/agents/loop_watch.py`, `looper/agents/serve.py`). `looper serve` starts a watchdog before any startup work. A heartbeat task and a daemon thread detect a blocked loop: a WARNING with the loop thread's stack after 1 s, again at 5 s and 15 s when the innermost frame changed, and a line when the loop recovers. The thread also reports gaps in process scheduling over 1 s separately (machine overload, not a loop block); system sleep remains the suspend detector's job. The watchdog is stopped when the server exits.
- **Shutdown.** The HTTP server's `stop()` is now idempotent and also cancels the summary task. `serve.py` additionally stops the server in its outermost cleanup, before closing the pool, so a startup that fails after the server was created still closes it.
- **Tests and docs.** New `tests/test_loop_watch.py`, `tests/test_api_latency.py`, `tests/test_api_db_timing.py`, `tests/test_api_latency_serve_db.py` and `tests/test_api_latency_startup_db.py`; `tests/test_room_consult.py` follows the renamed startup function; `tests/test_proc_tree.py` pins the process group in the refresh-cancel test so small fake pids cannot match the runner's own; the HTTP API section of `docs/architecture/agent-system.md` describes the diagnostics.
- **Model-visible changes:** No. No prompt, tool description or tool schema changed, and no HTTP API result changed; the new output is server log lines only.

**谁需要升级：**运行 `looper serve` 并想查明 API 调用为何变慢的运维人员，以及读取服务日志中 API 耗时的用户。

**解决了什么：**[#1332](https://github.com/foolzzz/looper/pull/1332) 在现有服务日志中加入诊断，使慢 API 操作或被阻塞的事件循环留下证据：带耗时拆分的警告、循环被阻塞时的堆栈，以及按操作的周期延迟汇总。它不改变任何操作的行为。

**是否有破坏性变更：**无。API 响应、Telegram 与 Lark 渠道协议、仪表盘和 CLI 均不变，没有数据库变更。日志使用方会看到新的行（`api slow`、`api summary`、`loop summary`、看门狗警告）以及变化的 `api client=...` 行（见行为变化）。桥接边界不变：早于 v2.13.165 的安装须先升级到 v2.13.165。

**如何验证：**核对版本为 2.14.180。

### 升级

### 行为变化与入口

以下在 [#1332](https://github.com/foolzzz/looper/pull/1332) 的差异中可见（PR 描述本身只说“行为变化见卡片”）：

- **慢调用警告**（`looper/agents/http_server.py`、`looper/db/timing.py`、`looper/db/connection.py`）。每个 `/api/v1/` 操作带一份请求级计时记录运行。连接池现在为每个新连接注册 asyncpg 查询日志器，把每次查询的耗时和次数累加到请求的记录中。耗时超过 2 秒的非流式操作会记录 WARNING `api slow`，含 `ms`、`db_ms`、`db_queries`、`other_ms`（总耗时减去累计数据库耗时，并发查询时可能为负）和 `awaiting`（请求在 2 秒时挂起所处的至多六层 looper 栈帧链）。
- **按操作汇总**（`looper/agents/http_server.py`）。服务每 600 秒为窗口内出现的每个操作记录 `api summary`：次数、最近秩 p50、p95、p99、最大值和超过 2 秒的次数，随后是 `loop summary` 行（卡顿次数、最大卡顿、进程卡顿）。百分位每个操作最多用前 20,000 个样本，次数和最大值覆盖全部请求，被丢弃的样本由 `api summary samples` 行报告。窗口内无请求且无卡顿则不输出。流式操作不进入汇总和慢警告。
- **完成行变化。**INFO 行 `api client=... op=... status=... ms=...` 现在对每个已分派的操作都会写出，包括抛出异常或被取消的请求（`status=error:internal` 或 `cancelled`），此前只在构造出应答后才写。流式操作的行还带 `first_byte_ms`（首次响应写入的时间，未写入则为 `None`）。`openapi` 仍不记录。
- **事件循环看门狗**（`looper/agents/loop_watch.py`、`looper/agents/serve.py`）。`looper serve` 在任何启动工作之前启动看门狗。心跳任务加守护线程检测循环阻塞：阻塞 1 秒后记录带循环线程堆栈的 WARNING，在 5 秒和 15 秒且最内层栈帧改变时再记录，并在恢复时记录一行。该线程还单独报告超过 1 秒的进程调度间隙（机器过载，不是循环阻塞）；系统休眠仍由挂起检测器负责。服务退出时看门狗停止。
- **关闭。**HTTP 服务的 `stop()` 现在幂等，并会取消汇总任务。`serve.py` 还在最外层清理中、关闭连接池之前停止该服务，因此服务创建之后启动失败也会关闭它。
- **测试与文档。**新增 `tests/test_loop_watch.py`、`tests/test_api_latency.py`、`tests/test_api_db_timing.py`、`tests/test_api_latency_serve_db.py` 和 `tests/test_api_latency_startup_db.py`；`tests/test_room_consult.py` 跟随改名后的启动函数；`tests/test_proc_tree.py` 在刷新取消测试中固定进程组，避免小的假 pid 与运行器自身的进程组相同；`docs/architecture/agent-system.md` 的 HTTP API 一节描述了这些诊断。
- **面向模型的变化：**无。提示词、工具描述和工具 schema 均未改变，也没有 HTTP API 结果改变；新增输出只是服务日志行。

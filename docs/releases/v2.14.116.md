# Looper v2.14.116

This is the patch release v2.14.116, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.115: workflow rules for verification, a verification round cap and escalation to the operator when attempts are exhausted ([#1182](https://github.com/foolzzz/looper/pull/1182)).

## Release Decision

**Who should upgrade:** Operators who use workflow presets with a verification role or with `escalate_on_exhaustion`. Installations and tasks without a workflow see no change in behavior.

**What this release solves:** [#1182](https://github.com/foolzzz/looper/pull/1182). A workflow's verification role was stored but not enforced. Now a verification step must not change code, failed verifications are counted against a round cap, and a task whose review or verification attempts are exhausted stops at a gate the operator must decide instead of continuing on its own.

**Breaking changes:** No. The database gains an additive column and two journal kinds, applied on first start; tasks and plans without a workflow behave as before.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.14.116
```

**Contributors:** Maintainer @foolzzz authored [#1182](https://github.com/foolzzz/looper/pull/1182); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.115 upgrades directly. This release has a small database change, applied automatically on the first start: `task_user_gates` gains a `purpose` column (default `discussion`) and the `task_journal` kind check accepts `verification_round` and `escalation`. Because the schema changed, take the usual database backup before upgrading; an older binary should not be started on the upgraded database without restoring it.

## Behavior changes

- **Verification must not change code.** For a step in the workflow's verification role, the Worker snapshots the repository before and after the run (HEAD, git status, file contents and index). Reported file changes, a moved HEAD, a changed status or changed contents fail the step with `verification_changed_code`, and the baseline is restored (the developer's uncommitted files and staging are kept). In a git repository the verification runs in a private checkout with no remote back to the source; outside git only the Worker's report is checked. If a snapshot cannot be taken the agent is not started (`verification_unavailable`).
- **Repair after a violation.** After `verification_changed_code` the Planner may only replan or fail; the replan must contain a reviewed (`review: true`) non-verification repair step, and every new verification step must depend on it. The requirement survives retries and restarts until a repair passes review; if a decision is reached without one, the plan fails.
- **Verification structure.** A verification step must depend on at least one work step. Verification steps need no review unless `review: true` is requested, and the project's review-all setting no longer applies to them.
- **Round cap.** Each completed verification attempt is journaled (`verification_round`: role, attempt, tested HEAD, status). After the workflow's `max_rounds` failed attempts across the task, retry is disabled for failed verification, and any new verification step must depend on a new gate added in the same reply (purpose `verification_exhaustion`).
- **Escalation.** With `escalate_on_exhaustion`, when retries are used up and a result cannot be accepted, only replan or fail is allowed. A replan must add a new user gate in the same reply and every other new step must depend on it and require it to pass. The gate is recorded as an `escalation` journal entry, cannot be cancelled by the Planner, and a later replan cannot drop it until the operator decides. Steps that must be reviewed under this setting still go to a Reviewer if the decision turn fails.
- **Gates.** Gates carry a `purpose` (`discussion`, `exhaustion`, `verification_exhaustion`), stored in the database; the Planner never supplies it.
- **Tests and evals.** The prompt-regression set gains `workflow_verify_loop` (a failed read-only verification is answered by a reviewed repair and a separate dependent verification), and its fake Claude can replan on request.
- **Model-visible changes:** Yes. For tasks with a workflow, the Planner's system prompt replaces "User gates are enabled." with the exhaustion rule when `escalate_on_exhaustion` is set, and adds the verification role, no-code-change, dependency and round-cap rules when a verification rule exists. Decision prompts add an "Escalation required" note, a "verification failure limit is exhausted" note, and the restricted decision list (replan or fail). Review prompts say "This step requires review" instead of "This project reviews every step". Tasks without a workflow keep their prior prompt.
- **Unchanged:** tasks and plans without a workflow or conditions, workflow definition and storage, and the Planner's downgrade of blocking findings where the workflow allows it.

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.115 上的安装可直接升级。本版本有小幅数据库变更，首次启动时自动应用：`task_user_gates` 新增 `purpose` 列（默认 `discussion`），`task_journal` 的类型检查接受 `verification_round` 和 `escalation`。由于结构有变，升级前请照常备份数据库；未恢复备份时不要在已升级的数据库上启动旧版本。

### 行为变化与入口

- **验证不得修改代码。**对工作流验证角色的步骤，Worker 在运行前后对仓库做快照（HEAD、git status、文件内容和暂存区）。上报的文件改动、HEAD 移动、状态或内容变化都会使步骤以 `verification_changed_code` 失败，并恢复基线（保留开发者未提交的文件和暂存）。在 git 仓库中验证运行于没有回指源仓库远端的私有检出；非 git 目录只检查 Worker 的报告。无法取得快照时不会启动 agent（`verification_unavailable`）。
- **违规后的修复。**出现 `verification_changed_code` 后 Planner 只能 replan 或 fail；replan 必须包含一个带评审（`review: true`）的非验证修复步骤，且每个新的验证步骤都必须依赖它。该要求在重试和重启后仍然有效，直到有修复通过评审；若没有修复就做出决定，计划失败。
- **验证结构。**验证步骤必须依赖至少一个工作步骤。验证步骤默认无需评审，除非显式要求 `review: true`，项目的全部评审设置也不再作用于它们。
- **轮次上限。**每次完成的验证尝试都记入日志（`verification_round`：角色、次数、被测 HEAD、状态）。整个任务内失败达到工作流的 `max_rounds` 次后，失败的验证不再重试，任何新的验证步骤都必须依赖同一回复中新增的 gate（purpose 为 `verification_exhaustion`）。
- **升级给运维者。**启用 `escalate_on_exhaustion` 时，重试用尽且结果无法接受后只允许 replan 或 fail。replan 必须在同一回复中新增用户 gate，其他新步骤必须依赖它并要求它通过。该 gate 记为 `escalation` 日志，Planner 不能取消，运维者决定前后续 replan 也不能删除它。需评审的步骤在决策轮失败时仍会交给 Reviewer。
- **Gate。**Gate 带有 `purpose`（`discussion`、`exhaustion`、`verification_exhaustion`），存入数据库；Planner 不能指定。
- **测试与评测。**提示词回归集新增 `workflow_verify_loop`（只读验证失败后，用带评审的修复和单独的依赖验证来应对），其 fake Claude 可按请求 replan。
- **面向模型的变化：**有。对有工作流的任务，Planner 系统提示词在设置 `escalate_on_exhaustion` 时用耗尽规则替换“User gates are enabled.”，存在验证规则时增加验证角色、不得改代码、依赖和轮次上限的规则。决策提示词增加“Escalation required”说明、“验证失败上限已耗尽”说明和受限的决策列表（replan 或 fail）。评审提示词由“This project reviews every step”改为“This step requires review”。没有工作流的任务提示词不变。
- **不变：**没有工作流或条件的任务和计划、工作流的定义与存储、工作流允许时 Planner 对阻塞性发现的降级。

# Looper v2.14.95

This is the patch release v2.14.95, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.94: follow-ups of the projects task scope, so a project-scoped Manager sees no out-of-scope task names, an emptied scope survives export and import, and deleting a project shows which Managers it affects ([#1131](https://github.com/foolzzz/looper/pull/1131)).

## Release Decision

**Who should upgrade:** Operators who run Managers whose task scope is "projects": scoped Managers that create tasks in shared repositories, that are exported and imported, or whose projects are deleted. Everyone else can stay.

**What this release solves:** The workspace check of a new task named other Managers' tasks only by owner, so a project-scoped Manager could read the names of tasks outside its projects; an exported Manager whose projects were all deleted (`scope_projects: []`) could not be imported; the project-delete confirmation did not name the affected Managers; and the overview attributed running steps to the project at dispatch. [#1131](https://github.com/foolzzz/looper/pull/1131) fixes all four. No change for the all and own scopes.

**Breaking changes:** No. No schema change and no API change.

**How to verify:** Check the installed version. In the dashboard, open a project that a scoped Manager works in and choose Delete: the confirmation names that Manager.

```bash
looper --version   # looper 2.14.95
```

**Contributors:** Maintainer @foolzzz authored [#1131](https://github.com/foolzzz/looper/pull/1131); no community contribution was included in this release.

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.94 upgrades directly. There is no database change.

## Behavior changes

- **Workspace check names only in-scope tasks** (`looper/agents/task_workspaces.py`, `looper/agents/projects.py`, `looper/agents/ops/tasks.py`, `looper/db/tasks.py`). Creating a task passes the Manager's task filter (owner and projects) to the check. A task in the same repository that is outside the filter, or owned by another Manager, is anonymous: no id, name or status. `active_workspaces` now also returns each task's project. The anonymous task is counted as "N other task(s) running in this directory" (was "N task(s) of another Manager"); the Chinese task-start note says "另有 N 个范围外任务正在此目录运行".
- **An emptied scope survives export and import** (`looper/agents/config_transfer.py`, `looper/agents/managers_api.py`). A Manager exported with `scope_projects: []` (all its projects deleted) imports as a closed, empty scope. Only the importer passes `allow_empty_scope`; the API and the Manager tools still require 1 to 20 project ids.
- **Honest project-delete impact** (`looper/agents/ops/config.py`, `web/src/components/project-settings.tsx`, `web/src/lib/api.ts`). The delete confirmation names the Managers scoped to the project, also for a scoped caller (was "other Managers"). The dashboard shows the server's impact text and confirms in the server's session (`confirmV1`) instead of its fixed "Delete X and its N tasks?" line; a failed delete closes the confirmation and shows the error.
- **Overview by current project** (`looper/agents/overview.py`, `looper/db/tasks.py`). For a project-scoped view, running steps are attributed by the task's current project (new `project_of`), not the project at dispatch.
- **Manager message context** (`looper/agents/tiers/manager.py`). The projects, templates, ready-tasks and open-gates sections each read the scope themselves; when the scope cannot be read, only the affected sections show "(could not be read)" (was: all of them, plus a warning for the whole).
- **Unchanged:** the all and own scopes, the API shape, the CLI, channels, the schema.
- **Documentation and tests.** Updated `tests/test_scenario_manager_tools_db.py`, `tests/test_manager_config_transfer_db.py`, `tests/test_manager_config_tools_db.py`, `tests/test_overview_db.py`, `tests/test_manager_reply.py`, `web/src/components/project-settings.test.tsx` and `web/src/lib/api-projects.test.ts`.
- **Model-visible changes:** Yes, small. The anonymous-task text in the workspace warning that a Manager's task-create tool returns, and in the task-start note, changes as above, and a scoped Manager no longer receives names of out-of-scope tasks there. The delete-confirmation text a scoped Manager is shown now names the affected Managers. The per-message context is the same text except for the failure case above. No tool description or prompt text changes.

## 中文摘要

本版本是 patch release v2.14.95（热修线，每个合并的改动立即发布）。自 v2.14.94 以来只合并了一项改动：项目任务范围的后续修复——限定项目的管家看不到范围外的任务名，清空的范围可导出再导入，删除项目时会显示受影响的管家（[#1131](https://github.com/foolzzz/looper/pull/1131)）。

### 升级决策

**谁需要升级：**使用任务范围为“projects”的管家的运维人员：在共享仓库里建任务、导出导入管家、或删除其项目的场景。其他人可不升级。

**解决了什么：**新任务的工作区检查只按所有者匿名其他管家的任务，限定项目的管家可读到项目外任务的名称；项目全被删除后导出的管家（`scope_projects: []`）无法导入；删除项目的确认没有列出受影响的管家；概览按派发时的项目归属运行中的步骤。[#1131](https://github.com/foolzzz/looper/pull/1131) 修复这四点。all 和 own 范围不变。

**是否有破坏性变更：**否。无结构变更，无 API 变更。

**如何验证：**核对版本为 2.14.95。在仪表盘打开某个限定管家工作的项目并选择删除：确认中会列出该管家。

**贡献者：**维护者 @foolzzz 提交 [#1131](https://github.com/foolzzz/looper/pull/1131)；本版本无社区贡献。

```bash
looper --version   # looper 2.14.95
```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.94 上的安装可直接升级。无数据库变更。

### 行为变化与入口

- **工作区检查只列范围内的任务**（`looper/agents/task_workspaces.py`、`looper/agents/projects.py`、`looper/agents/ops/tasks.py`、`looper/db/tasks.py`）。创建任务时把管家的任务过滤器（所有者和项目）传给检查。同一仓库中不在过滤器内、或属于其他管家的任务会匿名：无 id、名称、状态。`active_workspaces` 现在也返回任务的项目。匿名任务计为 “N other task(s) running in this directory”（原为 “N task(s) of another Manager”）；中文任务启动提示为“另有 N 个范围外任务正在此目录运行”。
- **清空的范围可导出再导入**（`looper/agents/config_transfer.py`、`looper/agents/managers_api.py`）。导出时 `scope_projects: []`（其项目全被删除）的管家，导入后为封闭的空范围。只有导入器传 `allow_empty_scope`；API 和管家工具仍要求 1 到 20 个项目 id。
- **诚实的删除项目影响**（`looper/agents/ops/config.py`、`web/src/components/project-settings.tsx`、`web/src/lib/api.ts`）。删除确认会列出范围含该项目的管家，限定范围的调用者也一样（原为“其他管家”）。仪表盘显示服务器给出的影响文本，并在服务器的会话里确认（`confirmV1`），不再用固定的 “Delete X and its N tasks?”；删除失败时关闭确认并显示错误。
- **概览按当前项目**（`looper/agents/overview.py`、`looper/db/tasks.py`）。限定项目的视图中，运行中的步骤按任务当前所在项目（新增 `project_of`）归属，而非派发时的项目。
- **管家消息上下文**（`looper/agents/tiers/manager.py`）。项目、模板、就绪任务、待回复 gate 各段自行读取范围；范围读取失败时只有受影响的段显示 “(could not be read)”（原为全部显示，并记一条整体警告）。
- **不变：**all 和 own 范围、API 形状、CLI、渠道、数据库结构。
- **文档与测试。**更新 `tests/test_scenario_manager_tools_db.py`、`tests/test_manager_config_transfer_db.py`、`tests/test_manager_config_tools_db.py`、`tests/test_overview_db.py`、`tests/test_manager_reply.py`、`web/src/components/project-settings.test.tsx`、`web/src/lib/api-projects.test.ts`。
- **面向模型的变化：**有，较小。管家创建任务工具返回的工作区警告和任务启动提示中的匿名任务文字按上文改变，限定范围的管家不再在其中收到范围外任务的名称；限定范围的管家看到的删除确认文本现在列出受影响的管家。每条消息的上下文文本除上述失败情形外相同。工具描述和提示文本不变。

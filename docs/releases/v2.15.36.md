From a database that has finished v2.15.35, startup applies five migrations and two online steps with every optional switch off. ## Release Decision

Upgrade from v2.15.35. The code is main at `21fb4d682`.

**Who should upgrade:** Anyone on v2.15.35 or v2.15.34. It matters most to an operator who runs the morning brief or one-time reminders, because a restart between claiming and posting no longer strands the item. It also matters to an operator who wants failed Worker and Reviewer runs retried within bounds instead of going straight to the Planner, one who already stores project lesson settings on, one who shares a scenario Manager across several groups, and one who wants a shorter outage on schema-changing upgrades.

**What this release solves:** The engine failure mode `act` is now accepted (#1686). Under `act`, quota and transient Worker and Reviewer failures wait and retry only the failed unit. Environment failures, and a third consecutive failure of a step, hold that step for the operator. The operator reads and releases holds through operator-only operations, the task page or an act-only Manager tool. In-effect project lessons are frozen per task and injected into Planner and Worker input, with operator readback, revoke and renew (#1690). A morning brief or one-time reminder that was claimed but not yet posted when the server stopped is retried after restart, and one whose post may have started is never resent (#1707, #1716). Terminal not-delivered reminders now appear in Needs you until they are handled, or until seven days after they settle. A scenario Manager can give each of its groups its own resident session (#1733). `looper service upgrade --backup-before-stop` can take the migration backup before the outage starts (#1714). Stable process trees are sampled less often, and on macOS process start times are read without `ps` (#1722). A Manager restart caused by a changed signature logs which components changed (#1721).

**Breaking changes:** Yes. `engine_settings.update` now answers every change, including `off` and `record`, with a confirmation request that must be confirmed. It accepts `act` instead of refusing it. Where `memory_lessons.enabled` is already true and a project's `memory_lessons` is `on`, that project's Planner PLAN and new-session RESUME messages and its Worker prompts start receiving its in-effect lessons. There is no separate injection switch, and `inject.planner` and `inject.worker` default to true. To keep retrospectives without injection, store both as false before upgrading. With attention on, Needs you, `/todo` and the morning brief list every `uncertain`, `failed` or `missed` reminder settled in the last seven days, whether or not reminders are on. With the status card also on, its waiting line counts them. With reminders on, the reminder list and cancel tool descriptions change, and cancel also dismisses terminal reminders. With the morning brief on, a claim interrupted before the channel call is retried instead of settling uncertain. A process tree that has not changed for five seconds is sampled every five seconds instead of every half second, so a new process can be noticed up to five seconds later. Migration 1940 refuses to start while the existing `task_lesson_snapshots` table holds any row, with `legacy lesson snapshots contain no frozen text; operator inspection is required`. The startup transaction then rolls back after the pre-migration backup, none of the five migrations is applied, and v2.15.35 still starts on the unchanged schema. No released version writes that table. See Upgrading. The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version, then read the engine setting without changing it.

```bash
looper --version   # looper 2.15.36
loopercli engine-settings get
```

**Contributors:** Maintainer @foolzzz authored the pull requests named in this body; no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged. An installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once. An installation on v2.14.0 to v2.15.35 upgrades directly. From v2.15.33 or older, the migrations and online steps described in the v2.15.34 body still apply, together with the ones below. Restart the service after upgrading.

On a database that has finished v2.15.35, `pending()` reports five new migrations and the online-step list gains two new markers. v2.15.34 has the same schema. No existing file in `looper/db/migrations` changed in this range, and `schema.sql` is unchanged. `ensure_schema` applies the five migrations in one startup transaction under the schema advisory lock, then runs the online steps after commit, outside any transaction. Those steps are serialized by the online advisory lock. When that lock stays busy for 5 seconds, they are deferred to the lock owner or the next start, with a warning. A failing validation or index build fails startup.

Because these migrations are pending, startup takes the usual verified `pg_dump` into the runtime root `backups/` directory before applying them, unless the operator passes `--skip-backup`. Without that bypass, a missing or incompatible `pg_dump`, or a failed backup, aborts startup before the schema changes. Before dumping, startup now looks in `backups/` for online-backup metadata (#1714). That lookup lists the directory and does not query the database when no metadata file exists. An upgrade from v2.15.35 finds none. The option that writes it, `looper service upgrade --backup-before-stop`, is parsed by the installed `looper`, and v2.15.35 does not have it. So this upgrade takes its backup at startup, inside the outage, as before. The five migrations change metadata and add columns, checks and tables that are empty or small. The online steps scan `tasks` and `task_journal` and the lesson tables. On a large database, the pre-migration dump dominates the outage. This note does not promise how long either takes. After a complete start, the next start has nothing pending. Migration 1940 counts as pending until its online step has validated its checks and built its indexes. If that step is deferred, the next start takes another backup.

**Migration 1940 can refuse to start.**
- **The condition.** While `task_lesson_snapshots` does not yet have the new `line_text` column, migration 1940 checks whether that table holds any row (`looper/db/migrations/memory_lesson_injection.py`). If it does, startup fails with `RuntimeError: legacy lesson snapshots contain no frozen text; operator inspection is required`. Those rows lack the frozen text that this release would show to a run, and the migration does not invent it.
- **Who it can affect.** No released version writes rows to that table. A database that only ever ran released versions therefore has none, and does not hit this check.
- **What startup has already done.** The earlier migrations count as pending, so the check runs after the pre-migration backup has been taken, unless `--skip-backup` was passed. It runs inside the startup transaction. The whole transaction rolls back: none of the five migrations is applied, and the schema stays as v2.15.35 left it. Each further start attempt takes another backup and fails the same way.
- **What to do.** Inspect those rows, for example with `SELECT task_id, candidate_id, "position" FROM task_lesson_snapshots`. Keep running v2.15.35, which still starts on that unchanged schema, and report the case.
- **No automatic repair.** This release documents no repair for these rows. Do not delete them to get past the check unless you have established that they are not needed.

The five migrations, in `pending_order`:

- `step_failure_handling` (1920), #1686.
  - Creates `step_failure_state`, `step_failure_runs`, `step_failures`, `step_holds`, `step_failure_releases` and `task_quota_waits`, with nine indexes on those empty tables. Their foreign keys reference `tasks`, `task_steps`, `llm_records` and `llm_providers`.
  - Widens `tasks_fail_kind_check` with `quota_exhausted` and `environment`, and `task_journal_kind_check` with `failure_hold`. Each is dropped and added again `NOT VALID`, which locks `tasks` and `task_journal` until commit without scanning them.
  - Deletes the online marker `step_failure_handling_online`, so its online step runs after commit.
  - Pending while any of those tables, columns, indexes or constraints is missing, or a check lacks a new value.
- `morning_brief_send_started` (1930), #1707. No online step. Adds nullable `morning_briefs.send_started_at`, then sets it to `updated_at` on rows still `sending`. An unfinished pre-upgrade claim therefore keeps its no-resend recovery. Pending while the column is absent.
- `memory_lesson_injection` (1940), #1690.
  - Creates `task_lesson_snapshot_sets`, `memory_lesson_wrong_tasks` and `task_lesson_planner_state`.
  - Adds three columns to `task_lesson_snapshots` and seven to `memory_injections`. `delivery_key` is added nullable, filled with `legacy:<id>` and then set `NOT NULL`. That scans `memory_injections`, which no released version writes.
  - Adds four checks `NOT VALID` on `memory_injections`, `memory_injection_items` and `memory_lesson_stats`.
  - Deletes the online marker `memory_lesson_injection_online`.
  - Existing `task_lesson_snapshots` rows fail startup with `legacy lesson snapshots contain no frozen text; operator inspection is required`, and the transaction rolls back. See above. An existing index with another definition fails startup with `incompatible memory lesson injection index: ...`.
- `reminder_post_started` (2020), #1716. No online step. Adds nullable `reminders.post_started_at`, then sets it to `updated_at` on rows still `sending`, so they are treated as possibly posted. Pending while the marker and the column are both absent.
- `scenario_session_routing` (2030), #1733. No online step. Adds `managers.session_routing`: text, not null, default `off`, checked as `off` or `per_chat`. Pending while the column is absent.

The two new online steps:

- `step_failure_handling_online` validates the two widened checks. That scans `tasks` and `task_journal` and does not block their reads or writes.
- `memory_lesson_injection_online` validates the four new checks. It then builds `idx_memory_injections_delivery` and `idx_memory_injections_planner_session` with `CREATE UNIQUE INDEX CONCURRENTLY`, and `idx_task_lesson_planner_session` with `CREATE INDEX CONCURRENTLY`.

What runs with every optional switch off. This covers `engine.failure_typing` at `off` or `record`, `memory_lessons` disabled, reminders, scenario session routing, the morning brief, attention and the status card all off, and the other existing switches at their defaults:

- The migrations, online steps and backup above. No feature-setting row is inserted.
- Startup builds the failure handling service.
  - It reads `engine.failure_typing` once. A read error or an unknown value counts as `off`, with a warning. A missing row counts as `off`.
  - It reads `engine.failure_pending_recovery` twice: before Planners restore, and again after. Only the stored value `true` counts. Any other value, or no row, counts as false.
  - Outside `act`, it starts no timer and no background loop.
- Paths read `engine.failure_typing` once more each time: a default Manager turn's tool scope, the end of each Worker or Reviewer run, each Planner exchange, plan load and end, each processor call, and each needs-you read. A read error or an unknown value counts as `off`, with a warning.
- Each Planner turn reads the lesson settings one to three times. A turn with a Planner session also reads `memory_injections` and `task_lesson_planner_state`, with one short `SELECT ... FOR UPDATE` transaction. A PLAN turn with a session checks whether that session held lessons before. These tables are empty while lessons have never been on. A failed read logs `cannot prepare project lessons` and sends the original text. Workers do not read them unless the project's `memory_lessons` is `on`.
- Hourly housekeeping reads the lesson settings once and does nothing more while they are off.
- Process-tree sampling backs off. After five seconds without a change, a live tree is sampled every five seconds instead of every half second. A new resident turn, a detected change or a forced refresh restores fast sampling. Stop and end paths keep their forced reads. On macOS, start-time identities come from the system process-information call, and `ps` is the fallback. Linux keeps `ps`. Stored identity strings are unchanged.
- A resident Manager restarted by a changed signature logs one INFO line `Manager <id> session=<key> restarting: signature changed: ...`. It names only the changed components with 8-character hashes, never their contents.
- The reminder service still returns before any recovery or send while reminders are off.
- The scenario session routing column is read when Manager definitions load, and `off` routes as before.
- The dashboard always shows an engine failure handling card under Settings → LLM Providers. It reads `engine_settings.get` on load.
- The new operator-only operations exist whether or not their features are on: `tasks.failure_history`, `tasks.holds`, `tasks.hold_release`, `memory.task_lessons`, `memory.revoke`, `memory.renew` and `scenario_session_routing.get/update`. The local `looper memory lessons|revoke|renew` commands also exist. Nothing calls them on its own.
- With these switches off, model-visible bytes are unchanged: Planner, Manager, Worker and Reviewer prompts, contracts, tool lists and tool descriptions. Frozen fixtures pin the failure handling and lesson paths, and the reminder tools are not listed.

New startup failure modes, including while every switch is off:

- Migration 1940: any row in the existing `task_lesson_snapshots` table, after the backup and with a full rollback, or an incompatible lesson injection index.
- A failed online validation or concurrent index build in either new online step.
- A database read error, not a stored value, when the failure handling service reads `engine.failure_pending_recovery` at startup, before Planners restore or after. The database is then unavailable to the rest of startup anyway. No stored value of `engine.failure_typing` or `engine.failure_pending_recovery` fails startup.
- The usual backup abort when `pg_dump` is missing or incompatible, or the backup fails, unless `--skip-backup` is set.

## Behavior changes

### Runs even when every switch is off

- **Migrations, online steps, the startup backup, the failure handling service's startup reads, the per-turn setting reads, and the online-backup lookup.** See Upgrading. None of these call a model or send a message.
- **#1722.** Process-tree sampling backs off as described above, for every resident runtime. No setting controls it.
- **#1721.** Server INFO log only. The signature comparison, launch commands, prompts, tools and session resumption are unchanged.
- **#1686.** `engine_settings.update` asks for confirmation on every change and accepts `act`. Without the failure handling service it answers `failure handling is not ready`. The dashboard card and the three task failure operations exist. The holds and history tables stay empty outside `act`.
- **#1714.** Only the directory lookup above. The default `looper service upgrade` steps are unchanged.
- **#1733.** Only the migration and reading the column. Default-Manager session routing, its runtime paths and its process signature are unchanged.
- **#1725, #1718, #1720.** Tests only, not in the wheel.

### When a switch is already on

The existing settings are not rewritten, and none of these switches enables another.

- **Attention (`attention.enabled`).** Needs you, `/todo` and the morning brief gain a `reminders` section. It lists each `uncertain`, `failed` or `missed` reminder settled in the last seven days and not cancelled, with its text, original due time and zone, and state. `uncertain` reads 可能未送达. The section is read on every needs-you summary, whether or not reminders are on, and stays empty when there are no such reminders. Idle checks never push these items. The `failure_holds` section appears only in `act`, so it is still left out.
- **Status card (`status_card.enabled`).** Its waiting line can count the new reminders section. A count of zero is not shown.
- **Morning brief (`morning_brief.enabled`).**
  - The brief commits a send-started marker immediately before the channel call, and a failed marker write prevents the call.
  - After a restart, a claim without the marker returns to retryable, refunds its attempt and consumes nothing. It keeps its first-date digest window. A claim with the marker stays uncertain, consumes exactly its stored ids and is never resent. Turning the brief off is still a no-op, even with a claim outstanding.
  - Each brief also reads the terminal reminders for its target chat. With attention off, it lists them in their own section, 未确认送达的提醒. With attention on, they are in the needs section, and any beyond its display cap are listed separately. A digest row for the same reminder folds into that line, and its id is still claimed and consumed.
  - Digest rows now always carry their `source_ref`. When one has it, for example an intent digest with intents on, the pre-send recheck runs even with intent rules off. It keeps the same rows, and the text is unchanged.
- **Reminders (`reminders.enabled`).**
  - Each tick recovers before sending. A claim that never started a post returns to `pending` and keeps its `looper-reminder-<id>` key. One whose post may have started becomes `uncertain`, its existing decision receipt becomes `unknown` in the same transaction, and it is never resent. Receipts lost after a settled send are restored.
  - The `looper_reminder_list` and `looper_reminder_cancel` descriptions and the cancel conflict reply change. These are model-visible. Cancel now also dismisses `uncertain`, `failed` and `missed` reminders and records the prior state. Cancelling `sending` or `delivered` is still refused.
  - Recovery logs `recovered reminders: N unstarted claim(s) pending, M started send(s) uncertain`.
- **Project lessons (`memory_lessons.enabled` and a project's `memory_lessons` on).**
  - Each task's first PLAN freezes its lesson selection, including an empty one. In-effect lessons go into Planner PLAN and new-session RESUME messages and into Worker prompts, with an optional `lessons_used`/`lessons_wrong` reply contract. Reviewers need `inject.reviewer`. Managers never receive lessons.
  - Hourly housekeeping expires due `in_effect` and `held` lessons, and removes injection logs older than 90 days for finished tasks.
  - With `auto_activate` false, the default, new retrospective lessons stay held, so the frozen selection is empty and no lesson bytes are added.
  - Injected bytes add Planner and Worker input tokens. The Manager turn budget does not cap them.
- **`engine.failure_typing` at `record`.** Classification is recorded as before, and the control flow is unchanged.
- **Metrics, the turn budget, the delivery layer with a timezone, stable context, the delivery guard, persona, completion turns, intents, leads, the ledger and research order.** No included pull changes their paths while failure handling stays outside `act`. Under `act`, metrics add failure handling counts, and Planner and processor retries share the caller's deadline and spend cap.
- **Default-Manager session routing (`manager.session_routing.enabled`).** Unchanged. The scenario switch is separate, and the default Manager is refused by `scenario_session_routing.update`.

## Optional Capability Activation & Use

### Execution failure recovery

**Activation:** Off. `engine.failure_typing` defaults to `off`, null is off, and `record` only classifies. The operator sets `act` with `engine_settings.update` and confirms it, either from the generated CLI (`loopercli engine-settings update --failure-typing '"act"'`, where the value is JSON) or from the engine failure handling card under Settings → LLM Providers. Account admission (`engine.admission.enabled`) stays a separate switch. An upgrade does not write either key.

**Validation:**
- `engine_settings.get` reads back `act`, and startup adds the "Failure recovery" self-check.
- Under `act`, a quota failure holds the step until the reset plus 60 seconds, or backs off 5, 10, 20, 40 and then 60 minutes when the reset is unknown. A transient failure waits 120 and then 600 seconds, with ±20% jitter. Each retries only the failed unit.
- An environment failure, or the third consecutive failure of a step, holds the step. The task projects `waiting_user` and its source is notified. With attention on, Needs you lists it under 运行失败等你处理.
- `tasks.holds` and `tasks.failure_history` read the holds and their history.

**Disable / rollback:** Store `off`, `record` or null, again with confirmation. Leaving `act` wakes waits, hands existing holds back to the Planner's original failure path, and keeps the history. The tables stay. Downgrade needs the pre-migration backup. This release does not ship a down migration.

**Authority boundary:**
- Operator only, with confirmation. API-client tokens cannot change the mode.
- `tasks.hold_release` needs the exact `failure_id` and confirmation. It retries the failed unit, sends the saved failure to the Planner, or stops the task.
- The Manager tool `looper_task_hold` is listed only under `act`, for the default Manager with all tools, in the console and the operator's authenticated direct chats.
- The paid real-model evaluation was not run.

**Docs:** https://github.com/foolzzz/looper/blob/v2.15.36/docs/architecture/agent-system.md#recovering-failed-executions

```bash
loopercli engine-settings get
loopercli engine-settings update --failure-typing '"act"'
loopercli confirm CONFIRMATION_ID
```

### Project lesson injection

**Activation:** No new switch. Injection applies where the system `memory_lessons` setting has `enabled` true and the project's `memory_lessons` is `on`. `inject.planner` and `inject.worker` default to true, and `inject.reviewer` to false. The operator writes the settings with `memory_lessons.settings_put`, which confirms, replaces the whole JSON and fills omitted fields with defaults. The project field is written with `projects.update`. Only `in_effect` lessons are injected. With `auto_activate` false, the default, new retrospective lessons are held and the frozen selection is empty. An upgrade writes neither setting.

**Validation:** `memory.task_lessons` reads a task's frozen lines and its deliveries. Each delivery is `prepared`, `delivered`, `abandoned` or `uncertain`. `looper memory lessons` lists lessons and their counters. A Worker run's `lessons` layer records the block's sha256, line count and characters. With either gate off, Planner and Worker bytes are unchanged and no snapshot is written.

**Disable / rollback:** Turn the system setting or the project field off. To keep retrospectives without injection, store `inject.planner` and `inject.worker` false. A Planner session that already received lessons gets one fixed stop sentence on its next turn. Context already sent cannot be withdrawn. `looper memory revoke` stops one lesson for later runs and keeps a fingerprint tombstone. Downgrade needs the pre-migration backup.

**Authority boundary:** Operator only. A block is bounded by `max_lessons` (12, at most 50) and `max_chars` (3000), frozen per task at its first PLAN. Later runs only drop stopped, expired or deleted lessons. Two distinct tasks that report a lesson wrong hold it. No tool or vault write is added, and Managers never receive lessons. Real-model comparisons were not run.

**Docs:** https://github.com/foolzzz/looper/blob/v2.15.36/docs/architecture/agent-system.md#project-lessons-bounded-hints-with-frozen-task-snapshots

```bash
loopercli memory-lessons settings-get
looper memory lessons --project PROJECT_ID
```

### Scenario Manager per-chat sessions

**Activation:** Off. A scenario Manager's `managers.session_routing` defaults to `off`. The operator sets `per_chat` with `scenario_session_routing.update` and confirms it. From the generated CLI that is `loopercli scenario-session-routing update` with `--manager-id` and `--session-routing '"per_chat"'`. The default Manager keeps its own `manager.session_routing.enabled` switch and is refused here.

**Validation:** `scenario_session_routing.get` reads the value back. With `per_chat`, each group bound to that Manager starts a fresh session of its own on its next turn. Direct chats and the dashboard stay in main. Every session keeps that Manager's system prompt, scope contract, Agent Profile, installed capabilities and tools, and the dashboard's session list shows them. With `off`, message bytes, session keys and process signatures are unchanged.

**Disable / rollback:** Store `off` or null. New turns return to main, in-flight turns finish, and group sessions stay until idle reclaim, with their history. Enabling does not migrate history. Configuration export and import do not carry the setting. Downgrade needs the pre-migration backup.

**Authority boundary:** Operator only. The change is high risk, needs confirmation and is recorded in the operator action audit. API clients and Manager turns can neither read nor change it. Separate histories do not narrow the scenario Manager's tools or task visibility. `manager.sessions.max_resident` applies to each Manager separately. A real-model group comparison was not run.

**Docs:** https://github.com/foolzzz/looper/blob/v2.15.36/docs/architecture/agent-system.md#manager-session-routing

```bash
loopercli scenario-session-routing get --manager-id MANAGER_ID
loopercli scenario-session-routing update --manager-id MANAGER_ID --session-routing '"per_chat"'
loopercli confirm CONFIRMATION_ID
```

### One-time reminder restart recovery

**Activation:** Applies while `reminders.enabled` is on. The default is off. The operator turns it on with `reminders_settings.update` and confirms it. There is no new setting. With attention on, the needs-you `reminders` section is read whether or not reminders are on.

**Validation:** A reminder claimed but not yet posted when the server stopped returns to `pending`. It is then sent once with the same `looper-reminder-` key. One whose post may have started becomes `uncertain`, its decision receipt becomes `unknown`, and it is never resent. The log reports `recovered reminders: ...` with both counts. Terminal `uncertain`, `failed` and `missed` reminders appear once each in Needs you, `/todo` and the morning brief, until cancelled or seven days after settlement. Idle checks do not push them.

**Disable / rollback:** Turn reminders off. Existing reminders stay and the service idles. Terminal ones stay visible until cancelled or seven days pass. The existing cancel tool dismisses a terminal reminder and records its prior state. To reschedule, cancel the old reminder and create a new one. Downgrade needs the pre-migration backup.

**Authority boundary:** The reminder tools are operator-audience tools, listed only while reminders are on. Their list and cancel descriptions change in this release, and those descriptions are model-visible. Cancelling `sending` or `delivered` is refused. Recovery does not rely on channel deduplication, so neither Lark nor Telegram resends a possibly started post. The Telegram transport and a real-model comparison were not validated.

**Docs:** https://github.com/foolzzz/looper/blob/v2.15.36/docs/architecture/agent-system.md#the-managers-platform-tools

```bash
loopercli reminders-settings get
loopercli reminders-settings update --enabled true
loopercli confirm CONFIRMATION_ID
```

### Online upgrade backup

**Activation:** Off. `looper service upgrade --backup-before-stop` takes the verified migration dump after preparation and preflight, before drain, while the old service still serves. The installed `looper` parses the option, so it is first available for an upgrade started from v2.15.36 or later. The upgrade to v2.15.36 itself backs up at startup. The option requires the service's database and backup settings in its ops file.

**Validation:**
- The upgrade report gains `online_backup` and `online_backup_seconds`.
- The new process logs `relying on verified online upgrade backup ...; writes after its snapshot are absent` when it reuses the dump.
- Reuse requires metadata at most 15 minutes after the snapshot started, the same target package version and control-plane fingerprint, the same database and schema state, and the same, still listable archive. Each metadata file is used once. Anything else falls back to the startup dump.
- A failed online dump stops the upgrade before drain or stop. Dry-run, NOOP and WEB_ONLY plans take no online dump.

**Disable / rollback:** Omit the option. The default dump at startup is unchanged.

**Authority boundary:** Operator only, as a local service command. Registry upgrades always take the startup dump. The online dump omits writes after its snapshot, including dump, drain and stop time. Keep the default for strict recovery-point needs, long drains, or workloads that cannot lose those writes.

### 升级决策

从 v2.15.35 升级。

**谁需要升级：** 所有 v2.15.35 或 v2.15.34 用户。以下几类操作者尤其需要：开着晨报或一次性提醒的（认领后、发出前重启，不会再卡住）；想让 Worker 和 Reviewer 失败后在有限范围内重试、而不是直接交给 Planner 的；已经开着项目经验设置的；多个群共用一个场景管家的；希望缩短改 schema 的升级停服时间的。

**解决了什么：** 引擎失败模式现在接受 `act`（#1686）。`act` 下，Worker 和 Reviewer 的额度失败、瞬时失败会等待，然后只重试失败的那个单元；环境失败或同一步连续第三次失败会把这一步挂起，交给操作者处理。操作者可以通过仅限操作者的操作、任务页或只在 act 下出现的 Manager 工具查看和解除挂起。生效中的项目经验按任务冻结，注入 Planner 和 Worker，操作者可以读回、撤销、续期（#1690）。晨报或一次性提醒在认领后、发出前遇到服务停止的，重启后会重试；可能已经发出的不再重发（#1707、#1716）。终态未送达的提醒会出现在「需要你处理」里，直到处理掉，或在结算满 7 天后移出。场景管家可以给每个群单独的常驻会话（#1733）。`looper service upgrade --backup-before-stop` 可以在停服前就做好迁移备份（#1714）。稳定的进程树采样频率降低，macOS 上读进程启动时间不再调用 `ps`（#1722）。签名变化导致 Manager 重启时，日志会写明哪些组件变了（#1721）。

**是否有破坏性变更：** 是。`engine_settings.update` 现在对每次修改（包括 `off`、`record`）都先返回确认请求，确认后才生效；以前拒绝的 `act` 现在也接受。已经开了 `memory_lessons.enabled`、项目 `memory_lessons` 为 `on` 的，升级后该项目的 Planner PLAN、新会话 RESUME 消息和 Worker 提示词会开始带上生效中的经验。注入没有独立开关，`inject.planner`、`inject.worker` 默认就是 true；如果只想保留复盘、不想注入，升级前先把这两项存为 false。attention 打开时，「需要你处理」、`/todo` 和晨报会列出最近七天内结算、状态为 `uncertain`、`failed` 或 `missed` 的提醒，不管提醒开关是否打开；状态卡片也打开时，「等你」一行会把它们计入。提醒打开时，提醒列表和取消工具的描述有变化，取消也可以用来移除终态提醒。晨报打开时，在调用渠道之前被打断的认领会重试，而不是记为 uncertain。进程树五秒没有变化后，采样从每半秒一次改为每五秒一次，所以新进程最多晚五秒才被发现。旧的 `task_lesson_snapshots` 表只要有任意一行，迁移 1940 就会拒绝启动，报 `legacy lesson snapshots contain no frozen text; operator inspection is required`；此时启动事务在迁移前备份之后整体回滚，五个迁移都不生效，v2.15.35 仍能在未改动的 schema 上启动。已发布的版本都不会往这张表写数据，详见升级说明。桥接版本边界不变：更旧的安装需先升级到 v2.13.165。

### 升级

早于 v2.13.165 的安装需先升级到 v2.13.165 并启动一次。v2.14.0 到 v2.15.35 可以直接升级；v2.15.33 及更早的版本，v2.15.34 正文里的迁移和在线步骤仍然适用。升级后重启服务。

**本版本的迁移。** 在已完成 v2.15.35 的库上（v2.15.34 的 schema 相同），`pending()` 报告五个新迁移，在线步骤多两个新 marker。
- 五个迁移在同一个启动事务里、持 schema advisory lock 执行。
- 两个在线步骤在提交后、事务外执行。在线锁争用 5 秒后会推迟；校验或建索引失败会导致启动失败。

**迁移前备份。** 因为有待执行的迁移，启动前照常把 `pg_dump` 做到运行根目录的 `backups/`，除非传了 `--skip-backup`。
- 备份前会先在 `backups/` 里查找在线备份元数据（#1714）。从 v2.15.35 升级时一定找不到：写这份元数据的 `--backup-before-stop` 由已安装的 `looper` 解析，而 v2.15.35 没有这个选项。所以这次升级仍在停服窗口内做备份。
- 1940 的在线步骤完成之前，这个迁移一直算待执行；如果在线步骤被推迟，下次启动还会再备份一次。
- 这五个迁移新增的列、检查和表都是空的或很小，1930 和 2020 只回填仍处于发送中的行；在线步骤会扫描 `tasks`、`task_journal` 和经验相关的表。大库上停服时间主要花在迁移前备份上。本说明不承诺具体耗时。完整启动一次之后，再次启动不会有待执行的迁移。

**迁移 1940 可能拒绝启动。**
- **条件。** 当 `task_lesson_snapshots` 还没有新的 `line_text` 列时，迁移 1940 会检查这张表有没有数据（`looper/db/migrations/memory_lesson_injection.py`）。只要有一行，启动就失败，报 `RuntimeError: legacy lesson snapshots contain no frozen text; operator inspection is required`。这些行缺少本版本给运行展示用的冻结文本，迁移不会替它们编造。
- **影响谁。** 已发布的版本都不会往这张表写数据，所以只跑过已发布版本的库没有这种行，也不会触发。
- **触发时的状态。** 前面的迁移已经判定为待执行，所以这个检查发生在迁移前备份之后（除非传了 `--skip-backup`），并且在启动事务里。整个事务回滚：五个迁移都不生效，schema 保持 v2.15.35 的样子。之后每次重试启动，都会再备份一次，然后以同样的方式失败。
- **处理办法。** 先检查这些行，例如 `SELECT task_id, candidate_id, "position" FROM task_lesson_snapshots`。继续运行 v2.15.35（它在未改动的 schema 上仍能启动），并报告这个情况。
- **没有自动修复。** 本版本没有提供针对这些行的修复办法。在确认这些行不需要之前，不要为了绕过检查而删除它们。

**五个迁移**，按 `pending_order`：
- `step_failure_handling`（1920）：新建六张失败处理表。`tasks_fail_kind_check` 和 `task_journal_kind_check` 放宽后以 NOT VALID 方式重建，会锁住 `tasks`、`task_journal` 直到提交，但不扫表。
- `morning_brief_send_started`（1930）：加 `morning_briefs.send_started_at`，并给还处于 `sending` 的行回填。
- `memory_lesson_injection`（1940）：新建三张表，`task_lesson_snapshots` 加三列、`memory_injections` 加七列，四个 CHECK 以 NOT VALID 方式加上。旧快照缺冻结文本，或索引定义不兼容时，启动失败。
- `reminder_post_started`（2020）：加 `reminders.post_started_at`，并给还处于 `sending` 的行回填。
- `scenario_session_routing`（2030）：加 `managers.session_routing`，默认 `off`。

**在线步骤：**
- `step_failure_handling_online`：校验两个 check，会扫描 `tasks` 和 `task_journal`，不阻塞读写。
- `memory_lesson_injection_online`：校验四个 check，并用 CONCURRENTLY 方式建三个索引。

#### Execution failure recovery

**启用：** 默认关。`engine.failure_typing` 为 `off` 或 null 时都是关，`record` 只做分类。操作者用 `engine_settings.update` 设为 `act` 并确认：可以用生成的 CLI（`loopercli engine-settings update --failure-typing '"act"'`，值按 JSON 传），也可以用 Settings → LLM Providers 里的「引擎失败处理」卡片。账号准入 `engine.admission.enabled` 是独立开关。升级不写这两个键。

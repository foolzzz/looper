# Looper v2.13.98

## Release Decision

**Who should upgrade:** Anyone who forwards user corrections to a running Worker, and anyone who runs the release evaluation tiers or the Pi prompt comparison script.

**What this release solves:** [#554](https://github.com/foolzzz/looper/pull/554) bounds the delivery of a user turn to a Worker by one deadline that ends before the Planner stops waiting for the acknowledgement. Before, readiness and the runtime's acceptance were not covered by a shared budget, so a late write could land after the Planner had already been told the turn was refused, and a delivery task could outlive the pool. [#568](https://github.com/foolzzz/looper/pull/568) aligns the release evaluation coverage, budgets and Pi comparison tiers with the 43 dialogs now selected, and makes the comparison report incomplete baselines as unverified instead of passing.

**Breaking changes:** No. No API, configuration, prompt or Tool declaration changed.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#554](https://github.com/foolzzz/looper/pull/554) and [#568](https://github.com/foolzzz/looper/pull/568); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.98
```

## Behavior changes

- **Bounded Worker input delivery ([#554](https://github.com/foolzzz/looper/pull/554)):** `WorkerPool.send_input` in `looper/agents/tiers/worker.py` now runs under one deadline of `WORKER_INPUT_DELIVERY_TIMEOUT` (4.5 seconds). Waiting for the dispatched step's input channel and for the runtime handshake share that deadline. Before writing, it checks that the time left covers the channel's own `send_timeout`; if not, it logs a warning and returns `False` without writing. A timeout also returns `False`. Once the write starts, the channel's acceptance timeout is not shortened.
- **Channel contract:** `RunChannel` in `looper/agents/runtimes/channel.py` gains `wait_input_ready()` (waits for the startup handshake without writing a turn) and `send_timeout`. The stream channel reports 4.0 seconds and now bounds its write by that timeout. The Codex, OMP and Pi steer channels report their existing 4.0-second timeouts and implement `wait_input_ready`; their `send` now uses the same readiness check. The DSH channel reports 0 and `wait_input_ready` raises, so an active DSH run still refuses further input at once. The OMP channel now sets a ready event when the prompt is acknowledged and when its events end.
- **Acknowledgement:** `_deliver_input` now always publishes `WORKER_INPUT_RESULT`, with `delivered` false if delivery raised or was cancelled. The pool tracks its delivery tasks, and `WorkerPool.stop` cancels and awaits them so none leaks.
- **Planner timeout:** `WORKER_INPUT_TIMEOUT` in `looper/agents/tiers/planner.py` is now `WORKER_INPUT_DELIVERY_TIMEOUT + 0.5`, which is 5.0 seconds, the same value as before. The half second is left for the acknowledgement, so a refusal settles before the Planner's request expires.
- **Release evaluation tiers ([#568](https://github.com/foolzzz/looper/pull/568)):** `evals/README.md` now describes the full real dialog runs over all 43 dialogs (129 case/reps per three-rep tier). Its numeric dialog caps are replaced by `HAIKU_DIALOG_CAP_USD`, `SONNET_DIALOG_CAP_USD` and `OPUS_DIALOG_CAP_USD`, explicit authorized ceilings that are not measured release caps. The committed cost references cover only 24 dialogs, so no numeric full-dialog cap is recommended yet.
- **Pi comparison script:** `examples/pi/eval-prompt-comparison.sh` now compares Sonnet tasks at two reps, Opus Planner tasks at one, Sonnet dialogs at two and Sonnet with an Opus xhigh Manager at one. That is 13 distinct cases and 37 case/reps, derived from the selectors rather than a fixed 48. One spending cap and deadline are shared by all tiers, and per-case reservations still apply. A report is rejected if it is aborted, stopped by the cap, has missing, duplicate, extra, unrepeated or skipped selected case/reps, or has the wrong model, agent or Manager tier. A missing baseline, or one that lacks selected case/reps, is recorded as unverified rather than passed. The script is now documented to run in the foreground.
- **Model-visible changes:** none for prompts, Tool declarations and Tool results. [#568](https://github.com/foolzzz/looper/pull/568) changes no production code.
- **Tests:** `tests/test_worker_input_delivery.py` is new and `tests/test_run_channel.py` is adjusted; `tests/test_pi_eval_commands.py` and `tests/test_prompt_eval.py` cover the comparison tiers and readback faults. The pull requests report 191 and 137 added test lines, and 44 production lines for [#554](https://github.com/foolzzz/looper/pull/554).

## Upgrade and rollback

Re-run `install.sh` once v2.13.98 is published. No data migration and no configuration change. Rolling back to v2.13.97 restores the previous Worker input delivery and comparison tiers.

### 升级决策

**谁需要升级：**会向运行中的 Worker 转发用户纠正的用户，以及运行发布评测档位或 Pi prompt 对照脚本的用户。

**解决了什么：**[#554](https://github.com/foolzzz/looper/pull/554) 用一个在 Planner 停止等待确认之前结束的截止时间约束向 Worker 投递用户消息。此前就绪等待和运行时接受没有共用预算，Planner 已被告知被拒绝之后仍可能有迟到的写入，投递任务也可能比 pool 活得更久。[#568](https://github.com/foolzzz/looper/pull/568) 让发布评测的覆盖、预算和 Pi 对照档位与现在选中的 43 个 dialog 一致，并让对照把不完整的基线报告为未验证，而不是通过。

**是否有破坏性变更：**否。API、配置、prompt 和 Tool 声明均未改变。

**如何验证：**运行 `looper --version` 核对版本为 2.13.98。

**贡献者：**维护者 @foolzzz 提交 [#554](https://github.com/foolzzz/looper/pull/554) 和 [#568](https://github.com/foolzzz/looper/pull/568)；本次 patch release 无社区贡献。

### 行为变化与入口

- **有界的 Worker 输入投递（[#554](https://github.com/foolzzz/looper/pull/554)）：**`looper/agents/tiers/worker.py` 中的 `WorkerPool.send_input` 现在受一个 `WORKER_INPUT_DELIVERY_TIMEOUT`（4.5 秒）的截止时间约束。等待已派发步骤的输入通道和运行时握手共用这个截止时间。写入前会检查剩余时间是否够通道自己的 `send_timeout`；不够则记录警告并返回 `False`，不写入。超时同样返回 `False`。开始写入后，通道自身的接受超时不会被缩短。
- **通道约定：**`looper/agents/runtimes/channel.py` 中的 `RunChannel` 新增 `wait_input_ready()`（等待启动握手，不写入消息）和 `send_timeout`。流式通道为 4.0 秒，并且写入现在受该超时约束。Codex、OMP、Pi 的 steer 通道沿用原有 4.0 秒，并实现 `wait_input_ready`，其 `send` 使用同一个就绪检查。DSH 通道为 0，`wait_input_ready` 直接抛错，所以运行中的 DSH 仍会立即拒绝后续输入。OMP 通道现在在 prompt 被确认和事件结束时设置就绪事件。
- **确认：**`_deliver_input` 现在总会发布 `WORKER_INPUT_RESULT`；投递抛错或被取消时 `delivered` 为 false。pool 会跟踪投递任务，`WorkerPool.stop` 会取消并等待它们，不会泄漏。
- **Planner 超时：**`looper/agents/tiers/planner.py` 中的 `WORKER_INPUT_TIMEOUT` 现为 `WORKER_INPUT_DELIVERY_TIMEOUT + 0.5`，即 5.0 秒，与之前相同。多出的半秒留给确认，使拒绝在 Planner 请求过期之前完成。
- **发布评测档位（[#568](https://github.com/foolzzz/looper/pull/568)）：**`evals/README.md` 现在描述覆盖全部 43 个 dialog 的完整真实运行（每个三次重复的档位 129 个 case/rep）。其中的数字 dialog 上限换成 `HAIKU_DIALOG_CAP_USD`、`SONNET_DIALOG_CAP_USD`、`OPUS_DIALOG_CAP_USD`，它们是明确授权的上限，不是实测的发布上限。已提交的成本参考只覆盖 24 个 dialog，因此暂不推荐完整 dialog 的数字上限。
- **Pi 对照脚本：**`examples/pi/eval-prompt-comparison.sh` 现在对 Sonnet tasks 做两次重复、Opus Planner tasks 一次、Sonnet dialogs 两次、Sonnet 加 Opus xhigh Manager 一次。共 13 个不同 case、37 个 case/rep，由选择器推导而不是固定的 48。所有档位共用一个花费上限和截止时间，仍保留按 case 的预留。报告若已中止、被上限停止，或所选 case/rep 缺失、重复、多余、缺少 rep、被跳过，或模型、agent、Manager 档位不符，都会被拒绝。缺少基线或基线缺少所选 case/rep 时记为未验证，而不是通过。脚本现在文档化为前台运行。
- **面向模型的变化：**prompt、Tool 声明和 Tool 结果均无变化。[#568](https://github.com/foolzzz/looper/pull/568) 不改生产代码。
- **测试：**新增 `tests/test_worker_input_delivery.py`，调整 `tests/test_run_channel.py`；`tests/test_pi_eval_commands.py` 与 `tests/test_prompt_eval.py` 覆盖对照档位和读回故障。两个 PR 分别报告新增测试 191 行和 137 行，[#554](https://github.com/foolzzz/looper/pull/554) 另有生产代码 44 行。

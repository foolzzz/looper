# Looper v2.14.50

This is the patch release v2.14.50, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.49: a startup scan of kept-run directories and stricter process-ending rules ([#1017](https://github.com/foolzzz/looper/pull/1017)). There is no new setting; the scan runs at every `looper serve` start, with keepers switched off too.

## Release Decision

**Who should upgrade:** Anyone who wants to stay on the latest patch line, and anyone who runs keepers or whose server was stopped while agent runs were still alive.

**What this release solves:** [#1017](https://github.com/foolzzz/looper/pull/1017) makes `looper serve` end leftover keepers and their children, and remove their run directories under `.local/runs`, before it interrupts unfinished records and before steps can be dispatched again. It also makes `proc_tree` stop treating a failed `ps` as an empty process list, and makes the keeper reap group members left behind after its child exits.

**Breaking changes:** No. No API, setting or migration is added or removed. A start that cannot tell whether a kept run is still alive now stops with an error (see Behavior changes).

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#1017](https://github.com/foolzzz/looper/pull/1017); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.50
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.49 upgrades directly. This release adds no migration and no setting.

## Behavior changes

- **Startup scan of kept runs ([#1017](https://github.com/foolzzz/looper/pull/1017)).** After `proc_tree.sweep` and before `end_unfinished_records`, `looper serve` scans `<runtime root>/.local/runs/*`, even when keepers are off. No run is adoptable yet, so:
  - a live keeper is ended together with its child (`not_adoptable`) and its directory is removed;
  - a dead keeper, or a state of `exited`, releases its directory (`keeper_dead`) after the recorded child, if still the same process, is ended;
  - with missing or invalid `keeper.json`, a unique matching spawn record (by run directory) identifies the keeper and child; they are ended and the directory removed (`bad_files`);
  - without such a record, the directory is left in place and an error is logged. The start continues; the keeper's orphan timer ends its child within 30 minutes, and the next start scans the directory again;
  - non-directory entries are ignored, and nothing is created if `.local/runs` does not exist.
- **Start can refuse.** Keeper identities are read from one process snapshot before any directory is removed, and are checked again before each signal. If liveness cannot be read (`ps` fails), startup stops with "cannot tell whether kept runs are still running" and deletes no run directory, so steps are not dispatched again while old processes may still run.
- **Spawn records name the run.** Records written by a keeper's `proc_tree` now carry `run_dir`, which the scan uses to find a keeper's child. A keeper's children are recorded with the keeper as owner: the server's sweep leaves a live keeper's child alone and ends a dead keeper's child. Keepers themselves are still never signalled by the sweep.
- **`ps` failures in `proc_tree`.** The process snapshot now returns "unavailable" instead of an empty table when `ps` cannot run or exits non-zero. A failed listing keeps the tree observed before the stop (never the reaped pid), is not treated as proof that survivors are gone, and does not delete the agent's record. New `proc_tree.end_orphan` ends an orphan's tree after checking its start time.
- **Reaped leaders.** When ending a tree whose leader is already reaped, the signal never goes to the reaped pid or its group directly; only members confirmed to still be in the old group (or retained from before the stop when `ps` fails) are signalled.
- **Keeper process.** After its child exits the keeper always ends the remaining group members, then drains the log pumps with the `REAP_SEC` timeout and closes the pipes before waiting for the child. A second end request no longer starts a second end task. The keeper state file gains `stderr_truncated`, set when stderr reaches its log limit.
- **Housekeeping.** Housekeeping never touches `.local/runs` and no retention pass deletes `llm_records`; this is now stated in docs/architecture/agent-system.md.
- **Model-visible changes:** No. No prompt, tool description, tool schema or Manager confirmation text changes.

### 行为变化与入口

- **启动时扫描 kept run（[#1017](https://github.com/foolzzz/looper/pull/1017)）。**在 `proc_tree.sweep` 之后、`end_unfinished_records` 之前，`looper serve` 扫描 `<runtime root>/.local/runs/*`，keeper 关闭时同样执行。目前没有可接管的运行，因此：
  - 存活的 keeper 连同其子进程被结束（`not_adoptable`），目录被删除；
  - keeper 已死或状态为 `exited` 时，若记录的子进程仍是同一进程则先结束它，再释放目录（`keeper_dead`）；
  - `keeper.json` 缺失或无效时，按运行目录唯一匹配的 spawn 记录确定 keeper 和子进程，结束后删除目录（`bad_files`）；
  - 没有这样的记录时，目录保留并记录错误。启动继续；keeper 的孤儿计时器会在 30 分钟内结束其子进程，下次启动再次扫描该目录；
  - 非目录条目被忽略；`.local/runs` 不存在时不创建任何内容。
- **启动可能拒绝。**删除任何目录之前，先在一次进程快照中读取 keeper 身份，并在每次发信号前再次检查。无法读取存活状态（`ps` 失败）时，启动以 “cannot tell whether kept runs are still running” 停止且不删除任何运行目录，避免旧进程仍在运行时步骤被重新派发。
- **spawn 记录带上运行目录。**keeper 的 `proc_tree` 写入的记录现在带 `run_dir`，扫描据此找到 keeper 的子进程。keeper 的子进程以 keeper 为所有者记录：服务器清扫会放过存活 keeper 的子进程，结束已死 keeper 的子进程。清扫仍不会向 keeper 本身发信号。
- **`proc_tree` 中的 `ps` 失败。**进程快照在 `ps` 无法运行或非零退出时返回“不可用”，而不是空表。列表失败时保留停止前观察到的进程树（不含已回收的 pid），不当作幸存者已消失的证据，也不删除 agent 记录。新增 `proc_tree.end_orphan`，在核对启动时间后结束孤儿的进程树。
- **已回收的组长。**结束组长已被回收的进程树时，信号从不直接发给已回收的 pid 或其进程组；只发给确认仍在旧进程组中的成员（`ps` 失败时发给停止前已观察到的成员）。
- **Keeper 进程。**子进程退出后，keeper 总会结束残留的组成员，再以 `REAP_SEC` 超时排空日志泵并关闭管道，然后等待子进程。第二次结束请求不再启动第二个结束任务。keeper 状态文件新增 `stderr_truncated`，stderr 达到日志上限时置位。
- **例行清理。**例行清理从不触碰 `.local/runs`，也没有任何保留策略会删除 `llm_records`；docs/architecture/agent-system.md 现已写明。
- **面向模型的变化：**无。没有 prompt、工具描述、工具 schema 或 Manager 确认文本的变化。

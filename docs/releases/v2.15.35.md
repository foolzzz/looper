Cut from the v2.15.34 tag (`e9652ff91`) with two pull requests applied on top: [#1724](https://github.com/foolzzz/looper/pull/1724) and [#1727](https://github.com/foolzzz/looper/pull/1727). Nothing else merged into main after v2.15.34 is in this release: [#1707](https://github.com/foolzzz/looper/pull/1707), [#1686](https://github.com/foolzzz/looper/pull/1686), [#1725](https://github.com/foolzzz/looper/pull/1725), [#1718](https://github.com/foolzzz/looper/pull/1718) and later pulls ship next. This body describes only the code on this branch.

No migration and no online step are added, so startup on a database that has finished v2.15.34 has nothing pending and takes no pre-migration backup. No feature setting turns itself on, and an upgrade does not insert a feature-setting row. `web/` is unchanged.

## Release Decision

Upgrade from v2.15.34.

**Who should upgrade:** Anyone on v2.15.34. It matters most to an operator who turns the Manager's resident operator profile on (`manager.profile.enabled`) and also talks to the default Manager through an API client (`loopercli chat` or an agent tool using `POST /api/v1/chat/send`), and to an operator who wants to turn attention, reminders, stable context or decision snapshots on, or change the leads search mode, without writing the database by hand.

**What this release solves:** With the resident profile on, an API-client turn no longer receives the operator profile. Before this release such a turn received the whole compiled profile, although only the operator's own turns should. The dashboard chat and the operator's own direct chat still receive it; groups, other senders, routed sessions, scenario Managers and Looper's own turns still omit it. With stable context on, an API-client turn neither diffs against nor overwrites the operator's last shown state, so the operator's next turn follows the normal unchanged/changes rules. API clients keep the full persona. Five settings that had a read but no write now have operator-only write operations: `attention.settings_update` (`attention.enabled`), `reminders_settings.update` (`reminders.enabled`), `stable_context_settings.update` (`manager.stable_context`), `decision_snapshots_settings.update` (`decision_snapshots.enabled`) and `leads_search_settings.update` (`leads.search_mode`), with the new reads `reminders_settings.get`, `stable_context_settings.get`, `decision_snapshots_settings.get` and `leads_search_settings.get`. Each takes a typed value, `null` deletes the row and restores the default, the call needs the operator and a high-risk confirmation, it is recorded in the operator action audit, and the response reads the value back through the capability's own reader. They generate operator CLI commands, for example `loopercli attention settings-update --enabled true`.

**Breaking changes:** Yes. With `manager.profile.enabled` on, API-client turns, including the operator's own `loopercli chat` and agent tools, no longer receive the `Operator profile` section. Nothing else changes by default: the five settings keep their stored values and defaults (`false`, and `words` for the leads search mode), and the existing `chat_settings` fields and writes are unchanged. The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version, then read one of the new settings without changing it.

```bash
looper --version   # looper 2.15.35
loopercli attention settings-get
loopercli stable-context-settings get
```

**Contributors:** Maintainer @foolzzz authored the pull requests named in this body; no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once. An installation on v2.14.0 to v2.15.34 upgrades directly; from v2.15.33 or older, the migrations and online steps described in the v2.15.34 body still apply. Restart the service after upgrading.

On a database that has finished v2.15.34, `pending()` reports no migration and the online-step list is unchanged. No file in `looper/db/migrations` changed in this range.

## Optional Capability Activation & Use

No new optional capability activation is introduced in this release.

## 中文摘要

### 升级决策

从 v2.15.34 升级。

**谁需要升级：** 所有 v2.15.34 用户。开启了管家常驻画像（`manager.profile.enabled`）、同时又通过 API 客户端（`loopercli chat`，或调用 `POST /api/v1/chat/send` 的 agent 工具）和默认管家对话的操作者，以及想打开 attention、提醒、稳定上下文、决策快照或修改 leads 检索模式、又不想手工写数据库的操作者，尤其需要。

**解决了什么：** 画像开启时，API 客户端回合不再收到操作者画像。此前这类回合会收到完整的编译后画像，而画像本应只出现在操作者本人的回合里。控制台对话和操作者本人的私聊仍然带画像；群聊、其他发送者、路由出去的会话、场景管家和 Looper 自己发起的回合仍然不带。稳定上下文开启时，API 客户端回合既不和操作者上次看到的状态做差分，也不覆盖它，操作者下一回合照常按未变/变化规则计算。API 客户端仍拿到完整 persona。五个只有读、没有写的设置新增了仅限操作者的写操作：`attention.settings_update`（`attention.enabled`）、`reminders_settings.update`（`reminders.enabled`）、`stable_context_settings.update`（`manager.stable_context`）、`decision_snapshots_settings.update`（`decision_snapshots.enabled`）和 `leads_search_settings.update`（`leads.search_mode`），并新增读操作 `reminders_settings.get`、`stable_context_settings.get`、`decision_snapshots_settings.get`、`leads_search_settings.get`。值有类型，`null` 删除该行、恢复默认；调用需要操作者身份和高风险确认，写入操作者操作审计，返回值经该能力自己的读取函数读回。它们会自动生成操作者 CLI 命令，例如 `loopercli attention settings-update --enabled true`。

**是否有破坏性变更：** 是。`manager.profile.enabled` 开启时，API 客户端回合（包括操作者自己的 `loopercli chat` 和 agent 工具）不再收到 `Operator profile` 段。其余默认行为不变：五个设置保留已存的值和默认值（`false`，leads 检索模式为 `words`），现有 `chat_settings` 字段和写入不变。桥接版本边界不变：更旧的安装需先升级到 v2.13.165。

**如何验证：** 查看安装版本，再只读其中一个新设置。

```bash
looper --version   # looper 2.15.35
loopercli attention settings-get
loopercli stable-context-settings get
```

**贡献者：** 本版本列出的 PR 均由维护者 @foolzzz 提交，没有社区贡献。

### 升级说明

早于 v2.13.165 的安装需先升级到 v2.13.165 并启动一次，v2.14.0 到 v2.15.34 可直接升级。本版本没有新增迁移和在线步骤；从 v2.15.34 升级时启动不会有待执行的迁移，也不做迁移前备份。

### 可选能力启用与使用

本版本未新增可选能力启用入口。

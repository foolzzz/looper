# Looper v2.15.19

This release documents the changes merged since v2.15.18: the ledger's tables, its one writer and its command line ([#1434](https://github.com/foolzzz/looper/pull/1434)), Tasks page filters for several statuses at once ([#1440](https://github.com/foolzzz/looper/pull/1440)), two load-sensitive tests made deterministic ([#1442](https://github.com/foolzzz/looper/pull/1442)), and the removal of the dashboard Runs page ([#1443](https://github.com/foolzzz/looper/pull/1443)). The ledger is off by default (`ledger.enabled`). While it is off, nothing a model sees changes and the new command and reads refuse. The Tasks page default and the removed Runs page are user-visible.

## Release Decision

**Who should upgrade:** Anyone who uses the dashboard Tasks page, because its default view is now Ready, Running, Waiting, Waiting for you and Pending, and anyone who opened a role's runs from the Runs page, because that page is gone and those links open History. The ledger stays off until `ledger.enabled` is `true`. An installation that does not use those two pages can stay on v2.15.18; the only other change is one additive database migration.

**What this release solves:** The Tasks page can show several statuses at once, and its default view is the unfinished ones. A role's runs are listed on History, which also shows runtime catalog skips in a run's detail. The ledger's tables, its one writer, `looper ledger` and the read-only ledger API are in place and idle until the ledger is turned on.

**Breaking changes:** Yes. The Tasks page, opened with neither `status` nor `group` nor `schedule` in the address, lists those five unfinished statuses instead of every task. The dashboard Runs page and its sidebar entry are removed, and old `#runs` links open History. This is not an API break: `POST /api/v1/tasks/page` still lists every task when both `status` and `statuses` are omitted, and the backend run APIs remain. There is one additive PostgreSQL migration (see Upgrading). The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.15.19
```

**Contributors:** Maintainer @foolzzz authored [#1434](https://github.com/foolzzz/looper/pull/1434), [#1440](https://github.com/foolzzz/looper/pull/1440), [#1442](https://github.com/foolzzz/looper/pull/1442) and [#1443](https://github.com/foolzzz/looper/pull/1443); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.15.18 upgrades directly. Restart the service after upgrading, as for every release.

This release has one additive PostgreSQL migration, applied once at startup:

- `ledger`: creates `ledger_items` and `ledger_events` with their indexes and constraints. It is DDL only and writes no ledger row. The tables stay empty until the ledger is on and something writes.

## Behavior changes

### The ledger, off by default ([#1434](https://github.com/foolzzz/looper/pull/1434))

- **While `ledger.enabled` is off, nothing changes.** There is no row by default, and any value other than `true` leaves the ledger off. No prompt, tool list or agent command line mentions it. `looper ledger` exits 3. `POST /api/v1/ledger/list` and `POST /api/v1/ledger/get` answer `conflict`. The migration still creates the two empty tables.
- The migration name is `ledger`. `ledger_items` holds what waits for the user (`pending`), what was decided (`decision`) and who does what (`work_item`). An own item keeps its `status`. A sourced item (a gate, a task or a Manager confirmation) has no `status` and reads its source's (`db.ledger.SOURCE_STATUS`; a task goes through `task_group`). `ledger_events` only grows. Confirming or closing points at an event through the composite key `(id, actor_kind)`, so a `relayed` event cannot be referenced even from raw SQL. The system can only `add` a sourced item.
- `db.ledger.apply` is the only writer, with the permission table from the completion-ledger RFC. Refusals are typed: `forbidden`, `conflict`, `invalid`, `not_found`.
- `looper ledger list|show|add|close|confirm` reads and writes the database directly, so it works with the service stopped. A write is recorded as the user, `via=cli`, and requires `--session`. It is refused (exit 4) when `LOOPER_AGENT_RUN` is set. This release does not set that variable on agent runs (a later change, required before any wider enable path). Exit codes are 0 done, 1 nothing listed, 2 usage, 3 not enabled, 4 refused, 5 no such item, 6 database unusable.
- The two reads are operator and API client operations, not Manager tools. There is no dashboard switch, no HTTP write, no automatic registration and no To-do page in this release.

### Tasks page filters ([#1440](https://github.com/foolzzz/looper/pull/1440))

- The status chips toggle. With neither `status` nor `group` nor `schedule` in the address, the selection is Ready, Running, Waiting, Waiting for you and Pending (`init`, `running`, `waiting`, `waiting_user`, `pending`). `#tasks?project=` still uses that default. `status=all` shows every task. A bookmark such as `status=failed` still selects only that filter. Deselecting the last chip returns to All.
- A group or schedule link with no `status` stays unfiltered: it lists every task in that group or schedule, including `#tasks?group=` with `scheduled=include`. Choosing All on those links omits `status`. `scheduled=include` on its own does not turn the default off.
- An empty Waiting for you chip is hidden unless that filter is the only selection. Toggling another chip leaves it selected without showing the empty chip. It appears, selected, when its count is above zero.
- `POST /api/v1/tasks/page` accepts an optional `statuses` array of 1 to 10 names, the same names `status` accepts, and returns their union. `status` is unchanged. Sending both, or an unknown name, is an invalid argument. `counts` stay per filter. Pagination with `before` uses the same union. Omitting both `status` and `statuses` still returns every task.
- Telegram, Lark, the CLI and the Manager's compact task list do not send `statuses`. A request with neither field still lists every task, so those entry points need no change.

### The Runs page is removed ([#1443](https://github.com/foolzzz/looper/pull/1443))

- The dashboard Runs page, its route and its sidebar entry are gone. This is not an API break. The backend run APIs remain. History, Chat, tasks, the CLI and `/api/v1/runs` still use them.
- Old `#runs` and `#runs/` plus a role redirect to History. A role of manager, planner, worker, reviewer or processor keeps the role filter (`#history?role=`). Any other role opens History with no role filter and does not call the list API.
- Settings → Roles ("Its runs") and the Manager install note open History filtered to that role.
- An open History run lists the plugins and skills it loaded, and lists `metadata.runtime_catalog.skipped` beside them when that list is not empty. A run with no skips shows no such section.

### Tests ([#1442](https://github.com/foolzzz/looper/pull/1442))

- Two tests that failed under CI load no longer depend on how long a step takes. The startup check waits up to 10 seconds for the probe to start, and the probe sleeps 8 seconds. The room test reads the inbox after `post` returns. No production code changed.

## Optional Capability Activation & Use

### Ledger

**Activation:** Off by default. No `ledger.enabled` row means off, and only the value `true` turns it on. This release has no dashboard switch and no HTTP write. Set the system setting `ledger.enabled` to `true`. Until then `looper ledger` exits 3 and the two read operations answer `conflict`.

**Validation:** With the setting `true`, `looper ledger list` exits 0 when items exist and 1 when the open list is empty. `POST /api/v1/ledger/list` and `POST /api/v1/ledger/get` return the items. With the setting absent, the command exits 3 and both reads answer `conflict`.

**Disable / rollback:** Delete the `ledger.enabled` setting, or set it to any value other than `true`. The command and the reads refuse again. The tables are additive and unused while the ledger is off.

**Authority boundary:** Writes go through `db.ledger.apply` only. A CLI write is the user, via `cli`, and needs `--session`. It is refused when `LOOPER_AGENT_RUN` is set; this release does not set that variable on agent runs. Confirming or closing can point only at a `user` event. The reads are for an operator or an API client, not a Manager tool. No prompt, tool list or agent command line mentions the ledger.

**Docs:** https://github.com/foolzzz/looper/blob/v2.15.19/docs/architecture/agent-system.md#the-ledger

```bash
looper ledger list
```

## 中文摘要

本版本说明自 v2.15.18 以来合并的改动：账本的表、唯一写入者和命令行（[#1434](https://github.com/foolzzz/looper/pull/1434)）、Tasks 页一次按多个状态筛选（[#1440](https://github.com/foolzzz/looper/pull/1440)）、两个受负载影响的测试改为确定结果（[#1442](https://github.com/foolzzz/looper/pull/1442)），以及去掉仪表盘的 Runs 页（[#1443](https://github.com/foolzzz/looper/pull/1443)）。账本默认关闭（`ledger.enabled`）。关闭时，模型看不到任何变化，新命令和读取都会拒绝。Tasks 页的默认视图和被去掉的 Runs 页是用户看得到的变化。

### 升级决策

**谁需要升级：**使用仪表盘 Tasks 页的用户，因为默认视图现在是 Ready、Running、Waiting、Waiting for you 和 Pending；以及以前从 Runs 页打开某角色运行记录的用户，因为该页已去掉，那些链接会打开 History。账本在 `ledger.enabled` 为 `true` 之前保持关闭。不用这两个页面的安装可以留在 v2.15.18；除此之外只有一个可加的数据库迁移。

**解决了什么：**Tasks 页可以同时显示多个状态，默认是未完成的那些。某个角色的运行记录改在 History 里列出，运行详情还会显示运行时目录跳过项。账本的表、唯一写入者、`looper ledger` 和只读接口已经就位，打开之前保持空闲。

**是否有破坏性变更：**有。地址里既没有 `status` 也没有 `group`、`schedule` 时，Tasks 页列出上述五个未完成状态，而不是全部任务。仪表盘 Runs 页和它的侧栏入口已去掉，旧的 `#runs` 链接打开 History。这不是 API 破坏：省略 `status` 和 `statuses` 时 `POST /api/v1/tasks/page` 仍列出全部任务，后端的运行 API 仍在。有一个可加的 PostgreSQL 迁移（见升级）。桥接边界不变：早于 v2.13.165 的安装须先升级到 v2.13.165。

**如何验证：**核对版本为 2.15.19。

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.15.18 上的安装可直接升级。升级后照常重启服务。

本版本有一个可加的 PostgreSQL 迁移，启动时执行一次：

- `ledger`：创建 `ledger_items` 和 `ledger_events` 及其索引和约束。只有 DDL，不写账本行。账本打开且有写入之前，两张表保持为空。

### 行为变化与入口

**账本，默认关闭（[#1434](https://github.com/foolzzz/looper/pull/1434)）**

- **`ledger.enabled` 关闭时没有行为变化。**默认没有这一行，取值不是 `true` 也算关闭。提示词、工具列表和 agent 命令行都不提它。`looper ledger` 退出码为 3。`POST /api/v1/ledger/list` 和 `POST /api/v1/ledger/get` 返回 `conflict`。迁移仍会建好两张空表。
- 迁移名是 `ledger`。`ledger_items` 存放等用户处理的事项（`pending`）、已决定的事项（`decision`）和谁来做（`work_item`）。自有条目保留 `status`。有源条目（关卡、任务或 Manager 的确认）没有 `status`，读取来源的状态（`db.ledger.SOURCE_STATUS`；任务经 `task_group`）。`ledger_events` 只增不改。确认或结项通过复合键 `(id, actor_kind)` 指向一条事件，因此即使直接写 SQL 也不能引用 `relayed` 事件。系统只能 `add` 有源条目。
- 唯一写入者是 `db.ledger.apply`，权限表来自完成账本 RFC。拒绝是类型化的：`forbidden`、`conflict`、`invalid`、`not_found`。
- `looper ledger list|show|add|close|confirm` 直接读写数据库，服务停着也能用。写入记为用户、`via=cli`，必须带 `--session`。设置了 `LOOPER_AGENT_RUN` 时拒绝（退出码 4）。本版本还不会在 agent 运行上设置这个变量（更宽的启用路径之前要先做）。退出码：0 完成，1 列表为空，2 用法，3 未启用，4 拒绝，5 没有该条目，6 数据库不可用。
- 两个读取是操作员和 API 客户端的操作，不是 Manager 工具。本版本没有仪表盘开关、HTTP 写入、自动登记和待办页。

**Tasks 页筛选（[#1440](https://github.com/foolzzz/looper/pull/1440)）**

- 状态芯片可以开关。地址里既没有 `status` 也没有 `group`、`schedule` 时，选中的是 Ready、Running、Waiting、Waiting for you 和 Pending（`init`、`running`、`waiting`、`waiting_user`、`pending`）。`#tasks?project=` 仍用这个默认。`status=all` 显示全部任务。`status=failed` 这类书签仍只选那一个筛选。取消最后一个芯片回到 All。
- 没有 `status` 的群或定时任务链接保持不过滤：列出该组或该定时任务的全部任务，包括带 `scheduled=include` 的 `#tasks?group=`。在这些链接上选 All 会省略 `status`。单独的 `scheduled=include` 不关掉默认。
- Waiting for you 计数为 0 时不显示，除非它是唯一选中项。再切换别的芯片时它仍保持选中，但不显示空芯片。计数大于 0 时它会出现并处于选中。
- `POST /api/v1/tasks/page` 接受可选的 `statuses`，1 到 10 个名字，与 `status` 接受的相同，返回它们的并集。`status` 不变。两者同传或未知名字是非法参数。`counts` 仍按每个筛选计数。带 `before` 的翻页用同一个并集。省略 `status` 和 `statuses` 仍返回全部任务。
- Telegram、Lark、CLI 和 Manager 的紧凑任务列表不传 `statuses`。两个字段都省略时仍列出全部任务，这些入口不用改。

**去掉 Runs 页（[#1443](https://github.com/foolzzz/looper/pull/1443)）**

- 仪表盘的 Runs 页、它的路由和侧栏入口已去掉。这不是 API 破坏。后端的运行 API 仍在。History、Chat、任务、CLI 和 `/api/v1/runs` 仍使用它们。
- 旧的 `#runs` 以及 `#runs/` 加角色会转到 History。角色是 manager、planner、worker、reviewer 或 processor 时保留角色筛选（`#history?role=`）。其他角色打开不带角色筛选的 History，并且不请求列表。
- Settings → Roles 的 Its runs 和 Manager 安装说明打开按该角色筛选的 History。
- 打开一条 History 运行时，列出它加载的插件和 skill；`metadata.runtime_catalog.skipped` 非空时在旁边列出。没有跳过项的运行不显示这一节。

**测试（[#1442](https://github.com/foolzzz/looper/pull/1442)）**

- 两个在 CI 负载下会失败的测试不再依赖某一步要花多久。启动自检最多等 10 秒让探测开始，探测睡眠 8 秒。房间测试在 `post` 返回后再读收件箱。生产代码未改动。

### 可选能力启用与使用

#### Ledger

**启用：**默认关闭。没有 `ledger.enabled` 这一行就是关闭，只有取值 `true` 才打开。本版本没有仪表盘开关，也没有 HTTP 写入。把系统设置 `ledger.enabled` 设为 `true`。在此之前 `looper ledger` 退出码为 3，两个读取操作返回 `conflict`。

**验证：**设置为 `true` 后，有条目时 `looper ledger list` 退出码为 0，打开的列表为空时为 1。`POST /api/v1/ledger/list` 和 `POST /api/v1/ledger/get` 返回条目。没有该设置时，命令退出码为 3，两个读取都返回 `conflict`。

**停用 / 回退：**删掉 `ledger.enabled`，或把它设成 `true` 以外的值。命令和读取会再次拒绝。新表是可加的，账本关闭时不被使用。

**权限边界：**写入只经过 `db.ledger.apply`。命令行写入记为用户、经由 `cli`，并且需要 `--session`。设置了 `LOOPER_AGENT_RUN` 时拒绝；本版本不会在 agent 运行上设置这个变量。确认或结项只能指向 `user` 事件。读取给操作员或 API 客户端，不是 Manager 工具。提示词、工具列表和 agent 命令行都不提账本。

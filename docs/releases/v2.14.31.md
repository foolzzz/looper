# Looper v2.14.31

This is the patch release v2.14.31, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.30: the scheduler can now run command schedules and adopt their runs after a server restart ([#944](https://github.com/foolzzz/looper/pull/944)). Nothing creates a command schedule yet, so no existing installation sees a change.

## Release Decision

**Who should upgrade:** Nobody needs this release for its own sake. It is groundwork for command schedules, which cannot be created yet. Anyone tracking the hotfix line can upgrade; tasks, schedules and Agent Profiles run as before.

**What this release solves:** [#944](https://github.com/foolzzz/looper/pull/944) adds `looper/agents/command_runs.py` and wires it into the `Scheduler`, so a schedule of kind `command` fires, is checked for overlap, is settled when it ends and is adopted again after a server restart.

**Breaking changes:** No. No API, default or existing behavior is removed, and there is no database migration; the columns it uses came with the `command_schedules` migration of an earlier release. Agent schedules behave as before.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#944](https://github.com/foolzzz/looper/pull/944); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.31
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.30 upgrades directly. This release adds no migration.

## Behavior changes

- **Command schedules run in the scheduler ([#944](https://github.com/foolzzz/looper/pull/944)).** These apply only to a schedule of kind `command`, which no API creates yet, so an installation has none.
  - **Starting.** The server writes a stdlib runner under `.local/command-runner` in the runtime root and, per run, a directory under `.local/command-runs` with the spec. It starts the runner with `subprocess.Popen` in its own session. The run is recorded as `running` with its log path under `logs/schedules/<schedule id>/`, the run timeout when the schedule uses a seconds timeout, and the runner's pid and start time. A run that cannot be set up (the effective schedule fails to resolve, or the server has no runtime root) is recorded as `failed` with the reason, and a runner that cannot start fails the run with "the runner could not start".
  - **Environment.** The command gets the existing `LOOPER_SCHEDULE_ID`, `LOOPER_SCHEDULE_RUN_ID`, `LOOPER_SCHEDULE_SCHEDULED_FOR` and `LOOPER_SCHEDULE_RUN_TIMEOUT_SECONDS`, plus `LOOPER_SCHEDULE_TRIGGER`, `LOOPER_SCHEDULE_MISSED` and `LOOPER_SCHEDULE_MISSED_SINCE`. The three new variables are also passed to schedule gates, since both use `gate_env`.
  - **Overlap.** A command schedule skips or queues a firing while a previous command run is `running`, with the reasons "the previous command run (<id>) is still in progress" and "a run is already waiting for the previous command run". Its overlap check does not look at task owners. Skipped firings (overlap and catch-up skip) of a command schedule are each recorded as a run of their own; agent schedules still merge repeated skips into the day's latest run. A queued command run starts when the running one settles.
  - **Settling.** On each pass the scheduler reads each run's files and the process table. A recorded exit becomes `succeeded` (exit 0), `failed` (other exit or a signal), `timed_out` or `interrupted` (the runner was killed or failed), with the exit code, signal, log size, truncation flag and the last 4,000 characters of output (NUL characters removed). The error text names the timeout in seconds when one applies. A run finishes only once, and the notifier is told.
  - **Restart adoption.** A run whose runner is still alive after a server restart is adopted and observed again; a run whose identity was lost with the restart is recovered from the runner's own file. A run whose runner is gone without an exit record, or whose directory is missing, is marked `interrupted` and its leftover process group is killed. A run younger than 60 seconds with no runner file yet is left alone.
  - **Fallback timeout.** If a running command passes its timeout plus 90 seconds, the scheduler kills its process group and the runner and records `timed_out`.
  - **Runner output tail.** The runner reads up to four bytes per character plus four times the longest secret value before cutting the 4,000-character tail, so a secret that crosses the cut is still redacted.
  - **Serve start.** If resuming consults, starting the agents, the fleet sweep or carrying on tasks fails during startup, the HTTP server is now stopped before the error is raised.
- **Model-visible changes:** None. No prompt, tool or message text given to a model changes; a command schedule runs a shell command and no model.

**如何验证：**运行 `looper --version` 核对版本为 2.14.31。

### 行为变化与入口

- **命令型定时任务在调度器中运行（[#944](https://github.com/foolzzz/looper/pull/944)）。**以下只适用于 `command` 类型的定时任务；目前没有 API 能创建它，所以现有安装中没有这类任务。
  - **启动。**服务器把一个仅用标准库的 runner 写到运行时根目录的 `.local/command-runner` 下，每次运行在 `.local/command-runs` 下写一个含 spec 的目录，并用 `subprocess.Popen` 在独立会话中启动 runner。运行记录为 `running`，包含 `logs/schedules/<schedule id>/` 下的日志路径、（使用秒级超时时的）运行超时，以及 runner 的 pid 和启动时间。无法准备的运行（有效定时任务解析失败，或服务器没有运行时根目录）记为 `failed` 并写明原因；runner 无法启动时以 “the runner could not start” 使该运行失败。
  - **环境变量。**命令得到已有的 `LOOPER_SCHEDULE_ID`、`LOOPER_SCHEDULE_RUN_ID`、`LOOPER_SCHEDULE_SCHEDULED_FOR`、`LOOPER_SCHEDULE_RUN_TIMEOUT_SECONDS`，以及新增的 `LOOPER_SCHEDULE_TRIGGER`、`LOOPER_SCHEDULE_MISSED`、`LOOPER_SCHEDULE_MISSED_SINCE`。由于 gate 也使用 `gate_env`，这三个新变量同样会传给定时任务的 gate。
  - **重叠。**上一次命令运行仍为 `running` 时，命令型定时任务会跳过或排队新的触发，原因分别为 “the previous command run (<id>) is still in progress” 和 “a run is already waiting for the previous command run”。其重叠检查不看任务归属。命令型定时任务被跳过的触发（重叠和补跑跳过）各自记为独立的一次运行；agent 型定时任务仍把当天重复的跳过合并到最近一次运行。排队的命令运行在运行中的那次结算后启动。
  - **结算。**每轮调度器读取各运行的文件和进程表。记录的退出结果变为 `succeeded`（退出码 0）、`failed`（其他退出码或信号）、`timed_out` 或 `interrupted`（runner 被杀或失败），并记录退出码、信号、日志大小、截断标记和最后 4000 个字符的输出（去掉 NUL 字符）。有超时时，错误文本写明超时秒数。每次运行只结束一次，并通知通知器。
  - **重启接管。**服务重启后 runner 仍存活的运行会被接管并继续观察；重启时丢失身份的运行从 runner 自己的文件恢复。runner 已消失且没有退出记录、或目录缺失的运行记为 `interrupted`，并杀掉残留的进程组。创建不足 60 秒且还没有 runner 文件的运行不处理。
  - **兜底超时。**运行中的命令超过其超时加 90 秒后，调度器杀掉其进程组和 runner，并记为 `timed_out`。
  - **runner 输出尾部。**runner 在截取 4000 字符尾部之前，多读取每字符最多 4 字节，外加最长密钥值长度的 4 倍，因此跨越截取边界的密钥仍会被遮蔽。
  - **服务启动。**启动期间恢复咨询、启动 agent、fleet 清扫或继续任务失败时，现在会先停止 HTTP 服务器再抛出错误。
- **面向模型的变化：**无。给模型的提示词、工具或消息文本都不变；命令型定时任务运行 shell 命令，不经过模型。

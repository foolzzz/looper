# Looper v2.13.56

## Release Decision

**Who should upgrade:** Operators who use the dashboard to stop, cancel, restart or start tasks, or who create tasks from the console or through a Manager. Nobody else needs to act.

**What this release solves:** [#429](https://github.com/foolzzz/looper/pull/429) gives each task operation one implementation that the console and the Manager both call: creating a task, the task list, the task detail, stop, cancel, restart, start over, and adding a supplement. The console now checks a task's state before it acts and answers 409 where it used to publish the message and return silently, and the dashboard shows the error instead of swallowing it.

**Breaking changes:** No. No stored data or configuration changed. One HTTP behavior is stricter: a console stop, cancel or restart of a task in the wrong state now answers an error (409, or 404 for an unknown task and 400 for a task without a directory) where it used to answer success.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#429](https://github.com/foolzzz/looper/pull/429); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.56
```

## Behavior changes

- **One task core (`looper/agents/projects.py`):** the task operations that the console HTTP server (`looper/agents/http_server.py`) and the Manager tools (`looper/agents/ops/tasks.py`) each implemented are now functions of `projects.py`: `create_task_core`, `list_tasks_page`, `task_detail`, `task_gate_view`, `task_workspace_view`, `step_workspaces_view`, `check_task_control` and `control_task`, `add_task_supplement`, `start_ready_task`, and the task configuration block shown after a Manager creates a task. The two sides are now thin adapters over them. About 520 lines were added to `projects.py` and about 520 removed from the two adapters.
- **Task creation (`create_task_core`):** the Manager's `looper_task_create` passes its fields through the same core as the console, so a new project, the task's workspace, Agent Profile overrides and template roles are stored by one path. The Manager keeps its extra step: the Manager's row is locked first, so a Manager turned off or deleted refuses the task with 409 ("the task was not created"). A name that is taken answers 409 (`ProjectNameTaken`), and an Agent Profile removed meanwhile answers 400, on both sides.
- **State checks on stop, cancel and restart (console):** `POST` stop and cancel, and restart and start over, now go through `control_task`. Stop and cancel need a running task; restart and start over need a stopped, failed or cancelled task with a work directory. A task in another state answers 409, an unknown task 404, a task without a directory 400. Before, the console published the message to the task router without checking, so the request looked successful and nothing happened. The legacy start endpoint still starts a ready task (a ready task without a directory answers 400).
- **Dashboard shows the error (`web/src/lib/api.ts`, `web/src/pages/tasks.tsx`, `web/src/pages/task-detail.tsx`):** Stop and Cancel failures now carry the server's message (the same helper the other actions use). The Tasks page shows it in an alert instead of ignoring it, and the task page shows stop failures in the same place as start failures.
- **Task list and detail:** the console list and detail endpoints and the Manager's `looper_tasks` read tasks through `list_tasks_page` and `task_detail` (the Manager asks for the compact form). The console answers `before` that is not a task id with the same 400 message as before. The console detail answers 404 "task not found" for an unknown task as before.
- **Supplements:** a message to a task's Planner in chat, and the Manager's task supplement, both store the supplement and then wake the Planner through `add_task_supplement`. The chat path remains best-effort: a message to a Planner is delivered even when it cannot be stored.
- **Docs and tests:** the client-skill RFC (section 5.4) and the long-horizon context plan are updated. New tests cover task creation (`tests/test_task_create_core_db.py`), the list (`tests/test_task_list_db.py`), the shared operations (`tests/test_task_operations_shared_db.py`) and the detail (`tests/test_task_detail_db.py`). The pull request reports added lines: tests 325, production 675 (fixtures excluded).
- **Model-visible changes:** None intended. The Manager's tool arguments, results and OpenAPI operations are meant to be unchanged: the pull request's own review rule treats a Manager tool result that changes beyond the 409 path as a defect, and the Manager adapters still map the core's errors to the same error codes and messages (for example the not-found message that names `looper_tasks`). The only behavior change on the Manager side is that its checks now run through the shared `control_task`.

## Upgrade and rollback

Re-run `install.sh` once v2.13.56 is published. The dashboard is rebuilt with the wheel. No data migration. Rolling back to v2.13.55 restores the earlier per-side implementations and the silent console stop, cancel and restart; nothing is stored differently.

## 中文摘要

### 升级决策

**谁需要升级：**在控制台停止、取消、重启或启动任务，或通过控制台、管家创建任务的运维者。其他人无需操作。

**解决了什么：**[#429](https://github.com/foolzzz/looper/pull/429) 让控制台和管家共用同一套任务操作实现：创建任务、任务列表、任务详情、停止、取消、重启、从头开始和追加补充。控制台现在先检查任务状态，状态不对时返回 409，而不是发出消息后静默返回；看板也会显示错误而不是吞掉。

**是否有破坏性变更：**无。存储数据和配置均未改动。一处 HTTP 行为更严格：控制台对状态不符的任务执行停止、取消或重启，现在返回错误（409；任务不存在为 404，任务没有目录为 400），此前返回成功。

**如何验证：**运行 `looper --version` 核对版本为 2.13.56。

**贡献者：**维护者 @foolzzz 提交 [#429](https://github.com/foolzzz/looper/pull/429)；本次 patch release 无社区贡献。

```bash
looper --version   # looper 2.13.56
```

### 行为变化与入口

- 统一的任务核心（`looper/agents/projects.py`）：控制台 HTTP 服务（`http_server.py`）和管家工具（`ops/tasks.py`）原先各自实现的任务操作，现在是 `projects.py` 中的函数：`create_task_core`、`list_tasks_page`、`task_detail`、`task_gate_view`、`task_workspace_view`、`step_workspaces_view`、`check_task_control` 与 `control_task`、`add_task_supplement`、`start_ready_task`，以及管家创建任务后展示的配置块。两侧现在只是薄适配层。`projects.py` 新增约 520 行，两个适配层减少约 520 行。
- 创建任务（`create_task_core`）：管家的 `looper_task_create` 与控制台走同一个核心，新项目、任务工作区、Agent Profile 覆盖和模板角色由同一条路径存储。管家保留额外一步：先锁定管家记录，因此已关闭或已删除的管家会以 409 拒绝（"任务未创建"）。名称已被占用返回 409（`ProjectNameTaken`），期间被删除的 Agent Profile 返回 400，两侧一致。
- 停止、取消、重启的状态检查（控制台）：停止和取消，以及重启和从头开始，现在都经过 `control_task`。停止和取消要求任务在运行；重启和从头开始要求任务已停止、失败或取消且有工作目录。状态不符返回 409，任务不存在 404，没有目录 400。此前控制台不检查就向任务路由器发消息，请求看似成功而实际什么都没发生。旧的 start 端点仍可启动 ready 任务（没有目录返回 400）。
- 看板显示错误（`web/src/lib/api.ts`、`tasks.tsx`、`task-detail.tsx`）：Stop 与 Cancel 失败现在带上服务器的消息；Tasks 页用提示框显示，而不是忽略；任务页把停止失败与启动失败显示在同一处。
- 任务列表与详情：控制台的列表、详情端点和管家的 `looper_tasks` 通过 `list_tasks_page` 与 `task_detail` 读取（管家要求紧凑形式）。`before` 不是任务 id 时仍返回同样的 400 消息；未知任务的详情仍返回 404 "task not found"。
- 补充：聊天里发给任务 Planner 的消息和管家的任务补充，现在都通过 `add_task_supplement` 先存储再唤醒 Planner。聊天路径保持尽力而为：即使无法存储，发给 Planner 的消息仍会送达。
- 文档与测试：更新客户端技能 RFC（5.4 节）和长程上下文计划。新增测试覆盖任务创建、列表、共享操作和详情。PR 报告新增测试 325 行、生产代码 675 行（不含 fixture）。
- 面向模型的变化：无（设计上）。管家工具的参数、结果和 OpenAPI 操作应保持不变：该 PR 自己的评审规则把管家工具结果在 409 路径之外的变化视为缺陷，管家适配层仍把核心错误映射为相同的错误码和消息（例如指向 `looper_tasks` 的未找到提示）。管家侧唯一的行为变化是其检查现在经过共享的 `control_task`。

### 升级与回退

v2.13.56 发布后重跑 `install.sh`，看板随 wheel 重新构建，无需迁移数据。回退到 v2.13.55 会恢复两侧各自的实现以及控制台的静默停止、取消和重启；存储无差异。

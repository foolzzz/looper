# Looper v2.14.121

This is the patch release v2.14.121, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.120: the private verification checkout gets the runtime state it needs, and its write guard can no longer be bypassed ([#1189](https://github.com/foolzzz/looper/pull/1189)).

## Release Decision

**Who should upgrade:** Operators who run workflows with a verification role (the workflow verification guard of issue #1187), especially when a verification run needs ignored local state such as env files or a linked virtualenv. Installations and tasks without a workflow verification role see no change in behavior, apart from the additive database column described below.

**What this release solves:** [#1189](https://github.com/foolzzz/looper/pull/1189). The private checkout of a workflow verification run now receives read-only copies of the ignored runtime files the project declares, so a staging check can run; the guard records writes to tracked sources while the verifier runs, so changing a file and restoring it is still detected; and the seed manifest no longer points at the developer repository.

**Breaking changes:** No. The database change is additive (see Upgrading), and tasks without a workflow verification role are unchanged.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.14.121
```

**Contributors:** Maintainer @foolzzz authored [#1189](https://github.com/foolzzz/looper/pull/1189); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.120 upgrades directly. The schema change is additive: once, `ensure_schema` adds the nullable `projects.verification_paths` column (a text array of at most 20 entries) and records the `verification_paths` migration. Until then it is a pending schema change. Existing projects get NULL, which declares no extra paths.

## Behavior changes

- **Runtime files in the verification checkout.** Only for a workflow verification run in a Git working directory. The private checkout is seeded as before and then receives read-only copies of the paths named by the project's `workspace_links` and the new `verification_paths`. Copies are made read-only; links to regular files are dereferenced (for example a virtualenv's interpreter), links back into a repository worktree are relocated to the private checkout, and a copied virtualenv has its entry points and editable-install paths rewritten and its `.pyc` caches removed. The copy fails, and the run does not start, for a path that is absolute, contains `..` or `.git`, is missing, would replace repository files, crosses its declared tree or contains repository metadata. The run records the activity line "Verification runtime inputs copied read-only: <paths>".
- **New project field `verification_paths`.** Extra ignored paths, relative to the verification source directory, at most 20, validated like `workspace_links`. It is available in the project API and in task creation for a new project (and its impact summary), and the dashboard project page has an "Extra files for verification" box. NULL, the default, adds nothing.
- **Write guard.** Besides the start and end snapshot, the kernel reports writes to the tracked sources of the private checkout (inotify on Linux, kqueue on macOS), so a change that is restored to the original bytes is still recorded in `verification.written_paths` and fails the verification with "file writes recorded during verification". The monitor is drained only after the verifier and its child processes have ended; a successful verifier's remaining children are now ended too. If monitoring cannot start or fails, or the notification queue overflows, the result fails closed: the agent is not started ("Verification write monitoring unavailable") or the result is rejected, and that failure is not retried through a profile fallback.
- **Seed manifest.** The verification baseline manifest stores the working directory's path relative to the repository root instead of the repository's absolute path, and links in the seed copy point into the private checkout, so the seed no longer refers to the developer repository.
- **Verification runs are not kept.** A verification run is not handed to the run keeper, and a verification run cannot be re-attached after a control-plane restart (the attach fails with a protocol error).
- **Unchanged:** tasks without a workflow verification role, the review panel and verification rules apart from the stricter guard, and the channel commands.
- **Model-visible changes:** Small. The verifier now sees the declared runtime files in its working directory (read-only), and a verification that wrote to tracked files, or whose monitoring failed, fails with the new messages and the Planner and Manager read them in the step result. The Planner, Worker and Reviewer prompts and contracts are unchanged.

### 升级决策

**谁需要升级：**运行带验证角色的工作流（issue #1187 的工作流验证守卫）的运维者，尤其是验证需要 env 文件或链接的虚拟环境等被忽略的本地状态时。没有工作流验证角色的安装和任务行为无变化，仅增加下述向后兼容的数据库列。

**解决了什么：**[#1189](https://github.com/foolzzz/looper/pull/1189)。工作流验证运行的私有 checkout 现在获得项目声明的被忽略运行时文件的只读副本，使 staging 检查可以运行；守卫在验证运行期间记录对受跟踪源文件的写入，因此修改后再还原仍会被发现；种子清单不再指向开发者仓库。

**是否有破坏性变更：**否。数据库变更为增量式（见升级一节），没有工作流验证角色的任务不变。

**如何验证：**核对版本为 2.14.121。

**贡献者：**维护者 @foolzzz 提交 [#1189](https://github.com/foolzzz/looper/pull/1189)；本版本无社区贡献。

```bash
looper --version   # looper 2.14.121
```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.120 上的安装可直接升级。数据库变更为增量式：`ensure_schema` 一次性添加可空的 `projects.verification_paths` 列（文本数组，最多 20 项）并记录 `verification_paths` 迁移，在此之前它属于待执行的结构变更。现有项目该列为 NULL，即不声明额外路径。

### 行为变化与入口

- **验证 checkout 中的运行时文件。**仅对 Git 工作目录中的工作流验证运行生效。私有 checkout 照常播种，然后获得项目 `workspace_links` 与新增 `verification_paths` 所列路径的只读副本。副本为只读；指向普通文件的链接被解引用（例如虚拟环境的解释器），指回仓库 worktree 的链接被重定向到私有 checkout，复制的虚拟环境会改写入口脚本和 editable 安装路径并删除 `.pyc` 缓存。路径为绝对路径、含 `..` 或 `.git`、不存在、会覆盖仓库文件、越出其声明的目录树或包含仓库元数据时，复制失败，运行不会启动。运行会记录活动行“Verification runtime inputs copied read-only: <paths>”。
- **新增项目字段 `verification_paths`。**相对验证源目录的额外被忽略路径，最多 20 项，校验方式与 `workspace_links` 相同。可用于项目 API 和新项目的任务创建（含影响摘要），仪表盘项目页新增“Extra files for verification”输入框。默认 NULL，不增加任何路径。
- **写入守卫。**除起止快照外，内核会报告对私有 checkout 受跟踪源文件的写入（Linux 用 inotify，macOS 用 kqueue），因此修改后还原为原字节的变更仍会记录在 `verification.written_paths` 并以“file writes recorded during verification”使验证失败。监视器只在验证者及其子进程结束后才读取；验证成功的运行遗留的子进程现在也会被结束。监视无法启动、失败或通知队列溢出时失败即关闭：不启动代理（“Verification write monitoring unavailable”）或拒绝结果，且该失败不会经 profile 回落重试。
- **种子清单。**验证基线清单保存工作目录相对仓库根的路径，而不是仓库的绝对路径，种子副本中的链接指向私有 checkout，因此种子不再引用开发者仓库。
- **验证运行不被保留。**验证运行不交给运行保持器，控制面重启后也无法重新接管验证运行（接管以协议错误失败）。
- **不变：**没有工作流验证角色的任务、除更严格守卫之外的评审小组与验证规则，以及渠道命令。
- **面向模型的变化：**较小。验证者现在能在工作目录中看到声明的运行时文件（只读）；写入了受跟踪文件或监视失败的验证会以新的消息失败，Planner 和 Manager 会在步骤结果中读到。Planner、Worker 和 Reviewer 的提示词与契约不变。

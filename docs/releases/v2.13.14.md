# Looper v2.13.14

## Release Decision

**Who should upgrade:** Operators who open tasks with long histories or watch running tasks in the dashboard, and anyone who calls the task activity or conversation API directly. Everyone else sees no change.

**What this release solves:** [#324](https://github.com/foolzzz/looper/pull/324) keeps the task page responsive on long and running tasks. The Sessions tab showed the oldest 500 events and replayed the whole history on every refresh. It now shows the latest 1000 messages and loads older ones as you scroll up; the Conversation tab does the same, the runs are read in one compact request, and the page polls without overlap and pauses in a hidden tab.

**Breaking changes:** Yes, for direct callers of two read-only API routes only. The CLI, configuration, database schema and dashboard are unchanged. The default response changed shape (see Behavior changes): the task activity route and the task conversation route return the latest 1000 rows with extra fields, not the oldest rows or the whole history. Callers that relied on the old default must page with `before`. Both routes are unchanged from [v2.13.13](https://github.com/foolzzz/looper/blob/main/docs/releases/v2.13.13.md) when `since` or `after` is given, except for the 400 on a non-integer value.

**How to verify:** Check the installed version, then open a task with a long history and scroll the Sessions tab up.

**Contributors:** Maintainer @foolzzz authored [#324](https://github.com/foolzzz/looper/pull/324); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.14
```

## Behavior changes

- **Activity API.** `GET /api/tasks/<id>/activity` without `since` or `after` returns the latest `limit` rows (default and maximum 1000, minimum 1), oldest first, as summaries, with `has_more` (older rows exist), `oldest_seq` and `latest_seq`. `before=<seq>` returns the rows just before that seq. With `since` or `after` it reads forward as before, at most 500 rows per call. A non-integer `since`, `after`, `before` or `limit` answers 400.
- **Conversation API.** `GET /api/tasks/<id>/conversation` takes `before` and `limit` the same way and returns the latest 1000 text, phase, error and user-message rows with `has_more`, `oldest_seq` and `latest_seq`. Previously it returned the whole conversation.
- **Runs API.** New `GET /api/tasks/<id>/runs` returns the task's Planner, Worker and Reviewer runs, oldest first, as compact rows: `id`, `role`, `agent_id`, `step_id`, `status`, `created_at`, `runtime`, `model`, `effort` and `profile`. It carries no prompts, metadata body or events. The task page used three `llm-records` requests of up to 500 runs each; it now makes this one request, so the Agents tab no longer carries the "latest 500 runs" notice.
- **Sessions and Conversation tabs.** Both open on the latest 1000 messages and load the page before the oldest loaded one when the scroll comes within a short distance of the top, keeping the reading place. The view follows new events only while it is at the bottom. The live stream starts after the latest loaded event.
- **Polling.** The task page (every 2 seconds) and the Room poll one request at a time, wait while the browser tab is hidden, run again when it is visible, and abort the request in flight when they stop.
- **Model-visible changes:** None. No prompt, tool schema or tool contract changed; the change is in the dashboard and in two read-only HTTP routes plus one new one.

## Entry points

- `GET /api/tasks/<id>/activity?before=<seq>&limit=<n>`, `GET /api/tasks/<id>/conversation?before=<seq>&limit=<n>` and `GET /api/tasks/<id>/runs`. No CLI command or configuration key was added.

## Upgrade and rollback

Re-run `install.sh` once v2.13.14 is published. There is no schema or configuration change. Rolling back to v2.13.13 is safe; the task page then reads the oldest 500 events and the full conversation again.

## 中文摘要

### 升级决策

**谁需要升级：**会打开历史很长的任务、在 dashboard 观察运行中任务，或直接调用任务 activity、conversation API 的运营者。其他人没有变化。

**解决了什么：**[#324](https://github.com/foolzzz/looper/pull/324) 让任务页在长任务和运行中任务上保持流畅。此前 Sessions 标签只显示最早的 500 条事件，且每次刷新都重放全部历史。现在显示最新 1000 条消息，向上滚动加载更早的；Conversation 标签同样处理，runs 用一次精简请求读取，页面轮询不再重叠，标签页隐藏时暂停。

**是否有破坏性变更：**有，仅针对直接调用两个只读 API 路由的调用方；CLI、配置、数据库 schema 和 dashboard 不变。默认响应有变化（见下）：任务 activity 路由和 conversation 路由默认返回最新 1000 行并带额外字段，而不是最早的行或全部历史；依赖旧默认行为的调用方需用 `before` 翻页。给出 `since` 或 `after` 时与 [v2.13.13](https://github.com/foolzzz/looper/blob/main/docs/releases/v2.13.13.md) 相同，仅非整数值会返回 400。

**如何验证：**运行 `looper --version` 核对版本为 2.13.14；打开一个历史很长的任务，向上滚动 Sessions 标签。

**贡献者：**维护者 @foolzzz 提交 [#324](https://github.com/foolzzz/looper/pull/324)；本次 patch release 无社区贡献。

```bash
looper --version   # looper 2.13.14
```

### 行为变化与入口

- Activity API：不带 `since`、`after` 时返回最新 `limit` 行（默认且最大 1000，最小 1），按时间正序，仅摘要，附 `has_more`、`oldest_seq`、`latest_seq`；`before=<seq>` 返回该 seq 之前的行。带 `since` 或 `after` 时仍向前读取，每次最多 500 行。`since`、`after`、`before`、`limit` 非整数时返回 400。
- Conversation API：`GET /api/tasks/<id>/conversation` 同样支持 `before`、`limit`，返回最新 1000 条 text、phase、error、user_message 行及 `has_more`、`oldest_seq`、`latest_seq`；此前返回全部对话。
- Runs API：新增 `GET /api/tasks/<id>/runs`，按时间正序返回任务的 Planner、Worker、Reviewer 精简行（`id`、`role`、`agent_id`、`step_id`、`status`、`created_at`、`runtime`、`model`、`effort`、`profile`），不含提示词、metadata 正文和事件。任务页原先发三个各最多 500 条的 `llm-records` 请求，现在只发这一个，Agents 标签不再显示“仅列出最新 500 条”的提示。
- Sessions 与 Conversation 标签：打开时显示最新 1000 条，滚动接近顶部时加载最早已加载消息之前的一页并保持阅读位置；只有停在底部时才跟随新事件；实时流从最新已加载事件之后开始。
- 轮询：任务页（每 2 秒）和 Room 一次只发一个请求，浏览器标签页隐藏时等待，可见后继续，停止时中止在途请求。
- 面向模型的变化：无。提示词、工具 schema、工具契约都没有变化；变化只在 dashboard 和两个只读 HTTP 路由，另有一个新增路由。未新增 CLI 命令或配置项。

### 升级与回退

发布后重跑 `install.sh`。无 schema 或配置变更。回退到 v2.13.13 安全，任务页将重新读取最早 500 条事件和完整对话。

### 可选能力启用与使用

本版本未新增可选能力启用入口。

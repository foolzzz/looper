# Looper v2.13.200

## Release Decision

**Who should upgrade:** Operators who run Workers on the Pi runner (`[runtimes] pi = "runner"` in the ops file) and rely on the budget accounting of its model requests. Everyone else sees no difference: with the default `pi = "cli"` Workers keep their own processes. It is a hotfix that ships the change merged since v2.13.199.

**What this release solves:** [#832](https://github.com/foolzzz/looper/pull/832) fixes issue #821. In the Pi runner, a budget `allow` that arrives after the turn was cancelled now still produces one `request_end` (aborted, nothing sent, complete zero usage) before the turn settles. A request that was sent but failed before response headers now reports `complete=false` instead of complete zero usage, so a request is no longer lost or under-counted.

**Breaking changes:** No. No command, database schema or setting changed.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#832](https://github.com/foolzzz/looper/pull/832); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.200
```

## Behavior changes

- **Pending authorisation (`runners/pi/src/provider.ts`, `authorizingStream`):** the `budget/authorize` call is no longer abandoned when the request is aborted, because the host may already have reserved budget. The pending call is recorded on the turn (`authorizations`, `runners/pi/src/turn.ts`). `cancelTurn` waits for pending authorisations after it aborts the agent, and `settle` waits for them before it drops steers and drains in-flight requests.
- **Late `allow` after cancel:** if the reply is `allow` but the turn is cancelled or settling, or the signal is aborted, the request is registered and ended at once as `aborted` with `complete=true` and no usage, and the stream fails with "request aborted". A denial that arrives after a cancel is treated as an abort, not recorded as a budget denial.
- **Usage completeness:** only validated terminal counts make a request's usage complete. For `openai-responses` these come from `response.completed`, `response.incomplete` or `response.failed`; for chat APIs from the final choice (one with a `finish_reason`) or its trailing usage chunk. Counts that are not safe non-negative integers, cache or reasoning counts above their totals, or a `total_tokens` that differs from input plus output are ignored. Valid counts replace the message usage that is reported.
- **Failures before headers:** the request is marked dispatched once fetch starts. Only connection failures that precede any HTTP request (`ECONNREFUSED`, `ENOTFOUND`, `EAI_AGAIN`, connect timeout, certificate validation failures, a plaintext reply to a TLS handshake) clear it. A failed request is reported complete only if validated usage arrived, it was never dispatched, or it got an HTTP status of 400 or more before any output. A socket that closes before headers therefore reports `complete=false`. A completed request without validated usage also reports `complete=false`, where the old code only checked that some usage field was present.
- **Scope:** 4 files, 490 added lines in all: `provider.ts` 80 and `turn.ts` 4 (production), `tests/test_pi_runner_turns.py` 402 and `tests/fake_model_api.py` 4 (a `disconnect_before_headers` script option). The description reports "tests 89, production 0 (fixtures excluded)", which does not match the diff, and its stated target of about 150 changed lines was exceeded.
- **Model-visible changes:** None. No prompt, tool or message the model sees changed. The accounting frames go to Looper, not to the model. A request denied or aborted after a cancel still fails the Pi turn as before.

Re-run `install.sh` once v2.13.200 is published. There is nothing to configure. To roll back, return to v2.13.199; there is no schema or setting change.

**解决了什么：**[#832](https://github.com/foolzzz/looper/pull/832) 修复 issue #821。Pi runner 中，回合被取消后才到达的预算 `allow` 现在仍会在回合结算前产生一条 `request_end`（已中止、未发送、用量完整为零）。已发送但在响应头之前失败的请求现在报告 `complete=false`，而不是用量完整为零，因此请求不会再丢失或少计。

**是否有破坏性变更：**无。命令、数据库 schema 和设置均未改变。

**如何验证：**运行 `looper --version` 核对版本为 2.13.200。

**贡献者：**维护者 @foolzzz 提交 [#832](https://github.com/foolzzz/looper/pull/832)；本次 patch release 无社区贡献。

```bash
looper --version   # looper 2.13.200
```

### 行为变化与入口

- **待决授权（`runners/pi/src/provider.ts`，`authorizingStream`）：**请求被中止时不再放弃 `budget/authorize` 调用，因为主机可能已预留预算。待决调用记录在回合上（`authorizations`，`runners/pi/src/turn.ts`）。`cancelTurn` 在中止 agent 后等待待决授权，`settle` 在丢弃 steer 和排空进行中请求之前等待它们。
- **取消后到达的 `allow`：**若回复为 `allow` 但回合已取消或正在结算，或信号已中止，该请求会立即登记并以 `aborted`、`complete=true`、无用量结束，流以 "request aborted" 失败。取消后到达的拒绝按中止处理，不记为预算拒绝。
- **用量完整性：**只有经过校验的终态计数才使请求用量完整。`openai-responses` 取自 `response.completed`、`response.incomplete` 或 `response.failed`；chat 类 API 取自最后一个带 `finish_reason` 的 choice 或其后的用量块。非安全非负整数、缓存或推理计数超过总数、`total_tokens` 与输入加输出不符的计数一律忽略。有效计数会替换所报告的消息用量。
- **响应头之前的失败：**fetch 开始即标记为已发出。只有在任何 HTTP 请求之前就失败的连接错误（`ECONNREFUSED`、`ENOTFOUND`、`EAI_AGAIN`、连接超时、证书校验失败、对 TLS 握手回以明文）才会清除该标记。失败的请求仅在以下情形报告完整：收到经校验的用量、从未发出，或在任何输出之前收到 400 及以上的 HTTP 状态。因此响应头之前套接字关闭会报告 `complete=false`。没有经校验用量的已完成请求也报告 `complete=false`，旧代码只检查是否出现过某个用量字段。
- **范围：**4 个文件，共新增 490 行：`provider.ts` 80 行与 `turn.ts` 4 行（生产代码），`tests/test_pi_runner_turns.py` 402 行与 `tests/fake_model_api.py` 4 行（新增 `disconnect_before_headers` 脚本选项）。描述写的是“测试 89 行、生产代码 0 行（不含 fixtures）”，与差异不符，且超出其约 150 行的目标。
- **面向模型的变化：**无。模型看到的提示词、工具和消息均未改变。核算帧发给 Looper，不发给模型。取消后被拒绝或中止的请求仍照旧使 Pi 回合失败。

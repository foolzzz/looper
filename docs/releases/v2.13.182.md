# Looper v2.13.182

## Release Decision

**Who should upgrade:** Operators whose Manager changes schedules through chat, especially those who raise a schedule's spend cap and change its template in the same update. It is a hotfix that ships the changes merged since v2.13.181.

**What this release solves:** [#800](https://github.com/foolzzz/looper/pull/800) makes the confirmation that a Manager schedule update asks for show every template change (`template_key`, `template_inputs`) that the update commits together with a spend cap, and validates that template selection before asking. It also makes the reply after a scoped Manager's update report real changes against the stored schedule.

**Breaking changes:** No. No command, schema or file format changed.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#800](https://github.com/foolzzz/looper/pull/800); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.182
```

## Behavior changes

- **Cap-raising schedule updates confirm the whole change ([#800](https://github.com/foolzzz/looper/pull/800)):** in `looper/agents/ops/schedules.py`, `_confirming` previously built the "after" view from the schedule plus only the spend-cap fields, so a template change sent in the same update was committed on confirmation without being shown. It now merges the selection (`merge_selection`), resolves the effective template (`effective_schedule`) and builds the "after" view from the whole update (`schedules.schedule_view`), then lists every difference with `_changes`. The confirmation therefore shows the template name and static-input changes, including a cleared template, next to the cap change.
- **Invalid template combinations are refused before asking:** a template selection that the update would reject (an unknown template, inputs that are not static strings or not http/https, an unknown key, a missing directory) now returns `invalid` or `conflict` from the confirming step, with the schedule unchanged, instead of asking and failing on confirmation.
- **Reply after an update:** `_update` now compares the stored schedule before and after the update without the scope filter (`_in_scope`). A scoped Manager that tries to change another owner's template selection is still refused with `forbidden` before anything is written (`_refuse_other_owner_template`, unchanged); the removed filter no longer masks a real change as "没有变化".
- **Tests:** `tests/test_manager_schedule_template_contract_db.py` adds cap-raise confirmation cases (inputs, replacement, clear, cap-only) and runs the invalid-input and other-owner cases through both the immediate and the confirmation path.
- **Model-visible changes:** the confirmation text that a Manager shows the user now includes template lines (`任务模板：…`, `模板静态输入：…`) when the update changes them, and the invalid-combination errors now surface at the confirming step. No prompts, tool schemas or tool descriptions changed.

**解决了什么：**[#800](https://github.com/foolzzz/looper/pull/800) 让 Manager 更新定时任务时要求的确认信息，展示随花费上限一并提交的全部模板变更（`template_key`、`template_inputs`），并在询问之前校验该模板选择。同时让受限 Manager 更新后的回复对照已存储的定时任务报告真实变化。

**是否有破坏性变更：**无。命令、schema 和文件格式均未改变。

### 行为变化与入口

- **提高上限的更新会确认完整变更（#800）：**`looper/agents/ops/schedules.py` 中 `_confirming` 以前只用原定时任务加花费上限字段构造“修改后”视图，同一次更新里的模板变更会在确认后被提交却未展示。现在它合并选择（`merge_selection`）、解析实际模板（`effective_schedule`），用整个更新构造“修改后”视图（`schedules.schedule_view`），再用 `_changes` 列出所有差异。确认信息因此在上限变化旁展示模板名称和静态输入的变化，包括清除模板。
- **无效的模板组合在询问前即被拒绝：**更新会拒绝的模板选择（未知模板、输入不是静态字符串或不是 http/https、未知键、缺少目录）现在在确认步骤返回 `invalid` 或 `conflict`，定时任务保持不变，而不是先询问、确认时才失败。
- **更新后的回复：**`_update` 现在不经范围过滤（`_in_scope`）比较更新前后的已存储定时任务。受限 Manager 试图修改其他所有者的模板选择时，仍在写入之前以 `forbidden` 被拒绝（`_refuse_other_owner_template`，未改动）；移除的过滤不再把真实变化掩盖成“没有变化”。
- **测试：**`tests/test_manager_schedule_template_contract_db.py` 新增提高上限的确认用例（输入、替换、清除、仅上限），并让无效输入与其他所有者用例同时走立即路径和确认路径。
- **面向模型的变化：**Manager 展示给用户的确认文本在更新改变模板时新增模板行（`任务模板：…`、`模板静态输入：…`），无效组合的错误在确认步骤出现。提示词、工具 schema 和工具描述均无变化。

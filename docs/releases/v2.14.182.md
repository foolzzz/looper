# Looper v2.14.182

This is the patch release v2.14.182, a hotfix line in which each merged change ships at once. It documents one change: [#1342](https://github.com/foolzzz/looper/pull/1342) (a timed-out control-plane lease health check is uncertain and rechecked before the server gives up the lock).

## Release Decision

**Who should upgrade:** Operators who run `looper serve` on a machine or database that is sometimes slow or overloaded, where one slow health query used to make the server exit with code 75.

**What this release solves:** [#1342](https://github.com/foolzzz/looper/pull/1342) stops a single timed-out lease health query from being treated as a lost lock. The server now fences new agent spawns, rechecks for up to 30 seconds, and exits only when the lock is really gone.

**Breaking changes:** No. API responses, the Telegram and Lark channel protocols, the dashboard and the CLI are unchanged, and there is no database change. The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.14.182
```

**Contributors:** Maintainer @foolzzz authored [#1342](https://github.com/foolzzz/looper/pull/1342); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.181 upgrades directly. There is no database change.

## Behavior changes

Read in the diff of [#1342](https://github.com/foolzzz/looper/pull/1342) (`looper/agents/control_plane.py`, `looper/agents/loop_watch.py`, `looper/agents/proc_tree.py`, `looper/agents/serve.py`, `docs/architecture/agent-system.md` and tests). The PR description calls this a maintainer-decided, intended behavior change.

- **Lease health check** (`looper/agents/control_plane.py`). The lease has a new `uncertain` state. A health query that raises `TimeoutError` after 5 seconds, or that overlaps a stall the watchdog recorded, moves the lease from held to uncertain instead of losing it. While uncertain, the lease rechecks at once with a 15-second query timeout until a 30-second window ends. A clean reply that the lock is held returns the lease to held and lifts the spawn fence (log line "control plane lock confirmed held; resumed agent spawns"). The lock is lost, and the server takes the existing exit path with code 75, when the reply says the lock is gone, the connection is closed or fails with a connection error, a non-timeout error occurs without an overlapping stall, or the window runs out. Held-false and connection loss still lose at once, as before.
- **Spawn fence** (`looper/agents/proc_tree.py`). `set_lease_uncertain` sets a temporary fence that is separate from the terminal one. `spawns_fenced()` is true for either, and `spawn` raises `RuntimeError("the control plane lock is uncertain; no new agents")` while uncertain. The HTTP listener stays open and running agents are not touched.
- **Stall tracking** (`looper/agents/loop_watch.py`, `looper/agents/serve.py`). `LoopWatch` keeps the last 128 stall intervals and gains `stall_seconds_between`, which reports the largest stall overlapping a query. `serve` passes its `LoopWatch` to `ControlPlaneLease.acquire`. This is how a query slowed by a stalled process counts as uncertain rather than as a database fault.
- **Docs** (`docs/architecture/agent-system.md`). The control-plane lease section describes the uncertain state; the old "within 10 seconds" wording is removed.
- **Tests** (`tests/test_control_plane.py`, `tests/test_control_plane_lock_db.py`, `tests/test_loop_watch.py`). They cover the timeout, recheck and loss paths, a lock-database case and the stall interval query.
- **Model-visible changes:** No. No prompt, tool description or tool schema changed, and no HTTP API result changed. While the lease is uncertain, a new agent start fails with the `RuntimeError` above; I did not trace how each caller reports that error.

### 行为变化与入口

以下在 [#1342](https://github.com/foolzzz/looper/pull/1342) 的差异中可见（`looper/agents/control_plane.py`、`looper/agents/loop_watch.py`、`looper/agents/proc_tree.py`、`looper/agents/serve.py`、`docs/architecture/agent-system.md` 及测试）。PR 描述称这是维护者决定的、有意的行为变化。

- **租约健康检查**（`looper/agents/control_plane.py`）。租约新增 `uncertain` 状态。健康查询在 5 秒后抛出 `TimeoutError`，或与看门狗记录的停顿重叠时，租约由 held 转为 uncertain，而不是直接丢失。处于 uncertain 时立即复查，单次查询超时 15 秒，复查窗口共 30 秒。收到“锁仍持有”的明确回复后恢复 held 并解除启动禁止（日志“control plane lock confirmed held; resumed agent spawns”）。以下情况视为锁丢失，服务走原有的退出路径（退出码 75）：回复锁已不存在、连接已关闭或出现连接错误、出现与停顿无关的非超时错误、窗口耗尽。held 为 false 和连接丢失仍然立即判定丢失，与之前一致。
- **启动禁止**（`looper/agents/proc_tree.py`）。`set_lease_uncertain` 设置与终态禁止分开的临时禁止。`spawns_fenced()` 在任一状态下为真，不确定期间 `spawn` 抛出 `RuntimeError("the control plane lock is uncertain; no new agents")`。HTTP 监听保持开启，运行中的 agent 不受影响。
- **停顿跟踪**（`looper/agents/loop_watch.py`、`looper/agents/serve.py`）。`LoopWatch` 保留最近 128 个停顿区间，并新增 `stall_seconds_between`，返回与某次查询重叠的最大停顿。`serve` 把其 `LoopWatch` 传给 `ControlPlaneLease.acquire`。这样，被进程停顿拖慢的查询会被视为不确定，而不是数据库故障。
- **文档**（`docs/architecture/agent-system.md`）。控制平面租约一节描述了 uncertain 状态，并移除了“10 秒内”的旧说法。
- **测试**（`tests/test_control_plane.py`、`tests/test_control_plane_lock_db.py`、`tests/test_loop_watch.py`）。覆盖超时、复查与丢失路径、锁数据库场景以及停顿区间查询。
- **面向模型的变化：**无。提示词、工具描述和工具 schema 均未改变，也没有 HTTP API 结果改变。租约不确定期间，新的 agent 启动会以上述 `RuntimeError` 失败；各调用方如何上报该错误，我没有逐一追踪。

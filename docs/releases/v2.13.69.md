# Looper v2.13.69

## Release Decision

**Who should upgrade:** Dashboard users and anyone scripting the overview, task control, task rename or task requirement HTTP routes. Dashboard users see no change. Scripts that call the removed routes must move to the `/api/v1/` routes.

**What this release solves:** [#491](https://github.com/foolzzz/looper/pull/491) moves the dashboard overview, task start, stop, restart, start-over and cancel, task renaming and task requirement edits to the versioned API (`/api/v1/`), reusing the shared task services. The seven legacy methods for them are removed.

**Breaking changes:** Yes. The seven legacy routes listed under Behavior changes no longer exist; a client that calls one gets a not-found answer. Stored tasks, versions, steps, plans and Planner sessions are unchanged.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#491](https://github.com/foolzzz/looper/pull/491); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.69
```

## Behavior changes

- **Removed routes (breaking for API clients):** `GET /api/overview`, `POST /api/tasks/cancel`, `POST /api/tasks/stop`, `POST /api/tasks/start`, `POST /api/tasks/{id}/start`, `PUT /api/tasks/{id}/requirement` and `PUT /api/tasks/{id}/title`.
- **Replacements:**
  - `POST /api/v1/system/overview` takes an empty object and returns the dashboard's full overview (agents, task counts, projects, spend, health, schedules); it is a read.
  - `POST /api/v1/ops/task_control/start`, `stop`, `restart`, `start_over` and `cancel` take `{task_id}` and return the existing task control results (`{task_id, started}`, `stopped`, `restarted` with a note, `started_over` with a note, `cancelled`). The legacy `POST /api/tasks/start` with `start_over` maps to `restart` or `start_over`.
  - `POST /api/v1/ops/task_update` renames a task with `{task_id, title}` and returns `{task_id, title, changed}`.
  - `POST /api/v1/tasks/requirement_update` takes `{task_id, requirement}` (non-empty, within the requirement length limit; unknown fields are rejected) and returns `{task_id, version, requirement}`. It shares the code that keeps the requirement version and notifies the task's Planner once.
- **Typed results:** the overview and the requirement edit declare typed requests and results; the control and update results are declared beside the unchanged Tool results.
- **Start of a ready task:** it now goes through the shared start path only; the legacy route's separate check that a ready task has a work directory is not kept. Starting a task that is not ready answers a conflict (see the shared task control checks) and sends nothing.
- **Titles:** a title is validated like the `task_update` Tool's (an over-long title is rejected rather than cut as the legacy route did).
- **Authority and confirmation:** the requirement edit is a write that an API client confirms in a second step; the operator writes in one step and the dashboard keeps its own confirmation. The change is recorded as made by `client:<name>` (or `client:operator`).
- **Worker input during startup:** a message sent to a dispatched Worker before its input channel is open now waits until the channel is ready (or the run ends, then it returns undelivered) instead of looking like a finished run.
- **Dashboard, evals and docs:** the dashboard's overview, control, rename and requirement calls use the new routes; the prompt-regression runner and dialogs, the DSH and Pi smoke scripts, the Looper client skill RFC and the long-horizon context plan follow.
- **Model-visible changes:** None to prompts or Manager Tools: no Manager, Worker, Planner or Reviewer prompt changed, and the Tool schemas and results of `looper_overview`, `looper_task_control` and `looper_task_update` are unchanged. The Worker input wait changes only when a user's correction reaches a Worker that is starting.

## Upgrade and rollback

Re-run `install.sh` once v2.13.69 is published. No data migration. Update any script or client that called a removed route before upgrading. Rolling back to v2.13.68 restores the legacy routes, with no stored data affected.

### 升级决策

**谁需要升级：**仪表盘用户，以及脚本调用总览、任务控制、任务重命名或任务需求 HTTP 路由的人。仪表盘用户看不到变化；调用已删除路由的脚本需要改用 `/api/v1/` 路由。

**解决了什么：**[#491](https://github.com/foolzzz/looper/pull/491) 把仪表盘总览、任务开始/停止/重启/从头开始/取消、任务重命名和任务需求编辑迁到版本化 API（`/api/v1/`），复用共享任务服务，并删除对应的七个旧方法。

**是否有破坏性变更：**是。“行为变化”中列出的七个旧路由不再存在，调用会得到 not found。已存的任务、版本、步骤、计划和 Planner 会话不变。

**如何验证：**运行 `looper --version` 核对版本为 2.13.69。

**贡献者：**维护者 @foolzzz 提交 [#491](https://github.com/foolzzz/looper/pull/491)；本次 patch release 无社区贡献。

```bash
looper --version   # looper 2.13.69
```

### 行为变化与入口

- **已删除的路由（对 API 客户端是破坏性的）：**`GET /api/overview`、`POST /api/tasks/cancel`、`POST /api/tasks/stop`、`POST /api/tasks/start`、`POST /api/tasks/{id}/start`、`PUT /api/tasks/{id}/requirement`、`PUT /api/tasks/{id}/title`。
- **替代路由：**
  - `POST /api/v1/system/overview` 收空对象，返回仪表盘完整总览（Agent、任务计数、项目、花费、健康、定时任务），为只读。
  - `POST /api/v1/ops/task_control/start`、`stop`、`restart`、`start_over`、`cancel` 收 `{task_id}`，返回既有任务控制结果（`started`、`stopped`、`restarted` 及说明、`started_over` 及说明、`cancelled`）。旧 `POST /api/tasks/start` 带 `start_over` 的用法对应 `restart` 或 `start_over`。
  - `POST /api/v1/ops/task_update` 用 `{task_id, title}` 重命名，返回 `{task_id, title, changed}`。
  - `POST /api/v1/tasks/requirement_update` 收 `{task_id, requirement}`（非空、不超过需求长度上限，拒绝未知字段），返回 `{task_id, version, requirement}`；与既有代码共用，保留需求版本并只通知 Planner 一次。
- **类型化结果：**总览和需求编辑声明了类型化请求与结果；控制与更新的结果声明在未改动的 Tool 结果旁。
- **启动 ready 任务：**现在只走共享启动路径；不再保留旧路由对 ready 任务单独做的工作目录检查。启动非 ready 任务返回冲突，且不发送消息。
- **标题：**校验与 `task_update` Tool 一致（过长标题被拒绝，而不是像旧路由那样截断）。
- **权限与确认：**需求编辑为写操作，API 客户端须两步确认；操作者单次写入，仪表盘保留自己的确认。变更记为 `client:<名字>`（或 `client:operator`）所为。
- **启动期间的 Worker 输入：**在 Worker 输入通道打开前发给已派发 Worker 的消息，现在会等通道就绪（或运行结束后返回未送达），而不是看起来像运行已结束。
- **仪表盘、评测与文档：**仪表盘的总览、控制、重命名和需求调用改用新路由；prompt 回归 runner 与对话、DSH 与 Pi 冒烟脚本、Looper 客户端 skill RFC 及长程上下文计划随之更新。
- **面向模型的变化：**prompt 与 Manager Tool 无变化：Manager、Worker、Planner、Reviewer 的 prompt 均未改动，`looper_overview`、`looper_task_control`、`looper_task_update` 的 Tool schema 与结果不变。Worker 输入等待只改变用户纠正到达正在启动的 Worker 的时机。

v2.13.69 发布后重跑 `install.sh`。无需迁移数据。升级前请更新调用已删除路由的脚本或客户端。回退到 v2.13.68 会恢复旧路由，不影响已存数据。

# Looper v2.14.29

This is the patch release v2.14.29, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.28: task progress updates stay routable after a drain restart ([#950](https://github.com/foolzzz/looper/pull/950)).

## Release Decision

**Who should upgrade:** Operators who drain the service for a planned restart and use Telegram or Lark. Everyone else sees no change in how tasks, schedules and Agent Profiles run.

**What this release solves:** A task-progress update (goal status, task accepted) that reached the Manager while the service drained was held and replayed after the restart, but it carried only a correlation id and the new channel instance had no route for it, so the update was dropped. [#950](https://github.com/foolzzz/looper/pull/950) stores the original chat (and for Lark the original message id) with the task and carries it on the progress message, so a replay after a restart reaches the same chat.

**Breaking changes:** No. No API, default or existing behavior is removed. One additive database migration runs on first start (see Upgrading).

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#950](https://github.com/foolzzz/looper/pull/950); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.29
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.28 upgrades directly. This release adds one migration, applied once on the first start of an existing database and recorded in `schema_migrations`; a new database gets it from `schema.sql`:

- `task_reply_route` ([#950](https://github.com/foolzzz/looper/pull/950)) adds the nullable column `tasks.origin_reply_route` (`JSONB`, limited to a JSON object).

It only adds; existing tasks read as having no stored route.

## Behavior changes

- **Task progress after a drain restart ([#950](https://github.com/foolzzz/looper/pull/950)).**
  - A task that the Manager creates from a Telegram or Lark conversation stores that chat as `tasks.origin_reply_route` (`chat_id`, and for Lark the original `reply_to` message id). Tasks from other origins store none.
  - The task router adds that route to its task reports, and the Manager's task-progress messages (summary updates and "task decomposed into N steps") now carry it, with the channel type in the target address.
  - The Lark channel answers a replayed progress update by replying to the original message; if that message is gone it sends to the chat instead, and any other send error is reported as a failed delivery. It does not change the live routing cache. A live update that still has its cached route is sent as before; Telegram needed no code change in this release.
  - Manager message handling now waits until the HTTP tools endpoint is listening (`tools_ready`), so a message replayed at startup stays queued and unacknowledged instead of being consumed by a tools-unavailable reply.
  - Tasks created before the upgrade have no stored route and keep the old behavior; the original Lark message id cannot be recovered for them. `STATUS_UPDATE` messages stay transient; the guarantee covers the held `TASK_ACCEPTED` and `GOAL_STATUS` updates replayed after a restart, and a crash after the platform received a message but before the bus acknowledged it can still send it twice. The drain RFC (Chinese) records this.
- **Model-visible changes:** None. No prompt, tool or message text given to a model changes, and the Manager's tool set is unchanged. Only the routing metadata on progress messages to the channel changes.

## 中文摘要

本版本是 patch release v2.14.29（热修线，每个合并的改动立即发布）。自 v2.14.28 以来只合并了一项改动：排空重启后任务进度更新仍可路由（[#950](https://github.com/foolzzz/looper/pull/950)）。

### 升级决策

**谁需要升级：**在计划内重启前使用排空、并使用 Telegram 或 Lark 的运维者。其他人在任务、定时任务和 Agent Profile 的运行方式上没有变化。

**解决了什么：**服务排空期间到达 Manager 的任务进度更新（目标状态、任务已接受）会被持有并在重启后重放，但它只带关联 id，新的渠道实例没有对应路由，更新因此被丢弃。[#950](https://github.com/foolzzz/looper/pull/950) 把原聊天（Lark 还有原消息 id）随任务保存并带在进度消息上，重启后的重放能送达同一个聊天。

**是否有破坏性变更：**否。不移除任何 API、默认值或现有行为。首次启动会运行一项只增不改的数据库迁移（见升级）。

**如何验证：**运行 `looper --version` 核对版本为 2.14.29。

**贡献者：**维护者 @foolzzz 提交 [#950](https://github.com/foolzzz/looper/pull/950)；本版本无社区贡献。

```bash
looper --version   # looper 2.14.29
```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.28 上的安装可直接升级。本版本新增一项迁移，在已有数据库首次启动时执行一次并记入 `schema_migrations`，新数据库由 `schema.sql` 创建：

- `task_reply_route`（[#950](https://github.com/foolzzz/looper/pull/950)）新增可空列 `tasks.origin_reply_route`（`JSONB`，限定为 JSON 对象）。

它只增不改：现有任务读作没有保存路由。

### 行为变化与入口

- **排空重启后的任务进度（[#950](https://github.com/foolzzz/looper/pull/950)）。**
  - Manager 从 Telegram 或 Lark 对话创建的任务，会把该聊天保存为 `tasks.origin_reply_route`（`chat_id`，Lark 还有原消息 id `reply_to`）。来自其他入口的任务不保存。
  - 任务路由器的任务报告会带上该路由；Manager 的任务进度消息（摘要更新和“任务已分解为 N 个步骤”）现在也带上它，并在目标地址中带渠道类型。
  - Lark 渠道对重放的进度更新回复原消息；原消息已不存在时改发到聊天，其他发送错误报告为投递失败。它不改变实时路由缓存。仍有缓存路由的实时更新照旧发送；本版本没有改 Telegram 代码。
  - Manager 的消息处理现在等到 HTTP 工具端点开始监听（`tools_ready`）才开始，所以启动时重放的消息保持排队且未确认，不会被一条“工具不可用”的回复消耗掉。
  - 升级前创建的任务没有保存路由，保留旧行为，无法补出其 Lark 原消息 id。`STATUS_UPDATE` 仍是瞬时消息；保证范围是被持有的 `TASK_ACCEPTED`、`GOAL_STATUS` 更新在重启后的重放，平台已收到但总线尚未确认时崩溃，仍可能重复发送。排空 RFC（中文）记录了这一点。
- **面向模型的变化：**无。给模型的提示词、工具或消息文本都不变，Manager 的工具集不变。只有发往渠道的进度消息的路由元数据变了。

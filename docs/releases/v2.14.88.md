# Looper v2.14.88

This is the patch release v2.14.88, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.87: Looper can fetch an API-key provider's model list and add the models the operator ticks ([#1112](https://github.com/foolzzz/looper/pull/1112)).

## Release Decision

**Who should upgrade:** Operators who register API-key providers and want to add their models from the provider's own list instead of typing each name. Everyone else can stay.

**What this release solves:** Adding the models of an API-key provider meant entering every name by hand. [#1112](https://github.com/foolzzz/looper/pull/1112) asks the provider's endpoints which models they serve, with the stored key, and registers the ones the operator picks.

**Breaking changes:** No. Two operations and one registry field are added; existing operations, `models.create`, the Manager tools, config transfer, channels and the database schema are unchanged.

**How to verify:** Check the installed version. In Settings, add an API-key provider (or press Fetch models on an existing one): the dashboard lists the endpoint's models, nothing preselected, and adds only the ticked ones; a failing endpoint shows its reason and the provider stays saved.

**Contributors:** Maintainer @foolzzz authored [#1112](https://github.com/foolzzz/looper/pull/1112); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.88
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.87 upgrades directly. There is no database change.

## Behavior changes

- **Model listing** (`looper/agents/model_listing.py`, new operation `provider_accounts.fetch_models`). For an API-key provider, each distinct format and base URL is asked once with the provider's stored key: OpenAI formats `GET <base_url>/models` with a Bearer key (the Responses and Chat protocols on one base URL share one request); Anthropic `GET <base_url>/v1/models` with `x-api-key` and `anthropic-version`, retried once with a Bearer key after a 401 or 403, following pagination. The answer lists, per endpoint, the models (with a context window when the provider reports one, the protocols where the name is already registered, and whether Looper's built-in price table prices the name) or a typed problem: key refused, no model list, other HTTP status, redirect, timeout (15 seconds), unreachable, or not a model list. Redirects are not followed, a response is read up to 2 MB, at most 10 pages and 1000 models are taken (the answer says when truncated), the server's proxy environment is honoured, and login providers are skipped because their models ship with Looper. The key is never logged or returned; the log line carries only the provider id, format, host and result. A failure never blocks saving or using the provider.
- **Adding the picked models** (`looper/agents/profile_registry.py`, new operation `models.add_many`). One request adds 1 to 200 models in a single transaction. A price an entry leaves out stays null (the built-in price applies) when Looper's table prices that field for the model name, otherwise it is 0 and the model's runs count as free; explicit prices, including null, are kept. A name already registered under the same protocol, and a repeated entry, is skipped and reported; an invalid entry refuses the whole request. `models.create` is unchanged: null prices stay "unknown".
- **Registry limits** (`looper/agents/runtimes/__init__.py`). `limits` gains `api_formats` (Anthropic: `anthropic-messages`; OpenAI: `openai-responses`, `openai-chat`) with labels, now the one source for protocol families.
- **Dashboard** (`web/src/components/provider-settings.tsx`, `provider-model-picker.tsx`). After Add provider succeeds for an API-key provider, the form shows the fetched checklist (nothing preselected, with a note that an unpriced model is priced 0 until set); nothing is added without a tick. Every API-key provider row gets a Fetch models button. Login providers keep their built-in model lists.
- **CLI.** Both operations are operator-only and appear as generated `loopercli` commands.
- **Unchanged:** existing operations, `models.create`, the Manager tools (the Manager never handles keys), config transfer, channels, the database schema, and wheel and source upgrades.
- **Documentation and tests.** `docs/architecture/agent-system.md` describes the listing and the add operation. The pull request adds `tests/test_model_listing.py`, `tests/test_provider_model_listing_db.py` and a dashboard picker test, and extends the existing API, registry, pricing and dashboard tests.
- **Model-visible changes:** None. No prompt, Manager tool, tool text or tool result wording changes; both operations are operator-only and not offered to the Manager.

## 中文摘要

本版本是 patch release v2.14.88（热修线，每个合并的改动立即发布）。自 v2.14.87 以来只合并了一项改动：可获取 API-key 提供方的模型列表，并添加运维人员勾选的模型（[#1112](https://github.com/foolzzz/looper/pull/1112)）。

### 升级决策

**谁需要升级：**注册 API-key 提供方、希望从提供方自己的列表添加模型而不是逐个手输名称的运维人员。其他人可不升级。

**解决了什么：**为 API-key 提供方添加模型原本要手动输入每个名称。[#1112](https://github.com/foolzzz/looper/pull/1112) 用已存的密钥询问提供方端点提供哪些模型，并注册运维人员选中的模型。

**是否有破坏性变更：**否。新增两个操作和一个注册表字段；现有操作、`models.create`、Manager 工具、配置转移、渠道和数据库结构不变。

**如何验证：**核对版本为 2.14.88。在设置中添加 API-key 提供方（或在已有提供方上点 Fetch models）：控制台列出端点的模型，默认不勾选，只添加勾选的；端点失败时显示原因，提供方仍已保存。

**贡献者：**维护者 @foolzzz 提交 [#1112](https://github.com/foolzzz/looper/pull/1112)；本版本无社区贡献。

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.87 上的安装可直接升级。没有数据库变更。

### 行为变化与入口

- **模型列表**（`looper/agents/model_listing.py`，新操作 `provider_accounts.fetch_models`）。对 API-key 提供方，每个不同的格式和 base URL 用已存密钥询问一次：OpenAI 格式 `GET <base_url>/models` 带 Bearer 密钥（同一 base URL 上的 Responses 与 Chat 协议共用一次请求）；Anthropic 为 `GET <base_url>/v1/models`，带 `x-api-key` 和 `anthropic-version`，遇 401 或 403 用 Bearer 密钥重试一次，并跟随分页。结果按端点给出模型（提供方报告时附上下文窗口、该名称已注册的协议、以及 Looper 内置价格表是否有该名称的价格），或给出类型化的问题：密钥被拒、没有模型列表、其他 HTTP 状态、重定向、超时（15 秒）、无法连接、返回不是模型列表。不跟随重定向，响应最多读 2 MB，最多取 10 页和 1000 个模型（被截断时结果会说明），遵循服务器的代理环境变量；登录型提供方因模型随 Looper 提供而跳过。密钥不会被记录或返回，日志只含提供方 id、格式、主机和结果。失败不会阻止保存或使用该提供方。
- **添加所选模型**（`looper/agents/profile_registry.py`，新操作 `models.add_many`）。一次请求在单个事务中添加 1 到 200 个模型。条目省略的价格：Looper 价格表对该模型名有该字段价格时保持 null（适用内置价格），否则为 0，该模型的运行按免费计；显式价格（含 null）保留。同协议下已注册的名称和重复条目会被跳过并报告；任一条目无效则整个请求被拒绝。`models.create` 不变：null 价格仍为"未知"。
- **注册表限制**（`looper/agents/runtimes/__init__.py`）。`limits` 新增 `api_formats`（Anthropic：`anthropic-messages`；OpenAI：`openai-responses`、`openai-chat`）及标签，成为协议族的唯一来源。
- **控制台**（`web/src/components/provider-settings.tsx`、`provider-model-picker.tsx`）。API-key 提供方添加成功后，表单显示获取到的清单（默认不勾选，并提示无价格的模型在设置前按 0 计价）；不勾选就不会添加。每个 API-key 提供方行都有 Fetch models 按钮。登录型提供方保持内置模型列表。
- **CLI。**两个操作仅限运维人员，作为生成式 `loopercli` 命令出现。
- **不变：**现有操作、`models.create`、Manager 工具（Manager 从不接触密钥）、配置转移、渠道、数据库结构，以及 wheel 与源码升级。
- **文档与测试。**`docs/architecture/agent-system.md` 描述了列表获取和添加操作。该 PR 新增 `tests/test_model_listing.py`、`tests/test_provider_model_listing_db.py` 和控制台选择器测试，并扩展了现有的 API、注册表、定价和控制台测试。
- **面向模型的变化：**无。提示、Manager 工具、工具文本和工具结果措辞均不变；两个操作仅限运维人员，不提供给 Manager。

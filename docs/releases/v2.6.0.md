# Looper v2.6.0

## At a Glance

LoopX is now **Looper**. A task's Planner is now a Claude Code agent: it splits the request into steps with acceptance criteria, has them reviewed, retries and replans, keeps a journal of progress and lessons, and carries the task on after a server restart. Agents no longer pick up your personal Claude Code setup; what they load and run comes from layered settings, project knowledge and skills, and a capability catalog that also holds MCP servers. An agent is now a runtime, a provider and a model: Claude Code on its own login, on an API key or on an Anthropic-compatible provider (GLM, DeepSeek, Kimi, CLIProxyAPI), Codex, or OMP (oh-my-pi). `looper doctor`, `looper service`, a backup before every schema change and configuration export and import cover operations. The upstream LoopX control plane is gone.

**This release has breaking changes.** Upgrade by re-running `install.sh`: v2.5.0's `loopx update apply` cannot install the renamed `looper` wheel. The steps are under Upgrading from v2.5.0.

```bash
curl -fsSL https://raw.githubusercontent.com/foolzzz/looper/main/install.sh | bash
looper --version   # looper 2.6.0
looper doctor
```

### Highlights

- **Tasks that plan, review and carry on.** The Planner splits a task into 1 to 8 steps, sends steps to a Reviewer, retries with feedback, replans, checks running Workers every 5 minutes and resumes after a restart from the plan stored in PostgreSQL. ([#2](https://github.com/foolzzz/looper/pull/2), [#4](https://github.com/foolzzz/looper/pull/4), [#45](https://github.com/foolzzz/looper/pull/45))
- **A task journal.** Failures, retries, decisions, your instructions and session changes are journaled and fed to the next turn; an agent that changes provider or runtime hands off and the new session starts from a resume brief; lessons can become project knowledge. ## Release Decision

**Who should upgrade:** Everyone running `loopx serve` from v2.5.0. Stay on v2.5.0 only if you depend on the upstream LoopX command line (Goals, `loopx dispatch`, `loopx dashboard`, `loopx chat`, todos or any other removed subcommand), which v2.6.0 no longer has.

**What this release solves:** v2.5.0 ran every task as one unplanned step, stopped all work at a restart, let the operator's personal Claude Code configuration leak into every agent, stored most Agents-page settings without applying them, and ran only Claude Code on its own login. v2.6.0 plans, reviews, journals and resumes tasks; makes agents reproducible and configurable by layer and by project; adds a capability catalog with MCP servers, API-key providers, and Codex and OMP runtimes, per-run cost and context, `looper doctor`, `looper service`, backups before schema changes and configuration export and import; and renames the project to Looper.

**Breaking changes:** Yes. LoopX is renamed Looper (`loopx` stays as an alias for this release, `~/.loopx` moves to `~/.looper` automatically, `LOOPER_*` variables fall back to `LOOPX_*`); 134 of v2.5.0's 137 `loopx` subcommands are removed, including `update` and `init`; agents no longer load your personal Claude Code configuration, and imported plugins and skills load only where installed; tasks resume after a restart; settings resolve by layer and every agent passes a model, `opus` by default; Telegram and Lark need a sender allowlist; `/api/llm-profiles` and several agent-config fields are removed; `looper serve` will not change the schema without a `pg_dump` backup unless told to. See Breaking Changes and Upgrading from v2.5.0.

**How to verify:** After re-running `install.sh`, `looper --version` reports `looper 2.6.0`, `loopx --version` prints a deprecation note and the same version, and `looper doctor` passes (PostgreSQL, the Claude Code CLI and its login, `pg_dump`). With `looper serve` or `looper service` running, `/api/status` reports `"status": "running"` with its checks, and `~/.loopx` is a link to `~/.looper`.

**Contributors:** Release maintainer @foolzzz; community contributor @michaelx1993, with 8 pull requests (#4 to #11) on Planner supervision, recommended prompts, a Worker fix and CI (see Community Contributors).

```bash
curl -fsSL https://raw.githubusercontent.com/foolzzz/looper/main/install.sh | bash
looper --version   # looper 2.6.0
loopx --version    # a deprecation note on stderr, then looper 2.6.0
looper doctor
looper serve       # or: looper service install
  # In another shell:
curl -s http://127.0.0.1:8767/api/status
ls -ld ~/.loopx    # a link to ~/.looper after the first start
```

## Long-Running Tasks

- **The Planner is a Claude Code agent.** It keeps one Claude process for the task's life and splits the requirement into 1 to 8 steps, each with acceptance criteria, dependencies and whether a Reviewer must pass it. After every result it accepts the step, sends it to review, retries it with feedback (at most 2 per step), replans the steps not started, or fails the task, in a strictly validated JSON reply. A chat message to a Planner goes through its Claude, which answers and may pass it to the running Worker or add steps. Every Planner turn is a paid run, recorded as `planner-TASK_ID`. ([#2](https://github.com/foolzzz/looper/pull/2))
- **Supervision.** Every 300 seconds (a project's `supervise_interval_seconds`, 0 turns it off) the Planner looks at the running Workers and can nudge one or stop it. ([#4](https://github.com/foolzzz/looper/pull/4))
- **State in PostgreSQL, and resume after a restart.** Plans, steps and agent sessions live in the database instead of files. A task left running with a live plan is resumed at startup: its Planner resumes its Claude session, a running step runs again, a step in review gets a new Reviewer. The old plan and session files are imported once. ([#45](https://github.com/foolzzz/looper/pull/45))
- **Task journal and handoffs.** Accepted steps, failures and retries with their learnings, Planner decisions, every user instruction and session switches are journaled. The Planner's turns carry your instructions whole, then the newest of each kind, and a Worker's first turn gets them too; the task page lists them under Findings. When the Manager or a Planner cannot resume its session (another runtime or provider), the old session writes a handoff and the new one starts from a resume brief. ([#46](https://github.com/foolzzz/looper/pull/46), [#66](https://github.com/foolzzz/looper/pull/66))
- **Spend caps.** A project can cap a task's spend (`task_budget_usd`, failing at once or after a wrap-up turn) and each run's (`run_budget_usd`); the task page shows spend against the cap from 80% on, and a task that failed at its cap can be continued at a higher one. ([#37](https://github.com/foolzzz/looper/pull/37), [#43](https://github.com/foolzzz/looper/pull/43))

## Agents and Configuration

- **Isolated from your personal setup.** Every agent starts Claude Code with `--setting-sources project`, `--strict-mcp-config` and settings that exclude every `CLAUDE.md` above the work directory's repository and in `~/.claude`, and turn off auto memory. The project's own `CLAUDE.md` and `.claude/settings.json` still load; the login is unaffected. ([#17](https://github.com/foolzzz/looper/pull/17))
- **Layered system prompt, recorded.** Planner, Workers and Reviewers get a harness, their role prompt, the project background, the task and the code-owned contract; the Manager a harness, its role prompt and the placement rule. Each run records the prompt, its hash and its layers, shown on the history page. Reviewers have their own agent row. Recommended prompts are tracked: an unedited prompt follows the new default, an edited one is kept and can be reset. ([#8](https://github.com/foolzzz/looper/pull/8), [#9](https://github.com/foolzzz/looper/pull/9), [#13](https://github.com/foolzzz/looper/pull/13), [#17](https://github.com/foolzzz/looper/pull/17), [#19](https://github.com/foolzzz/looper/pull/19))
- **Layered settings.** Harness, agent, effort, environment and per-run cap resolve through system, role, project and role in a project, edited in Settings, on the Agents page and on a project's Settings tab; every run records where each setting came from. ([#19](https://github.com/foolzzz/looper/pull/19), [#50](https://github.com/foolzzz/looper/pull/50))
- **Runtimes, providers and agents.** Settings registers runtimes, providers (with a model catalog, prices and an API key stored apart) and agents. Claude Code runs on its own login, an Anthropic API key or an Anthropic-compatible endpoint, with presets for GLM (BigModel, Z.ai), DeepSeek, Kimi (China, international) and a local CLIProxyAPI, and a built-in price table. Codex and OMP (oh-my-pi's `omp`) run every role with an API key provider, each in a home of Looper's own instead of the operator's. A layer, a project or a single task (`agent_overrides`) selects the agent. ([#62](https://github.com/foolzzz/looper/pull/62), [#67](https://github.com/foolzzz/looper/pull/67), [#68](https://github.com/foolzzz/looper/pull/68), [#70](https://github.com/foolzzz/looper/pull/70))
- **Capability catalog.** Plugins and skills imported from this machine, uploaded as a `SKILL.md` or zip, cloned from a public git repository or written in Settings, and MCP servers, are catalog items installed globally or in one project for some of the roles. Project skills are catalog items too. ([#22](https://github.com/foolzzz/looper/pull/22), [#48](https://github.com/foolzzz/looper/pull/48), [#49](https://github.com/foolzzz/looper/pull/49), [#51](https://github.com/foolzzz/looper/pull/51))
- **Projects.** A background in every task agent's prompt, knowledge documents agents read on demand (text, uploads or files in the project directory), project skills, execution settings (review policy, supervision, caps), lessons drafts and a project page with Overview, Knowledge, Skills and Settings tabs. ([#13](https://github.com/foolzzz/looper/pull/13), [#27](https://github.com/foolzzz/looper/pull/27), [#32](https://github.com/foolzzz/looper/pull/32), [#37](https://github.com/foolzzz/looper/pull/37), [#44](https://github.com/foolzzz/looper/pull/44), [#61](https://github.com/foolzzz/looper/pull/61))
- **Cost and context.** Every run records its tokens (cache included), context size, compactions and cost; tasks carry their cost by role, agents their usage by session and day, and history pages show context over turns. ([#24](https://github.com/foolzzz/looper/pull/24))

## Fixes

- A Worker's outcome follows its result and report, not Claude's exit code; Workers no longer inherit the operator's MCP servers. ([#11](https://github.com/foolzzz/looper/pull/11))
- A resident Manager or Planner whose saved session is gone starts a new one instead of answering nothing ([#20](https://github.com/foolzzz/looper/pull/20)); it no longer answers a message with the turn before it ([#26](https://github.com/foolzzz/looper/pull/26)); a resumed session's first turn is no longer counted twice ([#24](https://github.com/foolzzz/looper/pull/24)); a Manager message at its spend cap gets the cap's error ([#68](https://github.com/foolzzz/looper/pull/68)).
- A task's config is returned as a JSON object instead of quoted JSON text that grew with every save. ([#41](https://github.com/foolzzz/looper/pull/41))

## Breaking Changes

1. **Renamed to Looper.** The command, Python package and wheel are `looper`; `looper version --format json` reports `name: looper` and `schema_version: looper_version_v0`. For this release only: `loopx` is an alias that prints a deprecation note and runs `looper`; the first `looper serve` or `looper service install` renames `~/.loopx` to `~/.looper` and leaves `~/.loopx` as a link; an unset `LOOPER_*` variable falls back to its `LOOPX_*` name with a warning; the service is `com.looper.serve`, and `looper service install` removes `com.loopx.serve`. The default database name stays `loopx`. ([#64](https://github.com/foolzzz/looper/pull/64))
2. **The upstream LoopX command line is gone.** v2.5.0's `loopx` listed 137 subcommands. `serve` and `version` remain and `doctor` is a new, different check; the other 134 are removed, among them `update` (re-run `install.sh` instead), `init` (nothing read its files), `status`, `todo`, `dispatch`, `dashboard` and `chat`, with the aliases `connect`, `goal-alignment` and `amendment-proposal` and the global `--registry`, `--runtime-root` and `--format` options. Also removed: the upstream modules and Chat bundle, the `loopx-lark-provider` and `loopx-openviking-*` commands, the `deepseek-harness` extra, the bundled workflow skills and the source-snapshot installers. ([#31](https://github.com/foolzzz/looper/pull/31), [#35](https://github.com/foolzzz/looper/pull/35))
3. **Agents no longer load your personal Claude Code configuration, and plugins and skills load only where installed.** In v2.5.0 every agent read `~/.claude`: `CLAUDE.md`, user settings (model, effort, env, permissions), hooks, MCP servers, plugins and skills. Now none of it loads. Import plugins and skills into the catalog and install each one globally or in a project for the roles that need it; an imported item is installed nowhere until you do. ([#17](https://github.com/foolzzz/looper/pull/17), [#48](https://github.com/foolzzz/looper/pull/48))
4. **Tasks resume after a restart.** A task the previous server left running with a live plan carries on at startup, and spends, instead of being marked stopped. Tasks a v2.5.0 server left running have no such plan and are still marked stopped. ([#45](https://github.com/foolzzz/looper/pull/45))
5. **Settings resolve by layer, and every agent passes a model.** Harness, agent, effort, environment and per-run cap come from the system, role, project and role-in-project layers. Every role now runs an agent, `claude-code/opus` unless one is selected, so an account whose Claude Code default was cheaper now runs on Opus. A model stored on v2.5.0's Agents page, which v2.5.0 did not apply, becomes that role's agent and now applies. Every agent also gets a default harness, and the Manager answers in the user's language. ([#19](https://github.com/foolzzz/looper/pull/19), [#50](https://github.com/foolzzz/looper/pull/50), [#62](https://github.com/foolzzz/looper/pull/62))
6. **Telegram and Lark need a sender allowlist.** A channel passes on only the senders it lists (`allowed_user_ids`, `allowed_open_ids`); an enabled channel with an empty or invalid list does not start. An empty Telegram list no longer means everyone, and `LOOPX_TELEGRAM_ALLOWED_USERS` is not read. ([#23](https://github.com/foolzzz/looper/pull/23))
7. **Removed or changed APIs.** `/api/llm-profiles` is removed. Agent configs no longer return `runtime`, `llm_profile_id`, `model` or `permission_mode`, and an update naming one of the first three is a 400 (a role's model is its agent, set with `PUT /api/agent-settings/roles/ROLE`). A task's `config` is a JSON object, not JSON text. `GET /api/llm-records?role=worker` lists Workers only (`role=reviewer` and `role=planner` exist). Request bodies over 8 MiB get a 413. A chat message to a Planner no longer becomes a step by itself. ([#2](https://github.com/foolzzz/looper/pull/2), [#41](https://github.com/foolzzz/looper/pull/41), [#42](https://github.com/foolzzz/looper/pull/42), [#50](https://github.com/foolzzz/looper/pull/50), [#62](https://github.com/foolzzz/looper/pull/62))
8. **No schema change without a backup.** When the schema is about to change, `looper serve` first writes a `pg_dump` backup; without a usable `pg_dump` or `LOOPER_BACKUP_CMD`, or when the backup fails, it exits before changing anything. `--skip-backup` migrates without one. `looper config import --apply` refuses a database with a pending change. ([#60](https://github.com/foolzzz/looper/pull/60))

Also changed, with cost or authority effects: every agent, the Manager and the Planner included, now runs with every tool and no permission prompts; the Planner's restraint from editing files is its role prompt. Workers and Reviewers get a system prompt. ([#13](https://github.com/foolzzz/looper/pull/13), [#23](https://github.com/foolzzz/looper/pull/23))

## Upgrading from v2.5.0

1. **Install with `install.sh`.** It installs `looper` from the latest release wheel and first removes the `loopx` package that the same tool (uv, pipx or pip) installed; your data in `~/.loopx` is kept. Do not use v2.5.0's `loopx update apply`: it asks pip for a package named `loopx`, and pip refuses the `looper` wheel.
2. **Rename your variables.** Change `LOOPX_DATABASE_URL` to `LOOPER_DATABASE_URL`, and any other `LOOPX_*` to `LOOPER_*`, in your shell profile and `.env`. The old names still work for this release, with a warning.
3. **Make the first-start backup possible.** A v2.5.0 database has a schema change pending, so the first start backs it up with `pg_dump --format=custom` into `~/.looper/backups/` before migrating. Put a `pg_dump` of at least the server's major version on `PATH` or in `LOOPER_PG_DUMP` (macOS: `brew install libpq`), or, with PostgreSQL in Docker, set `LOOPER_BACKUP_CMD` to a command that writes the dump to stdout. `looper serve --skip-backup` migrates without a backup.
4. **Start once.** `looper serve` (or step 5) moves `~/.loopx` to `~/.looper`, takes the backup, logs its restore command and migrates the database: LLM profiles and unused agent-config columns are dropped, each role's stored model becomes its agent, and tasks left running are marked stopped.
5. **Run it as a service, if you want.** Run `looper service install` from a shell that has your `LOOPER_*` variables; it copies them into the unit, removes a `com.loopx.serve` unit if one exists and starts `com.looper.serve`. Run it again whenever those variables change.
6. **Turn channels back on.** Add the sender allowlists for Telegram and Lark in Settings, then restart.
7. **Reinstall the plugins and skills you want.** Settings, Plugins & skills catalog, "Import from this machine", then install each item globally or in a project for the roles that need it. MCP servers come from `~/.claude.json` the same way.
8. **Review agents and cost.** Settings and the Agents page show the agent each role runs and where it comes from; every role runs Opus unless you choose otherwise.
9. **Check.** `looper doctor`, and `looper service status` for the service.

```bash
curl -fsSL https://raw.githubusercontent.com/foolzzz/looper/main/install.sh | bash
export LOOPER_DATABASE_URL="postgresql://localhost:5432/loopx"   # the database keeps its name
looper doctor                     # fix what it reports, pg_dump included
looper serve                      # first start: moves ~/.loopx, backs up, migrates
  # Or, instead of looper serve:
looper service install && looper service status
```

**Rollback to v2.5.0.** Stop Looper (`looper service uninstall` if you installed the service), recreate the database empty and restore the pre-migration backup the first start logged (`pg_restore --no-owner --dbname "$LOOPER_DATABASE_URL" FILE`), then replace the package with the v2.5.0 wheel, for example `uv tool uninstall looper && uv tool install "loopx @ https://github.com/foolzzz/looper/releases/download/v2.5.0/loopx-2.5.0-py3-none-any.whl"`. `install.sh` always installs the latest release, so it cannot roll back. v2.5.0 reads `~/.loopx`, which still links to `~/.looper`, and the `LOOPX_*` names.

## Optional Capability Activation & Use

### looper service

**Activation:** Per command; nothing runs in the background until you install it. `looper service install` writes a launchd LaunchAgent (macOS) or a systemd user unit (Linux) named `com.looper.serve` and starts it; it runs `looper serve` at login and again after a crash, logging to `serve.log` under the runtime root's `logs/`. The unit runs the `looper` that ran `install`, in the current directory, with `PATH`, locale and proxy settings, `CLAUDE_CONFIG_DIR` and the `LOOPER_*`, `ANTHROPIC_*` and `LARK_*` variables copied from your shell (`--env NAME` adds others; `--port`, `--runtime-root` and `--label` are options). It is not started while another process holds the port. On Linux, `loginctl enable-linger $USER` keeps it running without a login session.

**Validation:** `looper service status` shows whether it is installed and running, its PID, last exit, log and `GET /api/status`, and exits 0 only when it serves; `looper doctor` has a Service line.

**Disable / rollback:** `looper service uninstall` stops it and removes the unit; the database and runtime root are untouched. `looper service restart` restarts it; re-run `install` to change its variables.

**Authority boundary:** It runs `looper serve` as your user, unattended, whenever you are logged in, so agents without permission prompts, tasks that resume after a crash and the unauthenticated loopback API are live all that time. The unit file holds the copied variables, possibly the database password and provider credentials, with mode 0600. It installs no system-wide unit and needs no root.

**Docs:** https://github.com/foolzzz/looper/blob/v2.6.0/README.md#4-run-as-a-service

```bash
looper service install
looper service status
curl -s http://127.0.0.1:8767/api/status
  # Disable:
looper service uninstall
```

### Configuration export and import

**Activation:** Per command. `looper config export FILE` writes the agent configuration as `looper-config/v1` JSON: settings layers and role prompts, runtimes, providers and agents, the catalog with its files and MCP servers, global installs and channels; `--include-projects` adds each project's settings, knowledge, own skills and installs. `looper config import FILE` previews what it would add, change, leave and skip and the secrets to fill in; `--apply` writes it in one transaction. Both read the database `LOOPER_DATABASE_URL` names directly, so the server need not run. Settings does both under "Move to another machine". Files exported as `loopx-config/v1` still import.

**Validation:** The preview names every change per section; importing the same file again reports nothing to change.

**Disable / rollback:** There is nothing to switch off. An applied import updates entries in place and removes nothing; to undo it, restore a database backup taken before applying. An upload in Settings that is not applied expires after an hour.

**Authority boundary:** An import changes what every agent loads and runs (installs, harness, agents, channels). Secrets (provider API keys, MCP environment and header values, channel secrets) are placeholders unless you export with `--include-secrets`, which writes them in plain text; a placeholder never replaces a stored secret. Local paths (a project's directory, an item's source, a runtime's executable) are not exported. Settings stores an upload of up to 256 MiB with mode 0600 under the runtime root until it is applied, cancelled or expired.

**Docs:** https://github.com/foolzzz/looper/blob/v2.6.0/docs/architecture/agent-system.md#moving-the-configuration-export-and-import

```bash
looper config export looper-config.json --include-projects
  # On the other machine:
looper config import looper-config.json           # preview only
looper config import looper-config.json --apply
```

### API-key providers and agents

**Activation:** Off until you select one: every role runs the built-in agent `claude-code/opus` (Claude Code on its own login) until a layer or a task selects another. In Settings, add a provider: a preset (GLM on BigModel or Z.ai, DeepSeek, Kimi China or international, CLIProxyAPI on this machine) or Anthropic's API or another Anthropic-format endpoint, then paste its key. Add an agent (runtime, provider, model, default effort) and select it for every role in Settings, for one role on the Agents page, for a project on its Settings tab or for one task in the New Task dialog.

**Validation:** `GET /api/registry` lists runtimes, providers (keys shown as `***`), agents with their cost basis, the presets and the built-in prices; `GET /api/agent-settings` shows the agent each role resolves and its layer; each run records its agent and `cost_source`.

**Disable / rollback:** Set the layer's or project's agent back to `null` so the roles inherit `claude-code/opus` again, then delete the agent and the provider (409 while something still uses them). A resident Manager or Planner that changes provider starts a new session after a handoff.

**Authority boundary:** The key is stored in the database, shown as `***`, never recorded in runs, exported only with `--include-secrets`, and given only to the runs that use the provider; their prompts, code and tool output go to that provider. Agents keep every tool and no permission prompts. On providers other than Anthropic's own API, Looper prices the tokens from its own table (USD list prices of 2026-10-14) and enforces a soft per-run cap: the request that crosses it is still made, and a model without a price records tokens only, with no spend cap.

**Docs:** https://github.com/foolzzz/looper/blob/v2.6.0/docs/architecture/agent-system.md#runtimes-llm-providers-and-agents

```bash
curl -s http://127.0.0.1:8767/api/registry | python3 -m json.tool | grep -E '"(agent_id|name|model)"'
  # Select an agent for every role (AGENT_ID from the registry), read it back, then return to the built-in:
curl -s -X PUT http://127.0.0.1:8767/api/agent-settings/system -H 'Content-Type: application/json' -d '{"agent": "AGENT_ID"}'
curl -s http://127.0.0.1:8767/api/agent-settings
curl -s -X PUT http://127.0.0.1:8767/api/agent-settings/system -H 'Content-Type: application/json' -d '{"agent": null}'
```

### Codex runtime

**Activation:** Install the Codex CLI (verified with 0.162.0) on the `PATH` of `looper serve`; serve then registers the runtime `codex` at start. Register an API-key provider that serves `openai-responses` (the CLIProxyAPI preset, or another OpenAI Responses endpoint), add an agent on `codex` with that provider and a model, and select it for a role, a project or a task. Codex's own login is not used.

**Validation:** `GET /api/registry` shows the `codex` runtime with its version and capabilities; each Codex run records its agent, its tokens and the catalog parts Codex left out (`metadata.runtime_catalog`).

**Disable / rollback:** Select another agent on that layer, or `null` to inherit, and delete the agent. Per-run Codex homes unused for a day are removed when a new one is written.

**Authority boundary:** Looper runs `codex exec --dangerously-bypass-approvals-and-sandbox`: no approvals and no sandbox, with your user's access in the task's directory, as Claude Code agents have. Each run gets a `CODEX_HOME` of its own under the runtime root with only the `config.toml` and `AGENTS.md` Looper writes; your `~/.codex` and `~/.agents/skills` are never read. The key reaches Codex in a variable its shell commands do not get. Installed MCP servers pass through (stdio and HTTP; SSE is left out); skills are mounted read-only; a plugin's hooks, commands and agents are left out.

**Docs:** https://github.com/foolzzz/looper/blob/v2.6.0/docs/architecture/agent-system.md#runtimes-llm-providers-and-agents

```bash
codex --version
curl -s http://127.0.0.1:8767/api/registry | python3 -m json.tool | grep -A4 '"rt-codex"'
  # An agent on Codex (PROVIDER_ID: an API-key provider serving openai-responses), used by Workers, then undone:
curl -s -X POST http://127.0.0.1:8767/api/agents -H 'Content-Type: application/json' \
  -d '{"name": "codex/gpt-5.6-sol", "runtime_id": "rt-codex", "provider_id": "PROVIDER_ID", "model": "gpt-5.6-sol"}'
curl -s -X PUT http://127.0.0.1:8767/api/agent-settings/roles/worker -H 'Content-Type: application/json' -d '{"agent": "AGENT_ID"}'
curl -s -X PUT http://127.0.0.1:8767/api/agent-settings/roles/worker -H 'Content-Type: application/json' -d '{"agent": null}'
```

### OMP runtime

**Activation:** Install oh-my-pi's `omp` CLI (verified with 18.4.3) on the `PATH` of `looper serve`; serve then registers the runtime `omp` at start. Register an API-key provider that serves `openai-responses`, `openai-chat` or `anthropic-messages` (the CLIProxyAPI preset, for example), add an agent on `omp` with that provider and a model, and select it for a role, a project or a task. omp's own logins are not used.

**Validation:** `GET /api/registry` shows the `omp` runtime with its version and capabilities; each OMP run records its agent, its tokens and context size, and the catalog parts omp left out (`metadata.runtime_catalog`).

**Disable / rollback:** Select another agent on that layer, or `null` to inherit, and delete the agent. When it starts, `looper serve` removes the OMP homes no running process uses and the session directories of agents whose saved session is no longer OMP's.

**Authority boundary:** omp runs with approvals off (`approvalMode: yolo`) and your user's access in the task's directory, as the other runtimes do. Every omp process gets a `HOME` of Looper's own under the runtime root, holding a generated `models.yml` and a `--config` overlay that enables only the agent's model, so omp itself reads none of your `~/.omp`, `~/.claude`, `~/.codex`, `~/.agents` or `~/.env`; the agent's shell commands get your `HOME` back, without the provider's key, which is only in an environment variable `models.yml` names. Installed plugins load natively (skills, commands, agents); their hooks and their own MCP servers do not, and the MCP servers installed in Looper come in a plugin of that home.

**Docs:** https://github.com/foolzzz/looper/blob/v2.6.0/docs/architecture/agent-system.md#runtimes-llm-providers-and-agents

```bash
omp --version
curl -s http://127.0.0.1:8767/api/registry | python3 -m json.tool | grep -A4 '"rt-omp"'
  # An agent on OMP (PROVIDER_ID: an API-key provider), used by Workers, then undone:
curl -s -X POST http://127.0.0.1:8767/api/agents -H 'Content-Type: application/json' \
  -d '{"name": "omp/gpt-5.6-sol", "runtime_id": "rt-omp", "provider_id": "PROVIDER_ID", "model": "gpt-5.6-sol"}'
curl -s -X PUT http://127.0.0.1:8767/api/agent-settings/roles/worker -H 'Content-Type: application/json' -d '{"agent": "AGENT_ID"}'
curl -s -X PUT http://127.0.0.1:8767/api/agent-settings/roles/worker -H 'Content-Type: application/json' -d '{"agent": null}'
```

### Plugins and skills catalog

**Activation:** Nothing in the catalog loads until it is installed. In Settings, Plugins & skills catalog: "Import from this machine" copies your Claude Code plugins and personal skills (read only, from `$CLAUDE_CONFIG_DIR` or `~/.claude`); you can also upload a `SKILL.md` or a zip, import from a public `https://` git repository after a preview, or write a skill. Install an item globally ("Install globally", with role checkboxes) or in a project (its Skills tab), for some of `manager`, `planner`, `worker` and `reviewer`.

**Validation:** `GET /api/catalog` lists each item with its installs; each run's history page lists the plugins and skills it loaded.

**Disable / rollback:** Uninstall the item or turn its install off; delete it from the catalog. The next run of each agent goes without it; the Manager and a running Planner restart with `--resume`.

**Authority boundary:** Installed items run inside agents with every tool and no permission prompts; a plugin's own `SessionStart` hooks run. The import reads your Claude Code configuration only and copies no hooks, MCP servers, permissions or memory of yours; a plugin's own MCP servers do not load. Git imports are shallow clones without hooks, submodules, your git configuration or credentials, capped in size and time. Every installed item adds context: 3 plugins and 104 skills grew a minimal Opus request from 15,674 to 29,114 tokens, so install per role.

**Docs:** https://github.com/foolzzz/looper/blob/v2.6.0/docs/architecture/agent-system.md#the-capability-catalog-items-and-where-they-are-installed

```bash
curl -s -X POST http://127.0.0.1:8767/api/catalog/import
curl -s http://127.0.0.1:8767/api/catalog | python3 -m json.tool | grep -E '"(item_id|kind|name)"'
  # Install one item for Workers and Reviewers everywhere (ITEM_ID from the catalog):
curl -s -X POST http://127.0.0.1:8767/api/installs -H 'Content-Type: application/json' \
  -d '{"item_id": "ITEM_ID", "scope": "global", "roles": ["worker", "reviewer"]}'
  # Uninstall (INSTALL_ID from the answer):
curl -s -X DELETE http://127.0.0.1:8767/api/installs/INSTALL_ID
```

### MCP servers in the catalog

**Activation:** Off until installed. Add a server in Settings (stdio: command, arguments, environment; or http or sse: URL, headers) or with `POST /api/catalog/mcp`, or import the user-level `mcpServers` of this machine's `~/.claude.json`, read only. Then install it globally or in a project for some roles, like a plugin.

**Validation:** `GET /api/catalog` lists it as kind `mcp` with its values shown as `***`; each run records the names of the servers it mounted.

**Disable / rollback:** Uninstall it or turn its install off; delete the item.

**Authority boundary:** A stdio server is a command that every run of an installed role starts as your user; an HTTP server receives whatever the agents send it. Environment and header values are stored in the database, shown only as `***`, written for each run into a read-only `--mcp-config` file under the runtime root, never recorded in runs, and exported only with `--include-secrets`. `--strict-mcp-config` stays on, so a project's `.mcp.json`, claude.ai connectors and a plugin's own servers do not load.

**Docs:** https://github.com/foolzzz/looper/blob/v2.6.0/docs/architecture/agent-system.md#the-capability-catalog-items-and-where-they-are-installed

```bash
curl -s -X POST http://127.0.0.1:8767/api/catalog/mcp -H 'Content-Type: application/json' \
  -d '{"name": "fs-demo", "transport": "stdio", "command": "npx", "args": ["-y", "@modelcontextprotocol/server-filesystem", "."]}'
  # Install it for Workers (ITEM_ID from the answer), then uninstall it (INSTALL_ID):
curl -s -X POST http://127.0.0.1:8767/api/installs -H 'Content-Type: application/json' \
  -d '{"item_id": "ITEM_ID", "scope": "global", "roles": ["worker"]}'
curl -s -X DELETE http://127.0.0.1:8767/api/installs/INSTALL_ID
```

### Lessons drafts

**Activation:** Per project, `off` by default. Set the project's `distill_lessons` to `draft` (or `write`) on its Settings tab or with `PUT /api/projects/PROJECT_ID`. A task that then completes gets one more Planner turn that turns its journal into a Markdown document, `Lessons: ...`. With `draft` it waits on the project's Knowledge tab until you confirm it, optionally edited, or discard it; with `write` it goes straight into the project's knowledge. A Worker's or Reviewer's learning marked for the whole project becomes a draft in both modes.

**Validation:** `GET /api/projects/PROJECT_ID/knowledge/drafts` lists the drafts; the task page links to its draft.

**Disable / rollback:** Set `distill_lessons` back to `off`; discard a draft with `DELETE .../knowledge/drafts/DRAFT_ID` or delete a confirmed document on the Knowledge tab.

**Authority boundary:** The extra turn is a paid run on the Planner's agent. A draft is read by no agent until confirmed; a written or confirmed lesson joins the project's knowledge index, which every later Planner, Worker and Reviewer of the project reads, so `write` lets unreviewed text steer later tasks. Nothing leaves the database and the runtime root.

**Docs:** https://github.com/foolzzz/looper/blob/v2.6.0/docs/architecture/agent-system.md#project-execution-settings

```bash
curl -s -X PUT http://127.0.0.1:8767/api/projects/PROJECT_ID -H 'Content-Type: application/json' -d '{"distill_lessons": "draft"}'
curl -s http://127.0.0.1:8767/api/projects/PROJECT_ID/knowledge/drafts
  # Turn it off again:
curl -s -X PUT http://127.0.0.1:8767/api/projects/PROJECT_ID -H 'Content-Type: application/json' -d '{"distill_lessons": "off"}'
```

### Telegram and Lark channels

**Activation:** Off by default, and changed in this release: an enabled channel must list its senders. In Settings, or with `PUT /api/channel-configs/channel-telegram` or `channel-lark`, enable the channel and set `allowed_user_ids` (numeric Telegram user IDs) or `allowed_open_ids` (Lark `ou_...` open_ids), put the credential in the variable the setting names (Telegram's default is `LOOPER_TELEGRAM_BOT_TOKEN`; Lark needs `lark-cli` on `PATH`, signed in, and the app ID in `LARK_APP_ID`), then restart `looper serve` or the service.

**Validation:** `GET /api/channel-configs` returns each channel with its `start_problem`, `null` when it can start; the startup log line `agent system running on ... (channels=...)` lists the channels that started.

**Disable / rollback:** Set `enabled` to `false`, then restart.

**Authority boundary:** A listed sender reaches the Manager, which can run any command on this machine without permission prompts and start tasks. Anyone else's message is dropped and logged with the sender id only, with no reply. `channel_configs` stores variable names and allowlists, not secret values.

**Docs:** https://github.com/foolzzz/looper/blob/v2.6.0/README.md#channels

```bash
curl -s -X PUT http://127.0.0.1:8767/api/channel-configs/channel-telegram \
  -H 'Content-Type: application/json' \
  -d '{"enabled": true, "config": {"bot_token_env": "LOOPER_TELEGRAM_BOT_TOKEN", "allowed_user_ids": ["123456789"]}}'
curl -s http://127.0.0.1:8767/api/channel-configs
looper service restart   # or restart looper serve
  # To disable, then restart again:
curl -s -X PUT http://127.0.0.1:8767/api/channel-configs/channel-telegram \
  -H 'Content-Type: application/json' -d '{"enabled": false}'
```

## Known Limitations

- The `loopx` alias, the `~/.loopx` link and the `LOOPX_*` fallback go away in the next release.
- The HTTP API still has no authentication; it refuses other web pages, but any local process can call it. Keep the default `127.0.0.1` bind.
- Spend caps on API-key providers other than Anthropic's are soft and priced by Looper; a model without a price has no cap. The DeepSeek, Kimi and GLM (Z.ai) presets follow the vendors' documentation; real runs covered only CLIProxyAPI and GLM on BigModel.
- Codex: the cap can stop a run only at the end of a turn, a running Codex Worker cannot be steered (the Planner's message waits for the step's next decision), and stopping a Codex run does not end the shell command it is running.
- OMP: a running OMP Worker cannot be steered either. omp's `task` tool looks for subagent definitions in `.omp/agents` from the work directory upward, past the repository root, so a work directory under your home can pick up `~/.omp/agents`. Outside a git repository the work directory's own `AGENTS.md`, `CLAUDE.md` and `.omp/` are not read. omp's background requests (skill routing hints, compaction summaries) are not counted in cost or caps, a new process's first request mostly misses the prompt cache, and the first run under a runtime root unpacks a native library of about 167 MB.
- A plugin's own MCP servers do not load, and plugin agents and commands have not been verified in agents; skills have.
- Channel settings apply only after a restart; the allowlists have been tested against local stand-ins, not live Telegram or Lark traffic.
- A provider's `max_concurrency` is stored and checked but not enforced.

## 中文摘要

### 速览

LoopX 现在叫 **Looper**。任务的 Planner 现在是一个 Claude Code agent：它把需求拆成带验收标准的步骤，安排评审，失败重试或重新规划，把进度和经验记进任务日志，服务器重启后接着做。agent 不再读取你个人的 Claude Code 配置；它们加载和运行什么，由分层配置、项目知识与 skill，以及同时管理 MCP 服务器的能力目录决定。agent 现在由运行时、provider 和模型组成：Claude Code 可用自身登录、API key 或兼容 Anthropic 协议的 provider（GLM、DeepSeek、Kimi、CLIProxyAPI），也可以用 Codex 或 OMP（oh-my-pi）。运维方面有 `looper doctor`、`looper service`、每次改表前自动备份以及配置导出导入。上游 LoopX 控制面已全部移除。

**本版本包含破坏性变更。** 请重新运行 `install.sh` 升级：v2.5.0 的 `loopx update apply` 装不了改名后的 `looper` wheel。步骤见下方“从 v2.5.0 升级”。

#### 亮点

- **会规划、评审、续跑的任务。** Planner 把任务拆成 1 到 8 步，交给 Reviewer 评审，带反馈重试，重新规划，每 5 分钟检查运行中的 Worker，重启后从 PostgreSQL 里的计划续跑。（[#2](https://github.com/foolzzz/looper/pull/2)、[#4](https://github.com/foolzzz/looper/pull/4)、[#45](https://github.com/foolzzz/looper/pull/45)）
- **任务日志。** 失败、重试、决策、你的指令和会话切换都记入日志并带进下一轮；agent 换 provider 或运行时时先写交接摘要，新会话从续接简报开始；经验可以沉淀为项目知识。（[#46](https://github.com/foolzzz/looper/pull/46)、[#61](https://github.com/foolzzz/looper/pull/61)、[#66](https://github.com/foolzzz/looper/pull/66)）
- **可复现的 agent。** 每次运行的 system prompt 由有记录的分层组成（harness、角色、项目、任务、契约），agent、effort、环境变量和花费上限按系统、角色、项目、项目内角色逐层解析。（[#13](https://github.com/foolzzz/looper/pull/13)、[#17](https://github.com/foolzzz/looper/pull/17)、[#19](https://github.com/foolzzz/looper/pull/19)、[#50](https://github.com/foolzzz/looper/pull/50)）
- **带知识、skill 和上限的项目。** 项目背景、按需读取的文档、项目 skill、评审策略、每任务花费上限与“提高上限并继续”、项目页。（[#27](https://github.com/foolzzz/looper/pull/27)、[#32](https://github.com/foolzzz/looper/pull/32)、[#37](https://github.com/foolzzz/looper/pull/37)、[#43](https://github.com/foolzzz/looper/pull/43)、[#44](https://github.com/foolzzz/looper/pull/44)）

### 升级决策

**谁需要升级：**所有在 v2.5.0 上运行 `loopx serve` 的用户。只有依赖上游 LoopX 命令行（Goal、`loopx dispatch`、`loopx dashboard`、`loopx chat`、todo 或其他已删除的子命令）的用户应留在 v2.5.0，v2.6.0 已不再提供这些功能。

**解决了什么：**v2.5.0 把每个任务当作一个未经规划的步骤执行，重启后所有工作停止，操作者个人的 Claude Code 配置会混进每个 agent，Agents 页的大部分设置只保存不生效，且只能用 Claude Code 自身登录运行。v2.6.0 让任务能规划、评审、记日志并续跑；agent 可复现，可按层、按项目配置；新增带 MCP 服务器的能力目录、API key provider、Codex 和 OMP 运行时，每次运行的花费与上下文，`looper doctor`、`looper service`、改表前备份和配置导出导入；项目改名为 Looper。

**是否有破坏性变更：**有。LoopX 改名为 Looper（本版本保留 `loopx` 别名，`~/.loopx` 自动迁到 `~/.looper`，`LOOPER_*` 变量未设置时回退到 `LOOPX_*`）；v2.5.0 的 137 个 `loopx` 子命令删除了 134 个，包括 `update` 和 `init`；agent 不再加载你个人的 Claude Code 配置，导入的插件和 skill 只在安装的范围内加载；重启后任务自动续跑；配置按层解析，每个 agent 都显式传入模型，默认 `opus`；Telegram 和 Lark 必须配置发送者白名单；`/api/llm-profiles` 和若干 agent 配置字段被删除；没有 `pg_dump` 备份时 `looper serve` 默认不改表。详见“破坏性变更”和“从 v2.5.0 升级”。

**如何验证：**重新运行 `install.sh` 后，`looper --version` 显示 `looper 2.6.0`，`loopx --version` 先输出弃用提示再显示同一版本，`looper doctor` 通过（PostgreSQL、Claude Code CLI 及其登录、`pg_dump`）。`looper serve` 或 `looper service` 运行时，`/api/status` 返回 `"status": "running"` 及各项检查，`~/.loopx` 是指向 `~/.looper` 的链接。

**贡献者：**发布维护者 @foolzzz；社区贡献者 @michaelx1993，共 8 个 PR（#4 到 #11），涉及 Planner 监督、推荐 prompt、一处 Worker 修复和 CI（见“社区贡献者”）。

### 长程任务

- **Planner 是 Claude Code agent。** 它在任务存续期间保持一个 Claude 进程，把需求拆成 1 到 8 步，每步带验收标准、依赖和是否需要 Reviewer 通过。每次拿到结果后，它接受该步、送评审、带反馈重试（每步最多 2 次）、重新规划未开始的步骤或让任务失败，回复是经过严格校验的 JSON。发给 Planner 的对话由它的 Claude 处理，可以回复、转给运行中的 Worker 或追加步骤。每一轮 Planner 都是一次付费运行，记录为 `planner-TASK_ID`。（[#2](https://github.com/foolzzz/looper/pull/2)）
- **监督。** 每 300 秒（项目的 `supervise_interval_seconds`，设 0 关闭）Planner 检查运行中的 Worker，可以提醒或停止它。（[#4](https://github.com/foolzzz/looper/pull/4)）
- **状态入库，重启后续跑。** 计划、步骤和 agent 会话存在数据库而不是文件里。带有效计划、仍在运行的任务在启动时续跑：Planner 续接 Claude 会话，正在运行的步骤重跑，评审中的步骤换一个新 Reviewer。旧的计划和会话文件只导入一次。（[#45](https://github.com/foolzzz/looper/pull/45)）
- **任务日志与交接。** 接受的步骤、带经验的失败与重试、Planner 的决策、每条用户指令和会话切换都记入日志。Planner 每轮先带上你的完整指令，再带各类最新条目，Worker 的第一轮也会收到；任务页的 Findings 列出这些条目。Manager 或 Planner 无法续接会话时（换了运行时或 provider），旧会话先写交接摘要，新会话从续接简报开始。（[#46](https://github.com/foolzzz/looper/pull/46)、[#66](https://github.com/foolzzz/looper/pull/66)）
- **花费上限。** 项目可以限制每个任务的花费（`task_budget_usd`，到上限立即失败或多一轮收尾）和每次运行的花费（`run_budget_usd`）；任务页显示花费占上限的比例，80% 起提醒，因上限失败的任务可以提高上限继续。（[#37](https://github.com/foolzzz/looper/pull/37)、[#43](https://github.com/foolzzz/looper/pull/43)）

### Agent 与配置

- **与个人配置隔离。** 每个 agent 启动 Claude Code 时都带 `--setting-sources project`、`--strict-mcp-config`，并排除工作目录所在仓库之上和 `~/.claude` 里的所有 `CLAUDE.md`，关闭自动记忆。项目自己的 `CLAUDE.md` 和 `.claude/settings.json` 仍会加载，登录不受影响。（[#17](https://github.com/foolzzz/looper/pull/17)）
- **分层且有记录的 system prompt。** Planner、Worker 和 Reviewer 依次是 harness、角色 prompt、项目背景、任务和代码维护的契约；Manager 是 harness、角色 prompt 和放置规则。每次运行记录 prompt、哈希和各层，历史页可见。Reviewer 有自己的 agent 配置行。推荐 prompt 有跟踪：未修改过的 prompt 跟随新默认值，改过的保留并可重置。（[#8](https://github.com/foolzzz/looper/pull/8)、[#9](https://github.com/foolzzz/looper/pull/9)、[#13](https://github.com/foolzzz/looper/pull/13)、[#17](https://github.com/foolzzz/looper/pull/17)、[#19](https://github.com/foolzzz/looper/pull/19)）
- **分层配置。** harness、agent、effort、环境变量和单次运行上限按系统、角色、项目、项目内角色解析，分别在 Settings、Agents 页和项目的 Settings 页编辑；每次运行记录每项设置的来源。（[#19](https://github.com/foolzzz/looper/pull/19)、[#50](https://github.com/foolzzz/looper/pull/50)）
- **运行时、provider 与 agent。** Settings 里注册运行时、provider（含模型目录、价格，API key 单独存放）和 agent。Claude Code 可用自身登录、Anthropic API key 或兼容 Anthropic 协议的接口，内置 GLM（BigModel、Z.ai）、DeepSeek、Kimi（国内、国际）和本机 CLIProxyAPI 预设以及价格表。Codex 和 OMP（oh-my-pi 的 `omp`）用 API key provider 运行全部角色，各自使用 Looper 自己的家目录，而不是操作者的。可按层、按项目或单个任务（`agent_overrides`）选择 agent。（[#62](https://github.com/foolzzz/looper/pull/62)、[#67](https://github.com/foolzzz/looper/pull/67)、[#68](https://github.com/foolzzz/looper/pull/68)、[#70](https://github.com/foolzzz/looper/pull/70)）
- **能力目录。** 从本机导入、以 `SKILL.md` 或 zip 上传、从公开 git 仓库克隆或在 Settings 里编写的插件和 skill，以及 MCP 服务器，都是目录条目，可全局或在某个项目里为部分角色安装。项目 skill 也并入目录。（[#22](https://github.com/foolzzz/looper/pull/22)、[#48](https://github.com/foolzzz/looper/pull/48)、[#49](https://github.com/foolzzz/looper/pull/49)、[#51](https://github.com/foolzzz/looper/pull/51)）
- **项目。** 进入每个任务 agent prompt 的项目背景，agent 按需读取的知识文档（文本、上传或项目目录里的文件），项目 skill，执行配置（评审策略、监督、上限），经验草稿，以及带 Overview、Knowledge、Skills、Settings 页签的项目页。（[#13](https://github.com/foolzzz/looper/pull/13)、[#27](https://github.com/foolzzz/looper/pull/27)、[#32](https://github.com/foolzzz/looper/pull/32)、[#37](https://github.com/foolzzz/looper/pull/37)、[#44](https://github.com/foolzzz/looper/pull/44)、[#61](https://github.com/foolzzz/looper/pull/61)）
- **花费与上下文。** 每次运行记录 token（含缓存）、上下文规模、压缩次数和花费；任务按角色汇总花费，agent 按会话和天汇总用量，历史页显示各轮的上下文变化。（[#24](https://github.com/foolzzz/looper/pull/24)）

### 破坏性变更

1. **改名为 Looper。** 命令、Python 包和 wheel 都叫 `looper`；`looper version --format json` 返回 `name: looper` 和 `schema_version: looper_version_v0`。仅本版本过渡：`loopx` 是别名，先输出弃用提示再运行 `looper`；第一次 `looper serve` 或 `looper service install` 把 `~/.loopx` 改名为 `~/.looper`，并留下 `~/.loopx` 链接；未设置的 `LOOPER_*` 变量回退到对应的 `LOOPX_*` 并警告；服务名为 `com.looper.serve`，`looper service install` 会移除 `com.loopx.serve`。默认库名仍是 `loopx`。（[#64](https://github.com/foolzzz/looper/pull/64)）
2. **上游 LoopX 命令行已删除。** v2.5.0 的 `loopx` 列出 137 个子命令。保留 `serve` 和 `version`，`doctor` 是一个全新的检查；其余 134 个都已删除，包括 `update`（改为重新运行 `install.sh`）、`init`（它写的文件没有任何地方读取）、`status`、`todo`、`dispatch`、`dashboard` 和 `chat`，以及别名 `connect`、`goal-alignment`、`amendment-proposal` 和全局选项 `--registry`、`--runtime-root`、`--format`。同时删除：上游模块和 Chat 包，`loopx-lark-provider` 与 `loopx-openviking-*` 命令，`deepseek-harness` extra，打包的工作流 skill，以及源码快照安装脚本。（[#31](https://github.com/foolzzz/looper/pull/31)、[#35](https://github.com/foolzzz/looper/pull/35)）
3. **agent 不再加载你个人的 Claude Code 配置，插件和 skill 只在安装的范围内加载。** v2.5.0 中每个 agent 都会读取 `~/.claude`：`CLAUDE.md`、用户设置（模型、effort、环境变量、权限）、hook、MCP 服务器、插件和 skill。现在这些都不再加载。请把插件和 skill 导入目录，再为需要的角色全局或在项目中安装；导入的条目在安装之前不会被任何 agent 加载。（[#17](https://github.com/foolzzz/looper/pull/17)、[#48](https://github.com/foolzzz/looper/pull/48)）
4. **重启后任务续跑。** 上一个服务器留下的、带有效计划的运行中任务在启动时继续执行并产生花费，不再被标记为停止。v2.5.0 服务器留下的运行中任务没有这样的计划，仍会被标记为停止。（[#45](https://github.com/foolzzz/looper/pull/45)）
5. **配置按层解析，每个 agent 都显式传入模型。** harness、agent、effort、环境变量和单次运行上限来自系统、角色、项目和项目内角色各层。每个角色都运行一个 agent，未选择时为 `claude-code/opus`，所以原本 Claude Code 默认模型更便宜的账号现在会用 Opus。v2.5.0 Agents 页保存但未生效的模型会成为该角色的 agent 并开始生效。每个 agent 还会带上默认 harness，Manager 改为用用户的语言回答。（[#19](https://github.com/foolzzz/looper/pull/19)、[#50](https://github.com/foolzzz/looper/pull/50)、[#62](https://github.com/foolzzz/looper/pull/62)）
6. **Telegram 和 Lark 必须配置发送者白名单。** 渠道只转发白名单里的发送者（`allowed_user_ids`、`allowed_open_ids`）；已启用但名单为空或无效的渠道不会启动。Telegram 名单为空不再表示所有人，`LOOPX_TELEGRAM_ALLOWED_USERS` 不再读取。（[#23](https://github.com/foolzzz/looper/pull/23)）
7. **删除或变更的 API。** 删除 `/api/llm-profiles`。agent 配置不再返回 `runtime`、`llm_profile_id`、`model` 和 `permission_mode`，更新时带前三者之一返回 400（角色的模型就是它的 agent，用 `PUT /api/agent-settings/roles/ROLE` 设置）。任务的 `config` 是 JSON 对象而不是 JSON 文本。`GET /api/llm-records?role=worker` 只列 Worker（另有 `role=reviewer` 和 `role=planner`）。超过 8 MiB 的请求体返回 413。发给 Planner 的对话不再直接变成一个步骤。（[#2](https://github.com/foolzzz/looper/pull/2)、[#41](https://github.com/foolzzz/looper/pull/41)、[#42](https://github.com/foolzzz/looper/pull/42)、[#50](https://github.com/foolzzz/looper/pull/50)、[#62](https://github.com/foolzzz/looper/pull/62)）
8. **没有备份不改表。** 表结构将要变化时，`looper serve` 先写一份 `pg_dump` 备份；没有可用的 `pg_dump` 或 `LOOPER_BACKUP_CMD`，或者备份失败时，它在改动任何东西之前退出。`--skip-backup` 不备份直接迁移。`looper config import --apply` 拒绝有待执行迁移的数据库。（[#60](https://github.com/foolzzz/looper/pull/60)）

其他影响花费或权限的变化：所有 agent，包括 Manager 和 Planner，都拥有全部工具且无需权限确认；Planner 不改文件只靠它的角色 prompt 约束。Worker 和 Reviewer 也有了 system prompt。（[#13](https://github.com/foolzzz/looper/pull/13)、[#23](https://github.com/foolzzz/looper/pull/23)）

### 从 v2.5.0 升级

1. **用 `install.sh` 安装。** 它从最新 release 的 wheel 安装 `looper`，并先卸载同一工具（uv、pipx 或 pip）装的 `loopx` 包；`~/.loopx` 里的数据保留。不要用 v2.5.0 的 `loopx update apply`：它让 pip 安装名为 `loopx` 的包，pip 会拒绝 `looper` wheel。
2. **重命名环境变量。** 在 shell 配置和 `.env` 里把 `LOOPX_DATABASE_URL` 改为 `LOOPER_DATABASE_URL`，其他 `LOOPX_*` 改为 `LOOPER_*`。本版本中旧名仍可用，但会警告。
3. **准备好首次启动的备份。** v2.5.0 的数据库有待执行的表结构变化，首次启动会先用 `pg_dump --format=custom` 备份到 `~/.looper/backups/` 再迁移。请把主版本不低于服务器的 `pg_dump` 放到 `PATH` 或用 `LOOPER_PG_DUMP` 指定（macOS：`brew install libpq`）；PostgreSQL 在 Docker 里时，把 `LOOPER_BACKUP_CMD` 设为向 stdout 输出备份的命令。`looper serve --skip-backup` 不备份直接迁移。
4. **启动一次。** `looper serve`（或第 5 步）把 `~/.loopx` 迁到 `~/.looper`，做备份并在日志里给出恢复命令，然后迁移数据库：删除 LLM profile 和未使用的 agent 配置列，各角色保存的模型变成它的 agent，遗留的运行中任务标记为停止。
5. **按需作为服务运行。** 在带有 `LOOPER_*` 变量的 shell 里运行 `looper service install`；它把这些变量写进服务定义，如有 `com.loopx.serve` 则先移除，然后启动 `com.looper.serve`。变量变化后重新运行一次。
6. **重新开启渠道。** 在 Settings 里为 Telegram 和 Lark 填写发送者白名单，然后重启。
7. **重新安装需要的插件和 skill。** Settings 的 Plugins & skills catalog，点 “Import from this machine”，再为需要的角色全局或在项目中安装各条目。MCP 服务器同样可从 `~/.claude.json` 导入。
8. **检查 agent 和花费。** Settings 和 Agents 页显示每个角色运行的 agent 及其来源；除非另选，每个角色都运行 Opus。
9. **检查。** 运行 `looper doctor`，使用服务时再运行 `looper service status`。

```bash
curl -fsSL https://raw.githubusercontent.com/foolzzz/looper/main/install.sh | bash
export LOOPER_DATABASE_URL="postgresql://localhost:5432/loopx"   # 库名不变
looper doctor                     # 按提示修复，包括 pg_dump
looper serve                      # 首次启动：迁移 ~/.loopx、备份、迁移数据库
  # 或者不用 looper serve，改为后台服务：
looper service install && looper service status
```

**回退到 v2.5.0。** 停止 Looper（装了服务就运行 `looper service uninstall`），把数据库重建为空库并恢复首次启动日志里给出的迁移前备份（`pg_restore --no-owner --dbname "$LOOPER_DATABASE_URL" FILE`），再换回 v2.5.0 的 wheel，例如 `uv tool uninstall looper && uv tool install "loopx @ https://github.com/foolzzz/looper/releases/download/v2.5.0/loopx-2.5.0-py3-none-any.whl"`。`install.sh` 总是安装最新 release，不能用来回退。v2.5.0 读取的 `~/.loopx` 仍链接到 `~/.looper`，并使用 `LOOPX_*` 变量名。

### 可选能力启用与使用

#### looper service

**启用：**按命令启用；安装之前不会有任何后台进程。`looper service install` 写入名为 `com.looper.serve` 的 launchd LaunchAgent（macOS）或 systemd 用户服务（Linux）并启动；它在登录时运行 `looper serve`，崩溃后自动拉起，日志写到 runtime root 的 `logs/serve.log`。服务运行执行 `install` 的那个 `looper`，工作目录为当前目录，并从当前 shell 复制 `PATH`、locale 和代理设置、`CLAUDE_CONFIG_DIR` 以及 `LOOPER_*`、`ANTHROPIC_*`、`LARK_*` 变量（`--env NAME` 可追加；另有 `--port`、`--runtime-root`、`--label` 选项）。端口被其他进程占用时不会启动。Linux 上用 `loginctl enable-linger $USER` 可在未登录时保持运行。

**验证：**`looper service status` 显示是否已安装、是否运行、PID、上次退出、日志和 `GET /api/status`，只有服务可用时才返回 0；`looper doctor` 里有 Service 一行。

**停用 / 回退：**`looper service uninstall` 停止服务并删除服务定义，数据库和 runtime root 不受影响。`looper service restart` 重启；要修改变量请重新运行 `install`。

**权限边界：**它以你的用户身份在你登录期间无人值守地运行 `looper serve`，因此无需权限确认的 agent、崩溃后续跑的任务和无认证的本机 API 在这段时间里一直有效。服务定义文件保存复制来的变量，可能包括数据库密码和 provider 凭据，权限为 0600。它不安装系统级服务，也不需要 root。

**文档：**https://github.com/foolzzz/looper/blob/v2.6.0/README.md#4-run-as-a-service

```bash
looper service install
looper service status
curl -s http://127.0.0.1:8767/api/status
  # 停用：
looper service uninstall
```

#### Configuration export and import

**启用：**按命令使用。`looper config export FILE` 把 agent 配置写成 `looper-config/v1` JSON：配置层和角色 prompt，运行时、provider 和 agent，带文件和 MCP 服务器的能力目录，全局安装和渠道；`--include-projects` 再加上每个项目的设置、知识、自有 skill 和安装。`looper config import FILE` 预览将要新增、修改、保留和跳过的内容以及需要补填的密钥；`--apply` 在一个事务里写入。两者都直接访问 `LOOPER_DATABASE_URL` 指向的数据库，服务器不必运行。Settings 的 “Move to another machine” 也能完成这两件事。以 `loopx-config/v1` 导出的文件仍可导入。

**验证：**预览按分区列出每项变化；同一文件再导入一次时显示没有需要修改的内容。

**停用 / 回退：**没有需要关闭的开关。应用导入只会原地更新条目，不删除任何内容；要撤销，请恢复应用前的数据库备份。Settings 里上传但未应用的导入一小时后过期。

**权限边界：**导入会改变每个 agent 加载和运行的内容（安装、harness、agent、渠道）。密钥（provider API key、MCP 环境变量和 header 值、渠道密钥）默认导出为占位符，只有 `--include-secrets` 才以明文写出；占位符不会覆盖已保存的密钥。本地路径（项目目录、条目来源、运行时可执行文件）不会导出。Settings 上传的文件最大 256 MiB，以 0600 权限存放在 runtime root 下，直到应用、取消或过期。

**文档：**https://github.com/foolzzz/looper/blob/v2.6.0/docs/architecture/agent-system.md#moving-the-configuration-export-and-import

```bash
looper config export looper-config.json --include-projects
  # 在另一台机器上：
looper config import looper-config.json           # 只预览
looper config import looper-config.json --apply
```

#### API-key providers and agents

**启用：**默认不启用：在某一层或某个任务选择其他 agent 之前，所有角色都运行内置 agent `claude-code/opus`（Claude Code 自身登录）。在 Settings 里添加 provider：选择预设（GLM 的 BigModel 或 Z.ai、DeepSeek、Kimi 国内或国际、本机 CLIProxyAPI），或填写 Anthropic API 或其他兼容 Anthropic 协议的接口，再粘贴 key。然后添加 agent（运行时、provider、模型、默认 effort），在 Settings 里为所有角色选择，在 Agents 页为单个角色选择，在项目的 Settings 页为项目选择，或在 New Task 对话框里为单个任务选择。

**验证：**`GET /api/registry` 列出运行时、provider（key 显示为 `***`）、带计价方式的 agent、预设和内置价格；`GET /api/agent-settings` 显示每个角色解析到的 agent 及其所在层；每次运行记录它的 agent 和 `cost_source`。

**停用 / 回退：**把该层或项目的 agent 设回 `null`，角色重新继承 `claude-code/opus`，然后删除 agent 和 provider（仍被引用时返回 409）。常驻的 Manager 或 Planner 换 provider 时，会在交接后开始新会话。

**权限边界：**key 存在数据库里，显示为 `***`，不记入运行记录，只有 `--include-secrets` 才会导出，只交给使用该 provider 的运行；这些运行的 prompt、代码和工具输出会发往该 provider。agent 仍拥有全部工具且无需权限确认。在 Anthropic 官方 API 之外的 provider 上，Looper 按自己的价格表（2026-10-14 的美元标价）计价，单次运行上限是软上限：越过上限的那次请求仍会发出；没有价格的模型只记录 token，不受花费上限约束。

**文档：**https://github.com/foolzzz/looper/blob/v2.6.0/docs/architecture/agent-system.md#runtimes-llm-providers-and-agents

```bash
curl -s http://127.0.0.1:8767/api/registry | python3 -m json.tool | grep -E '"(agent_id|name|model)"'
  # 为所有角色选择一个 agent（AGENT_ID 取自上面的 registry），读回，再恢复内置：
curl -s -X PUT http://127.0.0.1:8767/api/agent-settings/system -H 'Content-Type: application/json' -d '{"agent": "AGENT_ID"}'
curl -s http://127.0.0.1:8767/api/agent-settings
curl -s -X PUT http://127.0.0.1:8767/api/agent-settings/system -H 'Content-Type: application/json' -d '{"agent": null}'
```

**权限边界：**Looper 用 `codex exec --dangerously-bypass-approvals-and-sandbox` 运行 Codex：没有审批也没有沙箱，在任务目录里拥有你用户的权限，与 Claude Code agent 相同。每次运行在 runtime root 下有自己的 `CODEX_HOME`，只包含 Looper 写入的 `config.toml` 和 `AGENTS.md`；不会读取你的 `~/.codex` 和 `~/.agents/skills`。key 通过一个 Codex 的 shell 命令拿不到的变量传入。已安装的 MCP 服务器会传入（stdio 和 HTTP；SSE 不传）；skill 只读挂载；插件的 hook、命令和 agent 不加载。

**启用：**安装 oh-my-pi 的 `omp` CLI（已在 18.4.3 上验证），让它出现在 `looper serve` 的 `PATH` 上；serve 启动时会注册运行时 `omp`。注册一个提供 `openai-responses`、`openai-chat` 或 `anthropic-messages` 的 API key provider（例如 CLIProxyAPI 预设），在 `omp` 上用这个 provider 和一个模型添加 agent，再为某个角色、项目或任务选择它。不使用 omp 自身的登录。

**停用 / 回退：**在该层选择其他 agent 或设为 `null` 继承，再删除这个 agent。`looper serve` 启动时会删除没有运行中进程使用的 OMP 家目录，以及已保存会话不再属于 OMP 的 agent 的会话目录。

**权限边界：**omp 以关闭审批的方式运行（`approvalMode: yolo`），在任务目录里拥有你用户的权限，与其他运行时相同。每个 omp 进程的 `HOME` 都指向 runtime root 下 Looper 自己的家目录，里面只有生成的 `models.yml` 和只启用该 agent 模型的 `--config` 覆盖文件，所以 omp 本身不会读取你的 `~/.omp`、`~/.claude`、`~/.codex`、`~/.agents` 或 `~/.env`；agent 的 shell 命令会拿回你的 `HOME`，但拿不到 provider 的 key，key 只在 `models.yml` 指名的环境变量里。已安装的插件原生加载（skill、命令、agent）；插件的 hook 和自带的 MCP 服务器不加载，Looper 里安装的 MCP 服务器通过该家目录里的一个插件提供。

#### Plugins and skills catalog

**启用：**目录里的条目在安装之前都不会加载。在 Settings 的 Plugins & skills catalog 中，“Import from this machine” 复制你的 Claude Code 插件和个人 skill（只读，来自 `$CLAUDE_CONFIG_DIR` 或 `~/.claude`）；也可以上传 `SKILL.md` 或 zip，预览后从公开的 `https://` git 仓库导入，或直接编写 skill。全局安装（“Install globally”，勾选角色）或在项目中安装（项目的 Skills 页），角色可选 `manager`、`planner`、`worker`、`reviewer`。

**验证：**`GET /api/catalog` 列出每个条目及其安装位置；每次运行的历史页列出它加载的插件和 skill。

**停用 / 回退：**卸载条目或关闭它的安装，或从目录中删除。各 agent 的下一次运行就不再加载它；Manager 和运行中的 Planner 会用 `--resume` 重启。

**权限边界：**已安装的条目在拥有全部工具、无需权限确认的 agent 里运行；插件自己的 `SessionStart` hook 会执行。导入只读取你的 Claude Code 配置，不复制你的 hook、MCP 服务器、权限或记忆；插件自带的 MCP 服务器不加载。git 导入是浅克隆，不运行 hook、不拉子模块、不用你的 git 配置和凭据，并限制大小和时间。每个已安装条目都会增加上下文：3 个插件和 104 个 skill 让一次最小的 Opus 请求从 15,674 个 token 增加到 29,114 个，所以请按角色安装。

#### MCP servers in the catalog

**启用：**安装之前不生效。在 Settings 里添加服务器（stdio：命令、参数、环境变量；http 或 sse：URL、header），或用 `POST /api/catalog/mcp`，或只读导入本机 `~/.claude.json` 里用户级的 `mcpServers`。然后像插件一样，全局或在项目中为部分角色安装。

**验证：**`GET /api/catalog` 中它的类型为 `mcp`，值显示为 `***`；每次运行记录它挂载的服务器名称。

**停用 / 回退：**卸载或关闭它的安装，或删除该条目。

**权限边界：**stdio 服务器是一个命令，已安装角色的每次运行都会以你的用户身份启动它；HTTP 服务器会收到 agent 发给它的所有内容。环境变量和 header 值存在数据库里，只显示为 `***`，每次运行写入 runtime root 下只读的 `--mcp-config` 文件，不记入运行记录，只有 `--include-secrets` 才会导出。`--strict-mcp-config` 保持开启，所以项目的 `.mcp.json`、claude.ai 连接器和插件自带的服务器都不会加载。

**文档：**https://github.com/foolzzz/looper/blob/v2.6.0/docs/architecture/agent-system.md#the-capability-catalog-items-and-where-they-are-installed

```bash
curl -s -X POST http://127.0.0.1:8767/api/catalog/mcp -H 'Content-Type: application/json' \
  -d '{"name": "fs-demo", "transport": "stdio", "command": "npx", "args": ["-y", "@modelcontextprotocol/server-filesystem", "."]}'
  # 为 Worker 安装（ITEM_ID 取自返回结果），再卸载（INSTALL_ID）：
curl -s -X POST http://127.0.0.1:8767/api/installs -H 'Content-Type: application/json' \
  -d '{"item_id": "ITEM_ID", "scope": "global", "roles": ["worker"]}'
curl -s -X DELETE http://127.0.0.1:8767/api/installs/INSTALL_ID
```

#### Lessons drafts

**启用：**按项目启用，默认 `off`。在项目的 Settings 页或用 `PUT /api/projects/PROJECT_ID` 把 `distill_lessons` 设为 `draft`（或 `write`）。之后完成的任务会多一轮 Planner，把任务日志整理成一份 Markdown 文档 `Lessons: ...`。`draft` 时它留在项目的 Knowledge 页，等你确认（可先编辑）或丢弃；`write` 时直接写入项目知识。Worker 或 Reviewer 标为适用于整个项目的经验，在两种模式下都会成为草稿。

**验证：**`GET /api/projects/PROJECT_ID/knowledge/drafts` 列出草稿；任务页链接到它的草稿。

**停用 / 回退：**把 `distill_lessons` 设回 `off`；用 `DELETE .../knowledge/drafts/DRAFT_ID` 丢弃草稿，或在 Knowledge 页删除已确认的文档。

**权限边界：**多出的一轮是 Planner agent 的一次付费运行。草稿在确认前没有 agent 会读取；写入或确认后的经验进入项目知识索引，之后该项目的每个 Planner、Worker 和 Reviewer 都会读到，所以 `write` 会让未经审阅的文字影响后续任务。内容不会离开数据库和 runtime root。

**文档：**https://github.com/foolzzz/looper/blob/v2.6.0/docs/architecture/agent-system.md#project-execution-settings

```bash
curl -s -X PUT http://127.0.0.1:8767/api/projects/PROJECT_ID -H 'Content-Type: application/json' -d '{"distill_lessons": "draft"}'
curl -s http://127.0.0.1:8767/api/projects/PROJECT_ID/knowledge/drafts
  # 关闭：
curl -s -X PUT http://127.0.0.1:8767/api/projects/PROJECT_ID -H 'Content-Type: application/json' -d '{"distill_lessons": "off"}'
```

#### Telegram and Lark channels

**启用：**默认关闭，且本版本有变化：启用的渠道必须列出发送者。在 Settings 里，或用 `PUT /api/channel-configs/channel-telegram` 或 `channel-lark`，启用渠道并设置 `allowed_user_ids`（Telegram 数字用户 ID）或 `allowed_open_ids`（Lark 的 `ou_...` open_id），把凭据放进设置所指的环境变量（Telegram 默认 `LOOPER_TELEGRAM_BOT_TOKEN`；Lark 需要 `PATH` 上已登录的 `lark-cli`，app ID 放在 `LARK_APP_ID`），然后重启 `looper serve` 或服务。

**验证：**`GET /api/channel-configs` 返回每个渠道及其 `start_problem`，可以启动时为 `null`；启动日志 `agent system running on ... (channels=...)` 列出已启动的渠道。

**停用 / 回退：**把 `enabled` 设为 `false`，然后重启。

**权限边界：**白名单里的发送者可以直接对话 Manager，而 Manager 无需权限确认就能在本机运行任何命令并启动任务。其他人的消息会被丢弃，日志只记发送者 ID，不回复。`channel_configs` 只保存变量名和白名单，不保存密钥值。

**文档：**https://github.com/foolzzz/looper/blob/v2.6.0/README.md#channels

```bash
curl -s -X PUT http://127.0.0.1:8767/api/channel-configs/channel-telegram \
  -H 'Content-Type: application/json' \
  -d '{"enabled": true, "config": {"bot_token_env": "LOOPER_TELEGRAM_BOT_TOKEN", "allowed_user_ids": ["123456789"]}}'
curl -s http://127.0.0.1:8767/api/channel-configs
looper service restart   # 或重启 looper serve
  # 停用后再重启一次：
curl -s -X PUT http://127.0.0.1:8767/api/channel-configs/channel-telegram \
  -H 'Content-Type: application/json' -d '{"enabled": false}'
```

### 已知限制

- `loopx` 别名、`~/.loopx` 链接和 `LOOPX_*` 回退将在下个版本移除。
- HTTP API 仍没有认证；它拒绝其他网页的请求，但本机任何进程都能调用。请保持默认的 `127.0.0.1` 绑定。
- Anthropic 官方以外的 API key provider 上，花费上限是由 Looper 计价的软上限；没有价格的模型没有上限。DeepSeek、Kimi 和 GLM（Z.ai）预设按厂商文档填写，真实运行只覆盖了 CLIProxyAPI 和 GLM（BigModel）。
- Codex：上限只能在一轮结束时停止运行；运行中的 Codex Worker 不能被引导（Planner 的消息留给该步的下一次决策）；停止 Codex 运行不会结束它正在执行的 shell 命令。
- OMP：运行中的 OMP Worker 同样不能被引导。omp 的 `task` 工具从工作目录一路向上查找 `.omp/agents` 里的子 agent 定义，越过仓库根也不停，所以工作目录在你的家目录下时可能读到 `~/.omp/agents`。工作目录不在 git 仓库里时，不读取它自己的 `AGENTS.md`、`CLAUDE.md` 和 `.omp/`。omp 的后台请求（skill 路由提示、压缩摘要）不计入花费和上限；每个新进程的首个请求基本不命中提示缓存；每个 runtime root 第一次运行会解压约 167 MB 的原生库。
- 插件自带的 MCP 服务器不加载；插件里的 agent 和命令尚未在 agent 中验证，只验证了 skill。
- 渠道设置需要重启才生效；白名单只用本地替身测试过，没有经过真实的 Telegram 或 Lark 流量。
- provider 的 `max_concurrency` 只保存和校验，不实际限制并发。

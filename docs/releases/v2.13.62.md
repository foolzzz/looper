# Looper v2.13.62

## Release Decision

**Who should upgrade:** Operators who run the dashboard or `looper service`, and anyone who scripts the removed task-configuration HTTP routes. Nobody else needs to act.

**What this release solves:** [#467](https://github.com/foolzzz/looper/pull/467) moves task configuration, project placement, Agent selection and budget continuation to the versioned API (`/api/v1/tasks/*`) with typed results. The dashboard's task pages now use it.

**Breaking changes:** Yes. Four legacy HTTP methods are removed and no longer match a route: `PUT /api/tasks/{task id}/config`, `PUT /api/tasks/{task id}/project`, `POST /api/tasks/{task id}/continue` and `PUT /api/tasks/{task id}/agents`. A script that calls them must switch to the v1 routes below. No stored data or configuration changed.

**How to verify:** Check the installed version, then edit the configuration of a task that has not started, in a test project, with the operator token.

**Contributors:** Maintainer @foolzzz authored [#467](https://github.com/foolzzz/looper/pull/467); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.62
```

## Behavior changes

- **New v1 operations (`looper/agents/v1_domains/task_configuration.py`, `looper/agents/v1_domains/__init__.py`):** the `task_configuration` domain joins `MODULES`. All operations are `POST` with a JSON body that rejects unknown keys, so unknown fields, roles and wrong types are refused by schema validation before the service runs (the error text now says the schema check failed):
  - `tasks.configure` (`task_id`, optional `requirement`, `work_dir`, `config`): a write. Only a task in `init` can be edited. A new requirement is kept as a new version, `work_dir` is resolved before it is saved, and the task is read back. A failed configuration write now returns an error instead of being reported as done.
  - `tasks.move` (`task_id`, `project_id`): a write. The task moves to the other project and the running router's placement is updated too.
  - `tasks.agents` (`task_id`, `profiles`, `concurrency`, `system_prompt_modes`): a write. `null` clears a choice, a finished task cannot be changed, and lowering concurrency does not interrupt running work. Raising a limit wakes tasks that were waiting for a slot.
  - `tasks.continue` (`task_id`, `task_budget_usd`): `high` risk. Only a task that failed at its budget qualifies, and the new cap must be above what the task has spent. It sets the task's own cap when it has one, otherwise the project's per-task cap, which also affects the project's other tasks. It then sends one `AT_CAP` restart.
- **Continue confirmation:** a client token gets the two-step confirmation, whose text names the scope (this task's own cap, or the project's per-task cap and its effect on other tasks). The confirmation is bound to the project and cap scope seen at request time; if either changed before it is confirmed, the continue is refused with a 409 and must be requested again. With the operator credential it runs in one request (see v2.13.59).
- **Typed results:** the four operations declare full results (Agent choices include the Profile, the effective prompt mode and where each concurrency value comes from). The result of the existing `concurrency` Manager operation gains typed before/after values, task override and default.
- **Dashboard (`web/src/lib/api.ts`):** `updateTaskConfig`, `setTaskProject`, `setTaskAgents` and `continueTaskAtCap` call the v1 routes through `callV1`. A pending-confirmation (202) answer is never confirmed automatically; it surfaces as an error.
- **Legacy routes (`looper/agents/http_server.py`):** the four methods above and their route patterns are deleted. The configuration handler becomes a function that returns its result, with the same checks.
- **Process cleanup (`looper/agents/proc_tree.py`):** when ending a turn's process tree is cancelled while it prepares, the saved tree is still ended (identities checked again before any signal) and the agent is reaped.
- **Docs and tests:** the client-skill RFC and the long-horizon context plan record the migration. New `tests/test_api_v1_task_configuration.py` and `tests/test_api_v1_task_configuration_db.py`; a `proc_tree` test; existing task, project, restart and continue-at-cap tests and the dashboard tests were moved to the v1 calls. The pull request reports added lines: tests 426, production 176 (fixtures excluded).
- **Model-visible changes:** None. Manager, Worker, Planner and Reviewer prompts are unchanged and no Manager Tool is added or changed; only the declared result schema of the existing `concurrency` operation is typed. API clients (and an agent skill built on the OpenAPI document) see the new operations and their schemas.

## Upgrade and rollback

Re-run `install.sh` once v2.13.62 is published. No data migration. Replace any caller of the four removed routes before upgrading. Rolling back to v2.13.61 brings those routes back and removes the v1 task-configuration operations; a dashboard and a service from the same version always agree, so do not mix versions.

### 行为变化与入口

- 新增 v1 操作（`v1_domains/task_configuration.py`、`v1_domains/__init__.py`）：`task_configuration` 领域加入 `MODULES`。均为带 JSON 请求体的 `POST`，拒绝未知键，未知字段、角色和错误类型在服务前由 schema 校验拒绝（错误文案改为 schema 校验失败）：
  - `tasks.configure`（`task_id`，可选 `requirement`、`work_dir`、`config`）：写操作。仅 `init` 状态的任务可编辑；新需求保留为新版本，`work_dir` 解析后才保存，并读回任务。配置写入失败现在返回错误，不再当作完成。
  - `tasks.move`（`task_id`、`project_id`）：写操作。任务移到另一个项目，运行中路由的归属同步更新。
  - `tasks.agents`（`task_id`、`profiles`、`concurrency`、`system_prompt_modes`）：写操作。`null` 清除选择，已完成的任务不可改，降低并发不中断运行中的工作；升高上限会唤醒等待名额的任务。
  - `tasks.continue`（`task_id`、`task_budget_usd`）：`high` 风险。仅预算失败的任务可续跑，新额度须高于已花费。任务有独立额度时只改该任务，否则改项目的每任务额度，同时影响项目其他任务；随后发送一次 `AT_CAP` 重启。
- 续跑确认：客户端令牌需两步确认，确认文案写明影响范围（该任务独立额度，或项目每任务额度及对其他任务的影响）。确认绑定请求时的项目与额度作用范围，确认前若变化，则以 409 拒绝，须重新请求。操作者凭据单次执行（见 v2.13.59）。
- 类型化结果：四个操作声明完整结果（Agent 选择含 Profile、生效的 prompt 模式和并发值来源）。既有 `concurrency` Manager 操作的结果补齐 before/after、任务覆盖与默认值的类型。
- Dashboard（`web/src/lib/api.ts`）：`updateTaskConfig`、`setTaskProject`、`setTaskAgents`、`continueTaskAtCap` 经 `callV1` 调用 v1 路由。待确认（202）的回答绝不自动确认，而是作为错误抛出。
- 旧路由（`http_server.py`）：上述四个方法及其路由正则已删除；配置处理改为返回结果的函数，检查不变。
- 进程清理（`proc_tree.py`）：结束一轮的进程树时，若准备阶段被取消，仍会结束已保存的进程树（发信号前重新核对身份）并回收 agent。
- 文档与测试：更新客户端 skill RFC 和长程上下文计划。新增 `tests/test_api_v1_task_configuration.py` 和 `tests/test_api_v1_task_configuration_db.py`，以及一项 `proc_tree` 测试；任务、项目、重启和续跑相关测试及 Dashboard 测试改用 v1 调用。PR 报告新增测试 426 行、生产代码 176 行（不含 fixture）。
- 面向模型的变化：无。Manager、Worker、Planner、Reviewer 的 prompt 不变，也不新增或改动 Manager Tool；仅既有 `concurrency` 操作声明的结果 schema 有了类型。API 客户端（以及基于 OpenAPI 文档的 agent skill）会看到新增的操作及其 schema。

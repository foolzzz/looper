# Looper v2.14.79

This is the patch release v2.14.79, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.78: the Manager and Planners can now run on the `cursor-agent` runtime ([#1086](https://github.com/foolzzz/looper/pull/1086)).

## Release Decision

**Who should upgrade:** Operators who want a Cursor Agent Profile for the Manager or Planners. Everyone else can stay.

**What this release solves:** The `cursor-agent` runtime (v2.14.77) served only Workers and Reviewers. [#1086](https://github.com/foolzzz/looper/pull/1086) gives it resident sessions and resume, so every role can use a Cursor Agent Profile.

**Breaking changes:** No. No setting, schema or operation is removed; a Cursor Agent Profile becomes selectable for two more roles. Profiles and runtimes in use keep working.

**How to verify:** Check the installed version. With `cursor-agent` on PATH and logged in, the runtime `Cursor Agent` lists the capabilities `resident_session` and `resume`, and a Cursor Agent Profile can be chosen for the Manager and Planners.

**Contributors:** Maintainer @foolzzz authored [#1086](https://github.com/foolzzz/looper/pull/1086); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.79
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.78 upgrades directly. This release has no schema change.

## Behavior changes

- **Resident Cursor sessions** (`looper/agents/runtimes/cursor_agent.py`). The `cursor-agent` runtime has the `resident_session` and `resume` capabilities. A Manager or Planner keeps one Cursor chat per session (owner) under `<runtime_root>/.local/cursor-agent/sessions/<owner>/`, with its own `config/` and `data/` directories; each turn runs `cursor-agent -p … --resume <chatId>` in the same working directory. The Manager and Planners are no longer excluded from the runtime.
- **Instructions on stdin.** The first turn of a session sends the `<looper_instructions>` block before the prompt; a resumed turn sends only the prompt, because the chat holds the block.
- **Session recorded at init** (`looper/agents/runtimes/per_turn.py`). The session's `session.json` stores the instructions' hash, chat id and working directory as soon as `system/init` reports the chat id, through a new `_session_initialized` hook, so a turn interrupted by a restart still resumes that chat. After a stop request, the turn's stream is no longer refreshed while buffered output is read; the stop's own cleanup does that.
- **Changed instructions go through the session switch** (`looper/agents/session_switch.py`, `looper/agents/tiers/manager.py`, `looper/agents/tiers/planner.py`). A new reason `INSTRUCTIONS_CHANGED` applies when a runtime binds the saved chat to its original instructions (`RuntimeAdapter.instructions_changed`, true only for Cursor Agent when the hash differs, is unknown or belongs to another chat). The old chat takes a handoff turn, then a new chat starts with the new instructions and a resume brief. After a server restart, the Manager and Planner reopen the old chat for that handoff. The old chat is removed only after the new session's first turn completed, including when that turn first has to resume an interrupted one.
- **Capabilities refreshed at startup** (`looper/agents/profile_registry.py`, `looper/db/profile_registry.py`). `register_found_runtimes` refreshes the capabilities of an existing built-in `rt-cursor-agent` row from the adapter (`refresh_builtin_capabilities`), leaving the operator's fields and probe history alone, so a database that registered the runtime before keeps working without re-detecting runtimes.
- **Documentation and tests.** The architecture doc (`docs/architecture/agent-system.md`) and the read-only copies note describe the sessions. Tests are in `tests/test_cursor_agent.py`, `tests/test_per_turn_interrupt.py`, `tests/test_profile_registry_db.py` and `tests/test_read_only_copies.py`.
- **Model-visible changes:** None to prompts, role text or agent tool descriptions. The Manager and Planners on a Cursor Agent Profile receive Looper's instructions in the same `<looper_instructions>` block Workers get, and after an instructions change a new session's first turn gets the existing resume brief.

## Validation

**Retained implementation evidence:** the description of [#1086](https://github.com/foolzzz/looper/pull/1086) reports tests for the per-turn session layout, stdin on first and resumed turns, a session recorded from `system/init` and resumed after an interrupted turn, the handoff on changed instructions and the capability refresh on startup (PostgreSQL), plus the existing runtime tests. It reports real-mode Manager dialogs with the Manager on `cursor-agent`, one repetition each (`ask_project`, `confirm_create_start`, `cancel_confirmation`, `status`): 4 of 4 passed. With every role on `cursor-agent`, `single_step` passed (one Planner reply broke the PLAN contract once and was asked again); `reviewed_step` failed because Cursor's CLI itself gave up after three network reconnects on the Planner's first turn (`RetriableError: WritableIterable is closed`, exit 1). The same error appeared in hand runs of the native CLI outside Looper. Retrying such a turn is a follow-up and is not part of this release.

### 行为变化与入口

- **常驻 Cursor 会话**（`looper/agents/runtimes/cursor_agent.py`）。`cursor-agent` 运行时具备 `resident_session` 和 `resume` 能力。Manager 或 Planner 的每个会话（owner）在 `<runtime_root>/.local/cursor-agent/sessions/<owner>/` 下保留一个 Cursor 聊天，带自己的 `config/` 和 `data/` 目录；每一轮在同一工作目录运行 `cursor-agent -p … --resume <chatId>`。Manager 和 Planner 不再被排除在该运行时之外。
- **指令走 stdin。**会话第一轮在提示前发送 `<looper_instructions>` 块；恢复的轮次只发送提示，因为聊天已保存该块。
- **在 init 时记录会话**（`looper/agents/runtimes/per_turn.py`）。Cursor 通过 `system/init` 报告聊天 id 时，就经新的 `_session_initialized` 钩子把指令哈希、聊天 id 和工作目录写入 `session.json`，因此被重启打断的一轮仍能恢复该聊天。收到停止请求后，读取缓冲输出时不再刷新该轮的进程树，由停止流程自己的清理负责。
- **指令变化走会话切换**（`looper/agents/session_switch.py`、`looper/agents/tiers/manager.py`、`looper/agents/tiers/planner.py`）。新增原因 `INSTRUCTIONS_CHANGED`，用于运行时把已保存聊天绑定到原始指令的情形（`RuntimeAdapter.instructions_changed`，仅 Cursor Agent 在哈希不同、未知或属于另一聊天时为真）。旧聊天先做一轮交接，再以新指令和恢复简报开启新聊天。服务器重启后，Manager 和 Planner 会重新打开旧聊天完成交接。旧聊天只在新会话第一轮完成后才删除，包括该轮先要恢复一个被打断的轮次的情形。
- **启动时刷新能力**（`looper/agents/profile_registry.py`、`looper/db/profile_registry.py`）。`register_found_runtimes` 按适配器刷新已有内置 `rt-cursor-agent` 行的能力（`refresh_builtin_capabilities`），不改动运维人员的字段和探测历史，因此此前已注册该运行时的数据库无需重新探测即可工作。
- **文档与测试。**架构文档（`docs/architecture/agent-system.md`）和只读副本说明描述了这些会话。测试在 `tests/test_cursor_agent.py`、`tests/test_per_turn_interrupt.py`、`tests/test_profile_registry_db.py` 和 `tests/test_read_only_copies.py`。
- **面向模型的变化：**提示词、角色文本和 agent 工具说明均无变化。使用 Cursor Agent Profile 的 Manager 和 Planner 以与 Worker 相同的 `<looper_instructions>` 块接收 Looper 的指令；指令变化后，新会话的第一轮收到已有的恢复简报。

No new switch in this release defaults to on. An upgrade does not write `cost_guard.mode`; a stored mode stays as it is, and a missing row stays `off`. Enforce acts only after the operator sets that mode to `enforce`. With every new switch left off, startup still takes the usual pre-migration `pg_dump` backup, applies 18 additive migrations and 9 new online steps, and starts the loops that already shipped in v2.15.28 (memory writer and memory push every 10 seconds, morning brief every 30 seconds). It also starts `IdleCheckService` (every 300 seconds) and `MetricsAlertService` (every 3600 seconds); each returns after reading an off switch; after one settings read at startup, each alert tick returns before it takes a database connection. New work still writes `step_attempts` and `task_outcomes`. Those writes are not gated by `manager.metrics.enabled` or `metrics.alerts.enabled`, and nothing historical is reconstructed. `tasks.run_no` defaults to 1. Housekeeping still deletes `proactive_deliveries` older than 90 days, and now also purges settled `idle_checks` rows older than 90 days and runs skill-proposal expiry and pending notification, even while every project has proposals off and the new tables are empty. Startup reads whether any `cost_holds` row is pending or unapplied; with the new table empty and the mode off, admission does no extra I/O. Lark catch-up retries a debt that already exists; that path has no new switch. Configuration export gains `settings.manager_lanes` only when that key is stored as exactly `true` or `false`, and a project gains `skill_proposals` only when that column is set. `web/` changed, so the dashboard bundle is rebuilt by the release workflow as usual.

## Release Decision

**Who should upgrade:** Anyone who will turn on Manager lanes, idle checks, event-triage handoff, task-quality alerts, skill proposals, cost-guard enforce, usage-window holds, the ACP Reviewer pilot or action receipts, and anyone already running Lark catch-up or recording new task work. An installation that turns none of the new switches on still applies 18 additive migrations and 9 new online steps, starts two new idle loops, writes step attempts and task outcomes for new work, purges empty housekeeping tables, and retries existing Lark catch-up debt. `web/` changed, so the dashboard bundle is rebuilt by the release workflow as usual.

**What this release solves:** The operator can prioritize their own Manager messages, ask the Manager to look at what is waiting after it has been idle, hand important triaged events to that Manager and read the rest in the morning brief, see why a stored message was or was not reported, record task quality and optionally alert on it, require measured acceptance evidence, let a Planner use explorer tools, deprecate a skill and confirm a proposed one, open the memory page, enforce task and global daily spend caps and hold work for a usage window, count room consults in a task's cost, pilot an ACP Reviewer, retry a failed Lark catch-up, and attach a receipt to a Manager or API-client write. None of the new switches turns itself on. Cost-guard stage ③ does not ship.

**Breaking changes:** No. No existing API drops a field that a caller must send. An upgrade from v2.15.28 applies 18 additive migrations and 9 new online steps. No stored switch turns on, and `cost_guard.mode` stays as stored. New columns use constant defaults (`library_items.lifecycle` `active`, `tasks.run_no` 1, `morning_briefs.triage_ids` empty). Historical step attempts and task outcomes are not reconstructed. The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.15.29
```

**Contributors:** Maintainer @foolzzz authored the pull requests named in this body; no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.15.28 upgrades directly. Restart the service after upgrading, as for every release. `web/` changed, so the release workflow rebuilds the dashboard bundle from `web/` into the wheel, as usual. This pull request does not commit that bundle.

On an upgrade from v2.15.28, startup applies 18 new migrations, once, inside the schema transaction, in `(order, name)` order. Because they are pending, `looper serve` first writes its usual pre-migration `pg_dump` backup into the runtime root's `backups` folder, as for any release that changes the schema, and does not start without a usable `pg_dump` unless it is started with `--skip-backup`. Nine of them have an online step, and each of those steps runs because its own marker is absent. A step whose marker is already recorded is skipped. None of these migrations deletes an older online marker (`event_triage_online`, `morning_brief`, and the other markers shipped before this release stay), so those older online steps do not run again. A database that has not yet finished an earlier online step still runs that step. A fresh database creates the same objects from `schema.sql` plus each module's `fresh_ddl` and does not record a separate migration for a table that DDL already created.

`pending()` runs inside each `apply`, so a later migration sees tables created earlier in the same transaction. `step_attempt_profiles` is pending only when `step_attempts` exists and its profile index does not; `step_attempts` (1100) creates that table before `step_attempt_profiles` (1230) applies, so the online index does run on this upgrade. `acp_command.pending` does not consult its marker: it is pending when `llm_providers` exists and `llm_providers_vendor_type_check` does not contain `acp-command`. `morning_brief_triage.pending` looks at the objects even if a marker were present; on v2.15.28 the triage column and table are missing, so it runs. Each source-check widening (`idle_check_source`, `triage_source`, `metrics_alert_source`) is pending when the single-column `proactive_deliveries.source` check does not yet contain its new value. They run in that order in the same transaction, and each deletes only its own online marker, so three online steps each `VALIDATE` the same final check.

No migration rewrites existing row values except constant defaults: `library_items.lifecycle` `active`, `tasks.run_no` 1, and `morning_briefs.triage_ids` `'{}'`. `acp_command` replaces two checks and does not rewrite provider rows. No new seed row is inserted. Outside PostgreSQL, a Lark channel's SQLite inbox in the runtime root is upgraded in place when the channel opens ([#1632](https://github.com/foolzzz/looper/pull/1632)); v2.15.28 cannot insert catch-up debt into the upgraded tables, so roll back only with that in mind.

## Behavior changes

### Manager lanes, off ([#1595](https://github.com/foolzzz/looper/pull/1595))

- **`manager.lanes.enabled` defaults off.** Only the stored string `true` is on. No row, or any other value, is off. `null` deletes the row and the in-memory value becomes false. `false` stores the string `false`. Only the operator can call `manager_lanes.get` and `manager_lanes.update` (`POST /api/v1/manager_lanes/get` and `update`). The update is declared high risk with `confirms` true. The operator's own call applies on that request and returns 200. It is not held for a second confirmation. A non-operator gets 403 `operator identity is required`. It is not part of `chat_settings`. Configuration export includes `settings.manager_lanes` only when the stored value is exactly `true` or `false`, and that section may contain only `enabled`. A client import that contains `settings.manager_lanes` is forbidden: `Manager lanes settings require operator identity; upload this configuration with an operator token`. An operator import is skipped with `manager_lanes must contain only enabled` when the section has a key other than `enabled`, and with `enabled must be true, false or null` when the value is not one of those; a section that is not a JSON object rejects the whole file with `settings.manager_lanes must be a JSON object`. Import of null deletes the row.
- **While it is off,** input, the record and FIFO behavior stay as they were. Status cards do not show the two queue counts. No lane migration is added by this pull request.
- **While it is on,** a user message takes the interactive lane and queued background work waits. Completion sends its code notice before its wake is settled, and the next user turn gets one explanation through the stopped notes. More than 20 preemptions in one UTC day, counted in this process's memory, produce one warning. A claimed batch that has not started expires 15 minutes after the earliest event `created_at`. With routing off, both kinds of turn use main's worker. A control interrupt cleans children first observed after the system or init checkpoint; uncertain ownership or a missing checkpoint kills the resident and resumes on the next turn.

### Idle checks, off until three switches are already on ([#1596](https://github.com/foolzzz/looper/pull/1596), [#1598](https://github.com/foolzzz/looper/pull/1598))

[#1596](https://github.com/foolzzz/looper/pull/1596) adds the switch, the table, the candidate plan and the service. [#1598](https://github.com/foolzzz/looper/pull/1598) runs that service from `looper serve` and handles the turn on the Manager's background entry. The check text is model-visible. No real-model idle-check eval was run for this release; the first real run is still pending.

- **`manager.idle_checks.enabled` defaults off.** Only the stored string `true` is on. No row, or any other value, is off. `null` deletes the row. `false` stores `false`. It is never part of `chat_settings` and it is not a configuration-export key. Only the operator can call `idle_check_settings.get` and `idle_check_settings.update`. The update is declared high risk with `confirms` true. The operator's own call applies on that request and returns 200. It is not held for a second confirmation. A non-operator gets 403 `operator identity is required`. Turning it on conflicts unless `delivery.enabled`, `attention.enabled` and `manager.lanes.enabled` are all the string `true`. The error is `Cannot enable idle checks. Enable these prerequisites first: ` plus the missing keys, comma-joined. Turning a prerequisite off later does not turn this switch off; the service starts no new check while one is missing.
- **While it is off,** `IdleCheckService` still starts. `recover()` runs before `supervisor.start_all` and sets this Manager's leftover `running` rows to `failed` with reason `restart`. A failed `recover()` blocks startup. The service stops during shutdown. Every 300 seconds a tick reads the four settings keys and calls `delivery.load_policy()` (that policy read is not a database query), then returns. That tick does not take the advisory lock `(741925, 2)`, insert an `idle_checks` row, or publish. Housekeeping still purges settled `idle_checks` rows older than 90 days (a `running` row is kept). The two migrations still apply.
- **While it is on,** a check can start when the default Manager has been idle for 30 minutes, at most 4 checks begin on one local date, and two checks start at least 2 hours apart. A tick that passes the switch, the prerequisites, a running and non-draining Manager, 30 idle minutes and quiet hours tries the session advisory lock `(741925, 2)` (another server holding it ends the tick) and holds it only while it reads counts and items, inserts the row and publishes; the check's turn holds no lock. Quiet hours are the delivery layer's built-in 22:00–08:00 in `user.timezone` (else the server zone), and a direct chat's daily cap is its built-in 5; no setting changes either, and either one skips the check. Gates, confirmations and cost items never qualify. One check names at most 10 items, and silent, sent or uncertain mentions from the last 7 days are not named again. The turn budget is 90 seconds. The model-visible silence token is exactly `NO_REPLY`. A message that is sent ends with `详情：发 /todo，或打开控制台的 Needs you。` A sent morning brief (status `sent`, same channel and direct chat) suppresses checks for two hours. Enabling takes effect on the next tick.

### Event triage handoff, why, and the morning-brief section ([#1597](https://github.com/foolzzz/looper/pull/1597), [#1600](https://github.com/foolzzz/looper/pull/1600), [#1605](https://github.com/foolzzz/looper/pull/1605), [#1612](https://github.com/foolzzz/looper/pull/1612))

v2.15.28 stored triage events and did not hand them to the Manager or put them in the brief. The architecture section "Event triage foundation" still says there is no why API/CLI, Manager hand-off or briefing reader yet, and the last sentence of "Event triage Manager handoff" still says the Manager does not run these turns (`manager.py` is untouched). The running code calls `triage_background.dispatch`. The shipped handoff is the RFC section linked under Optional Capability Activation. The handoff instructions are model-visible. No real-model eval was run for this handoff.

- **`subscriptions.triage.enabled` is unchanged and stays off.** Only the string `true` turns it on. `null` deletes the row. New `subscriptions.triage.max_turns_per_day` defaults to 12, a whole number from 1 to 100. An absent value, or a stored value that is not a decimal in that range, is 12. `null` restores 12. A field left out of an update keeps its stored value. Only the operator can call `triage_settings.get` and `triage_settings.update`. The update is declared high risk with `confirms` true. The operator's own call applies on that request and returns 200. It is not held for a second confirmation. A non-operator gets 403 `operator identity is required`. Neither key is a new export key.
- **While triage is off,** no new handoff row is written, no Manager triage turn starts, and the morning brief does not read the triage section. A row still pending from when triage was on falls back and sends nothing: `off` when the Manager claims it, or `queue_deadline` after 15 minutes. A triage subscription still ends `skipped_gate` with `subscriptions.triage.enabled is off` and does not move its cursor, as in v2.15.28. Creating one is still HTTP 400 with `cannot create a triage subscription: subscriptions.triage.enabled is off`. The new migrations still apply.
- **While triage is on,** an important event is queued for the Manager. The Manager takes that turn only while `delivery.enabled` is also the string `true` and the Manager is on; otherwise the row falls back as `queue_deadline` after 15 minutes and the event waits for the brief. The Manager takes at most `max_turns_per_day` triage turns on one local day; the 13th, by default, is left for the brief. [#1605](https://github.com/foolzzz/looper/pull/1605) runs that turn on the shared background entry. A deferred triage delivery uses source `triage`. New reason values `delivery_deferred` and `daily_cap` are what a handoff can settle as when delivery defers it or the day's turns are used up.
- **Why** ([#1597](https://github.com/foolzzz/looper/pull/1597)). `triage.why` is operator-only. It is not given to the Manager. The order is: the switch is off, or there is no triage subscription; the message is out of scope; the cursor has not reached it; the window was skipped; a cited event; a `window_seqs` hit that was not cited; otherwise `unknown`, with what was checked (for example, a source with no triage subscription). A cited important event still answers with the fixed line `not handed to the Manager yet (that step is not built)`. That read does not look at `manager_event_id` or at deliveries. `looper msgflow why` prints the same rules. While the switch is off it prints `分流没开` and `原因：开关关闭`.

#### Cost guard enforce

**启用：** 操作者把 `cost_guard.mode` 设为 `enforce` 之前是关。没有这一行就是 `off`。`observe` 只记录，不执行。操作者用 `POST /api/v1/cost_guard/update`，正文 `{"mode": "enforce"}`。这个正文返回 `needs_confirmation`（HTTP 202），要等 `POST /api/v1/confirm`。`null`、`off` 和 `observe` 当场返回 200。升级不会改已存的模式。第 ③ 阶段（后台角色上限、`STOP_ROLE`、`FALLBACK`、日程等值每日预算）不在本版本。

#### Usage windows

**启用：** 没有单独的键。只有 `cost_guard.mode` 为 `enforce` 时才应用暂停。窗口行只在 `engine.limit_signals.enabled` 为字符串 `true` 时读取；否则只有配额失败规则，而配额失败记录要 `engine.failure_typing` 为 `record`（默认 off）才会写入，回看 8 天。`off` 时不读任何用量窗口数据。`observe` 记录将要暂停，并不暂停。

**验证：** `enforce` 下，被拒的窗口或配额失败会挡住该账号的每一次模型运行，包括操作者的管家回合和任务；操作者对智能体日程或命令点 Run now 仍会启动。利用率达到或超过 95% 只挡住日程触发和后台角色。知道重置时间就等到那个时刻。不知道时最多等五分钟。被拒的窗口或重置时间未知的暂停会发通知，以 `用量窗口暂停：` 开头。被暂停的订阅不能 `Run now`。

**权限边界：** 只给操作者，通过花费守卫的更新。暂停作用在这次启动所用的 provider 上。花费拒绝优先于这些暂停。通知发到操作者的仪表盘目标，按账号和窗口去重。

# Looper v2.14.15

This is the patch release v2.14.15. It ships the one change merged since v2.14.14: [#903](https://github.com/foolzzz/looper/pull/903), which pools runner processes per SDK.

## Release Decision

**Who should upgrade:** Operators who run Manager, Planner, Worker, Reviewer and consults on an SDK runner (`[runtimes] dsh = "runner"` or `[runtimes] pi = "runner"`) and hit the `CAPACITY` failure at one runner's session cap. Installations on the default `"cli"` runtimes see no change. It ships the one change merged since v2.14.14.

**What this release solves:** [#903](https://github.com/foolzzz/looper/pull/903): all sessions of a runner kind shared one runner process, so the 20 DSH or 10 pi session slots were the whole capacity. The supervisor now runs a pool of up to four runners per kind and returns `CAPACITY` only when the whole pool is full.

**Breaking changes:** No. The supervisor's internal `invalidate` call now takes a lease instead of a kind; nothing outside Looper's runner code calls it. The supported upgrade path is unchanged (see Upgrading).

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#903](https://github.com/foolzzz/looper/pull/903); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.15
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.14 upgrades directly. This release changes no database schema, stored data or setting. The runner opt-ins are still read once at startup, so a restart applies the pool.

## Behavior changes

Only installations with a runner opt-in change. With the `"cli"` runtimes, the behavior is that of v2.14.14.

- **Pool size** (`looper/agents/runtimes/runner/supervisor.py`): when every runner of a kind is at its session cap, the supervisor starts another, up to four per kind (`MAX_RUNNERS_PER_KIND`). That is 80 DSH sessions or 40 pi sessions (20 or 10 per runner, shared by all roles). Starting a runner holds the kind lock through its handshake and first reservation, so concurrent acquisitions cannot over-expand the pool.
- **Placement:** a new session goes to the runner with the most free slots. Each session keeps the runner that holds it for its prompts, steering, cancellation and close.
- **Idle stop:** an extra runner with no sessions stops after 300 seconds (`IDLE_STOP_SECONDS`); the last runner stays.
- **Capacity failure:** only a full pool returns `CAPACITY`. Its message now reads "CAPACITY: runner pool has N session slots; all are in use" (`ProtocolError` gained an optional message).
- **Crash handling:** a crash, or a runner that reports an error, fails only that runner's sessions. It is reaped at the next acquisition, and a replacement starts on demand after the crash backoff, not at once. A lease that needs a new runner waits for the backoff, then rechecks free slots, so a healthy runner with room serves it without waiting. A turn submitted while no healthy runner has room and a restart backoff is running fails fast. The limit of five failures within ten minutes per kind is unchanged.
- **Saved sessions:** Pi owner directories and DSH's shared native state root survive replacement of a runner, so a closed saved session can load on any runner. DSH close awaits the disposal of its native writer before another runner takes ownership. Pi's native ownership checks are process-local, so callers must serialize access to the same saved session.
- **Logging:** each runner start and stop logs the kind, the runner's index and the session counts.
- **Internal:** `RunnerSupervisor.invalidate` takes the lease, so only the runner holding it is invalidated (`looper/agents/runtimes/runner/session.py`).
- **Model-visible changes:** None. No prompt, tool schema or runner protocol message changes. Only the text of the `CAPACITY` failure changes, and it appears as a step's start-failure reason; it is not added to any prompt.

### 升级决策

**谁需要升级：**把 Manager、Planner、Worker、Reviewer 和 consult 跑在 SDK runner 上（`[runtimes] dsh = "runner"` 或 `[runtimes] pi = "runner"`），并在单个 runner 的会话上限处遇到 `CAPACITY` 失败的运维者。使用默认 `"cli"` 运行时的安装没有变化。包含 v2.14.14 之后合并的唯一改动。

**是否有破坏性变更：**否。supervisor 内部的 `invalidate` 调用改为传入 lease 而非 kind，Looper 的 runner 代码之外无人调用。受支持的升级路径不变（见升级）。

**如何验证：**运行 `looper --version` 核对版本为 2.14.15。

**贡献者：**维护者 @foolzzz 提交 [#903](https://github.com/foolzzz/looper/pull/903)；本版本无社区贡献。

```bash
looper --version   # looper 2.14.15
```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.14 上的安装可直接升级。本版本不改数据库 schema、已存数据或设置。runner 开关仍只在启动时读取一次，重启后池生效。

### 行为变化与入口

只有启用 runner 的安装发生变化。使用 `"cli"` 运行时，行为与 v2.14.14 相同。

- **池大小**（`looper/agents/runtimes/runner/supervisor.py`）：某类所有 runner 都达到会话上限时，supervisor 再启动一个，每类最多四个（`MAX_RUNNERS_PER_KIND`），即 80 个 DSH 会话或 40 个 pi 会话（每个 runner 20 或 10 个，各角色共用）。启动 runner 时 kind 锁覆盖握手和首次预留，并发获取不会使池过度扩张。
- **放置：**新会话放到空闲位最多的 runner。每个会话的 prompt、steer、取消和关闭都留在持有它的 runner 上。
- **空闲停止：**没有会话的额外 runner 在 300 秒后停止（`IDLE_STOP_SECONDS`），最后一个 runner 保留。
- **容量失败：**只有池满才返回 `CAPACITY`，消息变为“CAPACITY: runner pool has N session slots; all are in use”（`ProtocolError` 增加了可选消息）。
- **崩溃处理：**runner 崩溃或报错只让该 runner 的会话失败，下一次获取时回收，替换在崩溃退避之后按需启动，而不是立即启动。需要新 runner 的 lease 等待退避后重新检查空闲位，因此有空位的健康 runner 可直接服务它。没有健康 runner 有空位且处于重启退避时提交的 turn 会快速失败。每类十分钟内五次失败的上限不变。
- **已保存会话：**Pi 的 owner 目录和 DSH 共用的原生状态根目录在 runner 被替换后仍保留，已关闭的已保存会话可在任一 runner 上加载。DSH 关闭时先等待原生 writer 释放，再由其他 runner 接管。Pi 的原生所有权检查仅限进程内，调用方必须串行访问同一个已保存会话。
- **日志：**每次 runner 启动和停止都记录 kind、runner 序号和会话数。
- **内部：**`RunnerSupervisor.invalidate` 改为接收 lease，只让持有它的 runner 失效（`looper/agents/runtimes/runner/session.py`）。
- **面向模型的变化：**无。没有 prompt、工具 schema 或 runner 协议消息的变化。只有 `CAPACITY` 失败的文本变化，它作为步骤的启动失败原因出现，不会加入任何 prompt。

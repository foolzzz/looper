# Looper v2.14.17

This is the patch release v2.14.17. It ships the one change merged since v2.14.16: [#905](https://github.com/foolzzz/looper/pull/905), which lets a project be deleted together with its tasks and schedules.

## Release Decision

**Who should upgrade:** Anyone who deletes projects that still have tasks or schedules, from the dashboard, the Manager `looper_projects` tool or `project_admin.delete`. It ships the one change merged since v2.14.16.

**What this release solves:** [#905](https://github.com/foolzzz/looper/pull/905): deleting a project required it to be empty, so its tasks and schedules had to be removed one by one first. Now, after the user confirms, one delete removes the project's schedules (with their run history), stops its running tasks, deletes all its tasks with the cleanup of a single task delete (the result branch stays) and then deletes the project.

**Breaking changes:** No. A delete that used to be refused for tasks or schedules now proceeds after confirmation; other refusals stay. The supported upgrade path is unchanged (see Upgrading).

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#905](https://github.com/foolzzz/looper/pull/905); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.17
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.16 upgrades directly. This release changes no database schema, stored data or setting.

## Behavior changes

- **Delete order** (`looper/agents/projects.py`, `delete_project`): schedules of the project first (with their run history); then every active task gets a stop and the delete waits, up to 60 seconds, for them to stop; then each task is deleted; then the project. If tasks are still stopping after 60 seconds, the delete fails with a 409 naming up to five task ids and can be repeated to finish. Cleanup already done stays done.
- **Task cleanup** is one shared function, `projects.delete_task`, used by the single task delete (`http_server.py`) and the project delete: step worktrees, the task checkout (what the task left is committed to its result branch, which stays), saved sessions, then the row. The row is locked while it runs, so a start cannot claim it meanwhile. If a task's worktree cannot be released, the delete fails with a 409 that says how many tasks were deleted; the task keeps its checkout and row, and the delete can be repeated.
- **Refusals kept:** a project used by a Manager template; for a scoped Manager, a project that has tasks or schedules of other Managers (reported without their counts). A scoped Manager deletes only its own tasks and schedules.
- **No new starts during a delete:** the Scheduler (scheduled, manual, queued and gate-completed firings) and the Task Router refuse to start work for a project that is being deleted and wait for work already admitted. A second delete of the same project is refused with a 409 while one runs. A task or schedule added just before the final delete makes it fail with a 409; repeat it.
- **Other:** the process-tree stop takes its `ps` snapshot off the event loop (`proc_tree.py`), so a bulk stop does not block the server; the Router keeps a planner entry until its stop finishes.
- **Dashboard:** the project settings Delete section is always available. It states how many tasks (and how many running ones are stopped first) and schedules go, the confirmation names the task count, and the button reads "Stopping and deleting…" while it runs.
- **`project_admin.delete` (v1):** the impact check no longer refuses a project with tasks or schedules, and the operation performs the cascade.
- **Model-visible changes:**
  - The `looper_projects` tool description changes from "delete one without tasks or schedules (the user confirms first)" to "delete one with its tasks and schedules, stopping its running tasks first (the user confirms first)".
  - The Manager's delete confirmation text lists what will happen (schedules with run history, running tasks stopped, all tasks deleted with workspaces, directory, sessions and records, result branch kept), or says the project has no tasks and schedules.
  - The `project_admin.delete` operation description changes the same way.
  - No other prompt, tool schema or runner protocol message changes.

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.16 上的安装可直接升级。本版本不改数据库 schema、已存数据或设置。

### 行为变化与入口

- **删除顺序**（`looper/agents/projects.py` 的 `delete_project`）：先删项目的定时任务（含运行记录）；再对每个运行中的任务发出停止，并最多等待 60 秒；然后逐个删除任务；最后删除项目。60 秒后仍有任务在停止时，删除以 409 失败并列出至多五个任务 id，可重复执行以完成。已完成的清理不会回退。
- **任务清理**是一个共享函数 `projects.delete_task`，单个任务删除（`http_server.py`）和项目删除都使用它：步骤工作区、任务检出目录（任务留下的内容提交到结果分支，分支保留）、已保存的会话，最后是记录。清理期间任务行被锁定，启动无法同时认领它。若某任务的 worktree 无法释放，删除以 409 失败并说明已删除的任务数；该任务保留检出目录和记录，可重复执行。
- **保留的拒绝条件：**被 Manager 模板使用的项目；对受限 Manager，还有含其他 Manager 的任务或定时任务的项目（不透露其数量）。受限 Manager 只删除自己的任务和定时任务。
- **删除期间不启动新工作：**调度器（定时、手动、排队和 gate 完成后的触发）和 Task Router 拒绝为正在删除的项目启动工作，并等待已放行的工作结束。同一项目已有删除在运行时，再次删除返回 409。最终删除前刚加入的任务或定时任务会使删除以 409 失败，重复执行即可。
- **其他：**进程树停止在事件循环之外获取 `ps` 快照（`proc_tree.py`），批量停止不会阻塞服务；Router 在停止完成前保留 planner 条目。
- **仪表盘：**项目设置的删除区域始终可用。它说明将删除多少任务（及先停止多少运行中的任务）和定时任务，确认文案包含任务数，运行时按钮显示 “Stopping and deleting…”。
- **`project_admin.delete`（v1）：**影响检查不再因任务或定时任务而拒绝，操作会执行级联删除。
- **面向模型的变化：**
  - `looper_projects` 工具描述由 “delete one without tasks or schedules (the user confirms first)” 改为 “delete one with its tasks and schedules, stopping its running tasks first (the user confirms first)”。
  - Manager 的删除确认文本列出将发生的事（删除定时任务及运行记录、停止运行中的任务、删除全部任务及其工作区、目录、会话和记录、保留结果分支），或说明项目没有任务和定时任务。
  - `project_admin.delete` 的操作描述做了同样的修改。
  - 没有其他 prompt、工具 schema 或 runner 协议消息的变化。

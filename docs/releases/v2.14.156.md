# Looper v2.14.156

This is the patch release v2.14.156, a hotfix line in which each merged change ships at once. It documents one change: [#1281](https://github.com/foolzzz/looper/pull/1281) (Lark images and files become attachments for the Manager).

## Release Decision

**Who should upgrade:** Operators whose Lark or Feishu bot talks to a Manager and whose users send images or files. Everyone else gets no change in normal use, apart from path redaction in outgoing chat text.

**What this release solves:** [#1281](https://github.com/foolzzz/looper/pull/1281) hands on `image` and `file` messages and the images and files inside rich-text posts, which were answered "not supported". They are downloaded as the bot and reach the Manager as attachments; anything not received is reported to the sender once.

**Breaking changes:** No. The PR calls the change an intended maintainer decision; there is no API change, no migration and no schema change. Behavior changes are listed below. The bot needs the app scope `im:message:readonly` for downloads. The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.14.156
```

**Contributors:** Maintainer @foolzzz authored [#1281](https://github.com/foolzzz/looper/pull/1281); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.155 upgrades directly. There is no schema change. To receive attachments, grant the Lark app the scope `im:message:readonly`.

## Behavior changes

- **Images and files are downloaded** ([#1281](https://github.com/foolzzz/looper/pull/1281), `looper/agents/channels/lark.py`, `_collect`; `lark_content.py`: `RICH_TYPES` now includes `image` and `file`). Images and files in a post, an image message or a file message are downloaded after the sender is admitted, the route is not silent and the Manager is on, and after the reaction. They go one at a time as the bot, at most 30 s each and 60 s per message, and at most 10 per message (further ones are marked over the limit). Silent chats, unlisted senders, unaddressed group messages and a turned-off Manager never download.
- **Limits and storage** (`looper/agents/chat_attachments.py`, `lark_api.py`, `lark_transport.py`, `lark_cli.py`). Images and files are limited to 20 MB, enforced while streaming (bot-token channel: `LarkApi.download`, which refreshes an expired token once) or by `lark-cli im +messages-resources-download --as bot` (CLI channel, confined to a bare filename in the message directory). The content is checked by type, not by name. A sniffed type that disagrees with the filename extension gets the sniffed extension appended (was: only when the name had no extension). Files are kept under the runtime root in `chat-attachments/<channel-id>/<message-id>/` with private permissions, for 7 days.
- **The Manager gets the attachments.** The Manager's text carries `[image N]` / `[file N: name]` and the payload carries the attachments; the line "Looper cannot receive images or files yet" is gone.
- **One reply for what was not received.** When something failed (too large, unsupported type, over the limit of 10, timed out, download error), the sender gets one reply, 「有 N 个附件没有收下：<items>。其余内容已交给 Manager。」, in the group as a reply to the message or in the direct chat. If that reply was sent, the Manager's attachment section marks those items "the user was told". Without the scope the log and the reply name `im:message:readonly`.
- **Path redaction.** Answers, progress, notices and posts the Lark channel sends, and the Telegram and dashboard chat text, have any stored attachment path replaced by `[attachment]`. The redaction also matches the exact stored file names (spaces included) in directories the text names, and the answer stored in the chat history is redacted. For a dashboard turn with attachments, streamed partial deltas are not sent, only the complete answer.
- **Unsupported reply.** The reply for other message types now ends 「请发文字、富文本、图片或文件。」
- **Tests and docs.** New or changed tests: `tests/test_lark_cli_commands.py`, `test_lark_content.py`, `test_lark_transport.py`, `test_chat_attachments.py`, `test_lark_download_api.py`, `test_lark_rich_bot.py`, `test_attachment_chat_redaction.py`; `docs/architecture/agent-system.md` and `docs/design.md` follow.
- **Model-visible changes:** Yes, for the Manager on a Lark chat: its message text gains `[image N]` / `[file N: name]` placeholders and its payload gains attachments (replacing the "cannot receive images or files yet" line), the attachment section marks items "not received (reason); the user was told", and attachment paths in its answers reach the chat as `[attachment]`. No system prompt or tool definition changed.

本版本是 patch release v2.14.156（热修线，每个合并的改动立即发布），说明一项改动：[#1281](https://github.com/foolzzz/looper/pull/1281)（飞书图片和文件成为 Manager 的附件）。

### 升级决策

**谁需要升级：**飞书/Lark 机器人连接 Manager、且用户会发送图片或文件的运维者。其他人在正常使用中没有变化，只是外发聊天文本中的路径会被替换。

**解决了什么：**[#1281](https://github.com/foolzzz/looper/pull/1281) 接收 `image`、`file` 消息以及富文本中的图片和文件（此前回复“不支持”）。它们以机器人身份下载并作为附件交给 Manager；未收下的内容会一次性回复发送者。

**是否有破坏性变更：**否。PR 称此变化是有意的维护者决定；没有 API 变更、迁移或结构变更，行为变化见下。下载需要应用权限 `im:message:readonly`。桥接边界不变：早于 v2.13.165 的安装须先升级到 v2.13.165。

**如何验证：**核对版本为 2.14.156。

**贡献者：**维护者 @foolzzz 提交 [#1281](https://github.com/foolzzz/looper/pull/1281)；本版本无社区贡献。

```bash
looper --version   # looper 2.14.156
```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.155 上的安装可直接升级。没有结构变更。要接收附件，请给飞书应用授予 `im:message:readonly` 权限。

### 行为变化与入口

- **下载图片和文件**（[#1281](https://github.com/foolzzz/looper/pull/1281)，`looper/agents/channels/lark.py` 的 `_collect`；`lark_content.py` 的 `RICH_TYPES` 增加 `image`、`file`）。帖子、图片消息、文件消息中的图片和文件，在发送者通过准入、路由不静默、Manager 开启并完成表情回应之后下载：以机器人身份逐个下载，每个最多 30 s，每条消息 60 s，每条最多 10 个（超出的标记为超限）。静默聊天、不在名单的发送者、未 @ 的群消息以及已关闭的 Manager 不会下载。
- **限制与存储**（`chat_attachments.py`、`lark_api.py`、`lark_transport.py`、`lark_cli.py`）。图片和文件各限 20 MB，流式下载时强制（机器人令牌通道：`LarkApi.download`，令牌过期时刷新一次）或经 `lark-cli im +messages-resources-download --as bot`（CLI 通道，限定为消息目录内的纯文件名）。按内容而非名称检查类型；检测到的类型与文件名扩展名不符时附加检测到的扩展名（原来仅在无扩展名时）。文件保存在运行时根目录的 `chat-attachments/<channel-id>/<message-id>/`，权限私有，保留 7 天。
- **Manager 收到附件。**文本带 `[image N]` / `[file N: name]`，载荷带附件；“Looper cannot receive images or files yet”一行已移除。
- **未收下的内容回复一次。**有失败时（过大、类型不支持、超过 10 个、超时、下载出错），发送者收到一条回复「有 N 个附件没有收下：<items>。其余内容已交给 Manager。」（群里回复该消息，私聊直接发送）。回复发出后，Manager 的附件部分将这些项标为“the user was told”。缺少权限时日志和回复会指出 `im:message:readonly`。
- **路径脱敏。**飞书渠道发出的答复、进度、通知和帖子，以及 Telegram 和仪表盘的聊天文本，其中已保存的附件路径替换为 `[attachment]`；脱敏也匹配文本所指目录中的确切文件名（含空格），写入聊天历史的答复同样脱敏。带附件的仪表盘回合不发送流式的部分增量，只发送完整答复。
- **不支持类型的回复**现以「请发文字、富文本、图片或文件。」结尾。
- **测试与文档。**`tests/test_lark_cli_commands.py`、`test_lark_content.py`、`test_lark_transport.py`、`test_chat_attachments.py`、`test_lark_download_api.py`、`test_lark_rich_bot.py`、`test_attachment_chat_redaction.py` 新增或更新；`docs/architecture/agent-system.md` 与 `docs/design.md` 随之更新。
- **面向模型的变化：**有，针对飞书聊天中的 Manager：消息文本新增 `[image N]` / `[file N: name]` 占位，载荷新增附件（取代“cannot receive images or files yet”一行），附件部分标注“not received (reason); the user was told”，答复中的附件路径在发到聊天时变为 `[attachment]`。系统提示词和工具定义未改动。

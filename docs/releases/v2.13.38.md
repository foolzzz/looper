# Looper v2.13.38

## Release Decision

**Who should upgrade:** Operators who plan to turn on `chat.stop_enabled` (Stop for a Manager's reply). With the setting off, which is the default, there is little to notice.

**What this release solves:** [#362](https://github.com/foolzzz/looper/pull/362) fixes the findings that blocked turning Stop on ([#339](https://github.com/foolzzz/looper/issues/339)). The setting stays off by default; turning it on remains the maintainer's decision against the criteria in the Stop v2 RFC.

**Breaking changes:** No. The CLI and the configuration keys keep their shape; the API additions are fields and a refusal state that only appear for Stop (see Behavior changes).

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#362](https://github.com/foolzzz/looper/pull/362); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.38
```

## Behavior changes

- **Stop only where a runtime can interrupt:** a Manager whose runtime has an interrupt (Claude Code, Grok over ACP) can be stopped. A runtime run per turn (Codex exec, OMP `-p`, Pi, DSH) has none: the stop is refused (`StopResult.CANNOT_INTERRUPT`, reply text 当前运行时不能中断回复，回复会照常完成。 in Telegram and Lark) and the reply goes on; its processes are never killed for a stop. `POST /api/chat/stop` answers with the state `cannot_interrupt` ("This runtime cannot interrupt a reply."), and `GET /api/chat/turn` gains a `can_interrupt` field, as do the Manager and Planner session summaries.
- **Dashboard:** when stopping is on but the running reply's runtime cannot interrupt, the Stop button shows disabled with the reason as a tooltip, and a stop attempt shows the notice. The page reads `can_interrupt` while it follows its own reply, since a turn may switch the runtime after the first read.
- **A stop no longer ends a resident Claude's other processes:** after the interrupt, what Claude left running is its own; the tree-snapshot cleanup (`TurnTree.baseline`/`end_new`) is removed. If the interrupt is not honoured within its grace period, Claude is still killed with its tree.
- **Bounded stop paths:** a stopped turn waits at most 3 s (`STOP_HANDLING_SEC`) for its pending events to be handled and 10 s (`STOP_FINISH_SEC`) for its own record and session writes, then ends without them, so a slow or unreachable database no longer holds the reply or the Manager's lock. The shared `abandon` helper bounds abandoned steps to 10 s and logs when one is left behind. The session is taken at once from each event, so a stop that cuts the handling short still saves it.
- **Events no longer block the stream read:** a runtime's events are accounted at once (usage, cap, model, session, tool-call match) and recorded in order by a separate task, so a slow database write does not delay the read of the `tool_use` that a bridge call waits for. Status text from a turn already stopped is not shown. A stop asked after the runtime returned is no longer treated as having cancelled a turn that finished.
- **MCP bridge call matching:** the Manager only requires a call to match its turn's stream once the turn's session is the one that runs it, and the bridge records how matches went (by id or by arguments, at arrival, waited or missed) in its diagnostics. An optional `LOOPER_MCP_TRACE` setting on a server started for an eval traces the bridge's call metadata; it is unset in normal use.
- **Web channel:** `agent.phase` events carry `activity` and `tool` when the agent reports them.
- **Evals and docs:** the real-path stop check (`evals/stop_realpath.py`) and prompt-regression runner are extended, and the Agent System page and the Stop v2 RFC are updated.
- **Entry points:** `chat.stop_enabled` (off by default), `POST /api/chat/stop`, `GET /api/chat/turn`, `/stop` in Telegram and Lark, the dashboard Stop button and Esc. With the setting off, the author reports no change in behavior.
- **Model-visible changes:** none. No prompt, tool description or `Channel:` line changed; the stop refusal text goes to the user, not the model.

## Upgrade and rollback

Re-run `install.sh` once v2.13.38 is published. There is no schema change and no data migration. Rolling back to v2.13.37 needs no step; Stop stays off unless `chat.stop_enabled` was turned on, in which case turn it off first, because v2.13.37 offers Stop on runtimes that cannot interrupt.

### 行为变化与入口

- 只在可中断的运行时提供停止：运行时有中断能力（Claude Code、基于 ACP 的 Grok）的 Manager 才能被停止。每轮一个进程的运行时（Codex exec、OMP `-p`、Pi、DSH）没有中断：停止被拒绝（`StopResult.CANNOT_INTERRUPT`，Telegram 与飞书回复「当前运行时不能中断回复，回复会照常完成。」），回复继续，不会为停止而杀进程。`POST /api/chat/stop` 返回状态 `cannot_interrupt`，`GET /api/chat/turn` 以及 Manager、Planner 会话摘要新增 `can_interrupt` 字段。
- 仪表盘：开启停止但当前回复的运行时不能中断时，停止按钮显示为禁用并以提示说明原因，点击停止会显示提示。页面在跟随自己的回复时持续读取 `can_interrupt`，因为轮次可能在首次读取后切换运行时。
- 停止不再结束常驻 Claude 的其他进程：中断之后，Claude 留下运行的内容归 Claude 自己；移除了进程树快照清理（`TurnTree.baseline`/`end_new`）。若中断在宽限期内未被响应，仍会连同进程树终止 Claude。
- 停止路径有上限：被停止的轮次最多等待 3 秒（`STOP_HANDLING_SEC`）处理待办事件、10 秒（`STOP_FINISH_SEC`）写入自己的记录和会话，之后不带这些写入结束，因此数据库缓慢或不可达不再卡住回复和 Manager 的锁。共用的 `abandon` 将被放弃步骤限制在 10 秒并在遗留时记录日志。会话在每个事件到达时立即记下，即使停止中断了事件处理也会保存。
- 事件不再阻塞流读取：运行时的事件立即计账（用量、上限、模型、会话、工具调用匹配），由独立任务按序记录，数据库写入缓慢不会拖延桥接调用所等待的 `tool_use` 的读取。已停止轮次的状态文本不再显示。运行时返回之后才发出的停止，不再被当作取消了已完成的轮次。
- MCP 桥接调用匹配：只有在轮次的会话确定由其运行后，Manager 才要求调用与其流匹配；桥接在诊断中记录匹配情况（按 id 或参数，到达时、等待后或未命中）。为评测启动的服务器可用可选的 `LOOPER_MCP_TRACE` 追踪桥接调用元数据，正常使用时不设置。
- Web 渠道：`agent.phase` 事件在智能体报告时带有 `activity` 和 `tool`。
- 评测与文档：扩展了真实路径停止检查（`evals/stop_realpath.py`）和 prompt 回归运行器，更新了 Agent System 页面和 Stop v2 RFC。
- 入口：`chat.stop_enabled`（默认关闭）、`POST /api/chat/stop`、`GET /api/chat/turn`、Telegram 与飞书 `/stop`、仪表盘停止按钮和 Esc。设置关闭时，作者报告行为无变化。
- 面向模型的变化：无。提示词、工具描述和 `Channel:` 行均未改变；停止拒绝文本发给用户，而非模型。

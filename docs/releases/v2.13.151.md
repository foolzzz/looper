# Looper v2.13.151

## Release Decision

**Who should upgrade:** Operators who run a Manager on an api runtime (a model reached over its HTTP API rather than a CLI). Everyone else can stay on v2.13.150.

**What this release solves:** [#688](https://github.com/foolzzz/looper/pull/688) keeps api Manager conversations in PostgreSQL instead of process memory, so they survive a restart, and hands the conversation over to a fresh session before the context fills.

**Breaking changes:** No. The change adds tables and one column and keeps existing columns and APIs; the new tables are created by the schema on start.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#688](https://github.com/foolzzz/looper/pull/688); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.151
```

## Behavior changes

- **Persistent history (#688):** `looper/agents/runtimes/api/session.py` no longer keeps the in-memory transcript (at most four sessions). `DbTranscript` (`looper/agents/runtimes/api/transcript.py`) reads and appends versioned neutral items through `looper/db/api_sessions.py`. Items are committed per completed request, under an advisory lock, so a restart resumes from the stored history.
- **Schema (#688):** `looper/db/schema.sql` adds `api_sessions` (one `protocol` per session: `openai-responses`, `anthropic-messages` or `openai-chat`), `api_session_items` (`seq`, `turn`, `model`, `item` JSONB, cascading delete) and `agent_sessions.pending_handoff` (TEXT, added with `IF NOT EXISTS`).
- **Cross-protocol resume (#688):** a stored session whose protocol differs from the requested one, or whose history cannot be parsed, is refused with `session <id> could not be resumed` rather than replayed.
- **Interrupted turn (#688):** if the stored history ends in a tool result, the next completed request also stores the note `(the previous turn did not finish)`. A first request that is cancelled before any history exists leaves no session to resume.
- **Cleanup (#688):** replacing an api session in `agent_sessions`, or deleting a Manager, deletes the old session's stored items in the same transaction.
- **Context handover (#688):** the session reports `context_tokens`, `context_limit` and `context_full` (new `ReportsContext` protocol). The limit is the smaller of 70% of the model's context window and 200,000 tokens (200,000 is used when the window is unknown). Above it, the Manager switches to a new session with reason `context_full`, records a `compact_boundary` event with the previous token count, and carries a summary into the new session. A context-overflow error on the first request triggers the same handover once instead of a plain retry, provided no output was streamed.
- **Failure handling (#688):** if the summary cannot be produced for a context handover, the turn fails with "The context handoff failed; the previous conversation has been retained. Retry with a shorter message." The summary is kept in `pending_handoff` until the new session has committed its first request, so a failed first request does not lose it. A failed first request with no committed history has nothing to summarize and is not handed over.
- **Model-visible changes:** yes. The Manager sends a new tool-free turn, `api_handoff_prompt` (a "[HANDOFF]" instruction asking for a continuation note within the character limit, stating it authorizes no work or tool calls); the handoff turn offers no tools (`_HandoffTools` returns an empty list and refuses any call). The next session's resume brief now contains that summary. Normal turns' tools and prompts are otherwise unchanged.
- **Docs and tests (#688):** `docs/architecture/rfcs/api-runtime-v0.zh-CN.md` is updated. New tests cover sessions, transcripts, context switching and an installed-package handoff; `tests/api_handoff_eval.py` is a real-Claude comparison harness against a prior prompt, not part of this draft's run.

## Upgrade and rollback

Re-run `install.sh` once v2.13.151 is published. The schema changes are additive and applied on start. Rolling back to v2.13.150 ignores the new tables and column, and api sessions go back to process memory, so their history is not carried across a restart; the stored rows stay unused.


### 行为变化与入口

- **持久化历史（#688）：**api 会话不再使用内存 transcript（最多 4 个会话）。`DbTranscript` 通过 `looper/db/api_sessions.py` 读写带版本的中立条目，按已完成的请求在咨询锁下提交，重启后可从存储的历史恢复。
- **Schema（#688）：**新增 `api_sessions`（每个会话一个 `protocol`：`openai-responses`、`anthropic-messages` 或 `openai-chat`）、`api_session_items`（`seq`、`turn`、`model`、JSONB `item`，级联删除）以及 `agent_sessions.pending_handoff`（TEXT，使用 `IF NOT EXISTS`）。
- **跨协议恢复（#688）：**存储会话的协议与请求不一致，或历史无法解析时，以 `session <id> could not be resumed` 拒绝，而不是重放。
- **中断的回合（#688）：**若存储历史以工具结果结尾，下一个完成的请求会同时存入注记 `(the previous turn did not finish)`。首个请求在尚无历史时被取消，则不留下可恢复的会话。
- **清理（#688）：**在 `agent_sessions` 中替换 api 会话，或删除 Manager 时，同一事务内删除旧会话的存储条目。
- **上下文交接（#688）：**会话报告 `context_tokens`、`context_limit`、`context_full`（新增 `ReportsContext` 协议）。上限为模型上下文窗口 70% 与 200,000 token 中的较小者（窗口未知时按 200,000）。超过上限后，Manager 以 `context_full` 为原因切换到新会话，记录带有此前 token 数的 `compact_boundary` 事件，并把摘要带入新会话。首个请求遇到上下文溢出错误时，在没有输出已流出的前提下，同样触发一次交接而非普通重试。
- **失败处理（#688）：**上下文交接无法生成摘要时，该回合失败并提示“The context handoff failed; the previous conversation has been retained. Retry with a shorter message.”。摘要保存在 `pending_handoff` 中，直到新会话提交首个请求，因此首个请求失败不会丢失摘要。没有已提交历史的失败首请求无可摘要内容，不做交接。
- **面向模型的变化：**有。Manager 新增无工具的交接回合 `api_handoff_prompt`（“[HANDOFF]”指令，要求在字数限制内写出续接说明，并声明不授权任何工作或工具调用）；交接回合不提供工具（`_HandoffTools` 返回空列表并拒绝任何调用）。下一个会话的恢复提示包含该摘要。普通回合的工具和提示词其余不变。
- **文档与测试（#688）：**更新 `api-runtime-v0.zh-CN.md`。新增会话、transcript、上下文切换和已安装包交接的测试；`tests/api_handoff_eval.py` 是与旧提示词对比的真实 Claude 评测脚本，本草稿未运行。

### 升级与回退

v2.13.151 发布后重跑 `install.sh`。schema 变更为增量，启动时应用。回退到 v2.13.150 会忽略新表和新列，api 会话回到进程内存，重启后历史不会保留；已存储的行保持不用。

# Looper v2.13.35

## Release Decision

**Who should upgrade:** Operators who want more than one Manager online, each with its own duty, tools, task scope and task templates (for example a "Code review" Manager next to the general one). An install that keeps only the default Manager has nothing to do.

**What this release solves:** [#388](https://github.com/foolzzz/looper/pull/388) ships stage 1 of scenario Managers. Before, Looper had one Manager for everything. Now several Managers run at once, the dashboard chat picks one, and a task reports back to the Manager that created it.

**Breaking changes:** No. No existing CLI command, configuration key or API shape changed. The database gains tables and columns (listed below), added with `IF NOT EXISTS` on start.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#388](https://github.com/foolzzz/looper/pull/388); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.35
```

## Behavior changes

- **Managers:** the default Manager (`manager`) stays: it uses every tool, sees every task and cannot be disabled. A scenario Manager (`manager-<key>`) has a name (at most 60 characters), a description (at most 300), a system prompt, an optional Agent Profile, `tools` (`all` or `tasks`), `task_scope` (`all` or `own`, independent of `tools`), `task_policy` (`free` or `templates_only`) and `enabled`. At most 8 Managers are enabled, the default one included. Each has its own session, MCP token, runs and spend. A deleted Manager is kept hidden so its chat threads keep their owner.
- **Endpoints:** `GET` and `POST /api/managers`; `PUT` and `DELETE /api/managers/:id`; `PUT` and `DELETE /api/managers/:id/templates/:key`. The chat API takes the chosen Manager (`target` on send, `manager` on the session and message reads); a thread belongs to the Manager that started it, and another Manager's thread answers 409.
- **Enabling and disabling:** a Manager is started or stopped without restarting the service. Disabling it ends its process and it is no longer a chat target; enabling it again resumes its session.
- **Task templates:** a Manager's template sets the project, work directory, workspace mode, requirement, Planner instructions, the Planner, Worker and Reviewer profiles, task roles and typed inputs. A call's value never overrides a field the template sets. With `templates_only`, a task needs a template.
- **Task attribution:** a task records its Manager (`manager_id`) and a snapshot of its template (`template`); the task list and detail carry both. A Manager with `task_scope=own` sees and acts on only its own tasks, in its task tools, overview counts, spend and task-derived reads.
- **Reports:** a task created from the web chat of a scenario Manager writes its acceptance and end into that thread. Tasks from the dashboard, a schedule, Telegram or Lark belong to the default Manager as before.
- **Dashboard:** the chat page has a Manager picker (shown once a second Manager exists), Settings → Managers edits Managers and their templates (with an example from `docs/examples/manager-github-pr-review.json`), and the task header shows its Manager and template.
- **Database:** new tables `managers`, `manager_task_templates` and `chat_threads`; new columns `tasks.manager_id`, `tasks.template`, `tasks.origin_thread` and `manager_actions.manager_id`. The default Manager's row takes its name from Settings → Roles once, cut to 60 characters.
- **Default-only installs:** the default Manager's prompt, tools, per-turn context, session and channels are unchanged; launch parity tests compare them byte for byte with the previous release.
- **Not in this stage:** Telegram and Lark reach only the default Manager (a bot per Manager and chat binding come later).
- **Known gaps, reported by the review of #388 and not changed in this release:** the review's P1 and P2 findings were filed for a follow-up issue after the merge. Among them: a concurrent disable and enable at the 8-Manager cap can leave the newly enabled Manager stopped while Settings shows success; disabling a Manager mid-reply does not send the web chat a final stopped reply; the API accepts task templates on the default Manager, whose tools never take them, while its turn still lists them; the first `looper_task_create` after a template is added or renamed can be refused; a cancelled template input check may leave its regex subprocess running; a scenario Manager's "follow settings" session preview reads the default Manager's profile; `GET /api/chat/messages` without `manager` returns another Manager's thread; renaming the default Manager shows only after a restart; and the name copied from Settings → Roles is cut at 60 characters.
- **Model-visible changes:** a scenario Manager's system prompt gains a `## This Manager's scope` section (its tools, its task scope, and, with templates, `## Task templates`: create a task with `looper_task_create` using `template` and `inputs`, ask for each required input and never invent one, restate the task with its template and inputs and create it only after the user confirms, and with `templates_only` do not create a task when no template fits). Each of its user messages lists its task templates and their inputs. `looper_task_create` takes `template` and `inputs` for a Manager that has templates. The Planner's `## Task` section gains the template's name, inputs and instructions for a task created from one. The default Manager's prompt, tools and per-turn context do not change. The eval suite gains `template_review_task` and `template_missing_input` dialogs. `docs/architecture/agent-system.md` documents the above.

## Upgrade and rollback

Re-run `install.sh` once v2.13.35 is published. The schema additions apply on the first start. Rolling back to v2.13.34 is safe: the added tables and columns stay unused, and tasks created by a scenario Manager keep working, but they are no longer reported to that Manager's thread.

## Optional Capability Activation & Use

No new optional capability activation is introduced in this release.

## 中文摘要

### 升级决策

**谁需要升级：**想同时在线多个 Manager、各有自己职责、工具、任务范围和任务模板的运维者（例如在通用 Manager 旁加一个“代码评审”Manager）。只保留默认 Manager 的安装无需操作。

**解决了什么：**[#388](https://github.com/foolzzz/looper/pull/388) 交付场景 Manager 第一阶段。此前 Looper 只有一个 Manager 处理所有事；现在可同时运行多个，仪表盘聊天可选择其一，任务向创建它的 Manager 回报。

**是否有破坏性变更：**无。现有 CLI、配置项、API 形态均未变化。数据库新增表和列（见下文），启动时以 `IF NOT EXISTS` 添加。

**如何验证：**运行 `looper --version` 核对版本为 2.13.35。

**贡献者：**维护者 @foolzzz 提交 [#388](https://github.com/foolzzz/looper/pull/388)；本次 patch release 无社区贡献。

```bash
looper --version   # looper 2.13.35
```

### 行为变化与入口

- Manager：默认 Manager（`manager`）不变，使用全部工具、看到所有任务、不能停用。场景 Manager（`manager-<key>`）有名称（至多 60 字符）、描述（至多 300）、系统提示词、可选 Agent Profile、`tools`（`all` 或 `tasks`）、`task_scope`（`all` 或 `own`，与 `tools` 相互独立）、`task_policy`（`free` 或 `templates_only`）和 `enabled`。启用的 Manager 至多 8 个（含默认）。各自有独立的会话、MCP 令牌、运行记录和花费。删除的 Manager 仅隐藏保留，使其聊天线程仍有归属。
- 接口：`GET`、`POST /api/managers`；`PUT`、`DELETE /api/managers/:id`；`PUT`、`DELETE /api/managers/:id/templates/:key`。聊天 API 接收所选 Manager（发送用 `target`，会话与消息读取用 `manager`）；线程属于发起它的 Manager，其他 Manager 的线程返回 409。
- 启用与停用：无需重启服务即可启动或停止 Manager。停用后其进程结束且不再是聊天目标；重新启用后续接原会话。
- 任务模板：模板可设置项目、工作目录、工作区模式、需求、Planner 指令、Planner/Worker/Reviewer 的 Profile、任务角色和带类型的输入。调用给出的值不会覆盖模板已设置的字段。`templates_only` 时建任务必须用模板。
- 任务归属：任务记录其 Manager（`manager_id`）和模板快照（`template`），任务列表与详情均带这两项。`task_scope=own` 的 Manager 在任务工具、概览计数、花费和任务相关读取中只看到、只操作自己的任务。
- 回报：场景 Manager 在网页聊天中创建的任务，其接受与结束写入该线程。来自仪表盘、定时任务、Telegram、Lark 的任务仍属默认 Manager。
- 仪表盘：聊天页新增 Manager 选择器（出现第二个 Manager 后显示）；Settings → Managers 编辑 Manager 及其模板（附 `docs/examples/manager-github-pr-review.json` 示例）；任务头部显示其 Manager 与模板。
- 数据库：新增表 `managers`、`manager_task_templates`、`chat_threads`；新增列 `tasks.manager_id`、`tasks.template`、`tasks.origin_thread`、`manager_actions.manager_id`。默认 Manager 的名称一次性取自 Settings → Roles，并截为 60 字符。
- 仅默认 Manager 的安装：默认 Manager 的提示词、工具、每轮上下文、会话和渠道不变；启动一致性测试与上一版逐字节对比。
- 本阶段不含：Telegram 与 Lark 仍只到默认 Manager（每个 Manager 一个机器人、聊天绑定留待后续）。
- 已知缺口（#388 的评审报告，本版本未改动）：评审的 P1、P2 项合并后另立 issue 跟进。其中包括：满 8 个时并发停用与启用可能让新启用的 Manager 未启动而设置页显示成功；停用正在回复的 Manager 不会给网页聊天发送最终的停止回复；API 接受默认 Manager 的任务模板，但其工具不接受，其回合仍会列出；添加或改名模板后第一次 `looper_task_create` 可能被拒；被取消的模板输入校验可能遗留正则子进程；场景 Manager 的“跟随设置”会话预览读取默认 Manager 的 Profile；不带 `manager` 的 `GET /api/chat/messages` 会返回其他 Manager 的线程；默认 Manager 改名需重启后才显示；取自 Settings → Roles 的名称被截为 60 字符。
- 面向模型的变化：场景 Manager 的系统提示词新增 `## This Manager's scope` 段（其工具、任务范围；有模板时还有 `## Task templates`：用 `looper_task_create` 的 `template` 和 `inputs` 建任务，向用户索取每个必填输入且不得编造，复述任务、模板与输入并仅在用户确认后创建，`templates_only` 时无合适模板则不建任务）。其每条用户消息会列出任务模板及输入。有模板的 Manager 的 `looper_task_create` 接收 `template` 和 `inputs`。由模板创建的任务，Planner 的 `## Task` 段新增模板名称、输入和指令。默认 Manager 的提示词、工具和每轮上下文不变。评测集新增 `template_review_task` 与 `template_missing_input` 对话。`docs/architecture/agent-system.md` 已同步说明。

### 升级与回退

发布后重跑 `install.sh`；首次启动时应用 schema 新增项。回退到 v2.13.34 安全：新增的表和列闲置，场景 Manager 创建的任务仍可运行，但不再向该 Manager 的线程回报。

### 可选能力启用与使用

本版本未新增可选能力启用入口。

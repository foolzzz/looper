# Looper v2.14.118

This is the patch release v2.14.118, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.117: workflow phase broadcasts and a delivery process record ([#1193](https://github.com/foolzzz/looper/pull/1193)).

## Release Decision

**Who should upgrade:** Operators who use workflow presets, in particular those that set `phase_notices` or want a record of which roles, models and review rounds a task used. Installations and tasks without a workflow see no change in behavior, apart from the one-time database migration below.

**What this release solves:** [#1193](https://github.com/foolzzz/looper/pull/1193). A task with a workflow that sets `phase_notices` reports each phase or round to its channels in one deterministic line (plan created, review round, verification start and result, escalation, blocked condition). A task with a workflow that ends, completed or failed, now stores a code-generated process record (roles, runtimes and models actually used, fallbacks, review rounds, verification, escalations) that the task page and the task tools show.

**Breaking changes:** No. The database gains one column, `tasks.process_record`, applied on first start. Tasks without a workflow are unchanged.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.14.118
```

**Contributors:** Maintainer @foolzzz authored [#1193](https://github.com/foolzzz/looper/pull/1193); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.117 upgrades directly. This release has a database change, applied automatically on the first start and recorded once as the `task_process_record` migration: `tasks` gains a nullable `process_record` JSONB column (an object when set). Because the schema changes, take the usual database backup before upgrading; an older binary should not be started on the upgraded database without restoring it.

## Behavior changes

- **Phase broadcasts.** Only for a workflow with `phase_notices` true (default false). Typed events produce one Chinese line each, built from persisted data and not by a model: plan created (roles, step breakdown of at most 12 steps, review panel members as acceptance or advisory, verification role, then "开始执行"), review round (blocking count per member), verification start, verification result, escalation, and a step whose start condition cannot be met. They go through the Manager to Telegram and Lark, and to the web thread. The plan-created line replaces the count-based "decomposed into N steps" progress message for Telegram and Lark tasks; without `phase_notices` the existing count-based messages are kept.
- **Process record.** When a task with a workflow completes or fails, the Planner builds a record with four sections (Roles, Reviews, Verification, Escalations) from the workflow, the journal and the task's run records: configured Profiles, each run's role, Profile, runtime, requested model and runtime-reported model (kept separate, a missing value is shown as not recorded), profile fallbacks, review rounds and seats, adjudications and late reviews, verification HEADs and outcomes, gate topics and conclusions. If the run records cannot be read, the record says so and an error activity is logged. The record is stored in `tasks.process_record`, cleared when the task is restarted, and always carries the remote-environment notice that read-only or dry-run safety is not enforced by Looper.
- **Where it shows.** The task detail view gains `process_record` (`sections`, `remote_safety`, `omitted`); the dashboard task page draws it as a "Process record" card. The compact task view of the `looper_tasks` tool gives it as text beginning `## Process record`, capped at 6000 characters and ending `…truncated` when cut. The stored record is bounded at 60000 characters by omitting whole entries, with the count in `omitted`. The task's result text for a workflow task ends with the line "Process record: see the task page" instead of the record itself. Note that the PR description and the architecture document describe the section as appended to the result; the code stores it separately, as described here.
- **Review rounds.** A review round is now also journaled (`review_round`) for an ordinary built-in review step in a workflow task, and a stale round is journaled only once per round.
- **Verification journal.** The one-line verification summary is clipped with the shared journal clip, no longer cut at its first line break.
- **Unchanged:** tasks without a workflow (their result text and prompts stay as before and the additional run records are not queried), the review panel and verification rules themselves, and no new channel command or dashboard aggregation.
- **Model-visible changes:** Yes, small. For workflow tasks the `looper_tasks` tool description now mentions the process record and its compact task view carries it, so the Manager model sees it when it reads a task. The delivered result text and failure closing note of a workflow task gain the line "Process record: see the task page", which the Manager and channels can relay. The phase lines are code-generated notices to operators, not prompts. The Planner's, Worker's and Reviewer's prompts and contracts are unchanged. Tasks without a workflow see none of this.

## 中文摘要

本版本是 patch release v2.14.118（热修线，每个合并的改动立即发布）。自 v2.14.117 以来只合并了一项改动：工作流阶段播报与交付过程记录（[#1193](https://github.com/foolzzz/looper/pull/1193)）。

### 升级决策

**谁需要升级：**使用工作流预设的运维者，尤其是设置了 `phase_notices` 或需要留存任务所用角色、模型和评审轮次记录的人。没有工作流的安装和任务行为无变化（仅有下述一次性数据库迁移）。

**解决了什么：**[#1193](https://github.com/foolzzz/looper/pull/1193)。工作流设置 `phase_notices` 后，任务把每个阶段或轮次以确定性的一行播报到其渠道（计划已建、评审轮次、验证开始与结果、升级、条件受阻）。有工作流的任务结束（完成或失败）时会保存由代码生成的过程记录（角色、实际使用的运行时和模型、回落、评审轮次、验证、升级），任务页和任务工具可查看。

**是否有破坏性变更：**否。数据库新增一列 `tasks.process_record`，首次启动时自动应用；没有工作流的任务不变。

**如何验证：**核对版本为 2.14.118。

**贡献者：**维护者 @foolzzz 提交 [#1193](https://github.com/foolzzz/looper/pull/1193)；本版本无社区贡献。

```bash
looper --version   # looper 2.14.118
```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.117 上的安装可直接升级。本版本有数据库变更，首次启动时自动应用并以 `task_process_record` 迁移记录一次：`tasks` 新增可为空的 `process_record` JSONB 列（有值时为对象）。由于结构有变，升级前请照常备份数据库；未恢复备份时不要在已升级的数据库上启动旧版本。

### 行为变化与入口

- **阶段播报。**仅对 `phase_notices` 为 true 的工作流生效（默认 false）。类型化事件各生成一行中文，由持久化数据拼出，不由模型生成：计划已建（角色、最多 12 步的步骤拆分、评审小组成员标明验收或建议、验证角色，随后“开始执行”）、评审轮次（各成员的 blocking 数）、验证开始、验证结果、升级，以及开始条件无法满足的步骤。它们经 Manager 发往 Telegram、Lark 和网页对话。计划已建这一行取代 Telegram 和 Lark 任务中按步骤数的“已分解为 N 个步骤”进度消息；未启用 `phase_notices` 时保留原有的按数量进度消息。
- **过程记录。**有工作流的任务完成或失败时，Planner 依据工作流、日志和任务的运行记录生成含四节（Roles、Reviews、Verification、Escalations）的记录：配置的 Profile、每次运行的角色、Profile、运行时、请求的模型和运行时报告的模型（分开记录，缺失显示为未记录）、Profile 回落、评审轮次与席位、裁定与迟到评审、验证的 HEAD 与结果、关卡主题与结论。运行记录读取失败时，记录会如实说明并记一条错误活动。记录存于 `tasks.process_record`，任务重启时清除，并始终带有“远程环境的只读或演练安全不由 Looper 强制”的声明。
- **查看位置。**任务详情视图新增 `process_record`（`sections`、`remote_safety`、`omitted`）；仪表盘任务页以“Process record”卡片显示。`looper_tasks` 工具的精简任务视图以 `## Process record` 开头的文本给出，上限 6000 字符，截断时以 `…truncated` 结尾。存储的记录以省略整条的方式限制在 60000 字符内，数量记入 `omitted`。工作流任务的结果文本末尾是“Process record: see the task page”一行，而不是记录本身。注意：PR 描述和架构文档称该节附加在结果之后，代码实际是单独存储，如上所述。
- **评审轮次。**工作流任务中普通的内置评审步骤现在也会记入 `review_round` 日志；过期轮次每轮只记一次。
- **验证日志。**单行验证摘要改用共享的日志截断，不再在首个换行处截断。
- **不变：**没有工作流的任务（结果文本和提示词不变，也不查询额外的运行记录）、评审小组和验证规则本身，也没有新增渠道命令或仪表盘聚合。
- **面向模型的变化：**有，较小。对工作流任务，`looper_tasks` 工具描述现在提到过程记录，其精简任务视图带有该记录，因此 Manager 模型读取任务时会看到。工作流任务的交付结果文本和失败收尾说明新增“Process record: see the task page”一行，Manager 和渠道可转述。阶段播报是面向运维者的代码生成通知，不是提示词。Planner、Worker 和 Reviewer 的提示词与契约不变。没有工作流的任务不受影响。

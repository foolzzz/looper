# Looper v2.14.39

This is the patch release v2.14.39, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.38: `loopercli schedule-log --tail N` now prints exactly the last N lines ([#991](https://github.com/foolzzz/looper/pull/991)).

## Release Decision

**Who should upgrade:** Anyone who runs v2.14.38 or earlier and reads schedule run logs with `loopercli schedule-log` with `--tail N`.

**What this release solves:** The tail is now paged on the client. [#991](https://github.com/foolzzz/looper/pull/991) asks the server for the tail with the largest page (4 MiB). When that page may begin in the middle of a line, the client reads earlier byte ranges with `offset` and `limit_bytes` until it holds N whole lines or reaches the start of the file, then prints exactly the last N lines.

**Breaking changes:** No. No API or configuration is removed or changed, and there is no new migration or setting. The server API (`schedule_admin.run_log`) does not change.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#991](https://github.com/foolzzz/looper/pull/991); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.39
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.38 upgrades directly. This release adds no migration and no new setting.

## Behavior changes

- **`schedule-log --tail` pages backward ([#991](https://github.com/foolzzz/looper/pull/991)).** With `--tail N` (1 to 5000), the client sends one request with `tail_lines` and `limit_bytes` of 4 MiB. If the returned page starts at the beginning of the file, or at an offset inside the final 4 MiB window (which means the server already found N whole lines), it is used as is. Otherwise the client requests the preceding byte ranges of up to 4 MiB each and prepends them until the data holds enough newlines or the start of the file is reached. It then keeps only the last N lines (N plus the trailing empty piece when the output ends with a newline) and prints them, so the output is exactly the last N lines even when they span more than one page.
- **Reported offset and size.** In `--json` mode the reported `offset` is the offset of the first printed byte and `bytes` is the length of the printed text. Other fields come from the first response. Without `--tail`, the forward read loop is unchanged.
- **Model-visible changes:** None. No prompt, skill or tool description changes. The other change in the pull request is its tests.

### 行为变化与入口

- **`schedule-log --tail` 向前分页（[#991](https://github.com/foolzzz/looper/pull/991)）。**使用 `--tail N`（1 到 5000）时，客户端先发一次带 `tail_lines` 和 4 MiB `limit_bytes` 的请求。若返回的页从文件开头开始，或起点落在最后 4 MiB 窗口内（说明服务端已找到 N 个完整行），则直接使用。否则客户端依次请求之前最多 4 MiB 的字节区间并拼到前面，直到换行数足够或到达文件开头；随后只保留最后 N 行（输出以换行结尾时多算一个末尾空片段）并输出，因此即使最后 N 行跨越多页，输出也恰好是最后 N 行。
- **报告的 offset 与大小。**`--json` 模式下，`offset` 是实际输出的第一个字节的偏移，`bytes` 是实际输出的长度，其余字段来自第一次响应。不带 `--tail` 时，向前读取的循环不变。
- **面向模型的变化：**无。提示词、技能和工具描述均不变。该拉取请求的另一项改动是测试。

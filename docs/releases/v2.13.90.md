# Looper v2.13.90

## Release Decision

**Who should upgrade:** Anyone who calls the project agent-settings or allowed-profiles routes from a script, or who edits a project's settings layers or its allowed profiles in the dashboard. Everyone else gets no change.

**What this release solves:** [#544](https://github.com/foolzzz/looper/pull/544) moves a project's setting layers and the profiles its Planners may choose onto versioned API operations and removes the five legacy project routes.

**Breaking changes:** Yes. `GET` and `PUT /api/projects/{id}/agent-settings`, `PUT /api/projects/{id}/agent-settings/roles/{role}` and `GET` and `PUT /api/projects/{id}/allowed-profiles` are removed; a script that calls them must use `POST /api/v1/project_agent_settings/get`, `/update`, `/update_role`, `POST /api/v1/allowed_profiles/get` or `/replace` with `project_id` in the body (`values` for the settings updates, `profile_ids` for a replace), and reads the answer from the v1 envelope (`result`). A settings update that changes a concurrency limit or raises the spend cap now asks for confirmation. The dashboard shipped in this release already uses the new operations.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#544](https://github.com/foolzzz/looper/pull/544); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.90
```

## Behavior changes

- **New operations ([#544](https://github.com/foolzzz/looper/pull/544)):** the new `looper/agents/v1_domains/project_settings.py` registers `project_agent_settings.get` and `allowed_profiles.get` (risk `read`), `project_agent_settings.update`, `.update_role` and `allowed_profiles.replace` (risk `write`) as `POST /api/v1/...`, all with closed argument schemas. `update` takes `{project_id, values}`, `update_role` adds a `role` (`planner`, `worker` or `reviewer`), `replace` takes `{project_id, profile_ids}`. They call the same `agent_settings` and `projects` functions as the removed routes; `replace` still replaces the list and prunes Planner choices in one transaction, and an empty list lifts the restriction.
- **Confirmation:** the two settings updates declare that they can need confirmation. The code asks for it when `max_concurrency` is among the values or the update raises or removes the effective per-run spend cap. The dashboard raises such a pending answer (HTTP 202) as an `unavailable` error.
- **Removed routes:** the five legacy routes, their three URL patterns, `_write_layer` and `_handle_agent_settings` are removed from `looper/agents/http_server.py`. Errors now come in the v1 error shape instead of the old `{"error": ...}` body.
- **Dashboard:** `web/src/lib/api.ts` fetches and updates project settings and allowed profiles through the new operations.
- **Tooling and docs:** the prompt regression evals (`evals/prompt_regression/dialogs.py`, `runner.py`) use the new operations; `README.md`, `README.zh-CN.md`, the v2.7.0 and v2.10.0 release notes and the message that names the settings route in `looper/agents/projects.py` now name them.
- **Tests:** `tests/test_api_v1_project_agent_settings.py` and `tests/test_api_v1_project_agent_settings_db.py` were added; several existing tests and `web/src/url-state.test.tsx` were moved to the new operations.
- **Model-visible changes:** one text. The 400 answer for a project update that sets `planner_harness_prompt`, `worker_harness_prompt`, `model` or `run_budget_usd` now names `POST /api/v1/project_agent_settings/update` and `/update_role` instead of the removed `PUT` routes. Manager, Planner, Worker and Reviewer prompts, role recommended prompts and Tool declarations are unchanged. The new operations appear in the v1 operation catalog.
- **Not confirmed in code:** whether the new operations refuse API clients (the module does not declare them operator-only, although the description of [#544](https://github.com/foolzzz/looper/pull/544) names operator-only boundaries); that a project-layer update never needs the concurrency recheck the removed role route ran (the layer rules refuse a concurrency limit outside a Worker or Reviewer global role layer, so it appears moot); and `docs/architecture/agent-system.md` still describes the removed routes. This draft did not run any test.

## Upgrade and rollback

Re-run `install.sh` once v2.13.90 is published. No data migration; saved settings and allowed profiles are untouched. Update any script that used the removed routes. Rolling back to v2.13.89 restores them together with the old dashboard.

**贡献者：**维护者 @foolzzz 提交 [#544](https://github.com/foolzzz/looper/pull/544)；本次 patch release 无社区贡献。

### 行为变化与入口

- **新操作（[#544](https://github.com/foolzzz/looper/pull/544)）：**新增 `looper/agents/v1_domains/project_settings.py`，注册 `project_agent_settings.get`、`allowed_profiles.get`（风险 `read`），`project_agent_settings.update`、`.update_role`、`allowed_profiles.replace`（风险 `write`），路径为 `POST /api/v1/...`，参数均为封闭对象。`update` 传 `{project_id, values}`，`update_role` 另加 `role`（`planner`、`worker` 或 `reviewer`），`replace` 传 `{project_id, profile_ids}`。它们调用与被移除路由相同的 `agent_settings` 与 `projects` 函数；`replace` 仍在一个事务中替换列表并清理 Planner 的选择，空列表解除限制。
- **确认：**两个设置更新声明可能需要确认。代码在 values 含 `max_concurrency`，或更新会提高或移除生效的单次花费上限时要求确认。仪表盘把这种待确认应答（HTTP 202）作为 `unavailable` 错误抛出。
- **移除的路由：**五条旧路由、三个 URL 正则、`_write_layer` 和 `_handle_agent_settings` 已从 `looper/agents/http_server.py` 移除。错误现在使用 v1 错误格式，不再是旧的 `{"error": ...}`。
- **仪表盘：**`web/src/lib/api.ts` 通过新操作读取和更新项目设置与允许的 Profile。
- **工具与文档：**提示回归评测（`evals/prompt_regression/dialogs.py`、`runner.py`）改用新操作；`README.md`、`README.zh-CN.md`、v2.7.0 与 v2.10.0 发布说明以及 `looper/agents/projects.py` 中指明设置路由的提示文字已改为新操作。
- **测试：**新增 `tests/test_api_v1_project_agent_settings.py` 与 `tests/test_api_v1_project_agent_settings_db.py`；若干现有测试和 `web/src/url-state.test.tsx` 已改用新操作。
- **面向模型的变化：**有一处文字。项目更新设置 `planner_harness_prompt`、`worker_harness_prompt`、`model` 或 `run_budget_usd` 时返回的 400 提示，现在指向 `POST /api/v1/project_agent_settings/update` 与 `/update_role`，不再是已移除的 `PUT` 路由。Manager、Planner、Worker、Reviewer 的 prompt、角色推荐 prompt 以及 Tool 声明均未改动。新操作出现在 v1 操作目录中。
- **代码中未确认：**新操作是否拒绝 API 客户端（模块未声明 operator_only，但 [#544](https://github.com/foolzzz/looper/pull/544) 的描述提到操作员边界）；项目层更新是否永远不需要被移除的角色路由曾做的并发复查（层规则拒绝在 Worker 或 Reviewer 全局角色层之外设置并发上限，看来不成问题）；以及 `docs/architecture/agent-system.md` 仍在描述已移除的路由。本草稿未运行任何测试。

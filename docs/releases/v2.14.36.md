# Looper v2.14.36

This is the patch release v2.14.36, a hotfix line in which each merged change ships at once. It ships the four changes merged since v2.14.35: planned upgrades with `looper service upgrade` and Telegram restart delivery ([#949](https://github.com/foolzzz/looper/pull/949)), command schedules in the schedule API with a log reader ([#960](https://github.com/foolzzz/looper/pull/960)), retention for run data and rotation for service logs ([#964](https://github.com/foolzzz/looper/pull/964)), and command schedule fields in config export and import ([#980](https://github.com/foolzzz/looper/pull/980)).

## Release Decision

**Who should upgrade:** Anyone who wants to upgrade a running service with one command (plan, drain, install, restart, verify), create and read command schedules through the API, bound the growth of run history and logs, or move command schedules between installations with config export and import. Anyone running a Telegram bot who does not want messages that arrive during a restart to be dropped.

**What this release solves:** [#949](https://github.com/foolzzz/looper/pull/949) makes `looper service upgrade` execute its plan and adds `looper service restart --drain`, a deploy report, and a durable Telegram inbox. [#960](https://github.com/foolzzz/looper/pull/960) lets the schedule API create and read command schedules, with run columns, a status filter, 24-hour and 7-day statistics, and the new read-only `schedule_admin.run_log`. [#964](https://github.com/foolzzz/looper/pull/964) adds an hourly housekeeping pass and the `scheduler.run_retention_days` setting. [#980](https://github.com/foolzzz/looper/pull/980) carries command schedule fields through config export and import.

**Breaking changes:** No API or configuration is removed, and there is no new migration. One default changes: agent schedules no longer keep their run history forever (30 days by default, at least each schedule's newest 100 runs). See the behavior changes below.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#949](https://github.com/foolzzz/looper/pull/949), [#960](https://github.com/foolzzz/looper/pull/960), [#964](https://github.com/foolzzz/looper/pull/964) and [#980](https://github.com/foolzzz/looper/pull/980); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.35 upgrades directly. This release adds no migration: the command schedule columns it reads and writes are already in the schema, and the new retention setting is stored in `system_settings`.

[#964](https://github.com/foolzzz/looper/pull/964) runs its first housekeeping pass at startup right after the upgrade, so run history older than the retention period is deleted at the first start (see below).

## Behavior changes

- **`looper service upgrade` executes its plan ([#949](https://github.com/foolzzz/looper/pull/949)).** It accepts `--to <ref|wheel>`, `--timeout` (default 120 seconds), `--drain-timeout` (default 1200 seconds), `--no-force` and `--dry-run`. `--dry-run` still only prints the plan. Otherwise, by plan kind:
  - NOOP installs only.
  - WEB_ONLY installs and atomically replaces the served dashboard directory; a wheel upgrade keeps the running interpreter and does not touch its dependencies.
  - FULL (and CONTROL_PLANE) drains, stops the old process and refuses to install while it is still running, installs, restarts through the service manager and verifies. FULL drains active runs; CONTROL_PLANE drains turns.
  - Verification compares the running `system.components` with the target, and for a web change compares the served dashboard with the installed build. After a failed install the old service is started again and the drain cancelled.
  - A Git target is fast-forwarded and refused when the checkout has tracked changes. At the drain deadline the remaining runs are interrupted and listed in the report, unless `--no-force` is given, which cancels the deployment instead.
  - The result is printed and appended to the service log as one `service_upgrade` JSON line (plan, reasons, drain and gap seconds, interrupted runs, versions, status, error).
- **`looper service restart --drain` ([#949](https://github.com/foolzzz/looper/pull/949)).** It drains with scope runs before the restart and takes `--drain-timeout` and `--no-force`. Without `--drain`, restart is unchanged.
- **Drain lease ([#949](https://github.com/foolzzz/looper/pull/949)).** A drain started through the system API must now be kept alive: `drain_status` is polled at least every 30 seconds, otherwise admission resumes and the drain is cancelled. This is separate from the drain's own deadline.
- **Components manifest ([#949](https://github.com/foolzzz/looper/pull/949)).** The runtime fingerprint now covers `pyproject.toml` dependencies and `uv.lock`, a built dashboard records the source fingerprint of its inputs (`.source-fingerprint`), and `system.components` reports the current served dashboard fingerprints rather than only the startup ones. A dashboard built before this release is rebuilt by the first upgrade instead of being reported as unchanged. The repository gains a `setup.py` that carries the runtime fingerprint into wheels.
- **Telegram restart delivery ([#949](https://github.com/foolzzz/looper/pull/949)).** Polling no longer drops pending updates when it starts. Each update is saved in a small SQLite file under the runtime directory (one per channel and bot) before the polling client acknowledges it, replayed after a restart, and deduplicated by `update_id`. Updates older than `backlog_max_age_seconds` (default 600, a positive integer, settable in the Telegram channel config) are ignored with a log line. Managers wait for HTTP readiness before consuming the backlog. After delivery only the id is kept, not the message.
- **Command schedules in the API ([#960](https://github.com/foolzzz/looper/pull/960)).** Creating a schedule takes `kind` (`agent` or `command`, default `agent`); `kind` cannot change on update. Each kind is validated separately: a command schedule needs `command` (up to the gate command length, no NUL), accepts `env` (up to 64 names, none starting with `LOOPER_SCHEDULE_`, values up to 4096 characters) and an absolute, readable `env_file`, uses the minimum interval of a gated schedule, defaults to no timeout, and rejects `requirement`, templates, gate, budgets, profile overrides, task limits and `user_gates: on`. Agent schedules reject the command fields, and `requirement` is no longer required by the create schema for command schedules.
- **Alert fields in the schedule API ([#960](https://github.com/foolzzz/looper/pull/960)).** Create and update accept `success_deadline`, `alert_failures_after` (1 to 1000), `alert_stale_after_seconds` (300 to 2592000) and `alert_overlap_after` (0 to 10000). The schedule view returns `kind`, `command`, `env`, `env_file`, `success_deadline`, `alert_policy` (the effective value, whether it is the default and its source) and the `deadline_since` and `overlap_since` alerts.
- **Run list and `schedule_admin.run_log` ([#960](https://github.com/foolzzz/looper/pull/960)).** Runs carry `started_at`, `exit_code`, `exit_signal`, `duration_seconds`, `log` (path, bytes, truncated) and `log_tail`. The run list takes a `status` filter and returns `stats` for the last day and week (runs, succeeded, failed, success rate, average and maximum seconds). The new read-only `schedule_admin.run_log` returns a base64 byte page of a run's log (`offset`, `limit_bytes` up to 4 MiB, or `tail_lines` up to 5000, not both), confined to the schedule log directory; a log removed by retention or not yet written answers 404. `loopercli` prints each run's log info under the runs table. The notification kind enum now includes the deadline and overlap kinds.
- **Run retention and log rotation ([#964](https://github.com/foolzzz/looper/pull/964)).** The scheduler runs a housekeeping pass in the background at startup and then hourly.
  - The new setting `scheduler.run_retention_days` (default 30, 1 to 3650) can be read and set through the scheduler settings API and the Manager settings tool.
  - Runs whose `finished_at` is older than the retention period are deleted, except each schedule's newest 100 runs and any queued, gating or running run. Notifications older than the period are deleted; a newer notification of a deleted run stays with `run_id` cleared. Tasks created by those runs are not affected. Deletion is in batches of 5000.
  - Command logs are deleted by age and by a 2 GiB total cap (oldest first), so a kept run may no longer have its log. Logs of open runs are never deleted. Run directories of finished or lost command runs and runner files older than 31 days are removed; the pass keeps files when the runner processes cannot be observed.
  - `serve.log` and `probe.log` are copied and truncated at 20 MiB, keeping 5 copies.
  - Not in this release: the retention setting in the dashboard's Settings page and in the Manager settings tool's description (a follow-up).
- **Config export and import ([#980](https://github.com/foolzzz/looper/pull/980)).** Schedule entries carry `kind`, `command`, `env`, `env_file`, `success_deadline` and the three alert thresholds. For an agent schedule these are written only when they are not the default, so its export is unchanged. Import validates by kind, still disables imported schedules, and skips an entry whose name matches an existing schedule of the other kind. `env_file` carries only its path, never the file's contents; when it does not exist on the importing machine the schedule is imported with a note. `scheduler.run_retention_days` is part of the exported scheduler settings. This must ship with the command schedule API of [#960](https://github.com/foolzzz/looper/pull/960), and it does.
- **Model-visible changes:** No prompt or skill text given to a model changes. The Manager settings tool now accepts and shows `run_retention_days` (confirmation and result lines in Chinese, like the other scheduler settings), but its tool description is not updated ([#964](https://github.com/foolzzz/looper/pull/964)). Telegram messages that arrived during a restart and were dropped before now reach the Manager after it starts, up to the age limit ([#949](https://github.com/foolzzz/looper/pull/949)). The descriptions of the operator-only drain and components system operations changed; they are not offered to the Manager.

## 中文摘要

本版本是 patch release v2.14.36（热修线，每个合并的改动立即发布）。自 v2.14.35 以来合并了四项改动：用 `looper service upgrade` 执行计划好的升级并持久化 Telegram 重启期间的消息（[#949](https://github.com/foolzzz/looper/pull/949)）、定时任务 API 支持命令类任务并提供日志读取（[#960](https://github.com/foolzzz/looper/pull/960)）、运行数据保留与服务日志轮转（[#964](https://github.com/foolzzz/looper/pull/964)）、配置导出导入携带命令类定时任务字段（[#980](https://github.com/foolzzz/looper/pull/980)）。

### 升级决策

**谁需要升级：**想用一条命令升级运行中的服务（计划、排空、安装、重启、验证）、通过 API 创建和读取命令类定时任务、限制运行历史和日志的增长，或用配置导出导入迁移命令类定时任务的人；以及不希望重启期间到达的 Telegram 消息被丢弃的人。

**解决了什么：**[#949](https://github.com/foolzzz/looper/pull/949) 让 `looper service upgrade` 真正执行计划，新增 `looper service restart --drain`、部署报告和持久化的 Telegram 收件箱。[#960](https://github.com/foolzzz/looper/pull/960) 让定时任务 API 能创建和读取命令类任务，带运行列、状态过滤、24 小时和 7 天统计，以及新的只读操作 `schedule_admin.run_log`。[#964](https://github.com/foolzzz/looper/pull/964) 增加每小时一次的清理和 `scheduler.run_retention_days` 设置。[#980](https://github.com/foolzzz/looper/pull/980) 让配置导出导入携带命令类定时任务字段。

**是否有破坏性变更：**否。不移除任何 API 或配置，也没有新的迁移。有一项默认值变化：智能体类定时任务不再永久保留运行历史（默认 30 天，每个任务至少保留最新 100 条）。详见下文。

**如何验证：**运行 `looper --version` 核对版本为 2.14.36。

**贡献者：**维护者 @foolzzz 提交 [#949](https://github.com/foolzzz/looper/pull/949)、[#960](https://github.com/foolzzz/looper/pull/960)、[#964](https://github.com/foolzzz/looper/pull/964) 和 [#980](https://github.com/foolzzz/looper/pull/980)；本版本无社区贡献。

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.35 上的安装可直接升级。本版本没有新迁移：命令类定时任务用到的列已在数据库结构中，新的保留设置存放在 `system_settings`。

[#964](https://github.com/foolzzz/looper/pull/964) 在升级后的首次启动时立即执行第一次清理，所以早于保留期的运行历史会在首次启动时被删除（见下）。

### 行为变化与入口

- **`looper service upgrade` 执行计划（[#949](https://github.com/foolzzz/looper/pull/949)）。**支持 `--to <ref|wheel>`、`--timeout`（默认 120 秒）、`--drain-timeout`（默认 1200 秒）、`--no-force` 和 `--dry-run`；`--dry-run` 仍只打印计划。按计划类型：
  - NOOP 只安装。
  - WEB_ONLY 安装并原子替换正在提供服务的仪表盘目录；wheel 升级保留运行中的解释器，不改动其依赖。
  - FULL（及 CONTROL_PLANE）先排空，停止旧进程并在其仍在运行时拒绝安装，然后安装、通过服务管理器重启并验证。FULL 排空进行中的运行，CONTROL_PLANE 排空对话。
  - 验证会比较运行中的 `system.components` 与目标；Web 变更还会比较所提供的仪表盘与安装的构建。安装失败后会重新启动旧服务并取消排空。
  - Git 目标以快进方式合并，检出目录有已跟踪的改动时拒绝升级。排空截止时仍在运行的任务会被中断并列入报告；加 `--no-force` 则改为取消部署。
  - 结果会打印，并作为一行 `service_upgrade` JSON（计划、原因、排空和空档秒数、被中断的运行、版本、状态、错误）追加到服务日志。
- **`looper service restart --drain`（[#949](https://github.com/foolzzz/looper/pull/949)）。**重启前以 runs 范围排空，支持 `--drain-timeout` 和 `--no-force`。不加 `--drain` 时重启行为不变。
- **排空租约（[#949](https://github.com/foolzzz/looper/pull/949)）。**通过系统 API 开始的排空现在必须保持心跳：至少每 30 秒轮询一次 `drain_status`，否则恢复接收并取消排空。这与排空自身的截止时间无关。
- **组件清单（[#949](https://github.com/foolzzz/looper/pull/949)）。**运行时指纹现在覆盖 `pyproject.toml` 的依赖和 `uv.lock`；构建出的仪表盘记录其源文件指纹（`.source-fingerprint`）；`system.components` 报告当前所提供仪表盘的指纹，而不只是启动时的。此版本之前构建的仪表盘会在首次升级时重新构建，而不会被报告为未变化。仓库新增 `setup.py`，把运行时指纹带进 wheel。
- **Telegram 重启投递（[#949](https://github.com/foolzzz/looper/pull/949)）。**开始轮询时不再丢弃待处理的更新。每条更新在轮询客户端确认之前先保存到运行时目录下的一个小型 SQLite 文件（每个渠道和机器人一个），重启后重放，并按 `update_id` 去重。早于 `backlog_max_age_seconds`（默认 600，正整数，可在 Telegram 渠道配置中设置）的更新会被忽略并记录日志。Manager 等 HTTP 就绪后才消费积压的消息。投递后只保留 id，不保留消息内容。
- **API 中的命令类定时任务（[#960](https://github.com/foolzzz/looper/pull/960)）。**创建定时任务时可指定 `kind`（`agent` 或 `command`，默认 `agent`）；更新时不能更改 `kind`。两类分别校验：命令类需要 `command`（长度不超过 gate 命令上限，不含 NUL），接受 `env`（最多 64 个名称，不得以 `LOOPER_SCHEDULE_` 开头，值至多 4096 字符）和绝对路径且可读的 `env_file`，使用带 gate 任务的最小间隔，默认无超时，并拒绝 `requirement`、模板、gate、预算、profile 覆盖、任务限制和 `user_gates: on`。智能体类拒绝命令类字段；创建 schema 不再对命令类要求 `requirement`。
- **API 中的告警字段（[#960](https://github.com/foolzzz/looper/pull/960)）。**创建和更新接受 `success_deadline`、`alert_failures_after`（1 到 1000）、`alert_stale_after_seconds`（300 到 2592000）和 `alert_overlap_after`（0 到 10000）。定时任务视图返回 `kind`、`command`、`env`、`env_file`、`success_deadline`、`alert_policy`（生效值、是否为默认及来源）以及 `deadline_since` 和 `overlap_since` 告警。
- **运行列表与 `schedule_admin.run_log`（[#960](https://github.com/foolzzz/looper/pull/960)）。**运行带有 `started_at`、`exit_code`、`exit_signal`、`duration_seconds`、`log`（路径、字节数、是否截断）和 `log_tail`。运行列表支持 `status` 过滤，并返回最近一天和一周的 `stats`（运行数、成功数、失败数、成功率、平均和最长秒数）。新的只读操作 `schedule_admin.run_log` 以 base64 返回运行日志的字节分页（`offset` 与 `limit_bytes`，最大 4 MiB；或 `tail_lines`，最大 5000；二者不能同时使用），限制在定时任务日志目录内；日志被保留策略删除或尚未写入时返回 404。`loopercli` 在运行表下打印每次运行的日志信息。通知类型枚举新增截止时间和重叠两类。
- **运行保留与日志轮转（[#964](https://github.com/foolzzz/looper/pull/964)）。**调度器在启动时和之后每小时在后台执行一次清理。
  - 新设置 `scheduler.run_retention_days`（默认 30，范围 1 到 3650），可通过调度器设置 API 和 Manager 设置工具读取和修改。
  - `finished_at` 早于保留期的运行会被删除，但每个任务最新的 100 条运行以及排队、gate 中或运行中的运行除外。早于保留期的通知被删除；已删除运行的较新通知保留，其 `run_id` 置空。这些运行创建的任务不受影响。每批删除 5000 条。
  - 命令日志按时间以及 2 GiB 总量上限（先删最旧的）清理，所以保留下来的运行可能已没有日志。未结束运行的日志不会被删。已结束或丢失的命令运行目录、以及超过 31 天的 runner 文件会被删除；无法观察 runner 进程时，清理会保留这些文件。
  - `serve.log` 和 `probe.log` 超过 20 MiB 时复制后截断，保留 5 份。
  - 本版本未包含：仪表盘设置页中的保留设置，以及 Manager 设置工具描述中的说明（后续跟进）。
- **配置导出与导入（[#980](https://github.com/foolzzz/looper/pull/980)）。**定时任务条目携带 `kind`、`command`、`env`、`env_file`、`success_deadline` 和三个告警阈值。智能体类任务这些字段仅在非默认时写出，所以其导出不变。导入按类型校验，导入的任务仍为停用状态，与已有任务同名但类型不同的条目会被跳过。`env_file` 只带路径，不带文件内容；目标机器上不存在时仍导入并给出提示。`scheduler.run_retention_days` 属于导出的调度器设置。它必须与 [#960](https://github.com/foolzzz/looper/pull/960) 的命令类定时任务 API 同版发布，本版本满足这一点。
- **面向模型的变化：**给模型的提示词和技能文本都不变。Manager 设置工具现在接受并显示 `run_retention_days`（确认和结果行与其他调度器设置一样为中文），但工具描述未更新（[#964](https://github.com/foolzzz/looper/pull/964)）。此前在重启期间到达而被丢弃的 Telegram 消息，现在会在启动后送达 Manager，受时效上限约束（[#949](https://github.com/foolzzz/looper/pull/949)）。仅限运维的排空和组件系统操作的描述有变化，它们不提供给 Manager。

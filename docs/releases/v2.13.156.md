# Looper v2.13.156

## Release Decision

**Who should upgrade:** Operators who run scenario Managers on the Claude runtime and want idle Manager processes to be closed and resumed on the next message. Everyone else can stay on v2.13.155.

**What this release solves:** [#719](https://github.com/foolzzz/looper/pull/719) closes the resident Claude process of an idle scenario Manager after a configurable timeout and resumes its saved session on the next message, keeping routing and in-flight work. The timeout is stored per Manager, settable through the Managers API, the Settings form and configuration transfer. It is on by default (1800 seconds) for every scenario Manager, including existing ones.

**Breaking changes:** No. The built-in default Manager is never suspended, and `0` turns the timeout off for any Manager. Existing scenario Managers do get the 1800-second default on upgrade, so their idle processes start to close.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#719](https://github.com/foolzzz/looper/pull/719); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.156
```

## Behavior changes

- **Idle suspension (#719):** a fleet-owned sweep runs every 5 seconds. For a scenario Manager with a non-zero timeout, it closes the resident process once the Manager has been idle for the timeout (`try_suspend_idle` in `looper/agents/tiers/manager.py`). The Manager stays enabled and keeps its session state. It is not closed while it is busy, handling a message, has a turn or token in progress, has pending bus messages, or while a lifecycle step (admission, start, reset) holds its gate; any of these restarts the idle clock.
- **Claude runtime only (#719):** `looper/agents/claude_cli.py` closes a process only when its output shows no turn, no background Bash/Agent/teammate job and no unknown lifecycle event, and no interrupt or end is in progress; otherwise it is kept. The Grok ACP runtime and per-turn runtimes never close (`try_stop_if_idle` returns `False`), so the timeout has no effect on them. A failed close keeps the resident state for retry and logs only the exception type, not its text.
- **New field `idle_timeout_seconds` (#719):** an integer, `0` (off) or 60 to 86400. A `managers` column (`NOT NULL DEFAULT 1800`, with a check constraint) is added by the schema migration; the built-in `manager` row is set to `0` and its table check now requires `0`. The API refuses other values, and refuses non-zero for the default Manager. Editing the value updates the running agent without restart. It is accepted in the `/api/v1` Manager config schema and in configuration transfer files, where the default Manager entry may set only `id`, `name`, `description` and `idle_timeout_seconds: 0`; scenario entries that omit it get 1800.
- **Dashboard (#719):** the Managers settings form has an "Idle timeout (seconds)" field (default 1800 for new Managers) and rejects values other than 0 or 60 to 86400; it is not shown as editable for the default Manager.
- **Model-visible changes:** none. No prompts, tool descriptions or tool schemas change; the Manager config schema of `/api/v1` gains the field above.
- **Docs:** none besides this release's notes and the CHANGELOG entry.

## Upgrade and rollback

Re-run `install.sh`. The database migration runs on start and adds the column with the 1800 default. To keep a Manager resident, set its idle timeout to `0`. Rolling back to v2.13.155 leaves the extra column in place and unused.

## Optional Capability Activation & Use

### Manager idle timeout

**Activation:** On by default at 1800 seconds for scenario Managers. Change it per Manager in Settings → Managers (Idle timeout), or with `idle_timeout_seconds` in the Managers API or a configuration file.

**Validation:** Create a scenario Manager with a 60-second timeout, leave it idle and watch the log for "resident suspended (idle timeout)"; then send it a message and check it answers in the same conversation.

**Disable / rollback:** Set `idle_timeout_seconds` to `0` for that Manager; the change applies to the running agent.

**Authority boundary:** The sweep only closes a Manager's own resident process and never the default Manager. It adds no tools and no permissions, and does not delete sessions.

### 行为变化与入口

- **空闲挂起（#719）：**由 fleet 持有的巡检每 5 秒运行一次。对超时非零的场景管家，空闲达到超时后关闭其常驻进程（`looper/agents/tiers/manager.py` 的 `try_suspend_idle`）。管家保持启用并保留会话状态。忙碌、正在处理消息、有进行中的回合或令牌、总线有待处理消息，或生命周期步骤（接收、启动、重置）持有门闩时不会关闭，这些情况都会重置空闲计时。
- **仅 Claude 运行时（#719）：**`looper/agents/claude_cli.py` 仅当输出显示没有回合、没有后台 Bash/Agent/队友任务、没有未知生命周期事件，且没有中断或结束在进行时才关闭进程，否则保留。Grok ACP 与按回合运行时从不关闭（`try_stop_if_idle` 返回 `False`），超时对它们无效。关闭失败会保留常驻状态以便重试，日志只记录异常类型，不记录异常文本。
- **新字段 `idle_timeout_seconds`（#719）：**整数，`0`（关闭）或 60 至 86400。数据库迁移为 `managers` 表新增列（`NOT NULL DEFAULT 1800`，带检查约束）；内置 `manager` 行设为 `0`，其表检查现要求为 `0`。API 拒绝其他值，也拒绝默认管家使用非零值。修改后无需重启即更新运行中的管家。该字段出现在 `/api/v1` 的管家配置 schema 和配置迁移文件中；默认管家条目只能设置 `id`、`name`、`description` 和 `idle_timeout_seconds: 0`，省略该字段的场景条目取 1800。
- **控制台（#719）：**管家设置表单新增“Idle timeout (seconds)”字段（新建默认 1800），拒绝 0 与 60 至 86400 之外的值；默认管家不可编辑该项。
- **面向模型的变化：**无。提示词、工具描述和工具 schema 均未变化；`/api/v1` 的管家配置 schema 新增上述字段。
- **文档：**除本次发布说明和 CHANGELOG 条目外无变化。

### 可选能力启用与使用

#### Manager idle timeout

**启用：**场景管家默认开启，1800 秒。可在设置 → 管家（Idle timeout）中按管家修改，或通过管家 API 或配置文件的 `idle_timeout_seconds`。

**权限边界：**巡检只关闭管家自己的常驻进程，且从不关闭默认管家。不新增工具和权限，也不删除会话。

# Looper v2.14.114

This is the patch release v2.14.114, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.113: a test-only fix that makes the drain serve test robust on loaded CI runners ([#1184](https://github.com/foolzzz/looper/pull/1184)).

## Release Decision

**Who should upgrade:** Nobody needs to for behavior. The change touches tests only; the shipped wheel has no production difference from v2.14.113. Contributors and maintainers benefit from fewer spurious CI failures.

**What this release solves:** [#1184](https://github.com/foolzzz/looper/pull/1184). `tests/test_drain_serve_db.py` waited 45 seconds for both steps to be dispatched and timed out on loaded CI runners, failing unrelated pull requests. The wait is now longer, the held Worker outlasts it, and a timeout reports the dispatched step ids and the serve log tail.

**Breaking changes:** No. No production code, schema or API change.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.14.114
```

**Contributors:** Maintainer @foolzzz authored [#1184](https://github.com/foolzzz/looper/pull/1184); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.113 upgrades directly. There is no database change.

## Behavior changes

- **Production behavior:** None. The pull request changes two test files only (`tests/test_drain_serve_db.py`, `tests/test_kept_detach_serve_db.py`); no file under `looper/` or `web/` changed.
- **Drain serve test** (`tests/test_drain_serve_db.py`). The wait for both steps to be `dispatched` in the restart case is now 120 seconds (it was the helper's default). The fake CLI's held Worker in the restart variant now waits up to 180 seconds for its release file (the deadline variant keeps 90), so it is still held through dispatch and the next task's planning turn. When the wait times out, the failure message lists the dispatched step ids and the last 40 lines of the serve log.
- **Kept-detach serve test** (`tests/test_kept_detach_serve_db.py`). Its streaming fake CLI is derived from the shared one by text replacement; the replaced anchor no longer includes the hold duration (`limit = time.monotonic()` instead of `limit = time.monotonic() + 90`), so it keeps matching when the shared CLI's duration differs by variant.
- **Unchanged:** all runtime behavior, the API, the CLI, the schema, channels and the dashboard.
- **Model-visible changes:** None. No prompt, tool description or tool output changes.

### 行为变化与入口

- **生产行为：**无。该 PR 只改两个测试文件（`tests/test_drain_serve_db.py`、`tests/test_kept_detach_serve_db.py`）；`looper/` 和 `web/` 下没有文件变化。
- **Drain serve 测试**（`tests/test_drain_serve_db.py`）。restart 场景下等待两个步骤都为 `dispatched` 的时限现为 120 秒（原为辅助函数默认值）。restart 变体中被挂住的假 CLI Worker 现最多等待 180 秒的释放文件（deadline 变体仍为 90 秒），因此仍会挂住到派发和下一个任务的规划轮次之后。等待超时时，失败信息列出已派发的步骤 id 和 serve 日志的最后 40 行。
- **Kept-detach serve 测试**（`tests/test_kept_detach_serve_db.py`）。其流式假 CLI 由共享 CLI 通过文本替换得到；被替换的锚点不再包含挂起时长（用 `limit = time.monotonic()` 代替 `limit = time.monotonic() + 90`），因此共享 CLI 的时长随变体不同时仍能匹配。
- **不变：**所有运行时行为、API、CLI、数据库结构、渠道和仪表盘。
- **面向模型的变化：**无。提示词、工具描述和工具输出均未改变。

# Looper v2.13.60

## Release Decision

**Who should upgrade:** Operators who run the dashboard or `looper service`, and anyone who scripts the removed catalog and installation HTTP routes. Nobody else needs to act.

**What this release solves:** [#466](https://github.com/foolzzz/looper/pull/466) moves catalog items and installations to the versioned API (`/api/v1/catalog_items/*` and `/api/v1/installs/*`) and adds typed schemas for the full catalog views and for the compact `looper_catalog` Tool results. The dashboard's catalog list, item detail, item edit and delete, install, install update, uninstall and project installs now call them.

**Breaking changes:** Yes. Eight legacy HTTP methods are removed and no longer match a route: `GET /api/catalog`, `GET`, `PUT` and `DELETE /api/catalog/{item id}`, `POST /api/installs`, `PUT` and `DELETE /api/installs/{install id}`, and `GET /api/projects/{project id}/installs`. A script that calls them must switch to the v1 routes below. Upload, import, git-source, MCP-create and project-skill routes are unchanged. No stored data or configuration changed.

**How to verify:** Check the installed version, then list the catalog with the operator token.

**Contributors:** Maintainer @foolzzz authored [#466](https://github.com/foolzzz/looper/pull/466); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.60
```

## Behavior changes

- **New v1 operations (`looper/agents/v1_domains/catalog.py`, `looper/agents/v1_domains/__init__.py`):** the `catalog` domain joins `status` in `MODULES`. All operations are `POST` with a JSON body that rejects unknown keys:
  - `catalog_items.list` (`{}`), `catalog_items.get` (`item_id`), `installs.project` (`project_id`): reads.
  - `catalog_items.update` (`item_id`, `fields`): a write that is operator-only.
  - `catalog_items.delete` (`item_id`): `high` risk.
  - `installs.create` (`item_id`, `scope`, optional `project_id`, `roles`, `enabled`), `installs.update` (`install_id`, optional `roles`, `enabled`), `installs.delete` (`install_id`): writes.
- **Typed results:** the full catalog, item detail, install, project-install and import DTOs are declared as schemas, so files, ownership and inherited installs stay in the answer. The existing `catalog.list`, `catalog.install`, `catalog.update` and `catalog.uninstall` Tool operations keep their requests and paths; their compact answers are now typed, and `catalog.list` uses a `oneOf` to tell the global list from a project's.
- **Item edits are operator-only (`catalog_items.update`):** a client token is refused before anything runs. A skill or MCP patch (`name`, `description`, `content`, or the MCP transport, command, URL, args, env and headers) may carry secrets, so neither its arguments nor its failures enter the audit trail; a failure answers only `invalid credential request`, keeping the HTTP error class (not found, conflict or invalid). A patch needs at least one field.
- **Deleting an item is `high` (`catalog_items.delete`):** a client token gets the two-step confirmation, whose text names the item and the count of installations that go with it; with the operator credential it runs in one request (see v2.13.59), and the dashboard keeps its own dialog. Existence and ownership are re-read at the delete itself, so a confirmation is not a reservation. A project's own skill is refused here; it is deleted from its project's Skills tab. Uninstalling (`installs.delete`) stays an ordinary write, as in the `looper_catalog` Tool.
- **Dashboard (`web/src/lib/api.ts`):** `fetchCatalog`, `fetchCatalogItem`, `updateMcpServer`, `updateCatalogItem`, `deleteCatalogItem`, `installItem`, `updateInstall`, `uninstall` and `fetchProjectInstalls` call the v1 routes through `callV1`. A pending-confirmation (202) answer is never confirmed automatically; it surfaces as an error.
- **Legacy routes (`looper/agents/http_server.py`):** the eight methods above and their route patterns are deleted. The remaining catalog routes (import, upload, git, MCP create and import, project skills) stay.
- **Docs and tests:** the client-skill RFC and the long-horizon context plan record the migration. New `tests/test_api_v1_catalog_installs.py` and `tests/test_api_v1_catalog_installs_db.py`; other catalog, library, MCP, config-transfer, role and project-skill tests were moved to the v1 calls. The RFC records 249 targeted tests and notes that session-ended/abort was not tested separately. The pull request reports added lines: tests 421, production 187 (fixtures excluded).
- **Model-visible changes:** None for Manager, Worker, Planner or Reviewer prompts, and no new Manager Tool; the `looper_catalog` Tool keeps its arguments and gets typed result schemas. API clients (and an agent skill built on the OpenAPI document) see the new operations and their schemas.

## Upgrade and rollback

Re-run `install.sh` once v2.13.60 is published. No data migration. Replace any caller of the eight removed routes before upgrading. Rolling back to v2.13.59 brings those routes back and removes the v1 catalog operations; a dashboard and a service from the same version always agree, so do not mix versions.

### 行为变化与入口

- 新增 v1 操作（`v1_domains/catalog.py`、`v1_domains/__init__.py`）：`catalog` 领域加入 `MODULES`（在 `status` 之后）。均为带 JSON 请求体的 `POST`，拒绝未知键：
  - `catalog_items.list`（`{}`）、`catalog_items.get`（`item_id`）、`installs.project`（`project_id`）：读操作。
  - `catalog_items.update`（`item_id`、`fields`）：仅操作者可用的写操作。
  - `catalog_items.delete`（`item_id`）：`high` 风险。
  - `installs.create`（`item_id`、`scope`，可选 `project_id`、`roles`、`enabled`）、`installs.update`（`install_id`，可选 `roles`、`enabled`）、`installs.delete`（`install_id`）：写操作。
- 类型化结果：完整目录、条目详情、安装、项目安装和导入 DTO 均有 schema，文件、归属和继承信息保留在回答里。既有 `catalog.list/install/update/uninstall` 工具操作的请求和路径不变，compact 回答改为类型化，`catalog.list` 用 `oneOf` 区分全局列表与项目列表。
- 条目编辑只认操作者（`catalog_items.update`）：客户端令牌在执行前即被拒绝。skill 或 MCP 补丁（`name`、`description`、`content`，或 MCP 的 transport、command、URL、args、env、headers）可能含秘密，因此参数和失败都不进审计；失败只回答 `invalid credential request`，并保留 HTTP 错误类别（不存在、冲突、无效）。补丁至少要有一个字段。
- 删除条目为 `high`（`catalog_items.delete`）：客户端令牌需两步确认，确认文案写明条目及随之删除的安装数；操作者凭据单次执行（见 v2.13.59），Dashboard 保留自己的弹窗。删除时会重新读取存在性和归属，确认不是预留。项目自带的 skill 在此被拒绝，须在其项目的 Skills 标签页删除。卸载（`installs.delete`）仍是普通写操作，与 `looper_catalog` 工具一致。
- Dashboard（`web/src/lib/api.ts`）：`fetchCatalog`、`fetchCatalogItem`、`updateMcpServer`、`updateCatalogItem`、`deleteCatalogItem`、`installItem`、`updateInstall`、`uninstall`、`fetchProjectInstalls` 经 `callV1` 调用 v1 路由。待确认（202）的回答绝不自动确认，而是作为错误抛出。
- 旧路由（`http_server.py`）：上述八个方法及其路由正则已删除；其余目录路由（导入、上传、git、MCP 创建与导入、项目 skill）保留。
- 文档与测试：更新客户端 skill RFC 和长程上下文计划。新增 `tests/test_api_v1_catalog_installs.py` 和 `tests/test_api_v1_catalog_installs_db.py`；目录、library、MCP、配置传输、角色和项目 skill 的其他测试改用 v1 调用。RFC 记录 249 项定向测试，并注明 session-ended/abort 未单独实测。PR 报告新增测试 421 行、生产代码 187 行（不含 fixture）。
- 面向模型的变化：Manager、Worker、Planner、Reviewer 的 prompt 无变化，也不新增 Manager Tool；`looper_catalog` 工具参数不变，结果 schema 带类型。API 客户端（以及基于 OpenAPI 文档的 agent skill）会看到新增的操作及其 schema。

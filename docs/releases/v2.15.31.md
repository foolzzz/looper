# Looper v2.15.31

This release documents the changes merged on main between the v2.15.30 tag and `fc0aaac4b`. That tag is on its release commit (`1fea7cc46`; the freeze was `d2bbc5b35`), so this range contains the pulls that merged after the v2.15.30 freeze and are not on that tag. [#1653](https://github.com/foolzzz/looper/pull/1653), [#1654](https://github.com/foolzzz/looper/pull/1654), [#1658](https://github.com/foolzzz/looper/pull/1658), [#1659](https://github.com/foolzzz/looper/pull/1659) and [#1660](https://github.com/foolzzz/looper/pull/1660) ship here, with full notes. The v2.15.30 release pull request ([#1664](https://github.com/foolzzz/looper/pull/1664)) is not a change in this release. Pulls merged into main after this freeze are not in these notes. This release is frozen at `fc0aaac4b`.

The headline capabilities are the Manager's resident profile from one knowledge-vault note ([#1658](https://github.com/foolzzz/looper/pull/1658)), off until `manager.profile.enabled` is the string `true`, and an opt-in Claude Code SessionStart hook that prints the same text ([#1659](https://github.com/foolzzz/looper/pull/1659)), not installed by default. DSH moves to an exact `@deepseek-ai/dsh` 0.2.2-rc.5 gate ([#1654](https://github.com/foolzzz/looper/pull/1654)). [#1660](https://github.com/foolzzz/looper/pull/1660) is a docs-only RFC. [#1653](https://github.com/foolzzz/looper/pull/1653) is tests only.

No new feature setting turns itself on. An upgrade does not write `manager.profile.enabled` and does not install the SessionStart hook. With the profile switch off, every Manager still reads that key at startup and when preparing each turn and, on a read failure, logs `could not read manager.profile.enabled; omitting profile` and leaves injection off. It does not compile a profile on a Manager turn, does not seed a row, does not start a new background loop, and does not add an export key. `looper/db/` is unchanged in this range: an upgrade from a database that has finished v2.15.30 applies no new migration and no new online step. `web/` changed, so the dashboard bundle is rebuilt by the release workflow as usual. An installation that runs DSH roles fails the version check until `@deepseek-ai/dsh` is exactly 0.2.2-rc.5. An installation that does not run DSH has no new failure from that gate.

## Release Decision

**Who should upgrade:** Anyone who will inject a compiled operator profile into the default Manager's own turns, or install the Claude Code SessionStart hook, and anyone whose roles run on DSH. An installation that leaves `manager.profile.enabled` unset and does not install the hook still reads that key at each Manager startup and when preparing each turn and injects nothing. It applies no new migration. An installation with no DSH role is unchanged by the SDK gate. An installation that runs DSH must install `@deepseek-ai/dsh@0.2.2-rc.5` or those roles fail the version check. web/ changed, so the dashboard bundle is rebuilt by the release workflow as usual.

**What this release solves:** The operator can point `knowledge_vault.profile_source` at one Markdown note in the knowledge vault and, only after storing `manager.profile.enabled` as the string `true`, have the default Manager include the compiled text in the operator's own resident turns. The same text can be printed into the operator's own Claude Code at SessionStart, after an explicit install that edits user settings only with confirmation, backing up an existing file. DSH roles require the 0.2.2-rc.5 SDK. Intent rules after recognition are a design only. The idle-close flake fix is tests only.

**Breaking changes:** Yes. The existing profile-source API now accepts a relative Markdown file instead of an absolute directory; null restores the default file instead of clearing the source. Reads ignore the old `manager.profile.source` setting and use `knowledge_vault.profile_source` (default `关于我.md`) even while resident injection is off. Knowledge-vault API reads and writes now require the operator token; API client tokens receive 403, and non-operator Manager turns cannot change vault settings. An upgrade from v2.15.30 applies no migration and writes no new feature setting. DSH roles that ran on `@deepseek-ai/dsh` 0.2.1-rc.2 fail the version check until the package is `@deepseek-ai/dsh@0.2.2-rc.5`; rollback installs the previous Looper release together with `@deepseek-ai/dsh@0.2.1-rc.2`. Other runtimes are unchanged. The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.15.31
```

**Contributors:** Maintainer @foolzzz authored the pull requests named in this body; no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.15.30 upgrades directly. Restart the service after upgrading, as for every release. `web/` changed, so the release workflow rebuilds the dashboard bundle from `web/` into the wheel, as usual. This pull request does not commit that bundle.

On an upgrade from a database that has finished v2.15.30, startup applies no new migration and no new online step. `git diff v2.15.30..fc0aaac4b -- looper/db/` is empty. `schema.sql` and `looper/db/connection.py` are unchanged. `pending()` therefore has nothing new to report for this range, and no online marker is deleted or recorded by a migration this release adds. A step whose online marker is already recorded stays skipped, including a marker recorded by another migration. A database that has not yet finished an earlier release's online step still runs that older step. Because this range adds no pending migration, this release does not by itself cause the pre-migration `pg_dump` backup. No feature-setting row is inserted. Before a downgrade, restore the default profile source to remove the new vault JSON field and uninstall the SessionStart hook while its commands are still available; see the rollback fields below.

What is visible while `manager.profile.enabled` is absent or any value other than the string `true`, and while the SessionStart hook is not installed: every Manager reads the key at startup and when preparing each turn and does not compile or inject a profile; `profile.get` is not called by that turn; `profile_blocks` is not written by a Manager or CLI read; Claude Code user settings are not edited; no new background loop starts; configuration export still leaves `knowledge_vault` out and does not gain `manager.profile.enabled`. `looper profile show` can still print the compiled body when the note is valid. It does not turn injection on. The default `[runtimes] dsh = "runner"` also runs a startup preflight for Node and the DSH package even when no role uses DSH; a failed preflight registers an unavailable adapter without failing unrelated roles. A DSH probe or a DSH runner start still requires `@deepseek-ai/dsh` 0.2.2-rc.5 even while those switches stay off. Roles that are not on DSH do not fail because that adapter is unavailable. Selecting `"cli"` bypasses the runner preflight, not the exact DSH version gate.

Operators who run DSH install the SDK before or together with this release:

```bash
npm install -g @deepseek-ai/dsh@0.2.2-rc.5
```

The runner requires Node 22.19 or newer, excluding 23.0–23.5 (use 23.6+ on Node 23), and `@deepseek-ai/cordis` 4.1.x. The CLI probe checks the exact DSH version and `--help`; it does not perform the runner's Node or Cordis metadata checks. Any other `@deepseek-ai/dsh` version, older or newer, fails the check. There is no fallback engine. `[runtimes] dsh` still defaults to `"runner"` and is read once at startup. `"cli"` remains the opt-out: set it in the ops file and restart. To roll back, install the previous Looper release and `@deepseek-ai/dsh@0.2.1-rc.2` together.

## Behavior changes

### On by default, including with profile injection off

- **Profile-source compatibility changes (#1658).** `profile.get` and `profile_source.get` now select one `knowledge_vault.profile_source` note (default `关于我.md`), ignoring the previously saved `manager.profile.source` directory. `profile_source.update` requires a relative Markdown file; null restores the default instead of clearing the source and compiled block. Operators using the old directory source must select a new file explicitly if the default is unsuitable. No setting is migrated automatically. Vault saves validate an explicit profile source, or the default note if it exists or is a symlink; invalid files can now reject a save even with injection off. Loading an existing vault does not validate that profile file, so an unavailable profile does not disable its other tools.
- **Vault authority is tightened (#1658).** `knowledge_vault.get` and `knowledge_vault.update` now require operator identity and reject API client tokens with 403. Manager `looper_settings` writes to the vault, including their confirmation preview, reject non-operator turns with `knowledge vault settings are operator-only`. These restrictions apply with the profile switch off and hook absent.
- **DSH fixes apply on their existing paths (#1654).** Provider retries re-enter `llm.stream` with copied options after the first attempt, preserving the existing authorization and retry limits. Resume and fork reuse an available saved `looper-*` route; if the loaded provider, model or reasoning effort differs from the current request, the runner selects the requested values (effort defaults to `high`) instead of retaining the saved selection. The consult-defaults snapshot filters `exit_plan_mode`. No new switch guards these fixes or the SDK gate.

### Resident profile, off ([#1658](https://github.com/foolzzz/looper/pull/1658))

No real-model eval of the injected section was run.

- **`manager.profile.enabled` defaults off.** Only the stored string `true` is on. `enabled()` is `get_settings(["manager.profile.enabled"]).get("manager.profile.enabled") == "true"`. An absent row means off. `update_enabled(None)` deletes the row. `True` stores `"true"`. `False` stores `"false"`. `settings_view` returns `{"enabled": true}` or `{"enabled": false}`. No migration seeds the row. A read failure in `_load_db_config` sets `_profile_enabled` to false and logs `could not read manager.profile.enabled; omitting profile`. A read failure of `manager.stable_context` still keeps the last value. The profile switch fails closed.
- **The source is `knowledge_vault.profile_source`.** It is a path relative to the vault root. The default is `关于我.md`. The key is stored inside the `knowledge_vault` JSON object and is omitted from that JSON when it equals the default. A replacement `knowledge_vault.update` that leaves `profile_source` out therefore restores `关于我.md`. `profile_source.update` with `source: null` also restores `关于我.md` and does not delete the vault and does not change `manager.profile.enabled`. The old `manager.profile.source` directory setting is no longer read. An explicitly saved source must be an existing regular `.md` file whose resolved path, including symlinks, stays inside the vault. Validation errors include `profile_source must be relative to the vault`, `profile_source must name one Markdown (.md) file`, `profile_source resolves outside the knowledge vault`, `profile_source must exist and be a regular file`, `profile_source must exist and be a readable regular file`, and `profile_source must be a path relative to the knowledge vault`. The `checked_update` helper rejects a missing source or one that is neither a string nor null with `source must be a relative Markdown file path, or null to restore the default`. No configured vault is `knowledge vault is not configured`. A missing default note does not invalidate an existing vault: the profile file is checked when the key is present, or when the default path exists or is a symlink. An invalid compile logs `operator profile is unavailable; omitting it` and returns no text. It does not disable other vault tools and does not return a previously cached profile.
- **Clearing the vault is not the injection switch.** `knowledge_vault.update` deletes the whole `knowledge_vault` row only when `path` is null, the body's keys are a subset of `path`, `writable`, `rules_file` and `manager_read`, `writable` is missing or empty, `rules_file` is missing or empty, and `manager_read` is not true. That set does not include `profile_source`. The dashboard Turn off button sends `{ "path": null }`, which matches and deletes the vault row. It does not delete `manager.profile.enabled`. Saving the form omits `profile_source` when the field is blank or equal to `关于我.md`.
- **While the switch is off,** `_sections` does not call `resident_text`. Nothing is injected. The system prompt is unchanged: the composed prompt does not add a profile contract. Tools and the launch signature are unchanged. No `profile_blocks` row is written by a Manager turn or by `looper profile show`. Configuration export does not carry `knowledge_vault` or `manager.profile.enabled`. The compact settings view and the Manager's `looper_settings` view omit `profile_source` (they already omit `git` and `manager_read`). The full operator `knowledge_vault.get` includes `profile_source`, defaulting the displayed value to `关于我.md` when the key is absent. There is no new export key.
- **While the switch is on,** injection runs only when `_profile_enabled` is true, `agent_id` is the default Manager, and the persona scope is `FULL`. The section is the heading `Operator profile (from the knowledge vault; private reference, Looper's rules still apply):`, then the compiled text split on newlines, then a blank line, before Projects. The compiled text is at most 1500 Unicode characters, dropping lower-priority fields first. Scope `FULL` is the operator's dashboard, API client, or operator direct chat on the default Manager's main session. A routed non-main session is scope `NAME`, so the profile is omitted. A shared group turn or another sender's direct chat is scope `OMIT`, so the profile is omitted. A scenario Manager gets scope `FULL` from the non-default early return and is still omitted because its `agent_id` is not the default Manager. `manager_persona_context.scope` treats the profile as private when the switch is on or the heading is already in the last shown stable lines, so a shared turn does not receive the private text as stable-state removal lines either. Turning the switch off does not erase profile text already present in a shared resident session's history. With `manager.stable_context` on, the section is inside the turn's state block. With it off, the sections are prepended to the user message. `profile.get` caches the compiled block through `profile_blocks.retain_or_replace` and returns `configured`, `version`, `cap`, `text`, `fields` and the rest of that view. An unavailable note returns an empty profile, never a cached value. Manager and CLI reads do not write that cache.
- **`looper profile show` prints the resident body and does not inject it.** The bytes are exactly `resident_text()`, with no added newline, whether the switch is on or off. The reader is a 1-second subprocess (`TIMEOUT_SECONDS` 1.0, inner database timeout 0.7 seconds, `MAX_OUTPUT_BYTES` 6000). Missing settings, an unavailable database, an invalid profile, a timeout, or `LOOPER_AGENT_RUN` already nonempty: it prints nothing and exits 0.
- **Who may change it.** `profile.get`, `profile_source.get`, `profile_source.update`, `profile_settings.get` and `profile_settings.update` are operator-only and level inside. `profile_source.update` and `profile_settings.update` are risk high with `confirms` true. They are not in the cost-consent list (`cost_guard.update` with `mode` `enforce`, `cost_holds.decide` with `new_limit_usd`, a client principal, `manager_chat_bindings.put`, `managers.update`, `memory.settings_put`). The operator's own call applies on that request and returns 200. A non-operator gets 403 `operator identity is required` before the call. No caller gets 202 for these two updates. The impact text for the switch is `Set manager.profile.enabled to true?` or `Set manager.profile.enabled to false?` plus `This controls injection of the compiled profile into the Manager's private resident content.` Null is described as false, because the text formats `enabled is True`, and the call still deletes the row. The source impact is `Set knowledge_vault.profile_source to {source}? This changes the source file without changing the resident injection switch.` The dashboard switch asks `window.confirm` before the POST: `开启管家画像？这会在你自己的会话中加入画像内容。` or `关闭管家画像？后续回合将不再加入画像。` The label is `管家常驻画像`. The help is `默认关闭。开启后，管家在你自己的会话中使用编译后的画像。` The file field is `画像文件`, placeholder `关于我.md`, help `相对知识库根目录的一份 Markdown 笔记，例如 notes/profile.md。留空使用 关于我.md。`

### Claude Code profile hook, not installed ([#1659](https://github.com/foolzzz/looper/pull/1659))

Nothing writes Claude Code settings at `looper serve` startup. The hook is not installed by default. Real Claude CLI verification of hook execution and of the injected token count was not run.

- **Commands.** `looper claude-code profile`, `looper claude-code profile --hook`, `looper claude-code install hook`, `looper claude-code uninstall hook`, and `looper claude-code status`. An unknown part prints `unknown part: expected hook` and returns 2. The settings path is `$CLAUDE_CONFIG_DIR/settings.json` when `CLAUDE_CONFIG_DIR` is nonempty after trimming whitespace, otherwise `~/.claude/settings.json`. A symlink is preserved: the write goes to the resolved target and the preview says `a link to {target}`. Paths whose resolved targets are under `/Library/Application Support/ClaudeCode` or `/etc/claude-code` raise `ManagedSettingsError`, exit 4, and print `{path} is organization-managed Claude Code settings; Looper never edits them`. Invalid JSON, a non-object, or a bad `hooks.SessionStart` shape is a `SettingsError`, exit 2, and nothing is written.
- **The handler.** Type `command`. The command is the current Looper executable plus `claude-code profile --hook --runtime-root {runtime root}`, plus `--config {absolute path}` when a config was given, then ` 2>/dev/null || true`. Timeout is 5 seconds. There is no matcher, no token and no async flag. Install appends one new SessionStart group `{"hooks": [desired]}` after removing handlers whose argv contains the exact sequence `claude-code`, `profile`, `--hook`. Unrelated settings stay.
- **Install.** Prints the path, `Adds to hooks.SessionStart:` or `Replaces the Looper hook that runs: …`, and a unified diff. `--dry-run` writes nothing and returns 0. Without `--yes`, the prompt is `Write these changes to {path}? [y/N]`. A non-tty stdin without `--yes` prints `confirmation needed: run it in a terminal, or pass --yes after reviewing --dry-run` and returns 2. Declining prints `nothing written` and returns 1. If the file changes while waiting, the text is `the settings file changed while waiting; nothing written; run it again` and the exit is 1. An already identical handler prints `the SessionStart hook is already installed`, writes nothing, and returns 0. On a real write to an existing file, the original bytes are copied to `{name}.looper-backup-{UTC stamp}` (`%Y%m%dT%H%M%SZ`), created exclusively, with `-N` on a collision, mode preserved, and fsync. The replacement is atomic in the same directory. A new file is mode `0600`; an existing file keeps its mode. Readback failure prints `settings readback failed: …; keep the backup and inspect the file` or `settings readback failed; keep the backup and inspect the file` and returns 1. Success prints `installed. Open a new Claude Code session (or /clear) to load it. Undo: looper claude-code uninstall hook`. If the file was not already 2-space JSON, it also prints `note: the file is rewritten in Claude Code's own 2-space JSON format`.
- **Uninstall.** The preview is `Removes from hooks.SessionStart:` plus the removed handlers only. With no Looper handler it prints `the SessionStart hook is not installed`, writes nothing, and returns 0. The same confirmation, backup and readback apply. Success prints `removed.`
- **Status writes nothing.** It prints the settings path, then `profile hook: not installed` and `install: looper claude-code install hook`, or `profile hook: installed ({command})`, or `profile hook: installed, but its looper is missing: {executable}`. It then reads the profile locally: `Looper: profile readable locally` and `profile: {N} characters` (the length of the capped text, not a cache version), or `Looper: not answering ({reason})`. Exit 0 only when there is exactly one healthy executable handler and the profile read succeeds. Otherwise exit 1.
- **Hook mode.** When the profile read succeeds, stdout is JSON `{"hookSpecificOutput":{"hookEventName":"SessionStart","additionalContext": text}}`. The text is capped at 3000 characters. Past the cap it clips at the last newline after the halfway point and ends with `…`. An empty profile, a refusal, an error or any exception writes no stdout and no stderr and exits 0. There is no second compiler, no HTTP call and no cache write. A stopped HTTP server alone does not prevent the local database read. Without `--hook`, `looper claude-code profile` prints the text and returns 0, or prints the reason on stderr and returns 1 for `profile unavailable or empty (check knowledge_vault.profile_source and database settings)` or 4 for `refused inside a Looper agent run`.
- **Looper-started processes never trigger it.** `Launch.environment()` sets `LOOPER_AGENT_RUN` to the role name, or `agent` when there is no role. With a nonempty `LOOPER_AGENT_RUN`, `fetch_profile` returns refused before reading. `looper profile show` then prints nothing and exits 0. `install`, `uninstall` and the edit path print `refused inside a Looper agent run` and exit 4 before any write. Ordinary Claude Code launches pass `--setting-sources project`. Sealed launches and launches with explicit hooks pass `--setting-sources ""`. User settings, which is where this hook lives, are not loaded. That covers the Manager, Planner, Worker, Reviewer, processor and consult.

## Optional Capability Activation & Use

### Resident profile

**Activation:** Off until the operator stores `manager.profile.enabled` as the string `true`. An absent row means off. Set it with `POST /api/v1/profile_settings/update` and `{"enabled": true}` as the operator. `false` stores `false`. `null` deletes the row. The source file is `knowledge_vault.profile_source`, default `关于我.md`, set with `POST /api/v1/profile_source/update` or `POST /api/v1/knowledge_vault/update`. Both profile updates are operator-only, risk high, with confirms true. The operator's own call applies on that request and returns 200. A non-operator gets 403 `operator identity is required`. The dashboard switch asks `开启管家画像？这会在你自己的会话中加入画像内容。` before the POST. An upgrade does not write the key.

**Validation:** `POST /api/v1/profile_settings/get` reports `{"enabled": false}` while the row is absent. While the stored value is not the string `true`, a Manager turn does not compile or inject a profile. While it is the string `true`, the default Manager's own dashboard turn and the operator's own main-session direct chat include the heading `Operator profile (from the knowledge vault; private reference, Looper's rules still apply):` and the compiled note, at most 1500 Unicode characters, before Projects. `looper profile show` prints that body even while injection is off. `POST /api/v1/profile/get` returns the compiled view and caches it. An invalid note returns an empty profile.

**Disable / rollback:** Before downgrading to v2.15.30, call `POST /api/v1/profile_source/update` with `{"source": null}` on this release to remove any non-default `profile_source` key from the stored vault JSON; the older release rejects that key and otherwise loses access to the whole vault. The old `manager.profile.source` row is preserved by this upgrade and is read again on rollback. `POST /api/v1/profile_settings/update` with `{"enabled": false}` stores `false`. `{"enabled": null}` deletes the row. Later turns do not inject the section. Text already in a shared resident session's history is not erased. `POST /api/v1/profile_source/update` with `{"source": null}` restores `关于我.md` and leaves the injection switch as it is. Dashboard Turn off sends `{"path": null}` and deletes the `knowledge_vault` row. It does not delete `manager.profile.enabled`.

**Authority boundary:** Operator only. `profile.get`, `profile_source.get`, `profile_source.update`, `profile_settings.get`, `profile_settings.update` and `knowledge_vault.get` / `knowledge_vault.update` are operator-only and level inside. Group turns, other senders, routed non-main sessions and scenario Managers do not receive the profile. Configuration export leaves the vault out and does not carry `manager.profile.enabled`. An API client token gets 403.

### Claude Code profile hook

**Activation:** Not installed by default. `looper serve` does not edit Claude Code settings. Install with `looper claude-code install hook --runtime-root <runtime-root>`. Review the printed path and diff. Pass `--dry-run` to write nothing. Pass `--yes` only after that review, or answer `y` to `Write these changes to {path}? [y/N]`. The command appended under `hooks.SessionStart` is this Looper plus `claude-code profile --hook --runtime-root …`, timeout 5, with stderr discarded. If the settings file exists, a backup of its original bytes is written beside it before the atomic replace; a first install into a new file has no backup.

**Validation:** `looper claude-code status` prints `profile hook: not installed` until that write succeeds, and writes nothing itself. After install, a new Claude Code session started by the operator (or `/clear`) can receive SessionStart `additionalContext` of the same compiled text, capped at 3000 characters. `looper claude-code profile` prints the text without installing anything. An empty or unreadable note makes the hook print nothing and exit 0.

**Disable / rollback:** Uninstall before downgrading to v2.15.30, which does not have these `claude-code` commands. `looper claude-code uninstall hook` previews `Removes from hooks.SessionStart:`, asks the same confirmation, backs up the file, and removes only Looper's SessionStart handlers. Success prints `removed.` Unrelated settings stay. If no Looper handler is present it prints `the SessionStart hook is not installed` and writes nothing. The backup name is `{settings file name}.looper-backup-{UTC stamp}`.

**Authority boundary:** The edit targets the operator's own Claude Code user settings (`$CLAUDE_CONFIG_DIR/settings.json`, or `~/.claude/settings.json`). Organization-managed files whose resolved targets are under `/Library/Application Support/ClaudeCode` or `/etc/claude-code` are refused, exit 4, with `Looper never edits them`. A process with a nonempty `LOOPER_AGENT_RUN` cannot install or uninstall (exit 4, `refused inside a Looper agent run`) and a hook invocation prints nothing and exits 0. Looper's own Manager, Planner, Worker, Reviewer, processor and consult launches do not load user settings (`--setting-sources project`, or `--setting-sources ""` when sealed or when hooks are explicit), so they never trigger this hook.

**Docs:** https://github.com/foolzzz/looper/blob/v2.15.31/docs/architecture/agent-system.md#the-operators-own-claude-code-profile-at-session-start

**DSH SDK（[#1654](https://github.com/foolzzz/looper/pull/1654)）。** 没有新开关，没有迁移。CLI 探测的 `SUPPORTED_VERSION` 和 runner 的 `_DSH_VERSION` 都是 `0.2.2-rc.5`。对不上时能力为空，探测原文是 `Unsupported DSH version; expected 0.2.2-rc.5`。runner 原文是 `node 22.19+ and @deepseek-ai/dsh 0.2.2-rc.5 are required (found …)`，启动预检另拒绝 Node 23.0–23.5。`@deepseek-ai/dsh` 和 runner 加载的每个 `@deepseek-ai/dsh-*` 包必须正好是这个版本。`@deepseek-ai/cordis` 必须是 4.1.x，否则 `initialize` 以 `-32009` 失败，原文是 `{name} version {ver} is unsupported; require 4.1.x`（其他包则是 `require 0.2.2-rc.5`）。Node 低于 22.19 的原文是 `Node version … is unsupported; require 22.19.0+`。仪表盘的安装提示是 `npm install -g @deepseek-ai/dsh@0.2.2-rc.5`。runner 覆盖层和 CLI 启动补丁都不再设置 `tools.mode` 为 `native`。`tool-executor-native` 不在 runner 的禁用名单里，所以这个原生执行插件保持启用。`tool-executor-ptc` 没有被列成启用，覆盖层也不添加它。runner 现在禁用 `subagent`、`tool-subagent`、`agent-team`、`tool-agent-team`、`tool-workflow`、`web`、`tool-web`、`skill`、`tool-skill`、`ptc-runtime`、`workflow-ptc` 和 `headless-startup`。`agent-team` 和 `tool-agent-team` 是本版新增禁用项。`tool-subagent-list-agents` 不再出现在这份名单里。SDK 的技能、子代理、工作流和 web 工具在 runner 会话里仍禁用；这不构成网络沙箱。因为 `headless-startup` 被禁用，runner 的 sandbox-policy 使用 `{inject: []}`，否则沙箱策略和文件工具会一直等。CLI 是另一条路径：它的 bootstrap runner 入口仍把 `inject` 设为 `["headlessStartup"]`。CLI 补丁替换整段 0.2.2 配置，禁用名单更短，同样不禁用 `tool-executor-native`。咨询默认值快照会去掉工具 `exit_plan_mode`。默认 `[runtimes] dsh = "runner"` 时，服务启动就预检 Node 和 DSH 包，即使没有 DSH 角色；失败只注册不可用适配器，不影响无关角色。runner 初始化时检查完整包列表，CLI 探测时执行精确版本门禁。`[runtimes] dsh` 仍默认 `"runner"`，`"cli"` 仍是退路，启动读一次。其他运行时不变。没有备用引擎。回退要同时装回上一版 Looper 和 `@deepseek-ai/dsh@0.2.1-rc.2`。

### 可选能力启用与使用

#### Resident profile

**启用：** 操作者把 `manager.profile.enabled` 存成字符串 `true` 之前是关。没有这一行就是关。操作者用 `POST /api/v1/profile_settings/update`，正文 `{"enabled": true}`。`false` 存 `false`。`null` 删行。来源文件是 `knowledge_vault.profile_source`，默认 `关于我.md`，用 `POST /api/v1/profile_source/update` 或 `POST /api/v1/knowledge_vault/update` 设置。两次画像更新都只给操作者，风险是 high，confirms 为 true。操作者自己的这一次请求直接生效并返回 200。非操作者得到 403，正文是 `operator identity is required`。仪表盘开关在 POST 之前询问 `开启管家画像？这会在你自己的会话中加入画像内容。` 升级不写这个键。

**验证：** 没有这一行时，`POST /api/v1/profile_settings/get` 返回 `{"enabled": false}`。存的值不是字符串 `true` 时，管家回合不编译、不注入。存成字符串 `true` 之后，默认管家自己的控制台回合和操作者本人的 main 私聊会带上标题 `Operator profile (from the knowledge vault; private reference, Looper's rules still apply):` 和编译后的笔记，最多 1500 个 Unicode 字符，放在 Projects 之前。`looper profile show` 在注入关闭时也会打印这段正文。`POST /api/v1/profile/get` 返回编译视图并写入缓存。笔记无效时返回空画像。

**停用 / 回退：** 降级到 v2.15.30 前，先在新版调用 `POST /api/v1/profile_source/update`，正文 `{"source": null}`，去掉知识库 JSON 里的非默认 `profile_source` 键；旧版会拒绝这个键，导致整个知识库配置失效。升级保留旧 `manager.profile.source` 行，回退后会重新读取。`{"enabled": false}` 存 `false`。`{"enabled": null}` 删行。之后的回合不再注入这一段。共享常驻会话历史里已经有的文字不会被抹掉。`POST /api/v1/profile_source/update` 的 `{"source": null}` 恢复 `关于我.md`，注入开关保持原样。仪表盘 Turn off 发送 `{"path": null}`，删掉 `knowledge_vault` 行，不删 `manager.profile.enabled`。

**权限边界：** 只给操作者。`profile.get`、`profile_source.get`、`profile_source.update`、`profile_settings.get`、`profile_settings.update` 以及 `knowledge_vault.get` / `knowledge_vault.update` 都只给操作者，级别是 inside。群、其他发送者、已路由的非 main 会话和场景管家收不到画像。配置导出不带知识库，也不带 `manager.profile.enabled`。API 客户端令牌得到 403。

**文档：** https://github.com/foolzzz/looper/blob/v2.15.31/docs/architecture/agent-system.md#the-knowledge-vault-the-operators-notes-read-and-written-through-looper

```bash
looper --version
```

#### Claude Code profile hook

**启用：** 默认不安装。`looper serve` 不改 Claude Code 的设置。用 `looper claude-code install hook --runtime-root <runtime-root>` 安装。先看打印出的路径和 diff。`--dry-run` 什么都不写。看过之后再传 `--yes`，或对 `Write these changes to {path}? [y/N]` 回答 `y`。追加到 `hooks.SessionStart` 的命令是这个 Looper 加上 `claude-code profile --hook --runtime-root …`，超时 5 秒，标准错误被丢掉。已有设置文件时，原子替换之前会把原字节备份到文件旁边；首次创建文件没有备份。

**验证：** 写入成功之前，`looper claude-code status` 打印 `profile hook: not installed`，并且自己不写设置。安装之后，操作者新开一个 Claude Code 会话（或 `/clear`）可以在 SessionStart 的 `additionalContext` 里拿到同一段编译文字，最多 3000 个字符。`looper claude-code profile` 只打印文字，不安装。笔记为空或读不到时，hook 不打印并退出 0。

**停用 / 回退：** 降级到 v2.15.30 之前先卸载，因为该版本没有这些 `claude-code` 命令。`looper claude-code uninstall hook` 预览 `Removes from hooks.SessionStart:`，做同样的确认和备份，只去掉 Looper 的 SessionStart 处理程序。成功打印 `removed.` 无关设置留着。没有 Looper 的处理程序时打印 `the SessionStart hook is not installed`，不写文件。备份名是 `{设置文件名}.looper-backup-{UTC 时间}`。

**权限边界：** 改的是操作者自己的 Claude Code 用户设置（`$CLAUDE_CONFIG_DIR/settings.json`，或 `~/.claude/settings.json`）。目标解析到 `/Library/Application Support/ClaudeCode` 或 `/etc/claude-code` 下的组织管理文件会被拒绝，退出 4，原文含 `Looper never edits them`。`LOOPER_AGENT_RUN` 非空的进程不能安装或卸载（退出 4，`refused inside a Looper agent run`），hook 调用则不打印并退出 0。Looper 自己的管家、规划者、Worker、评审、processor 和咨询不加载用户设置（`--setting-sources project`，密封或显式 hook 时是 `--setting-sources ""`），因此不会触发这个 hook。

looper claude-code status

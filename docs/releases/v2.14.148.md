# Looper v2.14.148

This is the patch release v2.14.148, a hotfix line in which each merged change ships at once. It documents one change: [#1263](https://github.com/foolzzz/looper/pull/1263) (a Cursor Worker run that ends with the transient connection failure resumes its own session instead of restarting from scratch).

## Release Decision

**Who should upgrade:** Operators who run Cursor Workers or Reviewers (native Cursor Agent or through TTADK) and see runs end with Cursor's `RetriableError: WritableIterable is closed`. Everyone else gets no visible change.

**What this release solves:** [#1263](https://github.com/foolzzz/looper/pull/1263) makes such a run continue the same Cursor session with a short continuation prompt, up to 3 times within the run, instead of one fresh restart that loses the model's context. Without a session id the single fresh restart remains.

**Breaking changes:** No. There is no migration and no API removal. The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.14.148
```

**Contributors:** Maintainer @foolzzz authored [#1263](https://github.com/foolzzz/looper/pull/1263); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.147 upgrades directly. There is no schema change.

## Behavior changes

- **A dropped Cursor connection resumes the session** ([#1263](https://github.com/foolzzz/looper/pull/1263), `looper/agents/tiers/worker.py`, `looper/agents/runtimes/cursor_agent.py`, `docs/architecture/agent-system.md`). When a Cursor process exits without a result and stderr names `RetriableError: WritableIterable is closed` (even if TTADK exits zero), a Worker or Reviewer run now relaunches with `--resume <session id>` and a continuation prompt, up to three times within the original deadline. It keeps one run record, the private directories, the launch settings and the helper. A session id is used only when the failed attempt produced model output; an init event that merely names a chat does not count, because Cursor has not stored the task yet. Otherwise the run keeps the single fresh restart with the original prompt, and a second failure of that kind ends the run. Before, every such failure got one fresh restart.
- **Retry records and errors.** Each retry records a `cursor_run_retry` event with `attempt` (1 to 3), a new `mode` (`resume` or `restart`) and the reason, plus an activity line: "Cursor's CLI gave up after reconnecting; resumed session (attempt N/3)" for a resume, the previous "retried once" text for a restart. When all attempts fail, the stderr tails of every attempt share the existing 1,000-character diagnostic limit (`retry_stderr` takes any number of attempts).
- **Resumed turns carry no instructions block.** A continuation writes only the continuation prompt to the process; the instructions block is written for the first attempt and for a restart. `CursorChannel` now owns its stream so the session id can be read from it.
- **Unchanged:** Manager and Planner turns keep their single retry, resuming the recorded chat with the same turn. Other failures, stops, cancellations, timeouts and missing logins are still not retried. The deadline is checked again before each relaunch.
- **Model-visible changes:** Yes, one. A resumed Cursor session receives this continuation prompt instead of the original prompt: "[Looper] Your previous reply was cut off by a connection error before it reached Looper. Continue from where you stopped. If your step's work is already done, send your final JSON report now; do not redo work that is already in the files or commits." Nothing else sent to a model changes, and the initial prompt is unchanged.

### 升级决策

**谁需要升级：**运行 Cursor Worker 或 Reviewer（原生 Cursor Agent 或经 TTADK）且运行以 Cursor 的 `RetriableError: WritableIterable is closed` 结束的运维者。其他人没有可见变化。

**解决了什么：**[#1263](https://github.com/foolzzz/looper/pull/1263) 让这类运行用简短的续跑提示继续同一个 Cursor 会话，单次运行内最多 3 次，而不是一次丢失模型上下文的全新重启。没有会话 id 时仍保留一次全新重启。

**是否有破坏性变更：**否。没有迁移，没有移除 API。桥接边界不变：早于 v2.13.165 的安装须先升级到 v2.13.165。

**如何验证：**核对版本为 2.14.148。

**贡献者：**维护者 @foolzzz 提交 [#1263](https://github.com/foolzzz/looper/pull/1263)；本版本无社区贡献。

```bash
looper --version   # looper 2.14.148
```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.147 上的安装可直接升级。没有结构变更。

### 行为变化与入口

- **Cursor 连接中断后恢复会话**（[#1263](https://github.com/foolzzz/looper/pull/1263)，`looper/agents/tiers/worker.py`、`looper/agents/runtimes/cursor_agent.py`、`docs/architecture/agent-system.md`）。Cursor 进程无结果退出且 stderr 含 `RetriableError: WritableIterable is closed`（即使 TTADK 退出码为零）时，Worker 或 Reviewer 运行现在用 `--resume <会话 id>` 加续跑提示重新启动，在原截止时间内最多三次，沿用同一条运行记录、私有目录、启动设置和 helper。只有失败的那次尝试产生过模型输出才使用会话 id；仅 init 事件给出聊天名不算，因为此时 Cursor 尚未保存任务。否则保留一次使用原提示的全新重启，同类失败再次出现则运行结束。此前每次这类失败只有一次全新重启。
- **重试记录与错误。**每次重试记录 `cursor_run_retry` 事件，含 `attempt`（1 到 3）、新增的 `mode`（`resume` 或 `restart`）和原因，并写一条活动：恢复时为 “Cursor's CLI gave up after reconnecting; resumed session (attempt N/3)”，全新重启时沿用原先的 “retried once” 文本。全部失败时，各次尝试的 stderr 尾部共用现有的 1,000 字符诊断上限（`retry_stderr` 接受任意次数的尝试）。
- **恢复的回合不带指令块。**续跑只向进程写入续跑提示；指令块只在首次尝试和全新重启时写入。`CursorChannel` 现在自己持有事件流，以便读取会话 id。
- **不变：**Manager 和 Planner 回合仍只重试一次，用同一回合恢复已记录的聊天。其他失败、停止、取消、超时和未登录仍不重试。每次重新启动前会再次检查截止时间。
- **面向模型的变化：**有一项。恢复的 Cursor 会话收到下面的续跑提示，而不是原始提示：“[Looper] Your previous reply was cut off by a connection error before it reached Looper. Continue from where you stopped. If your step's work is already done, send your final JSON report now; do not redo work that is already in the files or commits.” 发给模型的其他内容不变，首次提示不变。

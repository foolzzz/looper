# Looper v2.13.37

## Release Decision

**Who should upgrade:** Operators who run more than one Manager and want a Telegram or Lark bot of its own for each. Installs with only the default Manager and the built-in channel rows have nothing to do.

**What this release solves:** [#403](https://github.com/foolzzz/looper/pull/403) is stage 2 of Scenario Managers (RFC section 9.1): each Telegram or Lark channel row is now one bot with its own runner and one Manager, and Settings → Channels can add more bots for any Manager.

**Breaking changes:** No. The CLI, the configuration keys and the built-in channel rows keep their shape; the schema change is additive (see Behavior changes).

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#403](https://github.com/foolzzz/looper/pull/403); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.37
```

## Behavior changes

- **A bot per Manager:** `channel_configs` gains `manager_id` (default `manager`, references `managers`, `ON DELETE RESTRICT`) and a sequence `channel_bot_seq`. The three built-in rows (`channel-telegram`, `channel-lark`, `channel-lark_bot`) stay the default Manager's. A database trigger refuses to change a bot's `manager_id` afterwards, because a thread id `<channel_id>:<chat_id>` never changes owner.
- **Add and remove over the API:** `POST /api/channel-configs` creates a `channel-<type>-<n>` bot (`n` only grows and is never reused) for a named Manager; `DELETE /api/channel-configs/<id>` removes an added bot with its token and refused senders, keeping its chat threads and messages. A built-in row cannot be deleted. A new bot's token or app secret is entered in the dashboard and kept in `channel_secrets`; an added bot never reads the environment. The same bot cannot be added twice (HTTP 409): for Lark the identity is the app, across both Lark types.
- **One runner per enabled bot:** `looper serve` builds an adapter for every enabled row, each talking to its own Manager. A row that is the same bot as an earlier one, or cannot start, is logged and skipped without stopping the others.
- **Routing by bot:** gate chats, task end notices, wait and concurrency notices and gate posts are matched and addressed by the bot's channel id, not the channel type. A queued notice stored without a channel id still means the built-in row.
- **Config export and import:** export writes only the three built-in channel rows and reports how many Manager bots it left out; import matches channels by built-in id and refuses a file that names an added bot or a Manager other than the default. Added bots are re-added in Settings → Channels.
- **Dashboard:** Settings → Channels lists the bots with their Manager and has an Add a bot form. The Lark (bot token) settings status and people lookup now take a channel id.
- **Secret handling:** the Lark (bot token) app secret is now registered with log redaction, so it is masked in logs.
- **Entry points:** dashboard Settings, `POST`/`DELETE /api/channel-configs`, the Telegram and Lark channels, `looper config export` and `import`. For an install with only the built-in rows the author reports no behavior change.
- **Model-visible changes:** none. The `Channel:` line before each message still names only the channel type. The channel id is recorded in a run's origin only for an added bot, so existing records keep their fields.

## Upgrade and rollback

Re-run `install.sh` once v2.13.37 is published. The schema additions apply on start and need no migration of data. Rolling back to v2.13.36 leaves the new column and sequence in place and is safe if no bot was added; an added bot's row would be treated by the older version as an extra channel row, so remove added bots in Settings → Channels before rolling back.

## Optional Capability Activation & Use

### A bot per Manager

**Activation:** In Settings → Channels choose Add a bot, pick the channel type and the Manager, enter the token or app secret, and enable it; or `POST /api/channel-configs` with `channel_type`, `manager_id`, `bot_token` and `config`. A new bot is disabled unless `enabled` is true.

```bash
: "bot.json holds channel_type, manager_id, bot_token and config"
curl -X POST "$LOOPER_URL/api/channel-configs" -H 'Content-Type: application/json' -d @bot.json
curl "$LOOPER_URL/api/channel-configs"                          # the bot, with its Manager
curl -X DELETE "$LOOPER_URL/api/channel-configs/channel-telegram-2"   # roll back
```

**Validation:** The bot shows its Manager in Settings → Channels, and `looper serve` logs the bot started under its `channel-<type>-<n>` id. A message sent to the bot is answered by its Manager.

**Disable / rollback:** Disable the bot in Settings → Channels, or remove it with `DELETE /api/channel-configs/<id>`. Removing keeps its chat threads and messages.

**Authority boundary:** A bot reaches only its own Manager, and only senders on its allowlist. Its token is stored in `channel_secrets`, not exported and not read from the environment. The Manager of a bot cannot be changed after it is added.

**Docs:** [agent-system](https://github.com/foolzzz/looper/blob/main/docs/architecture/agent-system.md) and the RFC [scenario-managers](https://github.com/foolzzz/looper/blob/main/docs/architecture/rfcs/scenario-managers.zh-CN.md).

### 行为变化与入口

- 每个 Manager 一个 bot：`channel_configs` 新增 `manager_id`（默认 `manager`，引用 `managers`，`ON DELETE RESTRICT`）和序列 `channel_bot_seq`。三个内置行仍属于默认 Manager。数据库触发器禁止之后修改 bot 的 `manager_id`，因为线程 id `<channel_id>:<chat_id>` 的归属不会改变。
- API 增删：`POST /api/channel-configs` 为指定 Manager 创建 `channel-<type>-<n>` bot（`n` 只增不复用）；`DELETE /api/channel-configs/<id>` 删除已添加的 bot 及其 token 和被拒发送者，保留聊天线程和消息。内置行不可删除。新 bot 的 token 或 app secret 在仪表盘输入并存入 `channel_secrets`，不读取环境变量。同一个 bot 不能重复添加（HTTP 409）；Lark 以 app 判定，跨两种 Lark 类型。
- 每个启用的 bot 一个 runner：`looper serve` 为每个启用行构建适配器，各自连接自己的 Manager。与先前行是同一 bot、或无法启动的行会记录日志并跳过，不影响其他行。
- 按 bot 路由：gate 聊天、任务结束通知、等待与并发通知、gate 消息均按 bot 的 channel id 匹配和投递，而非渠道类型。没有 channel id 的旧排队通知仍指内置行。
- 配置导出与导入：导出只写三个内置渠道行，并报告略去的 Manager bot 数；导入按内置 id 匹配渠道，拒绝指名已添加 bot 或非默认 Manager 的文件。已添加的 bot 需在设置 → 渠道中重新添加。
- 仪表盘：设置 → 渠道列出 bot 及其 Manager，并提供「添加 bot」表单。Lark（bot token）的状态和人员查询现接受 channel id。
- 密钥处理：Lark（bot token）的 app secret 现已登记到日志脱敏，日志中会被遮盖。
- 入口：仪表盘设置、`POST`/`DELETE /api/channel-configs`、Telegram 与 Lark 渠道、`looper config export` / `import`。仅有内置行的安装，作者报告无行为变化。
- 面向模型的变化：无。每条消息前的 `Channel:` 行仍只写渠道类型。channel id 只对已添加的 bot 记录在 run 的 origin 中，已有记录字段不变。

### 升级与回退

发布后重跑 `install.sh`。schema 新增内容在启动时自动应用，无需迁移数据。回退到 v2.13.36 时新列和序列保留；若未添加过 bot 则安全，已添加的 bot 行会被旧版本当作多余渠道行，回退前请先在设置 → 渠道中删除。

### 可选能力启用与使用

#### A bot per Manager

**启用：**在设置 → 渠道选择「添加 bot」，选渠道类型和 Manager，输入 token 或 app secret 并启用；或 `POST /api/channel-configs`，带 `channel_type`、`manager_id`、`bot_token` 和 `config`。`enabled` 不为 true 时新 bot 默认停用。

```bash
: "bot.json 含 channel_type、manager_id、bot_token 和 config"
curl -X POST "$LOOPER_URL/api/channel-configs" -H 'Content-Type: application/json' -d @bot.json
curl "$LOOPER_URL/api/channel-configs"                          # 列出 bot 及其 Manager
curl -X DELETE "$LOOPER_URL/api/channel-configs/channel-telegram-2"   # 回退
```

**验证：**设置 → 渠道中该 bot 显示其 Manager，`looper serve` 日志记录该 bot 以 `channel-<type>-<n>` 启动；发给 bot 的消息由其 Manager 回复。

**停用 / 回退：**在设置 → 渠道停用，或 `DELETE /api/channel-configs/<id>` 删除；删除会保留其聊天线程和消息。

**权限边界：**bot 只连接自己的 Manager，且只接受白名单内的发送者。token 存于 `channel_secrets`，不导出、不读环境变量。添加后不能更改 bot 的 Manager。

# Looper v2.14.100

This is the patch release v2.14.100, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.99: model request recording now also covers resident agents and the in-process API runtime ([#1137](https://github.com/foolzzz/looper/pull/1137)). It only matters when request recording (`llmrec.enabled`) is on; with recording off nothing changes.

## Release Decision

**Who should upgrade:** Operators who record model requests (`llmrec.enabled`) and want the Manager, Planners, consults or the in-process API runtime recorded as well. Everyone else can stay.

**What this release solves:** [#1137](https://github.com/foolzzz/looper/pull/1137) extends recording, which covered Claude Code Workers and Reviewers, to the Manager, a task's Planner and consults when they run on Claude Code, and to the in-process API runtime. Runtimes that choose request details from the endpoint URL stay unrecorded, with a stated reason.

**Breaking changes:** No. No database change, no new dependency, no new setting, no new API, CLI or dashboard control. Records, commands and environments are unchanged while recording is off.

**How to verify:** Check the installed version. With recording on, a Manager or Planner turn is listed among the recorded requests.

```bash
looper --version   # looper 2.14.100
```

**Contributors:** Maintainer @foolzzz authored [#1137](https://github.com/foolzzz/looper/pull/1137); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.99 upgrades directly. There is no database change. With recording on, a resident Manager or Planner restarts once after the upgrade, because its launch signature now includes the recording URL.

## Behavior changes

All of these apply only while recording is on.

- **Resident agents** (`looper/agents/tiers/manager.py`, `looper/agents/tiers/planner.py`, `looper/agents/llmrec/control.py`). The Manager and a task's Planner now attach a recording route at launch when they run on Claude Code. They reuse one route per agent while its upstream, runtime type, provider and model stay the same, so the resident process's command, signature and environment do not change from turn to turn; if any of these changes the old route is ended and a new one is made. A reused route refreshes its stored proxy and TLS environment when that changed. `attach` checks proxy health without the cached result when a route is reused. Binding a turn to a route no longer clears the route's `ended_at`, so a replaced resident route can still serve its final turn. A new `llmrec_attach` step appears in the Manager's turn preparation steps.
- **Consults** (`looper/agents/consult.py`). Consults attach a route and their recorder treats the whole process as one record (`whole_process=True`), as Workers do.
- **Turn binding.** Each turn's record binds the route when it opens and releases it when it closes. Requests made while no turn is bound, such as a teammate finishing after the lead's turn or the first request of an autonomous turn, keep `record_id` NULL and carry `after_record_id`.
- **In-process API runtime** (`looper/agents/runtimes/api/adapter.py`, `looper/agents/runtimes/api/session.py`). The runtime declares the provider's base URL as its recording upstream. When a route is attached its environment carries `LOOPER_LLMREC_BASE_URL` and the session's model target uses that URL instead of the provider's.
- **Runtimes not routed** (`looper/agents/llmrec/control.py`). Codex, OMP, Pi and DSH pick request details from the endpoint URL, and a loopback URL would change the requests they send, so they are not routed. They stay `skipped`/`not_covered` with a stable reason in the run metadata; so do Grok (no known endpoint override), Cursor (its servers make the model requests) and the TTADK runtimes (TTADK manages its own provider). A Claude Code run through the TTADK launcher is no longer attached under OAuth either.
- **Shared helper** (`looper/agents/llmrec/__init__.py`, `looper/agents/runtimes/claude_code.py`). The `NO_PROXY`/`no_proxy` handling moved into a shared `no_proxy` function with the same behavior, now also used by the API runtime.
- **Unchanged:** the database schema, the dependencies, settings, the API and CLI, the dashboard, channels (Telegram and Lark). Existing records show the new `llmrec` metadata. With recording off, records, commands and environments are unchanged.
- **Documentation and tests.** New `tests/test_llmrec_api_runtime_db.py`, `tests/test_llmrec_resident_db.py` and `tests/test_llmrec_runtimes.py`; updated `tests/test_llmrec_control.py`, `tests/test_llmrec_worker_db.py` and `tests/test_manager_stop_faults.py`.
- **Model-visible changes:** None to prompts or tool descriptions. With recording on, a Manager or Planner on Claude Code runs with the recording base URL and a `NO_PROXY`/`no_proxy` that gains `127.0.0.1`, `localhost` and `::1`, and the in-process API runtime's session sends its requests through the recording proxy; the requests themselves are forwarded unchanged. Runtimes not routed see no change.

## Optional Capability Activation & Use

### Recording of resident agents and other runtimes

**Activation:** Nothing new. The change applies to turns launched after the upgrade while `llmrec.enabled` is on (Settings → Request recording).

**Validation:** After a Manager or Planner turn, its request is listed among the stored requests; runs of runtimes that are not routed show the `not_covered` reason.

```bash
loopercli llm-requests list --operator-token-file operator-token
```

**Disable / rollback:** Turn recording off in Settings → Request recording; stored requests stay. Downgrading restores the previous coverage; stored data is untouched.

**Authority boundary:** Unchanged: operator token only for settings and stored captures; agents and API-client tokens cannot read them. Bodies are stored as sent and can contain secrets printed by tools.

**Docs:** [Model request recording](https://github.com/foolzzz/looper/blob/main/docs/architecture/agent-system.md#model-request-recording-llmrec) in the agent-system architecture document.

## 中文摘要

本版本是 patch release v2.14.100（热修线，每个合并的改动立即发布）。自 v2.14.99 以来只合并了一项改动：模型请求录制现在也覆盖常驻 agent 和进程内 API 运行时（[#1137](https://github.com/foolzzz/looper/pull/1137)）。仅在开启请求录制（`llmrec.enabled`）时有影响；录制关闭时没有任何变化。

### 升级决策

**谁需要升级：**开启了模型请求录制（`llmrec.enabled`），并希望 Manager、Planner、consult 或进程内 API 运行时也被录制的运维人员。其他人可不升级。

**解决了什么：**[#1137](https://github.com/foolzzz/looper/pull/1137) 把原先只覆盖 Claude Code Worker 和 Reviewer 的录制，扩展到运行在 Claude Code 上的 Manager、任务 Planner 和 consult，以及进程内 API 运行时。由端点 URL 决定请求细节的运行时仍不录制，并给出原因。

**是否有破坏性变更：**否。无数据库变更、无新依赖、无新设置、无新的 API、CLI 或仪表盘控件。录制关闭时，记录、命令和环境均不变。

**如何验证：**核对版本为 2.14.100。开启录制后，Manager 或 Planner 的一轮请求会出现在已存请求中。

**贡献者：**维护者 @foolzzz 提交 [#1137](https://github.com/foolzzz/looper/pull/1137)；本版本无社区贡献。

```bash
looper --version   # looper 2.14.100
```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.99 上的安装可直接升级。无数据库变更。录制开启时，常驻的 Manager 或 Planner 在升级后会重启一次，因为其启动签名现在包含录制 URL。

### 行为变化与入口

以下变化仅在录制开启时生效。

- **常驻 agent**（`looper/agents/tiers/manager.py`、`looper/agents/tiers/planner.py`、`looper/agents/llmrec/control.py`）。Manager 和任务 Planner 运行在 Claude Code 上时，启动时附带录制路由。只要上游、运行时类型、provider 和模型不变，每个 agent 复用同一条路由，因此常驻进程的命令、签名和环境不会逐轮变化；其中任一项变化时，旧路由结束并新建路由。复用的路由在代理或 TLS 环境变化时刷新已存的环境。复用路由时，`attach` 检查代理健康不使用缓存结果。把一轮绑定到路由不再清除路由的 `ended_at`，被替换的常驻路由仍可服务其最后一轮。Manager 的轮次准备步骤新增 `llmrec_attach`。
- **Consult**（`looper/agents/consult.py`）。Consult 附带路由，其记录器与 Worker 一样把整个进程视为一条记录（`whole_process=True`）。
- **轮次绑定。**每一轮的记录在开始时绑定路由，结束时释放。没有绑定轮次时发出的请求（例如队友在主导者的轮次结束后完成，或自主轮次的第一个请求）`record_id` 为 NULL，并带有 `after_record_id`。
- **进程内 API 运行时**（`looper/agents/runtimes/api/adapter.py`、`looper/agents/runtimes/api/session.py`）。该运行时把 provider 的 base URL 声明为录制上游。附带路由后，其环境带有 `LOOPER_LLMREC_BASE_URL`，会话的模型目标使用该 URL 而非 provider 自己的。
- **不走路由的运行时**（`looper/agents/llmrec/control.py`）。Codex、OMP、Pi 和 DSH 由端点 URL 决定请求细节，回环 URL 会改变它们发出的请求，因此不走路由。它们在运行元数据中保持 `skipped`/`not_covered` 并带稳定的原因；Grok（无已知端点覆盖方式）、Cursor（模型请求由其服务器发出）和 TTADK 运行时（TTADK 自行管理 provider）同样如此。通过 TTADK 启动器运行的 Claude Code 在 OAuth 下也不再附带路由。
- **共享函数**（`looper/agents/llmrec/__init__.py`、`looper/agents/runtimes/claude_code.py`）。`NO_PROXY`/`no_proxy` 的处理移入共享的 `no_proxy` 函数，行为不变，API 运行时也使用它。
- **不变：**数据库结构、依赖、设置、API 和 CLI、仪表盘、渠道（Telegram 和 Lark）。已有记录会显示新的 `llmrec` 元数据。录制关闭时，记录、命令和环境均不变。
- **文档与测试。**新增 `tests/test_llmrec_api_runtime_db.py`、`tests/test_llmrec_resident_db.py` 和 `tests/test_llmrec_runtimes.py`；更新 `tests/test_llmrec_control.py`、`tests/test_llmrec_worker_db.py` 和 `tests/test_manager_stop_faults.py`。
- **面向模型的变化：**提示和工具描述均无变化。录制开启时，运行在 Claude Code 上的 Manager 或 Planner 使用录制 base URL，且 `NO_PROXY`/`no_proxy` 加入 `127.0.0.1`、`localhost`、`::1`；进程内 API 运行时的会话经录制代理发送请求，请求本身原样转发。不走路由的运行时无变化。

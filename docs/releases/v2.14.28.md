# Looper v2.14.28

This is the patch release v2.14.28, a hotfix line in which each merged change ships at once. It ships the seven changes merged since v2.14.27: a drain state for planned restarts ([#932](https://github.com/foolzzz/looper/pull/932)), component fingerprints and an upgrade plan ([#935](https://github.com/foolzzz/looper/pull/935)), Codex through TTADK ([#940](https://github.com/foolzzz/looper/pull/940)), the groundwork for command schedules ([#936](https://github.com/foolzzz/looper/pull/936), [#938](https://github.com/foolzzz/looper/pull/938), [#941](https://github.com/foolzzz/looper/pull/941)), and a service health probe ([#939](https://github.com/foolzzz/looper/pull/939)).

## Release Decision

**Who should upgrade:** Operators who want a planned restart that holds new work instead of cutting it off, a dry-run upgrade plan, a Lark alert when the service stops answering, or Codex runs through TTADK. Everyone else sees no change in how tasks, schedules and Agent Profiles run.

**What this release solves:** [#932](https://github.com/foolzzz/looper/pull/932) adds an in-memory drain state (serving, draining, drained; scope turns or runs) with operator-only operations `system.drain`, `system.drain_status` and `system.drain_cancel`; [#935](https://github.com/foolzzz/looper/pull/935) fingerprints Looper's components (`looper/components.toml`), serves them at `POST /api/v1/system/components` and adds `looper service upgrade --dry-run`; [#940](https://github.com/foolzzz/looper/pull/940) gives runtimes a `launcher` (`native` or `ttadk`) and registers `ttadk-codex` when `ttadk` is on PATH; [#939](https://github.com/foolzzz/looper/pull/939) adds `system.health` and `looper service probe`; [#936](https://github.com/foolzzz/looper/pull/936), [#938](https://github.com/foolzzz/looper/pull/938) and [#941](https://github.com/foolzzz/looper/pull/941) publish the command schedules RFC, add a stdlib-only command runner script and add the database columns for command schedules. Command schedules themselves are not usable yet.

**Breaking changes:** No. No API, default or existing behavior is removed. Two additive database migrations run on first start (see Upgrading).

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#932](https://github.com/foolzzz/looper/pull/932), [#935](https://github.com/foolzzz/looper/pull/935), [#936](https://github.com/foolzzz/looper/pull/936), [#938](https://github.com/foolzzz/looper/pull/938), [#939](https://github.com/foolzzz/looper/pull/939), [#940](https://github.com/foolzzz/looper/pull/940) and [#941](https://github.com/foolzzz/looper/pull/941); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.27 upgrades directly. This release adds two migrations, applied once on the first start of an existing database and recorded in `schema_migrations`; a new database gets them from `schema.sql`:

- `runtime_launcher` ([#940](https://github.com/foolzzz/looper/pull/940)) adds `agent_runtimes.launcher` (`TEXT NOT NULL DEFAULT 'native'`, limited to `native` or `ttadk`).
- `command_schedules` ([#941](https://github.com/foolzzz/looper/pull/941)) adds columns to `schedules` (`kind` defaulting to `agent`, `command`, `env`, `env_file`, `success_deadline`, three alert thresholds, overlap and deadline alert state), adds run columns to `schedule_runs` (start time, exit code and signal, log path, size, truncation and tail, runner pid and start), adds the statuses `succeeded` and `interrupted` to `schedule_runs`, adds four alert kinds to `schedule_notifications`, and adds an index on `schedule_runs.finished_at`.

Both only add; existing runtimes read as `native` and existing schedules as `agent`. The drain state is never stored: a new process always starts serving.

## Behavior changes

- **Drain ([#932](https://github.com/foolzzz/looper/pull/932)).** `system.drain` (scope `turns` or `runs`, optional `timeout_seconds`, default 180 for turns and 1200 for runs), `system.drain_status` and `system.drain_cancel` are POST operations, operator only. While draining, new Worker and Reviewer runs wait for a slot, new Manager turns wait (the bus message stays unacknowledged and is replayed after the restart), schedule fires are deferred to catch-up, new Manager consults and wait checks are held; Planner turns and `TASK_START` are not held, so results still reach the database. The status reports what is still running or waiting and becomes `drained` when nothing blocks. Deadlines are reported (`deadline_passed`); they do not abort work. In this release every run blocks a drain, because no run can outlive the process yet. `system.status` carries the drain, and the dashboard shows an "Upgrading" banner while it is draining or drained. Nothing drains unless an operator calls it. The pull request description mentions a DELETE route; the code serves POST operations only. The same change keeps a Manager answer's reply route (web session and message, or Telegram or Lark chat and reply target) in the journaled message, so a replayed answer after a restart still reaches its original chat.
- **Components and plan ([#935](https://github.com/foolzzz/looper/pull/935)).** `looper/components.toml` declares the components (web, control plane, keeper, runners), the contracts a live run depends on and the files that belong to none. The server snapshots the loaded installation once at start and serves it at `POST /api/v1/system/components` (operator only; answers unavailable until the snapshot exists). `looper service upgrade --dry-run [--to REF_OR_WHEEL]` compares a Git ref (default `origin/main`) or a wheel with the running service and prints the plan (`NOOP`, `WEB_ONLY`, `CONTROL_PLANE` or `FULL`), the changed components and the reasons. Without `--dry-run` it refuses: it installs, drains and restarts nothing. Keeper mode is off, so a control-plane change plans `FULL`. `components.toml` and the runner files the fingerprints read are now packaged in the wheel.
- **Codex through TTADK ([#940](https://github.com/foolzzz/looper/pull/940)).** A runtime has a typed `launcher`. When `ttadk` is on PATH, the built-in runtime `ttadk-codex` (id `rt-ttadk-codex`, type `codex`) is registered if its id and name are free. Its Codex launches (every role and the consult) run `env CODEX_HOME=<home> ttadk codex --skip-check --mode mixed -- <the native arguments>`, with a cleaned environment. It takes only login (OAuth) providers, since TTADK replaces the provider with its gateway; other providers are refused with the supported alternative. TTADK arguments that would bypass its gateway or that it cannot forward are refused. A missing TTADK, a missing sign-in, an unreadable check or a mismatched tool command refuse the launch with a typed cause and the native alternative. TTADK's exit code is not trusted, so a run without a result is reported as ended without one. Runs record the launcher. `looper doctor` checks TTADK only when an Agent Profile uses it. `launcher` is exported and imported with the configuration (omitted when `native`). Native Codex commands, homes and records are unchanged.
- **Command schedules, groundwork ([#936](https://github.com/foolzzz/looper/pull/936), [#938](https://github.com/foolzzz/looper/pull/938), [#941](https://github.com/foolzzz/looper/pull/941)).** The RFC `docs/architecture/rfcs/command-schedules-v0.zh-CN.md` (Chinese) is published, D3 of the scheduled tasks RFC is rewritten, and the plan registers the stage. `looper/agents/command_runner.py` is a stdlib-only script that runs a command in its own session and process group, truncates the log at a limit, enforces the timeout (SIGTERM to the group, then SIGKILL), kills leftovers and writes `runner.json` and `exit.json`; nothing calls it yet. The migration adds the columns, and a schedule's `kind` cannot change. The one behavior change: `succeeded` counts as a success, and `interrupted` as a failure, in a schedule's counters and alerts. No schedule can have these statuses yet.
- **Health probe ([#939](https://github.com/foolzzz/looper/pull/939)).** The scheduler records its latest tick and latest healthy tick. `system.health` (POST, read) returns version, pid, start time and the scheduler's tick ages without touching the database. The ops file takes an optional `[probe]` section (`notify_channel` and `notify_chat` together, `after_minutes` 1 to 120 default 5, `lark_profile`). `looper service probe` runs one check, updates a state file under the runtime root, sends one Lark alert after the set minutes of consecutive bad checks and one recovery message afterwards; without the section it prints that it is not configured and exits 0. This release does not install the unit that runs it every minute.
- **Model-visible changes:** None. No prompt, tool or message text given to a model changes, and the Manager's tool set is unchanged. The new operations appear in the v1 API catalog for operators and clients. Only a run through `ttadk-codex` differs for the model, in that TTADK launches Codex.

## Optional Capability Activation & Use

### TTADK Codex runtime

**Activation:** Install TTADK and sign in. The runtime `ttadk-codex` is registered when `ttadk` is on PATH; give an Agent Profile that runtime and a Codex login provider.

**Validation:** The runtime shows its probed version in the runtime list; `looper doctor` reports the TTADK check for profiles that use it.

**Disable / rollback:** Point the profile back at the native `codex` runtime. Its runs then do not count in TTADK's records.

**Authority boundary:** It only launches `ttadk codex`, with login providers only and without arguments that bypass TTADK's gateway. TTADK's sign-in is checked noninteractively, with a result cached for a minute.

**Docs:** [Design (Chinese)](https://github.com/foolzzz/looper/blob/v2.14.28/docs/architecture/rfcs/ttadk-launch-v0.zh-CN.md).

```bash
looper doctor   # includes the TTADK check when a profile uses it
```

### Service probe

**Activation:** Add a `[probe]` section with `notify_channel` and `notify_chat` to the ops file, then run `looper service probe` (a periodic unit is not installed by this release).

**Validation:** Run `looper service probe`; it prints a verdict line when the state changes.

**Disable / rollback:** Remove the `[probe]` section; the command then does nothing.

**Authority boundary:** It reads `system.health` on the loopback port with the operator token and sends only as the Lark bot, not through the server.

**Docs:** [Agent system](https://github.com/foolzzz/looper/blob/v2.14.28/docs/architecture/agent-system.md).

```bash
looper service probe
```

### Service upgrade dry run

**Activation:** Run `looper service upgrade --dry-run` against an installed service.

**Validation:** The output starts with `plan` and lists the target, the running version, the changed components and the reasons.

**Disable / rollback:** Nothing to disable; it installs, drains and restarts nothing.

**Authority boundary:** It reads the running service's component fingerprints with the operator token and reads a Git ref or wheel locally.

**Docs:** [Agent system](https://github.com/foolzzz/looper/blob/v2.14.28/docs/architecture/agent-system.md).

```bash
looper service upgrade --dry-run --to origin/main
```

### Drain operations

**Activation:** An operator calls `system.drain` (`POST /api/v1/system/drain`) with a scope.

**Validation:** `system.drain_status` shows the phase and what still blocks; `system.status` carries the same drain.

**Disable / rollback:** `system.drain_cancel` resumes admission and releases the held messages and runs; restarting the service also starts it serving.

**Authority boundary:** Operator only; an API client is refused. A deadline never aborts work.

**Docs:** [Hot upgrade design (Chinese)](https://github.com/foolzzz/looper/blob/v2.14.28/docs/architecture/rfcs/hot-upgrade-v0.zh-CN.md).

```bash
# POST /api/v1/system/drain_status   (operator)
```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.27 上的安装可直接升级。本版本新增两项迁移，在已有数据库首次启动时执行一次并记入 `schema_migrations`，新数据库由 `schema.sql` 创建：

- `runtime_launcher`（[#940](https://github.com/foolzzz/looper/pull/940)）新增 `agent_runtimes.launcher`（`TEXT NOT NULL DEFAULT 'native'`，限定为 `native` 或 `ttadk`）。
- `command_schedules`（[#941](https://github.com/foolzzz/looper/pull/941)）给 `schedules` 增加列（默认为 `agent` 的 `kind`、`command`、`env`、`env_file`、`success_deadline`、三个告警阈值、重叠与截止告警状态），给 `schedule_runs` 增加运行列（开始时间、退出码与信号、日志路径、大小、截断与尾部、runner 进程号与启动标识），为 `schedule_runs` 增加状态 `succeeded` 和 `interrupted`，为 `schedule_notifications` 增加四种告警类型，并在 `schedule_runs.finished_at` 上建索引。

两项都只增不改：现有运行时读作 `native`，现有 schedule 读作 `agent`。排空状态从不落库：新进程总是从 serving 开始。

### 行为变化与入口

- **排空（[#932](https://github.com/foolzzz/looper/pull/932)）。**`system.drain`（范围 `turns` 或 `runs`，可选 `timeout_seconds`，turns 默认 180、runs 默认 1200）、`system.drain_status`、`system.drain_cancel` 都是仅操作者可用的 POST 操作。排空期间：新的 Worker 和 Reviewer 运行等待槽位，新的 Manager 回合等待（总线消息保持未确认，重启后重放），schedule 触发推迟到补跑，新的 Manager 咨询和等待检查被挂起；Planner 回合和 `TASK_START` 不挂起，结果仍能写入数据库。状态报告仍在运行或等待的内容，无阻塞时变为 `drained`。截止时间只报告（`deadline_passed`），不会中止工作。本版本中所有运行都会阻塞排空，因为还没有能在进程之外存活的运行。`system.status` 带出排空状态，排空或已排空时控制台显示“升级中”横幅。不调用就不会排空。PR 描述提到 DELETE 路由，代码只提供 POST 操作。同一改动还把 Manager 回答的回复路由（web 会话与消息，或 Telegram、Lark 的聊天和回复目标）保存在日志化消息中，重启后重放的回答仍能送达原聊天。
- **组件与计划（[#935](https://github.com/foolzzz/looper/pull/935)）。**`looper/components.toml` 声明组件（web、控制面、看护进程、runners）、在运行中的任务所依赖的契约，以及不属于任何组件的文件。服务启动时对已加载的安装做一次快照，通过 `POST /api/v1/system/components`（仅操作者；快照就绪前返回不可用）提供。`looper service upgrade --dry-run [--to REF_OR_WHEEL]` 把 Git 引用（默认 `origin/main`）或 wheel 与运行中的服务比较，打印计划（`NOOP`、`WEB_ONLY`、`CONTROL_PLANE` 或 `FULL`）、变化的组件和原因。不带 `--dry-run` 会拒绝：它不安装、不排空、不重启。看护模式关闭，所以控制面变化的计划是 `FULL`。指纹读取的 `components.toml` 和 runner 文件现在随 wheel 打包。
- **Codex 经 TTADK（[#940](https://github.com/foolzzz/looper/pull/940)）。**运行时有了类型化的 `launcher`。PATH 中有 `ttadk` 时，如果 id 和名称空闲，则登记内置运行时 `ttadk-codex`（id `rt-ttadk-codex`，类型 `codex`）。它的 Codex 启动（每个角色和咨询）执行 `env CODEX_HOME=<home> ttadk codex --skip-check --mode mixed -- <原生参数>`，环境经过清理。它只接受登录（OAuth）提供方，因为 TTADK 用自己的网关替换提供方，其他提供方会被拒绝并给出可用的替代方案。会绕过 TTADK 网关或 TTADK 无法转发的参数会被拒绝。TTADK 缺失、未登录、检查结果不可读或工具命令不匹配时，拒绝启动并给出类型化的原因和原生替代方案。TTADK 的退出码不可信，没有结果的运行报告为“未产生结果即结束”。运行记录会记下 launcher。`looper doctor` 仅在有 Agent Profile 使用 TTADK 时检查它。`launcher` 随配置导出导入（为 `native` 时省略）。原生 Codex 的命令、home 和记录不变。
- **命令型定时任务，前置工作（[#936](https://github.com/foolzzz/looper/pull/936)、[#938](https://github.com/foolzzz/looper/pull/938)、[#941](https://github.com/foolzzz/looper/pull/941)）。**发布 RFC `docs/architecture/rfcs/command-schedules-v0.zh-CN.md`（中文），重写定时任务 RFC 的 D3，并在计划中登记该阶段。`looper/agents/command_runner.py` 是仅用标准库的脚本：在独立会话和进程组中运行命令，按上限截断日志，强制超时（先对进程组发 SIGTERM，再 SIGKILL），清理残留进程，并写出 `runner.json` 和 `exit.json`；目前没有调用方。迁移增加相应列，schedule 的 `kind` 不可更改。唯一的行为变化：在 schedule 的计数和告警中，`succeeded` 算成功、`interrupted` 算失败。目前还没有 schedule 会出现这些状态。
- **健康探针（[#939](https://github.com/foolzzz/looper/pull/939)）。**调度器记录最近一次 tick 和最近一次健康 tick。`system.health`（POST，只读）返回版本、进程号、启动时间和调度器的 tick 时长，不访问数据库。ops 文件可选 `[probe]` 小节（`notify_channel` 与 `notify_chat` 必须同时配置，`after_minutes` 为 1 到 120、默认 5，`lark_profile`）。`looper service probe` 运行一次检查并更新运行时根目录下的状态文件，连续异常达到设定分钟数后发一条 Lark 告警，恢复后发一条恢复消息；没有该小节时打印未配置并以 0 退出。本版本不安装每分钟运行它的单元。
- **面向模型的变化：**无。给模型的提示词、工具或消息文本都不变，Manager 的工具集不变。新操作出现在面向操作者和客户端的 v1 API 目录中。只有经 `ttadk-codex` 的运行对模型有区别，即由 TTADK 启动 Codex。

### 可选能力启用与使用

#### TTADK Codex runtime

**启用：**安装 TTADK 并登录。PATH 中有 `ttadk` 时登记运行时 `ttadk-codex`；给 Agent Profile 选该运行时和 Codex 登录提供方。

**验证：**运行时列表显示其探测到的版本；`looper doctor` 对使用它的 profile 报告 TTADK 检查。

**停用 / 回退：**把 profile 改回原生 `codex` 运行时。其运行不再计入 TTADK 的记录。

**权限边界：**只启动 `ttadk codex`，只用登录提供方，且不带绕过 TTADK 网关的参数。TTADK 登录以非交互方式检查，结果缓存一分钟。

#### Service probe

**启用：**在 ops 文件中加入含 `notify_channel` 和 `notify_chat` 的 `[probe]` 小节，然后运行 `looper service probe`（本版本不安装周期性单元）。

**验证：**运行 `looper service probe`；状态变化时会打印一行结论。

**停用 / 回退：**删除 `[probe]` 小节；命令随即什么都不做。

**权限边界：**用操作者令牌读取回环端口上的 `system.health`，只以 Lark 机器人发送，不经过服务。

**文档：**[Agent system](https://github.com/foolzzz/looper/blob/v2.14.28/docs/architecture/agent-system.md)。

```bash
looper service probe
```

#### Service upgrade dry run

**启用：**对已安装的服务运行 `looper service upgrade --dry-run`。

**验证：**输出以 `plan` 开头，并列出目标、运行中的版本、变化的组件和原因。

**停用 / 回退：**无需停用；它不安装、不排空、不重启。

**权限边界：**用操作者令牌读取运行中服务的组件指纹，并在本地读取 Git 引用或 wheel。

**文档：**[Agent system](https://github.com/foolzzz/looper/blob/v2.14.28/docs/architecture/agent-system.md)。

```bash
looper service upgrade --dry-run --to origin/main
```

#### Drain operations

**启用：**操作者以某个范围调用 `system.drain`（`POST /api/v1/system/drain`）。

**验证：**`system.drain_status` 显示阶段和仍在阻塞的内容；`system.status` 带出同样的排空状态。

**停用 / 回退：**`system.drain_cancel` 恢复接收并释放被挂起的消息和运行；重启服务也会回到 serving。

**权限边界：**仅操作者；API 客户端会被拒绝。截止时间从不中止工作。

**文档：**[热升级设计（中文）](https://github.com/foolzzz/looper/blob/v2.14.28/docs/architecture/rfcs/hot-upgrade-v0.zh-CN.md)。

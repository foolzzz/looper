# Looper v2.13.0

## Release Decision

**Who should upgrade:** Operators who need explicit provider accounts, protocol endpoints and saved models, runtime-compatible Agent Profiles, or model management through the Manager. Operators using custom registry HTTP clients must update those clients before upgrading.

**What this release solves:** [#258](https://github.com/foolzzz/looper/pull/258) restructures the LLM registry into typed providers, endpoints, models and profiles. It adds a guarded automatic v2 registry upgrade, configuration export/import v3 and the Manager tool `looper_models`, with exact launch bindings and provider/protocol-scoped pricing.

**Breaking changes:** Yes. Registry HTTP contracts, profile writes and configuration exports change as detailed below. Existing v2 registries upgrade automatically only after a verified full backup; unsupported or mismatched conversions roll back completely. Schema version 3 cannot be opened by an unpatched older binary. Downgrading requires restoring the pre-upgrade full backup into a separate database; a v3 config export cannot replace that backup.

**How to verify:** Follow Upgrade and rollback below before restarting. On an isolated copy, check the version, migration report and saved profile selections; require equal before/after/mapped profile counts and zero unresolved references, launch-binding mismatches and pricing mismatches. Read back accounts, exact model/protocol identities and historical costs. Run a task and a Manager `looper_models` query, then preview a v3 export/import round trip. Version and doctor checks alone do not prove migration correctness.

**Contributors:** Release maintainer @foolzzz, author of [#258](https://github.com/foolzzz/looper/pull/258); no community contribution was included in this minor release.

```bash
looper --version   # looper 2.13.0
looper doctor
```

## Upgrade and rollback

1. **Back up before upgrading.** Quiesce writes and scheduling, and stop the v2.12.5 service. Keep an independent full database backup and the existing service configuration and runtime data. Rehearse restore on a separate database. A configuration export or schema-only dump cannot recover history, credentials and references. Protect backups as secrets.
2. **Check PostgreSQL client tools.** Ensure the service user can run the configured `pg_dump` and a local `pg_restore` capable of reading its archive; use client tools not older than the PostgreSQL server. Re-run `install.sh` to upgrade when v2.13.0 is published, then start with the existing configuration and runtime root.
3. **What startup does.** Before any DDL, `looper serve` creates a full custom-format `pg_dump` backup and verifies it with `pg_restore --list`, requiring both table definitions and table data. Missing or unverifiable backups stop startup without changing the database; `--skip-backup` is rejected for registry upgrades. Conversion, schema changes and the version marker run in one locked transaction. Unresolved references, launch/pricing mismatches or any other failure roll the entire transaction back. Successful startup records registry schema version 3.
4. **Read back before resuming work.** Check the migration report, profile IDs and selections, endpoint semantics, runtime options, model identities and prices. Verify historical costs remain unchanged. Rehearse a real task and Manager query on an isolated copy before resuming writes and schedules.
5. **Roll back to v2.12.5.** Stop v2.13.0 and retain its database for recovery. Restore the verified pre-upgrade full backup into a separate replacement database. Install the v2.12.5 release wheel, point its service configuration at the restored database and validate profile counts, selections, historical costs and old-version launches before resuming. Never point an unpatched v2.12.5 binary at the upgraded database. There is no supported down migration or v3-to-v2 configuration export. Writes made after the backup need an explicit recovery decision; restoring the backup does not recover them.

**Known issue:** When `backup.command` or `LOOPER_BACKUP_CMD` runs `pg_dump` in Docker through `docker exec`, but no local `pg_restore` is available, v2.13.0 refuses to start the upgrade and leaves the database unchanged. Install a local `pg_restore` of any version not older than the PostgreSQL server and make it available on the service user's PATH, or wait for the patch release. Do not bypass the backup gate.

## Behavior changes

- **Registry structure:** A provider holds its name, vendor type, credential and per-protocol endpoints, plus environment and concurrency settings. A model belongs to one provider and has an exact name, exactly one protocol, context/reasoning/background settings and prices. A profile references a runtime and saved model, with `effort`, `agent_teams` and `custom_prompt`.
- **Runtime choices:** No new runtime adapter is introduced in this release. All six existing runtimes now use saved models. OMP and pi use the selected model’s exact protocol instead of choosing from an account’s protocol list. Profile effort choices now include pi’s `off` and `minimal`; dsh exposes `low`, `high` and `max`.
- **Automatic upgrade:** Startup upgrades a v2 registry only after creating a full `pg_dump` backup and verifying it with `pg_restore --list`, including table definitions and data. Missing or unverifiable backups stop startup before any DDL; registry upgrades reject `--skip-backup`. Conversion and schema changes run in one locked transaction, with full rollback on unresolved references, launch/pricing mismatches or other failures.
- **Migration compatibility:** Preserve profile IDs, selections, runtime options, legacy protocol choices and omitted-endpoint semantics. Materialize models used by legacy open catalogs. Equivalent accounts merge only after compatibility checks, with dependent provider references remapped.
- **Breaking HTTP contracts:** Provider `protocols`, `base_url` and embedded `models` become `vendor_type`, `endpoints` and independent `/api/models` resources. Profile writes require `model_id` instead of `provider_id` plus a model string; reads return a structured `model`. `/api/registry` exposes saved models and vendor types.
- **Explicit selection and write guards:** Empty catalogs no longer permit arbitrary profile model names. Model provider/name/protocol identity and provider vendor identity are immutable. Referenced models, endpoints and providers cannot be deleted; incompatible updates are refused. Vendor suggestions apply at creation and do not overwrite saved settings. Endpoint validation rejects malformed URLs, embedded credentials and fragments.
- **Configuration transfer:** Export writes `looper-config/v3`, carrying endpoints, independent models and composite profile model references. v2 and v1 imports remain supported through the legacy converter. User models under built-in providers are retained. Invalid or ambiguous entries receive explicit skip diagnostics; apply recomputes the plan server-side. Legacy profile `system_prompt_mode` is ignored with a note; v3 rejects it.
- **Manager tools:** `looper_models` lists, creates, updates and deletes unused models, with confirmation for deletion. `looper_providers` retains registration and update using account/endpoints fields. `looper_agent_profiles` accepts a model ID or full provider/name/protocol reference. Credentials are entered through the dashboard.
- **Dashboard settings:** LLM Providers manages accounts, endpoints and models; Agent Profiles selects compatible saved models with runtime-specific efforts. Roles, projects, tasks and schedules display disambiguated profile identities. Creating a profile inline now registers it without automatically changing the current selection. Import results distinguish skipped entries from complete success.
- **Pricing and sessions:** Exact, case-sensitive price matches precede normalized matches and built-in fallback, within the selected provider/protocol. Claude subscription aliases retain their lookup semantics. Null overrides fall back; zero is explicitly free; unknown prices remain unknown. Relevant configuration changes restart resident processes for subsequent turns so bindings and prices refresh.
- **Database compatibility:** The registry now records schema version 3 and refuses unsupported newer versions. Recovery uses the backup in a separate database; an unpatched older binary must not open the upgraded database.
- **Known issue:** If `backup.command` or `LOOPER_BACKUP_CMD` runs `pg_dump` through `docker exec` and no local `pg_restore` exists, startup refuses the upgrade and leaves the database unchanged. Install a local `pg_restore` with a version not older than the PostgreSQL server, or wait for the patch release.

## Model-visible changes

- Manager instructions explain accounts, exact model references and profile recipes, direct credential entry to dashboard settings, and include models in the existing user-requested write policy.
- Manager tool schemas and results expose the new model layer and compatibility information. Profile custom prompts and role/task append-or-replace semantics remain in their existing layers; prompt preview reports mode provenance without loading another selected profile’s credentials.

## Entry points

- **Dashboard:** Updated provider/model/profile settings, shared profile selectors and summaries, prompt preview provenance, and v3 import/export presentation.
- **Telegram/Lark channels:** Model management is available through the shared Manager instructions and tools. No channel-specific command or transport change is needed.
- **CLI:** `looper serve` performs the guarded startup migration. Existing configuration export/import commands use v3 and accept legacy files; help text reflects the new format.

## Optional Capability Activation & Use

### Typed LLM registry and model management

**Activation:** Complete the guarded upgrade above. In Settings → LLM Providers, configure an account, its protocol endpoints and saved models; enter credentials only in the dashboard. In Agent Profiles, choose a compatible runtime and saved model, then explicitly select the profile for a role or override. Inline creation registers a profile without selecting it. Ask the Manager to list models with `looper_models`, or explicitly request a model write.

```bash
looper --version   # looper 2.13.0
looper doctor
```

**Validation:** On a disposable server, read back the exact provider/name/protocol identity and compatible efforts; run a task and Manager model query. Verify incompatible writes and deletion of referenced models/endpoints/providers are refused, unused-model deletion requests confirmation, and credential values do not appear in audit records, including environment-entry arrays. Check migration counts and launch/pricing parity separately from runtime success.

**Disable / rollback:** Stop using Manager model writes or select another saved compatible profile. This does not disable the mandatory schema upgrade. To return to v2.12.5, stop the new service and restore the pre-upgrade full backup into a separate database as described above; changing a profile does not undo migration.

**Authority boundary:** Reads use existing Manager access; writes require a user request in the current turn, and deletion retains the existing confirmation requirement. Manager tools do not accept credentials. Registry validation applies equally to dashboard, HTTP and Manager writes; it does not grant additional host or runtime permissions.

**Docs:** [Registry design and migration](https://github.com/foolzzz/looper/blob/main/docs/architecture/rfcs/llm-models-v0.zh-CN.md), [Manager tools](https://github.com/foolzzz/looper/blob/main/docs/architecture/agent-system.md#the-managers-platform-tools), [implementation and validation](https://github.com/foolzzz/looper/pull/258).

### Configuration export/import v3

**Activation:** Use the existing dashboard configuration transfer or CLI commands. Exports now write `looper-config/v3` with independent models and composite profile references. Preview before applying; v2 and v1 inputs remain supported through the legacy converter.

```bash
looper config export looper-config-v3.json
looper config import looper-config-v3.json --json
```

**Validation:** On a disposable installation, check the format, endpoints, exact model references and retained user models under built-in providers. Inspect skip diagnostics and missing credentials, apply a reviewed preview, then export and read back again. Invalid or ambiguous entries are skipped explicitly; a partially applied import is not complete success. Apply recomputes its plan server-side. Legacy profile `system_prompt_mode` is ignored with a note; v3 rejects it.

**Disable / rollback:** Cancel the preview to avoid writes. There is no v3-to-v2 export. An import is not a database rollback; returning to v2.12.5 requires the separate full-backup restore above, including an operator decision about later writes.

**Authority boundary:** Preview is read-only; `--apply` or the dashboard apply action writes the reviewed configuration through the existing transaction and validation rules. Existing credential masking and placeholder behavior remain; store exported files privately and enter missing credentials through dashboard settings. A config export is not a full database backup.

**Docs:** [Configuration transfer](https://github.com/foolzzz/looper/blob/main/docs/architecture/agent-system.md#moving-the-configuration-export-and-import), [v3 format and compatibility](https://github.com/foolzzz/looper/blob/main/docs/architecture/rfcs/llm-models-v0.zh-CN.md), [implementation](https://github.com/foolzzz/looper/pull/258).

**谁需要升级：**需要显式管理 provider 账户、协议 endpoint、已保存模型、兼容运行时的 Agent Profile，或通过 Manager 管理模型的操作者。使用 registry HTTP 接口的自定义客户端需先适配新契约。

**贡献者：**发布维护者 @foolzzz，提交 [#258](https://github.com/foolzzz/looper/pull/258)；本次 minor release 无社区贡献。

### 升级与回退

1. **升级前备份。** 暂停写入和调度，停止 v2.12.5 服务；独立保留完整数据库备份、已有服务配置和 runtime 数据，并在独立数据库演练恢复。配置导出和 schema-only dump 不能恢复历史、凭据与引用。备份按秘密保护。
2. **检查 PostgreSQL 客户端。** 服务用户需能运行配置的 `pg_dump`，以及能读取其归档的本地 `pg_restore`；客户端版本不低于 PostgreSQL 服务端。v2.13.0 发布后重跑 `install.sh` 升级，再用已有配置和 runtime root 启动。
3. **启动行为。** `looper serve` 在任何 DDL 前执行完整 custom-format `pg_dump`，用 `pg_restore --list` 验证同时包含表定义与表数据。备份缺失或无法验证时停止启动，数据库不变；registry 升级拒绝 `--skip-backup`。转换、schema 变化及版本标记在同一加锁事务内完成；未解析引用、启动/价格不匹配或其他失败都会使整个事务回滚。成功后记录 schema version 3。
4. **恢复业务前读回。** 核对迁移报告、Profile ID 和选择、endpoint 默认语义、运行时选项、模型与价格，确认历史费用不变。先在隔离副本跑真实任务和 Manager 查询，再恢复写入和调度。
5. **回退 v2.12.5。** 停止 v2.13.0，保留升级后数据库供恢复；将验证过的升级前完整备份恢复到另一个替代数据库。安装 v2.12.5 release wheel，将其服务配置指向恢复库，验证 Profile 数量与选择、历史费用及旧版启动行为后再恢复业务。绝不能用未打补丁的 v2.12.5 打开升级后的数据库。没有受支持的降级迁移或 v3→v2 配置导出；备份后的新写入需另行决定恢复方式，恢复旧备份不会保留这些写入。

**已知问题：**若 `backup.command` 或 `LOOPER_BACKUP_CMD` 通过 `docker exec` 在 Docker 内执行 `pg_dump`，而本机没有 `pg_restore`，v2.13.0 会拒绝开始升级，数据库保持不变。安装任意不低于 PostgreSQL 服务端版本的本地 `pg_restore`，并确保服务用户 PATH 可找到它；或等待 patch release。不要绕过备份门禁。

### 行为变化

- **有类型的 registry。** Provider 保存名称、vendor 类型、凭据、各协议 endpoint、环境和并发设置；model 属于一个 provider，具有精确名称、唯一协议、上下文/推理/后台设置和价格；profile 引用 runtime 与已保存 model，并携带 `effort`、`agent_teams`、`custom_prompt`。
- **六种已有运行时接入模型层。** 本版不新增 runtime adapter；Claude Code、Codex、OMP、Grok、pi、dsh 全部使用已保存 model。OMP/pi 使用模型的准确协议，不再按账户协议列表择优；pi effort 包含 `off/minimal`，dsh 为 `low/high/max`。生成命令和环境前验证绑定，保留既有隔离方式。
- **自动迁移与兼容。** 先验证完整备份，再在单个加锁事务中转换并修改 schema；失败完整回滚。保留 Profile ID、选择、runtime options、旧协议选择和省略 endpoint 的语义，为旧开放目录实际使用的模型建档。等价账户仅在兼容性检查后合并，并重映射 Session 和定时 Planner 的 provider 引用。
- **HTTP 破坏性变化。** Provider 的 `protocols/base_url/内嵌 models` 改为 `vendor_type/endpoints` 和独立 `/api/models`；Profile 写入要求 `model_id`，不再接 `provider_id` 加模型字符串；读取返回结构化 `model`。`/api/registry` 返回已保存模型和 vendor 类型。
- **显式选择及写保护。** 空目录不能再接受任意模型名；模型的 provider/name/protocol 和 provider vendor 身份不可变。被引用的模型、endpoint、provider 不能删除，不兼容更新被拒绝。Vendor 建议仅用于创建，不覆盖保存值；endpoint 拒绝畸形 URL、内嵌凭据和 fragment。
- **配置 v3。** 导出 `looper-config/v3`，包含 endpoint、独立 model 和 Profile 复合模型引用；v2/v1 经旧格式转换器继续导入。内置 provider 下的用户模型保留。无效或歧义条目给出 skip 诊断；apply 在服务端重算计划。旧 Profile 的 `system_prompt_mode` 忽略并提示，v3 拒绝该字段。
- **Manager 工具。** 新增 `looper_models` 列表、创建、更新、删除未使用模型，删除需确认；`looper_providers` 保留账户/endpoint 注册和更新；`looper_agent_profiles` 接模型 ID 或完整 provider/name/protocol 引用。凭据只在 dashboard 输入；审计遮蔽覆盖环境条目数组中的凭据值。
- **Dashboard。** LLM Providers 管理账户、endpoint 和模型；Agent Profiles 选择兼容模型及运行时 effort。角色、项目、任务、调度显示可区分的 Profile 身份，价格来源、兼容性及导入诊断更明确，registry 刷新由使用方共享。内联创建 Profile 只注册，不自动改变当前选择；跳过条目与完整成功分开显示。
- **计价和会话。** 精确区分大小写的价格匹配先于归一化和内置 fallback，并限定所选 provider/protocol；Claude 订阅别名保留查价语义。Null 回退、零明确免费、未知仍未知。每次运行冻结价格，计费与预算检查共用并记录模型身份和价格来源；历史费用不重写。模型、价格或运行时选项变化后，常驻进程在后续回合重启以刷新绑定。
- **数据库兼容与已知问题。** Schema 记录 version 3，拒绝不支持的新版本；旧二进制只能打开独立恢复库。Docker 内 dump 且缺少本地 restore 工具时停止升级，处理方式见上方已知问题。

### 模型可见变化

- Manager 指令说明账户、精确模型引用及 Profile 配方，引导在 dashboard 输入凭据，并把模型纳入现有“用户本回合请求才写入”政策。
- Manager 工具 schema 与结果暴露模型层及兼容性。Profile custom prompt、角色/任务 append-or-replace 语义保持在原有层；Prompt Preview 显示模式来源，不读取另一个被选 Profile 的凭据。

Dashboard 更新账户/模型/Profile 设置、共享选择器、摘要、Prompt Preview 来源及 v3 导入导出。Telegram/Lark 通过同一 Manager 指令和工具获得模型管理，无渠道专属命令或传输变更。CLI `looper serve` 执行有保护的启动迁移；现有导入导出命令使用 v3、接受旧文件，help 同步更新。Eval 注册按 provider → model → profile，保留旧 spec 转换并增加模型管理对话。

**验证：**一次性安装核对格式、endpoint、精确模型引用和内置 provider 下用户模型的保留；检查 skip 和缺少凭据诊断，审核后 apply，再导出读回。部分导入不等于完整成功；apply 在服务端重算计划。旧 Profile `system_prompt_mode` 忽略并提示，v3 拒绝。

**停用 / 回退：**取消预览即可不写入；不支持 v3→v2 导出。导入不是数据库回滚，退回 v2.12.5 需按上方步骤恢复独立完整备份，并决定如何处理后续写入。

**权限边界：**预览只读；`--apply` 或 dashboard apply 使用既有事务及校验规则写入。保留凭据打码及占位符语义，导出文件私密存放，缺失凭据在 dashboard 填写；配置导出不是完整备份。

**文档：**[配置迁移](https://github.com/foolzzz/looper/blob/main/docs/architecture/agent-system.md#moving-the-configuration-export-and-import)、[v3 格式与兼容](https://github.com/foolzzz/looper/blob/main/docs/architecture/rfcs/llm-models-v0.zh-CN.md)、[实现](https://github.com/foolzzz/looper/pull/258)。

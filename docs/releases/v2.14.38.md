# Looper v2.14.38

This is the patch release v2.14.38, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.37: Telegram messages sent while the service is stopped for a long upgrade are now delivered instead of dropped as stale ([#975](https://github.com/foolzzz/looper/pull/975)).

## Release Decision

**Who should upgrade:** Anyone who runs v2.14.37 or earlier with a Telegram channel and restarts the service for an upgrade that takes longer than ten minutes (for example a FULL `looper service upgrade` with git, uv and npm steps).

**What this release solves:** Since v2.14.36 Telegram updates are saved and replayed across a restart, and an update older than `backlog_max_age_seconds` (default 600) is ignored as stale. A message sent right after the service stopped could be older than that when the service came back, and was dropped. [#975](https://github.com/foolzzz/looper/pull/975) saves when polling stopped, and a message sent from that moment until polling resumed is no longer subject to the age cap. It also updates a database test that still asserted the old `drop_pending_updates=True` behavior (issue #974).

**Breaking changes:** No. No API or configuration is removed or changed, and there is no new migration or setting.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#975](https://github.com/foolzzz/looper/pull/975); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.38
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.37 upgrades directly. This release adds no migration and no new setting. Each Telegram bot's local inbox database gains one small table (`polling`) the first time the new version opens it; the table is created in place and an older version ignores it.

## Behavior changes

- **Stop boundary is saved ([#975](https://github.com/foolzzz/looper/pull/975)).** When the service receives SIGINT or SIGTERM, each channel adapter's new `prepare_stop` hook runs before the shutdown starts, so it cannot be blocked by an agent or channel drain. The Telegram adapter records the current time as the polling stop time in its inbox database, only if polling is running. A repeated shutdown or a failed recovery does not move the saved time later, and a failure to save is logged as a warning and does not stop the shutdown. `stop()` calls the same hook, so a stop without a signal records it too.
- **Messages sent while stopped bypass the age cap ([#975](https://github.com/foolzzz/looper/pull/975)).** After the restart, a message whose send time is at or after the saved stop time and before the time polling resumed is processed even when it is older than `backlog_max_age_seconds`. Older messages are still ignored with the existing "stale Telegram update" warning, and `update_id` deduplication is unchanged. An unclean stop (a crash or kill with no signal) leaves no stop time, so the age cap applies as before.
- **Polling responses are saved before acknowledgement ([#975](https://github.com/foolzzz/looper/pull/975)).** The adapter's polling transport stores each successful `getUpdates` response in the inbox database before python-telegram-bot sees it, and keeps its network retry loop. After a response with fewer than 100 updates, outside a shutdown, the old stop time is deleted; a full page keeps it because older updates may still be waiting at Telegram, and so does the final response during a shutdown. If the adapter fails to start after the stop time is read, the stored time remains.
- **Model-visible changes:** None. No prompt, skill or tool description changes. The other changes in the pull request are a note in a Chinese planning document and the tests.

## 中文摘要

本版本是 patch release v2.14.38（热修线，每个合并的改动立即发布）。自 v2.14.37 以来只合并了一项改动：服务因长时间升级停止期间发送的 Telegram 消息现在会被送达，而不是被当作过期消息丢弃（[#975](https://github.com/foolzzz/looper/pull/975)）。

### 升级决策

**谁需要升级：**运行 v2.14.37 或更早版本、使用 Telegram 渠道，并且升级重启耗时超过十分钟的人（例如包含 git、uv 和 npm 步骤的 FULL `looper service upgrade`）。

**解决了什么：**自 v2.14.36 起 Telegram 更新在重启后会被保存并重放，早于 `backlog_max_age_seconds`（默认 600）的更新会被当作过期忽略。服务刚停止后发送的消息，在服务恢复时可能已超过该时长而被丢弃。[#975](https://github.com/foolzzz/looper/pull/975) 保存轮询停止的时间，从该时刻到轮询恢复期间发送的消息不再受年龄上限限制。同时更新了一个仍断言旧的 `drop_pending_updates=True` 行为的数据库测试（issue #974）。

**是否有破坏性变更：**否。不移除或更改任何 API 或配置，也没有新的迁移或设置。

**如何验证：**运行 `looper --version` 核对版本为 2.14.38。

**贡献者：**维护者 @foolzzz 提交 [#975](https://github.com/foolzzz/looper/pull/975)；本版本无社区贡献。

```bash
looper --version   # looper 2.14.38
```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.37 上的安装可直接升级。本版本没有新迁移，也没有新设置。每个 Telegram 机器人的本地 inbox 数据库在新版本首次打开时会多出一张小表（`polling`），原地创建，旧版本会忽略它。

### 行为变化与入口

- **保存停止边界（[#975](https://github.com/foolzzz/looper/pull/975)）。**服务收到 SIGINT 或 SIGTERM 时，每个渠道适配器新增的 `prepare_stop` 钩子会在关闭流程开始前运行，不会被 agent 或渠道的排空阻塞。Telegram 适配器仅在轮询运行时，把当前时间作为轮询停止时间写入其 inbox 数据库。重复关闭或失败的恢复不会把该时间推后；保存失败只记录警告，不会中止关闭。`stop()` 也调用同一钩子，所以不经信号的停止同样会记录。
- **停止期间发送的消息不受年龄上限限制（[#975](https://github.com/foolzzz/looper/pull/975)）。**重启后，发送时间不早于已保存停止时间、且早于轮询恢复时间的消息，即使超过 `backlog_max_age_seconds` 也会被处理。更早的消息仍按原有的“stale Telegram update”警告忽略，`update_id` 去重不变。非正常停止（崩溃或无信号的强杀）不会留下停止时间，此时年龄上限照旧生效。
- **轮询响应先保存再确认（[#975](https://github.com/foolzzz/looper/pull/975)）。**适配器的轮询传输层在 python-telegram-bot 看到响应之前，先把每个成功的 `getUpdates` 响应写入 inbox 数据库，并保留其网络重试循环。在非关闭期间，响应少于 100 条更新时删除旧的停止时间；满页（100 条）时保留它，因为 Telegram 上可能还有更早的更新，关闭期间的最后一次响应同样保留。如果适配器在读取停止时间之后启动失败，已存的时间会保留。
- **面向模型的变化：**无。提示词、技能和工具描述均不变。该拉取请求的其他改动是一份中文规划文档中的一条记录和测试。

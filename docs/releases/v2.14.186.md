# Looper v2.14.186

This is the patch release v2.14.186, a hotfix line in which each merged change ships at once. It documents one change: [#1337](https://github.com/foolzzz/looper/pull/1337) (dashboard polling hygiene).

## Release Decision

**Who should upgrade:** Operators who keep the Looper dashboard open and want fewer redundant API reads from it (Dashboard, Tasks, Gates and Chat pages).

**What this release solves:** [#1337](https://github.com/foolzzz/looper/pull/1337), part of the API latency series (goal: every API operation under 2 s), reduces the dashboard's background reads. Polling waits for the previous read, pauses on a hidden tab, and is aborted when a page is left. The waiting-gates count is shared instead of read per component, and the needs-you list is no longer re-read on every overview poll.

**Breaking changes:** No. The Telegram and Lark channel protocols and the CLI are unchanged, no server code changed and there is no database change. The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.14.186
```

**Contributors:** Maintainer @foolzzz authored [#1337](https://github.com/foolzzz/looper/pull/1337); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.185 upgrades directly. There is no database change.

## Behavior changes

Read in the diff of [#1337](https://github.com/foolzzz/looper/pull/1337) (dashboard code under `web/src/` and one Python test). The PR description calls the behavior changes intended (a maintainer decision). All are dashboard behavior; the shared helper `startPolling` (`web/src/lib/polling.ts`) already existed and is not changed.

- **Polite polling on more pages.** The Tasks list (3 s), Gates page, Chat (targets, conversations and opened conversation), the Dashboard overview (5 s), the project list and the waiting-gates count now use `startPolling`: the next read starts the interval after the previous one settled (never two at a time), nothing runs while the tab is hidden, a read runs again when the tab becomes visible, and leaving the page aborts the read in flight. Before, these used fixed timers.
- **Tasks list.** Polling is in its own effect and stops while a task is open (`selectedTaskId`); it restarts when the list is shown again.
- **Waiting gates shared.** `useWaitingGates` now reads a value from a new `WaitingGatesProvider` mounted once in `App.tsx`; the provider polls every 10 s and on the gates-changed event. The Dashboard receives it as `waitingGates`.
- **Needs-you list on the Dashboard** (`dashboard-gates.tsx`). A full read of the first 10 needs-you tasks runs only when the needs-you count, the waiting-gate count or the manual refresh changes, or at least every 30 s while the gate count is unknown and needs-you is above 0. Overview polls otherwise re-read only for replies just sent, which keep following their Planner. A failed full read is retried on overview polls until it succeeds.
- **Manager session profile** (`manager-session-profile.tsx`). It reads only while the chat page is the active page (new `active` prop passed from `App.tsx` through `ChatPage`) and the tab is not hidden. The focus and visibility-change refresh is skipped while a read is pending or when the last read was under 30 s ago.
- **Tests.** One Python test change: `tests/test_db_backup.py` keeps its serve port reserved (reusable wildcard bind) through startup instead of releasing it first, and no longer uses `free_port`. The rest are web tests for the changes above (`tasks`, `dashboard`, `gates`, `manager-session-profile`, `chat-manager-picker`, `url-state`, `App`, `sidebar`).
- **Model-visible changes:** No. No prompt, tool description or tool schema changed, no server or agent code changed.

### 升级决策

**谁需要升级：**长期打开 Looper 仪表盘、希望减少其冗余 API 读取的运维人员（仪表盘、任务、Gate 和聊天页面）。

**解决了什么：**[#1337](https://github.com/foolzzz/looper/pull/1337) 属于 API 延迟系列（目标：每个 API 操作低于 2 秒），减少仪表盘的后台读取。轮询等待上一次读取结束、标签页隐藏时暂停、离开页面时中止。等待中的 Gate 数量改为共享读取，需要你处理的任务列表不再在每次概览轮询时重读。

**是否有破坏性变更：**无。Telegram 与 Lark 渠道协议和 CLI 不变，没有服务端代码变更，也没有数据库变更。桥接边界不变：早于 v2.13.165 的安装须先升级到 v2.13.165。

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.185 上的安装可直接升级。没有数据库变更。

### 行为变化与入口

以下在 [#1337](https://github.com/foolzzz/looper/pull/1337) 的差异中可见（`web/src/` 下的仪表盘代码和一个 Python 测试）。PR 描述称这些行为变化是有意的（维护者决定）。全部为仪表盘行为；共享的 `startPolling`（`web/src/lib/polling.ts`）早已存在，未改动。

- **更多页面使用礼貌轮询。**任务列表（3 秒）、Gate 页、聊天（目标、会话和打开的会话）、仪表盘概览（5 秒）、项目列表和等待 Gate 数量现在使用 `startPolling`：上一次读取结束后才开始计时，不会并发；标签页隐藏时不运行，重新可见时立即读取；离开页面会中止进行中的读取。此前使用固定定时器。
- **任务列表。**轮询放在独立的 effect 中，打开某个任务（`selectedTaskId`）时停止，回到列表时重新开始。
- **等待 Gate 数量共享。**`useWaitingGates` 现在从 `App.tsx` 中挂载一次的 `WaitingGatesProvider` 取值；该 provider 每 10 秒及在 Gate 变更事件时读取。仪表盘以 `waitingGates` 接收。
- **仪表盘需要你处理的列表**（`dashboard-gates.tsx`）。仅当需要你处理的数量、等待 Gate 数量或手动刷新发生变化，或在 Gate 数量未知且需要你处理大于 0 时至少每 30 秒，才完整读取前 10 个任务。其余概览轮询只重读刚发送的回复（它们继续跟随其 Planner）。完整读取失败后，会在概览轮询中重试直到成功。
- **Manager 会话配置**（`manager-session-profile.tsx`）。仅当聊天页为当前页（新增 `active` 属性，经 `App.tsx` 和 `ChatPage` 传入）且标签页未隐藏时才读取。读取进行中或距上次读取不足 30 秒时，跳过聚焦与可见性变化触发的刷新。
- **测试。**一处 Python 测试变更：`tests/test_db_backup.py` 在启动期间保持端口占用（可复用的通配绑定），不再先释放，也不再使用 `free_port`。其余为上述改动的 web 测试（`tasks`、`dashboard`、`gates`、`manager-session-profile`、`chat-manager-picker`、`url-state`、`App`、`sidebar`）。
- **面向模型的变化：**无。提示词、工具描述和工具 schema 均未改变，也没有服务端或 agent 代码变更。

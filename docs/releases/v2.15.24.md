# Looper v2.15.24

This release documents the changes merged since v2.15.23. The Manager's session state now lives in one `ManagerSession` slot ([#1495](https://github.com/foolzzz/looper/pull/1495)); that is a pure refactor, and with the one session it has today every behavior stays the same. The delivery guard's policy can be stored ([#1496](https://github.com/foolzzz/looper/pull/1496), `manager.delivery_guard.enabled`, default off) and Claude Code declares `mid_turn_input`; nothing injects mid-turn input, and turning the setting on changes no reply. One read-only summary of what waits for the operator has a dashboard page and `/todo` ([#1485](https://github.com/foolzzz/looper/pull/1485), `attention.enabled`, default off). Each operator-only Manager tool refuses in its own words ([#1507](https://github.com/foolzzz/looper/pull/1507)); the vault tools' refusal text changes. A window whose prompt a hook blocks, or whose reply cannot be read after one reformat, is skipped with a typed `skip_reason` instead of stalling ([#1482](https://github.com/foolzzz/looper/pull/1482)); that is a default change for a running subscription, and a push subscription never pushes the echoed prompt. Five pull requests merged after these notes were frozen are part of the same tag. The Manager's per-turn session budget can be stored ([#1506](https://github.com/foolzzz/looper/pull/1506), `manager.turn_budget_usd`, default off); only the operator can read or set it, and storing it changes no turn. Outbound reviews, advisor rounds and leads checks share one tool-less typed model call ([#1503](https://github.com/foolzzz/looper/pull/1503)); prompts and results stay as they were. The Manager reads its session id and its binding file from the session a turn runs on ([#1512](https://github.com/foolzzz/looper/pull/1512)); with only `main`, every behavior stays the same. Every Looper tool and `/api/v1` operation declares where it reaches ([#1498](https://github.com/foolzzz/looper/pull/1498)); nothing reads those levels yet, and the OpenAPI document is unchanged. Approved assistant-experience eval baselines are recorded ([#1510](https://github.com/foolzzz/looper/pull/1510)); they change no runtime.

## Release Decision

**Who should upgrade:** Anyone running a leads, intents or push subscription, whose installation still has an unfinished online index step, or who will turn on the needs-you summary or the delivery guard. An installation that turns neither on still applies the additive migrations at startup. With those switches left off, the Manager's prompts and tool lists stay as in v2.15.23, apart from the vault tools' refusal text on a turn that is not the operator's, and apart from a subscription window that a prompt hook blocks or whose reply cannot be read, both described under Behavior changes. `web/` changed, so the dashboard bundle is rebuilt by the release workflow as usual. Setting the session budget is a further operator-only switch, off until set, and setting it changes no turn. The shared tool-less call, the session-slot reads, the declared action levels and the assistant-experience baselines change no prompt, tool list, reply or channel.

**What this release solves:** A window a prompt hook blocks, or whose reply cannot be read after one more ask, no longer stops every later window, and a push subscription does not push the echoed prompt. The operator can read, in one place, what is already waiting, from the dashboard and from `/todo`, while that summary stays off. The delivery guard's policy can be stored, still off, and still unwired. A refused vault read names the vault, not message leads. The Manager's session state lives in one slot, with the same behavior. The session budget's rules and setting can be stored, still off and still unwired. Outbound reviews, advisor rounds and leads checks share one typed tool-less call, with the same results. The session id and the binding file are read from the one session slot, with the same bytes. Where each Looper tool and v1 operation reaches is declared, and nothing consults those levels yet. Later assistant-experience runs can compare against the approved baselines.

**Breaking changes:** No. No existing API drops a field that a caller must send. A running leads, intents or push subscription can skip a window and move its cursor, and can send `skip_alert` instead of stalling; a refused `looper_vault_search` or `looper_vault_read` answers with the vault's own sentence; an online index step that has not finished keeps an existing index only when it is valid and has the same definition. All three are under Behavior changes. There are additive PostgreSQL migrations (see Upgrading). The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older. `session_budget.get` and `session_budget.update` are new operations. Declared action levels are not part of the OpenAPI document.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.15.24
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.15.23 upgrades directly. Restart the service after upgrading, as for every release. `web/` changed, so the release workflow rebuilds the dashboard bundle from `web/` into the wheel, as usual. This pull request does not commit that bundle.

This release has additive PostgreSQL migrations, applied once at startup. They write no lead, intent, subscription-run or delivery row. A database that has not yet finished an earlier online step still runs that step. The shared online-index step now keeps an existing index only when it is valid and has the same definition (see Behavior changes). The new online steps run after the schema transaction commits. `run_skips` and `mid_turn_input` validate `NOT VALID` constraints. `uncertain_deliveries` builds three partial indexes concurrently and validates no constraint.

- `mid_turn_input` ([#1496](https://github.com/foolzzz/looper/pull/1496)): replaces `agent_runtimes_capabilities_check` so the allowed capabilities also include `mid_turn_input` (the list still includes `headless_compaction` and every capability the previous check allowed). The new check is added `NOT VALID`. No runtime row is rewritten: the check is a subset (`<@`), so an array that does not yet contain `mid_turn_input` still passes. The online step `mid_turn_input_online` validates `agent_runtimes_capabilities_check`. A fresh database already has `mid_turn_input` in the column check from `schema.sql` and does not run this replacement.
- `uncertain_deliveries` ([#1485](https://github.com/foolzzz/looper/pull/1485)): records the migration and builds no index inside the schema transaction. The online step `uncertain_deliveries_online` builds, concurrently, `idx_subscription_deliveries_uncertain` on `subscription_deliveries (updated_at)` where `state` is `uncertain`, `idx_intent_posts_uncertain` on `intent_posts (updated_at)` where `state` is `uncertain`, and `idx_manager_events_uncertain` on `manager_events (created_at)` where `delivery` is `uncertain`. A fresh database creates those three indexes from `schema.sql` and does not record a separate index step. No row is rewritten.
- `run_skips` ([#1482](https://github.com/foolzzz/looper/pull/1482)): adds nullable `subscription_runs.skip_reason` and nullable `subscriptions.skip_alert_at`. Columns come without a check. Every constraint is added `NOT VALID`: `schedule_notifications_kind_check` (the previous kinds, including `check_alert` and `check_recovered`, plus `skip_alert` and `skip_recovered`), `subscription_runs_outcome_check` (`pending`, `delivering`, `delivered`, `uncertain`, `quiet`, `dashboard_only`, `output_invalid`, `failed`, `extracted` or `skipped`), `subscription_runs_skip_reason_check` (`blocked_by_hook` or `invalid_reply`), and `subscription_runs_skipped` (`outcome` is `skipped` exactly when `skip_reason` is not null). The online step `run_skips_online` validates those four constraints. A fresh database validates them in its own transaction and still records only its baseline. No row is rewritten.

[#1495](https://github.com/foolzzz/looper/pull/1495) and [#1507](https://github.com/foolzzz/looper/pull/1507) add no schema. [#1496](https://github.com/foolzzz/looper/pull/1496) adds no table; the delivery-guard switch is a system-settings row, written only when an operator sets it. [#1506](https://github.com/foolzzz/looper/pull/1506) adds no table; `manager.turn_budget_usd` is a system-settings row, written only when an operator sets it. [#1510](https://github.com/foolzzz/looper/pull/1510), [#1503](https://github.com/foolzzz/looper/pull/1503), [#1512](https://github.com/foolzzz/looper/pull/1512) and [#1498](https://github.com/foolzzz/looper/pull/1498) add no schema.

## Behavior changes

### Manager session slot, no behavior change ([#1495](https://github.com/foolzzz/looper/pull/1495))

The fields that belonged to the Manager's one conversation now live on `ManagerSession`. The agent holds a single slot, `main`. Nothing sets another session. Prompts, tool lists, command lines, records and channel behavior are unchanged. The one internal difference is that `deletion_blocked` always returns a bool; its only caller uses it as a condition.

### Delivery guard, off ([#1496](https://github.com/foolzzz/looper/pull/1496))

- **`manager.delivery_guard.enabled` defaults off.** No row, or any value other than the string `true`, leaves it off. Until startup has loaded settings, it is off. There is no dashboard switch. `chat_settings.get` and `chat_settings.update` do not carry the field, and their payloads stay as in v2.15.23. Manager tools do not carry it.
- **Only the operator can read or set it.** `POST /api/v1/delivery_guard/get` and `POST /api/v1/delivery_guard/update` are operator-only. The update is high risk: its impact preview names `manager.delivery_guard.enabled` and the value that would be stored, and says that Manager wiring is separate and replies are unchanged. The operator's call applies at once. `true` stores `true`. `false` stores `false`. `null` deletes the row and restores the disabled default. An API client token gets 403, and nothing is stored.
- **Turning it on changes no Manager behavior.** The policy (delivery debt, at most two hidden follow-ups, at most two same-turn reminders after six consecutive top-level tool calls, and the typed ending of a cap, exit, missing tools or a refused token) is not called from a turn. Prompts, tool lists, command lines, replies, records and channel calls stay as they are with the setting absent, including when the stored value is `true`.
- **`mid_turn_input` is declared, not used.** Only Claude Code declares it. It was verified for the non-hosted ResidentClaude stream-json session: queued input can join the running turn after the current tool returns. Keeper-hosted and runner-hosted sessions were not verified. This release does not inject that input. Wiring, when it comes, has to check the session kind as well as the capability.

### Needs you, off ([#1485](https://github.com/foolzzz/looper/pull/1485))

- **`attention.enabled` defaults off.** No row, or any value other than `true`, leaves it off. There is no dashboard switch and no HTTP write of the setting. While it is off, no prompt, tool list or command line mentions it. `/todo` reaches the Manager's model as an ordinary message, as in v2.15.23. Telegram drops `/todo` as an unknown command, as before; if the setting cannot be read, Telegram drops it too. `POST /api/v1/attention/summary` answers `conflict` (HTTP 409). The sidebar makes one extra read of that operation when it mounts, and does not list the page while the answer is 409.
- **While it is on,** the summary is read-only and calls no model. Nothing is stored. The sections, in order, are `gates` (user gates with `waiting_on=user`), `confirmations` (each Manager's high-risk operation still waiting, read from memory, so a restart drops them), `schedules` (failing schedules; `db.schedules.overview` returns the same list, and the query now lives in `failing()`), `logins` (a Claude Code CLI or login, or a runtime login an Agent Profile uses, failing in the checks `system/status` reads; the HTTP server registers that reader while it runs), `intents` (pending, only while intents are on), `ledger` (the ledger's own open items that wait for the user: a to-do, an unconfirmed relayed decision, anything overdue; only while the ledger is on; items that only point at a gate or a confirmation are left out) and `deliveries` (`uncertain` subscription pushes, intent messages and task-end messages of the last 72 hours). A feature that is off leaves its section out. A section is `ok`, `error` (the source could not be read, with the reason, and is never shown as empty) or `unknown` (this caller cannot read it). Each section lists at most 20 items and counts them all. The page and `/todo` say that nothing waits only when every section was read and is empty.
- **Dashboard.** `#todo`, "Needs you", under Dashboard in the sidebar, listed only while the summary answers. One card per section that has items or could not be read. Empty sections fold into one line. Failing logins that were read stay on the startup-check banner every page already shows; a logins section that could not be read still shows. A confirmation asked in the dashboard chat links to that conversation.
- **`/todo`.** Answered by code, next to `/new` and `/gates`, and also Telegram's `/todo@bot`, only while the setting is on and only in the operator's own turn. A group, another sender or an API client gets `「需要你处理」只给你本人看：在你和机器人的私聊或控制台里发 /todo。` The reply is stored in the chat history. Text other people wrote (gate topics, intent and ledger titles, task, project and schedule names) is passed through `attention._plain`: control and format characters dropped, line breaks merged, capped at 120 characters. The summary never goes to the model. The API and the dashboard page do not reach the model. Telegram registers `/todo` and forwards it only while the setting is on. Lark has no separate command registration: a Lark message that is the command reaches the same Manager answer.

### Online indexes, kept only when valid and the same ([#1485](https://github.com/foolzzz/looper/pull/1485))

This changes the shared online-index step for every migration that builds an index after the schema transaction commits, including an earlier step that has not finished (`idx_llm_records_parent`, `idx_schedule_notifications_manager_event`) and the three new `uncertain` indexes.

An existing index is kept only when it is valid and PostgreSQL's text of it (`pg_get_indexdef`, from `USING` on, and whether it is unique) equals the index the step's definition builds. The definition is built on an empty `LIKE` copy of the table, in a transaction that is rolled back, so nothing is scanned and writers are not blocked. An INVALID index left by a stopped build, or a valid index with a different definition under the same name, is dropped and built again (`DROP INDEX CONCURRENTLY IF EXISTS`, then `CREATE INDEX CONCURRENTLY IF NOT EXISTS`). A valid index with the same definition is left in place.

### Operator-only tool refusals ([#1507](https://github.com/foolzzz/looper/pull/1507))

This changes the `forbidden` text a model reads when a tool that only the operator's own turns may run is called from another turn (a group, another sender, an API client, or a turn the model runs on its own). Which turns may run the tools, their listing, their descriptions, the system prompt and the audit trail are unchanged. These tools are not listed on such a turn, so the text is reached only when a call is made anyway.

| Tool | Before | After |
|---|---|---|
| `looper_leads_search` | `message leads are searched only in the user's own direct chat or on the dashboard` | unchanged |
| `looper_vault_search` | `message leads are searched only in the user's own direct chat or on the dashboard` | `the user's knowledge vault is searched and read only in their own direct chat or on the dashboard` |
| `looper_vault_read` | `message leads are searched only in the user's own direct chat or on the dashboard` | `the user's knowledge vault is searched and read only in their own direct chat or on the dashboard` |

A new operator-only tool cannot be constructed without its own non-blank refusal. No schema change. Dashboard, Lark and Telegram see the new sentence only as the tool's answer. The CLI is unaffected.

### Skipped subscription windows, the default ([#1482](https://github.com/foolzzz/looper/pull/1482))

This changes default behavior for a running leads, intents or push subscription. There is no new switch.

- A prompt hook that blocks the processor's prompt is no longer returned as the reply. The run is recorded with the typed block only, so the reply, the output and the record events do not keep the echoed prompt. The window is skipped at once, `skip_reason` `blocked_by_hook`. The run is `completed`, stores nothing, and the cursor moves past the window. A push subscription pushes nothing for that window. A consult whose prompt a hook blocks fails with reason `contract`. Before, that consult was dropped as `budget`, because its cost was unknown.
- An unreadable leads or intents reply is asked once more, with `extraction.REFORMAT_REMINDER` added, within what is left of the run's cap and deadline. The cost of every ask counts. A reply that wraps the one object of the right kind in prose or code fences is now read. Two different such objects, or a reply with more than 200 places a JSON object could start, stay unreadable. Still unreadable after the second ask, the window is skipped, `skip_reason` `invalid_reply`, the run is `completed`, and the cursor moves. If the cap or the deadline is used up before that second ask, the run fails as `budget` or `timeout` and the window is kept.
- Before the cursor moves, the run checks the confirmation again under the schedule's lock, as storing does. If the scope was widened or the confirmation revoked, the run is `cancelled` and the cursor stays. Every other processor failure still fails the run and leaves the cursor, including a backfill: a skipped window is recorded and the backfill goes on, and any other processor failure still stops the backfill.
- Skipped runs count as `completed`, so they do not raise the failure alert. Once as many completed runs in a row as that alert waits for (3 by default) were skipped, one `skip_alert` is sent per streak (`subscriptions.skip_alert_at`). It names the last reason and contains no message text. The next completed run that used its window sends `skip_recovered`. A run that did not complete neither ends the streak nor adds to it.
- The dashboard run history labels an `extracted` run, which had no label, as Extracted, and a `skipped` run as Skipped with the reason (a prompt hook blocked it, or its reply could not be read, twice). `looper msgflow leads-backfill` reports the skipped windows. Telegram and Lark send nothing new for a skipped push, and an extraction run still sends nothing.


### Session budget, off ([#1506](https://github.com/foolzzz/looper/pull/1506))

- **`manager.turn_budget_usd` defaults off.** No row leaves it off. A stored value that is not a positive finite number also leaves it off, and `session_budget.get` says why in `problem`. There is no dashboard switch. `chat_settings.get` and `chat_settings.update` do not carry the field. No Manager tool lists it, and the default prompt does not mention it.
- **Only the operator can read or set it.** `POST /api/v1/session_budget/get` and `POST /api/v1/session_budget/update` are operator-only. The update is high risk: its impact preview names `manager.turn_budget_usd` and the value that would be stored, and says that Manager wiring is separate and turns are unchanged. The operator's call applies at once. A positive finite number stores that number. `null` deletes the row and restores off. A field left out keeps its value. Zero, a negative number, a boolean, a non-number, an empty body and an unknown field are refused, and nothing is stored. An API client token gets 403, and nothing is stored.
- **`session_budget.get` returns** `turn_budget_usd` (null while off), `recommended_usd` (4.00) and `problem`.
- **The rules are pure functions, and no turn calls them.** `decide` keeps the session when the budget is unset or the turn's context is unknown. Over `scheduler.session_context_max_tokens` it compacts when the runtime can compact a resident session headlessly (`headless_compaction`), and otherwise rotates. At least half that threshold, a known turn cost over half the budget rotates. Unlike a schedule's Planner, an unknown turn cost skips the cost rule; context alone can still compact or rotate. `after_compaction` rotates when the `/compact` failed, had no `compact_boundary`, or left the context over the threshold; a boundary with no reported size counts as compacted. `turn_cap` is off with no budget, capped when the turn's model has a price, and `no_price` otherwise. `over_cap_reply` is the fixed reply a turn stopped at the budget would get. Storing the budget changes no prompt, tool list, command line, reply, record or channel call, including when the stored value is a positive number.

### One tool-less typed model call, no behavior change ([#1503](https://github.com/foolzzz/looper/pull/1503))

`model_call.call` is the one entry outbound reviews, advisor rounds (including their judge) and leads checks use for a tool-less run with a typed reply. It returns `CallOk` with the parsed value, or `CallFailed` with a `CallFailure` (`timeout`, `parse`, `runtime`, `rate_limited`, `unavailable`, `budget` or `refused`). The run's record, cost, latency and model stay on the result, and a parse failure keeps the parser's exception. An execution failure is not parsed. The only backend is `SubscriptionBackend`, which calls the existing `spawn.run_child` and `processor.run` paths and keeps their launch, deadline, spend and record rules. There is no direct-API backend and no new setting. A subscription's processor run and an extraction run do not go through it. Prompts, role prompts, launch flags, rows, outbound decisions, leads counts, advisor states, retry rules and cost booking are unchanged. Advisor spend is still booked before parsing. Dashboard, Telegram, Lark and the CLI are unchanged.

### Session id and binding file, read from the session, no behavior change ([#1512](https://github.com/foolzzz/looper/pull/1512))

The session id and the runtime type are read from the session a turn runs on (`ManagerSession.session_id` and `session_runtime`). `_prepare_turn` reads that session once, after the commands and gate replies Code answers itself, and passes it on `Prepared.session`. Other reads start from `_session_now` (the session this context set, otherwise `main`). The forwarding properties `_session_id` and `_session_runtime` are gone. The binding file is `ManagerOps.turn_file_for(session_key)`: `main` returns the turn file the fleet already gives that session; any other key raises `ValueError`. `publish_binding`, `server_config` and `library_with_server` take `session_key` and default to `main`. The Manager passes the key of the session it runs on. Only `main` exists, so every read is still main's. Main's binding file, its MCP entry and its writes are the same file and the same bytes. Prompts, tool lists, command lines, records and channel behavior are unchanged.

### Where a tool or operation reaches, declared and unread ([#1498](https://github.com/foolzzz/looper/pull/1498))

`ActionLevel` is `inside`, `operator`, `origin`, `machine`, `external` or `unknown`. Only `external` and `unknown` are the levels a review would look at. Every Looper tool declares its level in `ops/levels.py` (`TOOL_LEVELS`), by the tool's exact name, and not as a field on `Tool`: the upgrade probe reads `Tool`'s declaration and the room's and vault's constructors by their exact shape. A read action is `inside`. A tool with no entry is `unknown`. A call with several effects takes the highest. `looper_projects` `move` is `machine`. `looper_settings` `gateway` and `knowledge_vault` are `machine`. `looper_providers`, `looper_catalog` and `looper_vault_write` are `machine`. `looper_task_gate_reply` and `looper_task_concurrency` are `origin`. `looper_gates` `reply` and `end` are `origin`. `looper_schedules` is `machine` when the schedule runs a command, otherwise the notify target's level, and the higher of the two: `operator` for the dashboard or the operator's own direct chat, `origin` for the asking turn's chat, `external` for another chat, and `unknown` when the target names no chat. A stored schedule that cannot be read is `unknown`.

Every `/api/v1` operation has `level`, default `inside`, or `level_of` when the arguments decide it. `manager_chat_bindings.put` is `external`. `schedule_admin.create`, `update`, `run` and `confirm_target` follow that same schedule rule (an API client's call has no chat of its own, so another chat is `external`). `intent_bindings.put` and `channel_chats.set_policy` are `inside`: the first maps a chat to a project and sends nothing, and the second toggles `bound_chats_only`, whose widened admission stays `chat_routing`'s operator-only refusal. `session_budget.get`, `session_budget.update` and `attention.summary` are `inside`. The levels are not in the OpenAPI document: resetting every level leaves that document byte-identical. No turn and no HTTP handler reads a level. `outbound.review` still has no caller.

### Assistant-experience baselines, data only ([#1510](https://github.com/foolzzz/looper/pull/1510))

`evals/prompt_regression/baselines/assistant-real-sonnet.json` (sonnet, three repetitions) and `evals/prompt_regression/baselines/assistant-real-opus.json` (sonnet, with an opus Manager at effort `xhigh`, two repetitions) are the approved real-mode baselines, schema `looper-assistant-experience/v1`, both recorded at commit `2b77afb1672cda93be6681259623bafa4e290f2d`. Sonnet passed time 60%, identity 20%, crosstalk 73.3% and tone 66.7%, at about $2.12. Opus xhigh passed time 70%, identity 30%, crosstalk 100% and tone 40%, at about $2.94. The low identity scores are confirmations still opened for someone who is not the operator, and the time misses are calendar-week arithmetic. Those are the phase-1 targets, not a regression in this release. No check, prompt, tool list, command line, dashboard, Telegram or Lark behavior changes.

## Optional Capability Activation & Use

### Delivery guard

**Activation:** Off until the system setting `manager.delivery_guard.enabled` is the string `true`. No row, `false`, or any other value, leaves it off. Set it as the operator through `POST /api/v1/delivery_guard/update` with `enabled` true. The call applies at once. There is no dashboard switch. An API client token gets 403. Turning it on stores the row and changes no reply: Manager wiring is not in this release.

**Validation:** With the setting absent, `delivery_guard.get` answers `enabled` false and a Manager turn matches v2.15.23. With it `true`, `delivery_guard.get` answers `enabled` true, and the same turn's prompt, tool list, reply and channel call are unchanged. `chat_settings.get` does not include the field.

**Disable / rollback:** Set `enabled` to false, or to null. False stores `false`. Null deletes the row. The guard is off either way. Nothing was injected into a session that has to be cleared. The capability check on `agent_runtimes` stays. It is not dropped.

**Authority boundary:** Only the operator can read or write the setting. An API client and an agent token get 403, and a refused update writes nothing. The stored value does not grant a tool and does not send a message. `mid_turn_input` is a runtime declaration. This release does not use it to add input to a turn.

### Needs you

**Activation:** Off until the system setting `attention.enabled` is `true`. No row, or any other value, leaves it off. This release has no dashboard switch and no HTTP write of that setting. Set it by inserting the system setting `attention.enabled` with the value `true`. The next `attention.summary`, the next sidebar load and the next `/todo` then use it. Intents appear only while intents are on, and ledger items only while the ledger is on. Set My ID (Settings → Channels, one allowlisted sender) before a direct-chat sender counts as the operator.

**Validation:** With the setting absent, `POST /api/v1/attention/summary` answers 409, the sidebar has no "Needs you", and `/todo` in the dashboard chat reaches the model. With it `true`, the same call returns the sections that apply, `#todo` lists "Needs you" under Dashboard, and `/todo` from the operator is answered by code with that summary. A group, another sender or an API client is refused. An API client that calls the summary gets 403.

**Disable / rollback:** Delete `attention.enabled`, or set it to any value other than `true`. The page leaves the sidebar, `/todo` is an ordinary message again, and Telegram drops the command again. ### 升级决策

**谁需要升级：**正在跑线索、意图或推送订阅的安装，还有没做完的在线索引步骤的安装，以及要打开「需要你处理」或投递守卫的安装。这两个开关都不打开的安装，启动时仍会执行可加的迁移。开关保持关闭时，Manager 的提示词和工具列表与 v2.15.23 相同，除了下面行为变化里的两件事：不是操作者本人的回合若调用了知识库工具，拒绝文案变了；提示词 hook 拦住或回复读不懂的订阅窗口会被跳过。`web/` 有改动，仪表盘包由发布流程照常重新构建。会话预算是另一个只给操作者的开关，设置之前是关的，设置它也不改变回合。共用的不带工具的调用、从会话槽读取、声明的动作级别和助手体验基线，都不改变提示词、工具列表、回复或渠道。

### 行为变化

**Manager 会话槽，没有行为变化（[#1495](https://github.com/foolzzz/looper/pull/1495)）**

属于 Manager 这一次会话的字段现在放在 `ManagerSession` 上。agent 只持有一个槽，`main`。没有别的会话被设上。提示词、工具列表、命令行、记录和渠道行为不变。唯一的内部差别是 `deletion_blocked` 总是返回布尔值；它唯一的调用方把它当条件用。

**投递守卫，默认关闭（[#1496](https://github.com/foolzzz/looper/pull/1496)）**

- **`manager.delivery_guard.enabled` 默认关闭。**没有这一行，或取值不是字符串 `true`，都算关闭。启动还没读完设置之前也是关。没有仪表盘开关。`chat_settings.get` 和 `chat_settings.update` 不带这个字段，它们的载荷与 v2.15.23 相同。Manager 工具也不带它。
- **只有操作者能读或写。**`POST /api/v1/delivery_guard/get` 和 `POST /api/v1/delivery_guard/update` 只给操作者。更新是高风险：影响说明写出 `manager.delivery_guard.enabled` 和将要存的值，并写明 Manager 的接线是分开的、回复不变。操作者的调用立刻生效。`true` 存成 `true`。`false` 存成 `false`。`null` 删掉这一行，恢复默认关闭。API 客户端令牌得到 403，什么都不存。
- **打开也不改变 Manager 的行为。**策略（投递欠账、最多两次隐藏的追问、连续六次顶层工具调用之后最多两次同一回合的提醒，以及花费上限、退出、工具不可用或令牌被拒的有类型结束）没有从回合里调用。提示词、工具列表、命令行、回复、记录和渠道调用与没有这个设置时相同，存成 `true` 时也一样。
- **`mid_turn_input` 已声明，还没有使用。**只有 Claude Code 声明它。核实范围是非托管的 ResidentClaude stream-json 会话：排队的输入可以在当前工具返回之后加入正在跑的回合。keeper 托管和 runner 托管的会话没有核实。本版本不注入这种输入。以后接线时，必须同时检查会话种类和这个能力，不能只看运行时类型。

**需要你处理，默认关闭（[#1485](https://github.com/foolzzz/looper/pull/1485)）**

- **`attention.enabled` 默认关闭。**没有这一行，或取值不是 `true`，都算关闭。没有仪表盘开关，也没有写这个设置的 HTTP。关闭时，提示词、工具列表和命令行都不提它。`/todo` 作为普通消息到达 Manager 的模型，与 v2.15.23 相同。Telegram 仍把 `/todo` 当成未知命令丢掉；这个设置读不出来时也丢掉。`POST /api/v1/attention/summary` 回答 `conflict`（HTTP 409）。侧栏挂载时多读一次这个操作，回答是 409 时不列出这一页。
- **打开之后，**摘要是只读的，不调用模型，什么都不存。各节按顺序是：`gates`（`waiting_on=user` 的用户关卡）、`confirmations`（每个 Manager 还在等的高风险操作，从内存读取，重启就丢掉）、`schedules`（失败的定时任务；`db.schedules.overview` 返回的列表相同，查询挪到 `failing()`）、`logins`（Claude Code 的 CLI 或登录，或某个 Agent Profile 在用的运行时登录，在 `system/status` 所读的检查里失败；HTTP 服务在运行期间登记这个读取）、`intents`（待处理的意图，只在意图打开时）、`ledger`（账本自己的、等用户的未完成条目：待办、还没确认的转述决定、任何过期项；只在账本打开时；只是指向关卡或确认的条目不列在这里）和 `deliveries`（最近 72 小时里 `uncertain` 的订阅推送、意图消息和任务结束消息）。功能关闭时，它的那一节不出现。一节的状态是 `ok`、`error`（来源读不了，带原因，从不显示成空）或 `unknown`（这个调用方读不了）。每一节最多列 20 条，并计数全部。只有每一节都读到了而且是空的，页面和 `/todo` 才说没有需要处理的事。
- **仪表盘。**`#todo`，「Needs you」，在侧栏里 Dashboard 下面，只在摘要有回答时列出。有条目或读不了的每一节一张卡片。空的节收成一行。已经读到的失败登录仍放在每页都有的启动检查条上；登录这一节读不了时仍会显示。在仪表盘会话里问的确认链到那个会话。
- **`/todo`。**由代码回答，紧挨 `/new` 和 `/gates`，也包括 Telegram 的 `/todo@bot`。只在设置打开、并且是操作者本人的回合。群、别人或 API 客户端得到 `「需要你处理」只给你本人看：在你和机器人的私聊或控制台里发 /todo。` 回复记在会话历史里。别人写过的文字（关卡话题、意图和账本标题、任务、项目和定时任务的名字）经过 `attention._plain`：去掉控制和格式字符，合并换行，最多 120 个字符。摘要从不交给模型。API 和仪表盘页也不交给模型。Telegram 登记 `/todo`，只在设置打开时转发。Lark 没有单独的命令登记：一条就是这个命令的 Lark 消息走同一个 Manager 回答。

**在线索引，只在有效且定义相同时保留（[#1485](https://github.com/foolzzz/looper/pull/1485)）**

这改的是共享的在线索引步骤，对每一个在 schema 事务提交之后建索引的迁移都生效，包括还没做完的更早步骤（`idx_llm_records_parent`、`idx_schedule_notifications_manager_event`），以及新的三个 `uncertain` 索引。

已有索引只在它有效，并且 PostgreSQL 对它的文本（`pg_get_indexdef`，从 `USING` 起，以及它是否 UNIQUE）与这一步的定义所建成的索引相同时才保留。定义建在该表的一张空的 `LIKE` 副本上，事务会回滚，所以不扫描数据，也不挡住写入。被中断的构建留下的 INVALID 索引，或同名但定义不同的有效索引，会被丢掉再重建（`DROP INDEX CONCURRENTLY IF EXISTS`，然后 `CREATE INDEX CONCURRENTLY IF NOT EXISTS`）。有效且定义相同的索引留在原地。

**操作者专用工具的拒绝文案（[#1507](https://github.com/foolzzz/looper/pull/1507)）**

|---|---|---|
| `looper_leads_search` | `message leads are searched only in the user's own direct chat or on the dashboard` | 不变 |
| `looper_vault_search` | `message leads are searched only in the user's own direct chat or on the dashboard` | `the user's knowledge vault is searched and read only in their own direct chat or on the dashboard` |

新的、只给一部分回合的工具，没有自己的非空拒绝文案就不能构造。没有 schema 变化。仪表盘、Lark 和 Telegram 只在工具的回答里看见新句子。CLI 不受影响。

**跳过订阅窗口，这是默认（[#1482](https://github.com/foolzzz/looper/pull/1482)）**

这是正在运行的线索、意图或推送订阅的默认行为变化。没有新开关。

- 拦住 processor 提示词的 hook 不再把那段提示词当成回复返回。这次运行只记下有类型的拦住原因，回复、输出和记录事件都不留回显的提示词。窗口立刻跳过，`skip_reason` 为 `blocked_by_hook`。运行是 `completed`，什么都不存，游标移过这个窗口。推送订阅对这个窗口什么都不推。咨询的提示词被 hook 拦住时，以原因 `contract` 失败。以前这条咨询因为花费未知而被当成 `budget` 丢掉。
- 读不懂的线索或意图回复会再问一次，指令里加上 `extraction.REFORMAT_REMINDER`，并且仍在这次运行剩下的花费上限和截止时间之内。每一次询问的花费都计入。用散文或代码围栏包住那一个正确种类的对象，现在可以读到。两个不同的这种对象，或一处回复里 JSON 对象可能开始的位置超过 200 处，仍然算读不懂。第二次询问之后仍然读不懂，窗口跳过，`skip_reason` 为 `invalid_reply`，运行是 `completed`，游标移动。若花费上限或截止时间在第二次询问之前已经用尽，运行以 `budget` 或 `timeout` 失败，窗口留下。
- 游标移动之前，运行在定时任务的锁下再检查一次确认，与写入时相同。若范围被放宽或确认被撤销，运行是 `cancelled`，游标不动。其他 processor 失败仍然让运行失败并留下游标。回补也一样：跳过的窗口记下来，回补继续；任何其他 processor 失败仍然停住回补。
- 跳过的运行算 `completed`，所以不触发失败告警。连续完成且被跳过的次数达到失败告警所等的次数（默认 3）时，每一段连续跳过发一次 `skip_alert`（`subscriptions.skip_alert_at`）。它写出最后一次的原因，不含消息正文。下一次用掉自己窗口的已完成运行发 `skip_recovered`。没有完成的运行既不结束这段连续，也不增加它。
- 仪表盘的运行历史给以前没有标签的 `extracted` 运行标上 Extracted，给 `skipped` 运行标上 Skipped 和原因（a prompt hook blocked it，或 its reply could not be read, twice）。`looper msgflow leads-backfill` 报告被跳过的窗口。跳过的推送不会让 Telegram 或 Lark 多发一条，抽取运行仍然什么都不发。


**会话预算，默认关闭（[#1506](https://github.com/foolzzz/looper/pull/1506)）**

- **`manager.turn_budget_usd` 默认关闭。**没有这一行就是关。存下来的值不是正的有限数字时也是关，`session_budget.get` 在 `problem` 里说明原因。没有仪表盘开关。`chat_settings.get` 和 `chat_settings.update` 不带这个字段。没有 Manager 工具列出它，默认提示词也不提它。
- **只有操作者能读或写。**`POST /api/v1/session_budget/get` 和 `POST /api/v1/session_budget/update` 只给操作者。更新是高风险：影响说明写出 `manager.turn_budget_usd` 和将要存的值，并写明 Manager 的接线是分开的、回合不变。操作者的调用立刻生效。正的有限数字存成这个数字。`null` 删掉这一行，恢复关闭。没带上的字段保持原值。0、负数、布尔值、非数字、空的请求体和未知字段都会被拒绝，什么都不存。API 客户端令牌得到 403，什么都不存。
- **`session_budget.get` 返回** `turn_budget_usd`（关闭时为 null）、`recommended_usd`（4.00）和 `problem`。
- **规则是纯函数，没有回合调用它们。**预算没设，或这一轮的上下文未知时，`decide` 保留会话。超过 `scheduler.session_context_max_tokens` 时，运行时能够无头压缩常驻会话（`headless_compaction`）就压缩，否则轮换。上下文至少达到这个门槛的一半，并且已知的这一轮花费超过预算的一半，就轮换。和定时任务的规划者不同，花费未知时跳过花费规则；单凭上下文仍可以压缩或轮换。`/compact` 失败、没有 `compact_boundary`，或压缩后上下文仍超过门槛时，`after_compaction` 轮换；有边界但没有报大小，算压缩成功。没有预算时 `turn_cap` 是关；这一轮的模型有价格时是加上限；否则是 `no_price`。`over_cap_reply` 是花费在预算处停下的那一轮会得到的固定回复。存下预算不改变提示词、工具列表、命令行、回复、记录和渠道调用，存的是正数时也一样。

**一次不带工具的类型化模型调用，没有行为变化（[#1503](https://github.com/foolzzz/looper/pull/1503)）**

出站核对、Advisor 回合（含它的判别）和线索复核，用不带工具、回复有类型的运行时，都走 `model_call.call` 这一个入口。它返回 `CallOk`（解析出的值）或 `CallFailed`（`CallFailure`：`timeout`、`parse`、`runtime`、`rate_limited`、`unavailable`、`budget` 或 `refused`）。结果上留着这次运行的记录、花费、延迟和模型；解析失败时留着解析器自己的异常。执行失败不会再去解析。唯一的后端是 `SubscriptionBackend`，它调用原有的 `spawn.run_child` 和 `processor.run`，启动、截止时间、花费和记录规则都保持原样。没有直接调用 API 的后端，也没有新设置。订阅的 processor 运行和抽取运行不走这个入口。提示词、角色提示词、启动参数、行、出站决定、线索计数、Advisor 状态、重试规则和花费入账都不变。Advisor 的花费仍在解析之前入账。仪表盘、Telegram、Lark 和 CLI 不变。

**会话 id 和绑定文件从会话读取，没有行为变化（[#1512](https://github.com/foolzzz/looper/pull/1512)）**

会话 id 和运行时类型从回合所在的会话读取（`ManagerSession.session_id` 和 `session_runtime`）。`_prepare_turn` 在代码自己回答的命令和关卡回复之后，把这个会话读一次，放在 `Prepared.session` 上。其他读取从 `_session_now` 开始（这个上下文设过的会话，否则是 `main`）。转发属性 `_session_id` 和 `_session_runtime` 已去掉。绑定文件是 `ManagerOps.turn_file_for(session_key)`：`main` 返回 fleet 已经给这个会话的那个回合文件；其他 key 抛出 `ValueError`。`publish_binding`、`server_config` 和 `library_with_server` 接受 `session_key`，默认 `main`。Manager 传入它正在跑的会话的 key。现在只有 `main`，所以每次读取仍是 main 的。main 的绑定文件、它的 MCP 条目和它的写入，仍是同一个文件、同样的字节。提示词、工具列表、命令行、记录和渠道行为不变。

**工具和操作到达哪里，已声明、还没人读（[#1498](https://github.com/foolzzz/looper/pull/1498)）**

`ActionLevel` 是 `inside`、`operator`、`origin`、`machine`、`external` 或 `unknown`。审查只会看 `external` 和 `unknown`。Looper 的每个工具都在 `ops/levels.py`（`TOOL_LEVELS`）里按工具的准确名字声明级别，而不是 `Tool` 上的字段：升级探针按精确形状读取 `Tool` 的声明，以及房间和知识库的构造。只读动作是 `inside`。没有条目的工具是 `unknown`。一次调用有多个效果时，取最高的一级。`looper_projects` 的 `move` 是 `machine`。`looper_settings` 的 `gateway` 和 `knowledge_vault` 是 `machine`。`looper_providers`、`looper_catalog` 和 `looper_vault_write` 是 `machine`。`looper_task_gate_reply` 和 `looper_task_concurrency` 是 `origin`。`looper_gates` 的 `reply` 和 `end` 是 `origin`。`looper_schedules` 在定时任务要跑命令时是 `machine`，否则是通知目标的级别，两者取更高的：仪表盘或操作者自己的私聊是 `operator`，询问这一回合的会话是 `origin`，别的会话是 `external`，目标没有会话名时是 `unknown`。读不到的已存定时任务是 `unknown`。

每个 `/api/v1` 操作有 `level`，默认 `inside`；由参数决定时用 `level_of`。`manager_chat_bindings.put` 是 `external`。`schedule_admin.create`、`update`、`run` 和 `confirm_target` 走同一条定时任务规则（API 客户端的调用没有自己的会话，所以别的会话是 `external`）。`intent_bindings.put` 和 `channel_chats.set_policy` 是 `inside`：前者把会话映射到项目，哪里都不发送；后者切换 `bound_chats_only`，放宽之后的准入仍由 `chat_routing` 只给操作者的拒绝来守。`session_budget.get`、`session_budget.update` 和 `attention.summary` 是 `inside`。级别不在 OpenAPI 文档里：把每个级别都重置之后，文档逐字节相同。没有回合、也没有 HTTP 处理读取级别。`outbound.review` 仍然没有调用方。

**助手体验基线，只有数据（[#1510](https://github.com/foolzzz/looper/pull/1510)）**

`evals/prompt_regression/baselines/assistant-real-sonnet.json`（sonnet，三次重复）和 `evals/prompt_regression/baselines/assistant-real-opus.json`（sonnet，Manager 为 opus、effort `xhigh`，两次重复）是已核准的真实模式基线，schema 为 `looper-assistant-experience/v1`，两份都记在提交 `2b77afb1672cda93be6681259623bafa4e290f2d`。Sonnet 的通过率是时间 60%、身份 20%、串话 73.3%、语气 66.7%，花费约 $2.12。Opus xhigh 是时间 70%、身份 30%、串话 100%、语气 40%，花费约 $2.94。身份分低，是因为仍会为不是操作者的人打开确认；时间没过，是日历周的算术。这些是第一期要解决的目标，不是本版本的回退。检查、提示词、工具列表、命令行、仪表盘、Telegram 和 Lark 的行为都不变。

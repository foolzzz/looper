# Looper v2.14.189

This is the patch release v2.14.189, a hotfix line in which each merged change ships at once. It documents two changes: [#1351](https://github.com/foolzzz/looper/pull/1351) (keep process-table reads off the event loop) and [#1349](https://github.com/foolzzz/looper/pull/1349) (the request-recording proxy ends when `looper serve` ends).

## Release Decision

**Who should upgrade:** Operators who run the request-recording proxy and want it to stop with the server instead of lingering, and operators who start many agent processes and want the control plane to stay responsive while the process table is read.

**What this release solves:** [#1349](https://github.com/foolzzz/looper/pull/1349) makes the request-recording proxy stop on every `looper serve` shutdown path, and exit by itself when its owner is gone; a planned kept-run upgrade hands the proxy over instead. [#1351](https://github.com/foolzzz/looper/pull/1351) runs three process-table reads (agent spawn, graceful-stop preparation, consult result handling) in worker threads, and fixes the process ownership and cleanup the move would otherwise have put at risk.

**Breaking changes:** No. The Telegram and Lark channel protocols and the CLI are unchanged, no new command or dashboard control is added and there is no database schema change. [#1349](https://github.com/foolzzz/looper/pull/1349) is a stated behavior change (see Behavior changes). The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.14.189
```

**Contributors:** Maintainer @foolzzz authored [#1351](https://github.com/foolzzz/looper/pull/1351) and [#1349](https://github.com/foolzzz/looper/pull/1349); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.188 upgrades directly. There is no database schema change. Restart the service after upgrading, as for every release.

## Behavior changes

Read in the diffs of [#1349](https://github.com/foolzzz/looper/pull/1349) and [#1351](https://github.com/foolzzz/looper/pull/1351).

### #1349: the request-recording proxy ends when `looper serve` ends

The PR calls this an intended behavior change by maintainer decision.

- **Ownership record.** `ProxyControl` writes an owner file (`.local/llmrec/owner.json` under the runtime root) with the server pid, its start time and a random token, in `owned` mode. `ProxyControl.close()` is new: it stops the owned proxy, terminates any child that has not yet published its state file and escalates to kill after the grace period. It does nothing if a replacement controller has already adopted the endpoint (different token).
- **Server shutdown.** `serve.py` stops the proxy on the normal shutdown path and again in the final cleanup (a failure is logged, not raised). The lock-loss fence (`Fence.recording_proxy`) closes it concurrently with `proc_tree.end_owned`.
- **Kept-run upgrades are the exception.** When shutdown detaches kept runs (`DETACH_KEPT`), `close(handover=True)` rewrites the owner file as `handover` and leaves the proxy running, so the endpoint stays pinned until the next controller adopts it.
- **The proxy exits by itself.** The proxy process watches its owner once a second. In `owned` mode it stops when the owner pid is reparented away or `process_alive` reports the pid gone or reborn (matching pid and start time); in `handover` mode it keeps running; with no owner file (a direct CLI boot) it follows its original parent. If the owner file changes between the check and the stop (adoption), it does not stop. A 5-second backstop forces exit if its own shutdown drain hangs.
- **Smaller changes.** Stop reasons are logged (signal, state removed, idle 24 hours, owner disappeared, kill after timeout). `_running` treats an exited child as not running and uses the new `process_alive` (a pid plus `ps` birth time check, with a `ps` timeout) instead of `proc_tree._start_time`. Waiting for a stopped child is bounded to 5 seconds.
- **Also in the diff, not in the PR text:** `room.py`. A waiting room inbox now joins the run's in-flight reminder send before deciding whether a message already pushed to the agent's stdin still belongs in its pull inbox, and marks the wait as `waited` when such a message was delivered. A new test (`tests/test_room_delivery_race.py`) covers accepted, rejected and absent pushes. Visible consequence: a concurrent push is resolved first, so the inbox returns `delivered_message_ids` and no duplicate message when the push was accepted, and returns the message when it was rejected.

### #1351: process-table reads off the event loop

- **Three reads moved to `asyncio.to_thread`:** `proc_tree.spawn` (start time of the new process), `proc_tree.begin_end` (the tree of a process before graceful stop) and the consult result handler (`consult.py`, tree read when a result event arrives).
- **Ownership preserved.** `begin_end` now marks the process as ending before yielding to the thread, so the reaper cannot remove its durable record in the meantime, and records the tree afterwards. A spawn cancelled before its handle reaches the caller ends the process (`end(..., label="cancelled agent spawn")`) and re-raises.
- **Deliberately unchanged:** `TurnTree.track` and its callers stay synchronous, because asynchronous registration would open cancellation windows before cleanup is established; `_end`, `sweep`, tickers and command runs are untouched. This is deferred work, not a gap in the change.
- **Visible consequence:** the loop keeps ticking during a slow process-table read; no output, command or setting changes.

### Model-visible changes

None to a prompt, tool description or tool schema. The one visible effect on an agent is the room-inbox race fix above: the result of a waiting inbox call can differ only when a push to the same run is in flight.

### 行为变化与入口

以下在 [#1349](https://github.com/foolzzz/looper/pull/1349) 和 [#1351](https://github.com/foolzzz/looper/pull/1351) 的差异中可见。

**#1349：请求记录代理随 `looper serve` 结束**（PR 称之为维护者决定的有意行为变化）

- **属主记录。**`ProxyControl` 在运行时根目录的 `.local/llmrec/owner.json` 写入服务 pid、启动时间和随机令牌（`owned` 模式）。新增 `ProxyControl.close()`：停止自己拥有的代理，终止尚未发布状态文件的子进程，宽限期后升级为强杀；若替代控制器已接管（令牌不同）则不做任何事。
- **服务关闭。**`serve.py` 在正常关闭路径和最终清理中停止代理（失败只记录日志）。锁丢失栅栏（`Fence.recording_proxy`）与 `proc_tree.end_owned` 并行关闭它。
- **保留运行的升级是例外。**关闭时若分离保留运行（`DETACH_KEPT`），`close(handover=True)` 把属主文件改为 `handover` 并让代理继续运行，该端点保持固定，直到下一个控制器接管。
- **代理自行退出。**代理进程每秒检查属主。`owned` 模式下，属主 pid 被重新归属，或 `process_alive` 判定该 pid 已不存在或已被复用（pid 与启动时间需同时匹配）时停止；`handover` 模式下继续运行；没有属主文件（直接用 CLI 启动）时跟随其原始父进程。若检查与停止之间属主文件变化（被接管），则不停止。若自身关闭排空卡住，5 秒后备份机制强制退出。
- **其他变化。**记录停止原因（信号、状态被移除或替换、空闲 24 小时、属主消失、超时后强杀）。`_running` 把已退出的子进程视为未运行，并用新增的 `process_alive`（pid 加 `ps` 启动时间校验，`ps` 有超时）代替 `proc_tree._start_time`。等待已停止的子进程最多 5 秒。
- **差异中还有、PR 正文未提：**`room.py`。等待中的房间收件箱现在会先等待该运行正在进行的提醒发送，再判断已推送到智能体 stdin 的消息是否仍属于其拉取收件箱，并在有此类消息送达时标记 `waited`。新测试 `tests/test_room_delivery_race.py` 覆盖推送被接受、被拒绝和不存在三种情况。可见后果：并发推送先被确定，推送被接受时收件箱返回 `delivered_message_ids` 且不重复返回消息，被拒绝时返回该消息。

**#1351：进程表读取移出事件循环**

- **三处读取改用 `asyncio.to_thread`：**`proc_tree.spawn`（新进程的启动时间）、`proc_tree.begin_end`（优雅停止前读取进程树）和 consult 结果处理（`consult.py`，结果事件到达时读取进程树）。
- **进程归属得以保持。**`begin_end` 在让出给线程之前先把进程标记为正在结束，回收器因此不会在此期间删除其持久记录，读取完成后再记录进程树。在句柄交给调用方之前被取消的启动会结束该进程（`end(..., label="cancelled agent spawn")`）并重新抛出取消。
- **有意不改：**`TurnTree.track` 及其调用方保持同步，因为异步注册会在清理建立之前引入取消窗口；`_end`、`sweep`、定时器和命令运行不变。这是推迟的工作，不是遗漏。
- **可见后果：**进程表读取变慢时事件循环仍能继续运转；输出、命令和设置均无变化。

**面向模型的变化：**提示词、工具描述和工具 schema 均无变化。对智能体唯一可见的影响是上述房间收件箱竞态修复：只有在向同一运行的推送正在进行时，等待中的收件箱调用结果才可能不同。

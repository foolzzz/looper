# Looper v2.13.16

## Release Decision

**Who should upgrade:** Operators who turn on the experimental `chat.stop_enabled` setting to stop Manager replies, and anyone who wants the groundwork for that. With the setting off (the default) users see no change.

**What this release solves:** [#337](https://github.com/foolzzz/looper/pull/337) redesigns how a Manager reply is stopped. A stop now covers the whole turn from the moment its message is received (queued, preparing, running), uses one cancellation for every runtime, ends process trees from a snapshot taken at spawn, and binds each Manager tool call to its own turn so a late call of a stopped turn is refused. `chat.stop_enabled` stays **off by default**.

**Breaking changes:** No. No CLI command, configuration key or database schema changed. `POST /api/chat/stop` and `GET /api/chat/turn` gain fields, `GET /api/status` gains `turn_binding`, and Manager tool calls carry an `X-Looper-Turn` header.

**How to verify:** Check the installed version, then read the binding report.

**Contributors:** Maintainer @foolzzz authored [#337](https://github.com/foolzzz/looper/pull/337); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.16
curl -s "$LOOPER_URL"/api/status | python3 -c 'import json,sys; print(json.load(sys.stdin)["turn_binding"])'
```

## Behavior changes

- **Only with `chat.stop_enabled` on:** a stop is honored in every phase of a turn; a message waiting in the queue can be stopped (it used to answer `other_message`); `/stop` stops the running and queued messages of that chat. A message stopped before the model saw it leaves no Runs record.
- **Stop answers.** `POST /api/chat/stop` answers `stopping` or `already_stopping` with the `phase` and `method`; `GET /api/chat/turn` also returns `state` and `method`, and its `started_at` is when the message was received.
- **Runtimes.** One cancellation (`run_turn(cancel=)`) serves every runtime: Claude Code is interrupted with a control request and then its process tree from the spawn snapshot, Grok through `session/cancel` (and the same cancel through its fallback), the others by ending the tree, which is snapshotted at spawn, refreshed, and reaped within a bound.
- **Records.** A stopped turn is recorded `interrupted` with the phase and method of the stop. Usage that is wholly unknown is recorded as `null` and shown as "usage not reported" instead of 0.
- **Tool calls bound to their turn.** The Manager's MCP bridge (and Pi's own bridge) reads a binding file per call and sends it as `X-Looper-Turn`. Calls that arrive after a stop or after the turn ended are refused (`stopped`, `expired`). With the setting on, on resident runtimes a write call that matches no tool call in its own turn's stream is refused with `not_this_turn`. With the setting off the binding only observes: no call is refused for a mismatch, each is logged as `turn binding mismatch` and counted in `GET /api/status` under `turn_binding`; zero mismatches over real use is a criterion for turning Stop on.
- **Model-visible changes:** The next user turn after a stopped reply gets one `[Looper]` line: either that the user stopped the previous reply (with its first line quoted) and its tool calls were not undone, or that the user withdrew a message before the model saw it and it should not be acted on. A refused tool call returns the error `stopped`, `expired` or `not_this_turn` to the model. Tool calls carry `X-Looper-Turn`. No tool schema changed.

## Entry points

- `POST /api/chat/stop`, `GET /api/chat/turn`, `GET /api/status` (`turn_binding`), `GET`/`PUT /api/chat-settings`, `/stop` on the web chat, Telegram and Lark, and Esc or the Stop button in the Manager chat.

## Upgrade and rollback

Re-run `install.sh` once v2.13.16 is published. There is no schema or configuration change; the setting stays as it was. Rolling back to v2.13.15 is safe.

## Optional Capability Activation & Use

### Stopping a Manager reply

**Activation:** Still off by default; turning it on is a separate decision against the RFC's criteria. In Settings → Chat turn on the experimental stop, or `PUT /api/chat-settings` with `{"stop_enabled": true}` (`null` returns to the default, off).

```bash
curl -s -X PUT "$LOOPER_URL"/api/chat-settings -d '{"stop_enabled": true}'
```

**Validation:** `GET /api/chat-settings` shows `stop_enabled` true and `GET /api/status` shows `turn_binding.enforced` true. While the Manager replies or a message waits, `POST /api/chat/stop` answers `stopping` with a `phase`, and the reply is recorded `interrupted`.

**Disable / rollback:** `PUT /api/chat-settings` with `{"stop_enabled": false}`. The Stop button and Esc go away, `/stop` is answered "停止功能暂未开放", `POST /api/chat/stop` answers `409`, and the turn binding only observes again.

**Authority boundary:** Stopping ends only the Manager's turn for that chat, from the dashboard or an allowlisted channel sender. Tool calls already made are not undone. The binding file lives under the runtime directory and stores no secret.

**Docs:** [Agent system](https://github.com/foolzzz/looper/blob/main/docs/architecture/agent-system.md), [chat stop v2 RFC](https://github.com/foolzzz/looper/blob/main/docs/architecture/rfcs/chat-stop-v2.zh-CN.md).

### 行为变化与入口

- 仅在 `chat.stop_enabled` 开启时：任何阶段都能停止；排队中的消息可以停止（此前返回 `other_message`）；`/stop` 停止该聊天正在运行和排队的消息。模型尚未看到就被停止的消息不留 Runs 记录。
- 停止应答：`POST /api/chat/stop` 返回 `stopping` 或 `already_stopping`，带 `phase` 与 `method`；`GET /api/chat/turn` 增加 `state`、`method`，`started_at` 为收到消息的时间。
- 运行时：一个取消（`run_turn(cancel=)`）适用所有运行时：Claude Code 先发控制请求中断，再按启动快照结束进程树；Grok 用 `session/cancel`（回退路径同样）；其余结束进程树，进程树在启动时快照、会刷新，并在限定时间内回收。
- 记录：被停的一轮记为 `interrupted`，带停止的阶段与方式；用量完全未知时记为 `null`，显示“usage not reported”而不是 0。
- 工具调用绑定回合：管家 MCP 桥（及 Pi 自己的桥）每次调用读取绑定文件并作为 `X-Looper-Turn` 发送。停止后或回合结束后到达的调用被拒绝（`stopped`、`expired`）。设置开启时，常驻运行时上与本回合流中任何工具调用都不匹配的写调用以 `not_this_turn` 拒绝。设置关闭时绑定只做观察：不会因不匹配拒绝任何调用，每次不匹配记为 `turn binding mismatch` 日志并计入 `GET /api/status` 的 `turn_binding`；真实使用中零不匹配是开启 Stop 的条件之一。
- 面向模型的变化：被停止的回复之后，下一轮用户消息会收到一行 `[Looper]`：要么说明用户停止了上一次回复（引用其首行）且工具调用不会撤销，要么说明用户在模型看到前撤回了一条消息、不应据此行动。被拒绝的工具调用向模型返回 `stopped`、`expired` 或 `not_this_turn` 错误。工具调用带 `X-Looper-Turn`。工具 schema 没有变化。
- 入口：`POST /api/chat/stop`、`GET /api/chat/turn`、`GET /api/status`（`turn_binding`）、`GET`/`PUT /api/chat-settings`、web 聊天、Telegram、Lark 的 `/stop`，以及管家聊天中的 Esc 或 Stop 按钮。

### 可选能力启用与使用

#### Stopping a Manager reply

**启用：**仍默认关闭；是否开启需另行依据 RFC 的条件决定。在 Settings → Chat 打开实验性的停止功能，或 `PUT /api/chat-settings` 传 `{"stop_enabled": true}`（`null` 恢复默认，即关闭）。

```bash
curl -s -X PUT "$LOOPER_URL"/api/chat-settings -d '{"stop_enabled": true}'
```

**验证：**`GET /api/chat-settings` 显示 `stop_enabled` 为 true，`GET /api/status` 显示 `turn_binding.enforced` 为 true；管家回复或消息排队期间 `POST /api/chat/stop` 返回带 `phase` 的 `stopping`，该回复记为 `interrupted`。

**停用 / 回退：**`PUT /api/chat-settings` 传 `{"stop_enabled": false}`。Stop 按钮和 Esc 消失，`/stop` 被回复“停止功能暂未开放”，`POST /api/chat/stop` 返回 `409`，回合绑定恢复为只观察。

**权限边界：**停止只结束管家对该聊天的一轮，来自 dashboard 或名单内的渠道发送者。已执行的工具调用不会撤销。绑定文件位于运行时目录，不存储密钥。

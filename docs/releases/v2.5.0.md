# LoopX v2.5.0

## At a Glance

A self-hosted agent system behind `loopx serve`: chat with a Manager, which turns requests into tasks that Claude Code workers carry out, with a web dashboard, PostgreSQL persistence, projects and Telegram/Lark channels. Its local API now refuses requests from other web pages, so a page open in your browser can no longer start tasks. Install and update come from this fork, which also drops the desktop client, four retired host integrations and other unused upstream surfaces.

This fork releases as **v2.5.0**, with **breaking changes**. Versions 2.1.1 through 2.4.0 were tagged and released only in [michaelx1993/loopx](https://github.com/michaelx1993/loopx/releases), on commits this release includes, so the fork goes from v2.1.0 to v2.5.0. The minor version does not imply compatibility with v2.1.0.

Releases now come from [foolzzz/looper](https://github.com/foolzzz/looper), where development continues after GitHub disabled Actions on foolzzz/loopx. The earlier releases (v2.0.0, v2.1.0) and the pull requests and issues linked in these notes are in [foolzzz/loopx](https://github.com/foolzzz/loopx), and those links stay valid. ([foolzzz/looper#1](https://github.com/foolzzz/looper/pull/1))

### Upgrade

From v2.5.0 on, `install.sh` and `loopx update apply` install this fork's release wheel. An installation older than v2.5.0 still follows its old source, so upgrade to v2.5.0 once from the tag, as below, or with looper's `install.sh`; the full steps are under Install / Update.

```bash
git clone https://github.com/foolzzz/looper.git loopx && cd loopx
git checkout v2.5.0
uv sync --extra test
uv run loopx --version   # loopx 2.5.0
```

### Highlights

- **Agent system behind `loopx serve`.** The Manager turns a chat request into a task, and a Claude Code worker carries it out as one step; chatting with the task's Planner reaches the running worker or adds a step. A step counts as done only when the worker's report matches the files on disk. Usage: install the release wheel, start PostgreSQL, sign in the Claude CLI, then run `loopx serve`; the wheel carries the database schema and the dashboard. ([michaelx1993/loopx#38](https://github.com/michaelx1993/loopx/pull/38), [michaelx1993/loopx#39](https://github.com/michaelx1993/loopx/pull/39), [michaelx1993/loopx#40](https://github.com/michaelx1993/loopx/pull/40), [michaelx1993/loopx#41](https://github.com/michaelx1993/loopx/pull/41), [michaelx1993/loopx#49](https://github.com/michaelx1993/loopx/pull/49), [#154](https://github.com/foolzzz/loopx/pull/154), [#156](https://github.com/foolzzz/loopx/pull/156), [#167](https://github.com/foolzzz/loopx/pull/167), [#179](https://github.com/foolzzz/loopx/pull/179))
- **The local API refuses other web pages.** A request whose `Origin` is not the server's own gets 403, responses carry no CORS headers, and on a loopback bind the `Host` must be a loopback name, which blocks DNS rebinding. Before, any page open in the browser could create and start tasks, whose workers run without permission prompts, and read chat and run history. Usage: nothing to configure; curl and the CLI are unaffected. ([#176](https://github.com/foolzzz/loopx/pull/176))
- **Install and update from this fork.** `install.sh` and `loopx update apply` install the wheel of the latest foolzzz/looper release, and refuse instead of installing the PyPI package when there is none. Usage: `curl -fsSL https://raw.githubusercontent.com/foolzzz/looper/main/install.sh | bash`. ([#177](https://github.com/foolzzz/loopx/pull/177), [foolzzz/looper#1](https://github.com/foolzzz/looper/pull/1))
- **Every Claude run is recorded and can be watched.** The launch command, transcript, thinking progress, tool calls and cost of each Manager, worker and reviewer run, live on the agent history page; the Chat page lists every agent. Usage: task detail → Agent Timeline → History. ([michaelx1993/loopx#50](https://github.com/michaelx1993/loopx/pull/50), [michaelx1993/loopx#51](https://github.com/michaelx1993/loopx/pull/51), [#164](https://github.com/foolzzz/loopx/pull/164), [#165](https://github.com/foolzzz/loopx/pull/165), [#169](https://github.com/foolzzz/loopx/pull/169), [#172](https://github.com/foolzzz/loopx/pull/172))
- **Projects.** Every task belongs to a project with an optional default directory; the sidebar lists projects and the Tasks page filters by them. Usage: the sidebar `+`, or `POST /api/projects`. ([#174](https://github.com/foolzzz/loopx/pull/174))
- **Responsive chat.** The Manager keeps one Claude process across messages, streams its reply and always answers; a message to a task's Planner reaches the running worker. ([#158](https://github.com/foolzzz/loopx/pull/158), [#159](https://github.com/foolzzz/loopx/pull/159), [#162](https://github.com/foolzzz/loopx/pull/162), [#170](https://github.com/foolzzz/loopx/pull/170), [#173](https://github.com/foolzzz/loopx/pull/173))
- **Telegram and Lark from Settings.** Both channels are off by default and are turned on in the dashboard Settings page, with no command-line flags. Usage: enable, set the environment variable names, restart `loopx serve`. ([michaelx1993/loopx#56](https://github.com/michaelx1993/loopx/pull/56), [#153](https://github.com/foolzzz/loopx/pull/153), [#161](https://github.com/foolzzz/loopx/pull/161))
- **A smaller fork.** The native desktop client, the OpenCode, Kiro CLI, Gemini CLI and Cline hosts, the demo launchers, the benchmark archives, Doubao qualification and the release and Pages automation are removed. ([#110](https://github.com/foolzzz/loopx/pull/110), [#112](https://github.com/foolzzz/loopx/pull/112), [#127](https://github.com/foolzzz/loopx/pull/127), [#129](https://github.com/foolzzz/loopx/pull/129), [#130](https://github.com/foolzzz/loopx/pull/130), [#131](https://github.com/foolzzz/loopx/pull/131))

## Release Decision

**Who should upgrade:** Fork users who want the `loopx serve` agent system, and anyone running a michaelx1993/loopx 2.2.1 to 2.4.0 build, whose agent API any web page could drive. Stay on v2.1.0 if you depend on the native desktop client, the OpenCode, Kiro CLI, Gemini CLI or Cline hosts, `loopx auto-research`, `loopx multi-agent` or `loopx authority-shadow`. Role dispatcher (`loopx dispatch`) users without those dependencies can upgrade; their Goal state needs no migration.

**What this release solves:** A chat message from the dashboard, Telegram or Lark becomes a task that a Claude Code worker carries out and that is checked against the files on disk, with every agent run open to inspection. It closes the cross-site hole in the agent API, through which any web page open in the browser could create and start tasks and read their history. Install and update now come from this fork instead of michaelx1993/loopx or the upstream PyPI package. It also fixes the first agent-system builds: tasks that never finished, steps marked done without their files, chat replies that hung or arrived twice, work replayed after a restart, and dashboard settings that had no effect.

**Breaking changes:** Yes. `loopx serve` is new and needs PostgreSQL and the Claude CLI. The desktop client, four host integrations, several commands and wire fields are removed. `loopx update apply` and `install.sh` install this fork's release wheel and refuse when a release has none, instead of installing the PyPI package. The agent API answers requests from other web pages with 403. Databases of michaelx1993/loopx 2.3.0 and 2.4.0 builds migrate forward on first start. No LoopX Goal state migration is needed. The steps are under Documentation & Compatibility.

**How to verify:** After installing, expect `loopx 2.5.0` and a passing `loopx doctor`. With PostgreSQL and the Claude CLI ready, `loopx serve` answers `/api/status` with `"status": "running"`, and the same request with a foreign `Origin` gets 403.

**Contributors:** Release maintainer @foolzzz; community contributor @michaelx1993, with 29 pull requests merged through michaelx1993/loopx (see Community Contributors).

```bash
loopx --version
loopx doctor
loopx serve --help
  # After starting `loopx serve` in another shell:
curl -s http://127.0.0.1:8767/api/status
curl -s -o /dev/null -w '%{http_code}\n' -H 'Origin: https://example.com' http://127.0.0.1:8767/api/status   # 403
```

## State Kernel & Control Plane

- **The agent API refuses cross-site requests.** It used to send `Access-Control-Allow-Origin: *` and approve every preflight, so any page open in the browser could create and start a task, whose workers run Claude without permission prompts, or read chat and run history. A request whose `Origin` is not the server's own now gets 403, no response carries CORS headers, and while the server is bound to loopback the `Host` must be a loopback name, against DNS rebinding. curl, the CLI and the Vite dev proxy are unaffected. The API still has no authentication. ([#176](https://github.com/foolzzz/loopx/pull/176))
- **PostgreSQL holds the agent system's state.** Tasks, steps, activity, chat, agent configs, LLM profiles, run records and channel settings are stored in PostgreSQL, which `loopx serve` requires at startup. Tasks a previous server left running are marked `stopped` when it starts. ([michaelx1993/loopx#44](https://github.com/michaelx1993/loopx/pull/44), [michaelx1993/loopx#45](https://github.com/michaelx1993/loopx/pull/45), [michaelx1993/loopx#48](https://github.com/michaelx1993/loopx/pull/48), [michaelx1993/loopx#49](https://github.com/michaelx1993/loopx/pull/49), [michaelx1993/loopx#53](https://github.com/michaelx1993/loopx/pull/53))
- **Tasks finish, and fail, honestly.** Worker results reach the task's own Planner, and a Planner's `failed` outcome is stored as `failed`. A step completes only when Claude's run succeeds, its JSON report says `completed`, the files it lists as changed exist and the ones it lists as deleted are gone. Reviewers must return a boolean `passed`. ([#154](https://github.com/foolzzz/loopx/pull/154), [#156](https://github.com/foolzzz/loopx/pull/156))
- **A restart no longer replays per-task work.** At startup the message bus drops undelivered Planner and worker messages from the previous run and compacts its journal; consumed work is marked delivered. Each reply reaches a channel once. ([#160](https://github.com/foolzzz/loopx/pull/160), [#161](https://github.com/foolzzz/loopx/pull/161))
- **One work directory and one project per task.** A task runs only in its own `work_dir` or its project's default directory, never in a server default. On first start the old `project_root` is folded into `work_dir` and dropped, and existing tasks are placed in one project per directory, a backfill that runs once and is recorded in `schema_migrations`. ([#167](https://github.com/foolzzz/loopx/pull/167), [#174](https://github.com/foolzzz/loopx/pull/174))
- Control-plane cleanup: project-state and Codex-home paths come from one owner; the retired local-authority observation interfaces and the `authority-shadow` CLI are replaced by `coordination-shadow drain` and `status`; the unused `loopx.visible_governance` projection is removed. ([#109](https://github.com/foolzzz/loopx/pull/109), [#111](https://github.com/foolzzz/loopx/pull/111), [#115](https://github.com/foolzzz/loopx/pull/115))

## Capabilities & Workflows

- **Agent system.** User outcome: one chat request becomes a task that a Claude Code worker carries out and that is checked against the files on disk. Shipped layer: a Manager, a TaskRouter (three tasks at a time), a Planner per task, which calls no model and runs the task as one step, and a WorkerPool (four Claude runs at a time) on a typed message bus, plus the HTTP API and web dashboard, all started by `loopx serve`. Last mile: PostgreSQL and a signed-in Claude CLI are prerequisites. The release wheel carries the database schema and the dashboard, staged by `scripts/stage-dashboard.sh`, so `install.sh` or `loopx update apply` gives a working `loopx serve`; a checkout serves its own `web/dist` once built. ([michaelx1993/loopx#38](https://github.com/michaelx1993/loopx/pull/38), [michaelx1993/loopx#39](https://github.com/michaelx1993/loopx/pull/39), [michaelx1993/loopx#40](https://github.com/michaelx1993/loopx/pull/40), [michaelx1993/loopx#41](https://github.com/michaelx1993/loopx/pull/41), [michaelx1993/loopx#42](https://github.com/michaelx1993/loopx/pull/42), [#179](https://github.com/foolzzz/loopx/pull/179))
- **Chat.** Talk to the Manager or to a running task's Planner. A Planner message reaches the running worker as its next turn, or becomes a new step when no worker is running. The Manager keeps one Claude process, streams its reply and always answers, with an error when Claude fails. The Chat page lists every agent; finished ones are read-only. ([#155](https://github.com/foolzzz/loopx/pull/155), [#158](https://github.com/foolzzz/loopx/pull/158), [#159](https://github.com/foolzzz/loopx/pull/159), [#162](https://github.com/foolzzz/loopx/pull/162), [#170](https://github.com/foolzzz/loopx/pull/170), [#172](https://github.com/foolzzz/loopx/pull/172), [#173](https://github.com/foolzzz/loopx/pull/173))
- **Run history.** Each Manager, worker and reviewer run is one `llm_records` row with its launch command, working directory, stream events, status, tokens and cost, readable through `/api/llm-records/:id/events`. The history page follows a run live, shows thinking progress, hooks, background tasks and rate limits, and flags a run with no output for two minutes. ([#163](https://github.com/foolzzz/loopx/pull/163), [#164](https://github.com/foolzzz/loopx/pull/164), [#165](https://github.com/foolzzz/loopx/pull/165), [#168](https://github.com/foolzzz/loopx/pull/168), [#169](https://github.com/foolzzz/loopx/pull/169))
- **Task controls and agent settings.** Create a task in `init` and edit it before it starts; stop, start, cancel and delete tasks; edit agent prompts and limits on the Agents page. The worker's `timeout_seconds` (default now 86400 s) and `max_turns` apply to each run. ([michaelx1993/loopx#46](https://github.com/michaelx1993/loopx/pull/46), [michaelx1993/loopx#47](https://github.com/michaelx1993/loopx/pull/47), [michaelx1993/loopx#52](https://github.com/michaelx1993/loopx/pull/52), [michaelx1993/loopx#53](https://github.com/michaelx1993/loopx/pull/53), [michaelx1993/loopx#55](https://github.com/michaelx1993/loopx/pull/55), [michaelx1993/loopx#57](https://github.com/michaelx1993/loopx/pull/57), [#166](https://github.com/foolzzz/loopx/pull/166), [#171](https://github.com/foolzzz/loopx/pull/171))
- **Projects** group tasks, carry an optional default directory, and drive the sidebar, the Tasks filter and where the Manager places a task. ([#174](https://github.com/foolzzz/loopx/pull/174))
- **`loopx init`** writes provider and agent files for the role dispatcher. The `loopx dashboard` Settings page gains Agent config and Update tabs, Chat gains a session panel, and a Goal is created from a one-line prompt. ([michaelx1993/loopx#32](https://github.com/michaelx1993/loopx/pull/32), [michaelx1993/loopx#36](https://github.com/michaelx1993/loopx/pull/36), [michaelx1993/loopx#37](https://github.com/michaelx1993/loopx/pull/37))
- Retired: the source-checkout demo with the `loopx auto-research` and `loopx multi-agent` commands, and the native desktop client with its signed updates. Use `loopx dashboard` for the browser workspace. ([#110](https://github.com/foolzzz/loopx/pull/110), [#127](https://github.com/foolzzz/loopx/pull/127))

## Benchmarks & Integrations

- **Telegram and Lark** are configured only in the dashboard Settings page (`channel_configs`) and are off by default. `python-telegram-bot` is a default dependency, a malformed Telegram allowlist keeps Telegram off, and a channel that fails to start no longer stops the server. ([michaelx1993/loopx#38](https://github.com/michaelx1993/loopx/pull/38), [michaelx1993/loopx#56](https://github.com/michaelx1993/loopx/pull/56), [#153](https://github.com/foolzzz/loopx/pull/153), [#161](https://github.com/foolzzz/loopx/pull/161))
- **Agent runtime:** the agent system runs only the Claude Code CLI. Agent-config fields for other runtimes, models and permission modes are stored but not applied. ([michaelx1993/loopx#46](https://github.com/michaelx1993/loopx/pull/46), [#153](https://github.com/foolzzz/loopx/pull/153))
- **Hosts removed:** OpenCode (including OpenCode 2), Kiro CLI, Gemini CLI and Cline, with their flags; the default slash-command install targets Codex and Claude Code. Codex CLI (including app-server), Claude Code, Cursor Agent, Pi, dsh, Ark and custom runners remain. ([#130](https://github.com/foolzzz/loopx/pull/130))
- **Benchmarks:** the bundled benchmark workspace, archives, frozen snapshots and study pages are removed; the provider-neutral toolkit and CLI remain. No benchmark jobs, uploads, leaderboard submissions or long-horizon outcome improvements are claimed. ([#129](https://github.com/foolzzz/loopx/pull/129))

## Documentation & Compatibility

The [versioned CHANGELOG](https://github.com/foolzzz/looper/blob/v2.5.0/CHANGELOG.md) lists every change. Persisted state: LoopX Goal state needs no migration; the agent system's PostgreSQL schema migrates forward automatically on start.

Upgrading from v2.1.0:

1. Back up `~/.loopx` and your projects' `.loopx` directories. 2.5.0 does not move or migrate them, but rolling back means reinstalling v2.1.0.
2. Replace removed surfaces first. The native desktop client is gone; use `loopx dashboard`. `opencode2-goal-worker`, `--with-goal-bridge`, `--opencode-home`, `--gemini-home` and `--kiro-cli-bin` now fail, as do OpenCode, Kiro CLI, Gemini CLI and Cline host bindings. `loopx auto-research` and `loopx multi-agent` are unknown commands. `loopx authority-shadow` is replaced by `loopx coordination-shadow drain` and `status`, and `--local-authority-shadow-file` and `--clear-local-authority-shadow` are removed. A visible `generic-cli` plan now fails closed instead of using an implicit OpenCode connector. ([#110](https://github.com/foolzzz/loopx/pull/110), [#115](https://github.com/foolzzz/loopx/pull/115), [#127](https://github.com/foolzzz/loopx/pull/127), [#130](https://github.com/foolzzz/loopx/pull/130))
3. Update readers of removed wire fields. `loopx doctor` no longer returns `desktop_installation` or the `desktop_app_runtime_pairing` check; canary plans no longer emit `active_scan_changed_files` or `excluded_changed_files`; the exact release-qualification manifest rejects `doubao_actual_default`; `coordination-shadow` responses omit `historical_only`; configuration summaries omit `local_authority_shadow`. ([#112](https://github.com/foolzzz/loopx/pull/112), [#115](https://github.com/foolzzz/loopx/pull/115), [#127](https://github.com/foolzzz/loopx/pull/127), [#129](https://github.com/foolzzz/loopx/pull/129))
4. Install and update now come from foolzzz/looper releases. From v2.5.0 on, `install.sh` and `loopx update apply` install the wheel attached to the latest foolzzz/looper release. When that release has no wheel or cannot be read, they install nothing and point to a tag install; they no longer install the PyPI `loopx` package, which is the upstream distribution. Older installations keep their own source and cannot reach v2.5.0 through it: an installed v2.1.0 runs `loopx update apply` against upstream `loopx-project/loopx` at `stable` on a release snapshot (through the upstream installer on `loopx-project.github.io`) and upgrades the PyPI `loopx` package on a pip or pipx install; a michaelx1993/loopx 2.1.1 to 2.4.0 build follows michaelx1993/loopx (the wheel of its latest release, else the PyPI package, or an archive of its `main`); and an installation built from foolzzz/loopx `main` after [#177](https://github.com/foolzzz/loopx/pull/177) follows foolzzz/loopx releases, which will not get v2.5.0 (its latest, v2.1.0, has no wheel, so update and install refuse). Upgrade to v2.5.0 once with looper's `install.sh` or from the tag; later updates follow foolzzz/looper. ([#177](https://github.com/foolzzz/loopx/pull/177), [foolzzz/looper#1](https://github.com/foolzzz/looper/pull/1))
5. To use `loopx serve`, follow the agent-system entry under Optional Capability Activation & Use: PostgreSQL and a signed-in Claude CLI; the release wheel brings the schema and the dashboard.

Upgrading from a michaelx1993/loopx 2.2.x to 2.4.0 build:

1. Back up the database first, for example with `pg_dump`; the 2.3.0 and 2.4.0 builds use one. The first `loopx serve` start migrates it forward, and reinstalling an older build does not undo the migration: `tasks.project_root` is folded into `work_dir` and dropped; every task is placed in a project, one per directory, and `tasks.project_id` becomes required; a worker `timeout_seconds` still at the seeded 600 becomes 86400; `llm_records` gains `status`, `cost_usd`, `finished_at` and an events table, and older rows that recorded an error are marked `failed`. ([#164](https://github.com/foolzzz/loopx/pull/164), [#166](https://github.com/foolzzz/loopx/pull/166), [#167](https://github.com/foolzzz/loopx/pull/167), [#168](https://github.com/foolzzz/loopx/pull/168), [#174](https://github.com/foolzzz/loopx/pull/174))
2. `loopx serve --enable-telegram`, `--enable-lark` and `--lark-app-id` now exit with status 2; enable channels in the Settings page. ([#153](https://github.com/foolzzz/loopx/pull/153))
3. API clients: `POST /api/tasks/create` needs a `requirement`, a `work_dir` or a project default directory, and exactly one of `project_id` and `project`; `POST /api/tasks/start` refuses a task without a directory; `/api/agents/:id/sessions` is removed in favour of `/api/llm-records?role=`. Worker steps that end without a JSON report matching the files now fail. A browser request whose `Origin` is not the server's own gets 403 and responses carry no CORS headers; on a loopback bind the `Host` must be a loopback name. ([#156](https://github.com/foolzzz/loopx/pull/156), [#165](https://github.com/foolzzz/loopx/pull/165), [#167](https://github.com/foolzzz/loopx/pull/167), [#174](https://github.com/foolzzz/loopx/pull/174), [#176](https://github.com/foolzzz/loopx/pull/176))
4. A task request queued in the bus journal before projects existed is dropped, with an error log, when it is replayed. ([#174](https://github.com/foolzzz/loopx/pull/174))

Rollback: reinstall v2.1.0 from its tag with the same steps and restore your `~/.loopx` backup if needed; v2.1.0 has no agent system and ignores its database. `loopx update --rollback RELEASE_ID` switches back to an earlier installed snapshot but does not migrate state or the database backwards. On a pip or pipx install the rollback still installs `loopx==VERSION` from PyPI, the upstream distribution, so reinstall from the tag instead.

## Optional Capability Activation & Use

### loopx serve agent system

**Activation:** Per command; there is no persistent switch. Start PostgreSQL, point `LOOPX_DATABASE_URL` at a database for LoopX (default `postgresql://localhost:5432/loopx`), sign in the Claude CLI, then run `loopx serve`. It listens on `127.0.0.1:8767` (`--host`, `--port`) and applies its schema on start. The release wheel that `install.sh` and `loopx update apply` install carries the schema and the dashboard. In a checkout, `uv run loopx serve` serves `web/dist` once built and otherwise the copy staged by `scripts/stage-dashboard.sh`. A `scripts/install-local.sh` snapshot has the dashboard only if `scripts/stage-dashboard.sh` ran in the checkout before installing. Set `LOOPX_DATABASE_URL` in the environment: `.env` is read only from the directory above the `loopx` package, which is the repository root in a checkout but `site-packages` for an installed wheel and the snapshot root for a release snapshot.

**Validation:** `/api/status` returns `"status": "running"` and lists the Manager, TaskRouter and WorkerPool, and the same request with a foreign `Origin` gets 403; the startup log line `agent system running on ...` names the channels that started.

**Disable / rollback:** Stop the server with Ctrl-C or SIGTERM; it stops the Manager's Claude process and kills running workers. Nothing runs while `loopx serve` is stopped, and tasks left `running` are marked `stopped` at the next start. To remove its data, drop the database you created for it; LoopX Goal state is not stored there.

**Authority boundary:** Workers run `claude --dangerously-skip-permissions` in the task's work directory, with your user's file and command access and no permission prompts, so give tasks only directories you accept being changed. The HTTP API has no authentication. It refuses requests from other web pages, but any local process can call it: keep the default `127.0.0.1` bind and do not expose the port. With a non-loopback `--host` the `Host` check is off, and anyone who can reach the port can drive it. LoopX itself does not merge, push or write Goal state here, but a worker can run any command your account can, including `git push` where credentials exist. Run records store full prompts, transcripts and tool output in the database.

**Docs:** https://github.com/foolzzz/looper/blob/v2.5.0/docs/architecture/agent-system.md

```bash
export LOOPX_DATABASE_URL="postgresql://localhost:5432/loopx"
createdb loopx   # only if the database does not exist yet
loopx serve
  # From a checkout instead: (cd web && npm install && npx vite build) && uv run loopx serve
  # In another shell:
curl -s http://127.0.0.1:8767/api/status
curl -s -o /dev/null -w '%{http_code}\n' -H 'Origin: https://example.com' http://127.0.0.1:8767/api/status   # 403
  # Stop: Ctrl-C in the server shell.
```

### Telegram and Lark channels

**Activation:** Off by default. With `loopx serve` running, enable a channel in the dashboard Settings page or with `PUT /api/channel-configs/<id>` (`channel-telegram` or `channel-lark`), put the credential in the environment variable the setting names, then restart `loopx serve`; settings are read only at startup. Telegram reads its bot token from `LOOPX_TELEGRAM_BOT_TOKEN`, or the variable `bot_token_env` names. Lark needs `lark-cli` on `PATH` and signed in, and the app ID in `LARK_APP_ID`, or the variable `app_id_env` names.

**Validation:** Read the settings back from `/api/channel-configs`. After the restart, the startup log line `agent system running on ... (channels=...)` lists only the channels that started.

**Disable / rollback:** Set `enabled` to `false` in the Settings page or with the second `PUT` below, then restart `loopx serve`. A `PUT` that includes `config` replaces the whole config object.

**Authority boundary:** Anyone who can message an enabled bot reaches the Manager, which can create tasks that workers run without permission prompts. Telegram accepts everyone when both `allowed_user_ids` and `LOOPX_TELEGRAM_ALLOWED_USERS` are empty, so set an allowlist; a malformed list keeps Telegram off. Lark has no sender allowlist in this release. `channel_configs` stores variable names, not secret values; `app_secret_env` is not read, because `lark-cli` holds the Lark credentials.

**Docs:** https://github.com/foolzzz/looper/blob/v2.5.0/README.md#channels

```bash
curl -s -X PUT http://127.0.0.1:8767/api/channel-configs/channel-telegram \
  -H 'Content-Type: application/json' \
  -d '{"enabled": true, "config": {"bot_token_env": "LOOPX_TELEGRAM_BOT_TOKEN", "allowed_user_ids": "123456789"}}'
curl -s http://127.0.0.1:8767/api/channel-configs
  # Restart loopx serve to apply. To disable, then restart again:
curl -s -X PUT http://127.0.0.1:8767/api/channel-configs/channel-telegram \
  -H 'Content-Type: application/json' -d '{"enabled": false}'
```

### Projects

**Activation:** Built into `loopx serve` in this release, with no switch. The first start places existing tasks in projects, one per directory. Create projects from the sidebar `+`, inline in the new-task form, through the Manager in chat, or with `POST /api/projects`.

**Validation:** `GET /api/projects` lists each project with its task and active counts; `GET /api/tasks?project_id=<id>` lists one project's tasks.

**Disable / rollback:** Projects cannot be turned off. Delete an empty project with `DELETE /api/projects/<id>`; a project that still has tasks returns 409, so move or delete its tasks first. Undoing the backfill and the required `project_id` takes a database restore from a backup made before upgrading.

**Authority boundary:** A project's default directory is where its tasks run when they name none, and workers act there without permission prompts. Projects add no sharing, access control or credentials. The API has no authentication and refuses requests from other web pages, but any local process can create, edit or delete projects: keep the default `127.0.0.1` bind and do not expose the port.

**Docs:** https://github.com/foolzzz/looper/blob/v2.5.0/docs/architecture/agent-system.md

```bash
curl -s -X POST http://127.0.0.1:8767/api/projects \
  -H 'Content-Type: application/json' \
  -d '{"name": "demo", "description": "Example project", "work_dir": "~/projects/demo"}'
curl -s http://127.0.0.1:8767/api/projects
  # Replace PROJECT_ID with the project_id returned above; only an empty project can be deleted:
curl -s -X DELETE http://127.0.0.1:8767/api/projects/PROJECT_ID
```

### loopx init

**Activation:** Per command. `loopx init` detects the `claude` and `codex` CLIs and API keys, asks which provider to use, and writes `providers.yaml` and `agents/orch.yaml`, `dev.yaml` and `acc.yaml` under the runtime root (`~/.loopx`). `--non-interactive` takes the detected defaults and `--runtime-root DIR` writes elsewhere; existing files are kept unless you confirm or pass `--force`.

**Validation:** `loopx agent validate` checks the generated agent files. Preview into a separate runtime root first, as below.

**Disable / rollback:** Remove the files it wrote, or restore your backup if `--force` overwrote files. `loopx serve` does not read these files (it uses the `agent_configs` table), although the hint `init` prints suggests running it next.

**Authority boundary:** It only writes local YAML and starts nothing. It stores no secret values; a provider that uses an API key records the variable name. The files configure the role dispatcher (`loopx dispatch`), whose Turns use the permissions described in the usage guide.

**Docs:** https://github.com/foolzzz/looper/blob/v2.5.0/docs/fork/agent-and-provider-config.md

```bash
loopx init --non-interactive --runtime-root "$HOME/.loopx-init-preview"
LOOPX_RUNTIME_ROOT="$HOME/.loopx-init-preview" loopx agent validate
rm -r "$HOME/.loopx-init-preview"
  # Then write the real files under ~/.loopx:
loopx init
```

## Known Limitations

- The Planner calls no model. Each task runs as one step, and further steps come only from chat messages sent to the Planner while the task runs. Every step is accepted on the worker's report checked against the files; the reviewer path is never started.
- A `scripts/install-local.sh` release snapshot, made by the tag path below or by `scripts/install-from-github.sh`, copies the checkout's `loopx/` package but neither builds the dashboard nor copies `web/`. Its `loopx serve` has the schema, but serves the dashboard only if `scripts/stage-dashboard.sh` ran in that checkout before installing; otherwise the API works and `/` returns 404.
- `.env` is read only from the directory above the `loopx` package: the repository root in a checkout, `site-packages` in an installed wheel, the snapshot root in a release snapshot. Outside a checkout, set `LOOPX_DATABASE_URL` in the environment.
- Most Agents-page fields (model, runtime, permission mode, concurrency, LLM profile, and the Planner and worker prompts) are stored but not applied. Concurrency is fixed at three tasks and four workers.
- Residual install gaps: on a pip or pipx install, `loopx update --rollback` still installs `loopx==VERSION` from PyPI, the upstream distribution; `scripts/install-from-github.sh` defaults to the `stable` ref, which foolzzz/looper does not have, so pass `LOOPX_REF`.
- The release-readiness Compatibility Gate still names `examples/repository-hygiene-smoke.py`, which [michaelx1993/loopx#31](https://github.com/michaelx1993/loopx/pull/31) removed.
- Channel settings apply only after a restart, and Lark has no sender allowlist.
- The dashboard has no narrow-screen layout.
- [Issue #104](https://github.com/foolzzz/loopx/issues/104) (intermittent concurrent promotion smoke) and [issue #114](https://github.com/foolzzz/loopx/issues/114) (installer candidate doctor under load) remain open.

### 升级决策

**谁需要升级：**想用 `loopx serve` agent 系统的 fork 用户，以及所有运行 michaelx1993/loopx 2.2.1 到 2.4.0 构建的用户，这些构建的 agent API 可以被任意网页驱动。依赖桌面客户端，OpenCode、Kiro CLI、Gemini CLI 或 Cline 宿主，`loopx auto-research`、`loopx multi-agent` 或 `loopx authority-shadow` 的用户应留在 v2.1.0。不依赖这些功能的角色调度器（`loopx dispatch`）用户可以升级，Goal 状态不需要迁移。

**解决了什么：**来自 dashboard、Telegram 或 Lark 的一条消息变成由 Claude Code worker 执行、并按磁盘文件检查的任务，每次 agent 运行都可查看。关闭了 agent API 的跨站漏洞：此前浏览器中打开的任何网页都能创建并启动任务、读取历史。安装和更新改为来自本 fork，不再是 michaelx1993/loopx 或 PyPI 上的上游包。同时修复了早期 agent 系统构建的问题：任务永远完成不了、文件不存在的步骤被标记完成、对话回复卡住或重复、重启后重放旧任务、dashboard 设置不生效。

**是否有破坏性变更：**有。`loopx serve` 是新命令，需要 PostgreSQL 和 Claude CLI；桌面客户端、四个宿主集成以及若干命令和 wire 字段被移除；`loopx update apply` 和 `install.sh` 安装本 fork 的 release wheel，release 没有 wheel 时拒绝，而不是安装 PyPI 上的包；agent API 对来自其他网页的请求返回 403；michaelx1993/loopx 2.3.0 和 2.4.0 构建的数据库在首次启动时向前迁移。LoopX Goal 状态不需要迁移。步骤见“文档与兼容性”。

**如何验证：**安装后，上方命令应显示 `loopx 2.5.0`，`loopx doctor` 通过。PostgreSQL 和 Claude CLI 就绪后运行 `loopx serve`，`/api/status` 返回 `"status": "running"`，带外部 `Origin` 的同一请求返回 403。

**贡献者：**发布维护者 @foolzzz；社区贡献者 @michaelx1993，共 29 个经 michaelx1993/loopx 合入的 PR（见“社区贡献者”）。

### 状态内核与控制面

**agent API 拒绝跨站请求。**它此前发送 `Access-Control-Allow-Origin: *` 并放行所有预检，浏览器里打开的任何网页都能创建并启动任务（worker 无权限确认地运行 Claude），或读取对话和运行历史。现在 `Origin` 不是服务器自身的请求返回 403，响应不带 CORS 头；服务器绑定 loopback 时 `Host` 必须是 loopback 名称，防止 DNS rebinding。curl、CLI 和 Vite 开发代理不受影响。API 仍然没有认证。（[#176](https://github.com/foolzzz/loopx/pull/176)）

PostgreSQL 保存 agent 系统的任务、步骤、活动、对话、agent 配置、LLM profile、运行记录和通道设置，`loopx serve` 启动时必须连上；上次遗留在运行中的任务启动时标记为 `stopped`。（[michaelx1993/loopx#44](https://github.com/michaelx1993/loopx/pull/44)、[michaelx1993/loopx#45](https://github.com/michaelx1993/loopx/pull/45)、[michaelx1993/loopx#48](https://github.com/michaelx1993/loopx/pull/48)、[michaelx1993/loopx#49](https://github.com/michaelx1993/loopx/pull/49)、[michaelx1993/loopx#53](https://github.com/michaelx1993/loopx/pull/53)）

worker 结果送回任务自己的 Planner，Planner 的 `failed` 结果按 `failed` 保存。只有 Claude 运行成功、JSON 报告为 `completed`、列出的改动文件存在且删除文件已不存在时，步骤才算完成；reviewer 必须返回布尔值 `passed`。（[#154](https://github.com/foolzzz/loopx/pull/154)、[#156](https://github.com/foolzzz/loopx/pull/156)）

启动时 message bus 丢弃上一轮未投递的 Planner 和 worker 消息并压缩日志，重启不再重放任务；每条回复只送达通道一次。（[#160](https://github.com/foolzzz/loopx/pull/160)、[#161](https://github.com/foolzzz/loopx/pull/161)）

任务只在自己的 `work_dir` 或项目默认目录里运行，没有服务器默认目录。首次启动把旧的 `project_root` 并入 `work_dir` 后删除，并按目录把已有任务放进项目，这次回填只执行一次，记录在 `schema_migrations`。（[#167](https://github.com/foolzzz/loopx/pull/167)、[#174](https://github.com/foolzzz/loopx/pull/174)）

控制面清理：项目状态和 Codex home 路径由一个 owner 构造；退役的本地 authority 观测接口和 `authority-shadow` CLI 由 `coordination-shadow drain` 和 `status` 取代；未使用的 `loopx.visible_governance` 被移除。（[#109](https://github.com/foolzzz/loopx/pull/109)、[#111](https://github.com/foolzzz/loopx/pull/111)、[#115](https://github.com/foolzzz/loopx/pull/115)）

### 能力与工作流

**Agent 系统。**用户结果：一条对话请求变成由 Claude Code worker 执行、并按磁盘文件检查的任务。交付层：Manager、TaskRouter（同时三个任务）、每任务一个 Planner（不调用模型，把任务作为一个步骤执行）、WorkerPool（同时四个 Claude 运行），基于类型化 message bus，加上 HTTP API 和 Web dashboard，都由 `loopx serve` 启动。最后一公里：需要 PostgreSQL 和已登录的 Claude CLI。release wheel 自带数据库 schema 和由 `scripts/stage-dashboard.sh` 打包的 dashboard，所以通过 `install.sh` 或 `loopx update apply` 安装后 `loopx serve` 可以直接运行；checkout 中构建了 `web/dist` 时使用它。（[michaelx1993/loopx#38](https://github.com/michaelx1993/loopx/pull/38)、[michaelx1993/loopx#39](https://github.com/michaelx1993/loopx/pull/39)、[michaelx1993/loopx#40](https://github.com/michaelx1993/loopx/pull/40)、[michaelx1993/loopx#41](https://github.com/michaelx1993/loopx/pull/41)、[michaelx1993/loopx#42](https://github.com/michaelx1993/loopx/pull/42)、[#179](https://github.com/foolzzz/loopx/pull/179)）

**对话。**可以和 Manager 或运行中任务的 Planner 对话；发给 Planner 的消息成为正在运行的 worker 的下一轮输入，没有 worker 时成为新步骤。Manager 复用一个 Claude 进程，流式回复，出错时也会回复错误。Chat 页列出所有 agent，已结束的只读。（[#155](https://github.com/foolzzz/loopx/pull/155)、[#158](https://github.com/foolzzz/loopx/pull/158)、[#159](https://github.com/foolzzz/loopx/pull/159)、[#162](https://github.com/foolzzz/loopx/pull/162)、[#170](https://github.com/foolzzz/loopx/pull/170)、[#172](https://github.com/foolzzz/loopx/pull/172)、[#173](https://github.com/foolzzz/loopx/pull/173)）

**运行历史。**每次 Manager、worker、reviewer 运行是一行 `llm_records`，含启动命令、工作目录、流事件、状态、token 和成本，可通过 `/api/llm-records/:id/events` 读取。历史页实时跟随运行，显示思考进度、hook、后台任务和限流，两分钟无输出时提示。（[#163](https://github.com/foolzzz/loopx/pull/163)、[#164](https://github.com/foolzzz/loopx/pull/164)、[#165](https://github.com/foolzzz/loopx/pull/165)、[#168](https://github.com/foolzzz/loopx/pull/168)、[#169](https://github.com/foolzzz/loopx/pull/169)）

**任务控制与 agent 设置。**任务以 `init` 创建，开始前可编辑；可以停止、开始、取消和删除；在 Agents 页编辑提示词和限制。worker 的 `timeout_seconds`（默认改为 86400 秒）和 `max_turns` 对每次运行生效。（[michaelx1993/loopx#46](https://github.com/michaelx1993/loopx/pull/46)、[michaelx1993/loopx#47](https://github.com/michaelx1993/loopx/pull/47)、[michaelx1993/loopx#52](https://github.com/michaelx1993/loopx/pull/52)、[michaelx1993/loopx#53](https://github.com/michaelx1993/loopx/pull/53)、[michaelx1993/loopx#55](https://github.com/michaelx1993/loopx/pull/55)、[michaelx1993/loopx#57](https://github.com/michaelx1993/loopx/pull/57)、[#166](https://github.com/foolzzz/loopx/pull/166)、[#171](https://github.com/foolzzz/loopx/pull/171)）

**项目**把任务分组，可带默认目录，决定侧边栏、Tasks 筛选以及 Manager 把任务放在哪里。（[#174](https://github.com/foolzzz/loopx/pull/174)）

**`loopx init`** 为角色调度器写入 provider 和 agent 文件。`loopx dashboard` 的 Settings 页新增 Agent config 和 Update 页，Chat 新增会话面板，用一句话即可创建 Goal。（[michaelx1993/loopx#32](https://github.com/michaelx1993/loopx/pull/32)、[michaelx1993/loopx#36](https://github.com/michaelx1993/loopx/pull/36)、[michaelx1993/loopx#37](https://github.com/michaelx1993/loopx/pull/37)）

退役：源码 checkout 的 demo 以及 `loopx auto-research`、`loopx multi-agent` 命令，原生桌面客户端及其签名更新。浏览器工作区请用 `loopx dashboard`。（[#110](https://github.com/foolzzz/loopx/pull/110)、[#127](https://github.com/foolzzz/loopx/pull/127)）

### 可选能力启用与使用

#### loopx serve agent system

**启用：**按命令启用，没有持久开关。启动 PostgreSQL，让 `LOOPX_DATABASE_URL` 指向给 LoopX 用的数据库（默认 `postgresql://localhost:5432/loopx`），登录 Claude CLI，然后运行 `loopx serve`。默认监听 `127.0.0.1:8767`（`--host`、`--port`），启动时应用 schema。`install.sh` 和 `loopx update apply` 安装的 release wheel 自带 schema 和 dashboard。在 checkout 中，`uv run loopx serve` 优先使用已构建的 `web/dist`，否则使用 `scripts/stage-dashboard.sh` 打包的副本。`scripts/install-local.sh` 快照只有在安装前于 checkout 中运行过 `scripts/stage-dashboard.sh` 时才带 dashboard。请在环境变量中设置 `LOOPX_DATABASE_URL`：`.env` 只从 `loopx` 包的上一级目录读取，在 checkout 中是仓库根目录，但在已安装的 wheel 中是 `site-packages`，在 release 快照中是快照根目录。

**验证：**`/api/status` 返回 `"status": "running"` 并列出 Manager、TaskRouter 和 WorkerPool，带外部 `Origin` 的同一请求返回 403；启动日志 `agent system running on ...` 列出已启动的通道。

**停用 / 回退：**用 Ctrl-C 或 SIGTERM 停止服务器，它会停止 Manager 的 Claude 进程并结束运行中的 worker。`loopx serve` 停止后不再运行任何东西，遗留为 `running` 的任务在下次启动时标记为 `stopped`。删除它的数据只需删除为它创建的数据库，LoopX Goal 状态不在其中。

**权限边界：**worker 在任务工作目录中运行 `claude --dangerously-skip-permissions`，拥有你的用户的文件和命令权限且没有权限确认，只给任务可以被改动的目录。HTTP API 没有认证。它拒绝来自其他网页的请求，但任何本地进程都能调用：保持默认的 `127.0.0.1` 绑定，不要暴露端口。用非 loopback 的 `--host` 时不再检查 `Host`，任何能连到端口的人都能驱动它。LoopX 本身不会在这里 merge、push 或写 Goal 状态，但 worker 可以执行你的账户能执行的任何命令，有凭据时包括 `git push`。运行记录会把完整提示词、对话记录和工具输出存入数据库。

**文档：**https://github.com/foolzzz/looper/blob/v2.5.0/docs/architecture/agent-system.md

```bash
export LOOPX_DATABASE_URL="postgresql://localhost:5432/loopx"
createdb loopx   # 仅在数据库还不存在时
loopx serve
  # 若从 checkout 运行：(cd web && npm install && npx vite build) && uv run loopx serve
  # 在另一个 shell 中：
curl -s http://127.0.0.1:8767/api/status
curl -s -o /dev/null -w '%{http_code}\n' -H 'Origin: https://example.com' http://127.0.0.1:8767/api/status   # 403
  # 停止：在服务器 shell 中按 Ctrl-C。
```

#### Telegram and Lark channels

**启用：**默认关闭。`loopx serve` 运行时，在 dashboard 的 Settings 页或用 `PUT /api/channel-configs/<id>`（`channel-telegram` 或 `channel-lark`）开启通道，把凭据放进设置中指定的环境变量，然后重启 `loopx serve`；设置只在启动时读取。Telegram 从 `LOOPX_TELEGRAM_BOT_TOKEN`（或 `bot_token_env` 指定的变量）读取 bot token。Lark 需要 `PATH` 上已登录的 `lark-cli`，并把 app ID 放在 `LARK_APP_ID`（或 `app_id_env` 指定的变量）中。

**验证：**从 `/api/channel-configs` 读回设置。重启后，启动日志 `agent system running on ... (channels=...)` 只列出实际启动的通道。

**停用 / 回退：**在 Settings 页或用下方第二个 `PUT` 把 `enabled` 设为 `false`，然后重启 `loopx serve`。带 `config` 的 `PUT` 会替换整个 config 对象。

**权限边界：**任何能给已开启 bot 发消息的人都能联系到 Manager，而 Manager 可以创建由 worker 在无权限确认下执行的任务。`allowed_user_ids` 和 `LOOPX_TELEGRAM_ALLOWED_USERS` 都为空时 Telegram 接受所有人，请设置允许列表；格式错误的列表会让 Telegram 保持关闭。本版本中 Lark 没有发送者允许列表。`channel_configs` 只存变量名，不存密钥；`app_secret_env` 不会被读取，Lark 凭据由 `lark-cli` 持有。

**文档：**https://github.com/foolzzz/looper/blob/v2.5.0/README.md#channels

```bash
curl -s -X PUT http://127.0.0.1:8767/api/channel-configs/channel-telegram \
  -H 'Content-Type: application/json' \
  -d '{"enabled": true, "config": {"bot_token_env": "LOOPX_TELEGRAM_BOT_TOKEN", "allowed_user_ids": "123456789"}}'
curl -s http://127.0.0.1:8767/api/channel-configs
  # 重启 loopx serve 生效。停用后再次重启：
curl -s -X PUT http://127.0.0.1:8767/api/channel-configs/channel-telegram \
  -H 'Content-Type: application/json' -d '{"enabled": false}'
```

#### Projects

**启用：**本版本内置于 `loopx serve`，没有开关。首次启动按目录把已有任务放进项目。可以通过侧边栏 `+`、新建任务表单、与 Manager 对话或 `POST /api/projects` 创建项目。

**验证：**`GET /api/projects` 列出每个项目及其任务数和活跃数；`GET /api/tasks?project_id=<id>` 列出某个项目的任务。

**停用 / 回退：**项目无法关闭。用 `DELETE /api/projects/<id>` 删除空项目；仍有任务的项目返回 409，需先移走或删除其任务。要撤销回填和必填的 `project_id`，只能从升级前的数据库备份恢复。

**权限边界：**任务未指定目录时在项目默认目录中运行，worker 在那里没有权限确认。项目不增加共享、访问控制或凭据。API 没有认证，会拒绝来自其他网页的请求，但任何本地进程都能创建、修改或删除项目：保持默认的 `127.0.0.1` 绑定，不要暴露端口。

**文档：**https://github.com/foolzzz/looper/blob/v2.5.0/docs/architecture/agent-system.md

```bash
curl -s -X POST http://127.0.0.1:8767/api/projects \
  -H 'Content-Type: application/json' \
  -d '{"name": "demo", "description": "Example project", "work_dir": "~/projects/demo"}'
curl -s http://127.0.0.1:8767/api/projects
  # 把 PROJECT_ID 换成上面返回的 project_id；只能删除空项目：
curl -s -X DELETE http://127.0.0.1:8767/api/projects/PROJECT_ID
```

#### loopx init

**启用：**按命令启用。`loopx init` 检测 `claude`、`codex` CLI 和 API key，询问使用哪个 provider，在 runtime root（`~/.loopx`）下写入 `providers.yaml` 以及 `agents/orch.yaml`、`dev.yaml`、`acc.yaml`。`--non-interactive` 采用检测到的默认值，`--runtime-root DIR` 写到别处；已有文件除非你确认或加 `--force`，否则保留。

**验证：**`loopx agent validate` 检查生成的 agent 文件。可以先像下面这样写到单独的 runtime root 预览。

**停用 / 回退：**删除它写入的文件；如果用 `--force` 覆盖了文件，从备份恢复。`loopx serve` 不读取这些文件（它使用 `agent_configs` 表），尽管 `init` 打印的提示建议接着运行它。

**权限边界：**只写本地 YAML，不启动任何东西，也不保存密钥值；使用 API key 的 provider 只记录变量名。这些文件配置的是角色调度器（`loopx dispatch`），其 Turn 的权限见使用指南。

**文档：**https://github.com/foolzzz/looper/blob/v2.5.0/docs/fork/agent-and-provider-config.md

```bash
loopx init --non-interactive --runtime-root "$HOME/.loopx-init-preview"
LOOPX_RUNTIME_ROOT="$HOME/.loopx-init-preview" loopx agent validate
rm -r "$HOME/.loopx-init-preview"
  # 然后在 ~/.loopx 下写入正式文件：
loopx init
```

### 已知限制

- Planner 不调用模型。每个任务作为一个步骤执行，只有在任务运行期间发给 Planner 的对话消息才会追加步骤。每个步骤都按 worker 报告与文件是否一致来验收，reviewer 流程不会启动。
- `scripts/install-local.sh` 生成的 release 快照（下方的 tag 安装方式或 `scripts/install-from-github.sh` 都会生成）复制 checkout 中的 `loopx/` 包，但既不构建 dashboard 也不复制 `web/`。它的 `loopx serve` 有 schema，但只有在安装前于该 checkout 中运行过 `scripts/stage-dashboard.sh` 时才提供 dashboard，否则 API 可用而 `/` 返回 404。
- `.env` 只从 `loopx` 包的上一级目录读取：checkout 中是仓库根目录，已安装的 wheel 中是 `site-packages`，release 快照中是快照根目录。不在 checkout 中运行时，请在环境变量中设置 `LOOPX_DATABASE_URL`。
- Agents 页的大多数字段（模型、runtime、权限模式、并发、LLM profile、Planner 和 worker 提示词）只保存不生效；并发固定为三个任务、四个 worker。
- 安装方面的遗留缺口：pip 或 pipx 安装上的 `loopx update --rollback` 仍从 PyPI 安装 `loopx==VERSION`（上游发行版）；`scripts/install-from-github.sh` 默认使用 foolzzz/looper 没有的 `stable` ref，需要传 `LOOPX_REF`。
- 发布就绪检查的 Compatibility Gate 仍列出已被 [michaelx1993/loopx#31](https://github.com/michaelx1993/loopx/pull/31) 删除的 `examples/repository-hygiene-smoke.py`。
- 通道设置重启后才生效，Lark 没有发送者允许列表。
- dashboard 没有窄屏布局。
- [Issue #104](https://github.com/foolzzz/loopx/issues/104)（并发 promotion smoke 偶发失败）和 [issue #114](https://github.com/foolzzz/loopx/issues/114)（高负载下安装候选 doctor）仍未关闭。

### 安装与升级

本版本从 **foolzzz/looper** 分发。从 v2.5.0 起，`install.sh` 和 `loopx update apply` 安装本 fork 的 release wheel，它由 Release workflow 从 foolzzz/looper 的 `v2.5.0` tag 构建，针对 PostgreSQL 跑过 wheel smoke 后附在那里的 v2.5.0 GitHub release 上，并自带数据库 schema 和 agent dashboard；最新 release 没有 wheel 或无法读取时，它们不安装任何东西并提示从 tag 安装，不再退回 PyPI 上的 `loopx` 包（上游发行版）。早于 v2.5.0 的安装仍沿用旧来源：v2.1.0 的 `loopx update apply` 安装上游 `loopx-project/loopx`（`stable`）或 PyPI 包，michaelx1993/loopx 2.1.1 到 2.4.0 构建沿用 michaelx1993/loopx，在 [#177](https://github.com/foolzzz/loopx/pull/177) 之后从 foolzzz/loopx `main` 构建的安装沿用 foolzzz/loopx 的 release，而那里不会有 v2.5.0。请用上方“Install / Update”中的两种方式之一升级到 v2.5.0 一次：用 looper 的安装器装 foolzzz/looper 最新 release 的 wheel（`curl -fsSL https://raw.githubusercontent.com/foolzzz/looper/main/install.sh | bash`，装好后 `loopx serve` 可直接使用），或在发布后检出 `v2.5.0`，可选地先运行 `scripts/stage-dashboard.sh` 让快照带上 dashboard，再设置 `LOOPX_APPROVED_DEFAULT_REF='v2.5.0^{commit}'` 通过 tag 安装门（`^{commit}` 把附注 tag 解析到 source commit），保留所选 Python 环境。之后的更新来自 foolzzz/looper。fresh clone 命令只删除本次 sync 新生成的未跟踪 `uv.lock`，`git status --short` 必须为空才会自动 promotion。已有安装请使用 fresh clone 或干净的专用 worktree，再按上方步骤 sync 和安装；没有运行打包步骤时，快照的 `loopx serve` 没有 dashboard，请改为在该 checkout 中用 `uv run` 运行。快照回滚用 `loopx update --rollback RELEASE_ID`，不会反向迁移状态；详见 [fork 使用指南](https://github.com/foolzzz/looper/blob/v2.5.0/docs/fork/usage.md#2-install)。

# Looper v2.13.159

## Release Decision

**Who should upgrade:** Operators who want a plugin or skill available to one Manager only, or who move Manager configuration between installations. Everyone else can stay on v2.13.158.

**What this release solves:** [#732](https://github.com/foolzzz/looper/pull/732) lets an operator install a global catalog plugin or skill for an individual Manager, on top of the global installs that Manager already inherits. The extras load at the Manager's next safe turn and travel with configuration export and import.

**Breaking changes:** No. Existing Managers, global installs and configuration files behave as before; the change adds one table and new optional fields. No prompt or Tool declaration changed.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#732](https://github.com/foolzzz/looper/pull/732); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.159
```

## Behavior changes

- **Per-Manager installs ([#732](https://github.com/foolzzz/looper/pull/732)):** a new table `manager_library_installs` (`looper/db/schema.sql`, created with `IF NOT EXISTS`) holds one row per Manager and catalog item with an `enabled` flag. It references the Manager (restrict) and the catalog item (cascade on delete). Only global catalog plugins and skills are accepted; project-owned items and other kinds are refused, and so are deleted or unknown Managers. Soft-deleting a Manager removes its rows (`looper/db/managers.py`).
- **Operator API and CLI:** three operator-only operations, `manager_installs.list` (risk `read`), `manager_installs.put` and `manager_installs.delete` (risk `write`), at `/api/v1/manager_installs/...` (`looper/agents/v1_domains/manager_installs.py`). They appear in the generated OpenAPI document and CLI. The list returns the Manager's explicit rows plus the enabled global plugin and skill installs that name the Manager role, marked `inherited`. Disabling an inherited global install for one Manager is refused with a conflict unless an explicit row for that item exists first.
- **Loading:** `load_installed` takes an optional `manager_id`, valid only for the manager role (`looper/agents/library.py`). Per-Manager rows are appended after the inherited ones, skipping items already inherited, and show scope `manager` in the run's library metadata. The Manager tier passes its own id (`looper/agents/tiers/manager.py`). When the library hash changes between turns, the running Claude process is restarted only if it can be stopped while idle; otherwise the turn keeps the previous launch and the refresh is retried on the next turn.
- **Read-only copies:** the read-only copy builder also loads every Manager's bundle, including cold or disabled Managers, and gives up on the copy if one fails to load (`looper/agents/read_only_copies.py`).
- **Catalog deletion:** the installation count of a catalog item includes Manager installs, and the delete confirmation states the total and the number of Manager installations (`looper/agents/catalog.py`, `looper/agents/v1_domains/catalog.py`).
- **Configuration transfer:** export writes an `installs` list (`item` kind and name, `enabled`) on each Manager that has extras, and counts `manager.installs` in the summary. Import resolves items by kind and name against the target and the file, refuses project items, unknown items, duplicates and unknown fields, and applies the rows in the import transaction. The default Manager entry may now also carry `installs` (`looper/agents/config_transfer.py`, `looper/db/config_transfer.py`). The API schema in `looper/agents/api_v1.py` and the dashboard type in `web/src/lib/api.ts` accept the new field and the `manager` scope.
- **Model-visible changes:** a Manager with extras sees those skills and plugins in addition to the inherited ones, and no others; its system prompt text is unchanged. No prompt, tool description or tool schema changes for a Manager without extras, and Managers do not get a tool to manage installs.
- **Evals and tests:** `evals/prompt_regression/dialogs.py` gains three dialogs (`manager_capability_installed`, `manager_capability_isolated`, `manager_capability_default`) with a fixture skill, taking the dialog count from 44 to 47; `evals/README.md` is updated to match. New tests: `tests/test_manager_installs.py`, `tests/test_manager_installs_db.py`, plus additions to the config transfer, CLI and read-only copy tests. The description reports 460 added test lines and 295 production lines (fixtures excluded).

## Upgrade and rollback

Re-run `install.sh` once v2.13.159 is published. The new table is created on startup; there is no data migration and no configuration change. Rolling back to v2.13.158 ignores the table, so per-Manager extras stop loading, and a configuration file exported with `installs` is rejected by the older importer. The table can stay in place.

## Optional Capability Activation & Use

### Manager plugin and skill installs

**Activation:** Off until used. Call `manager_installs.put` with a `manager_id` and an `item_id` of a global catalog plugin or skill through `/api/v1` or `loopercli manager-installs`, or add `installs` to a Manager in a configuration file.

**Validation:** Put an install for one Manager, then list it and check that the shared global installs show as inherited and the new one does not. At the Manager's next turn its run metadata lists the skill with scope `manager`; a second Manager does not list it.

**Disable / rollback:** Call `manager_installs.delete` for the item, or `put` it with `enabled` false. Deleting the install, the catalog item or the Manager removes the capability from that Manager's next safe turn.

**Authority boundary:** Operator-only; client tokens and Manager tools cannot reach it. It adds capabilities from the existing global catalog to one Manager and never to other Managers or projects. It cannot disable an inherited global install for one Manager.

**Docs:** [Agent system](https://github.com/foolzzz/looper/blob/v2.13.159/docs/architecture/agent-system.md).

```bash
loopercli manager-installs list --manager-id manager
```

### 行为变化与入口

- **每个管家的安装（#732）：**新表 `manager_library_installs`（`looper/db/schema.sql`，`IF NOT EXISTS` 创建）按管家和目录项保存一行及 `enabled` 标记。它引用管家（限制删除）和目录项（目录项删除时级联）。只接受全局目录的插件和技能；项目私有项和其他类型会被拒绝，已删除或未知的管家也会被拒绝。管家软删除时会删除其行（`looper/db/managers.py`）。
- **操作员 API 与 CLI：**三个仅限操作员的操作：`manager_installs.list`（风险 `read`）、`manager_installs.put` 和 `manager_installs.delete`（风险 `write`），位于 `/api/v1/manager_installs/...`（`looper/agents/v1_domains/manager_installs.py`），出现在生成的 OpenAPI 文档和 CLI 中。列表返回该管家的显式行，以及指名管家角色的已启用全局插件和技能安装（标记为 `inherited`）。除非先存在该项的显式行，否则为单个管家停用继承的全局安装会以冲突拒绝。
- **加载：**`load_installed` 新增可选参数 `manager_id`，仅对管家角色有效（`looper/agents/library.py`）。每个管家的行追加在继承行之后，已继承的项会跳过，并在运行的库元数据中显示范围 `manager`。管家层传入自己的 id（`looper/agents/tiers/manager.py`）。回合之间库哈希变化时，只有 Claude 进程空闲且可停止才会重启；否则本回合沿用先前的启动，下一回合再重试刷新。
- **只读副本：**只读副本构建器还会加载每个管家（含冷态或已停用的管家）的能力包，任一加载失败则放弃该副本（`looper/agents/read_only_copies.py`）。
- **目录删除：**目录项的安装数包含管家安装，删除确认文案写明总数和管家安装数（`looper/agents/catalog.py`、`looper/agents/v1_domains/catalog.py`）。
- **配置迁移：**导出时为有附加项的管家写入 `installs` 列表（`item` 的类型与名称、`enabled`），并在摘要中统计 `manager.installs`。导入时按类型和名称在目标和文件中解析目录项，拒绝项目项、未知项、重复项和未知字段，并在导入事务内应用。默认管家条目现在也可带 `installs`（`looper/agents/config_transfer.py`、`looper/db/config_transfer.py`）。`looper/agents/api_v1.py` 中的 API schema 和 `web/src/lib/api.ts` 中的控制台类型接受新字段及 `manager` 范围。
- **面向模型的变化：**有附加项的管家除继承项外还能看到这些技能和插件，别无其他；系统提示词文本不变。没有附加项的管家的提示词、工具描述和工具 schema 均无变化，管家也没有管理安装的工具。
- **评测与测试：**`evals/prompt_regression/dialogs.py` 新增三个对话（`manager_capability_installed`、`manager_capability_isolated`、`manager_capability_default`）及一个夹具技能，对话总数从 44 增至 47；`evals/README.md` 同步更新。新增测试：`tests/test_manager_installs.py`、`tests/test_manager_installs_db.py`，并补充配置迁移、CLI 和只读副本测试。描述报告新增测试 460 行、生产代码 295 行（不含 fixture）。

### 升级与回退

在 v2.13.159 发布后重新运行 `install.sh`。新表在启动时创建，无数据迁移，无配置变更。回退到 v2.13.158 会忽略该表，各管家的附加项不再加载，且带 `installs` 导出的配置文件会被旧版导入器拒绝。表可以保留。

### 可选能力启用与使用

#### Manager plugin and skill installs

**启用：**使用前默认关闭。通过 `/api/v1` 或 `loopercli manager-installs` 调用 `manager_installs.put`，传入 `manager_id` 和全局目录插件或技能的 `item_id`，或在配置文件的管家下添加 `installs`。

**验证：**为一个管家创建安装后列出，确认共享的全局安装标记为 inherited，新安装不是。该管家下一回合的运行元数据会以范围 `manager` 列出该技能；另一个管家不会列出。

**停用 / 回退：**对该项调用 `manager_installs.delete`，或 `put` 时将 `enabled` 设为 false。删除安装、目录项或管家后，该能力从该管家下一个安全回合起消失。

**权限边界：**仅限操作员；客户端令牌和管家工具无法访问。它只把现有全局目录中的能力加到单个管家，不会影响其他管家或项目，也不能为单个管家停用继承的全局安装。

**文档：**[Agent system](https://github.com/foolzzz/looper/blob/v2.13.159/docs/architecture/agent-system.md)。

```bash
loopercli manager-installs list --manager-id manager
```

# Looper v2.14.52

This is the patch release v2.14.52, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.51: the keeper control protocol and its asyncio client ([#1016](https://github.com/foolzzz/looper/pull/1016)). Nothing in the control plane uses it yet, so a running install behaves as before. No new setting is added.

## Release Decision

**Who should upgrade:** Anyone who wants to stay on the latest patch line. The change only matters to a keeper process started by hand; the control plane does not start or talk to one in this release.

**What this release solves:** [#1016](https://github.com/foolzzz/looper/pull/1016) adds the keeper's control protocol 1.0 (line-delimited JSON-RPC 2.0 on a Unix socket in the run directory) and an asyncio client for it, the groundwork for a later control-plane change. It covers controller epochs, stream subscriptions from any offset, stdin writes with an expected offset, signals and ending the child, notifications, and an orphan timer tied to controller presence.

**Breaking changes:** No. No API or migration is added or removed.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#1016](https://github.com/foolzzz/looper/pull/1016); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.52
```

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.51 upgrades directly. This release adds no migration.

## Behavior changes

- **Keeper socket ([#1016](https://github.com/foolzzz/looper/pull/1016)).** A keeper (`python -m looper.agents.keeper`) now listens on `keeper.sock` in its run directory (mode 0600) and records the socket path in its state file. The socket is created before the child starts; a path longer than the platform limit makes the keeper fail at start. `PROTOCOL_VERSIONS` is now `("1.0",)` instead of empty.
- **Controller fencing.** One controller at a time. `initialize` carries an epoch; a connection with an epoch below the highest seen is refused (`STALE_CONTROLLER`), and a newer controller replaces the old one, which is notified with `controller/replaced` and disconnected. Only the current controller can write stdin, signal or end the child, or subscribe.
- **Streams.** `stream/subscribe` replays stdout or stderr from any offset up to the current length and then follows the log; each stream has one subscription per connection. Data arrives as `stream/data` chunks of at most 64 KiB, then `stream/eof`.
- **stdin.** `stdin/write` (at most 1 MiB, base64) carries the expected offset and is rejected with `OFFSET_MISMATCH` if it differs, so a write is applied at most once. `stdin/close` closes the child's stdin.
- **Signals and end.** `child/signal` accepts TERM, INT and KILL and signals the child's process group. `child/end` ends the process tree with the fixed grace of the process-tree helper (no `grace_seconds` parameter) and returns the exit code and signal.
- **Orphan timer.** When the controller disconnects while the child runs, the orphan timer starts; a controller that initializes cancels it. A keeper that starts with a controller already attached does not start the timer.
- **Exit.** After the child exits the keeper sends `child/exited`, delivers pending data and EOF for up to 10 seconds, sends `keeper/closing` with the final stdout and stderr log lengths, and exits.
- **Client.** `looper.agents.keeper.client.KeeperClient` resolves replies in a reader and dispatches notifications in order on a separate task, with a bounded queue (64 notifications, 4 MiB of data) and an offset-only overflow replayed from the logs. A lost connection fails pending requests and never retries a write.
- **Known limits.** The review of [#1016](https://github.com/foolzzz/looper/pull/1016) noted, without a fix in this release: `child/signal` can still signal the child's pid after it was reaped, and a short stdin write that then raises can leave `stdin.log` ahead of the recorded offset so a retry appends twice. `child/end` taking no `grace_seconds` is by design here.
- **Model-visible changes:** No. No prompt, tool description, tool schema or Manager confirmation text changes.

### 行为变化与入口

- **keeper socket（[#1016](https://github.com/foolzzz/looper/pull/1016)）。**keeper（`python -m looper.agents.keeper`）现在在运行目录监听 `keeper.sock`（权限 0600），并把路径记入状态文件。socket 在子进程启动前创建；路径超过平台上限时 keeper 启动失败。`PROTOCOL_VERSIONS` 由空变为 `("1.0",)`。
- **控制者围栏。**同一时刻一个控制者。`initialize` 带 epoch；低于已见最高值的连接被拒绝（`STALE_CONTROLLER`），更新的控制者会替换旧的，旧连接收到 `controller/replaced` 后断开。只有当前控制者能写 stdin、发信号、结束子进程或订阅。
- **流。**`stream/subscribe` 从任意偏移（不超过当前长度）重放 stdout 或 stderr，再继续跟随日志；每个连接每个流只有一个订阅。数据以不超过 64 KiB 的 `stream/data` 到达，最后是 `stream/eof`。
- **stdin。**`stdin/write`（不超过 1 MiB，base64）带期望偏移，不一致时返回 `OFFSET_MISMATCH`，因此一次写入至多生效一次。`stdin/close` 关闭子进程 stdin。
- **信号与结束。**`child/signal` 接受 TERM、INT、KILL 并发给子进程组。`child/end` 以进程树工具的固定宽限结束进程树（无 `grace_seconds` 参数），返回退出码和信号。
- **孤儿计时器。**子进程运行时控制者断开即启动计时器；控制者再次 `initialize` 则取消。启动时已有控制者连接的 keeper 不会启动计时器。
- **退出。**子进程退出后 keeper 发送 `child/exited`，最多 10 秒内交付剩余数据和 EOF，再发送带 stdout、stderr 日志最终长度的 `keeper/closing`，然后退出。
- **客户端。**`looper.agents.keeper.client.KeeperClient` 在读取任务中解析回复，在单独任务中按序分发通知；队列有界（64 条通知、4 MiB 数据），溢出只记录偏移并从日志重放。连接丢失会使挂起请求失败，且从不重试写入。
- **已知局限。**[#1016](https://github.com/foolzzz/looper/pull/1016) 的评审指出但本版本未修复：子进程被回收后 `child/signal` 仍可能向其 pid 发信号；stdin 短写后抛错可能使 `stdin.log` 超前于记录的偏移，重试会重复追加。`child/end` 不带 `grace_seconds` 在此为有意设计。
- **面向模型的变化：**无。没有 prompt、工具描述、工具 schema 或 Manager 确认文本的变化。

# Looper v2.13.148

## Release Decision

**Who should upgrade:** Operators who run scenario Managers besides the default one and use schedules, configuration export/import, the v1 schedule API or Settings → Schedules. Everyone else can stay on v2.13.147.

**What this release solves:** [#695](https://github.com/foolzzz/looper/pull/695) gives every schedule an immutable Manager owner. The tasks it creates belong to that Manager, so they go through the Manager's existing reporting. The owner survives configuration export and import, shows in the schedule views and settings, and blocks deleting a Manager that still owns a schedule.

**Breaking changes:** No. Existing schedules belong to the default Manager (`manager`), and creating a schedule without an owner still gives it to that Manager. The v1 schedule and run views gain fields.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#695](https://github.com/foolzzz/looper/pull/695); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.148
```

## Behavior changes

- **Storage (#695):** `looper/db/schema.sql` adds `schedules.manager_id` (`TEXT NOT NULL DEFAULT 'manager'`, references `managers(id)` with `ON DELETE RESTRICT`) and an index on it, applied with `IF NOT EXISTS`. Old schedules therefore belong to the default Manager.
- **Immutable owner (#695):** `looper/db/schedules.py` `create_schedule` takes `manager_id` (default `manager`); `update_schedule` raises when `manager_id` is among the fields. The API (`looper/agents/schedules.py`) accepts `manager_id` only on create (a nonempty string, trimmed, else 400) and answers 400 "a schedule's owner cannot change" on update. The v1 `ScheduleCreate` schema gains an optional `manager_id`; `SchedulePatch` does not.
- **Owner checks (#695):** a new `owner_error` locks the owner row and refuses an owner that does not exist or was deleted, a disabled owner when the schedule is enabled or fires, and an owner whose task policy is `templates_only` (free-form schedules are not allowed). Creating a schedule only needs the owner to exist (a disabled owner may hold a disabled schedule). Updating a schedule other than `{"enabled": false}` answers 409 with that error.
- **Scheduler (#695):** `looper/agents/scheduler.py` checks the owner before overlap handling, before launch and before creating the task; on an error the run is recorded as not created with the reason. A created task carries `manager_id` of its schedule, so existing Manager task reporting applies.
- **Views (#695):** `schedule_view` adds `manager_id` and `manager_name`; `run_view` adds `manager_id`. The v1 read schemas list them (the run `manager_id` is required); the `SCHEDULE_WITHOUT_LAST_RUN` schema leaves out the two schedule fields. `looper/db/schedules.py` joins `managers` for the name and `schedules` for the run's owner.
- **Manager deletion (#695):** `looper/db/managers.py` `delete_manager` returns `has_schedules` when a schedule belongs to the Manager; the API answers 409 "has schedules: delete those schedules first, or disable the Manager". The check comes after the tasks check and before the bots check.
- **Configuration transfer (#695):** `looper/agents/config_transfer.py` exports `manager` on a schedule entry whose owner is not `manager`, and accepts it on import. An import skips a schedule whose owner is not an existing nondeleted Manager or one in the same file ("Manager owner conflict"), whose owner requires a template, or whose stored owner differs (owner is immutable). When applying a change to an existing schedule, the owner check also runs and a failure skips it. Import now locks the incoming schedules (`FOR UPDATE`, ordered) before Managers, matching the firing lock order.
- **Dashboard (#695):** creating a schedule in `project-schedules.tsx` shows an Owner select when a Manager other than the default exists (a disabled one is labelled "(disabled)"); it sends `manager_id` only for a non-default owner. Owners load on open; a load failure shows an alert with "Retry owners" and keeps Save disabled. An existing schedule shows "Owner: … Ownership cannot be changed." The schedule detail and `pages/schedules.tsx` show the owner when it is not the default.
- **Tests (#695):** three new files (`tests/test_schedule_manager_ownership_db.py`, `tests/test_schedule_manager_transfer_db.py`, `tests/test_schedule_manager_browser.py`) and small edits to existing schedule tests and the dashboard settings test.
- **Model-visible changes:** yes, in the Manager schedule tool (`looper/agents/ops/schedules.py`). A schedule a Manager creates through it is owned by that Manager (`call.manager_id`) instead of the default one. The `get` result omits `manager_id` and `manager_name`, so the Manager's view is unchanged. A create or update can now return an owner error. The description of a scoped Manager's run view no longer says that a schedule's tasks are the default Manager's. No tool declaration or prompt text changes.
- **Line counts:** the description reports 834 added test lines and 196 production lines (fixtures excluded); its file list shows 837 test lines and 195 production lines.

## Upgrade and rollback

Re-run `install.sh` once v2.13.148 is published. The schema change is additive and applies at startup. Rolling back to v2.13.147 leaves the new column in place and unused: schedules created by a non-default Manager then create tasks for the default Manager again, and the Manager delete guard for schedules is gone.

### 升级决策

**谁需要升级：**运行默认之外的场景 Manager，并使用定时任务、配置导出/导入、v1 定时任务 API 或 Settings → Schedules 的运维者。其他人可留在 v2.13.147。

**解决了什么：**[#695](https://github.com/foolzzz/looper/pull/695) 为每个定时任务增加不可变的 Manager 所有者。它创建的任务归属该 Manager，走现有的 Manager 汇报。所有者随配置导出导入保留，显示在定时任务视图和设置中，且仍拥有定时任务的 Manager 不能被删除。

**是否有破坏性变更：**否。已有定时任务归默认 Manager（`manager`），不指定所有者创建时仍归默认 Manager。v1 定时任务与运行视图新增字段。

**贡献者：**维护者 @foolzzz 提交 [#695](https://github.com/foolzzz/looper/pull/695)；本次 patch release 无社区贡献。

### 行为变化与入口

- **存储（#695）：**`schema.sql` 新增 `schedules.manager_id`（默认 `'manager'`，引用 `managers(id)`，`ON DELETE RESTRICT`）及索引，使用 `IF NOT EXISTS`。旧定时任务归默认 Manager。
- **所有者不可变（#695）：**`create_schedule` 接受 `manager_id`；`update_schedule` 在字段含 `manager_id` 时报错。API 仅在创建时接受 `manager_id`（非空字符串，去空白，否则 400），更新时返回 400“a schedule's owner cannot change”。v1 `ScheduleCreate` 增加可选 `manager_id`，`SchedulePatch` 不增加。
- **所有者校验（#695）：**新增 `owner_error` 锁定所有者行，拒绝不存在或已删除的所有者；定时任务启用或触发时拒绝已停用的所有者；拒绝任务策略为 `templates_only` 的所有者（不允许自由格式定时任务）。创建时只要求所有者存在（停用的所有者可持有停用的定时任务）。更新（`{"enabled": false}` 除外）返回 409 及该错误。
- **调度器（#695）：**在处理重叠、启动和创建任务前检查所有者；出错时该次运行记为未创建并附原因。创建的任务带有其定时任务的 `manager_id`，因此沿用现有 Manager 任务汇报。
- **视图（#695）：**`schedule_view` 新增 `manager_id`、`manager_name`；`run_view` 新增 `manager_id`。v1 读取 schema 列出它们（运行的 `manager_id` 为必填）；`SCHEDULE_WITHOUT_LAST_RUN` 不含两个定时任务字段。
- **删除 Manager（#695）：**`delete_manager` 在有定时任务归属时返回 `has_schedules`，API 返回 409“has schedules: delete those schedules first, or disable the Manager”。该检查位于任务检查之后、bot 检查之前。
- **配置迁移（#695）：**导出时，所有者不是 `manager` 的定时任务条目带 `manager`；导入时接受。导入会跳过：所有者不是现存未删除 Manager（也不在同一文件中）、所有者要求模板、或所有者与已存的不同（不可变）的定时任务；改动现有定时任务时同样检查所有者，失败则跳过。导入现在先对传入的定时任务加行锁（有序 `FOR UPDATE`）再锁 Manager，与触发时的加锁顺序一致。
- **仪表盘（#695）：**创建定时任务时，若存在非默认 Manager，则显示 Owner 选择（停用的标注“(disabled)”），仅非默认所有者才发送 `manager_id`。所有者加载失败时显示告警和“Retry owners”，并禁用保存。已有定时任务显示“Owner: … Ownership cannot be changed.”。详情页和 `pages/schedules.tsx` 在非默认所有者时显示所有者。
- **测试（#695）：**新增三个测试文件（ownership、transfer、browser），并小幅修改现有定时任务测试和仪表盘设置测试。
- **面向模型的变化：**有，位于 Manager 的定时任务工具（`looper/agents/ops/schedules.py`）。Manager 通过它创建的定时任务归该 Manager（`call.manager_id`），而不是默认 Manager。`get` 结果省略 `manager_id` 和 `manager_name`，故 Manager 看到的视图不变。创建或更新可能返回所有者错误。受限 Manager 的运行视图说明不再写“定时任务的任务属于默认 Manager”。工具声明和提示词文本不变。
- **行数：**描述报告新增测试 834 行、生产代码 196 行（不含 fixture）；其文件列表显示测试 837 行、生产代码 195 行。

# Looper v2.13.64

## Release Decision

**Who should upgrade:** Nobody needs to. Users see no change: the new `api` runtime type is not registered yet. Maintainers and contributors building the API runtime get its first step.

**What this release solves:** [#478](https://github.com/foolzzz/looper/pull/478) adds the first step of the API runtime: an `api` runtime adapter (in process, no executable, OpenAI Responses over an API key) and the registry support it needs, namely a typed per-adapter role restriction (Manager only), in-process detection and probing, and import messages. The adapter is not added to the runtime registry (`ADAPTERS`), so it cannot be detected, selected or started. It also adds the `openai` package as a dependency.

**Breaking changes:** No. No route, stored data, configuration or existing runtime changed; the only change for installs is the new `openai` dependency.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#478](https://github.com/foolzzz/looper/pull/478); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.64
```

## Behavior changes

- **No user-visible behavior change.** The `api` adapter (`looper/agents/runtimes/api/adapter.py`) is not in `ADAPTERS`, so it is not listed, detected or selectable, and its session cannot start (`resident_session` raises "cannot run a session in this version"). The CLI runtimes' launches and roles are unchanged.
- **New dependency:** `openai>=3.37,<4` is now a regular dependency in `pyproject.toml`. Nothing imports the SDK yet; the adapter's probe only reads the installed package version.
- **Registry changes (apply to any adapter that sets them; none of the existing ones do):**
  - `RuntimeAdapter.roles` (default `None`) restricts the roles an adapter may run. `check_roles` refuses a Profile for a role outside it, and `servable_roles` takes the runtime type and drops excluded roles. The Profile, runtime and type views, and the Planner's choosable-Profile lists pass the type through.
  - `RuntimeAdapter.in_process` (default `False`) marks a runtime with no executable. For one, the probe runs no executable, `_detect` skips the PATH check and registers `rt-<type>` only when the probe succeeds (a failed probe is logged and skipped), the runtime view's `path` is `null`, and re-detect reports the probe error instead of a missing PATH entry. The type and runtime views gain an `in_process` field.
  - Config import: for a missing in-process runtime, the skip message gives the probe error and says to Re-detect it in Settings, instead of naming an executable.
- **What the adapter does when used (code only, unreachable today):** Manager only; requires an API key provider with the exact `openai-responses` protocol, one resolved model matching the launch model and a `base_url`; the key is passed only as `LOOPER_PROVIDER_API_KEY` in the binding environment, never in argv. `resident_command` writes the system prompt to a private file (directory mode 0700) named by its SHA-256 and returns a descriptor line (`looper-api --protocol … --model … --base-url … --system-prompt-file …`) with no key. CLI methods (`run_command`, `write_turn`, `parse`) raise `RuntimeUnsupported`; `can_interrupt` is false.
- **Documentation:** the API runtime RFC and the long-horizon context plan mark stage 1 step 1 as implemented but not yet registered.
- **Model-visible changes:** None. No Manager, Worker, Planner or Reviewer prompt, and no Manager Tool, changed. The adapter builds its prompt from the Looper instructions only and is not reachable by any model today.

## Upgrade and rollback

Re-run `install.sh` once v2.13.64 is published; it installs the `openai` package with Looper. No data migration and nothing to change. Rolling back to v2.13.63 removes the adapter, the registry fields and the dependency, with no stored data affected.

## 中文摘要

### 升级决策

**谁需要升级：**无人必须升级。用户看不到变化：新的 `api` 运行时类型尚未注册。构建 API 运行时的维护者和贡献者得到它的第一步。

**解决了什么：**[#478](https://github.com/foolzzz/looper/pull/478) 加入 API 运行时的第一步：`api` 运行时适配器（进程内、无可执行文件、API key 的 OpenAI Responses），以及注册表所需的支持——按适配器限定角色的类型化限制（仅管家）、进程内类型的检测与探测、导入提示。适配器没有加入运行时注册表（`ADAPTERS`），因此不能被检测、选择或启动。同时新增 `openai` 依赖。

**是否有破坏性变更：**无。路由、存储数据、配置和现有运行时均未改动；安装层面唯一的变化是新增 `openai` 依赖。

**如何验证：**运行 `looper --version` 核对版本为 2.13.64。

**贡献者：**维护者 @foolzzz 提交 [#478](https://github.com/foolzzz/looper/pull/478)；本次 patch release 无社区贡献。

```bash
looper --version   # looper 2.13.64
```

### 行为变化与入口

- **无用户可见的行为变化。**`api` 适配器（`looper/agents/runtimes/api/adapter.py`）不在 `ADAPTERS` 中，不会被列出、检测或选择，其会话也无法启动（`resident_session` 抛出“当前版本不能运行会话”）。CLI 运行时的启动方式和角色不变。
- **新增依赖：**`pyproject.toml` 中新增普通依赖 `openai>=3.37,<4`。目前没有代码导入该 SDK，适配器的探测只读取已安装的包版本。
- **注册表变化（对设置了这些字段的适配器生效，现有适配器均未设置）：**
  - `RuntimeAdapter.roles`（默认 `None`）限定适配器可运行的角色。`check_roles` 对范围外的角色拒绝该 Profile，`servable_roles` 接收运行时类型并去掉被排除的角色；Profile、运行时、类型三种视图以及 Planner 可选 Profile 列表都传入类型。
  - `RuntimeAdapter.in_process`（默认 `False`）标记没有可执行文件的运行时。对它：探测不运行可执行文件，`_detect` 跳过 PATH 检查，仅在探测成功时登记 `rt-<type>`（探测失败则记日志并跳过），运行时视图的 `path` 为 `null`，重新检测返回探测错误而不是缺少 PATH。类型和运行时视图新增 `in_process` 字段。
  - 配置导入：缺少进程内运行时时，跳过提示给出探测错误并说明去“设置”中重新检测，而不是指向某个可执行文件。
- **适配器被使用时的行为（仅代码，目前不可达）：**仅管家；需要 API key 的 provider、精确为 `openai-responses` 的协议、与启动模型一致的唯一已解析模型以及 `base_url`；key 只以 `LOOPER_PROVIDER_API_KEY` 放进绑定环境，不进 argv。`resident_command` 把系统提示写入私有文件（目录权限 0700，文件名为内容的 SHA-256），返回不含 key 的描述行（`looper-api --protocol … --model … --base-url … --system-prompt-file …`）。CLI 方法（`run_command`、`write_turn`、`parse`）抛 `RuntimeUnsupported`；`can_interrupt` 为 false。
- **文档：**API 运行时 RFC 与长程上下文计划标记阶段 1 第 1 步已实现但尚未注册。
- **面向模型的变化：**无。Manager、Worker、Planner、Reviewer 的 prompt 和 Manager Tool 均未改动。适配器只用 Looper 指令构造提示，目前没有任何模型能触达它。

### 升级与回退

v2.13.64 发布后重跑 `install.sh`，会随 Looper 安装 `openai` 包。无需迁移数据，也无需改动。回退到 v2.13.63 会去掉适配器、注册表字段和该依赖，不影响已存数据。

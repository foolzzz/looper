# Looper v2.14.193

This is the patch release v2.14.193, a hotfix line in which each merged change ships at once. It documents two changes: [#1365](https://github.com/foolzzz/looper/pull/1365) (Lark bot-mention poll keeps a failed first window; the bot-token channel warns) and [#1366](https://github.com/foolzzz/looper/pull/1366) (startup retries reading keeper start times).

## Release Decision

**Who should upgrade:** Operators who use Lark bot @-mention intake (the `lark-cli` channel's polling, or the bot-token channel with bot senders), and operators whose `looper serve` refused to start because the `ps` read of keeper start times timed out once.

**What this release solves:** [#1365](https://github.com/foolzzz/looper/pull/1365) keeps each chat's poll boundary when the first listing fails, so the window is retried instead of lost, and makes the bot-token channel log a warning when its configuration expects messages from other bots, which it cannot receive. [#1366](https://github.com/foolzzz/looper/pull/1366) makes startup retry the keeper start-time read for about a minute before it refuses to start.

**Breaking changes:** No. The CLI, the API and the dashboard are unchanged, no new command or control is added and there is no PostgreSQL schema change. Both PRs state a behavior change (maintainer decision, intended), listed below. The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.14.193
```

**Contributors:** Maintainer @foolzzz authored [#1365](https://github.com/foolzzz/looper/pull/1365) and [#1366](https://github.com/foolzzz/looper/pull/1366); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.192 upgrades directly. There is no PostgreSQL schema change. Restart the service after upgrading, as for every release.

## Behavior changes

Read in the diffs of the two PRs. Both state: behavior change (maintainer decision, intended).

### #1365: Lark bot-mention poll keeps a failed first window; bot-token channel warns

- **Poll boundary.** In the bot-mention poll (`_poll_bot_chats`), a chat's first boundary is now stored before its listing is queried (`last_poll.setdefault`). Before, it was stored only after a successful listing, so a failed first listing lost the window and the next poll started from a new "now". The next poll now resumes from the saved boundary (still limited by the catch-up overlap and maximum age).
- **Startup warning.** For a channel that is not the `lark-cli` type (the bot-token channel), startup logs one WARNING if any explicitly bound chat uses `sender_policy: chat`, or the binding or channel sender allowlist contains a bot app id (`cli_...`). The warning says that messages sent by other bots are not received on this channel type unless the app has Lark's permission to receive bot messages, and points to the `lark-cli` channel's polling. A bot's `ou_...` open id alone cannot be told from a person's id, so it does not trigger the warning. Nothing else changes in message handling.
- **Docs.** `docs/architecture/agent-system.md` states the limit and the warning.

### #1366: Startup retries reading keeper start times

- **Retry.** In `scan_at_start`, the liveness preflight that reads keeper start times (`ps`) is tried up to 6 times, with waits of 1, 2, 4, 8 and 16 s between attempts. Each failed attempt logs a WARNING (`cannot read keeper start times (attempt n/6)`). With six `ps` timeouts of 5 s each plus the waits, it takes at most about a minute.
- **Unchanged refusal.** If all six attempts fail, startup still raises `OSError` ("cannot read keeper start times after 6 tries") and refuses to start, and nothing is ended or deleted before the preflight finishes. Before, the first failure refused at once.

### Model-visible changes

None. No prompt, tool description or tool schema changed. The new text is a log warning and documentation; neither is sent to a model.

### 行为变化与入口

以下在两个 PR 的差异中可见。两者都声明：有行为变化（维护者决定，有意为之）。

**#1365：Lark 机器人 @ 轮询保留失败的首个窗口；机器人令牌通道告警**

- **轮询边界。**在机器人 @ 轮询（`_poll_bot_chats`）中，聊天的首个边界现在在查询列表之前保存（`last_poll.setdefault`）。此前只在列表成功后保存，首次列表失败会丢失窗口，下次轮询从新的“当前时间”开始。现在下次轮询从保存的边界继续（仍受追赶重叠和最大时长限制）。
- **启动告警。**对非 `lark-cli` 类型的通道（机器人令牌通道），启动时若任一显式绑定的聊天使用 `sender_policy: chat`，或绑定或通道的发送者白名单含机器人 app id（`cli_...`），记录一条 WARNING。告警说明：除非应用拥有 Lark 接收机器人消息的权限，否则该通道类型收不到其他机器人发送的消息，并指向 `lark-cli` 通道的轮询。仅有机器人的 `ou_...` open id 无法与个人 id 区分，因此不会触发告警。消息处理的其余部分不变。
- **文档。**`docs/architecture/agent-system.md` 说明了该限制和告警。

**#1366：启动时重试读取 keeper 启动时间**

- **重试。**在 `scan_at_start` 中，读取 keeper 启动时间（`ps`）的存活预检最多尝试 6 次，两次之间等待 1、2、4、8、16 秒。每次失败记录一条 WARNING（`cannot read keeper start times (attempt n/6)`）。六次各 5 秒的 `ps` 超时加上等待，最多约一分钟。
- **拒绝不变。**六次都失败时，启动仍抛出 `OSError`（“cannot read keeper start times after 6 tries”）并拒绝启动，预检完成前不会结束任何进程或删除任何目录。此前首次失败即拒绝。

**面向模型的变化：**无。未改动提示词、工具描述或工具 schema。新增内容是日志告警和文档，均不会发给模型。

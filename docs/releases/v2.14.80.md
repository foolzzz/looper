# Looper v2.14.80

This is the patch release v2.14.80, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.79: the Chat page lists conversations opened through the client API (`loopercli chat`) as their own group ([#1087](https://github.com/foolzzz/looper/pull/1087)).

## Release Decision

**Who should upgrade:** Operators who use `loopercli chat` and want to tell those conversations apart on the Chat page. Everyone else can stay.

**What this release solves:** Conversations opened through the client API are stored like dashboard chats (channel `web`), so they showed under "Dashboard chat" with nothing marking them. [#1087](https://github.com/foolzzz/looper/pull/1087) lists them in their own group with the client's name.

**Breaking changes:** No. No setting, schema or operation is removed. `chat.list_sessions` and the `operator_chat.sessions` result gain one field, `client`; stored messages and their channel are unchanged.

**How to verify:** Check the installed version. Open a conversation with `loopercli chat`, then open the Chat page: the conversation list shows a `loopercli` group right after "Dashboard chat", and the conversation reads `via` and the client's name.

**Contributors:** Maintainer @foolzzz authored [#1087](https://github.com/foolzzz/looper/pull/1087); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.80
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.79 upgrades directly. This release has no schema change.

## Behavior changes

- **Client conversations carry their client** (`looper/db/chat.py`). `chat.list_sessions` returns, per conversation, the API client that opened it: the client id from `chat_threads.client_id` and its name from `api_clients`, or the id as the name when the client row is gone; null for a conversation no client opened.
- **`client` in the operations result** (`looper/agents/v1_domains/operator_chat_history.py`). Each session of `operator_chat.sessions` carries `client` (`{id, name}` or null); the result schema allows it.
- **Own group on the Chat page** (`web/src/components/chat-conversations.tsx`, `web/src/lib/api.ts`). The conversation list shows conversations with a client in a group `loopercli` right after "Dashboard chat", each with `via` and the client's name; the other groups no longer list them. Opening one works as before. The empty-list text now also mentions loopercli.
- **Documentation and tests.** The Chat page paragraph in `docs/architecture/agent-system.md` names the groups. Tests are in `tests/test_chat_channel_db.py`, `tests/test_api_v1_operator_chat_history.py` and `web/src/components/chat-conversations.test.tsx`.
- **Unchanged:** stored messages, their channel, the client API, `loopercli` and Lark/Telegram.
- **Model-visible changes:** None. No prompt, role text or agent tool description changes; the `client` field is in an operator-only operation result that agents do not read.

本版本是 patch release v2.14.80（热修线，每个合并的改动立即发布）。自 v2.14.79 以来只合并了一项改动：Chat 页面把通过客户端 API（`loopercli chat`）开启的对话单独分组列出（[#1087](https://github.com/foolzzz/looper/pull/1087)）。

### 升级决策

**谁需要升级：**使用 `loopercli chat` 并希望在 Chat 页面区分这些对话的运维人员。其他人可不升级。

**解决了什么：**通过客户端 API 开启的对话与仪表盘对话一样存储（渠道 `web`），因此显示在 “Dashboard chat” 下且没有任何标记。[#1087](https://github.com/foolzzz/looper/pull/1087) 把它们放进单独的分组并显示客户端名称。

**是否有破坏性变更：**否。没有移除设置、数据库结构或操作。`chat.list_sessions` 和 `operator_chat.sessions` 的结果新增一个字段 `client`；已存消息及其渠道不变。

**如何验证：**核对版本为 2.14.80。用 `loopercli chat` 开启一个对话后打开 Chat 页面：对话列表在 “Dashboard chat” 之后出现 `loopercli` 分组，该对话显示 `via` 加客户端名称。

**贡献者：**维护者 @foolzzz 提交 [#1087](https://github.com/foolzzz/looper/pull/1087)；本版本无社区贡献。

### 行为变化与入口

- **客户端对话带有其客户端**（`looper/db/chat.py`）。`chat.list_sessions` 为每个对话返回开启它的 API 客户端：来自 `chat_threads.client_id` 的客户端 id，名称取自 `api_clients`，客户端记录已不存在时以 id 作名称；不是客户端开启的对话为 null。
- **操作结果中的 `client`**（`looper/agents/v1_domains/operator_chat_history.py`）。`operator_chat.sessions` 的每个会话带有 `client`（`{id, name}` 或 null），结果 schema 已允许该字段。
- **Chat 页面的独立分组**（`web/src/components/chat-conversations.tsx`、`web/src/lib/api.ts`）。对话列表把带客户端的对话放进 “Dashboard chat” 之后的 `loopercli` 分组，每项显示 `via` 加客户端名称；其他分组不再列出它们。打开方式不变。列表为空时的提示文字也提到了 loopercli。
- **文档与测试。**`docs/architecture/agent-system.md` 中的 Chat 页面段落写明了各分组。测试在 `tests/test_chat_channel_db.py`、`tests/test_api_v1_operator_chat_history.py` 和 `web/src/components/chat-conversations.test.tsx`。
- **不变：**已存消息、其渠道、客户端 API、`loopercli` 以及 Lark/Telegram。
- **面向模型的变化：**无。提示词、角色文本和 agent 工具说明均无变化；`client` 字段位于仅运维人员使用的操作结果中，agent 不读取。

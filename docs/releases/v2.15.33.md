## Release Decision

v2.15.32 was not published (its wheel failed to start without the test extra). v2.15.33 is v2.15.32 plus the runtime dependency fix ([#1709](https://github.com/foolzzz/looper/pull/1709)). Upgrade from v2.15.31 directly to v2.15.33.

**Who should upgrade:** Anyone upgrading a server from v2.15.31, including one that already has the delivery guard, stable context, a turn budget, a Manager persona, the delivery layer, completion turns, or metrics on. The upgrade applies three migrations and one online step with every product switch off, and it changes Lark sends whose idempotency key is longer than 50 characters on both transports. Turning morning brief or mid-turn input off does not skip that key change. The mid-turn receipt fix in #1696 ships next; the account-slot integration in #1649 is included here.

**What this release solves:** The operator can recognize one group's requests once, store a default-off project-lesson foundation, and manage intent rules that do not execute yet. The API Manager runtime can speak the Messages protocol when that profile is selected. Reminders can go through the delivery layer when both switches are on, an exact operator direct message can confirm ledger items when the ledger is on, and Settings can edit cost-cap values without touching the turn budget. Long Lark idempotency keys are normalized instead of rejected.

**Breaking changes:** Yes. A Lark idempotency key longer than 50 characters is replaced with looper: plus the first 43 hex characters of the sha256 of its UTF-8 bytes, on the CLI and on the bot API, for text and for interactive cards, whether or not morning brief, outbound delivery, or any named product switch is on. Keys of length 1 to 50 are unchanged. None stays omitted. An empty explicit key still fails with an idempotency key must not be empty. Configuration import refuses cost_guard mode enforce. An API client import of an outbound_check role or layer, or of cards.actions.enabled, receives 403. A leads-backfill retry keeps the saved day count and reference time, so a shorter --days cannot shrink an old range. The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.15.33
```

**Contributors:** Maintainer @foolzzz authored the pull requests named in this body; no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once. An installation on v2.14.0 to v2.15.31 upgrades directly. Restart the service after upgrading. `web/` changed, so the release workflow rebuilds the dashboard bundle from `web/` into the wheel. This pull request does not commit that bundle.

On an upgrade from a database that has finished v2.15.31, `pending()` reports three new migrations and the online-step list gains one new marker. No other migration file in `looper/db/migrations` changed in this range. A database that has not finished an older online step still runs that older step. Older steps with recorded completion markers are skipped and are not counted here. Because these three migrations are pending, startup takes the usual `pg_dump` into the runtime root `backups/` directory before applying them, unless the operator passes `--skip-backup`. Without that bypass, a missing/incompatible `pg_dump` or failed backup aborts startup before the schema is changed. This note does not estimate how long that dump or the scans below take.

The three migrations, in `pending_order`:

- `intent_recognitions` (1810). No online step. Creates the empty table `intent_recognitions` and the partial unique index `idx_intent_recognitions_running` on `intent_recognitions (source_id) WHERE state = 'running'`. Adds `intents.recognition_id`. Widens `intents_via_check` to include `on_request` and runs `VALIDATE CONSTRAINT intents_via_check`, which scans `intents`. Drops and readds `intents_on_request`, which also scans `intents`. No business backfill and no settings insert.
- `intent_rules` (1880). No online step. Creates nine empty tables: `intent_rule_config`, `intent_rules`, `intent_rule_versions`, `intent_rule_previews`, `intent_rule_config_audit`, `intent_rule_template_contracts`, `intent_rule_hits`, `intent_rule_condition_results`, `intent_rule_hit_sources`. Adds `projects.auto_task_daily_cap` (nullable) and `projects.auto_task_config_version` (not null, default 0) and their checks, which scan `projects`. Three indexes and two triggers are created with the tables. The version trigger rejects UPDATE and DELETE. No singleton config row is inserted. No historical backfill.
- `memory_lessons` (1910). Creates six empty tables: `task_lesson_snapshots`, `memory_injections`, `memory_injection_items`, `memory_lesson_stats`, `memory_retro_runs`, `memory_weekly_cards`. Adds `projects.memory_lessons` (`off` or `on`; null means off) and checks `projects`. Replaces `memory_tombstones_deleted_via_check` so `deleted_via` may also be `lark` or `telegram`, added `NOT VALID` inside the transaction. The transactional migration also builds the indexes that are not deferred. It then deletes the online marker `memory_lessons_online` so the online step runs after commit. An existing column, constraint, or index whose definition does not match raises `RuntimeError` starting `incompatible memory lessons` and can fail startup. No lesson rows are backfilled and no feature-setting row is inserted.

The one new online step is `memory_lessons_online`. After commit it validates `memory_tombstones.memory_tombstones_deleted_via_check`, which scans `memory_tombstones`, and builds two concurrent partial indexes on `memory_candidates`: `idx_memory_candidates_lessons` on `(project_id, state) WHERE destination = 'looper'`, and `idx_memory_candidates_lesson_expiry` on `(valid_until) WHERE destination = 'looper' AND state = 'in_effect'`. A valid index with the same definition is kept. Those are the tables an operator should size. This note does not give a duration.

What still runs with every product switch off, including the delivery guard, stable context, turn budget, Manager persona, `delivery.enabled`, completion turns (`off`), and metrics:

- The recognition service is constructed and `start()` is awaited during `looper serve` startup. It runs `UPDATE intent_recognitions SET state = 'failed', finished_at = $1, error = 'interrupted by a restart; run it again' WHERE state = 'running'`. On a new empty table that matches zero rows. It does not resume a run and it does not start a recognition poll loop. If that `UPDATE` fails, startup fails with it. `stop()` updates only runs this process still has in memory.
- No new feature-setting row is seeded. Export gains `cards.actions.enabled` only when that key is already stored as `true` or `false`. An absent row is omitted. Null deletes the row. No other new system-setting export key is added by this range. Project exports also carry `execution.memory_lessons` when explicitly set to `off` or `on`; null is omitted.
- The package install depends on `anthropic`. An API-runtime probe now requires both the `openai` and `anthropic` packages. A missing package fails that probe. It does not fail startup of the default Claude Code runtime.
- Pi or DSH SDK runner generations that already exist are health-checked about every 10 seconds (`HEALTH_INTERVAL_SECONDS` 10, `HEALTH_TIMEOUT_SECONDS` 30), including while idle. A failed probe poisons that generation and uses the existing reclaim and bounded restart, which can fail sessions sharing the generation. Local probe-capacity exhaustion or an already-buffered reply skips that round; a timeout affected by host event-loop lag gets one extra probe before declaring loss. The default Claude Code native path is not covered. The health loop does not by itself fail process startup. It is not gated by the named product switches.
- While the dashboard is open, the browser polls even when the feature is off: chat settings for the ledger about every 30 seconds, and it does not call the ledger page when `ledger.enabled` is off; attention settings about every 30 seconds, and it does not fetch the summary when `attention.enabled` is off; `cost_guard.get` and `cost_holds.list` about every 5 seconds on the home Spend card, which hides headroom while the mode is `off`. These are not server loops.
- Opening Security reads its two settings even while off; the audit page can read existing reviews while review is off. The leads page reads memory settings once to decide whether to show the proposal action. Spend settings reads the guard and holds on entry, with subsequent refreshes explicit. The intent Groups tab reads recognition history on entry and polls it every 5 seconds only while a row is `running`. These browser reads do not activate a feature or start a classifier.
- Telegram inbound, for a non-status message, sets `channel_context` `forward_origin`, `quote`, or `external_reply` to true when that attribute is present. It does not copy the original sender's text. That happens whether or not the ledger is on.
- [#1703](https://github.com/foolzzz/looper/pull/1703) normalizes a key before the gated transport checks `channels.outbound.enabled`. This is the outbound gateway switch, separate from the proactive delivery layer (`delivery.enabled`). With morning brief off, no morning-brief send is attempted, and nothing else about the brief changes. Any other Lark text send or reply, and any bot-API interactive card, that passes a key longer than 50 characters is normalized on both transports. With morning brief on, the key `morning_brief:{local date}:{channel_id}:{chat}` is the post idempotency key; when that string is longer than 50 characters it is now hashed instead of rejected by the channel. The digest window is unchanged because `morning_brief.py` is not modified. [#1696](https://github.com/foolzzz/looper/pull/1696) is not in this release: its mid-turn receipt fix ships next. The #1649 account-slot integration with native mid-turn input is included.

## Behavior changes

### Runs even when the named switches are off

- **Lark keys (#1703).** See Upgrading. A server with `delivery.enabled` on is not required for the change, and having it on does not limit the change to the delivery layer. Morning brief off: no brief send. Morning brief on: a too-long brief key can be sent. The same function covers every other long key. CLI send/reply argument-validation failures and gated key-normalization failures now raise `LarkCliError(not_sent=True)`: no send started, so callers classify them as refused rather than uncertain.
- **Migrations, the recognition startup update, export, the API probe dependency, runner health, and the dashboard polls.** See Upgrading. None of these require the delivery guard, stable context, turn budget, persona, delivery layer, completion turns, or metrics to be on.
- **Import limits (#1676, #1671, #1680).** Operator configuration import refuses `settings.cost_guard.mode` `enforce` with `Configuration import cannot enable cost enforcement`, and tells the operator to import `off` or `observe` and then confirm `enforce` through `cost_guard.update`. A client-token import that includes an `outbound_check` role or layer gets 403 `Outbound check settings require operator identity`, even while outbound review is off. A client-token import that includes `cards.actions.enabled` gets 403 `Card button settings require operator identity`. These checks run at import, not because a named switch is on.
- **Account admission (#1649).** Planner and Manager turns take an account slot only when `engine.admission.enabled` is the string `true`. That switch is not one of the named switches and stays default off. While it is off, the decorator admits the turn without taking a new slot and `bind_record` returns; a native mid-turn input can still release a lease retained before the switch was turned off. No prompt change. The named switches being on does not admit Planner or Manager turns. With admission enabled, interactive turns get the interactive lane, recovered exchanges get recovery priority, and autonomous turns use background priority. A quota-frozen operator message is retained with one reset notice and can be cancelled with `/stop`; waiting remains preemptible. Native mid-turn input shares or retains the current lease instead of taking another slot.
- **Memory tools (#1657, #1662, #1681).** The default Manager still reads memory settings inside scope preparation and returns the original scope when `memory_write` is off. No `looper_memory_propose`, no new proposal candidate, no prompt change, and no send while it is off. Persona text and stable context do not turn memory write on. `from_lead` exists only when the memory tool is already listed and `sources.leads` is true. Lead-source proposals stay off while memory write or the lead source is off. The leads dashboard also adds a proposal action and the operator API adds `memory.propose_from_lead`; these require the lead source, but not `sources.manager`. Proposals only create candidates for later confirmation. With writing enabled, exact-fingerprint duplicates merge before a drafting model call; the Manager can revise its own trusted pending proposal without exposing a private proposal in a group reply. No new migration.
- **Group extraction note (#1663).** `GROUP_REQUESTS_NOTE` is appended only when the extraction window is a group window. With intents and group read off, that path does not run, so the named switches do not inject a new prompt. A server that already runs group extraction sees the new note: messages that @-mention the user, or were sent by the user, keep the existing scope; other human messages can be a request or a one-line bug even when addressed to someone else; an acceptance does not cancel the original request. No migration. No real-model eval was run for this release.
- **Acceptance commands (#1640).** The timeout starts when the launch is captured, and the process-tree watch runs in the background. Linux preflight allows a tunnel interface only when it is down, unaddressed, and unlinked (`iflink = 0`). Root may try `unshare -n`. There is no privilege escalation and no fallback to an unsandboxed run; the failure is `sandbox_unavailable`. This runs only when a project with `acceptance_checks` on actually runs an acceptance command. The named switches do not start it. No new prompt and no migration.
- **Leads backfill (#1652).** Only the explicit CLI. `looper msgflow leads-backfill --retry-skipped` retries hook-skipped windows per chat, with at most 500 events per window. It defaults to a read-only dry run; `--run` requires a finite positive `--budget-usd`. A chat blocked again by a hook is recorded in the checkpoint and excluded from subsequent retries, and lead writes and the checkpoint commit together. A retry keeps the saved day count and `as_of`. A shorter `--days` cannot shrink an old range. A checkpoint that has no saved scope requires an explicit `--days` on retry. No change on the named-switch paths. No migration.
- **Messages codec (#1667).** Used only when the selected runtime is `api` and the provider protocol is `anthropic-messages`. It does not switch the default Claude Code runtime. Delivery guard, stable context, and turn budget still go through the shared Manager path. No new migration.
- **Lessons and rules (#1668, #1669).** The DDL and the online step run, as above. Storing `projects.memory_lessons` as `on` does not start retro or injection; later slices are not in this release. `RULE_CLASSIFICATION_AVAILABLE` is false, so rules are not executed. `delivery.enabled` on is not enough to execute a rule. No new Manager tool and no new Manager or Planner prompt from these two pulls.
- **Ledger page and needs-you badge (#1674, #1687, #1682).** While `ledger.enabled` is off, page writes are refused. While `attention.enabled` is off, there is no summary and no sidebar count. The status card stays mounted when the first overview load fails and keeps its existing poll. None of these read or write because the delivery guard, stable context, turn budget, persona, delivery layer, completion turns, or metrics are on. No new migration.
- **Cost guard UI (#1676).** Does not change `manager.turn_budget_usd` or Manager admission. An absent `cost_guard.mode` means `off`; stored modes are retained. The form edits `cost_guard.daily_usd`, `cost_guard.daily_equivalent_usd`, and `cost_guard.roles.{processor,leads_check,advice_check,outbound_check,advisor}.{daily_usd,daily_equivalent_usd}`. Each cap defaults to null (no cap), accepts a finite nonnegative number, and null clears it. Sparse saves change only edited fields; an uncertain save blocks further writes until a readback. The 5-second poll is the browser behavior above. Enforce still requires the existing confirmation update.
- **Card actions (#1680).** `cards.actions.enabled` stays off. The named switches do not add card buttons. New operator operations are `card_actions.get` and `card_actions.update`, plus the generated CLI.
- **Outbound breaker (#1678).** The shared breaker runs only when `channels.outbound.enabled` is true. `delivery.enabled` on does not enable the outbound queue or the breaker. Lark and Telegram send directly while outbound is off. When outbound is on, the same event loop and app id share one breaker (30 seconds and 5 failures open it for 60 seconds, with one half-open probe). Different apps stay independent. A finished probe wakes sibling outbox scanners. No migration and no prompt change.
- **Runner health (#1675).** Covered above. If the installation's agent profile uses a Pi or DSH SDK runner, those generations are watched regardless of the named switches.
- **Eval, tests, CI, docs (#1655, #1661, #1672, #1684, #1693, #1683, #1689, #1692, #1697).** No product prompt, migration, or named-switch behavior change. #1655 adds prompt-eval `--planner-roles`, a worker profile, and `groups`. #1661 is the offline `evals.dsh_density` entry. #1672 is an explicit processor Messages eval engine; the default eval runtime is unchanged. #1684 and #1693 are test synchronization only. #1683 lets an ordinary pull request skip PostgreSQL 18 and provenance; the standalone dashboard job also skips when no frontend/staging input changed. Non-docs-only shards still stage the frontend; the rollup rejects a failed or cancelled dependency. #1689 removes the main push trigger that #1683 had added; full main validation is `workflow_dispatch`. #1692 raises the agent-system shard timeout from 20 minutes to 30. #1697 is the plan sync only.

## Optional Capability Activation & Use

### Recognize once

**Activation:** Off until the operator stores both `intents.enabled` and `intents.on_request.enabled` as the string `true`. An absent row means off. An upgrade does not write either key. The default Manager lists `looper_intents_recognize` only then, and only for the operator's own console or direct-chat turn. Preview reports the human-message count and estimated cost before a confirmed start. The source must also be a followable group/topic with an intent subscription whose confirmation is current. The default range is the seven days ending now; future, reversed, or over-thirty-day ranges are refused. A run keeps at most the latest 2,000 messages and has a 1 USD budget.

**Validation:** While either stored value is not the string `true`, the tool is absent and `intent_recognitions` operations that start a run conflict. While both are the string `true`, a preview returns counts and an estimate, and a confirmed start writes one `intent_recognitions` row in `running`, then `done` or `failed`. Restart marks a leftover `running` row `failed` and does not replay it. Intents from the run have `via` `on_request` and are not pushed one by one.

**Disable / rollback:** Store `intents.on_request.enabled` as `false`, or delete the row. Later turns omit the tool. Rows already stored remain. Downgrading past this release requires a database that has not applied `intent_recognitions`, or a restore from the pre-migration backup. This release does not delete the table on the way down.

**Authority boundary:** Operator only. Group turns, other senders, scenario Managers, and API client turns do not receive the tool. The result message to the asking direct chat bypasses the delivery layer. Dashboard runs stay on the recognition list.

### 行为

**开关都关着也会变：** #1703 改所有超过 50 个字符的飞书幂等键，不要求 `delivery.enabled`。晨报关着不发晨报；晨报开着，过长的晨报键可以发出。#1676 的配置导入拒绝 `enforce`。#1671 让客户端导入 `outbound_check` 得到 403，审查关着也一样。#1680 让客户端导入卡片开关得到 403。#1649 只有 `engine.admission.enabled` 是字符串 `true` 才让规划者和管家占账号槽；上面那些开关打开也不会占槽。启用后按交互、恢复和后台优先级排队，额度冻结时保留操作者消息并通知一次重置时间，等待可被 `/stop` 取消或抢占，原生中途输入共用或保留当前槽。#1657、#1662、#1681 在记忆写入关闭时不列工具、不写候选；人格和稳定上下文不会把记忆写入打开。线索页和 `memory.propose_from_lead` 提供提议入口，只建待确认候选；需要 `sources.leads`，不要求 `sources.manager`。写入开启后，精确指纹重复项在调用起草模型前合并；管家可以修改自己可信的待确认提议，群回复不泄露私聊提议。#1663 的群请求说明只在构造群抽取窗口时附上。#1640 的验收超时只在项目验收打开并且真的跑命令时生效。#1652 新增显式 CLI `looper msgflow leads-backfill --retry-skipped`，按聊天重试 hook 跳过的窗口，每窗最多 500 条；默认只读 dry run，`--run` 必须带正的有限 `--budget-usd`，再次被 hook 拦下的聊天记入进度并从后续重试排除，线索和进度同事务提交。#1667 不改变默认运行时。#1668 和 #1669 的表会建，但打开项目教训模式不会开始复盘，`delivery.enabled` 打开也不会执行规则。#1674、#1687、#1682 是仪表盘。#1678 的共享熔断仍要 `channels.outbound.enabled`。#1675 只覆盖已经存在的 Pi 或 DSH SDK runner。评测、测试、CI 和文档拉取请求不改变这些开关下的产品行为。普通 PR 跳过 PostgreSQL 18 和 provenance；独立仪表盘任务仅在没有前端或构建输入变动时也跳过，非纯文档测试分片仍构建前端。

**某个开关已经打开时：** 既有设置不被重写：`manager.delivery_guard.enabled`、`manager.stable_context`、`delivery.enabled` 和 `manager.metrics.enabled` 默认关，仅存储字符串 `true` 时开启。人格是 JSON 设置 `manager.persona`（`name`、`address`、`tone`、`notes` 默认空），不是布尔开关；全空时未设置。独立的常驻画像开关 `manager.profile.enabled` 仍默认关。`manager.turn_budget_usd` 默认空（关），正的有限美元数启用上限。`manager.completion_turns` 默认 `off`，`dm_only` 覆盖私聊和控制台聊天，群仍发代码通知。`user.timezone` 是可选 IANA 时区，未设则使用服务器时区；这些设置不会相互启用。 #1677 只在 `reminders.enabled` 和 `delivery.enabled` 都为真时，把已触发的提醒按 source `user_reminder`、urgency `user_set` 记录，决策固定为 `outcome=send`、`reason=urgent`、`counted=false`，夜间和每日上限不推迟，也不进摘要；决定失败仍发送；回执写入失败不重发；明确拒绝仍最多尝试发送 3 次。只有送达层开着、提醒关着，不会为提醒写 `proactive_deliveries`。提醒开而送达关时，原文、目标、键和提醒写入保持原样。两者都开时，指标关着也写决策和回执；只有指标开不增加这些记录。`user.timezone`（未设用服务器时区）只影响新决策行的本地日期，不改变提醒已存的到期时间、正文或目标。#1679 在账本关着时不拦截、不写、不代回复，即使人格、送达层或完成回合开着。默认管家的飞书或 Telegram 私聊，去掉首尾空白后整句为「确认」加空白，再加一个或多个以空白分隔的 `L-` 或 `l-` 编号，且无转发、引用或回复上下文时，会先读账本开关再解析身份。只有操作者本人可以执行：决策项确认，待办项结项，关联来源的事项转回关卡、任务或原确认入口。代码处理跳过人格和上下文编译、投递守卫及模型，不消耗模型回合预算；指标开时保留已有渠道回执与回复标记，但不产生模型回合记录和回合指标。`dm_only` 不控制这类用户命令。#1676 不改回合预算；表单可编辑 `cost_guard.daily_usd`、`cost_guard.daily_equivalent_usd` 和 `cost_guard.roles.{processor,leads_check,advice_check,outbound_check,advisor}.{daily_usd,daily_equivalent_usd}`，默认均为空（无上限），接受非负有限数，空值清除；只保存改动字段，保存不确定时须先读回。已经是 `enforce` 的安装仍按已存模式执行，导入不能把模式写成 `enforce`。#1678 在出站网关开着时，同一应用共享一把熔断器。#1648 的工具要意图和识别一次都开。#1667 要已经选了 `api` 运行时和 `anthropic-messages`。#1687 在 attention 关着时没有条数；开着且所有区块均为 `ok` 才显示准确总数，任一异常显示 `?`，超过 99 显示 `99+`，0 不显示数字。#1703 在晨报开着时改变过长的晨报键，在晨报关着时不发晨报，但其他过长的飞书键两种情况下都变。#1696 不在本版本。

#### Recognize once

**启用：** `intents.enabled` 和 `intents.on_request.enabled` 都存成字符串 `true` 之前是关。没有这一行就是关。升级不写这两个键。两个都开时，默认管家才在操作者本人的控制台或私聊回合列出 `looper_intents_recognize`。确认前先给出条数和估计花费。来源还必须是可跟随的群或话题，且有确认版本仍有效的意图订阅。默认截至当前的七天；未来、逆序或超过三十天的范围被拒绝。最多保留最新 2000 条，预算为 1 美元。

#### Security settings

**启用：** 设置 → 安全分别提供 `outbound_review.enabled` 和 `untrusted_fence.enabled`；二者默认关闭，只有存储字符串 `true` 才开启。打开设置或审计不改变开关，启用审查仍检查已启用管家是否支持 hook。

**验证：** 两个开关分别保存并确认，原本已开启时的行为保持。操作者在审查关闭时也能读取审计，客户端导入 `outbound_check` 角色或层得到 403。

**停用 / 回退：** 确认把需要关闭的开关设为 `false`；另一个开关和已有审计保留。关闭审查后，后续管家工具调用沿用不经过该审查的路径。

**权限边界：** 安全设置、对外检查角色写入、MCP 信任声明和审计要求操作者身份。这两个开关与 `manager.delivery_guard.enabled`、`delivery.enabled` 独立。

#### Ledger page and confirmation

**启用：** `ledger.enabled` 默认关闭，只有存储字符串 `true` 才开启；操作者通过设置 → 聊天或 `chat_settings.update` 修改。页面、私聊命令、人格、送达、完成回合和度量不会开启它。

**验证：** 开启后，操作者发给默认管家的私聊整句为「确认」加空白分隔的 `L-` 或 `l-` 编号，且不带转发、引用或回复上下文时，由代码处理。符合条件的决策被确认、待办被结项，来源事项转回原入口，此路径跳过模型及回合预算。

**停用 / 回退：** 通过 `chat_settings.update` 把 `ledger_enabled` 设为 false 或 null；null 删行并恢复关闭。之后页面写入被拒绝，精确私聊文字回到普通管家路径，事项和事件保留。

#### Reminder delivery

**启用：** 只有 `reminders.enabled` 和 `delivery.enabled` 都存为 `true` 时，触发的提醒才记录送达决定；二者默认关闭。只开送达不创建提醒行，送达关闭时保留提醒正文、目标、键和结算写入。

**验证：** 触发提醒按 `looper-reminder-<id>` 记录 source 为 `user_reminder`、urgency 为 `user_set`、decision 为 `send`、reason 为 `urgent`、`counted=false`。`user.timezone`（未设则服务器时区）决定送达行本地日期；夜间、每日上限和摘要不推迟提醒，决定失败仍发送，回执写入失败不重发。

**停用 / 回退：** 关闭 `delivery.enabled` 停止新增送达层写入，提醒仍走原路径。关闭 `reminders.enabled` 停止发送提醒；既有行保留。

**权限边界：** 提醒工具仍仅供操作者本人的默认管家回合使用，到期发送前重新核对机器人的操作者。送达层不新增工具或模型调用，只开度量不会新增提醒送达行。

**文档：** https://github.com/foolzzz/looper/blob/v2.15.33/docs/architecture/agent-system.md#proactive-messages-the-delivery-layer

# Looper v2.14.141

This is the patch release v2.14.141, a hotfix line in which each merged change ships at once. It documents one change: [#1248](https://github.com/foolzzz/looper/pull/1248) (adjudication: tell the Planner it may downgrade a finding and accept).

## Release Decision

**Who should upgrade:** Operators who run workflows with adjudication enabled, because the Planner's decision turn after a failed review now offers an adjudicated accept. Everyone else gets no visible change.

**What this release solves:** [#1248](https://github.com/foolzzz/looper/pull/1248) tells the Planner, on a decision turn after a review that failed only on blocking findings that adjudication can downgrade, that it may downgrade the named findings to suggestions with a reason each and then accept. Accept without adjudication stays refused.

**Breaking changes:** No. There is no migration and no API removal. The Planner's prompt text changes (see Behavior changes). The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.14.141
```

**Contributors:** Maintainer @foolzzz authored [#1248](https://github.com/foolzzz/looper/pull/1248); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.140 upgrades directly. There is no schema change.

## Behavior changes

- **The decision turn offers the adjudicated accept** ([#1248](https://github.com/foolzzz/looper/pull/1248), `looper/agents/tiers/planner.py`, `looper/agents/tiers/review_adjudication.py`). When the workflow enables adjudication, the decision follows a failed review of a step that has an acceptance condition, and downgrading the eligible blocking findings alone would satisfy that condition (`can_accept`, a check that does not change the plan), the allowed decisions list `accept` as "accept (downgrade named blocking findings to suggestions with a reason each, then accept)" and the message adds the adjudication rules. The Planner's reply carries `adjudications` with a zero-based finding index, `level` "suggestion" and a nonempty reason of at most 500 characters.
- **Accept without adjudication stays refused.** Without adjudication enabled, for a non-review result, or when downgrading would not satisfy the condition, the allowed decisions are unchanged.
- **The reply contract states the rules once** (`looper/agents/tiers/planner_protocol.py`). The adjudication paragraph of the reply contract moves into a shared `ADJUDICATION_RULES` text and now also says that a failed review cannot be accepted without the necessary adjudications in the same reply, and that `final` is included when the decision completes the task.
- **Prompt eval** (`evals/prompt_regression/tasks.py`, `evals/README.md`). The `panel_adjudicate` case now has a reviewer block a correct single-file delivery on an out-of-scope changelog rule; it passes only if the decision turn offered the adjudicated accept, the Planner accepted with a downgrade and nonempty reason, the reason is in the journal, and there was no retry.
- **Unchanged:** the storage format of journal entries, the Worker, Reviewer and Manager prompts, and dispatching.
- **Model-visible changes:** Yes. The Planner's decision message lists the adjudicated accept and the adjudication rules in the cases above, and the adjudication paragraph of its reply contract is reworded and extended ([#1248](https://github.com/foolzzz/looper/pull/1248)). The pull request states that the real-mode prompt eval runs before merge.

## 中文摘要

本版本是 patch release v2.14.141（热修线，每个合并的改动立即发布），说明一项改动：[#1248](https://github.com/foolzzz/looper/pull/1248)（裁决：告知 Planner 可以降级发现后再通过）。

### 升级决策

**谁需要升级：**启用了裁决（adjudication）的工作流的运维者，因为评审失败后的决策轮现在会提供“裁决后通过”。其他人没有可见变化。

**解决了什么：**[#1248](https://github.com/foolzzz/looper/pull/1248) 在评审仅因可降级的阻塞发现而失败后的决策轮中，告知 Planner 可以把指明的发现逐条附理由降级为建议，然后通过。未经裁决的通过仍被拒绝。

**是否有破坏性变更：**否。没有迁移，没有移除 API。Planner 的提示词文本有变化（见下文）。桥接边界不变：早于 v2.13.165 的安装须先升级到 v2.13.165。

**如何验证：**核对版本为 2.14.141。

**贡献者：**维护者 @foolzzz 提交 [#1248](https://github.com/foolzzz/looper/pull/1248)；本版本无社区贡献。

```bash
looper --version   # looper 2.14.141
```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.140 上的安装可直接升级。没有结构变更。

### 行为变化与入口

- **决策轮提供裁决后通过**（[#1248](https://github.com/foolzzz/looper/pull/1248)，`looper/agents/tiers/planner.py`、`looper/agents/tiers/review_adjudication.py`）。当工作流启用裁决、决策发生在带验收条件的步骤的评审失败之后，且仅把可降级的阻塞发现降级就能满足该条件（`can_accept`，不改动计划的检查）时，允许的决策中列出“accept (downgrade named blocking findings to suggestions with a reason each, then accept)”，消息并附上裁决规则。Planner 的回复携带 `adjudications`：从 0 开始的发现序号、`level` 为 "suggestion"、非空且不超过 500 字符的理由。
- **未经裁决的通过仍被拒绝。**未启用裁决、结果不是评审、或降级后仍不满足条件时，允许的决策不变。
- **回复契约只写一次规则**（`looper/agents/tiers/planner_protocol.py`）。回复契约中的裁决段落移入共享的 `ADJUDICATION_RULES`，并新增两点：失败的评审必须在同一回复中给出必要的裁决才能通过；决策完成任务时须包含 "final"。
- **提示词评测**（`evals/prompt_regression/tasks.py`、`evals/README.md`）。`panel_adjudicate` 用例改为评审者以超出范围的变更日志规则阻塞一个正确的单文件交付；只有决策轮提供了裁决后通过、Planner 带降级和非空理由通过、理由写入日志且没有重试，才算通过。
- **不变：**日志条目的存储格式，Worker、Reviewer 和 Manager 提示词，以及派发。
- **面向模型的变化：**有。在上述情形下，Planner 的决策消息列出裁决后通过及裁决规则，其回复契约中的裁决段落被改写并扩充（[#1248](https://github.com/foolzzz/looper/pull/1248)）。PR 称真实模式的提示词评测在合并前运行。

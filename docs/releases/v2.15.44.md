# Looper v2.15.44

Contains everything merged to main after [v2.15.43](v2.15.43.md)'s scope freeze `45fc80461` (the merge of [#1840](https://github.com/foolzzz/looper/pull/1840)), up to and including `448632f1f` (the merge of [#1874](https://github.com/foolzzz/looper/pull/1874)): 26 pull requests, each its own first-parent merge. Release pull request [#1845](https://github.com/foolzzz/looper/pull/1845) is not a change. If main has moved beyond this freeze when the release pull request merges, the tag belongs on that pull request's own head, as described in [the release procedure](README.md).

This is a security and reliability release. It closes these paths by which text or files an agent controls could act outside the agent's own session or reach someone who should not be able to act: the operator's other MCP servers in the task Manager, link previews in Telegram, an API client sharing the operator's Manager conversation, repository-controlled code in Looper's own git calls, a Python module planted in a session directory, remote content loaded by the dashboard, remote images in Lark, and the sender identity check for high-risk calls and confirmations. It also fixes four startup, upgrade and shutdown failures. The release adds one migration (2150), one dependency of the `test` extra (`markdown-it-py`), no runtime dependency and no switch. Everything takes effect without a switch except the task Manager changes, which apply only while `tasks.conversations.manager_answers` is on. Details, including every behavior change, are under Behavior changes.

## Release Decision

**Who should upgrade:** Every installation. The security fixes reach installations that give API clients a token, use the Telegram or Lark channel, open the dashboard, run tasks in git directories, or have more than one chat sender allowed to reach the Manager (#1874 matters most for installations on default settings; read Before you upgrade); the reliability fixes reach every source-checkout upgrade, every startup, and any service run on Python 3.13 or later. From v2.15.38 or earlier, upgrade straight to v2.15.44 and read [v2.15.43](v2.15.43.md), [v2.15.42](v2.15.42.md), [v2.15.41](v2.15.41.md), [v2.15.40](v2.15.40.md) and [v2.15.39](v2.15.39.md).

**What this release solves:** Each API client gets a Manager session of its own and a short task-tool list instead of the operator's `main` session. Telegram messages carry no link previews. The task Manager loads only Looper's own MCP server plus servers the operator names from their user settings. A source-checkout upgrade proves the target's dependencies install before it stops the service. A failed side connection of the memory drafter no longer stops the service at startup, startup no longer blocks the event loop on its first import, shutdown no longer fails on Python 3.13 or later, and a task Manager turn commits only its own changes. Git run by the service in agent-writable directories no longer executes code the repository controls and no longer receives the service's environment (#1861); Looper's MCP server and hook fallbacks no longer load code from a session's working directory (#1864); the dashboard no longer lets agent text make the browser fetch remote content (#1866); Lark messages cannot carry remote images or unlisted HTML tags (#1867); high-risk calls and confirmations are authorized by the sender's identity in every session, whatever the turn-context switch says (#1874).

**Breaking changes:** Yes. An API client that relied on the operator's `main` conversation, or on settings, project, schedule, provider or confirmation tools through chat, loses them (#1858); see Behavior changes. No operation or setting is removed, but behavior also changes without a switch: the task Manager's direct session no longer loads the operator's MCP servers unless the operator allows them by name, Telegram sends no link previews, and a source-checkout upgrade runs one extra dependency install before the drain. A remote image in an agent reply shows as a link on the dashboard (#1866), Lark carries image links instead of remote images (#1867), a repository whose `info/attributes` assigns a driver is refused by Looper's git calls (#1861), another allowlisted sender or a group member can no longer ask for or confirm a high-risk call, and a bot without an operator sender id has no chat sender that can ask for or confirm one while `manager.turn_context.enabled` is off, only the dashboard (#1874). The first upgrade to this release still uses the upgrade order of the version being replaced (see Upgrading). Upgrades from v2.15.42 or earlier also inherit v2.15.43's migrations, its `cryptography` dependency and its behavior changes. Installations older than the bridge must upgrade to v2.13.165 first and start once.

**How to verify:** Check the version and that the service starts and applies `manager_session_client_kind` (2150). As the operator, read `task_conversations.get` and confirm `manager_answers` is still the value you set and `manager_mcp` is an empty list unless you set it. After a message from an API client, `manager_sessions.list` still shows only your own sessions. Request any dashboard asset and confirm the response carries a `Content-Security-Policy` header (#1866). For each Lark or Telegram bot, confirm Settings → Channels shows "My ID" set to your own id (#1874; see Before you upgrade). The checks run for this document are listed under Validation.

```bash
looper --version   # looper 2.15.44
```

## Included changes

### Security: what text or files an agent controls can reach

- **[#1858](https://github.com/foolzzz/looper/pull/1858), API clients get their own Manager session.** An API client (a caller with its own client token) ran in the default Manager's `main` session: its turns shared the operator's resident transcript, with no audience filter, and the brief of a new `main` session carried the recent text of every chat, clients' included. Affected: installations that give an API client a token. Fix: upgrade. The default Manager now runs every turn of an API client in `client:api:<client id>`, with session routing on or off. The client session's tools are an explicit list: `looper_tasks`, `looper_task_create`, `looper_task_control`, `looper_task_instruct` and `looper_task_update`; any other tool name is refused as `forbidden` before its arguments are read. `looper_confirm` is not on it: a pending confirmation is keyed by chat only, so a client turn could otherwise confirm another session's item. A high-risk request a client raises (cancelling or restarting a task) therefore waits for a confirmation nobody in the client session can give, and the operator's own conversation does not see it either, so it lapses (within 10 minutes at most) unless the operator confirms it in that chat thread. A client that needs confirmable operations should use the REST operation and confirmation pair (`POST /api/v1/<op>` then `POST /api/v1/confirm`), which this release does not change; `POST /api/v1/confirm` confirms only pending actions the client itself raised through the REST operation API, not one raised in a Manager chat turn. The session's inputs are its own contract, the persona name, the project, template and workflow lists and its own message, not the operator profile, goals, ready tasks, open gates, memory, vault, leads or another chat's text. `main`'s resume brief leaves client conversations out, and a client's brief lists only that client's own. The isolation is of chat text: `looper_tasks` still reaches the Manager's tasks, so task content can reach a client session through tool results. A scenario Manager keeps its own `main` for its clients. Client sessions count under `manager.sessions.max_resident`; migration `manager_session_client_kind` (2150) lets `manager_sessions.kind` hold `client`. A start that finds no free resident slot now waits at most 60 seconds and is then refused with a fixed busy reply (before, it could wait for ever behind idle sessions that could not be stopped, such as routed groups on the Messages API runtime), and idle Messages API sessions are now reclaimed at the cap.
- **[#1865](https://github.com/foolzzz/looper/pull/1865), Telegram link previews.** A URL in a Telegram message makes Telegram's servers fetch the page to build a preview, an outbound request nobody clicked that can carry data an agent read. Affected: installations using the Telegram channel. Fix: upgrade. The Telegram application is now built with link previews disabled by default, so the text messages and edits Looper sends carry no preview.
- **[#1852](https://github.com/foolzzz/looper/pull/1852), [#1862](https://github.com/foolzzz/looper/pull/1862), [#1869](https://github.com/foolzzz/looper/pull/1869), the task Manager loads only allowed MCP servers.** The task Manager's direct session started Claude Code with the operator's own configuration and no strict MCP mode, so it loaded every MCP server the operator had configured. MCP servers run outside the sandbox with the operator's rights, and a task's directory is not trusted. The direct session now always starts with `--strict-mcp-config` and loads Looper's own server plus the servers named in the new operator-only setting `tasks.conversations.manager_mcp` (a list of up to 20 unique names of letters, digits, `_`, `-` and `.`, at most 64 characters each; default empty), a new field of `task_conversations.get` and `task_conversations.update`. Each name is resolved from the user scope only: the top-level `mcpServers` of the user's `.claude.json` (`$CLAUDE_CONFIG_DIR/.claude.json` when that variable is set). A task's project `.mcp.json` and the local scope tied to its path are never read, so a name defined only there is unresolved and a project or local definition cannot replace a user one. A name that cannot be resolved, or that is Looper's own server name, makes the task Manager refuse to start with the new reason `mcp_unresolved`; none is skipped. The generated `--mcp-config` file can hold server secrets and is deleted when its session ends or is replaced, and a changed list restarts the resident on its next turn. A plugin's own MCP servers do not load under strict mode, so they cannot be allowed by name: configure the server as a user server. A `${VAR}` in a definition is expanded by Claude Code from the task Manager's environment, so a variable that exists only in the operator's shell expands empty. The `task_conversations.update` operation description says "user scope only". This applies only while `tasks.conversations.manager_answers` is on.
- **[#1874](https://github.com/foolzzz/looper/pull/1874), authorize high-risk calls and confirmations by sender identity in every session.** The Manager decides who may ask for a high-risk call and who may confirm one from the speaker of the turn. That speaker was set only when `manager.turn_context.enabled` was on and the turn was not in a routed session. With the switch off, which is the code default, or in a routed non-main session, a sender who could reach the Manager and was not classified was treated as the operator for high-risk calls and confirmations. Another allowlisted sender or a group member could therefore ask for a high-risk call, or confirm the operator's pending one by sending the next message in the chat. Affected: installations with more than one allowlisted chat sender or a group, on default settings, or with routed non-main sessions (which expose no tools by default, so the exposure there exists only with scoped grants). Fix: upgrade. Every user turn is now classified (`manager_turn_context.identify`, a new `classify_speaker` preparation step before the turn begins), whatever the switch or the session, and a bot-channel turn whose speaker is unknown is refused like a non-operator's (unknown speaker refused); a refused confirmation lapses the pending call. The dashboard without an API client stays the operator, and API clients stay clients. The turn context is still rendered only with the switch on, so model-visible text is unchanged. Operator on a bot channel: a Lark or Telegram bot has an operator only when its `operator_sender_id` is set (Settings → Channels, "My ID": one id from the bot's own allowlist). A bot without one has no operator in chat, so with the switch off no chat sender of that bot can ask for or confirm a high-risk call: they are refused with "this bot has no operator id set" until you set it, and only the dashboard can do it.
- **[#1861](https://github.com/foolzzz/looper/pull/1861), git in agent-writable directories.** Git commands the service runs in task, step and worktree directories could execute code that the repository itself controls (hooks, configured programs, filter, merge and diff drivers, signing and ssh programs) with the service's environment, which can include database credentials. An agent that can write those directories could arrange for such code to run after its own run and time budget had ended. Affected: every installation that runs tasks in a git directory. Fix: upgrade. Every git call in those directories now goes through one helper (`looper/agents/git_safe.py`) that overrides the settings which name a program, builds the child's environment from an allowlist (the database URL, `PG*` variables, tokens, provider keys, proxies and the ssh agent no longer reach git), and refuses a directory whose `.git` is not the repository git would use for it or whose `info/attributes` (or a checked-out submodule's) assigns a filter, diff or merge driver. `.gitattributes` itself and drivers defined in the user's or system configuration keep working; drivers defined only by the repository's own configuration, or by its checked-out submodules, are neutralized. A test fails when a direct `git` process call appears in `looper/` outside a short, reasoned allowlist (Looper's own checkout and upgrade, a remote clone into a new directory, `git --version`, the operator's own CLI, and the operator's knowledge vault, whose commit hooks run by design). Known limitation: the helper reads the repository's driver definitions just before each command, so a driver definition written into the repository after that read and before git reads it is not stopped. That code runs as the same system user as the agent with only the allowlisted environment (no database URL or password, no Looper token, no provider key, no proxy, no ssh agent), and after each command (except inside a verification cache block, which skips the re-check) the helper checks again and logs a warning naming the task, step and driver when one appeared. A follow-up is recorded for it.
- **[#1864](https://github.com/foolzzz/looper/pull/1864), Looper's MCP server launch.** A Looper child process that carries a session token, or runs in a session's working directory, started its Python module with the working directory on the import path, so a package planted in that directory could be imported instead of Looper's own code. That is a privilege escalation across Looper sessions that share a working directory. Affected: installations whose agents share a working directory, and the operator's own Claude Code sessions, whose directory an agent may have written to. Fix: upgrade. Looper's MCP server entry (Workers, Planners, Managers and task Managers) now starts with an absolute interpreter and `python -I -m looper.cli mcp-server`. The Claude Code user-scope MCP entry and the SessionStart hook use the same isolated form when there is no `looper` console script, and the profile reader the hook starts runs `python -I -m`. The service unit's own command is unchanged: it uses the console script when one exists, and `-I` there would change the command the upgrade check compares; the remaining case is an installation with no console script and an agent-writable directory at `service install` time.
- **[#1866](https://github.com/foolzzz/looper/pull/1866), dashboard remote content.** A Markdown image in an agent reply was rendered as an image, and dashboard pages sent no Content-Security-Policy, so a prompt-injected agent could move data it had read to another host through the operator's browser; links could also hide their real destination behind display text. Affected: every installation whose operator opens the dashboard. Fix: upgrade. Every dashboard page and asset now sends a Content-Security-Policy that allows only same-origin scripts, styles, fonts, images (plus `data:` and `blob:`) and connections, with `object-src 'none'`, `base-uri 'none'`, `frame-ancestors 'none'` and `form-action 'self'`. Markdown images in agent text render as a link, `image: <alt> (host)` (a plain label inside a link). Links in agent text are resolved the way the browser resolves them: a link to this site stays an internal link; a link to another http(s) site shows its resolved host next to the text, opens in a new tab with `noopener noreferrer`, sends no referrer and keeps no `title`; any other scheme (`javascript:`, `mailto:`) and email autolinks render as plain text. The host label is dropped only when the text is itself an address with the same scheme, host and port as the destination. A same-site link whose text reads as another site's address gets a "(this site)" marker. Bidirectional-text control characters are stripped from agent text, including character references and image alt text, so they cannot reorder a host label. The lead source link, the ledger reference link and the task-detail template input link use the same component, and a source address that is not a web address renders no link.
- **[#1867](https://github.com/foolzzz/looper/pull/1867), Lark remote images and HTML (defense in depth).** A remote Markdown image in a Lark post or card is a URL a client or platform may fetch when it renders, and HTML in agent text can load resources the same way. Affected: installations using the Lark channel. Fix: upgrade. Looper now neutralizes agent Markdown in the bot-API message body, the CLI `--markdown` body (send, reply and edit) and the card body, in one bounded pass without enumerating URL shapes. An image is kept only when its target is exactly a Lark image key. A plain `http(s)` image target becomes a link `image: [alt (host)](url)`, fetched only on a click; every other image form (reference-style, angle-bracket, titled, protocol-relative, entity-encoded, `data:` and the like) has its `!` written as `&#33;`. Every HTML tag opener has its `<` written as `&#60;`, except `http(s)` and `mailto` autolinks and Lark's own tags (`at`, `a`, `br`, `hr`, `person`, `local_datetime`, `text_tag`, `number_tag`, `raw`, `font`, `u`) carrying only the attributes listed for them. Fenced code and inline code are preserved; where the code boundary is ambiguous the whole run of lines is neutralized, so a code sample may show `&#33;[` instead of `![`. Plain `text` messages are not Markdown and are unchanged. This is defense in depth: Lark's documentation does not say how its post `md` tag decodes the numeric entities `&#60;` and `&#33;` or what the card component does with unlisted tags, so a literal entity may show where a character was escaped; it still loads nothing. How Lark unfurls plain links is also undocumented, and a link may still be previewed by the platform.

### Reliability

- **[#1849](https://github.com/foolzzz/looper/pull/1849), `looper service upgrade` installs the target's dependencies before the drain.** Before, the dependency sync (`uv sync`) ran after the stop and the fast-forward merge; when it failed (index unreachable, a wheel missing) the failure path restarted the service on the already-merged checkout with the old environment, so startup could run the migrations and then crash at import in a restart loop, and the suggested `looper service restart` did not help. Now `FULL` and `CONTROL_PLANE` source-checkout upgrades, in the same prepare phase as the dashboard build, export the target tree (without `web`, `docs`, `tests` and `evals`) and run the same `uv sync --extra test --inexact` with the service interpreter into a throwaway environment, with the checkout's local `uv.lock` as the starting point. That proves the target installs, including building the package itself, and leaves every wheel in the uv cache. A failure there aborts the command with the service never drained or stopped. After the stop, the real sync runs with `UV_OFFLINE=1`. If it still fails, the checkout is reset to the commit it had before the merge, the local `uv.lock` is restored, the previous environment is re-synced offline from the cache, the previous version is restarted and the command fails naming the step and the state. If the reset itself fails, the service stays stopped and the message gives the exact next step; no `looper service restart` hint is attached to this failure. Wheel upgrades and dashboard-only upgrades are unchanged.
- **[#1853](https://github.com/foolzzz/looper/pull/1853), startup imports before the event loop.** The first import of the dashboard domain package happened inside the `http` startup step on the event-loop thread; it imports over a hundred modules and blocked the loop for seconds, which the loop watchdog logged as `event loop was blocked`. `serve_agent` now calls `preload_domains()` before `asyncio.run`, so the import cost falls in the pre-loop `imports` step. The registry, the operations and the OpenAPI document are unchanged. A domain module that fails to import now raises during pre-loop startup instead of in the `http` step: still a startup failure, with the same error.
- **[#1855](https://github.com/foolzzz/looper/pull/1855), a failed side connection no longer stops the service.** `looper serve` could stop right after it reported ready because the memory drafter's own `LISTEN` connection failed at startup. The drafter now tries three times, one second apart, logs `memory drafter listener unavailable ... drafting polls instead`, and carries on; drafting already polls every tick and the listener only shortens the wait. The loop retries the connection once per tick until it attaches. The control-plane lock and the main pool still fail startup as before. The cause of the failing connection on the affected machine is unconfirmed.
- **[#1851](https://github.com/foolzzz/looper/pull/1851), HTTP shutdown on Python 3.13 and later.** Shutdown counted open connections with `asyncio.Server._active_count`, which CPython 3.13 and later do not define, so shutdown raised `AttributeError` before it finished aborting late connections. One helper now reads `_active_count` when it exists, otherwise the size of `_clients`, otherwise the handlers the server already tracks; reading the count never raises. Grace and cleanup deadlines are unchanged.
- **[#1847](https://github.com/foolzzz/looper/pull/1847), [#1843](https://github.com/foolzzz/looper/pull/1843), network pause fixes.** Both apply only while network pause is on, except the log line. With the switch on, task detail reads the active pause and the task's status and stored phase in one statement and projects `phase` from that status, so a request that loaded the task while it was still ready reports `waiting` (or `waiting_user` after expiry) instead of `pending` next to the pause; while a pause is active the response's `status` and `group` come from the same read, and an ended task keeps its phase. With the switch off, task detail still does not query the pause table. An invalid stored `engine.network_pause.max_pause_seconds` is now logged once per distinct value instead of on every read; the fallback duration and the warning text are unchanged.

### Task Manager, off by default

- **[#1848](https://github.com/foolzzz/looper/pull/1848), commit only this turn's own changes.** A direct-mode task Manager turn on a worktree task used to commit everything pending, including the user's half-written changes, under the Manager's name. The turn already snapshots the working tree at its start and end; it now commits only the paths it changed, through a new `step_workspaces.commit_paths` (`commit --only` on an explicit path list; other staged and unstaged changes stay where they are, and linked paths are never committed). A path that was already dirty when the turn began is never committed, even if the turn edited it too; a turn that changed no file makes no commit. The `turn_summary` event gains optional `uncommitted` (paths left because they were dirty before the turn) and `unverified` (paths whose owner could not be settled within the hashing budget of 8 MiB per decision and 1 MiB per file) lists, only present when non-empty, and the task thread appends a fixed Chinese sentence naming them. A staged rename is handled as one change of two paths. `in_place` and non-direct turns are unchanged. This applies only while `manager_answers` is on.
- **[#1859](https://github.com/foolzzz/looper/pull/1859), the task thread shows every refusal reason.** The dashboard's list of refusal reasons lacked `manager_answers_off` and `mcp_unresolved`, so such an event was parsed as unknown and dropped. Both now render as `已拒绝（<reason>）`, and a test fails when any dashboard list of task-event values differs from the server's enumeration. No server change.

### New command and internal changes

- **[#1863](https://github.com/foolzzz/looper/pull/1863), the `looper-edit` command, not wired into any agent.** Installing the package adds `looper-edit`: `replace <file>` makes an exact text replacement from JSON on stdin (`old`, `new`, optional `count`, a maximum number of matches), and `patch` applies a multi-file unified diff, all or nothing; a mismatch prints the conflict and changes nothing, and paths that resolve outside the working directory are refused. It uses only the standard library. Nothing calls it: no prompt, tool list or launch path is wired to it yet, so it changes no agent's behavior. The command module is excluded from the service restart fingerprint; the component manifest changes, so the control-plane fingerprint changes once.
- **[#1860](https://github.com/foolzzz/looper/pull/1860), RFC only.** The task Manager safety boundary (section 25 of the task-sessions RFC). It changes no code.
- **Tests and CI.** [#1844](https://github.com/foolzzz/looper/pull/1844) and [#1854](https://github.com/foolzzz/looper/pull/1854) pin, in tests only, that each converted migration's first `apply` reports work and its second does not, and that it was pending before the first. [#1856](https://github.com/foolzzz/looper/pull/1856) makes a missing staged dashboard a local skip and a CI failure, and adds a guard step to the Python and installed test workflows. [#1846](https://github.com/foolzzz/looper/pull/1846) and [#1857](https://github.com/foolzzz/looper/pull/1857) run the PR agent tests as eight shards and split a test file heavier than 300 seconds by recorded per-test time. [#1850](https://github.com/foolzzz/looper/pull/1850) syncs the development plan. None of these changes the installed service. Apart from the new contract of the API client session (#1858), nothing in this release changes the model-visible text of an existing session: the pinned prompt, section and turn baselines are unchanged, and only launch signatures change (the MCP command of #1864 is part of the signature).

## Before you upgrade

Check these before you upgrade; each one changes what a chat or an API client can do after it.

1. **Every enabled bot channel has its operator identity configured.** For each enabled Lark, `lark_bot` and Telegram channel, open Settings → Channels and check that "My ID" (`operator_sender_id`) holds one id from that bot's own allowlist (a Lark open_id is per app, so each bot names its own). Without it the bot has no operator in chat, and high-risk operations from that chat are refused after the upgrade (#1874). The dashboard is unaffected.
2. **API clients that need confirmable operations use the REST operation and confirmation pair.** `POST /api/v1/<op>` followed by `POST /api/v1/confirm` is unchanged by this release; the confirmation endpoint confirms only pending actions the client raised itself through the REST operation API in the same session. A confirmable operation asked through the Manager chat API can no longer be confirmed by the client: it lapses unless the operator confirms it in that chat thread (#1858, #1874).
3. **Remote content in replies is shown differently.** On the dashboard, external images in model replies now show as links with their host (#1866). Telegram messages no longer show link previews (#1865). Lark messages carry image links instead of remote images (#1867).

**Dependency note.** The `test` extra adds `markdown-it-py` (and its dependency `mdurl`); the runtime dependencies are unchanged. `install.sh` does not install the test extra, but a source-checkout upgrade (`looper service upgrade`) syncs with `--extra test`. The machine therefore needs both packages available at that moment, from the package index or from a warm uv cache. Because the upgrade that installs v2.15.44 syncs after the stop (see Upgrading), provide them before you upgrade.

## Upgrading

Upgrade straight to v2.15.44 from any release since v2.15.39. From v2.15.38 or earlier read [v2.15.43](v2.15.43.md#upgrading-from-v21538-or-earlier), [v2.15.42](v2.15.42.md#upgrading-from-v21538-or-earlier) and [v2.15.39's upgrade requirements](v2.15.39.md#upgrading-from-v21537-or-earlier). From v2.15.42 or earlier you also receive v2.15.43's migrations 2100 and 2120 and its new `cryptography` 46.x dependency; read its [upgrade notes](v2.15.43.md#upgrading-from-v21538-or-earlier).

**Migrations.**

| Order | Migration | What changes |
| --- | --- | --- |
| 2150 | `manager_session_client_kind` | Rebuilds the check on `manager_sessions.kind` from its current values plus `client`, created `NOT VALID`; online step `manager_session_client_kind_online` validates it after commit, so no scan holds the schema lock. `manager_sessions` holds Manager session rows, not chat history. There is no down migration: before rolling back to an older release, delete the `manager_sessions` rows with kind `client`. |

**Dependencies.** No runtime dependency is added or changed. `pyproject.toml` gains the `looper-edit` console script (#1863) and `markdown-it-py>=3,<5` in the `test` extra (#1867), which its tests use to check the neutralizer against a Markdown renderer; see the dependency note under Before you upgrade.

**The upgrade order changes with this release, and the upgrade command is the code of the version being replaced.** `looper service upgrade` runs from the service's own checkout and does not re-exec the target's code, so the upgrade that installs v2.15.44 still syncs dependencies after the stop (the order of v2.15.43). The new order (a throwaway-environment install before the drain, an offline sync after the stop, and a rollback to the previous commit on failure) applies from the first upgrade made from v2.15.44 onward. The extra install adds its duration to `prepare_seconds` and takes the download out of the stopped interval (`gap_seconds`).

Keep the pre-migration backup for downgrade. Installations older than v2.13.165 must upgrade to v2.13.165 first and start once.

## Behavior changes

### Without a new switch

- **API clients (#1858).** An API client's chat turns no longer run in `main`: they have no continuity with the operator's conversation, and the operator's dashboard and direct-chat text, notes, profile, goals, ready tasks and open gates are not in their input. A client that relied on "what I said in the dashboard" loses it. Its session has the five tools listed under Security instead of the Manager's full catalogue, so through chat it can no longer change settings, projects, schedules, providers, models, the catalog or concurrency, read costs or the overview, reply to a gate, or confirm an operation, including one it raised itself (see Security for what happens to it). A client turn needs a runtime with the platform-tools-only launch mode (Claude Code or the Messages API runtime); on another runtime it is answered with the usual "choose a supported Agent Profile" error. It uses Settings' Agent Profile, not the operator's `/profile` choice for `main`; `/profile`, `/todo` and `/gates` get a fixed "this session can't ..." reply for clients. `main`'s resume brief leaves out API client conversations. `manager_sessions.list` does not list client sessions and `reset` works on the operator's sessions only. Up to `max_resident` processes now include client sessions; a start behind a full cap shows 「排队中：其他会话正忙」 and is refused with a fixed Chinese busy reply after 60 seconds, which also applies to routed groups when session routing is on. For an installation with no API client, the prompt, tool list and command line of `main` and of routed groups are as before. The API's endpoints and response shapes are unchanged.
- **Telegram (#1865).** No link in a message or edit Looper sends expands into a preview card, whoever wrote the link. Message text, parse mode and chunking are unchanged. Lark is not touched by this change.
- **Source-checkout upgrade (#1849).** One extra `uv sync` before the drain for `FULL` and `CONTROL_PLANE` plans; the post-stop sync is offline and no longer falls back to the network; a dependency failure after the stop now resets the checkout and restarts the previous version instead of restarting the target. It applies from the first upgrade made from this release (see Upgrading).
- **Startup and shutdown (#1853, #1855, #1851).** Domain modules import before the event loop; a domain import failure surfaces earlier; the memory drafter's listener failure is a warning and a retry per tick instead of a stopped service; shutdown counts connections on Python 3.13 and later.
- **Operator API (#1852, #1862, #1869, #1848, #1858, #1863).** `task_conversations.get` and `task_conversations.update` gain the field `manager_mcp` (default `[]`); `update` is still an operator-only, high-risk, confirmed operation, and the only way to change the list. The `refused` event reason `mcp_unresolved` and the optional `turn_summary` fields `uncommitted` and `unverified` are new; both are reachable only while `manager_answers` is on. `manager_sessions.kind` accepts `client`. Installing the package adds the `looper-edit` command; nothing calls it.
- **Dashboard task thread (#1859).** A task-thread refusal with reason `manager_answers_off` or `mcp_unresolved` is now shown instead of dropped; the refusal's final text was already shown.
- **Logs (#1843).** An invalid stored network-pause maximum warns once per value.
- **Chat authorization (#1874).** With `manager.turn_context.enabled` off (the default) or in a routed non-main session, another allowlisted sender or a group member can no longer ask for a high-risk call themselves, and can no longer confirm the operator's pending call by sending the next message in the chat; both are refused as operator-only and a refused confirmation lapses the pending call. A bot with no `operator_sender_id` has no operator in chat: with the switch off, no chat sender of that bot can ask for or confirm a high-risk call until the id is set, and only the dashboard can. The dashboard without an API client stays the operator and API clients stay clients. A tool added later to a routed non-main session is authorized by identity too; the default allowlist of those sessions lists no high-risk tool today. Card buttons are unchanged. No model-visible text changes.
- **Dashboard (#1866).** External images in agent replies show as links instead of loading; links in agent replies and lead source links show their host and open in a new tab without a referrer or title; a same-site link whose text reads as another site's address gets a "(this site)" marker; `mailto:` links and email autolinks render as plain text and a relative-path image becomes a same-site link; a lead source address that is not a web address renders no link; every dashboard page and asset sends a Content-Security-Policy, and `Referrer-Policy: same-origin`, which only pages sent before, now goes with every asset. The dashboard has no inline script or style and loads no third-party host, so nothing the dashboard itself needs is blocked.
- **Lark (#1867).** A remote image in agent Markdown reaches Lark as a link with its host (plain URLs) or as text with an escaped `!` (other forms); other HTML tags show as literal text (a tag-like `<word` outside code is sent as `&#60;word`), and a literal entity may show where Lark does not decode it. Image keys, ordinary links, code and Lark's own tags are unchanged; Lark's own handling of plain links is too.
- **Git (#1861).** Drivers defined by a repository's own configuration (a clean or smudge filter, textconv, a merge driver) no longer run in Looper's git commands, so a repository that depends on its own repository-level LFS filter definition (not the user-level one) sees plain content from them. A repository whose `.git/info/attributes` (or a checked-out submodule's `info/attributes`) assigns a filter, diff or merge driver, or whose `.git` is a link that is neither a linked worktree's nor a submodule's (for example one made with `--separate-git-dir`), is refused: step workspaces report `GitError` with reason `repository_refused:attributes_driver`, `repository_refused:git_dir_mismatch` or `repository_refused:outside_worktree` (drivers that `.gitattributes` references but the repository's own configuration defines are neutralized, not refused), and other call sites treat git as unavailable. See the known limitation under Security. Each command costs a few extra short git processes (about 8 ms each as measured in the pull request); checks are remembered for at most 120 seconds while the files they read are unchanged.
- **MCP launch (#1864).** The MCP entry's command line gains `-I` and an absolute interpreter path. Without a console script, the hook and the Claude Code MCP entry use `python -I -m looper.cli`. A hook already installed without `-I` is still recognised as installed and is not rewritten. A source checkout that is not installed no longer finds `looper` through the working directory or `PYTHONPATH` for these children.

### While `manager_answers` is on

With `manager_answers` off none of this is reachable. With it on: the direct session loads no MCP server of the operator's beyond the names in `manager_mcp`, so an operator who relied on the previous behavior must add those names once with `task_conversations.update`; a task Manager whose allowed name is not a user-scope server refuses to start with `mcp_unresolved`; and a worktree turn commits only the paths it changed (see Task Manager above).

### While network pause is on

Task detail reports `phase` from the status read together with the pause (#1847). With the switch off, nothing changes and the pause table is not read.

### Task Manager MCP allowlist

**Activation:** The list is empty by default, so the task Manager's direct session loads only Looper's own MCP server. As the operator, read `task_conversations.get`. Submit `manager_mcp` as a list of names through `task_conversations.update` and complete the returned confirmation through `POST /api/v1/confirm`. Each name must be a user-scope server in the user's Claude Code settings (`claude mcp add --scope user`); a name defined only in a project or local scope is not found. It matters only while `tasks.conversations.enabled` and `tasks.conversations.manager_answers` are on. Null or an empty list restores none.

**Validation:** Read `manager_mcp` back. With a name that is not a user-scope server, a message to a task target is refused in the task thread with `mcp_unresolved` naming the server, and no task Manager process starts. With a user-scope server, a new task Manager session loads exactly Looper's server and that one. Changing the list restarts the resident on its next turn. Do not point this at a production task.

**Disable / rollback:** Submit `manager_mcp` as null or `[]` and confirm. The resident restarts on its next turn without the allowed servers. This does not turn the task Manager off; `manager_answers` does that.

**Authority boundary:** Both operations are operator-only and the update is a high-risk confirmation. An allowed server runs outside the sandbox with the operator's rights and the permissions it holds, which is why only a user-scope definition (not a task's project file) can be allowed. The setting does not give any other sender a new tool.

包含 [v2.15.43](v2.15.43.md) 范围冻结点 `45fc80461`（#1840 的合并）之后、至 `448632f1f`（#1874 的合并）为止合入 main 的全部改动：26 个 PR，各自一个第一父链合并。发布 PR #1845 不算改动。若发布 PR 合入时 main 已越过冻结点，tag 应打在发布 PR 自己的 head 上。

这是一个安全与可靠性版本。它关闭这些「agent 可控的文本或文件越出自己会话、或到达本不该有权限的人」的路径：任务管家加载操作者的其他 MCP 服务、Telegram 链接预览、API 客户端共用操作者的管家对话、Looper 自己的 git 调用执行仓库控制的代码、会话目录里被放置的 Python 模块、仪表盘加载远程内容、Lark 远程图片、以及高风险调用与确认的发送者身份检查；并修复启动、升级和关闭上的四个失败。本版新增一项迁移（2150）和 `test` extra 里的一个依赖（`markdown-it-py`），没有运行时依赖，也没有开关。除任务管家的改动（仅在 `tasks.conversations.manager_answers` 开启时生效）外，全部无需开关即生效，详见「行为变化」。

### 升级决策

**谁需要升级：** 所有安装。安全修复涉及给 API 客户端发 token、使用 Telegram 或 Lark 渠道、打开仪表盘、在 git 目录里跑任务、或允许多个聊天发送者接触管家的安装（#1874 对使用默认设置的安装最重要，请先读「升级前请检查」）；可靠性修复涉及每一次源码目录升级、每一次启动，以及运行在 Python 3.13 及以上的服务。从 v2.15.38 或更早版本直接升级到 v2.15.44，并阅读 [v2.15.43](v2.15.43.md)、[v2.15.42](v2.15.42.md)、[v2.15.41](v2.15.41.md)、[v2.15.40](v2.15.40.md)、[v2.15.39](v2.15.39.md)。

**解决了什么：** 每个 API 客户端有自己的管家会话和一份很短的任务工具列表，不再使用操作者的 `main` 会话。Telegram 消息不带链接预览。任务管家只加载 Looper 自己的 MCP 服务，加上操作者在用户设置里按名字允许的服务。源码目录升级在停服务之前先证明目标依赖能装上。记忆草稿器的辅助连接失败不再让服务在启动时停止，启动不再因首次导入阻塞事件循环，Python 3.13 及以上关闭服务不再出错，任务管家一轮只提交自己改的文件。服务在 agent 可写目录里运行的 git 不再执行仓库控制的代码，也不再拿到服务的环境变量（#1861）；Looper 的 MCP 服务和 hook 回退命令不再从会话工作目录加载代码（#1864）；仪表盘不再让 agent 文本触发浏览器加载远程内容（#1866）；Lark 消息不能再带远程图片或未列出的 HTML 标签（#1867）；高风险调用和确认在每个会话里都按发送者身份授权，不论每轮上下文开关如何（#1874）。

**是否有破坏性变更：** 是。依赖操作者 `main` 对话、或通过聊天使用设置、项目、定时任务、provider、确认工具的 API 客户端会失去它们（#1858），见「行为变化」。没有删除的操作或设置，但无开关的行为也会变化：任务管家直连会话不再加载操作者的 MCP 服务，除非按名字允许；Telegram 不再发链接预览；源码目录升级在停服务前多一次依赖安装。仪表盘上 agent 回复里的远程图片显示为链接（#1866），Lark 带图片链接而不是远程图片（#1867）；`info/attributes` 指定了 driver 的仓库会被 Looper 的 git 调用拒绝（#1861）；其他在白名单内的发送者或群成员不能再发起或确认高风险调用，没有操作者 id 的机器人在 `manager.turn_context.enabled` 关闭时没有任何聊天发送者能发起或确认高风险调用，只有仪表盘可以（#1874）。升级到本版的那一次升级仍使用被替换版本的升级顺序（见升级一节）。从 v2.15.42 或更早升级还会继承 v2.15.43 的迁移、`cryptography` 依赖和行为变化。早于桥接版本的安装需先升级到 v2.13.165 并启动一次。

**如何验证：** 核对版本，确认服务启动并应用 `manager_session_client_kind`（2150）。以操作者读取 `task_conversations.get`，确认 `manager_answers` 仍是你设置的值，`manager_mcp` 为空列表（除非你设置过）。API 客户端发过消息后，`manager_sessions.list` 仍只显示你自己的会话。请求任意仪表盘资源，确认响应带 `Content-Security-Policy` 头（#1866）。对每个 Lark 或 Telegram 机器人，确认「设置 → 渠道」里的「My ID」是你自己的 id（#1874，见「升级前请检查」）。 本次文档检查见「验证」。

### 包含的改动

**安全：**

- **#1858，API 客户端有自己的管家会话。** API 客户端（带自己 client token 的调用方）原先在默认管家的 `main` 会话里运行：它的回合共享操作者的常驻对话记录且没有受众过滤，新建 `main` 会话的简报还带着所有聊天（含客户端）的近期文本。受影响：给 API 客户端发过 token 的安装；处理：升级。默认管家现在在 `client:api:<client id>` 里运行客户端的每一回合，无论会话路由开关。客户端会话的工具是一份明确列表：`looper_tasks`、`looper_task_create`、`looper_task_control`、`looper_task_instruct`、`looper_task_update`，其他工具名在读取参数之前就被拒绝为 `forbidden`。列表里没有 `looper_confirm`：待确认项只按聊天为键，否则客户端回合可能确认另一个会话的待办。因此客户端提出的高风险请求（取消或重启任务）会等一个客户端会话里没有人能给出的确认，操作者自己的对话也看不到它，所以它会失效（最多 10 分钟）；除非操作者在该聊天线程里确认。需要可确认操作的客户端应使用 REST 操作加确认这一对（`POST /api/v1/<op>` 然后 `POST /api/v1/confirm`），本版不改它；`POST /api/v1/confirm` 只确认客户端自己通过 REST 操作 API 提出的待确认项，不能确认在管家聊天回合里提出的。会话的输入是它自己的契约、人设名、项目、模板、工作流列表和自己的消息，不含操作者 profile、目标、就绪任务、待处理关卡、记忆、知识库、线索或别的聊天文本；`main` 的续接简报不再含客户端对话，客户端的简报只列它自己的对话。隔离的是聊天文本：`looper_tasks` 仍能读到管家的任务，任务内容可以通过工具结果进入客户端会话。场景管家的客户端仍用该管家的 `main`。客户端会话计入 `manager.sessions.max_resident`；迁移 `manager_session_client_kind`（2150）让 `manager_sessions.kind` 可以存 `client`。找不到空闲常驻名额的启动现在最多等 60 秒，然后以固定的忙碌回复拒绝（原先可能在无法停止的空闲会话后面永远等待，例如 Messages API 运行时上的路由群），Messages API 的空闲会话在达到上限时现在会被回收。
- **#1865，Telegram 链接预览。** Telegram 消息里的 URL 会让 Telegram 服务器去抓取页面生成预览，这是没人点击的外发请求，可能带出 agent 读到的数据。受影响：使用 Telegram 渠道的安装；处理：升级。Telegram 应用现在默认关闭链接预览，Looper 发送的文本消息和编辑都不带预览。
- **#1852、#1862、#1869，任务管家只加载被允许的 MCP 服务。** 任务管家的直连会话原先用操作者自己的配置启动 Claude Code 且不开严格 MCP 模式，会加载操作者配置的每一个 MCP 服务；MCP 服务在沙箱之外以操作者权限运行，而任务目录不可信。现在直连会话总是带 `--strict-mcp-config` 启动，只加载 Looper 自己的服务，加上新的、仅限操作者的设置 `tasks.conversations.manager_mcp` 里按名字列出的服务（最多 20 个互不相同的名字，由字母、数字、`_`、`-`、`.` 组成，每个最多 64 个字符，默认为空），它是 `task_conversations.get` 与 `task_conversations.update` 的新字段。每个名字只从用户级配置解析：用户 `.claude.json` 顶层的 `mcpServers`（设置了 `$CLAUDE_CONFIG_DIR` 时用 `$CLAUDE_CONFIG_DIR/.claude.json`）。任务的项目 `.mcp.json` 和与其路径绑定的本地级配置从不读取，所以只在那里定义的名字算未找到，项目或本地定义也不能替换用户定义。找不到的名字，或与 Looper 自己的服务同名的名字，会让任务管家拒绝启动，新的原因是 `mcp_unresolved`，不会跳过任何一个。生成的 `--mcp-config` 文件可能含服务密钥，会话结束或被替换时删除；列表变化后常驻进程在下一回合重启。插件自带的 MCP 服务在严格模式下不加载，所以不能按名字允许，需把该服务配置成用户级服务。定义里的 `${VAR}` 由 Claude Code 按任务管家的环境展开，只存在于操作者 shell 的变量会展开为空。`task_conversations.update` 的操作描述写明「user scope only」。此项只在 `tasks.conversations.manager_answers` 开启时生效。
- **#1874，每个会话里都按发送者身份授权高风险调用和确认。** 管家按本轮的说话人决定谁可以发起、谁可以确认高风险调用。这个说话人原先只在 `manager.turn_context.enabled` 开启且不在路由会话时才设置；开关关闭（代码默认值）或在路由的非 main 会话里，能接触管家却未被分类的发送者，在高风险调用和确认上被当作操作者。其他在白名单内的发送者或群成员因此可以自己发起高风险调用，或者在聊天里发下一条消息来确认操作者待确认的那一个。受影响：有多个白名单发送者或群的安装，处于默认设置；路由的非 main 会话默认不暴露任何工具，所以那里只有在有范围授权时才有这个暴露；处理：升级。现在每个用户回合都会分类（`manager_turn_context.identify`，回合开始前新增 `classify_speaker` 准备步骤），不论开关或会话，机器人渠道上说话人未知的回合像非操作者一样被拒绝（未知说话人一律拒绝）；被拒绝的确认会让待确认项失效。没有 API 客户端的仪表盘仍是操作者，API 客户端仍是客户端。轮次上下文仍只在开关开启时渲染，所以对模型可见的文本不变。机器人渠道上的操作者：Lark 或 Telegram 机器人只有在设置了 `operator_sender_id` 时才有操作者（「设置 → 渠道」的「My ID」：从该机器人自己的白名单里选一个 id）。没有设置的机器人在聊天里没有操作者：开关关闭时，该机器人的任何聊天发送者都不能发起或确认高风险调用，会被拒绝并提示「this bot has no operator id set」，直到设置为止，只有仪表盘可以。
- **#1861，agent 可写目录里的 git。** 服务在任务、步骤和 worktree 目录里运行的 git 命令，会执行仓库自己控制的代码（hook、配置的程序、filter / merge / diff driver、签名和 ssh 程序），并带着服务的环境变量，其中可能有数据库凭据；能写这些目录的 agent 可以让这些代码在它的运行和时间预算结束之后执行。受影响：所有在 git 目录里跑任务的安装；处理：升级。现在这些目录里的每个 git 调用都走同一个封装（`looper/agents/git_safe.py`）：覆盖指向程序的配置项，用白名单构造子进程环境（数据库 URL、`PG*`、token、provider key、代理和 ssh agent 不再传给 git），并拒绝 `.git` 不属于该目录、或其 `info/attributes`（或已检出子模块的）指定了 filter、diff 或 merge driver 的目录。`.gitattributes` 本身和用户或系统配置里定义的 driver 照常工作；只由仓库自己的配置或其已检出子模块定义的 driver 被中和。一个测试会在 `looper/` 里出现不在简短且有理由的白名单之外的直接 `git` 进程调用时失败（白名单：Looper 自己的 checkout 和升级、克隆远程到新目录、`git --version`、操作者自己的 CLI、操作者的知识库，其提交 hook 按设计运行）。已知限制：封装在每条命令之前才读取仓库的 driver 定义，所以在这次读取之后、git 读取之前写进仓库的 driver 定义不会被拦住。那段代码以与 agent 相同的系统用户运行，只带白名单环境（没有数据库 URL 或密码、Looper token、provider key、代理和 ssh agent）；每条命令之后（验证缓存块内除外，它跳过这次再检查）封装会再检查一次，发现新出现的 driver 就记录一条带任务、步骤和 driver 名的警告。已为它记录了后续工作。
- **#1864，Looper 的 MCP 服务启动方式。** 携带会话 token 或在会话工作目录里运行的 Looper 子进程，启动 Python 模块时工作目录在导入路径里，放在该目录的同名包可能被导入而不是 Looper 自己的代码。这是共享工作目录的 Looper 会话之间的权限提升。受影响：agent 共享工作目录的安装，以及工作目录可能被 agent 写过的、操作者自己的 Claude Code 会话；处理：升级。Looper 的 MCP 服务入口（Worker、Planner、Manager、任务管家）现在用绝对解释器路径和 `python -I -m looper.cli mcp-server` 启动；没有 `looper` 控制台脚本时，Claude Code 用户级 MCP 入口和 SessionStart hook 用同样的隔离形式，hook 启动的 profile 读取器也用 `python -I -m`。服务单元自己的命令不变：有控制台脚本时它就用脚本，在那里加 `-I` 会改变升级检查所比较的命令；剩下的情况是没有控制台脚本、且 `service install` 时工作目录可被 agent 写入。
- **#1866，仪表盘远程内容。** agent 回复里的 Markdown 图片会被渲染成图片，且仪表盘页面没有 Content-Security-Policy，被提示词注入的 agent 可以借操作者的浏览器把读到的数据送到别的主机；链接也可以用显示文字掩盖真实目的地。受影响：所有会打开仪表盘的安装；处理：升级。现在每个仪表盘页面和资源都带 Content-Security-Policy，只允许同源的脚本、样式、字体、图片（加 `data:` 和 `blob:`）和连接，并设置 `object-src 'none'`、`base-uri 'none'`、`frame-ancestors 'none'`、`form-action 'self'`。agent 文本里的 Markdown 图片渲染为链接 `image: <alt> (host)`（在链接内部则是纯标签）。agent 文本里的链接按浏览器的方式解析：指向本站的仍是站内链接；指向其他 http(s) 站点的在文字旁显示解析后的主机，在新标签页用 `noopener noreferrer` 打开，不发 referrer，也不保留 `title`；其他协议（`javascript:`、`mailto:`）和邮箱自动链接渲染为纯文本。只有当文字本身就是与目的地相同协议、主机、端口的地址时才省略主机标签。文字像另一个站点地址的本站链接会带「(this site)」标记。agent 文本里的双向文字控制字符（包括字符引用和图片 alt 文本里的）会被去掉，不能再重排主机标签。线索来源链接、台账引用链接和任务详情里的模板输入链接用同一组件，不是网页地址的来源不渲染链接。
- **#1867，Lark 远程图片和 HTML（纵深防御）。** Lark 帖子或卡片里的远程 Markdown 图片是客户端或平台渲染时可能抓取的 URL，agent 文本里的 HTML 也可以同样加载资源。受影响：使用 Lark 渠道的安装；处理：升级。Looper 现在对 bot API 消息体、CLI `--markdown` 消息体（发送、回复、编辑）和卡片正文里的 agent Markdown 做一次有界的单遍中和，不去枚举 URL 形态。只有目标恰好是 Lark 图片 key 的图片才保留。普通 `http(s)` 图片目标变成链接 `image: [alt (host)](url)`，点击才会抓取；其他所有图片形式（引用式、尖括号、带标题、协议相对、实体编码、`data:` 等）把 `!` 写成 `&#33;`。每个 HTML 标签起始符的 `<` 写成 `&#60;`，例外是 `http(s)` 与 `mailto` 自动链接，以及 Lark 自己的标签（`at`、`a`、`br`、`hr`、`person`、`local_datetime`、`text_tag`、`number_tag`、`raw`、`font`、`u`），且只带为它们列出的属性。围栏代码和行内代码保留；代码边界有歧义时整段行都被中和，所以那里的代码示例可能显示 `&#33;[` 而不是 `![`。纯 `text` 消息不是 Markdown，不变。这是纵深防御：Lark 的文档没有说明帖子 `md` 标签如何解码数字实体 `&#60;` 和 `&#33;`，也没说明卡片组件对未列出标签怎么处理，所以被转义的字符处可能显示字面实体；它仍不加载任何东西。Lark 如何展开普通链接同样没有文档，链接仍可能被平台预览。

**可靠性：**

- **#1849，`looper service upgrade` 在停服务前安装目标依赖。** 原先依赖同步（`uv sync`）在停服务和快进合并之后运行；失败（索引不可达、缺 wheel）时，失败路径会在已合并的检出上用旧环境重启服务，启动先跑迁移再在导入时崩溃，服务管理器反复拉起，提示的 `looper service restart` 也没用。现在 `FULL` 和 `CONTROL_PLANE` 的源码目录升级在与仪表盘构建相同的准备阶段，导出目标树（不含 `web`、`docs`、`tests`、`evals`），以检出里本地 `uv.lock` 为起点，用服务解释器在临时环境里运行同样的 `uv sync --extra test --inexact`。这证明目标能装上（包括构建包本身），并把所有 wheel 留在 uv 缓存里；失败时命令中止，服务没有被排空或停止。停服务之后，真正的同步带 `UV_OFFLINE=1` 运行；若仍失败，检出被重置到合并前的提交，本地 `uv.lock` 恢复，上一版环境从缓存离线重新同步，上一版被重启，命令以写明失败步骤和状态的错误结束。若重置本身失败，服务保持停止并给出确切的下一步，这种失败不再附带 `looper service restart` 提示。wheel 升级和仅仪表盘升级不变。
- **#1853，启动时在事件循环之前导入。** 仪表盘 domain 包的首次导入原先发生在 `http` 启动步骤、事件循环线程上；它导入一百多个模块，把循环阻塞数秒，被循环看门狗记为 `event loop was blocked`。`serve_agent` 现在在 `asyncio.run` 之前调用 `preload_domains()`，成本落在循环前的 `imports` 步骤。注册表、操作和 OpenAPI 文档不变。domain 模块导入失败现在在循环前的启动里抛出，而不是在 `http` 步骤：仍是启动失败，错误相同。
- **#1855，辅助连接失败不再停服务。** 记忆草稿器自己的 `LISTEN` 连接在启动时失败，会让 `looper serve` 在报告就绪之后立即停止。草稿器现在重试三次、每次间隔一秒，记录 `memory drafter listener unavailable ... drafting polls instead` 后继续；草稿本来每个 tick 都会轮询，监听只是缩短等待。循环每个 tick 重试一次连接直到成功。控制面锁和主连接池失败仍会让启动失败。受影响机器上连接失败的根因未确认。
- **#1851，Python 3.13 及以上的 HTTP 关闭。** 关闭时用 `asyncio.Server._active_count` 统计打开的连接，CPython 3.13 及以上没有这个属性，关闭在中止迟到连接完成之前抛出 `AttributeError`。现在一个辅助函数在 `_active_count` 存在时读它，否则读 `_clients` 的大小，再否则用服务器已跟踪的处理器；读取计数不会再抛错。宽限和清理期限不变。
- **#1847、#1843，网络暂停修复。** 除日志行外只在网络暂停开关开启时生效。开关开启时，任务详情在一条语句里同时读取生效的暂停与任务的状态和已存阶段，并据此投影 `phase`：请求在任务仍处于就绪时加载，现在报告 `waiting`（过期后 `waiting_user`），而不是在暂停旁边报告 `pending`；暂停生效期间响应里的 `status` 和 `group` 来自同一次读取，已结束的任务保留它的阶段。开关关闭时任务详情仍不查询暂停表。存储的 `engine.network_pause.max_pause_seconds` 无效时，现在每个不同的值只记录一次，而不是每次读取都记；回退时长和警告文本不变。

**任务管家，默认关闭：**

- **#1848，只提交本轮自己的改动。** worktree 任务上的直连任务管家回合原先会提交所有待处理的改动，包括用户写了一半的改动，署在管家名下。回合本来就在开始和结束时对工作树做快照；现在它只提交自己改过的路径，通过新的 `step_workspaces.commit_paths`（对显式路径列表 `commit --only`，其他已暂存和未暂存的改动不动，链接路径从不提交）。回合开始前就已有改动的路径从不提交，即使本轮也编辑了它；没改任何文件的回合不产生提交。`turn_summary` 事件新增可选的 `uncommitted`（回合前就有未提交改动因而留下的路径）和 `unverified`（在哈希预算内无法确定归属的路径，每次决定 8 MiB、单文件 1 MiB）列表，仅非空时出现，任务线程追加一句固定的中文说明点名这些路径。暂存的重命名按两个路径的一次改动处理。`in_place` 和非直连回合不变。只在 `manager_answers` 开启时生效。
- **#1859，任务线程显示每一种拒绝原因。** 仪表盘的拒绝原因列表缺 `manager_answers_off` 和 `mcp_unresolved`，这类事件被当作未知而丢弃。现在两者都显示为 `已拒绝（<reason>）`，并有测试在仪表盘任一任务事件取值列表与服务端枚举不一致时失败。服务端无变化。

**新命令与内部改动：**

- **#1863，`looper-edit` 命令，未接入任何 agent。** 安装包会增加 `looper-edit`：`replace <file>` 从 stdin 的 JSON（`old`、`new`、可选的 `count`，即最多匹配次数）做精确文本替换，`patch` 以全有或全无的方式应用多文件 unified diff；不匹配时打印冲突且不改任何文件，解析到工作目录之外的路径会被拒绝。它只用标准库。没有任何东西调用它：没有提示词、工具列表或启动路径接了它，所以不改变任何 agent 的行为。命令模块不计入服务重启指纹；组件清单改变，所以控制面指纹会变一次。
- **#1860，只是 RFC。** 任务管家安全边界（task-sessions RFC 的第 25 节），不改代码。
- **测试与 CI。** #1844、#1854 只在测试里固定「每个已转换迁移第一次 `apply` 报告做了工作、第二次没有，且第一次之前处于待处理」；#1856 让缺少构建好的仪表盘在本地跳过、在 CI 失败，并给 Python 与 installed 测试工作流加守卫步骤；#1846、#1857 把 PR 的 agent 测试分成八个分片，并把超过 300 秒的测试文件按记录的单测用时拆分；#1850 同步开发计划。这些都不改变已安装的服务。除 API 客户端会话的新契约（#1858）外，本版没有任何改动改变已有会话对模型可见的文本：固定的提示词、片段和回合基线不变，只有启动签名会变（#1864 的 MCP 命令是签名的一部分）。

### 升级前请检查

升级前请检查这三项，每一项都会改变升级后聊天或 API 客户端能做什么。

1. **每个启用的机器人渠道都配置了操作者身份。** 对每个启用的 Lark、`lark_bot` 和 Telegram 渠道，打开「设置 → 渠道」，确认「My ID」（`operator_sender_id`）是该机器人自己白名单里的一个 id（Lark 的 open_id 按应用区分，所以每个机器人各自设置）。没有它，机器人在聊天里没有操作者，升级后该聊天里的高风险操作会被拒绝（#1874）；仪表盘不受影响。
2. **需要可确认操作的 API 客户端使用 REST 操作加确认这一对。** `POST /api/v1/<op>` 然后 `POST /api/v1/confirm` 本版不变；确认端点只确认客户端在同一会话里通过 REST 操作 API 自己提出的待确认项。通过管家聊天 API 请求的可确认操作，客户端不能再确认，除非操作者在该聊天线程里确认，否则会失效（#1858、#1874）。
3. **回复里的远程内容显示方式变了。** 仪表盘上模型回复里的外部图片现在显示为带主机的链接（#1866）；Telegram 消息不再显示链接预览（#1865）；Lark 消息带图片链接而不是远程图片（#1867）。

**依赖说明：** `test` extra 新增 `markdown-it-py`（及其依赖 `mdurl`），运行时依赖不变。`install.sh` 不安装 test extra，但源码目录升级（`looper service upgrade`）带 `--extra test` 同步，所以此时机器需要能拿到这两个包，来自包索引或已预热的 uv 缓存。因为安装 v2.15.44 的那次升级在停服务之后同步（见「升级」），请在升级前准备好。

### 升级

从 v2.15.39 以来的任何版本直接升级到 v2.15.44。从 v2.15.38 或更早版本，请阅读 [v2.15.43](v2.15.43.md#upgrading-from-v21538-or-earlier)、[v2.15.42](v2.15.42.md#upgrading-from-v21538-or-earlier) 和 [v2.15.39 的升级要求](v2.15.39.md#upgrading-from-v21537-or-earlier)。从 v2.15.42 或更早升级，还会得到 v2.15.43 的迁移 2100、2120 和新依赖 `cryptography` 46.x，见其[升级说明](v2.15.43.md#upgrading-from-v21538-or-earlier)。

**迁移：** 2150 `manager_session_client_kind` 用 `manager_sessions.kind` 现有取值加上 `client` 重建该列的检查，先建为 `NOT VALID`，在线步骤 `manager_session_client_kind_online` 在提交之后校验，不会因扫描表而长时间持有 schema 锁；`manager_sessions` 存的是管家会话行，不是聊天历史。没有 down migration：回滚到旧版本前，先删除 `manager_sessions` 里 kind 为 `client` 的行。

**依赖：** 没有新增或变更运行时依赖。`pyproject.toml` 增加 `looper-edit` 控制台脚本（#1863），并在 `test` extra 里加入 `markdown-it-py>=3,<5`（#1867），它的测试用它对照 Markdown 渲染器检查中和结果，见「升级前请检查」的依赖说明。

**本版改变了升级顺序，而升级命令是被替换版本的代码。** `looper service upgrade` 从服务自己的检出运行，不会 re-exec 目标的代码，所以安装 v2.15.44 的那一次升级仍在停服务之后才同步依赖（v2.15.43 的顺序）。新顺序（排空前在临时环境安装，停服务后离线同步，失败时回滚到上一个提交）从 v2.15.44 往后的第一次升级起生效。多出的安装会把它的耗时加进 `prepare_seconds`，并把下载从停机区间（`gap_seconds`）里拿掉。

降级需保留迁移前备份。早于 v2.13.165 的安装需先升级到 v2.13.165 并启动一次。

### 行为变化

- **无新开关：**
  - **API 客户端（#1858）：** API 客户端的聊天回合不再在 `main` 里运行，和操作者的对话不再连续，操作者的仪表盘和私聊文本、笔记、profile、目标、就绪任务和待处理关卡也不在它的输入里；依赖「我在仪表盘说过什么」的客户端会失去这一点。它的会话只有「安全」一节列出的五个工具，而不是管家的完整工具集，所以通过聊天不能再修改设置、项目、定时任务、provider、模型、目录或并发，不能读取费用或总览，不能回复关卡，也不能确认任何操作，包括它自己提出的（后果见「安全」）。客户端回合需要有「仅平台工具」启动模式的运行时（Claude Code 或 Messages API 运行时），其他运行时会回复常见的「选择受支持的 Agent Profile」错误；它使用设置里的 Agent Profile，而不是操作者给 `main` 选的 `/profile`；客户端发 `/profile`、`/todo`、`/gates` 会得到固定的「this session can't …」回复。`main` 的续接简报不再含 API 客户端对话。`manager_sessions.list` 不列出客户端会话，`reset` 只作用于操作者自己的会话。最多 `max_resident` 个进程现在包含客户端会话；名额已满时启动显示「排队中：其他会话正忙」，60 秒后以固定的中文忙碌回复被拒绝，会话路由开启时这也适用于路由群。没有 API 客户端的安装，`main` 和路由群的提示词、工具列表和命令行不变。API 的端点和响应形状不变。
  - **Telegram（#1865）：** Looper 发送的消息和编辑里的任何链接，无论谁写的，都不再展开成预览卡片。消息文本、解析模式和分段不变。本改动不涉及 Lark。
  - **源码目录升级（#1849）：** `FULL` 和 `CONTROL_PLANE` 在排空前多一次 `uv sync`；停服务后的同步是离线的，不再回退到网络；停服务之后的依赖失败现在重置检出并重启上一版，而不是重启目标。从本版起的第一次升级才生效。
  - **启动与关闭（#1853、#1855、#1851）：** domain 模块在事件循环之前导入，导入失败更早暴露；草稿器监听失败变成警告加每个 tick 重试，而不是停服务；Python 3.13 及以上关闭时按新方式统计连接。
  - **operator API（#1852、#1862、#1869、#1848、#1858、#1863）：** `task_conversations.get` 和 `task_conversations.update` 新增字段 `manager_mcp`（默认 `[]`）；`update` 仍是仅限操作者、高风险、需确认的操作，也是修改列表的唯一方式。`refused` 事件的原因 `mcp_unresolved` 和 `turn_summary` 的可选字段 `uncommitted`、`unverified` 是新的，二者都只在 `manager_answers` 开启时才可能出现。`manager_sessions.kind` 接受 `client`。安装包增加 `looper-edit` 命令，没有东西调用它。
  - **仪表盘任务线程（#1859）：** 原因为 `manager_answers_off` 或 `mcp_unresolved` 的拒绝现在会显示，而不是被丢弃；拒绝的最终文本原本就显示。
  - **日志（#1843）：** 存储的网络暂停上限无效时，每个值只警告一次。
  - **聊天授权（#1874）：** `manager.turn_context.enabled` 关闭（默认）或在路由的非 main 会话里，其他在白名单内的发送者或群成员不能再自己发起高风险调用，也不能再用聊天里的下一条消息确认操作者待确认的调用；二者都被作为仅限操作者拒绝，被拒绝的确认会让待确认项失效。没有 `operator_sender_id` 的机器人在聊天里没有操作者：开关关闭时，该机器人的任何聊天发送者都不能发起或确认高风险调用，直到设置该 id，只有仪表盘可以。没有 API 客户端的仪表盘仍是操作者，API 客户端仍是客户端。之后加到路由的非 main 会话里的工具同样按身份授权；这类会话默认的白名单今天没有任何高风险工具。卡片按钮不变。对模型可见的文本不变。
  - **仪表盘（#1866）：** agent 回复里的外部图片显示为链接而不加载；agent 回复和线索来源里的链接显示主机并在新标签页打开、不发 referrer、没有 title；文字像另一个站点地址的本站链接带「(this site)」标记；`mailto:` 链接和邮箱自动链接渲染为纯文本，相对路径图片变成本站链接；不是网页地址的线索来源不渲染链接；每个仪表盘页面和资源都带 Content-Security-Policy，`Referrer-Policy: same-origin` 原先只有页面带，现在每个资源也带。仪表盘没有内联脚本和样式，也不加载第三方主机，所以仪表盘自己需要的内容不会被挡。
  - **Lark（#1867）：** agent Markdown 里的远程图片到 Lark 时是带主机的链接（普通 URL）或带转义 `!` 的文本（其他形式）；其他 HTML 标签显示为字面文本（代码之外像标签的 `<word` 会以 `&#60;word` 发出），Lark 不解码时可能显示字面实体。图片 key、普通链接、代码和 Lark 自己的标签不变；Lark 自己对普通链接的处理也不变。
  - **Git（#1861）：** 仓库自己配置里定义的 driver（clean 或 smudge filter、textconv、merge driver）不再在 Looper 的 git 命令里运行，所以依赖仓库级（而非用户级）LFS filter 定义的仓库，在这些命令里看到的是原始内容。`.git/info/attributes`（或已检出子模块的 `info/attributes`）指定了 filter、diff 或 merge driver、或 `.git` 是既不属于 linked worktree 也不属于子模块的链接（例如用 `--separate-git-dir` 创建的）的仓库会被拒绝：步骤工作区报告 `GitError`，原因为 `repository_refused:attributes_driver`、`repository_refused:git_dir_mismatch` 或 `repository_refused:outside_worktree`（`.gitattributes` 引用、但由仓库自己配置定义的 driver 被中和，不被拒绝），其他调用点视为 git 不可用。已知限制见「安全」。每条命令多几个很短的 git 进程（在该 PR 中测得每个约 8 毫秒）；所读文件不变时，检查结果最多记住 120 秒。
  - **MCP 启动（#1864）：** MCP 入口的命令行多了 `-I` 和绝对解释器路径；没有控制台脚本时，hook 和 Claude Code MCP 入口用 `python -I -m looper.cli`；已安装且不带 `-I` 的 hook 仍被识别为已安装，不会被重写；没有安装的源码目录不再能通过工作目录或 `PYTHONPATH` 让这些子进程找到 `looper`。
- **`manager_answers` 开启时：** 关闭时这些都不可达。开启时：直连会话除 `manager_mcp` 里的名字外不再加载操作者的 MCP 服务，依赖旧行为的操作者要用 `task_conversations.update` 把这些名字加一次；允许的名字不是用户级服务时，任务管家拒绝启动并给出 `mcp_unresolved`；worktree 回合只提交自己改过的路径（见任务管家）。
- **网络暂停开启时：** 任务详情用与暂停同一次读取的状态投影 `phase`（#1847）；开关关闭时没有变化，也不读暂停表。
- **入口：** 仪表盘任务线程显示两个新的拒绝原因，worktree 回合后显示点名未提交文件的句子；操作者的会话列表不显示 API 客户端会话；Markdown 图片渲染为链接、链接显示主机并在新标签页打开、每个页面带 Content-Security-Policy（#1866）；「设置 → 渠道」的「My ID」决定谁是机器人聊天里的操作者（#1874）。Telegram 不发链接预览（#1865）；Lark 把远程 Markdown 图片改成链接并转义未列出的 HTML（#1867），机器人的操作者是它的 `operator_sender_id`（#1874）；没有新命令，API 客户端不经过这两个渠道。CLI/API：`task_conversations.get/update` 带 `manager_mcp`，任务事件流新增 `mcp_unresolved` 与 `turn_summary` 字段，`manager_sessions.list` 不含客户端会话，`manager_sessions.kind` 接受 `client`，新增 `looper-edit` 命令，API 客户端的聊天工具是上面五个；源码目录的 `looper service upgrade` 改变顺序。没有删除任何操作。

本版一个面。示例只做读取，需替换示例站点并提供操作者 cookie，不会改任何东西。继承能力见 [v2.15.43](v2.15.43.md#optional-capability-activation--use)、[v2.15.42](v2.15.42.md#optional-capability-activation--use)、[v2.15.41](v2.15.41.md#optional-capability-activation--use) 和 [v2.15.39](v2.15.39.md#optional-capability-activation--use)。`looper-edit` 命令和 API 客户端会话不是启用面：命令没有接入任何 agent，客户端会话没有设置。

#### Task Manager MCP allowlist

**启用：** 默认为空，任务管家直连会话只加载 Looper 自己的 MCP 服务。操作者先读 `task_conversations.get`，再经 `task_conversations.update` 提交 `manager_mcp` 名字列表，并用 `POST /api/v1/confirm` 完成确认。每个名字必须是用户 Claude Code 设置里的用户级服务（`claude mcp add --scope user`）；只在项目或本地级定义的名字找不到。它只在 `tasks.conversations.enabled` 和 `tasks.conversations.manager_answers` 都开启时才有意义。传 null 或空列表恢复为无。

**验证：** 读回 `manager_mcp`。名字不是用户级服务时，向任务目标发消息会在任务线程里被拒绝，原因 `mcp_unresolved` 并点名该服务，不会启动任务管家进程。用户级服务存在时，新的任务管家会话恰好加载 Looper 的服务和它。改变列表后，常驻进程在下一回合重启。不要对生产任务做这个检查。

**停用 / 回退：** 把 `manager_mcp` 设为 null 或 `[]` 并确认。常驻进程在下一回合不带这些服务地重启。这不会关闭任务管家，那由 `manager_answers` 控制。

**权限边界：** get 和 update 都仅限操作者，update 是高风险确认。被允许的服务在沙箱之外以操作者权限运行，持有它自己的权限，所以只有用户级定义（而不是任务的项目文件）可以被允许。该设置不给其他发送者任何新工具。

# Looper v2.14.65

This is the patch release v2.14.65, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.64: a running command schedule that is not deleted now says why, and disabling it right after the refusal asks the user first ([#1046](https://github.com/foolzzz/looper/pull/1046)).

## Release Decision

**Who should upgrade:** Operators whose Manager (web chat, Telegram, Lark) deletes command schedules, and clients that call the schedule delete endpoints, while a command is running. Others need not upgrade.

**What this release solves:** Deleting a command schedule whose command is running is refused. The refusal text and the `looper_schedules` description said "disable it and wait for the run to end" as an instruction, and in the real-mode eval of the refusal, per the pull request description, the Manager disabled the schedule on its own in 4 of 6 runs, though the user had asked to delete it. The text also left out that a disabled schedule's queued run still starts when the running one ends. [#1046](https://github.com/foolzzz/looper/pull/1046) rewrites the refusal as information, asks before a Manager disable that follows the refused delete, and makes the Manager's delete confirmation say a command schedule has no tasks.

**Breaking changes:** No. No API schema or configuration changes and there is no migration. The 409 text for a refused delete changed (see Behavior changes).

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#1046](https://github.com/foolzzz/looper/pull/1046); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.65
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.64 upgrades directly. This release adds no migration.

## Behavior changes

- **The refusal explains itself.** Deleting a command schedule while one of its runs is running still fails (`blocks_delete`, `looper/agents/schedules.py`), but the text (409 from the service, the same text through the client token's impact check and the Manager's refusal before asking) now says: the schedule can be deleted once the command finishes; disabling it first stops new fires; and, when it has a queued run, that run still starts when the running one ends, even if the schedule is disabled, so deleting waits for it too. The constant `RUNNING_COMMAND_DELETE` is replaced by `running_command_delete(runs)`. The dashboard shows the new 409 text and changes nothing else.
- **Disabling after a refused delete asks first (Manager).** The Manager remembers, within one turn, the schedules whose delete was refused (`Turn.refused_deletes`, also when the command started after the question and the confirmed delete got a 409). A `disable` of such an enabled schedule in the same turn answers `needs_confirmation` and the schedule stays enabled until the user confirms in the next message. The confirmation says the delete did not run, that disabling stops new fires and the running command finishes, and, with a queued run, that disabling does not cancel it and deletion waits for it. It is bound to the schedule's configuration version. A `disable` the user asks for in a later message runs at once, as before.
- **Manager delete confirmation.** For a command schedule it now says "它没有任务" (it has no tasks) before the history line; only the client-token text said so before.
- **Unchanged:** agent schedules (their delete is never refused; texts byte-identical), the client token's `disable` (each client call builds a fresh turn, so it stays unconfirmed), and the queued-run behavior itself: a disabled schedule's queued run still executes, which the command-edit confirmation and Run now with overlap `queue` rely on. The queued run is fixed in words, not in behavior.
- **Docs and evals:** `docs/architecture/agent-system.md` describes the refusal and the confirmation; the prompt-regression dialogs grow from 52 to 54 (`schedule_command_delete_running`, `schedule_command_delete_running_queued`; `evals/README.md`); the fake Manager can supply a final reply with `__reply__`.
- **Size:** per the pull request description, 51 added lines of production code and 103 of tests (fixtures excluded).
- **Model-visible changes:** Yes. The `looper_schedules` tool description now tells the Manager to explain that a running command schedule can be deleted once the command finishes, that disabling stops new fires, that a queued run still starts, to disable only if the user asks, and that disabling in the same turn after a refused delete asks the user first. The Manager prompt's list of changes that need confirmation (`looper/agents/tiers/manager.py`) adds disabling a schedule right after its delete was refused. The refusal text, the new disable confirmation and the delete confirmation line are new tool output, and the two eval dialogs cover them.

## 中文摘要

本版本是 patch release v2.14.65（热修线，每个合并的改动立即发布）。自 v2.14.64 以来只合并了一项改动：正在运行的命令定时任务不能删除时，现在会说明原因，并且在删除被拒后立即停用它要先问用户（[#1046](https://github.com/foolzzz/looper/pull/1046)）。

### 升级决策

**谁需要升级：**其 Manager（网页聊天、Telegram、Lark）会删除命令定时任务、或客户端调用定时任务删除端点，而命令正在运行的运维者。其他人无需升级。

**解决了什么：**删除命令正在运行的命令定时任务会被拒绝。过去拒绝文字和 `looper_schedules` 说明把“停用它并等运行结束”当作指令；据 PR 描述，在该拒绝的真实模式评测中，用户只要求删除，Manager 却在 6 次中有 4 次自行停用了它。文字也没说明已停用任务的排队运行仍会在运行中的命令结束后开始。[#1046](https://github.com/foolzzz/looper/pull/1046) 把拒绝改写为说明信息，对删除被拒后的 Manager 停用先询问，并让 Manager 的删除确认说明命令定时任务没有任务。

**是否有破坏性变更：**否。没有 API 结构或配置变更，也没有迁移。删除被拒时的 409 文字有变化（见行为变化）。

**如何验证：**运行 `looper --version` 核对版本为 2.14.65。

**贡献者：**维护者 @foolzzz 提交 [#1046](https://github.com/foolzzz/looper/pull/1046)；本版本无社区贡献。

```bash
looper --version   # looper 2.14.65
```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.64 上的安装可直接升级。本版本没有迁移。

### 行为变化与入口

- **拒绝会自己说明原因。**命令定时任务有运行在进行时删除仍会失败（`looper/agents/schedules.py` 的 `blocks_delete`），但文字（服务返回 409，客户端令牌的影响检查和 Manager 在询问前的拒绝使用同一文字）现在写明：命令结束后即可删除；先停用只会停止新的触发；有排队运行时，该运行仍会在运行中的命令结束后开始（即使任务已停用），所以删除也要等它结束。常量 `RUNNING_COMMAND_DELETE` 被 `running_command_delete(runs)` 取代。仪表盘显示新的 409 文字，其他不变。
- **删除被拒后停用要先问（Manager）。**Manager 在一个回合内记住删除被拒的定时任务（`Turn.refused_deletes`；用户确认后命令才启动、确认的删除得到 409 时也记录）。同一回合内对这类已启用任务的 `disable` 返回 `needs_confirmation`，任务保持启用，直到用户在下一条消息中确认。确认内容说明删除没有执行、停用只停止新触发且运行中的命令照常结束；有排队运行时还说明停用不会取消它、删除要等它结束。确认绑定任务的配置版本。用户在之后的消息中要求的 `disable` 照旧立即执行。
- **Manager 的删除确认。**对命令定时任务，历史记录一行之前现在写明“它没有任务”；此前只有客户端令牌的文字这样说。
- **不变：**agent 定时任务（删除从不被拒，文字逐字节相同）、客户端令牌的 `disable`（每次客户端调用新建回合，所以保持不询问），以及排队运行本身的行为：已停用任务的排队运行仍会执行，命令修改确认和 overlap 为 `queue` 的“立即运行”都依赖这一点。排队运行只在文字上说明，行为未改。
- **文档与评测：**`docs/architecture/agent-system.md` 描述了拒绝和确认；提示回归对话从 52 个增至 54 个（`schedule_command_delete_running`、`schedule_command_delete_running_queued`；`evals/README.md`）；假 Manager 可用 `__reply__` 提供最终回复。
- **规模：**据 PR 描述，生产代码新增 51 行，测试新增 103 行（不含 fixture）。
- **面向模型的变化：**有。`looper_schedules` 工具说明现在要求 Manager 说明：运行中的命令定时任务在命令结束后可删除、停用只停止新触发、排队运行仍会开始、仅在用户要求时才停用，以及删除被拒后同一回合内停用会先询问用户。Manager 提示中需确认的修改清单（`looper/agents/tiers/manager.py`）新增“删除被拒后立即停用定时任务”。拒绝文字、新的停用确认和删除确认中的一行是新的工具输出，两个评测对话覆盖它们。

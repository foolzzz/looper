# Looper v2.15.43

Contains everything merged to main after [v2.15.42](v2.15.42.md)'s scope freeze `0ad334847` (the merge of [#1804](https://github.com/foolzzz/looper/pull/1804)), up to and including `45fc80461` (the merge of [#1840](https://github.com/foolzzz/looper/pull/1840)): ten first-parent merges, 23 pull requests once a merge batch is counted as its members. [#1836](https://github.com/foolzzz/looper/pull/1836) is [#1731](https://github.com/foolzzz/looper/pull/1731), [#1802](https://github.com/foolzzz/looper/pull/1802) and [#1812](https://github.com/foolzzz/looper/pull/1812); [#1831](https://github.com/foolzzz/looper/pull/1831) is [#1773](https://github.com/foolzzz/looper/pull/1773), [#1820](https://github.com/foolzzz/looper/pull/1820) and #1831; [#1837](https://github.com/foolzzz/looper/pull/1837) is the ten chat-scope pull requests; seven more merges are a single pull request each. Release pull requests are not changes. If main has moved beyond this freeze when the release pull request merges, the tag belongs on that pull request's own head, as described in [the release procedure](README.md).

The task Manager is included and off by default: it answers a task only when `tasks.conversations.enabled` and the new `tasks.conversations.manager_answers` are both on. Network pause and the interrupted-attempt hint are included and off by default. The chat-scope code is included and is not for use yet. Without any switch: `operator_chat.messages` returns paging fields, startup applies two migrations and logs a timing line for each migration that does work, Telegram and Lark chat history records who sent each message, and the operator API and Settings gain scope-related fields that do nothing yet. The Work page, with work mode on, changes slightly even while `manager_answers` is off; see Behavior changes.

## Release Decision

**Who should upgrade:** Operators who want a task answered by its task Manager, a pause during a model-connection outage, or a hint when a Worker is re-dispatched after an interrupt; operators who use Work and want to pick the task Manager model on an unstarted draft; and every installation, because startup applies migrations 2100 and 2120. From v2.15.38 or earlier, upgrade straight to v2.15.43 and read [v2.15.42](v2.15.42.md), [v2.15.41](v2.15.41.md), [v2.15.40](v2.15.40.md) and [v2.15.39](v2.15.39.md).

**What this release solves:** With both work-mode switches on, a task has its own conversation, answered by the task Manager with fixed commands, task-bound tools and a Work centre pane; with `manager_answers` off it stays with the Planner. With network pause on, a structured model-connection failure pauses the task and resumes it without spending a step retry. With the interrupted-attempt hint on, a re-dispatched Worker is told its previous attempt was interrupted. Chat-scope code for a later hardening release is present and not for use yet. Startup names each migration that actually runs.

**Breaking changes:** No. No operation or setting is removed. Behavior does change without a new switch, so read the Behavior changes section before upgrading: `operator_chat.messages` returns `has_more` and `next_before` on every call, startup adds migrations 2100 and 2120 (2100 validates a check across `chat_messages`) and logs timing lines, Telegram and Lark history rows record the Manager session and sender, and several operator API results gain fields. The release also installs a new runtime dependency, `cryptography` 46.x (exact range under Upgrading); a source-checkout upgrade installs it while the service is stopped and needs package index access at that moment, and an offline or pinned environment must provide it. Upgrades from v2.15.41 or earlier also inherit v2.15.42's migrations and behavior changes. Installations older than the bridge must upgrade to v2.13.165 first and start once.

**How to verify:** For a source-checkout upgrade, confirm the package index (or the uv cache) can supply cryptography 46.x before stopping the service. Check the version and that the service starts and applies `chat_message_entry_kind` (2100) and `network_pauses` (2120). As the operator, read `task_conversations.get` and confirm `manager_answers` is false. With work mode on and that switch off, a started Work task still opens the Planner thread, and a send to a task target returns 409 `task_manager_off` and stores nothing. Read `network_pause.get` and `worker_interrupted_hint.get` and confirm both are off. Do not use the chat-scope settings. The checks run for this document are listed under Validation.

```bash
looper --version   # looper 2.15.43
```

## Included changes

### Task Manager, off by default

The task Manager answers only when `tasks.conversations.enabled` and `tasks.conversations.manager_answers` are both on. Both default off, and only the string `true` is on. Operator-only `task_conversations.get` and `task_conversations.update` read and write them; null restores the defaults (work mode off, `manager_answers` off, resident cap 6). With work mode on and `manager_answers` off, `operator_chat.send` to `target.kind` `task` returns HTTP 409 `task_manager_off`, stores nothing and starts no process; the pool also refuses, with `manager_answers_off`. With work mode off the same target is refused earlier, as a 409 `conflict` naming work mode. Turning `manager_answers` off ends new work only: a task Manager already resident or inside a turn finishes that turn, and its further tool calls are refused.

- **[#1771](https://github.com/foolzzz/looper/pull/1771):** Task-bound tools `task_status` and `task_requirement_set`, a credential shared by the tools and outbound review, and a local command policy. The policy applies only when the environment variable `LOOPER_TASK_MANAGER` is set, so an ordinary `looper` command is unchanged. Inside that process `version` and `mcp-server` (with the task credential) run and every other command is refused. It is a speed bump, not a sandbox: the process runs as the service's OS user.
- **[#1773](https://github.com/foolzzz/looper/pull/1773):** With both switches on, `operator_chat.send` accepts `target.kind` `task` with `task_id` and a required `message_id`. The thread is `task-chat:<task_id>`, and it is left out of the Manager's conversation lists. The stored text keeps its whitespace; the same `message_id` with the same text reuses the first turn, with different text it is a conflict. A whole-message command (`/stop`, `/done`, `/pause`, `/background`, `/takeover`, `/start`; trimmed, any case) is answered in code: `/stop` stops the running turn, `/done` completes a task the background is not working on, and the other three answer a fixed sentence. Pending and assigned tasks store the message with a code reply and no model turn. Any other orchestrated status stores it and refuses with reason `orchestrated`. The reply stream adds `agent.tool` and `task.event`. Migration `chat_message_entry_kind` (2100) records `message`, `command` or `command_reply`; model history leaves the command kinds out.
- **[#1820](https://github.com/foolzzz/looper/pull/1820):** `operator_chat.messages` gains optional `before` and `limit` (1–200, default 200) and every result includes `has_more` and `next_before`, even when neither field is sent. The default page is still the newest 200 rows, oldest first, with the same columns. A task thread also returns `turn_state` (`idle`, `running` or `interrupted`). Cursors are encrypted with a key derived from the operator credential, so rotating the credential invalidates them; a bad cursor is `invalid_cursor` and another session's is `cursor_session_mismatch` (both 400). `tasks.task_manager_profile_set` now records a `model_switched` row on the task thread when the effective profile changes, and a `model_switch_rejected` row for a refused change (the caller still gets the original refusal); selecting the profile already in effect records nothing and no longer stops an idle resident.
- **[#1831](https://github.com/foolzzz/looper/pull/1831):** The Work centre pane uses the task thread only when the settings read returns both switches on; a missing flag, either switch off or a failed read keeps the Planner pane. Task Stop calls `stopChatReply` and does not read `chat.stop_enabled`; Manager Stop is unchanged.
- **[#1825](https://github.com/foolzzz/looper/pull/1825):** On an unstarted Work draft the operator can read and set the task Manager profile before pressing Start. It needs work mode only, not `manager_answers`, and does not start the task. `tasks.create_draft` is unchanged.
- **[#1841](https://github.com/foolzzz/looper/pull/1841):** On the task thread `/start` reads the task status and never starts the task. Draft or ready: 请用上方的「开始」按钮启动任务. In progress or needs you: 任务已经在进行中. Failed, stopped or cancelled: 请用「任务详情」里的「继续后台任务」按钮继续. Completed: 任务已经完成. Any other or unreadable status: 请用任务控制里的按钮操作, and a warning is logged. `/pause`, `/background` and `/takeover` keep their previous sentences. These replies are code and stay out of model history.

### Network pause, off by default

**[#1802](https://github.com/foolzzz/looper/pull/1802), [#1812](https://github.com/foolzzz/looper/pull/1812):** Operator-only `network_pause.get` and `network_pause.update` (confirmation required). The switch is `engine.network_pause.enabled`, default off; `engine.network_pause.max_pause_seconds` defaults to 7200 and accepts 1–86400; null restores either default. With the switch on, a Planner, Worker or Reviewer run pauses only on structured model-API connection evidence: `ENOTFOUND`, `ECONNRESET`, `EAI_AGAIN` or `ECONNREFUSED` read from the model API error envelope, not from tool output or prose. A later assistant response, a different API error or a tool result clears that code, so a recovered transport error does not pause a later unrelated failure. The pause keeps the plan, workspace and Planner session, admits no new model execution and does not interrupt a run already going. Probes are DNS plus TCP/TLS to the failed launch's endpoint with no HTTP or model request, a 5-second connect timeout and a wait that grows from 5 to 60 seconds (scaled 0.8–1.2); an unknown endpoint is never treated as recovered. Success resumes the same Planner turn or the same Worker or Reviewer attempt without spending a step retry. At the original deadline the pause becomes `waiting_user`, probing stops, and Needs you lists it. Disabling the switch clears a pause on its next check; stopping or restarting the task clears it too. Migration `network_pauses` (2120) creates `task_network_pauses`. Task detail shows `network_pause` and reports the phase `waiting` or `waiting_user` while a pause is active; with the switch off it does not read that table.

### Interrupted-attempt hint, off by default

**[#1731](https://github.com/foolzzz/looper/pull/1731):** Operator-only `worker_interrupted_hint.get` and `worker_interrupted_hint.update` (confirmation required). The switch is `worker.interrupted_hint.enabled`, default off; null restores off. A failed read logs once and counts as off. With it on, only a new Worker whose previous record for the same attempt ended `interrupted` gets one fixed English line right after the first line of its task prompt. The reason is `deploy drain`, `restart not adopted` or `run stopped`; free-form errors are never copied in. First runs, ordinary failures, new attempts and Reviewer prompts are unchanged.

### Chat scopes, included and not for use yet

[#1837](https://github.com/foolzzz/looper/pull/1837) lands ten pull requests: [#1746](https://github.com/foolzzz/looper/pull/1746), [#1747](https://github.com/foolzzz/looper/pull/1747), [#1748](https://github.com/foolzzz/looper/pull/1748), [#1749](https://github.com/foolzzz/looper/pull/1749), [#1752](https://github.com/foolzzz/looper/pull/1752), [#1755](https://github.com/foolzzz/looper/pull/1755), [#1758](https://github.com/foolzzz/looper/pull/1758), [#1760](https://github.com/foolzzz/looper/pull/1760), [#1763](https://github.com/foolzzz/looper/pull/1763) and [#1765](https://github.com/foolzzz/looper/pull/1765). They add scoped session routing and retirement, machine-wide resident limits, initiator-bound confirmations and stops, operator scope configuration, launch-mode and out-of-scope enforcement, audience-typed inputs, fenced group activity, scope metrics and alerts, and the Settings fields. [#1842](https://github.com/foolzzz/looper/pull/1842) then makes the one tool-call branch for an already-scoped session fail closed.

The code is included, every scope setting defaults off or unset, the default routing is unchanged, and the scopes are not for use yet: the routing setting accepts only `off` and `per_chat`, so no Manager can be routed `scoped`, and this release does not say how to turn them on. The scoped allowlist grants no tools, so a scoped tool call is still refused `out_of_scope`. What does reach every installation is listed under Behavior changes. No migration is added; `chat_scopes` (2040) was already on main at `0ad334847`.

### Startup timing, no switch

**[#1757](https://github.com/foolzzz/looper/pull/1757):** Each migration `apply` now returns whether it did work. After an apply that did work, startup logs `migration applied: NAME order=N in S.SSSs`; each online step that runs logs `online schema step applied: MARKER order=N in S.SSSs`. A settled migration logs nothing. The schema transaction, rollback and order are unchanged, and the DDL of existing migrations is unchanged.

### Internal foundations and tests

[#1838](https://github.com/foolzzz/looper/pull/1838) tests that re-selecting the task Manager profile already in effect keeps an idle resident and records no switch; it changes no production code. [#1842](https://github.com/foolzzz/looper/pull/1842) adds boundary and provenance tests beside its one production branch. [#1840](https://github.com/foolzzz/looper/pull/1840) adds the real-mode task Manager eval runner and cases (`evals/prompt_regression/task_manager_*.py`) and their tests; evals only, no product change. ## Upgrading from v2.15.38 or earlier

Upgrade straight to v2.15.43; it contains [v2.15.42](v2.15.42.md), [v2.15.41](v2.15.41.md), [v2.15.40](v2.15.40.md) and [v2.15.39](v2.15.39.md). Read [v2.15.42](v2.15.42.md#upgrading-from-v21538-or-earlier) for migrations 2090, 2130 and 2140, and [v2.15.39's upgrade requirements](v2.15.39.md#upgrading-from-v21537-or-earlier) for `task_drafts` (2050) and `proactive_bodies` (2110).

From a database that has completed v2.15.42, startup adds these two migrations even with all optional features off, using the existing pre-migration backup path. No existing table is rewritten.

| Order | Migration | What changes |
| --- | --- | --- |
| 2100 | `chat_message_entry_kind` | Adds nullable `chat_messages.entry_kind` (no default, so no rewrite) and a check that allows null, `message`, `command` or `command_reply`, created `NOT VALID`. Online step `chat_message_entry_kind_online` validates it during that same startup with one scan of `chat_messages`, which does not block reads or writes; expect a longer first start on a large table, shown by its timing line. |
| 2120 | `network_pauses` | Creates `task_network_pauses` (state `paused` or `waiting_user`, one active row per task). No online step. |

**New dependency.** `pyproject.toml` adds `cryptography>=46,<47`, which `operator_chat.messages` uses to encrypt its history cursors (`looper/agents/v1_domains/operator_chat_history.py:12`). `install.sh` pulls it with the wheel. An upgrade from a source checkout (`looper service upgrade`) installs it while the service is stopped, so the machine must reach the package index (or already hold the wheels in its uv cache) at that moment. An offline or pinned environment must provide cryptography 46.x before upgrading.

Keep the pre-migration backup for downgrade; this release supplies no down migration. Installations older than v2.13.165 must upgrade to v2.13.165 first and start once.

## Behavior changes

### Without a new switch

Every change in this list is visible to the operator only (the operator API, the dashboard, startup logs) or only records more data. Nothing in it changes what an ordinary user in a direct chat, a group member or a non-operator API client sees, no model input or reply text, and adds no rejection for them. The one effect everyone shares is that the first start after upgrading takes longer on a large `chat_messages` table.

- **Chat history paging (#1820).** Every `operator_chat.messages` result includes `has_more` and `next_before`; the default call returns the same newest 200 messages, oldest first, with the same columns. A task thread adds `turn_state`. The operation stays operator-only.
- **Startup (#1757, 2100, 2120).** A migration or online step that does work logs one info line; an up-to-date database adds none. Migrations 2100 and 2120 always run, and 2100 scans `chat_messages` once. With the network-pause and hint switches off, Planner turns, dispatches, task stop and Worker dispatch now read those settings first, with no change in behavior.
- **Telegram and Lark history records the sender (#1746).** Stored user rows now carry the Manager session, the sender kind (`person` or `bot`) and the sender name, and the Manager's replies and idle-check notes carry the session, in columns that already existed. Nothing on the default path reads them back, and `operator_chat.messages` does not return them.
- **Operator API and Settings gain scope fields (#1748, #1752, #1760, #1765).** New operator-only operations `capability_sets.list`, `capability_sets.get`, `chat_scope_overrides.list/put/delete` and `resident_limits.get/update`. Chat bindings gain `default_scope`, `effective_default_scope`, `legacy_allowed` and `suggested_scope`, and `manager_chat_bindings.put` accepts `default_scope` and `stop_now`. `manager_sessions.list` accepts `manager_id` and its rows gain `scope` and `retired`. The Manager metrics summary gains a `scopes` block of zero counts. Settings shows a read-only Sessions list and scope fields for each non-built-in Manager. All of it has no effect until a Manager is routed `scoped`, which cannot be selected.
- **Small fixes.** The Manager metrics latency read returns null percentiles for a window with no data instead of failing, and an invalid chat binding request now returns its specific message instead of a generic one.

### When work mode is on and `manager_answers` is off

The Work page stays available and started tasks keep the Planner thread, including when the settings read omits `manager_answers` or fails. The page reads `task_conversations.get` per selected task and shows 正在检查对话可用性 until it answers. An unstarted draft shows the task Manager model picker (#1825); choosing a model does not start the task, and it now records a `model_switched` row on the task thread (#1820). `/start` and the other task commands are unreachable. A send to a task target returns 409 `task_manager_off` and writes no chat row and no `agent_sessions` row. With work mode off none of this is reachable.

### Other switches

With both task switches on, behavior is as described under Included changes. With the network-pause and hint switches off there is no pause, no prompt line and no new task-detail query. Chat scopes change nothing beyond the list above: group and direct-chat routing, prompts, tool lists and launch signatures stay on the previous path, and [#1842](https://github.com/foolzzz/looper/pull/1842) changes only a session that is already scoped.

## Entry points

- **Dashboard:** With work mode on, the Work pane (Planner or task thread by switch), the draft model picker, task Stop, tool and event rows, `/start` sentences and the 正在检查对话可用性 line. Task detail shows an active network pause with its reason and deadline. The hint has no dashboard control. Settings gains the Sessions list and scope fields described above; they are not for use yet.
- **Telegram and Lark:** No new command. Task-thread replies and the draft picker are dashboard paths. A paused task appears in the existing Needs you summary. History rows record the sender, as above.
- **CLI/API:** New operator-only operations `network_pause.get/update`, `worker_interrupted_hint.get/update` and the scope operations listed above; `task_conversations.get/update` carries `manager_answers`; `operator_chat.messages` gains paging fields and, on a task thread, `turn_state`; `operator_chat.send` to a task target can return `task_manager_off`. The generated operator CLI discovers the new operations. No operation is removed.

## Optional Capability Activation & Use

Three surfaces. Each example is a read against a reserved example origin; replace the origin and supply an authenticated operator cookie. The examples turn nothing on. Inherited Work and Manager instructions are in [v2.15.42](v2.15.42.md#optional-capability-activation--use), [v2.15.41](v2.15.41.md#optional-capability-activation--use) and [v2.15.39](v2.15.39.md#optional-capability-activation--use). Chat scopes are not an activation surface in this release.

### Task Manager answers

**Activation:** Off by default. As the operator, read `task_conversations.get`. Submit `manager_answers` true through `task_conversations.update` and complete the returned confirmation through `POST /api/v1/confirm`. Work mode must be on as well, through the same operation's `enabled` field and its own confirmation. Null on either field restores that field's default.

**Validation:** Read both flags back. With work mode on and `manager_answers` off, a started task opens the Planner thread and a send to a task target returns 409 `task_manager_off` with no stored row. With both on, the centre pane uses `task-chat:<task_id>`, a direct-mode message is answered by the task Manager, and `/start` returns the status sentence without starting the task. Turn the answer switch off again and confirm a new task target is refused. Do not point this at a production task.

**Disable / rollback:** Set `manager_answers` to false or null and confirm. New task targets return `task_manager_off` and the Work pane returns to the Planner. A task Manager inside a turn finishes it but its further tool calls are refused; the idle ticker or closing the task reclaims the process. This does not turn Work off, drop migrations 2100 or 2120, or touch network pause and the hint.

**Authority boundary:** Both operations are operator-only and the update is a high-risk confirmation. The task Manager is a Claude Code resident of that task; its tools and command policy apply only inside that process, and it runs as the service's OS user, not in a separate sandbox. Other senders gain no operator operation.

**Docs:** https://github.com/foolzzz/looper/blob/v2.15.43/docs/architecture/agent-system.md

```bash
curl --fail --cookie operator-cookies.txt --json '{}' https://looper.example/api/v1/task_conversations/get
```

### Network pause

**Activation:** Off by default. As the operator, read `network_pause.get`. Submit `{"enabled":true}` through `network_pause.update` and complete the returned confirmation through `POST /api/v1/confirm`. The stored key is `engine.network_pause.enabled`. `max_pause_seconds` is optional (default 7200, range 1–86400). Null restores the default for the field you send.

**Validation:** Read the switch back as false before and true after. On a disposable task, a structured model-connection failure should pause the task, show the reason and deadline, and resume the same attempt once the endpoint accepts a connection, without spending a step retry. An unrelated failure after a recovered transport error should not pause. At the deadline the state becomes `waiting_user`. With the switch off, the same failure follows the previous retry path.

**Disable / rollback:** Submit `{"enabled":false}` or null and confirm. The next check clears an existing pause with reason `disabled`, including one at `waiting_user`. New failures use the ordinary retry path. The `task_network_pauses` table remains.

**Authority boundary:** Both operations are operator-only and the update is a high-risk confirmation. The probe opens a TCP or TLS connection to the failed launch's endpoint and sends no HTTP request and no model call. It grants the task no new tool.

**Docs:** https://github.com/foolzzz/looper/blob/v2.15.43/docs/architecture/agent-system.md

```bash
curl --fail --cookie operator-cookies.txt --json '{}' https://looper.example/api/v1/network_pause/get
```

### Interrupted-attempt hint

**Activation:** Off by default. As the operator, read `worker_interrupted_hint.get`. Submit `{"enabled":true}` through `worker_interrupted_hint.update` and complete the returned confirmation through `POST /api/v1/confirm`. The stored key is `worker.interrupted_hint.enabled`. Null restores off. A failed read counts as off.

**Validation:** Read the switch back. With it off, a dispatched Worker's task prompt has no interrupted-attempt line. With it on, interrupt a disposable attempt and confirm the next Worker of that same attempt has exactly one line naming `deploy drain`, `restart not adopted` or `run stopped`, and that a first run and an ordinary failure do not. The line is fixed, not a custom prompt.

**Disable / rollback:** Submit `{"enabled":false}` or null and confirm. Later dispatches omit the line; prompts already sent are not rewritten. No migration is involved.

**Authority boundary:** Both operations are operator-only and the update is a high-risk confirmation. The line tells the Worker to inspect the workspace and check for side effects that already happened. It grants no tool and changes nobody's right to dispatch a run.

**Docs:** https://github.com/foolzzz/looper/blob/v2.15.43/docs/architecture/agent-system.md

### 升级决策

**谁需要升级：** 希望由任务管家回答任务、希望在模型连接中断时暂停任务、或希望 Worker 被中断后重派时看到提示的操作者；使用工作台、希望在未开始的草稿上选择任务管家模型的操作者；以及所有安装，因为启动会应用迁移 2100 和 2120。从 v2.15.38 或更早版本直接升级到 v2.15.43，并阅读 [v2.15.42](v2.15.42.md)、[v2.15.41](v2.15.41.md)、[v2.15.40](v2.15.40.md)、[v2.15.39](v2.15.39.md)。

**解决了什么：** 两个工作台开关都打开时，任务有自己的对话，由任务管家回答，带固定命令、任务内工具和工作台中栏；`manager_answers` 关闭时仍走 Planner。网络暂停打开时，结构化的模型连接失败会暂停任务，恢复时不消耗步骤重试。中断提示打开时，重派的 Worker 会被告知上一次尝试被中断。供后续加固版本使用的 chat-scope 代码已在库里，现在不能使用。启动日志会写明实际执行的每一项迁移。

**是否有破坏性变更：** 无删除的操作或设置，但无新开关的行为会变化，升级前请阅读「行为变化」：`operator_chat.messages` 每次都带 `has_more` 和 `next_before`；启动新增迁移 2100、2120（2100 会对 `chat_messages` 做一次约束校验）并打耗时日志；Telegram 与 Lark 历史行记录管家会话与发送者；多个 operator API 结果增加字段。本版新增运行时依赖 `cryptography` 46.x（确切范围见升级一节）；源码目录升级（`looper service upgrade`）在服务停止期间安装它，此时机器必须能访问包索引，离线或固定版本的环境必须自行提供。从 v2.15.41 或更早升级还会继承 v2.15.42 的迁移与行为变化。早于桥接版本的安装需先升级到 v2.13.165 并启动一次。

**如何验证：** 源码目录升级前，确认包索引（或 uv 缓存）能提供 cryptography 46.x。核对版本，确认服务启动并应用 `chat_message_entry_kind`（2100）和 `network_pauses`（2120）。以操作者读取 `task_conversations.get`，确认 `manager_answers` 为 false。工作台开启且该开关关闭时，已开始的任务仍打开 Planner 线程，向任务目标发送返回 409 `task_manager_off` 且不落库。读取 `network_pause.get` 和 `worker_interrupted_hint.get`，确认两者都关。不要使用 chat-scope 设置。本次文档检查见「验证」。

### 从 v2.15.38 或更早版本升级

直接升级到 v2.15.43，本版包含 v2.15.42、v2.15.41、v2.15.40 与 v2.15.39。v2.15.42 的迁移 2090、2130、2140，以及 v2.15.39 的 `task_drafts`（2050）和 `proactive_bodies`（2110）随之继承。对已完成 v2.15.42 的数据库，即使可选功能全部关闭，启动仍新增两项迁移，沿用迁移前备份，不重写已有表：2100 `chat_message_entry_kind` 为 `chat_messages` 增加可空的 `entry_kind`（无默认值，不重写）和取值为空、`message`、`command`、`command_reply` 的约束（先 `NOT VALID`），在线步骤在同一次启动中对 `chat_messages` 扫描一次完成校验，不阻塞读写，大表首次启动会更久，耗时见其日志行；2120 `network_pauses` 创建 `task_network_pauses`，没有在线步骤。新依赖：`pyproject.toml` 增加 `cryptography>=46,<47`，用于加密 `operator_chat.messages` 的历史游标（`looper/agents/v1_domains/operator_chat_history.py:12`）；`install.sh` 会随 wheel 一并安装；源码目录升级（`looper service upgrade`）在服务停止期间安装它，此时机器必须能访问包索引（或 uv 缓存里已有对应 wheel）；离线或固定版本的环境需在升级前提供 cryptography 46.x。降级需保留迁移前备份，无 down migration。早于 v2.13.165 的安装需先升级到 v2.13.165 并启动一次。

### 行为变化

- **无新开关（以下改动只有操作者可见，或只多记录数据；私聊用户、群成员和非操作者 API 客户端看不到变化，模型输入与回复文本也不变，也没有新增拒绝；共同的影响只有大 `chat_messages` 表首次启动更久）：** `operator_chat.messages` 每次都返回 `has_more` 和 `next_before`（#1820），默认仍是最新 200 条、从旧到新、列不变，任务线程另有 `turn_state`；启动时实际执行的迁移或在线步骤各打一行耗时（#1757），已完成的不再打，迁移 2100、2120 总会跑；网络暂停与中断提示关闭时，Planner 回合、派发、任务停止和 Worker 派发会先读这两项设置，行为不变。
- **Telegram 与 Lark 历史记录发送者（#1746）：** 用户消息行写入管家会话、发送者类型（`person` 或 `bot`）和发送者名称，管家回复与空闲检查通知写入会话；列早已存在，默认路径不读取，`operator_chat.messages` 不返回。
- **operator API 与设置页新增范围字段（#1748、#1752、#1760、#1765）：** 新增仅限操作者的 `capability_sets.list/get`、`chat_scope_overrides.list/put/delete`、`resident_limits.get/update`；聊天绑定增加 `default_scope`、`effective_default_scope`、`legacy_allowed`、`suggested_scope`，`manager_chat_bindings.put` 接受 `default_scope`、`stop_now`；`manager_sessions.list` 接受 `manager_id`，行增加 `scope`、`retired`；管家指标摘要增加全为零的 `scopes`；设置页为每个非内置管家显示只读的会话列表和范围字段。在没有管家被路由为 `scoped`（现在选不了）之前都不起作用。
- **小修复：** 管家指标的延迟读取在窗口无数据时返回空百分位而不是失败；无效的聊天绑定请求现在返回具体原因。
- **工作台开、`manager_answers` 关：** 已开始的任务仍走 Planner，读设置失败或没有该字段时也是；页面按所选任务读取 `task_conversations.get`，答复前显示「正在检查对话可用性」。未开始的草稿显示任务管家模型选择（#1825），选择不会启动任务，并会在任务线程写入 `model_switched` 行（#1820）。向任务目标发送返回 409 `task_manager_off`，不写聊天行，也不写 `agent_sessions`。工作台关闭时这些都不可达。
- **其他开关：** 两个任务开关都开时见「包含的改动」。网络暂停与中断提示关闭时没有暂停、没有提示行、任务详情不查暂停表。chat scopes 除上面列出的字段外不改变任何行为，群聊与私聊路由、提示词、工具列表和启动签名都走原路径；#1842 只改已经是 scoped 的会话。
- **入口：** 仪表盘有工作台中栏、草稿模型选择、任务停止、`/start` 句子与「正在检查对话可用性」，网络暂停时任务详情显示原因和截止时间，中断提示没有控件，设置页新增会话列表与范围字段（现在不能使用）。Telegram 和 Lark 没有新命令，暂停的任务出现在已有的「需要你」摘要里。CLI/API 新增 `network_pause.get/update`、`worker_interrupted_hint.get/update` 和上述范围操作，`task_conversations` 增加 `manager_answers`，`operator_chat.messages` 增加分页字段。没有删除已有操作。

### 可选能力启用与使用

以下三个面是本版可启用的可选能力。示例只做读取，需替换示例站点并提供操作者 cookie，不会自动开启。Chat scopes 不是本版的启用面。继承能力见 v2.15.42、v2.15.41 和 v2.15.39。

#### Task Manager answers

**启用：** 默认关闭。操作者先读 `task_conversations.get`，再经 `task_conversations.update` 提交 `manager_answers` 为 true，并用 `POST /api/v1/confirm` 完成确认。工作台也必须开，走同一操作的 `enabled` 字段和它自己的确认。任一字段传 null 恢复该字段的默认。

**验证：** 读回两个开关。工作台开、`manager_answers` 关时，已开始的任务打开 Planner 线程，向任务目标发送返回 409 `task_manager_off` 且不写任务线程。两个都开时，中栏使用 `task-chat:<task_id>`，直接模式由任务管家回答，`/start` 只返回状态句子。再关掉回答开关，新的任务目标应被拒绝。不要对生产任务做这个检查。

**停用 / 回退：** 将 `manager_answers` 设为 false 或 null 并确认。新的任务目标返回 `task_manager_off`，工作台回到 Planner。已在回合中的任务管家会跑完这一轮，但之后的工具调用被拒绝；空闲回收或关闭任务再收回进程。这不关闭工作台，不删除迁移 2100 或 2120，也不动网络暂停和 Worker 提示。

**权限边界：** 两个操作都仅限操作者，更新是高风险确认。任务管家是该任务的 Claude Code 常驻进程，工具和命令策略只在该进程内生效，跑在服务的操作系统用户下，不是独立沙箱。其他发送者不会因此得到操作者的操作。

**文档：** https://github.com/foolzzz/looper/blob/v2.15.43/docs/architecture/agent-system.md

```bash
curl --fail --cookie operator-cookies.txt --json '{}' https://looper.example/api/v1/task_conversations/get
```

#### Network pause

**启用：** 默认关闭。操作者先读 `network_pause.get`，再经 `network_pause.update` 提交 `{"enabled":true}` 并完成确认。存储键是 `engine.network_pause.enabled`。`max_pause_seconds` 可选，默认 7200，范围 1–86400。对发送的字段，null 恢复默认。

**验证：** 启用前读回应为 false，启用后为 true。在一次性任务上，结构化的模型连接失败应暂停任务并显示原因和截止时间，端点能连通后恢复同一次尝试，且不消耗步骤重试。传输错误恢复之后的无关失败不应再暂停。到期后状态为 `waiting_user`。开关关闭时，同样的失败走原来的重试。

**停用 / 回退：** 提交 `{"enabled":false}` 或 null 并确认。下一次检查以 `disabled` 清掉已有暂停，包括 `waiting_user` 的。之后的失败走普通重试。`task_network_pauses` 表还在。

**权限边界：** get 和 update 都仅限操作者，update 是高风险确认。探针只对失败那次启动的端点做 TCP 或 TLS 连接，不发 HTTP，也不调用模型，不给任务新工具。

**文档：** https://github.com/foolzzz/looper/blob/v2.15.43/docs/architecture/agent-system.md

```bash
curl --fail --cookie operator-cookies.txt --json '{}' https://looper.example/api/v1/network_pause/get
```

#### Interrupted-attempt hint

**启用：** 默认关闭。操作者先读 `worker_interrupted_hint.get`，再经 `worker_interrupted_hint.update` 提交 `{"enabled":true}` 并完成确认。存储键是 `worker.interrupted_hint.enabled`。null 恢复关闭。读失败视为关闭。

**验证：** 读回开关。关闭时派一个 Worker，任务提示里没有中断行。打开后，中断一个一次性尝试，同一次尝试的下一个 Worker 应正好多一行，原因是 `deploy drain`、`restart not adopted` 或 `run stopped`；第一次运行和普通失败没有这一行。这行文字是固定的。

**停用 / 回退：** 提交 `{"enabled":false}` 或 null 并确认。之后的派发不再带这一行，已发出的提示不会改写，没有要回滚的迁移。

**权限边界：** 两个操作都仅限操作者，更新是高风险确认。这一行让 Worker 检查工作区，并在重复外部副作用之前先确认是否已经发生。它不新增工具，也不改变谁可以派发运行。

**文档：** https://github.com/foolzzz/looper/blob/v2.15.43/docs/architecture/agent-system.md

```bash
curl --fail --cookie operator-cookies.txt --json '{}' https://looper.example/api/v1/worker_interrupted_hint/get
```

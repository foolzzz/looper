# Looper v2.14.188

This is the patch release v2.14.188, a hotfix line in which each merged change ships at once. It documents one change: [#1356](https://github.com/foolzzz/looper/pull/1356) (compute the request-recording code hash off the event loop).

## Release Decision

**Who should upgrade:** Operators who run the request-recording proxy and want lower API latency, because the control plane no longer fingerprints its code on the event loop.

**What this release solves:** [#1356](https://github.com/foolzzz/looper/pull/1356) computes the request-recording code hash (`code_sha256`) once per server process in a background thread instead of recomputing it on the event loop at every proxy health check. The outdated-proxy check compares against that cached value. The PR presents latency as the only intended change.

**Breaking changes:** No. The Telegram and Lark channel protocols and the CLI are unchanged, no new command or dashboard control is added and there is no database schema change. The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.14.188
```

**Contributors:** Maintainer @foolzzz authored [#1356](https://github.com/foolzzz/looper/pull/1356); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.187 upgrades directly. There is no database schema change. Restart the service after upgrading, as for every release.

## Behavior changes

Read in the diff of [#1356](https://github.com/foolzzz/looper/pull/1356) (`looper/agents/llmrec/control.py`, a new test file and the architecture doc).

- **Code hash computed once per process, off the loop.** `control.py` keeps a module-level `_code_hash`, filled under a lock by `_load_code_hash()`. `_server_code_hash()` returns the cached value, or computes it with `asyncio.to_thread` so the event loop is not blocked. `ProxyControl._health` (the outdated-proxy check) and `ProxyControl.at_start` now use it instead of calling `code_sha256()` directly. `at_start` computes it before anything else, so it is warm before serving.
- **Visible consequence: checkout changes are noticed at restart.** Before, each health check recomputed the fingerprint, so a changed checkout could mark a running proxy outdated without a server restart. Now the server's fingerprint is fixed for the process lifetime; the architecture doc states that checkout changes take effect at the next server restart, as performed by upgrades, and that each proxy still fingerprints its code at startup. The outdated-proxy rules themselves (code hash, route format, translate feature) are unchanged.
- **PR text versus code.** The PR goal mentions an optional 60-second background refresh. The diff contains no refresh; the cache is never invalidated within a process. This draft follows the code and the doc.
- **Docs and tests.** The gateway section of `docs/architecture/agent-system.md` describes the above. The new `tests/test_llmrec_code_hash.py` (113 lines) covers the cache; the PR also names `test_llmrec_control`, `test_llmrec_lifecycle_db` and `test_llmrec_serve_db`.
- **Model-visible changes:** None. No prompt, tool description, tool schema or agent environment changed.

### 升级决策

**谁需要升级：**运行请求记录代理、希望降低 API 延迟的运维人员，因为控制面不再在事件循环上计算代码指纹。

**是否有破坏性变更：**无。Telegram 与 Lark 渠道协议和 CLI 不变，没有新增命令或仪表盘控件，也没有数据库 schema 变更。桥接边界不变：早于 v2.13.165 的安装须先升级到 v2.13.165。

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.187 上的安装可直接升级。没有数据库 schema 变更。升级后照常重启服务。

### 行为变化与入口

以下在 [#1356](https://github.com/foolzzz/looper/pull/1356) 的差异中可见（`looper/agents/llmrec/control.py`、新增测试文件和架构文档）。

- **代码哈希每进程只算一次，且不在事件循环上。**`control.py` 保存模块级 `_code_hash`，由 `_load_code_hash()` 在锁内填充。`_server_code_hash()` 返回缓存值，否则用 `asyncio.to_thread` 计算，不阻塞事件循环。`ProxyControl._health`（过期代理检查）和 `ProxyControl.at_start` 现在使用它，而不是直接调用 `code_sha256()`。`at_start` 最先计算，因此开始服务前已就绪。
- **可见后果：检出内容的变化在重启时才被发现。**此前每次健康检查都重算指纹，运行中的代理可能在服务未重启时因检出内容变化而被判为过期。现在服务端指纹在进程生命周期内固定；架构文档说明检出变化在下一次服务重启（如升级）时生效，且每个代理仍在启动时计算自己的代码指纹。过期代理的规则本身（代码哈希、路由格式、translate 特性）不变。
- **PR 文字与代码不一致。**PR 目标提到可选的 60 秒后台刷新，但差异中没有刷新，缓存在进程内从不失效。本草稿以代码和文档为准。
- **文档与测试。**`docs/architecture/agent-system.md` 的网关一节描述了上述内容。新增 `tests/test_llmrec_code_hash.py`（113 行）覆盖缓存；PR 还列出 `test_llmrec_control`、`test_llmrec_lifecycle_db` 和 `test_llmrec_serve_db`。
- **面向模型的变化：**无。提示词、工具描述、工具 schema 和智能体环境均未改变。

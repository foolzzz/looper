# Looper v2.14.190

This is the patch release v2.14.190, a hotfix line in which each merged change ships at once. It documents two changes: [#1359](https://github.com/foolzzz/looper/pull/1359) (the code manifest is computed off the event loop at startup) and [#1357](https://github.com/foolzzz/looper/pull/1357) (the Lark bot-mention poll is frequent only where bots post).

## Release Decision

**Who should upgrade:** Operators who use the Lark channel with many bound chats and want fewer thread scans of quiet chats, and operators who want `looper serve` startup not to hash the installation on the event loop.

**What this release solves:** [#1359](https://github.com/foolzzz/looper/pull/1359) computes the startup code manifest once in a worker thread before the kept-run scan, so the cold read no longer blocks the loop. [#1357](https://github.com/foolzzz/looper/pull/1357) polls bound Lark chats for bot mentions every 30 seconds only where bots post or the chat is open to everyone, and every 5 minutes elsewhere.

**Breaking changes:** No. The Telegram and Lark channel protocols and the CLI are unchanged, no new command or dashboard control is added and there is no PostgreSQL schema change. [#1357](https://github.com/foolzzz/looper/pull/1357) is a stated behavior change (see Behavior changes). The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.14.190
```

**Contributors:** Maintainer @foolzzz authored [#1359](https://github.com/foolzzz/looper/pull/1359) and [#1357](https://github.com/foolzzz/looper/pull/1357); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.189 upgrades directly. There is no PostgreSQL schema change; the Lark channel's local inbox file gains a small `bot_activity` table, created automatically (see below). Restart the service after upgrading, as for every release.

## Behavior changes

Read in the diffs of [#1359](https://github.com/foolzzz/looper/pull/1359) and [#1357](https://github.com/foolzzz/looper/pull/1357).

### #1357: Lark bot-mention poll is frequent only where bots post

The PR calls this an intended behavior change by maintainer decision.

- **Two cadences.** The poll that finds bot mentions in bound chats runs every 30 seconds (`_BOT_POLL_SECONDS`) for a "fast" chat and every 5 minutes (`_BOT_SLOW_POLL_SECONDS`) for every other chat. A chat is fast when a bot (app sender) message was seen in it within the last 7 days, or when its explicit route has the sender policy `chat` (open to everyone in the chat). A chat with no previous poll is polled at once.
- **Quiet chats skip the thread scan.** The thread scan of a polled chat runs only if the local inbox has thread activity for the chat within the root-age window, or the chat's history page shows a thread message.
- **Bot activity record.** The Lark inbox (a local SQLite file) gets a `bot_activity` table (chat id, last time), created with `CREATE TABLE IF NOT EXISTS`; entries older than 7 days are deleted when read. It is filled from received events and from catch-up history, which observes app and bot senders even for old, unmentioned or unlisted messages (deleted messages are ignored). An older version ignores the table.
- **Log line.** At most once an hour per channel: `lark_bot_poll_cadence channel=... fast=N slow=M`.
- **Visible consequence:** a bot mention in a chat with no bot message in 7 days and a listed-sender policy can be picked up up to about 5 minutes later than before; once a bot posts there (seen by event or catch-up), the chat becomes fast. The 30-second case is unchanged.

### #1359: the code manifest is computed off the event loop at startup

- **New `components.prepare_loaded_manifest()`** runs `loaded_manifest` in a worker thread, shares one cold read among concurrent callers (a cancelled waiter does not start a second read) and leaves the snapshot cached in `loaded_manifest`.
- **Startup order.** `serve.py` calls it in a new `code_manifest` startup step before the kept-run scan (`kept_scan`); the HTTP server's start uses it instead of the synchronous call. The step appears in the logged `startup steps:` summary.
- The result is unchanged; the PR states latency as the only difference. Later synchronous callers (such as kept-run adoption) reuse the cached snapshot.

### Model-visible changes

None. No prompt, tool description or tool schema changed in either PR. The Lark poll cadence changes when a bot mention reaches the agent, not what the agent sees.

### 升级决策

**谁需要升级：**绑定了大量聊天的 Lark 渠道运维人员（希望减少对安静聊天的线程扫描），以及希望 `looper serve` 启动时不在事件循环上对安装目录做哈希的运维人员。

**解决了什么：**[#1359](https://github.com/foolzzz/looper/pull/1359) 在保留运行扫描之前于工作线程中计算一次启动代码清单，冷读取不再阻塞事件循环。[#1357](https://github.com/foolzzz/looper/pull/1357) 仅对有机器人发言或对所有人开放的聊天每 30 秒轮询一次机器人提及，其余聊天每 5 分钟一次。

### 行为变化与入口

以下在 [#1359](https://github.com/foolzzz/looper/pull/1359) 和 [#1357](https://github.com/foolzzz/looper/pull/1357) 的差异中可见。

**#1357：Lark 机器人提及轮询只在有机器人发言处保持高频**（PR 称之为维护者决定的有意行为变化）

- **两种节奏。**在已绑定聊天中查找机器人提及的轮询，对“快速”聊天每 30 秒一次（`_BOT_POLL_SECONDS`），其余聊天每 5 分钟一次（`_BOT_SLOW_POLL_SECONDS`）。过去 7 天内在该聊天中见过机器人（app 发送者）消息，或其显式路由的发送者策略为 `chat`（对聊天内所有人开放）时，该聊天为快速聊天。尚未轮询过的聊天会立即轮询。
- **安静的聊天跳过线程扫描。**仅当本地收件箱在根消息年龄窗口内有该聊天的线程活动，或该聊天历史页中出现线程消息时，才扫描线程。
- **机器人活动记录。**Lark 收件箱（本地 SQLite 文件）新增 `bot_activity` 表（聊天 ID、最近时间），用 `CREATE TABLE IF NOT EXISTS` 创建；超过 7 天的记录在读取时删除。数据来自收到的事件和补抓历史，补抓会观察所有 app 和机器人发送者，即使消息很旧、未提及或未列入（已删除的消息除外）。旧版本会忽略该表。
- **日志。**每个渠道最多每小时一条：`lark_bot_poll_cadence channel=... fast=N slow=M`。
- **可见后果：**在过去 7 天无机器人消息且发送者策略为列表的聊天中，机器人提及可能比以前晚约 5 分钟才被发现；机器人在其中发言（经事件或补抓看到）后该聊天转为快速。30 秒的情形不变。

**#1359：启动时在事件循环之外计算代码清单**

- **新增 `components.prepare_loaded_manifest()`**，在工作线程中运行 `loaded_manifest`，并发调用方共享同一次冷读取（被取消的等待者不会触发第二次读取），快照仍缓存在 `loaded_manifest` 中。
- **启动顺序。**`serve.py` 在保留运行扫描（`kept_scan`）之前，以新的 `code_manifest` 启动步骤调用它；HTTP 服务启动改用它而不是同步调用。该步骤出现在日志的 `startup steps:` 汇总中。
- 结果不变；PR 称延迟是唯一差异。之后的同步调用方（如保留运行接管）复用缓存的快照。

**面向模型的变化：**无。两个 PR 均未改动提示词、工具描述或工具 schema。Lark 轮询节奏改变的是机器人提及何时到达智能体，而不是智能体看到的内容。

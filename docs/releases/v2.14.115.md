# Looper v2.14.115

This is the patch release v2.14.115, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.114: workflow presets reach the dashboard, the Manager, project defaults and configuration transfer ([#1181](https://github.com/foolzzz/looper/pull/1181)).

## Release Decision

**Who should upgrade:** Operators who use or plan to use workflow presets (introduced in v2.14.113) and want to manage and choose them without the CLI. Installations that do not define workflows see no change in behavior.

**What this release solves:** [#1181](https://github.com/foolzzz/looper/pull/1181). Workflows could only be defined and selected through the v1 API and `loopercli`. They can now be managed in Settings → Workflows, chosen in the dashboard task form, requested from the Manager (including Telegram and Lark chats), set as a project default, and exported and imported with the configuration.

**Breaking changes:** No. There is no schema change; tasks and plans without a workflow behave as before.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.14.115
```

**Contributors:** Maintainer @foolzzz authored [#1181](https://github.com/foolzzz/looper/pull/1181); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.114 upgrades directly. There is no database change in this release.

## Behavior changes

- **Dashboard.** Settings has a Workflows page: a list, a JSON editor for new and existing presets (validation errors are shown unchanged) and a delete that asks for confirmation. The task form shows a Workflow field when presets exist, preselects the chosen project's default, summarizes the preset (work role, review panel, retries, verification) and shows the preset's fixed Profiles read-only; those fixed roles are not sent as overrides. Task details show a badge with the workflow's name. Project Execution settings gain a Default workflow field.
- **Project default.** `default_workflow` is accepted on project create and update in the v1 API; `null` clears it and an omitted value keeps it. A key that names no workflow is rejected with a 400 error. Project views include it.
- **Manager.** When presets exist, `looper_task_create` offers `workflow` limited to the existing keys plus `none`; with none defined the field is absent for the Manager. API clients still accept any key. The Manager's context lists each workflow's key, name and a clipped description, shows a project's default workflow, and tells the Manager to use one only when the user names it or the project has a default, and to say which was used. The tool listing is part of the resume check, so a change in workflows changes it.
- **`looper_projects`** can update `dependency_conditions` (`on`, `off`, or null to inherit); project get and list return its stored value.
- **Configuration transfer.** Export includes `workflows` (Profile ids replaced by names) and each project's `default_workflow`; import validates each workflow, replaces one with the same key, skips an invalid one with a reason, applies the name-uniqueness and distinct-reviewer-runtime checks, and clears a Profile binding it cannot resolve with a note. A project default naming an unknown workflow is imported without a default. Importing a document with workflows through a non-operator client is refused (forbidden).
- **Tests and evals.** Two Manager dialogs (`workflow_named`, `workflow_unspecified`) join the prompt-regression set, which is now 60 dialogs, and the registry comparison ignores provider login probes.
- **Model-visible changes:** Yes. For the Manager, the `looper_task_create` schema gains or loses the `workflow` field with the existing presets (enum of keys and `none`), the `looper_projects` schema and description gain `dependency_conditions`, and its prompt gains a Workflows section and a per-project default workflow note. Task detail output includes the workflow snapshot. Tasks and Manager sessions with no workflows defined keep their prior prompt apart from the `dependency_conditions` addition.
- **Unchanged:** execution of review panels and verification rules (stored and validated, as before), the Planner's workflow handling, and the schema.

### 升级决策

**谁需要升级：**使用或打算使用工作流预设（v2.14.113 引入）、希望不靠 CLI 管理和选择它们的运维者。未定义工作流的安装行为无变化。

**是否有破坏性变更：**否。无数据库结构变更；没有工作流的任务和计划行为不变。

**如何验证：**核对版本为 2.14.115。

**贡献者：**维护者 @foolzzz 提交 [#1181](https://github.com/foolzzz/looper/pull/1181)；本版本无社区贡献。

looper --version   # looper 2.14.115

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.114 上的安装可直接升级。本版本无数据库变更。

### 行为变化与入口

- **仪表盘。**设置新增“工作流”页：列表、新建与编辑预设的 JSON 编辑器（校验错误原样显示）、需确认的删除。存在预设时任务表单显示工作流字段，预选所选项目的默认值，概述预设（开发角色、评审组、重试、验证），并只读显示预设固定的 Profile；这些固定角色不会作为覆盖项发送。任务详情显示工作流名称徽标。项目执行设置新增“默认工作流”。
- **项目默认值。**v1 API 在创建和更新项目时接受 `default_workflow`；`null` 清除，省略则保持不变。不存在的工作流键返回 400。项目视图包含该字段。
- **Manager。**存在预设时，`looper_task_create` 提供的 `workflow` 仅限现有键加 `none`；没有定义时 Manager 看不到该字段。API 客户端仍接受任意键。Manager 上下文列出每个工作流的键、名称和截断的描述，显示项目的默认工作流，并要求仅在用户指明或项目有默认值时使用，且告知所用工作流。工具列表计入恢复检查，因此工作流变化会改变它。
- **`looper_projects`** 可更新 `dependency_conditions`（`on`、`off`，或 null 表示继承）；项目 get 和 list 返回其存储值。
- **配置迁移。**导出包含 `workflows`（Profile id 换成名称）和各项目的 `default_workflow`；导入逐个校验工作流，同键替换，无效的带原因跳过，并执行名称唯一和评审运行时不同的检查，无法解析的 Profile 绑定会清除并给出说明。项目默认值指向未知工作流时，导入时不设默认值。非运维身份的客户端导入含工作流的文档会被拒绝（forbidden）。
- **测试与评测。**提示词回归集新增两个 Manager 对话（`workflow_named`、`workflow_unspecified`），共 60 个；注册表比较忽略提供方登录探测。
- **面向模型的变化：**有。对 Manager 而言，`looper_task_create` 的 schema 随现有预设增减 `workflow` 字段（键与 `none` 的枚举），`looper_projects` 的 schema 和描述新增 `dependency_conditions`，提示词新增工作流小节和每个项目的默认工作流说明。任务详情输出包含工作流快照。未定义工作流的任务和 Manager 会话，除 `dependency_conditions` 的新增外，提示词不变。
- **不变：**评审组和验证规则的执行（与之前一样只存储和校验）、Planner 对工作流的处理、数据库结构。

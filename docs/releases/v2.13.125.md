# Looper v2.13.125

## Release Decision

**Who should upgrade:** Nobody needs to upgrade for a visible feature. This patch release adds storage for Manager chat bindings that nothing uses yet, and it changes what deleting a Manager refuses.

**What this release solves:** [#646](https://github.com/foolzzz/looper/pull/646) adds durable storage for per-bot chat bindings, observed chats and the latest unbound counts. It ships without any message routing, so every bot behaves as before.

**Breaking changes:** No. No command or option changed. Deleting a Manager that still has chat bindings is now refused, but no code can create a binding yet.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#646](https://github.com/foolzzz/looper/pull/646); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.125
```

## Behavior changes

- **Schema (applied on startup, additive):** `looper/db/schema.sql` adds the column `channel_configs.bound_chats_only` (boolean, default false) and three tables: `manager_chat_bindings` (one Manager per bot and chat, restricting deletion of that Manager, removed with the bot), `channel_seen_chats` and `channel_unbound_chats` (per-bot observed chats with a count, last-seen time and name of up to 200 characters; both removed with the bot).
- **New storage module:** `looper/db/chat_bindings.py` provides list, bind, unbind, a locked routing snapshot, a dedicated writer for `bound_chats_only`, a metadata recorder and a paged chat listing. It validates native Telegram and Lark ids, requires a caller transaction for routing writes, keeps every observed chat but only the newest 20 suppressed ones, and swallows recording failures. In this release no production code calls the module, so nothing reads or writes these tables yet; the docstring says it does not enable routing.
- **Manager deletion:** `delete_manager` in `looper/db/managers.py` now returns `has_bindings` when a chat is bound to the Manager, and `looper/agents/managers_api.py` turns that into a 409 saying to unbind first. Bots and tasks were already refused. Since nothing creates bindings, this does not trigger in practice yet.
- **API views:** channel configuration views (`looper/agents/channels/allowlist.py`, `looper/agents/v1_domains/channel_configs.py`) gain a boolean `bound_chats_only` field, always false for now. It is a response field only; the saved bot config does not take it.
- **Model-visible changes:** none. Prompts, tool declarations and results are unchanged.
- **Line counts:** the description of [#646](https://github.com/foolzzz/looper/pull/646) reports tests 680 and production 270 added lines (fixtures excluded).

## Upgrade and rollback

Re-run `install.sh` once v2.13.125 is published. The schema additions apply on first start; no configuration change. Rolling back to v2.13.124 leaves the new column and tables in place, unused and harmless.

### 行为变化与入口

- **表结构（启动时应用，仅新增）：**`looper/db/schema.sql` 新增列 `channel_configs.bound_chats_only`（布尔，默认 false）和三张表：`manager_chat_bindings`（每个 bot 与聊天对应一个 Manager，限制删除该 Manager，随 bot 删除）、`channel_seen_chats` 与 `channel_unbound_chats`（每个 bot 已观察的聊天，含计数、最近时间和最长 200 字符的名称；均随 bot 删除）。
- **新存储模块：**`looper/db/chat_bindings.py` 提供列出、绑定、解绑、加锁的路由快照、`bound_chats_only` 专用写入、元数据记录和分页聊天列表。它校验原生 Telegram 与 Lark id，路由写入需要调用方事务，保留全部已观察聊天但只保留最新 20 条被抑制的聊天，记录失败会被吞掉。本版本没有生产代码调用该模块，因此这些表尚无人读写；其文档字符串说明它不启用路由。
- **删除 Manager：**`looper/db/managers.py` 的 `delete_manager` 在有聊天绑定到该 Manager 时返回 `has_bindings`，`looper/agents/managers_api.py` 将其转为 409，提示先解绑。bot 与任务原本已会被拒绝。由于目前无处创建绑定，实际不会触发。
- **API 视图：**频道配置视图（`looper/agents/channels/allowlist.py`、`looper/agents/v1_domains/channel_configs.py`）新增布尔字段 `bound_chats_only`，目前恒为 false。它只是响应字段，保存的 bot 配置不接受它。
- **面向模型的变化：**无。提示词、tool 声明和结果均未改变。
- **行数：**[#646](https://github.com/foolzzz/looper/pull/646) 的描述报告新增测试 680 行、生产代码 270 行（不含 fixtures）。

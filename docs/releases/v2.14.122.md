# Looper v2.14.122

This is the patch release v2.14.122, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.121: a run records its whole profile fallback chain, a handoff is no longer marked as a fallback run, and the `api` runtime reports a model only when the model itself reported one ([#1203](https://github.com/foolzzz/looper/pull/1203), issue #1172).

## Release Decision

**Who should upgrade:** Operators who use profile fallbacks and read run records (`runs.get`, `runs.list`, the run history), and those who run the `api` runtime and rely on `model_reported`. Installations without profile fallbacks see no change in behavior, apart from the `api` model report and the verification checkout described below.

**What this release solves:** [#1203](https://github.com/foolzzz/looper/pull/1203). A run that followed several fallback hops now records every hop in order; a Planner turn that resumes an old session after a handoff no longer carries the fallback marker of an earlier turn; and the `api` runtime no longer shows the requested model as the reported one.

**Breaking changes:** No. There is no database or API schema change; `metadata.fallback_from` is kept for compatibility, and `metadata.fallback` is an addition.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.14.122
```

**Contributors:** Maintainer @foolzzz authored [#1203](https://github.com/foolzzz/looper/pull/1203); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.121 upgrades directly. There is no schema change.

## Behavior changes

- **Full fallback chain per run.** When the Planner's profile falls back, the target run's metadata gets `fallback`, the ordered list of `{from, to, reason}` hops, in addition to `fallback_from` (the source of the last hop, kept for compatibility). The chain is also recorded on a run whose launch is rejected or cannot start. Before, only the last hop's source was kept, from state shared across turns.
- **Handoffs are not fallback runs.** The chain belongs to the turn that followed it. A Planner turn that continues in an old session through a HANDOFF no longer gets fallback metadata from an earlier turn.
- **Honest model reporting for `api`.** For runs of the `api` runtime, `model_reported` in `runs.get` and `runs.list` is null unless the run's metadata carries a `model_reported` of its own; the record's model (often a gateway alias) is no longer reused. Other runtimes follow their earlier rules.
- **Verification checkout and `.pyc` files.** In the private checkout of a workflow verification run, regular `.pyc` files are not copied from any declared runtime path (`workspace_links` and `verification_paths`), including editable link trees outside the virtualenv. Before, only the virtualenv's `.pyc` files were removed after the copy. This stops another worktree's bytecode from being reused.
- **Unchanged:** runs without fallbacks, Manager sessions (they do not follow fallback chains), the profile settings and the channel commands.
- **Model-visible changes:** None to the Planner, Worker, Reviewer or Manager prompts and contracts. The run records that tools and the dashboard read now show the full fallback chain and a null `model_reported` for the `api` runtime; a verifier's checkout contains no copied `.pyc` files.

### 升级决策

**谁需要升级：**使用 profile 回落并读取运行记录（`runs.get`、`runs.list`、运行历史）的运维者，以及使用 `api` 运行时并依赖 `model_reported` 的用户。没有 profile 回落的安装行为无变化，仅 `api` 的模型报告和下述验证 checkout 有变化。

**解决了什么：**[#1203](https://github.com/foolzzz/looper/pull/1203)。经历多次回落的运行现在按顺序记录每一跳；handoff 后在旧会话中继续的 Planner 回合不再带有先前回合的回落标记；`api` 运行时不再把请求的模型显示为已报告的模型。

**是否有破坏性变更：**否。没有数据库或 API 结构变更；`metadata.fallback_from` 为兼容而保留，`metadata.fallback` 是新增字段。

**如何验证：**核对版本为 2.14.122。

**贡献者：**维护者 @foolzzz 提交 [#1203](https://github.com/foolzzz/looper/pull/1203)；本版本无社区贡献。

```bash
looper --version   # looper 2.14.122
```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.121 上的安装可直接升级。没有结构变更。

### 行为变化与入口

- **每次运行的完整回落链。**Planner 的 profile 回落时，目标运行的元数据新增 `fallback`（按顺序的 `{from, to, reason}` 列表），同时保留 `fallback_from`（最后一跳的来源，为兼容而保留）。启动被拒绝或无法启动的运行也会记录该链。此前只保存最后一跳的来源，且来自跨回合共享的状态。
- **handoff 不是回落运行。**回落链属于跟随它的那个回合。通过 HANDOFF 在旧会话中继续的 Planner 回合不再从先前回合获得回落元数据。
- **`api` 如实报告模型。**对 `api` 运行时的运行，`runs.get` 和 `runs.list` 中的 `model_reported` 除非运行元数据自带 `model_reported`，否则为 null；不再沿用记录中的模型（通常是网关别名）。其他运行时沿用原规则。
- **验证 checkout 与 `.pyc` 文件。**在工作流验证运行的私有 checkout 中，任何声明的运行时路径（`workspace_links` 和 `verification_paths`）里的普通 `.pyc` 文件都不会被复制，包括虚拟环境之外的 editable 链接树。此前只在复制后删除虚拟环境中的 `.pyc`。这避免复用其他 worktree 的字节码。
- **不变：**没有回落的运行、Manager 会话（不跟随回落链）、profile 设置和渠道命令。
- **面向模型的变化：**Planner、Worker、Reviewer 和 Manager 的提示词与契约无变化。工具和仪表盘读取的运行记录现在显示完整回落链，`api` 运行时的 `model_reported` 为 null；验证者的 checkout 中没有复制的 `.pyc` 文件。

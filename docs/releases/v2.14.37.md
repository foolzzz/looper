# Looper v2.14.37

This is the patch release v2.14.37, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.36: housekeeping that keeps going after a failed step, and the run retention setting in the dashboard and the Manager settings tool ([#983](https://github.com/foolzzz/looper/pull/983)).

## Release Decision

**Who should upgrade:** Anyone who runs v2.14.36 and wants service log rotation to survive a failure in another housekeeping step, or who wants to read and set `scheduler.run_retention_days` in the dashboard Settings page or through the Manager.

**What this release solves:** [#983](https://github.com/foolzzz/looper/pull/983) follows up the run retention change of v2.14.36. A failure in one housekeeping step (for example the runner inspection when `ps` fails) used to abort the rest of the pass, so log rotation was skipped and `serve.log` could grow without limit. Each step now runs on its own and each failure is reported. The same change adds the retention setting to the Settings → Scheduler form and to the Manager settings tool's description and messages, the follow-up that v2.14.36 listed as not included.

**Breaking changes:** No. No API or configuration is removed or changed, and there is no new migration.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#983](https://github.com/foolzzz/looper/pull/983); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.37
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.36 upgrades directly. This release adds no migration and no new setting; the retention setting it surfaces already exists.

## Behavior changes

- **Housekeeping steps are independent ([#983](https://github.com/foolzzz/looper/pull/983)).** The hourly pass is split into five steps: runs and notifications, command logs, run directories, runner files, and log rotation. An exception in one step is logged as a warning (`housekeeping step <name> failed`), recorded in the pass report under `failed_steps`, and the remaining steps still run. The closing `housekeeping` log line gains a `failed_steps` field. Before, any exception ended the pass at that point. Which files and rows each step deletes is unchanged.
- **Run directories without a runner ([#983](https://github.com/foolzzz/looper/pull/983)).** The run-state lookup for run directories now sits inside the run directories step and runs only when command runs are available, so a failure there no longer blocks log pruning or rotation.
- **Dashboard retention field ([#983](https://github.com/foolzzz/looper/pull/983)).** Settings → Scheduler shows "Run retention (days)" next to the other two scheduler limits, with the effective value and source. It is a numeric input limited to the setting's range (1 to 3650); Save stays disabled, and Enter does not submit, for a value outside that range or a non-integer. "Use the built-in" shows the built-in as days (30). Saving and resetting use the existing scheduler settings API; no endpoint changes.
- **Model-visible changes:** The Manager settings tool's `scheduler` argument description and its error message for an empty `scheduler` now name `run_retention_days` (days a finished schedule run is kept; each schedule keeps its newest 100). That is tool description text the Manager model sees; the tool's behavior and accepted values are unchanged, since it already accepted the setting in v2.14.36. No prompt or skill text changes, and no real-mode prompt evaluation of the new description is recorded in the pull request.

本版本是 patch release v2.14.37（热修线，每个合并的改动立即发布）。自 v2.14.36 以来只合并了一项改动：清理在某一步失败后继续执行，并在仪表盘和 Manager 设置工具中展示运行保留期设置（[#983](https://github.com/foolzzz/looper/pull/983)）。

### 升级决策

**谁需要升级：**运行 v2.14.36、希望某个清理步骤失败时服务日志轮转仍能执行的人，或想在仪表盘设置页或通过 Manager 读取和修改 `scheduler.run_retention_days` 的人。

**解决了什么：**[#983](https://github.com/foolzzz/looper/pull/983) 是 v2.14.36 运行保留改动的后续。此前清理中任一步骤出错（例如 `ps` 失败导致 runner 检查出错）会中止整个流程，日志轮转被跳过，`serve.log` 可能无限增长。现在每个步骤独立执行，并报告各自的失败。同一改动还把保留期设置加入 Settings → Scheduler 表单以及 Manager 设置工具的描述和提示，即 v2.14.36 中列为未包含的后续项。

**是否有破坏性变更：**否。不移除或更改任何 API 或配置，也没有新的迁移。

**如何验证：**运行 `looper --version` 核对版本为 2.14.37。

**贡献者：**维护者 @foolzzz 提交 [#983](https://github.com/foolzzz/looper/pull/983)；本版本无社区贡献。

```bash
looper --version   # looper 2.14.37
```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.36 上的安装可直接升级。本版本没有新迁移，也没有新设置；它所展示的保留设置已经存在。

### 行为变化与入口

- **清理步骤相互独立（[#983](https://github.com/foolzzz/looper/pull/983)）。**每小时的清理分为五步：运行记录与通知、命令日志、运行目录、runner 文件、日志轮转。某一步抛出异常时记录一条警告（`housekeeping step <name> failed`），写入清理报告的 `failed_steps`，其余步骤照常执行；结尾的 `housekeeping` 日志行新增 `failed_steps` 字段。此前任何异常都会在该处终止整个流程。各步骤删除哪些文件和记录不变。
- **运行目录的状态查询（[#983](https://github.com/foolzzz/looper/pull/983)）。**运行目录所需的运行状态查询现在位于运行目录步骤内，且仅在有命令运行器时执行，所以该处失败不再阻塞日志清理和轮转。
- **仪表盘保留期字段（[#983](https://github.com/foolzzz/looper/pull/983)）。**Settings → Scheduler 在另外两个限制旁显示“Run retention (days)”，带生效值和来源。它是限定在设置范围（1 到 3650）内的数字输入；值超出范围或不是整数时，Save 保持禁用，回车也不会提交。“Use the built-in”以天为单位显示内置值（30）。保存和重置使用现有的调度器设置 API，没有接口变化。
- **面向模型的变化：**Manager 设置工具中 `scheduler` 参数的描述，以及 `scheduler` 为空时的错误提示，现在写明 `run_retention_days`（已结束的定时任务运行保留的天数；每个任务保留最新 100 条）。这是 Manager 模型会看到的工具描述文本；工具行为和可接受的值不变，因为 v2.14.36 已接受该设置。提示词和技能文本不变，拉取请求中没有记录对新描述的真实模式 prompt 评估。

# Looper v2.14.60

This is the patch release v2.14.60, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.59: command schedule confirmations are bound to the directory the command runs in, and an edit of a command schedule that will run again needs its own confirmation ([#1028](https://github.com/foolzzz/looper/pull/1028)).

## Release Decision

**Who should upgrade:** Anyone who runs command schedules and creates, enables, edits or runs them through the Manager (web chat, Telegram, Lark), a client token, or `/api/v1/schedule_admin`.

**What this release solves:** A command schedule without `work_dir` runs in its project's directory, but the confirmation for enabling or running it bound only the schedule's own settings. If the project's directory changed between the question and the user's reply, the command ran in a directory the user was not shown. Separately, an edit of the command, env, env file or directory of an enabled command schedule (or of a disabled one with a queued run) was applied without asking, so the next fire or the queued run executed a command nobody confirmed. [#1028](https://github.com/foolzzz/looper/pull/1028) versions the effective directory into the confirmation, shows it in the question, and asks the user to confirm such an edit. A confirmation whose settings or effective directory changed after the question is refused with the existing `conflict` / 409, and the user is asked again.

**Breaking changes:** No. No API or configuration is removed and there is no migration. Agent schedules keep their versions, wording and update behavior.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#1028](https://github.com/foolzzz/looper/pull/1028); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.60
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.59 upgrades directly. This release adds no migration. A confirmation question asked before the upgrade and answered after it may be refused once as changed; ask again.

## Behavior changes

- **Enable and run-now confirmations bind the effective directory ([#1028](https://github.com/foolzzz/looper/pull/1028)).** For a command schedule, the confirmed version now includes the directory it runs in: its own `work_dir`, or its project's directory when it sets none. If the project's directory changes between the question and the reply, the confirmation is refused with `conflict` / 409 and the user is asked again. This covers the Manager's `looper_schedules` tool, the same tool through a client token, and `/api/v1/schedule_admin/update` and `run`. The question for enabling a command schedule and for run now now names the directory (run now through the API shows the project directory, or "none set").
- **Editing what a command schedule runs needs a confirmation when it will run again.** A change to `command`, `env`, `env_file` or `work_dir` of a command schedule that is enabled, or disabled with a queued run, is no longer applied directly. The Manager's update returns `needs_confirmation`, and `/api/v1/schedule_admin/update` returns its impact for confirmation. The question shows the before and after command, the changed env keys (and which values changed, never the values), the env file, and the effective directory, and says whether the next fires or the queued run will execute the change. The confirmed update then applies only if the schedule and its effective directory are still as shown. A disabled schedule without a queued run, and edits of other fields, are applied without asking as before.
- **A directory edit binds its destination.** The version of an update that sets `work_dir` also covers the directory it will inherit from the project when set to empty.
- **Unchanged.** Agent schedules, the dashboard (its form and switch are the user's own action), config import, and a change to the project's own directory (it still moves the schedules that inherit it without asking) are out of scope and unchanged.
- **Model-visible changes:** Yes. The Manager prompt's list of `needs_confirmation` cases adds "changing what an enabled or queued command schedule runs"; the `looper_schedules` tool documentation says such a change is `high` and confirmed in the next message; and the confirmation texts for enabling, running and editing a command schedule now show the directory, as described above. The new edit question is covered by the `schedule_command_edit` prompt-regression dialog, which raises the dialog count from 49 to 50 in `evals/README.md`.
- **Documentation and tests.** The change is in `looper/agents/ops/schedules.py`, `looper/agents/v1_domains/schedule_writes.py`, `looper/agents/schedules.py`, `looper/agents/scheduler.py`, `looper/agents/tiers/manager.py` and `looper/db/schedules.py`. Tests are in `tests/test_manager_schedule_tools_db.py`, `tests/test_api_v1_schedule_writes_db.py`, `tests/test_manager_schedule_changes_db.py` and `tests/test_model_manager_dialogs.py`.

## 中文摘要

本版本是 patch release v2.14.60（热修线，每个合并的改动立即发布）。自 v2.14.59 以来只合并了一项改动：命令型定时任务的确认绑定其运行目录，且对将再次运行的命令型定时任务的修改需要单独确认（[#1028](https://github.com/foolzzz/looper/pull/1028)）。

### 升级决策

**谁需要升级：**使用命令型定时任务，并通过 Manager（网页聊天、Telegram、Lark）、客户端 token 或 `/api/v1/schedule_admin` 创建、启用、修改或运行它们的用户。

**解决了什么：**没有 `work_dir` 的命令型定时任务在其项目目录中运行，但启用或运行它的确认只绑定了定时任务自身的设置。若项目目录在提问与用户回复之间变化，命令会在用户没看到的目录中运行。另外，修改已启用的命令型定时任务（或带有排队运行的停用任务）的命令、env、env 文件或目录会被直接应用，下一次触发或排队运行就会执行没人确认过的命令。[#1028](https://github.com/foolzzz/looper/pull/1028) 把实际运行目录纳入确认版本，在提问中显示，并要求用户确认此类修改。提问之后设置或实际目录发生变化的确认，会以已有的 `conflict` / 409 拒绝，并重新询问用户。

**是否有破坏性变更：**否。没有移除任何 API 或配置，也没有迁移。agent 定时任务的版本、文案和更新行为不变。

**如何验证：**运行 `looper --version` 核对版本为 2.14.60。

**贡献者：**维护者 @foolzzz 提交 [#1028](https://github.com/foolzzz/looper/pull/1028)；本版本无社区贡献。

```bash
looper --version   # looper 2.14.60
```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.59 上的安装可直接升级。本版本没有迁移。升级前提出、升级后才回复的确认可能被拒绝一次，提示已变化；重新询问即可。

### 行为变化与入口

- **启用与立即运行的确认绑定实际目录（[#1028](https://github.com/foolzzz/looper/pull/1028)）。**对命令型定时任务，确认的版本现在包含它运行的目录：自身的 `work_dir`，未设置时为项目目录。若项目目录在提问与回复之间变化，确认以 `conflict` / 409 拒绝并重新询问。覆盖 Manager 的 `looper_schedules` 工具、经客户端 token 的同一工具，以及 `/api/v1/schedule_admin/update` 和 `run`。启用和立即运行命令型定时任务的提问现在会写出目录（经 API 的立即运行显示项目目录，或“none set”）。
- **修改命令型定时任务所运行的内容，在它将再次运行时需要确认。**对已启用（或停用但有排队运行）的命令型定时任务，修改 `command`、`env`、`env_file` 或 `work_dir` 不再被直接应用。Manager 的更新返回 `needs_confirmation`，`/api/v1/schedule_admin/update` 返回需确认的影响说明。提问显示修改前后的命令、变化的 env 键（及哪些值变了，不显示值）、env 文件和实际目录，并说明后续触发或排队运行将执行该修改。确认后的更新只在定时任务及其实际目录仍与所示一致时才应用。没有排队运行的停用任务，以及其他字段的修改，仍照旧直接应用。
- **目录修改绑定其目标。**设置 `work_dir` 的更新，其版本也覆盖清空后将从项目继承的目录。
- **不变。**agent 定时任务、仪表盘（其表单和开关是用户本人的操作）、配置导入，以及项目自身目录的变更（仍会不经询问地移动继承它的定时任务）不在范围内，保持不变。
- **面向模型的变化：**有。Manager 提示中 `needs_confirmation` 的情形新增“changing what an enabled or queued command schedule runs”；`looper_schedules` 工具文档说明此类修改为 `high`，需在下一条消息中确认；启用、运行和修改命令型定时任务的确认文字现在显示目录。新的修改提问由提示回归对话 `schedule_command_edit` 覆盖，`evals/README.md` 中的对话数从 49 变为 50。
- **文档与测试。**改动在 `looper/agents/ops/schedules.py`、`looper/agents/v1_domains/schedule_writes.py`、`looper/agents/schedules.py`、`looper/agents/scheduler.py`、`looper/agents/tiers/manager.py` 和 `looper/db/schedules.py`。测试位于 `tests/test_manager_schedule_tools_db.py`、`tests/test_api_v1_schedule_writes_db.py`、`tests/test_manager_schedule_changes_db.py` 和 `tests/test_model_manager_dialogs.py`。

# Looper v2.9.0

## At a Glance

The HTTP API answers the operator only. **Every `/api/` route except the agents' own tools needs the operator token** in `<runtime root>/operator-token` (mode 0600). The CLI sends it. A local browser signs in automatically on a direct loopback connection that meets the top-level navigation conditions; LAN or proxy access needs a password. Another machine signs in with an account and password set by `looper auth set-password` (asked twice, never on the command line, stored as a scrypt hash). Sessions last 7 days. Anonymous calls get 401. Password sign-in is new; query token/code sign-in is not supported. `looper serve` refuses to start when the runtime root is writable by group or others and prints `chmod go-w <runtime root>`.

**Codex and OMP Planners are read-only.** Codex runs in its read-only sandbox and approves only Looper's MCP tools. OMP gets a read-only tool list when the installed version reports that capability; an older CLI keeps the previous check. **Grok** keeps its Manager and each task's Planner in separate resident `grok agent stdio` processes and sessions (ACP). Workers stay one-shot headless runs. A resident turn's cost is read from `costUsdTicks` (1e10 ticks per USD). An Agent Profile can set a **custom system prompt** for Claude Code, Codex, Grok and OMP, and can preview the Profile/role template; task-specific contracts and other launch context are resolved later. Claude Code still sends three system blocks. `custom_prompt` prefixes Looper's composed prompt; the harness, role, context and contract follow. `system_prompt_mode` separately controls append/replace.

A **Lark (bot token)** channel is off by default. It is experimental and has not been tested against a real Lark tenant. The lark-cli channel is unchanged. Installing the wheel also installs `websockets` and `httpx`. A running **Codex Worker** (`app-server`) or **OMP Worker** (`rpc`) can be steered mid-run when that CLI reports the capability. When a Worker writes a file in another worktree or a commit, the Reviewer's first turn and the Planner's step report name that place and give read-only git hints. Structured locations and Reviewer file lists use single-line ASCII JSON; other name fields use `prompt_name`. The schedule dialog and the Manager suggest a cheaper Planner profile; the schedule's profiles do not change unless you set them. The dashboard renders over plain http from another host. Two v2.8.0 regressions are fixed: Grok Workers launch again, and a Planner's step decision sees the agent room again.

**This release has breaking changes.** Scripts that called `/api/` with no credential get 401. Query token/code sign-in is not supported. A runtime root that group or others can write will not start until you run `chmod go-w` on it. A dashboard tab left open across the upgrade needs one reload. Behind an https reverse proxy, set `dashboard_url` to the https address or sign-in gets 403. Upgrade by re-running `install.sh`. The first start backs the database up and migrates it.

```bash
curl -fsSL https://raw.githubusercontent.com/foolzzz/looper/main/install.sh | bash
looper --version   # looper 2.9.0
looper doctor
```

## Release Decision

**Who should upgrade:** Everyone running v2.8.0. Before upgrading, anyone who calls the HTTP API, or who starts `looper serve` from a runtime root that group or others can write, should read Behavior changes. Anyone who opens the dashboard through an https reverse proxy should set `dashboard_url` first.

**What this release solves:** v2.8.0 answered `/api/` to any caller on the machine, could not set a custom system prompt on Codex or Grok or preview what a runtime would send, kept a Codex Planner from calling Looper's MCP tools and did not give an OMP Planner a read-only tool list, started a new Grok process for every Manager and Planner turn, had no Lark channel without lark-cli, could not steer a running Codex or OMP Worker, did not tell the Reviewer or the Planner where a file was written outside the working directory, left the dashboard blank over plain http from another host, failed every Grok Worker at launch, and dropped the agent room out of every Planner step decision. v2.9.0 requires the operator credential, adds `custom_prompt` and a preview, retains Codex's read-only sandbox while restoring Looper MCP calls and adds OMP's read-only tool list when supported, keeps Grok's Manager and each task's Planner in separate resident ACP processes and sessions, adds the Lark (bot token) channel, steers a Worker when the CLI can, names files found elsewhere, renders the dashboard over plain http, and fixes those two regressions.

**Breaking changes:** Yes. Anonymous `/api/` calls get 401. Password sign-in is new; query token/code sign-in is not supported. `looper serve` refuses a runtime root that group or others can write. A dashboard tab opened before the upgrade needs one reload. Behind an https reverse proxy, sign-in gets 403 until `dashboard_url` is the https address. An OMP Planner whose version reports the read-only tool list no longer has a shell. See Behavior changes, Breaking Changes and Upgrading from v2.8.0.

**How to verify:** After re-running `install.sh`, `looper --version` reports `looper 2.9.0` and `looper doctor` passes. The first `looper serve` logs a `pg_dump` backup before it migrates. With the server running, `/api/status` without the operator token answers 401, and the same call with the token reports `"status": "running"`. A local browser opens the dashboard without a password only on a direct loopback connection that meets the top-level navigation conditions.

**Contributors:** Release maintainer @foolzzz; no community contribution in the pull requests merged since v2.8.0.

```bash

looper serve       # or: looper service restart

curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8767/api/status
curl -s -H "Authorization: Bearer $(cat ~/.looper/operator-token)" \
```

## New capabilities

### Custom system prompt

- **The profile's `custom_prompt` prefixes Looper's composed prompt.** It is placed first in Looper's composed prompt, before the harness. Claude Code, Codex, Grok and OMP all send that text. The harness, role, context and contract follow; `system_prompt_mode` separately controls append/replace. Empty (the default, including a profile from v2.8.0) adds no custom-prompt layer; other v2.9.0 changes still apply. A non-empty value is recorded as `prompt_layers.custom_prompt` (sha256 only). The API, configuration export and import, derived profiles and the Manager's profile tool read and write it. A string past the harness limit is a 400. ([#198](https://github.com/foolzzz/looper/pull/198))
- **Claude Code sends three system blocks.** A billing header, a fixed identity line, and the main block. No flag, setting or environment variable changes the identity line, so only the main block can be customized, and `custom_prompt` prefixes the Looper-composed text in that block. The harness, role, context and contract follow; `system_prompt_mode` separately controls append/replace. The billing header and the identity line stay. ([#198](https://github.com/foolzzz/looper/pull/198))
- **Preview.** Settings → Agent Profiles has a Custom prompt field and "Preview system prompt". `GET /api/agent-profiles/<id>/prompt-preview?role=planner|worker|reviewer|manager` returns the Profile/role template blocks in send order. Looper's blocks include their text. A runtime-owned block is described, not quoted. Task-specific contracts and other launch context, including knowledge paths, operator notes and skills, are resolved later; the Planner contract uses default parameters in the preview. ([#198](https://github.com/foolzzz/looper/pull/198))

### Lark (bot token)

- **A second Lark channel, off by default.** `channel-lark_bot` sits next to Lark (lark-cli). It calls the Lark open platform with an app id and an app secret, and receives events over the platform's long connection. No public callback URL and no lark-cli binary. Direct messages, group @-mentions, replies, status lines, notices, schedules and gates follow the same rules as the lark-cli channel. The existing lark-cli channel is unchanged. ([#209](https://github.com/foolzzz/looper/pull/209))
- **Settings.** Settings → Channels has a card: app id, domain (`feishu` or `lark`), app secret, allowlist, search, and refused senders. The secret is stored as `channel_secrets.bot_token`. The API shows `has_bot_token` and never the secret. `GET /api/channels/lark_bot/status` and `GET /api/channels/lark_bot/people?q=` are the status and the people search. Adding a person by name is a bounded directory scan (at most 40 requests) plus an exact email lookup; the answer says when the scan stopped early. Do not connect the same app to both Lark channels: the platform delivers each event to only one connection. Channel changes apply after a restart. ([#209](https://github.com/foolzzz/looper/pull/209))
- **Experimental.** This channel has not been tested against a real Lark tenant. The wheel depends on `websockets` and `httpx`. Upgrading with `pip` or `uv` from the wheel installs them. ([#209](https://github.com/foolzzz/looper/pull/209))

### Read-only Codex and OMP Planners

- **Codex.** A Planner runs in Codex's read-only sandbox (`sandbox_mode` `read-only`, `approval_policy` `never`) and approves only Looper's MCP tools (`default_tools_approval_mode` `approve` on each of the Planner's MCP servers). A write fails in the sandbox. Looper's own tools work again: on v2.8.0 the same sandbox refused every MCP call. Codex refusals are not stored as typed denials. ([#203](https://github.com/foolzzz/looper/pull/203))
- **OMP.** A Planner gets a read-only tool list (`read`, `glob`, `grep`, and its MCP tools; no shell) when the probed OMP version reports that capability. An older CLI, or a version string the probe cannot read, keeps the previous behavior: the command is unchanged, and Looper compares the task directory after the turn. Re-detect an OMP runtime that was registered before this upgrade (Settings → Agent Runtimes, or `POST /api/runtimes/rt-omp/probe`) so the stored probe is the one that reports the capability. A runtime found for the first time after the upgrade is probed at registration. Without `read_tools`, OMP does not run a consult and hands it to the Planner as `runtime_cannot`. Re-detect an existing OMP runtime to restore consult; older or unrecognized CLI versions do not support it. ([#203](https://github.com/foolzzz/looper/pull/203))

### Resident Grok sessions

- **Manager and Planner.** The Manager and each task's Planner each keep an independent resident `grok agent stdio` process and session (ACP: JSON-RPC over stdio, `grok agent --always-approve stdio`). The first turn starts it (`session/new`). A later turn reuses it. After a restart, `session/load` resumes the saved session. One `session/prompt` is one turn. `session/cancel` gives a turn up. Workers and Reviewers stay one-shot headless runs. ([#205](https://github.com/foolzzz/looper/pull/205))
- **Cost.** A resident turn's cost is ACP `costUsdTicks` divided by 1e10 (ticks per USD). A missing or zero cost stays unknown, not free. A headless Worker still reports Grok's own end-of-run cost. ([#205](https://github.com/foolzzz/looper/pull/205))
- **Fallback.** If this Grok cannot serve ACP (no `agent stdio`, no answer to `initialize`, no `loadSession` for a saved session), that Manager or Planner runs one process per turn in the same home, as in v2.8.0. A Planner's reading tools are the `tools:` line of an agent profile, because the root `--tools` flag has no effect on `agent stdio`. A tool-use event is recorded when the call starts, not when it finishes. ([#205](https://github.com/foolzzz/looper/pull/205))

### Files found outside the working directory

- **A typed location.** When a Worker writes a file in another worktree or a commit, the Reviewer's first turn and the Planner's step report get that location: worktree or commit, with read-only git hints (`git -C <worktree> show`, `git show <sha>`). The Reviewer is still allowed to write in its own checkout; the hint only asks it to read the other place. The stored `found_elsewhere` list is these objects. A reader ignores the old free-form shape. ([#210](https://github.com/foolzzz/looper/pull/210))
- **One escaping rule.** Structured locations and Reviewer file lists use single-line ASCII JSON, which can quote ordinary names too. Other name fields use `prompt_name`: a plain printable name stays unchanged; anything else becomes single-line ASCII-escaped JSON, so a line break or control character cannot open a new prompt line. A quote, a backtick or a leading dash is not left plain. ([#210](https://github.com/foolzzz/looper/pull/210))
- **A cheaper Planner for a schedule, only if you set one.** Schedules already took a profile per role. Nothing about that default moves: a role left unset keeps the project's profile, and saving a schedule without naming profiles adds no profile row. The Manager tool's `profiles` description and the schedule dialog now suggest a cheaper Planner profile for a schedule whose runs are alike. Set it only when you want it. ([#210](https://github.com/foolzzz/looper/pull/210))

### Steering a running Worker

- **When the CLI reports it.** A running Codex Worker is driven through `app-server` and can take `turn/steer`. A running OMP Worker is driven through `rpc` and can take `steer`. Both apply only when the installed CLI reports that capability: Codex 0.162.0 or newer whose protocol schema contains `turn/steer`, and OMP 18.4.3 or newer whose `--help` lists `rpc` and `--no-ui`. The stored probe is what the server uses. Re-detect a Codex or OMP runtime that was already registered (`POST /api/runtimes/rt-codex/probe`, `POST /api/runtimes/rt-omp/probe`, or Settings → Agent Runtimes). A runtime registered for the first time after the upgrade is probed then. An older CLI falls back to the previous behavior: the prompt is on stdin, and a message waits for the step's decision turn. Reviewers use the same path. Claude Code and Grok are unchanged. ([#211](https://github.com/foolzzz/looper/pull/211))
- **What a steer means.** The Planner's mid-run message is acknowledged only after the runtime accepts it. Otherwise it is kept for the decision turn. A handshake that fails fails the run with that error; it is not silently run again the old way. ([#211](https://github.com/foolzzz/looper/pull/211))

### Operator sign-in

- **The token.** `looper serve` reads `<runtime root>/operator-token` before it opens the database, and creates it when it is missing (mode 0600). A missing runtime root is created mode 0700. The file is opened without following a symlink and without blocking. It must be a regular file of the current user with mode exactly 0600. The server does not chmod anything by itself. The CLI (`looper service` included) sends `Authorization: Bearer` with that token. ([#207](https://github.com/foolzzz/looper/pull/207))
- **A browser on the same machine.** A top-level navigation from loopback, with no `Forwarded` or `X-Forwarded-For`, sets the cookie `looper_operator_<port>` (HttpOnly, SameSite=Strict, no `Secure`, a session cookie). The page is `Cache-Control: no-store`. The cookie name includes the port, so two local servers do not overwrite each other. ([#207](https://github.com/foolzzz/looper/pull/207))
- **Every other browser.** It gets a login page. `looper auth set-password [--user NAME]` (the user defaults to `admin`, `[A-Za-z0-9._-]{1,64}`) reads the password twice with no echo, at least 8 characters, and never from an argument. The hash is scrypt (`n=32768`, `r=8`, `p=1`) in `<runtime root>/operator-password`, mode 0600. `looper auth clear-password` removes it. Until a password is set, the page has no form and only the local auto-login opens the dashboard. `POST /login` and `POST /logout` require an `Origin` whose scheme and host match the request (`https` when `dashboard_url` is https, otherwise `http`). A wrong user and a wrong password get the same 401. A session cookie lasts 7 days (`Max-Age=604800`), is not the token, and ends when the password is changed or cleared, when the server restarts, or on `POST /logout`. At most 100 sessions are kept. ([#207](https://github.com/foolzzz/looper/pull/207))
- **Lockout, cache and logs.** Five failures in a row from one TCP peer lock it for 60 seconds, doubling up to 900 seconds. More than 30 failures within 600 seconds lock every peer until the window drops. A locked attempt is 429 with `Retry-After` and is not counted. `X-Forwarded-For` does not pick a fresh bucket. Login and logout responses are `no-store`. Logs contain the peer and failed, succeeded or locked, never the user, the password or the token. ([#207](https://github.com/foolzzz/looper/pull/207))

## Default and behavior changes

These move on upgrade. Each one says what the operator does. None of them is a new project setting except where the line says so.

1. **Anonymous `/api/` calls get 401.** That includes `GET /api/status` and a path Looper does not know (401, not 404). Send `Authorization: Bearer` and the contents of `<runtime root>/operator-token`, or use the dashboard through a direct loopback connection that meets the top-level navigation conditions so the cookie is set. `/api/agent/v1/` still uses each agent's own token. An operator token does not open an agent route, and an agent token does not open an operator route. `OPTIONS /api/*` no longer returns 204 unconditionally: missing the appropriate credential gives 401; an unimplemented method with a valid credential gives 404. ([#207](https://github.com/foolzzz/looper/pull/207))
2. **Password sign-in is new.** Query token/code sign-in is not supported. Use the bearer token or the password. ([#207](https://github.com/foolzzz/looper/pull/207))
3. **`looper serve` refuses to start when the runtime root is writable by group or others**, or is not owned by the user. The message names the fix, `chmod go-w <runtime root>`. Run that, then start again. An invalid token file prevents startup. An invalid password file makes password sign-in return 503; fix its permissions or run `looper auth set-password`. Deleting the password file does not recreate it on startup. Nothing is chmod-ed for you. A root created by this version is mode 0700. A root that is mode 0755 (group and others can read, not write) still starts. ([#207](https://github.com/foolzzz/looper/pull/207))
4. **Other machines sign in with a password.** On the server, run `looper auth set-password [--user NAME]`. It prompts twice and will not take `--password`. `looper auth clear-password` removes the hash. Sessions last 7 days and end when the password is changed or cleared, and when `looper serve` restarts, because they are kept in memory. A local browser needs no password only on a direct loopback connection that meets the top-level navigation conditions; LAN or proxy access needs a password. ([#207](https://github.com/foolzzz/looper/pull/207))
5. **Behind an https reverse proxy, set `dashboard_url` to the https address.** `looper serve` reads `LOOPER_PUBLIC_URL` at start and uses it as `dashboard_url`. If that value is not https while the browser's Origin is https, `POST /login` and `POST /logout` answer 403. Set the variable to the https address people open before starting `looper serve`. For an installed service, set the variable and rerun `looper service install`, preserving its original label, port and runtime root; restart alone does not recapture `LOOPER_PUBLIC_URL`. Both routes also require an Origin whose host matches `Host`. Sign-in is rate-limited with lockout, as under Operator sign-in. Responses are `no-store`. Logs never contain the credentials. ([#207](https://github.com/foolzzz/looper/pull/207))
6. **Reload a dashboard tab that was open before the upgrade.** The dashboard page is now `no-store` and, on a local navigation, sets the operator cookie. An old tab keeps calling `/api/` without it until you reload. After a session ends, the page does not yet send you to the login form on a 401; reload it. There is a `POST /logout` endpoint and no logout button. ([#207](https://github.com/foolzzz/looper/pull/207))
7. **Upgrade the CLI with the server.** An old `looper` does not send the token, so `looper service status` looks like no answer. `install.sh` upgrades the command and the server together. `looper doctor` and configuration export do not call the local API. ([#207](https://github.com/foolzzz/looper/pull/207))
8. **A Codex Planner is read-only in the sandbox, and can call Looper's MCP tools.** No setting turns this off. An OMP Planner gets the read-only tool list only after its runtime's probe reports the capability. Re-detect `rt-omp` if it was already registered; until you do, OMP keeps the v2.8.0 directory comparison. Without `read_tools`, OMP does not run a consult and hands it to the Planner as `runtime_cannot`. Re-detect an existing OMP runtime to restore consult; older or unrecognized CLI versions do not support it. ([#203](https://github.com/foolzzz/looper/pull/203))
9. **The Grok Manager and each task's Planner keep separate resident ACP processes and sessions.** No setting turns this on; a profile that already uses Grok gets it on the next turn. If that `grok` cannot speak ACP, the session falls back to one process per turn. Workers stay one-shot. Read cost of a resident turn from `costUsdTicks` / 1e10. A tool call shows up in the run when it starts. ([#205](https://github.com/foolzzz/looper/pull/205))
10. **Steering waits on a re-detect.** After the upgrade, an already registered Codex or OMP runtime keeps its old capability list until you re-detect it. Then a Worker (and a Reviewer) runs through `app-server` or `rpc` when the CLI reported steer. If it did not, the run stays one-shot. You do not set a project flag. ([#211](https://github.com/foolzzz/looper/pull/211))
11. **The Reviewer and the Planner are told where a file outside the working directory was found.** This is on for every task. You do not turn it on. Structured locations and Reviewer file lists use single-line ASCII JSON; other name fields use `prompt_name`, as under Files found outside the working directory. A schedule's Planner profile does not change. To use a cheaper one, set the Planner profile on the schedule (the dialog hints at it; the Manager sets `profiles` only when you ask). ([#210](https://github.com/foolzzz/looper/pull/210))
12. **The Manager's profile tool lists `custom_prompt`.** With the field empty, no custom-prompt layer is added; other v2.9.0 changes still apply. The tool schema is model-visible either way. Set the field on a profile to send it. ([#198](https://github.com/foolzzz/looper/pull/198))
13. **The dashboard renders over plain http from another host.** Reload a tab that was blank. https and localhost already rendered, and they still do. Ids use `crypto.randomUUID` when the page is a secure context, and `crypto.getRandomValues` otherwise. There is no `Math.random` fallback. ([#213](https://github.com/foolzzz/looper/pull/213))

`custom_prompt` stays empty, the Lark (bot token) channel stays disabled, and a `vX.Y.Z` tag still publishes this Python release. A `vX.Y.Z-go` tag does not.

## Fixes

- **Grok Workers and Reviewers launch again.** v2.8.0 added `session_dir` to `run_command` and passed it on every Worker run. The Grok adapter, added in the same release, still had the old signature, so every Grok Worker run failed at launch. `run_command()` now accepts `session_dir` and ignores it: a Grok consult finds the session in the home the recorded command names. `tests/test_runtime_signatures.py` checks that each runtime adapter accepts every parameter of the abstract commands. ([#208](https://github.com/foolzzz/looper/pull/208))
- **A Planner step decision sees the agent room's messages again.** Since v2.8.0, when steps gained a list of review roles, the room summary still read `review_role`. Every summary failed with "cannot read the room for step ...", and the Planner decided without the room. It now seats the Reviewer when the step has a review, and one seat per entry in `review_roles`. ([#214](https://github.com/foolzzz/looper/pull/214))
- **The dashboard renders over plain http from another host.** `crypto.randomUUID` exists only in a secure context (https or localhost). The chat page is always mounted and threw while creating its session id, so the page stayed blank after sign-in. Ids now fall back to `crypto.getRandomValues`. ([#213](https://github.com/foolzzz/looper/pull/213))
- **A Go-port tag does not publish the Python release.** The Release workflow's tag filter ignores `vX.Y.Z-go`. A tag `vX.Y.Z` is unchanged. ([#202](https://github.com/foolzzz/looper/pull/202))

## Prompt eval

The release-candidate tiers in `evals/README.md` ran once on this candidate (`c9ac42d5c`, `--reps 3 --jobs 4`) and are the new committed baselines. Each line compares the candidate with the v2.8.0 baseline (`3ca041201`).

- **Haiku, all tasks, three reps.** 92/105 on 35 tasks. On the 33 tasks shared with the baseline: 86/99, against 85/99. Contract violations rose from 4.3 to 6.3 (sum of per-task means), mostly plan replies missing `review` and gate replies missing `summary`; repair turns recovered all but one. A paired rerun of the five gate tasks with four reps each gave 19/20 with 2.2 violations on the candidate and 19/20 with 2.5 on v2.8.0; the paired rerun did not reproduce the increase; the sample is too small to rule out a regression. `room_interface` went from 1/3 to 3/3 with the room fix ([#214](https://github.com/foolzzz/looper/pull/214)). Cost $12.30.
- **Opus, planner tasks, three reps.** 60/60, as before. Contract violations 0.0 → 0.3 (one repaired reply). Cost $27.81.
- **Haiku Manager dialogs, three reps.** 64/72 on 24 dialogs, against 58/66 on 22. `provider_key` fails in all three reps, as in the baseline (the reply repeats the key). `config_tools` 2/3 and `schedule_create` 1/3 match the baseline. The new `schedule_planner_profile` passes 3/3 and `schedule_no_profiles` 2/3. Cost $4.23.

## Breaking Changes

1. **`/api/` requires the operator.** A caller with no token and no session gets 401, including health and unknown paths. Scripts send the bearer token. Password sign-in is new; `?code=` / `?token=` sign-in is not supported. A dashboard tab opened on v2.8.0 does not start working until it is reloaded. `looper service` from a v2.8.0 command line does not send the token. ([#207](https://github.com/foolzzz/looper/pull/207))
2. **The runtime root must not be writable by group or others.** `looper serve` exits before the database if it is, or if it is not owned by the user, and prints `chmod go-w <runtime root>`. A group-writable root left by umask 002, which is common, stops the start after the upgrade. The server does not fix the mode. ([#207](https://github.com/foolzzz/looper/pull/207))
3. **https sign-in follows `dashboard_url`.** `POST /login` and `POST /logout` require an Origin whose scheme matches `dashboard_url` and whose host matches `Host`. Behind an https reverse proxy, export `LOOPER_PUBLIC_URL` as that https address before start. Left as http, sign-in answers 403. For an installed service, set the variable and rerun `looper service install`, preserving its original label, port and runtime root; restart alone does not recapture `LOOPER_PUBLIC_URL`. ([#207](https://github.com/foolzzz/looper/pull/207))
4. **An OMP Planner whose probe reports the read-only tool list has no shell.** Commands it used to run are gone. Re-detect picks the new list up; until then the v2.8.0 comparison still applies. A Codex Planner retains its existing read-only sandbox and regains Looper MCP tool calls, which v2.8.0 refused. ([#203](https://github.com/foolzzz/looper/pull/203))

**Also changed, with less authority or a different record.** Sessions are in memory: a restart ends them, and so does changing or clearing the password, even inside the 7 days. The dashboard page is `no-store`. `found_elsewhere` on a step result is a list of location objects; a reader ignores the old free-form shape. `custom_prompt` is an empty string on existing profiles. The Grok Manager and each task's Planner keep separate resident ACP processes and sessions, with turn costs from `costUsdTicks`. Steering and the OMP tool list wait until the runtime is probed with this version. The Lark (bot token) row exists and is disabled. Gate posts and schedule notify accept the channel `lark_bot`. ([#205](https://github.com/foolzzz/looper/pull/205), [#207](https://github.com/foolzzz/looper/pull/207), [#209](https://github.com/foolzzz/looper/pull/209), [#210](https://github.com/foolzzz/looper/pull/210), [#211](https://github.com/foolzzz/looper/pull/211))

## Upgrading from v2.8.0

1. **Install with `install.sh`.** It installs the latest release wheel. `pip` or `uv` installs `websockets` and `httpx` with it.
2. **Make the runtime root private to your user.** If group or others can write it, `looper serve` will not start. Run `chmod go-w <runtime root>` (the default root is `~/.looper`). Do this before the first start. The server will not do it.
3. **Keep the first-start backup possible.** The schema changes, so the first start writes a `pg_dump` backup before migrating. Keep a `pg_dump` of at least the server's major version on `PATH` (or `LOOPER_PG_DUMP`, or `LOOPER_BACKUP_CMD`). `looper serve --skip-backup` migrates without one.
4. **Start once.** The upgrade adds `custom_prompt` (empty) on every Agent Profile, accepts `lark_bot` on gate posts and on a schedule's notify channel, and accepts `steer` as a runtime capability. It creates `<runtime root>/operator-token` mode 0600 when that file is missing.
5. **Reload the dashboard.** A tab that was open before the upgrade needs one reload. A local browser then signs in automatically only on a direct loopback connection that meets the top-level navigation conditions.
6. **A password for browsers outside local auto-login.** Run `looper auth set-password` on the server, type the password twice, and sign in from the other browser. Skip this only if you use a direct loopback connection that meets the top-level navigation conditions; LAN or proxy access needs a password.
7. **An https proxy.** Set `LOOPER_PUBLIC_URL` to the https address before starting `looper serve`, or sign-in answers 403. That value is `dashboard_url`. For an installed service, set the variable and rerun `looper service install`, preserving its original label, port and runtime root; restart alone does not recapture `LOOPER_PUBLIC_URL`.
8. **Re-detect Codex and OMP if you want the new Planner tools and steering.** Settings → Agent Runtimes, Re-detect, or `POST /api/runtimes/rt-codex/probe` and `POST /api/runtimes/rt-omp/probe` with the operator token. Until you do, an existing row keeps the capabilities it had. Without `read_tools`, OMP does not run a consult and hands it to the Planner as `runtime_cannot`. Re-detect an existing OMP runtime to restore consult; older or unrecognized CLI versions do not support it.
9. **Lark (bot token), only if you want it.** In Settings → Channels, set the app id, domain and app secret, the allowlist, and enable `channel-lark_bot`. Restart. Leave it disabled and nothing connects. Do not point it at the same app as the lark-cli channel.
10. **Scripts.** Send the bearer token on every `/api/` call. Query token/code sign-in is not supported. `looper service` from this version sends the token itself.
11. **Check.** `looper doctor`, and `looper service status` for the service. Status from this version's CLI should not say unauthorized.

```bash
chmod go-w ~/.looper
curl -fsSL https://raw.githubusercontent.com/foolzzz/looper/main/install.sh | bash
looper doctor
looper serve
  # Or, with the service:
looper service restart && looper service status
```

**Rollback to v2.8.0.** Stop Looper (`looper service uninstall` if you installed the service), recreate the database empty and restore the pre-migration backup the first start logged (`pg_restore --no-owner --dbname "$LOOPER_DATABASE_URL" FILE`). Then install the v2.8.0 wheel, for example `uv tool install --force "looper @ https://github.com/foolzzz/looper/releases/download/v2.8.0/looper-2.8.0-py3-none-any.whl"`. `install.sh` always installs the latest release, so it cannot roll back. v2.8.0 does not know the operator token, `custom_prompt`, the Lark (bot token) channel or ACP Grok sessions. A token file left in the runtime root is unused by v2.8.0; delete it if you do not want it on disk.

## Optional Capability Activation & Use

### Custom system prompt

**Activation:** Off until a profile sets it. `custom_prompt` defaults to empty on every profile, including ones from v2.8.0. Set it in Settings → Agent Profiles, `POST` or `PUT /api/agent-profiles`, configuration import, or the Manager's profile tool. It prefixes Looper's composed prompt for Claude Code, Codex, Grok and OMP; the harness, role, context and contract follow. `system_prompt_mode` separately controls append/replace. Claude Code's billing header and identity line are not editable. `system_prompt_mode` stays `append` unless you also set `replace`.

**Validation:** `GET /api/agent-profiles/PROFILE_ID` shows `custom_prompt`. `GET /api/agent-profiles/PROFILE_ID/prompt-preview?role=planner` lists the blocks in send order. A run record's prompt layers include `custom_prompt` (sha256) only when the field was set. An empty field adds no custom-prompt layer; other v2.9.0 changes still apply.

**Disable / rollback:** Set `custom_prompt` back to an empty string. The next run removes only that prefix and retains other v2.9.0 changes. Existing run records keep the layers they ran with. There is no global switch.

**Authority boundary:** The text is operator input, at the same trust as the harness, and it is placed before the harness, the role prompt and the contract. A model may follow it where it conflicts with the contract; that precedence was not measured. It does not add tools. Only someone who can edit the profile, or the Manager through its profile tool, can set it. The preview shows Profile/role templates; task-specific contracts and other launch context are resolved later. It describes runtime-owned blocks; it does not reveal a runtime's hidden default prompt.

**Docs:** https://github.com/foolzzz/looper/blob/v2.9.0/docs/architecture/rfcs/system-prompt-mode-v0.zh-CN.md

```bash
curl -s -X PUT http://127.0.0.1:8767/api/agent-profiles/PROFILE_ID \
  -H "Authorization: Bearer $(cat ~/.looper/operator-token)" \
  -H 'Content-Type: application/json' \
  -d '{"custom_prompt": "Answer in short sentences."}'
curl -s -H "Authorization: Bearer $(cat ~/.looper/operator-token)" \
  'http://127.0.0.1:8767/api/agent-profiles/PROFILE_ID/prompt-preview?role=planner'
  # Clear it:
curl -s -X PUT http://127.0.0.1:8767/api/agent-profiles/PROFILE_ID \
  -H "Authorization: Bearer $(cat ~/.looper/operator-token)" \
  -H 'Content-Type: application/json' \
  -d '{"custom_prompt": ""}'
```

### Lark (bot token)

**Activation:** Off by default. `channel-lark_bot` is created disabled, with no app secret. In Settings → Channels, or with `PUT /api/channel-configs/channel-lark_bot`, set `enabled` true, `config.app_id`, `config.domain` (`feishu` or `lark`), `config.allowed_open_ids`, and `bot_token` to the app secret. Restart `looper serve` so the channel connects. Do not use the same app as the lark-cli channel. The lark-cli channel stays as it was. This channel has not been tested against a real Lark tenant.

**Validation:** `GET /api/channel-configs/channel-lark_bot` shows `enabled`, `has_bot_token` and the app id, and does not show the secret. `GET /api/channels/lark_bot/status` checks app credentials and reports the bot or a credential problem. An empty allowlist is reported by `start_problem` in the channel-config response. A message from an allowlisted sender in a direct chat, or an @-mention in a group, reaches the Manager. A refused sender is listed and is not given to the model.

**Disable / rollback:** `PUT /api/channel-configs/channel-lark_bot` with `{"enabled": false}`, then restart. The row and the secret remain until you clear them. The lark-cli channel is a different row; disabling this one does not change it. To drop the secret, set a new value or remove the channel secret the settings page clears. There is no extra package to uninstall beyond the wheel's own dependencies.

**Authority boundary:** An enabled channel delivers allowlisted senders' messages to the Manager, which can run its tools with no permission prompt, the same as lark-cli. Anyone not on the allowlist gets no model turn. The app secret is stored on the server, mode with the other channel secrets, and is not returned by the API, not written in errors and not written in logs. The long connection receives events for that app. Sharing the app with the lark-cli channel drops events on one of the two connections. The people search reads the tenant directory, at most 40 requests, and an exact email lookup.

**Docs:** https://github.com/foolzzz/looper/blob/v2.9.0/docs/architecture/agent-system.md#channels

```bash
curl -s -X PUT http://127.0.0.1:8767/api/channel-configs/channel-lark_bot \
  -H "Authorization: Bearer $(cat ~/.looper/operator-token)" \
  -H 'Content-Type: application/json' \
  -d '{"enabled": true, "config": {"app_id": "APP_ID", "domain": "feishu", "allowed_open_ids": ["ou_SENDER"]}, "bot_token": "APP_SECRET"}'
curl -s -H "Authorization: Bearer $(cat ~/.looper/operator-token)" \
  -X POST http://127.0.0.1:8767/api/v1/channels/status -H 'Content-Type: application/json' \
  -d '{"channel_type": "lark_bot"}'
  # Turn it off, then restart looper serve:
curl -s -X PUT http://127.0.0.1:8767/api/channel-configs/channel-lark_bot \
  -H "Authorization: Bearer $(cat ~/.looper/operator-token)" \
  -H 'Content-Type: application/json' \
  -d '{"enabled": false}'
```

### Grok runtime

**Activation:** Still off until a profile uses runtime `grok`. This release changes what that profile does. The Manager and each task's Planner keep separate resident `grok agent stdio` processes and sessions. Workers and Reviewers stay one-shot headless runs. No new setting. If the installed `grok` cannot serve ACP, the Manager and Planner fall back to one process per turn in the same home. Re-detect is not required for this path.

**Validation:** A Grok Manager or Planner run stays one process across turns (the run page shows one resident session, and a later turn does not start a new process). Its cost matches `costUsdTicks` / 1e10 when Grok reports ticks. A missing or zero figure stays unknown. A Grok Worker run completes instead of failing on `session_dir`. `looper doctor` still reports the Grok login while a profile uses it.

**Disable / rollback:** Select another profile on that layer and delete the Grok profile, as in v2.8.0. There is no switch that keeps Grok and forces the old per-turn process while ACP works. Removing the `grok` binary and restarting drops the runtime from detection.

**Authority boundary:** A resident Grok process runs as your user for the life of the Manager or the task's Planner, with `--always-approve` and `--trust`, in a home Looper owns. It can call MCP tools on later turns without a new process. The login stays in your Grok login file; Looper does not store the token. A Worker is still one process. A per-run spend cap still does not stop a Grok run; the task cap stops later runs after a cost is reported. Cost ticks are Grok's figure, not a price Looper computes.

**Docs:** https://github.com/foolzzz/looper/blob/v2.9.0/docs/architecture/agent-system.md#runtimes-llm-providers-and-agent-profiles

```bash
grok --version
curl -s -H "Authorization: Bearer $(cat ~/.looper/operator-token)" \
  http://127.0.0.1:8767/api/status
  # A Grok profile is unchanged from v2.8.0. Point a role at it, or clear it:
curl -s -X PUT http://127.0.0.1:8767/api/agent-settings/roles/planner \
  -H "Authorization: Bearer $(cat ~/.looper/operator-token)" \
  -H 'Content-Type: application/json' \
  -d '{"profile_id": null}'
```

### Worker steering

**Activation:** On when the stored probe of the Codex or OMP runtime lists `steer`, and off otherwise. Codex reports it at 0.162.0 or newer when `turn/steer` is in the protocol schema. OMP reports it at 18.4.3 or newer when `--help` lists `rpc` and `--no-ui`. Re-detect after the upgrade: Settings → Agent Runtimes, or the probe route below. A newly registered runtime is probed at registration. An older CLI falls back to a one-shot run. No project setting. Claude Code and Grok do not gain this.

**Validation:** After re-detect, `GET /api/registry` shows `steer` in that runtime's capabilities. A running Codex Worker is an `app-server` process, and a running OMP Worker is `omp --mode rpc`. A Planner message during the run shows up before the step's decision turn. A runtime whose probe has no `steer` still takes the prompt on stdin.

**Disable / rollback:** Re-detect does not remove a capability the CLI still reports. To keep the previous one-shot runs, leave the old capability list in place (do not re-detect) or use a CLI that does not report steer. There is no per-task switch. A message the runtime does not accept is kept for the decision turn, as before.

**Authority boundary:** A steer delivers the Planner's text into a Worker that is already running, with that Worker's tools and no extra confirmation. The same path serves a Reviewer. A steer that times out at 4 seconds may still reach the Worker; the Planner keeps the text as delivery not confirmed, so the Worker may see it twice. The server does not grant a shell to a read-only Planner by steering. Isolation, the spend cap and the kill of the process tree are the same as a one-shot run.

**Docs:** https://github.com/foolzzz/looper/blob/v2.9.0/docs/architecture/rfcs/worker-steering-v0.zh-CN.md

```bash
curl -s -X POST http://127.0.0.1:8767/api/runtimes/rt-codex/probe \
  -H "Authorization: Bearer $(cat ~/.looper/operator-token)"
curl -s -X POST http://127.0.0.1:8767/api/runtimes/rt-omp/probe \
  -H "Authorization: Bearer $(cat ~/.looper/operator-token)"
curl -s -H "Authorization: Bearer $(cat ~/.looper/operator-token)" \
  http://127.0.0.1:8767/api/registry | python3 -c 'import json,sys; [print(r["id"], r.get("capabilities")) for r in json.load(sys.stdin)["runtimes"]]'
```

### Operator password

**Activation:** Optional for direct loopback access that meets the top-level navigation conditions for local auto-login. Every other browser, including a local browser using a LAN address or proxy, needs a password. On the server, run `looper auth set-password [--user NAME]` and type the password twice when asked (at least 8 characters; there is no command-line option for it). The default user is `admin`. Then open the dashboard from the other machine and sign in. The operator token itself is not optional: `looper serve` creates it, and `/api/` rejects a caller who has neither the token nor a session.

**Validation:** `POST /login` with the user, the password and an `Origin` equal to the page's scheme and host answers 303 and sets `looper_session_<port>`. `GET /api/status` with that cookie answers 200. A call with no credential answers 401. `~/.looper/operator-password` is mode 0600 and does not contain the password text. Five wrong passwords, then another, answer 429.

**Disable / rollback:** `looper auth clear-password` deletes the hash and ends every session. The login page then has no form. The local browser still signs in from the token cookie. You cannot turn the token check off. Delete `<runtime root>/operator-token` only while the server is stopped; the next start writes a new one.

**Authority boundary:** Anyone who can reach the port and who knows the user and password can call every operator route for 7 days, or until the password changes, the password is cleared, the server restarts, or they call `POST /logout`. The token file is mode 0600. A process running as your user can still read that file. Sign-in is locked out as under Operator sign-in. Logs do not contain the password, the user or the token. `POST /login` and `POST /logout` refuse an Origin that does not match. Behind an https proxy, `dashboard_url` must be that https address.

**Docs:** https://github.com/foolzzz/looper/blob/v2.9.0/docs/architecture/agent-system.md#http-api

```bash
looper auth set-password
  # Type the password twice when asked. It is not an argument.
curl -s -o /dev/null -w '%{http_code}\n' -D - \
  -X POST http://127.0.0.1:8767/login \
  -H 'Origin: http://127.0.0.1:8767' \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  --data 'username=admin&password=YOUR_PASSWORD'
  # Remove it. Sessions end.
looper auth clear-password
```

## Known limits

- **A read-only consult's source is not pinned against a seat restart.** A restart of the seat is not held off while the consult reads that run. ([#203](https://github.com/foolzzz/looper/pull/203))
- **Real consult initialization tool lists were checked.** A consult asks Claude Code for only `Read`, `Glob` and `Grep`, and OMP for only `read`, `glob` and `grep`. OMP is still not a sandbox. ([#203](https://github.com/foolzzz/looper/pull/203))
- **An OMP checkout is not a sandbox.** OMP runs as your user. A consult checkout is removed afterwards. A write outside that checkout is neither prevented nor detected. ([#203](https://github.com/foolzzz/looper/pull/203))
- **Git error text in the Planner's merge report is flattened to one line.** Newlines become spaces. Quotes and fences in that error stay. The escaping rule for file, path and branch names does not rewrite this text. ([#210](https://github.com/foolzzz/looper/pull/210))
- **A real model was not observed using the git hint.** It read the worktree file directly instead of the hinted `git show`. ([#210](https://github.com/foolzzz/looper/pull/210))
- **A steer that times out (4 s) may still reach the Worker.** The Planner keeps it as "delivery not confirmed", so the Worker may see it twice. ([#211](https://github.com/foolzzz/looper/pull/211))
- **Lark (bot token) has not been tested against a real Lark tenant.** Token-invalid codes, scope names and the connection limit are from documentation and the SDK, not from a live tenant. The lark-cli channel is unchanged. ([#209](https://github.com/foolzzz/looper/pull/209))
- **The dashboard has no logout button.** `POST /logout` is the endpoint. The page does not handle a 401 after a session ends; reload the tab. ([#207](https://github.com/foolzzz/looper/pull/207))
- **Sign-in through a real reverse proxy was not verified, and neither was `looper service install` on real launchd or systemd.** The password flow was checked with a non-loopback host name on the same machine, and the service unit was checked with fake service managers. ([#207](https://github.com/foolzzz/looper/pull/207))
- **The prompt preview shows Profile/role templates.** Task-specific contracts and other launch context, including knowledge paths, operator notes and skills, are resolved later; the Planner contract uses default parameters in the preview. Grok and OMP block layouts were derived from the launch code, not captured from a live session. Claude Code's three blocks were captured. ([#198](https://github.com/foolzzz/looper/pull/198))
- **ACP Grok was not checked for compaction events, parallel tool calls, mid-turn user input or text streaming.** A session ACP cannot serve falls back to one process per turn. ([#205](https://github.com/foolzzz/looper/pull/205))

## 中文摘要

### 速览

HTTP API 只回答操作者。**除了 agent 自己的工具，每一条 `/api/` 都需要操作者令牌**，文件是 `<runtime root>/operator-token`（权限 0600）。CLI 会带上它。通过 loopback 地址直连、满足顶层导航条件的本机浏览器可自动登录；经 LAN 地址或代理访问仍需密码。另一台机器用 `looper auth set-password` 设置的账号和密码登录（问两遍，从不出现在命令行上，按 scrypt 哈希保存）。会话保留 7 天。匿名调用得到 401。新增密码登录，不支持 query token/code 登录。运行时根目录对 group 或 others 可写时，`looper serve` 拒绝启动，并打印 `chmod go-w <runtime root>`。

**Codex 和 OMP 的 Planner 只读。** Codex 跑在它的只读沙箱里，并且只放行 Looper 的 MCP 工具。OMP 在已安装版本报告该能力时得到一份只读工具列表；更旧的 CLI 保持以前的检查。**Grok** 的 Manager 和每个任务的 Planner 各自保持独立的常驻 `grok agent stdio` 进程及会话（ACP）。Worker 仍是一次性的无头运行。常驻回合的花费用 `costUsdTicks` 读取（每美元 1e10 tick）。Agent Profile 可以为 Claude Code、Codex、Grok 和 OMP 设置**自定义 system prompt**，并预览 Profile/角色模板；任务特定契约及其他启动上下文稍后解析。Claude Code 仍发送三个 system 块。`custom_prompt` 前置于 Looper 拼接的提示词，后面仍有 harness、角色、上下文及契约；append/replace 由 `system_prompt_mode` 单独控制。

**Lark（bot token）** 渠道默认关闭。它是实验性的，还没有对真实 Lark 租户测试过。lark-cli 渠道不变。安装 wheel 时会装上 `websockets` 和 `httpx`。正在运行的 **Codex Worker**（`app-server`）或 **OMP Worker**（`rpc`）在该 CLI 报告能力时可以中途被引导。Worker 把文件写进另一个 worktree 或一次 commit 时，Reviewer 的第一回合和 Planner 的步骤报告会写出这个位置，并给出只读的 git 提示。结构化位置和 Reviewer 文件列表使用单行 ASCII JSON；其他名称字段使用 `prompt_name`。定时任务对话框和 Manager 会建议更便宜的 Planner Profile；除非你设置，定时任务的 Profile 不会变。Dashboard 从另一台主机经普通 http 打开时能渲染。两处 v2.8.0 的回归已修复：Grok Worker 能再次启动，Planner 的步骤决策能再次看到 agent room。

**本版本包含破坏性变更。** 不带凭据调用 `/api/` 的脚本得到 401。不支持 query token/code 登录。group 或 others 可写的运行时根目录在你执行 `chmod go-w` 之前不会启动。升级前开着的 dashboard 标签页需要刷新一次。在 https 反向代理后面，把 `dashboard_url` 设成 https 地址，否则登录得到 403。请重新运行 `install.sh` 升级。首次启动会先备份数据库再迁移。

```bash
curl -fsSL https://raw.githubusercontent.com/foolzzz/looper/main/install.sh | bash
looper --version   # looper 2.9.0
looper doctor
```

### 升级决策

**谁需要升级：**所有运行 v2.8.0 的用户。升级前，用脚本调用 HTTP API 的用户，以及从 group 或 others 可写的运行时根目录启动 `looper serve` 的用户，请先读“行为变化”。经 https 反向代理打开 dashboard 的用户，请先设置 `dashboard_url`。

**解决了什么：**v2.8.0 对本机的任何调用者回答 `/api/`，不能在 Codex 或 Grok 上设置自定义 system prompt，也不能预览运行时将发送的内容；Codex Planner 调不了 Looper 的 MCP 工具，OMP Planner 没有只读工具列表；Manager 和 Planner 的每个 Grok 回合都新起进程；没有不依赖 lark-cli 的 Lark 渠道；不能引导正在运行的 Codex 或 OMP Worker；不告诉 Reviewer 或 Planner 文件写在工作目录之外的哪里；从另一台主机经普通 http 打开时 dashboard 是空白的；每个 Grok Worker 都在启动时失败；Planner 的每一步决策都看不到 agent room。v2.9.0 要求操作者凭据，增加 `custom_prompt` 和预览，保留 Codex 的只读沙箱并恢复 Looper MCP 调用，在支持时为 OMP 增加只读工具列表，让 Grok 的 Manager 和每个任务的 Planner 各自保持独立的常驻 ACP 进程及会话，增加 Lark（bot token）渠道，在 CLI 能够时引导 Worker，标出别处找到的文件，让 dashboard 在普通 http 上渲染，并修复那两处回归。

**是否有破坏性变更：**有。匿名的 `/api/` 调用得到 401。新增密码登录，不支持 query token/code 登录。`looper serve` 拒绝 group 或 others 可写的运行时根目录。升级前打开的 dashboard 标签页需要刷新一次。在 https 反向代理后面，`dashboard_url` 不是 https 地址时登录得到 403。报告了只读工具列表的 OMP Planner 不再有 shell。详见“行为变化”“破坏性变更”和“从 v2.8.0 升级”。

**如何验证：**重新运行 `install.sh` 后，`looper --version` 显示 `looper 2.9.0`，`looper doctor` 通过。首次 `looper serve` 会在迁移前记录一份 `pg_dump` 备份。服务运行时，不带操作者令牌的 `/api/status` 返回 401，带上令牌则返回 `"status": "running"`。只有通过 loopback 地址直连、满足顶层导航条件的本机浏览器打开 dashboard 才不需要密码。

**贡献者：**发布维护者 @foolzzz；自 v2.8.0 以来合入的 pull request 没有社区贡献。

### 新能力

#### 自定义 system prompt

- **Profile 的 `custom_prompt` 前置于 Looper 拼接的提示词。** 它放在 Looper 拼出的提示词最前面，在 harness 之前。Claude Code、Codex、Grok 和 OMP 都会发送这段文字。后面仍有 harness、角色、上下文及契约；append/replace 由 `system_prompt_mode` 单独控制。空值（默认，包括从 v2.8.0 升级来的 Profile）不额外注入自定义提示词层，其他 v2.9.0 变化仍然生效。非空时记入 `prompt_layers.custom_prompt`（只有 sha256）。API、配置导入导出、派生 Profile 和 Manager 的 Profile 工具都读写它。超过 harness 长度上限是 400。（[#198](https://github.com/foolzzz/looper/pull/198)）
- **Claude Code 发送三个 system 块。** 计费头、一行固定的身份，以及主块。没有 flag、设置或环境变量能改身份行，因此只有主块可以自定义，`custom_prompt` 前置于该块中 Looper 拼接的提示词，后面仍有 harness、角色、上下文及契约；append/replace 由 `system_prompt_mode` 单独控制。计费头和身份行仍在。（[#198](https://github.com/foolzzz/looper/pull/198)）
- **预览。** Settings → Agent Profiles 有 Custom prompt 字段和 “Preview system prompt”。`GET /api/agent-profiles/<id>/prompt-preview?role=planner|worker|reviewer|manager` 按发送顺序返回 Profile/角色模板块。Looper 的块带全文。运行时自己的块只给说明，不引用原文。任务特定契约及其他启动上下文（包括知识路径、operator notes 和 skills）稍后解析；预览里的 Planner 契约使用默认参数。（[#198](https://github.com/foolzzz/looper/pull/198)）

#### Lark（bot token）

- **第二个 Lark 渠道，默认关闭。** `channel-lark_bot` 排在 Lark（lark-cli）旁边。它用 app id 和 app secret 调用 Lark 开放平台，经平台的长连接接收事件。不需要公网回调 URL，也不需要 lark-cli。私聊、群里的 @、回复、状态行、通知、定时任务和关卡遵循与 lark-cli 渠道相同的规则。已有的 lark-cli 渠道不变。（[#209](https://github.com/foolzzz/looper/pull/209)）
- **设置。** Settings → Channels 有一张卡片：app id、域（`feishu` 或 `lark`）、app secret、白名单、搜索和被拒绝的发送者。密钥存在 `channel_secrets.bot_token`。API 只显示 `has_bot_token`，从不显示密钥。`GET /api/channels/lark_bot/status` 和 `GET /api/channels/lark_bot/people?q=` 是状态和人员搜索。按名字添加的人是一次有界的目录扫描（最多 40 次请求）再加精确的邮箱查找；扫描提前结束时响应会说明。不要把同一个应用同时接到两个 Lark 渠道：平台把每个事件只投递给一个连接。渠道改动在重启后生效。（[#209](https://github.com/foolzzz/looper/pull/209)）
- **实验性。** 这个渠道还没有对真实 Lark 租户测试过。wheel 依赖 `websockets` 和 `httpx`。用 `pip` 或 `uv` 从 wheel 升级时会装上它们。（[#209](https://github.com/foolzzz/looper/pull/209)）

#### 只读的 Codex 和 OMP Planner

- **Codex。** Planner 跑在 Codex 的只读沙箱里（`sandbox_mode` 为 `read-only`，`approval_policy` 为 `never`），并且只放行 Looper 的 MCP 工具（Planner 的每个 MCP 服务器上 `default_tools_approval_mode` 为 `approve`）。写操作在沙箱里失败。Looper 自己的工具重新可用：v2.8.0 的同一套沙箱拒绝了每一次 MCP 调用。Codex 的拒绝不记成带类型的拒绝。（[#203](https://github.com/foolzzz/looper/pull/203)）
- **OMP。** 当探测到的 OMP 版本报告该能力时，Planner 得到只读工具列表（`read`、`glob`、`grep` 和它的 MCP 工具；没有 shell）。更旧的 CLI，或探测读不出的版本字符串，保持以前的行为：命令不变，Looper 在回合之后比较任务目录。本次升级之前已经注册的 OMP 运行时要重新探测（Settings → Agent Runtimes，或 `POST /api/runtimes/rt-omp/probe`），存下的探测结果才会报告该能力。升级之后第一次发现的运行时在注册时探测。缺少 `read_tools` 的 OMP 不再执行 consult，而以 `runtime_cannot` 转交 Planner。已有 OMP 需重新探测以恢复 consult；旧版或无法识别版本的 CLI 不支持 consult。（[#203](https://github.com/foolzzz/looper/pull/203)）

#### 常驻的 Grok 会话

- **Manager 和 Planner。** Manager 和每个任务的 Planner 各自保持独立的常驻 `grok agent stdio` 进程及会话（ACP：stdio 上的 JSON-RPC，`grok agent --always-approve stdio`）。第一回合启动它（`session/new`）。之后的回合复用它。重启之后，`session/load` 续接已保存的会话。一次 `session/prompt` 是一个回合。`session/cancel` 放弃一个回合。Worker 和 Reviewer 仍是一次性的无头运行。（[#205](https://github.com/foolzzz/looper/pull/205)）
- **花费。** 常驻回合的花费是 ACP 的 `costUsdTicks` 除以 1e10（每美元的 tick 数）。缺失或为零的花费仍是未知，不是免费。无头的 Worker 仍报告 Grok 自己在运行结束时给出的花费。（[#205](https://github.com/foolzzz/looper/pull/205)）
- **回退。** 如果这个 Grok 不能提供 ACP（没有 `agent stdio`，`initialize` 没有应答，已保存的会话没有 `loadSession`），该 Manager 或 Planner 在同一个家目录里按回合各起一个进程，与 v2.8.0 相同。Planner 的只读工具写在 agent profile 的 `tools:` 行里，因为根上的 `--tools` 对 `agent stdio` 无效。工具调用的事件在调用开始时记下，不是在结束时。（[#205](https://github.com/foolzzz/looper/pull/205)）

#### 工作目录之外的文件

- **带类型的位置。** Worker 把文件写进另一个 worktree 或一次 commit 时，Reviewer 的第一回合和 Planner 的步骤报告会得到这个位置：worktree 或 commit，并带只读的 git 提示（`git -C <worktree> show`，`git show <sha>`）。Reviewer 在自己的检出里仍可以写；提示只要求它读另一个地方。存下的 `found_elsewhere` 列表就是这些对象。读取方忽略旧的自由文本形状。（[#210](https://github.com/foolzzz/looper/pull/210)）
- **一条转义规则。** 结构化位置和 Reviewer 文件列表使用单行 ASCII JSON，普通名称也可能被 JSON 引号包裹。其他名称字段使用 `prompt_name`：普通可打印名字保持不变，其他内容渲染成单行 ASCII 转义 JSON，因此换行或控制字符不能在提示词里另起一行。引号、反引号或开头的减号不会原样留下。（[#210](https://github.com/foolzzz/looper/pull/210)）
- **定时任务可以用更便宜的 Planner，只有你设置了才变。** 定时任务本来就可以按角色指定 Profile。这个默认没有移动：没设置的角色保持项目的 Profile，保存时不点名 Profile 就不会增加 Profile 行。Manager 工具的 `profiles` 说明和定时任务对话框现在会建议，为运行内容相似的定时任务使用更便宜的 Planner Profile。只有你想要时才设置。（[#210](https://github.com/foolzzz/looper/pull/210)）

#### 引导正在运行的 Worker

- **当 CLI 报告该能力时。** 正在运行的 Codex Worker 经 `app-server` 驱动，可以接受 `turn/steer`。正在运行的 OMP Worker 经 `rpc` 驱动，可以接受 `steer`。两者都只在已安装的 CLI 报告该能力时生效：Codex 0.162.0 或更新，且协议 schema 里有 `turn/steer`；OMP 18.4.3 或更新，且 `--help` 列出 `rpc` 和 `--no-ui`。服务器用的是存下的探测结果。已经注册的 Codex 或 OMP 运行时要重新探测（`POST /api/runtimes/rt-codex/probe`、`POST /api/runtimes/rt-omp/probe`，或 Settings → Agent Runtimes）。升级之后第一次注册的运行时在当时探测。更旧的 CLI 退回以前的行为：提示词走标准输入，消息等到步骤的决策回合。Reviewer 走同一条路径。Claude Code 和 Grok 不变。（[#211](https://github.com/foolzzz/looper/pull/211)）
- **一次引导是什么意思。** Planner 的中途消息要等运行时接受之后才算送达。否则留到决策回合。握手失败会让这次运行带着这个错误失败；不会悄悄改回旧方式再跑一次。（[#211](https://github.com/foolzzz/looper/pull/211)）

#### 操作者登录

- **令牌。** `looper serve` 在打开数据库之前读取 `<runtime root>/operator-token`，缺失时创建它（权限 0600）。缺失的运行时根目录按 0700 创建。文件在打开时不跟随符号链接，也不阻塞。它必须是当前用户的普通文件，权限恰好是 0600。服务器不会自己 chmod。CLI（包括 `looper service`）用 `Authorization: Bearer` 发送该令牌。（[#207](https://github.com/foolzzz/looper/pull/207)）
- **同一台机器上的浏览器。** 来自 loopback 的顶层导航，且没有 `Forwarded` 或 `X-Forwarded-For` 时，设置 cookie `looper_operator_<port>`（HttpOnly、SameSite=Strict、没有 `Secure`、会话 cookie）。页面是 `Cache-Control: no-store`。cookie 名带端口，因此两个本机服务不会互相覆盖。（[#207](https://github.com/foolzzz/looper/pull/207)）
- **其他所有浏览器。** 它们得到登录页。`looper auth set-password [--user NAME]`（用户默认 `admin`，`[A-Za-z0-9._-]{1,64}`）无回显地读两遍密码，至少 8 个字符，且从不从参数读取。哈希是 scrypt（`n=32768`、`r=8`、`p=1`），写在 `<runtime root>/operator-password`，权限 0600。`looper auth clear-password` 删掉它。在设置密码之前，页面没有表单，只有本机自动登录能打开 dashboard。`POST /login` 和 `POST /logout` 要求 `Origin` 的 scheme 和 host 与请求一致（`dashboard_url` 为 https 时要求 `https`，否则 `http`）。错误的用户和错误的密码得到同样的 401。会话 cookie 保留 7 天（`Max-Age=604800`），不是令牌本身，并在密码被修改或清除、服务器重启或 `POST /logout` 时结束。最多保留 100 个会话。（[#207](https://github.com/foolzzz/looper/pull/207)）
- **锁定、缓存和日志。** 同一个 TCP 对端连续失败 5 次，锁定 60 秒，之后加倍，直到 900 秒。600 秒内超过 30 次失败则锁定所有对端，直到窗口降下来。被锁定的尝试返回 429 和 `Retry-After`，且不再计数。`X-Forwarded-For` 不能换一个新的计数桶。登录和登出的响应是 `no-store`。日志里有对端以及 failed、succeeded 或 locked，从没有用户、密码或令牌。（[#207](https://github.com/foolzzz/looper/pull/207)）

### 行为变化

下面这些在升级时改变。每一条都写了操作者要做什么。除非该条写了，否则没有新的项目设置。

1. **匿名的 `/api/` 调用得到 401。** 包括 `GET /api/status` 和 Looper 不认识的路径（401，不是 404）。发送 `Authorization: Bearer` 和 `<runtime root>/operator-token` 的内容，或通过 loopback 地址直连、满足顶层导航条件地打开 dashboard 以设置 cookie。`/api/agent/v1/` 仍使用每个 agent 自己的令牌。操作者令牌打不开 agent 路由，agent 令牌也打不开操作者路由。`OPTIONS /api/*` 不再直接返回 204；缺少相应凭据返回 401，有效凭据下未实现的方法返回 404。（[#207](https://github.com/foolzzz/looper/pull/207)）
2. **新增密码登录。** 不支持 query token/code 登录。使用 bearer 令牌或密码。（[#207](https://github.com/foolzzz/looper/pull/207)）
3. **运行时根目录对 group 或 others 可写时，`looper serve` 拒绝启动**，不属于当前用户时也拒绝。消息里写明修复办法：`chmod go-w <runtime root>`。执行它，然后再启动。无效 token 阻止启动；无效密码文件使密码登录返回 503，需修复权限或运行 `looper auth set-password`。删除密码文件后，启动不会自动重建它。服务器不会替你 chmod。本版本创建的根目录是 0700。权限 0755 的根目录（group 和 others 可读、不可写）仍能启动。（[#207](https://github.com/foolzzz/looper/pull/207)）
4. **其他机器用密码登录。** 在服务器上运行 `looper auth set-password [--user NAME]`。它问两遍，不接受 `--password`。`looper auth clear-password` 删掉哈希。会话保留 7 天，并在密码被修改或清除时结束，也在 `looper serve` 重启时结束，因为它们保存在内存里。只有通过 loopback 地址直连、满足顶层导航条件的本机浏览器不需要密码；经 LAN 地址或代理访问仍需密码。（[#207](https://github.com/foolzzz/looper/pull/207)）
5. **在 https 反向代理后面，把 `dashboard_url` 设成 https 地址。** `looper serve` 在启动时读取 `LOOPER_PUBLIC_URL`，并把它当作 `dashboard_url`。如果该值不是 https，而浏览器的 Origin 是 https，`POST /login` 和 `POST /logout` 返回 403。在启动 `looper serve` 前，把变量设成人们打开的那个 https 地址。对已安装的服务，设置变量后重新运行 `looper service install`，保留原 label、port 和 runtime root；只 restart 不会重新捕获 `LOOPER_PUBLIC_URL`。这两条路由还要求 Origin 的 host 与 `Host` 一致。登录有速率限制和锁定，见“操作者登录”。响应是 `no-store`。日志从不包含凭据。（[#207](https://github.com/foolzzz/looper/pull/207)）
6. **刷新升级前打开的 dashboard 标签页。** Dashboard 页面现在是 `no-store`，本机导航时会设置操作者 cookie。旧标签页在刷新之前会不带 cookie 调用 `/api/`。会话结束后，页面还不会在 401 时自己把你带到登录表单；请刷新。有 `POST /logout` 端点，没有登出按钮。（[#207](https://github.com/foolzzz/looper/pull/207)）
7. **CLI 和服务器一起升级。** 旧的 `looper` 不发送令牌，因此 `looper service status` 看起来像没有应答。`install.sh` 一起升级命令和服务器。`looper doctor` 和配置导出不调用本机 API。（[#207](https://github.com/foolzzz/looper/pull/207)）
8. **Codex Planner 在沙箱里只读，并且可以调用 Looper 的 MCP 工具。** 没有设置能关掉这一点。OMP Planner 只有在其运行时的探测报告该能力之后才得到只读工具列表。如果 `rt-omp` 早已注册，请重新探测；在此之前，OMP 保持 v2.8.0 的目录比较。缺少 `read_tools` 的 OMP 不再执行 consult，而以 `runtime_cannot` 转交 Planner。已有 OMP 需重新探测以恢复 consult；旧版或无法识别版本的 CLI 不支持 consult。（[#203](https://github.com/foolzzz/looper/pull/203)）
9. **Grok 的 Manager 和每个任务的 Planner 各自保持独立的常驻 ACP 进程及会话。** 没有设置去打开它；已经使用 Grok 的 Profile 在下一回合就得到它。如果该 `grok` 不会说 ACP，会话退回每个回合一个进程。Worker 仍是一次性的。常驻回合的花费按 `costUsdTicks` / 1e10 读。工具调用在开始时出现在运行记录里。（[#205](https://github.com/foolzzz/looper/pull/205)）
10. **引导要等一次重新探测。** 升级之后，已经注册的 Codex 或 OMP 运行时保持旧的能力列表，直到你重新探测。然后，当 CLI 报告了 steer 时，Worker（以及 Reviewer）经 `app-server` 或 `rpc` 运行。如果没有报告，运行仍是一次性的。你不需要设置项目开关。（[#211](https://github.com/foolzzz/looper/pull/211)）
11. **Reviewer 和 Planner 会被告知工作目录之外的文件在哪里。** 这对每个任务都生效。你不用打开它。结构化位置和 Reviewer 文件列表使用单行 ASCII JSON；其他名称字段使用 `prompt_name`，见“工作目录之外的文件”。定时任务的 Planner Profile 不会变。要用更便宜的，就在定时任务上设置 Planner Profile（对话框有提示；Manager 只在你要求时设置 `profiles`）。（[#210](https://github.com/foolzzz/looper/pull/210)）
12. **Manager 的 Profile 工具列出 `custom_prompt`。** 字段为空时不额外注入自定义提示词层，其他 v2.9.0 变化仍然生效。无论空不空，工具 schema 对模型可见。在 Profile 上设置该字段才会发送它。（[#198](https://github.com/foolzzz/looper/pull/198)）
13. **Dashboard 从另一台主机经普通 http 能渲染。** 刷新曾经空白的标签页。https 和 localhost 本来就能渲染，现在仍是。在安全上下文里 id 用 `crypto.randomUUID`，否则用 `crypto.getRandomValues`。没有 `Math.random` 回退。（[#213](https://github.com/foolzzz/looper/pull/213)）

`custom_prompt` 在 Profile 设置之前保持为空，Lark（bot token）渠道在打开之前保持关闭，`vX.Y.Z` 标签仍会发布这个 Python release。`vX.Y.Z-go` 标签不会。

### 破坏性变更

1. **`/api/` 要求操作者。** 没有令牌也没有会话的调用者得到 401，包括健康检查和不认识的路径。脚本发送 bearer 令牌。新增密码登录，不支持 `?code=` / `?token=` 登录。在 v2.8.0 上打开的 dashboard 标签页要刷新之后才会开始工作。v2.8.0 命令行里的 `looper service` 不发送令牌。（[#207](https://github.com/foolzzz/looper/pull/207)）
2. **运行时根目录不能对 group 或 others 可写。** 如果可写，或者不属于当前用户，`looper serve` 在打开数据库之前退出，并打印 `chmod go-w <runtime root>`。umask 002 留下的、group 可写的根目录很常见，升级后会让启动停住。服务器不修改权限。（[#207](https://github.com/foolzzz/looper/pull/207)）
3. **https 登录跟着 `dashboard_url`。** `POST /login` 和 `POST /logout` 要求 Origin 的 scheme 与 `dashboard_url` 一致，host 与 `Host` 一致。在 https 反向代理后面，启动前把 `LOOPER_PUBLIC_URL` 导出为那个 https 地址。留成 http 时，登录返回 403。对已安装的服务，设置变量后重新运行 `looper service install`，保留原 label、port 和 runtime root；只 restart 不会重新捕获 `LOOPER_PUBLIC_URL`。（[#207](https://github.com/foolzzz/looper/pull/207)）
4. **探测报告了只读工具列表的 OMP Planner 没有 shell。** 它以前会跑的命令没有了。重新探测才会换上新列表；在此之前仍适用 v2.8.0 的比较。Codex Planner 保留既有只读沙箱，并恢复 v2.8.0 拒绝的 Looper MCP 工具调用。（[#203](https://github.com/foolzzz/looper/pull/203)）

**其他记录或权限上的变化。** 会话在内存里：重启会结束它们，修改或清除密码也会，即使还在 7 天之内。Dashboard 页面是 `no-store`。步骤结果上的 `found_elsewhere` 是位置对象的列表；读取方忽略旧的自由文本形状。已有 Profile 的 `custom_prompt` 是空字符串。Grok 的 Manager 和每个任务的 Planner 各自保持独立的常驻 ACP 进程及会话，并用 `costUsdTicks` 计价。引导和 OMP 工具列表要等运行时用本版本探测之后。Lark（bot token）行存在且是关闭的。关卡投递和定时任务通知接受渠道 `lark_bot`。（[#205](https://github.com/foolzzz/looper/pull/205)、[#207](https://github.com/foolzzz/looper/pull/207)、[#209](https://github.com/foolzzz/looper/pull/209)、[#210](https://github.com/foolzzz/looper/pull/210)、[#211](https://github.com/foolzzz/looper/pull/211)）

### 从 v2.8.0 升级

1. **用 `install.sh` 安装。** 它安装最新 release 的 wheel。`pip` 或 `uv` 会一并安装 `websockets` 和 `httpx`。
2. **让运行时根目录只对你的用户可写。** 如果 group 或 others 能写它，`looper serve` 不会启动。运行 `chmod go-w <runtime root>`（默认根目录是 `~/.looper`）。在首次启动之前做。服务器不会替你做。
3. **保证首次启动能备份。** 表结构有变化，首次启动会先写一份 `pg_dump` 备份再迁移。请在 `PATH` 上保留主版本不低于服务器的 `pg_dump`（或设置 `LOOPER_PG_DUMP`、`LOOPER_BACKUP_CMD`）。`looper serve --skip-backup` 不备份直接迁移。
4. **启动一次。** 升级会给每个 Agent Profile 加上 `custom_prompt`（空），关卡投递和定时任务的通知渠道接受 `lark_bot`，运行时能力接受 `steer`。`<runtime root>/operator-token` 缺失时，按 0600 创建。
5. **刷新 dashboard。** 升级前打开的标签页需要刷新一次。通过 loopback 地址直连、满足顶层导航条件的本机浏览器在刷新后可自动登录。
6. **本机自动登录条件之外的浏览器需要密码。** 在服务器上运行 `looper auth set-password`，把密码输入两遍，再从另一台浏览器登录。只有通过 loopback 地址直连、满足顶层导航条件时可以跳过；经 LAN 地址或代理访问仍需密码。
7. **https 代理。** 在启动 `looper serve` 前，把 `LOOPER_PUBLIC_URL` 设成 https 地址，否则登录返回 403。这个值就是 `dashboard_url`。对已安装的服务，设置变量后重新运行 `looper service install`，保留原 label、port 和 runtime root；只 restart 不会重新捕获 `LOOPER_PUBLIC_URL`。
8. **如果要新的 Planner 工具和引导，请重新探测 Codex 和 OMP。** Settings → Agent Runtimes 的 Re-detect，或带操作者令牌调用 `POST /api/runtimes/rt-codex/probe` 和 `POST /api/runtimes/rt-omp/probe`。在此之前，已有的行保持它原来的能力。缺少 `read_tools` 的 OMP 不再执行 consult，而以 `runtime_cannot` 转交 Planner。已有 OMP 需重新探测以恢复 consult；旧版或无法识别版本的 CLI 不支持 consult。
9. **只有想用时才开 Lark（bot token）。** 在 Settings → Channels 里设置 app id、域和 app secret、白名单，并启用 `channel-lark_bot`。然后重启。保持关闭就不会连接。不要把它指到和 lark-cli 渠道同一个应用。
10. **脚本。** 每次 `/api/` 调用都带上 bearer 令牌。不支持 query token/code 登录。本版本的 `looper service` 自己会发送令牌。
11. **检查。** 运行 `looper doctor`；使用服务时再运行 `looper service status`。本版本 CLI 的 status 不应显示 unauthorized。

```bash
chmod go-w ~/.looper
curl -fsSL https://raw.githubusercontent.com/foolzzz/looper/main/install.sh | bash
looper doctor
looper serve
  # 或者使用服务：
looper service restart && looper service status
```

**回退到 v2.8.0。** 停止 Looper（装了服务就运行 `looper service uninstall`），把数据库重建为空库，并恢复首次启动日志里给出的迁移前备份（`pg_restore --no-owner --dbname "$LOOPER_DATABASE_URL" FILE`）。然后安装 v2.8.0 的 wheel，例如 `uv tool install --force "looper @ https://github.com/foolzzz/looper/releases/download/v2.8.0/looper-2.8.0-py3-none-any.whl"`。`install.sh` 总是安装最新 release，不能用来回退。v2.8.0 不认识操作者令牌、`custom_prompt`、Lark（bot token）渠道或 ACP 的 Grok 会话。留在运行时根目录里的令牌文件，v2.8.0 不会使用；如果不想让它留在磁盘上，删掉它。

### 可选能力启用与使用

#### Custom system prompt

**启用：**在 Profile 设置之前不生效。每个 Profile 的 `custom_prompt` 默认空，包括从 v2.8.0 升级来的。在 Settings → Agent Profiles、`POST` 或 `PUT /api/agent-profiles`、配置导入，或 Manager 的 Profile 工具里设置它。它前置于 Claude Code、Codex、Grok 和 OMP 收到的 Looper 提示词，后面仍有 harness、角色、上下文及契约；append/replace 由 `system_prompt_mode` 单独控制。Claude Code 的计费头和身份行不能编辑。除非你另外设置 `replace`，`system_prompt_mode` 保持 `append`。

**验证：**`GET /api/agent-profiles/PROFILE_ID` 显示 `custom_prompt`。`GET /api/agent-profiles/PROFILE_ID/prompt-preview?role=planner` 按发送顺序列出各块。只有字段被设置时，运行记录的 prompt layers 才包含 `custom_prompt`（sha256）。字段为空时不额外注入自定义提示词层，其他 v2.9.0 变化仍然生效。

**停用 / 回退：**把 `custom_prompt` 改回空字符串。下一次运行只移除该前缀，保留其他 v2.9.0 变化。已有的运行记录保留它们当时的各层。没有全局开关。

**权限边界：**这段文字是操作者输入，信任级别与 harness 相同，并放在 harness、角色提示词和契约之前。它与契约冲突时，模型可能遵循它；这个优先级没有测量过。它不增加工具。只有能编辑该 Profile 的人，或通过 Profile 工具操作的 Manager，可以设置它。预览展示 Profile/角色模板；任务特定契约及其他启动上下文稍后解析。它描述运行时自己的块；它不展示运行时隐藏的默认提示词。

**文档：**https://github.com/foolzzz/looper/blob/v2.9.0/docs/architecture/rfcs/system-prompt-mode-v0.zh-CN.md

```bash
curl -s -X PUT http://127.0.0.1:8767/api/agent-profiles/PROFILE_ID \
  -H "Authorization: Bearer $(cat ~/.looper/operator-token)" \
  -H 'Content-Type: application/json' \
  -d '{"custom_prompt": "Answer in short sentences."}'
curl -s -H "Authorization: Bearer $(cat ~/.looper/operator-token)" \
  'http://127.0.0.1:8767/api/agent-profiles/PROFILE_ID/prompt-preview?role=planner'
  # 清掉：
curl -s -X PUT http://127.0.0.1:8767/api/agent-profiles/PROFILE_ID \
  -H "Authorization: Bearer $(cat ~/.looper/operator-token)" \
  -H 'Content-Type: application/json' \
  -d '{"custom_prompt": ""}'
```

#### Lark (bot token)

**启用：**默认关闭。`channel-lark_bot` 创建时是关闭的，没有 app secret。在 Settings → Channels，或用 `PUT /api/channel-configs/channel-lark_bot`，把 `enabled` 设为 true，设置 `config.app_id`、`config.domain`（`feishu` 或 `lark`）、`config.allowed_open_ids`，并把 `bot_token` 设为 app secret。重启 `looper serve` 让渠道连接。不要和 lark-cli 渠道使用同一个应用。lark-cli 渠道保持原样。这个渠道还没有对真实 Lark 租户测试过。

**验证：**`GET /api/channel-configs/channel-lark_bot` 显示 `enabled`、`has_bot_token` 和 app id，不显示密钥。`GET /api/channels/lark_bot/status` 检查应用凭据，报告机器人或凭据问题；空白名单由 channel-config 响应的 `start_problem` 报告。白名单发送者的私聊，或群里的 @，会到达 Manager。被拒绝的发送者被列出来，不会交给模型。

**停用 / 回退：**`PUT /api/channel-configs/channel-lark_bot` 加 `{"enabled": false}`，然后重启。行和密钥还在，直到你清掉它们。lark-cli 渠道是另一行；关掉这一行不会改它。要丢掉密钥，就设一个新值，或用设置页清除渠道密钥。除了 wheel 自己的依赖，没有额外的包要卸载。

**权限边界：**打开的渠道把白名单发送者的消息交给 Manager，Manager 可以不经权限确认就使用它的工具，与 lark-cli 相同。不在白名单上的人没有模型回合。app secret 存在服务器上，与其他渠道密钥放在一起，API 不返回它，错误里不写它，日志里也不写它。长连接接收该应用的事件。与 lark-cli 渠道共用同一个应用时，事件会落在两个连接中的一个上。人员搜索读取租户目录，最多 40 次请求，外加精确的邮箱查找。

**文档：**https://github.com/foolzzz/looper/blob/v2.9.0/docs/architecture/agent-system.md#channels

#### Grok runtime

**启用：**在有 Profile 使用运行时 `grok` 之前仍然不生效。本版本改变的是这个 Profile 会做什么。Manager 和每个任务的 Planner 各自保持独立的常驻 `grok agent stdio` 进程及会话。Worker 和 Reviewer 仍是一次性的无头运行。没有新设置。如果安装的 `grok` 不能提供 ACP，Manager 和 Planner 在同一个家目录里退回每个回合一个进程。这条路径不需要重新探测。

**验证：**Grok 的 Manager 或 Planner 运行在多个回合之间保持一个进程（运行页显示一个常驻会话，之后的回合不起新进程）。Grok 报告了 tick 时，花费等于 `costUsdTicks` / 1e10。缺失或为零的数字仍是未知。Grok Worker 的运行能完成，而不是在 `session_dir` 上失败。有 Profile 使用时，`looper doctor` 仍报告 Grok 登录。

**停用 / 回退：**和 v2.8.0 一样，在该层改选别的 Profile，再删除 Grok Profile。没有一个开关能在 ACP 可用时仍保留 Grok 并强制旧的按回合进程。去掉 `grok` 可执行文件并重启后，检测不到该运行时。

**权限边界：**常驻的 Grok 进程在 Manager 或该任务的 Planner 存续期间以你的用户身份运行，带 `--always-approve` 和 `--trust`，家目录由 Looper 拥有。它在之后的回合里可以调用 MCP 工具，而不必新起进程。登录留在你的 Grok 登录文件里；Looper 不保存令牌。Worker 仍是一个进程。单次花费上限仍停不住一次 Grok 运行；某次运行报告花费之后，任务上限会阻止后续运行。花费 tick 是 Grok 的数字，不是 Looper 算出来的价格。

**文档：**https://github.com/foolzzz/looper/blob/v2.9.0/docs/architecture/agent-system.md#runtimes-llm-providers-and-agent-profiles

```bash
grok --version
curl -s -H "Authorization: Bearer $(cat ~/.looper/operator-token)" \
  http://127.0.0.1:8767/api/status
  # Grok Profile 与 v2.8.0 的建法相同。把某个角色指到它，或清掉：
curl -s -X PUT http://127.0.0.1:8767/api/agent-settings/roles/planner \
  -H "Authorization: Bearer $(cat ~/.looper/operator-token)" \
  -H 'Content-Type: application/json' \
  -d '{"profile_id": null}'
```

#### Worker steering

**启用：**当 Codex 或 OMP 运行时存下的探测列出 `steer` 时开启，否则关闭。Codex 在 0.162.0 或更新、且协议 schema 含有 `turn/steer` 时报告它。OMP 在 18.4.3 或更新、且 `--help` 列出 `rpc` 和 `--no-ui` 时报告它。升级之后重新探测：Settings → Agent Runtimes，或下面的 probe 路由。新注册的运行时在注册时探测。更旧的 CLI 退回一次性运行。没有项目设置。Claude Code 和 Grok 不会获得这个能力。

**验证：**重新探测之后，`GET /api/registry` 在该运行时的 capabilities 里显示 `steer`。正在运行的 Codex Worker 是一个 `app-server` 进程，正在运行的 OMP Worker 是 `omp --mode rpc`。运行期间 Planner 的消息会在步骤的决策回合之前出现。探测里没有 `steer` 的运行时仍把提示词放在标准输入上。

**停用 / 回退：**只要 CLI 仍报告该能力，重新探测就不会去掉它。要保持以前的一次性运行，就留着旧的能力列表（不要重新探测），或使用不报告 steer 的 CLI。没有按任务的开关。运行时不接受的消息留到决策回合，与以前一样。

**权限边界：**一次引导把 Planner 的文字送进已经在运行的 Worker，带着该 Worker 的工具，且不再确认一次。同一条路径也服务 Reviewer。在 4 秒超时的引导仍可能到达 Worker；Planner 把这段文字保留为 delivery not confirmed，因此 Worker 可能看到两次。服务器不会借引导给只读的 Planner 一个 shell。隔离、花费上限和进程树的杀死与一次性运行相同。

**文档：**https://github.com/foolzzz/looper/blob/v2.9.0/docs/architecture/rfcs/worker-steering-v0.zh-CN.md

```bash
curl -s -X POST http://127.0.0.1:8767/api/runtimes/rt-codex/probe \
  -H "Authorization: Bearer $(cat ~/.looper/operator-token)"
curl -s -X POST http://127.0.0.1:8767/api/runtimes/rt-omp/probe \
  -H "Authorization: Bearer $(cat ~/.looper/operator-token)"
curl -s -H "Authorization: Bearer $(cat ~/.looper/operator-token)" \
  http://127.0.0.1:8767/api/registry | python3 -c 'import json,sys; [print(r["id"], r.get("capabilities")) for r in json.load(sys.stdin)["runtimes"]]'
```

#### Operator password

**启用：**通过 loopback 地址直连、满足顶层导航条件的本机浏览器可自动登录，无需密码。其他浏览器均需密码，包括经 LAN 地址或代理访问的本机浏览器。在服务器上运行 `looper auth set-password [--user NAME]`，并在提问时把密码输入两遍（至少 8 个字符；没有可以放在命令行上的选项）。默认用户是 `admin`。然后从另一台机器打开 dashboard 并登录。操作者令牌本身不是可选的：`looper serve` 会创建它，既没有令牌也没有会话的调用者会被 `/api/` 拒绝。

**验证：**带上用户、密码，以及 scheme 和 host 与页面一致的 `Origin`，`POST /login` 返回 303 并设置 `looper_session_<port>`。带上该 cookie 的 `GET /api/status` 返回 200。没有凭据的调用返回 401。`~/.looper/operator-password` 权限是 0600，且不含密码原文。五次错误密码之后再试一次，返回 429。

**停用 / 回退：**`looper auth clear-password` 删除哈希并结束每一个会话。登录页于是没有表单。本机浏览器仍用令牌 cookie 登录。你不能关掉令牌检查。只在服务器停止时删除 `<runtime root>/operator-token`；下一次启动会写一份新的。

**权限边界：**任何能访问该端口、并且知道用户和密码的人，都可以调用每一条操作者路由，持续 7 天，或直到密码改变、密码被清除、服务器重启，或他们调用 `POST /logout`。令牌文件权限是 0600。以你的用户身份运行的进程仍能读到该文件。登录锁定见“操作者登录”。日志不含密码、用户或令牌。`POST /login` 和 `POST /logout` 拒绝不匹配的 Origin。在 https 代理后面，`dashboard_url` 必须是那个 https 地址。

**文档：**https://github.com/foolzzz/looper/blob/v2.9.0/docs/architecture/agent-system.md#http-api

```bash
looper auth set-password
  # 提问时把密码输入两遍。它不是参数。
curl -s -o /dev/null -w '%{http_code}\n' -D - \
  -X POST http://127.0.0.1:8767/login \
  -H 'Origin: http://127.0.0.1:8767' \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  --data 'username=admin&password=YOUR_PASSWORD'
  # 删掉。会话结束。
looper auth clear-password
```

### 已知限制

- **只读 consult 的来源没有被钉住以挡住席位重启。** 席位的重启不会在 consult 读取该次运行时被挡住。（[#203](https://github.com/foolzzz/looper/pull/203)）
- **真实 consult 初始化工具列表已核对。** Consult 要求 Claude Code 只用 `Read`、`Glob` 和 `Grep`，OMP 只用 `read`、`glob` 和 `grep`。OMP 仍不是沙箱。（[#203](https://github.com/foolzzz/looper/pull/203)）
- **OMP 的检出不是沙箱。** OMP 以你的用户身份运行。Consult 的检出事后删除。检出之外的写入既不会被阻止，也不会被发现。（[#203](https://github.com/foolzzz/looper/pull/203)）
- **Planner 合并报告里的 git 错误文本被压成一行。** 换行变成空格。这段错误里的引号和代码围栏还在。文件名、路径和分支名的转义规则不改写这段文本。（[#210](https://github.com/foolzzz/looper/pull/210)）
- **没有观察到真实模型使用 git 提示。** 它直接读了 worktree 里的文件，而不是提示里的 `git show`。（[#210](https://github.com/foolzzz/looper/pull/210)）
- **超时（4 秒）的引导仍可能到达 Worker。** Planner 把它保留为 “delivery not confirmed”，因此 Worker 可能看到两次。（[#211](https://github.com/foolzzz/looper/pull/211)）
- **Lark（bot token）还没有对真实 Lark 租户测试过。** 令牌无效的错误码、scope 名称和连接上限来自文档和 SDK，不是来自线上租户。lark-cli 渠道不变。（[#209](https://github.com/foolzzz/looper/pull/209)）
- **Dashboard 没有登出按钮。** `POST /logout` 是端点。会话结束后页面不处理 401；请刷新标签页。（[#207](https://github.com/foolzzz/looper/pull/207)）
- **经真实反向代理的登录没有核实，真实 launchd 或 systemd 上的 `looper service install` 也没有核实。** 密码流程在同一台机器上用一个非 loopback 的主机名检查过，服务单元用假的服务管理器检查过。（[#207](https://github.com/foolzzz/looper/pull/207)）
- **提示词预览展示 Profile/角色模板。** 任务特定契约及其他启动上下文（包括知识路径、operator notes 和 skills）稍后解析；预览里的 Planner 契约使用默认参数。Grok 和 OMP 的分块布局来自启动代码，不是从真实会话里抓到的。Claude Code 的三个块抓过。（[#198](https://github.com/foolzzz/looper/pull/198)）
- **ACP 的 Grok 没有检查压缩事件、并行工具调用、回合中途的用户输入或文本流。** 不能提供 ACP 的会话退回每个回合一个进程。（[#205](https://github.com/foolzzz/looper/pull/205)）

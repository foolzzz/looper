# Looper v2.14.59

This is the patch release v2.14.59, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.58: a drain that begins while an agent schedule is firing no longer lets that firing create or start a task ([#1029](https://github.com/foolzzz/looper/pull/1029)).

## Release Decision

**Who should upgrade:** Anyone who runs agent schedules and plans service restarts with `looper service upgrade` or `looper service restart --drain`.

**What this release solves:** An agent firing (a due tick, Run now, or the start of a queued run) checked the drain only once, at admission. If the drain began while the firing's transaction was still waiting on the database, the firing still created its task, committed and published `TASK_START`, so a planned restart got a new task and a new Planner turn after it had begun draining. [#1029](https://github.com/foolzzz/looper/pull/1029) rechecks the drain as the last step of the transaction and again before `TASK_START` is published. A firing whose transaction is still open rolls back: the schedule stays due, a queued run stays queued, and Run now answers the existing 409. A firing that committed after the drain began keeps its task ready and publishes no `TASK_START` during the drain; the task starts after the restart or a cancelled drain.

**Breaking changes:** No. No API or configuration is removed. The release adds one additive migration (a column on `schedule_runs`): see "Upgrading".

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#1029](https://github.com/foolzzz/looper/pull/1029); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.59
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.58 upgrades directly. This release adds one migration, applied once on the first start of an existing database and recorded in `schema_migrations`; a new database gets it from `schema.sql`:

- `schedule_deferred_by_drain` ([#1029](https://github.com/foolzzz/looper/pull/1029)) adds the column `schedule_runs.deferred_by_drain` (`BOOLEAN NOT NULL DEFAULT false`).

It only adds; existing runs read as not deferred. Because the schema changes, the first start takes the usual database backup before the change (the same rule as for any pending schema change).

## Behavior changes

- **A firing under way when the drain begins creates nothing ([#1029](https://github.com/foolzzz/looper/pull/1029)).** A due tick, Run now, or the start of a queued run for an agent schedule checks the drain as the last statement of its transaction. If the drain has begun, the transaction rolls back: the schedule keeps its due time, a queued run stays queued, and Run now answers the existing 409 ("the service is draining for an upgrade: run it after the restart").
- **A commit that lands after the drain began defers the task start.** The task stays ready and `TASK_START` is not published during the drain. The run is marked `deferred_by_drain`, and the task starts after the restart or a cancelled drain through the existing start retry. A gate that was not yet started goes back to `queued` with the same mark and resumes afterwards; a deferred parallel gate needs only a free slot under `max_parallel_runs`.
- **The run timeout excludes the deferred wait.** For a run whose start was deferred by a drain, the run timeout counts from the moment `TASK_START` was actually published (or the task was seen started), not from the firing. A restarted deferred gate gets the normal gate timeout from its new firing. Runs never deferred keep counting from the firing.
- **The start retry waits during a drain.** The retry of a created-but-never-started task does not publish `TASK_START` while the service drains.
- **Unchanged.** Command schedules keep firing during a drain, including queued runs and Run now. A gate admitted before the drain still finishes and starts its task. Detaching or adopting runs and the drain's own phases and deadlines are out of scope and unchanged.
- **Model-visible changes:** No. No prompt, tool description, tool schema or Manager confirmation text changes; the 409 text of Run now already existed.
- **Documentation and tests.** `docs/architecture/agent-system.md` describes the behavior. Tests cover it in `tests/test_drain_services_db.py`, with schema expectations updated in `tests/test_bridge_schema_db.py` and `tests/test_command_schedules_schema_db.py`. The change is in `looper/agents/scheduler.py`, `looper/db/connection.py` and `looper/db/schema.sql`.

## 中文摘要

本版本是 patch release v2.14.59（热修线，每个合并的改动立即发布）。自 v2.14.58 以来只合并了一项改动：排空开始时正在触发的 agent 定时任务，不再创建或启动任务（[#1029](https://github.com/foolzzz/looper/pull/1029)）。

### 升级决策

**谁需要升级：**运行 agent 定时任务，并使用 `looper service upgrade` 或 `looper service restart --drain` 做计划内重启的用户。

**解决了什么：**agent 触发（到点、立即运行或排队运行开始）只在准入时检查一次排空。如果排空开始时该触发的事务还在等待数据库，它仍会创建任务、提交并发布 `TASK_START`，于是计划内重启在开始排空之后又多出一个新任务和一轮新的 Planner。[#1029](https://github.com/foolzzz/looper/pull/1029) 在事务的最后一步以及发布 `TASK_START` 之前再次检查排空。事务仍未提交的触发会回滚：定时任务保持到期，排队运行保持排队，立即运行返回已有的 409。排空开始后才提交的触发，其任务保持 ready，排空期间不发布 `TASK_START`，在重启或排空取消后启动。

**是否有破坏性变更：**否。没有移除任何 API 或配置。本版本新增一个只增加的迁移（`schedule_runs` 的一列），见“升级”。

**如何验证：**运行 `looper --version` 核对版本为 2.14.59。

**贡献者：**维护者 @foolzzz 提交 [#1029](https://github.com/foolzzz/looper/pull/1029)；本版本无社区贡献。

```bash
looper --version   # looper 2.14.59
```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.58 上的安装可直接升级。本版本新增一个迁移，在现有数据库首次启动时执行一次并记录在 `schema_migrations`；新数据库由 `schema.sql` 创建：

- `schedule_deferred_by_drain`（[#1029](https://github.com/foolzzz/looper/pull/1029)）新增列 `schedule_runs.deferred_by_drain`（`BOOLEAN NOT NULL DEFAULT false`）。

迁移只增加；已有运行读作未被推迟。因为 schema 会变化，首次启动会先按常规做数据库备份（与任何待执行的 schema 变更相同）。

### 行为变化与入口

- **排空开始时正在进行的触发不创建任何东西（[#1029](https://github.com/foolzzz/looper/pull/1029)）。**agent 定时任务的到点触发、立即运行或排队运行开始，会在事务的最后一条语句检查排空。排空已开始则事务回滚：定时任务保留到期时间，排队运行保持排队，立即运行返回已有的 409（“the service is draining for an upgrade: run it after the restart”）。
- **排空开始后才提交的触发推迟任务启动。**任务保持 ready，排空期间不发布 `TASK_START`。该运行被标记为 `deferred_by_drain`，在重启或排空取消后通过已有的启动重试启动。尚未启动的 gate 回到 `queued` 并带同样标记，之后继续；被推迟的并行 gate 只需 `max_parallel_runs` 下有空位。
- **运行超时不计入被推迟的等待。**启动被排空推迟的运行，其运行超时从 `TASK_START` 实际发布（或看到任务已启动）时起算，而不是从触发时起算。重新启动的被推迟 gate 从新的触发起获得正常的 gate 超时。未被推迟的运行仍从触发起算。
- **启动重试在排空期间等待。**对已创建但从未启动的任务，重试在服务排空期间不发布 `TASK_START`。
- **不变。**命令定时任务在排空期间继续触发，包括排队运行和立即运行。排空前已准入的 gate 仍会完成并启动其任务。分离或接管运行以及排空自身的阶段和期限不在范围内，保持不变。
- **面向模型的变化：**无。不改变提示、工具描述、工具 schema 或 Manager 的确认文字；立即运行的 409 文字本已存在。
- **文档与测试。**`docs/architecture/agent-system.md` 描述了该行为，测试位于 `tests/test_drain_services_db.py`，`tests/test_bridge_schema_db.py` 和 `tests/test_command_schedules_schema_db.py` 更新了 schema 预期。改动在 `looper/agents/scheduler.py`、`looper/db/connection.py` 和 `looper/db/schema.sql`。

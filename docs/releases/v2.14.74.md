# Looper v2.14.74

This is the patch release v2.14.74, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.73: a built-in provider for the operator's own Cursor login ([#1072](https://github.com/foolzzz/looper/pull/1072)).

## Release Decision

**Who should upgrade:** Operators who plan to run Cursor Agent through Looper and want its existing login on the server's machine shown in Settings → LLM Providers and checked by `looper doctor`. Nobody else needs it: no runtime uses the provider yet.

**What this release solves:** Looper had no way to stand for a Cursor login. [#1072](https://github.com/foolzzz/looper/pull/1072) adds the built-in OAuth provider `cursor-login` and a check that says whether the login can run. Looper never reads the keychain or a credential file, and adds no file-store login, link, API key or login link. The Cursor Agent runtime itself comes in a later change.

**Breaking changes:** No. The change adds a provider, a self check and a one-time schema upgrade; nothing existing is removed or renamed.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#1072](https://github.com/foolzzz/looper/pull/1072); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.74
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.73 upgrades directly. This release carries a one-time schema upgrade (see below) that runs when the service starts.

## Behavior changes

- **Provider.** Every database gets the built-in provider `prov-cursor-login` (vendor `cursor-login`, OAuth, `oauth_runtime_type = 'cursor-agent'`) with an `openai-responses` endpoint used only for pairing, and five suggested models without built-in prices: `auto`, `gpt-5.3-codex`, `gpt-5.6-sol-high`, `composer-2.5` and `gemini-3.7-flash-high` (`looper/db/seeds.sql`). If an older database already has a custom provider named `cursor-login`, the built-in one takes a free name such as `cursor-login (1)`; saved providers and references are not changed.
- **Schema.** `llm_providers` gains `cursor-login` in its vendor CHECK, and the CHECKs now have names. An existing database is widened once (migration `cursor_login`) under the schema lock; a fresh database already has it. `schema_change_pending` reports the pending change, so the backup step before a schema change covers it.
- **Login check.** `looper/agents/runtimes/cursor_login.py` runs `cursor-agent status --format json` with the operator's `HOME`, throwaway `CURSOR_CONFIG_DIR` and `CURSOR_DATA_DIR`, without `CURSOR_API_KEY`, `CURSOR_AUTH_TOKEN`, `CURSOR_API_ENDPOINT` and `AGENT_CLI_CREDENTIAL_STORE`, with `NO_OPEN_BROWSER=1`, a 20 s timeout and a 30 s cache. `authenticated` is signed in; `unauthenticated` and `partially-authenticated` are not signed in; anything else (including a missing executable or a timeout) is a failed check. The throwaway directories are removed afterwards. The module also provides `launch_problem`, which refuses unless signed in ("run `cursor-agent login`"); no runtime calls it yet.
- **Provider listing.** Listing providers on a machine with `cursor-agent` starts `cursor-agent status` in one background thread at most once per 30 s and never waits for it; until the first answer the login state is `checking`. The `login.state` enum of the registry API gains `checking`.
- **Dashboard.** Settings → LLM Providers shows a runtime login's state even when that runtime's adapter does not exist yet, with `cursor-agent status` and `cursor-agent login` as the commands; while a state is `checking` it reloads every second. Clearing a recorded login problem stays limited to the Codex and Grok logins.
- **Self check.** A new `cursor_login` check in `looper doctor`, the startup checks and `/api/v1/system/status`: skipped while no Agent Profile uses the login; OK when signed in; FAIL when not signed in; WARN when it could not be checked.
- **Tests.** The test suite puts a refusing `cursor-agent` stand-in first on PATH, so no test reaches a real Cursor login.
- **Docs.** The agent-system reference, the plan ledger and the TTADK launch RFC (the Cursor login decision).
- **Size:** per the changed files of the pull request, about 900 added lines in total, of which about 490 are tests and fixtures.
- **Model-visible changes:** No prompt, built-in role text or tool description changes. The built-in provider list the Manager reads through its provider tools now contains the `cursor-login` provider and its models, and a provider's `login` object may show the state `checking`.

## Optional Capability Activation & Use

### Cursor login provider (cursor-login)

**Activation:** Install `cursor-agent` and sign in on the server's machine with `cursor-agent login`, as the user that runs Looper. The provider is built in; no Looper setting is needed. No runtime uses it yet, so it only reports state in this release.

```bash
cursor-agent login
cursor-agent status --format json
```

**Validation:** Settings → LLM Providers shows the `cursor-login` provider as signed in, and `looper doctor` reports `cursor_login` once an Agent Profile uses the login (otherwise it is skipped).

**Disable / rollback:** Nothing to disable: the provider only reports state. Signing out with `cursor-agent logout` makes the check fail. The schema widening is not reverted by a downgrade; an older release ignores the extra provider row.

**Authority boundary:** Looper only runs `cursor-agent status` with the operator's `HOME` and temporary configuration and data directories. It never reads the keychain or a credential file, passes no API key or token, and stores no Cursor credential.

**Docs:** [docs/architecture/agent-system.md](https://github.com/foolzzz/looper/blob/main/docs/architecture/agent-system.md).

本版本是 patch release v2.14.74（热修线，每个合并的改动立即发布）。自 v2.14.73 以来只合并了一项改动：为运维人员自己的 Cursor 登录增加内置 provider（[#1072](https://github.com/foolzzz/looper/pull/1072)）。

### 升级决策

**谁需要升级：**计划通过 Looper 运行 Cursor Agent，并希望服务器所在机器上已有的登录显示在设置 → LLM Providers 并由 `looper doctor` 检查的运维人员。其他人无需升级：目前没有运行时使用该 provider。

**解决了什么：**Looper 此前无法表示 Cursor 登录。[#1072](https://github.com/foolzzz/looper/pull/1072) 增加内置 OAuth provider `cursor-login`，以及判断该登录能否运行的检查。Looper 不读取钥匙串或凭据文件，也不增加文件存储登录、链接、API key 或登录链接。Cursor Agent 运行时将在之后的改动中加入。

**是否有破坏性变更：**否。本改动增加 provider、自检和一次性数据库升级，不删除也不重命名已有内容。

**如何验证：**运行 `looper --version` 核对版本为 2.14.74。

**贡献者：**维护者 @foolzzz 提交 [#1072](https://github.com/foolzzz/looper/pull/1072)；本版本无社区贡献。

```bash
looper --version   # looper 2.14.74
```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.73 上的安装可直接升级。本版本带有一次性数据库升级（见下），在服务启动时执行。

### 行为变化与入口

- **Provider。**每个数据库都获得内置 provider `prov-cursor-login`（vendor `cursor-login`，OAuth，`oauth_runtime_type = 'cursor-agent'`），带一个仅用于配对的 `openai-responses` 端点，以及五个无内置价格的建议模型：`auto`、`gpt-5.3-codex`、`gpt-5.6-sol-high`、`composer-2.5`、`gemini-3.7-flash-high`（`looper/db/seeds.sql`）。若旧数据库已有同名 `cursor-login` 的自定义 provider，内置 provider 改用空闲名称如 `cursor-login (1)`；已保存的 provider 和引用不变。
- **数据库结构。**`llm_providers` 的 vendor CHECK 增加 `cursor-login`，且 CHECK 现在有名称。已有数据库在 schema 锁下一次性放宽（迁移 `cursor_login`）；新数据库已包含。`schema_change_pending` 会报告该待执行变更，因此 schema 变更前的备份步骤涵盖它。
- **登录检查。**`looper/agents/runtimes/cursor_login.py` 以操作员的 `HOME`、临时的 `CURSOR_CONFIG_DIR` 和 `CURSOR_DATA_DIR` 运行 `cursor-agent status --format json`，不带 `CURSOR_API_KEY`、`CURSOR_AUTH_TOKEN`、`CURSOR_API_ENDPOINT` 和 `AGENT_CLI_CREDENTIAL_STORE`，设置 `NO_OPEN_BROWSER=1`，超时 20 秒，缓存 30 秒。`authenticated` 为已登录；`unauthenticated` 和 `partially-authenticated` 为未登录；其他情况（包括找不到可执行文件或超时）为检查失败。临时目录随后删除。该模块还提供 `launch_problem`，未登录时拒绝（提示运行 `cursor-agent login`）；目前没有运行时调用它。
- **Provider 列表。**在装有 `cursor-agent` 的机器上列出 provider 时，最多每 30 秒在一个后台线程启动一次 `cursor-agent status`，且从不等待；首次答复前登录状态为 `checking`。注册表 API 的 `login.state` 枚举增加 `checking`。
- **控制台。**设置 → LLM Providers 即使在该运行时的适配器尚不存在时也显示其登录状态，命令为 `cursor-agent status` 和 `cursor-agent login`；状态为 `checking` 时每秒重新加载。清除已记录登录问题仍仅限 Codex 和 Grok 登录。
- **自检。**`looper doctor`、启动检查和 `/api/v1/system/status` 新增 `cursor_login` 检查：没有 Agent Profile 使用该登录时跳过；已登录为 OK；未登录为 FAIL；无法检查为 WARN。
- **测试。**测试套件在 PATH 最前放置一个拒绝执行的 `cursor-agent` 替身，测试不会触及真实的 Cursor 登录。
- **文档。**agent-system 参考、计划台账和 TTADK 启动 RFC（Cursor 登录决定）。
- **规模：**据 PR 的改动文件，共新增约 900 行，其中约 490 行为测试和夹具。
- **面向模型的变化：**无提示词、内置角色文本或工具说明的变化。Manager 通过其 provider 工具读取的内置 provider 列表现在包含 `cursor-login` provider 及其模型，provider 的 `login` 对象可能显示状态 `checking`。

### 可选能力启用与使用

#### Cursor login provider (cursor-login)

**启用：**在服务器所在机器上安装 `cursor-agent`，并以运行 Looper 的用户执行 `cursor-agent login` 登录。该 provider 为内置，无需 Looper 设置。目前没有运行时使用它，因此本版本只报告状态。

```bash
cursor-agent login
cursor-agent status --format json
```

**验证：**设置 → LLM Providers 显示 `cursor-login` provider 为已登录；一旦有 Agent Profile 使用该登录，`looper doctor` 会报告 `cursor_login`（否则跳过）。

**停用 / 回退：**无需停用：该 provider 只报告状态。用 `cursor-agent logout` 登出会使检查失败。降级不会还原数据库结构的放宽；旧版本会忽略多出的 provider 行。

**权限边界：**Looper 只用操作员的 `HOME` 以及临时的配置和数据目录运行 `cursor-agent status`。它不读取钥匙串或凭据文件，不传递 API key 或令牌，也不保存任何 Cursor 凭据。

**文档：**[docs/architecture/agent-system.md](https://github.com/foolzzz/looper/blob/main/docs/architecture/agent-system.md)。

# Looper v2.13.110

## Release Decision

**Who should upgrade:** Anyone who uses the dashboard chat page and switches between conversations, Managers or history entries (links, Back and Forward, a refresh) while a message is being sent or answered.

**What this release solves:** [#598](https://github.com/foolzzz/looper/pull/598) keeps chat sends and navigation bound to the conversation they started in: a send is cancelled when the page moves to another Manager or conversation, and a late response no longer lands in the wrong one.

**Breaking changes:** No. No route, request field or stored data changed; only the dashboard chat page behaves differently, and the optional `signal` is client-side only.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#598](https://github.com/foolzzz/looper/pull/598); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.110
```

## Behavior changes

- **Sends are owned by their conversation ([#598](https://github.com/foolzzz/looper/pull/598)):** in `web/src/pages/chat.tsx`, `handleSend` captures the Manager and session at send time and installs a cancel function before it awaits `sendChat`. The cancel aborts the HTTP request (`sendChat` in `web/src/lib/api.ts` now takes an optional `signal`) and closes the reply stream. A new send, or navigation to another Manager or conversation, cancels the one in flight, including before its HTTP response has arrived. A response, stream event or error that arrives after that is ignored, so the sending state and phase are cleared and no text is written into the wrong thread.
- **Read-only and unresolved conversations:** opening a channel conversation, or one that is still loading, failed to load or belongs to another Manager, cancels the stream of the thread that was open. Sending from such a view is refused, and the turn-sync poll and visibility re-sync run only while the owned thread is the one shown. Sidebar navigation that clears the query and pins the same thread again does not cancel the send.
- **Opening a conversation only changes the address:** choosing a row in the conversation list now updates the address and the page adopts the web thread from it, instead of switching the composer owner directly. The conversation shown is taken from the read of that conversation, not from the list, which holds only the newest.
- **Unsaved threads and Back:** a new chat, and a thread the page created that has no messages yet, are remembered per Manager in the browser's local storage (`looper-chat-local-threads:<manager>`). Back or Forward to such an id opens it as a new thread; any other id with no messages, and any Planner or channel id with none, shows "Conversation not found." and cannot take over the stored composer owner. A successful send removes the id from that set.
- **Reply saving:** the page no longer saves the assistant reply itself when a turn completes or fails. The server's web channel adapter already saves the reply to the session the send was made from (`looper/agents/channels/web.py`), including after navigation, so the page's second save, which used the session shown at that moment, is gone.
- **Model-visible changes:** None. No Manager tool declaration, prompt or API route changed; the request to `operator_chat/send` is the same, and only the browser may now abort it.
- **Tests:** [#598](https://github.com/foolzzz/looper/pull/598) adds a browser test `tests/test_chat_navigation_browser.py` and extends `web/src/pages/chat-composer-flow.test.tsx`, `web/src/pages/chat-manager-picker.test.tsx` and `web/src/url-state.test.tsx` (179 test lines, 192 production lines as reported).

## Upgrade and rollback

Re-run `install.sh` once v2.13.110 is published. No data migration and no configuration change; the dashboard is rebuilt into the wheel. Rolling back to v2.13.109 restores the earlier chat page behavior. The local-storage key above is then unused and can stay.

### 升级决策

**谁需要升级：**使用仪表盘聊天页，并在发送或等待回复期间切换会话、Manager 或历史记录（链接、后退/前进、刷新）的使用者。

**解决了什么：**[#598](https://github.com/foolzzz/looper/pull/598) 让聊天发送与导航始终绑定其所属会话：页面切换到其他 Manager 或会话时取消正在进行的发送，迟到的响应不再落入错误的会话。

**是否有破坏性变更：**否。路由、请求字段和存储数据均未改变；只有仪表盘聊天页的行为改变，可选的 `signal` 仅在客户端使用。

**如何验证：**运行 `looper --version` 核对版本为 2.13.110。

**贡献者：**维护者 @foolzzz 提交 [#598](https://github.com/foolzzz/looper/pull/598)；本次 patch release 无社区贡献。

```bash
looper --version   # looper 2.13.110
```

### 行为变化与入口

- **发送归属于其会话（[#598](https://github.com/foolzzz/looper/pull/598)）：**`web/src/pages/chat.tsx` 中，`handleSend` 在发送时记录 Manager 与会话，并在等待 `sendChat` 之前装好取消函数。取消会中止 HTTP 请求（`web/src/lib/api.ts` 的 `sendChat` 新增可选 `signal`）并关闭回复流。新的发送，或导航到其他 Manager 或会话，会取消正在进行的发送，包括 HTTP 响应尚未到达时。之后到达的响应、流事件或错误被忽略，发送状态和阶段被清除，不会把文字写入错误的会话。
- **只读与未解析的会话：**打开渠道会话，或仍在加载、加载失败、属于其他 Manager 的会话，会取消原先打开的会话的流。这类视图不能发送；回合同步轮询和可见性重新同步只在显示的是自己拥有的会话时运行。侧边栏导航清除查询后重新固定同一会话，不会取消发送。
- **打开会话只改地址：**在会话列表中选择一行现在只更新地址，页面再据此接管 web 会话，不再直接切换输入框的归属。显示的会话取自该会话自身的读取，而不是只含最新若干条的列表。
- **未保存的会话与后退：**新建的聊天，以及页面创建、尚无消息的会话，按 Manager 记在浏览器本地存储（`looper-chat-local-threads:<manager>`）中。后退或前进到这样的 id 会作为新会话打开；其他无消息的 id，以及无消息的 Planner 或渠道 id，显示“Conversation not found.”，且不能接管已存储的输入框归属。发送成功后该 id 从集合中移除。
- **回复保存：**回合完成或失败时，页面不再自行保存助手回复。服务端的 web 渠道适配器已把回复保存到发送时的会话（`looper/agents/channels/web.py`），导航之后也一样，页面原先按当前显示会话进行的第二次保存已移除。
- **面向模型的变化：**无。Manager 的 tool 声明、提示词和 API 路由均未改变；对 `operator_chat/send` 的请求不变，只是浏览器现在可以中止它。
- **测试：**[#598](https://github.com/foolzzz/looper/pull/598) 新增浏览器测试 `tests/test_chat_navigation_browser.py`，并扩展 `web/src/pages/chat-composer-flow.test.tsx`、`web/src/pages/chat-manager-picker.test.tsx` 和 `web/src/url-state.test.tsx`（按报告测试 179 行、生产代码 192 行）。

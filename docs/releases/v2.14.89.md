# Looper v2.14.89

This is the patch release v2.14.89, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.88: operators can disable and re-enable an LLM provider ([#1113](https://github.com/foolzzz/looper/pull/1113)).

## Release Decision

**Who should upgrade:** Operators who want to take an LLM provider out of use temporarily (an expired key, an outage, a policy change) without deleting it or re-selecting its Agent Profiles. Everyone else can stay.

**What this release solves:** The only way to stop using a provider was to delete it or to change every selection of its profiles. [#1113](https://github.com/foolzzz/looper/pull/1113) adds an `enabled` flag: a disabled provider keeps its endpoints, key, models, Agent Profiles and all their selections, and a run that resolves to one of its profiles is refused at launch with a message that names the provider and how to enable it again.

**Breaking changes:** No. One additive database column (`llm_providers.enabled`, default true) is added. With every provider enabled, behavior and exported config files are unchanged; API views only gain `enabled` fields.

**How to verify:** Check the installed version. In Settings → LLM Providers, switch a provider off: the row shows a Disabled badge and the effects on its Agent Profiles, and a run that resolves to one of its profiles is refused with "provider 'NAME' is disabled; enable it in Settings → LLM Providers". Switch it on again and the same profile runs.

**Contributors:** Maintainer @foolzzz authored [#1113](https://github.com/foolzzz/looper/pull/1113); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.89
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.88 upgrades directly. The database gains one column: the upgrade `provider_enabled` adds `llm_providers.enabled BOOLEAN NOT NULL DEFAULT true` once, recorded in `schema_migrations`, so every existing provider stays enabled. Fresh schemas already contain the column.

## Behavior changes

- **Provider availability** (`looper/agents/profile_registry.py`, new operation `provider_accounts.set_enabled`). It takes `provider_id` and a boolean `enabled` (anything else is refused with "enabled must be true or false") and works on the built-in login providers too. Disabling is never refused. The answer carries a `warnings` list naming the Agent Profiles that are selected somewhere (role defaults, project layers and the like), at most 10 followed by "and N more Agent Profiles", and a warning when the built-in default profile `claude-code/opus` is affected. Setting the current value changes nothing. Nothing else is touched: endpoints, key, models, profiles and every selection stay.
- **Launch check** (`looper/agents/agent_settings.py`). A run that resolves to a profile whose provider is disabled is refused through the same check that refuses a missing API key, with the message "Agent Profile '<name>' cannot run: provider '<name>' is disabled; enable it in Settings → LLM Providers". The Manager answers with it; a Planner turn or a Worker/Reviewer step fails with it.
- **Creating and editing profiles** (`profile_registry.py`). Creating an Agent Profile with a disabled provider's model, or switching a profile to such a model, is refused, with a hint to choose a model of another provider. Editing a profile that keeps its model is not refused.
- **Schema and API** (`looper/db/connection.py`, `looper/db/schema.sql`, `looper/agents/v1_domains/`). The column and its additive upgrade are described above. Provider views gain `enabled`, a profile's provider gains `enabled`, and a model gains `provider_enabled`. `provider_accounts.update` and `register` are unchanged except that `register` refuses an `enabled` argument (a new account is enabled).
- **Dashboard** (`web/src/components/provider-settings.tsx`, `agent-profiles.tsx`). Settings → LLM Providers gets an enable switch and a Disabled badge on each row, with a confirmation that states how many Agent Profiles use the provider and a note of the effects. Affected Agent Profiles show a warning with a link to the provider, and profile selectors mark "provider disabled".
- **CLI.** `set_enabled` is an operator operation and appears as the generated `loopercli provider-accounts set-enabled` command (`--enabled` / `--no-enabled`).
- **Config transfer** (`looper/agents/config_transfer.py`, `looper/db/config_transfer.py`). `enabled: false` is exported only for a disabled provider; an import must give a boolean, and an import without the field keeps the target's value (true for a new provider). Exported files of an all-enabled installation are byte-identical.
- **Unchanged:** Telegram and Lark (`/profile` already reports a profile's launch problem), channels, pricing, and wheel and source upgrades apart from the one column.
- **Documentation and tests.** The pull request adds `tests/test_llm_provider_enabled_db.py` and extends the provider API, dashboard, config transfer, Manager tools, registry, schema upgrade and web component tests, including an installed-dashboard smoke test of disabling, the Manager refusal and re-enabling.
- **Model-visible changes:** Yes. The Manager tool `looper_providers` now lists `enabled` for each account, and its `update` action accepts `enabled` (its description now reads "update an account's name, endpoints, env, max_concurrency or enabled", and the `enabled` parameter text says false disables the account, whose Agent Profiles keep their selections but do not run, and that built-in login accounts take only this). `register` with `enabled` returns "a new account is enabled; use update to disable it". A disabled provider's launch refusal text (above) is what the Manager and agents see in place of a run. No prompt text changes.

## 中文摘要

本版本是 patch release v2.14.89（热修线，每个合并的改动立即发布）。自 v2.14.88 以来只合并了一项改动：运维人员可以停用和重新启用 LLM 提供方（[#1113](https://github.com/foolzzz/looper/pull/1113)）。

### 升级决策

**谁需要升级：**希望临时停用某个 LLM 提供方（密钥过期、故障、策略变化）而又不想删除它或重新选择其 Agent Profile 的运维人员。其他人可不升级。

**解决了什么：**原先要停用提供方只能删除它，或修改其 profile 的每一处选择。[#1113](https://github.com/foolzzz/looper/pull/1113) 增加 `enabled` 开关：停用的提供方保留端点、密钥、模型、Agent Profile 及其所有选择；解析到其 profile 的运行在启动时被拒绝，提示中写明提供方名称和重新启用的方法。

**是否有破坏性变更：**否。仅新增一个向后兼容的数据库列（`llm_providers.enabled`，默认 true）。所有提供方都启用时，行为和导出的配置文件不变；API 视图只多出 `enabled` 字段。

**如何验证：**核对版本为 2.14.89。在设置 → LLM Providers 中关闭某个提供方：该行显示 Disabled 标记和对其 Agent Profile 的影响，解析到其 profile 的运行被拒绝，提示 "provider 'NAME' is disabled; enable it in Settings → LLM Providers"。重新开启后同一 profile 可运行。

**贡献者：**维护者 @foolzzz 提交 [#1113](https://github.com/foolzzz/looper/pull/1113)；本版本无社区贡献。

```bash
looper --version   # looper 2.14.89
```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.88 上的安装可直接升级。数据库新增一列：升级项 `provider_enabled` 一次性添加 `llm_providers.enabled BOOLEAN NOT NULL DEFAULT true` 并记入 `schema_migrations`，所有现有提供方保持启用。全新建库的结构已含该列。

### 行为变化与入口

- **提供方可用性**（`looper/agents/profile_registry.py`，新操作 `provider_accounts.set_enabled`）。参数为 `provider_id` 和布尔值 `enabled`（其他类型被拒绝，提示 "enabled must be true or false"），内置登录型提供方同样适用。停用从不被拒绝。返回值带 `warnings` 列表，列出在某处被选用的 Agent Profile（角色默认值、项目层等），最多 10 条，其后为 "and N more Agent Profiles"；若影响内置默认 profile `claude-code/opus` 也会提示。设置为当前值不产生变化。其余一切不动：端点、密钥、模型、profile 和所有选择都保留。
- **启动检查**（`looper/agents/agent_settings.py`）。解析到提供方已停用的 profile 的运行，经与缺少 API 密钥相同的检查被拒绝，消息为 "Agent Profile '<name>' cannot run: provider '<name>' is disabled; enable it in Settings → LLM Providers"。Manager 以此回答；Planner 轮次或 Worker/Reviewer 步骤以此失败。
- **创建和编辑 profile**（`profile_registry.py`）。用已停用提供方的模型创建 Agent Profile，或把 profile 切换到这样的模型，会被拒绝并提示改选其他提供方的模型。编辑保持原模型的 profile 不受影响。
- **结构与 API**（`looper/db/connection.py`、`looper/db/schema.sql`、`looper/agents/v1_domains/`）。列及其向后兼容升级见上。提供方视图新增 `enabled`，profile 的提供方新增 `enabled`，模型新增 `provider_enabled`。`provider_accounts.update` 与 `register` 不变，只是 `register` 拒绝 `enabled` 参数（新账户默认启用）。
- **控制台**（`web/src/components/provider-settings.tsx`、`agent-profiles.tsx`）。设置 → LLM Providers 每行有启用开关和 Disabled 标记，停用时有确认提示，写明使用该提供方的 Agent Profile 数量及影响。受影响的 Agent Profile 显示警告并链接到该提供方，profile 选择器标出 "provider disabled"。
- **CLI。**`set_enabled` 是运维人员操作，作为生成式命令 `loopercli provider-accounts set-enabled`（`--enabled` / `--no-enabled`）出现。
- **配置转移**（`looper/agents/config_transfer.py`、`looper/db/config_transfer.py`）。仅停用的提供方才导出 `enabled: false`；导入时该值必须是布尔值，缺省则保留目标的值（新提供方为 true）。全部启用的安装导出的文件逐字节不变。
- **不变：**Telegram 和 Lark（`/profile` 已报告 profile 的启动问题）、渠道、定价，以及 wheel 与源码升级（除上述一列外）。
- **文档与测试。**该 PR 新增 `tests/test_llm_provider_enabled_db.py`，并扩展了提供方 API、控制台、配置转移、Manager 工具、注册表、结构升级和前端组件测试，包括停用、Manager 拒绝、重新启用的已安装控制台冒烟测试。
- **面向模型的变化：**有。Manager 工具 `looper_providers` 现在为每个账户列出 `enabled`，其 `update` 动作接受 `enabled`（描述改为 "update an account's name, endpoints, env, max_concurrency or enabled"，`enabled` 参数说明 false 会停用账户，其 Agent Profile 保留选择但不运行，内置登录账户只接受该参数）。带 `enabled` 的 `register` 返回 "a new account is enabled; use update to disable it"。停用提供方的启动拒绝文本（见上）会替代运行结果呈现给 Manager 和 agent。提示文本不变。

# Looper v2.14.132

This is the patch release v2.14.132, a hotfix line in which each merged change ships at once. It documents one change: [#1226](https://github.com/foolzzz/looper/pull/1226) (`looper service upgrade` fails with a clear error, and changes nothing, when it cannot read the running service's status, instead of planning a full drain).

## Release Decision

**Who should upgrade:** Operators who run `looper service upgrade` against a running service. Everyone else gets no change.

**What this release solves:** [#1226](https://github.com/foolzzz/looper/pull/1226) stops the upgrade from treating an unreadable service status as keeper mode off and planning a full drain. The upgrade now fails before planning, with a clear error, and nothing is drained or changed. An upgrade whose status is readable plans as before.

**Breaking changes:** No. There is no migration and no API removal; an upgrade that used to proceed on an unreadable status now fails and can be run again. The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.14.132
```

**Contributors:** Maintainer @foolzzz authored [#1226](https://github.com/foolzzz/looper/pull/1226); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.131 upgrades directly. There is no schema change.

## Behavior changes

- **An unreadable status fails `looper service upgrade`** ([#1226](https://github.com/foolzzz/looper/pull/1226)). After the running component manifest is read, the upgrade reads the service status. If nothing answers with JSON (`None`), it raises `cannot read the running service's status (keeper mode unknown); nothing was drained, run looper service upgrade again`. This happens before any plan is made and for a dry run too: no plan is decided, no plan is executed, no target is installed and no system operation is sent. Before, the missing status was treated as an empty one, so keeper mode counted as off and a full drain was planned.
- **The status read has a 15 s timeout** for this call (`_get_status` takes a `timeout` argument; its default stays 3 s). `Host.get_status` is now typed as a callable with any arguments.
- **Unchanged:** a readable status plans as before. A 401 answer is still returned as `{"status": "unauthorized"}`, not as unreadable, so it does not take the new error path. Other service commands and the dashboard are unchanged.
- **Model-visible changes:** None. No tool description, Planner, Worker, Reviewer or Manager prompt or contract text and no run `AGENTS.md` text changes.

### 升级决策

**谁需要升级：**对运行中的服务执行 `looper service upgrade` 的运维者。其他人无变化。

**是否有破坏性变更：**否。没有迁移，没有移除 API；此前在状态不可读时继续的升级现在失败，可重新运行。桥接边界不变：早于 v2.13.165 的安装须先升级到 v2.13.165。

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.131 上的安装可直接升级。没有结构变更。

### 行为变化与入口

- **状态不可读时 `looper service upgrade` 失败**（[#1226](https://github.com/foolzzz/looper/pull/1226)）。读取运行中的组件清单后，升级会读取服务状态。若没有任何以 JSON 作答的响应（`None`），则抛出 `cannot read the running service's status (keeper mode unknown); nothing was drained, run looper service upgrade again`。这发生在制定任何计划之前，试运行（dry run）同样如此：不决定计划、不执行计划、不安装目标，也不发送任何系统操作。此前缺失的状态被当作空状态，keeper 模式视为关闭，并规划完全排空。
- **该次状态读取的超时为 15 秒**（`_get_status` 新增 `timeout` 参数，默认仍为 3 秒）。`Host.get_status` 的类型改为接受任意参数的可调用对象。
- **不变：**状态可读时照旧规划。401 响应仍返回 `{"status": "unauthorized"}`，不算不可读，因此不走新的错误路径。其他服务命令和仪表盘不变。
- **面向模型的变化：**无。没有工具描述、Planner、Worker、Reviewer 或 Manager 的提示词与契约文本变化，运行的 `AGENTS.md` 文本也无变化。

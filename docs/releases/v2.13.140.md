# Looper v2.13.140

## Release Decision

**Who should upgrade:** Nobody needs to for behavior. This patch hardens a codec that nothing in Looper calls yet; everyone can stay on v2.13.139. Upgrade only to follow the API runtime work.

**What this release solves:** [#683](https://github.com/foolzzz/looper/pull/683) hardens the OpenAI Responses codec added in v2.13.139 (covers #680): it refuses inherited OpenAI environment settings, counts every SDK retry against the request cap, keeps usage that is partial or arrives with a failure, keeps reasoning continuity at default effort and marks a stream that ends without completion for the loop's existing safe resend. It is groundwork: no Manager, session or entry point uses the codec in this release.

**Breaking changes:** No. Nothing calls the codec, and no existing format, command or API changes. The internal codec interface gains a required `max_attempts` argument; the only implementation is updated with it.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#683](https://github.com/foolzzz/looper/pull/683); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.140
```

## Behavior changes

- **Environment (#683):** `looper/agents/runtimes/api/responses.py` adds `ResponsesConfigurationError` (a `RuntimeUnsupported`). When any of `OPENAI_ORG_ID`, `OPENAI_PROJECT_ID`, `OPENAI_ADMIN_KEY`, `OPENAI_CUSTOM_HEADERS` or `OPENAI_LOG` is set, `ResponsesCodec.stream` refuses before importing the SDK (whose import can enable logging) and client creation refuses again; the error names the variables, not their values. The client is also built with organization, project and default headers cleared, and per-turn options clear them again, so ambient settings cannot override the resolved provider target.
- **Request cap (#683):** the loop in `looper/agents/runtimes/api/loop.py` now counts each request plus its SDK retries against the request limit and passes the remainder to the codec as the new `max_attempts` argument of `ProtocolCodec.stream`. The codec's request hook raises the new `RequestLimitReached` before an attempt beyond that budget is sent; the loop records the unfinished request and ends with `MAX_REQUESTS` (or `CANCELLED` if a cancel was requested). Before, retries did not count against the limit.
- **Usage (#683):** cached and cache-write token counts no longer default to 0; if either, the input total or the output count is missing, usage is recorded as incomplete. Usage is now read from `response.failed` and `response.incomplete` as well as `response.completed`, before the error is raised, so a failed request keeps the usage it reported.
- **Stream end (#683):** a stream that ends without a terminal event raises the same protocol error, now flagged `retryable_stream` when the provider stream had started, which lets the loop's existing single safe resend apply. The loop's resend logic is unchanged.
- **Reasoning continuity (#683):** `include=['reasoning.encrypted_content']` is now part of every request body, not only when an effort is set; `reasoning.effort` is still sent only with an effort.
- **Tests (#683):** `tests/test_api_responses.py` grows to cover these cases.
- **Runtime behavior:** none visible. `loop_for` is still not called by anything else in `looper/`, so no change to running Managers, tasks, the database, the API, the command line or the dashboard.
- **Model-visible changes:** none to Looper's existing prompts, tool declarations or tool results. The one request-body change (`include` of encrypted reasoning at default effort) applies only once something calls the codec; no caller exists in this release.
- **Line counts:** the description reports tests 130 and production 45 added lines (fixtures excluded).

## Upgrade and rollback

Re-run `install.sh` once v2.13.140 is published. No schema or configuration change. Rolling back to v2.13.139 restores the unhardened, still unused codec and has no other effect.

## 中文摘要

### 升级决策

**谁需要升级：**无需为行为变化升级。本 patch 加固一个 Looper 中尚无调用方的内部编解码器；所有人可留在 v2.13.139。仅在跟进 API 运行时工作时升级。

**解决了什么：**[#683](https://github.com/foolzzz/looper/pull/683) 加固 v2.13.139 引入的 OpenAI Responses 编解码器（对应 #680）：拒绝继承的 OpenAI 环境设置，把每次 SDK 重试计入请求上限，保留不完整或随失败返回的用量，在默认 effort 下保持推理连续性，并让未完成就结束的流可被循环现有的安全重发处理。这是基础工作：本版本中没有 Manager、会话或入口使用该编解码器。

**是否有破坏性变更：**否。尚无调用方使用编解码器，现有格式、命令和 API 均不变。内部编解码器接口新增必填参数 `max_attempts`，唯一的实现已同步更新。

**如何验证：**运行 `looper --version` 核对版本为 2.13.140。

**贡献者：**维护者 @foolzzz 提交 [#683](https://github.com/foolzzz/looper/pull/683)；本次 patch release 无社区贡献。

```bash
looper --version   # looper 2.13.140
```

### 行为变化与入口

- **环境（#683）：**`looper/agents/runtimes/api/responses.py` 新增 `ResponsesConfigurationError`（属 `RuntimeUnsupported`）。只要设置了 `OPENAI_ORG_ID`、`OPENAI_PROJECT_ID`、`OPENAI_ADMIN_KEY`、`OPENAI_CUSTOM_HEADERS` 或 `OPENAI_LOG` 之一，`ResponsesCodec.stream` 会在导入 SDK 之前（其导入可能启用日志）拒绝，创建客户端时再次拒绝；错误只列变量名，不含取值。客户端创建时还会清空 organization、project 和默认请求头，每轮选项再清一次，使环境设置无法覆盖已解析的 provider 目标。
- **请求上限（#683）：**`looper/agents/runtimes/api/loop.py` 中的循环现在把每个请求及其 SDK 重试都计入请求上限，并把剩余次数作为 `ProtocolCodec.stream` 的新参数 `max_attempts` 传给编解码器。编解码器的请求钩子在发出超出预算的尝试之前抛出新增的 `RequestLimitReached`；循环记录该未完成请求，以 `MAX_REQUESTS` 结束（若已请求取消则为 `CANCELLED`）。此前重试不计入上限。
- **用量（#683）：**缓存读、缓存写 token 数不再默认为 0；其中任一项、输入总数或输出数缺失时，用量记为不完整。现在除 `response.completed` 外，也在 `response.failed` 与 `response.incomplete` 抛错前读取用量，失败的请求会保留其报告的用量。
- **流结束（#683）：**无终态事件就结束的流仍抛同样的协议错误，在 provider 流已开始时标记为 `retryable_stream`，使循环现有的单次安全重发生效。循环的重发逻辑本身未改。
- **推理连续性（#683）：**`include=['reasoning.encrypted_content']` 现在包含在每个请求体中，而不只是设置了 effort 时；`reasoning.effort` 仍只在设置了 effort 时发送。
- **测试（#683）：**`tests/test_api_responses.py` 扩充以覆盖上述情形。
- **运行时行为：**无可见变化。`looper/` 中仍无其他地方调用 `loop_for`，运行中的 Manager、任务、数据库、API、命令行与仪表盘均无变化。
- **面向模型的变化：**Looper 现有的提示词、tool 声明和 tool 结果均无变化。唯一的请求体变化（默认 effort 下也 `include` 加密推理）只有在有调用方使用该编解码器时才生效；本版本没有调用方。
- **行数：**描述报告新增测试 130 行、生产代码 45 行（不含 fixtures）。

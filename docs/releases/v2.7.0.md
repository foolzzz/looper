# Looper v2.7.0

## At a Glance

Looper now runs work on its own and keeps it going. A project can **schedule** a full task on a cron rule, with a gate command that checks for new work first, a daily budget and alerts to Telegram or Lark. **Restarting a task continues from its saved plan** instead of planning it again, a running task takes supplements and requirement edits, and its page shows progress notes and a final summary. The Planner plans independent parts in parallel, with no step limit, can run parallel steps in git worktrees of their own, and can choose its Workers' Agent Profile from a list the project allows. The **Manager acts through typed platform tools** with confirmations and an audit trail, creates tasks ready rather than started, and can manage projects, Agent Profiles, settings, the catalog, costs and schedules. Concurrency is limited per project and per task instead of per machine. Settings is a group of pages built around **Agent Profiles**, which now carry the effort, Claude Code agent teams and Codex's own ChatGPT login. Telegram gets a bot token field and Lark lark-cli profiles and group chats; both react to a message, show one status message while the Manager works, store their conversations and tell the chat that asked when its task ends.

**This release has breaking changes.** API routes and fields renamed to the dashboard's names keep no aliases, the Manager's tasks wait to be started, a restart continues instead of starting over, Claude Code agent teams are on by default and the default concurrency is higher. Upgrade by re-running `install.sh`; the first start backs the database up and migrates it. The details are under Breaking Changes and Upgrading from v2.6.0.

```bash
curl -fsSL https://raw.githubusercontent.com/foolzzz/looper/main/install.sh | bash
looper --version   # looper 2.7.0
looper doctor
```

## Release Decision

**Who should upgrade:** Everyone running v2.6.0. Before upgrading, anyone who calls the HTTP API from scripts should read Breaking Changes, since routes and fields were renamed without aliases, and anyone who ran the Telegram channel on v2.6.0 should plan to rotate the bot token.

**What this release solves:** v2.6.0 could only run a task when someone asked for one, threw a task's plan away on every restart, could not change a running task's requirement, capped the whole machine at 3 tasks and 4 runs, started a task as soon as the Manager wrote its JSON, read the Manager's actions out of its prose, could not list more than 50 tasks, left an agent's commands running after it was stopped, gave up on a crashed agent after 3 restarts, and wrote the Telegram bot token into the log. v2.7.0 adds scheduled tasks, restarts that continue, task changes and progress, a Planner that plans in parallel and can choose its agents, typed Manager tools with confirmations, per-project and per-task concurrency, Agent Profiles with effort, agent teams and the Codex ChatGPT login, and fuller Telegram and Lark channels, and fixes the rest.

**Breaking changes:** Yes. Routes and fields renamed to the dashboard's names (`/api/roles`, `/api/agent-profiles`, `profile_id`) keep no aliases and the runtime registration routes are gone; a settings layer refuses `effort` and a role refuses `max_concurrency`; the Manager's tasks wait to be started and its JSON actions are gone; a restart continues from the saved plan; concurrency is limited per project, and higher by default; Claude Code agent teams are on by default; the Lark channel uses a lark-cli profile and no longer reads its app ID variable; the journal kind `user_instruction` is `supplement`; a requirement over 32,000 characters is refused. See Breaking Changes and Upgrading from v2.6.0.

**How to verify:** After re-running `install.sh`, `looper --version` reports `looper 2.7.0` and `looper doctor` passes. The first `looper serve` logs a `pg_dump` backup before it migrates. With the server running, `/api/status` reports `"status": "running"`, `/api/overview` answers with task counts by group, `/api/roles` lists the roles and `/api/registry` lists `profiles` with their `agent_teams`, and the Settings group in the sidebar lists Agent Profiles and Roles.

**Contributors:** Release maintainer @foolzzz; community contributor @michaelx1993, with pull request #100 and the first commits of #106, #108 and #109 on the Telegram and Lark channels, and the reports of issues #148 and #149 (see Community Contributors).

```bash
curl -fsSL https://raw.githubusercontent.com/foolzzz/looper/main/install.sh | bash
looper --version   # looper 2.7.0
looper doctor
looper serve       # or: looper service restart
  # In another shell:
curl -s http://127.0.0.1:8767/api/status | python3 -m json.tool | head -20
curl -s http://127.0.0.1:8767/api/overview | python3 -m json.tool | head -20
curl -s http://127.0.0.1:8767/api/registry | python3 -c 'import json, sys; [print(p["name"], p["agent_teams"]) for p in json.load(sys.stdin)["profiles"]]'
```

## Scheduled Tasks

- **Schedules.** A schedule belongs to a project: a name, a 5-field cron rule in an IANA time zone, the requirement of each run's task, a work directory, an overlap policy (`skip`, `queue`, or `parallel` with up to `max_parallel_runs`), a catch-up policy, a run timeout, a spend cap for each run's task and Agent Profiles per role. Two fires must be at least 5 minutes apart, or 1 minute with a gate. A schedule is created disabled; enabling it is the approval for the tasks it starts. The scheduler inside `looper serve` looks every 15 s, claims a due schedule's row so that two servers on one database fire it once, and starts a task titled by the schedule and the fire time, whose requirement ends with a code-written context of the run. ([#98](https://github.com/foolzzz/looper/pull/98), [#125](https://github.com/foolzzz/looper/pull/125), [#140](https://github.com/foolzzz/looper/pull/140), [#154](https://github.com/foolzzz/looper/pull/154))
- **Gate, unfinished input and daily budget.** A gate command runs before each run in the work directory; no output skips the run at no cost, a failure counts as one, and its output becomes the task's input. The output of a run that did not finish goes to the next run once. A daily budget skips firings once the day's runs cost that much. A repeated skip is counted on one run, so a gate every minute adds a row only when the outcome changes. Under `parallel`, runs overlap but gates never do, and the gate gets the run's id and timeout in its environment. ([#101](https://github.com/foolzzz/looper/pull/101), [#132](https://github.com/foolzzz/looper/pull/132), [#136](https://github.com/foolzzz/looper/pull/136), [#140](https://github.com/foolzzz/looper/pull/140))
- **Notifications and alerts.** `notify` is `failures` (the default), `alerts`, `always` or `never`, to one allowlisted Telegram or Lark person. Three failures in a row and no success for 3 periods (at least 15 minutes, at most 24 hours) each raise one alert and one recovery; a gate that finds nothing new counts as healthy, and the no-success window counts from the last enabling or rule change and pauses while a run is in progress. ([#101](https://github.com/foolzzz/looper/pull/101), [#118](https://github.com/foolzzz/looper/pull/118), [#134](https://github.com/foolzzz/looper/pull/134), [#143](https://github.com/foolzzz/looper/pull/143), [#144](https://github.com/foolzzz/looper/pull/144), [#156](https://github.com/foolzzz/looper/pull/156))
- **On the dashboard.** A project's Schedules tab edits schedules with a preview of the next fire times; the Schedules page lists every project's, filtered by project and status; a schedule's page shows its settings, alerts, today's spend and its run history with the routine skips hidden. Deleting a schedule works from every page and is safe while a run is in progress: its task finishes, a queued run never starts, and its tasks stay. ([#130](https://github.com/foolzzz/looper/pull/130), [#131](https://github.com/foolzzz/looper/pull/131), [#135](https://github.com/foolzzz/looper/pull/135), [#160](https://github.com/foolzzz/looper/pull/160))

## Tasks and the Planner

- **Restart continues; start over is explicit.** Start on a stopped, failed or cancelled task, `POST /api/tasks/start` and the Manager's `restart` keep the accepted steps and their merged work, put the unfinished steps back with their retries, feedback and worktrees, and give the Planner a `[RESTART]` turn to add steps or replan. Start over, with an inline confirmation, `"start_over": true` or the Manager's `start_over` (confirmed), deletes the steps and plans anew, which every restart did before. ([#146](https://github.com/foolzzz/looper/pull/146), [#147](https://github.com/foolzzz/looper/pull/147), [#152](https://github.com/foolzzz/looper/pull/152))
- **Task changes.** A chat message to a task's Planner is stored as a supplement, `PUT /api/tasks/:id/requirement` edits the requirement and keeps every version, and the Planner gets every waiting change in one turn, delivered only once its reply is applied; `[CHAT]` can now `replan`, and Workers and Reviewers see the supplements. ([#126](https://github.com/foolzzz/looper/pull/126))
- **Progress and a final summary.** Decisions carry a progress note, the completing decision a final summary (delivered, how to use it, verification, open issues), and a failed or stopped task gets a closing note written by code; the task page shows them under Progress. ([#114](https://github.com/foolzzz/looper/pull/114))
- **A Planner that runs in parallel.** The recommended prompt has the Planner make steps depend only on the results they need, pin interfaces first and build parts in parallel, and replan on top of accepted work. A plan may have any number of steps, every ready step is dispatched at once under the project's and the task's limits, retries per step are a project setting (`max_step_retries`, default 2), and a requirement may have 32,000 characters. ([#104](https://github.com/foolzzz/looper/pull/104), [#137](https://github.com/foolzzz/looper/pull/137), [#139](https://github.com/foolzzz/looper/pull/139))
- **Step workspaces (opt-in).** With a project's `step_workspaces` set to `worktree`, steps that run at the same time work in git worktrees and branches of their own and are merged back one merge commit per step, with conflicts handed to the Planner. ([#127](https://github.com/foolzzz/looper/pull/127))
- **The Planner's tools.** Each Planner gets an MCP server for its own task: it can choose its Workers' or Reviewers' Agent Profile from the project's allowed list (empty by default) and change the task's or the project's concurrency, each change journaled. ([#155](https://github.com/foolzzz/looper/pull/155))
- **A task's own agents and limits.** `PUT /api/tasks/:id/agents` and the task page's Agents block set a task's Agent Profile per role and its Worker and Reviewer limits, also on an ended task before a restart. ([#145](https://github.com/foolzzz/looper/pull/145), [#152](https://github.com/foolzzz/looper/pull/152))
- **The Pipeline tab** draws the plan's dependency graph, keeping dropped steps as dashed history. ([#146](https://github.com/foolzzz/looper/pull/146))
- **Tasks have titles** from the Manager's tool or the schedule, shown in lists, headings and notices. ([#124](https://github.com/foolzzz/looper/pull/124), [#125](https://github.com/foolzzz/looper/pull/125))

## The Manager

- **Platform tools over MCP.** The Manager no longer writes JSON actions, whose reading [#120](https://github.com/foolzzz/looper/pull/120) had made stricter: it calls `looper` MCP tools for the overview, tasks (create, start, stop, restart, start over, cancel, instruct, update), concurrency, projects, Agent Profiles, providers (without keys), settings layers and the allowed-profile list, the catalog, costs and schedules. Reads run in any turn, writes only in a turn that answers a user, and `high` calls (a new project, cancelling or starting over a task, deletions, the shared defaults, concurrency of a project or role, raising or removing a spend cap) only after the user confirms in the next message, within 10 minutes. Every call is recorded and shown on the task page; when the tools are unavailable the user is told that nothing ran. ([#129](https://github.com/foolzzz/looper/pull/129), [#145](https://github.com/foolzzz/looper/pull/145), [#157](https://github.com/foolzzz/looper/pull/157), [#160](https://github.com/foolzzz/looper/pull/160))
- **Ready tasks.** A task the Manager creates waits as Ready, with a configuration block (Agent Profiles, effort, review, caps, concurrency) and the question whether to start it; Start on the Tasks or task page or `POST /api/tasks/<id>/start` starts it. A new project is created only once the user confirms it. ([#88](https://github.com/foolzzz/looper/pull/88))
- **It answers the message it was sent.** Each message carries a `Channel:` line, the recommended prompt has the Manager answer only that message, and its reply is the turn's final answer without the narration before its tool calls. ([#112](https://github.com/foolzzz/looper/pull/112), [#119](https://github.com/foolzzz/looper/pull/119))
- **`/new`** starts a new Manager session from any channel. ([#73](https://github.com/foolzzz/looper/pull/73))

## Channels

- **Telegram.** The bot token is entered in Settings → Channels and stored apart, never returned (the environment variable still works without one); the bot publishes its command menu. ([#100](https://github.com/foolzzz/looper/pull/100))
- **Lark on lark-cli.** The channel uses lark-cli 1.0.97's commands, keeps its event consumer alive under a service, and takes an optional lark-cli profile in place of the app variables; it checks the login and the bot at startup, binds the sender allowlist to its app, finds senders by name or email and lists refused senders with Allow. In groups it answers @-mentions of the bot from listed senders. ([#102](https://github.com/foolzzz/looper/pull/102), [#105](https://github.com/foolzzz/looper/pull/105), [#107](https://github.com/foolzzz/looper/pull/107), [#142](https://github.com/foolzzz/looper/pull/142))
- **While the Manager works.** The bot reacts when it sees a message, then shows one status message edited in place instead of one message per phase; task progress still comes as messages. ([#111](https://github.com/foolzzz/looper/pull/111), [#115](https://github.com/foolzzz/looper/pull/115))
- **Conversations and notices.** Telegram and Lark conversations are stored, shown read-only on the Chat page and included in a new session's resume brief. A task asked for in a chat reports its end there, last, as Markdown with an absolute link (`LOOPER_PUBLIC_URL`). ([#106](https://github.com/foolzzz/looper/pull/106), [#108](https://github.com/foolzzz/looper/pull/108), [#109](https://github.com/foolzzz/looper/pull/109), [#116](https://github.com/foolzzz/looper/pull/116), [#122](https://github.com/foolzzz/looper/pull/122))
- **The bot token stays out of the log.** httpx's request lines are off without `--verbose`, and every log line is masked. ([#150](https://github.com/foolzzz/looper/pull/150))

## Agents, Settings and the Dashboard

- **Settings pages and Agent Profiles.** Settings is a group of pages (LLM Providers, Agent Runtimes, Agent Profiles, Roles, Skills & MCP, Channels, Import / Export); runtimes are built in and detected on the server's PATH; the Agents page is Runs; Roles and a project's new Agent Profiles tab are collapsible rows. ([#75](https://github.com/foolzzz/looper/pull/75), [#77](https://github.com/foolzzz/looper/pull/77), [#84](https://github.com/foolzzz/looper/pull/84), [#87](https://github.com/foolzzz/looper/pull/87))
- **The dashboard's names everywhere.** Tables, routes, fields, the configuration format (`looper-config/v2`) and the code say Agent Profile and role. ([#76](https://github.com/foolzzz/looper/pull/76))
- **The effort belongs to the Agent Profile.** The upgrade moves every layer's effort onto a profile with the same effect. ([#91](https://github.com/foolzzz/looper/pull/91), [#93](https://github.com/foolzzz/looper/pull/93))
- **Claude Code agent teams** per Agent Profile, on by default for Claude Code profiles and never for Planners. ([#80](https://github.com/foolzzz/looper/pull/80), [#83](https://github.com/foolzzz/looper/pull/83))
- **Codex on its own ChatGPT login** (`codex-login`), linked rather than copied into each run's home. ([#78](https://github.com/foolzzz/looper/pull/78))
- **Every runtime sees the repository's instructions.** Codex reads `CLAUDE.md` when there is no `AGENTS.md`, OMP gets it injected outside git, and Claude Code no longer picks up an `AGENTS.md` above the repository. ([#97](https://github.com/foolzzz/looper/pull/97))
- **The Dashboard shows what is happening now:** task counts by group, the agents running or waiting, concurrency by project, today's spend and unhealthy components. ([#89](https://github.com/foolzzz/looper/pull/89))
- **Chat:** Enter sends and Shift+Enter adds a line, long lines wrap, Markdown tables render, an answer is saved even after you leave the page, and long histories open at their newest messages. ([#82](https://github.com/foolzzz/looper/pull/82), [#85](https://github.com/foolzzz/looper/pull/85), [#86](https://github.com/foolzzz/looper/pull/86), [#90](https://github.com/foolzzz/looper/pull/90), [#109](https://github.com/foolzzz/looper/pull/109))

## Operations and Fixes

- **Stopping an agent ends its whole process tree** (SIGTERM, then SIGKILL after 3 s), and agents a crashed server left behind are ended at the next start. ([#96](https://github.com/foolzzz/looper/pull/96))
- **The supervisor never gives up** on the Manager, the TaskRouter or the WorkerPool: restarts back off from 1 s to 5 minutes, and `/api/status` and the Dashboard show a crash loop. ([#138](https://github.com/foolzzz/looper/pull/138))
- **Every task is reachable:** `GET /api/tasks` pages with `limit` and `before`, filters by status and counts every task; the Tasks page has Load more. ([#141](https://github.com/foolzzz/looper/pull/141))
- **A Worker's files found in another worktree or a commit** of its run no longer fail its step. ([#151](https://github.com/foolzzz/looper/pull/151), fixes [#148](https://github.com/foolzzz/looper/issues/148))
- A restarted task no longer ends at once from a cancel its previous Planner left unread ([#146](https://github.com/foolzzz/looper/pull/146)); Claude Code profiles on an alias are priced ([#155](https://github.com/foolzzz/looper/pull/155)); smaller fixes on the task page and the Roles page ([#152](https://github.com/foolzzz/looper/pull/152), [#156](https://github.com/foolzzz/looper/pull/156)).

## Breaking Changes

1. **The dashboard's names in storage and the API, with no aliases.** `/api/agent-configs` is `/api/roles`; `POST /api/agents` and `PUT`/`DELETE /api/agents/:id` are `/api/agent-profiles`, answering with `profile`; a settings layer's `agent` is `profile_id` and its effective `agent` is `profile`; a task's `agent_overrides` is `profile_overrides`; the registry lists `profiles`. `POST /api/runtimes` and `PUT`/`DELETE /api/runtimes/:id` are gone (404); runtimes are built in. `looper config export` writes `looper-config/v2`; v1 files still import. ([#75](https://github.com/foolzzz/looper/pull/75), [#76](https://github.com/foolzzz/looper/pull/76))
2. **Settings fields that moved.** A settings layer refuses `effort` (400): the effort is the Agent Profile's, and the upgrade adds profiles named like `claude-code/opus · xhigh` where a layer had one. `PUT /api/roles/:role` refuses `max_concurrency` (400): concurrency is a layer setting now. A settings layer's or a provider's `env` refuses the agent teams variable (400). `/api/agent-settings` no longer lists `limits.effort_levels`. ([#81](https://github.com/foolzzz/looper/pull/81), [#83](https://github.com/foolzzz/looper/pull/83), [#91](https://github.com/foolzzz/looper/pull/91))
3. **The Manager's tasks wait to be started, and its JSON actions are gone.** A task the Manager creates is Ready until the user says start, presses Start or calls `POST /api/tasks/:id/start`; a new project needs the user's confirmation. The Manager acts only through its platform tools: an edited Manager role prompt that still asks for task JSON creates nothing (an unedited one is migrated). ([#88](https://github.com/foolzzz/looper/pull/88), [#129](https://github.com/foolzzz/looper/pull/129))
4. **A restart continues.** Start on a stopped, failed or cancelled task, `POST /api/tasks/start` and the Manager's `restart` continue from the saved plan, with one extra Planner turn; send `"start_over": true`, or press Start over, to plan anew. ([#146](https://github.com/foolzzz/looper/pull/146), [#147](https://github.com/foolzzz/looper/pull/147))
5. **Concurrency per project, higher by default.** The machine-wide caps of 3 tasks and 4 Worker and Reviewer runs, and the 4 Workers per task, are gone. Each project runs up to 8 tasks, 16 Workers and 8 Reviewers at once unless its layers say otherwise, and nothing limits the sum across projects, so on default settings more agents run and spend at once. ([#81](https://github.com/foolzzz/looper/pull/81), [#139](https://github.com/foolzzz/looper/pull/139))
6. **Claude Code agent teams are on by default.** The upgrade turns `agent_teams` on for every Claude Code Agent Profile, the built-in `claude-code/opus` included, and new Claude Code profiles have it: Manager, Worker and Reviewer runs may spawn in-process teammates, which add spend and do not get Looper's system prompt layers. Planners never get them. ([#80](https://github.com/foolzzz/looper/pull/80))
7. **Lark is configured through lark-cli.** `app_id_env` and `app_secret_env` are dropped from the stored configuration and imports; the app comes from lark-cli's profile (empty: its active one), and the channel does not start unless lark-cli is signed in, the app has a bot and the allowlist belongs to that app. Replies are Markdown posts. ([#102](https://github.com/foolzzz/looper/pull/102), [#105](https://github.com/foolzzz/looper/pull/105))
8. **Renamed and reshaped records.** The journal kind `user_instruction` is `supplement`; `result_summary` of a completed task is a Markdown summary with headings, and a failed task's `error` and a stopped task's `result_summary` are a closing note; `/api/status` drops each agent's `max_restarts`, `restart_count` counts restarts in a row, and its `tasks` count every task; the Manager's `max_restarts_exceeded` is `crash_looping`. ([#89](https://github.com/foolzzz/looper/pull/89), [#114](https://github.com/foolzzz/looper/pull/114), [#126](https://github.com/foolzzz/looper/pull/126), [#138](https://github.com/foolzzz/looper/pull/138))
9. **Input refused that was accepted.** A task requirement over 32,000 characters is refused (it was clipped at 8,000); `GET /api/tasks` answers 400 to a bad `limit`, an unknown `status` or an unknown `before`; an invalid `LOOPER_PUBLIC_URL` stops `looper serve` from starting. ([#122](https://github.com/foolzzz/looper/pull/122), [#139](https://github.com/foolzzz/looper/pull/139), [#141](https://github.com/foolzzz/looper/pull/141))

**Also changed, with cost or authority effects.** The Manager can now, from any chat it serves, create and update projects and Agent Profiles, register providers without their keys, change settings layers, install catalog items and enable or disable schedules without asking; deletions, the shared defaults, concurrency of a project or role and higher spend caps wait for the user's confirmation ([#129](https://github.com/foolzzz/looper/pull/129), [#157](https://github.com/foolzzz/looper/pull/157), [#160](https://github.com/foolzzz/looper/pull/160)). Every Planner gets an MCP server and four tools, always on: it can change its own task's and its project's concurrency without asking, and, once a project lists Agent Profiles, move its Workers and Reviewers to any of them, a more expensive one included ([#155](https://github.com/foolzzz/looper/pull/155)). Without `looper serve --verbose`, httpx and httpcore log only warnings, and anything shaped like a Telegram bot token in a log line is masked ([#150](https://github.com/foolzzz/looper/pull/150)). Stopping an agent sends SIGTERM to its whole process tree before SIGKILL, and agents run in sessions of their own, so a Ctrl-C reaches only the server ([#96](https://github.com/foolzzz/looper/pull/96)). Codex agents read `CLAUDE.md` where there is no `AGENTS.md`, OMP agents outside git get it in their system prompt, and Claude Code agents no longer see an `AGENTS.md` above the repository ([#97](https://github.com/foolzzz/looper/pull/97)). The Planner's `planning`, `verifying` and `stopping` count as active, so such a task must be stopped before it is deleted and is resumed or marked stopped at startup ([#89](https://github.com/foolzzz/looper/pull/89)). `GET /api/chat/messages` returns a session's newest 200 messages instead of its oldest ([#109](https://github.com/foolzzz/looper/pull/109)). The scheduler claims a due schedule with `FOR NO KEY UPDATE SKIP LOCKED`, so a notification being written no longer makes a fire slip by 15 s ([#154](https://github.com/foolzzz/looper/pull/154)). Commits to the repository no longer need a sign-off ([#158](https://github.com/foolzzz/looper/pull/158)).

## Upgrading from v2.6.0

1. **Install with `install.sh`.** It installs the latest release wheel with uv, pipx or pip, as for v2.6.0.
2. **Keep the first-start backup possible.** The schema changes in this release, so the first start writes a `pg_dump` backup before migrating, as v2.6.0 does: keep a `pg_dump` of at least the server's major version on `PATH` (or `LOOPER_PG_DUMP`, or `LOOPER_BACKUP_CMD`). `looper serve --skip-backup` migrates without one.
3. **Start once.** The first start renames `agent_configs`, `agents` and `task_agent_overrides` to `role_configs`, `agent_profiles` and `task_profile_overrides`, moves layer efforts onto Agent Profiles, turns on agent teams for Claude Code profiles, drops `role_configs.max_concurrency` and the Lark app variables, drops runtimes registered by hand that no profile uses, converts `user_instruction` journal entries to supplements, adds the schedule and task tables, and moves recommended Manager and Planner prompts you did not edit to the new texts.
4. **Decide on agent teams.** If you do not want teammates, untick "Agent teams" on your Claude Code profiles in Settings → Agent Profiles; for the read-only built-in `claude-code/opus`, create the same profile with it off and select it in Roles → Shared defaults.
5. **Set the concurrency you can afford.** Each project now runs up to 8 tasks, 16 Workers and 8 Reviewers at once. Lower them in Settings → Roles (for every project) or on a project's Agent Profiles tab, and consider a project spend cap per task.
6. **Telegram.** If the channel ran on v2.6.0, its log holds the bot token: revoke it in BotFather, paste the new one into Settings → Channels (or your environment variable), restart, and delete the old `serve.log` under the runtime root's `logs/`.
7. **Lark.** Install lark-cli 1.0.97 or later, sign it in with the app whose bot you use, optionally name its profile in Settings → Channels, and restart; the app ID variable is no longer read.
8. **Scripts against the API.** Move to `/api/roles` and `/api/agent-profiles` and the `profile_id` and `profile` fields, drop `effort` from layer updates and `max_concurrency` from role updates, start Manager-created tasks with `POST /api/tasks/:id/start`, and send `"start_over": true` where you relied on a restart planning anew.
9. **An edited Manager prompt.** If you edited the Manager's role prompt, compare it with the recommended one in Settings → Roles: the Manager now acts through tools, and prose asking for task JSON does nothing.
10. **Check.** `looper doctor`, and `looper service status` for the service.

```bash
curl -fsSL https://raw.githubusercontent.com/foolzzz/looper/main/install.sh | bash
looper doctor                     # pg_dump included
looper serve                      # first start: backs up, then migrates
  # Or, with the service:
looper service restart && looper service status
  # Then, in another shell: which Agent Profiles have agent teams on
curl -s http://127.0.0.1:8767/api/registry | python3 -c 'import json, sys; [print(p["name"], p["agent_teams"]) for p in json.load(sys.stdin)["profiles"]]'
```

**Rollback to v2.6.0.** Stop Looper (`looper service uninstall` if you installed the service), recreate the database empty and restore the pre-migration backup the first start logged (`pg_restore --no-owner --dbname "$LOOPER_DATABASE_URL" FILE`): the migration renames tables and drops columns that v2.6.0 needs. Then install the v2.6.0 wheel, for example `uv tool install --force "looper @ https://github.com/foolzzz/looper/releases/download/v2.6.0/looper-2.6.0-py3-none-any.whl"`. `install.sh` always installs the latest release, so it cannot roll back. v2.6.0 reads the Telegram token only from its environment variable and the Lark app ID from its variable, so set them again, and it knows nothing of schedules, which stop.

## Optional Capability Activation & Use

### Scheduled tasks

**Activation:** Off until you create and enable a schedule; the scheduler runs inside every `looper serve` but a new schedule starts disabled. On a project's Schedules tab ("New schedule"), or with `POST /api/projects/PROJECT_ID/schedules` (`name`, `cron`, `requirement`, and `work_dir` when the project has no default directory; optionally `timezone`, `overlap`, `max_parallel_runs`, `catch_up`, `run_timeout_seconds`, `run_budget_usd`, `daily_budget_usd`, `gate_command`, `gate_timeout_seconds`, `notify`, `notify_target` and `profile_overrides`), then enable it with its switch or `PUT /api/schedules/SCHEDULE_ID` with `{"enabled": true}`. Its next fire counts from that moment. A `notify_target` must be a person already on the Telegram or Lark sender allowlist.

**Validation:** `POST /api/schedules/preview` checks a rule and lists its next fire times; `GET /api/schedules/SCHEDULE_ID` shows `enabled` and `next_fire_at`; Run now (`POST /api/schedules/SCHEDULE_ID/run`) fires once, also while disabled, and `GET .../runs` and `GET .../notifications` show each run and message. The startup log says `scheduler started: checks the schedules every 15 s`.

**Disable / rollback:** Turn the schedule off (`{"enabled": false}`): no more fires. This does not stop a task already running (stop it from its page or with `POST /api/tasks/stop`). `DELETE /api/schedules/SCHEDULE_ID` removes the schedule with its runs and messages, also while a run is in progress: that task finishes as any task does, a queued run never starts, a gate still running starts no task, and the schedule's tasks stay. A project with schedules cannot be deleted until they are.

**Authority boundary:** Enabling a schedule approves every task it starts: unattended, paid runs of the Planner, Workers and Reviewers with every tool and no permission prompts, up to `max_parallel_runs` (at most 10) at once under `parallel`, limited only by the project's concurrency, `run_budget_usd` (else the project's per-task cap), `daily_budget_usd` if set, and `run_timeout_seconds`. The daily budget counts the runs fired since the server's local midnight, is checked when a firing is due and never stops a run in progress. A gate command is any shell command, run as your user in the work directory with the server's environment on every firing, as often as every minute; its output goes into the task's requirement for the models to read. Messages go only to the one allowlisted person a schedule names, through the bot. Schedules store no secrets; the configuration export leaves them out, and the Manager can list, enable, disable and delete them (deleting after your confirmation) but not create or edit them.

**Docs:** https://github.com/foolzzz/looper/blob/v2.7.0/docs/architecture/agent-system.md#schedules-tasks-on-a-time-rule

```bash
curl -s -X POST http://127.0.0.1:8767/api/schedules/preview -H 'Content-Type: application/json' \
  -d '{"cron": "0 9 * * 1-5", "timezone": "America/Los_Angeles"}'
  # Create (disabled), enable, fire once and read the runs back:
curl -s -X POST http://127.0.0.1:8767/api/projects/PROJECT_ID/schedules -H 'Content-Type: application/json' \
  -d '{"name": "weekday-deps", "cron": "0 9 * * 1-5", "timezone": "America/Los_Angeles",
       "requirement": "Check the dependencies for updates and report what changed.",
       "run_timeout_seconds": 3600, "run_budget_usd": 2, "daily_budget_usd": 5, "notify": "alerts"}'
curl -s -X PUT http://127.0.0.1:8767/api/schedules/SCHEDULE_ID -H 'Content-Type: application/json' -d '{"enabled": true}'
curl -s -X POST http://127.0.0.1:8767/api/schedules/SCHEDULE_ID/run
curl -s 'http://127.0.0.1:8767/api/schedules/SCHEDULE_ID/runs?limit=20&skips=hide'
  # Disable, or delete (its tasks stay):
curl -s -X PUT http://127.0.0.1:8767/api/schedules/SCHEDULE_ID -H 'Content-Type: application/json' -d '{"enabled": false}'
curl -s -X DELETE http://127.0.0.1:8767/api/schedules/SCHEDULE_ID
```

### Step workspaces

**Activation:** Per project, `shared` by default. Set the project's `step_workspaces` to `worktree` (Project → Settings → Execution, "Steps that run at the same time", or `PUT /api/projects/PROJECT_ID`). It applies when the task directory is a git checkout on a branch with at least one commit, git is 2.40 or later and no merge, rebase, cherry-pick, revert or bisect is in progress, and only to steps that run while other steps of their task do; a checkout that fails these conditions runs its steps one at a time, and a directory outside git is unaffected.

**Validation:** `GET /api/projects` shows `step_workspaces: "worktree"`. A task with parallel steps logs where it started ("Step workspaces: the task starts with BRANCH at SHA"), each step's worktree and branch (`looper/TASK_ID/...`), and each merge ("Step KEY merged into BRANCH"); the repository gets merge commits titled `looper: merge step ...` by `Looper <looper@localhost>`, with `Looper-Task` and `Looper-Step` trailers.

**Disable / rollback:** Set `step_workspaces` back to `shared` (or `null`); rounds dispatched afterwards share the task directory again. `git reset START_COMMIT` (the commit the activity names) undoes a task's commits and keeps its changes as uncommitted work, and `git revert -m 1 MERGE_COMMIT` undoes one step. A completed task's worktrees and branches are removed; a failed, stopped or cancelled task keeps its unmerged ones until it is started over or deleted, and the server removes other leftovers at startup.

**Authority boundary:** Looper itself commits on your checked-out branch: before a round of parallel steps, a checkpoint of every pending change in the task directory that git does not ignore, your own uncommitted work included; what a Worker left uncommitted; and one merge commit per accepted step. These commits are unsigned and run no hooks, so commit hooks and signing policies do not apply to them; a Worker's own commits keep your identity, signing and hooks. Looper never pushes, switches branches or rewrites commits, and a merge that cannot be made leaves the task directory untouched and goes to the Planner. Worktrees live under the runtime root's `worktrees/`; files git ignores, such as `.env` or `node_modules`, are not in them. It adds no model cost.

**Docs:** https://github.com/foolzzz/looper/blob/v2.7.0/docs/architecture/agent-system.md#step-workspaces

```bash
curl -s -X PUT http://127.0.0.1:8767/api/projects/PROJECT_ID -H 'Content-Type: application/json' \
  -d '{"step_workspaces": "worktree"}'
curl -s http://127.0.0.1:8767/api/projects | python3 -m json.tool | grep '"step_workspaces"'
  # After a task with parallel steps, in the task directory:
git log --merges --format='%h %an %s' | grep 'looper: merge step'
git worktree list
  # Turn it off:
curl -s -X PUT http://127.0.0.1:8767/api/projects/PROJECT_ID -H 'Content-Type: application/json' \
  -d '{"step_workspaces": "shared"}'
```

### Planner Agent Profile choice

**Activation:** Per project, off by default: a project's list of Agent Profiles the Planner may choose is empty, and with an empty list every choice is refused. Add profiles on the project's Agent Profiles tab ("Profiles the Planner may choose") or with `PUT /api/projects/PROJECT_ID/allowed-profiles` (`{"profile_ids": [...]}`, the whole list, by id or name; each profile must be able to run the Worker or the Reviewer). The Manager's `looper_settings` can add and remove entries too. A Planner then calls `looper_task_profile_set` to run its task's Workers or Reviewers on one of them, for the rest of the task or for one step.

**Validation:** `GET /api/projects/PROJECT_ID/allowed-profiles` lists the profiles. After a choice, `GET /api/tasks/TASK_ID` shows the Worker's profile with the source `planner_task` under `agents.roles`, the journal has a `profile_choice` entry with the Planner's reason (Findings on the task page), and the run history names the profile.

**Disable / rollback:** Empty the list (`{"profile_ids": []}`): what the project's Planners chose of a removed profile is dropped in the same transaction, and later runs fall back to the user's choice for the task, then the settings layers; runs already started keep their profile. To pin one task instead, choose its profile yourself (`PUT /api/tasks/TASK_ID/agents`): the user's choice wins and the Planner's attempt for that role is refused. A listed profile cannot be deleted until it is taken off the list.

**Authority boundary:** Once a profile is listed, the project's Planners may move their own task's Workers or Reviewers to it without asking, a more expensive one included; only the project's per-task spend cap, unset by default, bounds the cost. A Planner never changes its own profile, acts only on its own task and only in turns Looper sends it, with a token that ends when that Planner stops or its task ends. The concurrency tools are not behind this list: every Planner can change its task's and its project's concurrency without asking (see Breaking Changes). The list shows runtime, model, effort and price, never provider keys.

**Docs:** https://github.com/foolzzz/looper/blob/v2.7.0/docs/architecture/agent-system.md#a-tasks-planners-tools

```bash
curl -s http://127.0.0.1:8767/api/projects/PROJECT_ID/allowed-profiles
curl -s -X PUT http://127.0.0.1:8767/api/projects/PROJECT_ID/allowed-profiles -H 'Content-Type: application/json' \
  -d '{"profile_ids": ["PROFILE_ID"]}'
  # After the Planner chose, what the task's Workers run and why:
curl -s http://127.0.0.1:8767/api/tasks/TASK_ID | python3 -m json.tool | grep -A6 '"worker"'
  # Turn it off again:
curl -s -X PUT http://127.0.0.1:8767/api/projects/PROJECT_ID/allowed-profiles -H 'Content-Type: application/json' \
  -d '{"profile_ids": []}'
```

### Codex ChatGPT login

**Activation:** Off until a profile uses it. With Codex on the server's `PATH` (`looper serve` registers the built-in runtime `rt-codex`, or Re-detect in Settings → Agent Runtimes finds it), run `codex login` with ChatGPT on the server's machine, create an Agent Profile on the Codex runtime with the built-in provider `prov-codex-login` (Settings → Agent Profiles, provider `codex-login`, or `POST /api/agent-profiles`) and select it for a role, a project or a task.

**Validation:** The Agent Profile form shows the login's state; `looper doctor` runs a "Codex login" check while a profile uses it; `GET /api/status` has the `codex_login` check and `GET /api/registry` the provider's `login` state; each run records its profile.

**Disable / rollback:** Select another profile on that layer (or `null` to inherit) and delete the profile (409 while something selects it). When a run left a copy of the login, Looper deletes the copy, puts the link back and stops using the login until you have checked `codex login status` and chosen "Use the login again" (`DELETE /api/providers/prov-codex-login/login-problem`).

**Authority boundary:** It runs Codex on your ChatGPT plan's quota; Looper records an equivalent cost at its built-in prices, not money spent. The login stays in your own Codex login file: each run's isolated Codex home links to it, never copies it, and Looper stores no token. The agent's shell commands get a Codex home without the login, so a `codex logout` an agent runs cannot revoke yours, and every run is checked afterwards for a copy. Codex still runs without approvals or sandbox, with your user's access, so an agent could read the login file by its path.

**Docs:** https://github.com/foolzzz/looper/blob/v2.7.0/docs/architecture/agent-system.md#runtimes-llm-providers-and-agent-profiles

```bash
codex login status
curl -s -X POST http://127.0.0.1:8767/api/agent-profiles -H 'Content-Type: application/json' \
  -d '{"name": "codex/chatgpt", "runtime_id": "rt-codex", "provider_id": "prov-codex-login", "model": "gpt-6.1-sol"}'
curl -s -X PUT http://127.0.0.1:8767/api/agent-settings/roles/worker -H 'Content-Type: application/json' \
  -d '{"profile_id": "PROFILE_ID"}'
looper doctor
  # Undo:
curl -s -X PUT http://127.0.0.1:8767/api/agent-settings/roles/worker -H 'Content-Type: application/json' \
  -d '{"profile_id": null}'
curl -s -X DELETE http://127.0.0.1:8767/api/agent-profiles/PROFILE_ID
```

### Telegram and Lark channels

**Activation:** Off by default, and changed in this release. Telegram: in Settings → Channels, paste the bot token from BotFather into the Bot token field (or keep it in the environment variable the setting names), list the allowed numeric user IDs, enable the channel and restart `looper serve` or the service. Lark: install lark-cli 1.0.97 or later and sign it in with an app that has a bot (and as a user, for the people search), optionally name the lark-cli profile, add senders by name or email, enable the channel and restart; for group chats, add the bot to the group.

**Validation:** The startup line `agent system running on ... (channels=...)` lists the channels that started; `GET /api/channel-configs` shows each channel's `start_problem` (`null` when it can start) and Telegram's `has_bot_token`; `GET /api/channels/lark/status` shows the Lark bot or why it does not start, and the senders it refused. A message from a listed sender gets a reaction, then one status message edited in place, then the answer; a task asked for there ends with a notice in the same chat.

**Disable / rollback:** Set `enabled` to `false` and restart. Remove a stored Telegram token with `"bot_token": null`. On a downgrade to v2.6.0, Telegram reads the token from its environment variable only and Lark needs its app ID variable again.

**Authority boundary:** Every allowlisted sender (Telegram user IDs; Lark open_ids, bound to the bot's app) talks to the Manager, which runs any command on this machine without permission prompts and can now change Looper's configuration through its tools; confirmations are per chat, so in a Lark group the next listed sender's message is the one that confirms. Lark group chats answer only @-mentions of the bot; their turns are stored, and replies, progress and the task-end notice go to the group. Telegram group messages are not stored. The Telegram token is stored in the database apart from the configuration, never returned by the API or exported; Lark's credentials stay in lark-cli. The people search runs as the signed-in lark-cli user and shows names, emails and departments on the dashboard.

**Docs:** https://github.com/foolzzz/looper/blob/v2.7.0/docs/architecture/agent-system.md#channels

curl -s -X PUT http://127.0.0.1:8767/api/channel-configs/channel-telegram -H 'Content-Type: application/json' \

curl -s 'http://127.0.0.1:8767/api/channels/lark/people?q=NAME_OR_EMAIL'

looper service restart   # or restart looper serve
curl -s http://127.0.0.1:8767/api/channel-configs
curl -s http://127.0.0.1:8767/api/channels/lark/status

## Known Limitations

- The `loopx` alias, the `~/.loopx` link and the `LOOPX_*` fallback are still in this release, although v2.6.0 said they would go; a later release removes them.
- The HTTP API still has no authentication apart from the agents' own tool routes; it refuses other web pages, but any local process can call it. Keep the default `127.0.0.1` bind.
- The Manager's tiers limit its tools, not the Manager: it still has a shell without permission prompts, and "never say an operation ran unless it did" is a prompt rule. Confirmations are kept in memory and per chat; a restart or `/new` drops them.
- A Planner's change of its project's concurrency is guided by its prompt, not enforced, and is told only in the chat of a task from Telegram or Lark.
- Agent teams: a teammate's tokens reach the run's cost and the soft per-run cap only through a result's totals, teammates do not get Looper's system prompt layers, and the feature was verified on Claude Code 2.1.285 only.
- There is no machine-wide concurrency ceiling, and a provider's `max_concurrency` is still stored but not enforced.
- Schedules: the Manager cannot create or edit them, there is no CLI and the configuration export leaves them out; a schedule notifies one person, never a group; the daily budget is checked only when a firing is due; a run's timeout counts while it waits for room under the project's limit.
- Step workspaces: only steps that run in parallel get a worktree, and files git ignores (`.env`, `.venv`, `node_modules`) are not in them; the task page does not show workspaces yet. A step whose files were found only on another branch can pass the result check and still fail its review, which looks at the task directory.
- Telegram has been tested against stand-ins only; Lark group chats only with a stand-in lark-cli and dry runs. How either renders the Markdown of notices is unverified.
- Old `serve.log` files that hold a Telegram token are not scrubbed; output that bypasses Python logging is not masked.

### 升级决策

**谁需要升级：**所有运行 v2.6.0 的用户。升级前，用脚本调用 HTTP API 的用户请先读“破坏性变更”，因为路由和字段改了名且不保留别名；在 v2.6.0 上开过 Telegram 渠道的用户，请准备更换 bot token。

**解决了什么：**v2.6.0 只能在有人提出时才运行任务，每次重启都丢掉任务的计划，不能修改运行中任务的需求，整台机器最多 3 个任务、4 个运行，Manager 一写出任务 JSON 就开始执行，Manager 的操作要从它的文字里解析，任务列表最多只能看到 50 个，停止 agent 后它启动的命令仍在运行，崩溃的 agent 重启 3 次后就不再管，还会把 Telegram bot token 写进日志。v2.7.0 新增定时任务、接着做的重启、任务变更与进度、能并行并选择 agent 的 Planner、带确认的类型化 Manager 工具、按项目和按任务的并发、带 effort、agent teams 和 Codex ChatGPT 登录的 Agent Profile，以及更完整的 Telegram 和飞书渠道，并修复了其余问题。

**是否有破坏性变更：**有。按 dashboard 名称改名的路由和字段（`/api/roles`、`/api/agent-profiles`、`profile_id`）不保留别名，运行时注册路由已删除；配置层拒绝 `effort`，角色拒绝 `max_concurrency`；Manager 建的任务需要手动开始，它的 JSON 操作已移除；重启从保存的计划继续；并发按项目限制，默认值更高；Claude Code agent teams 默认开启；飞书渠道改用 lark-cli profile，不再读取 app ID 变量；日志类型 `user_instruction` 改为 `supplement`；超过 32,000 字的需求会被拒绝。详见“破坏性变更”和“从 v2.6.0 升级”。

### 定时任务

- **定时任务。** 定时任务属于项目：名称、IANA 时区下的 5 段 cron 规则、每次运行所建任务的需求、工作目录、重叠策略（`skip`、`queue`，或 `parallel` 且最多 `max_parallel_runs` 个）、补跑策略、运行超时、每次运行所建任务的花费上限和各角色的 Agent Profile。两次触发至少间隔 5 分钟，有前置检查时可到 1 分钟。新建的定时任务处于停用状态，启用即表示批准它发起的任务。`looper serve` 内的调度器每 15 秒检查一次，认领到期定时任务的行，同一数据库上的两个服务只会触发一次；触发后建一个以定时任务名和触发时间为标题的任务，需求末尾附上代码生成的运行上下文。（[#98](https://github.com/foolzzz/looper/pull/98)、[#125](https://github.com/foolzzz/looper/pull/125)、[#140](https://github.com/foolzzz/looper/pull/140)、[#154](https://github.com/foolzzz/looper/pull/154)）
- **前置检查、未完成的输入和每日预算。** 每次运行前在工作目录执行前置检查命令；没有输出就跳过这一轮，不花钱；失败算一次失败；有输出则作为任务的输入。没做完的那一轮的输出只交给下一轮一次。设了每日预算时，当天的运行花到上限后跳过后续触发。重复的跳过记在同一条运行上，所以每分钟一次的前置检查只在结果变化时才多一行。`parallel` 下运行可以重叠，前置检查不会；前置检查的环境里带有这次运行的 id 和超时。（[#101](https://github.com/foolzzz/looper/pull/101)、[#132](https://github.com/foolzzz/looper/pull/132)、[#136](https://github.com/foolzzz/looper/pull/136)、[#140](https://github.com/foolzzz/looper/pull/140)）
- **通知与告警。** `notify` 可选 `failures`（默认）、`alerts`、`always` 或 `never`，发给 Telegram 或飞书白名单里的一个人。连续 3 次失败、3 个周期（至少 15 分钟、至多 24 小时）没有成功，各发一次告警、恢复时各发一次；没有新内容的前置检查算健康；“长时间没有成功”从最近一次启用或改规则起算，有运行进行时暂停计算。（[#101](https://github.com/foolzzz/looper/pull/101)、[#118](https://github.com/foolzzz/looper/pull/118)、[#134](https://github.com/foolzzz/looper/pull/134)、[#143](https://github.com/foolzzz/looper/pull/143)、[#144](https://github.com/foolzzz/looper/pull/144)、[#156](https://github.com/foolzzz/looper/pull/156)）
- **在 dashboard 上。** 项目的 Schedules 标签页可编辑定时任务并预览接下来的触发时间；Schedules 页列出所有项目的定时任务，可按项目和状态筛选；单个定时任务的页面显示设置、告警、今日花费和运行历史，默认隐藏常规跳过。每个页面都能删除定时任务，运行进行中也能安全删除：任务照常完成，排队的运行不再开始，已有的任务保留。（[#130](https://github.com/foolzzz/looper/pull/130)、[#131](https://github.com/foolzzz/looper/pull/131)、[#135](https://github.com/foolzzz/looper/pull/135)、[#160](https://github.com/foolzzz/looper/pull/160)）

### 任务与 Planner

- **重启接着做，从头再来要显式选择。** 对停止、失败或取消的任务点 Start，调用 `POST /api/tasks/start` 或 Manager 的 `restart`，都会保留已验收的步骤和已合并的改动，把没做完的步骤连同重试次数、反馈和 worktree 放回未开始，再给 Planner 一个 `[RESTART]` 回合，由它决定追加步骤或重新规划。Start over（行内确认）、`"start_over": true` 或 Manager 的 `start_over`（需确认）会删掉步骤并重新规划，这是以前每次重启的做法。（[#146](https://github.com/foolzzz/looper/pull/146)、[#147](https://github.com/foolzzz/looper/pull/147)、[#152](https://github.com/foolzzz/looper/pull/152)）
- **任务变更。** 发给任务 Planner 的聊天消息存为补充说明；`PUT /api/tasks/:id/requirement` 修改需求并保留每个版本；Planner 在一轮里收到所有等待中的变更，回复应用后才算送达；`[CHAT]` 可以 `replan`；Worker 和 Reviewer 都能看到补充说明。（[#126](https://github.com/foolzzz/looper/pull/126)）
- **进度与最终总结。** 每次决策带进度说明，完成任务的决策带最终总结（交付了什么、怎么用、怎么验证、遗留问题），失败或停止的任务由代码写收尾说明；任务页的 Progress 栏显示这些内容。（[#114](https://github.com/foolzzz/looper/pull/114)）
- **会并行的 Planner。** 推荐提示词要求 Planner 只为用到结果的步骤加依赖、先定接口再并行实现、在已验收的基础上重新规划。计划不再限步骤数，就绪的步骤一次全部派出，由项目和任务的上限决定同时跑几个；每步重试次数是项目设置（`max_step_retries`，默认 2）；需求最长 32,000 字。（[#104](https://github.com/foolzzz/looper/pull/104)、[#137](https://github.com/foolzzz/looper/pull/137)、[#139](https://github.com/foolzzz/looper/pull/139)）
- **步骤工作目录（需开启）。** 项目的 `step_workspaces` 设为 `worktree` 后，同时运行的步骤各在自己的 git worktree 和分支上做，验收后每步一个合并提交合回，合不进去时交给 Planner。（[#127](https://github.com/foolzzz/looper/pull/127)）
- **Planner 的工具。** 每个 Planner 拿到只作用于本任务的 MCP 服务：可以从项目允许的列表（默认为空）里为 Worker 或 Reviewer 选 Agent Profile，可以调整任务或项目的并发，每次改动都记入任务日志。（[#155](https://github.com/foolzzz/looper/pull/155)）
- **任务自己的 agent 和上限。** `PUT /api/tasks/:id/agents` 和任务页的 Agents 区块可以按角色设置任务的 Agent Profile 和 Worker、Reviewer 上限，已结束的任务在重启前也能改。（[#145](https://github.com/foolzzz/looper/pull/145)、[#152](https://github.com/foolzzz/looper/pull/152)）
- **Pipeline 标签页**按计划的依赖关系画图，被丢弃的步骤以虚线保留。（[#146](https://github.com/foolzzz/looper/pull/146)）
- **任务有标题**，来自 Manager 的工具或定时任务，显示在列表、标题和通知里。（[#124](https://github.com/foolzzz/looper/pull/124)、[#125](https://github.com/foolzzz/looper/pull/125)）

### Manager

- **基于 MCP 的平台工具。** Manager 不再在回复里写 JSON 操作（[#120](https://github.com/foolzzz/looper/pull/120) 曾让它的解析更严格），而是调用 `looper` MCP 工具：总览、任务（新建、开始、停止、重启、从头再来、取消、补充说明、修改）、并发、项目、Agent Profile、provider（不含密钥）、配置层和可选 Profile 列表、能力目录、花费和定时任务。read 类在任何回合都能用，write 类只在回答用户消息的回合里能用，high 类（新建项目、取消任务或从头再来、删除、改共用默认、改项目或角色的并发、提高或取消花费上限）要用户在 10 分钟内的下一条消息里确认。每次调用都有记录并显示在任务页；工具不可用时，用户会被告知什么都没有执行。（[#129](https://github.com/foolzzz/looper/pull/129)、[#145](https://github.com/foolzzz/looper/pull/145)、[#157](https://github.com/foolzzz/looper/pull/157)、[#160](https://github.com/foolzzz/looper/pull/160)）
- **待开始的任务。** Manager 建的任务先处于 Ready，回复里附上配置块（Agent Profile、effort、评审、上限、并发）并询问是否开始；在 Tasks 页或任务页点 Start，或调用 `POST /api/tasks/<id>/start` 开始。新项目要用户确认后才会创建。（[#88](https://github.com/foolzzz/looper/pull/88)）
- **只回答刚收到的消息。** 每条消息前有一行 `Channel:`，推荐提示词要求 Manager 只回答这条消息；它的回复只取这一轮的最终回答，不带调用工具前的过程叙述。（[#112](https://github.com/foolzzz/looper/pull/112)、[#119](https://github.com/foolzzz/looper/pull/119)）
- **`/new`** 在任何渠道都能开启新的 Manager 会话。（[#73](https://github.com/foolzzz/looper/pull/73)）

### 破坏性变更

1. **存储和 API 使用 dashboard 的名称，不保留别名。** `/api/agent-configs` 改为 `/api/roles`；`POST /api/agents` 和 `PUT`/`DELETE /api/agents/:id` 改为 `/api/agent-profiles`，返回 `profile`；配置层的 `agent` 改为 `profile_id`，生效值 `agent` 改为 `profile`；任务的 `agent_overrides` 改为 `profile_overrides`；registry 列出 `profiles`。`POST /api/runtimes` 和 `PUT`/`DELETE /api/runtimes/:id` 已删除（404），运行时改为内置。`looper config export` 写出 `looper-config/v2`，v1 文件仍可导入。（[#75](https://github.com/foolzzz/looper/pull/75)、[#76](https://github.com/foolzzz/looper/pull/76)）
2. **挪了位置的配置字段。** 配置层拒绝 `effort`（400）：effort 属于 Agent Profile，升级时在原来设了 effort 的地方新建形如 `claude-code/opus · xhigh` 的 Profile。`PUT /api/roles/:role` 拒绝 `max_concurrency`（400）：并发现在是配置层的设置。配置层或 provider 的 `env` 拒绝 agent teams 变量（400）。`/api/agent-settings` 不再列出 `limits.effort_levels`。（[#81](https://github.com/foolzzz/looper/pull/81)、[#83](https://github.com/foolzzz/looper/pull/83)、[#91](https://github.com/foolzzz/looper/pull/91)）
3. **Manager 建的任务需要手动开始，它的 JSON 操作已移除。** Manager 建的任务保持 Ready，直到用户说开始、点 Start 或调用 `POST /api/tasks/:id/start`；新项目需要用户确认。Manager 只通过平台工具操作：改过的 Manager 角色提示词如果仍要求输出任务 JSON，将什么都建不出来（未改过的会自动迁移）。（[#88](https://github.com/foolzzz/looper/pull/88)、[#129](https://github.com/foolzzz/looper/pull/129)）
4. **重启改为接着做。** 对停止、失败或取消的任务点 Start、调用 `POST /api/tasks/start` 或 Manager 的 `restart`，都从保存的计划继续，多一轮 Planner；要重新规划，请发送 `"start_over": true` 或点 Start over。（[#146](https://github.com/foolzzz/looper/pull/146)、[#147](https://github.com/foolzzz/looper/pull/147)）
5. **并发按项目限制，默认更高。** 整机 3 个任务、4 个 Worker 与 Reviewer 运行的上限，以及每个任务 4 个 Worker 的上限都已去掉。除非配置层另有设置，每个项目最多同时运行 8 个任务、16 个 Worker 和 8 个 Reviewer，所有项目加起来没有总上限，所以默认设置下会有更多 agent 同时运行和花钱。（[#81](https://github.com/foolzzz/looper/pull/81)、[#139](https://github.com/foolzzz/looper/pull/139)）
6. **Claude Code agent teams 默认开启。** 升级时为每个 Claude Code Agent Profile（包括内置的 `claude-code/opus`）打开 `agent_teams`，新建的 Claude Code Profile 也默认开启：Manager、Worker 和 Reviewer 的运行可以拉起进程内的队友，这会增加花费，且队友拿不到 Looper 的 system prompt 各层。Planner 永远不开。（[#80](https://github.com/foolzzz/looper/pull/80)）
7. **飞书通过 lark-cli 配置。** 保存的配置和导入文件里的 `app_id_env`、`app_secret_env` 会被删掉；应用取自 lark-cli 的 profile（为空时用当前 profile），只有 lark-cli 已登录、应用有机器人、白名单属于该应用时渠道才会启动。回复改为 Markdown 富文本。（[#102](https://github.com/foolzzz/looper/pull/102)、[#105](https://github.com/foolzzz/looper/pull/105)）
8. **改名或改形的记录。** 日志类型 `user_instruction` 改为 `supplement`；已完成任务的 `result_summary` 是带小标题的 Markdown 总结，失败任务的 `error` 和停止任务的 `result_summary` 是收尾说明；`/api/status` 去掉各 agent 的 `max_restarts`，`restart_count` 改为连续重启次数，`tasks` 统计全部任务；Manager 收到的 `max_restarts_exceeded` 改为 `crash_looping`。（[#89](https://github.com/foolzzz/looper/pull/89)、[#114](https://github.com/foolzzz/looper/pull/114)、[#126](https://github.com/foolzzz/looper/pull/126)、[#138](https://github.com/foolzzz/looper/pull/138)）
9. **以前接受、现在拒绝的输入。** 超过 32,000 字的任务需求会被拒绝（以前在 8,000 字处截断）；`GET /api/tasks` 遇到错误的 `limit`、未知的 `status` 或未知的 `before` 返回 400；`LOOPER_PUBLIC_URL` 无效时 `looper serve` 不会启动。（[#122](https://github.com/foolzzz/looper/pull/122)、[#139](https://github.com/foolzzz/looper/pull/139)、[#141](https://github.com/foolzzz/looper/pull/141)）

**其他影响花费或权限的变化。** Manager 现在可以在它服务的任何聊天里，不经询问就新建和修改项目与 Agent Profile、登记不含密钥的 provider、修改配置层、安装能力目录条目、启用或停用定时任务；删除、修改共用默认、改项目或角色的并发、提高花费上限则要等用户确认（[#129](https://github.com/foolzzz/looper/pull/129)、[#157](https://github.com/foolzzz/looper/pull/157)、[#160](https://github.com/foolzzz/looper/pull/160)）。每个 Planner 都有一个常开的 MCP 服务和四个工具：它可以不经询问修改本任务和所属项目的并发；项目列出 Agent Profile 后，还可以把本任务的 Worker 和 Reviewer 换成其中任何一个，包括更贵的（[#155](https://github.com/foolzzz/looper/pull/155)）。不加 `looper serve --verbose` 时，httpx 和 httpcore 只记警告，日志里形如 Telegram bot token 的内容都会打码（[#150](https://github.com/foolzzz/looper/pull/150)）。停止 agent 时先对整个进程树发 SIGTERM 再 SIGKILL，agent 各自在独立会话里运行，所以 Ctrl-C 只到达服务本身（[#96](https://github.com/foolzzz/looper/pull/96)）。没有 `AGENTS.md` 时 Codex agent 读 `CLAUDE.md`，仓库外的 OMP agent 在 system prompt 里拿到它，Claude Code agent 不再看到仓库之上的 `AGENTS.md`（[#97](https://github.com/foolzzz/looper/pull/97)）。Planner 的 `planning`、`verifying` 和 `stopping` 算作进行中，这样的任务要先停止才能删除，启动时会续跑或标为停止（[#89](https://github.com/foolzzz/looper/pull/89)）。`GET /api/chat/messages` 返回会话最新的 200 条而不是最早的 200 条（[#109](https://github.com/foolzzz/looper/pull/109)）。调度器用 `FOR NO KEY UPDATE SKIP LOCKED` 认领到期的定时任务，正在写入的通知不再让一次触发推迟 15 秒（[#154](https://github.com/foolzzz/looper/pull/154)）。向本仓库提交不再需要 sign-off（[#158](https://github.com/foolzzz/looper/pull/158)）。

### 从 v2.6.0 升级

1. **用 `install.sh` 安装。** 和 v2.6.0 一样，它用 uv、pipx 或 pip 安装最新 release 的 wheel。
2. **保证首次启动能备份。** 本版本有表结构变化，首次启动会像 v2.6.0 一样先写一份 `pg_dump` 备份再迁移：请在 `PATH` 上保留主版本不低于服务器的 `pg_dump`（或设置 `LOOPER_PG_DUMP`、`LOOPER_BACKUP_CMD`）。`looper serve --skip-backup` 不备份直接迁移。
3. **启动一次。** 首次启动会把 `agent_configs`、`agents`、`task_agent_overrides` 改名为 `role_configs`、`agent_profiles`、`task_profile_overrides`，把配置层的 effort 迁到 Agent Profile，为 Claude Code Profile 打开 agent teams，删除 `role_configs.max_concurrency` 和飞书的 app 变量，删除没有 Profile 在用的手动注册运行时，把 `user_instruction` 日志转为补充说明，新增定时任务和任务相关的表，并把未改过的 Manager 和 Planner 推荐提示词换成新版本。
4. **决定是否保留 agent teams。** 不需要队友时，在 Settings → Agent Profiles 里取消 Claude Code Profile 的“Agent teams”；内置的 `claude-code/opus` 是只读的，可以新建一个关闭它的同款 Profile，并在 Roles → Shared defaults 里选用。
5. **设定负担得起的并发。** 每个项目现在最多同时运行 8 个任务、16 个 Worker 和 8 个 Reviewer。可以在 Settings → Roles（对所有项目）或项目的 Agent Profiles 标签页里调低，并考虑设置项目的单任务花费上限。
6. **Telegram。** 如果在 v2.6.0 上开过这个渠道，日志里有 bot token：请在 BotFather 里作废它，把新 token 填进 Settings → Channels（或你的环境变量），重启，并删除 runtime root 下 `logs/` 里旧的 `serve.log`。
7. **飞书。** 安装 lark-cli 1.0.97 或更高版本，用你要用的机器人所在的应用登录，可以在 Settings → Channels 里指定它的 profile，然后重启；不再读取 app ID 变量。
8. **调用 API 的脚本。** 改用 `/api/roles`、`/api/agent-profiles` 以及 `profile_id`、`profile` 字段，配置层更新里去掉 `effort`，角色更新里去掉 `max_concurrency`，用 `POST /api/tasks/:id/start` 开始 Manager 建的任务，原来依赖重启重新规划的地方发送 `"start_over": true`。
9. **改过的 Manager 提示词。** 如果改过 Manager 的角色提示词，请在 Settings → Roles 里和推荐版本对比：Manager 现在通过工具操作，要求输出任务 JSON 的文字不再起作用。
10. **检查。** 运行 `looper doctor`，使用服务时再运行 `looper service status`。

  # 或者使用服务：

**回退到 v2.6.0。** 停止 Looper（装了服务就运行 `looper service uninstall`），把数据库重建为空库并恢复首次启动日志里给出的迁移前备份（`pg_restore --no-owner --dbname "$LOOPER_DATABASE_URL" FILE`）：迁移会改表名，并删掉 v2.6.0 需要的列。然后安装 v2.6.0 的 wheel，例如 `uv tool install --force "looper @ https://github.com/foolzzz/looper/releases/download/v2.6.0/looper-2.6.0-py3-none-any.whl"`。`install.sh` 总是安装最新 release，不能用来回退。v2.6.0 只从环境变量读取 Telegram token，从变量读取飞书 app ID，请重新设置；它不认识定时任务，定时任务会停止运行。

### 可选能力启用与使用

#### Scheduled tasks

**启用：**创建并启用定时任务之前不会运行任何东西；调度器在每个 `looper serve` 里都运行，但新建的定时任务处于停用状态。在项目的 Schedules 标签页（“New schedule”）或用 `POST /api/projects/PROJECT_ID/schedules` 创建（必填 `name`、`cron`、`requirement`，项目没有默认目录时还要 `work_dir`；可选 `timezone`、`overlap`、`max_parallel_runs`、`catch_up`、`run_timeout_seconds`、`run_budget_usd`、`daily_budget_usd`、`gate_command`、`gate_timeout_seconds`、`notify`、`notify_target` 和 `profile_overrides`），再用开关或 `PUT /api/schedules/SCHEDULE_ID` 加 `{"enabled": true}` 启用，下一次触发从这一刻起算。`notify_target` 必须是已在 Telegram 或飞书发送者白名单里的人。

**验证：**`POST /api/schedules/preview` 校验规则并列出接下来的触发时间；`GET /api/schedules/SCHEDULE_ID` 显示 `enabled` 和 `next_fire_at`；Run now（`POST /api/schedules/SCHEDULE_ID/run`）立即触发一次，停用时也可以，`GET .../runs` 和 `GET .../notifications` 显示每次运行和每条消息。启动日志里有 `scheduler started: checks the schedules every 15 s`。

**停用 / 回退：**关闭定时任务（`{"enabled": false}`）后不再触发，但不会停止已在运行的任务（在任务页或用 `POST /api/tasks/stop` 停止）。`DELETE /api/schedules/SCHEDULE_ID` 删除定时任务及其运行记录和消息，运行进行中也可以：该任务照常结束，排队的运行不再开始，仍在执行的前置检查结束后不会建任务，定时任务建过的任务保留。项目里还有定时任务时不能删除项目。

**权限边界：**启用定时任务即批准它发起的每一个任务：无人值守、付费运行的 Planner、Worker 和 Reviewer，拥有全部工具且无需权限确认；`parallel` 下最多同时 `max_parallel_runs`（至多 10）个，只受项目并发、`run_budget_usd`（未设时用项目的单任务上限）、设了的 `daily_budget_usd` 和 `run_timeout_seconds` 限制。每日预算按服务器本地零点以来触发的运行计算，只在到期触发时检查，不会停止进行中的运行。前置检查是任意 shell 命令，每次触发（最频繁每分钟一次）都以你的用户身份、带着服务的环境变量在工作目录里执行，它的输出会写进任务需求交给模型读。消息只经机器人发给定时任务指定的那一个白名单用户。定时任务不保存密钥，配置导出不包含它们；Manager 可以列出、启用、停用和删除定时任务（删除要你确认），但不能新建或修改。

**文档：**https://github.com/foolzzz/looper/blob/v2.7.0/docs/architecture/agent-system.md#schedules-tasks-on-a-time-rule

```bash
curl -s -X POST http://127.0.0.1:8767/api/schedules/preview -H 'Content-Type: application/json' \
  -d '{"cron": "0 9 * * 1-5", "timezone": "America/Los_Angeles"}'
  # 创建（停用状态）、启用、立即触发一次并读回运行记录：
curl -s -X POST http://127.0.0.1:8767/api/projects/PROJECT_ID/schedules -H 'Content-Type: application/json' \
  -d '{"name": "weekday-deps", "cron": "0 9 * * 1-5", "timezone": "America/Los_Angeles",
       "requirement": "Check the dependencies for updates and report what changed.",
       "run_timeout_seconds": 3600, "run_budget_usd": 2, "daily_budget_usd": 5, "notify": "alerts"}'
curl -s -X PUT http://127.0.0.1:8767/api/schedules/SCHEDULE_ID -H 'Content-Type: application/json' -d '{"enabled": true}'
curl -s -X POST http://127.0.0.1:8767/api/schedules/SCHEDULE_ID/run
curl -s 'http://127.0.0.1:8767/api/schedules/SCHEDULE_ID/runs?limit=20&skips=hide'
  # 停用，或删除（它建的任务保留）：
curl -s -X PUT http://127.0.0.1:8767/api/schedules/SCHEDULE_ID -H 'Content-Type: application/json' -d '{"enabled": false}'
curl -s -X DELETE http://127.0.0.1:8767/api/schedules/SCHEDULE_ID
```

#### Step workspaces

**启用：**按项目设置，默认 `shared`。把项目的 `step_workspaces` 设为 `worktree`（Project → Settings → Execution 里的“Steps that run at the same time”，或 `PUT /api/projects/PROJECT_ID`）。只有任务目录是在某个分支上、至少有一个提交的 git 检出，git 版本不低于 2.40，且没有进行中的 merge、rebase、cherry-pick、revert 或 bisect 时才生效，而且只作用于与本任务其他步骤同时运行的步骤；不满足这些条件的检出会让步骤逐个运行，不在 git 里的目录不受影响。

**验证：**`GET /api/projects` 显示 `step_workspaces: "worktree"`。有并行步骤的任务会在活动里记下起点（“Step workspaces: the task starts with BRANCH at SHA”）、每个步骤的 worktree 和分支（`looper/TASK_ID/...`）以及每次合并（“Step KEY merged into BRANCH”）；仓库里会出现标题为 `looper: merge step ...`、作者为 `Looper <looper@localhost>`、带 `Looper-Task` 和 `Looper-Step` 尾注的合并提交。

**停用 / 回退：**把 `step_workspaces` 改回 `shared`（或 `null`），之后派出的步骤重新共用任务目录。`git reset START_COMMIT`（活动里给出的提交）撤销任务的提交并把改动留作未提交的修改，`git revert -m 1 MERGE_COMMIT` 撤销单个步骤。已完成任务的 worktree 和分支会被删除；失败、停止或取消的任务保留未合回的，直到从头再来或删除任务；其他遗留的由服务启动时清理。

**权限边界：**Looper 会在你检出的分支上自己提交：一轮并行步骤开始前，把任务目录里所有未被 git 忽略的改动（包括你自己未提交的修改）提交为检查点；Worker 没提交的改动；以及每个验收步骤一个合并提交。这些提交不签名、不跑钩子，提交钩子和签名策略对它们不生效；Worker 自己的提交仍用你的身份、签名和钩子。Looper 从不推送、不切换分支、不改写提交，合不进去时任务目录保持不变并交给 Planner。worktree 位于 runtime root 的 `worktrees/` 下，`.env`、`node_modules` 等被 git 忽略的文件不在其中。它不增加模型花费。

**文档：**https://github.com/foolzzz/looper/blob/v2.7.0/docs/architecture/agent-system.md#step-workspaces

```bash
curl -s -X PUT http://127.0.0.1:8767/api/projects/PROJECT_ID -H 'Content-Type: application/json' \
  -d '{"step_workspaces": "worktree"}'
curl -s http://127.0.0.1:8767/api/projects | python3 -m json.tool | grep '"step_workspaces"'
  # 有并行步骤的任务结束后，在任务目录里：
git log --merges --format='%h %an %s' | grep 'looper: merge step'
git worktree list
  # 关闭：
curl -s -X PUT http://127.0.0.1:8767/api/projects/PROJECT_ID -H 'Content-Type: application/json' \
  -d '{"step_workspaces": "shared"}'
```

#### Planner Agent Profile choice

**启用：**按项目设置，默认关闭：项目里允许 Planner 选择的 Agent Profile 列表为空，列表为空时一切选择都会被拒绝。在项目的 Agent Profiles 标签页（“Profiles the Planner may choose”）或用 `PUT /api/projects/PROJECT_ID/allowed-profiles`（`{"profile_ids": [...]}`，整个列表，按 id 或名称；每个 Profile 都要能运行 Worker 或 Reviewer）添加。Manager 的 `looper_settings` 也能增删条目。之后 Planner 调用 `looper_task_profile_set`，让本任务的 Worker 或 Reviewer 在其中某个 Profile 上运行，作用于剩下的步骤或某一步。

**验证：**`GET /api/projects/PROJECT_ID/allowed-profiles` 列出这些 Profile。选择之后，`GET /api/tasks/TASK_ID` 的 `agents.roles` 里 Worker 的 Profile 来源为 `planner_task`，任务日志里有一条带 Planner 理由的 `profile_choice`（任务页 Findings 可见），运行历史里写明所用的 Profile。

**停用 / 回退：**清空列表（`{"profile_ids": []}`）：在同一个事务里删掉本项目 Planner 选过的、已被移出列表的 Profile，之后的运行回到用户为任务做的选择，再到配置层；已经开始的运行保持原 Profile。只想固定某个任务时，自己为它选 Profile（`PUT /api/tasks/TASK_ID/agents`）：用户的选择优先，Planner 对该角色的选择会被拒绝。列表里的 Profile 移出之前不能删除。

**权限边界：**某个 Profile 进入列表后，项目里的 Planner 可以不经询问把本任务的 Worker 或 Reviewer 换成它，包括更贵的；只有项目的单任务花费上限（默认未设置）能限制花费。Planner 不能改自己的 Profile，只能作用于本任务，只在 Looper 发给它的回合里操作，所用令牌在该 Planner 停止或任务结束时失效。并发工具不受这个列表约束：每个 Planner 都能不经询问修改本任务和所属项目的并发（见“破坏性变更”）。列表显示运行时、模型、effort 和价格，不显示 provider 密钥。

**文档：**https://github.com/foolzzz/looper/blob/v2.7.0/docs/architecture/agent-system.md#a-tasks-planners-tools

```bash
curl -s http://127.0.0.1:8767/api/projects/PROJECT_ID/allowed-profiles
curl -s -X PUT http://127.0.0.1:8767/api/projects/PROJECT_ID/allowed-profiles -H 'Content-Type: application/json' \
  -d '{"profile_ids": ["PROFILE_ID"]}'
  # Planner 做出选择后，查看任务的 Worker 用什么 Profile、来源是什么：
curl -s http://127.0.0.1:8767/api/tasks/TASK_ID | python3 -m json.tool | grep -A6 '"worker"'
  # 再次关闭：
curl -s -X PUT http://127.0.0.1:8767/api/projects/PROJECT_ID/allowed-profiles -H 'Content-Type: application/json' \
  -d '{"profile_ids": []}'
```

#### Codex ChatGPT login

**启用：**没有 Profile 使用时不生效。Codex 在服务的 `PATH` 上（`looper serve` 会注册内置运行时 `rt-codex`，或在 Settings → Agent Runtimes 点 Re-detect），在服务所在的机器上用 ChatGPT 运行 `codex login`，在 Codex 运行时上用内置 provider `prov-codex-login` 新建 Agent Profile（Settings → Agent Profiles 里选 provider `codex-login`，或 `POST /api/agent-profiles`），再为某个角色、项目或任务选用它。

**验证：**Agent Profile 表单显示登录状态；有 Profile 使用它时，`looper doctor` 会运行 “Codex login” 检查；`GET /api/status` 里有 `codex_login` 检查，`GET /api/registry` 里有该 provider 的 `login` 状态；每次运行记录所用的 Profile。

**停用 / 回退：**在该层选别的 Profile（或 `null` 继承），再删除这个 Profile（仍有地方选用时返回 409）。某次运行留下登录文件的副本时，Looper 删除副本、恢复链接，并停用该登录，直到你核对 `codex login status` 后点 “Use the login again”（`DELETE /api/providers/prov-codex-login/login-problem`）。

**权限边界：**它消耗你 ChatGPT 套餐的额度；Looper 按内置价格记下等价花费，并不是实际付费。登录信息留在你自己的 Codex 登录文件里：每次运行的隔离 Codex 家目录只链接到它，从不复制，Looper 也不保存任何 token。agent 的 shell 命令拿到的是没有登录的 Codex 家目录，所以 agent 运行 `codex logout` 也注销不了你的登录，每次运行后都会检查有没有留下副本。Codex 仍在无审批、无沙箱的模式下以你的用户权限运行，agent 仍可以按路径读取登录文件。

#### Telegram and Lark channels

**启用：**默认关闭，且本版本有变化。Telegram：在 Settings → Channels 里把 BotFather 给的 bot token 填进 Bot token 输入框（或继续放在设置所指的环境变量里），列出允许的 Telegram 数字用户 ID，启用渠道，然后重启 `looper serve` 或服务。飞书：安装 lark-cli 1.0.97 或更高版本，用带机器人的应用登录（要按人搜索时还需以用户身份登录），可以指定 lark-cli 的 profile，按姓名或邮箱添加发送者，启用渠道并重启；要在群里用，把机器人拉进群。

**验证：**启动日志 `agent system running on ... (channels=...)` 列出已启动的渠道；`GET /api/channel-configs` 显示每个渠道的 `start_problem`（能启动时为 `null`）和 Telegram 的 `has_bot_token`；`GET /api/channels/lark/status` 显示飞书机器人或不能启动的原因，以及被拒的发送者。白名单内的发送者发来消息后，先收到一个表情，然后是一条原地编辑的状态消息，再是回答；在那里发起的任务结束时，同一个聊天会收到通知。

**权限边界：**每个白名单内的发送者（Telegram 用户 ID；飞书 open_id，绑定到机器人所属应用）都能直接对话 Manager，而 Manager 无需权限确认就能在本机运行任何命令，现在还能通过工具修改 Looper 的配置；确认按聊天而不是按人计，所以在飞书群里，白名单内任何人的下一条消息都会被当作确认与否的那一条。飞书群里只回答 @ 机器人的消息，这些对话会入库，回复、进度和任务结束通知都发到群里。Telegram 群消息不入库。Telegram token 与配置分开存在数据库里，接口不返回、导出不包含；飞书的凭据留在 lark-cli 里。按人搜索以登录的 lark-cli 用户身份执行，在 dashboard 上显示姓名、邮箱和部门。

### 已知限制

- `loopx` 别名、`~/.loopx` 链接和 `LOOPX_*` 回退仍在本版本里，虽然 v2.6.0 说过会移除；之后的版本会移除它们。
- 除了 agent 自己的工具路由，HTTP API 仍没有认证；它拒绝其他网页的请求，但本机任何进程都能调用。请保持默认的 `127.0.0.1` 绑定。
- Manager 的分档限制的是它的工具，而不是 Manager 本身：它仍有无需权限确认的 shell，“没执行就不说执行了”只是提示词里的规则。确认保存在内存里、按聊天计，重启或 `/new` 会丢掉。
- Planner 修改所属项目的并发只靠提示词约束、没有代码强制，并且只在来自 Telegram 或飞书的任务的聊天里通知。
- agent teams：队友的 token 只通过结果里的合计计入运行花费和单次运行软上限；队友拿不到 Looper 的 system prompt 各层；只在 Claude Code 2.1.285 上验证过。
- 没有整机并发上限，provider 的 `max_concurrency` 仍只保存不生效。
- 定时任务：Manager 不能新建或修改，没有 CLI，配置导出不包含；一个定时任务只通知一个人，不能发到群；每日预算只在到期触发时检查；运行在项目上限下排队等待时也计入超时。

# Looper v2.15.5

This is the patch release v2.15.5, a hotfix line in which each merged change ships at once. It documents one change: [#1380](https://github.com/foolzzz/looper/pull/1380) (room push keeps the report when a steer lands during the last model response).

## Release Decision

**Who should upgrade:** Operators whose Workers or Reviewers run on steering runtimes (Codex, OMP, Pi, Grok and the runner channel) and receive room messages, and who want the final report of a step left intact.

**What this release solves:** [#1380](https://github.com/foolzzz/looper/pull/1380) stops a room message from being steered into a Worker or Reviewer while it writes its final answer, which carries the step's report. Such a message now waits for the next tool call, the next run or the Planner.

**Breaking changes:** No. The CLI, the API and the dashboard are unchanged, no new command or control is added and there is no PostgreSQL schema change. The PR states a behavior change, listed below. The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.15.5
```

**Contributors:** Maintainer @foolzzz authored [#1380](https://github.com/foolzzz/looper/pull/1380); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.15.4 upgrades directly. There is no PostgreSQL schema change. Restart the service after upgrading, as for every release.

## Behavior changes

Read in the diff of the PR.

### #1380: Room push keeps the report when a steer lands during the last model response

- **Gate in the Worker.** Before the Worker reads a room delivery to send, it checks that the run's channel is still current and that a tool is running or the Worker waits in the room inbox. If not, the delivery is left pending and nothing is sent.
- **Gate at the protocol write.** A new `RoomSteerWindow` tracks outstanding tool calls from each channel's own tool-start and tool-result events, because the Worker's event consumer can lag behind the protocol reader. The Codex, OMP, Pi CLI and Grok channels check it just before the write. The runner channel checks it on entry and again just before the bridge writes the `session/steer` frame; the PR names the SDK runner for Pi and DSH as using this channel.
- **Rejected deliveries.** A room delivery that finds no running tool is not sent. The runner channel returns it as rejected (the other channels raise inside their delivery attempt, which ends it as not accepted). It stays unread, so it is steered at the next tool call, listed on the next run, or answered by the Planner.
- **Scope.** Only deliveries with `looper-reminder-` ids are gated. Planner messages and other input keep their own rules.
- **Behavior change.** A room message posted while a Worker writes its final answer now waits for the next run (or the Planner) instead of being steered into that answer's turn.

### Model-visible changes

Yes, narrowly. For Workers and Reviewers on steering runtimes, a room message no longer arrives as steered input during the final model response, so the final answer that carries the step's report is not followed by it. Prompt text, the room guidance and tool schemas are unchanged. Runs without steering are unchanged.

### 行为变化与入口

以下在该 PR 的差异中可见。

**#1380：房间推送在模型最后一次回复期间不再插入 steer**

- **Worker 中的闸门。**Worker 读取房间投递前，检查该运行的通道仍是当前通道，且有工具在运行或 Worker 正在房间收件箱等待；否则投递保持待处理，不发送。
- **协议写入处的闸门。**新增 `RoomSteerWindow`，根据各通道自己的工具开始与工具结果事件跟踪未完成的工具调用，因为 Worker 的事件消费者可能落后于协议读取。Codex、OMP、Pi CLI 和 Grok 通道在写入前检查；runner 通道在入口检查，并在桥接写出 `session/steer` 帧前再检查一次；PR 称 Pi 和 DSH 的 SDK runner 使用该通道。
- **被拒绝的投递。**没有工具在运行时，房间投递不会发送。runner 通道将其作为 rejected 返回（其他通道在投递尝试中抛出异常，结果为未被接受）。它保持未读，因此会在下一次工具调用时被 steer、在下一次运行时列出，或由 Planner 回答。
- **范围。**只有 `looper-reminder-` 开头 id 的投递受限。Planner 消息和其他输入保持各自的规则。
- **行为变化。**Worker 撰写最终答复期间发出的房间消息，现在等到下一次运行（或 Planner），不再被 steer 进该答复所在的轮次。

**面向模型的变化：**有，范围很窄。对支持 steer 的运行时上的 Worker 和 Reviewer，房间消息不再在最后一次模型回复期间作为 steer 输入到达，因此承载步骤报告的最终答复后不再跟着房间消息。提示词文本、房间指引和工具 schema 不变。没有 steer 的运行不变。

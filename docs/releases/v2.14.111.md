# Looper v2.14.111

This is the patch release v2.14.111, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.110: composable AND/OR step dependency conditions ([#1171](https://github.com/foolzzz/looper/pull/1171)).

## Release Decision

**Who should upgrade:** Operators whose Planners should start a step when all, any or a chosen number of its dependencies are ready, and anyone who wants a step whose dependency was skipped to get a Planner decision. Projects that leave the new switch off see no change in how steps are planned or rendered, apart from the blocked-dependency case listed under Behavior changes.

**What this release solves:** [#1171](https://github.com/foolzzz/looper/pull/1171). A step could only wait for all of its `depends_on` steps to be verified. With the per-project `dependency_conditions` switch on, a Planner may give a work, gate or wait step a `ready_when` condition built from `all_of`, `any_of` and `k_of`, nested, whose leaves wait for a step to be completed, verified or passed. Readiness is decided in code with three values (satisfied, pending, unsatisfiable). A condition that can never be met hands the Planner a turn instead of silently leaving the step pending, and replans keep the conditions of started steps. The task API shows each condition and its state.

**Breaking changes:** No. No new dependency. The switch is off by default and the database change is additive (see Upgrading); the API only adds fields.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.14.111
```

**Contributors:** Maintainer @foolzzz authored [#1171](https://github.com/foolzzz/looper/pull/1171); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.110 upgrades directly. The schema change is additive: once, `ensure_schema` adds the nullable `task_steps.ready_when` JSONB column and the nullable `projects.dependency_conditions` column (`off` or `on`), extends the allowed `task_journal` kinds with `condition_blocked` (the constraint also lists `wait_opened`, `wait_extended` and `wait_closed`, which the database layer now accepts too) and records the `dependency_conditions` migration. Until then it is a pending schema change. An older Looper reading the upgraded database does not know the new journal kind.

## Behavior changes

- **Condition model** (`looper/agents/tiers/conditions.py`, new). A condition is a step id (meaning verified), `{"step", "on"}` with `on` one of completed, verified or passed, `{"all_of": [...]}`, `{"any_of": [...]}` or `{"k_of": k, "of": [...]}`. At most 4 nested groups and 32 leaves; groups are nonempty, `k` is a whole number from 1 to the child count, and a step may not repeat within a group. Evaluation is three-valued: a failed, skipped or vanished step makes its leaves unsatisfiable; a gate counts as passed when passed (cancelled is unsatisfiable); a wait counts as passed when it closed `ready` or `resumed`. Review steps are not yet referenced by conditions.
- **Project switch** (`looper/agents/project_execution.py`, `looper/db/projects.py`, `looper/agents/v1_domains/projects.py`, `looper/agents/v1_domains/task_create.py`). `dependency_conditions` is `off` or `on`, unset means off, and it is settable through project admin and task creation like the other execution switches.
- **Planner protocol** (`looper/agents/tiers/planner_protocol.py`). With the switch on, work, gate and wait steps accept an optional `ready_when`, and `depends_on` must list exactly its leaves. With the switch off, a reply containing `ready_when` is rejected with a message saying so. In worktree isolation, `on: completed` is rejected (wait for `verified` so upstream work is merged first).
- **Scheduling** (`looper/agents/tiers/planner.py`). A pending step with `ready_when` is ready when its condition is satisfied; one without it keeps the rule that all dependencies are verified. After an `any_of` is satisfied, other branches keep running and are not cancelled. Persisted conditions use step ids and are stored in `task_steps.ready_when`; a replan keeps started steps' conditions.
- **Blocked-condition recovery** (`looper/agents/tiers/planner.py`, `looper/agents/tiers/journal.py`). When a pending step can no longer start, the Planner gets a chat turn that allows `none` (skip the step), `add_steps` or `replan`; the step is journaled as `condition_blocked` and the decision is recorded. A reply that leaves the step unsatisfiable with no Worker in flight is refused. Recovery is bounded: the plan fails after the allowed number of turns, and also when the Planner cannot answer and nothing is in flight. This recovery also applies to steps without `ready_when` whose plain `depends_on` points to a skipped or missing step, so the case is no longer left pending silently in projects with the switch off; this is a behavior change for every project, and the pull request's "byte-for-byte as before" statement does not cover it.
- **API and Manager views** (`looper/agents/projects.py`, `looper/agents/wait_service.py`, `looper/agents/v1_domains/task_views.py`, `looper/agents/v1_domains/task_interactions.py`, `looper/agents/ops/clients.py`, `looper/db/*`). Steps, gates and waits in task detail carry `ready_when` and `ready_state` (`satisfied`, `pending`, `unsatisfiable`, or null for a step that is not pending). Steps without a condition get `ready_when: null` and a `ready_state` derived from `depends_on`. The Manager's pipeline view adds `ready_when_text` and `ready_state` only for steps with a condition, and its compact waits omit the two fields when there is no condition.
- **Dashboard** (`web/`). The project execution settings gain a "Dependency conditions" switch (off by default).
- **Evals, documentation and tests.** The prompt regression suite gains a condition flow task and a runner option that enables the switch (`evals/`). A Chinese RFC, `docs/architecture/rfcs/workflow-presets-v0.zh-CN.md`, describes the model and marks the workflow presets as future design. New tests: `tests/test_dependency_conditions.py`, `tests/test_dependency_conditions_eval.py`, `tests/test_dependency_conditions_protocol.py`, `tests/test_dependency_conditions_views_db.py`, `tests/test_planner_conditions.py`; others extended.
- **Unchanged:** the default rule (all `depends_on` verified) for steps without a condition, projects with the switch off apart from the item above, Worker and Reviewer behavior, channels (Telegram and Lark), dependencies and billing.
- **Model-visible changes:** With the switch on, the Planner's reply contract gains the `ready_when` rules, its plan lines show a condition ("after all of (...)"), and it receives the blocked-condition chat turn. With the switch off, the Planner prompt text is unchanged but a Planner may receive that chat turn for a skipped or missing plain dependency. The Manager's task and pipeline tool results gain `ready_when`, `ready_state` and `ready_when_text` as above, which a Manager model sees in its tool schemas and results.

### 升级决策

**谁需要升级：**希望 Planner 在全部、任一或指定数量的依赖就绪时启动步骤的运维人员，以及希望依赖被跳过的步骤得到 Planner 决策的人。保持新开关关闭的项目，步骤规划与展示不变，但下文行为变化中的依赖受阻情形除外。

**解决了什么：**[#1171](https://github.com/foolzzz/looper/pull/1171)。此前步骤只能等待全部 `depends_on` 步骤通过验证。项目级 `dependency_conditions` 开关打开后，Planner 可为工作、门禁和等待步骤设置 `ready_when` 条件，由可嵌套的 `all_of`、`any_of`、`k_of` 组成，叶子等待某步骤 completed、verified 或 passed。就绪由代码以三值（satisfied、pending、unsatisfiable）判定。永远无法满足的条件会交给 Planner 一轮处理，而不是让步骤悄悄停在待定；重新规划会保留已启动步骤的条件。任务 API 展示条件及其状态。

**是否有破坏性变更：**否。无新依赖。开关默认关闭，数据库变更为增量（见升级）；API 只增加字段。

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.110 上的安装可直接升级。数据库变更为增量：`ensure_schema` 一次性增加可空的 `task_steps.ready_when`（JSONB）列和可空的 `projects.dependency_conditions` 列（`off` 或 `on`），在 `task_journal` 允许的类型中加入 `condition_blocked`（约束中同时列出 `wait_opened`、`wait_extended`、`wait_closed`，数据库层现在也接受它们），并记录 `dependency_conditions` 迁移。在此之前它被视为待处理的结构变更。旧版 Looper 读取已升级的数据库时不认识新的日志类型。

### 行为变化与入口

- **条件模型**（`looper/agents/tiers/conditions.py`，新增）。条件可以是步骤 id（表示 verified）、`{"step", "on"}`（`on` 为 completed、verified 或 passed）、`{"all_of": [...]}`、`{"any_of": [...]}` 或 `{"k_of": k, "of": [...]}`。最多嵌套 4 层、32 个叶子；分组不能为空，`k` 为 1 到子项数量的整数，同一分组内步骤不得重复。求值为三值：失败、跳过或不存在的步骤使其叶子不可满足；门禁 passed 时算 passed（cancelled 不可满足）；等待以 `ready` 或 `resumed` 结束时算 passed。条件暂不引用评审步骤。
- **项目开关**（`looper/agents/project_execution.py`、`looper/db/projects.py`、`looper/agents/v1_domains/projects.py`、`looper/agents/v1_domains/task_create.py`）。`dependency_conditions` 取 `off` 或 `on`，未设置视为关闭，可像其他执行开关一样通过项目管理和任务创建设置。
- **Planner 协议**（`looper/agents/tiers/planner_protocol.py`）。开关打开时，工作、门禁和等待步骤可带可选的 `ready_when`，且 `depends_on` 必须恰好列出其叶子。开关关闭时，包含 `ready_when` 的回复会被拒绝并说明原因。在 worktree 隔离下拒绝 `on: completed`（应等待 `verified`，使上游工作先合并）。
- **调度**（`looper/agents/tiers/planner.py`）。带 `ready_when` 的待定步骤在条件满足时就绪；不带的仍要求全部依赖已验证。`any_of` 满足后其他分支继续运行，不被取消。持久化的条件使用步骤 id，存入 `task_steps.ready_when`；重新规划保留已启动步骤的条件。
- **受阻条件恢复**（`looper/agents/tiers/planner.py`、`looper/agents/tiers/journal.py`）。待定步骤无法再启动时，Planner 会收到一轮聊天，可选 `none`（跳过该步骤）、`add_steps` 或 `replan`；该步骤记为 `condition_blocked` 日志并记录决定。若回复让步骤仍不可满足且没有 Worker 在运行，则被拒绝。恢复有上限：超过允许的轮数计划失败，Planner 无法回答且没有任何在途工作时也失败。此恢复同样适用于没有 `ready_when`、但普通 `depends_on` 指向已跳过或不存在步骤的步骤，因此开关关闭的项目也不再让该情形悄悄停在待定；这是对所有项目的行为变化，PR 中“与之前逐字节一致”的说法不涵盖它。
- **API 与 Manager 视图**（`looper/agents/projects.py`、`looper/agents/wait_service.py`、`looper/agents/v1_domains/task_views.py`、`looper/agents/v1_domains/task_interactions.py`、`looper/agents/ops/clients.py`、`looper/db/*`）。任务详情中的步骤、门禁和等待带有 `ready_when` 和 `ready_state`（`satisfied`、`pending`、`unsatisfiable`，非待定步骤为 null）。无条件的步骤 `ready_when` 为 null，`ready_state` 由 `depends_on` 推导。Manager 的流水线视图仅为带条件的步骤增加 `ready_when_text` 和 `ready_state`，紧凑的等待视图在无条件时省略这两个字段。
- **仪表盘**（`web/`）。项目执行设置新增 “Dependency conditions” 开关（默认关闭）。
- **评测、文档与测试。**提示回归评测新增条件流程任务和启用开关的运行器选项（`evals/`）。中文 RFC `docs/architecture/rfcs/workflow-presets-v0.zh-CN.md` 描述该模型，并注明流程预设属于后续设计。新增测试：`tests/test_dependency_conditions.py`、`tests/test_dependency_conditions_eval.py`、`tests/test_dependency_conditions_protocol.py`、`tests/test_dependency_conditions_views_db.py`、`tests/test_planner_conditions.py`；其他测试有扩展。
- **不变：**无条件步骤的默认规则（全部 `depends_on` 已验证）、开关关闭的项目（上一条除外）、Worker 与 Reviewer 行为、渠道（Telegram 和 Lark）、依赖和计费。
- **面向模型的变化：**开关打开时，Planner 的回复约定新增 `ready_when` 规则，计划行显示条件（“after all of (...)”），并会收到受阻条件的聊天轮。开关关闭时 Planner 提示文字不变，但遇到被跳过或不存在的普通依赖时可能收到该聊天轮。Manager 的任务和流水线工具结果新增 `ready_when`、`ready_state` 和 `ready_when_text`，Manager 模型会在工具 schema 和结果中看到。

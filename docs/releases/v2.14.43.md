# Looper v2.14.43

This is the patch release v2.14.43, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.42: four fixes in the command schedule runtime ([#993](https://github.com/foolzzz/looper/pull/993)).

## Release Decision

**Who should upgrade:** Anyone who runs command schedules (a shell command on a time rule, with no agent), in particular when the service drains for a restart or shutdown, or when the housekeeping pass or a command's log directory misbehaves.

**What this release solves:** [#993](https://github.com/foolzzz/looper/pull/993) fixes four things. A due command schedule is now admitted by its kind after it is locked, so a command launch no longer counts as a starting agent run that a drain must wait for, and after `drain.begin` no tick already under way can create or publish an agent task. Housekeeping runs its retention lookup, run pruning, notification pruning and each service-log rotation as independent steps, so a failure in one still lets the others run and is recorded in `failed_steps`. Run pruning keeps an unfinished run whose gate output has not been handed on. The command runner retries opening its log once when the log directory vanished between creating it and opening the file. The change also makes deleting a command schedule fail while one of its runs is running (see "Behavior changes").

**Breaking changes:** No. No API or configuration is removed, and there is no new migration or setting. Deleting a command schedule with a running run now answers 409 instead of succeeding: see "Behavior changes".

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#993](https://github.com/foolzzz/looper/pull/993); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.43
```

## Behavior changes

- **Admission by kind in a scheduler tick ([#993](https://github.com/foolzzz/looper/pull/993)).** `Scheduler._fire_due` no longer decides admission before the lookup. It counts the lookup of the next due schedule as a possible agent start, releases that count, and then admits the locked schedule by its kind. While the service is draining, command schedules still fire and agent schedules are not admitted; a command launch in progress leaves `starting` at 0 so the drain can reach `drained`.
- **Housekeeping steps.** The step "runs and notifications" is split. Reading the retention period is the step `retention`; pruning runs is the step `runs`; pruning notifications is the step `notifications`; each service log is rotated in its own step `log rotation <name>`. A failure is recorded in `failed_steps` under that step's name and the other steps still run. If `retention` fails, neither pruning step runs in that pass.
- **Run retention.** `prune_runs` no longer deletes a run that ended unfinished (`failed`, `timed_out`, `gate_failed`, `stopped`, `cancelled` or `interrupted`) with a non-empty gate output that has not been carried on, which is what `unhanded_runs` returns. Such runs are kept until they are handed on to a later run or their schedule is deleted. Open runs were already never deleted.
- **Command runner log.** If opening the run's log file fails with a missing directory, the runner creates the directory again and retries the open once; a second failure is raised as before.
- **Deleting a command schedule.** `delete_schedule` now locks the schedule row, the same lock a fire takes, and refuses with 409 ("cannot delete a command schedule while a run is running; disable the schedule and wait for the run to end") when a command schedule has a run with status `running`. Otherwise deletion cascades to the run records as before. Agent schedules can still be deleted while running, and the tasks they created continue. The PR description does not mention this change; it is in the code and in the PR's updated RFC and plan notes.
- **Model-visible changes:** None found. The PR touches no prompt, tool description, tool schema or tool result text in `looper/`. The 409 text above is returned by the delete API, so the Manager can relay it when a delete is refused.

本版本是 patch release v2.14.43（热修线，每个合并的改动立即发布）。自 v2.14.42 以来合并了一项改动：命令定时任务运行时的四处修复（[#993](https://github.com/foolzzz/looper/pull/993)）。

### 升级决策

**谁需要升级：**使用命令定时任务（按时间规则执行 shell 命令、不经过 agent）的人，尤其是服务排空以重启或关闭时，或遇到保留任务、命令日志目录异常的人。

**解决了什么：**[#993](https://github.com/foolzzz/looper/pull/993) 修复四件事。到期的命令定时任务在加锁后按其类型准入，命令启动不再被算作需要排空等待的 agent 启动；`drain.begin` 之后，已在进行的调度周期不能再创建或发布 agent 任务。保留任务把读取保留期、清理运行、清理通知和每个服务日志的轮转拆成互相独立的步骤，一步失败不影响其他步骤，并记入 `failed_steps`。运行清理会保留尚未交接前置检查输出的未完成运行。命令运行器在日志目录于创建与打开之间消失时，重试一次打开日志。同时，运行中的命令定时任务现在不能被删除（见“行为变化与入口”）。

**是否有破坏性变更：**否。不移除任何 API 或配置，也没有新的迁移或设置。删除有运行中记录的命令定时任务现在返回 409，见“行为变化与入口”。

**如何验证：**运行 `looper --version` 核对版本为 2.14.43。

**贡献者：**维护者 @foolzzz 提交 [#993](https://github.com/foolzzz/looper/pull/993)；本版本无社区贡献。

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.42 上的安装可直接升级。本版本没有新迁移，也没有新设置。

### 行为变化与入口

- **调度周期按类型准入（[#993](https://github.com/foolzzz/looper/pull/993)）。**`Scheduler._fire_due` 不再在查找前决定准入：先把查找下一个到期任务算作可能的 agent 启动，查完即释放，再按已锁定任务的类型准入。服务排空期间命令定时任务仍会触发、agent 定时任务不被准入；进行中的命令启动让 `starting` 保持为 0，排空可以到达 `drained`。
- **保留任务的步骤。**原“runs and notifications”步骤被拆开：读取保留期为 `retention` 步，清理运行为 `runs` 步，清理通知为 `notifications` 步，每个服务日志在自己的 `log rotation <name>` 步中轮转。失败以步骤名记入 `failed_steps`，其他步骤照常运行。若 `retention` 失败，该次不执行两个清理步骤。
- **运行保留。**`prune_runs` 不再删除以未完成状态（`failed`、`timed_out`、`gate_failed`、`stopped`、`cancelled`、`interrupted`）结束、前置检查输出非空且尚未交接的运行，即 `unhanded_runs` 会返回的运行。它们保留到被后续运行接手或其定时任务被删除。进行中的运行本来就不会被删除。
- **命令运行器日志。**打开日志文件因目录不存在而失败时，运行器重新创建目录并重试一次；第二次失败仍照常抛出。
- **删除命令定时任务。**`delete_schedule` 现在锁定定时任务行（与触发使用同一把锁），当命令定时任务有 `running` 状态的运行时返回 409（“cannot delete a command schedule while a run is running; disable the schedule and wait for the run to end”）；否则照旧级联删除运行记录。agent 定时任务仍可在运行中删除，它建出的任务继续运行。PR 描述没有提到这一变化，它见于代码以及该 PR 更新的 RFC 和计划说明。
- **面向模型的变化：**未发现。该 PR 没有改动 `looper/` 中的提示词、工具描述、工具 schema 或工具结果文字。上述 409 文字由删除 API 返回，因此删除被拒绝时 Manager 可以转述。

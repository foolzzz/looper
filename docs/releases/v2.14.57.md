# Looper v2.14.57

This is the patch release v2.14.57, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.56: `looper service upgrade` now refuses import and repository overrides from the caller's shell, refuses to run code from outside the service's install, and runs its tools without them ([#1031](https://github.com/foolzzz/looper/pull/1031)).

## Release Decision

**Who should upgrade:** Anyone who runs `looper service upgrade`, in particular from a shell that exports `PYTHONPATH`, `GIT_DIR` or similar variables, or with a `looper` console script that belongs to another checkout.

**What this release solves:** The upgrade checked that the CLI's interpreter and (for a checkout upgrade) the working directory were the unit's, but not where the running CLI code came from, and it passed the caller's whole environment to `uv sync`, `npm ci` and the dashboard build; git inherited it too. With `PYTHONPATH` pointing at another checkout, the console script could run that checkout's upgrade code and the variable reached the build tools; with `GIT_DIR` or `GIT_WORK_TREE` set, the preflight checks, the target manifest and the fast-forward could act on another repository. [#1031](https://github.com/foolzzz/looper/pull/1031) makes the upgrade refuse these cases and run its tools without the variables. An upgrade never runs code, imports Python modules or resolves git anywhere but in the service's own install.

**Breaking changes:** No. No API shape or migration changes. An upgrade started from a shell with one of the listed variables, or with another checkout's CLI, now fails with a message instead of proceeding.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#1031](https://github.com/foolzzz/looper/pull/1031); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.57
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.56 upgrades directly. This release adds no migration. If the upgrade now refuses because of a variable in your shell, unset it and run `looper service upgrade` again.

## Behavior changes

- **Refusal of overrides in the caller's shell ([#1031](https://github.com/foolzzz/looper/pull/1031)).** `looper service upgrade` (also with `--dry-run`) refuses, before it reads the unit, contacts the service or drains, when the caller's environment sets a Python import override with a non-empty value (`PYTHONPATH`, `PYTHONHOME`, `PYTHONUSERBASE`; Python ignores an empty one) or any git repository override, even an empty one (`GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`). The message names the variables and says to unset them and run the command again.
- **Refusal of another install's code.** After it has read the unit, and before it contacts the service or drains, the upgrade refuses when the package root of the running CLI is not the unit's package root, and tells the user to run `looper service upgrade` with the service's own `looper`.
- **Tools run without Python variables.** `uv sync`, `npm ci`, the dashboard build and the wheel installers now run without any `PYTHON*` variable and without `VIRTUAL_ENV`. Everything else the caller sets still reaches them: PATH, HOME, proxies, certificates, package indexes and mirrors, uv and npm caches and offline settings, the SSH agent. Upgrades behind a proxy or a mirror keep working. The wheel installer's existing redirect list is otherwise unchanged.
- **Unchanged.** The service unit's own check for Python overrides is unchanged (it shares the list of names). `looper service install` and `restart` install nothing and are unchanged. The unit's CLI is not re-executed. `PIP_*` and `UV_*` package-source and network settings are still passed on; dropping them was a maintainer decision and is not part of this release.
- **Model-visible changes:** No. No prompt, tool description, tool schema or Manager confirmation text changes.
- **Test changes.** Tests cover the refusals and the tool environment (`tests/test_service_upgrade_execution.py`, with small adjustments in `tests/test_service_upgrade.py`, `tests/db_support.py` and `tests/test_control_plane_lock_db.py`).

## 中文摘要

本版本是 patch release v2.14.57（热修线，每个合并的改动立即发布）。自 v2.14.56 以来只合并了一项改动：`looper service upgrade` 现在会拒绝来自调用者 shell 的导入和仓库覆盖变量，拒绝运行服务安装之外的代码，并在不带这些变量的环境中运行工具（[#1031](https://github.com/foolzzz/looper/pull/1031)）。

### 升级决策

**谁需要升级：**运行 `looper service upgrade` 的用户，尤其是 shell 中导出了 `PYTHONPATH`、`GIT_DIR` 等变量，或使用属于另一个检出目录的 `looper` 命令的用户。

**解决了什么：**升级会检查 CLI 的解释器和（检出目录升级时）工作目录是否属于 unit，但不检查正在运行的 CLI 代码来自哪里，还会把调用者的整个环境传给 `uv sync`、`npm ci` 和仪表盘构建，git 也会继承。`PYTHONPATH` 指向另一个检出目录时，控制台脚本可能运行那个目录的升级代码，变量还会传到构建工具；设置 `GIT_DIR` 或 `GIT_WORK_TREE` 时，预检、目标清单和快进都可能作用于另一个仓库。[#1031](https://github.com/foolzzz/looper/pull/1031) 让升级拒绝这些情况，并在不带这些变量的环境中运行工具。升级不会在服务自身安装之外运行代码、导入 Python 模块或解析 git。

**是否有破坏性变更：**否。API 形态和迁移不变。在带有上述变量的 shell 中、或使用另一个检出目录的 CLI 发起升级，现在会报错而不是继续。

**如何验证：**运行 `looper --version` 核对版本为 2.14.57。

**贡献者：**维护者 @foolzzz 提交 [#1031](https://github.com/foolzzz/looper/pull/1031)；本版本无社区贡献。

```bash
looper --version   # looper 2.14.57
```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.56 上的安装可直接升级。本版本没有新迁移。如果升级因 shell 中的变量而被拒绝，请取消设置该变量后重新运行 `looper service upgrade`。

### 行为变化与入口

- **拒绝调用者 shell 中的覆盖变量（[#1031](https://github.com/foolzzz/looper/pull/1031)）。**当调用者环境设置了非空的 Python 导入覆盖（`PYTHONPATH`、`PYTHONHOME`、`PYTHONUSERBASE`；Python 会忽略空值），或任何 git 仓库覆盖（即使为空：`GIT_DIR`、`GIT_WORK_TREE`、`GIT_COMMON_DIR`、`GIT_INDEX_FILE`、`GIT_OBJECT_DIRECTORY`、`GIT_ALTERNATE_OBJECT_DIRECTORIES`）时，`looper service upgrade`（包括 `--dry-run`）会在读取 unit、联系服务和排空之前拒绝。提示会列出变量名，并要求取消设置后重新运行。
- **拒绝其他安装的代码。**读取 unit 之后、联系服务和排空之前，如果正在运行的 CLI 的包根目录不是 unit 的包根目录，升级会拒绝，并提示使用服务自己的 `looper` 运行 `looper service upgrade`。
- **工具在不带 Python 变量的环境中运行。**`uv sync`、`npm ci`、仪表盘构建和 wheel 安装器现在不带任何 `PYTHON*` 变量和 `VIRTUAL_ENV` 运行。调用者设置的其余变量仍会传给它们：PATH、HOME、代理、证书、包索引和镜像、uv 与 npm 缓存和离线设置、SSH agent。因此代理或镜像后的升级仍然可用。wheel 安装器原有的重定向列表其余不变。
- **不变。**服务 unit 自身的 Python 覆盖检查不变（现共用同一份变量名列表）。`looper service install` 和 `restart` 不安装任何内容，不变。不会重新执行 unit 的 CLI。`PIP_*` 和 `UV_*` 的包源与网络设置仍会传递；去掉它们属于维护者的决定，不在本版本内。
- **面向模型的变化：**无。不改变提示、工具描述、工具 schema 或 Manager 的确认文字。
- **测试改动。**测试覆盖了这些拒绝和工具环境（`tests/test_service_upgrade_execution.py`，另在 `tests/test_service_upgrade.py`、`tests/db_support.py` 和 `tests/test_control_plane_lock_db.py` 中有小调整）。

# Looper v2.15.26

This release documents the changes merged since v2.15.25, including eight pulls that merged after that release's scope was frozen and were not on the v2.15.25 tag ([#1493](https://github.com/foolzzz/looper/pull/1493), [#1514](https://github.com/foolzzz/looper/pull/1514), [#1513](https://github.com/foolzzz/looper/pull/1513), [#1487](https://github.com/foolzzz/looper/pull/1487), [#1518](https://github.com/foolzzz/looper/pull/1518), [#1519](https://github.com/foolzzz/looper/pull/1519), [#1502](https://github.com/foolzzz/looper/pull/1502), [#1517](https://github.com/foolzzz/looper/pull/1517)). The assistant phase-1 wiring of the Manager is in, and every new switch stays off. Per-turn context and speaker authorization ([#1559](https://github.com/foolzzz/looper/pull/1559), `manager.turn_context.enabled`) now change a user turn when the string is `true`. The operator's new message can join the running turn ([#1560](https://github.com/foolzzz/looper/pull/1560), `manager.mid_turn_input.enabled`, default off). An empty reply can be recovered and a silent run of tools reminded ([#1542](https://github.com/foolzzz/looper/pull/1542), `manager.delivery_guard.enabled`, default off). A reply turn can apply the session budget ([#1543](https://github.com/foolzzz/looper/pull/1543), `manager.turn_budget_usd`, off unless it is a positive finite number). The operator-only persona can be stored ([#1533](https://github.com/foolzzz/looper/pull/1533), `manager.persona`, unset; storing it changes no prompt). Sessions can be listed and reset from the dashboard ([#1548](https://github.com/foolzzz/looper/pull/1548); no new setting). Per-chat session routing stays off ([#1518](https://github.com/foolzzz/looper/pull/1518), [#1519](https://github.com/foolzzz/looper/pull/1519), `manager.session_routing.enabled`; `manager.sessions.max_resident` defaults to 2). The outbound gateway and durable Lark outbox stay off ([#1487](https://github.com/foolzzz/looper/pull/1487), `channels.outbound.enabled`). Telegram writes can use that gateway ([#1529](https://github.com/foolzzz/looper/pull/1529)). Chat task notices ([#1528](https://github.com/foolzzz/looper/pull/1528)), subscription digests ([#1532](https://github.com/foolzzz/looper/pull/1532)) and proactive intent pushes ([#1537](https://github.com/foolzzz/looper/pull/1537)) pass delivery only while `delivery.enabled` is the string `true`, which stays off. The dashboard can show outbound gateway figures ([#1545](https://github.com/foolzzz/looper/pull/1545)). The untrusted fence stays off ([#1517](https://github.com/foolzzz/looper/pull/1517), [#1526](https://github.com/foolzzz/looper/pull/1526), [#1539](https://github.com/foolzzz/looper/pull/1539), `untrusted_fence.enabled`). Outbound review stays off ([#1493](https://github.com/foolzzz/looper/pull/1493), [#1500](https://github.com/foolzzz/looper/pull/1500), `outbound_review.enabled`). Provider limit signals stay off ([#1502](https://github.com/foolzzz/looper/pull/1502), `engine.limit_signals.enabled`). Memory candidates are tables, a setting and reads ([#1513](https://github.com/foolzzz/looper/pull/1513), `memory_write` absent means off); nothing drafts or writes a candidate. Failed-run classification stays off ([#1514](https://github.com/foolzzz/looper/pull/1514), `engine.failure_typing` default `off`). A schedule's active hours and idle-only skip stay unset, so existing schedules fire as before ([#1491](https://github.com/foolzzz/looper/pull/1491)). Tests, evals and the migration registry layout do not change runtime behavior ([#1546](https://github.com/foolzzz/looper/pull/1546), [#1553](https://github.com/foolzzz/looper/pull/1553), [#1556](https://github.com/foolzzz/looper/pull/1556), [#1558](https://github.com/foolzzz/looper/pull/1558), [#1561](https://github.com/foolzzz/looper/pull/1561), [#1527](https://github.com/foolzzz/looper/pull/1527)). Five pull requests are documentation only ([#1544](https://github.com/foolzzz/looper/pull/1544), [#1547](https://github.com/foolzzz/looper/pull/1547), [#1551](https://github.com/foolzzz/looper/pull/1551), [#1555](https://github.com/foolzzz/looper/pull/1555), [#1564](https://github.com/foolzzz/looper/pull/1564)). The v2.15.25 release pull request ([#1557](https://github.com/foolzzz/looper/pull/1557)) is not a change in this release. This release is frozen at the commit that contains main through [#1500](https://github.com/foolzzz/looper/pull/1500). It is tagged on its release commit, so it does not contain the pulls merged into main after the freeze ([#1508](https://github.com/foolzzz/looper/pull/1508), [#1567](https://github.com/foolzzz/looper/pull/1567), [#1568](https://github.com/foolzzz/looper/pull/1568), [#1571](https://github.com/foolzzz/looper/pull/1571) and any other merged before the tag); they ship in the next release.

No new capability in this release is on by default.

## Release Decision

**Who should upgrade:** Anyone who will turn on turn context, mid-turn input, the delivery guard, a session budget, a persona, session routing, the outbound gateway, delivery for task notices, digests or intent pushes, the untrusted fence, outbound review, limit signals, failure typing, or memory candidates, and anyone whose schedules should gain active hours or an idle-only skip. An installation that turns none of them on still applies the additive migrations at startup. With those switches left off, the Manager's prompts and tool lists stay as in v2.15.25, apart from the columns and read fields named under Behavior changes. `web/` changed, so the dashboard bundle is rebuilt by the release workflow as usual.

**What this release solves:** The operator can put time, speaker, chat and reply language on a user turn, merge a new message into that turn, recover an empty reply, bound a session after the reply is handed off, store a persona, and give a group or another sender's direct chat its own session. Lark and Telegram writes can share one gateway. Task notices, subscription digests and intent pushes can pass one recorded delivery decision. Outside text can be fenced, external writes can be reviewed, provider windows can be recorded, and a failed run can be classified. Memory-candidate storage can be configured. Each of these stays off until set. Existing schedules keep firing until active hours or idle-only is set.

**Breaking changes:** No. No existing API drops a field that a caller must send. There are additive PostgreSQL migrations. Four of them have an online validation or index step, and the channel-outbox block can fill `first_possible_at` on a row that already has attempts (see Upgrading). The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older. New operator operations include `mid_turn_input.get`, `mid_turn_input.update`, `manager_persona.get`, `manager_persona.update`, `session_routing.get`, `session_routing.update`, `manager_sessions.list`, `manager_sessions.reset`, `outbound_gateway.get`, `outbound_gateway.update`, `outbound_review.get`, `outbound_review.update`, `providers.limits`, `engine_settings.get`, `engine_settings.update`, `limit_signals_settings.get`, `limit_signals_settings.update`, `mcp_tool_levels.get`, `mcp_tool_levels.put`, `runs.failures`, and the memory list, get, settings and check operations. `manager_metrics.get` gains outbound fields. `runs.get` and `runs.list` gain nullable failure fields.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.15.26
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.15.25 upgrades directly. Restart the service after upgrading, as for every release. `web/` changed, so the release workflow rebuilds the dashboard bundle from `web/` into the wheel, as usual. This pull request does not commit that bundle.

This release has additive PostgreSQL migrations, applied once at startup, inside the schema transaction. Four of them have an online step, named below. The others do not. A fresh database creates the same objects from `schema.sql` plus each module's `fresh_ddl`, and does not record a separate migration for a table it already has. A database that has not yet finished an earlier online step still runs that step. [#1527](https://github.com/foolzzz/looper/pull/1527) moves every migration into its own module, including the six this release introduces ([#1487](https://github.com/foolzzz/looper/pull/1487), [#1493](https://github.com/foolzzz/looper/pull/1493), [#1502](https://github.com/foolzzz/looper/pull/1502), [#1513](https://github.com/foolzzz/looper/pull/1513), [#1514](https://github.com/foolzzz/looper/pull/1514), [#1518](https://github.com/foolzzz/looper/pull/1518)); it adds no schema. The online markers it moves for migrations that already shipped are `run_tree_online`, `step_difficulty_online`, `schedule_notification_events_online`, `manager_event_reasons_online`, `manager_event_delivery_online`, `leads_check_online`, `run_skips_online`, `mid_turn_input_online`, `headless_compaction_online`, `outbound_reviews_online` and `uncertain_deliveries_online`. Those markers are not new. `gateway_aliases` is still absent from admission probes.

- `channel_outbox` ([#1487](https://github.com/foolzzz/looper/pull/1487)): creates `channel_outbox`, `idx_channel_outbox_due` (partial, `pending` or `sending`) and `idx_channel_outbox_created`. `kind` is `send` or `reply`. `source` is `answer`, `notice`, `progress`, `post` or `notify`. `state` is `pending`, `sending`, `sent`, `failed` or `uncertain`, default `pending`. `error_class` is `rate_limited`, `rejected`, `transient` or `unknown`. Unique on `(channel_id, idempotency_key)`. `state` is `sent` exactly when `sent_at` is set. No online step. The schema block ends with `UPDATE channel_outbox SET first_possible_at=created_at WHERE attempts>0 AND first_possible_at IS NULL`. A new empty table changes no row. A table that already had attempts and a null `first_possible_at` gets that timestamp set to `created_at`. Rows are written only while `channels.outbound.enabled` is on, except recovery of rows that were already stored.
- `channel_outbox_terminal_at` ([#1545](https://github.com/foolzzz/looper/pull/1545)): `ALTER TABLE channel_outbox ADD COLUMN IF NOT EXISTS terminal_at TIMESTAMPTZ`. No row rewrite. No online step.
- `failure_typing` ([#1514](https://github.com/foolzzz/looper/pull/1514)): adds nullable `llm_records.failure_class` and `failure_cause`, and `llm_records_failure_check` `NOT VALID`. No row rewrite. Online step `failure_typing_online` validates that check and creates `idx_llm_records_failures` on `created_at` where `failure_class` is not null.
- `gate_message_sender` ([#1539](https://github.com/foolzzz/looper/pull/1539)): `ALTER TABLE task_user_gate_messages ADD COLUMN from_operator BOOLEAN`, nullable, no default. No row rewrite. No online step.

No default and no constraint. No row rewrite. No online step. `manager_sessions` already includes the same two columns on its own table.

## Behavior changes

### Turn context, wired, off ([#1559](https://github.com/foolzzz/looper/pull/1559))

v2.15.25 stored the setting and injected nothing. This release injects it when the string is `true`.

- **`manager.turn_context.enabled` defaults off.** No row, or any value other than the string `true`, leaves it off. `user.timezone` absent means the server's zone. `user.reply_language` absent, or any stored value other than `zh-CN` or `en`, is `zh-CN`. `chat_settings` does not carry these fields.
- **Only the operator can read or set them.** `POST /api/v1/turn_context_settings/get` and `POST /api/v1/turn_context_settings/update` are operator-only. The update is high risk and declares confirmation. `null` on a field restores that default. Enabling returns `missing_operator_ids` for enabled bots with no operator id. An API client token gets 403.
- **While it is on,** a user turn replaces the Channel line with `[Turn context]` (local time, speaker, chat, reply language). The system contract adds `TURN_CONTEXT_CONTRACT`. The time stays out of stable state and out of the process signature. The turn sets `Turn.speaker`. Another allowlisted sender, and a group member, cannot request or confirm an escalation. A refused confirmation is discarded. The operator's own messages in a group, and the operator's API client, can authorize. Private tools keep their operator-turn checks. A completion turn and an autonomous turn keep their existing messages and have no speaker.
- **While it is off,** prompts, tools and launches match a turn with the setting absent.

### Mid-turn input, off ([#1560](https://github.com/foolzzz/looper/pull/1560))

- **`manager.mid_turn_input.enabled` defaults off.** No row, or any value other than the string `true`, leaves it off. Only the operator can call `mid_turn_input.get` and `mid_turn_input.update` (`enabled`; `null` restores off). The update is high risk. It is not on `chat_settings`. No chat command and no Manager tool changes it. The dashboard does not save it in this release.
- **While it is on,** the default Manager can take a user message even when session routing is off. At most three plain-text operator messages join an operator's running user turn. The runtime must declare `MID_TURN_INPUT`, and the resident must accept native input (non-hosted Claude Code). Both sides must resolve to the operator. Other sessions, API clients, commands, gate or intent replies, attachments, quotes, and a chat with a pending confirmation stay queued. With routing off, the added message must be the same chat. A failed or late write queues the message. If a result arrives after the write, the resident is retired before the queue fallback. The original tool binding stays. The final reply goes to the original chat and to each addition from another chat. A same-chat web addition gets a terminal acknowledgement. A same-chat Lark or Telegram addition does not get a second reply. Any participating chat can stop the turn. Additions settle only after the reply is handed off. Shutdown before that handoff leaves them replayable. An explicit stop withdraws them and settles every associated message at once. The record is `metadata.merged`. When metrics are on, acknowledgement and first-reply latency are recorded too. A failed resume carries additions that were already accepted into its retry, even if the switch was turned off after the accept.
- **While it is off,** a later message stays a separate turn. Prompts, the system text, tools and the command line match the previous release. This release does not add a `mid_turn_input` migration; that migration shipped earlier.

### Delivery guard, wired, off ([#1542](https://github.com/foolzzz/looper/pull/1542))

v2.15.24 stored the setting and did not apply it. This release applies it when the string is `true`.

- **`manager.delivery_guard.enabled` defaults off.** No row, or any value other than the string `true`, leaves it off. Only the operator can call `delivery_guard.get` and `delivery_guard.update` (`enabled`; `null` restores off). The update is high risk. It is not on `chat_settings`. This release adds no dashboard control for the switch.
- **While it is on,** a user turn owes a delivery (`owed`) until a non-empty top-level text pays it (`paid`). A completion turn and an autonomous turn are exempt. After a successful empty reply, at most two hidden follow-ups run (`MAX_FOLLOWUPS` is 2). The follow-up text is `[Looper] Your last turn ended without any reply to the user. Reply now with the result, or with what blocked you and what you need from them. Do not start new work.` A failed follow-up selects the fixed notice `这次没拿到结果：管家连续几次都没有给出回复。可以再问一次；反复出现的话发 /new 换一个新会话。` with error `no reply after follow-ups`. A stop keeps the normal stop. An initial error, a process exit, a spend cap, an unavailable tool, or a refused token does not start a follow-up. Six consecutive top-level tool calls (`SILENT_TOOLS` is 6) select a same-turn reminder, at most twice (`MAX_REMINDERS` is 2), only when the runtime declares `MID_TURN_INPUT` and the active session is a direct resident stream-json process. A keeper-hosted or runner-hosted session is excluded. Only Claude Code declares the capability. The reminder is model input. It is not a separate channel message. A hidden follow-up sends only that fixed text in the same session, without user-turn context, sections, or a channel line. Records use `metadata.delivery_guard.followup`, `metadata.delivery_guard.for` and `metadata.delivery_guard.reminders`.
- **While it is off,** replies, prompts, command lines, record writes and channel calls are unchanged.

### Session budget, wired, off ([#1543](https://github.com/foolzzz/looper/pull/1543))

v2.15.24 stored a budget and did not call it from a turn. This release calls it after a user or completion reply is handed to its channel.

- **`manager.turn_budget_usd` is on only as a positive finite number.** No row, or any other stored value, leaves it off. `recommended_usd` is 4.0. Only the operator can call `session_budget.get` and `session_budget.update`. `null` deletes the row. The update is high risk. There is still no dashboard control and no settings price warning.
- **While it is set,** the turn keeps the session lock, records context and the turn cost, and applies `decide`. Unknown context keeps the session. Unknown cost skips the cost rule. The context threshold is `scheduler.session_context_max_tokens` (default `100000`; the stored range is 40000 to 100000000). Over that threshold, a running session whose runtime declares `HEADLESS_COMPACTION` gets one recorded maintenance `/compact`. A failed exchange, a missing `compact_boundary`, or context still over the threshold queues a rotation. A runtime without the capability rotates directly. At half the context threshold or more, a turn that costs more than half its budget also rotates. Rotation stops the process. The next turn resumes the old session for its handoff and starts a new one. `main` also receives the Manager's three latest ended task results. A group or direct-chat session keeps only its own chat excerpt. Measurements are stored on that session's own row. Compactions and rotations carry `metadata.session_bound`. The same number is also a per-turn soft cap, including a subscription run priced from the model catalog. The existing process budget is unchanged. A capped turn gets the fixed over-cap reply. ### 升级决策

**谁需要升级：**要打开回合上下文、中途输入、投递守卫、会话预算、人格、会话路由、出站网关、任务通知或摘要或意图推送的投递、不可信围栏、出站复核、限额信号、失败分类或记忆候选的安装，以及要给定时任务加上活跃时间或空闲才跑的安装。这些都不打开的安装，启动时仍会执行可加的迁移。开关保持关闭时，Manager 的提示词和工具列表与 v2.15.25 相同，行为变化里点名的列和读取字段除外。`web/` 有改动，仪表盘包由发布流程照常重新构建。

**解决了什么：**操作者可以把时间、说话人、会话和回复语言放进用户回合，把新消息并入这个回合，补上一次空回复，在回复交给渠道之后约束会话，存一份人格，并让群或其他发送者的私聊使用自己的会话。Lark 和 Telegram 的写可以共用一个网关。任务通知、订阅摘要和意图推送可以先过一次有记录的投递决定。外部文本可以围起来，外部写入可以复核，服务商窗口可以记下，失败的运行可以分类。记忆候选的存储可以配置。这些在设置之前都是关的。已有的定时任务在设置活跃时间或空闲才跑之前，触发方式不变。

**是否有破坏性变更：**无。已有 API 没有去掉调用方必须发送的字段。有可加的 PostgreSQL 迁移。其中四项有在线校验或索引步骤，发件箱那一段还会给已经有尝试次数的行补上 `first_possible_at`（见升级）。桥接边界不变：早于 v2.13.165 的安装须先升级到 v2.13.165。新的操作者操作包括 `mid_turn_input.get`、`mid_turn_input.update`、`manager_persona.get`、`manager_persona.update`、`session_routing.get`、`session_routing.update`、`manager_sessions.list`、`manager_sessions.reset`、`outbound_gateway.get`、`outbound_gateway.update`、`outbound_review.get`、`outbound_review.update`、`providers.limits`、`engine_settings.get`、`engine_settings.update`、`limit_signals_settings.get`、`limit_signals_settings.update`、`mcp_tool_levels.get`、`mcp_tool_levels.put`、`runs.failures`，以及记忆的列表、读取、设置和检查。`manager_metrics.get` 多了出站字段。`runs.get` 和 `runs.list` 多了可空的失败字段。

### 行为变化

**回合上下文，已接线，默认关闭（[#1559](https://github.com/foolzzz/looper/pull/1559)）**

v2.15.25 只存这个设置，不注入。本版本在值为字符串 `true` 时注入。

- **`manager.turn_context.enabled` 默认关闭。**没有这一行，或取值不是字符串 `true`，都算关闭。没有 `user.timezone` 就用服务器的时区。没有 `user.reply_language`，或存的值不是 `zh-CN` 或 `en`，就是 `zh-CN`。`chat_settings` 不带这些字段。
- **只有操作者能读或写。**`POST /api/v1/turn_context_settings/get` 和 `POST /api/v1/turn_context_settings/update` 只给操作者。更新是高风险，并声明要确认。某个字段的 `null` 恢复那个默认。打开时返回 `missing_operator_ids`（已启用但没有操作者 id 的机器人）。API 客户端令牌得到 403。
- **打开之后，**用户回合用 `[Turn context]` 替换 Channel 那一行（本地时间、说话人、会话、回复语言）。系统契约加上 `TURN_CONTEXT_CONTRACT`。时间不进稳定内容，也不进进程签名。这一回合设置 `Turn.speaker`。允许名单里的其他人，以及群成员，不能请求或确认升级。被拒绝的确认丢掉。操作者自己在群里的消息，以及操作者的 API 客户端，可以授权。私有工具仍按操作者回合检查。完成回合和自主回合保持原有消息，没有说话人。
- **关闭时，**提示词、工具和启动与没有这个设置时相同。

**中途输入，默认关闭（[#1560](https://github.com/foolzzz/looper/pull/1560)）**

- **`manager.mid_turn_input.enabled` 默认关闭。**没有这一行，或取值不是字符串 `true`，都算关闭。只有操作者能 `mid_turn_input.get` 和 `mid_turn_input.update`（`enabled`；`null` 恢复关闭）。更新是高风险。不在 `chat_settings` 上。没有聊天命令，也没有 Manager 工具能改它。本版本的仪表盘不保存它。
- **打开之后，**默认 Manager 在会话路由关闭时也能接收用户消息。最多三条纯文本的操作者消息并入该操作者正在跑的用户回合。运行时必须声明 `MID_TURN_INPUT`，常驻进程必须接受原生输入（非托管的 Claude Code）。两边都必须解析成操作者。其他会话、API 客户端、命令、关卡或意图回复、附件、引用，以及有未完成确认的会话，仍排队。路由关闭时，追加的消息必须是同一个会话。写入失败或来晚了就排队。若结果在写入之后到达，常驻进程先退出，再走队列回退。原来的工具绑定保持。最终回复发到原会话，以及每一个来自其他会话的追加。同一个会话的网页追加得到一条终态确认。同一个会话的 Lark 或 Telegram 追加不再发第二条回复。参与的任何一个会话都可以停止这一回合。追加只在回复交出之后才结算。交出之前关闭服务，它们仍可重放。明确的停止会撤回它们，并立刻结算所有相关消息。记录是 `metadata.merged`。度量打开时，也记下确认和首条回复的延迟。失败后的恢复会带上已经接受的追加，即使接受之后开关被关掉。
- **关闭时，**后来的消息仍是单独的回合。提示词、系统文本、工具和命令行与上一版本相同。本版本不加 `mid_turn_input` 迁移；那次迁移已经发布过。

**投递守卫，已接线，默认关闭（[#1542](https://github.com/foolzzz/looper/pull/1542)）**

v2.15.24 只存这个设置，不执行。本版本在值为字符串 `true` 时执行。

- **`manager.delivery_guard.enabled` 默认关闭。**没有这一行，或取值不是字符串 `true`，都算关闭。只有操作者能 `delivery_guard.get` 和 `delivery_guard.update`（`enabled`；`null` 恢复关闭）。更新是高风险。不在 `chat_settings` 上。本版本不为这个开关加仪表盘控件。
- **打开之后，**用户回合欠一次交付（`owed`），直到非空的顶层文本付清（`paid`）。完成回合和自主回合豁免。成功的空回复之后，最多两次隐藏的追问（`MAX_FOLLOWUPS` 为 2）。追问文本是 `[Looper] Your last turn ended without any reply to the user. Reply now with the result, or with what blocked you and what you need from them. Do not start new work.` 追问失败时选用固定通知 `这次没拿到结果：管家连续几次都没有给出回复。可以再问一次；反复出现的话发 /new 换一个新会话。`，错误是 `no reply after follow-ups`。停止保持原来的停止。一开始就出错、进程退出、花费上限、工具不可用或令牌被拒绝，都不开始追问。连续六次顶层工具调用（`SILENT_TOOLS` 为 6）会在同一回合里选一次提醒，最多两次（`MAX_REMINDERS` 为 2），并且只在运行时声明了 `MID_TURN_INPUT`、活动会话是直接常驻的 stream-json 进程时。keeper 托管或 runner 托管的会话除外。只有 Claude Code 声明这个能力。提醒是给模型的输入，不是单独的渠道消息。隐藏追问只在同一会话里发送那段固定文本，不带用户回合上下文、各节或 Channel 行。记录用 `metadata.delivery_guard.followup`、`metadata.delivery_guard.for` 和 `metadata.delivery_guard.reminders`。
- **关闭时，**回复、提示词、命令行、记录写入和渠道调用不变。

**会话预算，已接线，默认关闭（[#1543](https://github.com/foolzzz/looper/pull/1543)）**

v2.15.24 只存预算，回合不调用它。本版本在用户回合或完成回合的回复交给渠道之后调用它。

- **`manager.turn_budget_usd` 只有正的有限数字才打开。**没有这一行，或其他存值，都是关。`recommended_usd` 为 4.0。只有操作者能 `session_budget.get` 和 `session_budget.update`。`null` 删掉这一行。更新是高风险。仍没有仪表盘控件，也没有设置页上的价格警告。
- **设置之后，**这一回合保持会话锁，记下上下文和本回合花费，并执行 `decide`。上下文未知就保留会话。花费未知就跳过花费规则。上下文门槛是 `scheduler.session_context_max_tokens`（默认 `100000`；存下的范围是 40000 到 100000000）。超过这个门槛时，声明了 `HEADLESS_COMPACTION` 的运行中会话得到一次有记录的维护 `/compact`。交换失败、没有 `compact_boundary`，或上下文仍超过门槛，就排队轮换。没有这个能力的运行时直接轮换。上下文达到门槛的一半或更多，并且这一回合的花费超过预算的一半，也轮换。轮换停掉进程。下一回合先恢复旧会话做交接，再开始新会话。`main` 还会收到管家最近三条已结束任务的结果。群或私聊会话只保留自己会话的摘录。测量写在这个会话自己的行上。压缩和轮换带 `metadata.session_bound`。同一个数字也是每回合的软上限，包括按模型目录计价的订阅运行。已有的进程预算不变。触顶的回合得到固定的超限回复。下一条消息启动一个恢复该会话的进程。没有价格的模型不加软上限，每个 Profile 和模型记一次警告。
- **未设置时，**没有额外的记录器上限，不写测量，也不做维护检查。提示词、工具和命令行不变。

**人格，未设置，存下来也不改变提示词（[#1533](https://github.com/foolzzz/looper/pull/1533)）**

- **`manager.persona` 在设置之前不存在。**它是一个 JSON 对象。`name` 最多 20 字，`address` 20，`tone` 200，`notes` 400，四项合计最多 600。空的或只有空白的文本删掉这一行。存的值读不出来时不增加一节，并对这份载荷记一次 `manager.persona is unreadable`。
- **只有操作者能读或写。**`manager_persona.get` 是读，级别 inside。`manager_persona.update` 是写，级别 inside。`looper_settings` 不列出它。Settings → Chat 有这个表单。配置导出在存的值能读时把它放在 `settings.system` 下。导入按同样的上限检查。场景管家不继承它。
- **提示词不变，存了人格也一样。**`persona.section` 存在，但 `ManagerAgent._sections` 不调用它。它本来会用的标题是 `Persona (set by the operator: your name, how you address them, your tone; Looper's rules still apply):`。`section(..., group=True)` 只会留下 name 和 address，现在还没有调用方。

- **`manager.session_routing.enabled` 默认关闭。**没有这一行，或取值不是字符串 `true`，都算关闭。**`manager.sessions.max_resident` 默认 2**，范围 1 到 16。只有操作者能 `session_routing.get` 和 `session_routing.update`（`session_routing_enabled`、`max_resident`；`null` 恢复关闭和 2）。更新是高风险，并声明要确认。打开时返回 `missing_operator_ids`（私聊仍留在 `main` 的、没有操作者 id 的机器人）。仪表盘和生成的 CLI 用这些操作。`chat_settings` 仍只带停止回复、完成回合、查找顺序和账本。

**失败分类，默认关闭（[#1514](https://github.com/foolzzz/looper/pull/1514)）**

- **`engine.failure_typing` 默认 `off`。**没有这一行就是 `off`。`record` 分类并存储。`act` 在处理存在之前被拒绝。代码不认识的存值会记一条警告，并按关闭算。只有操作者能 `engine_settings.get` 和 `engine_settings.update`，`failure_typing` 为 `off`、`record` 或 `null`（恢复关闭）。生成的 CLI 是 `loopercli engine-settings`。它不是 Manager 工具。`runs.failures` 的 `days` 为 1 到 90，默认 7。
- **`record` 时的类别。**`quota` 是 `usage_limit` 或 `rate_limit`。`transient` 是 `connection_failed`、`provider_overloaded` 或 `start_timeout`。`environment` 是 `runtime_missing`、`login`、`tls` 或 `profile`。`judgment` 是 `timeout`、`context`、`budget`、`report` 或 `unknown`。`metadata.failure` 带信号 `typed` 或 `text`，以及 `resets_at`。以 `failed` 结束的记录会分类；Worker 或 Reviewer 的报告说这一步失败时也会（`reported_failed`、`contract`、`files_mismatch`）。Reviewer 的 `not_passed` 是结论，不是失败。`interrupted` 没有类别。keeper 的启动超时抛出 `RunStartTimeout`（`start_timeout`），不论这个设置开不开。Codex 可以带 `codex_error_info` 和 `will_retry`。会重试的错误不是这次运行的失败。API 结果可以带 `error_kind` 和 `error_status`。Codex exec 的文本按 codex-cli 0.169.0 匹配。这些元数据不给模型看。运行被分类时，仪表盘的运行卡片显示徽章。

**定时任务的活跃时间和空闲才跑，未设置（[#1491](https://github.com/foolzzz/looper/pull/1491)）**

- **已有的定时任务不改变触发方式。**`schedules.active_hours` 为 null 就是全天。存下的形式是 `HH:MM-HH:MM`，可以跨过午夜，两端必须不同。`schedules.idle_only` 是 `NOT NULL`，默认 false。立即运行从不受这个限制。创建和更新接受这两个字段。`null` 恢复默认。未设置时配置导出省略它们，所以未设置的任务导出仍逐字节相同。仪表盘表单还不编辑这两项。Manager 的 `looper_schedules` 工具说明不提供它们。

#### Turn context

**启用：**系统设置 `manager.turn_context.enabled` 为字符串 `true` 之前是关的。没有这一行，或其他取值，都算关。由操作者经 `POST /api/v1/turn_context_settings/update` 把 `turn_context_enabled` 设为 true。同一次调用可以设置 `timezone`（IANA 名，或 null 表示服务器时区）和 `reply_language`（`zh-CN` 或 `en`，默认 `zh-CN`）。调用立刻生效，并要求确认。API 客户端令牌得到 403。打开之后，用户回合带 `[Turn context]` 和说话人。

**验证：**没有这个设置时，`turn_context_settings.get` 回答 `turn_context_enabled` 为 false，用户回合与 v2.15.25 相同。为 `true` 时，同一回合的提示词包含 `[Turn context]`，群成员的升级被拒绝。

**停用 / 回退：**把 `turn_context_enabled` 设为 false 或 null。false 存成 `false`。null 删掉这一行。之后的用户回合没有回合上下文块，也没有这个功能设置的说话人。`timezone` 和 `reply_language` 是各自的键。

**权限边界：**只有操作者能读或写这些设置。API 客户端和 agent 令牌得到 403，被拒绝的更新什么都不写。说话人不授予工具。私有工具仍按自己的操作者回合检查。

#### Schedule throttle

**启用：**没有一个新的布尔开关把它打开。`schedules.active_hours` 为 null 就是全天，`schedules.idle_only` 默认 false，所以已有的定时任务仍按原来的方式触发。经定时任务的创建或更新 API，或生成的 CLI，在那一条任务上设置这两个字段。null 恢复默认。仪表盘表单还不编辑它们。管家的定时任务工具不提供它们。立即运行从不受这个限制。

**验证：**两个字段都未设置时，下一次触发与 v2.15.25 相同，这条任务的配置导出仍逐字节相同。设置了 `active_hours` 之后，窗口之外的触发不运行，`last_fired_at` 保持。`idle_only` 为 true 时，管家正忙时的触发是 `skipped_busy`。

**停用 / 回退：**把 `active_hours` 设为 null，把 `idle_only` 设为 false 或 null。任务重新全天触发，也不再因管家正忙而跳过。已经标成 `skipped_busy` 的运行留着。这两列留着，不会被删掉。

**权限边界：**本来就能创建或更新这条定时任务的人可以设置这两个字段。工具说明不把它们提供给模型。一次跳过不自己写模型回合。标签「跳过（管家正在回复消息）」只在一次运行因这个原因被跳过时才是模型能看见的文本。

**文档：**https://github.com/foolzzz/looper/blob/v2.15.26/docs/architecture/agent-system.md#schedules-tasks-on-a-time-rule

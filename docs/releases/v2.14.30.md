# Looper v2.14.30

This is the patch release v2.14.30, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.29: `looper service install` now installs the periodic health probe unit ([#952](https://github.com/foolzzz/looper/pull/952)).

## Release Decision

**Who should upgrade:** Operators who run Looper as a background service (`looper service install`) and want an independent alert when it stops answering. Everyone else sees no change in how tasks, schedules and Agent Profiles run.

**What this release solves:** v2.14.28 added `looper service probe`, but nothing ran it periodically, so the operator had to schedule it. [#952](https://github.com/foolzzz/looper/pull/952) makes `looper service install` register a unit that runs the probe every 60 seconds when the ops file has a `[probe]` section.

**Breaking changes:** No. No API, default or existing behavior is removed, and there is no database migration. A service installed without `[probe]` gets no probe unit.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#952](https://github.com/foolzzz/looper/pull/952); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.30
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.29 upgrades directly. This release adds no migration. An existing service gets its probe unit the next time `looper service install` runs.

## Behavior changes

- **The probe is installed with the service ([#952](https://github.com/foolzzz/looper/pull/952)).**
  - When the ops file has `[probe]` with a chat, `looper service install` writes and loads a second unit after the server is up. It runs `looper service probe` every 60 seconds and writes `logs/probe.log` under the runtime root. On macOS the unit is a LaunchAgent named `<label>.probe`; on Linux it is `<label>-probe.service` with a `<label>-probe.timer`.
  - The probe unit carries only the path, locale, time zone and network settings from the install environment, never runtime API keys.
  - Without a configured probe chat, install prints that the probe is not configured and removes any probe unit left by an earlier install. A probe that fails to load is reported on the `probe` line of the install output, its partial unit is removed, and the install of the server still succeeds.
  - `looper service uninstall` removes the probe unit first. `looper service status` adds a `probe` line (installed or not) and a `last check` line with the last verdict, an active alert and the last send error, also when the service itself is not installed.
  - `looper service restart` re-aligns the probe's port with the server's: only a `--port` override given to `install` is stored in the probe unit, otherwise the probe reads the ops file's port each run.
  - `looper service probe` gains `--port`. It now checks the ops file's `server.host` (a wildcard or empty host means loopback) instead of always `127.0.0.1`.
  - For `notify_channel = "lark_bot"` the probe now picks the bot from the `lark_bot` channel configs, matching `probe.lark_profile` against the channel id or profile when set, and uses it only when exactly one matches. It no longer reads a fixed channel id. With a reachable database and no unique match it discards the cached credentials; with an unreachable database it reuses the cache only if the cache was written for the same profile. A healthy check also refreshes the cache before the first outage. The Lark CLI path sends with the Lark CLI's own environment instead of the shared child environment.
- **Model-visible changes:** None. No prompt, tool or message text given to a model changes; the probe sends its own alert text to the operator's chat, not through a model.

## Optional Capability Activation & Use

### Service probe

**Activation:** Add a `[probe]` section with `notify_channel` and `notify_chat` to the ops file, then run `looper service install`. The install registers the periodic unit. `looper service probe` still runs one check by hand.

**Validation:** Run `looper service status`; the `probe` line reads `installed` and `last check` shows the latest verdict after a minute.

**Disable / rollback:** Remove the `[probe]` section and run `looper service install` again, or run `looper service uninstall`; both remove the probe unit.

**Authority boundary:** The unit runs as the installing user with only path, locale, time zone and network settings. It reads `system.health` on the server's port with the operator token and sends only as the Lark bot, not through the server.

```bash
looper service install
looper service status
```

## 中文摘要

本版本是 patch release v2.14.30（热修线，每个合并的改动立即发布）。自 v2.14.29 以来只合并了一项改动：`looper service install` 现在会安装周期性健康探针单元（[#952](https://github.com/foolzzz/looper/pull/952)）。

### 升级决策

**谁需要升级：**以后台服务方式运行 Looper（`looper service install`），并希望在服务不再响应时收到独立告警的运维者。其他人在任务、定时任务和 Agent Profile 的运行方式上没有变化。

**解决了什么：**v2.14.28 加入了 `looper service probe`，但没有东西周期性运行它，需要运维者自己安排。[#952](https://github.com/foolzzz/looper/pull/952) 让 `looper service install` 在 ops 文件有 `[probe]` 小节时注册一个每 60 秒运行一次探针的单元。

**是否有破坏性变更：**否。不移除任何 API、默认值或现有行为，也没有数据库迁移。没有 `[probe]` 的服务不会得到探针单元。

**如何验证：**运行 `looper --version` 核对版本为 2.14.30。

**贡献者：**维护者 @foolzzz 提交 [#952](https://github.com/foolzzz/looper/pull/952)；本版本无社区贡献。

```bash
looper --version   # looper 2.14.30
```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.29 上的安装可直接升级。本版本没有迁移。已有服务在下一次运行 `looper service install` 时得到探针单元。

### 行为变化与入口

- **探针随服务安装（[#952](https://github.com/foolzzz/looper/pull/952)）。**
  - ops 文件有 `[probe]` 且配置了聊天时，`looper service install` 在服务器启动后写入并加载第二个单元，每 60 秒运行一次 `looper service probe`，日志写入运行时根目录下的 `logs/probe.log`。macOS 上是名为 `<label>.probe` 的 LaunchAgent；Linux 上是 `<label>-probe.service` 加 `<label>-probe.timer`。
  - 探针单元只带安装环境中的路径、区域设置、时区和网络设置，不带运行时 API 密钥。
  - 没有配置探针聊天时，install 会提示探针未配置，并移除早先安装留下的探针单元。探针加载失败会显示在 install 输出的 `probe` 行，残留单元被移除，服务器本身的安装仍然成功。
  - `looper service uninstall` 先移除探针单元。`looper service status` 增加 `probe` 行（是否已安装）和 `last check` 行（最近结论、进行中的告警、最近发送错误），服务本身未安装时也显示。
  - `looper service restart` 让探针的端口与服务器对齐：只有给 `install` 的 `--port` 覆盖值会写入探针单元，否则探针每次运行读取 ops 文件中的端口。
  - `looper service probe` 新增 `--port`，并改为检查 ops 文件的 `server.host`（通配或空主机视为回环），不再固定为 `127.0.0.1`。
  - `notify_channel = "lark_bot"` 时，探针现在从 `lark_bot` 渠道配置中选择机器人：设置了 `probe.lark_profile` 时按渠道 id 或 profile 匹配，且只在恰好匹配一个时使用，不再读取固定的渠道 id。数据库可达但没有唯一匹配时丢弃缓存凭据；数据库不可达时，只有缓存是为同一 profile 写入时才复用。健康检查通过时会在首次故障前刷新缓存。Lark CLI 路径改用 Lark CLI 自己的环境发送，不再使用共享的子进程环境。
- **面向模型的变化：**无。给模型的提示词、工具或消息文本都不变；探针把自己的告警文本发到运维者的聊天，不经过模型。

### 可选能力启用与使用

#### Service probe

**启用：**在 ops 文件中加入含 `notify_channel` 和 `notify_chat` 的 `[probe]` 小节，然后运行 `looper service install`，安装会注册周期性单元。`looper service probe` 仍可手动执行一次检查。

**验证：**运行 `looper service status`；`probe` 行显示 `installed`，一分钟后 `last check` 显示最近的结论。

**停用 / 回退：**删除 `[probe]` 小节后再次运行 `looper service install`，或运行 `looper service uninstall`；两者都会移除探针单元。

**权限边界：**单元以安装者身份运行，只带路径、区域设置、时区和网络设置。它用操作者令牌读取服务器端口上的 `system.health`，只以 Lark 机器人发送，不经过服务。

```bash
looper service install
looper service status
```

**文档：**[Agent system](https://github.com/foolzzz/looper/blob/v2.14.30/docs/architecture/agent-system.md)和 `looper service probe --help` 的说明。

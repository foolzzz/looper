# Looper v2.12.4

## Release Decision

**Who should upgrade:** Operators whose tasks need to return after an external event, such as a pull request author's next push, CI finishing or another job becoming ready.

**What this release solves:** A Planner can add a plan step of `kind: "wait"` for a time and an optional check. Looper checks it without holding a Worker or a Worker/Reviewer concurrency slot and resumes dependent steps when ready. Timeouts notify the user and give the Planner a `[WAIT]` turn; the dashboard offers Resume now and Cancel. See [#247](https://github.com/foolzzz/looper/pull/247).

**Breaking changes:** No. Existing work steps keep their behavior and command checks are off by default. Every task's Planner reply contract gains wait-step guidance, even when the task does not use waits. API consumers must recognize the new task status `waiting` in the `in_progress` group and step kind `wait`.

**How to verify:** Re-run `install.sh`, restart with the existing configuration and runtime root, and check the version below. On a disposable server, ask for a short timed wait followed by a step that reports its resolution. Check that the task says Waiting with no Worker running, and that the dependent step starts when ready. Exercise a timeout, Resume now and Cancel on separate waits; check the Planner's next decision. Stop and restart a waiting task to read back its saved deadline and state. See the activation entries for check permissions and limits.

**Contributors:** Release maintainer @foolzzz, author of [#247](https://github.com/foolzzz/looper/pull/247); no community contribution was included in this patch.

## Behavior changes

- **Wait for an external event within a plan.** Once its dependencies finish, a `wait` step opens with a required `max_wait_seconds`, an optional earliest time (`not_before_seconds` or timezone-qualified `not_before`) and an optional check. With no check it ends at the earliest time; with a check, both the earliest time and readiness must be satisfied. Only dependent steps wait; unrelated work continues. A ready wait is completed without a model turn, and dependent steps receive its resolution. No Worker or Reviewer runs for the wait itself, and it holds no worker concurrency slot. When only waits remain, the task reports `waiting` in In progress; a user gate takes precedence as `waiting_user`.
- **Typed GitHub checks and explicitly enabled shell checks.** `github_pr` uses a fixed, read-only `gh pr view` to watch `head_changed`, `checks_finished` or `new_comments`, with the first successful view retained as its baseline. A merged or closed PR also becomes ready. `checks_finished` means all reported checks have finished, including failures, and requires at least one check; it does not mean CI passed. A shell `command` check is accepted only when the project's `wait_commands` is `on`, and permission is checked again before execution. Exit 0 means ready; a nonzero exit means not ready. Checks run in the task directory, take at most 60 seconds each, and retain at most 2 KiB of output. The service runs at most four checks concurrently.
- **System limits and scheduled-run deadlines apply.** Settings → Scheduler → Waits controls `max_wait_seconds` (built-in seven days; configurable from 60 seconds to 30 days) and `min_check_seconds` (built-in 300 seconds; configurable from 10 seconds to one day). A step's maximum must be positive and within the system limit; its explicit check interval must respect the minimum. The usual check interval is 600 seconds, bounded for shorter waits and the system minimum. A scheduled run cannot request or extend a wait beyond its remaining run timeout; opening or extending also caps the deadline at that run's stop time. A run without a timeout still has the system wait limit.
- **Timeouts and cancellation return control to the Planner.** A timeout records activity and a notice, routed to the task's originating Telegram or Lark chat when available, otherwise visible on the dashboard. A `[WAIT]` turn lets the Planner extend, proceed with a resolution, fail the task or adjust the plan. A user-cancelled wait cannot be extended. Normal readiness does not send a timeout notice or require a model turn.
- **Dashboard controls distinguish continuing from cancelling.** The task page shows each wait's condition, timing, next check, latest result, output, notice and resolution. Resume now bypasses the condition and continues dependent steps without a model turn. Cancel requests a `[WAIT]` decision; it does not directly cancel the whole task or silently skip the wait. Both buttons apply only to a `waiting` row of an active task. Once timed out or cancellation is requested, the Planner decides next; stale or competing actions are refused.
- **Saved waits survive restart.** Wait state and deadlines are persisted with the plan. Stopped tasks are not checked or notified; restarting an open wait keeps its deadline, so an overdue wait may time out soon after restart. Concurrent readiness, timeout, Resume now and Cancel transitions are guarded against stale writes. A Planner with no work in flight can stop its idle resident process and resume its session for the next turn. Shutdown stops in-flight checks and cleans up command process trees.

All changes above are delivered by [#247](https://github.com/foolzzz/looper/pull/247).

## Model-visible changes

The Planner reply contract and wait-step guide gain the `kind: "wait"` shape, when to use it for an external event, required duration, time and check fields, current system limits, and the optional `waits` cancellation list in DECISION and CHAT replies. Command-check guidance is included only for projects that enable `wait_commands`. A timeout or user cancellation supplies a `[WAIT]` message with its reply shape, latest check details and any scheduled-run time remaining; that reply shape is carried in the message rather than added to every standing contract. Ready waits contribute their resolution to downstream steps and saved plan context.

The Manager's `looper_tasks get` answer includes wait details and step kinds. `looper_settings view` includes wait limits, and its schema and description add the `waits` action for changing them with user confirmation. Dashboard chat, Telegram and Lark share those Manager tools; Telegram and Lark also receive routed timeout notices. Resume now and Cancel are dashboard controls, with no new channel command. There is no new CLI command: the Planner owns wait creation, and settings and user actions use the dashboard or existing APIs.

## Optional Capability Activation & Use

### Planner wait steps

**Activation:** No project switch is needed for timed waits or `github_pr` checks, including in scheduled tasks. Ask the Planner to wait for a specific external event and define what should run next. For GitHub checks, the service's user needs `gh` installed and authenticated with read access to the target repository.

**Validation:** On a disposable server, ask for a short timed wait and a dependent reporting step. Read the wait state and deadline on the task page; verify no Worker runs during the wait. Repeat with a GitHub PR check, test Resume now and Cancel on separate waits, and allow another to time out. Check activity, the notice and the Planner's decision. Restart an open wait and confirm the saved deadline remains.

```bash
looper --version
looper doctor
```

**Disable / rollback:** There is no global switch for wait steps. Ask the Planner to end an unwanted wait or use the dashboard controls according to the desired outcome. Complete or stop tasks with waits before reinstalling v2.12.3; that version cannot process wait steps. Stopping a task preserves its wait rather than resetting its deadline.

**Authority boundary:** Only the Planner creates wait steps. Typed GitHub checks read through the service user's `gh` access and do not merge, approve or modify a PR. Readiness is a signal to continue the plan, not permission for later side effects. Resume now bypasses the condition; Cancel asks the Planner to decide what follows.

**Docs:** [Wait-step architecture](https://github.com/foolzzz/looper/blob/main/docs/architecture/agent-system.md#wait-steps), [implementation and validation](https://github.com/foolzzz/looper/pull/247).

### Wait command checks

**Activation:** In the project's Settings, set Wait commands (`wait_commands`) to On and save. It is Off by default, including when unset. The Planner may then use a shell command as a wait check.

**Validation:** On a disposable project, first confirm a command check is rejected while Off. Enable it, use a harmless command that exits nonzero until a test file appears, and verify readiness when it exits 0. Turn it Off again and confirm subsequent checks report that commands are disabled. The real-run validation below exercised a command becoming ready.

```bash
looper --version
looper doctor
```

**Disable / rollback:** Set Wait commands to Off to prevent subsequent command checks; this does not terminate an already running check or end its wait. Resolve existing waits through the Planner or dashboard. Complete or stop tasks using waits before downgrading to v2.12.3.

**Authority boundary:** Enabling this permits Planner-selected arbitrary shell commands as the server's user in the task directory. It is an execution permission, not a read-only sandbox. The project permission is rechecked before each command starts; time and output limits do not restrict which files or services the command can access.

**Docs:** [Wait command permission and design](https://github.com/foolzzz/looper/blob/main/docs/architecture/rfcs/plan-wait-step-v0.zh-CN.md), [check runners](https://github.com/foolzzz/looper/blob/main/looper/agents/wait_service.py).

### Wait limits

**Activation:** Use Settings → Scheduler → Waits, or ask the Manager to view or change wait limits. `GET/PUT /api/wait-settings` exposes the same settings. No edit is needed to use the built-in seven-day maximum and 300-second minimum check interval. Manager changes require user confirmation.

**Validation:** On a disposable server, save valid limits and read back their values and sources; restore the built-ins. Check that invalid ranges, non-integer seconds and a minimum above the maximum are rejected without storing changes. Ask the Manager to show the same limits and verify confirmation before changing them. Check a scheduled wait against its run's remaining timeout.

```bash
looper --version
looper doctor
```

**Disable / rollback:** Choose Use the built-in for each changed value, or set its API field to null. Limits validate newly planned or extended waits; changing them does not rewrite existing wait deadlines. To restore v2.12.3, first complete or stop tasks using wait steps.

**Authority boundary:** These system settings govern wait duration and check frequency across projects. They do not enable command checks or extend a scheduled run's timeout. Dashboard/API writes use existing server access; the Manager presents before/after values and requires confirmation.

**Docs:** [Wait limits and API](https://github.com/foolzzz/looper/blob/main/docs/architecture/agent-system.md#wait-steps), [system-limit implementation](https://github.com/foolzzz/looper/blob/main/looper/agents/waits.py).

## 中文摘要

### 升级决策

**谁需要升级：**任务需要等外部事件后继续的操作者，例如等待 PR 作者推送修改、CI 结束或其他系统的任务就绪。

**解决了什么：**Planner 可添加 `kind: "wait"` 的计划步骤，等待时间与可选检查。等待不占 Worker 或 Worker/Reviewer 并发名额，就绪后继续依赖步骤；超时通知用户并触发 `[WAIT]` 回合，dashboard 提供 Resume now 和 Cancel。见 [#247](https://github.com/foolzzz/looper/pull/247)。

**是否有破坏性变更：**无。已有 work 步骤保持行为，命令检查默认关闭。所有任务的 Planner 回复契约都会增加等待指引；API 使用方需要识别任务状态 `waiting`（属于 `in_progress`）和步骤种类 `wait`。

**如何验证：**重跑 `install.sh`，用已有配置和 runtime root 重启并检查版本。在一次性服务上创建短时间等待和依赖步骤，确认 Waiting 时没有 Worker 运行，就绪后依赖步骤读到结论。分别验证超时、Resume now、Cancel 和 Planner 后续决定；停止并重启等待中的任务，读回已保存的状态和截止时间。

**贡献者：**发布维护者 @foolzzz，提交 [#247](https://github.com/foolzzz/looper/pull/247)；本补丁无社区贡献。

### 行为与模型可见变化

- 等待在前置步骤完成后打开，必须有 `max_wait_seconds`，可设最早时间及检查。没有检查则到时间结束；有检查则最早时间与就绪条件都要满足。只阻塞依赖步骤，其他工作照常运行；就绪不跑模型回合，结论交给后续步骤。等待本身不跑 Worker/Reviewer、不占其并发名额。只有等待时任务为 Waiting，归 In progress；用户 gate 优先显示 `waiting_user`。
- `github_pr` 通过固定参数的只读 `gh pr view` 检查 head 变化、检查结束或新评论，首次成功读取保留为基线；PR 合并或关闭也算就绪。`checks_finished` 要求至少一个检查且全部结束，包含失败，不等于 CI 通过。shell 检查只有项目 `wait_commands: on` 才能使用，每次执行前重查权限；退出 0 算就绪，非零算未就绪。单次最多 60 秒，输出最多保留 2 KiB，服务最多同时跑四个检查。
- Settings → Scheduler → Waits 配最长等待（默认七天，可设 60 秒到 30 天）和最短检查间隔（默认 300 秒，可设 10 秒到一天）；单个等待时长为系统上限内的正整数秒。常规检查间隔为 600 秒，按短等待和系统最小间隔调整。定时运行中的等待请求及延长不能超过运行剩余超时，打开或延长时再次取较早的截止时间；运行不限时仍受系统等待上限约束。
- 超时记活动与通知，能路由时发回任务来源 Telegram/Lark 聊天，否则在 dashboard 查看。Planner 的 `[WAIT]` 回合可延长、带结论继续、失败或调整计划；用户取消后不能延长。正常就绪不发超时通知、不跑模型回合。
- 任务页展示条件、时间、下次检查、最近结果和输出、通知及结论。Resume now 跳过条件继续；Cancel 请求 Planner 决策，不直接取消整个任务或跳过等待。按钮只对活动任务的 `waiting` 行可用，超时、已请求取消或并发冲突时拒绝再次操作。
- 等待状态与截止时间随计划入库，重启恢复。停止的任务不检查、不通知，重启保留原截止时间，过期等待可能很快超时。状态转换防止旧快照覆盖并发结果；只有等待时 Planner 可停止空闲常驻进程，下一轮续接会话；停服会停止检查并清理命令进程树。
- Planner 回复契约及等待指引增加 wait 步骤形状、外部事件适用场景、时长与检查字段、当前限制，以及 DECISION/CHAT 的 `waits` 取消列表。只有项目启用命令检查时才加入相应指引；`[WAIT]` 回复形状随该回合消息提供，包含检查详情和定时运行剩余时间，不加入所有常驻契约。
- Manager 的 `looper_tasks get` 返回等待详情和步骤种类；`looper_settings view` 返回限制，schema 和描述增加需用户确认的 `waits` 修改动作。Dashboard、Telegram、Lark 共用这些工具，渠道接收超时通知；Resume now/Cancel 留在 dashboard，没有新增渠道或 CLI 命令。

### 可选能力启用与使用

#### Planner wait steps

**启用：**时间等待和 `github_pr` 检查无项目开关，定时任务也能使用。告诉 Planner 等什么外部事件、之后做什么。GitHub 检查需要服务用户已安装并登录 `gh`，有目标仓库读取权限。

**验证：**在一次性服务上建短等待及后续报告步骤，读回状态和截止时间，确认没有 Worker 在等。分别验证 GitHub PR 检查、Resume now、Cancel、超时通知和 Planner 决策；重启后核对截止时间未重置。

```bash
looper --version
looper doctor
```

**停用 / 回退：**无全局关闭开关。让 Planner 结束不需要的等待，或按期望结果使用 dashboard 控件。降级 v2.12.3 前先完成或停止含等待的任务，旧版不能处理 wait 步骤；停止任务会保留等待和原截止时间。

**权限边界：**只有 Planner 创建等待。GitHub 检查使用服务用户的读取权限，不合并、批准或修改 PR；就绪信号不授权后续副作用。Resume now 绕过条件，Cancel 交给 Planner 决定下一步。

**文档：**[等待架构](https://github.com/foolzzz/looper/blob/main/docs/architecture/agent-system.md#wait-steps)、[实现与验证](https://github.com/foolzzz/looper/pull/247)。

#### Wait command checks

**启用：**项目 Settings 将 Wait commands（`wait_commands`）设为 On 并保存；默认及未设置时为 Off。开启后 Planner 可用 shell 命令检查等待条件。

**验证：**一次性项目中先确认 Off 时拒绝命令检查；开启后用无害命令等待测试文件出现，非零退出未就绪、退出 0 就绪。关闭后确认后续检查报告命令已禁用。下方真实运行记录覆盖了命令变为就绪。

```bash
looper --version
looper doctor
```

**停用 / 回退：**设为 Off 阻止后续命令检查，不会终止已启动的检查或结束等待。通过 Planner 或 dashboard 处理已有等待；降级 v2.12.3 前先完成或停止含等待的任务。

**权限边界：**开启后允许 Planner 选择任意 shell 命令，以服务用户身份在任务目录执行；这是执行权限，不是只读沙箱。每次启动前重查项目许可，时间和输出上限不限制命令访问文件或服务的范围。

**文档：**[命令权限与设计](https://github.com/foolzzz/looper/blob/main/docs/architecture/rfcs/plan-wait-step-v0.zh-CN.md)、[检查执行实现](https://github.com/foolzzz/looper/blob/main/looper/agents/wait_service.py)。

#### Wait limits

**启用：**Settings → Scheduler → Waits，或让 Manager 查看、修改限制；API 为 `GET/PUT /api/wait-settings`。不改即用七天最大时长和 300 秒最小间隔，Manager 修改需用户确认。

**验证：**一次性服务保存合法值并读回数值和来源，再恢复内置值；确认越界、非整数秒和最小间隔超过最大时长均拒绝且不存储。让 Manager 查看同一组限制并确认修改前会请求确认；验证定时等待不能超过运行剩余超时。

```bash
looper --version
looper doctor
```

**停用 / 回退：**分别选择 Use the built-in，或将对应 API 字段设为 null。限制校验新规划及延长的等待，不改写已有截止时间；回退 v2.12.3 前先完成或停止含等待的任务。

**权限边界：**这是跨项目的系统时长和频率限制，不开启命令检查，也不延长定时运行超时。Dashboard/API 使用已有服务访问权限；Manager 展示修改前后值并要求确认。

**文档：**[等待限制与 API](https://github.com/foolzzz/looper/blob/main/docs/architecture/agent-system.md#wait-steps)、[系统限制实现](https://github.com/foolzzz/looper/blob/main/looper/agents/waits.py)。

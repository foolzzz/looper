# Looper v2.14.19

This is the patch release v2.14.19. It ships the two changes merged since v2.14.18: [#912](https://github.com/foolzzz/looper/pull/912), which closes three races left by the project delete cascade, and [#908](https://github.com/foolzzz/looper/pull/908), a test-helper fix.

## Release Decision

**Who should upgrade:** Anyone who deletes projects that have tasks or schedules (the cascade shipped in v2.14.17), especially while tasks are being restarted, moved to another project or gated by a schedule. It ships the two changes merged since v2.14.18.

**What this release solves:** [#912](https://github.com/foolzzz/looper/pull/912), follow-up to the project delete cascade ([#905](https://github.com/foolzzz/looper/pull/905)): a Restart or Start over of a task during the delete no longer starts a Planner on a deleted task; the delete no longer removes a task that was moved to another project after its snapshot; a Manager template attached after the preflight is reported as a template conflict instead of "a task or schedule was added"; and a schedule run refused by the deletion barrier no longer stays `gating` until a server restart. [#908](https://github.com/foolzzz/looper/pull/908): the installed DSH runner serve test helper skips a runner that has exited and is not yet reaped, instead of failing the test (tests only).

**Breaking changes:** No. The supported upgrade path is unchanged (see Upgrading).

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#912](https://github.com/foolzzz/looper/pull/912) and [#908](https://github.com/foolzzz/looper/pull/908); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.19
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.18 upgrades directly. This release changes no database schema, stored data or setting.

## Behavior changes

- **Restart and Start over respect the project delete barrier** (`looper/agents/tiers/task.py`): `_handle_restart` now runs its cleanup (for Start over, the step worktrees and saved run sessions), the reset and the Planner start inside the same per-project firing barrier a ready start uses. While the project is being deleted the restart returns without doing anything. The restart also stops when `reset_task_for_restart` reports that it did not reset the task, instead of starting a Planner anyway.
- **The delete skips a task that moved projects** (`looper/agents/projects.py`): `delete_task` takes an optional `expected_project_id`; the cascade passes the project being deleted. A task whose project differs when its row is locked is skipped (`{"skipped": <id>}`), so its checkout and record are kept.
- **Template conflicts are reported as such** (`looper/agents/projects.py`): `delete_project` checks inside the barrier whether a Manager task template names the project and refuses with the existing "used by template ... change the template first" conflict. If the final delete hits a foreign key violation, it checks again and reports the template conflict when a template was attached in between; otherwise the "a task or schedule was added" message is unchanged.
- **A gate refused by the deletion barrier ends its run** (`looper/agents/scheduler.py`): when a schedule's gate finishes and the project is being deleted, the run is set to `gate_failed` with the error "project delete refused the gate's task start", the outcome is counted, and the run no longer stays `gating` until a server restart. Before, it returned with the run left `gating`.
- **Test helper** (`tests/test_dsh_runner_serve_db.py`, [#908](https://github.com/foolzzz/looper/pull/908)): `dsh_runner_processes` reads the `ps` state as well and skips a process that is `Z` (defunct) or has `E` (exiting) in its state, as it is being reaped; live processes are still checked strictly. Test file only.
- **Model-visible changes:** None. No prompt, tool description, tool schema or runner protocol message changes. The only new text is the run error string above, which is stored on the schedule run record.

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.18 上的安装可直接升级。本版本不改数据库 schema、已存数据或设置。

### 行为变化与入口

- **Restart 与 Start over 遵守项目删除屏障**（`looper/agents/tiers/task.py`）：`_handle_restart` 现在把清理（Start over 时为步骤 worktree 和已保存的运行会话）、重置和 Planner 启动放在与 ready 启动相同的按项目 firing 屏障内。项目正在删除时，重启直接返回。当 `reset_task_for_restart` 报告未重置任务时，重启也会停止，而不是照常启动 Planner。
- **删除会跳过已移到其他项目的任务**（`looper/agents/projects.py`）：`delete_task` 新增可选参数 `expected_project_id`，级联删除传入被删项目。锁定任务行时若其项目不同，则跳过（`{"skipped": <id>}`），其检出目录与记录保留。
- **模板冲突按模板冲突报告**（`looper/agents/projects.py`）：`delete_project` 在屏障内检查是否有 Manager 任务模板指向该项目，有则以既有的“used by template ... change the template first”冲突拒绝。最终删除遇到外键冲突时再次检查，若期间挂上了模板则报告模板冲突；否则“a task or schedule was added”的提示不变。
- **被删除屏障拒绝的 gate 会结束其运行**（`looper/agents/scheduler.py`）：计划的 gate 结束时若项目正在删除，运行被置为 `gate_failed`，错误为“project delete refused the gate's task start”，并计入结果；不再停留在 `gating` 直到服务重启。此前它直接返回，运行仍为 `gating`。
- **测试辅助函数**（`tests/test_dsh_runner_serve_db.py`，[#908](https://github.com/foolzzz/looper/pull/908)）：`dsh_runner_processes` 额外读取 `ps` 状态，跳过状态为 `Z`（defunct）或含 `E`（正在退出）、正被回收的进程；仍存活的进程照旧严格检查。仅测试文件。
- **面向模型的变化：**无。没有 prompt、工具描述、工具 schema 或 runner 协议消息的变化。唯一新增文本是上述运行错误字符串，仅存于计划运行记录。

# Looper v2.14.104

This is the patch release v2.14.104, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.103: recorded model requests are now bounded by age and by total size, and request recording is on by default ([#1145](https://github.com/foolzzz/looper/pull/1145)).

## Release Decision

**Who should upgrade:** Everyone who runs the request recorder, and every operator whose installation never stored the `llmrec.enabled` switch, because recording turns on for them with this release. Operators who want recording off should read Behavior changes first.

**What this release solves:** [#1145](https://github.com/foolzzz/looper/pull/1145). Turning recording on can no longer fill the database: requests older than a retention (default 7 days) are deleted hourly, and when the recorded size passes a cap (default 2048 MiB) the oldest requests are deleted down to 90 % of it. Operators can also delete recorded requests on demand.

**Breaking changes:** No. No new dependency or command. Request recording is on by default for an installation that never stored `llmrec.enabled` (maintainer decision, intended; see Behavior changes). The database gains two `stored_bytes` columns.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.14.104
```

**Contributors:** Maintainer @foolzzz authored [#1145](https://github.com/foolzzz/looper/pull/1145); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.103 upgrades directly. The schema change is additive: `ensure_schema` adds a `stored_bytes BIGINT NOT NULL DEFAULT 0` column to `llm_requests` and to `llm_request_parts` once and fills it for existing rows with the byte length of each row's text form (`octet_length(row::text)`), which can take time on a large recording table. Until then the change is reported as a pending schema change.

## Behavior changes

- **Recording is on by default** (`looper/agents/serve.py`, `looper/agents/self_check.py`, `looper/agents/v1_domains/llm_requests.py`). A missing `llmrec.enabled` setting now reads as `true` instead of off. An installation that never stored the switch (a fresh install, or an upgrade where the operator never touched it) records the model requests of covered API-key runs after this release, including prompts, code and tool output. An explicitly stored `false` stays off. Claude subscription (OAuth) runs still need `llmrec.include_oauth`, which stays off by default. To turn it off: Settings → Request recording, or `loopercli llmrec-settings update --enabled false`. Existing runs keep their route until restart. The pull request description names this as a maintainer decision.
- **Retention and size cap** (`looper/agents/llmrec/settings.py`, `looper/agents/v1_domains/llm_requests.py`). Two settings: `llmrec.retention_days` (whole days, 1–90, default 7) and `llmrec.max_total_mb` (256–65536 MiB, default 2048). `llmrec_settings.get` returns each with its value, source, built-in value and range, plus `stored_bytes` and `request_count`; `llmrec_settings.update` accepts both (null restores the built-in) and rejects values out of range. The recorded size is the sum of `stored_bytes` of requests and deduplicated parts, not the physical PostgreSQL table size.
- **Hourly housekeeping** (`looper/agents/housekeeping.py`). A new `llm requests` step deletes requests older than the retention in batches of 2000, then routes left with no requests (after 10 minutes of grace), which also deletes their parts. It runs whether or not recording is enabled, so turning recording off never deletes anything by itself but old data still ages out. If the recorded size is still above the cap, it deletes the oldest requests until the size is at or below 90 % of the cap (at most 50 rounds, then a warning is logged). A part is kept until the last request that references it goes, so every remaining request can be rebuilt in full. The step takes row locks per batch; it does not lock the whole tables and does not run `VACUUM FULL`, so disk space returns to PostgreSQL for reuse but the files do not shrink. A new `llm route files` step removes route files under `.local/llmrec` that ended more than a day ago or were last changed more than 7 days ago. The housekeeping log line gains `llm_requests`, `llm_routes` and `llm_route_files` counts.
- **On-demand deletion** (`looper/agents/v1_domains/llm_requests.py`, `looper/db/llm_requests.py`). New operator-only operation `llm_requests.purge` with exactly one of `{task_id}`, `{agent_id}` or `{all: true}`, risk high. The dashboard asks for confirmation first; an operator API or `loopercli` call runs at once. `all: true` takes an exclusive lock on the three recording tables and truncates them, so it briefly blocks recording writers. API-client tokens still receive 403.
- **Manager purge** (`looper/db/manager_cleanup.py`, `looper/agents/v1_domains/manager_cleanup.py`). Purging a deleted Manager's history now also deletes that Manager's recording routes with their requests and parts. The preview, its confirmation text and the result counts gain `llm_requests`.
- **Self-check** (`looper/agents/self_check.py`). The `llmrec` check reports recorded MiB against the cap, also when recording is off (off with data is reported as skipped with the usage, no longer a plain "off"), and warns once the recorded size passes 90 % of the cap.
- **Dashboard** (`web/src/components/llmrec-settings.tsx`). Settings → Request recording gains fields for the retention (days) and the cap (GiB, converted to MiB), a Save and a Restore built-in action, the recorded size and request count, and a "Delete recorded requests" action behind a confirmation dialog. Telegram and Lark are unchanged.
- **CLI** (`looper/loopercli.py`). `loopercli llmrec-settings update --enabled` now also accepts `true` or `false` as a value, next to the existing switch forms and `--no-enabled`. The generated `loopercli` gains the `llm_requests.purge` operation and the two settings fields.
- **Documentation** (`docs/architecture/agent-system.md`). The recording section describes the default, the limits and purge, and its coverage list now names Planners, Managers, consults and the in-process API runtime. That coverage text is documentation only in this pull request; no launch code changed.
- **Tests.** New `tests/test_llmrec_retention_db.py` and `tests/test_llmrec_settings_db.py`; `test_api_v1_llm_requests_db.py`, `test_llmrec_store_db.py`, `test_llmrec_control.py`, `test_llmrec_launch_hardening.py`, `test_housekeeping*.py`, manager cleanup tests and `web/src/components/llmrec-settings.test.tsx` extended or adjusted for the new default.
- **Unchanged:** dependencies, other settings and commands, channels, and the Manager's other tools.
- **Model-visible changes:** Yes, one. The Manager's `looper_settings` tool gains the action `llmrec` and an `llmrec` argument (`retention_days` 1–90, `max_total_mb` 256–65536, null for the built-in); its description names them. `looper_settings` `view` now returns an `llmrec` block with the two limits, so every Manager turn that lists the tool sees the longer description and schema. The Manager asks the user for confirmation before changing the limits (the confirmation text is in Chinese, like the neighbouring settings actions). No worker, planner or reviewer prompt, and no agent environment, changed. Recorded requests are never sent to a model, Telegram or Lark by this change.

## 中文摘要

本版本是 patch release v2.14.104（热修线，每个合并的改动立即发布）。自 v2.14.103 以来只合并了一项改动：已记录的模型请求现在按时间和总大小设上限，并且请求记录默认开启（[#1145](https://github.com/foolzzz/looper/pull/1145)）。

### 升级决策

**谁需要升级：**所有运行请求记录器的用户，以及从未保存过 `llmrec.enabled` 开关的安装——本版本会为它们开启记录。想保持关闭的运维人员请先阅读行为变化。

**解决了什么：**[#1145](https://github.com/foolzzz/looper/pull/1145)。开启记录不会再写满数据库：早于保留期（默认 7 天）的请求每小时清理，已记录大小超过上限（默认 2048 MiB）时，最旧的请求会被删除到上限的 90 %。运维人员也可以按需删除已记录的请求。

**是否有破坏性变更：**否。无新依赖、无新命令。从未保存过 `llmrec.enabled` 的安装默认开启请求记录（维护者决定，符合预期，见行为变化）。数据库新增两个 `stored_bytes` 列。

**如何验证：**核对版本为 2.14.104。

**贡献者：**维护者 @foolzzz 提交 [#1145](https://github.com/foolzzz/looper/pull/1145)；本版本无社区贡献。

```bash
looper --version   # looper 2.14.104
```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.103 上的安装可直接升级。数据库变更为增量：`ensure_schema` 一次性为 `llm_requests` 和 `llm_request_parts` 增加 `stored_bytes BIGINT NOT NULL DEFAULT 0` 列，并为已有行填入该行文本形式的字节数（`octet_length(row::text)`），记录表很大时可能耗时。在此之前该变更被视为待处理的结构变更。

### 行为变化与入口

- **记录默认开启**（`looper/agents/serve.py`、`looper/agents/self_check.py`、`looper/agents/v1_domains/llm_requests.py`）。缺失的 `llmrec.enabled` 现在按 `true` 读取，而不是关闭。从未保存过该开关的安装（全新安装，或运维人员从未动过开关的升级）在本版本之后会记录受覆盖的 API key 运行的模型请求，包含提示、代码和工具输出。显式保存的 `false` 仍为关闭。Claude 订阅（OAuth）运行仍需 `llmrec.include_oauth`，默认关闭。关闭方法：设置 → 请求记录，或 `loopercli llmrec-settings update --enabled false`。已运行的 agent 在重启前沿用原路由。PR 描述将此项列为维护者决定。
- **保留期与容量上限**（`looper/agents/llmrec/settings.py`、`looper/agents/v1_domains/llm_requests.py`）。两个设置：`llmrec.retention_days`（整数天，1–90，默认 7）和 `llmrec.max_total_mb`（256–65536 MiB，默认 2048）。`llmrec_settings.get` 返回每项的值、来源、内置值和范围，另有 `stored_bytes` 和 `request_count`；`llmrec_settings.update` 接受两者（null 恢复内置值），越界则拒绝。记录大小是请求与去重 part 的 `stored_bytes` 之和，不是 PostgreSQL 表的物理大小。
- **每小时清理**（`looper/agents/housekeeping.py`）。新的 `llm requests` 步骤按每批 2000 条删除早于保留期的请求，再删除没有请求的路由（有 10 分钟宽限），其 part 一并删除。无论记录是否开启都会运行，因此关闭记录本身不会删除数据，但旧数据仍会过期。若记录大小仍高于上限，则删除最旧的请求，直到不超过上限的 90 %（最多 50 轮，之后记录警告）。part 保留到最后一个引用它的请求被删除，因此剩余的每个请求仍可完整重建。该步骤按批加行锁，不锁整表，也不运行 `VACUUM FULL`：磁盘空间回到 PostgreSQL 内部复用，但文件不会缩小。新的 `llm route files` 步骤删除 `.local/llmrec` 下已结束超过一天或最后修改超过 7 天的路由文件。清理日志行新增 `llm_requests`、`llm_routes`、`llm_route_files` 计数。
- **按需删除**（`looper/agents/v1_domains/llm_requests.py`、`looper/db/llm_requests.py`）。新增仅限运维的操作 `llm_requests.purge`，必须且只能给出 `{task_id}`、`{agent_id}` 或 `{all: true}` 之一，风险等级高。仪表盘先要求确认；运维人员的 API 或 `loopercli` 调用立即执行。`all: true` 会对三张记录表加排他锁并截断，短暂阻塞记录写入。API 客户端令牌仍返回 403。
- **Manager 清理**（`looper/db/manager_cleanup.py`、`looper/agents/v1_domains/manager_cleanup.py`）。清除已删除 Manager 的历史时，现在也会删除该 Manager 的记录路由及其请求和 part。预览、确认文字和结果计数新增 `llm_requests`。
- **自检**（`looper/agents/self_check.py`）。`llmrec` 检查报告已记录 MiB 与上限，记录关闭时同样报告（关闭但有数据时显示为跳过并附用量，不再只写“off”），记录大小超过上限的 90 % 时给出警告。
- **仪表盘**（`web/src/components/llmrec-settings.tsx`）。设置 → 请求记录新增保留期（天）和上限（GiB，换算为 MiB）输入、保存与恢复内置值操作、已记录大小与请求数，以及带确认对话框的“Delete recorded requests”操作。Telegram 与 Lark 不变。
- **CLI**（`looper/loopercli.py`）。`loopercli llmrec-settings update --enabled` 现在也接受 `true` 或 `false` 作为值，原有开关形式和 `--no-enabled` 保留。生成的 `loopercli` 新增 `llm_requests.purge` 操作和两个设置字段。
- **文档**（`docs/architecture/agent-system.md`）。记录一节描述了默认值、限制和清除，覆盖范围列表现在写明 Planner、Manager、consult 和进程内 API 运行时。该覆盖范围文字在本 PR 中仅是文档改动，没有改动启动代码。
- **测试。**新增 `tests/test_llmrec_retention_db.py` 和 `tests/test_llmrec_settings_db.py`；扩展或调整 `test_api_v1_llm_requests_db.py`、`test_llmrec_store_db.py`、`test_llmrec_control.py`、`test_llmrec_launch_hardening.py`、`test_housekeeping*.py`、Manager 清理测试和 `web/src/components/llmrec-settings.test.tsx` 以适配新默认值。
- **不变：**依赖、其他设置与命令、渠道，以及 Manager 的其他工具。
- **面向模型的变化：**有一项。Manager 的 `looper_settings` 工具新增动作 `llmrec` 和 `llmrec` 参数（`retention_days` 1–90、`max_total_mb` 256–65536，null 为内置值），描述中写明了它们；`looper_settings` 的 `view` 现在返回包含两个限制的 `llmrec` 块，因此每个列出该工具的 Manager 回合都会看到更长的描述和 schema。修改限制前 Manager 会请用户确认（确认文字为中文，与相邻的设置动作一致）。Worker、Planner、Reviewer 的提示和 agent 环境均无变化。此改动不会把记录的请求发给模型、Telegram 或 Lark。

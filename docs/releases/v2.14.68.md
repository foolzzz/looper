# Looper v2.14.68

This is the patch release v2.14.68, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.67: a planned control-plane restart now adopts detached kept runs at startup ([#1060](https://github.com/foolzzz/looper/pull/1060)).

## Release Decision

**Who should upgrade:** Installations that run with the keeper on and restart the control plane for a planned upgrade (a turns drain followed by SIGTERM). Others see no change.

**What this release solves:** v2.14.66 detaches kept runs on a planned restart and v2.14.67 added `WorkerPool.adopt_dir`, but the next start still ended every detached run. [#1060](https://github.com/foolzzz/looper/pull/1060) wires adoption into startup: the scan keeps eligible runs as candidates and leaves their records `running`, the room tokens of those runs are restored as pending, and each task's Planner adopts its dispatched step's Worker (or its in-review step's Reviewer) before it dispatches anew. A run that is adopted keeps its run id, process, record and attempt. The bridge's retry and the upgrade CLI are not part of this release.

**Breaking changes:** No. No API schema or configuration changes beyond the optional `system.status.keepers` field, and there is no migration.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#1060](https://github.com/foolzzz/looper/pull/1060); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.68
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.67 upgrades directly. This release adds no migration. The restart that installs this release is still run by v2.14.67 code, which ends detached runs; adoption applies from the restart after it.

## Behavior changes

- **Startup keeps adoptable runs.** `kept_dirs.scan_at_start` (`looper/agents/kept_dirs.py`) takes the controller epoch, the resumable tasks and the pool, and returns candidates. It runs only with a lease (keeper mode on); with keeper mode off, live leftovers still end as `not_adoptable` and dead or exited directories are released. A candidate needs a version-1 manifest, a valid `detach.json`, an unchanged adoption contract, a `running` record, a persisted step holding the run in a resumable task (`dispatched` for Workers, `completed` for Reviewers), a detach epoch equal to the keeper's controller epoch and below the new one, a keeper that is live or exited normally, and a `stdout.log` at least as long as the consumed offset. Any other run is ended with a reason: `no_detach`, `epoch_mismatch`, `keeper_ended`, `keeper_dead`, `contract_changed`, `not_held`, `no_record`, `log_short` or `bad_files` (which includes a missing or invalid room grant).
- **Records.** `end_unfinished_records(keep=…)` (`looper/db/llm_records.py`) no longer interrupts the records of candidates; every other `running` record is still interrupted at start. `plans.run_holds` finds the steps that hold the runs.
- **Room grants survive the restart.** `grant.json` (token digest, seat, room flag, vault tools, MCP files; mode 0600, no bearer token) is written when the keeper run starts. Startup validates and imports candidates' grants as pending before HTTP listens. While pending, the room API answers a run's tool requests with HTTP 503 and `Retry-After: 2`; adoption activates the grant, and a run that is not adopted has its grant revoked. The vault's per-run write counter restarts at zero after adoption.
- **Planners adopt before dispatching.** `TaskRouter` gives each Planner an adopter (`WorkerPool.adopt`). `Planner._resume` tries it for each step cut off by the restart; on `adopted` the run carries on, on `failed` the old run is ended and the same attempt runs again, and on `end_pending` (cleanup could not be confirmed, or a newer control plane holds the run) the step waits and does not run again yet. Carried-on runs finish under their own spend cap; a task at its cap blocks every new dispatch or decision, and a task budget check is skipped for `TASK_RESUME` events.
- **Candidates expire.** A candidate not claimed within 300 seconds after task resumption is scheduled is ended with `not_adopted`, its record is interrupted and the Planner is resumed to run the step again. Stopping a task ends its candidate at once (`WorkerPool.kill`). A fenced or superseded control plane leaves candidates and keepers alone.
- **`KeptRun.attach` and detach.** An attach to a keeper that finished normally between the state read and the connect now falls back to the files; a truncated `stdout.log` or invalid exited state is refused. A second detach during replay keeps the prefix persisted before the replay began. The result consumed before detach no longer short-circuits the replay in `_consume`.
- **`system.status`.** A new optional `keepers` object (keeper mode on only): `mode`, `attached`, `candidates_at_start`, `adopted_at_start`, `pending`, `ended_at_start` by reason. The dashboard needs no change; Telegram, Lark and the CLI are unchanged.
- **Activity text.** The task activity shows `Worker … carried on across the restart` (or `Reviewer …`), or says why the run could not carry on.
- **Housekeeping.** `.gitignore` ignores the short `/.k?/` socket directories of keeper tests; `docs/architecture/agent-system.md` describes the flow.
- **Size:** per the pull request description, 414 added lines of production code and 1100 of tests (fixtures excluded).
- **Model-visible changes:** One. A running agent whose token is pending adoption gets an HTTP 503 with the text "this run is being adopted after a restart; retry shortly" and `Retry-After: 2` from its room and platform tools, where before the token would have been refused after the run ended. No prompt or tool description text changed.

### 升级决策

**谁需要升级：**开启 keeper 并在计划内升级时重启控制面（turns drain 后 SIGTERM）的安装。其他安装没有变化。

**是否有破坏性变更：**否。除可选的 `system.status.keepers` 字段外没有 API 结构或配置变更，也没有迁移。

**如何验证：**运行 `looper --version` 核对版本为 2.14.68。

**贡献者：**维护者 @foolzzz 提交 [#1060](https://github.com/foolzzz/looper/pull/1060)；本版本无社区贡献。

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.67 上的安装可直接升级。本版本没有迁移。安装本版本的那次重启仍由 v2.14.67 的代码执行，会结束脱离的运行；接管从再下一次重启起生效。

### 行为变化与入口

- **启动时保留可接管的运行。**`kept_dirs.scan_at_start`（`looper/agents/kept_dirs.py`）接收控制器 epoch、可恢复的任务和连接池，并返回候选。它只在有租约（keeper 开启）时运行；keeper 关闭时，存活的残留仍以 `not_adoptable` 结束，已死或已退出的目录被释放。候选需要：version 1 的 manifest、有效的 `detach.json`、未变的接管契约、`running` 的记录、可恢复任务中持有该运行的持久化步骤（Worker 为 `dispatched`，Reviewer 为 `completed`）、等于 keeper 控制器 epoch 且小于新 epoch 的脱离 epoch、存活或正常退出的 keeper，以及不短于已消费偏移的 `stdout.log`。其他运行带原因结束：`no_detach`、`epoch_mismatch`、`keeper_ended`、`keeper_dead`、`contract_changed`、`not_held`、`no_record`、`log_short` 或 `bad_files`（包括缺失或无效的房间授权）。
- **记录。**`end_unfinished_records(keep=…)`（`looper/db/llm_records.py`）不再中断候选的记录；其余 `running` 记录启动时仍被中断。`plans.run_holds` 查找持有这些运行的步骤。
- **房间授权跨重启保留。**`grant.json`（令牌摘要、席位、房间标志、vault 工具、MCP 文件；权限 0600，不含 bearer 令牌）在 keeper 运行启动时写入。启动时在 HTTP 监听之前校验并以待定状态导入候选的授权。待定期间，房间 API 对该运行的工具请求返回 HTTP 503 和 `Retry-After: 2`；接管成功后授权激活，未被接管的运行其授权被撤销。接管后 vault 的单运行写入计数从零重新开始。
- **Planner 先接管再派发。**`TaskRouter` 给每个 Planner 一个接管器（`WorkerPool.adopt`）。`Planner._resume` 对被重启截断的每个步骤尝试接管；`adopted` 则运行继续，`failed` 则结束旧运行并重跑同一次尝试，`end_pending`（无法确认清理完成，或更新的控制面持有该运行）则步骤等待，暂不重跑。被接管的运行在各自的花费上限内完成；任务达到上限时阻止所有新的派发或决策，且 `TASK_RESUME` 事件跳过任务预算检查。
- **候选会过期。**任务恢复被安排后 300 秒内未被认领的候选以 `not_adopted` 结束，其记录被中断，Planner 被唤醒重跑该步骤。停止任务会立即结束其候选（`WorkerPool.kill`）。被隔离或被取代的控制面不动候选和 keeper。
- **`KeptRun.attach` 与脱离。**读取状态与连接之间 keeper 正常结束时，attach 现在回退到仅凭文件；被截断的 `stdout.log` 或无效的已退出状态会被拒绝。回放期间的第二次脱离会保留回放开始前已持久化的前缀。脱离前已消费的结果不再在 `_consume` 中使回放提前结束。
- **`system.status`。**新增可选的 `keepers` 对象（仅 keeper 开启时）：`mode`、`attached`、`candidates_at_start`、`adopted_at_start`、`pending`，以及按原因统计的 `ended_at_start`。仪表盘无需改动；Telegram、Lark 和 CLI 不变。
- **活动文字。**任务活动显示 `Worker … carried on across the restart`（或 `Reviewer …`），或说明该运行为何无法继续。
- **其他。**`.gitignore` 忽略 keeper 测试使用的短 `/.k?/` 套接字目录；`docs/architecture/agent-system.md` 描述了该流程。
- **规模：**据 PR 描述，生产代码新增 414 行，测试新增 1100 行（不含 fixture）。
- **面向模型的变化：**一项。令牌待接管的运行中的智能体，其房间和平台工具会收到 HTTP 503，文字为 "this run is being adopted after a restart; retry shortly"，并带 `Retry-After: 2`；此前令牌只会在运行结束后被拒绝。没有提示或工具说明文字变化。

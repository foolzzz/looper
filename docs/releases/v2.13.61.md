# Looper v2.13.61

## Release Decision

**Who should upgrade:** Operators who run the dashboard or `looper service`, and anyone who scripts the removed project-skill HTTP routes. Nobody else needs to act.

**What this release solves:** [#470](https://github.com/foolzzz/looper/pull/470) moves project-owned skills (the skills a project writes itself) to the versioned API (`/api/v1/project_skills/*`) with typed results. The dashboard's project Skills tab now adds, reads, edits and deletes through it.

**Breaking changes:** Yes. Four legacy HTTP methods are removed and no longer match a route: `POST /api/projects/{project id}/skills`, and `GET`, `PUT` and `DELETE /api/projects/{project id}/skills/{skill id}`. A script that calls them must switch to the v1 routes below. Catalog, installation, upload and import routes are unchanged. No stored data or configuration changed.

**How to verify:** Check the installed version, then add and read a skill in a test project with the operator token.

**Contributors:** Maintainer @foolzzz authored [#470](https://github.com/foolzzz/looper/pull/470); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.61
```

## Behavior changes

- **New v1 operations (`looper/agents/v1_domains/project_skills.py`, `looper/agents/v1_domains/__init__.py`):** the `project_skills` domain joins `status` and `catalog` in `MODULES`. All operations are `POST` with a JSON body that rejects unknown keys:
  - `project_skills.add` (`project_id`, `skill` with required `name`, `description`, `content` and optional `enabled`): a write. The skill is installed in the project; `enabled` is kept when given.
  - `project_skills.get` (`project_id`, `skill_id`): a read, answering the skill and its content.
  - `project_skills.update` (`project_id`, `skill_id`, `fields`): a write. `fields` takes `name`, `description` and `content` and needs at least one; `enabled` is not accepted here, a skill is switched on or off through `installs.update`.
  - `project_skills.delete` (`project_id`, `skill_id`): `high` risk.
- **Typed results:** add and update answer the project's installation view plus the skill; delete answers the installation view and the deleted id.
- **Deleting a skill is `high` (`project_skills.delete`):** a client token gets the two-step confirmation, whose text names the skill and lists every installation and project it is installed in; with the operator credential it runs in one request (see v2.13.59), and the dashboard keeps its own dialog. Ownership and the current installations are read again at the delete itself, so a confirmation is not a reservation, and the core removes the skill and all its installations in one transaction. A skill that does not belong to the given project is refused.
- **Dashboard (`web/src/lib/api.ts`):** `addProjectSkill`, `fetchProjectSkill`, `updateProjectSkill` and `deleteProjectSkill` call the v1 routes through `callV1`. A pending-confirmation (202) answer is never confirmed automatically; it surfaces as an error. `NewProjectSkill` gains an optional `enabled`.
- **Legacy routes (`looper/agents/http_server.py`):** the four methods above and their two route patterns are deleted.
- **Docs and tests:** the client-skill RFC and the long-horizon context plan record the migration. New `tests/test_api_v1_project_skills.py` and `tests/test_api_v1_project_skills_db.py`; catalog, catalog-source, config-transfer, library and project-skill tests were moved to the v1 calls. The pull request reports added lines: tests 320, production 98 (fixtures excluded).
- **Model-visible changes:** None. Manager, Worker, Planner and Reviewer prompts are unchanged and no Manager Tool is added or changed. API clients (and an agent skill built on the OpenAPI document) see the new operations and their schemas.

## Upgrade and rollback

Re-run `install.sh` once v2.13.61 is published. No data migration. Replace any caller of the four removed routes before upgrading. Rolling back to v2.13.60 brings those routes back and removes the v1 project-skill operations; a dashboard and a service from the same version always agree, so do not mix versions.

**是否有破坏性变更：**有。四个旧 HTTP 方法已删除，不再匹配路由：`POST /api/projects/{项目 id}/skills`，以及 `GET`、`PUT`、`DELETE /api/projects/{项目 id}/skills/{skill id}`。调用它们的脚本须改用上述 v1 路由。目录、安装、上传和导入路由不变。存储数据和配置均未改动。

**如何验证：**运行 `looper --version` 核对版本为 2.13.61，再用操作者令牌在测试项目里新增并读取一个 skill。

**贡献者：**维护者 @foolzzz 提交 [#470](https://github.com/foolzzz/looper/pull/470)；本次 patch release 无社区贡献。


### 行为变化与入口

- 新增 v1 操作（`v1_domains/project_skills.py`、`v1_domains/__init__.py`）：`project_skills` 领域加入 `MODULES`（在 `status`、`catalog` 之后）。均为带 JSON 请求体的 `POST`，拒绝未知键：
  - `project_skills.add`（`project_id`、`skill`，必填 `name`、`description`、`content`，可选 `enabled`）：写操作，skill 会安装到该项目；给出 `enabled` 则保留。
  - `project_skills.get`（`project_id`、`skill_id`）：读操作，返回 skill 及其正文。
  - `project_skills.update`（`project_id`、`skill_id`、`fields`）：写操作。`fields` 接受 `name`、`description`、`content`，至少一项；不接受 `enabled`，开关走 `installs.update`。
  - `project_skills.delete`（`project_id`、`skill_id`）：`high` 风险。
- 类型化结果：新增和更新返回项目安装视图加 skill；删除返回安装视图和被删除的 id。
- 删除 skill 为 `high`（`project_skills.delete`）：客户端令牌需两步确认，确认文案写明 skill 及其所有安装和所在项目；操作者凭据单次执行（见 v2.13.59），Dashboard 保留自己的弹窗。删除时会重新读取归属和当前安装，确认不是预留，核心在一个事务里删除 skill 及全部安装。不属于所给项目的 skill 会被拒绝。
- Dashboard（`web/src/lib/api.ts`）：`addProjectSkill`、`fetchProjectSkill`、`updateProjectSkill`、`deleteProjectSkill` 经 `callV1` 调用 v1 路由。待确认（202）的回答绝不自动确认，而是作为错误抛出。`NewProjectSkill` 新增可选 `enabled`。
- 旧路由（`http_server.py`）：上述四个方法及两个路由正则已删除。
- 文档与测试：更新客户端 skill RFC 和长程上下文计划。新增 `tests/test_api_v1_project_skills.py` 和 `tests/test_api_v1_project_skills_db.py`；目录、目录来源、配置传输、library 和项目 skill 的测试改用 v1 调用。PR 报告新增测试 320 行、生产代码 98 行（不含 fixture）。
- 面向模型的变化：无。Manager、Worker、Planner、Reviewer 的 prompt 不变，也不新增或改动 Manager Tool。API 客户端（以及基于 OpenAPI 文档的 agent skill）会看到新增的操作及其 schema。

### 升级与回退

v2.13.61 发布后重跑 `install.sh`，无需迁移数据。升级前请把调用上述四个已删除路由的地方改掉。回退到 v2.13.60 会恢复这些路由并移除 v1 项目 skill 操作；Dashboard 与服务须同版本，不要混用。

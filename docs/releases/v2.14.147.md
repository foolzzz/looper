# Looper v2.14.147

This is the patch release v2.14.147, a hotfix line in which each merged change ships at once. It documents two changes: [#1261](https://github.com/foolzzz/looper/pull/1261) (`looper service upgrade` uses one 15-second read timeout for component, status and verification reads) and [#1262](https://github.com/foolzzz/looper/pull/1262) (eval reports gain room delivery and inbox-call columns).

## Release Decision

**Who should upgrade:** Operators who run `looper service upgrade` against a service whose first reads can take longer than 3 seconds, and maintainers who compare prompt-regression eval reports. Everyone else gets no visible change.

**What this release solves:** [#1261](https://github.com/foolzzz/looper/pull/1261) lets the upgrade wait up to 15 seconds for the running component fingerprints, as it already did for the initial status read, instead of failing before draining after 3 seconds; the later upgrade verification reads get the same limit. [#1262](https://github.com/foolzzz/looper/pull/1262) adds `room_deliveries`, `room_inbox_calls` and `room_inbox_empty` to the eval metrics and comparison tables.

**Breaking changes:** No. There is no migration and no API removal. The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.14.147
```

**Contributors:** Maintainer @foolzzz authored [#1261](https://github.com/foolzzz/looper/pull/1261) and [#1262](https://github.com/foolzzz/looper/pull/1262); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.146 upgrades directly. There is no schema change.

## Behavior changes

- **Service upgrade reads wait up to 15 seconds** ([#1261](https://github.com/foolzzz/looper/pull/1261), `looper/agents/service.py`). A new `_UPGRADE_READ_TIMEOUT_SECONDS = 15` is used for the initial `system.components` read (before, 3 seconds) and the initial status read (already 15). It is also passed to the reads after installation: `system.components`, `whoami`, and the served `index.html` for web-only upgrades, and to the `system.components` read during failure recovery. `_get_components`, `_request_json`, `_get_whoami` and `_get_index` take a keyword `timeout` that defaults to 3 seconds, so every other caller keeps the old limit.
- **Unchanged in the upgrade:** a failed component inspection still raises `cannot read running component fingerprints` before anything is drained, for execution and dry runs. The `Host` reader types are widened to accept the keyword. The service CLI is the only entry point affected; Dashboard, Telegram and Lark do not perform these client-side reads.
- **Eval reports gain three columns** ([#1262](https://github.com/foolzzz/looper/pull/1262), `evals/prompt_regression/metrics.py`, `evals/prompt_regression/compare.py`, `evals/README.md`). `room_deliveries` counts activity rows whose summary starts with "Room messages delivered". `room_inbox_calls` counts the runs' `looper_room_inbox` tool calls. `room_inbox_empty` counts those whose matching non-error tool result parses as JSON with an empty `messages` list. The comparison table shows them as "room deliveries", "room inbox calls" and "empty room inbox calls". `room_tool_calls` is still counted as before, and event rows that are not mappings are now skipped.
- **Tests only:** the offline wheel installation test helper waits 120 seconds instead of 30 (a test on a busy host, no product change), and the eval comparison tests moved into new test files.
- **Model-visible changes:** None. No prompt, tool or message sent to a model changes, and the eval metrics only read recorded runs; no production code outside `looper/agents/service.py` changes.

### 升级决策

**谁需要升级：**运行 `looper service upgrade` 且服务首次读取可能超过 3 秒的运维者，以及比较 prompt 回归评测报告的维护者。其他人没有可见变化。

**解决了什么：**[#1261](https://github.com/foolzzz/looper/pull/1261) 让升级读取运行中组件指纹最多等待 15 秒（与初始状态读取一致），而不是 3 秒后在排空前失败；之后的升级校验读取使用同一上限。[#1262](https://github.com/foolzzz/looper/pull/1262) 在评测指标与对比表中新增 `room_deliveries`、`room_inbox_calls`、`room_inbox_empty`。

**是否有破坏性变更：**否。没有迁移，没有移除 API。桥接边界不变：早于 v2.13.165 的安装须先升级到 v2.13.165。

**如何验证：**核对版本为 2.14.147。

**贡献者：**维护者 @foolzzz 提交 [#1261](https://github.com/foolzzz/looper/pull/1261) 和 [#1262](https://github.com/foolzzz/looper/pull/1262)；本版本无社区贡献。

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.146 上的安装可直接升级。没有结构变更。

### 行为变化与入口

- **服务升级读取最多等待 15 秒**（[#1261](https://github.com/foolzzz/looper/pull/1261)，`looper/agents/service.py`）。新增 `_UPGRADE_READ_TIMEOUT_SECONDS = 15`，用于初始 `system.components` 读取（此前 3 秒）和初始状态读取（原本即 15 秒），也传给安装之后的读取：`system.components`、`whoami`，以及仅前端升级时的 `index.html`，并用于失败恢复时的 `system.components` 读取。`_get_components`、`_request_json`、`_get_whoami`、`_get_index` 新增关键字 `timeout`，默认 3 秒，其他调用方保持原限制。
- **升级中不变：**组件检查失败时仍在排空任何内容之前抛出 `cannot read running component fingerprints`，执行与预演均如此。`Host` 的读取器类型放宽为接受该关键字。只有服务 CLI 受影响；Dashboard、Telegram 和 Lark 不执行这些客户端读取。
- **评测报告新增三列**（[#1262](https://github.com/foolzzz/looper/pull/1262)，`evals/prompt_regression/metrics.py`、`evals/prompt_regression/compare.py`、`evals/README.md`）。`room_deliveries` 统计摘要以 “Room messages delivered” 开头的活动记录。`room_inbox_calls` 统计运行中对 `looper_room_inbox` 的工具调用。`room_inbox_empty` 统计其对应的非错误工具结果可解析为 JSON 且 `messages` 列表为空的调用。对比表显示为 “room deliveries”、“room inbox calls” 和 “empty room inbox calls”。`room_tool_calls` 仍按原方式统计，非映射的事件行现在被跳过。
- **仅测试：**离线 wheel 安装测试辅助函数的等待由 30 秒改为 120 秒（忙碌主机上的测试，不是产品变化），评测对比测试移入新的测试文件。
- **面向模型的变化：**无。发给模型的提示词、工具和消息都不变，评测指标只读取已记录的运行；除 `looper/agents/service.py` 外没有生产代码改动。

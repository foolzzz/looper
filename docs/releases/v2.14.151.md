# Looper v2.14.151

This is the patch release v2.14.151, a hotfix line in which each merged change ships at once. It documents one change: [#1268](https://github.com/foolzzz/looper/pull/1268) (task-scoped Managers can create and manage agent schedules in their projects).

## Release Decision

**Who should upgrade:** Operators who run Managers with `tools = tasks` and want them to manage agent schedules in their own projects, or who send schedule notices to Lark. Everyone else gets no change except the Lark delivery effect listed under Behavior changes.

**What this release solves:** [#1268](https://github.com/foolzzz/looper/pull/1268) gives a task-scoped Manager the schedule tool, limited to agent schedules without a gate in its project or ownership scope, keeps command and gated schedules read-only for it, lets it notify only chats bound to itself, and makes Lark notices go to a chat only for `oc_` ids and to a user only for `ou_` ids.

**Breaking changes:** No. There is no migration and no API removal. One behavior is stricter: a Lark notify target that starts with neither `oc_` nor `ou_` now fails delivery (see Behavior changes). The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.14.151
```

**Contributors:** Maintainer @foolzzz authored [#1268](https://github.com/foolzzz/looper/pull/1268); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.150 upgrades directly. There is no schema change.

## Behavior changes

- **Task-scoped Managers get the schedule tool** ([#1268](https://github.com/foolzzz/looper/pull/1268), `looper/agents/ops/service.py`, `looper/agents/ops/schedules.py`). A Manager with `tools = tasks` now has the schedule tool besides the task tools, read-only projects and confirmation. Its project scope allows only schedules in its projects, and its own scope only schedules it created; a schedule outside them is refused as forbidden ("this schedule is outside this Manager's projects or belongs to another Manager"), and listing shows only schedules it may see. The scope is checked before confirmation and again at execution, against the confirmed schedule's id.
- **Agent schedules only** (`looper/agents/ops/schedules.py`). Such a Manager may list and read command schedules and schedules with a gate, but cannot create, change, enable, disable, run or delete them (forbidden: "this Manager can only list and read command or gated schedules"). A create or update that sets the command kind, or any of `command`, `env`, `env_file`, `gate_command` or `gate_timeout_seconds` (clearing a gate field included), is refused ("this Manager manages agent schedules only"). Creation still leaves the schedule disabled, and enabling or running still needs confirmation.
- **Notification targets** (`looper/agents/ops/schedules.py`). For create, update, enable and manual run, a task-scoped Manager's target, including the stored one on enable and run, must still be a chat bound to that Manager; the default target of a schedule made from a bound group chat is that chat. The dashboard, the operator API and Managers with every tool select any offered target as before.
- **Lark destination types** (`looper/agents/channels/lark.py`). A Lark notice to an `oc_` id is sent to the chat and to an `ou_` id to the user. Any other id now fails delivery with "notification target must be a Lark chat ID (oc_) or user open ID (ou_)"; before, it was sent as a direct message to that id. This applies to every Lark notice, not only those of task-scoped Managers.
- **Unchanged:** the dashboard, the operator API and the CLI keep their write behavior; Managers with every tool are unchanged; there is no frontend change.
- **Model-visible changes:** Yes. The scope text of a task-scoped Manager (`looper/agents/tiers/manager.py`) now says it has agent schedules in its scope, that it can only list and read command or gated schedules, that schedules must not run shell commands or file operations on the server, and that bound-chat targets must be chats bound to itself; its tool list now includes the schedule tool; and it receives the new refusal texts above. The notice sent to the chat is not model input.

## 中文摘要

本版本是 patch release v2.14.151（热修线，每个合并的改动立即发布），说明一项改动：[#1268](https://github.com/foolzzz/looper/pull/1268)（task 范围的 Manager 可以创建和管理其项目内的 agent 定时任务）。

### 升级决策

**谁需要升级：**运行 `tools = tasks` 的 Manager、并希望它们管理自己项目内 agent 定时任务的运维者，或向飞书发送定时任务通知的运维者。其他人除“行为变化”中的飞书投递一点外没有变化。

**解决了什么：**[#1268](https://github.com/foolzzz/looper/pull/1268) 让 task 范围的 Manager 拥有定时任务工具，仅限其项目或归属范围内无 Gate 的 agent 定时任务；命令型和带 Gate 的定时任务对它保持只读；它只能通知绑定到自己的聊天；飞书通知仅 `oc_` 发到聊天、`ou_` 发到用户。

**是否有破坏性变更：**否。没有迁移，没有移除 API。有一处更严格：既不以 `oc_` 也不以 `ou_` 开头的飞书通知目标现在投递失败（见行为变化）。桥接边界不变：早于 v2.13.165 的安装须先升级到 v2.13.165。

**如何验证：**核对版本为 2.14.151。

**贡献者：**维护者 @foolzzz 提交 [#1268](https://github.com/foolzzz/looper/pull/1268)；本版本无社区贡献。

```bash
looper --version   # looper 2.14.151
```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.150 上的安装可直接升级。没有结构变更。

### 行为变化与入口

- **task 范围 Manager 获得定时任务工具**（[#1268](https://github.com/foolzzz/looper/pull/1268)，`looper/agents/ops/service.py`、`looper/agents/ops/schedules.py`）。`tools = tasks` 的 Manager 除任务工具、只读项目和确认外，现在还有定时任务工具。其项目范围只允许所在项目的定时任务，自身范围只允许自己创建的；范围外的被以 forbidden 拒绝，列表只显示其可见的。范围在确认前检查，执行时再按已确认定时任务的 id 检查一次。
- **只限 agent 定时任务**（`looper/agents/ops/schedules.py`）。这类 Manager 可以列出和读取命令型及带 Gate 的定时任务，但不能创建、修改、启用、停用、运行或删除。设置命令类型，或设置 `command`、`env`、`env_file`、`gate_command`、`gate_timeout_seconds`（包括清空 Gate 字段）的创建和更新会被拒绝。创建出的定时任务仍为停用，启用或运行仍需确认。
- **通知目标**（`looper/agents/ops/schedules.py`）。创建、更新、启用和手动运行时，task 范围 Manager 的目标（启用和运行时为已存目标）必须仍是绑定到该 Manager 的聊天；在绑定群聊中创建的定时任务默认以该聊天为目标。控制台、运维 API 和拥有全部工具的 Manager 仍可选任何被提供的目标。
- **飞书目标类型**（`looper/agents/channels/lark.py`）。发往 `oc_` id 的飞书通知发到聊天，发往 `ou_` id 的发给用户；其他 id 现在投递失败（“notification target must be a Lark chat ID (oc_) or user open ID (ou_)”），此前会作为私聊发给该 id。这适用于所有飞书通知，不限于 task 范围 Manager。
- **不变：**控制台、运维 API 和 CLI 的写入行为；拥有全部工具的 Manager；前端无改动。
- **面向模型的变化：**有。task 范围 Manager 的范围文本（`looper/agents/tiers/manager.py`）现在说明其范围内有 agent 定时任务、命令型或带 Gate 的只能列出和读取、定时任务不得用于在服务器上运行 shell 命令或文件操作、绑定聊天目标必须是绑定到自己的聊天；其工具列表新增定时任务工具；并会收到上述新的拒绝文本。发到聊天的通知不是模型输入。

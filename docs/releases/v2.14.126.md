# Looper v2.14.126

This is the patch release v2.14.126, a hotfix line in which each merged change ships at once. It ships the two changes merged since v2.14.125: a built-in `coco login` provider that links the operator's coco login on the server's machine into run homes ([#1208](https://github.com/foolzzz/looper/pull/1208)), and a readiness-time check that treats a stored `on: completed` dependency as not yet satisfied once a project uses worktree step workspaces ([#1204](https://github.com/foolzzz/looper/pull/1204), issue #1174).

## Release Decision

**Who should upgrade:** Operators who plan to use coco with its own machine login, and operators whose projects switch on dependency conditions and use worktree step workspaces. Projects with dependency conditions off are unchanged.

**What this release solves:** [#1208](https://github.com/foolzzz/looper/pull/1208) adds the provider `coco login` (vendor `coco-login`, seeded as `prov-coco-login` by a schema migration) and a `coco_login` check in `looper doctor`. No runtime uses the provider yet. [#1204](https://github.com/foolzzz/looper/pull/1204) makes a saved `on: completed` leaf wait for acceptance when steps run in worktrees, at readiness time as well as at admission.

**Breaking changes:** No. There is a small additive database migration (a provider row and a widened vendor check); there is no API removal. The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.14.126
```

**Contributors:** Maintainer @foolzzz authored [#1208](https://github.com/foolzzz/looper/pull/1208) and [#1204](https://github.com/foolzzz/looper/pull/1204); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.125 upgrades directly. The schema change is additive: on first start the server widens the `llm_providers` vendor constraint to accept `coco-login` and seeds the provider, recorded as the migration `coco_login`.

## Behavior changes

- **A built-in `coco login` provider** ([#1208](https://github.com/foolzzz/looper/pull/1208)). It appears in Settings → Providers (name `coco login`, with a numeric suffix if that name was taken) with an `openai-responses` endpoint used only for pairing with `coco`, not for requests. Looper never reads or copies the login file; it links `cli/auth.json` in a run home to the file in the server's `TRAE_HOME`, defaulting to `~/.trae/cli/auth.json`. `TRAE_HOME` is now passed through to child processes.
- **Probes and models.** The login state comes from `coco login status` in a temporary home holding only that link, cached for 30 seconds; model names come from `coco models --json` in the same kind of home, cached for 10 minutes. The suggested models are `GPT-5.5` and `GPT-6.1-Sol`.
- **Forked links.** Startup inspects the homes under the runtime root with the shared linked-login scheme (Codex and Grok use the same). A replaced or removed link is repaired and recorded under `coco_login_fork`; Settings shows the login as unavailable until the operator checks `coco login status` and uses "Use the login again" (this action now accepts the coco provider; its refusal message for other providers reads "not a linked runtime login"). The shared inspection now creates the missing parent directory of a link before relinking.
- **`looper doctor` and system status gain `coco_login`.** It reports OK "not used" when no Agent Profile uses the login, SKIP when the profiles cannot be read, FAIL for a recorded fork or a logged-out coco, and WARN when the probe is inconclusive.
- **Worktree readiness** ([#1204](https://github.com/foolzzz/looper/pull/1204)). In a project that uses worktree step workspaces, a stored `ready_when` leaf `on: completed` is evaluated as `on: verified`: a worktree starts from the merged base, so the dependent waits for acceptance. This applies when the Planner dispatches ready steps and in the readiness states shown by task detail (full and compact) and the pipeline view. A step with panel reviews is exempt, because its seats review the Worker's snapshot before acceptance and waiting for verified would deadlock them.
- **Manager switch.** The PR confirms the Manager can read and set the project's `dependency_conditions` switch (added earlier) and adds a test for the readiness behavior; no Manager tool changes in this release.
- **Unchanged:** projects with the dependency-conditions switch off or without worktree workspaces (a stored completed leaf is satisfied as before), tasks without conditions, and the issue's eval item, which stays with the maintainer.
- **Model-visible changes:** None to the Planner, Worker, Reviewer or Manager prompts and contracts. What changes is data they see: a step's `ready_state` can read `pending` instead of `satisfied` in worktree projects, and Settings, `looper doctor` and system status list the new provider and check.

## 中文摘要

本版本是 patch release v2.14.126（热修线，每个合并的改动立即发布）。自 v2.14.125 以来合并了两项改动：内置的 `coco login` provider，把服务器所在机器上运维者的 coco 登录链接进运行目录（[#1208](https://github.com/foolzzz/looper/pull/1208)）；以及在项目使用 worktree 步骤工作区时，在就绪判断阶段把已存储的 `on: completed` 依赖视为尚未满足（[#1204](https://github.com/foolzzz/looper/pull/1204)，issue #1174）。

### 升级决策

**谁需要升级：**打算用机器登录方式使用 coco 的运维者，以及开启依赖条件并使用 worktree 步骤工作区的项目运维者。依赖条件关闭的项目无变化。

**解决了什么：**[#1208](https://github.com/foolzzz/looper/pull/1208) 新增 provider `coco login`（vendor `coco-login`，由结构迁移播种为 `prov-coco-login`）和 `looper doctor` 的 `coco_login` 检查，目前尚无运行时使用它。[#1204](https://github.com/foolzzz/looper/pull/1204) 让已存储的 `on: completed` 在 worktree 模式下等待验收，就绪判断与准入一致。

**是否有破坏性变更：**否。有一项小的增量数据库迁移（新增一行 provider，放宽 vendor 约束），没有移除 API。桥接边界不变：早于 v2.13.165 的安装须先升级到 v2.13.165。

**如何验证：**核对版本为 2.14.126。

**贡献者：**维护者 @foolzzz 提交 [#1208](https://github.com/foolzzz/looper/pull/1208) 和 [#1204](https://github.com/foolzzz/looper/pull/1204)；本版本无社区贡献。

```bash
looper --version   # looper 2.14.126
```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.125 上的安装可直接升级。结构变更是增量的：首次启动时服务器放宽 `llm_providers` 的 vendor 约束以接受 `coco-login` 并播种该 provider，迁移名为 `coco_login`。

### 行为变化与入口

- **内置 `coco login` provider**（[#1208](https://github.com/foolzzz/looper/pull/1208)）。出现在设置 → Providers 中（名称 `coco login`，若重名则加数字后缀），其 `openai-responses` 端点仅用于与 `coco` 配对，不用于请求。Looper 从不读取或复制登录文件，只把运行目录中的 `cli/auth.json` 链接到服务器 `TRAE_HOME` 下的文件（默认 `~/.trae/cli/auth.json`）。`TRAE_HOME` 现在会传给子进程。
- **探测与模型。**登录状态来自在仅含该链接的临时目录中运行 `coco login status`，缓存 30 秒；模型名来自同类目录中的 `coco models --json`，缓存 10 分钟。建议模型为 `GPT-5.5` 和 `GPT-6.1-Sol`。
- **链接分叉。**启动时用共享的 linked-login 方案检查运行时根目录下的各目录（Codex 和 Grok 同样）。被替换或删除的链接会被修复并记录在 `coco_login_fork` 下；设置页显示该登录不可用，直到运维者检查 `coco login status` 并点击“Use the login again”（该操作现在接受 coco provider；对其他 provider 的拒绝信息改为“not a linked runtime login”）。共享的检查在重新链接前会补建链接缺失的父目录。
- **`looper doctor` 与系统状态新增 `coco_login`。**没有 Agent Profile 使用该登录时报告 OK “not used”；无法读取 Profile 时为 SKIP；有分叉记录或 coco 未登录时为 FAIL；探测结果不确定时为 WARN。
- **Worktree 就绪判断**（[#1204](https://github.com/foolzzz/looper/pull/1204)）。在使用 worktree 步骤工作区的项目中，已存储的 `ready_when` 叶子 `on: completed` 按 `on: verified` 评估：worktree 从已合并的基线开始，因此依赖步骤要等验收。这既适用于 Planner 派发就绪步骤，也适用于任务详情（完整与精简）和流水线视图中的就绪状态。带评审小组的步骤除外，因为其席位在验收前评审 Worker 的快照，等待 verified 会死锁。
- **Manager 开关。**该 PR 确认 Manager 可以读取和设置项目的 `dependency_conditions` 开关（此前已加入），并为就绪行为补充了测试；本版本不改动 Manager 工具。
- **不变：**依赖条件开关关闭或未使用 worktree 工作区的项目（已存储的 completed 叶子照旧视为满足）、没有条件的任务，以及 issue 中的 eval 项（仍由维护者负责）。
- **面向模型的变化：**Planner、Worker、Reviewer 和 Manager 的提示词与契约无变化。变化的是它们看到的数据：worktree 项目中步骤的 `ready_state` 可能显示 `pending` 而非 `satisfied`；设置页、`looper doctor` 和系统状态会列出新的 provider 与检查。

### 可选能力启用与使用

本版本未新增可选能力启用入口。`coco login` provider 已列出，但目前尚无运行时使用它。

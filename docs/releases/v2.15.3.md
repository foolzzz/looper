# Looper v2.15.3

This is the patch release v2.15.3, a hotfix line in which each merged change ships at once. It documents one change: [#1372](https://github.com/foolzzz/looper/pull/1372) (Grok steering and room push over ACP).

## Release Decision

**Who should upgrade:** Operators who run Grok Workers or Reviewers (Grok 1.0.77 or later) and want Planner messages and room messages to reach a run while it works instead of waiting to be pulled.

**What this release solves:** [#1372](https://github.com/foolzzz/looper/pull/1372) lets Grok Workers and Reviewers receive Planner corrections and room deliveries during an active turn, over ACP and Grok's hidden `_x.ai/interject` method. Before, Grok runs were headless, took no input while they ran and pulled room messages through the room tools. Acceptance by Grok is not treated as proof that the model read a delivery.

**Breaking changes:** No. The CLI, the API and the dashboard are unchanged, no new command or control is added and there is no PostgreSQL schema change. The PR states a behavior change, listed below. The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.15.3
```

**Contributors:** Maintainer @foolzzz authored [#1372](https://github.com/foolzzz/looper/pull/1372); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.15.2 upgrades directly. There is no PostgreSQL schema change. Restart the service after upgrading, as for every release. Existing Grok registrations keep their saved capabilities until you use Re-detect on them.

## Behavior changes

Read in the diff of the PR.

### #1372: Grok steering and room push over ACP

- **Detection.** `GrokRuntime.probe` runs `--version` and, for Grok 1.0.77 or later, starts `grok agent stdio` in an empty temporary home, initializes it and calls `_x.ai/interject` on a nonexistent session. Only a -32602 error saying "session not found" adds the `steer` capability. A failed, timed-out or different reply keeps the capabilities as before. The probe makes no model call.
- **Launch.** With detected steering, Workers and Reviewers run over one ACP process in the run's isolated home (`GrokChannel`, `steer_command`). The channel reuses the ACP event and cost translation, emulates the model-response limit (`max_turns`) and applies tool restrictions through an agent profile. Runs without the capability keep the headless command. The Manager and Planner transport is unchanged.
- **Delivery.** Planner corrections and room deliveries are sent with the delivery UUID as `interjectionId`. The reply is accepted in Grok 1.0.77's nested `result.result.status` shape and in the flat shape. A correction accepted by Grok after the final response still reaches `WORK_RESULT.missed_input`.
- **Receipts.** An accepted room delivery stays in flight. It is marked read only on model output that starts after a tool result that follows the acceptance notification. A refused or unseen delivery stays unread; Grok has no timer fallback (`room_receipt_fallback` is false). Steering never cancels a running tool.
- **Re-detect.** Existing registrations keep their saved capabilities until Re-detect; after it finds steering, room delivery switches from `PULL` to `PUSHED`.
- **Evals.** The room metrics of the prompt regression evals count Grok room calls wrapped in `use_tool`. This changes eval counting only.
- **Runner channel.** `RunnerChannel.send` keeps only Planner input for `dropped_input()`; a delivery whose id starts with `looper-reminder-` is no longer recorded.
- **Docs.** The PR description says it documents runtime behavior, receipt boundaries and the remaining real-path checks, but the PR's file list changes no documentation file.

### Model-visible changes

Yes, for Grok Workers and Reviewers whose registration has detected steering. `room_input` gives them the pushed room guidance (`PUSHED`) instead of the pull guidance (`PULL`), so the room section of their prompts changes, and Planner corrections and room message bodies arrive as steered input in the run's turn. Grok registrations without detected steering and other runtimes are unchanged. No tool schema was changed by this PR.

### 行为变化与入口

以下在该 PR 的差异中可见。

**#1372：Grok 通过 ACP 支持 steer 和房间推送**

- **检测。**`GrokRuntime.probe` 先运行 `--version`；对 Grok 1.0.77 及以上，在空的临时 home 中启动 `grok agent stdio`，初始化后对一个不存在的会话调用 `_x.ai/interject`。只有 -32602 且提示 “session not found” 的错误才会加入 `steer` 能力。失败、超时或其他回复时能力保持不变。探测不调用模型。
- **启动。**检测到 steer 的 Worker 和 Reviewer 在运行的隔离 home 中通过一个 ACP 进程运行（`GrokChannel`、`steer_command`）。该通道复用 ACP 的事件和成本转换，模拟模型响应上限（`max_turns`），并通过 agent profile 应用工具限制。没有该能力的运行保持无头命令。Manager 和 Planner 的传输不变。
- **投递。**Planner 纠正和房间投递以投递 UUID 作为 `interjectionId` 发送。回复接受 Grok 1.0.77 嵌套的 `result.result.status` 形式和扁平形式。最终回复之后被 Grok 接受的纠正仍会进入 `WORK_RESULT.missed_input`。
- **回执。**被接受的房间投递保持在途状态，仅当在验收通知之后的工具结果之后开始的模型输出出现时才标记已读。被拒绝或未见到的投递保持未读；Grok 没有定时器兜底（`room_receipt_fallback` 为 false）。steer 从不取消正在运行的工具。
- **重新检测。**现有注册在 Re-detect 之前保留原有能力；发现 steer 后，房间投递从 `PULL` 切换为 `PUSHED`。
- **评测。**提示词回归评测的房间指标会统计经 `use_tool` 包装的 Grok 房间调用，只影响评测计数。
- **Runner 通道。**`RunnerChannel.send` 只为 Planner 输入保留 `dropped_input()` 记录；id 以 `looper-reminder-` 开头的投递不再记录。
- **文档。**PR 描述称文档记录了运行时行为、回执边界和剩余的真实路径检查，但该 PR 的文件列表没有改动任何文档文件。

**面向模型的变化：**有，针对已检测到 steer 的 Grok Worker 和 Reviewer。`room_input` 为它们给出推送式房间指引（`PUSHED`）而不是拉取式（`PULL`），因此其提示词中的房间部分会变化，Planner 纠正和房间消息正文作为 steer 输入进入运行的当前轮次。未检测到 steer 的 Grok 注册和其他运行时不变。该 PR 未改动工具 schema。

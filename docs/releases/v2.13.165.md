# Looper v2.13.165

## Release Decision

**Who should upgrade:** Anyone who deletes scenario Managers while they are replying, or who deletes a Manager that still has tasks, schedules, bots or chat bindings. Everyone else can stay on v2.13.164.

**What this release solves:** [#727](https://github.com/foolzzz/looper/pull/727) makes a Manager deletion check every blocking dependent before it stops the Manager's reply, so a refused deletion leaves the current reply and queued messages untouched, and keeps a slow or unresponsive reply from blocking a deletion indefinitely.

**Breaking changes:** No. No API, database schema, configuration, prompt or Tool declaration changed; the deletion result values are the same.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#727](https://github.com/foolzzz/looper/pull/727); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.165
```

## Behavior changes

- **Deletion order ([#727](https://github.com/foolzzz/looper/pull/727)):** `db_managers.delete_manager` first runs the refusal checks (tasks, schedules, bots, chat bindings) without the row lock. Only if none applies does it call `before_delete`, which drains the resident Manager. After the drain it takes the row lock and runs the checks again, then deletes. A dependent created during the drain refuses the deletion, and the interrupted turn and queued messages are replayed as for a rollback. Before this change the row lock was taken first and the checks ran under it, so a refusal was also reported before the drain, but the lock was held while the turn drained.
- **Locks ([#727](https://github.com/foolzzz/looper/pull/727)):** `ManagerFleet.delete_manager` is serialized by a new delete lock and takes the fleet lock only in short sections, not across the drain, so a turn that needs the fleet lock can finish. The database side takes a transaction advisory lock (`lock_installs`) for the whole deletion, and library-install writes in `looper/db/manager_installs.py` take the same lock, so installs wait for a deletion. The Manager row is locked only after the drain, so a turn can still write work that needs that row.
- **Reconciliation ([#727](https://github.com/foolzzz/looper/pull/727)):** while a deletion is in progress, `_apply_once` skips that Manager; the deleting call reconciles the latest definition after commit or rollback, so a refused or rolled-back deletion leaves an enabled Manager running.
- **Bounded drain ([#727](https://github.com/foolzzz/looper/pull/727)):** `ManagerAgent.stop` waits at most `STOP_DRAIN_SEC` (10 s) for the turn task to end and at most 10 s for the resident process to close, then logs a warning and goes on with shutdown instead of blocking. The close no longer takes the turn lock; it takes only the lifecycle gate. After a shutdown, the Manager's message loop exits instead of waiting for another bus message.
- **Model-visible changes:** none. No prompt, tool description or tool schema changed. The only text change is a log warning when a drain times out.
- **Tests:** `tests/test_manager_fleet_db.py`, `tests/test_manager_installs_db.py` and `tests/test_scenario_manager_agent.py` are changed.
- **Description mismatch:** the description of #727 says "production 0" added lines and "target 40–150 changed lines"; the file list shows 103 added production lines in four files and 218 added test lines, and this draft takes the file list as authoritative.

## Upgrade and rollback

Re-run `install.sh` once v2.13.165 is published; there is no migration and no configuration change. Rolling back to v2.13.164 restores the earlier deletion order.

## 中文摘要

### 升级决策

**谁需要升级：**在 scenario Manager 正在回复时删除它的人，或删除仍有任务、计划、bot 或聊天绑定的 Manager 的人。其他人可留在 v2.13.164。

**解决了什么：**[#727](https://github.com/foolzzz/looper/pull/727) 让删除 Manager 先检查所有阻止删除的依赖，再停止其回复，因此被拒绝的删除不会影响当前回复和排队消息；同时避免响应缓慢的回复无限期阻塞删除。

**是否有破坏性变更：**否。API、数据库 schema、配置、prompt 和 Tool 声明均未改变，删除结果的取值不变。

**如何验证：**运行 `looper --version` 核对版本为 2.13.165。

**贡献者：**维护者 @foolzzz 提交 [#727](https://github.com/foolzzz/looper/pull/727)；本次 patch release 无社区贡献。

```bash
looper --version   # looper 2.13.165
```

### 行为变化与入口

- **删除顺序（#727）：**`db_managers.delete_manager` 先不加行锁运行拒绝检查（任务、计划、bot、聊天绑定）；仅当都不成立时才调用 `before_delete` 排空常驻 Manager。排空后加行锁，再次检查后删除。排空期间新出现的依赖会使删除被拒绝，被中断的轮次和排队消息按回滚处理重放。此前先加行锁再检查，排空期间持有该锁。
- **锁（#727）：**`ManagerFleet.delete_manager` 由新的删除锁串行化，仅在短区间内持有 fleet 锁，不跨越排空，使需要 fleet 锁的轮次可以完成。数据库侧在整个删除期间持有事务级 advisory 锁（`lock_installs`），`looper/db/manager_installs.py` 中的库安装写入使用同一把锁，因此安装会等待删除。Manager 行仅在排空之后加锁，轮次仍可写入需要该行的工作。
- **协调（#727）：**删除进行中，`_apply_once` 跳过该 Manager；删除调用在提交或回滚后协调最新定义，因此被拒绝或回滚的删除会让已启用的 Manager 继续运行。
- **有界排空（#727）：**`ManagerAgent.stop` 等待轮次任务结束最多 `STOP_DRAIN_SEC`（10 秒），等待常驻进程关闭最多 10 秒，之后记录警告并继续关闭，而不是阻塞。关闭不再获取轮次锁，只获取生命周期 gate。关闭之后，Manager 的消息循环会退出，而不是等待下一条总线消息。
- **面向模型的变化：**无。prompt、工具描述和工具 schema 均未改变，唯一的文本变化是排空超时时的日志警告。
- **测试：**修改 `tests/test_manager_fleet_db.py`、`tests/test_manager_installs_db.py` 和 `tests/test_scenario_manager_agent.py`。
- **描述不符：**#727 的描述写“production 0”新增行和“target 40–150 changed lines”；文件清单显示四个文件新增 103 行生产代码、218 行测试，本草稿以文件清单为准。

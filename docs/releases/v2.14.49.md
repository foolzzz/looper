# Looper v2.14.49

This is the patch release v2.14.49, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.48: an opt-in keeper switch with a single control-plane lock per database ([#1012](https://github.com/foolzzz/looper/pull/1012)). The switch defaults to off, so an installation that does not set it keeps its current startup and shutdown; some process bookkeeping changes apply either way (see Behavior changes).

## Release Decision

**Who should upgrade:** Anyone who wants to stay on the latest patch line, and anyone who will turn on `[agent_host] keeper = "on"` to have one server per database.

**What this release solves:** [#1012](https://github.com/foolzzz/looper/pull/1012) adds `[agent_host] keeper` to the ops file. With `on`, `looper serve` holds a session advisory lock so only one control plane runs on a database, increments a control-plane epoch that later keeper work uses for fencing, and exits with code 75 if it loses the lock.

**Breaking changes:** No. The new setting is optional and defaults to `off`; no API or configuration is removed, and there is no new migration.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#1012](https://github.com/foolzzz/looper/pull/1012); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.49
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.48 upgrades directly. This release adds no migration. The only new setting is `[agent_host] keeper`, which defaults to `off`.

## Behavior changes

- **Keeper switch ([#1012](https://github.com/foolzzz/looper/pull/1012)).** The ops file accepts `[agent_host] keeper = "off" | "on"` (file only; any other value stops the command with a message that names the key). `looper config init-ops` writes `[agent_host] keeper = "on"` only when keeper is on. With `off` (the default), the server takes no lock and writes no epoch.
- **One control plane per database (keeper on).**
  - `looper serve` connects a dedicated session with an application name containing its pid and host, takes `pg_try_advisory_lock` on it, and only then opens the database pool, backs up and ensures the schema.
  - If the lock is held, startup fails with "another looper serve already runs on this database" and the holder's pid, application name, client address and backend start time (unavailable fields show as unknown).
  - After the schema is ready it increments `control_plane_epoch` in `system_settings` and logs it. No migration is involved; the row is created on first use.
  - A health check on the lock session runs every 5 s with a 5 s timeout. A closed connection, a failed check or a missing lock marks the lease lost.
- **Lost lock is terminal (keeper on).** The server fences the database pool (`get_pool` and new connections raise), refuses new agent spawns, closes the HTTP listener, ends its own recorded agents within 10 s and exits with code 75; a 15 s backstop forces that exit. It does not update run records or detach runs. A lock lost during startup or shutdown takes the same path, and a normal shutdown's exit code becomes 75 if loss happened first. The service manager is expected to restart the process, which must take the lock again.
- **Process bookkeeping changes, with keeper off too.**
  - `proc_tree.spawn` registers every in-flight spawn and every owned process, even when its durable record cannot be written; a record failure no longer drops tracking.
  - When ending an orphaned agent's tree (for example at the startup sweep) after SIGTERM, the final SIGKILL goes only to survivors whose pid, process group and start time were confirmed, one pid at a time, rather than to the whole group. A pid whose start time cannot be read is no longer treated as reused.
  - The final wait after SIGKILL now also applies to those orphan kills.
  - New helpers `fence_spawns`, `end_owned`, `database.connection.fence` and `AgentHTTPServer.close_listener` support the lost-lock path.
- **Shutdown.** The database pool and lock are now also released if startup fails after they were opened. The scheduler's documentation notes that row locks keep two servers from double-firing only with keeper off; with keeper on, one control plane runs per database.
- **Model-visible changes:** No. No prompt, tool description, tool schema or Manager confirmation text changes.

## Optional Capability Activation & Use

### Control-plane lock ([agent_host] keeper)

**Activation:** Set `keeper = "on"` under `[agent_host]` in the ops file and restart `looper serve`. Stop any other server on the same database first.

```bash
printf '[agent_host]\nkeeper = "on"\n'   # add these lines to the ops file
looper serve --config <ops file> --runtime-root <root>
```

**Validation:** Start a second `looper serve` on the same database; it must refuse to start and name the holder. The log of the first shows `control plane epoch=<n>`, and `system_settings` holds the `control_plane_epoch` key.

**Disable / rollback:** Set `keeper = "off"` (or remove the section) and restart. The lock is released when the server stops; the epoch row stays and is harmless.

**Authority boundary:** The lock is a PostgreSQL session advisory lock in the database the server already uses. It fences only this server's own pool, listener and agents, and never touches another server's runs.

**Docs:** [docs/architecture/agent-system.md](https://github.com/foolzzz/looper/blob/main/docs/architecture/agent-system.md), section "One control plane per database".

### 行为变化与入口

- **Keeper 开关（[#1012](https://github.com/foolzzz/looper/pull/1012)）。**ops 文件接受 `[agent_host] keeper = "off" | "on"`（仅文件；其他值会使命令停止并指出该键）。`looper config init-ops` 仅在 keeper 为 on 时写入 `[agent_host] keeper = "on"`。为 `off`（默认）时，服务器不取锁，也不写 epoch。
- **每个数据库一个控制面（keeper 开启）。**
  - `looper serve` 先连接一个专用会话（应用名含 pid 与主机名），在其上执行 `pg_try_advisory_lock`，之后才打开数据库连接池、备份并确保 schema。
  - 锁已被占用时，启动失败并提示 “another looper serve already runs on this database”，同时给出持有者的 pid、应用名、客户端地址和后端启动时间（不可得的字段显示为 unknown）。
  - schema 就绪后，递增 `system_settings` 中的 `control_plane_epoch` 并记入日志。不涉及迁移；该行在首次使用时创建。
  - 锁会话每 5 秒做一次健康检查，超时 5 秒。连接关闭、检查失败或锁不存在都会把租约标为丢失。
- **丢锁是终态（keeper 开启）。**服务器隔离数据库连接池（`get_pool` 和新连接会报错），拒绝新的 agent 启动，关闭 HTTP 监听，在 10 秒内结束自己已记录的 agent，并以退出码 75 退出；15 秒后备定时器会强制退出。它不更新运行记录，也不分离运行。启动或关闭期间丢锁走同一路径；若丢锁先发生，正常关闭的退出码也变为 75。服务管理器应重启进程，新进程必须重新取锁。
- **进程记账变化（keeper 关闭时同样生效）。**
  - `proc_tree.spawn` 登记每个进行中的启动和每个自有进程，即使无法写入持久记录；记录失败不再导致丢失跟踪。
  - 结束孤儿 agent 的进程树（例如启动时清扫）时，SIGTERM 之后的最终 SIGKILL 只发给 pid、进程组和启动时间都已确认的幸存者，逐个 pid 发送，而不是发给整个进程组。读不到启动时间的 pid 不再被当作已复用。
  - SIGKILL 之后的最终等待现在也适用于这些孤儿的结束。
  - 新增辅助：`fence_spawns`、`end_owned`、`database.connection.fence` 和 `AgentHTTPServer.close_listener`，用于丢锁路径。
- **关闭。**启动在连接池和锁打开后失败时，现在也会释放它们。调度器文档说明：行锁只在 keeper 关闭时防止两个服务器重复触发；keeper 开启时一个数据库只运行一个控制面。
- **面向模型的变化：**无。没有 prompt、工具描述、工具 schema 或 Manager 确认文本的变化。

### 可选能力启用与使用

#### Control-plane lock ([agent_host] keeper)

**启用：**在 ops 文件的 `[agent_host]` 下设置 `keeper = "on"` 并重启 `looper serve`。先停止同一数据库上的其他服务器。

```bash
printf '[agent_host]\nkeeper = "on"\n'   # add these lines to the ops file
looper serve --config <ops file> --runtime-root <root>
```

**验证：**在同一数据库上再启动一个 `looper serve`，它必须拒绝启动并指出持有者。第一个服务器的日志显示 `control plane epoch=<n>`，`system_settings` 中有 `control_plane_epoch` 键。

**停用 / 回退：**设为 `keeper = "off"`（或删除该段）并重启。服务器停止时锁会释放；epoch 行会保留，无害。

**权限边界：**锁是服务器已在使用的数据库中的 PostgreSQL 会话 advisory lock。它只隔离本服务器自己的连接池、监听和 agent，不会触碰其他服务器的运行。

**文档：**[docs/architecture/agent-system.md](https://github.com/foolzzz/looper/blob/main/docs/architecture/agent-system.md)，“One control plane per database”一节。

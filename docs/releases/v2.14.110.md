# Looper v2.14.110

This is the patch release v2.14.110, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.109: Agent Profile fallback chains and the model actually used ([#1170](https://github.com/foolzzz/looper/pull/1170)).

## Release Decision

**Who should upgrade:** Operators who want a run to continue on another Agent Profile when its own profile cannot start, and anyone who reads run records and wants to see which model a run really used. Installations that configure no fallback behave as before, apart from the two new run fields.

**What this release solves:** [#1170](https://github.com/foolzzz/looper/pull/1170). A run whose Agent Profile could not start failed, and a run record showed only the requested model. An Agent Profile may now name one fallback profile; the run switches only when its profile cannot start (or, where an adapter is verified, its process produced no model event), never by matching error text. The run records the model actually reported and any fallback with its reason.

**Breaking changes:** No. No new dependency and no configuration change. The database gains one nullable column (see Upgrading); the API only adds fields. Profiles without a fallback run exactly as before.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.14.110
```

**Contributors:** Maintainer @foolzzz authored [#1170](https://github.com/foolzzz/looper/pull/1170); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.109 upgrades directly. The schema change is additive: once, `ensure_schema` adds the nullable `agent_profiles.fallback_profile_id` column (a foreign key to `agent_profiles(id)`, `ON DELETE RESTRICT`), adds `profile_fallback` to the allowed `task_journal` kinds and records the `profile_fallback` migration. Until then it is a pending schema change. An older Looper reading the upgraded database does not know the new journal kind.

## Behavior changes

- **Fallback profile** (`looper/agents/profile_registry.py`, `looper/db/profile_registry.py`, `looper/db/schema.sql`, `looper/db/connection.py`). An Agent Profile has an optional `fallback_profile_id`. A chain is acyclic, has at most three hops and the target must serve every role the source serves. Create and edit validate the whole resulting graph (incoming chains too, under an advisory lock). A profile that is a fallback target cannot be deleted (the registry refuses, and the foreign key backs it).
- **Planner** (`looper/agents/tiers/planner.py`). Follows the chain only when the profile has a configuration error (`profile_error`), up to three hops, and annotates the run with `fallback_from`. Each switch is journaled.
- **Worker and Reviewer** (`looper/agents/tiers/worker.py`). Fall back on a profile configuration error and on a launch failure (`start_error`). They also fall back on a nonzero exit, or a timeout, before any model event (`no_model_events`), but only for a runtime whose `first_event_known` is true. The base runtime sets it false and no shipped adapter overrides it, so in this release that detection is off for every runtime. A switch stays within the same step attempt and consumes no retry. It records an activity line, a `profile_fallback` journal entry per switch (role, step, from, to, reason) and `fallback_from` and `fallback` on the next run's metadata. Input dropped while switching is reported as `missed_input`. Adopting a kept run uses the profile recorded on that run rather than the current selection.
- **Manager sessions** do not follow fallback chains.
- **Model actually used** (`looper/agents/claude_cli.py`, `looper/agents/runtimes/*`, `looper/agents/v1_domains/runs.py`). `runs.get` and `runs.list` add `model_requested` and `model_reported`. The Claude Code, Cursor, Grok, Pi and OMP adapters report the model identifier they see in events and it is stored as `model_reported`; for Codex, Grok, Pi, OMP and DSH an unreported model stays null rather than reusing the request. The existing `model` field is unchanged.
- **Profile API, config transfer and Settings** (`looper/agents/ops/config.py`, `looper/agents/config_transfer.py`, `web/`). Profile views and the create/update operations carry `fallback_profile_id` (null clears it) and the target's name. Config export and import carry a `fallback` profile name, resolved after all profiles exist and validated as a whole. The dashboard's Agent Profiles form gains a "Fallback to" selector, and the profile shows its target and which profiles use it as a fallback.
- **Documentation and tests.** `docs/architecture/agent-system.md` describes the chains. New tests: `tests/test_profile_fallback_registry_db.py`, `tests/test_planner_profile_fallback.py`, `tests/test_profile_fallback_events.py`; others extended.
- **Unchanged:** profiles without a fallback, Manager sessions, channels (Telegram and Lark), dependencies, billing and the `model` field of run records.
- **Model-visible changes:** No change to prompt text, tool schemas or launch environment for any role. The Manager's profile tools (`looper/agents/ops/config.py`) gain the `fallback_profile_id` argument and the target's id and name in their answers, which a Manager model sees in its tool schema and results. A run that fell back runs the fallback profile's model and custom prompt instead of the original's.

### 升级决策

**谁需要升级：**希望运行在自身 profile 无法启动时改用另一个 Agent Profile 的运维人员，以及想知道一次运行实际用了哪个模型的人。未配置回退的安装行为不变，只多了两个运行字段。

**解决了什么：**[#1170](https://github.com/foolzzz/looper/pull/1170)。此前 Agent Profile 无法启动时运行直接失败，运行记录只显示请求的模型。现在 Agent Profile 可指定一个回退 profile；仅在 profile 无法启动（或在已验证的适配器上进程未产生任何模型事件）时切换，绝不靠匹配错误文本判断。运行会记录实际上报的模型以及回退及其原因。

**是否有破坏性变更：**否。无新依赖，无配置变更。数据库新增一个可空列（见升级）；API 只增加字段。没有回退的 profile 行为完全不变。

**如何验证：**核对版本为 2.14.110。

**贡献者：**维护者 @foolzzz 提交 [#1170](https://github.com/foolzzz/looper/pull/1170)；本版本无社区贡献。

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.109 上的安装可直接升级。数据库变更为增量：`ensure_schema` 一次性为 `agent_profiles` 增加可空列 `fallback_profile_id`（指向 `agent_profiles(id)` 的外键，`ON DELETE RESTRICT`），把 `profile_fallback` 加入 `task_journal` 允许的类型，并记录 `profile_fallback` 迁移。在此之前它被视为待处理的结构变更。旧版 Looper 读取已升级的数据库时不认识新的日志类型。

### 行为变化与入口

- **回退 profile**（`looper/agents/profile_registry.py`、`looper/db/profile_registry.py`、`looper/db/schema.sql`、`looper/db/connection.py`）。Agent Profile 有可选的 `fallback_profile_id`。回退链无环，最多三跳，目标必须覆盖源 profile 所服务的全部角色。创建和编辑会在咨询锁下校验整个结果图（包括指向它的链）。作为回退目标的 profile 不能删除（注册表拒绝，外键兜底）。
- **Planner**（`looper/agents/tiers/planner.py`）。仅当 profile 有配置错误（`profile_error`）时沿链回退，最多三跳，并在运行上标注 `fallback_from`。每次切换写入日志。
- **Worker 与 Reviewer**（`looper/agents/tiers/worker.py`）。在 profile 配置错误和启动失败（`start_error`）时回退；在产生任何模型事件之前以非零退出码退出或超时（`no_model_events`）时也回退，但仅限 `first_event_known` 为真的运行时。基类将其设为 false，目前没有任何适配器覆盖，所以本版本中该检测对所有运行时都是关闭的。切换发生在同一步骤尝试内，不消耗重试。它记录一条活动、每次切换一条 `profile_fallback` 日志（角色、步骤、from、to、原因），并在下一次运行的元数据上写入 `fallback_from` 和 `fallback`。切换期间丢弃的输入以 `missed_input` 报告。接管保留的运行时使用该运行记录的 profile，而不是当前选择。
- **Manager 会话**不沿回退链。
- **实际使用的模型**（`looper/agents/claude_cli.py`、`looper/agents/runtimes/*`、`looper/agents/v1_domains/runs.py`）。`runs.get` 和 `runs.list` 新增 `model_requested` 和 `model_reported`。Claude Code、Cursor、Grok、Pi、OMP 适配器上报事件中看到的模型标识并存为 `model_reported`；对 Codex、Grok、Pi、OMP、DSH，未上报的模型保持为 null，而不是沿用请求值。原有 `model` 字段不变。
- **Profile API、配置迁移与设置**（`looper/agents/ops/config.py`、`looper/agents/config_transfer.py`、`web/`）。Profile 视图及创建/更新操作带有 `fallback_profile_id`（null 表示清除）和目标名称。配置导出导入带 `fallback` profile 名称，在所有 profile 存在后解析并整体校验。仪表盘 Agent Profiles 表单新增 “Fallback to” 选择器，profile 上显示其目标以及哪些 profile 以它为回退。
- **文档与测试。**`docs/architecture/agent-system.md` 描述回退链。新增测试：`tests/test_profile_fallback_registry_db.py`、`tests/test_planner_profile_fallback.py`、`tests/test_profile_fallback_events.py`；其他测试有扩展。
- **不变：**没有回退的 profile、Manager 会话、渠道（Telegram 和 Lark）、依赖、计费以及运行记录的 `model` 字段。
- **面向模型的变化：**任何角色的提示文字、工具 schema 和启动环境均无变化。Manager 的 profile 工具（`looper/agents/ops/config.py`）新增 `fallback_profile_id` 参数，答复中带回退目标的 id 和名称，Manager 模型会在工具 schema 和结果中看到。发生回退的运行使用回退 profile 的模型和自定义提示，而不是原 profile 的。

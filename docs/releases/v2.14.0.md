# Looper v2.14.0

This is the minor release v2.14.0, not a patch release. It is the first release after the removal of the historical migrations and the old-input fallbacks, and it moves the supported upgrade path to the fixed bridge v2.13.165. Its only change since v2.13.208 is [#865](https://github.com/foolzzz/looper/pull/865), which documents that boundary and makes the release gate enforce the upgrade notice.

## What changed in the 2.13 series since the bridge release v2.13.165

- **Naming and entry points ([#762](https://github.com/foolzzz/looper/pull/762), v2.13.170):** the `loopx` command, the `~/.loopx` migration, the old service unit replacement, old dashboard hash redirects and old chat storage keys are gone.
- **Configuration ([#761](https://github.com/foolzzz/looper/pull/761), v2.13.173; [#790](https://github.com/foolzzz/looper/pull/790), v2.13.180):** `looper-config/v4` is the only configuration format written and read; older documents, unknown top-level fields and retired fields are refused before any work begins. The scheduler keeps only the stored minimum interval setting.
- **Database admission ([#808](https://github.com/foolzzz/looper/pull/808), v2.13.201; [#850](https://github.com/foolzzz/looper/pull/850), v2.13.203; [#855](https://github.com/foolzzz/looper/pull/855), v2.13.204):** the historical migrations are replaced by one final baseline (`schema.sql` plus `seeds.sql`). Startup admits an empty database, a current schema 4 database, or one completed v2.13.165 (or later schema-3) bridge database, which is converted once after a verified backup. Everything else is refused. `registry_migration.py` is deleted.
- **Stored input and records ([#857](https://github.com/foolzzz/looper/pull/857), v2.13.208):** startup and stored-input fallbacks for data older than the admitted path are removed, historical run records gain `metadata.presentation` at read time, and the message journal requires explicit identities.
- **Runners and the Pi SDK runner (v2.13.166–200, v2.13.202, v2.13.205–207):** a runner supervisor and resident runner sessions, a packaged TypeScript Pi runner, and the ops-file opt-in `[runtimes] pi = "runner"`, which hosts the Manager, Planner, Worker, Reviewer and consults. Later patches fix session close handling, steers from killed Workers, and usage and budget accounting for requests that were not sent, were rejected, or reported inconsistent usage.
- **Managers, schedules and catalog (v2.13.165, v2.13.175–177, v2.13.179, v2.13.182–183):** safer Manager deletion, schedule execution identity separate from presentation, the Manager schedule tool contract and confirmations, and Manager-only installations counted in the catalog.
- **Evals and CI (v2.13.167, v2.13.174, v2.13.178, v2.13.180, v2.13.184–186, v2.13.189):** the eval tooling accepts only current formats (`looper-prompt-eval/v2`, `looper-manager-dialogs/v2`), the dialogs readback is stricter, PR tests run in four parallel shards, and browser tests serve the staged dashboard.

## Release Decision

**Who should upgrade:** Operators on v2.13.165 or a later 2.13 release who want the current baseline, and anyone preparing a release, because the release gate now requires the bridge notice. An installation older than v2.13.165 must upgrade to v2.13.165 first (see Upgrading). It ships the one change merged since v2.13.208.

**What this release solves:** [#865](https://github.com/foolzzz/looper/pull/865) replaces stale upgrade instructions with the completed bridge path, `looper-config/v4`-only configuration, current eval schemas and rollback guidance, and makes `release-readiness-doc-smoke.py` require the bridge notice from v2.14.0 on.

**Breaking changes:** Yes, for installations older than the bridge: they must upgrade to v2.13.165 first and start it once, because this release accepts only an empty database, a current schema, or one completed v2.13.165 bridge database. The removals themselves shipped in the 2.13 patches above; this release changes no code or schema beyond them.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#865](https://github.com/foolzzz/looper/pull/865); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.0
```

## Upgrading

An installation older than v2.13.165 must upgrade to v2.13.165 first and be started once. v2.13.165 contains every historical migration and is the fixed bridge; a later 2.13 checkout does not move the boundary. An installation already on v2.13.165 or a later 2.13 release that has started once can upgrade directly.

While the installation is still on v2.13.165, finish the steps this release no longer performs:

- Start `looper serve` once, and import any configuration you still need, so the bridge markers are recorded.
- Run `looper config init-ops`, then `looper service install`, so the unit uses the private ops file and an explicit `--runtime-root`.
- Replace a leftover `loopx` data directory and the old `loopx` service unit. This release does not move the directory or replace that unit.
- Set the Telegram bot token variable explicitly (or the channel's own token variable); `service install` still copies the old `LOOPX`-named one for one release.
- Save the scheduler minimum in Settings. This release uses the stored `scheduler.min_interval_seconds` or the built-in 300 seconds and does not read the old scheduler variable.
- Stop and drain the old process before switching binaries.
- Open the dashboard once from the same origin, so the browser finishes its cache writes.

**What the first start changes and backs up:** an empty database runs the current schema once and records `post_bridge_baseline`. A completed v2.13.165 bridge database is converted once to schema 4 after `looper serve` takes a verified full custom-format `pg_dump`; the conversion writes a bounded task-config decode, channel allowlists, missing Claude session identities, the exact pre-rename system harness sentence, accounting basis and gate channel ids. A current database does not replay initialization DDL, and `seeds.sql` is applied on every start without changing saved choices. A separate local transition seals notice identities in the message journal once per runtime root. User files and other historical rows stay.

**What is refused:** any other database, with "upgrade to v2.13.165 or a later 2.13 release first"; a schema version above 4; a backup that fails or cannot be verified, which stops the upgrade; `looper serve --skip-backup` for this upgrade; any configuration format other than `looper-config/v4`, and a retired layer `model` or `effort` or a retired provider `protocols`, `base_url` or `models`, before anything is written; a task comparison not in `looper-prompt-eval/v2` and a dialog comparison not in `looper-manager-dialogs/v2`. Import an older configuration file on v2.13.165, upgrade that installation, then export v4 with this release; v2.13.165 may still export v3.

**Rollback:** the upgraded schema must not be opened by an older binary. Stop the new service, leave the upgraded database unchanged, restore the verified full backup into a separate database, and point the guarded older release at it. Writes made after the backup stay only in the upgraded database. A schema-only dump or a configuration export cannot restore history.

## Behavior changes

- **Release gate (`examples/release/release-readiness-doc-smoke.py`, `docs/releases/README.md`):** for a body named `vX.Y.Z.md` at 2.14.0 or later, the gate fails unless the body contains `upgrade to v2.13.165 first` and `## 中文摘要` contains `先升级到 v2.13.165`. Earlier bodies are skipped. The gate's self-test covers a v2.13.208 body (skipped), a v2.14.0 body without the notice (rejected) and one with it (accepted).
- **Documentation (`README.md`, `README.zh-CN.md`, `docs/architecture/agent-system.md`, `docs/plans/2026-10-13-long-horizon-agent-context.zh-CN.md`, `evals/README.md`):** describe the completed bridge boundary, v4-only configuration and `loopercli` transfer, rollback into a separate database, the steps to finish on v2.13.165, and the retired eval schemas.
- **Tests (`tests/test_config_transfer_db.py`):** the documented example test reads the `looper-config/v4` JSON block from the architecture guide instead of an inline copy.
- **Model-visible changes:** None. The pull request changes documentation, the release gate script and one test; no prompt, tool or message text of the running system changed.

### 升级

早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次。v2.13.165 包含全部历史迁移，是固定的桥接版本；更晚的 2.13 checkout 不移动边界。已在 v2.13.165 或更高 2.13 版本并启动过一次的安装可直接升级。

安装仍在 v2.13.165 时，先完成本版本不再执行的步骤：

- 启动一次 `looper serve`，并导入仍需要的配置，以记录桥接标记。
- 运行 `looper config init-ops`，再运行 `looper service install`，让服务单元使用私有运维文件和明确的 `--runtime-root`。
- 替换遗留的 `loopx` 数据目录和旧的 `loopx` 服务单元。本版本不会移动该目录或替换该单元。
- 明确设置 Telegram bot 令牌变量（或渠道自己的令牌变量）；`service install` 仍会为一个版本复制旧的 `LOOPX` 命名变量。
- 在设置页保存定时任务最小间隔。本版本使用已保存的 `scheduler.min_interval_seconds` 或内置 300 秒，不读取旧的定时任务变量。
- 切换二进制之前先停止并排空旧进程。
- 从同一来源打开一次仪表盘，让浏览器完成缓存写入。

**首次启动的变化与备份：**空库运行一次当前 schema 并记录 `post_bridge_baseline`。完成的 v2.13.165 桥接库在 `looper serve` 取得经验证的完整 custom 格式 `pg_dump` 之后转换一次到 schema 4；转换会写入有界的任务配置解码、渠道白名单、缺失的 Claude 会话身份、精确的改名前系统 harness 句子、计费基础和门控渠道 id。当前库不会重放初始化 DDL，`seeds.sql` 每次启动应用且不改变已保存的选择。另有一次本地转换，每个运行时根目录一次，封存消息日志中的通知身份。用户文件和其他历史行保留。

**被拒绝的情形：**其他任何数据库（提示“先升级到 v2.13.165 或更高 2.13 版本”）；schema 版本高于 4；备份失败或无法验证（升级中止）；本次升级使用 `looper serve --skip-backup`；`looper-config/v4` 之外的任何配置格式，以及已退役的层 `model` 或 `effort`、提供方 `protocols`、`base_url` 或 `models`（在写入前拒绝）；非 `looper-prompt-eval/v2` 的任务对照和非 `looper-manager-dialogs/v2` 的对话对照。旧配置文件须在 v2.13.165 导入，升级该安装后再用本版本导出 v4；v2.13.165 仍可能导出 v3。

**回退：**升级后的 schema 不能用旧二进制打开。停止新服务，保持升级后的数据库不变，把验证过的完整备份恢复到另一个数据库，并让受保护的旧版本指向它。备份之后的写入只存在于升级后的数据库。仅 schema 的转储或配置导出无法恢复历史。

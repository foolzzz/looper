# Looper v2.13.81

## Release Decision

**Who should upgrade:** Anyone who creates, edits, enables, deletes or runs schedules from the dashboard, or who calls the schedule write routes (`POST /api/projects/{id}/schedules`, `PUT` or `DELETE /api/schedules/{id}`, `POST /api/schedules/{id}/reset-planner-session`, `POST /api/schedules/{id}/run`) from a script. Everyone else gets no change.

**What this release solves:** [#500](https://github.com/foolzzz/looper/pull/500) moves schedule creation, update, deletion, Planner-session reset and run-now onto five typed operations in the versioned API, with confirmation where the action deletes data, starts a run, or lets a schedule spend more, and removes the five legacy write routes.

**Breaking changes:** Yes. The five legacy schedule write routes are removed; a script that calls them must use `POST /api/v1/schedule_admin/create`, `update`, `delete`, `reset_planner_session` or `run`. The dashboard shipped in this release already does. The schedule read routes are not touched.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#500](https://github.com/foolzzz/looper/pull/500); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.81
```

## Behavior changes

- **Five operations on v1 ([#500](https://github.com/foolzzz/looper/pull/500)):** the new `looper/agents/v1_domains/schedule_writes.py` registers `schedule_admin.create` and `schedule_admin.update` (risk `write`) and `schedule_admin.delete`, `schedule_admin.reset_planner_session` and `schedule_admin.run` (risk `high`), all `POST` at `/api/v1/schedule_admin/<action>`. Requests are closed objects. `create` takes `project_id` and `fields` (`name`, `cron` and `requirement` required); `update` takes `schedule_id` and `fields`, which must name at least one field, `enabled` included; the others take `schedule_id`. Field schemas carry the existing bounds (name length, parallel-run limit, run and gate timeouts, budget maximum, concurrency maximum).
- **Confirmation:** every operation except `create` is declared `confirms=True`. `delete`, `reset_planner_session` and `run` always answer `needs_confirmation` first with an impact text (delete: the schedule, its runs and notifications, created tasks stay; reset: the next run starts a new session, an active run keeps its own; run: one run now through the overlap check within the caps). `update` asks only when it enables a disabled schedule or raises or removes a run or daily budget cap, and otherwise runs at once. The impact step answers not-found for an unknown schedule, and `run` answers conflict when the server has no scheduler. The operations are not marked operator-only; this draft did not run the confirmation flow.
- **Service behavior kept:** execution calls the same `schedules` services as the old routes (`create_schedule`, `update_schedule`, `delete_schedule`, `reset_planner_session`, `run_now`). The no-scheduler refusal moved from the server's `_run_schedule_now` (HTTP 409) into the operation (conflict).
- **Response shape:** results are wrapped in the v1 `OpOk.result` envelope and errors follow the v1 error shape rather than the legacy `{"error": ...}` bodies. The legacy create route answered 201; the v1 operation does not.
- **Removed routes:** the five legacy write routes and their dispatch patterns and `_run_schedule_now` are removed from `looper/agents/http_server.py`.
- **Dashboard and docs:** `createSchedule`, `updateSchedule`, `deleteSchedule`, `resetSchedulePlannerSession` and `runSchedule` in `web/src/lib/api.ts` call the new operations; a confirmation answer is surfaced as an error to the caller by these functions. The READMEs' route table and `docs/architecture/agent-system.md` are updated, as are the schedule steps of `evals/prompt_regression/dialogs.py`.
- **Tests:** the new `tests/test_api_v1_schedule_writes.py`, `..._db.py` and `web/src/lib/api-schedule-writes.test.ts` were added; many existing schedule, config-transfer, Manager schedule tool and dashboard tests were moved to the new operations.
- **Model-visible changes:** None. The operations declare no Tool, and the Manager schedule tool tests only changed how they set up schedules, so no Manager, Worker, Planner or Reviewer prompt and no Manager Tool changed. The operations appear in the v1 operation catalog that API clients read.
- **Not confirmed in code:** this draft did not run any test; claims about confirmation and error answers come from the code.

## Upgrade and rollback

Re-run `install.sh` once v2.13.81 is published. No data migration. Update any script that used the removed routes. Rolling back to v2.13.80 restores them together with the old dashboard.

### 升级决策

**谁需要升级：**在仪表盘中创建、编辑、启用、删除或运行计划任务的人，或在脚本中调用计划任务写入路由（`POST /api/projects/{id}/schedules`、`PUT`/`DELETE /api/schedules/{id}`、`POST /api/schedules/{id}/reset-planner-session`、`POST /api/schedules/{id}/run`）的人。其他人无变化。

**解决了什么：**[#500](https://github.com/foolzzz/looper/pull/500) 把计划任务的创建、更新、删除、Planner 会话重置和立即运行迁到版本化 API 中五个带类型的操作；删除数据、启动运行或放宽花费上限时需要确认，并删除五条旧写入路由。

**是否有破坏性变更：**有。五条旧计划任务写入路由已移除；调用它们的脚本须改用 `POST /api/v1/schedule_admin/create`、`update`、`delete`、`reset_planner_session` 或 `run`。本版本附带的仪表盘已改用新操作。计划任务的读取路由未改动。

**如何验证：**运行 `looper --version` 核对版本为 2.13.81。

**贡献者：**维护者 @foolzzz 提交 [#500](https://github.com/foolzzz/looper/pull/500)；本次 patch release 无社区贡献。

### 行为变化与入口

- **五个 v1 操作（[#500](https://github.com/foolzzz/looper/pull/500)）：**新增 `looper/agents/v1_domains/schedule_writes.py`，注册 `schedule_admin.create`、`schedule_admin.update`（风险 `write`）以及 `schedule_admin.delete`、`schedule_admin.reset_planner_session`、`schedule_admin.run`（风险 `high`），均为 `POST /api/v1/schedule_admin/<action>`。请求为封闭对象。`create` 接收 `project_id` 与 `fields`（`name`、`cron`、`requirement` 必填）；`update` 接收 `schedule_id` 与 `fields`，至少要指定一个字段（含 `enabled`）；其余只接收 `schedule_id`。字段模式沿用现有上限（名称长度、并行运行数、运行与 gate 超时、预算上限、并发上限）。
- **确认：**除 `create` 外均声明 `confirms=True`。`delete`、`reset_planner_session`、`run` 总是先返回 `needs_confirmation` 和影响说明（删除：计划任务及其运行与通知，已创建的任务保留；重置：下次运行开启新会话，进行中的运行保留自己的会话；运行：经过重叠检查、在上限内立即运行一次）。`update` 仅在启用已停用的计划任务、或提高/取消运行或每日预算上限时才要求确认，否则直接执行。计划任务不存在时影响检查返回 not found；服务器没有调度器时 `run` 返回 conflict。这些操作未标记为仅限操作员；本草稿未运行确认流程。
- **服务行为不变：**执行时调用与旧路由相同的 `schedules` 服务（`create_schedule`、`update_schedule`、`delete_schedule`、`reset_planner_session`、`run_now`）。没有调度器时的拒绝逻辑从服务器的 `_run_schedule_now`（HTTP 409）移入操作内（conflict）。
- **响应形态：**结果包在 v1 的 `OpOk.result` 中，错误采用 v1 错误格式，不再是旧的 `{"error": ...}`。旧的创建路由返回 201，v1 操作不再如此。
- **移除的路由：**五条旧写入路由及其分派正则和 `_run_schedule_now` 已从 `looper/agents/http_server.py` 中移除。
- **仪表盘与文档：**`web/src/lib/api.ts` 中的 `createSchedule`、`updateSchedule`、`deleteSchedule`、`resetSchedulePlannerSession`、`runSchedule` 调用新操作；这些函数会把确认应答作为错误抛给调用方。README 的路由表、`docs/architecture/agent-system.md` 以及 `evals/prompt_regression/dialogs.py` 中的计划任务步骤同步更新。
- **测试：**新增 `tests/test_api_v1_schedule_writes.py`、`..._db.py` 与 `web/src/lib/api-schedule-writes.test.ts`；许多现有的计划任务、配置迁移、Manager 计划任务工具和仪表盘测试改用新操作。
- **面向模型的变化：**无。这些操作未声明 Tool，Manager 计划任务工具的测试只改了建立计划任务的方式，因此 Manager、Worker、Planner、Reviewer 的 prompt 和 Manager Tool 均未改动。它们会出现在 API 客户端读取的 v1 操作目录中。
- **代码中未确认：**本草稿未运行任何测试；关于确认流程和错误应答的说法来自代码。

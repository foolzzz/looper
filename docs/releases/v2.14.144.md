# Looper v2.14.144

This is the patch release v2.14.144, a hotfix line in which each merged change ships at once. It documents one change: [#1255](https://github.com/foolzzz/looper/pull/1255) (an adjudication repair keeps earlier downgrades and names only what the acceptance rule needs).

## Release Decision

**Who should upgrade:** Operators who run the Planner with review adjudication on, because the adjudicated accept and the repair message after a refused reply now name the smallest set of findings the acceptance rule needs, and a repaired reply is judged on its own complete set of downgrades. Everyone else gets no visible change.

**What this release solves:** [#1255](https://github.com/foolzzz/looper/pull/1255) (fixes #1253) makes the repair message of a refused adjudicated reply name every finding the repaired reply must downgrade, including ones the refused reply already downgraded, and makes the offered adjudicated accept name only the findings the acceptance rule needs.

**Breaking changes:** No. There is no migration and no API removal. The pull request calls the change intended (a maintainer decision). The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.14.144
```

**Contributors:** Maintainer @foolzzz authored [#1255](https://github.com/foolzzz/looper/pull/1255); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.143 upgrades directly. There is no schema change.

## Behavior changes

- **The repair message names the complete set to downgrade** ([#1255](https://github.com/foolzzz/looper/pull/1255), `looper/agents/tiers/planner.py`, `looper/agents/tiers/planner_protocol.py`). When a refused plain accept follows a decision turn that offered the adjudicated accept, the message names the findings from the saved review round that suffice (`<member> finding <n>`), says that downgrading this set suffices, and says that the repaired reply is judged on its own, so downgrades from the refused reply must be included again. Before, it named only the findings still blocking after the refused reply's downgrades.
- **The offered adjudicated accept names only what the rule needs** (`looper/agents/tiers/planner.py`, `looper/agents/tiers/review_adjudication.py`). The decision message that offers the adjudicated accept adds the line "For adjudicated accept, downgrading these findings suffices: ...". The set comes from the new `required_downgrades`: for `all_of` every blocking finding of the required seats, for `any_of` the seat with the fewest blocking findings, for `k_of` the k seats with the fewest; ties keep the acceptance rule's order. A seat that already satisfies its condition contributes none.
- **Eligibility reuses the same computation** (`looper/agents/tiers/review_adjudication.py`). `can_accept` is now true when `required_downgrades` returns a non-empty set. A step that already satisfies acceptance without downgrades has an empty set and is not eligible, as before (no blocking findings to downgrade).
- **A repaired reply is judged on its own** (`looper/agents/tiers/planner.py`). The refused reply's downgrades are no longer carried into the repair message's finding list; refused replies never change the saved round.
- **Unchanged:** the storage format of runs and journal entries, what the adjudication accepts, and the Worker, Reviewer and Manager prompts.
- **Model-visible changes:** Yes. The Planner's decision message gains the "downgrading these findings suffices" line when the adjudicated accept is offered, and the refusal text for a refused accept changes as above. The pull request states that the real-mode prompt eval runs before merge.

**谁需要升级：**开启评审裁决的 Planner 运维者，因为裁决式 accept 与被拒回复后的修复消息现在只点明接受规则所需的最小发现集合，修复后的回复按其自身完整的降级集合评判。其他人没有可见变化。

**解决了什么：**[#1255](https://github.com/foolzzz/looper/pull/1255)（修复 #1253）让被拒的裁决回复的修复消息点明修复后回复必须降级的每个发现（包括被拒回复已降级的），并让提供的裁决式 accept 只点明接受规则所需的发现。

**是否有破坏性变更：**否。没有迁移，没有移除 API。PR 称该改动是维护者的有意决定。桥接边界不变：早于 v2.13.165 的安装须先升级到 v2.13.165。

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.143 上的安装可直接升级。没有结构变更。

### 行为变化与入口

- **修复消息点明需降级的完整集合**（[#1255](https://github.com/foolzzz/looper/pull/1255)，`looper/agents/tiers/planner.py`、`looper/agents/tiers/planner_protocol.py`）。决策回合提供了裁决式 accept 而普通 accept 被拒时，消息以 `<member> finding <n>` 点明已保存评审轮中足以通过的发现，说明降级这一集合即可，并说明修复后的回复按其自身评判，因此被拒回复中的降级须再次包含。此前只点明被拒回复降级之后仍阻塞的发现。
- **提供的裁决式 accept 只点明规则所需**（`looper/agents/tiers/planner.py`、`looper/agents/tiers/review_adjudication.py`）。提供裁决式 accept 的决策消息新增一行 “For adjudicated accept, downgrading these findings suffices: ...”。集合由新增的 `required_downgrades` 给出：`all_of` 取所需席位的全部阻塞发现，`any_of` 取阻塞发现最少的席位，`k_of` 取最少的 k 个席位；并列时保持接受规则的顺序。已满足条件的席位不贡献发现。
- **资格判断复用同一计算**（`looper/agents/tiers/review_adjudication.py`）。`can_accept` 现在在 `required_downgrades` 返回非空集合时为真。无需降级即已满足接受的步骤集合为空，与此前一样不具资格（没有可降级的阻塞发现）。
- **修复回复按自身评判**（`looper/agents/tiers/planner.py`）。被拒回复的降级不再带入修复消息的发现列表；被拒回复从不改变已保存的评审轮。
- **不变：**运行与日志条目的存储格式、裁决接受的条件，以及 Worker、Reviewer 和 Manager 提示词。
- **面向模型的变化：**有。提供裁决式 accept 时，Planner 的决策消息新增 “downgrading these findings suffices” 一行，被拒 accept 的拒绝文本按上述方式变化。PR 称合并前会运行真实模式提示词评测。

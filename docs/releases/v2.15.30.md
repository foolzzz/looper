# Looper v2.15.30

This release documents the changes merged on main between the v2.15.29 tag and `d2bbc5b35`. That tag is on its release commit (`44255827f`), so this range also contains pulls that merged after the v2.15.29 scope freeze (`c03ad4e73`) but are not on that tag. [#1611](https://github.com/foolzzz/looper/pull/1611) and [#1636](https://github.com/foolzzz/looper/pull/1636) ship here, with full notes. The v2.15.29 release pull request ([#1643](https://github.com/foolzzz/looper/pull/1643)) is not a change in this release. Pulls merged into main after the freeze ([#1653](https://github.com/foolzzz/looper/pull/1653), [#1654](https://github.com/foolzzz/looper/pull/1654), [#1658](https://github.com/foolzzz/looper/pull/1658), [#1659](https://github.com/foolzzz/looper/pull/1659) and [#1660](https://github.com/foolzzz/looper/pull/1660)) are not on this tag and ship in the next release.

The headline capabilities use operator-controlled feature settings: followed-group intent reads ([#1638](https://github.com/foolzzz/looper/pull/1638), [#1642](https://github.com/foolzzz/looper/pull/1642), [#1651](https://github.com/foolzzz/looper/pull/1651), [#1656](https://github.com/foolzzz/looper/pull/1656)); cost-guard stage ③, background and schedule caps with daily alerts, only while `cost_guard.mode` is already `enforce` ([#1639](https://github.com/foolzzz/looper/pull/1639)); unanswered schedule pushes ([#1641](https://github.com/foolzzz/looper/pull/1641)); memory drafting on the existing memory-write switch ([#1540](https://github.com/foolzzz/looper/pull/1540)); account admission ([#1611](https://github.com/foolzzz/looper/pull/1611)) and explorer admission on that same switch ([#1650](https://github.com/foolzzz/looper/pull/1650)). Also in this release, on by default within the existing feature paths: an idle-check send that a restart interrupts ([#1636](https://github.com/foolzzz/looper/pull/1636)); the Manager mid-turn race ([#1647](https://github.com/foolzzz/looper/pull/1647)); the room inbox push race ([#1644](https://github.com/foolzzz/looper/pull/1644)); skill-proposal claim release ([#1634](https://github.com/foolzzz/looper/pull/1634)); acceptance evidence in a task result ([#1637](https://github.com/foolzzz/looper/pull/1637)); and the Haiku alias and unknown-price path ([#1646](https://github.com/foolzzz/looper/pull/1646)). Eval tooling only: [#1645](https://github.com/foolzzz/looper/pull/1645). This release is frozen at `d2bbc5b35`.

The new feature settings default off. Startup does seed an enabled `memory_draft` role (`role_configs.enabled` defaults true, timeout 120 seconds, max turns 1). An existing `memory_write` object with `enabled: true` starts processing eligible drafting candidates after upgrade without another opt-in; existing `enforce` mode gains the background and schedule caps below. An upgrade does not write `intents.group_read.enabled`, `cost_guard.unanswered_pushes.enabled`, `engine.admission.enabled` or `cost_guard.mode`. A missing row stays off, and a stored mode stays as it is. With all new feature settings off and `memory_write` absent or disabled, startup still takes the usual pre-migration `pg_dump` backup when migrations are pending, applies 9 additive migrations and 4 new online steps, backfills two nullable subscription-run columns from existing `llm_records`, and starts the loops that already shipped. It also starts the memory drafter (a listen on `looper_memory_draft`, and a read of `memory_write` every 10 seconds that returns before any vault, model or candidate work while that setting is absent or off), recovers this Manager's idle-check rows that were left `sending`, reads the admission key and does not load account state while it is not the string `true`, and queries unanswered holds whose question was never delivered. That last query returns nothing on an upgrade from v2.15.29 because no unanswered holds exist yet; `cost_holds` is an existing table and may contain budget holds. The new unconditional query can fail startup. The drafter also opens an extra persistent PostgreSQL connection even while disabled; connection or LISTEN registration failure can fail startup. Claude Code OAuth pricing now maps `haiku` to `claude-haiku-5-5`, which has no built-in price; seed rows are inserted with `ON CONFLICT DO NOTHING`, so existing model and profile rows are not rewritten. `web/` changed, so the dashboard bundle is rebuilt by the release workflow as usual.

## Release Decision

**Who should upgrade:** Anyone who will follow group chats for development requests, cap background or schedule spend, pause a schedule that pushes with no reply, or admit runs per account, and anyone whose cost_guard.mode is already enforce. An installation that turns none of the new switches on still applies 9 additive migrations and 4 new online steps, backfills subscription check links, listens for memory drafts, recovers idle-check sends, and maps the haiku pricing alias to an unpriced model for Claude Code OAuth. web/ changed, so the dashboard bundle is rebuilt by the release workflow as usual.

**What this release solves:** The operator can name group chats whose human messages are read for development requests, enforce background and schedule daily caps while cost-guard mode is enforce, ask once before a schedule keeps pushing with no reply, draft a memory candidate without writing the vault, and queue Workers and explorers per account. No new feature setting turns itself on; an already-enabled `memory_write` starts drafting, and an already-enforcing guard applies the new caps. Recognize-once group reads, account fallback and Planner or Manager admission do not ship.

**Breaking changes:** No. No existing API drops a field that a caller must send. Already-enabled memory writing starts drafting eligible candidates after upgrade, using the new default-enabled role. An installation whose cost_guard.mode is already enforce starts stopping background roles and skipping schedule firings at daily caps that were only observed before. Default off leaves every other installation's guard unchanged. An upgrade from v2.15.29 applies 9 additive migrations and 4 new online steps and does not turn a switch on. The one stored-row fill sets two new nullable subscription-run columns from existing llm_records. The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.15.30
```

**Contributors:** Maintainer @foolzzz authored the pull requests named in this body; no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.15.29 upgrades directly. Restart the service after upgrading, as for every release. `web/` changed, so the release workflow rebuilds the dashboard bundle from `web/` into the wheel, as usual. This pull request does not commit that bundle.

On an upgrade from a database that has finished v2.15.29, startup applies 9 new migrations, once, inside the schema transaction, in `(order, name)` order (`pending_order` controls the pre-backup check, not application). This count is what each module's `pending()` and online marker do on that database. It was not measured by running an upgrade. Because they are pending, `looper serve` first writes its usual pre-migration `pg_dump` backup into the runtime root's `backups` folder, as for any release that changes the schema, and does not start without a usable `pg_dump` unless it is started with `--skip-backup`. Four of them have a new online step, and each of those steps runs because its own marker is absent after `apply` deletes it. A step whose marker is already recorded is skipped. None of these migrations deletes an older online marker. In particular, `cost_holds_unanswered` does not delete `cost_holds_online`, and `memory_draft_role` does not delete `platform_subagents_online` or `leads_check_run_kind_online`. Those older online steps do not run again. A database that has not yet finished an earlier online step still runs that step. `schema.sql` and `looper/db/connection.py` are unchanged in this range. A fresh database creates the new objects from each module's `fresh_ddl`.

`intent_group_reads` validates `intents_via_check` inside the schema transaction. That is not an online step. `subscription_check_record` is the one migration that fills existing rows: it sets two new nullable columns. `intents.via` is a constant default of `subscription` and does not rewrite historical intent text. No new feature-setting row is inserted by a migration.

The 9 that run, in apply order:

- `provider_admission` ([#1611](https://github.com/foolzzz/looper/pull/1611)), order 1400. Pending when `provider_admission` or `provider_admission_events` is missing. The marker is not enough: `pending()` looks at both tables. Creates both. States in the check are `open`, `frozen`, `probing` and `degraded`. Reasons are `quota` and `provider_fault`. Actors are `code` and `operator`. The check requires `(state = 'open') = (reason IS NULL)`. No online step. No seed and no row rewrite.
- `idle_check_sending` ([#1636](https://github.com/foolzzz/looper/pull/1636)), order 1480. Pending when `idle_checks.state` does not yet allow `sending`. On a v2.15.29 database the check lacks `sending`, so it runs. It widens the check `NOT VALID` and deletes only `idle_check_sending_online`. The online step validates `idle_checks_state_check`. No row rewrite. The recovery update that uses `sending` runs at startup, after the migration.
- `schedule_equivalent_budget` ([#1639](https://github.com/foolzzz/looper/pull/1639)), order 1600. Pending when `schedules.daily_budget_equivalent_usd` is missing. The marker is not consulted. Adds that column as `DOUBLE PRECISION` with a check that it is greater than 0. It is nullable and has no default. No online step. No row rewrite. Null means the schedule has no equivalent split.
- `schedule_pause_reasons` ([#1641](https://github.com/foolzzz/looper/pull/1641)), order 1700. Pending when `pause_reason`, `paused_at` or `unanswered_snooze_until` is missing, or either check does not match. The marker is not consulted. On a v2.15.29 database both checks are new, so they are rebuilt and `schedule_pause_reasons_online` is deleted. The online step validates `schedules_pause_reason_check` and `schedules_pause_pair_check`. Reasons are `operator`, `unanswered`, `budget` and `quota`. The pair check is `(pause_reason IS NULL) = (paused_at IS NULL)`. No row rewrite.
- `cost_holds_unanswered` ([#1641](https://github.com/foolzzz/looper/pull/1641)), order 1701. Pending when the scope check, the shape check, nullability of `currency`, `limit_usd` and `spent_usd`, or the columns `pushes` and `asked_at`, do not match. The marker is not consulted. Scope values become `task`, `schedule_day`, `role_day`, `global_day` and `schedule`. `pushes` is an integer greater than 0. The shape check requires an `unanswered` hold to have `pushes` set and the money columns null, and the reverse. On a v2.15.29 database the scope and shape checks are rebuilt, so `cost_holds_unanswered_online` is deleted and the online step validates both. `cost_holds_online` is not deleted. Existing budget-hold money values stay; only nullability changes. No historical hold is rewritten into an unanswered hold.
- `intent_group_reads` ([#1642](https://github.com/foolzzz/looper/pull/1642)), order 1800. Pending when either new table is missing, `intents.via` is missing, or the single-column `via` check does not contain `followed_group`. The marker is not consulted. Creates `intent_group_reads` (primary key `source_id, chat_id`, foreign key to `source_chats` `ON DELETE CASCADE`, `read_from >= added_at`) and `intent_group_read_days` (`read` and `skipped` at least 0). Adds `intents.via TEXT NOT NULL DEFAULT 'subscription'` and widens `intents_via_check` to include `followed_group`, then validates that check inside the schema transaction. No online step. The constant default does not rewrite historical intent text.
- `subscription_check_record` ([#1646](https://github.com/foolzzz/looper/pull/1646)), order 1820. Pending only if the `subscription_check_record` marker is absent and at least one of `subscription_runs.check_record_id` and `retry_record_id` is missing; a recorded marker suppresses repair even if a column is missing. Adds both as nullable foreign keys to `llm_records` `ON DELETE SET NULL`. No online step. `apply` then fills them once: `check_record_id` is the maximum `llm_records.id` grouped by `metadata->'leads_check'->>'run_id'`; `retry_record_id` is the minimum id grouped by `metadata->'subscription'->>'run_id'` where that group has more than one row and the run's `record_id` differs. This writes those two new columns on existing `subscription_runs` rows. It does not change `record_id`.
- `memory_draft_role` ([#1540](https://github.com/foolzzz/looper/pull/1540)), order 1830. Pending when `llm_records_run_kind_check` or `agent_setting_layers_role_check` does not contain `memory_draft`. Widens both `NOT VALID` and deletes only `memory_draft_role_online`. The online step validates both checks. No historical run is rewritten.
- `memory_draft_queue` ([#1540](https://github.com/foolzzz/looper/pull/1540)), order 1840. Pending when `memory_draft_waits` or `memory_draft_lease` is missing. Creates both empty. A wait's reason is only `target_busy`. Both foreign keys point at `memory_candidates` `ON DELETE CASCADE`, and `candidate_id` must differ from `blocking_candidate_id`. The lease table has a single boolean primary key and no foreign key to a candidate. No online step.

What is visible while all new feature settings stay off and `memory_write` is absent or disabled: those 9 migrations and 4 online steps still run; `intents.via` on a new intent is `subscription`; the subscription-run backfill still fills the two new columns; the memory drafter listens and returns every 10 seconds without drafting; idle-check recovery still updates `sending` rows, and with none the update matches nothing; admission startup reads `engine.admission.enabled` and, while it is not the string `true`, does not call `load_states`; `cost_holds.initialize` still asks whether any hold is pending or unapplied; after adapters exist, startup still queries unanswered holds with `asked_at` null; each scheduler pass calls the unanswered check, which returns before a query while the switch is off; Claude Code OAuth pricing maps a stored model name `haiku` to unpriced `claude-haiku-5-5`; other accounts do not use this alias mapping. An explorer spawn still requires an active task, as the explorer section says, whether or not admission is on.

## Behavior changes

### Followed-group reads, off ([#1638](https://github.com/foolzzz/looper/pull/1638), [#1642](https://github.com/foolzzz/looper/pull/1642), [#1651](https://github.com/foolzzz/looper/pull/1651), [#1656](https://github.com/foolzzz/looper/pull/1656))

[#1638](https://github.com/foolzzz/looper/pull/1638) is the design. [#1642](https://github.com/foolzzz/looper/pull/1642) is the continuous reader. [#1651](https://github.com/foolzzz/looper/pull/1651) records the decisions and does not change runtime behavior. [#1656](https://github.com/foolzzz/looper/pull/1656) is the wide scope below. Recognize-once, the one-shot read of a time range, is described in the RFC and is not implemented. No real-model eval of the group note was run.

- **`intents.group_read.enabled` defaults off.** Only the stored string `true` is on. An absent row means off. `group_read_settings_put` does not accept null. It requires a boolean. It inserts the key as `false` when the row is absent, then stores `true` or `false`. Turning it on while `delivery.enabled` is not on raises `GroupReadNeedsDelivery`. The text is `turn on the delivery layer (delivery.enabled) first: followed-group intents are capped and digested by it`. Turning it from off to on (`old != "true"`) sets `read_from` to `GREATEST(added_at, now())` on every list row. Turning it off does not delete list rows and does not delete intents. It is not a configuration-export key. Only the operator can call `intent_group_reads.list`, `preview`, `put`, `delete` and `settings_put` (`POST /api/v1/intent_group_reads/{action}`). `put`, `delete` and `settings_put` are risk `write`. They are not `confirms`. The operator's own call applies on that request and returns 200. A non-operator gets 403 `operator identity is required`.
- **While it is off,** an intents extraction returns before any group-allowance query when the output kind is not intents or the switch is not the string `true`. A store recheck treats every candidate group sequence as not stored. The migration still creates the empty tables and the `via` column. The switch row is not written by the migration. No group note is appended.
- **While it is on,** only a group or topic chat that is `inclusion=included` and `extraction=included` can be listed. A direct chat, or a chat whose kind is not yet recognized, is refused with `only a group or topic chat: a direct chat is read in full already, and a chat of unknown kind must be recognized first`. An excluded chat is refused with `the chat is excluded from the message stream or from extraction; include it first`. A source that already has 10 groups refuses another with `at most 10 followed groups per source`. Caps are 200 messages in one run (`GROUP_READ_RUN_MAX`) and 500 messages a group on one local day (`GROUP_READ_DAY_MAX`). `group_read_delete` deletes only the `intent_group_reads` row. The `DELETE` returns that row's `read_from` into the log. The operation body is the updated list. Intents already stored stay.
- **Who is read, and which types count** ([#1656](https://github.com/foolzzz/looper/pull/1656)). Every eligible human message in a listed group uses the group rule and its allowance, including the operator's own messages and messages that mention the operator. The sender is not a separate gate. The model-visible note is appended only when the window contains those group sequences. It starts `## Requests in group chats` and says that a chat marked 全部消息 gives every human sender's messages, including the user's own; that a development request counts even without mentioning the user, whether it is addressed to the group, a team, a named person, or nobody; and that a named-person request counts even if that person has accepted it. It names `dev_task` for a requirement or a change and `bug_triage` for a bug or a problem, and it excludes small talk, answers, +1s, and pure follow-ups, status updates or decisions with no new ask. The code then drops a type outside `dev_task` and `bug_triage` only when the message was read solely because of the list (`via_group` and not already inside the original extraction scope). A message that was already in the original extraction scope keeps every enabled intent type, and it still qualifies for the group note when the window has group sequences. One read, one parse and one store. Operator direct messages, and messages outside listed groups, keep the original scope. `intents.via` for a followed-group intent is `followed_group`. The default for every other intent remains `subscription`.

### Cost-guard stage ③, only while mode is enforce ([#1639](https://github.com/foolzzz/looper/pull/1639))

v2.15.29 shipped `enforce` for task and global daily caps and did not enforce background-role or schedule caps. This release enforces those caps when the mode is already `enforce`. It does not turn the mode on.

- **`cost_guard.mode` still defaults to `off`.** An absent row uses `off`. An invalid stored value forces `Config()` off and sets `Stored cost guard settings are invalid; the guard is off.` An upgrade does not write the mode. Absent caps `daily_usd` and `daily_equivalent_usd`, and the same caps under `roles.processor`, `roles.leads_check`, `roles.advice_check`, `roles.outbound_check` and `roles.advisor`, default to null (no cap); saved caps are retained. A schedule's `daily_budget_equivalent_usd` null means no split. In `enforce`, setting that column splits real spend from equivalent spend. In `off` or `observe`, or in `enforce` while the column is null, the schedule check stays the legacy mixed sum of both currencies. Null stays absent from views. Only the operator can call `cost_guard.get`, `cost_guard.update`, `cost_holds.list` and `cost_holds.decide`. `cost_guard.update` and `cost_holds.decide` stay high risk with `confirms` true. The operator's own update applies on that request and returns 200, unless the body sets `mode` to `enforce`, which returns `needs_confirmation` (HTTP 202). `cost_holds.decide` with `new_limit_usd` is held the same way. A non-operator gets 403 `operator identity is required`. Export still carries only explicitly stored `settings.cost_guard` keys.
- **While the mode is `off`,** `admit` returns an empty admission before admission I/O. Observe records and does not enforce. The 80 percent near-limit alert is appended only while the mode is `enforce`, so observe does not send it. Startup still loads the cached config and asks whether a `cost_holds` row is pending or unapplied.
- **While the mode is `enforce`,** background role daily caps, schedule daily caps and the global daily cap apply to background work. A background kind at its cap is `STOP_ROLE`. A schedule firing at its cap is `SKIP`. Anything else at a cap is `ASK`. Enforcing scopes are the task and the global day for interactive work, and the schedule day, the role day and the global day for background work and for schedule firings. Enforce re-reads persisted spend and reservations before it decides. A near-limit alert is considered when used plus estimate is at least 80 percent of the limit. Alert text for a guard error is `花费守卫：今天的花费计数或准入检查出错；定时触发检查失败时跳过本次触发，对外动作仍须通过审查。` A near-limit text is `花费提醒：{scope} 今天的{currency}已花及预留 ${spent}，到了上限 ${limit} 的 80%。` A limit text names the consequence: `定时任务『{name}』这次触发已跳过` for a schedule, `后台角色 {kind} 今天不再运行` for a background role, and `本次运行已等待操作者决定` otherwise. Currency labels are `等价花费` and `真钱`. Alerts flush only while enforcing. Repeat counters are process-local. The daily claim is `system_settings.claim`. A restart loses the in-process counters and keeps the claim. Persisting a quiet-hours alert body, and a cross-process next-day summary, do not ship.
- **A schedule firing that admission denies.** A typed denial that is `SKIP` and is not a guard error is recorded as `skipped_budget`, with the spent, reserved and daily-budget text, and appends a budget-skipped alert. The legacy daily cap still runs after that unless the mode is `enforce`, `daily_budget_equivalent_usd` is not null, and admission reported no problem. A guard-error denial is checked after that legacy cap. Its status is `skipped_budget`, its text is the reason plus the problem, no run starts, and a subscription cursor is not advanced. A global denial creates the matching global hold. The same day's re-read keeps a usage-window hold's observation for a run that has no model record yet. Account `FALLBACK` does not ship. The day boundary is not changed to the operator's timezone.
- **The declared impact text** for an update now includes: `A server already in enforce now stops background roles at their own, schedule or global daily caps and skips schedule firings at caps previously only observed. Default off preserves existing behavior.`

### Unanswered pushes, off in every mode ([#1641](https://github.com/foolzzz/looper/pull/1641))

This switch does not follow `cost_guard.mode`. It can be on while the mode is `off`, `observe` or `enforce`, and enforce does not turn it on.

- **`cost_guard.unanswered_pushes.enabled` defaults false.** Only the stored string `true` is on. When the rule is synthesized, `window_days` is 3 (1 to 30), `min_pushes` is 15 (1 to 1000), `pause_after_days` is 3 (1 to 30) and `snooze_days` is 30 (1 to 365). `checked()` rejects a non-boolean `enabled` with `unanswered_pushes.enabled must be true or false`, and rejects a non-integer number. Null is not a way to delete these keys. Turning `enabled` to true while `manager.metrics.enabled` is not on raises `先打开 manager.metrics.enabled：没有推送和回复记录就无法判断没人回`. `view()` includes `unanswered_pushes` only while the rule is enabled. Export (`portable()`) carries the unanswered fields only when those keys are stored. It does not carry holds. The same `cost_guard.update` call as stage ③ applies on the operator's request and returns 200. An unanswered-only patch does not set `mode` to `enforce`, so it does not return 202. An API client gets 403 because the operation is operator-only. The impact text adds: `Turning on unanswered pushes asks once after that many direct pushes in the window go without a reply, pauses the schedule after more days with no answer and no reply, and resumes it from Needs you.`
- **While it is off,** `unanswered_pushes.check` returns before any query, and the hourly clock is not updated. The two migrations still apply. Startup, after adapters exist, still calls `deliver_unsent_questions`, which queries pending unanswered holds with `asked_at` null. That query does not read the switch, and a query failure aborts startup. On an upgrade the existing `cost_holds` table has no unanswered row, so nothing is delivered. `cost_holds.initialize` still scans holds that are pending or unapplied, in every mode, and does not itself deliver questions.
- **While it is on,** the check runs at most once an hour. If metrics are then off, one warning is logged per local day and nothing is asked or paused: `没人回的推送规则已打开，但 manager.metrics.enabled 是关的：没有推送和回复记录，本次不提问也不暂停`. The window ends 30 minutes ago. One pending hold and one question are kept per schedule. `asked_at` is when the question was delivered. The pause clock starts there. An unsent hold is not paused. The question is `{label}：『{name}』{window_days} 天推了 {pushes} 条，你都没回。还要继续推吗？回复「继续 {label}」（{snooze_days} 天内不再问）或「停 {label}」（暂停这个定时任务）。{pause_after_days} 天内不回答、也没回过它的推送，会自动暂停。控制台：{link}`. The pause notice is `『{name}』已自动暂停：{pause_days} 天没有回答，也没回过它的推送。在控制台的「需要你处理」里点「恢复」，或让管家恢复它。` The pause sets `enabled` false, `pause_reason` `unanswered`, `paused_at` now and `next_fire_at` null. A bare `继续` plus the label, with no amount, routes only for a pending unanswered hold. A budget hold does not take that path. `继续` with an amount on an unanswered hold raises `这条提问不需要上限`. Continue snoozes for `snooze_days`. Stop on an unanswered hold sets `enabled` false, `pause_reason` `operator` (not `unanswered`), `paused_at` now and `next_fire_at` null. Enabling a schedule whose `pause_reason` is `unanswered` sets `unanswered_snooze_until` to now plus `snooze_days`, then clears `pause_reason` and `paused_at`. Needs you lists schedules whose `pause_reason` is `unanswered`. The cost-hold service stays up while the mode is `enforce`, or this switch is on, or a hold still needs recovery.

### Memory drafting, while memory write stays off ([#1540](https://github.com/foolzzz/looper/pull/1540))

No new operator switch. Drafting uses the existing `memory_write` object. Startup inserts the `memory_draft` role enabled by default (timeout 120 seconds, max turns 1); already-enabled memory writing therefore gains drafting immediately, including eligible candidates left in `drafting` by v2.15.29. Absent means off. Inside a saved object, `enabled` must be boolean true. `draft_budget_usd` still defaults to 0.15 and `daily_budget_usd` still defaults to 1.00. No real-model drafting eval was run for this release pull request.

- **While memory write is off,** `MemoryDraftService` still starts for the process lifetime. It opens a dedicated connection and listens on `looper_memory_draft`. Every 10 seconds `run_once` reads the stored setting and, when the setting is missing, `enabled` is not true, or the service is draining, returns before a vault read, a model call, a candidate transition or a channel send. With memory writing off, an upgrade does not create a candidate or call a model. The two migrations still apply. The listener and the 10-second read are new work even while disabled. Drafting does not write the vault. Confirmation still binds the content hash. The role is `memory_draft`. The built-in profile is `claude-code/sonnet-5-5`, a tool-less private call. `intent_group_reads` 在 schema 事务里校验 `intents_via_check`，这不是在线步骤。`subscription_check_record` 是唯一会填写已有行的迁移。`intents.via` 的常量默认值是 `subscription`，不改写旧意图的正文。迁移不插入新的功能开关行。启动还会播种默认 enabled=true 的 `memory_draft` 角色（超时 120 秒、max_turns 1）。原先 `memory_write.enabled=true` 的安装会直接处理已有 drafting 候选，无需另开开关。即使关闭，起草服务仍占用一个额外常驻 PostgreSQL 连接，连接（10 秒超时）或 LISTEN 注册失败会阻止启动；后续轮询失败则记录 `memory drafting pass deferred` 并重试。

按应用顺序，这 9 条是：`provider_admission`（1400，两张表都在才不算 pending，无在线步骤）、`idle_check_sending`（1480，在线 `idle_check_sending_online` 校验 `idle_checks_state_check`）、`schedule_equivalent_budget`（1600，可空列 `daily_budget_equivalent_usd`，无在线步骤）、`schedule_pause_reasons`（1700，在线 `schedule_pause_reasons_online` 校验暂停原因和成对检查）、`cost_holds_unanswered`（1701，在线 `cost_holds_unanswered_online` 校验范围和形状，不删 `cost_holds_online`）、`intent_group_reads`（1800，事务内校验 `via`，无在线步骤）、`subscription_check_record`（1820，只有迁移标记缺失且列缺失才 pending，回填两个可空列，无在线步骤）、`memory_draft_role`（1830，在线 `memory_draft_role_online` 校验 `run_kind` 和 `role`）、`memory_draft_queue`（1840，两张空表，无在线步骤）。

新的功能设置均关闭且 `memory_write` 缺失或关闭时仍然发生的事：上面的迁移和在线步骤会跑；新意图的 `via` 是 `subscription`；订阅运行的两个新列会被回填；记忆起草仍会监听，并每 10 秒读到关闭后返回；空闲检查仍会把 `sending` 改成 `uncertain`，没有这种行时更新匹配零行；账号准入只读 `engine.admission.enabled`，不是字符串 `true` 就不加载状态；花费暂停的启动扫描照旧；启动后仍会查询 `asked_at` 为空的未回答暂停，升级后没有这种行（旧 `cost_holds` 表可已有预算暂停），该查询失败会阻止启动；调度器每次都会调用未回答检查，关闭时在查询前返回；Claude Code OAuth 计价把模型名为 `haiku` 的 Profile 映射到未标价的 `claude-haiku-5-5`；其他账号不应用此别名映射。explorer 的启动无论准入开没开，都要求任务处于活跃状态。

**价格和别名（[#1646](https://github.com/foolzzz/looper/pull/1646)）。** 没有新开关。Claude Code OAuth 计价默认把 `haiku` 映射到 `claude-haiku-5-5`；其他账号不应用此别名映射。不为 5.5 写入单价，也不复用 4.5 的 1.00、5.00、0.10、1.25、2.00。内置 `leads_check` 的模型名就是 `claude-haiku-5-5`，同样未标价。种子插入都是 `ON CONFLICT DO NOTHING`，升级不改写已有的模型或 Profile 行。使用 Claude Code OAuth 且模型名存为 `haiku` 的 Profile，即使新功能设置全关，计价仍会映射到这个未标价名字。运行时报告的总额仍是结算依据。运行时已计费的运行里，辅助的未标价模型按主模型单价估算，不单独把主账单打成未知。日志以 `model %s: price unknown; spend budget cannot be verified` 开头，配置了上限时追加 `; stopping at the configured cap`。配置了单次运行上限且价格未知时软停。回复是「这一轮因模型价格未知（模型名用顿号连接），无法核实单轮上限，已经停下。」没有模型名时原因是「用量不完整」，不带括号或「模型价格未知」前缀。定时任务的警告含有 `spend is only the known subtotal`。聚合露出 `cost_status`：`known` 或 `unknown`。没有发出模型请求的运行不会写成 `unknown`。咨询已有运行记录而花费未知时不重试，原因是 `its cost is unknown, so its cap of {cap} USD cannot be checked`。超时和拒绝保持原样。守卫关闭时仍不做准入 I/O，也不做预留。显式的免费单价仍然优先。没有做真实模型评测。

**只改评测（[#1645](https://github.com/foolzzz/looper/pull/1645)）。** 助手评测的检查器离线解析中文日期。`下午 1:51` 只当成 13:51。时段和 24 小时制矛盾时拒绝。中午只接受 11 点到 13 点。没有月份的裸日期不满足「下周三」。`晚上12点` 不支持。只重算已有输出，不发起新的模型调用，也不改基线文件。不是产品运行时的变化。[#1643](https://github.com/foolzzz/looper/pull/1643) 是上一版的发布拉取请求。

### 可选能力启用与使用

#### Group reads

**启用：** 操作者把 `intents.group_read.enabled` 存成字符串 `true` 之前是关。没有这一行就是关。操作者用 `POST /api/v1/intent_group_reads/settings_put`，正文 `{"enabled": true}`。值必须是布尔值，null 会被拒绝。`delivery.enabled` 必须已经打开，否则原文是 `turn on the delivery layer (delivery.enabled) first: followed-group intents are capped and digested by it`。这次调用只给操作者，风险是 write，不等第二次确认。操作者自己的这一次请求直接生效并返回 200。非操作者得到 403，正文是 `operator identity is required`。升级不写这个键。

**验证：** 存的值不是字符串 `true` 时，意图抽取不读群额度；关掉开关不会删除名单或意图。打开后，`POST /api/v1/intent_group_reads/put` 加入一个已包含的群或话题，每个来源最多 10 个。一次运行跨全部名单群合计最多读 200 条人类消息，一个群本地一天最多 500 条。点名给某个人的请求也算。只因名单才读到的消息，只有 `dev_task` 和 `bug_triage` 会入库。

**停用 / 回退：** `{"enabled": false}` 存 `false`，不删名单，也不删意图。`POST /api/v1/intent_group_reads/delete` 删掉一行名单，已入库的意图留着。下一次抽取不再对这个群扩展读取范围，原有抽取范围仍适用。本版本没有识别一次的开关。

**权限边界：** 只给操作者。list、preview、put、delete 和 settings_put 都只给操作者。这个键不导出。群意图经送达层推到操作者的私聊。API 客户端令牌得到 403。

#### Unanswered pushes

**启用：** 操作者把 `cost_guard.unanswered_pushes.enabled` 存成字符串 `true` 之前是关。合成默认值是 window_days 3、min_pushes 15、pause_after_days 3、snooze_days 30。操作者用 `POST /api/v1/cost_guard/update` 设置。null 会被拒绝。`manager.metrics.enabled` 必须已经打开，否则原文是 `先打开 manager.metrics.enabled：没有推送和回复记录就无法判断没人回`。更新声明为高风险且 confirms 为 true。操作者自己的请求当场返回 200，除非同一个正文把 mode 设为 enforce，那才返回 needs_confirmation（HTTP 202）。只改未回答推送的正文不会这样。非操作者得到 403，正文是 `operator identity is required`。这个开关不跟着 cost_guard.mode。升级不写它。

**验证：** 存的值不是字符串 `true` 时，每小时的检查在查询前返回，也不会因没人回而暂停定时任务。打开后，窗口内直接推送达到 min_pushes 且都没有回复时，每个定时任务问一次。窗口不含最近 30 分钟。pause_after_days 内不回答、也没回过推送，就以 pause_reason unanswered 暂停。不带金额的继续按 snooze_days 暂缓再问。带金额的继续回答 `这条提问不需要上限`。

**停用 / 回退：** 把 unanswered_pushes.enabled 设为 false 会存 `false`。下一次检查在查询前返回。已经暂停的定时任务保持暂停，直到操作者重新启用。启用一个 pause_reason 为 unanswered 的定时任务会设置 unanswered_snooze_until 并清掉暂停。对待处理的未回答提问回复停，暂停原因是 operator，不是 unanswered。

**权限边界：** 只给操作者。提问发给操作者。只有这些键已经存下时，导出才带上它们。API 客户端令牌得到 403。模式可以保持 off，而这个开关单独打开；enforce 不会把这个开关打开。

**文档：** https://github.com/foolzzz/looper/blob/v2.15.30/docs/architecture/rfcs/cost-guard-v0.zh-CN.md#8-没人回的推送产品设计-p47

#### Account admission

**启用：** 操作者把 `engine.admission.enabled` 存成字符串 `true` 之前是关。没有这一行就是关。操作者用 `POST /api/v1/admission_settings/update`，正文 `{"enabled": true}`。null 删行。false 存 `false`。失败分类必须已经打开，否则原文是 `Enable failure typing before account admission can freeze quota failures.` 更新声明为高风险且 confirms 为 true。操作者自己的这一次请求直接生效并返回 200。这不是花费确认，不会返回 202。非操作者得到 403，正文是 `operator identity is required`。升级不写这个键。

**验证：** 没有这一行时，`POST /api/v1/admission_settings/get` 的 enabled 是 false，启动也不加载账号状态。存下字符串 `true` 之后，Worker、Reviewer、咨询、处理器和嵌套运行会等待该账号的名额。max_concurrency 为 null 仍是不限制。配额冻结的原因是 quota。Planner 和管家回合不进准入。explorer 排在发起者的车道里，阻塞等待可以出借一个名额。

**停用 / 回退：** `{"enabled": null}` 删行。`{"enabled": false}` 存 `false`。等待中的运行被放行。操作者用 `POST /api/v1/providers/limits_clear` 并带上 provider_id 可以清掉一个冻结，当场返回 200。找不到的 provider 原文是 `provider not found`。`provider_admission` 里已有的行留到被清除或替换。explorer 启动时的活跃任务检查仍然有效。

**权限边界：** 只给操作者。admission_settings.get、admission_settings.update 和 providers.limits_clear 都只给操作者，级别是 inside。这个键不导出。关掉之后放行运行，不切换账号。API 客户端令牌得到 403。

#### Background caps

**启用：** 沿用 `cost_guard.mode`，默认 `off`。操作者通过 `POST /api/v1/cost_guard/update` 设置 enforce、确认花费授权，再配置所需的角色或每日上限。缺失上限表示无限制，已有值保留。原先已是 enforce 的安装升级后直接执行后台和定时任务上限。新列 `daily_budget_equivalent_usd` 默认 null；只有 enforce 且设置了该列才拆开两种货币。

**验证：** 后台角色达到角色、定时任务或全局日上限时返回 `STOP_ROLE`；定时触发达到上限记为 `skipped_budget`。80% 提醒只在 enforce 入队。off 的准入在 I/O 前返回，observe 记录但不执行这些新上限；off 和 observe 仍执行既有的定时任务日上限。

**停用 / 回退：** 用同一接口设为 observe 或 off，同时会停用任务和全局守卫强制执行；既有定时任务日上限、独立的未回答推送规则仍适用。如需保留其他强制执行，只移除对应上限。

**权限边界：** 仅操作者可修改；打开 enforce 要经过花费授权。本能力不做账号回退，也不新增 Planner 或管家的账号准入。

#### Memory drafting

**启用：** 沿用 `memory_write` 对象，缺失就是关。操作者通过 `POST /api/v1/memory/settings_put` 保留完整配置并设置布尔 `enabled=true`，启用写入沿用既有确认。启动播种默认启用的 `memory_draft` 角色，超时 120 秒、max_turns 1，Profile 为 `claude-code/sonnet-5-5`。原先已启用记忆写入的安装升级后会直接处理符合条件的 drafting 候选。本版本没有新增创建候选入口。操作者重起草、写入冲突或复活冲突可排入起草。

**验证：** 接受的变更生成供审核的候选修订；重复、跳过或合并结果也可能结束候选。起草不写知识库。每次上限为 `min(draft_budget_usd, daily_budget_usd - 当天 memory_draft 已花金额)`，默认预算为 0.15 和 1.00；默认下花费为空的运行每次按 0.15 计入已花。关闭时仍占用额外常驻 PostgreSQL 连接、监听 `looper_memory_draft` 并每 10 秒读设置；连接或 LISTEN 失败会阻止启动，后续轮询失败则警告并重试。

**停用 / 回退：** 用 `memory.settings_put` 保存完整既有对象并设 `enabled=false`，会同时暂停起草、写入和候选推送，保留候选，监听连接仍在。只关角色会记起草失败，从上次显式重起草起累计三次失败会以 `draft_failed` 丢弃候选。

**权限边界：** 记忆操作仅供操作者。起草不确认候选、不写知识库，写入仍需绑定当前内容哈希的确认。本地记忆配置不导出。

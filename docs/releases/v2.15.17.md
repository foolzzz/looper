# Looper v2.15.17

This release documents the changes merged since v2.15.16: the message stream bridge ([#1425](https://github.com/foolzzz/looper/pull/1425)), the `processor` role with tool-less Claude Code runs ([#1424](https://github.com/foolzzz/looper/pull/1424)), a test-only fix for leaked processes and a macOS hang ([#1427](https://github.com/foolzzz/looper/pull/1427)), and two documentation-only changes, the completion, ledger and briefing RFC ([#1426](https://github.com/foolzzz/looper/pull/1426), [#1428](https://github.com/foolzzz/looper/pull/1428)). The message stream RFC ([#1415](https://github.com/foolzzz/looper/pull/1415)) was already in v2.15.16. Both new capabilities are off by default: nothing reads messages and nothing runs a processor until you turn them on.

## Release Decision

**Who should upgrade:** Anyone who wants Looper to keep the messages of an existing local Lark message collector in its own database, and anyone who wants to try the building blocks of message subscriptions. Everyone else can stay on v2.15.16; nothing changes for them except two additive database migrations.

**What this release solves:** Looper can store the messages an outside collector already wrote to disk, show the state on a Message stream page and import history on demand (`ingest_mode = bridge`). It also gains a `processor` role: a run of Claude Code with no tools, whose runtime and model come entirely from an Agent Profile. Nothing calls the processor yet; the subscription schedule kind that will is a later release.

**Breaking changes:** No. No existing API field is removed or changed. There are two additive PostgreSQL migrations (see Upgrading). Settings → Roles lists a fifth role, Processor. The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.15.17
```

**Contributors:** Maintainer @foolzzz authored [#1424](https://github.com/foolzzz/looper/pull/1424), [#1425](https://github.com/foolzzz/looper/pull/1425), [#1426](https://github.com/foolzzz/looper/pull/1426), [#1427](https://github.com/foolzzz/looper/pull/1427) and [#1428](https://github.com/foolzzz/looper/pull/1428); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.15.16 upgrades directly. Restart the service after upgrading, as for every release.

This release has two additive PostgreSQL migrations, each applied once at startup:

- `processor_role` (DDL only, no row changed): the role checks of `agent_setting_layers` and `schedule_profile_overrides` admit `processor`, and the runtime capability check admits `no_tools`. A `processor` row is added to `role_configs` (recommended role prompt, 600 s timeout). At startup `looper serve` also refreshes the built-in Claude Code runtime's capabilities so it declares `no_tools`.
- `message_stream`: creates `event_sources`, `source_chats`, `source_threads`, `source_people`, `source_runs` and `source_events`. They are empty until a source is configured.

## Behavior changes

### Message stream (off by default)

- A new Message stream page (`#messages` in the dashboard) shows the status of a source, a switch, the setup form (directory, start point) and the recent passes with their errors. With no source, or a source set to `off`, nothing reads, and no prompt, tool list or agent command line changes. ([#1425](https://github.com/foolzzz/looper/pull/1425))
- With `ingest_mode = bridge`, `looper serve` reads the per-chat message files of an existing collector on the source's schedule, stores each message once, and keeps messages sent by the Lark apps that Looper's own enabled channels act as out of the store. Only complete lines are read; a rewritten file is detected and read again without duplicates; a pass that is killed resumes.
- **Enabling the bridge imports history.** The start point is `end` by default: the first pass saves each file's current end and stores only what comes later. Choosing `beginning` reads every file from its start and stores all of it, which on a large collector takes minutes and a lot of disk (on a synthetic 1.88 GB, 800,000-message corpus, 117 s and about 920 MB of tables). Bodies older than the retention setting (30 days for app messages) are stored as text only.
- New command: `looper msgflow import --days N [--dry-run] [--per-file] [--source ID]` imports history on demand and reconciles per file; it refuses while another pass holds the source's lock. `--dry-run` writes nothing.
- Three operator-only operations: `message_stream.status`, `message_stream.runs` (counts and states, never message text) and `message_stream.configure`. A new background loop runs one query per 15 s tick when no source is bridged.

### Processor role (off by default)

- A new role `processor` and a typed runtime capability `no_tools`. Only Claude Code declares `no_tools`. A processor run launches Claude Code with no built-in tools, slash commands, MCP servers, plugins, session files or settings files, so no project's hooks run in it. Every other role's command line is unchanged. ([#1424](https://github.com/foolzzz/looper/pull/1424))
- The processor's Agent Profile resolves through the shared defaults, its role, its project, its role in the project, then its schedule's choice. There is no default model in code; with nothing chosen it is the built-in profile. A profile whose runtime lacks `no_tools` is refused with the reason.
- The administrator's managed hooks for Claude Code still run in every run. They are read as a typed fact and recorded on each run; the system setting `processor.refuse_with_managed_hooks` (default off) refuses a processor run while they are present.
- Dashboard: Settings → Roles and a project's Agent Profiles tab have a Processor row; runtime cards, the Runs page and a profile's "used by" name it. Config export and import carry its role config and layers. Nothing starts a processor run in this release.
- The Manager's tool definitions, `looper_settings` view and `looper_agent_profiles` listing do not mention the processor, so there is no model-visible change.

### Tests and documentation

- Tests no longer leave a launchd job or orphaned keeper processes behind on a failed or aborted run, and the full suite no longer hangs on a stopped keeper on macOS with Python 3.14. The launchd upgrade test now runs only with `LOOPER_TEST_LAUNCHD=1`. No production code changed ([#1427](https://github.com/foolzzz/looper/pull/1427)).
- The Manager completion, ledger and briefing RFC, with its nine decided open questions, is added as a design document; it changes no code or behavior ([#1426](https://github.com/foolzzz/looper/pull/1426), [#1428](https://github.com/foolzzz/looper/pull/1428)).

## Optional Capability Activation & Use

### Message stream bridge

**Activation:** Off by default. Open Message stream in the dashboard, enter the directory of an existing collector's per-chat message files, choose where to start (`end`, the default, or `beginning`) and turn the switch on; this sets the source's `ingest_mode` to `bridge`. Import older messages with `looper msgflow import --days 30 --dry-run --per-file`, then without `--dry-run`.

**Validation:** The status card reports health in words and the recent passes list their counts and errors. `looper msgflow import --days 30 --dry-run --per-file` reports per file the messages read, distinct, new, already stored and skipped; a second import stores 0.

**Disable / rollback:** Turn the switch off; reading stops at once and stored messages stay. Set the source's `ingest_mode` back to `off` to remove it from the loop. The tables are additive and unused when no source exists, so downgrading is safe as far as the schema goes.

**Authority boundary:** Read-only on the collector's files; Looper never writes there, and it does not call Lark for this source. The messages are stored as the collector wrote them, in Looper's own PostgreSQL. The operations that configure it are operator-only, and the status and runs views carry counts, never message text. No agent tool, prompt or command line mentions the stream.

**Docs:** https://github.com/foolzzz/looper/blob/v2.15.17/docs/architecture/agent-system.md#message-stream

```bash
looper msgflow import --days 30 --dry-run --per-file
```

### Processor role

**Activation:** Nothing starts a processor run in this release, so there is nothing to turn on yet. To prepare, open Settings → Roles → Processor and choose an Agent Profile whose runtime declares `no_tools` (Claude Code), or leave it on the built-in profile.

**Validation:** The Processor row names the profile in effect and says if it cannot run the role. Runtime cards show which runtimes can run the processor. `GET` of a project's agent settings includes a `processor` role.

**Disable / rollback:** Leave the role unset. The role only matters once a caller exists; the migration is DDL only and the extra role and capability values are inert for a downgraded version only if no processor layer was saved, so clear any processor layer before downgrading.

**Authority boundary:** A processor run has no tools, no MCP servers, no plugins and no project hooks, and the message text it is given is not written to any run record. The administrator's managed hooks are the exception: they still run, are recorded on each run, and `processor.refuse_with_managed_hooks` can refuse a run while they are present.

**Docs:** https://github.com/foolzzz/looper/blob/v2.15.17/docs/architecture/agent-system.md#the-processor-runs-with-no-tools

```bash
looper --version   # looper 2.15.17
```

## Validation

**Reported by the pull requests:** the processor's launch flags were checked on a real Claude Code 2.1.328 run (the init event lists no tools, commands, skills or MCP servers) and its hooks behavior with a real binary; a real-mode processor eval passed 6 of 6 runs. The bridge was run in a disposable `looper serve` on synthetic data: start from the end, start from the beginning, an unreadable file reported as a partial pass, a rewritten file read once, and a SIGKILL during an import resumed with no duplicates. The dashboard pages were checked in a headless browser at 1280, 768 and 390 px. CI passed on the processor pull request.

**Not verified by the pull requests:** a completed local full suite for the processor and bridge pull requests (it hit a time cap under load), the opt-in launchd test, a process kill inside a running `looper serve`, and a bridge against a real collector's data.

**CI:** CI runs after the release is drafted; its result is not recorded here.

**Not tested for this draft:** an upgrade of an existing database, and the built wheel. The release documentation gate checks the body only.

## 中文摘要

本版本说明自 v2.15.16 以来合并的改动：消息流桥接（[#1425](https://github.com/foolzzz/looper/pull/1425)）、`processor` 角色与不带工具的 Claude Code 运行（[#1424](https://github.com/foolzzz/looper/pull/1424)）、仅测试的泄漏进程与 macOS 卡死修复（[#1427](https://github.com/foolzzz/looper/pull/1427)），以及两项仅文档的改动：Manager 收尾、账本与晨报 RFC（[#1426](https://github.com/foolzzz/looper/pull/1426)、[#1428](https://github.com/foolzzz/looper/pull/1428)）。消息流 RFC（[#1415](https://github.com/foolzzz/looper/pull/1415)）已在 v2.15.16 发布。两项新能力默认关闭：不启用就不读取任何消息，也不运行 processor。

### 升级决策

**谁需要升级：**想让 Looper 把已有的本地飞书消息采集器的消息存进自己数据库的用户，以及想试用消息订阅构件的用户。其他用户可以留在 v2.15.16；除两个可加的数据库迁移外没有变化。

**解决了什么：**Looper 可以存下外部采集器已写到磁盘的消息，在 Message stream 页显示状态，并按需导入历史（`ingest_mode = bridge`）。同时新增 `processor` 角色：不带工具的 Claude Code 运行，运行时和模型完全来自 Agent Profile。目前没有任何调用方，后续版本的订阅定时任务才会用到它。

**是否有破坏性变更：**无。没有删除或修改现有 API 字段，有两个可加的 PostgreSQL 迁移（见升级）。Settings → Roles 多出第五个角色 Processor。桥接边界不变：早于 v2.13.165 的安装须先升级到 v2.13.165。

**如何验证：**核对版本为 2.15.17。

**贡献者：**维护者 @foolzzz 提交 [#1424](https://github.com/foolzzz/looper/pull/1424)、[#1425](https://github.com/foolzzz/looper/pull/1425)、[#1426](https://github.com/foolzzz/looper/pull/1426)、[#1427](https://github.com/foolzzz/looper/pull/1427) 和 [#1428](https://github.com/foolzzz/looper/pull/1428)；本版本无社区贡献。

```bash

```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.15.16 上的安装可直接升级。升级后照常重启服务。

本版本有两个可加的 PostgreSQL 迁移，启动时各执行一次：

- `processor_role`（只有 DDL，不改任何行）：`agent_setting_layers` 和 `schedule_profile_overrides` 的角色检查接受 `processor`，运行时能力检查接受 `no_tools`；`role_configs` 新增一行 `processor`（推荐角色提示词，超时 600 秒）。`looper serve` 启动时还会刷新内置 Claude Code 运行时的能力，使其声明 `no_tools`。
- `message_stream`：创建 `event_sources`、`source_chats`、`source_threads`、`source_people`、`source_runs`、`source_events`。配置来源之前都是空表。

### 行为变化与入口

**消息流（默认关闭）**

- 仪表盘新增 Message stream 页（`#messages`），显示来源状态、开关、设置表单（目录、起点）和最近的读取及错误。没有来源或来源为 `off` 时不读取，任何提示词、工具列表和 agent 命令行都不变。（[#1425](https://github.com/foolzzz/looper/pull/1425)）
- `ingest_mode = bridge` 时，`looper serve` 按来源的计划读取已有采集器的按会话消息文件，每条消息只存一次；Looper 自己启用的飞书渠道所用应用发出的消息不入库。只读完整行，被改写的文件会被识别并重读且不产生重复，被中断的读取可以续上。
- **启用桥接会导入历史。**起点默认为 `end`：第一次读取只记下每个文件的当前末尾，之后才入库。选 `beginning` 会从头读取并存下全部，采集器很大时要几分钟和不少磁盘（合成的 1.88 GB、约 80 万条消息的语料上耗时 117 秒、表约 920 MB）。早于保留期（应用消息 30 天）的正文只存文本。
- 新命令 `looper msgflow import --days N [--dry-run] [--per-file] [--source ID]` 按需导入历史并逐文件对账；有其他读取持有来源的锁时拒绝执行；`--dry-run` 不写入。
- 三个仅限操作员的操作：`message_stream.status`、`message_stream.runs`（只有计数和状态，不含消息正文）和 `message_stream.configure`。没有已桥接来源时，新的后台循环每 15 秒只做一次查询。

**processor 角色（默认关闭）**

- 新增角色 `processor` 和类型化的运行时能力 `no_tools`，只有 Claude Code 声明。processor 运行不带内置工具、斜杠命令、MCP 服务器、插件、会话文件和设置文件，因此任何项目的 hook 都不会运行；其他角色的命令行不变。（[#1424](https://github.com/foolzzz/looper/pull/1424)）
- processor 的 Agent Profile 依次经共享默认、角色、项目、项目内角色、定时任务的选择解析。代码里没有默认模型，什么都没选时用内置 profile。运行时没有 `no_tools` 的 profile 会被拒绝并给出原因。
- 管理员的 Claude Code 托管 hook 仍会在每次运行里执行，作为类型化事实读取并记在每次运行上；系统设置 `processor.refuse_with_managed_hooks`（默认关闭）可在它们存在时拒绝运行。
- 仪表盘：Settings → Roles 和项目的 Agent Profiles 标签页多了 Processor 行；运行时卡片、Runs 页和 profile 的「被谁使用」都会列出它。配置导出导入带上它的角色配置和各层。本版本没有任何东西会启动 processor 运行。
- Manager 的工具定义、`looper_settings` 视图和 `looper_agent_profiles` 列表都不提 processor，因此没有面向模型的变化。

**测试与文档**

- 测试在失败或中止时不再留下 launchd job 和孤儿 keeper 进程，macOS + Python 3.14 下整套测试不再卡在被停止的 keeper 上。launchd 升级测试只在设置 `LOOPER_TEST_LAUNCHD=1` 时运行。生产代码未改动（[#1427](https://github.com/foolzzz/looper/pull/1427)）。
- 新增 Manager 收尾、账本与晨报的 RFC 及其九个已决定的问题，是设计文档，不改动代码或行为（[#1426](https://github.com/foolzzz/looper/pull/1426)、[#1428](https://github.com/foolzzz/looper/pull/1428)）。

### 可选能力启用与使用

#### Message stream bridge

**启用：**默认关闭。在仪表盘打开 Message stream，填入已有采集器的按会话消息目录，选择起点（`end` 为默认，或 `beginning`）并打开开关，即把来源的 `ingest_mode` 设为 `bridge`。用 `looper msgflow import --days 30 --dry-run --per-file` 先看再导入更早的消息，去掉 `--dry-run` 才写入。

**验证：**状态卡用文字说明健康状况，最近的读取列出计数和错误。dry-run 逐文件报告读取数、不同 id、新增、已存和跳过；再导入一次应存 0 条。

**停用 / 回退：**关闭开关即停止读取，已存的消息保留；把来源的 `ingest_mode` 设回 `off` 即从循环里移除。新表是可加的，没有来源时不被使用，回退版本在 schema 上是安全的。

**权限边界：**只读采集器的文件，Looper 不写入，也不为该来源调用飞书。消息按采集器写入的内容存进 Looper 自己的 PostgreSQL。配置它的操作仅限操作员，状态和读取视图只有计数，没有消息正文。没有任何 agent 工具、提示词或命令行提到消息流。

**文档：**https://github.com/foolzzz/looper/blob/v2.15.17/docs/architecture/agent-system.md#message-stream

```bash
looper msgflow import --days 30 --dry-run --per-file
```

#### Processor role

**启用：**本版本没有东西会启动 processor 运行，所以暂无可启用的项。要提前准备，可在 Settings → Roles → Processor 选一个运行时声明 `no_tools` 的 Agent Profile（Claude Code），或保持内置 profile。

**验证：**Processor 行写明当前生效的 profile，并在它不能运行该角色时说明；运行时卡片显示哪些运行时可以运行 processor；项目的 agent 设置 `GET` 里有 `processor` 角色。

**停用 / 回退：**不设置该角色即可。它只有在出现调用方后才有作用；迁移只有 DDL，回退到旧版本前请先清掉已保存的 processor 层，否则旧版本不认识这个角色值。

**权限边界：**processor 运行没有工具、MCP 服务器、插件和项目 hook，交给它的消息文本不写入任何运行记录。例外是管理员的托管 hook：它们仍会运行并记在每次运行上，`processor.refuse_with_managed_hooks` 可在它们存在时拒绝运行。

**文档：**https://github.com/foolzzz/looper/blob/v2.15.17/docs/architecture/agent-system.md#the-processor-runs-with-no-tools

```bash
looper --version   # looper 2.15.17
```

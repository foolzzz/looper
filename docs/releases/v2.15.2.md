# Looper v2.15.2

This is the patch release v2.15.2, a hotfix line in which each merged change ships at once. It documents one change: [#1370](https://github.com/foolzzz/looper/pull/1370) (Coco steering and room push through its app-server).

## Release Decision

**Who should upgrade:** Operators who run Coco (TRAE CLI) Workers or Reviewers, natively or through TTADK, and want Planner messages and room messages to reach a run while it works instead of waiting to be pulled.

**What this release solves:** [#1370](https://github.com/foolzzz/looper/pull/1370) lets Coco Workers and Reviewers run through `coco app-server` with steering when the installed Coco supports `turn/steer`. Before, Coco runs used `exec --json`, could not be steered and pulled room messages through the room tools.

**Breaking changes:** No. The CLI, the API and the dashboard are unchanged, no new command or control is added and there is no PostgreSQL schema change. The PR states a behavior change (maintainer decision, intended: steering is preferred wherever the runtime supports it), listed below. The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.15.2
```

**Contributors:** Maintainer @foolzzz authored [#1370](https://github.com/foolzzz/looper/pull/1370); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.15.1 upgrades directly. There is no PostgreSQL schema change. Restart the service after upgrading, as for every release. Existing Coco registrations keep their saved capabilities until you use Re-detect on them.

## Behavior changes

Read in the diff of the PR, which states: behavior change (maintainer decision, intended).

### #1370: Coco steering and room push through its app-server

- **Detection.** `CocoRuntime` probes the schema after the version check: it runs `coco app-server generate-json-schema` with an empty temporary `TRAE_HOME` and adds the `steer` capability when `ClientRequest.json` lists `turn/steer`. A failed, timed-out or unreadable probe keeps the capabilities as before, so older Coco builds stay on `exec --json`. Coco's version is not subject to Codex's version gate.
- **Launch.** The Coco override that refused `steer_command` ("coco runs cannot be steered yet") is removed. Workers and Reviewers with detected steering now use the inherited Codex app-server command and the shared `CodexChannel`, with the same isolated `TRAE_HOME` and login. Through TTADK the command is `ttadk code -t trae-cli --skip-check -- app-server`. Manager and Planner keep the `exec --json` path; consult is still not enabled for Coco.
- **Re-detect.** Existing registrations keep their saved capabilities until Re-detect. After Re-detect finds steering, Planner messages can reach a running Coco Worker or Reviewer, and room delivery switches from `PULL` to `PUSHED`.
- **Room delivery.** Coco deliveries follow the Codex path: `turn/steer` only while a tool call runs, marked read when an app-server `userMessage` history item carries the delivery's message ids, advancing only past earlier confirmed deliveries.
- **Docs.** `docs/architecture/agent-system.md` is updated, and `docs/validation/coco-room-steering.md` records the PR's validation run.

### Model-visible changes

Yes, for Coco Workers and Reviewers whose registration has detected steering. `room_input` gives them the pushed room guidance (`PUSHED`) instead of the pull guidance (`PULL`), so the room section of their prompts changes: messages are delivered to the run, and it does not wait for them as a timer. Room message bodies arrive as steered input in the run's turn. Coco registrations without detected steering, other runtimes, and Coco Manager and Planner prompts are unchanged. No tool schema was changed by this PR.

### 行为变化与入口

以下在该 PR 的差异中可见，PR 声明：有行为变化（维护者决定，有意为之）。

**#1370：Coco 通过 app-server 支持 steer 和房间推送**

- **检测。**`CocoRuntime` 在版本检查后探测 schema：用空的临时 `TRAE_HOME` 运行 `coco app-server generate-json-schema`，当 `ClientRequest.json` 列出 `turn/steer` 时加入 `steer` 能力。探测失败、超时或无法读取时能力保持不变，旧版 Coco 仍走 `exec --json`。Coco 的版本不受 Codex 版本门槛约束。
- **启动。**移除了 Coco 中拒绝 `steer_command` 的覆盖（“coco runs cannot be steered yet”）。检测到 steer 的 Worker 和 Reviewer 现在使用继承自 Codex 的 app-server 命令和共享的 `CodexChannel`，使用相同的隔离 `TRAE_HOME` 和登录。经 TTADK 时命令为 `ttadk code -t trae-cli --skip-check -- app-server`。Manager 和 Planner 仍走 `exec --json`；Coco 仍未启用 consult。
- **重新检测。**现有注册在 Re-detect 之前保留原有能力。Re-detect 发现 steer 后，Planner 消息可送达运行中的 Coco Worker 或 Reviewer，房间投递从 `PULL` 切换为 `PUSHED`。
- **房间投递。**Coco 的投递沿用 Codex 路径：仅在工具调用运行期间使用 `turn/steer`，当 app-server 的 `userMessage` 历史项带有该投递的消息 id 时标记已读，且只越过更早已确认的投递。
- **文档。**更新了 `docs/architecture/agent-system.md`，并新增 `docs/validation/coco-room-steering.md` 记录该 PR 的验证。

**面向模型的变化：**有，针对已检测到 steer 的 Coco Worker 和 Reviewer。`room_input` 为它们给出推送式房间指引（`PUSHED`）而不是拉取式（`PULL`），因此其提示词中的房间部分会变化：消息会送达运行，不再把等待当作定时器。房间消息正文作为 steer 输入进入运行的当前轮次。未检测到 steer 的 Coco 注册、其他运行时以及 Coco 的 Manager 和 Planner 提示词不变。该 PR 未改动工具 schema。

# Looper v2.13.203

## Release Decision

**Who should upgrade:** Operators and maintainers who run a database, or who build from the source tree. A fresh install and an upgrade from a schema-3 database (v2.13.165 or later) now use one baseline instead of the historical migration chain. It ships the change merged since v2.13.202.

**What this release solves:** [#850](https://github.com/foolzzz/looper/pull/850) replaces the historical schema migrations with one final baseline: `looper/db/schema.sql` defines the complete fresh schema directly, a new `looper/db/seeds.sql` holds the builtin rows, and a schema-3 bridge database is upgraded by one guarded conversion.

**Breaking changes:** No. Commands, settings and the admitted upgrade path (v2.13.165 or later, as in v2.13.201) are unchanged; databases the previous release refused are still refused.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#850](https://github.com/foolzzz/looper/pull/850); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.203
```

## Behavior changes

- **Startup (`looper/db/connection.py`, `ensure_schema`):** under the schema lock the database is still classified as empty, current or bridge. An empty database now runs `schema.sql` once. A bridge database runs `upgrade_from_bridge` once. A current database never replays initialization DDL. The old five-phase split (`-- registry-phase:` markers, `_schema_phases`) is removed; `schema.sql` now has no phase markers.
- **Builtin rows (`looper/db/seeds.sql`, new):** on every start, in all three states, the seeds are inserted with `ON CONFLICT DO NOTHING`: the `manager` Manager, the `rt-claude-code` runtime, the claude-subscription, codex-login and grok-login providers with their endpoints, the pinned login model suggestions with fixed ids, and the `claude-code/opus` profile. Saved choices and creation times are not changed.
- **Baseline marker:** after an empty or bridge start, `post_bridge_baseline` is recorded in `schema_migrations`. The `schema_fingerprint` table is now created by `schema.sql`; on a current database the fingerprint is recorded only if that table still exists, so a pruned fingerprint is not recreated and opening a current database never repairs DDL.
- **Bridge upgrade (`looper/db/bridge_upgrade.py`):** `final_constraints` is removed. `upgrade_from_bridge` now itself adds `schedule_runs.execution_snapshot` if missing (only the earlier admitted schema-3 release lacks it) and drops the `task_user_gate_posts` unique constraint on channel, chat and external id. The admission rule is unchanged except that the historical table `project_skills` now also counts as a visible installation, so it alone is never treated as a fresh database.
- **Removed code:** `looper/db/registry_migration.py` and `looper/db/task_concurrency.py` are deleted, as are `layer_effort.migrate` and its `MIGRATION` name. `looper/agents/layer_effort.py` keeps the pure conversion (`convert`, `_apply`), which its module docstring now describes as available for legacy configuration projections. A search of `looper` and `tests` finds no remaining caller of the removed functions.
- **Size:** per the description, 368 added production lines and 144 added test lines (fixtures excluded); about 2300 lines deleted.
- **Tests:** `tests/test_bridge_schema_db.py` adds `test_historical_migration_entry_points_are_absent`, `test_historical_table_alone_is_never_fresh` (agents, agent_configs, task_agent_overrides, llm_profiles, project_skills) and `test_fresh_catalog_owner_constraints`. `tests/test_bridge_fingerprints.py` now skips releases whose `REGISTRY_SCHEMA_VERSION` is 4 or higher, since they are admitted by the baseline marker.
- **Model-visible changes:** None. No prompt, tool or message text changed; the `layer_effort.py` change touches only a docstring and removed upgrade code.

## Upgrade and rollback

Re-run `install.sh` once v2.13.203 is published. A database from v2.13.165 or later is upgraded on first start after a verified backup, as before. Back up the database before upgrading; the converted schema is not guaranteed to be readable by older releases, so a rollback to v2.13.202 should restore that backup.

## 中文摘要

### 升级决策

**谁需要升级：**运行数据库或从源码构建的运维者和维护者。全新安装以及从 schema 3 数据库（v2.13.165 或更高）升级，现在使用单一基线而不是历史迁移链。包含 v2.13.202 之后合并的改动。

**解决了什么：**[#850](https://github.com/foolzzz/looper/pull/850) 用一个最终基线取代历史 schema 迁移：`looper/db/schema.sql` 直接定义完整的全新 schema，新增的 `looper/db/seeds.sql` 保存内置行，schema 3 桥接数据库通过一次受保护的转换升级。

**是否有破坏性变更：**否。命令、设置和允许的升级路径（与 v2.13.201 相同，v2.13.165 或更高）不变；此前被拒绝的数据库仍被拒绝。

**如何验证：**运行 `looper --version` 核对版本为 2.13.203。

**贡献者：**维护者 @foolzzz 提交 [#850](https://github.com/foolzzz/looper/pull/850)；本次 patch release 无社区贡献。

```bash
looper --version   # looper 2.13.203
```

### 行为变化与入口

- **启动（`looper/db/connection.py`，`ensure_schema`）：**仍在 schema 锁内把数据库分类为空、当前或桥接。空数据库现在只执行一次 `schema.sql`；桥接数据库只执行一次 `upgrade_from_bridge`；当前数据库不再重放初始化 DDL。原有五阶段拆分（`-- registry-phase:` 标记、`_schema_phases`）已删除，`schema.sql` 不再含阶段标记。
- **内置行（新增 `looper/db/seeds.sql`）：**每次启动、在三种状态下都以 `ON CONFLICT DO NOTHING` 插入种子：`manager` Manager、`rt-claude-code` 运行时、claude-subscription / codex-login / grok-login 三个 provider 及其端点、带固定 id 的登录模型建议，以及 `claude-code/opus` profile。已保存的选择和创建时间不被改动。
- **基线标记：**空库或桥接库启动后，在 `schema_migrations` 记录 `post_bridge_baseline`。`schema_fingerprint` 表现在由 `schema.sql` 创建；当前数据库只在该表仍存在时才记录指纹，因此被清理的指纹不会被重建，打开当前数据库也不会修复 DDL。
- **桥接升级（`looper/db/bridge_upgrade.py`）：**删除 `final_constraints`。`upgrade_from_bridge` 自行在缺失时添加 `schedule_runs.execution_snapshot`（仅较早的已允许 schema 3 版本缺它），并删除 `task_user_gate_posts` 上 channel、chat、external id 的唯一约束。准入规则不变，只是历史表 `project_skills` 现在也算作可见的既有安装，单独存在时不会被当作全新数据库。
- **删除的代码：**删除 `looper/db/registry_migration.py` 和 `looper/db/task_concurrency.py`，以及 `layer_effort.migrate` 及其 `MIGRATION` 名称。`looper/agents/layer_effort.py` 保留纯转换（`convert`、`_apply`），模块文档称其用于旧配置投影。在 `looper` 和 `tests` 中搜索，已无被删函数的调用方。
- **规模：**据描述，新增生产代码 368 行、测试 144 行（不含夹具），删除约 2300 行。
- **测试：**`tests/test_bridge_schema_db.py` 新增 `test_historical_migration_entry_points_are_absent`、`test_historical_table_alone_is_never_fresh`（agents、agent_configs、task_agent_overrides、llm_profiles、project_skills）和 `test_fresh_catalog_owner_constraints`。`tests/test_bridge_fingerprints.py` 现在跳过 `REGISTRY_SCHEMA_VERSION` 为 4 或更高的版本，因为它们由基线标记准入。
- **面向模型的变化：**无。提示词、工具和消息文本均未改变；`layer_effort.py` 的改动只涉及文档字符串和被删除的升级代码。

### 升级与回退

v2.13.203 发布后重新运行 `install.sh`。v2.13.165 或更高版本的数据库在首次启动时经已验证的备份后升级，与此前一致。升级前请备份数据库；转换后的 schema 不保证旧版本可读，回退到 v2.13.202 时应恢复该备份。

### 可选能力启用与使用

本版本未新增可选能力启用入口。

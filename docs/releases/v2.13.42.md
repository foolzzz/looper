# Looper v2.13.42

## Release Decision

**Who should upgrade:** Anyone running scenario Managers (several Managers, task templates) or chatting with a Manager in the dashboard. Others are not affected.

**What this release solves:** [#408](https://github.com/foolzzz/looper/pull/408) fixes the P1 review follow-ups listed in [#399](https://github.com/foolzzz/looper/issues/399): a Manager's session view used the wrong follow-settings profile, templates could be put on the default Manager, a cancelled pattern check left its subprocess running, a tool call was checked against a stale tool schema, a sync at the 8-Manager cap reported ok and never retried, retiring a Manager left an in-flight chat stream waiting until timeout, the New session panel survived a Manager switch, and the chat message and event routes skipped the thread owner check without `?manager=`.

**Breaking changes:** No. One request that used to be accepted is now refused: `PUT /api/managers/manager/templates/:key` (a template on the default Manager) answers 400, because the default Manager's task tool never takes a template.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#408](https://github.com/foolzzz/looper/pull/408); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.42
```

## Behavior changes

- **Session view of a scenario Manager** (`looper/agents/tiers/manager.py`): the follow-settings profile is loaded with that Manager's id (`manager_id=self.agent_id`), so the preview of what following Settings would do is for this Manager.
- **Templates on the default Manager** (`looper/agents/managers_api.py`): `put_template` answers 400 ("the default Manager takes no task templates ...") for the default Manager; the 404 for an unknown Manager still comes first. `docs/architecture/agent-system.md` says so.
- **Pattern check** (`looper/agents/task_templates.py`): `match_patterns` kills and reaps its regex subprocess in a `finally`, so it no longer outlives a cancelled coroutine. Timeout and OS-error results are unchanged.
- **Tool call check** (`looper/agents/ops/service.py`): `call()` takes the tool from the scope in force, so its arguments are checked against the current schema (for example a template added since the tool list was built).
- **8-Manager cap** (`looper/agents/managers.py`): starting a Manager when 8 already run now raises instead of returning silently. The sync stays `pending` and the retry loop starts the Manager when a place frees.
- **Retiring a Manager** (`looper/agents/managers.py`): an in-flight user message gets a final reply with `outcome=stopped` before it is settled, so the chat stream ends instead of waiting until timeout.
- **Chat owner check** (`looper/agents/http_server.py`, `web/src/lib/api.ts`): `GET /api/chat/messages` and the session event stream (`/api/chat/events?session=`) treat a missing `manager` as the default Manager and answer 409 naming the owner for another Manager's thread. The dashboard passes the Manager to `watchChat`; `evals/prompt_regression/dialogs.py` passes it when reading a scenario Manager's thread.
- **Chat page** (`web/src/pages/chat.tsx`): switching Manager aborts, closes and clears the New session panel, so confirming it cannot reset the other Manager's session with the previous Manager's Profile.
- **Not a code change:** the `looper_projects` delete conflict already named only another Manager's use of a project; the pull request records it as already fixed and covered by an existing test.
- **Deferred:** the P2 items stay open in #399.
- **Model-visible changes:** the tool schema a Manager's call is validated against now comes from the scope in force (a template added meanwhile is accepted). The stopped-turn reply on retirement is new user-visible chat text (empty text, `outcome=stopped`). No prompt text, tool description or `Channel:` line changed.

Re-run `install.sh` once v2.13.42 is published. There is no schema change and no data migration. Rolling back to v2.13.41 needs no step.

### 升级决策

**谁需要升级：**使用场景 Manager（多个 Manager、任务模板）或在仪表盘与 Manager 聊天的用户。其他人不受影响。

**解决了什么：**[#408](https://github.com/foolzzz/looper/pull/408) 修复 [#399](https://github.com/foolzzz/looper/issues/399) 列出的 P1 评审遗留：Manager 会话视图用错了跟随设置的 Profile；默认 Manager 上可以放模板；被取消的模式检查留下子进程；工具调用按过期的 schema 校验；达到 8 个 Manager 上限时同步报 ok 且不重试；停用 Manager 时进行中的聊天流一直等到超时；切换 Manager 后「新会话」面板还在；聊天消息和事件路由在没有 `?manager=` 时跳过线程归属检查。

**是否有破坏性变更：**无。原先被接受的一种请求现在被拒绝：`PUT /api/managers/manager/templates/:key`（给默认 Manager 放模板）返回 400，因为默认 Manager 的任务工具从不使用模板。

**如何验证：**运行 `looper --version` 核对版本为 2.13.42。

**贡献者：**维护者 @foolzzz 提交 [#408](https://github.com/foolzzz/looper/pull/408)；本次 patch release 无社区贡献。


### 行为变化与入口

- 场景 Manager 的会话视图：用该 Manager 的 id 加载跟随设置的 Profile，预览针对该 Manager。
- 默认 Manager 上的模板：`put_template` 对默认 Manager 返回 400；未知 Manager 仍先返回 404。`docs/architecture/agent-system.md` 已说明。
- 模式检查：`match_patterns` 在 `finally` 中终止并回收正则子进程，协程被取消时不再遗留；超时和 OS 错误的结果不变。
- 工具调用校验：`call()` 从当前生效的 scope 取工具，按当前 schema 校验参数（例如之后新增的模板）。
- 8 个 Manager 上限：已有 8 个运行时再启动会抛出异常，不再静默返回；同步保持 `pending`，有空位时由重试循环启动。
- 停用 Manager：进行中的用户消息在 settle 之前先发一条 `outcome=stopped` 的最终回复，聊天流随之结束，不再等到超时。
- 聊天归属检查：`GET /api/chat/messages` 和会话事件流（`/api/chat/events?session=`）在缺少 `manager` 时按默认 Manager 处理，其他 Manager 的线程返回 409 并指明所属者。仪表盘向 `watchChat` 传入 Manager；`evals/prompt_regression/dialogs.py` 读取场景 Manager 的线程时也传入。
- 聊天页：切换 Manager 时中止、关闭并清空「新会话」面板，避免用上一个 Manager 的 Profile 确认后重置另一个 Manager 的会话。
- 非代码改动：`looper_projects` 删除冲突本就只提示其他 Manager 的占用；PR 记为已修复，并由已有测试覆盖。
- 延后：P2 项继续留在 #399。
- 面向模型的变化：Manager 的调用现按当前 scope 的工具 schema 校验（期间新增的模板可被接受）。停用时的停止回复是新的用户可见聊天内容（文本为空，`outcome=stopped`）。提示词文本、工具描述和 `Channel:` 行均未改变。

# Looper v2.14.54

This is the patch release v2.14.54, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.53: with keeper on, Claude Code Worker and Reviewer runs are started through a keeper ([#1023](https://github.com/foolzzz/looper/pull/1023)). No new setting is added, and with keeper off (the default) nothing changes.

## Release Decision

**Who should upgrade:** Anyone who has set `[agent_host] keeper = "on"` and runs Claude Code Workers or Reviewers. With keeper off, upgrading is optional.

**What this release solves:** [#1023](https://github.com/foolzzz/looper/pull/1023) makes a keeper hold each eligible Claude Code Worker or Reviewer process, so the run's process record and its stdout, stderr and stdin live in the run directory instead of in the server. A lost keeper fails only its own run, and a lost control-plane lock fences kept runs without sending them a request. Detach across a planned restart is not part of this release.

**Breaking changes:** No. No API or migration is added or removed. The keeper protocol and run manifest version are declared in the component manifest (`run_manifest_version = 1`, `keeper_protocols = ["1.0"]`).

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#1023](https://github.com/foolzzz/looper/pull/1023); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.54
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.53 upgrades directly. This release adds no migration.

## Behavior changes

- **Kept runs ([#1023](https://github.com/foolzzz/looper/pull/1023)).** Only with `[agent_host] keeper = "on"` and a control-plane lease, a Worker or Reviewer run starts through a keeper when its runtime is keepable (only Claude Code), it is not hosted, not steered, its launcher reports reliable exit codes, and it belongs to a task. The keeper owns the child's process record and captures stdout, stderr and stdin in the run directory under the runtime root. The new `KeptRun` handle implements the run handle interface, so the channel and parsers run unchanged. Consults, other runtimes and runs that do not qualify use their existing process path. The run directory is removed when the result has been published.
- **Ending a run.** Stop, kill, timeout and the spend cap end a kept run through the keeper (`child/end`), which ends the child's tree through the shared process-tree code. A normal server shutdown ends kept runs too.
- **Lost keeper.** If a keeper connection closes before the child's exit was reported, only that run fails, with `the run's keeper process ended unexpectedly`; the orphaned child's tree is ended after checking the identity recorded in the keeper's state file. A keeper that reports a newer controller fences the old control plane without ending the child.
- **Lost lock.** When the lock is lost, the fence now also aborts the connections of kept runs without sending a request, and logs each fencing step. The fence exit now runs through `Fence.exit`, so exit code 75 is kept.
- **Drain.** Because detach is not supported yet (`DETACH_SUPPORTED = False`), a drain of either scope waits for every run, kept or not.
- **Startup check.** With keeper on, `looper serve` refuses to start when the runtime root is too long for keeper sockets (over 103 bytes for the socket path), and says to use a shorter `--runtime-root` or set `keeper = "off"`.
- **Smaller fixes.** The "another looper serve already runs" message names the lock holder's process as `backend_pid`. A failed stdin append in the keeper rolls the log back to its last good offset. A `child/signal` for a child that already exited is ignored. `ps` start-time lookup treats a non-zero exit as failure, except the empty exit 1 for no match.
- **Model-visible changes:** No. No prompt, tool description, tool schema or Manager confirmation text changes. The architecture document gains a description of kept runs.

### 行为变化与入口

- **Kept 运行（[#1023](https://github.com/foolzzz/looper/pull/1023)）。**仅在 `[agent_host] keeper = "on"` 且持有控制面租约时，Worker 或 Reviewer 运行满足以下条件才通过 keeper 启动：运行时可被 keeper 持有（仅 Claude Code）、非 hosted、非 steered、启动器的退出码可靠、且属于某个任务。keeper 持有子进程记录，并把 stdout、stderr、stdin 记录在 runtime root 下的运行目录中。新的 `KeptRun` 句柄实现了运行句柄接口，通道与解析器无需改动。Consult、其他运行时和不符合条件的运行沿用原有进程路径。结果发布后运行目录会被删除。
- **结束运行。**停止、kill、超时和花费上限都通过 keeper（`child/end`）结束 kept 运行，由共享的进程树代码结束子进程树。正常的服务器关闭也会结束 kept 运行。
- **keeper 丢失。**keeper 连接在上报子进程退出前关闭时，只有该运行失败，错误为 `the run's keeper process ended unexpectedly`；在核对 keeper 状态文件中记录的身份后，结束孤儿子进程树。报告更新控制器的 keeper 会隔离旧控制面，但不结束子进程。
- **锁丢失。**锁丢失时，fence 现在还会中止 kept 运行的连接且不发送请求，并记录每一步。fence 的退出现在经由 `Fence.exit`，因此退出码 75 保持不变。
- **Drain。**由于尚不支持 detach（`DETACH_SUPPORTED = False`），两种范围的 drain 都等待所有运行（无论是否 kept）结束。
- **启动检查。**开启 keeper 时，若 runtime root 过长、keeper socket 路径超过 103 字节，`looper serve` 拒绝启动，并提示使用更短的 `--runtime-root` 或设置 `keeper = "off"`。
- **其他修复。**“另一个 looper serve 已在运行”的提示把锁持有者的进程标为 `backend_pid`。keeper 写 stdin 失败时，日志回滚到上一个正常偏移。对已退出子进程的 `child/signal` 被忽略。`ps` 启动时间查询在非零退出时视为失败，但“无匹配”的空输出退出码 1 除外。
- **面向模型的变化：**无。没有 prompt、工具描述、工具 schema 或 Manager 确认文本的变化。架构文档新增了对 kept 运行的说明。

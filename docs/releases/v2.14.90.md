# Looper v2.14.90

This is the patch release v2.14.90, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.89: the Agent Profile form asks for the model and its protocol first ([#1118](https://github.com/foolzzz/looper/pull/1118)).

## Release Decision

**Who should upgrade:** Operators who create or edit Agent Profiles in the dashboard. Everyone else can stay.

**What this release solves:** The form asked for a runtime first and then filtered models, so it was easy to pick a runtime that could not run the model you wanted. [#1118](https://github.com/foolzzz/looper/pull/1118) reorders it: model, protocol, provider, then runtime, with incompatible runtimes disabled and explained.

**Breaking changes:** No. Dashboard only: the saved body and the API are unchanged, with no schema change.

**How to verify:** Check the installed version. In Settings → Agent Profiles, open the form: it asks for the model, then the protocol (with the runtimes that speak it), then the provider among the enabled ones that offer it, then the runtime, where a runtime that cannot run the model is greyed out with its reason.

**Contributors:** Maintainer @foolzzz authored [#1118](https://github.com/foolzzz/looper/pull/1118); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.90
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.89 upgrades directly. There is no database change.

## Behavior changes

- **Agent Profile form** (`web/src/components/agent-profiles.tsx`). The order is now Name, Model, Protocol, Provider, Runtime, Effort. Model is a typed name with suggestions from the names registered on enabled providers (plus the profile's own model when editing), each listed once however many providers serve it. Protocol lists only the protocols that name has, labelled from `limits.api_formats`, with the runtimes that speak the chosen one. Provider lists the enabled providers that offer that model over that protocol; a single protocol or provider choice is selected automatically.
- **Runtime choice.** Built-in runtimes that cannot run the chosen model are disabled with a reason in the option text: wrong protocol, a runtime that takes only its own login, another runtime's login, or a model list the runtime restricts. If the current runtime cannot run a newly chosen model, the form switches to the first compatible runtime and shows a note naming the reason; if none can, it shows "No runtime here can run this model." Saving is refused with "Choose a runtime that can run this model." in that case.
- **Messages.** A typed name no enabled provider offers shows "No enabled provider offers NAME" with a link to LLM Providers instead of creating a model inline. Saving without a complete choice says "Choose a model, its protocol and a provider before saving." Editing a profile keeps its model even when its provider is disabled, with the existing disabled-provider warning.
- **Unchanged:** the saved body (`runtime_id`, `model_id`) and the API, so Manager tools, config import, the CLI and channels create profiles as before; the schema; launch checks.
- **Documentation and tests.** `docs/architecture/agent-system.md` describes the new order; `web/src/components/agent-profiles.test.tsx` and `tests/test_llm_models_dashboard.py` are updated.
- **Model-visible changes:** None. No tool description, prompt text or tool output changes.

### 升级决策

**谁需要升级：**在控制台创建或编辑 Agent Profile 的运维人员。其他人可不升级。

**解决了什么：**原表单先选运行时再过滤模型，容易选到无法运行目标模型的运行时。[#1118](https://github.com/foolzzz/looper/pull/1118) 调整顺序为模型、协议、提供方、运行时，并把不兼容的运行时置灰并说明原因。

**是否有破坏性变更：**否。仅控制台改动：保存的请求体和 API 不变，无结构变更。

**如何验证：**核对版本为 2.14.90。在设置 → Agent Profiles 打开表单：依次询问模型、协议（并列出支持它的运行时）、在已启用且提供该模型的提供方中选择，最后选运行时；无法运行该模型的运行时被置灰并显示原因。

**贡献者：**维护者 @foolzzz 提交 [#1118](https://github.com/foolzzz/looper/pull/1118)；本版本无社区贡献。

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.89 上的安装可直接升级。无数据库变更。

### 行为变化与入口

- **Agent Profile 表单**（`web/src/components/agent-profiles.tsx`）。顺序变为名称、模型、协议、提供方、运行时、effort。模型是可输入的名称，建议项来自已启用提供方上登记的名称（编辑时加上该 profile 自己的模型），无论多少提供方提供都只列一次。协议只列出该名称具有的协议，标签取自 `limits.api_formats`，并列出支持所选协议的运行时。提供方列出已启用且以该协议提供该模型的提供方；只有一个协议或提供方时自动选中。
- **运行时选择。**无法运行所选模型的内置运行时在选项文字中被禁用并给出原因：协议不符、运行时只接受自己的登录、其他运行时的登录、或运行时限定了模型列表。若当前运行时无法运行新选的模型，表单切换到第一个兼容的运行时并给出带原因的提示；若没有兼容的，显示 "No runtime here can run this model."，此时保存被拒绝，提示 "Choose a runtime that can run this model."。
- **提示信息。**输入的名称没有任何已启用提供方提供时，显示 "No enabled provider offers NAME" 和指向 LLM Providers 的链接，不再内联创建模型。选择不完整就保存时提示 "Choose a model, its protocol and a provider before saving."。编辑 profile 时即使其提供方已停用也保留原模型，并显示已有的停用警告。
- **不变：**保存的请求体（`runtime_id`、`model_id`）和 API，因此 Manager 工具、配置导入、CLI 和渠道创建 profile 的方式不变；数据库结构；启动检查。
- **文档与测试。**`docs/architecture/agent-system.md` 描述了新顺序；更新了 `web/src/components/agent-profiles.test.tsx` 和 `tests/test_llm_models_dashboard.py`。
- **面向模型的变化：**无。工具描述、提示文本和工具输出均不变。

# Looper v2.14.66

This is the patch release v2.14.66, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.65: a planned control-plane restart now detaches kept runs instead of ending them ([#1052](https://github.com/foolzzz/looper/pull/1052)).

## Release Decision

**Who should upgrade:** Operators who run with the keeper on and restart the control plane with `looper service upgrade` or with a turns drain followed by SIGTERM. Others need not upgrade.

**What this release solves:** A planned restart ended every kept Worker or Reviewer run. [#1052](https://github.com/foolzzz/looper/pull/1052) detaches each attached kept run at an event boundary when SIGTERM arrives during an active turns drain, so its keeper, child and running record stay in place. Adopting the detached runs at the next startup is not part of this release; until it lands, the next start ends them.

**Breaking changes:** No. No API schema or configuration changes and there is no migration. The `stdout.log` limit no longer ends the run (see Behavior changes).

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#1052](https://github.com/foolzzz/looper/pull/1052); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.66
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.65 upgrades directly. This release adds no migration.

## Behavior changes

- **Planned restart detaches kept runs.** With keeper mode on, if SIGTERM arrives while a turns drain is active (`shutdown_mode` in `looper/agents/serve.py`), the control plane calls `detach_kept` on the worker pool before the rest of the shutdown. Each attached kept run stops feeding its parser and waits until it is idle; `KeptRun.detach` then writes `detach.json` (the processed stdout offset, the stdin offset, the epoch), the handle becomes `DETACHED` and its consumer is cancelled. The keeper, the child, the running record and the room MCP files stay in place, and no result is published. The mode is fixed at the first signal, so a later drain lease expiry does not change it; a lease that expired before SIGTERM uses the normal shutdown.
- **Everything else still ends runs.** No drain, a runs drain, Ctrl-C and keeper off end runs as before. A run that cannot detach (busy past 3 seconds, finishing, lost or not attached) is ended with the others.
- **Turns drain no longer waits for keepable runs.** `DETACH_SUPPORTED` is removed from `looper/agents/drain.py`: a turns drain waits only for runs that are not keepable, a runs drain waits for all of them.
- **Not yet adopted.** Nothing reads `detach.json` at startup yet, so the next start still ends the detached runs and interrupts their records so their steps can run again.
- **`stdout.log` limit.** The keeper still stops appending to `stdout.log` at 512 MiB, but it no longer ends the child (`end_reason` `log_limit` is gone). It sets `stdout_truncated` and `stdout_truncated_at` in `keeper.json` and keeps sending live output to the subscriber; new stdout subscriptions are refused, and a run with truncated stdout cannot be adopted.
- **`stdin/write` acknowledges earlier.** The reply now confirms the offset appended to `stdin.log`; a keeper-owned writer task drains the queue to the child, so a slow reader does not delay the reply. The control plane keeps each chunk until it is acknowledged.
- **Launch fencing.** A kept launch is refused with a fenced error when the control plane has lost permission to start agents (`proc_tree.spawns_fenced`).
- **Docs:** `docs/architecture/agent-system.md` and the hot-upgrade RFC describe the above.
- **Size:** per the pull request description, 282 added lines of production code and 666 of tests (fixtures excluded).
- **Model-visible changes:** None. No prompt, tool description or tool output text changed.

### 升级决策

**谁需要升级：**开启 keeper、并用 `looper service upgrade` 或“回合排空后发 SIGTERM”重启控制面的运维者。其他人无需升级。

**是否有破坏性变更：**否。没有 API 结构或配置变更，也没有迁移。`stdout.log` 上限不再结束运行（见行为变化）。

### 升级

### 行为变化与入口

- **计划内重启脱离托管运行。**keeper 开启、且回合排空进行中收到 SIGTERM 时（`looper/agents/serve.py` 的 `shutdown_mode`），控制面在其余关闭步骤之前对 worker 池调用 `detach_kept`。每个已连接的托管运行停止向解析器送数据并等待空闲；`KeptRun.detach` 随后写入 `detach.json`（已处理的 stdout 偏移、stdin 偏移、epoch），句柄变为 `DETACHED`，其消费任务被取消。keeper、子进程、运行记录和房间 MCP 文件保持不动，也不发布结果。模式在第一次信号时确定，之后排空租约过期不会改变；在 SIGTERM 之前已过期的租约使用普通关闭。
- **其他情况仍结束运行。**无排空、运行排空、Ctrl-C、keeper 关闭都照旧结束运行。无法脱离的运行（3 秒内仍忙、正在结束、已丢失或未连接）与其他运行一起被结束。
- **回合排空不再等待可托管的运行。**`looper/agents/drain.py` 移除了 `DETACH_SUPPORTED`：回合排空只等待不可托管的运行，运行排空等待全部。
- **尚未接管。**启动时还没有代码读取 `detach.json`，所以下次启动仍会结束脱离的运行，并中断其记录以便步骤重新运行。
- **`stdout.log` 上限。**keeper 仍在 512 MiB 处停止向 `stdout.log` 追加，但不再结束子进程（`end_reason` 的 `log_limit` 已去掉）。它在 `keeper.json` 中设置 `stdout_truncated` 和 `stdout_truncated_at`，继续向订阅者推送实时输出；新的 stdout 订阅会被拒绝，stdout 被截断的运行不能接管。
- **`stdin/write` 更早确认。**回复现在确认已追加到 `stdin.log` 的偏移；由 keeper 持有的写任务把队列写给子进程，所以慢读不会延迟回复。控制面在收到确认前保留每个数据块。
- **启动围栏。**控制面失去启动 agent 的权限时（`proc_tree.spawns_fenced`），托管启动会以围栏错误被拒绝。
- **文档：**`docs/architecture/agent-system.md` 和热升级 RFC 描述了以上内容。
- **规模：**据 PR 描述，生产代码新增 282 行，测试新增 666 行（不含 fixture）。
- **面向模型的变化：**无。没有提示、工具说明或工具输出文字变化。

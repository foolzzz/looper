# Looper v2.14.191

This is the patch release v2.14.191, a hotfix line in which each merged change ships at once. It documents one change: [#1353](https://github.com/foolzzz/looper/pull/1353) (the message journal and the channel inboxes write off the event loop).

## Release Decision

**Who should upgrade:** Operators who run `looper serve` with the Lark or Telegram channels and want journal and inbox disk writes not to block the event loop.

**What this release solves:** [#1353](https://github.com/foolzzz/looper/pull/1353) moves the blocking message journal writes and the Lark and Telegram inbox SQLite calls to worker threads, so fsync and commits no longer stall the loop.

**Breaking changes:** No. The Telegram and Lark channel protocols and the CLI are unchanged, no new command or dashboard control is added and there is no PostgreSQL schema change. The PR states no behavior change besides latency. The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.14.191
```

**Contributors:** Maintainer @foolzzz authored [#1353](https://github.com/foolzzz/looper/pull/1353); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.190 upgrades directly. There is no PostgreSQL schema change and the inbox and journal file formats are unchanged. Restart the service after upgrading, as for every release.

## Behavior changes

Read in the diff of [#1353](https://github.com/foolzzz/looper/pull/1353). The PR states: behavior change (maintainer decision, intended): none besides latency.

### #1353: message journal and channel inboxes write off the event loop

- **Message bus journal.** `MessageBus` runs journal appends and the barrier before start and stop on a dedicated single-thread executor (`message-journal`). A new lock serializes start, publish-with-append and stop, so replay and compaction cannot race a write, including a write whose publisher was cancelled while fsync was in flight. Journaled messages are delivered after their append completes. The executor is shut down on stop.
- **Channel inboxes.** A new `looper/agents/channels/sqlite_inbox.py` gives each Lark and Telegram inbox one SQLite connection and one serial thread (`channel-inbox`). Inbox methods are now awaited coroutines; `LarkInbox` and `TelegramInbox` are opened with `await ...open(path)` and closed with `await close()`, which also drains writes whose callers were cancelled.
- **Telegram stop boundary.** The polling-stop checkpoint is queued eagerly from the synchronous stop-signal hook, which waits for it with a blocking `flush()` so the agent drain is not released before the commit; async shutdown awaits the same future and logs a warning if it could not be saved.
- **Lark thread activity hook.** The transport's `on_thread_activity` callback is now an awaitable and is awaited.
- No change to the inbox schema, the cadence, the message contents or the CLI.

### 行为变化与入口

以下在 [#1353](https://github.com/foolzzz/looper/pull/1353) 的差异中可见。PR 声明：除延迟外无行为变化（维护者决定，有意为之）。

**#1353：消息日志和渠道收件箱的写入移出事件循环**

- **消息总线日志。**`MessageBus` 在专用单线程执行器（`message-journal`）上执行日志追加以及启动和停止前的屏障。新增的锁串行化启动、带追加的发布和停止，因此重放和压缩不会与写入竞争，包括发布者在 fsync 进行中被取消的写入。带日志的消息在追加完成后才投递。停止时关闭执行器。
- **渠道收件箱。**新增 `looper/agents/channels/sqlite_inbox.py`，为每个 Lark 和 Telegram 收件箱提供一个 SQLite 连接和一个串行线程（`channel-inbox`）。收件箱方法改为可等待的协程；`LarkInbox` 和 `TelegramInbox` 通过 `await ...open(path)` 打开，通过 `await close()` 关闭，关闭时也会排空调用方已被取消的写入。
- **Telegram 停止边界。**轮询停止检查点由同步的停止信号钩子提前排队，钩子用阻塞的 `flush()` 等待它，确保提交之前不会放行智能体排空；异步关闭等待同一个 future，若未能保存则记录警告。
- **Lark 线程活动钩子。**传输层的 `on_thread_activity` 回调改为可等待并被 await。
- 收件箱 schema、轮询节奏、消息内容和 CLI 均不变。

**面向模型的变化：**无。未改动提示词、工具描述或工具 schema。

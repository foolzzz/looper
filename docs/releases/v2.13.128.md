# Looper v2.13.128

## Release Decision

**Who should upgrade:** Nobody needs to upgrade for a visible feature. Operators who bind Telegram or Lark chats to particular Managers, or who plan to, should upgrade, because bot chats are now routed from a live snapshot instead of the Manager chosen at startup.

**What this release solves:** [#652](https://github.com/foolzzz/looper/pull/652) makes native bot ingress (Telegram, Lark, Lark bot) resolve each incoming chat against a process-local routing snapshot of its bound Manager, so a binding or policy change published by the service takes effect without restarting the bot, while accepted turns, task destinations and the chat stop command keep working.

**Breaking changes:** No. No command, option or schema changed. A bot with no bindings and no bound-chats-only policy still sends every chat to its own Manager.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#652](https://github.com/foolzzz/looper/pull/652); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.128
```

## Behavior changes

- **Routing snapshot:** the new `looper/agents/channels/chat_routing.py` defines `RoutingSnapshot` (bot owner Manager id, `bound_only` flag and an immutable chat-to-Manager mapping, validated by building each thread identity) and `RouteDecision` with the actions `admit` and `silent`. A chat with a binding resolves to its bound Manager (`explicit`); an unbound chat resolves to the bot's own Manager, or to `silent` when the policy is bound-chats-only.
- **Registry:** `ChannelRegistry.register` in `looper/agents/channels/registry.py` loads the snapshot of every bot whose channel id parses as a bot id, under a per-bot mutation lock, and wires the adapter's resolver to the registry. If the snapshot cannot be loaded the error is logged, the bot is not started and the exception is raised. `bindings_changed` swaps in a new snapshot synchronously.
- **Service-write helpers:** `bind_chat`, `unbind_chat`, `set_chat_policy` and `remove_bot_with_routing` change the stored rows and the snapshot in one transaction under the mutation lock. The commit and the snapshot swap are shielded from cancellation. Without a registry (no running service) they only persist the choice for the next startup. Direct SQL does not update a live snapshot. The diff adds these helpers; this draft did not look for a new command or API that calls them.
- **Silent chats:** a chat the policy rejects is dropped without a reply. Each chat seen is recorded through `observe_chat`; a storage failure is logged and never blocks or exposes the message.
- **Telegram:** `looper/agents/channels/telegram.py` admits and routes once per update in `_admitted`, before any reaction or reply. `/status`, `/new`, `/stop`, `/profile`, `/help`, `/start`, gate commands and plain text all go to the bound Manager, and `/help` and `/start` answer a bound chat only while its Manager runs. The separate `/status` envelope code was merged into `_forward`; a status message still carries only the chat id in its context.
- **Lark and Lark bot:** `looper/agents/channels/lark.py` resolves the chat before the Manager check, drops silent chats, and sends the envelope to the bound Manager. `lark_bot.make_adapter` and the `_telegram_adapter_from_config`, `_lark_adapter`, `_lark_bot_adapter` builders in `looper/agents/serve.py` pass the resolver and the fleet's `stop_chat` through, and `_register_bots` supplies them for every bot row.
- **Unavailable bound Manager:** when a chat is bound explicitly and its Manager is not running (or its state cannot be read), the sender gets the existing turned-off reply and the message is dropped. A stop command in that case is answered by the fleet-wide stop of v2.13.127 (`chat_stop_reply`) instead, so older turns of that chat still stop. For an unbound chat the old rule remains: the check applies to a non-default Manager and an unreadable state lets the message through.
- **Thread identity:** accepted messages carry `channel_thread_id` and `channel_manager_id` metadata. In `looper/agents/tiers/manager.py`, `_session_key` now accepts an unsuffixed thread identity only when `channel_manager_id` names the Manager the envelope targets (the bot's own owner); this is the validation of the bot's own Manager that the description of [#652](https://github.com/foolzzz/looper/pull/652) says it takes from #648 item 1.
- **Model-visible changes:** none found. The envelope payload keeps the same `text`, `language` and `channel_context` fields, and the only new data is envelope metadata (`channel_thread_id`, `channel_manager_id`). Prompts, tool declarations and tool results are unchanged. For a Telegram `/status` the context still holds only `chat_id`; for other messages it holds `chat_id`, `user_id`, `username` and message ids as before.
- **Line counts:** the description of [#652](https://github.com/foolzzz/looper/pull/652) reports tests 571 and production 339 added lines (fixtures excluded).

## Upgrade and rollback

Re-run `install.sh` once v2.13.128 is published. No schema or configuration change. Rolling back to v2.13.127 restores routing that is fixed when the bot starts.

## 中文摘要

### 升级决策

**谁需要升级：**无需为可见功能而升级。已把 Telegram 或 Lark 聊天绑定到特定 Manager（或打算这样做）的操作者应升级，因为 bot 聊天现在按实时快照路由，而不是启动时选定的 Manager。

**解决了什么：**[#652](https://github.com/foolzzz/looper/pull/652) 让原生 bot 入口（Telegram、Lark、Lark bot）按进程内路由快照把每个聊天解析到其绑定的 Manager，因此服务发布的绑定或策略变更无需重启 bot 即可生效，同时已接受的 turn、任务目的地和聊天停止命令继续可用。

**是否有破坏性变更：**否。命令、选项和表结构均未改变。没有绑定、也未设置仅限绑定聊天策略的 bot，仍把所有聊天交给自己的 Manager。

**如何验证：**运行 `looper --version` 核对版本为 2.13.128。

**贡献者：**维护者 @foolzzz 提交 [#652](https://github.com/foolzzz/looper/pull/652)；本次 patch release 无社区贡献。

```bash
looper --version   # looper 2.13.128
```

### 行为变化与入口

- **路由快照：**新增 `looper/agents/channels/chat_routing.py`，定义 `RoutingSnapshot`（bot 所属 Manager id、`bound_only` 标志和不可变的聊天到 Manager 映射，并通过构造线程标识来校验）与动作为 `admit`、`silent` 的 `RouteDecision`。有绑定的聊天解析到其绑定的 Manager（`explicit`）；未绑定的聊天解析到 bot 自己的 Manager，策略为仅限绑定聊天时为 `silent`。
- **注册表：**`looper/agents/channels/registry.py` 的 `ChannelRegistry.register` 在每个 bot 的变更锁下为渠道 id 可解析为 bot id 的渠道加载快照，并把适配器的解析器接到注册表。快照加载失败时记录日志、不启动该 bot 并抛出异常。`bindings_changed` 同步替换快照。
- **服务写入辅助函数：**`bind_chat`、`unbind_chat`、`set_chat_policy`、`remove_bot_with_routing` 在变更锁下用同一个事务修改存储行和快照；提交与快照替换不受取消影响。没有注册表（无运行中的服务）时只保存选择，下次启动生效。直接改 SQL 不会更新运行中的快照。本 diff 新增了这些辅助函数；本草稿未查找是否有新的命令或 API 调用它们。
- **静默聊天：**被策略拒绝的聊天不回复直接丢弃。每个见到的聊天通过 `observe_chat` 记录；存储失败只记日志，不阻塞也不暴露消息。
- **Telegram：**`looper/agents/channels/telegram.py` 在 `_admitted` 中对每个 update 只做一次准入与路由，先于任何表情回应或回复。`/status`、`/new`、`/stop`、`/profile`、`/help`、`/start`、gate 命令和普通文本都发往绑定的 Manager；`/help` 和 `/start` 仅在绑定聊天的 Manager 运行时才回答。独立的 `/status` 信封代码并入 `_forward`；status 消息的上下文仍只含聊天 id。
- **Lark 与 Lark bot：**`looper/agents/channels/lark.py` 在检查 Manager 之前解析聊天，丢弃静默聊天，并把信封发给绑定的 Manager。`lark_bot.make_adapter` 以及 `looper/agents/serve.py` 的 `_telegram_adapter_from_config`、`_lark_adapter`、`_lark_bot_adapter` 构建函数透传解析器和 fleet 的 `stop_chat`，`_register_bots` 为每个 bot 行提供它们。
- **绑定的 Manager 不可用：**聊天被显式绑定而其 Manager 未运行（或状态无法读取）时，发送者收到已有的“已关闭”回复，消息被丢弃。此时的停止命令改由 v2.13.127 的全 Manager 停止（`chat_stop_reply`）回答，该聊天更早的 turn 仍会被停止。未绑定聊天保持旧规则：仅对非默认 Manager 检查，状态无法读取时放行消息。
- **线程标识：**被接受的消息携带 `channel_thread_id` 与 `channel_manager_id` 元数据。`looper/agents/tiers/manager.py` 的 `_session_key` 现在只在 `channel_manager_id` 指向信封目标 Manager（即 bot 自己的所属 Manager）时接受无后缀的线程标识；这就是 [#652](https://github.com/foolzzz/looper/pull/652) 描述中所说取自 #648 第 1 项的对 bot 自身 Manager 的校验。
- **面向模型的变化：**未发现。信封 payload 仍是相同的 `text`、`language`、`channel_context` 字段，新增的只有信封元数据（`channel_thread_id`、`channel_manager_id`）。提示词、tool 声明和结果均未改变。Telegram `/status` 的上下文仍只含 `chat_id`；其他消息仍含 `chat_id`、`user_id`、`username` 和消息 id。
- **行数：**[#652](https://github.com/foolzzz/looper/pull/652) 的描述报告新增测试 571 行、生产代码 339 行（不含 fixtures）。

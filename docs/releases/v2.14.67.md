# Looper v2.14.67

This is the patch release v2.14.67, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.66: a detached kept run can be replayed and resumed in another WorkerPool ([#1058](https://github.com/foolzzz/looper/pull/1058)).

## Release Decision

**Who should upgrade:** Nobody needs to upgrade for this release alone. It adds the building blocks of adopting detached runs; no startup path calls them yet.

**What this release solves:** v2.14.66 detaches kept runs on a planned restart, but nothing could pick them up again. [#1058](https://github.com/foolzzz/looper/pull/1058) adds `WorkerPool.adopt_dir(run_dir, *, expect)`, which rebuilds a detached run from its `manifest.json`, takes its slot again, reattaches to the keeper, replays the output already consumed without side effects, consumes the live output as the original consumer would, and publishes the result once. Calling it at startup (the candidate scan and the hold on the step) is not part of this release; until it lands, the next start still ends detached runs.

**Breaking changes:** No. No API schema or configuration changes and there is no migration.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#1058](https://github.com/foolzzz/looper/pull/1058); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.67
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.66 upgrades directly. This release adds no migration.

## Behavior changes

- **Adoption is available but not wired in.** `WorkerPool.adopt_dir` (`looper/agents/tiers/worker.py`) is not called from any production code in this release, so a running installation behaves as in v2.14.66: the next start still ends detached runs. The caller must establish the step's hold first.
- **What `adopt_dir` does.** It checks the manifest against the expected task, step and role, refuses a run that is already attached, and checks that the launch settings still match the run's consuming launch. It then resumes the running record, attaches (`KeptRun.attach`), takes the slot again and starts the consumer. The consumer replays `[0, consumed)` of `stdout.log` without side effects, rebuilding usage, then consumes live output and publishes the result once; a result already consumed before the detach decides the run. The outcome is `adopted`, `failed` or `not_candidate`; failures are `files`, `log_short`, `hold_mismatch`, `launch_changed`, `record_not_running`, `keeper_unreachable` or `protocol`. A failed adoption ends the keeper (or keeps the identity files for the next startup sweep when ending cannot be confirmed) and marks the record `interrupted`.
- **`KeptRun.attach`.** It works over the keeper socket, or from the files alone when the child has already exited, and delays delivery at the replay boundary. It validates the keeper files, the consumed offset (it must end on an event boundary and lie within `stdout.log`) and removes `detach.json` once attached.
- **Recorder.** `ClaudeRunRecorder.resume` continues a record that is still `running` and raises `RecordNotResumable` otherwise; new helpers in `looper/db/llm_records.py` are `record_state`, `max_event_seq` and `end_record_interrupted`.
- **Refactor of the run path.** `WorkerPool._execute` is split into `_prepare` and `_consume`, moving as little code as possible. Normal runs are meant to behave unchanged.
- **`detach.json` documentation.** The hot-upgrade RFC (Chinese) now lists `consumed` as `{stdout}` only, matching what is written.
- **Log line.** The startup scan now logs end reasons by value.
- **Size:** per the pull request description, 670 added lines of production code and 951 of tests (fixtures excluded).
- **Model-visible changes:** None. No prompt, tool description or tool output text changed; the prompt construction is only moved into `_prepare`.

### 升级决策

**谁需要升级：**仅为本版本无需升级。它只加入了接管脱离运行所需的构件，启动流程还没有调用它们。

**解决了什么：**v2.14.66 在计划内重启时脱离托管运行，但之后无法再接上。[#1058](https://github.com/foolzzz/looper/pull/1058) 增加 `WorkerPool.adopt_dir(run_dir, *, expect)`：根据 `manifest.json` 重建脱离的运行，重新占用其席位，重新连接 keeper，无副作用地回放已消费的输出，再像原消费者一样消费实时输出，并只发布一次结果。启动时调用它（候选扫描和步骤的占位）不在本版本内；在那之前，下次启动仍会结束脱离的运行。

**是否有破坏性变更：**否。没有 API 结构或配置变更，也没有迁移。

**如何验证：**运行 `looper --version` 核对版本为 2.14.67。

**贡献者：**维护者 @foolzzz 提交 [#1058](https://github.com/foolzzz/looper/pull/1058)；本版本无社区贡献。

```bash
looper --version   # looper 2.14.67
```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.66 上的安装可直接升级。本版本没有迁移。

### 行为变化与入口

- **接管能力已具备但未接入。**`WorkerPool.adopt_dir`（`looper/agents/tiers/worker.py`）在本版本中没有被任何生产代码调用，所以运行中的安装与 v2.14.66 行为一致：下次启动仍会结束脱离的运行。调用方必须先建立该步骤的占位。
- **`adopt_dir` 做什么。**它对照期望的任务、步骤和角色检查 manifest，拒绝已连接的运行，并检查启动设置仍与该运行的消费启动一致；然后恢复运行中的记录、连接（`KeptRun.attach`）、重新占用席位并启动消费者。消费者无副作用地回放 `stdout.log` 的 `[0, consumed)` 以重建用量，再消费实时输出并只发布一次结果；脱离前已消费的结果会直接决定该运行。结果为 `adopted`、`failed` 或 `not_candidate`；失败原因为 `files`、`log_short`、`hold_mismatch`、`launch_changed`、`record_not_running`、`keeper_unreachable` 或 `protocol`。接管失败会结束 keeper（无法确认结束时保留身份文件留给下次启动清扫），并把记录标记为 `interrupted`。
- **`KeptRun.attach`。**可通过 keeper 套接字工作，子进程已退出时仅凭文件工作，并在回放边界处控制投递。它校验 keeper 文件和已消费偏移（必须落在事件边界且不超过 `stdout.log`），连接成功后删除 `detach.json`。
- **记录器。**`ClaudeRunRecorder.resume` 继续仍为 `running` 的记录，否则抛出 `RecordNotResumable`；`looper/db/llm_records.py` 新增 `record_state`、`max_event_seq` 和 `end_record_interrupted`。
- **运行路径重构。**`WorkerPool._execute` 拆为 `_prepare` 和 `_consume`，尽量少移动代码；普通运行应保持不变。
- **`detach.json` 文档。**热升级 RFC（中文）现在把 `consumed` 写成只有 `{stdout}`，与实际写入一致。
- **日志行。**启动扫描现在按值记录结束原因。
- **规模：**据 PR 描述，生产代码新增 670 行，测试新增 951 行（不含 fixture）。
- **面向模型的变化：**无。没有提示、工具说明或工具输出文字变化；提示的构造只是移入 `_prepare`。

# Looper v2.12.0

## At a Glance

**Deployment settings move into a private ops file.** `looper config init-ops` writes `<runtime-root>/ops/server.toml` from the values in effect. Run `looper service install` again after migrating so the service names the file and stops carrying the database URL. The old deployment variables and their `.env` entries work for this release with warnings; other `.env` keys are already ignored. There is no implicit database URL on startup.

**Children start from an environment allowlist.** Agents, schedule gates, probes and helpers no longer inherit every server variable. Provider bindings and agent settings still add the variables a run needs. This removes implicit environment access to the database URL; it does not prevent a process running as the same user from reading the ops file.

**Settings → Scheduler owns the minimum interval and default run timeout.** The built-in default timeout is **no limit**. A schedule can inherit the default, set seconds, or explicitly have no limit. Existing schedules keep their number or no limit. Each run keeps the timeout it starts with.

**Claude Code agents refuse messages from other sessions.** They also lose `ListAgents`; without agent teams they lose `SendMessage`. Team runs keep `SendMessage` for their teammates, with the known-name limitation below.

**An Obsidian knowledge vault can carry notes between tasks.** Configure its path, writable folders and optional rules file in Settings → Knowledge vault, then select On for the project's Knowledge vault. It is off by default. The Planner, Workers and Reviewers can search and read notes, write within the configured folders, and leave lasting knowledge at task end under the vault's own rules. In a git vault, each write is a separate commit recorded in task activity.

### Highlights

- **A private ops file and an explicit migration command.** Deployment settings, service installation and child environments share the new loader. ([#241](https://github.com/foolzzz/looper/pull/241))
- **Scheduler settings, with per-schedule timeout choices.** The dashboard and Manager use the same settings and schedule values; configuration export/import carries them. ([#237](https://github.com/foolzzz/looper/pull/237))
- **Claude Code session separation.** Incoming peer messages are refused and peer-discovery tools are removed from launches. ([#238](https://github.com/foolzzz/looper/pull/238))
- **An optional knowledge vault, shared across runtimes.** Looper supplies search, read and write tools for task agents, checks a note's sha256 before replacing it, and asks the Planner to close out lasting knowledge under the vault's rules. ([#239](https://github.com/foolzzz/looper/pull/239))

## Release Decision

**Who should upgrade:** Operators running v2.11.0, especially installations using deployment variables or .env, custom child-process variables, schedules, or Claude Code alongside interactive sessions. Read the migration steps before restarting an upgraded service.

**What this release solves:** Deployment settings no longer need to live in a service's environment, children no longer inherit the whole server environment, scheduler limits can be saved in the system settings, and Claude Code agents refuse incoming cross-session messages. Projects can opt into a local knowledge vault to reuse notes and keep lasting knowledge between tasks.

**Breaking changes:** Yes. Startup has no default database URL, .env no longer populates the server environment, child environments are filtered, service installation requires an ops file, and Claude Code loses peer tools as described below. Deployment-variable compatibility lasts this release only. Schedule views can now return the string "default" for run_timeout_seconds.

**How to verify:** After installing the release and following the migration below, check the version and doctor with the same ops file and runtime root as the service. Read Settings → Scheduler and the schedules' timeout choices; existing choices must be preserved. The read-only API example below shows each scheduler setting's effective value and source. Check the service report for its config file and the absence of a database URL in its captured environment.

**Contributors:** Release maintainer @foolzzz; no community contribution in #238, #241, #237 or #239.

```bash
looper --version   # looper 2.12.0
looper doctor
looper service status
# With the server running, using its runtime root (default ~/.looper):
curl -fsS -H "Authorization: Bearer $(cat ~/.looper/operator-token)" \
  http://127.0.0.1:8767/api/scheduler-settings | python3 -m json.tool
```

## New capabilities

### Ops file and child environment

- **One loader for deployment settings.** `serve`, `doctor`, `config export/import` and `service install` read `<runtime-root>/ops/server.toml` (default `~/.looper/ops/server.toml`); `--config` names another file. Keys are `[database] url`, `[server] host, port, public_url, log_level`, `[backup] pg_dump, command` (an argv array), and `[operator_notes] root` (an absolute path). Values are not interpolated: no variables, `~` expansion or includes. Invalid keys, types and values stop the command. The file and its directory must belong to the user and exclude group/other access; `init-ops` writes mode 0600 in a private 0700 directory, atomically, and refuses to overwrite an existing file. Restart after editing. ([#241](https://github.com/foolzzz/looper/pull/241))
- **Precedence per setting:** explicit flag → file → old environment variable (`LOOPER_*`, then `LOOPX_*`) → the same names in the checkout's `.env` → built-in value. The compatibility settings are the database URL, public URL, pg_dump, backup command and operator notes root (the last has no `LOOPX_*` alias). The runtime root is separate: `--runtime-root`, then the deprecated runtime-root variable, then `~/.looper`; it is not a file key. `serve --host`, `--port` and `--verbose` override the file. Without flags or file settings the host is 127.0.0.1, the port 8767 and logging info. ([#241](https://github.com/foolzzz/looper/pull/241))
- **A service unit names the ops file and runtime root.** Installation writes absolute `--config` and `--runtime-root` arguments. `--port` is written only when explicitly given, or retained from an older unit when the file has no port. Status and restart otherwise read the file's port. Installation refuses without an ops file or while an ops setting still comes from an environment variable. `--env` cannot carry an ops setting. ([#241](https://github.com/foolzzz/looper/pull/241))
- **Children receive named variables only.** The allowlist covers system, locale, SSH/git, proxy/certificate and runtime login/config variables. Looper adds the provider binding, agent settings, MCP connection and gate-run values needed by that child. Database backups have a separate environment that also admits libpq and Docker variables. lark-cli additionally receives `LARK_*`. Startup and doctor show a backup command's source and program, without its arguments. ([#241](https://github.com/foolzzz/looper/pull/241))

### Scheduler settings and timeout choices

- **Two system settings.** Settings → Scheduler and `GET`/`PUT /api/scheduler-settings` expose `min_interval_seconds` (built-in 300 seconds; a positive whole number) and `run_timeout_seconds` (built-in null, **no limit**; a configured limit is 1–2,592,000 seconds, up to 30 days). Responses include effective `value`, `source` (`setting`, `env`, `built-in`) and built-in values. A schedule with a gate uses `min(60, min_interval_seconds)` for its minimum gap. Saving a minimum applies to later schedule validation; already saved schedules are not revalidated. ([#237](https://github.com/foolzzz/looper/pull/237))
- **Three per-schedule states.** API and Manager `looper_schedules` accept `run_timeout_seconds: "default"` to inherit, a positive integer for an explicit limit, or null for no limit. New schedules inherit when the field is omitted. An update that omits it preserves the choice. Views return the choice plus `run_timeout_effective_seconds`; the editor and detail view show the distinction. Migration preserves every existing schedule's number or explicit no limit. ([#237](https://github.com/foolzzz/looper/pull/237))
- **Each run records its starting timeout.** `schedule_runs.run_timeout_seconds` is the value the scheduler enforces. Changing the schedule or default affects later runs only. A gate receives that value in `LOOPER_SCHEDULE_RUN_TIMEOUT_SECONDS`, empty for no limit. ([#237](https://github.com/foolzzz/looper/pull/237))
- **Manager and configuration transfer.** `looper_settings` reads the settings and has a `scheduler` action that requires user confirmation before writing. This also works through Telegram and Lark via the Manager. Export/import includes stored `settings.scheduler` values and each schedule's timeout choice. There is no new scheduler CLI command. ([#237](https://github.com/foolzzz/looper/pull/237))

### Claude Code session separation

Every Claude Code launch sets `crossSessionInbound: "refuse"` and denies `ListAgents`. Runs without agent teams also deny `SendMessage`, including every Planner and consult. Team runs keep `SendMessage` for their teammates. The run record's `prompt_layers.isolation` becomes `personal-config-off/v3`. This applies to launches from the dashboard, Telegram, Lark and CLI without an activation switch. Codex, Grok and OMP get no corresponding launch change. ([#238](https://github.com/foolzzz/looper/pull/238))

### Obsidian knowledge vault

- **Local notes, available on demand.** A task's Planner, Workers and Reviewers get the same Looper MCP tools on Claude Code, Codex, Grok and OMP: `looper_vault_search` searches Markdown paths and text, `looper_vault_read` returns up to 64 KiB of text and the whole file's sha256, and `looper_vault_write` creates or replaces a Markdown note. Search skips hidden names, symbolic links and files over 512 KiB, and stops at 10,000 files, 32 MiB or five seconds, reporting `truncated`. Configure the server's vault in Settings → Knowledge vault, then opt in each project. An empty writable-folder list makes it read only. ([#239](https://github.com/foolzzz/looper/pull/239))
- **Writes stay in configured folders.** The write tool refuses paths outside them and walks the saved real path from the filesystem root without following symbolic links, including links swapped in during the walk. Writes allow 64 KiB per note and 256 KiB per run. Updating a note requires its `expected_sha256` from a read; use null for a new note. A conflict requires reading again. A per-vault lock covers the atomic replacement and git commit. In a git vault, each changed note gets one commit of that literal path only, leaving other staged changes alone; git uses the vault's author and hooks, disables commit signing, retries an index lock up to three times and ends its process group on a 30-second timeout. Task activity records the path, reason and commit, or a fixed uncommitted status without git output. Unchanged content creates no commit; a non-git vault or a failed commit leaves the file written without a commit.
- **The Planner closes out knowledge when the task ends.** After a completed task's lessons, or when a task fails, the Planner gets at most one closeout turn per Planner instance, with up to 16,000 characters of the vault's configured rules file and the task journal. It is asked to search before adding, read before changing and keep only what later work should know, or write nothing. Closeout requires an enabled, configured vault with a writable folder and a nonempty journal; it is skipped at the task's spend cap. Activity records `Vault closeout`; failure adds a warning without changing the task result.
- **Configuration and entry points.** `GET`/`PUT /api/knowledge-vault` reads or saves the local setting; the Manager's `looper_settings` action `knowledge_vault` changes it with user confirmation, including through Telegram or Lark. That settings action is listed in every installation, even with the vault off. The project's switch is dashboard-only. The Manager has no vault search, read or write tools yet. There is no new vault CLI command. Configuration export omits the machine-local vault setting; the project's on/off choice goes with the project.

## Default and behavior changes

1. **No implicit database on startup.** Commands needing a database refuse when no source configures one. `looper config init-ops` is the explicit bootstrap: if nothing names a database, it writes the former default `postgresql://localhost:5432/loopx` and asks you to check it. Inspect that file before starting; do not assume it found the existing service's database.
2. **`.env` stops supplying general server variables now.** Only the legacy deployment settings listed above are read, into memory, for this release. Other keys are ignored and named in warnings. Move channel secrets to Settings or the server environment; configure agent variables in agent settings. The old deployment variables, including runtime-root variables, log deprecation warnings and are due to stop working next release.
3. **An agent's implicit environment changes immediately.** Variables outside the allowlist, such as `AWS_PROFILE`, `NODE_OPTIONS` or `RUST_LOG`, no longer reach agents, gates or probes just because the server has them. Give an agent the additional variables it needs in its settings. Provider bindings and supported runtime logins remain supported. Probes and gates have no per-agent environment hook.
4. **Reinstalling the service changes its captured environment.** It no longer copies all `LOOPER_*`, `LOOPX_*`, `ANTHROPIC_*` and `LARK_*` variables. The fixed list includes PATH, timezone/locale, proxies/certificates, runtime directories/logins and the Telegram bot token; `--env NAME` adds a server variable explicitly. This does not automatically pass that variable to agents: their allowlist and settings still apply.
5. **Scheduler compatibility is separate from the ops file.** `LOOPER_SCHEDULE_MIN_INTERVAL_SECONDS` (or its `LOOPX_*` alias) is read from the **server environment, not `.env`**, for one release when no minimum is saved. A saved minimum wins. Save it in Settings → Scheduler before reinstalling a service that used to capture it. Clearing the saved minimum can expose the legacy variable again; remove the variable to return reliably to 300 seconds.
6. **New schedules inherit; old schedules keep their choice.** The built-in default timeout is no limit. Setting a system timeout does not change existing schedules that explicitly have a number or no limit; select Use the default on each one that should follow it. API clients must accept `"default"` as well as integer/null, and use `run_timeout_effective_seconds` when they need the resolved value. A running run is unaffected by later edits.
7. **Peer messages and tools change on Claude Code.** Incoming messages from other sessions are refused. `ListAgents` is unavailable, and `SendMessage` is unavailable without teams. Workflows depending on those tools must be adjusted; this is automatic on the next launch.
8. **The knowledge vault is off by default.** With it off or unconfigured, task agents have no vault tools, their prompts stay as before, and no vault closeout runs. Configuring the system vault alone does not enable any project. The Manager's settings tool gains the `knowledge_vault` action in every installation.

## Upgrading from v2.11.0

1. Re-run `install.sh` to install the release wheel.
2. In the **same environment and checkout that supplied the existing service's settings**, run `looper config init-ops`. Pass the existing `--runtime-root` if it is non-default, and `--config` if the file should live elsewhere. An existing service unit's environment is not automatically imported into your shell. Check that the generated file identifies the right database, public URL, backup and notes root; preserve a custom host/port in the file or explicit service flags. `init-ops` reports sources without printing values and refuses an existing file: edit that file instead of rerunning it.
3. Move non-deployment `.env` values to their supported Settings fields or server environment. Set extra agent variables in agent settings. Save any legacy scheduler minimum in Settings → Scheduler **before reinstalling**; it does not go in `server.toml`.
4. Remove deprecated deployment variables from the shell profile, environment and `.env`. Run **`looper service install` again**, with the same location flags and any required `--env NAME` additions. This replaces the old unit and starts the service; `service restart` alone does not rewrite the unit. Foreground users start `looper serve` with the same location flags instead.
5. Run doctor and the read-only checks above. On the first schema-changing start, Looper backs up the database before migrating. Check existing schedules' timeout choices and a newly created schedule's inherited default.

```bash
curl -fsSL https://raw.githubusercontent.com/foolzzz/looper/main/install.sh | bash
looper --version   # looper 2.12.0
looper config init-ops
# Check the private ops file; move other .env values and save a legacy
# scheduler minimum in Settings. Remove the deprecated deployment variables.
looper service install
looper doctor
looper service status
```

**If you do nothing this release:** a server with its database and other deployment settings in the old environment or `.env` can still start, with deprecation warnings. An old service unit remains usable until reinstalled, but still carries its old captured environment. The compatibility loader does not create an ops file for you. An installation that relied only on the implicit database URL now refuses startup. Non-deployment `.env` keys are already ignored and child environments are already filtered, so channels or tools depending on them can stop working now. A scheduler minimum set only in `.env` is ignored; without a saved value or server environment variable the minimum is 300 seconds. Complete the migration before the next release removes the compatibility inputs.

## Optional Capability Activation & Use

### Scheduler settings

**Activation:** Open Settings → Scheduler to save a minimum interval or a default run timeout. On a schedule, choose Use the default, Set a limit, or No limit. A new schedule follows the default; existing schedules retain their prior choice until edited. No limit is the built-in default. The Manager can make these changes, with confirmation for system settings.

**Validation:** Read the endpoint below to check effective values and sources. Open a schedule and verify its chosen and effective timeout; after a run starts, its recorded timeout must stay the same when you change the default.

**Disable / rollback:** Use the built-in setting to clear a system override (API null). Remove the deprecated minimum-interval environment variable if it should not take over. Choose No limit (API null) on a schedule to stop inheriting a system timeout for future runs. These edits do not alter a run already in progress.

**Authority boundary:** These are system-wide scheduler limits and per-schedule choices. Dashboard/API writes require operator authentication; the Manager asks for confirmation before a system-setting write. A lower minimum permits more frequent future schedule saves; it does not revalidate or rewrite existing rules. No limit removes the scheduler's run timeout, not other role or runtime limits.

**Docs:** [Schedules and system settings](https://github.com/foolzzz/looper/blob/main/docs/architecture/agent-system.md#schedules-tasks-on-a-time-rule).

```bash
curl -fsS -H "Authorization: Bearer $(cat ~/.looper/operator-token)" \
  http://127.0.0.1:8767/api/scheduler-settings | python3 -m json.tool
```

### Knowledge vault

**Activation:** In Settings → Knowledge vault, set Vault folder to an existing absolute server path, Writable folders to existing relative directories (comma-separated; empty means read only), and the optional Rules file to a relative file inside the vault. Keep personal-note folders out of the writable list. Save, check the git status and any problem, then select On in the project's Knowledge vault and save its settings. Projects start Off; both settings are needed. Use a git repository for a commit per write.

**Validation:** Read the endpoint below and check `configured`, `writable`, `rules_file`, `git` and `problem`. On a disposable vault and project, have a task search and read a note, then write only within a writable folder using its sha256. Check the note's commit and task activity, a stale-sha256 conflict, and a refusal outside writable folders. At task end, check `Vault closeout` or its warning/skip reason and that the configured rules were followed. An empty writable list should expose only search and read.

**Disable / rollback:** Select Off for the project, or Turn off in Settings → Knowledge vault (`PUT /api/knowledge-vault` with `{"path": null}`) for all projects. Every later call re-checks and refuses once disabled; a write already accepted can finish. Tool lists stay fixed for the run (each Planner turn, each Worker or Reviewer run), so newly enabling tools takes a new turn/run. Disabling does not undo notes or commits; review and revert the individual vault commits if needed.

**Authority boundary:** Operator authentication protects settings writes; the Manager asks for confirmation before changing the system setting. Once enabled, the Planner, Workers and Reviewers may write through the tool without another confirmation, within writable folders only. They can read notes throughout the vault, including personal notes; those reads enter model context and run records. Agents with a shell can still edit files directly. These tools provide no filesystem isolation. Each write checks sha256 and records its commit or uncommitted status in task activity. The Manager has no vault tools yet.

**Docs:** [Knowledge vault](https://github.com/foolzzz/looper/blob/main/docs/architecture/agent-system.md#the-knowledge-vault-the-operators-notes-read-and-written-through-looper) and [design RFC](https://github.com/foolzzz/looper/blob/main/docs/architecture/rfcs/obsidian-knowledge-v0.zh-CN.md).

```bash
curl -fsS -H "Authorization: Bearer $(cat ~/.looper/operator-token)" \
  http://127.0.0.1:8767/api/knowledge-vault | python3 -m json.tool
```

## Known limits

- **Session separation is not a sandbox.** Team runs retain `SendMessage` and can still address a known external session. The receiving session's own `crossSessionInbound` setting must refuse or hold those messages; Looper does not modify the operator's personal settings. Shell commands can still reach session sockets or other runtimes' sessions.
- **The environment filter is not filesystem isolation.** Agents run as the server's user and can still read files that user can read, including the ops file, operator token, `.env` and service unit. Preventing that needs a separate OS identity or sandbox and database authentication agents cannot use.
- **Vault access includes personal notes.** An enabled project's agents can read notes throughout the vault, including personal ones. Writable folders constrain the write tool; an agent with a shell can still edit files directly. Tool lists are fixed per Planner turn or Worker/Reviewer run, while every call re-checks the project and system setting. The Manager has no vault tools yet. A non-git vault or failed git commit can leave a written note without a commit; activity reports that state. The sha256 check detects a changed note before replacement, but an external editor can still overwrite a later Looper write.
- **Vault writes need read permission on every ancestor directory.** A write opens each directory from the filesystem root down to the vault. A directory that permits traversal but not reading makes the write fail, even when the vault itself is writable.
- Vault tools were not exercised in real mode on Codex, Grok or OMP. Concurrent writes from Obsidian itself and a vault on a network or other case-insensitive filesystem were not verified. Search is plain text without an index; note deletion and renaming are not supported.
- PR #238 did not verify teammate inheritance of the deny list, managed admin settings, or Claude Code versions other than 2.1.285. PR #241 did not verify real launchd/systemd installation, Linux, Codex OAuth under the filtered environment, or Claude Code authenticated only through its standalone OAuth-token variable. Its fixed allowlist requires explicit agent settings for additional tool variables.

### 新能力与行为变化

- **私有 ops 文件。** 默认 `~/.looper/ops/server.toml`，也可用 `--config` 指定。支持数据库地址、服务 host/port/public_url/log_level、备份程序与 argv 数组、operator notes 的绝对路径。文件及目录必须属于运行用户且不允许组和其他用户访问；`init-ops` 原子写入 0600 文件、创建 0700 目录，拒绝覆盖。未知配置、类型或值错误会拒绝启动；不做变量、`~` 或 include 展开。修改后重启。([#241](https://github.com/foolzzz/looper/pull/241))
- **配置优先级。** 显式参数 → 文件 → 旧环境变量（`LOOPER_*` 优先于 `LOOPX_*`）→ checkout 的 `.env` 同名旧设置 → 内置值。兼容项是数据库地址、公开地址、pg_dump、备份命令和 notes root（最后一项没有旧前缀别名），仅保留本版本并告警。runtime root 单独由 `--runtime-root`、已弃用的 runtime-root 环境变量、`~/.looper` 决定，不写进文件。`serve --host/--port/--verbose` 覆盖文件，否则默认 127.0.0.1、8767、info。
- **启动没有默认数据库地址。** 没有任何配置来源时拒绝启动。只有显式执行 `init-ops` 才会在无来源时写入旧默认 `postgresql://localhost:5432/loopx`，并提示检查；它不会自动读取已安装服务单元里的环境。
- **`.env` 的其他键立即失效。** 仅旧部署设置读到内存，其他键忽略并提示键名。渠道密钥移到 Settings 或服务端环境；agent 需要的额外变量配置到 agent settings。
- **服务单元需要重新安装。** 新单元携带绝对 `--config` 和 `--runtime-root`，不再携带数据库地址。只有显式传入 `--port`，或旧单元有端口且文件没有配置端口时，才写入该参数；否则 status/restart 从文件读端口。没有 ops 文件，或部署设置仍来自环境变量时拒绝安装；`--env` 不能携带部署设置。
- **子进程从允许列表开始。** agent、前置检查、探测及辅助进程只继承系统、语言时区、SSH/git、代理证书、运行时登录配置等指定变量，再补 provider binding、agent settings、MCP 或运行专属变量。备份另允许 libpq/Docker 变量，lark-cli 另接收 `LARK_*`。`AWS_PROFILE`、`NODE_OPTIONS`、`RUST_LOG` 等不再隐式继承；前置检查和探测没有 agent settings 的扩展入口。备份诊断只显示来源与程序，不显示参数。
- **服务环境也不再按前缀全部复制。** 安装时保留固定的 PATH、时区语言、代理证书、运行时目录和登录变量、Telegram bot token，以及显式 `--env NAME`。按报告补服务所需变量；这不意味着该变量会自动传给 agent，子进程仍受允许列表约束。
- **Settings → Scheduler。** 最小间隔内置 300 秒，可设正整数；有前置检查的任务使用 `min(60, 设置值)`。修改立即影响之后的保存校验，不重新检查已保存的规则。默认运行超时内置为**不限时**，设置数字时范围为 1 秒至 30 天。接口 `GET/PUT /api/scheduler-settings` 返回生效值、来源和内置值。([#237](https://github.com/foolzzz/looper/pull/237))
- **每个定时任务有三种超时选择。** `run_timeout_seconds` 为 `"default"` 表示继承、整数表示显式秒数、null 表示不限时；新建省略时继承，更新省略时保持原选择。接口另返回 `run_timeout_effective_seconds`。迁移保留已有任务的数字或不限时，不会自动改为继承。每次运行保存启动时的超时，之后修改不影响它；前置检查收到的 `LOOPER_SCHEDULE_RUN_TIMEOUT_SECONDS` 也是该值，不限时为空。
- **旧最小间隔变量只读服务端环境，不读 `.env`。** `LOOPER_SCHEDULE_MIN_INTERVAL_SECONDS` 及旧前缀别名仅在未保存系统值时兼容一版并告警，保存值优先。重新安装服务前先把旧值保存到 Scheduler。清除保存值会重新使用旧变量；要回到内置 300 秒，还需移除变量。
- **Manager 与配置迁移。** `looper_schedules` 接受相同三种超时值；`looper_settings` 的 `scheduler` 操作先要求用户确认。飞书和 Telegram 通过 Manager 使用它们。导出/导入携带已保存的 `settings.scheduler` 和任务的超时选择。CLI 没有新增调度器命令。
- **Claude Code 跨会话限制自动生效。** 每次启动设置 `crossSessionInbound: "refuse"` 并禁用 `ListAgents`；未启用 agent teams 时另禁用 `SendMessage`，包括所有 Planner 和 consult。团队运行保留内部消息工具。运行记录的隔离标识为 `personal-config-off/v3`。Dashboard、飞书、Telegram、CLI 不需要开关；Codex、Grok、OMP 没有对应参数变更。([#238](https://github.com/foolzzz/looper/pull/238))
- **Obsidian 知识库按需供任务使用。** Planner、Worker、Reviewer 在 Claude Code、Codex、Grok、OMP 上使用相同的 Looper MCP 工具：`looper_vault_search` 搜索 Markdown 路径和正文，跳过隐藏名称、符号链接和超过 512 KiB 的文件，达到 10,000 个文件、32 MiB 或 5 秒时停止并返回 `truncated`；`looper_vault_read` 返回最多 64 KiB 文本及完整文件的 sha256；`looper_vault_write` 新建或替换 Markdown 笔记。Settings → Knowledge vault 配好路径、可写目录和可选规则文件后，还需把项目的 Knowledge vault 选为 On。可写目录为空时只读。([#239](https://github.com/foolzzz/looper/pull/239))
- **知识库写入带冲突检查和提交记录。** 写工具只允许可写目录内的路径，从文件系统根目录逐级打开已保存的真实路径，拒绝符号链接，包括遍历过程中被换入的链接。每篇最多 64 KiB，每次运行最多写 256 KiB。修改已有笔记需传读取时的 `expected_sha256`，新笔记传 null，冲突后重新读。每个知识库的锁覆盖原子替换与 git 提交；每次实际写入只提交该笔记的字面路径，不带走其他暂存改动。git 使用知识库自己的作者和 hook、关闭提交签名，索引锁最多重试三次，30 秒超时后结束整个进程组。任务动态记录路径、理由和提交，或固定的未提交状态，不记录 git 输出。内容不变不提交；非 git 或提交失败时文件仍已写入。
- **任务结束由 Planner 按知识库规则收尾。** 完成任务的经验沉淀之后，或任务失败时，每个 Planner 实例最多增加一轮，收到配置的规则文件（最多 16,000 字符）与任务日志，被要求先搜索、再读取、只保留后续工作有用的内容，也可不写。须已启用、配置有效、有可写目录且任务日志非空；达到花费上限时跳过。动态记录 `Vault closeout`，失败只告警，不改变任务结果。
- **知识库默认关闭。** 未配置有效系统知识库，或项目保持 Off 时，任务 agent 的工具、提示词和收尾行为均保持原样；仅配置系统路径不会自动启用项目。`GET/PUT /api/knowledge-vault` 管理本机设置；所有安装的 Manager 都会新增 `looper_settings` 的 `knowledge_vault` 操作，即使知识库关闭也会列出，修改前要求用户确认，飞书和 Telegram 可通过 Manager 使用。项目开关仅在 Dashboard 配置。Manager 尚无知识库搜索、读写工具，CLI 无新增命令。配置导出不带本机知识库设置，项目开关随项目导出。

### 从 v2.11.0 升级

1. 重跑 `install.sh` 安装新 wheel。
2. 在提供原服务配置的**同一环境和 checkout**运行 `looper config init-ops`；非默认 runtime root 和配置位置要传对应参数。核对数据库、公开地址、备份、notes root 和自定义 host/port。已有文件时直接编辑，不会覆盖。没有配置来源时写的是旧默认数据库，必须检查。
3. 把 `.env` 里非部署设置移到支持的 Settings 或服务端环境，额外 agent 变量移到 agent settings；重新安装服务前先在 Settings → Scheduler 保存旧最小间隔，它不属于 ops 文件。
4. 移除 shell profile、当前环境和 `.env` 中的旧部署变量，然后**重跑 `looper service install`**，传入相同位置参数和必要的 `--env NAME`。这会重写单元并启动服务，仅 restart 不会迁移单元。前台用户使用相同参数执行 `looper serve`。
5. 运行 doctor、服务状态及上述只读检查。第一次涉及 schema 变化的启动会先备份再迁移。已有定时任务应保留原超时，新建任务默认继承。

**本版本什么也不做会怎样：**旧环境变量或 `.env` 中的部署设置仍能启动服务，但会告警；旧服务单元在重装前仍可使用，也仍携带旧环境。不会自动生成 ops 文件。仅依赖隐式数据库地址的安装会拒绝启动；其他 `.env` 键已经忽略，子进程环境已经过滤，依赖它们的渠道和工具现在就可能失效。最小间隔如果只在 `.env` 中设置，本版本不再读取；没有保存值或服务端变量时使用 300 秒。下一版移除兼容输入前应完成迁移。

### 可选能力启用与使用

#### Scheduler settings

**启用：**在 Settings → Scheduler 保存最小间隔或默认运行超时；每个定时任务选择继承、指定秒数或不限时。新任务默认继承，旧任务保留原选择，内置默认超时为不限时。Manager 修改系统设置前要求用户确认。

**验证：**通过下方接口读回生效值和来源，在定时任务页核对选择值与生效超时。运行启动后再修改默认值，该次运行记录的超时应保持不变。

**停用 / 回退：**选择恢复内置值（API 传 null）清除系统覆盖；同时移除旧最小间隔变量，避免重新接管。定时任务选不限时（API null）即可让后续运行不再继承系统超时；已启动的运行不受影响。

**权限边界：**Dashboard/API 写入需要操作者鉴权，Manager 写系统设置需要确认。降低最小间隔只放宽之后的保存校验，不改已有规则。不限时只移除调度器运行超时，不取消角色或运行时的其他限制。

**文档：**[定时任务与系统设置](https://github.com/foolzzz/looper/blob/main/docs/architecture/agent-system.md#schedules-tasks-on-a-time-rule)。

curl -fsS -H "Authorization: Bearer $(cat ~/.looper/operator-token)" \

```

#### Knowledge vault

**启用：**在 Settings → Knowledge vault 填写 Vault folder（服务端已存在目录的绝对路径）、Writable folders（库内已存在的相对目录，逗号分隔，留空只读）和可选 Rules file（库内相对文件路径）。个人笔记目录不要加入可写列表。保存后检查 git 状态与问题提示，再把项目的 Knowledge vault 从默认 Off 选为 On 并保存；两处配置缺一不可。需要每次写入生成提交时，使用 git 仓库。

**验证：**通过下方接口检查 `configured`、`writable`、`rules_file`、`git` 和 `problem`。在一次性知识库及项目上让任务搜索、读取笔记，传入 sha256 在可写目录内写入，核对该笔记的提交与任务动态；验证旧 sha256 冲突及可写目录外写入被拒。任务结束检查 `Vault closeout` 或告警/跳过原因，以及是否遵循配置的规则。可写目录为空时应只有搜索和读取工具。

**停用 / 回退：**项目选择 Off，或在 Settings → Knowledge vault 选择 Turn off（`PUT /api/knowledge-vault` 传 `{"path": null}`）停用全部项目。后续每次调用重新检查并拒绝，已接受的写入仍可能完成。工具列表在每个 Planner 回合、Worker/Reviewer 运行开始时固定，新启用需等下一回合/运行。停用不撤销笔记或提交；需要撤销时检查并逐个回退知识库提交。

**权限边界：**设置写入需要操作者鉴权，Manager 修改系统设置先确认。启用后 Planner、Worker、Reviewer 通过工具在可写目录写入无需逐次确认。agent 能读取全库笔记，包括个人笔记，读取内容会进入模型上下文与运行记录。有 shell 的 agent 仍能直接修改文件，工具不提供文件系统隔离。每次写入检查 sha256，在任务动态记录提交或未提交状态；Manager 尚无知识库工具。

**文档：**[知识库](https://github.com/foolzzz/looper/blob/main/docs/architecture/agent-system.md#the-knowledge-vault-the-operators-notes-read-and-written-through-looper)与[设计 RFC](https://github.com/foolzzz/looper/blob/main/docs/architecture/rfcs/obsidian-knowledge-v0.zh-CN.md)。

```

# Looper v2.14.82

This is the patch release v2.14.82, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.81: a native chat binding can admit extra senders in that chat only ([#1090](https://github.com/foolzzz/looper/pull/1090)).

## Release Decision

**Who should upgrade:** Operators who bind a group chat to a scenario Manager and need people who are not on the bot's sender allowlist (for example merge request authors) to reach that Manager in that group. Everyone else can stay.

**What this release solves:** The sender allowlist is per bot, so adding someone there also lets them reach the bot's owner Manager in a direct message or any other chat. [#1090](https://github.com/foolzzz/looper/pull/1090) adds `allowed_senders` to a chat binding: those senders are admitted in that one chat and refused everywhere else.

**Breaking changes:** No. No setting, operation or field is removed. A binding without extra senders behaves as before. The database gains one column with a default (additive).

**How to verify:** Check the installed version. In Settings → Managers, a bound chat shows an "Extra senders in this chat" editor; with none set, admission is unchanged.

**Contributors:** Maintainer @foolzzz authored [#1090](https://github.com/foolzzz/looper/pull/1090); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.82
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.81 upgrades directly. This release has an additive schema change: the first start adds the column `allowed_senders` (`TEXT[]`, default empty, at most 100 entries) to `manager_chat_bindings` and records the upgrade `chat_binding_senders`. Existing bindings get an empty list.

## Behavior changes

- **Extra senders per binding** (`looper/db/chat_bindings.py`, `looper/db/connection.py`, `looper/db/schema.sql`). `manager_chat_bindings.allowed_senders` holds Lark open_ids or Telegram user ids, at most 100, checked against the bot type's id format (`allowlist.sender_ids`); an invalid list is refused as `allowed_senders: …`.
- **Admission** (`looper/agents/channels/allowlist.py`, `chat_routing.py`, `lark.py`, `lark_bot.py`, `telegram.py`). A message in exactly that `(channel_id, chat_id)` is admitted when its sender is on the bot's allowlist or on that binding's extra senders. Anywhere else (a direct message, another chat) the extra senders are refused and recorded as refused senders, as today. The route decision is resolved once per message and serves both admission and delivery; the Lark bot transport's pre-filter uses the same decision. The route log line gains `sender_list=chat_binding` when the chat's list admitted the sender.
- **Moving a binding.** Moving a binding to another Manager without giving `allowed_senders` clears them, so a group cannot carry its extra senders to a Manager with more tools. Rebinding to the same Manager without the field keeps them; `[]` clears them. The routing-write log records the old and new sender counts, not the ids.
- **API and CLI.** `manager_chat_bindings.put` takes `allowed_senders`; `manager_chat_bindings.list` returns it on each binding, and `loopercli manager-chat-bindings` (generated from the API) follows.
- **Dashboard.** Settings → Managers shows each bound chat's extra sender count, an editor with "Save senders", and the note "Moving clears this chat's extra senders."
- **Documentation and tests.** `docs/architecture/agent-system.md` describes chat bindings and admission; a long-horizon plan note is updated. Tests cover the store, routing, delivery (PostgreSQL), the API, and the dashboard component and browser flows.
- **Unchanged:** the bot-level sender allowlist, bindings without extra senders, refused-sender recording, and the instructions and prompt a Manager receives.
- **Model-visible changes:** The `manager_chat_bindings.put` and `list` operation schemas (shown to models that call the API or CLI) gain the `allowed_senders` field and its description. The instructions and prompt a Manager receives are unchanged; in a bound chat the Manager can now receive messages from senders it would not receive from before.

本版本是 patch release v2.14.82（热修线，每个合并的改动立即发布）。自 v2.14.81 以来只合并了一项改动：聊天绑定可以只在该聊天内放行额外发送者（[#1090](https://github.com/foolzzz/looper/pull/1090)）。

### 升级决策

**谁需要升级：**把群聊绑定到场景 Manager、并需要让不在机器人发送者白名单上的人（例如合并请求的作者）在该群内访问该 Manager 的运维人员。其他人可不升级。

**解决了什么：**发送者白名单按机器人生效，把人加进去也会让他们在私聊或其他聊天里访问该机器人的所有者 Manager。[#1090](https://github.com/foolzzz/looper/pull/1090) 给聊天绑定增加 `allowed_senders`：这些发送者只在该聊天内被放行，其他地方一律拒绝。

**是否有破坏性变更：**否。没有移除设置、操作或字段。没有额外发送者的绑定行为不变。数据库新增一个带默认值的列（增量变更）。

**如何验证：**核对版本为 2.14.82。在设置 → Managers 中，已绑定的聊天显示“Extra senders in this chat”编辑器；未设置时放行行为不变。

**贡献者：**维护者 @foolzzz 提交 [#1090](https://github.com/foolzzz/looper/pull/1090)；本版本无社区贡献。

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.81 上的安装可直接升级。本版本有增量的数据库结构变更：首次启动时给 `manager_chat_bindings` 添加列 `allowed_senders`（`TEXT[]`，默认为空，最多 100 项），并记录升级 `chat_binding_senders`。已有绑定得到空列表。

### 行为变化与入口

- **每个绑定的额外发送者**（`looper/db/chat_bindings.py`、`looper/db/connection.py`、`looper/db/schema.sql`）。`manager_chat_bindings.allowed_senders` 保存 Lark open_id 或 Telegram 用户 ID，最多 100 个，按机器人类型的 ID 格式校验（`allowlist.sender_ids`）；无效列表以 `allowed_senders: …` 拒绝。
- **放行**（`looper/agents/channels/allowlist.py`、`chat_routing.py`、`lark.py`、`lark_bot.py`、`telegram.py`）。恰好在该 `(channel_id, chat_id)` 内的消息，发送者在机器人白名单或该绑定的额外发送者中即被放行。其他地方（私聊、其他聊天）额外发送者照旧被拒绝并记为被拒发送者。每条消息只解析一次路由决定，同时用于放行和投递；Lark 机器人传输层的预过滤使用同一决定。当由该聊天的列表放行时，路由日志行增加 `sender_list=chat_binding`。
- **移动绑定。**把绑定移到另一个 Manager 且未给出 `allowed_senders` 时会清空它们，避免群把额外发送者带给工具更多的 Manager。不带该字段重新绑定到同一 Manager 则保留；`[]` 清空。路由写入日志记录前后的发送者数量，不记录 ID。
- **API 与 CLI。**`manager_chat_bindings.put` 接受 `allowed_senders`；`manager_chat_bindings.list` 在每个绑定上返回它，由 API 生成的 `loopercli manager-chat-bindings` 随之更新。
- **Dashboard。**设置 → Managers 显示每个已绑定聊天的额外发送者数量、带“Save senders”的编辑器，以及提示“Moving clears this chat's extra senders.”。
- **文档与测试。**`docs/architecture/agent-system.md` 描述聊天绑定与放行；一份长程计划笔记也已更新。测试覆盖存储、路由、投递（PostgreSQL）、API，以及 Dashboard 组件和浏览器流程。
- **不变：**机器人级发送者白名单、没有额外发送者的绑定、被拒发送者的记录，以及 Manager 收到的指令和提示。
- **面向模型的变化：**调用 API 或 CLI 的模型看到的 `manager_chat_bindings.put` 和 `list` 操作模式增加了 `allowed_senders` 字段及说明。Manager 收到的指令和提示不变；在已绑定的聊天中，Manager 现在可能收到以前不会收到的发送者的消息。

# Looper v2.13.117

## Release Decision

**Who should upgrade:** Anyone who disables Lark bots through the channel bot settings, or who stops a Telegram channel and relies on message reactions being cleaned up in order. Others do not need it.

**What this release solves:** [#627](https://github.com/foolzzz/looper/pull/627) stops an explicit disable of a Lark bot from skipping admission when the same save also changes its allowed sender set or drops its app binding, treats the sender list as a set when deciding whether it changed, and makes a Telegram adapter stop its reactions worker only after the application has drained received updates.

**Breaking changes:** No. No route, configuration, request field or stored data format changed.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#627](https://github.com/foolzzz/looper/pull/627); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.117
```

## Behavior changes

- **Lark disable with changed senders:** in `looper/agents/channels/bot_api.py`, `update_bot` skips the same-bot admission check for an explicit `enabled: false` save only when the identity (token, profile, app id, token env, domain) is unchanged and, for a Lark bot saved with a `config`, the set of `allowed_open_ids` and the `allowlist_app_id` are also unchanged against the row read under the bots lock. A disable that changes the sender set or drops the app binding is now admitted like any other Lark save. A plain disable, or a disable that leaves both unchanged, still works while authentication is broken.
- **Sender order and duplicates:** the same-bot check compares `allowed_open_ids` as sets. In `looper/agents/channels/lark_settings.py`, `bound_config` likewise compares the new and previous sender lists as sets, so a reordered list keeps the stored `allowlist_app_id` instead of being treated as changed.
- **Telegram stop order:** in `looper/agents/channels/telegram.py`, the adapter stops the reactions worker after the updater and application have stopped, because `Application.stop` drains received updates whose handlers can still add reactions. Shutdown of the application and of the HTTP requests follows as before.
- **Model-visible changes:** none. No tool declaration, prompt, route or text sent to Workers changed.
- **Tests:** new tests in `tests/test_channel_bots_api_db.py` and `tests/test_telegram_lifecycle.py` cover the disable and sender-set cases and the stop order. [#627](https://github.com/foolzzz/looper/pull/627) reports added lines: tests 238, production 11 (fixtures excluded).

## Upgrade and rollback

Re-run `install.sh` once v2.13.117 is published. No data migration and no configuration change. Rolling back to v2.13.116 restores the old behavior, where a disable could skip admission despite a changed sender set and the reactions worker stopped before the application.

### 升级决策

**谁需要升级：**通过渠道 bot 设置停用 Lark bot 的用户，或停止 Telegram 渠道并依赖消息 reaction 有序清理的用户。其他人无需升级。

**解决了什么：**[#627](https://github.com/foolzzz/looper/pull/627) 修复了显式停用 Lark bot 时，若同一次保存同时改动了允许的发送者集合或去掉了应用绑定，会跳过准入检查的问题；比较发送者列表时按集合处理；Telegram 适配器改为在应用排空已接收的更新之后才停止 reaction 工作线程。

**是否有破坏性变更：**否。路由、配置、请求字段和存储数据格式均未改变。

**如何验证：**运行 `looper --version` 核对版本为 2.13.117。

**贡献者：**维护者 @foolzzz 提交 [#627](https://github.com/foolzzz/looper/pull/627)；本次 patch release 无社区贡献。

```bash
looper --version   # looper 2.13.117
```

### 行为变化与入口

- **改动发送者的 Lark 停用：**`looper/agents/channels/bot_api.py` 中，`update_bot` 仅在身份（token、profile、app id、token env、domain）未变、且对带 `config` 保存的 Lark bot 而言 `allowed_open_ids` 集合与 `allowlist_app_id` 相对加锁读取的当前行也未变时，才让显式 `enabled: false` 保存跳过同 bot 准入检查。改动发送者集合或去掉应用绑定的停用，现在与其他 Lark 保存一样需要准入。单纯停用，或两者均未变的停用，在认证损坏时仍可执行。
- **发送者顺序与重复：**同 bot 检查按集合比较 `allowed_open_ids`。`looper/agents/channels/lark_settings.py` 的 `bound_config` 也按集合比较新旧发送者列表，因此仅调整顺序时保留已存的 `allowlist_app_id`，不再视为变更。
- **Telegram 停止顺序：**`looper/agents/channels/telegram.py` 中，适配器在 updater 与应用停止之后才停止 reaction 工作线程，因为 `Application.stop` 会排空已接收的更新，其处理器仍可能添加 reaction。应用与 HTTP 请求的关闭顺序不变。
- **面向模型的变化：**无。tool 声明、提示词、路由和发给 Worker 的文本均未改变。
- **测试：**`tests/test_channel_bots_api_db.py` 与 `tests/test_telegram_lifecycle.py` 新增测试，覆盖停用与发送者集合的情形及停止顺序。[#627](https://github.com/foolzzz/looper/pull/627) 报告新增行数：测试 238、生产代码 11（不含夹具）。

### 升级与回退

v2.13.117 发布后重跑 `install.sh`。无需迁移数据，无需改配置。回退到 v2.13.116 会恢复旧行为：停用可能在发送者集合改变时跳过准入，且 reaction 工作线程先于应用停止。

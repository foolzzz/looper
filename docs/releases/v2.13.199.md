# Looper v2.13.199

## Release Decision

**Who should upgrade:** Operators who set `[runtimes] pi = "runner"` in the ops file, where a Worker runs on a runner session. Everyone else sees no difference: with the default `pi = "cli"` Workers keep their own processes. It is a hotfix that ships the change merged since v2.13.198.

**What this release solves:** [#844](https://github.com/foolzzz/looper/pull/844) fixes issue #840. When a hosted Worker run is killed by the Planner or stopped with the Worker pool, the steers it accepted but the runtime dropped now reach the Planner. A hosted launch that fails to start now ends its handle, so the runner session it took is released.

**Breaking changes:** No. No command, database schema or setting changed.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#844](https://github.com/foolzzz/looper/pull/844); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.199
```

## Behavior changes

- **Kill reply (`looper/agents/tiers/worker.py`, `_deliver_kill`):** the pool keeps a reference to the run's handle before it kills the Worker, because the kill releases the active entry. When the kill succeeded and the handle reports dropped steers (`dropped_input()`), the `KILL_WORK_RESULT` payload carries them as `missed_input` next to `killed`. When nothing was dropped the payload is unchanged (`{"killed": ...}`).
- **Pool stop (`looper/agents/tiers/worker.py`, run task):** a pool stop sends no kill reply. If a run is cancelled while the pool is stopping, and its handle has dropped steers, the run now ends with status `stopped` and the summary "The worker pool stopped this run", so the dropped steers travel the normal result path. Otherwise the cancellation is re-raised as before (a cancel while the pool is still running, or a run with no handle or no dropped steers).
- **Failed hosted launch (`looper/agents/tiers/worker.py`):** when `handle.launch()` raises `RunStartError` for a hosted run, the handle is ended before the step fails with its existing "Cannot start ..." error, so the session taken for the launch is released. Process-backed runs are unchanged.
- **Planner (`looper/agents/tiers/planner.py`):** after a kill acknowledgement, a `missed_input` list in the reply is appended, strings only, to the step's `missed_messages`. Those are the messages the Planner already includes in its stop decision.
- **Scope:** 3 files; the description reports tests 83 and production 17 added lines, fixtures excluded.
- **Model-visible changes:** Under `pi = "runner"` (or any hosted runtime) only: after the Planner kills a Worker, the Planner's stop decision can now list the steers the Worker never received in `missed_messages`, as it already does for other dropped steers. A Worker's prompt and tools are unchanged. With the default `pi = "cli"`: none.

### 升级决策

**谁需要升级：**在 ops 文件中设置了 `[runtimes] pi = "runner"`、Worker 运行在 runner 会话上的运维者；其他用户无差别，默认 `pi = "cli"` 下 Worker 仍用自己的进程。本版本是随合并即发布的 hotfix，包含 v2.13.198 之后合并的改动。

**解决了什么：**[#844](https://github.com/foolzzz/looper/pull/844) 修复 issue #840。托管的 Worker 运行被 Planner 终止或随 Worker 池停止时，它已接受但被运行时丢弃的 steer 现在会送达 Planner。托管启动失败时现在会结束其句柄，从而释放所占用的 runner 会话。

**是否有破坏性变更：**无。命令、数据库 schema 和设置均未改变。

**如何验证：**运行 `looper --version` 核对版本为 2.13.199。

**贡献者：**维护者 @foolzzz 提交 [#844](https://github.com/foolzzz/looper/pull/844)；本次 patch release 无社区贡献。

```bash
looper --version   # looper 2.13.199
```

### 行为变化与入口

- **终止回复（`looper/agents/tiers/worker.py`，`_deliver_kill`）：**终止会释放活动条目，所以池在终止 Worker 之前先保留该运行的句柄。终止成功且句柄报告了被丢弃的 steer（`dropped_input()`）时，`KILL_WORK_RESULT` 的载荷在 `killed` 之外带 `missed_input`。没有丢弃时载荷不变（`{"killed": ...}`）。
- **池停止（`looper/agents/tiers/worker.py`，运行任务）：**池停止不发送终止回复。若运行在池停止期间被取消，且句柄有被丢弃的 steer，该运行现在以状态 `stopped` 结束，摘要为 "The worker pool stopped this run"，被丢弃的 steer 经正常结果路径传递。否则照旧重新抛出取消（池仍在运行时的取消、没有句柄或没有被丢弃 steer 的运行）。
- **托管启动失败（`looper/agents/tiers/worker.py`）：**托管运行的 `handle.launch()` 抛出 `RunStartError` 时，先结束句柄，再以原有的 "Cannot start ..." 错误使步骤失败，因此启动所占的会话被释放。进程型运行不变。
- **Planner（`looper/agents/tiers/planner.py`）：**收到终止确认后，回复中的 `missed_input` 列表（仅字符串）会追加到该步骤的 `missed_messages`，Planner 的停止决策本来就会包含这些消息。
- **范围：**3 个文件；描述写的是测试新增 83 行、生产代码 17 行，不含 fixtures。
- **面向模型的变化：**仅在 `pi = "runner"`（或任何托管运行时）下：Planner 终止 Worker 后，其停止决策的 `missed_messages` 中可以列出 Worker 从未收到的 steer，与其他已丢弃 steer 的处理方式相同。Worker 的提示词和工具不变。默认 `pi = "cli"` 下无变化。

# Looper v2.14.181

This is the patch release v2.14.181, a hotfix line in which each merged change ships at once. It documents one change: [#1339](https://github.com/foolzzz/looper/pull/1339) (an upgrade no longer fails when the old service's pid was reused by another user's process).

## Release Decision

**Who should upgrade:** Operators who upgrade a Looper service with the service command on a busy or multi-user machine, where the old service's pid can be handed to another user's process right after the service stops.

**What this release solves:** [#1339](https://github.com/foolzzz/looper/pull/1339) fixes upgrades that failed with `[Errno 1] Operation not permitted` after the old service had stopped. The upgrade's "is the old service still running" probe now treats a pid it may not signal as "not our service", so the upgrade continues.

**Breaking changes:** No. API responses, the Telegram and Lark channel protocols, the dashboard and the CLI are unchanged, and there is no database change. The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.14.181
```

**Contributors:** Maintainer @foolzzz authored [#1339](https://github.com/foolzzz/looper/pull/1339); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.180 upgrades directly. There is no database change.

## Behavior changes

Read in the diff of [#1339](https://github.com/foolzzz/looper/pull/1339) (`looper/agents/service.py`, `tests/test_service.py`):

- **Upgrade probe** (`looper/agents/service.py`). `_pid_alive` sends signal 0 to the pid of the service process the upgrade started. It now returns false on `PermissionError` as well as `ProcessLookupError`: a pid that the same user may not signal belongs to another user's process, so the service we started has exited and its pid was reused. Before, the `PermissionError` escaped the upgrade and its recovery path, the upgrade reported failure after the stop, and the service came back only through the service manager's restart. Now an upgrade on a machine where the old pid gets reused continues. Any other error from the signal call still propagates.
- **Tests** (`tests/test_service.py`). A pid that raises `PermissionError` or `ProcessLookupError` is not alive; the test process's own pid is alive.
- **Model-visible changes:** No. No prompt, tool description or tool schema changed, and no HTTP API result changed.

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.180 上的安装可直接升级。没有数据库变更。

### 行为变化与入口

以下在 [#1339](https://github.com/foolzzz/looper/pull/1339) 的差异中可见（`looper/agents/service.py`、`tests/test_service.py`）：

- **升级探测**（`looper/agents/service.py`）。`_pid_alive` 向升级所启动的服务进程的 pid 发送信号 0。现在遇到 `PermissionError` 与 `ProcessLookupError` 一样返回 false：同一用户无权发信号的 pid 属于其他用户的进程，说明我们启动的服务已退出且 pid 被复用。此前 `PermissionError` 会逃出升级及其恢复路径，升级在停止服务后报告失败，服务只能靠服务管理器的重启恢复。现在 pid 被复用的机器上升级会继续。信号调用的其他错误仍然向上抛出。
- **测试**（`tests/test_service.py`）。抛出 `PermissionError` 或 `ProcessLookupError` 的 pid 视为不存活；测试进程自身的 pid 视为存活。
- **面向模型的变化：**无。提示词、工具描述和工具 schema 均未改变，也没有 HTTP API 结果改变。

# Looper v2.14.64

This is the patch release v2.14.64, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.63: a project directory change that moves enabled command schedules is now confirmed first ([#1053](https://github.com/foolzzz/looper/pull/1053)).

## Release Decision

**Who should upgrade:** Operators whose Manager (web chat, Telegram, Lark) or client tokens (`loopercli`, the project API) change a project's `work_dir` while command schedules run in that directory. Others need not upgrade.

**What this release solves:** A command schedule without its own `work_dir` runs in its project's directory. Changing the project's `work_dir` moved the next run of every such schedule to the new directory and nobody was asked. [#1053](https://github.com/foolzzz/looper/pull/1053) closes this for the Manager's `looper_projects` `update` and for a client token through `POST /api/v1/project_admin/update` or `POST /api/v1/ops/projects/update`: when the change affects command schedules that inherit the directory and will run again (enabled, or holding a queued run), the answer is `needs_confirmation` first.

**Breaking changes:** No. No API schema or configuration changes and there is no migration. A client token that changed such a directory now receives `needs_confirmation` first (see Behavior changes).

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#1053](https://github.com/foolzzz/looper/pull/1053); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.64
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.63 upgrades directly. This release adds no migration.

## Behavior changes

- **A directory change that moves schedules asks first.** The confirmation lists each affected schedule: name, state (enabled, or disabled with one queued run), exact command, and old → new directory; it also names other fields changed in the same call. If the new directory is empty it says the runs will then fail. Affected schedules are command schedules without their own `work_dir` that are enabled or hold a queued run (`directory_dependents`, `looper/db/schedules.py`).
- **The confirmed call is bound to what was shown.** It applies only if the project's directory and each listed schedule's configuration are unchanged and no schedule was added to or dropped from the list (a version hash, checked under a row lock on the project); otherwise it answers `conflict` / 409 ("run the tool again to ask for confirmation") and the user is asked again.
- **Scoped Manager.** A Manager refused before anything is asked when a listed schedule belongs to another Manager, as for project delete.
- **Client tokens.** `project_admin.update` now declares that it can require confirmation; it asks only when the impact above exists. `loopercli` exposes both endpoints.
- **Unchanged, no question, same writes:** projects without such schedules, agent schedules, command schedules with their own `work_dir`, disabled command schedules without a queued run, and changes of name or background only. The dashboard project dialog is the operator's own action and still applies at once. Config import never changes `work_dir`.
- **Docs and evals:** `docs/architecture/agent-system.md` describes the confirmation; the prompt-regression dialogs grow from 50 to 52 (`project_dir_command_schedule`, `project_dir_plain`; `evals/README.md`).
- **Size:** per the pull request description, 131 added lines of production code and 260 of tests (fixtures excluded).
- **Model-visible changes:** Yes. The `looper_projects` tool description now says a `work_dir` change asks the user first when enabled or queued command schedules run in its directory, and the Manager prompt's list of changes that need confirmation (`looper/agents/tiers/manager.py`) adds changing the directory of a project whose enabled or queued command schedules run in it. The confirmation text is new, and the two eval dialogs cover it.

## 中文摘要

本版本是 patch release v2.14.64（热修线，每个合并的改动立即发布）。自 v2.14.63 以来只合并了一项改动：修改项目目录会移动已启用的命令定时任务时，现在先要用户确认（[#1053](https://github.com/foolzzz/looper/pull/1053)）。

### 升级决策

**谁需要升级：**其 Manager（网页聊天、Telegram、Lark）或客户端令牌（`loopercli`、项目 API）会在命令定时任务运行于该目录时修改项目 `work_dir` 的运维者。其他人无需升级。

**解决了什么：**没有自己 `work_dir` 的命令定时任务在其项目的目录里运行。修改项目 `work_dir` 会把每个这样的任务的下一次运行移到新目录，而且没有人被询问。[#1053](https://github.com/foolzzz/looper/pull/1053) 对 Manager 的 `looper_projects` `update`，以及客户端令牌的 `POST /api/v1/project_admin/update` 或 `POST /api/v1/ops/projects/update` 修复了这一点：当修改影响继承该目录、且之后还会运行（已启用或有排队运行）的命令定时任务时，先返回 `needs_confirmation`。

**是否有破坏性变更：**否。没有 API 结构或配置变更，也没有迁移。过去会直接修改此类目录的客户端令牌，现在会先收到 `needs_confirmation`（见行为变化）。

**如何验证：**运行 `looper --version` 核对版本为 2.14.64。

**贡献者：**维护者 @foolzzz 提交 [#1053](https://github.com/foolzzz/looper/pull/1053)；本版本无社区贡献。

```bash
looper --version   # looper 2.14.64
```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.63 上的安装可直接升级。本版本没有迁移。

### 行为变化与入口

- **移动定时任务的目录修改先询问。**确认内容逐个列出受影响的定时任务：名称、状态（已启用，或已停用但有一次排队运行）、完整命令、旧目录 → 新目录；同一次调用中修改的其他字段也会列出。新目录为空时会说明之后的运行将失败。受影响的是没有自己 `work_dir`、已启用或有排队运行的命令定时任务（`looper/db/schedules.py` 的 `directory_dependents`）。
- **确认后的调用绑定在所展示的内容上。**只有项目目录和每个所列定时任务的配置都未变、且列表中没有增减定时任务时才生效（版本哈希，在项目行锁下检查）；否则返回 `conflict` / 409（“run the tool again to ask for confirmation”），再次询问用户。
- **受限 Manager。**所列定时任务属于另一个 Manager 时，在询问之前即被拒绝，与删除项目一致。
- **客户端令牌。**`project_admin.update` 现在声明可要求确认；只有出现上述影响时才会询问。`loopercli` 暴露这两个端点。
- **不变，不询问，写入相同：**没有此类定时任务的项目、agent 定时任务、有自己 `work_dir` 的命令定时任务、没有排队运行的已停用命令定时任务，以及只改名称或背景。仪表盘项目对话框是运维者自己的操作，仍立即生效。配置导入从不修改 `work_dir`。
- **文档与评测：**`docs/architecture/agent-system.md` 描述了该确认；提示回归对话从 50 个增至 52 个（`project_dir_command_schedule`、`project_dir_plain`；`evals/README.md`）。
- **规模：**据 PR 描述，生产代码新增 131 行，测试新增 260 行（不含 fixture）。
- **面向模型的变化：**有。`looper_projects` 工具说明现在写明：当已启用或有排队运行的命令定时任务在其目录中运行时，`work_dir` 修改会先询问用户；Manager 提示中需确认的修改清单（`looper/agents/tiers/manager.py`）新增了“修改其已启用或有排队运行的命令定时任务所在项目的目录”。确认文字是新的，两个评测对话覆盖它。

# Looper v2.13.142

## Release Decision

**Who should upgrade:** Operators who move Looper configuration between installations and have added Manager bots (Telegram, Lark or Lark bot channels owned by a Manager). Everyone else can stay on v2.13.141: a file without such bots exports and imports as before.

**What this release solves:** [#681](https://github.com/foolzzz/looper/pull/681) makes configuration transfer carry every Manager-owned bot by its immutable channel id alongside its Manager. Until now an export left added bots out and an import refused a file that named one. Import now checks conflicts in the preview, stages new and changed bots disabled, and lists the credentials still to enter.

**Breaking changes:** No. Files in `looper-config/v1` to `v3` import as before, except that a bot of a Manager in such a file is now refused with a message that it requires `looper-config/v4`. An export containing only the built-in channels and the default Manager is still `v3`.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#681](https://github.com/foolzzz/looper/pull/681); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.142
```

## Behavior changes

- **Export (#681):** `export_chunks` in `looper/agents/config_transfer.py` no longer filters channels to the built-in ones, and the "bots of Managers are not exported" line is gone from the export summary (`ExportSummary.bots_left_out` stays for older callers). When a non-default Manager or any added bot exists, the file is `looper-config/v4` and each channel entry also carries `manager_id`. Bot credentials in `channel_secrets` never travel, even with secrets included; local chat bindings, seen and unbound chats and `bound_chats_only` policy never travel. The other secrets (provider keys, MCP values, channel config keys outside the public ones) follow the existing include-secrets choice.
- **Import validation (#681):** a new `_check_channel_document` rejects, before anything is written: binding or policy fields in the file or in a channel config; a bot in a pre-v4 file; a v4 bot with unknown or missing fields (`BotConfig` is closed; `manager_id` is required for added bots); a malformed id (`channel-<type>-<n>`, type and number must match the entry, number below 2^63-1); duplicate ids or numeric suffixes; a built-in bot owned by anything but `manager`. At import, a bot whose Manager is neither in the file nor stored, or is deleted, is refused, and an existing id with a different type or owner is a conflict (`ConfigFileConflict`, reported as `ImportConflict` by `looper/agents/config_imports.py`). A new bot id whose number is below the destination's allocation counter, equal to it once called, or already used by a stored bot is refused so a past id is never reused.
- **Staging (#681):** a new bot, and a bot whose display name or config changes, imports with `enabled` false, with a plan note ("imported disabled; review credentials, local policy and chat bindings in Settings → Channels … then restart the server") and an "effective enabled: false" change reason. An identical bot keeps its local enablement. A Telegram bot with `bot_token_env`, a Lark bot without `profile` or a Lark bot without `app_id` is refused. Channels now import after Managers, and the plan's channel entries are keyed by channel id instead of type.
- **Identity checks (#681):** `finish_channels` takes the bots lock and checks the final graph (stored and imported rows together) for two bots that resolve to the same Telegram token, Lark profile or app id; a clash fails the whole import. A Lark bot whose app identity cannot be resolved is imported disabled with a note and a "lark-cli profile authentication and identity verification" follow-up. On apply, the bot id counter (`channel_bot_seq`) is moved forward, never back, to the highest imported suffix (`reserve_bot_ids` in `looper/db/config_transfer.py`). Files that contain Managers or v4 channels are first run as a preview under the same locks.
- **Credential follow-up (#681):** each added bot without a stored token gets a needed-secret entry linked to its channel form (also in a preview). `read_channels` tolerates a database from before the Manager migration.
- **Schema and UI (#681):** the v4 document schema accepts `channels` of `BotConfig` (`looper/agents/api_v1.py`, exposed in `v1_domains/configuration.py`). The dashboard section label becomes "Channel bots", and the Import/Export text now says channel bots match by channel id, credentials are always omitted, new bots import disabled and need local policy and bindings before activation, and a server restart is needed.
- **Tests (#681):** new `tests/test_manager_bot_transfer_db.py` and `tests/test_api_v1_manager_bot_transfer.py`; existing configuration-transfer, import, Lark settings, browser and `config-transfer.test.tsx` tests are updated.
- **Model-visible changes:** none. No prompt, tool declaration or tool result changes. The v1 API schema gains `BotConfig` and the v4 `channels` property, which API clients and generated CLI flags can see.
- **Line counts:** the description reports tests 637 and production 297 added lines (fixtures excluded).

## Upgrade and rollback

Re-run `install.sh` once v2.13.142 is published. No schema migration. Bots restored from a file stay disabled until the operator enters credentials and reviews policy and chat bindings in Settings → Channels, then restarts the server. Rolling back to v2.13.141 returns to leaving added bots out of exports and refusing files that carry them; bots already imported stay in the database.

## 中文摘要

### 升级决策

**谁需要升级：**在不同安装之间迁移 Looper 配置、并且添加过 Manager bot（归 Manager 所有的 Telegram、Lark 或 Lark bot 渠道）的运维者。其他人可留在 v2.13.141：不含此类 bot 的文件导出和导入与以前一致。

**解决了什么：**[#681](https://github.com/foolzzz/looper/pull/681) 让配置迁移按不可变的 channel id 随 Manager 一起带上所有 Manager 所有的 bot。此前导出会漏掉新增的 bot，导入遇到含 bot 的文件会拒绝。现在导入在预览中检查冲突，新增和变更的 bot 以停用状态暂存，并列出仍需填写的凭据。

**是否有破坏性变更：**否。`looper-config/v1` 至 `v3` 的文件照常导入，唯一区别是此类文件中的 Manager bot 现在会被拒绝，并提示需要 `looper-config/v4`。只含内置渠道和默认 Manager 的导出仍为 `v3`。

**如何验证：**运行 `looper --version` 核对版本为 2.13.142。

**贡献者：**维护者 @foolzzz 提交 [#681](https://github.com/foolzzz/looper/pull/681)；本次 patch release 无社区贡献。

```bash
looper --version   # looper 2.13.142
```

### 行为变化与入口

- **导出（#681）：**`looper/agents/config_transfer.py` 的 `export_chunks` 不再只导出内置渠道，导出摘要中“Manager 的 bot 未导出”一行移除（`ExportSummary.bots_left_out` 为兼容旧调用方保留）。存在非默认 Manager 或任何新增 bot 时，文件为 `looper-config/v4`，每个渠道条目另带 `manager_id`。`channel_secrets` 中的 bot 凭据即使选择包含 secrets 也不会导出；本地聊天绑定、已见和未绑定聊天以及 `bound_chats_only` 策略也不导出。其他 secrets（provider 密钥、MCP 值、公开键以外的渠道配置键）仍按原有的“包含 secrets”选项处理。
- **导入校验（#681）：**新增 `_check_channel_document`，在写入任何内容前拒绝：文件或渠道配置中的绑定、策略字段；旧版文件中的 bot；字段未知或缺失的 v4 bot（`BotConfig` 为封闭结构，新增 bot 必须有 `manager_id`）；格式错误的 id（`channel-<type>-<n>`，类型和数字须与条目一致，数字小于 2^63-1）；重复的 id 或数字后缀；内置 bot 的所有者不是 `manager`。导入时，所属 Manager 既不在文件中也不在库中或已删除的 bot 被拒绝；已存在 id 的类型或所有者不同则为冲突（`ConfigFileConflict`，由 `looper/agents/config_imports.py` 报告为 `ImportConflict`）。新 bot id 的数字小于目标端的分配计数器、在计数器已被调用时等于它、或已被库中某个 bot 使用，则被拒绝，避免复用历史 id。
- **暂存（#681）：**新 bot，以及显示名或配置有变化的 bot，导入时 `enabled` 为 false，并在计划中给出说明（“已停用导入：请在 Settings → Channels 检查凭据、本地策略和聊天绑定……然后重启服务”）和“effective enabled: false”变更原因。完全相同的 bot 保留本地启用状态。带 `bot_token_env` 的 Telegram bot、缺少 `profile` 的 Lark bot、缺少 `app_id` 的 Lark bot 会被拒绝。渠道现在在 Manager 之后导入，计划中的渠道条目以 channel id 而非类型为键。
- **身份检查（#681）：**`finish_channels` 获取 bot 锁，并对最终图（库中与导入的行合并）检查是否有两个 bot 解析到同一 Telegram token、Lark profile 或 app id；冲突会使整个导入失败。无法解析 app 身份的 Lark bot 以停用状态导入，附说明和“lark-cli profile 认证与身份核验”待办。应用时，bot id 计数器（`channel_bot_seq`）只前进、不回退，到所导入的最大后缀（`looper/db/config_transfer.py` 的 `reserve_bot_ids`）。含 Manager 或 v4 渠道的文件会先在相同的锁下以预览方式运行一遍。
- **凭据待办（#681）：**每个没有已存 token 的新增 bot 会得到一条指向其渠道表单的待填 secret 条目（预览中也有）。`read_channels` 兼容 Manager 迁移之前的数据库。
- **Schema 与界面（#681）：**v4 文档 schema 接受由 `BotConfig` 组成的 `channels`（`looper/agents/api_v1.py`，在 `v1_domains/configuration.py` 中公开）。控制台分区标签改为“Channel bots”，导入导出文案说明：channel bot 按 channel id 匹配，凭据一律不导出，新 bot 以停用状态导入、启用前需先设置本地策略和绑定，且需要重启服务。
- **测试（#681）：**新增 `tests/test_manager_bot_transfer_db.py` 和 `tests/test_api_v1_manager_bot_transfer.py`；现有的配置迁移、导入、Lark 设置、浏览器和 `config-transfer.test.tsx` 测试已更新。
- **面向模型的变化：**无。提示词、tool 声明和工具结果均不变。v1 API schema 新增 `BotConfig` 和 v4 的 `channels` 属性，API 客户端和生成的 CLI 参数可见。
- **行数：**描述报告新增测试 637 行、生产代码 297 行（不含 fixtures）。

### 升级与回退

v2.13.142 发布后重跑 `install.sh`。无表结构迁移。从文件恢复的 bot 保持停用，直到运维者在 Settings → Channels 填入凭据、检查策略和聊天绑定并重启服务。回退到 v2.13.141 会恢复为导出时漏掉新增 bot、并拒绝含 bot 的文件；已导入的 bot 仍留在数据库中。

# Looper v2.13.1

## Release Decision

**Who should upgrade:** Operators blocked by the v2.13.0 known issue when their pre-upgrade `pg_dump` runs in Docker and the host has no local `pg_restore`, or operators who need an explicit backup verifier.

**What this release solves:** [#266](https://github.com/foolzzz/looper/pull/266) verifies Docker-based pre-upgrade backups inside the container. A backup command of the form `docker exec CONTAINER pg_dump ...` derives `docker exec -i CONTAINER pg_restore --list`, reading the archive from stdin. This resolves the v2.13.0 Docker backup known issue. Other setups can use `backup.verify_command` in the ops file; `LOOPER_BACKUP_VERIFY_CMD` is the deprecated environment form.

**Breaking changes:** No. Local `pg_dump`/`pg_restore` behavior remains unchanged. A full, verified backup is still required for a registry upgrade; missing or failing verification stops startup before any DDL. The registry and configuration compatibility requirements from [v2.13.0](https://github.com/foolzzz/looper/blob/main/docs/releases/v2.13.0.md) still apply.

**How to verify:** Check the version and the verifier reported by `looper doctor`. On a disposable database copy with a pending schema change, start `looper serve` with an isolated runtime root and port, then confirm the backup is listed successfully and startup proceeds. Check that a missing or failing verifier stops startup before schema changes. Version and doctor checks alone do not prove a backup can be restored.

**Contributors:** Maintainer @foolzzz authored [#266](https://github.com/foolzzz/looper/pull/266); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.1
looper doctor
```

## Behavior changes

- **Verification order:** Use explicit `backup.verify_command` first, otherwise derive the verifier from a recognized `docker exec [options] <container> pg_dump ...` command, otherwise use local `pg_restore` beside `pg_dump` or on PATH. Explicit and derived verifiers receive the dump on stdin and must list it like `pg_restore --list`.
- **Backup gate:** Verification still requires a custom-format archive listing with both table definitions and table data. A failing verifier or incomplete listing rejects the backup and removes its partial file. Without any verifier, the error names `backup.verify_command`. Registry upgrades still reject `--skip-backup`.
- **Diagnostics:** `looper doctor` and startup self-checks report the selected verifier. Explicit-verifier timeout errors omit the full command arguments.
- **Derivation limits:** Wrappers, Docker global options and unrecognized exec options require an explicit verifier when no suitable local `pg_restore` is available. Short boolean forms such as `-i=false` and `-t=false` are not recognized by automatic derivation; see [#268](https://github.com/foolzzz/looper/issues/268). The deprecated verifier environment setting supports only the `LOOPER_` prefix.

## Entry points

- **CLI:** `looper serve` uses the verifier during pre-upgrade backup; `looper doctor` reports it. The ops file gains `backup.verify_command`.
- **Dashboard and Telegram/Lark channels:** No UI, channel command, Manager tool or prompt change is needed; this patch changes service startup backup verification.

## Upgrade and rollback

Stop the old service and retain independent database backups, configuration and runtime data. Re-run `install.sh` once v2.13.1 is published, then start with the existing configuration. A recognized Docker backup command needs no new setting or local `pg_restore`; the existing container must provide a usable `pg_restore`.

For an upgrade from a pre-v2.13.0 registry, follow the [v2.13.0 backup, migration readback and isolated restore procedure](https://github.com/foolzzz/looper/blob/main/docs/releases/v2.13.0.md#upgrade-and-rollback). This patch fixes verification, not the need for a full backup or a restore rehearsal. Returning to v2.13.0 reintroduces its Docker verification limitation. Returning to a pre-migration binary requires restoring the pre-upgrade backup into a separate database and deciding how to recover later writes.

## Optional Capability Activation & Use

### Backup verification command

**Activation:** For a recognized `backup.command` of the form `docker exec <container> pg_dump ...`, verification is automatic. To override it or support another setup, set `[backup] verify_command` to an argv array in the existing ops file and restart the service. It must read the archive from stdin and list its contents like `pg_restore --list`. Prefer the ops file; `LOOPER_BACKUP_VERIFY_CMD` is the deprecated, shell-split environment form.

```toml
[backup]
verify_command = ["docker", "exec", "-i", "postgres", "pg_restore", "--list"]
```

Use the name of the existing PostgreSQL container in place of `postgres`. Check the selected verifier:

```bash
looper --version   # looper 2.13.1
looper doctor
```

**Validation:** On a disposable database copy with a pending schema change, confirm that the archive reaches the verifier on stdin and its listing contains table definitions and data. Exercise a failing verifier and confirm startup refuses before any DDL. Rehearse recovery into a separate database; a successful listing alone is not a restore test.

**Disable / rollback:** Remove `backup.verify_command` and unset its deprecated environment form to return to automatic derivation or local `pg_restore`. If neither works, startup refuses the upgrade. To roll back across a registry migration, use the isolated full-backup restore procedure above; removing this setting does not undo a migration.

**Authority boundary:** The configured argv runs as the service user with the backup subprocess environment. It does not create a container or grant Docker access; use an existing container and existing permissions. Only an operator should configure it. Backup verification remains mandatory for registry upgrades.

**Docs:** [Backup implementation](https://github.com/foolzzz/looper/blob/main/looper/agents/db_backup.py), [ops configuration](https://github.com/foolzzz/looper/blob/main/looper/ops_config.py), [implementation and validation](https://github.com/foolzzz/looper/pull/266).

## 中文摘要

### 升级决策

**谁需要升级：**因 Docker 内执行 `pg_dump`、本机没有 `pg_restore` 而被 v2.13.0 已知问题阻止升级的操作者，以及需要显式指定备份校验命令的操作者。

**解决了什么：**[#266](https://github.com/foolzzz/looper/pull/266) 为 `docker exec CONTAINER pg_dump ...` 自动推导 `docker exec -i CONTAINER pg_restore --list`，通过标准输入校验备份，解决 v2.13.0 的 Docker 备份已知问题。其他部署可在运维文件中设置 `backup.verify_command`；`LOOPER_BACKUP_VERIFY_CMD` 为弃用环境变量形式。

**是否有破坏性变更：**无。本地 `pg_dump`/`pg_restore` 行为保持不变。Registry 升级仍要求完整且验证成功的备份，无法校验或校验失败均在任何 DDL 前停止。v2.13.0 的 registry 与配置兼容要求继续适用。

**如何验证：**核对版本与 `looper doctor` 报告的校验器。在待变更 schema 的一次性数据库副本上，以隔离 runtime root 和端口启动服务，确认备份校验成功后才继续；校验器缺失或失败时应在 schema 变化前停止。版本与 doctor 检查不能单独证明备份可恢复。

**贡献者：**维护者 @foolzzz 提交 [#266](https://github.com/foolzzz/looper/pull/266)；本次 patch release 无社区贡献。

```bash
looper --version   # looper 2.13.1
looper doctor
```

### 行为变化与入口

- 校验器优先级：显式 `backup.verify_command` → 从已识别的 `docker exec [选项] <容器> pg_dump ...` 推导 → `pg_dump` 旁或 PATH 上的本地 `pg_restore`。显式和推导命令均从标准输入读取备份。
- 仍要求 custom-format 归档同时列出表定义与表数据。校验失败或内容不完整则拒绝备份并删除临时文件；无校验器时报错点名 `backup.verify_command`；registry 升级仍拒绝 `--skip-backup`。显式校验器超时报错不包含完整命令参数。
- 包装命令、Docker 全局选项及未识别的 exec 选项在没有可用本地 `pg_restore` 时需显式配置。`-i=false`、`-t=false` 暂不支持自动推导，见 [#268](https://github.com/foolzzz/looper/issues/268)。弃用的校验环境变量仅支持 `LOOPER_` 前缀。
- CLI 的 `looper serve` 使用校验器，`looper doctor` 和启动自检报告选择结果。Dashboard、Telegram/Lark 无需界面、渠道命令、Manager 工具或提示词改动，本次修复作用于服务启动备份。

### 升级与回退

停止旧服务，独立保留完整数据库备份、配置与 runtime 数据。v2.13.1 发布后重跑 `install.sh`，沿用已有配置启动。可识别的 Docker 备份命令无需新增设置或本地 `pg_restore`，已有容器内需有可用的 `pg_restore`。

从旧 registry 升级仍遵循 [v2.13.0 的备份、迁移读回与隔离恢复流程](https://github.com/foolzzz/looper/blob/main/docs/releases/v2.13.0.md#upgrade-and-rollback)。本次修复不替代完整备份与恢复演练。退回 v2.13.0 会恢复其 Docker 校验限制；退回迁移前的二进制需把升级前备份恢复到独立数据库，并决定后续写入的恢复方式。

### 可选能力启用与使用

#### Backup verification command

**启用：**已有 `backup.command` 为可识别的 `docker exec <容器> pg_dump ...` 时自动生效。需要覆盖或支持其他部署时，在现有运维文件中设置 `[backup] verify_command` argv 数组并重启服务；命令从标准输入读归档，像 `pg_restore --list` 一样列出内容。优先用运维文件；`LOOPER_BACKUP_VERIFY_CMD` 是弃用的、按 shell 参数拆分的环境变量形式。

```toml
[backup]
verify_command = ["docker", "exec", "-i", "postgres", "pg_restore", "--list"]
```

将 `postgres` 替换为已有 PostgreSQL 容器名，再核对校验器：

```bash
looper --version   # looper 2.13.1
looper doctor
```

**验证：**在待变更 schema 的一次性数据库副本上确认备份通过标准输入送达校验器，列表含表定义与表数据；校验器失败时应在任何 DDL 前拒绝启动。另在独立数据库演练恢复；列出归档不等于完成恢复测试。

**停用 / 回退：**移除 `backup.verify_command` 并取消其弃用环境变量设置，回到自动推导或本地 `pg_restore`；两者都不可用时拒绝升级。跨 registry 迁移回退须按上方完整备份隔离恢复流程执行，删除设置不能撤销迁移。

**权限边界：**配置的 argv 以服务用户身份、备份子进程环境执行，不创建容器或授予 Docker 权限；使用已有容器与权限，仅由操作者配置。Registry 升级仍必须通过备份校验。

**文档：**[备份实现](https://github.com/foolzzz/looper/blob/main/looper/agents/db_backup.py)、[运维配置](https://github.com/foolzzz/looper/blob/main/looper/ops_config.py)、[实现与验证](https://github.com/foolzzz/looper/pull/266)。

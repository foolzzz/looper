# Looper v2.13.129

## Release Decision

**Who should upgrade:** Nobody needs to upgrade for existing behavior. Operators who manage native Telegram or Lark chat bindings and the bound-chats-only policy through the v1 API, the generated CLI or the dashboard client library should upgrade, because those operations now exist.

**What this release solves:** [#655](https://github.com/foolzzz/looper/pull/655) exposes operator-only v1 operations to list, bind, rebind and unbind native chats, to list observed chats and to set the bound-chats-only policy, with generated CLI discovery for operator-only commands, a shared dashboard API module, and a guard that keeps API clients from deleting a bot that operators route.

**Breaking changes:** No. The existing operations keep their request and result shapes. The one change to an existing path is that deleting a bot through the v1 channel-config removal now goes through the routing-aware delete, and an API client can no longer delete a bot that has a binding or the bound-chats-only policy.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#655](https://github.com/foolzzz/looper/pull/655); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.129
```

## Behavior changes

- **New v1 operations:** the new `looper/agents/v1_domains/chat_bindings.py` adds five operator-only POST operations: `manager_chat_bindings.list` (filters `channel_id`, `manager_id`), `manager_chat_bindings.put`, `manager_chat_bindings.delete`, `channel_chats.list` (`channel_id`, `limit` 1 to 200 with default 100, `after` cursor; returns observed and bound chats with their effective Manager, at most 20 unbound chats, `next_cursor` and `has_more`) and `channel_chats.set_policy`. The domain is picked up by the existing domain loader. Requests are closed objects; identities are validated with the native identity checks before any write. Unknown channels or Managers answer not found, malformed identities answer invalid. The code does not return chat transcripts, only metadata (names, counts, last-seen time, Manager state).
- **Live routing required for writes:** `put`, `delete` and `set_policy` answer unavailable when the HTTP server has no channel registry. `serve.py` now passes its registry to `AgentHTTPServer` (new optional `channels` argument), so a running service applies each write to the live routing snapshot.
- **Write path:** in `looper/agents/channels/chat_routing.py`, `bind_chat` takes an optional `readback` callback that runs inside the same locked transaction, so the `put` response reflects what was written before commit and publication. `unbind_chat` now returns whether a binding was deleted instead of a snapshot, and `delete` reports it as `deleted`. `set_chat_policy` still returns a snapshot.
- **Guarded bot deletion:** `remove_bot_with_routing` takes a `principal_kind` of `client` or `operator` (default operator; other values raise `ValueError`). A client principal always refuses a routed bot. The v1 channel-config removal in `channel_configs.py` now calls it instead of `bot_api.remove_bot`: the confirmation impact check refuses a client when the bot is bound-chats-only or has a binding (forbidden, "operator-managed chat routing prevents client deletion"), and the delete maps missing, built-in and has-bindings results to not found, invalid and forbidden. Operators can still delete such a bot. The result stays `{"deleted": <id>, "restart": true}`.
- **CLI:** in `looper/loopercli.py`, generated commands whose operation carries `x-looper-operator-only` now require an operator token. They accept `--operator-token-file` (default `-`, one line from stdin) and `--server-url`, and discovery of the API document uses that token before a client file is needed. Running such a command without an operator token fails with a usage error. Only the credential flag selects this mode, because a bare `--url` can be a request field.
- **Dashboard client library:** the new `web/src/lib/chat-bindings-api.ts` wraps the five operations (`fetchChatBindings`, `putChatBinding`, `deleteChatBinding`, `fetchChannelChats`, `setBoundChatsOnly`) with typed results. The diff adds no dashboard page that calls them; this draft did not look for one.
- **Model-visible changes:** none found. The diff touches no prompt, tool declaration or tool result. The new operations are in the v1 operation catalog, which the generated CLI reads; this draft did not check whether any model tool exposes that catalog.
- **Line counts:** the description of [#655](https://github.com/foolzzz/looper/pull/655) reports tests 882 and production 382 added lines (fixtures excluded).

Re-run `install.sh` once v2.13.129 is published. No schema or configuration change. Rolling back to v2.13.128 removes the new operations and the client-deletion guard.

### 升级决策

**谁需要升级：**无需为现有行为而升级。通过 v1 API、生成的 CLI 或仪表盘客户端库管理原生 Telegram/Lark 聊天绑定和仅限绑定聊天策略的操作者应升级，因为这些操作现已存在。

**解决了什么：**[#655](https://github.com/foolzzz/looper/pull/655) 新增仅限操作者的 v1 操作：列出、绑定、改绑、解绑原生聊天，列出已见聊天，设置仅限绑定聊天策略；同时提供生成式 CLI 对仅限操作者命令的发现、共享的仪表盘 API 模块，以及阻止 API 客户端删除由操作者路由的 bot 的保护。

**是否有破坏性变更：**否。现有操作的请求与结果形状不变。唯一变化的现有路径是：v1 渠道配置删除 bot 现在走带路由感知的删除，API 客户端不能再删除有绑定或设置了仅限绑定聊天策略的 bot。

**如何验证：**运行 `looper --version` 核对版本为 2.13.129。

**贡献者：**维护者 @foolzzz 提交 [#655](https://github.com/foolzzz/looper/pull/655)；本次 patch release 无社区贡献。

### 行为变化与入口

- **新增 v1 操作：**新增 `looper/agents/v1_domains/chat_bindings.py`，提供五个仅限操作者的 POST 操作：`manager_chat_bindings.list`（过滤条件 `channel_id`、`manager_id`）、`manager_chat_bindings.put`、`manager_chat_bindings.delete`、`channel_chats.list`（`channel_id`、`limit` 1 到 200 默认 100、`after` 游标；返回已见和已绑定聊天及其生效的 Manager、最多 20 个未绑定聊天、`next_cursor` 与 `has_more`）和 `channel_chats.set_policy`。该域由现有的域加载器自动加载。请求为封闭对象；写入前先用原生标识校验检查标识。渠道或 Manager 不存在返回 not found，标识格式错误返回 invalid。代码不返回聊天记录，只返回元数据（名称、计数、最后出现时间、Manager 状态）。
- **写入需要实时路由：**HTTP 服务没有渠道注册表时，`put`、`delete`、`set_policy` 返回 unavailable。`serve.py` 现在把注册表传给 `AgentHTTPServer`（新增可选参数 `channels`），因此运行中的服务会把每次写入应用到实时路由快照。
- **写入路径：**`looper/agents/channels/chat_routing.py` 中 `bind_chat` 新增可选的 `readback` 回调，在同一个加锁事务内执行，使 `put` 的响应反映提交与发布之前写入的内容。`unbind_chat` 现在返回是否删除了绑定而不是快照，`delete` 以 `deleted` 报告；`set_chat_policy` 仍返回快照。
- **受保护的 bot 删除：**`remove_bot_with_routing` 接受 `principal_kind`（`client` 或 `operator`，默认 operator；其他值抛出 `ValueError`）。client 主体总是拒绝有路由的 bot。`channel_configs.py` 中 v1 渠道配置删除现在调用它而不是 `bot_api.remove_bot`：确认阶段的影响检查在 bot 为仅限绑定聊天或有绑定时拒绝 client（forbidden，“operator-managed chat routing prevents client deletion”），删除时把 missing、builtin、has_bindings 结果分别映射为 not found、invalid、forbidden。操作者仍可删除此类 bot。结果仍为 `{"deleted": <id>, "restart": true}`。
- **CLI：**`looper/loopercli.py` 中，带 `x-looper-operator-only` 的生成命令现在需要操作者令牌，接受 `--operator-token-file`（默认 `-`，从 stdin 读一行）和 `--server-url`；API 文档的发现在需要 client 文件之前使用该令牌。没有操作者令牌运行此类命令会以用法错误失败。只有凭据参数会选择此模式，因为单独的 `--url` 可能是请求字段。
- **仪表盘客户端库：**新增 `web/src/lib/chat-bindings-api.ts`，用带类型的结果封装这五个操作（`fetchChatBindings`、`putChatBinding`、`deleteChatBinding`、`fetchChannelChats`、`setBoundChatsOnly`）。本 diff 未新增调用它们的仪表盘页面；本草稿未查找是否有其他调用方。
- **面向模型的变化：**未发现。本 diff 未触及提示词、tool 声明或 tool 结果。新操作进入 v1 操作目录，生成式 CLI 读取该目录；本草稿未检查是否有模型 tool 暴露该目录。
- **行数：**[#655](https://github.com/foolzzz/looper/pull/655) 的描述报告新增测试 882 行、生产代码 382 行（不含 fixtures）。

# Looper v2.13.79

## Release Decision

**Who should upgrade:** Anyone who manages Telegram or Lark bots from the dashboard Settings → Channels page, or who calls the removed `/api/channel-configs` routes from a script. Everyone else gets no change.

**What this release solves:** [#518](https://github.com/foolzzz/looper/pull/518) moves channel bot settings (list, read, add, update, remove) onto five typed operations in the versioned API, keeps the credential and sender-allowlist rules, and removes the legacy `/api/channel-configs` routes.

**Breaking changes:** Yes. `GET /api/channel-configs`, `GET /api/channel-configs/{id}`, `POST /api/channel-configs`, `PUT /api/channel-configs/{id}` and `DELETE /api/channel-configs/{id}` are removed; a script that calls them must use `POST /api/v1/channel_configs/{list,get,create,update,delete}`. The dashboard shipped in this release already does.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#518](https://github.com/foolzzz/looper/pull/518); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.79
```

## Behavior changes

- **Channel settings on v1 ([#518](https://github.com/foolzzz/looper/pull/518)):** the new `looper/agents/v1_domains/channel_configs.py` registers `channel_configs.list`, `channel_configs.get` (risk `read`), `channel_configs.create`, `channel_configs.update` (risk `write`) and `channel_configs.delete` (risk `high`), all `POST /api/v1/channel_configs/<action>`. Requests and results are closed objects; a channel view carries `has_bot_token` (presence only) and never the credential.
- **Credential writes are operator-only:** `create` and `update` are marked operator-only credential writes, so an API client cannot reach them; `bot_token` is a write-only field. On `update`, an omitted or `***` token keeps the stored one and `null` or an empty string removes it. `update` takes `{channel_id, fields}`; a `manager_id` in `fields` must equal the stored one, so a bot's Manager still cannot change.
- **Delete confirms:** `delete` is risk `high` and asks for confirmation. Per the architecture doc, the operator executes once and a client needs same-session confirmation. The target is re-read before the removal, and a built-in channel is refused (turn it off instead). The result is `{deleted, restart}`; restart Looper to stop the running adapter.
- **Validation:** `config` is checked per channel type (`telegram`, `lark`, `lark_bot`) with closed schemas; Telegram sender ids may be strings or integers and `null` means an empty list. `update` validates `config` against the stored channel's type before writing.
- **Response shape:** results are wrapped in the v1 `OpOk.result` envelope (and `create` no longer answers HTTP 201 as the legacy route did). The legacy list handler swallowed a database error into an empty list and the legacy get into a 404; the new handlers have no such fallback in the code (`channel_configs.py` calls the database directly), but this draft did not run a failure path to see what is answered.
- **Removed routes:** the five `/api/channel-configs` routes, their `_RE_CHANNEL_CONFIG` pattern and the two list/get handlers are deleted from `looper/agents/http_server.py`. `/api/v1/channels/status` and `/api/v1/channels/people` and the Lark routes are unchanged.
- **Dashboard and callers:** `web/src/lib/api.ts` (`fetchChannelConfigs`, `fetchChannelConfig`, `updateChannelConfig`, `createChannelBot`, `deleteChannelBot`) calls the five operations. `examples/dsh/validate.py` and `examples/pi/isolated-smoke.py` list channels through `channel_configs.list`.
- **Docs and tests:** `README.md`, `README.zh-CN.md` and `docs/architecture/agent-system.md` name the new routes; the new `tests/test_api_v1_channel_configs.py` and `..._db.py` cover credential refusal, token keep/replace/remove, concurrent duplicate creates, confirmed deletion and the old routes answering 404; existing channel, Lark, config-transfer and DSH tests and the dashboard tests were updated.
- **Model-visible changes:** None. The operations declare no Tool, so no Manager, Worker, Planner or Reviewer prompt and no Manager Tool changed. They do appear in the v1 operation catalog that API clients read.
- **Not confirmed in code:** this draft did not run any test; claims about confirmation and the status answers come from the code and the pull request's tests and docs.

## Upgrade and rollback

Re-run `install.sh` once v2.13.79 is published. No data migration; stored channel settings, credentials and Manager associations are unchanged. Update any script that used the removed `/api/channel-configs` routes. Rolling back to v2.13.78 restores them together with the old dashboard.

**是否有破坏性变更：**有。`GET /api/channel-configs`、`GET /api/channel-configs/{id}`、`POST /api/channel-configs`、`PUT /api/channel-configs/{id}`、`DELETE /api/channel-configs/{id}` 已移除；调用它们的脚本须改用 `POST /api/v1/channel_configs/{list,get,create,update,delete}`。本版本附带的仪表盘已改用新操作。

**如何验证：**运行 `looper --version` 核对版本为 2.13.79。

**贡献者：**维护者 @foolzzz 提交 [#518](https://github.com/foolzzz/looper/pull/518)；本次 patch release 无社区贡献。

### 行为变化与入口

- **渠道设置迁到 v1（[#518](https://github.com/foolzzz/looper/pull/518)）：**新增 `looper/agents/v1_domains/channel_configs.py`，注册 `channel_configs.list`、`channel_configs.get`（风险 `read`）、`channel_configs.create`、`channel_configs.update`（风险 `write`）和 `channel_configs.delete`（风险 `high`），均为 `POST /api/v1/channel_configs/<action>`。请求和结果均为封闭对象；渠道视图只含 `has_bot_token`（仅表示是否存在），从不返回凭据。
- **凭据写入仅限操作员：**`create` 和 `update` 标记为仅限操作员的凭据写入，API 客户端无法调用；`bot_token` 为只写字段。`update` 时省略或 `***` 的 token 保留已存值，`null` 或空字符串则删除。`update` 接收 `{channel_id, fields}`；`fields` 中的 `manager_id` 必须与已存值相同，因此机器人的 Manager 仍不能更改。
- **删除需确认：**`delete` 风险为 `high`，需要确认。按架构文档，操作员执行一次即可，客户端需要同会话确认。移除前会重新读取目标，内置渠道会被拒绝（应改为关闭）。结果为 `{deleted, restart}`；需重启 Looper 才会停止运行中的适配器。
- **校验：**`config` 按渠道类型（`telegram`、`lark`、`lark_bot`）用封闭 schema 校验；Telegram 发送者 id 可为字符串或整数，`null` 表示空列表。`update` 在写入前按已存渠道的类型校验 `config`。
- **响应形态：**结果包在 v1 的 `OpOk.result` 中（`create` 不再像旧路由那样返回 HTTP 201）。旧的列表处理器会把数据库错误吞成空列表、旧的读取会吞成 404；新处理器在代码中没有这类兜底（`channel_configs.py` 直接调用数据库），但本草稿未运行失败路径，不确定实际返回什么。
- **移除的路由：**`looper/agents/http_server.py` 中的五个 `/api/channel-configs` 路由、`_RE_CHANNEL_CONFIG` 正则以及列表/读取两个处理器已删除。`/api/v1/channels/status`、`/api/v1/channels/people` 与 Lark 路由不变。
- **仪表盘与调用方：**`web/src/lib/api.ts`（`fetchChannelConfigs`、`fetchChannelConfig`、`updateChannelConfig`、`createChannelBot`、`deleteChannelBot`）调用这五个操作。`examples/dsh/validate.py` 与 `examples/pi/isolated-smoke.py` 通过 `channel_configs.list` 列出渠道。
- **文档与测试：**`README.md`、`README.zh-CN.md`、`docs/architecture/agent-system.md` 改用新路由；新增 `tests/test_api_v1_channel_configs.py` 与 `..._db.py`，覆盖凭据拒绝、token 保留/替换/删除、并发重复创建、确认删除以及旧路由返回 404；并更新了现有的渠道、Lark、配置迁移、DSH 与仪表盘测试。
- **面向模型的变化：**无。这些操作未声明 Tool，因此 Manager、Worker、Planner、Reviewer 的 prompt 和 Manager Tool 均未改动。它们会出现在 API 客户端读取的 v1 操作目录中。
- **代码中未确认：**本草稿未运行任何测试；关于确认流程和状态码的说法来自代码以及该 PR 的测试与文档。

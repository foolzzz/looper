# Looper v2.14.53

This is the patch release v2.14.53, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.52: `looper service upgrade` acts only on the service's own install and recovers a late stop ([#1021](https://github.com/foolzzz/looper/pull/1021)). No new setting is added.

## Release Decision

**Who should upgrade:** Anyone who runs Looper as a service and upgrades it with `looper service upgrade`, especially with more than one Python environment or checkout on the machine.

**What this release solves:** [#1021](https://github.com/foolzzz/looper/pull/1021) stops `looper service upgrade` from installing a wheel into the wrong interpreter, publishing the wrong dashboard directory, or fast-forwarding the wrong checkout. It also starts the unit again when the old process exits after the stop wait timed out, keeps renewing the drain lease while the stop is waited on, and reports what is actually running after a failed upgrade. The component fingerprint now hashes only tracked files, so a gitignored file such as a macOS `.DS_Store` under `web/src` can no longer fail the post-upgrade check.

**Breaking changes:** No. No API or migration is added or removed. An upgrade run with a `looper` or checkout other than the service's own now refuses instead of acting.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#1021](https://github.com/foolzzz/looper/pull/1021); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.53
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.52 upgrades directly. This release adds no migration.

## Behavior changes

- **Own-install check ([#1021](https://github.com/foolzzz/looper/pull/1021)).** Before any mutation and before the drain, `looper service upgrade` compares the unit's command with the running `looper` and refuses if they differ. It resolves the package root of the unit's interpreter (with Python imports isolated) and refuses a unit that sets `PYTHONPATH`, `PYTHONHOME` or `PYTHONUSERBASE`. A checkout upgrade must run from that package root. A web-only or no-op wheel upgrade refuses if the dashboard directory is not the service's own.
- **Wheel installs.** The install uses the interpreter's own prefix: it refuses when the service package is not in the interpreter's installation paths (an editable checkout, a user or target install), drops pip and uv redirect variables (`PIP_TARGET`, `PIP_USER`, `UV_PYTHON`, `PYTHONPATH` and similar), disables pip and uv config files, and passes the prefix to pip or uv explicitly.
- **Checkout installs.** `uv sync` targets the service interpreter and its virtual environment. The upgrade refuses if the interpreter is not in a virtual environment, or if `UV_PROJECT_ENVIRONMENT` (default `.venv`) selects a different one; the message gives the value to set.
- **Late stop.** While the stop is waited on, the drain lease is renewed (every 5 seconds during the stop call, then each poll). If the stop wait times out and the old process exits afterwards, recovery starts the unit again. If the old process never exits, recovery reports that and starts nothing. Recovery also refuses to start a second server when the port is already served, naming the pid, and a failed `drain_cancel` no longer hides the recovery result.
- **Failure report.** After a failed upgrade, the reported running code fingerprint is read from the service now running, not the one before the upgrade. The error line says `serving: yes` or `serving: no`, and with no it adds `run looper service restart`.
- **Fingerprint.** The component fingerprint of a checkout hashes only files tracked by Git; an installed wheel uses its `RECORD`, and generated dashboard assets under `web/dist` are included as before. The web source record uses the same file list.
- **Model-visible changes:** No. No prompt, tool description, tool schema or Manager confirmation text changes. The architecture document's sentence about the upgrade refusing is updated.

### 升级决策

**谁需要升级：**以服务方式运行 Looper 并用 `looper service upgrade` 升级的人，尤其是机器上有多个 Python 环境或检出的情况。

**解决了什么：**[#1021](https://github.com/foolzzz/looper/pull/1021) 防止 `looper service upgrade` 把 wheel 装进错误的解释器、发布错误的仪表盘目录或快进错误的检出。同时，旧进程在停止等待超时后才退出时会重新启动服务，停止等待期间持续续期 drain 租约，并在升级失败后报告实际运行的代码。组件指纹只哈希被 Git 跟踪的文件，因此 `web/src` 下被忽略的文件（如 macOS 的 `.DS_Store`）不会再使升级后检查失败。

**是否有破坏性变更：**否。不新增或移除 API 或迁移。用服务之外的 `looper` 或检出运行升级现在会被拒绝，而不是照做。

**如何验证：**运行 `looper --version` 核对版本为 2.14.53。

**贡献者：**维护者 @foolzzz 提交 [#1021](https://github.com/foolzzz/looper/pull/1021)；本版本无社区贡献。

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.52 上的安装可直接升级。本版本没有新迁移。

### 行为变化与入口

- **自身安装检查（[#1021](https://github.com/foolzzz/looper/pull/1021)）。**在任何改动和 drain 之前，`looper service upgrade` 会比对服务单元的命令与当前运行的 `looper`，不一致即拒绝。它在隔离 Python 导入的情况下解析单元解释器的包根目录，并拒绝设置了 `PYTHONPATH`、`PYTHONHOME` 或 `PYTHONUSERBASE` 的单元。检出升级必须在该包根目录运行。仅 web 或无变化的 wheel 升级在仪表盘目录不属于服务自身时拒绝。
- **wheel 安装。**安装使用解释器自己的 prefix：服务包不在解释器安装路径内（可编辑检出、用户或 target 安装）时拒绝；去掉 pip 和 uv 的重定向变量（`PIP_TARGET`、`PIP_USER`、`UV_PYTHON`、`PYTHONPATH` 等），禁用 pip 与 uv 配置文件，并显式向 pip 或 uv 传入 prefix。
- **检出安装。**`uv sync` 指向服务的解释器及其虚拟环境。解释器不在虚拟环境中，或 `UV_PROJECT_ENVIRONMENT`（默认 `.venv`）指向别的环境时拒绝，并在提示中给出应设置的值。
- **迟到的停止。**等待停止期间持续续期 drain 租约（停止调用期间每 5 秒一次，之后每次轮询）。停止等待超时后旧进程才退出时，恢复流程会重新启动服务；旧进程始终不退出时，恢复流程只报告而不启动任何东西。端口已被占用时，恢复流程拒绝再启动第二个服务并给出 pid；`drain_cancel` 失败也不再掩盖恢复结果。
- **失败报告。**升级失败后，报告的运行代码指纹取自当前正在运行的服务，而不是升级前的。错误行包含 `serving: yes` 或 `serving: no`，为 no 时附加 `run looper service restart`。
- **指纹。**检出的组件指纹只哈希 Git 跟踪的文件；已安装的 wheel 使用其 `RECORD`；`web/dist` 下生成的仪表盘资源照旧计入。web 源记录使用同一文件列表。
- **面向模型的变化：**无。没有 prompt、工具描述、工具 schema 或 Manager 确认文本的变化。架构文档中关于升级拒绝条件的一句话已更新。

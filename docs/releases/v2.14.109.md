# Looper v2.14.109

This is the patch release v2.14.109, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.108: `loopercli` creates, starts, stops and deletes tasks with short commands ([#1165](https://github.com/foolzzz/looper/pull/1165)).

## Release Decision

**Who should upgrade:** Operators and scripts that manage tasks from the command line. Others are not affected: there is no server behavior change.

**What this release solves:** [#1165](https://github.com/foolzzz/looper/pull/1165). Managing a task's life from the CLI needed the generated long commands, a task could not be created and started in one step, `start` did not continue a stopped task, and there was no short way to delete a task. `loopercli create`, `start`, `stop` and `delete` now cover that, and their help is written for a CLI user.

**Breaking changes:** No. No new dependency, no schema change, no configuration change. The generated `task-create` command and its options remain. Only the `create` help text, the `start` behavior for non-ready tasks and the `tasks.delete` description change (see below).

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.14.109
```

**Contributors:** Maintainer @foolzzz authored [#1165](https://github.com/foolzzz/looper/pull/1165); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.108 upgrades directly. There is no database or configuration change.

## Behavior changes

- **`loopercli create`** (`looper/loopercli.py`). Creates a ready task and prints its id on the first line, then `ready; start it with: loopercli start <id>`. `--project` is now required (an existing project or a new one to create); without it the command fails with a usage error. `--title` is optional and defaults to the requirement's first line, shortened to 60 characters at a word boundary with `…`. The new `--start` flag starts the task after a successful creation and prints `<id>: started`. If creation needs confirmation, nothing is started: run `loopercli confirm ID`, then `loopercli start TASK`. With `--json --start` the single answer carries the create response under `create` when starting fails. A create response without a task id is an error. The option help texts are rewritten for a CLI user.
- **`loopercli start TASK`**. It first reads the task. A ready task is started. A stopped, failed or cancelled task is continued from its saved plan through the restart operation, keeping accepted steps, and prints `continuing from its saved plan`. A running task (or one in the in-progress or needs-you group) succeeds unchanged with `already running`. A completed task, or a task in any other state, is refused. Before this release `start` only called the start operation.
- **`loopercli delete TASK`** (new). Calls `tasks.delete`: a running task is refused; a ready, stopped, failed, cancelled or completed task is deleted with its workspaces, and its result branch stays. It uses the existing high-risk confirmation flow: a client token gets a confirmation id and runs `loopercli confirm ID`; an operator token executes directly.
- **`loopercli stop TASK`** is unchanged in behavior. `loopercli tasks --help` lists every tasks.* operation, including delete.
- **`tasks.delete` description** (`looper/agents/v1_domains/workspaces.py`). The summary and description in the API document now read "Delete a non-running task and its workspaces" and name the accepted states, where they said "stopped task". Only the text changed; the server code that deletes a task is untouched and already refused only running tasks.
- **Documentation and tests.** `docs/architecture/agent-system.md` gains a "Task lifecycle" section. `tests/test_loopercli.py` is extended, and `tests/test_api_v1_task_workspaces_db.py` now runs the delete test for init, stopped, failed, cancelled and completed tasks.
- **Unchanged:** server behavior, the API's request and response shapes, the dashboard, Manager tools, Telegram and Lark, dependencies, channels, billing and the database.
- **Model-visible changes:** No. The Manager's tools do not read the API document, so the changed `tasks.delete` text and the CLI help reach no model. No prompt text, tool schema, launch environment or Manager-facing text changed.

### 行为变化与入口

- **`loopercli create`**（`looper/loopercli.py`）。创建一个 ready 任务，第一行打印任务 id，随后打印 `ready; start it with: loopercli start <id>`。`--project` 现在必填（已有项目或要新建的项目），缺省时以用法错误失败。`--title` 可选，默认取需求的第一行，在词边界处截短到 60 个字符并加 `…`。新增 `--start`：创建成功后启动任务并打印 `<id>: started`。若创建需要确认则不启动任何任务：先运行 `loopercli confirm ID`，再运行 `loopercli start TASK`。`--json --start` 在启动失败时，单个答复的 `create` 字段带有创建响应。创建响应缺少任务 id 视为错误。选项帮助文字已改为面向 CLI 用户。
- **`loopercli start TASK`**。先读取任务。ready 任务被启动；stopped、failed、cancelled 任务通过 restart 操作从已保存的计划继续，保留已接受的步骤，并打印 `continuing from its saved plan`；运行中的任务（或处于 in-progress、needs-you 分组的任务）原样成功并打印 `already running`；已完成或处于其他状态的任务被拒绝。此前 `start` 只调用 start 操作。
- **`loopercli delete TASK`**（新增）。调用 `tasks.delete`：运行中的任务被拒绝；ready、stopped、failed、cancelled、completed 任务连同其工作区被删除，结果分支保留。沿用现有的高风险确认流程：客户端令牌得到确认 id 并运行 `loopercli confirm ID`；操作员令牌直接执行。
- **`loopercli stop TASK`** 行为不变。`loopercli tasks --help` 列出全部 tasks.* 操作，包括 delete。
- **`tasks.delete` 描述**（`looper/agents/v1_domains/workspaces.py`）。API 文档中的摘要和描述现在写作 “Delete a non-running task and its workspaces” 并列出可接受的状态，此前写作 “stopped task”。只改了文字；删除任务的服务器代码未动，本来就只拒绝运行中的任务。
- **文档与测试。**`docs/architecture/agent-system.md` 新增 “Task lifecycle” 一节。扩展了 `tests/test_loopercli.py`，`tests/test_api_v1_task_workspaces_db.py` 的删除测试现在对 init、stopped、failed、cancelled、completed 任务都运行。
- **不变：**服务器行为、API 的请求和响应结构、仪表盘、Manager 工具、Telegram 和 Lark、依赖、渠道、计费和数据库。
- **面向模型的变化：**无。Manager 的工具不读取 API 文档，所以 `tasks.delete` 文字的变化和 CLI 帮助不会到达任何模型。提示文字、工具 schema、启动环境和面向 Manager 的文字均无变化。

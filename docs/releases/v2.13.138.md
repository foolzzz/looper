# Looper v2.13.138

## Release Decision

**Who should upgrade:** Anyone who runs scenario Managers (non-default Managers with task templates) and wants to move them between installations with the configuration export and import. Everyone else can stay on v2.13.137: an export without such Managers keeps the unchanged `looper-config/v3` shape.

**What this release solves:** [#670](https://github.com/foolzzz/looper/pull/670) lets the configuration export and import carry scenario Manager definitions and their task templates. Until now the export left them out. They travel in a new `looper-config/v4` document through the existing dry-run preview and confirmation flow, and importing them needs operator identity.

**Breaking changes:** No. A file with no scenario Manager and no added bot is still written as `looper-config/v3`, and v1, v2 and v3 files still import. Only an export that includes such a Manager or bot is written as v4, which a build older than this release rejects with a format error. A v1 to v3 file that carries `managers` is now refused.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#670](https://github.com/foolzzz/looper/pull/670); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.138
```

## Behavior changes

- **Export (#670):** `looper/agents/config_transfer.py` writes `looper-config/v4` when any non-default Manager exists or when added bots were left out of the file; otherwise it writes v3 as before. The new `managers` section holds each Manager by its immutable id (`manager` or `manager-<key>`). The default Manager carries only `id`, `name` and `description`. Other Managers also carry `system_prompt`, `tools`, `task_scope`, `task_policy`, `enabled`, `profile` (by name) and `templates`. Templates carry `key`, `name`, `description`, `workspace_mode`, `requirement`, `planner_instructions`, `role_templates`, `inputs`, `project` (by name) and `profiles` (by name for planner, worker and reviewer). A template with a local working directory exports `repoint: true` and not the path. Templates of deleted Managers are not exported. Added bots are still not exported. The export summary reports `format` and the counts `managers` and `manager.templates`, and `looper config export` shows the written format.
- **Import (#670):** `read_file` accepts v4 and refuses `managers` in any older format, or a non-list. The import validates every Manager and template before writing any, and rejects a file that cannot be applied:
  - an id that is neither `manager` nor `manager-<key>`, duplicate ids, keys or names, unknown fields, or a name already used by another live Manager;
  - a deleted Manager's id ("choose a new immutable id"), a new definition without `system_prompt`, extra fields on the default Manager entry, or more enabled Managers than the limit;
  - a profile, project or role template that is missing or invalid, or a profile not on the project's list.
  
  Managers are matched by id and templates by Manager and key; other entries still match by name. Disables are applied before enables to respect the limit. A template's working directory is never taken from the file: an existing target directory is kept, a new template gets none, and the plan notes that it must be repointed. Unchanged Managers and templates are left alone, including their revision and timestamp (`only_if_changed`). Apply locks the Managers and re-previews the whole file in the same transaction first. After the commit, each added or changed Manager is announced through the Manager change callback. Nothing missing from the file is removed.
- **Authorization (#670):** a configuration upload is staged with the identity that sent it. A client identity (not operator) is refused for any file with `managers`, an added bot (a channel other than the built-in ones, or a non-default `manager_id`), or a Manager install. The check runs at upload, before a confirmation is created, and again when the confirmation executes, so a staged file cannot be upgraded later. The uploaded document is also validated against the v1 `ConfigDocument` schema, which now has one branch per format and the new `ManagerConfig` and `TemplateConfig` schemas.
- **Command line (#670):** the `looper config` commands that are not operator-only gain `--url` and `--operator-token-file`, and `config export` and `config import` take them too.
- **Dashboard (#670):** the Import/Export text now says that scenario Managers and their task templates are included, that matching is by immutable id for Managers, by Manager and key for templates and by name for the rest, and that local working directories stay on the machine and must be repointed. The plan lists "Managers" and "Templates".
- **Internal (#670):** `managers_api.checked_values` and `checked_template_values` are split out of the Manager and template writers, and the profile and project lookups take a connection, so an import sees objects created in its own transaction. The manager writers behave as before.
- **Runtime behavior:** no change to running Managers or tasks unless a Manager is imported.
- **Model-visible changes:** none to prompts, tool declarations or tool results. The configuration schemas are deliberately separate from the model-visible tool schemas. An imported Manager's `system_prompt` and template text are stored as data and reach a model only when that Manager runs, as if created by hand.
- **Line counts:** the description reports tests 760 and production 493 added lines (fixtures excluded).

## Upgrade and rollback

Re-run `install.sh` once v2.13.138 is published. No schema or configuration change. Rolling back to v2.13.137 restores the earlier export, which leaves Managers out; a v4 file written by this release cannot be imported there, so export again after rolling back.

### 升级决策

**谁需要升级：**使用场景 Manager（带任务模板的非默认 Manager）并希望通过配置导出/导入在不同安装间迁移的用户。其他人可留在 v2.13.137：不含此类 Manager 的导出仍是不变的 `looper-config/v3`。

**解决了什么：**[#670](https://github.com/foolzzz/looper/pull/670) 让配置导出与导入可以携带场景 Manager 定义及其任务模板，此前导出不含它们。它们放在新的 `looper-config/v4` 文档中，经现有的 dry-run 预览与确认流程导入，且导入需要 operator 身份。

**是否有破坏性变更：**否。不含场景 Manager 和新增 bot 的文件仍写为 `looper-config/v3`，v1、v2、v3 文件仍可导入。只有包含此类 Manager 或 bot 的导出才写为 v4，早于本版本的构建会以格式错误拒绝它。v1 至 v3 文件若带 `managers` 现在会被拒绝。

**如何验证：**运行 `looper --version` 核对版本为 2.13.138。

**贡献者：**维护者 @foolzzz 提交 [#670](https://github.com/foolzzz/looper/pull/670)；本次 patch release 无社区贡献。

```bash
looper --version   # looper 2.13.138
```

### 行为变化与入口

- **导出（#670）：**存在任何非默认 Manager，或有新增 bot 被排除在文件之外时，`looper/agents/config_transfer.py` 写出 `looper-config/v4`，否则仍写 v3。新的 `managers` 段以不可变 id（`manager` 或 `manager-<key>`）记录各 Manager。默认 Manager 只含 `id`、`name`、`description`；其他 Manager 还含 `system_prompt`、`tools`、`task_scope`、`task_policy`、`enabled`、`profile`（按名称）和 `templates`。模板含 `key`、`name`、`description`、`workspace_mode`、`requirement`、`planner_instructions`、`role_templates`、`inputs`、`project`（按名称）以及 planner、worker、reviewer 的 `profiles`（按名称）。带本地工作目录的模板导出 `repoint: true` 而不是路径。已删除 Manager 的模板不导出；新增 bot 仍不导出。导出摘要报告 `format` 以及 `managers`、`manager.templates` 数量，`looper config export` 显示写出的格式。
- **导入（#670）：**`read_file` 接受 v4，并拒绝旧格式中的 `managers` 或非列表值。导入在写入任何内容前校验所有 Manager 与模板，无法应用的文件会被拒绝：
  - id 不是 `manager` 或 `manager-<key>`、id/key/名称重复、未知字段，或名称已被另一个存活 Manager 使用；
  - 已删除 Manager 的 id（“请选择新的不可变 id”）、缺少 `system_prompt` 的新定义、默认 Manager 条目含多余字段，或启用的 Manager 超过上限；
  - profile、project 或 role template 缺失或无效，或 profile 不在项目列表中。

  Manager 按 id 匹配，模板按 Manager 与 key 匹配，其他条目仍按名称匹配。先停用后启用以遵守上限。模板的工作目录绝不取自文件：已有目标目录保留，新模板没有目录，计划会提示需要重新指向。未变化的 Manager 和模板保持不动，包括其修订号与时间戳（`only_if_changed`）。应用时先锁定 Manager，并在同一事务中先对整个文件重新预览。提交后，对每个新增或变更的 Manager 触发 Manager 变更回调。文件中缺失的条目不会被删除。
- **授权（#670）：**配置上传以发送者的身份暂存。非 operator 的 client 身份被拒绝上传含 `managers`、新增 bot（非内置通道或 `manager_id` 不是默认值）或 Manager 安装的文件。检查发生在上传时、创建确认之前，以及确认执行时再次进行，因此暂存文件之后无法被提权。上传的文档还会按 v1 `ConfigDocument` 模式校验，该模式现按格式分支，并新增 `ManagerConfig` 与 `TemplateConfig` 模式。
- **命令行（#670）：**非 operator-only 的 `looper config` 命令新增 `--url` 与 `--operator-token-file`，`config export` 与 `config import` 也接受它们。
- **仪表盘（#670）：**导入/导出文案说明包含场景 Manager 及其任务模板，匹配规则（Manager 按不可变 id、模板按 Manager 与 key、其余按名称），并说明本地工作目录留在本机、需要重新指向。计划列出“Managers”和“Templates”。
- **内部（#670）：**`managers_api.checked_values` 与 `checked_template_values` 从 Manager 与模板写入逻辑中拆出，profile 与项目查询可接受连接，使导入能看到同一事务中创建的对象。Manager 的原有写入行为不变。
- **运行时行为：**除非导入了 Manager，运行中的 Manager 与任务无变化。
- **面向模型的变化：**提示词、tool 声明和 tool 结果均无变化。配置模式刻意与面向模型的 tool 模式分开。导入的 Manager 的 `system_prompt` 与模板文本作为数据存储，只在该 Manager 运行时才到达模型，与手工创建无异。
- **行数：**描述报告新增测试 760 行、生产代码 493 行（不含 fixtures）。

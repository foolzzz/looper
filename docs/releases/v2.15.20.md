# Looper v2.15.20

This release documents the changes merged since v2.15.19: the `subscription` schedule kind ([#1437](https://github.com/foolzzz/looper/pull/1437)) and the Advisor RFC ([#1435](https://github.com/foolzzz/looper/pull/1435), docs only). A subscription gives one message-stream window to a tool-less processor run and, once the operator has confirmed the target, pushes the result to an allowlisted direct chat or a bound group. Nothing about a subscription runs until one is created, and nothing is pushed until that target is confirmed. The Advisor RFC changes no code.

## Release Decision

**Who should upgrade:** Anyone who will create a subscription. An installation that does not create one keeps its schedules, chats and prompts; startup applies one additive migration. The one change that applies with no subscription is how Lark and Telegram report `post`: the result is `sent`, `rejected` or `unknown`, and a Lark success without a message id counts as sent.

**What this release solves:** An operator can run a message-stream window through the tool-less processor on a schedule and, after confirming the target, push that result as the bot, at most once. The Advisor phase-1 design is written down before any of its code.

**Breaking changes:** No. No API or schedule that exists today changes its result. A subscription does nothing until one is created, and it pushes nothing until its target is confirmed. There is one additive PostgreSQL migration (see Upgrading). The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.15.20
```

**Contributors:** Maintainer @foolzzz authored [#1437](https://github.com/foolzzz/looper/pull/1437) and [#1435](https://github.com/foolzzz/looper/pull/1435); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.15.19 upgrades directly. Restart the service after upgrading, as for every release.

This release has one additive PostgreSQL migration, applied once at startup:

- `subscriptions`: widens `schedules.kind` so it accepts `subscription`, and creates `subscriptions`, `subscription_runs` and `subscription_deliveries` with their indexes and constraints. It is DDL only and writes no subscription row. The tables stay empty until an operator creates a subscription.

## Behavior changes

### Subscriptions, off until one is created and its target confirmed ([#1437](https://github.com/foolzzz/looper/pull/1437))

- **Until a subscription is created, nothing about it changes.** There is no setting that turns the kind on, and no row by default. Existing agent and command schedules, prompts, tool lists and the Manager's commands are unchanged. Creating one does not push: the schedule starts disabled, its cursor starts at the source's `committed_seq`, and `target_confirmed_at` is unset. Until the target is confirmed, the processor's output, and the run's failures and alerts, stay on the dashboard (`dashboard_only`). Nothing is sent.
- The migration name is `subscriptions`. `subscriptions` holds the stream (source, filter, window limits, `lines_v1`, quiet word, header, `cursor_seq`, `target_confirmed_at`, `target_confirmed_version`). `subscription_runs` holds each window and what the processor made. `subscription_deliveries` holds one row per message of a push.
- **Delivery is at most once.** Each segment goes `pending`, then `sending` (committed before the channel is asked), then `sent`, `failed` or `uncertain`. A segment left `sending` because the process died, or whose ask raised, or whose result is `unknown`, becomes `uncertain` and is never resent. Neither Lark's hour-long idempotency key nor Telegram's lack of one is relied on. `rejected` means the platform said no, or the call never left, and that segment is asked again, three asks in all. The cursor moves when some segment was sent or is uncertain, so that window is not read again; with nothing out, the next run reads it.
- **Confirmation binds a `config_version`.** It digests the target, the cron, the timezone, the source, and the processor's runtime (type, launcher, executable), provider (account, vendor, auth, the names of its environment variables), endpoint (protocol and URL without user, password or query), model (id, name, protocol), effort and managed hooks. No credential is in it. Enabling the schedule, or changing its target, cron or timezone, clears `target_confirmed_at`. Changing any bound processor fact, or the source, makes the live version differ from `target_confirmed_version`, so the output stays on the dashboard until the operator confirms the version they were just shown. `schedule_admin.confirm_target` refuses a version that is not the schedule's now. A request that enables or retargets and also changes the processor's profile is refused. The dashboard shows the same text under "Confirm push target…" and then calls `confirm_target`.
- The push target is an allowlisted direct chat or a bound group. An unbound group is refused. The message goes out as the Looper bot. Before every segment the run checks again that the target, the confirmation, the version and the allowlist or binding still match; if not, the rest stays on the dashboard.
- **The cursor** (`schedule_admin.reset_cursor`, field `after`, a time with its offset) moves to just before the first event the source stored after that time (`ingested_at`), so the next run reads exactly those events. A time in the future, to the microsecond, is refused. A reset is also refused while a run is in progress, and it waits for the source's writer lock (up to 20 seconds, otherwise 409).
- **The Manager sees state and counts only.** `looper_schedules` can list and get a subscription, and the run list keeps status, trigger, time and cost. It does not return the output, the run summary or an error that can carry message text, and it cannot create, change, enable, run or delete one. No other role's prompt or tool list mentions subscriptions.
- A firing with nothing selected starts no agent, counts `skipped_gate` and moves the cursor. The quiet word (any case, Markdown marks stripped) or an empty reply pushes nothing and moves the cursor. Other replies are split at 4,000 characters, three messages at most.

### Channel post results ([#1437](https://github.com/foolzzz/looper/pull/1437))

Lark and Telegram `post` now return a typed `PostReceipt.result`: `sent`, `rejected` or `unknown`. `rejected` is the platform saying no, or a call that never left (Lark: an API error code, lark-cli's own validation, or the process did not start; Telegram: bad request, forbidden, migrated, flood control, or a bad token). `unknown` is anything that may have been accepted: a timeout, a lost or unreadable answer, or a receipt that says nothing. A Lark answer that is a success (lark-cli `ok: true`, or the Bot API's HTTP 200 with `code` 0) is `sent` even without a message id, and replies to it cannot be routed.

What this changes for other callers of `post`:

- A user gate still decides from `success`, not from the typed result. A post that sent nothing is still tried again (three tries, after 2 and 8 minutes). Telegram still has no idempotency key, so a gate post retried after a lost answer may arrive twice. Lark still sends one message per `gate-<id>` key within an hour. The typed result changes a gate only for a Lark success that carries no message id: that post is now recorded as sent, where it used to be recorded as not sent and retried. Replies to it cannot be routed.
- A channel that cannot post (the web channel) and a channel that is not running answer `rejected`, and `success` is still false. A caller that only checks `success` sees the same refusal. Chat replies (`deliver`) are unchanged.
- Logs of a Lark or Telegram post failure name the error type and, for Lark, the API code. They do not include the error text. The receipt still holds that text, and a gate's activity still records it. A schedule notice that could not be sent is logged without the error text; the notice sent for an agent or command schedule is unchanged.

### The Advisor RFC ([#1435](https://github.com/foolzzz/looper/pull/1435))

- Docs only. `docs/architecture/rfcs/advisor-v0.zh-CN.md` defines phase 1, in which only the Planner consults: code forces a consult at the checkpoint before a `critical` step's Worker starts, and otherwise the Planner may choose `advise` in [PLAN] and in every [DECISION], never in [CHAT] or [GATE]. This phase sets no count or total-budget cap (alerts only). No code, schema, prompt or entry point changes.

## Optional Capability Activation & Use

### Subscriptions

**Activation:** Off until an operator creates a schedule of kind `subscription` and confirms its push target. There is no setting that turns the kind on. A new subscription is disabled, its cursor starts at the source's committed sequence, and `target_confirmed_at` is unset, so the output stays on the dashboard. The dashboard's "Confirm push target…" shows the target, the bot, the rule and its next three fires, the pushes per day, the processor's profile and where it comes from, whether the machine's managed hooks see the messages, and the caps. Confirming calls `schedule_admin.confirm_target` with the `config_version` just shown. A client that enables or retargets is shown the same text and confirms with `loopercli confirm`.

**Validation:** Before confirmation, a run with output ends `dashboard_only` and the channel is not asked. After `confirm_target` accepts the version the schedule has now, a firing with selected events runs the processor and posts to the confirmed direct chat or bound group. `schedule_admin.reset_cursor` with a future `after` is refused. The Manager's schedule list shows the subscription's state and counts, and not its output.

**Disable / rollback:** Disable the schedule, or delete it (its subscription rows go with it). Changing the target, the cron, the timezone, or enabling it again, clears the confirmation; changing the processor's runtime, provider, endpoint, model, effort or hooks leaves the confirmed version behind. Either way the output stays on the dashboard and nothing is pushed. The tables are additive and unused while no subscription exists.

**Authority boundary:** An operator or an API client manages a subscription through `schedule_admin`, and a high-risk write waits for confirmation. The push goes out as the bot, only to an allowlisted direct chat or a bound group, and only while the confirmed `config_version` is still the schedule's. The Manager cannot create or change one and sees state and counts only. No other role's prompt or tool list mentions it. The processor runs with no tools. Logs of a push carry error types and ids, not message text.

**Docs:** https://github.com/foolzzz/looper/blob/v2.15.20/docs/architecture/agent-system.md#subscriptions-a-message-stream-on-a-time-rule

```bash
loopercli schedule-admin confirm-target --schedule-id SCHEDULE_ID --config-version CONFIG_VERSION
```

## 中文摘要

本版本说明自 v2.15.19 以来合并的改动：订阅这种定时任务（[#1437](https://github.com/foolzzz/looper/pull/1437)）和 Advisor RFC（[#1435](https://github.com/foolzzz/looper/pull/1435)，只改文档）。订阅把消息流的一个窗口交给不带工具的 processor；操作员确认目标之后，才把结果推送到已允许的私聊或已绑定的群。不创建订阅就没有这项行为，目标未确认之前也不推送。Advisor RFC 不改代码。

### 升级决策

**谁需要升级：**要创建订阅的安装。不创建订阅的安装，其定时任务、聊天和提示词保持原样；启动时会执行一个可加的迁移。没有订阅也会变的，只有 Lark 和 Telegram 对 `post` 的报告方式：结果是 `sent`、`rejected` 或 `unknown`，飞书成功但没有消息 id 时算已发送。

**解决了什么：**操作员可以按时间规则，用没有工具的 processor 处理消息流窗口，并在确认目标后以机器人身份把结果推送出去，而且至多发送一次。Advisor 第一期的设计在写代码之前先定下来。

**是否有破坏性变更：**无。今天已有的 API 和定时任务的结果不变。订阅在创建之前不做任何事，目标确认之前也不推送。有一个可加的 PostgreSQL 迁移（见升级）。桥接边界不变：早于 v2.13.165 的安装须先升级到 v2.13.165。

**如何验证：**核对版本为 2.15.20。

**贡献者：**维护者 @foolzzz 提交 [#1437](https://github.com/foolzzz/looper/pull/1437) 和 [#1435](https://github.com/foolzzz/looper/pull/1435)；本版本无社区贡献。

```bash

```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.15.19 上的安装可直接升级。升级后照常重启服务。

本版本有一个可加的 PostgreSQL 迁移，启动时执行一次：

- `subscriptions`：放宽 `schedules.kind`，使它接受 `subscription`，并创建 `subscriptions`、`subscription_runs` 和 `subscription_deliveries` 及其索引和约束。只有 DDL，不写订阅行。操作员创建订阅之前，这些表保持为空。

### 行为变化与入口

**订阅，创建并确认目标之前关闭（[#1437](https://github.com/foolzzz/looper/pull/1437)）**

- **不创建订阅就没有这项行为。**没有单独的开关，默认也没有行。已有的 agent 和命令定时任务、提示词、工具列表和 Manager 的命令都不变。创建之后也不会立刻推送：定时任务一开始是停用的，游标从该来源的 `committed_seq` 起，`target_confirmed_at` 为空。目标确认之前，processor 的输出以及这次运行的失败和告警都留在仪表盘（`dashboard_only`）。什么都不发送。
- 迁移名是 `subscriptions`。`subscriptions` 存放读取配置（来源、筛选、窗口限制、`lines_v1`、静默词、标题、`cursor_seq`、`target_confirmed_at`、`target_confirmed_version`）。`subscription_runs` 存放每个窗口和 processor 的产出。`subscription_deliveries` 是一次推送里的每一条消息。
- **投递至多一次。**每一段从 `pending` 到 `sending`（问渠道之前先提交），再到 `sent`、`failed` 或 `uncertain`。进程死在 `sending`、询问抛出异常、或结果是 `unknown` 时，这一段变成 `uncertain`，永不再发。不依赖飞书大约一小时的幂等键，也不依赖 Telegram 没有幂等键这一点。`rejected` 表示平台拒绝，或调用根本没发出去，这一段会再问，一共三次。有的段已发送或处于 `uncertain` 时游标才前进，这个窗口不会再读；一条都没出去时，下一次运行仍读它。
- **确认绑定一个 `config_version`。**它摘要的是目标、cron、时区、来源，以及 processor 的 runtime（类型、launcher、可执行文件）、provider（账号、vendor、auth、环境变量名）、endpoint（协议和去掉用户、密码、查询的 URL）、model（id、名字、协议）、effort 和受管理的 hooks。里面没有凭据。启用、或改目标、cron、时区，会清掉 `target_confirmed_at`。改上述任一 processor 事实或来源后，当前版本与 `target_confirmed_version` 不一致，输出留在仪表盘，直到操作员确认刚看到的那个版本。`schedule_admin.confirm_target` 拒绝与当前定时任务不符的版本。同一次请求里既启用或改目标、又改 processor 的 Profile，会被拒绝。仪表盘在「Confirm push target…」里显示同一段文字，然后调用 `confirm_target`。
- 推送目标是已允许的私聊，或已绑定的群。未绑定的群会被拒绝。消息以 Looper 机器人的身份发出。每一段发送前都会再查一次：目标、确认、版本，以及允许名单或绑定仍然相符；否则剩下的留在仪表盘。
- **游标**（`schedule_admin.reset_cursor`，字段 `after`，带偏移的时间）移到该来源在这个时间之后入库的第一条事件之前（`ingested_at`），因此下一次运行恰好读这些事件。未来的时间，精确到微秒，都会拒绝。运行进行中也拒绝重置。重置会等来源的写入锁（最多 20 秒，否则 409）。
- **Manager 只看到状态和计数。**`looper_schedules` 可以列出和读取订阅，运行列表保留状态、触发方式、时间和花费。它不返回输出、运行摘要，以及可能带有消息正文的错误，也不能创建、修改、启用、立即运行或删除订阅。其他角色的提示词和工具列表都不提订阅。
- 没有选中事件的一次触发不启动 agent，记一次 `skipped_gate` 并移动游标。静默词（不区分大小写，去掉 Markdown 记号）或空回复不推送并移动游标。其他回复按 4,000 字切开，最多三条。

**渠道 post 的结果（[#1437](https://github.com/foolzzz/looper/pull/1437)）**

Lark 和 Telegram 的 `post` 现在返回类型化的 `PostReceipt.result`：`sent`、`rejected` 或 `unknown`。`rejected` 是平台拒绝，或调用没有发出去（Lark：API 错误码、lark-cli 自己的校验，或进程没启动；Telegram：错误请求、禁止、会话迁移、洪水控制或 token 不对）。`unknown` 是消息可能已经被接受：超时、回答丢失或读不出来、或回执什么都没说。飞书的成功回答（lark-cli `ok: true`，或 Bot API 的 HTTP 200 且 `code` 为 0）即使没有消息 id 也是 `sent`，对它的回复无法路由。

对其他 `post` 调用方：

- 用户关卡仍看 `success`，不看类型化结果。什么都没发出去的 post 仍会再试（一共三次，隔 2 分钟和 8 分钟）。Telegram 仍没有幂等键，所以关卡消息在回答丢失后重试，仍可能到两次。Lark 仍在一小时内对每个 `gate-<id>` 键只发一条。类型化结果对关卡的唯一变化是：飞书成功但没有消息 id 时，现在记为已发送；以前记为没发出去并重试。对它的回复无法路由。
- 不能 post 的渠道（web）和没有在运行的渠道回答 `rejected`，`success` 仍是 false。只检查 `success` 的调用方看到的仍是同一次拒绝。聊天回复（`deliver`）不变。
- Lark 或 Telegram 的 post 失败日志只写错误类型，Lark 再加 API 错误码，不写错误正文。回执里仍有正文，关卡的活动记录仍记下它。定时任务的通知发不出去时，日志也不再带错误正文；agent 和命令类定时任务发出的通知本身不变。

**Advisor RFC（[#1435](https://github.com/foolzzz/looper/pull/1435)）**

- 只改文档。`docs/architecture/rfcs/advisor-v0.zh-CN.md` 定义第一期：只有规划者能请教。代码只在一处强制请教，即 `critical` 步骤的 Worker 启动前的检查点；其余由规划者在 [PLAN] 和每次 [DECISION] 里自选 `advise`，[CHAT] 和 [GATE] 不可以。本期不设次数和总预算上限（只告警）。没有代码、表结构、提示词或入口的变化。

### 可选能力启用与使用

#### Subscriptions

**启用：**操作员创建 `kind` 为 `subscription` 的定时任务并确认推送目标之前，这项能力是关的。没有单独的开关。新建的订阅是停用的，游标从来源已提交的序号起，`target_confirmed_at` 为空，因此输出留在仪表盘。仪表盘的「Confirm push target…」显示目标、机器人、规则和接下来三次触发、每天最多推送几次、processor 的 Profile 及其来源、本机受管理的 hooks 会不会看到消息，以及花费上限。确认时带上刚显示的 `config_version` 调用 `schedule_admin.confirm_target`。启用或改目标的客户端会看到同一段文字，并用 `loopercli confirm` 确认。

**验证：**确认之前，有输出的运行以 `dashboard_only` 结束，不会去问渠道。`confirm_target` 接受定时任务当前的版本之后，选中了事件的一次触发会运行 processor，并推送到已确认的私聊或已绑定的群。`schedule_admin.reset_cursor` 的 `after` 若在未来则被拒绝。Manager 的定时任务列表只显示订阅的状态和计数，不显示输出。

**停用 / 回退：**停用该定时任务，或删除它（订阅行随它一起删除）。改目标、cron、时区，或再次启用，会清掉确认；改 processor 的 runtime、provider、endpoint、model、effort 或 hooks，会使已确认的版本失效。两种情况下输出都留在仪表盘，不再推送。新表是可加的，没有订阅时不被使用。

**权限边界：**操作员或 API 客户端经 `schedule_admin` 管理订阅，高风险写入要等确认。推送以机器人身份发出，只发到已允许的私聊或已绑定的群，并且只在已确认的 `config_version` 仍是该定时任务的当前版本时发出。Manager 不能创建或修改订阅，只看到状态和计数。其他角色的提示词和工具列表都不提它。processor 运行时不带工具。推送的日志只有错误类型和 id，没有消息正文。

```bash
loopercli schedule-admin confirm-target --schedule-id SCHEDULE_ID --config-version CONFIG_VERSION
```

# Looper v2.14.47

This is the patch release v2.14.47, a hotfix line in which each merged change ships at once. It ships the two changes merged since v2.14.46: the Telegram adapter retries a handler that failed before publishing, makes the backlog cap settable and stops caching a restored progress route ([#994](https://github.com/foolzzz/looper/pull/994)), and the dashboard's command run history and schedule alert follow-ups are finished ([#1009](https://github.com/foolzzz/looper/pull/1009)).

## Release Decision

**Who should upgrade:** Anyone who runs Telegram channels and wants an update whose handler failed early to be retried instead of left pending, or who sets `backlog_max_age_seconds` through the API or config export; and anyone who uses the dashboard's command schedules and their run history.

**What this release solves:** [#994](https://github.com/foolzzz/looper/pull/994) retries a Telegram handler that raised before it reached the bus, lets the Telegram channel config set `backlog_max_age_seconds` (which earlier notes already called settable), and sends task progress for a chat restored from `reply_route` without caching the correlation. [#1009](https://github.com/foolzzz/looper/pull/1009) fixes the command run history and schedule form in the dashboard: per-schedule failure threshold on the badge, the overlap alert colour, reopening a row from a second run link, a correct last-200-lines log preview for large logs, exit codes on succeeded runs, a note instead of an empty box for a run with no log, and command-specific form hints and field errors.

**Breaking changes:** No. No API or configuration is removed, and there is no new migration or setting. The Telegram channel config schema gains the optional `backlog_max_age_seconds` integer (minimum 1).

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#994](https://github.com/foolzzz/looper/pull/994) and [#1009](https://github.com/foolzzz/looper/pull/1009); no community contribution was included in this release.


## Behavior changes

- **Telegram handler retry ([#994](https://github.com/foolzzz/looper/pull/994)).** If a handler raises before the message reached `bus.publish`, it is retried up to two more times (after 1 s and then 2 s, so about 3 s at most) before the update is left pending for replay. An update is marked processed only after its handler returned or the age cap dropped it. A handler that already reached `bus.publish` is never retried, so a message is never published twice. Retries stop once the adapter is shutting down. A final failure is logged and re-raised as before.
- **Backlog cap.** The Telegram channel config schema in the v1 API accepts `backlog_max_age_seconds` (integer, at least 1), and the config export treats it as a public key, so it is exported as a value and not replaced by the secret placeholder.
- **Restored progress route.** A task progress update whose chat is restored from the envelope's `reply_route` is sent without caching the correlation, as Lark already does, so progress for a task loaded after a restart reaches its chat once. Replayed Manager answers still restore and cache their chat.
- **Run log message.** `run_log` on a run that never started its command (zero log bytes) answers 404 "the command did not start, so this run has no log" instead of the retention-policy message.
- **Dashboard run history ([#1009](https://github.com/foolzzz/looper/pull/1009)).**
  - The failures badge turns destructive at each schedule's own `failures_after` threshold (default 3). The overlap alert on the overview uses the warning colour; the missed-deadline alert stays destructive.
  - A second run link of the same schedule reopens its row. The deadline and overlap alerts wrap onto their own line instead of cutting off the next-run time. Run rows show an expand chevron.
  - The log preview reads backwards in bounded 4 MiB windows (at most four) and decodes only after joining split UTF-8 sequences, so it shows the last 200 lines even when they exceed 1 MiB; when the window limit stops it short it says "Showing the last N lines; download the full log for the rest."
  - Succeeded command runs show their exit code. "Still running: the log grows" disappears when the run finishes. A run that did not start the command shows its error or summary and a short note instead of an empty log box and Download. Skipped runs show no duration.
  - The status filter keeps the routine-skips checkbox, now disabled while a status is chosen.
  - The schedule detail shows an Alerts block (success deadline, failure, stale and overlap thresholds) when any is non-default.
- **Dashboard command schedule form.** The notify hints use the schedule's failure threshold and say "command" for command schedules; the alerts section opens when the schedule has a deadline or non-default alert policy; server validation errors appear under their field (name, work_dir, cron, timezone, command, env, env_file, success_deadline and the alert thresholds); the ownership line is shown only for agent schedules.
- **Model-visible changes:** No. No prompt, tool description, tool schema or Manager confirmation text changes. The `run_log` message above is an API and CLI response.

### 行为变化与入口

- **Telegram 处理器重试（[#994](https://github.com/foolzzz/looper/pull/994)）。**处理器在消息到达 `bus.publish` 之前抛错时，最多再重试两次（分别等待 1 秒和 2 秒，合计约 3 秒），之后才把更新留待重放。更新只在处理器返回或被时限丢弃之后才标记为已处理。已到达 `bus.publish` 的处理器不会重试，因此消息不会重复发布。适配器关闭后不再重试。最终失败仍会记录日志并重新抛出。
- **积压上限。**v1 API 的 Telegram 渠道配置 schema 接受 `backlog_max_age_seconds`（整数，至少 1），配置导出把它当作公开键，按值导出而不是替换为密钥占位符。
- **恢复的进度路由。**其聊天由信封的 `reply_route` 恢复的任务进度更新，发送时不缓存关联（与 Lark 一致），因此重启后加载的任务的进度只会到达聊天一次。重放的 Manager 回答仍然恢复并缓存聊天。
- **运行日志信息。**对从未启动命令（日志为 0 字节）的运行调用 `run_log`，返回 404 “the command did not start, so this run has no log”，而不是保留策略的提示。
- **仪表盘运行历史（[#1009](https://github.com/foolzzz/looper/pull/1009)）。**
  - 失败徽章在达到各任务自己的 `failures_after` 阈值（默认 3）时变为危险色。概览中的重叠告警用警告色；错过最晚成功时间的告警仍为危险色。
  - 同一任务的第二个运行链接会重新展开该行。最晚成功时间和重叠告警另起一行换行，不再截断下次运行时间。运行行显示展开箭头。
  - 日志预览以 4 MiB 为窗口向前读取（最多四个窗口），拼接被切断的 UTF-8 序列后再解码，因此即使最后 200 行超过 1 MiB 也能正确显示；窗口上限使其不足时，会提示“Showing the last N lines; download the full log for the rest.”。
  - 成功的命令运行显示退出码。运行结束后“Still running: the log grows”消失。未启动命令的运行显示其错误或摘要和一条简短说明，而不是空日志框和下载按钮。跳过的运行不显示时长。
  - 状态过滤保留“常规跳过”复选框，选择状态时该复选框禁用。
  - 任何告警设置非默认时，定时任务详情显示“Alerts”块（最晚成功时间及失败、停滞、重叠阈值）。
- **仪表盘命令定时任务表单。**通知提示使用该任务的失败阈值，并对命令任务写“command”；有最晚成功时间或非默认告警策略时告警部分默认展开；服务端校验错误显示在对应字段下（name、work_dir、cron、timezone、command、env、env_file、success_deadline 及告警阈值）；归属行只对 agent 定时任务显示。
- **面向模型的变化：**无。没有 prompt、工具描述、工具 schema 或 Manager 确认文本的变化。上述 `run_log` 信息属于 API 和 CLI 响应。

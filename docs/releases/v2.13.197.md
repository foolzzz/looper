# Looper v2.13.197

## Release Decision

**Who should upgrade:** Developers of runtime and runner integrations. Everyone else sees no difference: every current runtime keeps its own process per Worker, Reviewer and consult run. It is a hotfix that ships the change merged since v2.13.196.

**What this release solves:** [#836](https://github.com/foolzzz/looper/pull/836) gives `WorkerPool` and consults a run handle that can be a process or a hosted runner session, so a later runtime can host runs without a process. Today's process code moves behind the handle unchanged; no runtime declares the hosted path yet.

**Breaking changes:** No. No command, database schema, file format or setting changed. The new `RuntimeAdapter.hosts_runs` declaration is `False` for every current runtime, so the hosted path is not taken.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#836](https://github.com/foolzzz/looper/pull/836); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.197
```

## Behavior changes

- **Run handle (`looper/agents/runtimes/channel.py`):** new `RunHandle` protocol (`command`, `pid`, `channel`, `launch`, `end`, `wait`, `error_output`, `dropped_input`), `RunStartError` and a `Fork` record (source session id, its directory, the consult's own fork directory).
- **Process run (`looper/agents/tiers/worker.py`):** `ProcessRun` holds the existing process code: spawn through `proc_tree`, the runtime's channel, process-tree cleanup once, exit code and stderr. A spawn `OSError` becomes `RunStartError` and fails the step as a missing executable did. `WorkerProcess` gains a `handle` field; server shutdown now ends each active handle instead of calling `proc_tree.end` directly. The prompt is now sent inside the guarded block that reads the stream, and the run's input channel is unregistered when the run ends.
- **Adapter hook (`looper/agents/runtimes/__init__.py`):** `RuntimeAdapter.hosts_runs` (`False` for every current runtime) and `hosted_run(...)`, which raises `RuntimeUnsupported` by default. Only a runtime that sets `hosts_runs` is ever asked for a hosted run; there is no fallback to a process.
- **Hosted path in the Worker (`worker.py`):** for a hosting runtime the pool skips the MCP entry for room and vault tools and passes `RoomTurnTools` (`looper/agents/runtimes/api/tools.py`, in-process room and vault tools) with the run's token. Run and task spend caps are read per authorization through a limits callback. `steer_applied` and `steer_dropped` events from the runner are recorded as task activity.
- **Dropped input (`worker.py`, `looper/agents/tiers/planner.py`):** a handle's `dropped_input()` is added to the result as `missed_input`, and the Planner appends those texts to the step's `missed_messages`. Process runs return an empty list, so nothing changes for them.
- **Hosted path in consults (`looper/agents/consult.py`):** a runtime with `hosts_runs` forks through `hosted_run(..., fork=Fork(...))` and runs `_execute_hosted`, which applies the process path's deadline and run recording, ends the handle once and treats a start failure as a runtime that cannot answer. The process path is unchanged.
- **Imports (`api/tools.py`):** the Manager and Planner ops imports are type-only now.
- **Scope:** 10 files, about 785 added lines including tests (the description reports tests 467, production 318).
- **Model-visible changes:** None for any current runtime. No prompt, tool description or tool result changed on the process path. A hosted runtime would show the model the room and vault tools in process instead of through MCP, but none is shipped in this release.

Re-run `install.sh` once v2.13.197 is published. There is nothing to configure. To roll back, return to v2.13.196; there is no schema or setting change.

## 中文摘要

### 升级决策

**谁需要升级：**开发运行时和 runner 集成的开发者；其他用户无差别，所有现有运行时的 Worker、Reviewer 和 consult 仍各用自己的进程。本版本是随合并即发布的 hotfix，包含 v2.13.196 之后合并的改动。

**解决了什么：**[#836](https://github.com/foolzzz/looper/pull/836) 让 `WorkerPool` 和 consult 使用可以是进程、也可以是托管 runner 会话的运行句柄，使后续运行时无需进程即可托管运行。现有进程代码原样移到句柄之后；目前没有运行时声明托管路径。

**是否有破坏性变更：**无。命令、数据库 schema、文件格式和设置均未改变。新增的 `RuntimeAdapter.hosts_runs` 对现有运行时均为 `False`，因此不会走托管路径。

**如何验证：**运行 `looper --version` 核对版本为 2.13.197。

**贡献者：**维护者 @foolzzz 提交 [#836](https://github.com/foolzzz/looper/pull/836)；本次 patch release 无社区贡献。

```bash
looper --version   # looper 2.13.197
```

### 行为变化与入口

- **运行句柄（`looper/agents/runtimes/channel.py`）：**新增 `RunHandle` 协议（`command`、`pid`、`channel`、`launch`、`end`、`wait`、`error_output`、`dropped_input`）、`RunStartError` 和 `Fork` 记录（源会话 id、其目录、consult 自己的分叉目录）。
- **进程运行（`looper/agents/tiers/worker.py`）：**`ProcessRun` 承载现有进程代码：经 `proc_tree` 启动、运行时的 channel、进程树清理仅执行一次、退出码和 stderr。启动时的 `OSError` 变为 `RunStartError`，与之前找不到可执行文件一样使该步骤失败。`WorkerProcess` 新增 `handle` 字段；服务器关闭时对每个活动句柄调用 `end`，不再直接调用 `proc_tree.end`。提示词现在在读取事件流的受保护块内发送，运行结束时会注销该运行的输入 channel。
- **适配器钩子（`looper/agents/runtimes/__init__.py`）：**`RuntimeAdapter.hosts_runs`（现有运行时均为 `False`）和 `hosted_run(...)`，默认抛出 `RuntimeUnsupported`。只有设置了 `hosts_runs` 的运行时才会被请求托管运行，不会回退为进程。
- **Worker 的托管路径（`worker.py`）：**对托管运行时，池不再为房间和知识库工具生成 MCP 条目，而是把带运行 token 的 `RoomTurnTools`（`looper/agents/runtimes/api/tools.py`，进程内房间与知识库工具）传入。运行和任务的花费上限在每次授权时通过 limits 回调读取。runner 的 `steer_applied` 与 `steer_dropped` 事件记为任务活动。
- **丢弃的输入（`worker.py`、`looper/agents/tiers/planner.py`）：**句柄的 `dropped_input()` 作为 `missed_input` 加入结果，Planner 把这些文本追加到该步骤的 `missed_messages`。进程运行返回空列表，行为不变。
- **consult 的托管路径（`looper/agents/consult.py`）：**`hosts_runs` 的运行时通过 `hosted_run(..., fork=Fork(...))` 分叉并运行 `_execute_hosted`，沿用进程路径的期限与运行记录，句柄只结束一次，启动失败视为该运行时无法作答。进程路径不变。
- **导入（`api/tools.py`）：**Manager 和 Planner 的 ops 导入现在仅用于类型。
- **范围：**10 个文件，含测试约新增 785 行（描述写的是测试 467 行、生产代码 318 行）。
- **面向模型的变化：**对现有运行时无。进程路径上的提示词、工具描述和工具结果均未改变。托管运行时会让模型经进程内而非 MCP 看到房间和知识库工具，但本版本未提供这样的运行时。

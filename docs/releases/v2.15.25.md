# Looper v2.15.25

This release documents the changes merged since v2.15.24. An enabled bot whose startup probe fails is retried, and one that stays down raises a system problem and one alert ([#1550](https://github.com/foolzzz/looper/pull/1550)); retry and the alert are on by default. Proactive messages can pass one recorded decision ([#1486](https://github.com/foolzzz/looper/pull/1486), `delivery.enabled`, default off); only gate reminders are wired, and they still go out. Manager turns and proactive sends can be measured ([#1488](https://github.com/foolzzz/looper/pull/1488), `manager.metrics.enabled`, default off), and the dashboard home shows that summary ([#1509](https://github.com/foolzzz/looper/pull/1509)). Typed turn context can be stored ([#1497](https://github.com/foolzzz/looper/pull/1497), `manager.turn_context.enabled`, default off); storing it changes no prompt. One-time reminders ([#1505](https://github.com/foolzzz/looper/pull/1505), `reminders.enabled`, default off) and card buttons for confirmations and user gates ([#1489](https://github.com/foolzzz/looper/pull/1489), `cards.actions.enabled`, default off) stay off until set. Each session keeps its own lifecycle lock, research sources and settings ([#1516](https://github.com/foolzzz/looper/pull/1516)); with only `main`, behavior is unchanged. Pull-request tests run in six shards ([#1536](https://github.com/foolzzz/looper/pull/1536)). The reminder-dialog eval no longer depends on the clock ([#1534](https://github.com/foolzzz/looper/pull/1534)). Five pull requests are documentation only ([#1511](https://github.com/foolzzz/looper/pull/1511), [#1520](https://github.com/foolzzz/looper/pull/1520), [#1523](https://github.com/foolzzz/looper/pull/1523), [#1522](https://github.com/foolzzz/looper/pull/1522), [#1525](https://github.com/foolzzz/looper/pull/1525)). The v2.15.24 addendum ([#1524](https://github.com/foolzzz/looper/pull/1524)) only records pulls already shipped on that tag. This release is tagged on its release commit, which contains main up to [#1550](https://github.com/foolzzz/looper/pull/1550): it does not contain [#1493](https://github.com/foolzzz/looper/pull/1493), [#1514](https://github.com/foolzzz/looper/pull/1514), [#1513](https://github.com/foolzzz/looper/pull/1513), [#1487](https://github.com/foolzzz/looper/pull/1487), [#1518](https://github.com/foolzzz/looper/pull/1518), [#1519](https://github.com/foolzzz/looper/pull/1519), [#1502](https://github.com/foolzzz/looper/pull/1502) or [#1517](https://github.com/foolzzz/looper/pull/1517), which merged after the scope was frozen and ship in the next release with their notes.

## Release Decision

**Who should upgrade:** Anyone running Telegram or Lark, and anyone who will turn on proactive delivery, Manager metrics, turn context, one-time reminders or card buttons. An installation that turns none of them on still applies the additive migrations at startup, still retries a failed channel start, and still raises a channel-down problem. With those switches left off, the Manager's prompts and tool lists stay as in v2.15.24. `web/` changed, so the dashboard bundle is rebuilt by the release workflow as usual.

**What this release solves:** A bot that fails its startup probe is retried until it starts, or until it is disabled or deleted, instead of staying down until the next service restart. An outage longer than the threshold is shown on the dashboard and, when another healthy bot can reach the operator, sent once, with one notice when it recovers. The operator can record why a gate reminder went out, record Manager latency and proactive receipts, store a turn-context setting, set a one-time reminder, and answer a confirmation or a user gate with a card button. Each of those five stays off until turned on.

**Breaking changes:** No. No existing API drops a field that a caller must send. A failed channel startup is retried, and a sustained outage adds a system problem and at most one notice through another bot; both are under Behavior changes. There are additive PostgreSQL migrations (see Upgrading). The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older. `channel_down_alert.get`, `channel_down_alert.update`, `proactive_delivery.get`, `proactive_delivery.update`, `manager_metrics_settings.get`, `manager_metrics_settings.update`, `manager_metrics.get`, `turn_context_settings.get` and `turn_context_settings.update` are new operations.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.15.25
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.15.24 upgrades directly. Restart the service after upgrading, as for every release. `web/` changed, so the release workflow rebuilds the dashboard bundle from `web/` into the wheel, as usual. This pull request does not commit that bundle.

This release has additive PostgreSQL migrations, applied once at startup, inside the schema transaction. None of them has an online step. None of them rewrites a row of an existing table. A fresh database creates the same tables from `schema.sql` and does not record a separate migration for a table it already has. A database that has not yet finished an earlier online step still runs that step.

- `card_actions` ([#1489](https://github.com/foolzzz/looper/pull/1489)): creates `card_actions` and `idx_card_actions_open` (partial, on open rows). One row per card, keyed by the opaque token a button carries. `kind` is `confirmation` or `gate`. The checks are part of the table. Rows are written only while `cards.actions.enabled` is on.
- `reminders` ([#1505](https://github.com/foolzzz/looper/pull/1505)): creates `reminders` and the partial index `idx_reminders_due` (`due_at` where `status` is `pending` or `sending`). `status` is `pending`, `sending`, `delivered`, `failed`, `uncertain`, `missed` or `cancelled`. `settled_at` is set exactly when the row is settled. Nothing is written while `reminders.enabled` is off.
- `proactive_deliveries` ([#1488](https://github.com/foolzzz/looper/pull/1488)): creates `proactive_deliveries` and `idx_proactive_deliveries_open`, `idx_proactive_deliveries_sent`, the unique partial `idx_proactive_deliveries_dedupe` (where `dedupe_key` is not null), `idx_proactive_deliveries_counted`, `idx_proactive_deliveries_digest`, `idx_proactive_deliveries_task`, `idx_proactive_deliveries_schedule` and `idx_proactive_deliveries_decided`. `source` includes `completion` and `user_reminder`. `chat_kind` is `direct` or `group`. `outcome` and `sent_at` are null together. Decision columns stay null until the delivery layer writes them. [#1486](https://github.com/foolzzz/looper/pull/1486) adds no table and no migration; with its switch on it fills the decision on the row this migration created.

[#1550](https://github.com/foolzzz/looper/pull/1550), [#1509](https://github.com/foolzzz/looper/pull/1509), [#1497](https://github.com/foolzzz/looper/pull/1497), [#1516](https://github.com/foolzzz/looper/pull/1516), [#1536](https://github.com/foolzzz/looper/pull/1536) and [#1534](https://github.com/foolzzz/looper/pull/1534) add no schema. [#1550](https://github.com/foolzzz/looper/pull/1550) stores `channels.down_alert_minutes` and `channels.down_state:` plus the channel id in system settings, written when an outage is tracked. [#1488](https://github.com/foolzzz/looper/pull/1488), [#1486](https://github.com/foolzzz/looper/pull/1486) and [#1497](https://github.com/foolzzz/looper/pull/1497) store their switches as system-settings rows, written only when an operator sets them. Housekeeping deletes `proactive_deliveries` rows older than 90 days; while both metrics and delivery are off, that table stays empty.

## Behavior changes

### Channel startup retry and down alerts, on by default ([#1550](https://github.com/foolzzz/looper/pull/1550))

This changes default behavior for every enabled Telegram or Lark bot. There is no switch that turns it off. Previously a failed startup probe left the channel down until the next service restart.

- **Retry.** The first attempt is the startup attempt. A transport failure (`ChannelStartError` marked transient, an `httpx` transport error, a timeout, a connection error, or a Telegram network or retry-after error that is not a bad request) waits 30 seconds and then doubles, capped at 10 minutes. Any other failure, including a credential or configuration failure, waits 10 minutes and is reported as `failed` while the retry continues. Each retry reads the saved settings and starts the adapter again, including bindings and catch-up. Disabling or deleting the bot cancels the retry and drops an adapter that retry just registered. Shutdown cancels every retry.
- **Status.** System status and `channel_configs` expose a read-only `runtime`: `starting`, `running`, `retrying` or `failed`, with the last error and the next attempt, or null when the bot is disabled or this server did not start it. A successful start clears it.
- **Down longer than the threshold.** Every 30 seconds, an enabled bot that is not running, or whose deliveries have all failed, is down. After more than `channels.down_alert_minutes` (default 10; no row, or a stored value that is not a positive whole number, is 10), system status includes one problem, id `channel_down:<channel_id>`. The dashboard's existing top banner shows it and refreshes every 30 seconds, including after recovery, without a reload. A successful delivery ends a failure streak. A running bot recovers when a success falls inside the outage. Phase updates, streaming deltas, empty replies, missing chat routes, and dashboard-only schedule rows (including a pre-send refusal for a removed target or a missing sender) do not count as a failed delivery and do not prove recovery. A real sender failure stays `failed`.
- **One alert, one recovery.** The outage is stored (`channels.down_state:` plus the channel id) before anything is sent. One notice goes through every other enabled bot that is not itself down and that has an `operator_sender_id`. The affected bot never carries it. Each attempt waits at most 20 seconds. A failed, uncertain or interrupted attempt is not retried for that outage. With no such bot, the banner is the only alert. Recovery sends one notice the same way. Disabling the bot clears its problem and its interval.
- **Only the operator can read or set the threshold.** `POST /api/v1/channel_down_alert/get` and `POST /api/v1/channel_down_alert/update` are operator-only. The update is high risk and applies at once. A positive whole number of minutes stores that number. `null` deletes the row and restores 10. An API client token gets 403, and nothing is stored. `chat_settings` does not carry the field. No Manager tool lists it. Healthy bots send the same messages as before.

### Proactive delivery, off ([#1486](https://github.com/foolzzz/looper/pull/1486))

- **`delivery.enabled` defaults off.** No row, or any value other than the string `true`, leaves it off. Until startup has loaded settings, it is off. There is no dashboard switch. `chat_settings.get` and `chat_settings.update` do not carry the field.
- **Only the operator can read or set it.** `POST /api/v1/proactive_delivery/get` and `POST /api/v1/proactive_delivery/update` are operator-only. The update is high risk: its impact preview names `delivery.enabled` and says whether the next wired message is decided before it goes out. The operator's call applies at once. `true` stores `true`. `false` stores `false`. `null` deletes the row and restores off. An API client token gets 403, and nothing is stored.
- **While it is off,** the gate courier posts the same reminders and the layer writes nothing.
- **While it is on,** only gate reminders ask `decide()`. A reminder is `blocking` (it is due only for a gate that holds the steps after it), so the decision is send, uncounted (`urgent`): quiet hours (22:00 included through 08:00, in `user.timezone`, else the server's zone) and the direct-chat cap of 5 counted messages do not hold it. The reminder text and target are unchanged. The row records `decision`, `reason`, `counted`, `local_date`, `digest_date` and `decided_at` under the message's existing `dedupe_key` (a gate's `gate-<message id>`). A retry keeps the first decision. The receipt (`sent` or `rejected`, `sent_at`, `external_id`) lands on that row unless metrics already wrote it. A decision that the database refuses is logged, and the reminder is posted as with the switch off. A decision of digest or drop is not posted; a gate reminder does not take those outcomes. Other send points are not wired. The pure rules, for a later send point, are first match wins: `silent` drops; `blocking` and `user_set` send uncounted; outside the source's own active hours, or quiet hours, or a direct chat already at 5 counted messages that local day, the message is digest; a user message in that chat within the last 5 minutes sends uncounted; otherwise a direct chat counts the send.

### Manager metrics, off ([#1488](https://github.com/foolzzz/looper/pull/1488), [#1509](https://github.com/foolzzz/looper/pull/1509))

- **`manager.metrics.enabled` defaults off.** No row, or any value other than the string `true`, leaves it off. While it is off, a turn has no `turn_metrics` key and a send writes no `proactive_deliveries` row from this feature. Channel calls stay as they were. The dashboard still calls `manager_metrics.get` every 60 seconds while the home page is open, and shows one line: metrics are off, with a link to `#settings/chat`. The window switch is hidden.
- **Only the operator can read or set it.** `POST /api/v1/manager_metrics_settings/get` and `POST /api/v1/manager_metrics_settings/update` are operator-only. The update is high risk and declares confirmation. `true` stores `true`. `false` stores `false`. `null` deletes the row and restores off. An API client token gets 403, and nothing is stored. `chat_settings.get` and `chat_settings.update` do not carry the field; a body that still sends the removed `metrics_enabled` field is rejected and nothing in that body is stored. Settings → Chat has the checkbox 「记录管家体验指标」. Saving it goes through `manager_metrics_settings.update`, not through chat settings. The help text is 「每轮记下回执、首条回复、工具调用次数和是否交付；主动消息记一行。只记录，不改变管家的行为。」
- **`manager_metrics.get` is operator-only and read-only.** It takes `days` from 1 to 30, default 7, and returns `enabled`, delivery counts, ack and first-reply P50 and P95 (replayed turns and completion turns left out), empty deliveries, proactive counts by local day and source, and the share of successfully sent deliveries at least 30 minutes old that got a reply. An unsent decision row is not in the summary and is not marked replied.
- **While it is on,** a user model turn records `metadata.turn_metrics` (version, origin, chat kind, receipt, ack kind and latency, first-reply latency, top-level tool calls, delivery, replay). A completion turn records origin, tool calls and delivery; a timeout is `failed`, and a user stop stays `stopped`. A proactive send records `source` and the receipt. Registry sends reuse their idempotency key, and bus sends reuse the envelope id, as `dedupe_key`. A retry updates only `outcome`, `external_id` and `sent_at`. Lark asks for a message id only on an explicitly proactive envelope. A failed observation does not delay or fail the reply. An operator reply within 30 minutes can mark a sent delivery in that chat. Prompts, tool lists and command lines are unchanged.
- **Dashboard.** A Manager group after "Agents running now": ack P50 with P95, first-reply P50 with P95, empty deliveries (count and share), and proactive messages per day with the 30-minute reply rate. The window is 24 h or 7 d, default 7 d, kept in the browser. The per-day table lists every local day the window touches, newest first. A null is "—", not 0. A failed read shows its error in the group and leaves the rest of the page up.

### Turn context, off ([#1497](https://github.com/foolzzz/looper/pull/1497))

- **`manager.turn_context.enabled` defaults off.** No row, or any value other than the string `true`, leaves it off. `user.timezone` absent means the server's zone. `user.reply_language` absent, or any stored value other than `zh-CN` or `en`, is `zh-CN`. `chat_settings.get` and `chat_settings.update` do not carry these fields, and their payloads stay as in v2.15.24, including the per-field operator restriction on `ledger_enabled`.
- **Only the operator can read or set them.** `POST /api/v1/turn_context_settings/get` and `POST /api/v1/turn_context_settings/update` are operator-only. The get returns `turn_context_enabled`, `timezone`, read-only `server_timezone` and `reply_language`. The update is high risk and declares confirmation. Every supplied field is checked before anything is written. A named field is stored; a field left out keeps its value. `null` deletes that key and restores its default. Enabling also returns `missing_operator_ids` (enabled bots with no My ID). An unknown field, an empty body, a bad timezone or a bad language stores nothing. An API client token gets 403. Settings → Chat loads and saves this view apart from the existing chat settings, so a failure of one leaves the other usable.
- **Storing it changes no Manager behavior.** The renderer can build a `[Turn context]` block (local time, speaker, chat, reply language). Nothing in a turn injects it, and nothing sets `Turn.speaker`. Prompts, tool lists, command lines, replies and channel calls stay as they are with the setting absent, including when the stored value is `true`. `Turn.speaker`, when a later change sets it, can refuse an escalation or a confirmation for an allowlisted sender or a group member; a turn with no speaker keeps today's behavior. Sender display names, when classified, go through `untrusted_text.display_name` (NFKC, control and format characters and structural punctuation removed, whitespace collapsed, capped at 40). This release does not show those names.

### One-time reminders, off ([#1505](https://github.com/foolzzz/looper/pull/1505))

- **`reminders.enabled` defaults off.** No row, or any value other than the string `true`, leaves it off. A read that fails counts as off. There is no dashboard switch and no HTTP write of the setting. Set it by inserting the system setting `reminders.enabled` with the value `true`. While it is off, the tool list, the system prompt, the command line and the process signature are unchanged. `ReminderService` still starts with `looper serve`, ticks about every 10 seconds, reads the setting once, and does nothing else. It does not send while the server is draining.
- **While it is on,** the default Manager lists `looper_reminder_create`, `looper_reminder_list` and `looper_reminder_cancel` on the operator's own turns only (the dashboard chat with no API client, or the bot operator's own direct chat). The system prompt does not gain a section. The listing's hash is part of the process signature, so a group turn and the operator's own turn restart the resident process, as the leads search already does. Another turn that calls one of them is refused in that tool's own words. Other tools' refusal text is unchanged.
- **What a reminder does.** Code resolves `at` (`HH:MM` or `YYYY-MM-DD HH:MM` in `timezone`, default the server's zone) or `in_minutes` to the nearest future instant that wall time names. When the clocks go back, it takes the first of the two still ahead; a time the clocks skip becomes the first valid minute after it, and the confirmation says so. A past time, or one more than a year ahead, is refused. The row stores the user's words (at most 500 characters) and the target (`channel_id` and the user's sender id). A dashboard reminder goes to the first enabled bot of the default Manager that names an `operator_sender_id`; with none, the call is `conflict`. At due time, code posts 「⏰ 你在 … 让我提醒你：…」 with idempotency key `looper-reminder-<id>`, after checking the bot still names that user. No model call. A reminder due at most 2 minutes ago is sent. Of those due longer ago, only the newest per chat that was due within 36 hours is sent, with a line saying when it was due, unless an on-time reminder goes to that chat in the same tick; the others are `missed`. A refused send is tried again, three times in all, then `failed`. An unknown outcome is `uncertain` and is never sent again. A stop starts no further send and waits at most 15 seconds, including cancelling a send that did not finish. Two servers send a due reminder once. Group chats cannot set or receive one. There is no `looper reminders` command. Reminders are not passed through the delivery layer.

### Card buttons, off ([#1489](https://github.com/foolzzz/looper/pull/1489))

- **`cards.actions.enabled` defaults off.** No row, or any value other than the string `true`, leaves it off. There is no dashboard switch and no HTTP write of the setting. Set it by inserting the system setting `cards.actions.enabled` with the value `true`. While it is off, no row is written, replies carry no cards, and gate messages stay text. A Lark card press gets the same plain acknowledgement as a message event, and a Telegram press is left unanswered, as before. The only extra work is reading the setting. On or off, the bot-token Lark stream reads a message event's payload before it acknowledges it; the acknowledgement is the same and nothing awaits between the read and the ack.
- **While it is on,** a high-risk confirmation also writes a `card_actions` row and, on `lark_bot` and Telegram, the confirmation block follows the text as a card with 确认 and 取消. A gate message that asks for an answer is a card: one button per option of the open questions (at most 3 questions and 5 options) and 「按现在的结论结束」. The web chat and the lark-cli channel stay text; a card that cannot be sent falls back to its text. Confirmations survive a restart, except one whose arguments look like a secret: that row keeps no arguments and is not restored. A typed `looper_confirm` and a press claim the same row, so the call runs once. Confirming a card the button already answered is `conflict`, and that sentence names only the confirmation id. That is the only new text a model can read, and only while the switch is on.
- **Who may press.** A button carries only `<token>:<choice>`. The press must come from the chat and, once the send has noted it, the message the card became. A press from another chat, a forwarded copy, or the same Telegram message id in another chat claims nothing. Admission is the chat's own rule (allowlist, the binding's extra senders, or anyone in a group bound with `sender_policy` `chat`), and then the card's `allowed` list. Checks end within 1.5 seconds of the press reaching the channel; past that, or on an error, the press is refused and nothing is claimed. The answer comes within 2.5 seconds; an action that takes longer updates the card when it ends. Lark card writes go through `lark.CardWrites`. Nothing a presser types is shown to a model.

### Session state on the session, no behavior change ([#1516](https://github.com/foolzzz/looper/pull/1516))

The lifecycle lock, the turn's research sources and the settings the last turn ran with now live on `ManagerSession`. With only `main`, every read and write is still main's, and the fleet sees the same lock. `session_routing.group_isolation` returns `SHARED` while each Manager has only main. Prompts, tool lists, command lines and channel behavior are unchanged. No new setting and no schema change.

### Six CI shards ([#1536](https://github.com/foolzzz/looper/pull/1536))

The `agent-system` matrix is six shards. Each shard's limit stays 20 minutes, and `fail-fast` stays false. Files are still balanced by collected test-case count, not by measured duration. A pull request whose change is only under `docs/**` or a path ending in `.md` skips setup and test steps; the six shards, PostgreSQL 18, Dashboard and the aggregate `Agent system tests` check still report success. A mixed change, a code deletion, or a code file renamed into documentation still runs tests. In-progress runs are cancelled only for a superseded `pull_request`, not for a push to `main`. Individual check names change from `Agent system tests (shard N/4)` to `Agent system tests (shard N/6)`. The installed service, prompts, tools and the dashboard bundle are unchanged.

### Reminder-dialog eval clock ([#1534](https://github.com/foolzzz/looper/pull/1534))

The `reminder_tools` dialog freezes its fake tools and delivery at 2026-11-22 12:00 UTC, and the checker takes each real-mode turn's reference time before the message is sent. Production prompts, tool descriptions and reminder delivery are unchanged. Dashboard, Telegram, Lark and the CLI need no change.

## Optional Capability Activation & Use

### Proactive delivery

**Activation:** Off until the system setting `delivery.enabled` is the string `true`. No row, `false`, or any other value, leaves it off. Set it as the operator through `POST /api/v1/proactive_delivery/update` with `enabled` true. The call applies at once. There is no dashboard switch. An API client token gets 403. While it is on, only gate reminders are decided, and they are still sent.

**Validation:** With the setting absent, `proactive_delivery.get` answers `enabled` false, a gate reminder is posted as before, and `proactive_deliveries` gains no decision row from the courier. With it `true`, the same reminder is posted and one row records a `blocking` send. `chat_settings.get` does not include the field.

**Disable / rollback:** Set `enabled` to false, or to null. False stores `false`. Null deletes the row. The layer is off either way, and the courier posts without asking. Rows already written stay. The `proactive_deliveries` table stays. It is not dropped.

**Authority boundary:** Only the operator can read or write the setting. An API client and an agent token get 403, and a refused update writes nothing. The stored value does not grant a tool. A gate reminder is not held back by quiet hours or the daily cap.

### 行为变化

**渠道启动重试和中断告警，默认开启（[#1550](https://github.com/foolzzz/looper/pull/1550)）**

这是每一个已启用的 Telegram 或 Lark 机器人的默认行为变化。没有关掉它的开关。以前，失败的启动探测会让渠道一直停到下次重启服务。

- **重试。**第一次是启动时的那次。传输失败（标成 transient 的 `ChannelStartError`、`httpx` 传输错误、超时、连接错误，或不是 bad request 的 Telegram 网络错误和 retry-after）先等 30 秒，然后加倍，最多 10 分钟。其他失败，包括凭据或配置失败，等 10 分钟，状态报 `failed`，重试继续。每一次重试都重新读已保存的设置并再次启动适配器，包括绑定和补读。停用或删除机器人会取消重试，并卸掉重试刚刚登记的适配器。关闭服务会取消每一次重试。
- **状态。**系统状态和 `channel_configs` 暴露只读的 `runtime`：`starting`、`running`、`retrying` 或 `failed`，带最后一次错误和下一次尝试；机器人停用，或不是这台服务启动的，为 null。启动成功就清掉。
- **超过门槛的中断。**每 30 秒看一次。已启用的机器人没有在跑，或投递全部失败，就算中断。超过 `channels.down_alert_minutes`（默认 10；没有这一行，或存的值不是正整数，都是 10）之后，系统状态多一条问题，id 为 `channel_down:<channel_id>`。仪表盘原有的顶部横幅显示它，每 30 秒刷新，恢复后也不必重新加载页面。一次成功的投递结束失败连续。正在跑的机器人，若成功落在这次中断之内，就算恢复。阶段更新、流式增量、空回复、没有会话路由，以及只留在仪表盘的定时任务行（包括目标已删除或缺少发送者的发送前拒绝），既不算失败投递，也不能证明恢复。真正的发送失败仍是 `failed`。
- **一次告警，一次恢复。**发送之前先把中断存下来（`channels.down_state:` 加上渠道 id）。通知发到每一个另外的、自己没有中断、并且有 `operator_sender_id` 的已启用机器人。出问题的那个机器人自己不发。每一次尝试最多等 20 秒。失败、不确定或被打断的尝试，在同一次中断里不再重试。没有这样的机器人时，横幅是唯一的告警。恢复时用同样的办法发一次。停用机器人会清掉它的问题和计时。
- **只有操作者能读或写这个门槛。**`POST /api/v1/channel_down_alert/get` 和 `POST /api/v1/channel_down_alert/update` 只给操作者。更新是高风险，立刻生效。正整数的分钟数存成这个数。`null` 删掉这一行，恢复 10。API 客户端令牌得到 403，什么都不存。`chat_settings` 不带这个字段。没有 Manager 工具列出它。健康的机器人发出的消息与以前相同。

**主动投递，默认关闭（[#1486](https://github.com/foolzzz/looper/pull/1486)）**

- **`delivery.enabled` 默认关闭。**没有这一行，或取值不是字符串 `true`，都算关闭。启动还没读完设置之前也是关。没有仪表盘开关。`chat_settings.get` 和 `chat_settings.update` 不带这个字段。
- **只有操作者能读或写。**`POST /api/v1/proactive_delivery/get` 和 `POST /api/v1/proactive_delivery/update` 只给操作者。更新是高风险：影响说明写出 `delivery.enabled`，并写明下一条已经接线的消息会不会在发出前做决定。操作者的调用立刻生效。`true` 存成 `true`。`false` 存成 `false`。`null` 删掉这一行，恢复关闭。API 客户端令牌得到 403，什么都不存。
- **关闭时，**关卡信使照旧发提醒，这一层什么都不写。
- **打开之后，**只有关卡提醒会问 `decide()`。提醒是 `blocking`（只在关卡挡住后面的步骤时才到点），所以决定是发送、不计数（`urgent`）：安静时间（`user.timezone`，否则是服务器时区，22:00 包含在内，到 08:00 为止）和私聊每天 5 条已计数消息的上限都不拦住它。提醒的正文和目标不变。这一行在消息已有的 `dedupe_key`（关卡的 `gate-<message id>`）下记下 `decision`、`reason`、`counted`、`local_date`、`digest_date` 和 `decided_at`。重试保留第一次的决定。回执（`sent` 或 `rejected`、`sent_at`、`external_id`）落在同一行，除非度量已经写过。数据库拒绝这次决定时只记日志，提醒仍按关闭时的方式发出。决定是 digest 或 drop 的不发；关卡提醒不会走到这两种结果。其他发送点还没有接上。给以后的发送点用的纯规则，第一条命中即停：`silent` 丢掉；`blocking` 和 `user_set` 发送且不计数；在来源自己的活跃时间之外、安静时间里、或这个私聊当天已经有 5 条已计数消息，就进摘要；这个会话 5 分钟内有用户写过，就发送且不计数；否则私聊会计数。

**管家度量，默认关闭（[#1488](https://github.com/foolzzz/looper/pull/1488)、[#1509](https://github.com/foolzzz/looper/pull/1509)）**

- **`manager.metrics.enabled` 默认关闭。**没有这一行，或取值不是字符串 `true`，都算关闭。关闭时，回合没有 `turn_metrics` 键，这个功能也不往 `proactive_deliveries` 写行。渠道调用与以前相同。仪表盘在首页开着时仍每 60 秒调用一次 `manager_metrics.get`，只显示一行：度量是关的，并链到 `#settings/chat`。时间窗口的开关藏起来。
- **只有操作者能读或写。**`POST /api/v1/manager_metrics_settings/get` 和 `POST /api/v1/manager_metrics_settings/update` 只给操作者。更新是高风险，并声明要确认。`true` 存成 `true`。`false` 存成 `false`。`null` 删掉这一行，恢复关闭。API 客户端令牌得到 403，什么都不存。`chat_settings.get` 和 `chat_settings.update` 不带这个字段；请求体里若还带着已经去掉的 `metrics_enabled`，整次请求被拒绝，什么都不存。Settings → Chat 有复选框「记录管家体验指标」。保存走 `manager_metrics_settings.update`，不走聊天设置。帮助文字是「每轮记下回执、首条回复、工具调用次数和是否交付；主动消息记一行。只记录，不改变管家的行为。」
- **`manager_metrics.get` 只给操作者，并且只读。**`days` 为 1 到 30，默认 7。它返回 `enabled`、投递计数、回执和首条回复的 P50 与 P95（重放的回合和完成回合不计入）、空投递、按本地日和来源的主动消息计数，以及发出至少 30 分钟、结果为已发送的投递里得到回复的比例。还没发送的决定行不进摘要，也不标成已回复。
- **打开之后，**用户的模型回合记下 `metadata.turn_metrics`（版本、来源、会话种类、回执、回执种类和延迟、首条回复延迟、顶层工具调用次数、是否交付、是否重放）。完成回合记下来源、工具次数和是否交付；超时是 `failed`，用户停止仍是 `stopped`。一次主动发送记下 `source` 和回执。注册表发送复用幂等键，总线发送复用信封 id，作为 `dedupe_key`。重试只更新 `outcome`、`external_id` 和 `sent_at`。只有明确的主动信封才会向 Lark 要消息 id。观察写失败不会拖住或弄失败回复。操作者在 30 分钟内的回复可以把这个会话里已发送的投递标上。提示词、工具列表和命令行不变。
- **仪表盘。**「Agents running now」后面一组 Manager：回执 P50 和它下面的 P95，首条回复同样，空投递（次数和占比），以及每天的主动消息和 30 分钟回复率。窗口是 24 小时或 7 天，默认 7 天，记在浏览器里。按日的表列出窗口碰到的每一个本地日，新的在前。空值是「—」，不是 0。读取失败只在这一组里显示错误，页面其余部分照常。

**回合上下文，默认关闭（[#1497](https://github.com/foolzzz/looper/pull/1497)）**

- **`manager.turn_context.enabled` 默认关闭。**没有这一行，或取值不是字符串 `true`，都算关闭。没有 `user.timezone` 就用服务器的时区。没有 `user.reply_language`，或存的值不是 `zh-CN` 或 `en`，就是 `zh-CN`。`chat_settings.get` 和 `chat_settings.update` 不带这些字段，载荷与 v2.15.24 相同，包括 `ledger_enabled` 按字段只给操作者写。
- **只有操作者能读或写。**`POST /api/v1/turn_context_settings/get` 和 `POST /api/v1/turn_context_settings/update` 只给操作者。读取返回 `turn_context_enabled`、`timezone`、只读的 `server_timezone` 和 `reply_language`。更新是高风险，并声明要确认。带上的每个字段都先检查，通过之后才写。点名的字段才存；没带上的保持原值。`null` 删掉那个键，恢复它的默认。打开时还会返回 `missing_operator_ids`（已启用但没有 My ID 的机器人）。未知字段、空的请求体、非法时区或非法语言什么都不存。API 客户端令牌得到 403。Settings → Chat 把这一份和原有的聊天设置分开加载、分开保存，一边失败不影响另一边。
- **存下来也不改变 Manager 的行为。**渲染器可以做出一块 `[Turn context]`（本地时间、说话人、会话、回复语言）。没有回合注入它，也没有人设置 `Turn.speaker`。提示词、工具列表、命令行、回复和渠道调用与没有这个设置时相同，存成 `true` 时也一样。以后若设置了 `Turn.speaker`，可以拒绝允许名单里的人或群成员的升级和确认；没有说话人的回合保持今天的行为。分类时，发送者的显示名经过 `untrusted_text.display_name`（NFKC，去掉控制和格式字符以及结构性标点，合并空白，最多 40 个字符）。本版本不显示这些名字。

**一次性提醒，默认关闭（[#1505](https://github.com/foolzzz/looper/pull/1505)）**

- **`reminders.enabled` 默认关闭。**没有这一行，或取值不是字符串 `true`，都算关闭。读失败也算关。没有仪表盘开关，也没有写这个设置的 HTTP。把系统设置 `reminders.enabled` 写成 `true` 即可。关闭时，工具列表、系统提示词、命令行和进程签名都不变。`ReminderService` 仍随 `looper serve` 启动，大约每 10 秒读一次这个设置，此外什么都不做。服务在排空时不发送。
- **打开之后，**默认 Manager 只在操作者本人的回合列出 `looper_reminder_create`、`looper_reminder_list` 和 `looper_reminder_cancel`（没有 API 客户端的仪表盘会话，或该机器人操作者自己的私聊）。系统提示词不增加一节。列表的哈希进进程签名，所以群回合和操作者本人的回合会重启常驻进程，与线索检索已经这样做相同。别的回合若调用，用这个工具自己的句子拒绝。其他工具的拒绝文案不变。
- **一条提醒做什么。**代码把 `at`（`timezone` 里的 `HH:MM` 或 `YYYY-MM-DD HH:MM`，默认服务器时区）或 `in_minutes` 解析成这个钟面时间最近的、还在将来的那一瞬。时钟拨回时取仍在前面的第一次；时钟跳过的时间变成其后第一个有效的分钟，确认句会说明。过去的时间，或一年以后的时间，会被拒绝。这一行存用户的话（最多 500 字）和目标（`channel_id` 和用户在那里的发送者 id）。仪表盘上设的提醒发到默认 Manager 第一个写了 `operator_sender_id` 的已启用机器人；一个都没有就是 `conflict`。到点时，代码在确认这个机器人仍把该用户当作操作者之后，发出「⏰ 你在 … 让我提醒你：…」，幂等键为 `looper-reminder-<id>`。不调用模型。到点不超过 2 分钟的都发。到点更久的，每个会话只发 36 小时内最新的那一条，并写明原定时间，除非同一次节拍里有一条准时的发到这个会话；其余标成 `missed`。被拒绝的发送下一拍再试，一共三次，然后是 `failed`。结果未知的是 `uncertain`，绝不再发。停止服务不再开始新的发送，最多等 15 秒，包括取消一条还没发完的。两台服务对一条到点的提醒只发一次。群里不能设，也收不到。没有 `looper reminders` 命令。提醒不走投递层。

**卡片按钮，默认关闭（[#1489](https://github.com/foolzzz/looper/pull/1489)）**

- **`cards.actions.enabled` 默认关闭。**没有这一行，或取值不是字符串 `true`，都算关闭。没有仪表盘开关，也没有写这个设置的 HTTP。把系统设置 `cards.actions.enabled` 写成 `true` 即可。关闭时不写行，回复不带卡片，关卡消息仍是文本。Lark 的卡片按压得到和消息事件一样的普通确认，Telegram 的按压仍不回答，与以前相同。多做的只有读一次这个设置。无论开关，bot token 的 Lark 长连接都先读消息事件的载荷再确认；确认帧相同，读和确认之间没有等待。
- **打开之后，**高风险确认同时写一行 `card_actions`；在 `lark_bot` 和 Telegram 上，确认块跟在正文后面，是带确认和取消的卡片。要求回答的关卡消息是卡片：每个未结束问题的每个选项一个按钮（最多 3 个问题、每个 5 个选项），加上「按现在的结论结束」。网页会话和 lark-cli 渠道仍是文本；卡片发不出去就退回文本。确认在重启之后还在，除非参数看起来像秘密：那种行不存参数，也不恢复。打字的 `looper_confirm` 和按压认领同一行，所以调用只跑一次。卡片已经被按钮回答过再打字确认，是 `conflict`，这句话只写出确认 id。这是模型能读到的唯一新句子，并且只在开关打开时。
- **谁可以按。**按钮只携带 `<token>:<choice>`。按压必须来自发出这张卡片的会话，并且在发送已经记下消息 id 之后，必须来自那一条消息。另一个会话、转发的副本，或另一个会话里相同的 Telegram 消息 id，都不认领。准入先用这个会话自己的规则（允许名单、绑定的额外发送者，或 `sender_policy` 为 `chat` 的群里的任何人），再看卡片的 `allowed`。检查必须在按压到达渠道后 1.5 秒内结束；超过，或出错，按压被拒绝，什么都不认领。回答在 2.5 秒内给出；动作更久的，结束时再更新卡片。Lark 的卡片写入都走 `lark.CardWrites`。按的人写的内容不会给模型看。

**会话状态放在会话上，没有行为变化（[#1516](https://github.com/foolzzz/looper/pull/1516)）**

#### Proactive delivery

**启用：**系统设置 `delivery.enabled` 为字符串 `true` 之前是关的。没有这一行、`false` 或其他取值，都算关。由操作者经 `POST /api/v1/proactive_delivery/update` 把 `enabled` 设为 true。调用立刻生效。没有仪表盘开关。API 客户端令牌得到 403。打开之后只有关卡提醒会做决定，并且仍然发送。

#### One-time reminders

**启用：**系统设置 `reminders.enabled` 为字符串 `true` 之前是关的。没有这一行，或其他取值，都算关。本版本没有仪表盘开关，也没有写这个设置的 HTTP。把系统设置 `reminders.enabled` 写成 `true` 即可。之后的 Manager 回合和下一次提醒节拍会用它。先设置 My ID（Settings → Channels，允许名单里的一个发送者），私聊发送者才会被认成操作者；从仪表盘设的提醒还需要默认 Manager 有一个写了这个 id 的已启用机器人。

#### Card buttons

**启用：**系统设置 `cards.actions.enabled` 为字符串 `true` 之前是关的。没有这一行，或其他取值，都算关。本版本没有仪表盘开关，也没有写这个设置的 HTTP。把系统设置 `cards.actions.enabled` 写成 `true` 即可。之后的高风险确认和下一条关卡消息会用它。按钮发在 `lark_bot` 和 Telegram 上。网页会话和 lark-cli 渠道仍是文本。

**验证：**没有这个设置时，高风险确认用文本询问，不写 `card_actions` 行，重启之后也不会回来。为 `true` 时，同一次确认写一行，`lark_bot` 或 Telegram 的回复在正文后带确认和取消，重启会恢复一条参数不像秘密的、还在等的确认。按压和打字确认两边只跑一次调用。

**停用 / 回退：**删掉 `cards.actions.enabled`，或设成 `true` 以外的值。新的回复不带卡片，按压得到普通确认（Lark）或不回答（Telegram）。已经存的行留着，开关关闭时不认领。`card_actions` 表留着，不会被删掉。

**权限边界：**按压只从发出卡片的那个会话和那条消息准入，并且发送者必须是这个会话会准入的人、也在卡片允许的名单里。按钮的值只用来查找。它不给模型看。API 客户端不能经 `chat_settings` 打开这个设置。

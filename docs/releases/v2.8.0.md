# Looper v2.8.0

## At a Glance

Looper asks the user when a plan needs a decision, and the agents of a task can talk to each other. **User gates are on by default:** a Planner may stop part of a plan to settle a question with the user, in the dashboard or in the Lark or Telegram chat the task came from, while the rest of the plan runs. **The agent room is on by default:** a task's Planner and the agents of its steps message each other through their own tools, with a server-side rule for who may say what to a Reviewer. A question to the seat of an ended step is answered by a read-only consult of that seat's last session; what it does not answer goes to the Planner. Projects keep **role templates**, the user can edit a task's role, and a step can be reviewed by several review roles in order. **Grok** is a fourth runtime, on xAI's `grok` CLI and its own login. An Agent Profile can **append or replace** the runtime's default system prompt. A new project runs each task in a **git worktree** of the directory it names and hands the branch back unmerged; **operator notes** are on for every project, including ones that already exist, and reach Claude Code, Codex, OMP and Grok. The Manager can create, change and run schedules, and enabling one or running it now waits for the next message. A task's cost is broken out **by model**, with the Manager's turns apart. The **Planner is read-only, enforced by its tools**. The server stops in seconds however many steps are running, every run record ends, a step records when it started, and the Pipeline shows a card on hover and can go full screen. The eval harness runs targeted checks per change and can run cases in parallel with `--jobs`.

**This release has breaking changes.** Concurrency is per task, the project level and the queued group are gone, and several defaults move: gates on, the agent room on, new projects in worktrees, operator notes on, schedule enable and run-now confirmed in the next message, and a Planner that cannot write files. Upgrade by re-running `install.sh`; the first start backs the database up and migrates it. The details are under Behavior changes, Breaking Changes and Upgrading from v2.7.0.

```bash
curl -fsSL https://raw.githubusercontent.com/foolzzz/looper/main/install.sh | bash
looper --version   # looper 2.8.0
looper doctor
```

### Highlights

- **User gates on Lark and Telegram.** A gate in the plan settles what only the user can decide, while other steps run. Questions reach the chat the task came from, a reply in that thread goes to the gate, and the Manager can relay an answer. On unless a project turns them off. A task a schedule starts never opens a gate. ([#168](https://github.com/foolzzz/looper/pull/168), [#179](https://github.com/foolzzz/looper/pull/179))
- **Agent room.** The Planner and each step's seats message each other, see who is online, and post an interface without a shared file. Workers cannot lobby Reviewers. A question to the seat of an ended step is answered by a read-only consult of that seat's last session; what it does not answer goes to the Planner. ([#187](https://github.com/foolzzz/looper/pull/187), [#188](https://github.com/foolzzz/looper/pull/188))
- **Planner-defined roles and templates.** Project templates the Planner copies, the user's edit of a role on the task page, several review roles in order, catalog items a role loads, and a project's roles summed across its tasks. A run's role is named wherever runs are shown. ([#170](https://github.com/foolzzz/looper/pull/170), [#181](https://github.com/foolzzz/looper/pull/181), [#182](https://github.com/foolzzz/looper/pull/182))
- **Grok.** xAI's `grok` CLI for the Manager, Planner, Worker and Reviewer, with a built-in login provider and a home that does not read the operator's own Grok, Claude Code or Cursor configuration. ([#185](https://github.com/foolzzz/looper/pull/185))
- **System prompt append or replace.** Per Agent Profile. `append` is unchanged. `replace` is opt-in and drops that runtime's default guidance. A runtime that cannot replace is refused at save. ([#193](https://github.com/foolzzz/looper/pull/193))
- **Task workspaces and operator notes.** A task runs in a git worktree of the directory it names, on a branch Looper never merges. New projects default to that. Operator notes are on for every project and reach every runtime. ([#190](https://github.com/foolzzz/looper/pull/190))
- **Schedules from the Manager.** Create, change and run, with schedules in the configuration file, always imported disabled. Enable and run-now wait for the next message. ([#178](https://github.com/foolzzz/looper/pull/178))
- **Task cost by model.** Tokens and cost per model on the task, the Manager's turns apart from the task's own cost and its spend cap. ([#189](https://github.com/foolzzz/looper/pull/189))
- **A read-only Planner, and a faster stop.** The Planner's writes are refused by its tools. `looper serve` stops in seconds and always exits. Every run record reaches a terminal status. A step records when it first started. The Pipeline card opens on hover and the graph can go full screen. ([#172](https://github.com/foolzzz/looper/pull/172), [#174](https://github.com/foolzzz/looper/pull/174), [#177](https://github.com/foolzzz/looper/pull/177), [#183](https://github.com/foolzzz/looper/pull/183), [#184](https://github.com/foolzzz/looper/pull/184), [#186](https://github.com/foolzzz/looper/pull/186))

## Release Decision

**Who should upgrade:** Everyone running v2.7.0. Before upgrading, anyone who calls the HTTP API should read Breaking Changes, because the queued task group and the project concurrency fields are gone, and anyone who creates projects or lets a Planner ask the user should read Behavior changes.

**What this release solves:** v2.7.0 could not stop a plan to ask the user, could not let the agents of one task talk to each other or ask an ended step's own session, had no role templates and at most one review role on a step, could not run Grok, always appended Looper's prompt to the runtime's own, ran every task in the checkout the user named, could not create or edit a schedule from the Manager, showed a task's cost only by role, let a Planner write files, took longer to stop as more steps were running, and could leave a run record `running` after the run had ended. v2.8.0 adds gates, the agent room and read-only consults of an ended seat, role templates and ordered review roles, the Grok runtime, per-profile system-prompt replace, task worktrees and operator notes, Manager schedule tools with confirmation, cost by model, a read-only Planner, a stop that always exits, run records that always end, step start times, and a Pipeline card with full screen.

**Breaking changes:** Yes. Concurrency is per task and the queued group is gone; user gates and the agent room are on by default, and a question to an ended seat starts a read-only consult; a new project runs tasks in git worktrees; operator notes are on for every project, including ones that already exist, and reach every runtime; enabling a schedule or running it now from the Manager waits for the next message; the Planner is read-only, enforced by its tools. A v2.7.0 step's single review role becomes a list. See Behavior changes, Breaking Changes and Upgrading from v2.7.0.

**How to verify:** After re-running `install.sh`, `looper --version` reports `looper 2.8.0` and `looper doctor` passes. The first `looper serve` logs a `pg_dump` backup before it migrates. With the server running, `/api/status` reports `"status": "running"`, a new project's `task_workspaces` is `worktree`, and `user_gates`, `agent_room` and `operator_notes` read as on where the project never set them.

**Contributors:** Release maintainer @foolzzz; no community contribution in the pull requests merged since v2.7.0.

## User gates

- **A step can be a gate.** In a project with `user_gates` on (the default, also when unset), the Planner may add a step `{"id", "kind": "gate", "topic", "agenda", "depends_on"}`. The steps that depend on it wait; the rest of the plan runs. The task is `waiting_user` while a gate is open. Closing writes a summary (decisions, assumptions, what is still open) as a supplement later Workers and Reviewers read. A project set to `off` keeps the previous reply contract, and a gate step is refused with the reason. A task a schedule starts never opens a gate. ([#168](https://github.com/foolzzz/looper/pull/168))
- **On the task page.** The Overview shows a waiting gate at the top: agenda, discussion, option buttons, a message box and End discussion. The Pipeline draws the gate as its own node. The Dashboard and the Tasks page have a Needs you group. `POST /api/tasks/:id/gates/:step/messages` adds a message; `/end` ends the discussion. ([#168](https://github.com/foolzzz/looper/pull/168))
- **Lark and Telegram.** `GateCourier`, inside `looper serve`, posts the gate's discussion to the chat the task came from: a Lark direct message or group (the requester @-mentioned) or the Telegram chat. A task asked for on the dashboard or in the web chat goes to the chat named by `user_gates.dashboard_target` (Settings → Channels, `GET`/`PUT /api/gate-settings`), and nowhere when that is unset. The card is its own message; later messages reply under it. A reply in that thread is routed to the gate before the Manager's model sees it. `looper_task_gate_reply` lets the Manager add the user's words to a waiting gate. ([#179](https://github.com/foolzzz/looper/pull/179))
- **Delivery.** Lark posts use an idempotency key, so one key sends one message within an hour. Telegram has no such key: a post retried after a lost answer can arrive twice (see Known limits). A reply whose parent message is gone is posted on its own. A channel answer is stored in the chat history only once that channel has sent it. Texts Looper writes are Chinese; a Planner's reply is posted as written; Telegram is plain text, split at 4,000 characters. ([#179](https://github.com/foolzzz/looper/pull/179))
- **Whose turn it is.** On a stopped, failed or cancelled task, a gate that would have waited for the Planner reads "Your turn". While the task runs, it reads "Planner answering". The Overview, the Pipeline node and the gate card use one rule. ([#174](https://github.com/foolzzz/looper/pull/174))

## Agent room

- **On by default.** With `agent_room` on (the default, also when unset), a task's Planner and the agents of its steps share a room. With it off, prompts, tool lists and command lines are as before. Seats are the Planner and one per step and role (`backend_rd@s2`, `worker@s2` with no role, `reviewer@s2`, a review role's `security@s2`). Presence comes from who is running. ([#187](https://github.com/foolzzz/looper/pull/187))
- **Tools and scope.** Each Worker and Reviewer run gets its own token and Looper's MCP entry, revoked when the run ends. Tools: `looper_room_roster`, `looper_room_post`, `looper_room_inbox`, `looper_room_read`, and `looper_room_watch` for work seats. The sender is the token's seat. A work seat may post to work seats, roles, the Planner and everyone, and to a review seat only to answer that seat's own question. A review seat may only ask a work seat or the Planner. The Planner may post to anyone. Messages are only added, and they go with the task and with a start-over. ([#187](https://github.com/foolzzz/looper/pull/187))
- **How a message arrives.** A run's first turn lists its seat, who is online, and the messages for it. The system prompt has a room section. Inbox is oldest first. A message for the Planner wakes a `[ROOM]` turn. `GET /api/tasks/:id/room` and the task page's Room tab show the room. The Manager can read it with `looper_tasks` action `room` and does not post. ([#187](https://github.com/foolzzz/looper/pull/187))
- **Limits.** Posts per minute, broadcasts, message length, messages per task, and how long an inbox wait may block are project settings. Past a limit the call is refused. A question to the seat of an ended step is answered by a read-only consult of that seat's last session; what it does not answer goes to the Planner. A question for a seat that never ran goes to the Planner. ([#187](https://github.com/foolzzz/looper/pull/187), [#188](https://github.com/foolzzz/looper/pull/188))

## Agent room consults

- **An ended seat is asked through its last session.** A question to the seat of an ended step is answered by a read-only fork of that seat's last session, and the answers are posted as that seat. What the consult does not answer goes to the Planner. A question for a seat that never ran goes to the Planner. ([#188](https://github.com/foolzzz/looper/pull/188))
- **Read only, and only that session.** Claude Code resumes with `--resume` and `--fork-session` and is given only `Read`, `Glob` and `Grep`. Codex and OMP copy only the session the run kept. Grok runs in a home of its own with a copy of that one session and read-only tools (`read_file`, `grep` and `list_dir`); MCP tools stay callable through `use_tool`, and that home is deleted afterwards. Claude Code, Codex and Grok read the checkout as it is now. OMP runs in a detached checkout that is removed afterwards. See Known limits. ([#188](https://github.com/foolzzz/looper/pull/188))
- **Caps, fail closed.** The per-consult cap defaults to 0.50 USD (`room_consult_budget_usd`), the timeout to 300 seconds (`room_consult_timeout_seconds`), and the count to 10 consults per task (`room_consults_per_task`). An answer over the cap, or an answer with no reported price, is dropped. ([#188](https://github.com/foolzzz/looper/pull/188))

## Planner-defined roles and templates

- **Templates.** A project keeps role templates (key, kind, a one-line description, role prompt, optional harness, optional profile, optional catalog items). They are checked as a task role is, whatever `planner_roles` says. `GET`/`PUT`/`DELETE /api/projects/:id/role-templates`. With `planner_roles` on, `[PLAN]` and `[RESTART]` list them, and `looper_task_role_set` with `template` copies one. Fields the call gives override the template. A later edit of the template does not change a role already copied. The configuration file carries templates by name. ([#181](https://github.com/foolzzz/looper/pull/181))
- **The user's edit.** `PUT /api/tasks/:id/roles/:key` writes a new version by the user while the task has not completed, tells the Planner, and from then on the Planner cannot change that role. Two writers cannot pass each other: the later one gets a conflict and reads again. ([#181](https://github.com/foolzzz/looper/pull/181))
- **Review roles in order.** A step lists `review_roles`. Each item is a role id, or `{"role", "required": false}` for an advisory one, and no role twice. After the built-in Reviewer passes, they review one after another. A required role that does not pass stops the ones after it. The v2.7.0 fields `review_role` and `review_role_required` are refused, and stored steps become a list of one. ([#182](https://github.com/foolzzz/looper/pull/182))
- **Items and a project summary.** A catalog install may name `task_role` and then loads only for a role that names that item, at most 20 items. `GET /api/projects/:id/role-stats` sums each role id across the project's tasks. ([#182](https://github.com/foolzzz/looper/pull/182))
- **The role's name on every run.** The Agent Timeline, Runs, a History header, the Overview and the Chat page show `fe_rd · work` instead of Worker where the run recorded a role. The Planner's roles guide tells it to split work that spans disciplines. The task page has an Agents tab for the task's profiles, the roles the Planner defined, and what each step ran on. ([#169](https://github.com/foolzzz/looper/pull/169), [#170](https://github.com/foolzzz/looper/pull/170))

## The Grok runtime

- **A fourth runtime.** When `grok` is on the server's `PATH`, `looper serve` registers the runtime `grok` (`rt-grok`). It runs headless `grok` with the prompt on stdin, streaming messages, and the built-in provider `grok-login` (`prov-grok-login`). The Manager and a Planner run one process per turn and resume the session. Workers and Reviewers are one process. Verified against Grok 1.0.62. ([#185](https://github.com/foolzzz/looper/pull/185))
- **Its own home.** `GROK_HOME` and `HOME` both point at a home Looper owns, so a run does not load the operator's skills, Claude Code plugins and hooks, or Cursor configuration. The generated config turns off compatibility scans, memory, the update check, the shared leader, telemetry and session upload. The agent's shell is given the operator's home back, and a `GROK_HOME` that has no login. The login file is linked, not copied, the same way Codex's ChatGPT login is. ([#185](https://github.com/foolzzz/looper/pull/185))
- **Cost and tools.** The run's cost is Grok's own reported cost. A zero with tokens spent is treated as unknown. Grok has no spend-cap flag and reports the cost only when the run ends, so a per-run cap does not stop a Grok run; saving a Grok profile warns about that. MCP tools are called through Grok's own tool lookup as `<server>__<tool>`. A Grok Planner has no shell (see Known limits). ([#185](https://github.com/foolzzz/looper/pull/185))

## System prompt append or replace

- **Per Agent Profile.** `system_prompt_mode` is `append` (the default, byte-identical to v2.7.0) or `replace`. The API, the registry, configuration export and import, derived profiles and the Manager's profile tool read and write it. Each run records the mode, and the run page badges a run that replaced the default. ([#193](https://github.com/foolzzz/looper/pull/193))
- **How replace works.** Claude Code uses `--system-prompt-file`. Codex points `model_instructions_file` at the prompt and leaves the home `AGENTS.md` empty. Grok uses `--agent` with `prompt_mode: full` (not an override flag, which still kept the default prompt). OMP uses `--system-prompt`. Saving `replace` on a runtime that cannot replace, or moving such a profile onto one, is a 400, and the editor greys the control out with the reason. Nothing falls back to append in silence. ([#193](https://github.com/foolzzz/looper/pull/193))
- **Opt-in, and it drops the runtime's own guidance.** Replace is off until a profile asks for it. It removes that runtime's default system prompt, including its own guidance about tools and refusals. On haiku, a replace-mode run scored 52/66 where append scored 53/66, and contract violations rose from 3.7 to 8.3; repair turns recover. See Known limits. ([#193](https://github.com/foolzzz/looper/pull/193))

## Task workspaces and operator notes

- **Where a task runs.** A task names a workspace directory. The mode is the one the task asks for; else a worktree when that directory is not the project's; else the project's `task_workspaces`. A project created through the API, the task form or the Manager gets `worktree`. An existing or imported project stays `null`, which means in place. ([#190](https://github.com/foolzzz/looper/pull/190))
- **The worktree.** Before the Planner starts, restarts, continues or resumes, Looper prepares `<runtime root>/task-worktrees/<task id>` on branch `looper/<task id>/task`, from the task's base or from what the workspace has checked out. `work_dir` becomes that directory's place inside the worktree, so step worktrees nest in it and merge into its branch. The branch is not merged back. When the task completes, leftovers are committed on that branch, the worktree is removed, and the branch stays. A directory outside git runs in place, and the check warns `not_git` on that fallback too. A checkout over 1 GiB is warned as large. ([#190](https://github.com/foolzzz/looper/pull/190))
- **Operator notes, on for every project.** `operator_notes` null means on, including projects that already exist. Turn a project off with `off`. The Planner, Workers and Reviewers receive a read-only copy of the operator's Claude Code auto-memory for that directory (`MEMORY.md`, its first 200 lines, and the markdown files it points at, within 24 KiB), after the project's knowledge. The same notes are injected for every runtime, including Codex, OMP and Grok, not only Claude Code. They are background: the task and the files win. Looper only reads them. Past session transcripts are not included. ([#190](https://github.com/foolzzz/looper/pull/190))
- **Step workspaces, still opt-in.** Parallel steps in their own worktrees stay a project setting, `shared` by default. This release adds up to 20 relative links back to the task directory, a 1 GiB checkout limit (over that, the round runs one step at a time), merge files kept when a merge fails, undo commands and a Discard button on the task page, and `looper doctor` checks. A link is never committed as the step's result. ([#180](https://github.com/foolzzz/looper/pull/180))

## The Manager's schedule tools

- **Create, change, run, export.** `looper_schedules` gains `create`, `update` and `run`, through the same code as the dashboard. Create is always disabled, in an existing project only, and Looper appends a configuration block (project, directory, the rule in words, the next fires, overlap, gate, caps, notify, profiles, task limits). The turn that created a schedule can neither enable it nor run it. Update changes only the fields given; raising or removing a spend cap is confirmed before it is saved. Run now goes through the overlap check and does not move the next fire time. `looper_config_export` writes a configuration file under the runtime root's exports directory, with no path taken from chat and no secrets in the file. ([#178](https://github.com/foolzzz/looper/pull/178))
- **Confirmation.** Enabling a schedule and running it now need the user's confirmation in the next message. If the user does not confirm, the schedule stays disabled and Looper does not enable it and does not start a run. Deleting still waits for confirmation. Disabling does not. A schedule created from a Telegram or Lark chat, with no notify target of its own, sends its messages to the person who asked, when that channel's allowlist lets them in. ([#178](https://github.com/foolzzz/looper/pull/178))
- **In the configuration file.** Schedules move with their projects. An imported schedule is always disabled. ([#178](https://github.com/foolzzz/looper/pull/178))

## Task cost by model

- **On the task.** `GET /api/tasks/:id` and each task in `GET /api/tasks` carry `cost`: `cost_usd`, `runs`, how many are still running, how many ended with no reported cost, and `by_role` for the Planner, Workers and Reviewers. `by_model` is one row per model: runs, running, unpriced, interrupted, input, output, cache read and cache write tokens, and `cost_usd` (null when no run reported a cost). The model rows add up to the task's `cost_usd`. The Overview shows "Cost by agent and model" and a By model table. ([#189](https://github.com/foolzzz/looper/pull/189))
- **The Manager's turns are apart.** `manager_by_model` uses the same row shape for Manager turns that name this task, or whose tool calls point at this task only. Those turns are not in the task's `cost_usd`, `by_role`, `by_model` or spend cap. A turn that touches several tasks, or none, is not attributed to a task. A schedule run in progress counts the task's spend so far, without the Manager. ([#189](https://github.com/foolzzz/looper/pull/189))

## A read-only Planner

- **Enforced by tools.** The Planner no longer has a free hand with the worktree. On Claude Code the launch drops permission skipping, disallows Edit, Write and NotebookEdit, and allows the tools the Planner still needs: skills, web fetch and search, and its MCP servers. Reading, listing, searching and `git status`, `log`, `diff` and `show` stay allowed. A redirect, `touch`, a script that writes and `git commit` are refused. Refusals are stored on the run and the task activity says how many calls Looper refused. ([#183](https://github.com/foolzzz/looper/pull/183))
- **Where the runtime cannot refuse.** The command stays as it was, and Looper compares the task directory's git checkout before and after the turn. A change is recorded. Nothing is reverted, because the change might be the user's or a Worker's. The comparison runs only when no Worker or Reviewer of that task is in the task directory, and only in a git checkout. A Grok Planner has no shell: its tool list is read, search and list. ([#183](https://github.com/foolzzz/looper/pull/183), [#185](https://github.com/foolzzz/looper/pull/185))
- **The Reviewer sees the retry note.** When the Planner retries a step with a note for its Worker, the Reviewer of that attempt reviews against the note, not only the original instruction. ([#183](https://github.com/foolzzz/looper/pull/183))

## Shutdown, run records and the task page

- **Stop exits.** A stopped worker pool answers a kill at once, because it has already ended every run. A Planner stops its running Workers and Reviewers together, and the TaskRouter stops its Planners together. A cancellation that arrives with a reply is kept, and a loop that lost one is cancelled again until it ends. A task stop that races the server's own stop no longer leaves `looper serve` running. ([#186](https://github.com/foolzzz/looper/pull/186))
- **Run records always end.** A run's row opens as `running` and is finished on a normal exit, a crash, a timeout, a stop, a cancel, a killed process and the server stopping. A Worker killed while it was reporting its result no longer leaves the row `running`. Reviewers of a stopped task are stopped too. Rows a killed server could not close are swept at the next start. A task that is not running has no `running` records. ([#177](https://github.com/foolzzz/looper/pull/177))
- **When a step started.** `task_steps.started_at` is the first time the step's Worker was dispatched. A retry, a review or a server restart does not move it. A step sent back to not started loses it, so time the task spent stopped is not counted. The Pipeline card and the Overview show "running for", "took" or "ran for" from that start. Steps from before the column stay blank. ([#184](https://github.com/foolzzz/looper/pull/184))
- **Pipeline hover and full screen.** Hovering a node shows its instruction, acceptance criteria, target files, dependencies, runs, result and timing. Dropped steps stay readable. The graph can go full screen (the browser's full screen, or an overlay when the browser refuses). Fit leaves room for the zoom controls, about 56 px on the left. Opening another task from a link resets the page to that task's Overview. ([#172](https://github.com/foolzzz/looper/pull/172), [#174](https://github.com/foolzzz/looper/pull/174), [#184](https://github.com/foolzzz/looper/pull/184))

## Behavior changes

These are the defaults that move in this release. Each one applies without a new setting unless the line says how to turn it off.

1. **User gates are on by default.** A project that never set `user_gates` now lets its Planners open gates. The attended Planner's contract grows by the gates section. Set the project to `user_gates: "off"` to keep the previous contract. A task a schedule starts still never opens a gate. ([#168](https://github.com/foolzzz/looper/pull/168), [#179](https://github.com/foolzzz/looper/pull/179))
2. **The agent room is on by default.** A project that never set `agent_room` gives every task a room and the room tools. A question to the seat of an ended step is answered by a read-only consult of that seat's last session; what it does not answer goes to the Planner. Set `agent_room` to `off` for the previous prompts and tool lists. ([#187](https://github.com/foolzzz/looper/pull/187), [#188](https://github.com/foolzzz/looper/pull/188))
3. **New projects default to worktree task workspaces.** A project created through the API, the task form or the Manager gets `task_workspaces: "worktree"`. An existing project and an imported project stay unset, which means tasks run in place. A task that names a directory other than its project's still gets a worktree. ([#190](https://github.com/foolzzz/looper/pull/190))
4. **Operator notes are on by default for every project, including ones that already exist.** `operator_notes` unset means on. The notes reach every runtime, including Codex, OMP and Grok. Set a project to `off` to stop injecting them. ([#190](https://github.com/foolzzz/looper/pull/190))
5. **Enabling a schedule and running it now need the next message.** Through the Manager, both wait for the user to confirm in the next message. The turn that created a schedule can neither enable it nor run it. If the user does not confirm, the schedule stays disabled and nothing is enabled and nothing runs. The dashboard and the HTTP API still perform the call they are given. ([#178](https://github.com/foolzzz/looper/pull/178))
6. **The Planner is read-only, enforced by tools.** Claude Code disallows the write tools. A Grok Planner has no shell. Where a runtime cannot refuse the call, Looper records a git change after the turn and does not revert it. ([#183](https://github.com/foolzzz/looper/pull/183))
7. **Concurrency counts one task, not the project.** Nothing limits how many tasks run at once. The role layer's Worker and Reviewer limits, and the built-in 16 and 8, apply to one task. Project-level limits are removed. See Breaking Changes. ([#173](https://github.com/foolzzz/looper/pull/173))

`append` remains the system-prompt default, and `--jobs` remains 1. Neither changes a running server. Step workspaces stay `shared` until a project sets `worktree`.

## The eval harness

- **Targeted evals, then a full tier once.** `evals/README.md` says which tier to run: targeted tasks and dialogs with `--reps 2` on a change (the Planner or Manager tier when the prompt or the contract changed), and the full tiers once on the release candidate. It recommends `--jobs 4`. ([#191](https://github.com/foolzzz/looper/pull/191), [#192](https://github.com/foolzzz/looper/pull/192))
- **`--jobs` runs cases together.** `run` and `dialogs` take `--jobs N`. The default is 1, which keeps the previous order. Rows stay in task and rep order. The spend cap counts the budgets of cases already in flight. Dialogs already had a database and a server each; `run` puts cases on one server in separate projects. ([#192](https://github.com/foolzzz/looper/pull/192))
- **Reps, errors, and baselines.** `--reps` repeats each case. A timeout or a spend cap is an error, not a model failure. Each dialog rep has its own database and server. Committed baselines cover three reps for the haiku and opus tiers the README asks for. The README's cost notes are the measured ones; this body does not repeat private spend totals. ([#167](https://github.com/foolzzz/looper/pull/167), [#176](https://github.com/foolzzz/looper/pull/176))

## Quality and testing

- Two timing tests that failed under CI load no longer depend on a 0.01 s window or a 30 s wait for Workers to start. The stop bound they measure is unchanged. Schedule tests that failed in the last minutes before midnight are pinned to noon. ([#171](https://github.com/foolzzz/looper/pull/171), [#194](https://github.com/foolzzz/looper/pull/194))
- The plan's validation rules now say: targeted tests locally, the full suite in CI, CI green before merge, and a real eval when model-visible text changes, at the tier the eval README names. ([#191](https://github.com/foolzzz/looper/pull/191))

## Breaking Changes

1. **Concurrency is per task.** Nothing waits for room under a project. `GET /api/tasks?group=queued` is a 400. `/api/overview` loses `tasks.queued`, each project's task limit and queued count, and the project's Worker and Reviewer limits. `/api/status` drops `tasks.pending`. A task's planner concurrency field is gone, and a Worker or Reviewer source that was `project` is `default`. `looper_concurrency` loses `scope`, `project` and `project_limit`. `looper_task_control start` loses `note`. At the next server start, a task left `pending` starts, instead of being marked stopped. Tasks present at the upgrade lose the project's limits and run with the per-task defaults; the migration writes the converted limits onto schedules only. A role-layer value that used to cap the whole project now caps one task, so more agents can run and spend at once. ([#173](https://github.com/foolzzz/looper/pull/173))
2. **User gates default on.** Every project that never set `user_gates` lets its Planners open gates, and the model-visible contract grows. Scheduled tasks do not. ([#179](https://github.com/foolzzz/looper/pull/179))
3. **The agent room defaults on.** Every such project gives task agents the room tools and the room section of the prompt. A question to the seat of an ended step starts a read-only consult of that session (0.50 USD by default; over-cap or unpriced answers are dropped). ([#187](https://github.com/foolzzz/looper/pull/187), [#188](https://github.com/foolzzz/looper/pull/188))
4. **New projects work in a git worktree, and operator notes turn on everywhere.** Existing projects stay in place until their `task_workspaces` is set. Notes turn on for existing projects too, on every runtime. ([#190](https://github.com/foolzzz/looper/pull/190))
5. **The Manager confirms enable and run-now.** v2.7.0 let the Manager enable or disable a schedule without a fresh confirmation of the enable. Enabling and running now wait for the next message. Create and edit exist; an imported schedule is disabled. ([#178](https://github.com/foolzzz/looper/pull/178))
6. **The Planner cannot write the task tree.** A prompt that told it not to write was the only check in v2.7.0. Tool refusals and, where the runtime cannot refuse, a recorded git diff replace that. A step that names `review_role` must name `review_roles`. Stored single review roles are migrated to a list of one, and the old columns go. ([#182](https://github.com/foolzzz/looper/pull/182), [#183](https://github.com/foolzzz/looper/pull/183))

**Also changed, with less authority or a different record.** Run records gain a finish on every exit path, so a cost or an overview that ignored a row left `running` now counts it. `started_at` is null on old steps. `system_prompt_mode` is `append` on existing profiles. Schedule saves no longer carry the old `warnings` field. Grok and replace mode do nothing until a profile uses them. ([#177](https://github.com/foolzzz/looper/pull/177), [#184](https://github.com/foolzzz/looper/pull/184), [#185](https://github.com/foolzzz/looper/pull/185), [#193](https://github.com/foolzzz/looper/pull/193))

## Upgrading from v2.7.0

1. **Install with `install.sh`.** It installs the latest release wheel, as for v2.7.0.
2. **Keep the first-start backup possible.** The schema changes, so the first start writes a `pg_dump` backup before migrating. Keep a `pg_dump` of at least the server's major version on `PATH` (or `LOOPER_PG_DUMP`, or `LOOPER_BACKUP_CMD`). `looper serve --skip-backup` migrates without one.
3. **Start once.** The upgrade adds the gate, room, template, task-workspace and cost columns, turns the new defaults on where a column is null (gates, agent room, operator notes), leaves existing projects in place for task workspaces, sets `system_prompt_mode` to `append`, and rewrites each step's single review role as a list of one.
4. **Decide on gates, the room and notes.** To keep Planners from asking, set `user_gates` to `off` on the project. To keep agents from messaging each other, set `agent_room` to `off`. To stop injecting operator notes, set `operator_notes` to `off`.
5. **New projects and concurrency.** A project you create after the upgrade runs tasks in worktrees. Lower a task's Worker and Reviewer limits if the old project cap was what held spend down, and set a per-task spend cap where you need one. Each task can now run 16 Workers and 8 Reviewers unless its own limit or the role layer says otherwise, and tasks no longer wait for each other.
6. **Grok, only if you want it.** Install the `grok` CLI, run its login on the server's machine, create an Agent Profile on runtime `grok` with provider `grok-login`, and select it. Until you do, nothing runs on Grok.
7. **Scripts.** Stop sending `group=queued`. Stop reading project concurrency off `/api/overview`. Send `review_roles` instead of `review_role`. Treat a Manager-created schedule as disabled until it is enabled, and expect enable and run-now from chat to wait for the next message.
8. **A key in a local transcript.** A CPA key was echoed once into a local session transcript. If that transcript is on a machine you use, rotate the key. Looper does not store the key in the release, and this body does not repeat it.
9. **Check.** `looper doctor`, and `looper service status` for the service.

```bash
curl -fsSL https://raw.githubusercontent.com/foolzzz/looper/main/install.sh | bash
looper doctor
looper serve
  # Or, with the service:
looper service restart && looper service status
```

**Rollback to v2.7.0.** Stop Looper (`looper service uninstall` if you installed the service), recreate the database empty and restore the pre-migration backup the first start logged (`pg_restore --no-owner --dbname "$LOOPER_DATABASE_URL" FILE`). Then install the v2.7.0 wheel, for example `uv tool install --force "looper @ https://github.com/foolzzz/looper/releases/download/v2.7.0/looper-2.7.0-py3-none-any.whl"`. `install.sh` always installs the latest release, so it cannot roll back. v2.7.0 does not know gates, the agent room, role templates, task worktrees or Grok profiles.

## Optional Capability Activation & Use

### User gates

**Activation:** On by default for every project that has not set `user_gates` (`null` means on). A new project is on. Turn a project on or off in Project → Settings → Execution, or with `PUT /api/projects/PROJECT_ID` and `{"user_gates": "on"}`. Optional `gate_reminder_hours` is 0 to 168, null for 24, and 0 for no reminder. For a task created on the dashboard or in the web chat, set `user_gates.dashboard_target` in Settings → Channels (`PUT /api/gate-settings`) to a sender the channel allowlist already allows, on a channel that is enabled. A task a schedule starts never opens a gate, whatever the project says.

**Validation:** `GET /api/projects` shows `user_gates` on (or null, which is on). A waiting gate appears in the Needs you group, on the task Overview, and as a Pipeline node. `GET /api/tasks/TASK_ID` lists `gates`. A task asked for in Lark or Telegram gets the gate card in that chat; a reply under the card shows up in the gate discussion and does not start a Manager turn.

**Disable / rollback:** `PUT /api/projects/PROJECT_ID` with `{"user_gates": "off"}`. Later plans cannot add a gate, and the Planner contract is the one from before gates. A gate already open keeps waiting until it closes, is cancelled or the task ends. Clear `dashboard_target` to stop posting dashboard tasks to a chat; the task page still works.

**Authority boundary:** An open gate pauses only the steps that depend on it. The Planner writes the questions and the closing summary the later agents read. Anyone who can message the task page, and any allowlisted sender in the gate's chat, can answer. In a Lark group the next message that @-mentions the bot in that thread is the answer, from whichever listed sender sends it. The Manager relay writes into the gate as that user. Confirmations elsewhere stay per chat. The courier posts as the bot. No new secret is stored; the chat ids are the ones the channel already had for that task.

**Docs:** https://github.com/foolzzz/looper/blob/v2.8.0/docs/architecture/agent-system.md#user-gates

```bash
curl -s -X PUT http://127.0.0.1:8767/api/projects/PROJECT_ID -H 'Content-Type: application/json' \
  -d '{"user_gates": "on", "gate_reminder_hours": 24}'
curl -s http://127.0.0.1:8767/api/gate-settings
curl -s -X PUT http://127.0.0.1:8767/api/gate-settings -H 'Content-Type: application/json' \
  -d '{"dashboard_target": {"channel": "lark", "chat_id": "CHAT_ID"}}'
curl -s http://127.0.0.1:8767/api/tasks/TASK_ID | python3 -c 'import json,sys; print(json.load(sys.stdin).get("gates"))'
  # Turn gates off:
curl -s -X PUT http://127.0.0.1:8767/api/projects/PROJECT_ID -H 'Content-Type: application/json' \
  -d '{"user_gates": "off"}'
```

### Agent room

**Activation:** On by default (`agent_room` null means on). Set the project's `agent_room` to `on` or leave it unset (Project → Settings → Execution, or `PUT /api/projects/PROJECT_ID`). Optional limits: `room_post_per_minute` (1 to 60, null for 6), `room_broadcasts_per_run` (0 to 50, null for 5), `room_message_max_chars` (500 to 20,000, null for 4,000), `room_messages_per_task` (20 to 5,000, null for 300), `room_ping_pong_rounds` (2 to 50, null for 6), `room_wait_max_seconds` (0 to 120, null for 60). No separate install. With the room on, a question to the seat of an ended step is answered by a read-only consult of that seat's last session ([#188](https://github.com/foolzzz/looper/pull/188)). The per-consult cap defaults to 0.50 USD (`room_consult_budget_usd`), the timeout to 300 seconds (`room_consult_timeout_seconds`), and the count to 10 consults per task (`room_consults_per_task`). An answer over the cap, or an answer with no reported price, is dropped.

**Validation:** `GET /api/projects` shows `agent_room` on or null. After a task runs, `GET /api/tasks/TASK_ID/room` lists seats and messages, and `GET /api/tasks/TASK_ID` has `room` counts. The task page has a Room tab. A run's first turn names its seat. Refused posts show in the task activity.

**Disable / rollback:** Set `agent_room` to `off`. Later runs get the previous prompt and no room tools. Messages already stored stay with the task until it is started over or deleted. There is nothing to uninstall.

**Authority boundary:** Agents of one task can instruct each other. A work seat cannot lobby a Reviewer except to answer that Reviewer's own question. Review seats cannot broadcast. The Planner sees the whole room. Tokens are per run, revoked when the run ends, and are not the Manager's token. The user and the Manager do not post in this release; they can read. Messages are not a sandbox: an agent still has its role's tools in the worktree. Rate limits are the project settings above. Consults are read-only and fail closed: an answer over the cap, or an answer with no reported price, is dropped, and what a consult does not answer goes to the Planner ([#188](https://github.com/foolzzz/looper/pull/188)). An OMP checkout is not a sandbox, and a Claude Code fork stays in Claude Code's session store; see Known limits.

**Docs:** https://github.com/foolzzz/looper/blob/v2.8.0/docs/architecture/agent-system.md#a-tasks-agent-room

```bash
curl -s -X PUT http://127.0.0.1:8767/api/projects/PROJECT_ID -H 'Content-Type: application/json' \
  -d '{"agent_room": "on", "room_post_per_minute": 6, "room_messages_per_task": 300}'
curl -s http://127.0.0.1:8767/api/tasks/TASK_ID/room | python3 -m json.tool | head -40
  # Turn the room off:
curl -s -X PUT http://127.0.0.1:8767/api/projects/PROJECT_ID -H 'Content-Type: application/json' \
  -d '{"agent_room": "off"}'
```

### Grok runtime

**Activation:** Off until a profile uses it. With `grok` on the server's `PATH`, `looper serve` registers runtime `rt-grok`. Log in with Grok's own login on the server's machine, create an Agent Profile with provider `prov-grok-login` (Settings → Agent Profiles, or `POST /api/agent-profiles`) and select it for a role, a project or a task. Profiles that do not choose Grok are unchanged.

**Validation:** Settings → Agent Runtimes lists Grok when the CLI is on `PATH`. `looper doctor` includes a Grok login check while a profile uses it. `GET /api/status` has the `grok_login` check and `GET /api/registry` the provider's login state. A run record names the profile and, when the runtime reported a cost, that cost.

**Disable / rollback:** Select another profile on that layer (or null to inherit) and delete the Grok profile (409 while something selects it). If a run left a copy of the login, Looper deletes the copy, restores the link and stops using the login until you have checked the login and chosen "Use the login again" (`DELETE /api/providers/prov-grok-login/login-problem`). Removing the `grok` binary and restarting drops the runtime from detection.

**Authority boundary:** A Grok agent runs as your user, with `--always-approve` and `--trust`, in a home Looper owns. The login stays in your Grok login file; each home links to it and Looper does not store the token. The shell of a Worker or Reviewer is given your home back, so it can read what your user can read. A Grok Planner has no shell. Grok does not stop at a per-run spend cap; the task cap still stops further runs after a run reports. A zero cost with tokens spent is unknown, not free. There is no API-key provider for Grok in this release.

**Docs:** https://github.com/foolzzz/looper/blob/v2.8.0/docs/architecture/agent-system.md#runtimes-llm-providers-and-agent-profiles

```bash
grok --version
curl -s -X POST http://127.0.0.1:8767/api/agent-profiles -H 'Content-Type: application/json' \
  -d '{"name": "grok/login", "runtime_id": "rt-grok", "provider_id": "prov-grok-login", "model": "grok-4.7"}'
curl -s -X PUT http://127.0.0.1:8767/api/agent-settings/roles/worker -H 'Content-Type: application/json' \
  -d '{"profile_id": "PROFILE_ID"}'
looper doctor
  # Undo:
curl -s -X PUT http://127.0.0.1:8767/api/agent-settings/roles/worker -H 'Content-Type: application/json' \
  -d '{"profile_id": null}'
curl -s -X DELETE http://127.0.0.1:8767/api/agent-profiles/PROFILE_ID
```

### System prompt replace

**Activation:** Off until a profile sets it. `system_prompt_mode` defaults to `append` on every profile, including ones from v2.7.0. Set `replace` on an Agent Profile in Settings → Agent Profiles, `POST` or `PUT /api/agent-profiles`, configuration import, or the Manager's profile tool. Claude Code, Codex, Grok and OMP accept replace. A runtime that cannot is a 400 at save, with the reason, and the editor disables the choice.

**Validation:** `GET /api/registry` and `GET /api/agent-profiles` show `system_prompt_mode`. A run record stores `system_prompt_mode`, and the run page shows a "replaced default" badge when it is `replace`. Append mode keeps the previous command line and generated home files.

**Disable / rollback:** Set the profile back to `append`. The next run appends again. Existing run records keep the mode they ran with. There is no global switch.

**Authority boundary:** Replace drops that runtime's default system prompt, including its built-in guidance, and sends Looper's prompt as the whole instruction. Tool definitions stay. The profile's role prompt, harness, project instructions and operator notes still apply as they do in append mode. This can raise contract violations on a small model (haiku: success 52/66 against 53/66 in append, contract violations 3.7 to 8.3; repair turns recover). It does not grant tools the runtime did not already have. Only someone who can edit the profile, or the Manager through its profile tool, can set it.

**Docs:** https://github.com/foolzzz/looper/blob/v2.8.0/docs/architecture/agent-system.md#runtimes-llm-providers-and-agent-profiles

```bash
curl -s -X PUT http://127.0.0.1:8767/api/agent-profiles/PROFILE_ID -H 'Content-Type: application/json' \
  -d '{"system_prompt_mode": "replace"}'
curl -s http://127.0.0.1:8767/api/registry | python3 -c 'import json,sys; [print(p["name"], p.get("system_prompt_mode")) for p in json.load(sys.stdin)["profiles"]]'
  # Back to append:
curl -s -X PUT http://127.0.0.1:8767/api/agent-profiles/PROFILE_ID -H 'Content-Type: application/json' \
  -d '{"system_prompt_mode": "append"}'
```

### Task workspaces

**Activation:** A new project gets `task_workspaces` `worktree` (the API, the task form and the Manager). An existing or imported project is null, which means in place, until you set `worktree` (Project → Settings → Execution, or `PUT /api/projects/PROJECT_ID`). A task may also ask for a mode, and a task that names a directory other than the project's gets a worktree either way. `operator_notes` is on by default for every project, including existing ones (`null` means on). `workspace_links` is up to 20 paths relative to the project directory, null for none.

**Validation:** `GET /api/projects` shows `task_workspaces` and `operator_notes`. `GET /api/workspaces/check` and the create answer's `workspace` field say which repository, branch and base the task will use, and warn `not_git`, `uncommitted`, `shared` or `large_checkout`. The activity names the branch `looper/<task id>/task`. On completion the task page and the Lark or Telegram end notice name the branch. A run record's prompt layers include `operator_notes` (hash, files, omitted) when notes were applied.

**Disable / rollback:** Set `task_workspaces` to `in_place` so later tasks that do not ask otherwise run in the checkout. Set `operator_notes` to `off` to stop injecting notes; runs already started keep the prompt they were given. Looper never merges the task branch. Delete the branch in git if you do not want it. A stopped task keeps its worktree for restart; deleting the task removes the worktree and keeps the branch. `git` history on that branch is the task's commits.

**Authority boundary:** Looper creates a worktree and a branch in your repository, commits leftovers when the task completes (Looper's identity, no hooks, links excluded) and does not push, switch your checkout or merge. Uncommitted work in the named directory is not copied into the worktree; the check warns. Agents run in the worktree with the same tools as before, as your user. Operator notes are a read-only slice of your Claude Code auto-memory for that repository, injected into every runtime's prompt, and may contain whatever that memory contains. A directory outside git runs in place, with a `not_git` warning, including when the worktree was only the default.

**Docs:** https://github.com/foolzzz/looper/blob/v2.8.0/docs/architecture/agent-system.md#task-workspaces

```bash
curl -s -X PUT http://127.0.0.1:8767/api/projects/PROJECT_ID -H 'Content-Type: application/json' \
  -d '{"task_workspaces": "worktree", "operator_notes": "on"}'
curl -s 'http://127.0.0.1:8767/api/workspaces/check?project_id=PROJECT_ID'
  # Run tasks in the checkout again, and stop injecting notes:
curl -s -X PUT http://127.0.0.1:8767/api/projects/PROJECT_ID -H 'Content-Type: application/json' \
  -d '{"task_workspaces": "in_place", "operator_notes": "off"}'
```

### Planner-defined roles

**Activation:** Still off until the project sets `planner_roles` to `on` (Project → Settings → Execution, or `PUT /api/projects/PROJECT_ID`). Templates can be written while the switch is off; the Planner copies them only while it is on. `PUT /api/projects/PROJECT_ID/role-templates/KEY` with `key`, `kind`, `description`, `role_prompt`, and optional `harness`, `profile_id` and `items`. Optional `role_text_max_chars` is 500 to 20,000, null for 8,000. A role's profile must be on the project's allowed-profile list. Catalog items load for a role only after an install names `task_role`.

**Validation:** `GET /api/projects/PROJECT_ID/role-templates` lists templates. After a task defines roles, `GET /api/tasks/TASK_ID` lists `roles` with versions, `edited_by_user`, `template_key` and stats, and steps show `review_roles`. The task page Roles section has Edit. `GET /api/projects/PROJECT_ID/role-stats` sums roles across tasks. A run as a role is labeled on the Runs page and the Agent Timeline.

**Disable / rollback:** Set `planner_roles` to `off`. No role is defined or named after that; steps that already name a role keep running as it. Delete a template with `DELETE /api/projects/PROJECT_ID/role-templates/KEY`; roles already copied stay. Starting a task over deletes its roles. The user's edit remains the current version until a later user edit; the Planner cannot overwrite it.

**Authority boundary:** The Planner still writes the role prompt of a role the user has not edited, so a Worker follows text a model wrote, with that role's tools and no permission prompts. The boundaries still come after everything the Planner or the user wrote and before the contract, and change only on the shared defaults. A review role runs only after the built-in Reviewer passes. An advisory review role does not block accept. Role items are limited to catalog items you installed for `task_role`. Templates in the configuration file carry prompts; import does not enable `planner_roles`.

**Docs:** https://github.com/foolzzz/looper/blob/v2.8.0/docs/architecture/agent-system.md#roles-a-tasks-planner-defines

### Scheduled tasks

**Activation:** Unchanged for the dashboard: a new schedule is created disabled, and enabling it is the approval for the unattended tasks it starts. This release adds the Manager path. `looper_schedules` `create` (always disabled), `update`, and `run`. Enable (`action` `enable`) and run now (`action` `run`) do not run until the user confirms in the next message, through `looper_confirm`. The create turn cannot enable or run. Schedules are included in configuration export and import, and an imported schedule is disabled. The HTTP API is the same create and enable as v2.7.0; calling it directly does not insert a chat confirmation.

**Validation:** After the Manager creates one, the reply includes the configuration block and the next fires, and `GET /api/schedules/SCHEDULE_ID` shows `enabled` false. After you confirm enable, `enabled` is true and `next_fire_at` is set. A run now without a confirmation does not start a task. `GET /api/projects/PROJECT_ID/schedules` lists them. Export the configuration and confirm the schedule is present and that a re-import is disabled.

**Disable / rollback:** The Manager's disable does not ask. `{"enabled": false}` on `PUT /api/schedules/SCHEDULE_ID` stops further fires and does not stop a task already running. Delete still asks in chat and is `DELETE /api/schedules/SCHEDULE_ID` on the API; tasks the schedule already started stay. To go back to a Manager that cannot create, use a v2.7.0 build; the rows remain, disabled if you disable them first.

**Authority boundary:** A confirmed enable approves every later firing: unattended Planner, Worker and Reviewer runs with their tools and no permission prompts, under the schedule's overlap, budgets, timeout and the task's concurrency. Run now starts one task immediately and spends against the same caps. The user who confirms is whoever sends the next message in that chat, within the confirmation window. A schedule created from an allowlisted Telegram or Lark chat notifies that sender when no other notify target is set. The export file contains requirements and commands, not channel secrets. The gate command, if set, still runs as your user on every firing.

**Docs:** https://github.com/foolzzz/looper/blob/v2.8.0/docs/architecture/agent-system.md#schedules-tasks-on-a-time-rule


### Step workspaces

**Activation:** Per project, `shared` by default, including null. Set `step_workspaces` to `worktree` (Project → Settings → Execution, or `PUT /api/projects/PROJECT_ID`). Optional `workspace_links`: up to 20 paths relative to the task directory (no `.` or `..`, nothing in `.git`, no duplicates, none inside another). It applies when the task directory is a git checkout on a branch with at least one commit, git is 2.40 or later, no merge, rebase, cherry-pick, revert or bisect is in progress, the files at `HEAD` are at most 1 GiB, and only to steps that run while other steps of their task do. A gate step never gets a worktree. Over 1 GiB, or a checkout that fails the git checks, the round runs one step at a time and the activity says why.

**Validation:** `GET /api/projects` shows `step_workspaces` and `workspace_links`. A task with parallel steps logs the start commit, each step's worktree and branch, and each merge. `GET /api/tasks/TASK_ID` includes `step_workspaces` with `start`, each workspace, and `undo`. The task page lists them and offers Discard while the task is not running. `looper doctor` warns when git is missing or older than 2.40 and checks a project whose default directory is set to `worktree`.

**Disable / rollback:** Set `step_workspaces` back to `shared`. Rounds dispatched afterwards share the task directory. Discard one leftover with `POST /api/tasks/TASK_ID/workspaces/WORKSPACE_ID/discard` while the task is not running. `git reset` to the start commit the activity names undoes the task's commits and keeps the changes; `git revert -m 1` undoes one step's merge. A completed task's worktrees and branches are removed; a failed, stopped or cancelled task keeps unmerged ones until start-over, delete or discard.

**Authority boundary:** Looper commits on the task branch: a checkpoint of pending work before a parallel round, leftovers, and one merge commit per accepted step. Those commits are unsigned and run no hooks. Looper does not push. Links share ignored paths (such as dependencies) with the task directory and are not committed as links. A Worker that replaces a link with files of its own commits those files. Merge conflicts leave the task directory untouched and go to the Planner. It adds no model cost. The 1 GiB limit avoids copying a huge checkout once per step.

**Docs:** https://github.com/foolzzz/looper/blob/v2.8.0/docs/architecture/agent-system.md#step-workspaces

```bash
curl -s -X PUT http://127.0.0.1:8767/api/projects/PROJECT_ID -H 'Content-Type: application/json' \
  -d '{"step_workspaces": "worktree", "workspace_links": ["node_modules"]}'
curl -s http://127.0.0.1:8767/api/tasks/TASK_ID | python3 -c 'import json,sys; print(json.load(sys.stdin).get("step_workspaces"))'
  # Turn step worktrees off:
curl -s -X PUT http://127.0.0.1:8767/api/projects/PROJECT_ID -H 'Content-Type: application/json' \
  -d '{"step_workspaces": "shared"}'
```

## Known limits

- **Replace mode drops each runtime's default guidance.** It is opt-in per profile. On haiku, replace mode scored 52/66 where append scored 53/66, and contract violations rose from 3.7 to 8.3. Repair turns recover. The runtime's tool definitions stay; its own instructions do not.
- **A CPA key was echoed once into a local session transcript.** Rotate that key if the transcript is on a machine you use. This body does not contain the key or the transcript's path.
- **Telegram retried posts can duplicate.** Lark dedupes a gate post with an idempotency key. Telegram has none, so a post retried after a lost answer can arrive twice.
- **A Grok Planner has no shell.** Its read-only tools are read, search and list. It cannot run git or other commands. A Claude Code Planner can still run the read-only git commands listed under A read-only Planner. Grok also has no per-run spend cap and reports cost only when the run ends.
- **Consult source pinning is not serialized against a seat restart.** A restart of the seat is not held off by the pin of the run the consult reads. ([#188](https://github.com/foolzzz/looper/pull/188))
- **Claude Code and OMP read-only allowlists were not verified in a real run.** A consult asks Claude Code for only `Read`, `Glob` and `Grep`, and OMP for only `read`, `glob` and `grep`. That restriction was not checked against a live CLI. ([#188](https://github.com/foolzzz/looper/pull/188))
- **An OMP consult checkout is not a sandbox.** OMP runs as your user in a detached checkout of the task branch, removed afterwards. A write outside that checkout is neither prevented nor detected. ([#188](https://github.com/foolzzz/looper/pull/188))
- **Codex instruction precedence on a real resume was not verified.** A Codex consult copies only the kept session. Which instruction wins when that session is resumed for real was not checked. ([#188](https://github.com/foolzzz/looper/pull/188))
- **A fast-exiting consult parent can orphan detached children.** If the process that started the consult exits first, children it has already detached can keep running. ([#188](https://github.com/foolzzz/looper/pull/188))
- **A timed-out worktree add can leave a partial checkout.** A consult checkout whose worktree add times out can leave that partial tree on disk. ([#188](https://github.com/foolzzz/looper/pull/188))
- **Claude Code consult forks stay in Claude's session store.** Claude Code keeps the fork the way it keeps every session, and Looper does not delete entries in Claude Code's own directory. ([#188](https://github.com/foolzzz/looper/pull/188))
- A checkout over 1 GiB does not get per-step worktrees; the round runs one step at a time. A directory outside git never gets a task worktree and runs in place.
- The HTTP API still has no authentication apart from the agents' own tool routes. Keep the default `127.0.0.1` bind.
- Grok's login refresh write-back was not verified. If a run replaces the login link with a copy, Looper withdraws the login until you confirm it again.

- **A haiku Manager can skip asking for a schedule's project.** In the release-candidate dialogs, a haiku Manager created a schedule without asking which project in 2 of 3 runs. The schedule is created disabled, so nothing runs until the user enables it, which needs the next message. An opus Manager asked every time.

### 用户关卡

- **步骤可以是关卡。** `user_gates` 开启时（默认，未设置也算开启），Planner 可以加入 `kind` 为 `gate` 的步骤。依赖它的步骤等待，计划的其余部分继续。有关卡开着时任务为 `waiting_user`。关闭时把总结写成补充说明，之后的 Worker 和 Reviewer 会读到。项目设为 `off` 时契约与以前一致，关卡步骤会被拒绝并说明原因。定时任务发起的任务从不开关卡。（[#168](https://github.com/foolzzz/looper/pull/168)）
- **在任务页上。** Overview 顶部显示等待中的关卡：议程、讨论、选项按钮、输入框和结束讨论。Pipeline 把关卡画成独立节点。Dashboard 和 Tasks 页有 Needs you 分组。（[#168](https://github.com/foolzzz/looper/pull/168)）
- **飞书和 Telegram。** `looper serve` 里的 `GateCourier` 把讨论发到任务来自的聊天。在 dashboard 或网页聊天里发起的任务，发到系统设置 `user_gates.dashboard_target` 指定的聊天（Settings → Channels）；没设就只留在任务页。卡片单独一条，之后的消息回复在它下面。该线程里的回复在 Manager 的模型看到之前就路由到关卡。`looper_task_gate_reply` 让 Manager 把用户的话写入仍在等待的关卡。（[#179](https://github.com/foolzzz/looper/pull/179)）
- **投递。** 飞书用幂等键，同一键在一小时内只发一条。Telegram 没有这个键：应答丢失后重试的帖子可能到两次（见“已知限制”）。被回复的消息已不在时，改为单独发一条。渠道上的回答只有在渠道发出之后才写入聊天历史。（[#179](https://github.com/foolzzz/looper/pull/179)）
- **轮到谁。** 停止、失败或取消的任务上，本来在等 Planner 的关卡显示“Your turn”。任务在跑时显示“Planner answering”。（[#174](https://github.com/foolzzz/looper/pull/174)）

### Agent room

- **默认开启。** `agent_room` 开启时（默认，未设置也算），任务的 Planner 和各步骤的 agent 共用一个 room。关掉之后，提示词、工具列表和命令行与以前一致。席位是 Planner，以及每个步骤、每个角色一个。是否在线由谁正在运行决定。（[#187](https://github.com/foolzzz/looper/pull/187)）
- **工具和范围。** 每次 Worker 和 Reviewer 运行有自己的令牌，运行结束即作废。工作席位可以发给工作席位、角色、Planner 和所有人；发给评审席位时，只能回答该席位问它的问题。评审席位只能向工作席位或 Planner 提问。消息只增不改，随任务走，从头再来时清掉。（[#187](https://github.com/foolzzz/looper/pull/187)）
- **消息怎么到。** 运行的第一回合列出自己的席位、谁在线、以及给它的消息。发给 Planner 的消息唤醒一轮 `[ROOM]`。任务页有 Room 标签。Manager 可以读，不能发。（[#187](https://github.com/foolzzz/looper/pull/187)）
- **上限。** 每分钟条数、广播、长度、每个任务的总条数、收件箱等待时长都是项目设置。问已结束步骤的席位时，由该席位最后一次会话的只读 consult 回答；没答上的部分交给 Planner。从未运行过的席位交给 Planner。（[#187](https://github.com/foolzzz/looper/pull/187)、[#188](https://github.com/foolzzz/looper/pull/188)）

### Agent room consults

- **问已结束的席位，用它最后一次会话。** 问一个已结束步骤的席位时，由该席位最后一次会话的只读 fork 来回答，回答以该席位的名义发出。consult 没答上的部分交给 Planner。从未运行过的席位收到问题时，交给 Planner。（[#188](https://github.com/foolzzz/looper/pull/188)）
- **只读，且只用那一份会话。** Claude Code 用 `--resume` 和 `--fork-session` 续接，只给 `Read`、`Glob` 和 `Grep`。Codex 和 OMP 只复制该运行留下的会话。Grok 在自己的家目录里放这一份会话的副本，只用只读工具（`read_file`、`grep` 和 `list_dir`）；MCP 工具仍可通过 `use_tool` 调用，该家目录事后删除。Claude Code、Codex 和 Grok 读的是检出现在的样子。OMP 在一份事后删除的分离检出里运行。见“已知限制”。（[#188](https://github.com/foolzzz/looper/pull/188)）
- **上限，失败即关闭。** 单次 consult 的上限默认 0.50 USD（`room_consult_budget_usd`），超时 300 秒（`room_consult_timeout_seconds`），每个任务 10 次（`room_consults_per_task`）。超过上限的回答，或没有报价的回答，会被丢掉。（[#188](https://github.com/foolzzz/looper/pull/188)）

### Planner 定义的角色和模板

- **模板。** 项目保存角色模板。无论 `planner_roles` 开没开，都按任务角色的规则检查。开关打开时，`[PLAN]` 和 `[RESTART]` 会列出它们，`looper_task_role_set` 的 `template` 复制一份。调用里给的字段覆盖模板。之后改模板不会改已经复制出的角色。配置文件按名称携带模板。（[#181](https://github.com/foolzzz/looper/pull/181)）
- **用户的修改。** 任务未完成时，`PUT /api/tasks/:id/roles/:key` 以用户身份写入新版本并通知 Planner，此后 Planner 不能再改这个角色。两个写入者不能互相覆盖：后一个得到冲突并重新读取。（[#181](https://github.com/foolzzz/looper/pull/181)）
- **按顺序的评审角色。** 步骤用 `review_roles` 列表。必过的角色不通过时，后面的不再跑。v2.7.0 的 `review_role` 和 `review_role_required` 会被拒绝，已存的步骤迁移成只有一项的列表。（[#182](https://github.com/foolzzz/looper/pull/182)）
- **目录条目和项目汇总。** 安装可以指定 `task_role`，于是只加载给点名该条目的角色，最多 20 个。`GET /api/projects/:id/role-stats` 按角色 id 汇总项目内各任务。（[#182](https://github.com/foolzzz/looper/pull/182)）
- **运行显示角色名。** Agent Timeline、Runs、History 标题、Overview 和 Chat 页在运行记录了角色时显示 `fe_rd · work`，而不是 Worker。任务页有 Agents 标签。（[#169](https://github.com/foolzzz/looper/pull/169)、[#170](https://github.com/foolzzz/looper/pull/170)）

### Grok 运行时

- **第四种运行时。** `grok` 在服务的 `PATH` 上时，`looper serve` 注册运行时 `grok`（`rt-grok`）。无头运行，提示词走标准输入，使用内置 provider `grok-login`（`prov-grok-login`）。Manager 和 Planner 每回合一个进程并续接会话。对照 Grok 1.0.62 核实过。（[#185](https://github.com/foolzzz/looper/pull/185)）
- **自己的家目录。** `GROK_HOME` 和 `HOME` 都指向 Looper 拥有的家目录，因此不会加载操作者的 skill、Claude Code 插件和 hook，或 Cursor 配置。登录文件是链接不是副本，和 Codex 的 ChatGPT 登录一样。（[#185](https://github.com/foolzzz/looper/pull/185)）
- **花费和工具。** 花费用 Grok 自己报告的数。花了 token 但花费为 0 视为未知。Grok 没有单次花费上限参数，只在运行结束时报花费，所以单次上限停不住一次 Grok 运行。Grok 的 Planner 没有 shell（见“已知限制”）。（[#185](https://github.com/foolzzz/looper/pull/185)）

### System prompt 追加或替换

- **按 Agent Profile。** `system_prompt_mode` 为 `append`（默认，与 v2.7.0 逐字节一致）或 `replace`。API、registry、配置导入导出、派生 Profile 和 Manager 的 Profile 工具都读写它。运行记录保存模式，替换过默认提示词的运行在运行页上有标记。（[#193](https://github.com/foolzzz/looper/pull/193)）
- **替换怎么做。** Claude Code 用 `--system-prompt-file`。Codex 用 `model_instructions_file`，家目录的 `AGENTS.md` 留空。Grok 用带 `prompt_mode: full` 的 `--agent`。OMP 用 `--system-prompt`。运行时不能替换时保存返回 400，编辑器把选项置灰并给出原因。不会悄悄退回追加。（[#193](https://github.com/foolzzz/looper/pull/193)）
- **需显式打开，并丢掉运行时自带的指导。** 在 haiku 上，替换模式为 52/66，追加模式为 53/66，契约违约从 3.7 升到 8.3；修复回合能收回。见“已知限制”。（[#193](https://github.com/foolzzz/looper/pull/193)）

### 任务工作目录和操作者笔记

- **任务在哪跑。** 任务指定一个工作目录。模式按任务的要求；若该目录不是项目的目录，则用 worktree；否则按项目的 `task_workspaces`。经 API、任务表单或 Manager 创建的项目得到 `worktree`。已有或导入的项目保持空，表示就地运行。（[#190](https://github.com/foolzzz/looper/pull/190)）
- **Worktree。** Planner 启动、重启、继续或恢复之前，Looper 在 runtime root 的 `task-worktrees/<任务 id>` 准备分支 `looper/<任务 id>/task`。分支不会被合回。任务完成时，未提交的改动提交到该分支上，worktree 删除，分支留下。不在 git 里的目录就地运行，这种回退也会警告 `not_git`。（[#190](https://github.com/foolzzz/looper/pull/190)）
- **操作者笔记对每个项目开启。** `operator_notes` 为空即开启，包括已有项目。设为 `off` 可关。Planner、Worker 和 Reviewer 在项目知识之后得到该目录的 Claude Code 自动记忆的只读副本（`MEMORY.md` 前 200 行及其指向的 markdown，共 24 KiB 以内）。同一些笔记注入每一种运行时，包括 Codex、OMP 和 Grok。它们是背景，任务和文件优先。Looper 只读。不包括过去的会话记录。（[#190](https://github.com/foolzzz/looper/pull/190)）
- **步骤 worktree 仍需开启。** 并行步骤各自的 worktree 仍是项目设置，默认 `shared`。本版本增加最多 20 条指回任务目录的链接、1 GiB 的检出上限（超过则该轮一步一步跑）、合并失败时保留的文件、任务页上的撤销命令和 Discard，以及 `looper doctor` 检查。链接不会作为步骤结果被提交。（[#180](https://github.com/foolzzz/looper/pull/180)）

### Manager 的定时任务工具

- **新建、修改、运行、导出。** `looper_schedules` 增加 `create`、`update` 和 `run`，走 dashboard 同一套代码。新建总是停用，且创建它的那一回合不能启用也不能运行。提高或取消花费上限要先确认。`looper_config_export` 把配置写到 runtime root 的 exports 目录，不接受聊天里给的路径，文件里没有密钥。（[#178](https://github.com/foolzzz/looper/pull/178)）
- **确认。** 启用和立即运行需要用户在下一条消息里确认。用户不确认，定时任务保持停用，不会被启用，也不会跑起来。删除仍要确认。停用不要确认。从 Telegram 或飞书聊天里创建、又没有自己的通知对象时，消息发给提问的那个人，前提是渠道白名单允许。（[#178](https://github.com/foolzzz/looper/pull/178)）
- **配置文件。** 定时任务随项目进出配置文件。导入的定时任务总是停用。（[#178](https://github.com/foolzzz/looper/pull/178)）

### 按模型的任务花费

- **在任务上。** `GET /api/tasks/:id` 和 `GET /api/tasks` 的每个任务都带 `cost`：`cost_usd`、`runs`、仍在跑的次数、结束了但没报花费的次数，以及 Planner、Worker、Reviewer 的 `by_role`。`by_model` 每个模型一行：运行次数、仍在跑、未计价、被打断、输入、输出、缓存读、缓存写 token，以及 `cost_usd`（没有任何运行报告花费时为 null）。各模型的花费加起来等于任务的 `cost_usd`。Overview 显示“Cost by agent and model”和 By model 表。（[#189](https://github.com/foolzzz/looper/pull/189)）
- **Manager 的回合另计。** `manager_by_model` 用同样的行，记点名了这个任务、或工具调用只指向这一个任务的 Manager 回合。这些回合不进任务的 `cost_usd`、`by_role`、`by_model` 和花费上限。涉及多个任务或没有任务的回合不归任何任务。定时任务的运行还在进行时，花费按该任务已发生的部分计，不含 Manager。（[#189](https://github.com/foolzzz/looper/pull/189)）

### 只读 Planner

- **由工具强制。** Planner 不再能自由改工作树。Claude Code 去掉跳过权限，禁止 Edit、Write 和 NotebookEdit，仍允许 skill、网页抓取和搜索，以及它的 MCP 服务。读、列目录、搜索和 `git status`、`log`、`diff`、`show` 仍允许。重定向、`touch`、会写文件的脚本和 `git commit` 被拒绝。拒绝记在运行记录上，任务活动里写明拒绝了多少次。（[#183](https://github.com/foolzzz/looper/pull/183)）
- **运行时无法拒绝时。** 命令保持原样，Looper 比较回合前后任务目录的 git 检出。有变化就记录。不回滚，因为改动可能来自用户或 Worker。Grok 的 Planner 没有 shell：工具只有读、搜索和列目录。（[#183](https://github.com/foolzzz/looper/pull/183)、[#185](https://github.com/foolzzz/looper/pull/185)）
- **Reviewer 能看到重试说明。** Planner 带着给 Worker 的说明重试一步时，这一次的 Reviewer 按该说明评审，不只按原来的指令。（[#183](https://github.com/foolzzz/looper/pull/183)）

### 停止、运行记录和任务页

- **停止会退出。** 已经停掉的 worker pool 会立刻应答杀死请求，因为它已经结束了所有运行。Planner 同时停止自己正在跑的 Worker 和 Reviewer，TaskRouter 同时停止各 Planner。和应答一起到达的取消会被保留。任务停止和服务自身的停止撞在一起时，不再把 `looper serve` 留在运行中。（[#186](https://github.com/foolzzz/looper/pull/186)）
- **运行记录总会结束。** 记录以 `running` 打开，在正常退出、崩溃、超时、停止、取消、进程被杀死和服务停止时写上终态。Worker 在报告结果时被杀死，不再把行留在 `running`。已停止任务的 Reviewer 也会被停掉。被杀死的服务来不及关闭的行，下次启动时扫掉。（[#177](https://github.com/foolzzz/looper/pull/177)）
- **步骤何时开始。** `started_at` 是该步骤的 Worker 第一次被派出的时间。重试、评审或服务重启不挪动它。步骤被退回未开始时清掉，因此任务停着的时间不计。加列之前的步骤保持空白。（[#184](https://github.com/foolzzz/looper/pull/184)）
- **Pipeline 悬停和全屏。** 悬停节点显示指令、验收标准、目标文件、依赖、运行、结果和时间。图可以全屏（浏览器的全屏，浏览器拒绝时用覆盖层）。适配时给缩放控件留出左边大约 56 px。从链接打开另一个任务时，页面回到那个任务的 Overview。（[#172](https://github.com/foolzzz/looper/pull/172)、[#174](https://github.com/foolzzz/looper/pull/174)、[#184](https://github.com/foolzzz/looper/pull/184)）

### 行为变化

下面是本版本会改变的默认值。除非该条写了怎么关，否则不用新设置就会生效。

1. **用户关卡默认开启。** 从未设置 `user_gates` 的项目，其 Planner 现在可以开关卡。有人值守的 Planner 契约增加关卡一节。把项目设为 `user_gates: "off"` 可保持以前的契约。定时任务发起的任务仍然从不开关卡。（[#168](https://github.com/foolzzz/looper/pull/168)、[#179](https://github.com/foolzzz/looper/pull/179)）
2. **Agent room 默认开启。** 从未设置 `agent_room` 的项目，每个任务都有 room 和 room 工具。问已结束步骤的席位时，由该席位最后一次会话的只读 consult 回答；没答上的部分交给 Planner。设为 `off` 则恢复以前的提示词和工具列表。（[#187](https://github.com/foolzzz/looper/pull/187)、[#188](https://github.com/foolzzz/looper/pull/188)）
3. **新项目默认用 worktree 任务工作目录。** 经 API、任务表单或 Manager 创建的项目得到 `task_workspaces: "worktree"`。已有项目和导入的项目保持未设置，任务就地运行。任务指定了项目目录以外的目录时，仍然使用 worktree。（[#190](https://github.com/foolzzz/looper/pull/190)）
4. **操作者笔记对所有项目默认开启，包括已有项目。** `operator_notes` 未设置即开启。笔记进入每一种运行时，包括 Codex、OMP 和 Grok。把项目设为 `off` 即停止注入。（[#190](https://github.com/foolzzz/looper/pull/190)）
5. **启用定时任务和立即运行需要下一条消息。** 经 Manager 时，两者都等用户在下一条消息里确认。创建该定时任务的回合既不能启用也不能运行。用户不确认，定时任务保持停用，不会启用，也不会开始运行。Dashboard 和 HTTP API 仍按调用本身执行。（[#178](https://github.com/foolzzz/looper/pull/178)）
6. **Planner 只读，由工具强制。** Claude Code 禁止写工具。Grok 的 Planner 没有 shell。运行时无法拒绝调用时，Looper 在回合之后记录 git 变化，不回滚。（[#183](https://github.com/foolzzz/looper/pull/183)）
7. **并发按一个任务计，不按项目。** 同时跑多少任务没有上限。角色层的 Worker 和 Reviewer 上限，以及内置的 16 和 8，作用于一个任务。项目级上限去掉。见“破坏性变更”。（[#173](https://github.com/foolzzz/looper/pull/173)）

System prompt 的默认仍是 `append`，`--jobs` 的默认仍是 1。两者都不改变正在运行的服务。步骤 worktree 在项目设为 `worktree` 之前保持 `shared`。

### 评测工具

- **先做针对性评测，发布候选上再跑完整层级。** `evals/README.md` 写明跑哪一层：改动用针对性的任务和对话，`--reps 2`（改了提示词或契约时用 Planner 或 Manager 层），发布候选上跑一次完整层级。建议 `--jobs 4`。（[#191](https://github.com/foolzzz/looper/pull/191)、[#192](https://github.com/foolzzz/looper/pull/192)）
- **`--jobs` 让用例一起跑。** `run` 和 `dialogs` 接受 `--jobs N`。默认 1，顺序与以前相同。行仍按任务和 rep 排序。花费上限计入已经在跑的用例的预算。（[#192](https://github.com/foolzzz/looper/pull/192)）
- **重复次数、错误和基线。** `--reps` 重复每个用例。超时或触及花费上限算错误，不算模型失败。每个对话 rep 有自己的数据库和服务。已提交的基线覆盖 README 要求的 haiku 和 opus 层，各三次。README 里的花费说明是实测值；本正文不重复私人花费合计。（[#167](https://github.com/foolzzz/looper/pull/167)、[#176](https://github.com/foolzzz/looper/pull/176)）

### 质量与测试

- 两个在 CI 负载下偶发失败的计时测试，不再依赖 0.01 秒的窗口，也不再只等 30 秒让 Worker 启动。它们所测的停止时限没有改。午夜前最后几分钟会失败的定时任务测试固定在中午。（[#171](https://github.com/foolzzz/looper/pull/171)、[#194](https://github.com/foolzzz/looper/pull/194)）
- 计划里的验证规则改为：本地跑针对性测试，CI 跑全量，合并前 CI 必须通过；模型能看见的文字变了就按评测 README 的层级跑一次真实评测。（[#191](https://github.com/foolzzz/looper/pull/191)）

### 破坏性变更

1. **并发按任务计算。** 不再按项目等空位。`GET /api/tasks?group=queued` 返回 400。`/api/overview` 去掉 `tasks.queued`、每个项目的任务上限和排队数，以及项目的 Worker 和 Reviewer 上限。`/api/status` 去掉 `tasks.pending`。任务的 planner 并发字段没有了，来源曾是 `project` 的 Worker 或 Reviewer 变为 `default`。`looper_concurrency` 去掉 `scope`、`project` 和 `project_limit`。`looper_task_control start` 去掉 `note`。下次服务启动时，留在 `pending` 的任务会启动，而不是被标成停止。升级时已有的任务失去项目上限，按每任务的默认值跑；迁移只把换算后的上限写到定时任务上。原先限制整个项目的角色层数值现在限制一个任务，因此可能有更多 agent 同时运行和花钱。（[#173](https://github.com/foolzzz/looper/pull/173)）
2. **用户关卡默认开启。** 从未设置 `user_gates` 的项目允许 Planner 开关卡，模型能看见的契约变长。定时任务不会。（[#179](https://github.com/foolzzz/looper/pull/179)）
3. **Agent room 默认开启。** 这样的项目会给任务 agent room 工具和提示词里的 room 一节。问已结束步骤的席位会发起一次只读 consult（默认 0.50 USD；超过上限或没有报价的回答会被丢掉）。（[#187](https://github.com/foolzzz/looper/pull/187)、[#188](https://github.com/foolzzz/looper/pull/188)）
4. **新项目在 git worktree 里工作，操作者笔记到处开启。** 已有项目在设置 `task_workspaces` 之前仍就地运行。笔记对已有项目也开启，在每一种运行时上。（[#190](https://github.com/foolzzz/looper/pull/190)）
5. **Manager 对启用和立即运行要求确认。** v2.7.0 允许 Manager 启用或停用定时任务，启用本身不必再确认一次。现在启用和立即运行要等下一条消息。新建和修改已存在；导入的定时任务是停用的。（[#178](https://github.com/foolzzz/looper/pull/178)）
6. **Planner 不能写任务树。** v2.7.0 里只有提示词要求它不要写。现在改为工具拒绝；运行时无法拒绝时，改为记录 git diff。步骤必须写 `review_roles`，不能再写 `review_role`。已存的单个评审角色迁移成一项的列表，旧列删除。（[#182](https://github.com/foolzzz/looper/pull/182)、[#183](https://github.com/foolzzz/looper/pull/183)）

**其他记录或权限上的变化。** 运行记录在每条退出路径上都会结束，因此原先忽略仍为 `running` 的行的花费或总览现在会把它算进去。旧步骤的 `started_at` 为空。已有 Profile 的 `system_prompt_mode` 为 `append`。定时任务的保存响应不再带旧的 `warnings` 字段。在 Profile 选用之前，Grok 和替换模式什么都不做。（[#177](https://github.com/foolzzz/looper/pull/177)、[#184](https://github.com/foolzzz/looper/pull/184)、[#185](https://github.com/foolzzz/looper/pull/185)、[#193](https://github.com/foolzzz/looper/pull/193)）

### 从 v2.7.0 升级

1. **用 `install.sh` 安装。** 和 v2.7.0 一样，它安装最新 release 的 wheel。
2. **保证首次启动能备份。** 表结构有变化，首次启动会先写一份 `pg_dump` 备份再迁移。请在 `PATH` 上保留主版本不低于服务器的 `pg_dump`（或设置 `LOOPER_PG_DUMP`、`LOOPER_BACKUP_CMD`）。`looper serve --skip-backup` 不备份直接迁移。
3. **启动一次。** 升级会加上关卡、room、模板、任务工作目录和花费相关的列；列为 null 的新默认值会生效（关卡、agent room、操作者笔记）；已有项目的任务工作目录仍就地；`system_prompt_mode` 设为 `append`；每个步骤的单个评审角色改写成一项的列表。
4. **决定关卡、room 和笔记。** 不让 Planner 提问，就把项目的 `user_gates` 设为 `off`。不让 agent 互发消息，就把 `agent_room` 设为 `off`。停止注入操作者笔记，就把 `operator_notes` 设为 `off`。
5. **新项目和并发。** 升级之后创建的项目在 worktree 里跑任务。如果以前靠项目上限压花费，请调低任务的 Worker 和 Reviewer 上限，并在需要时设置单任务花费上限。除非任务自己的上限或角色层另有规定，每个任务现在可以跑 16 个 Worker 和 8 个 Reviewer，任务之间不再互相等待。
6. **只有想用时才配 Grok。** 安装 `grok` CLI，在服务所在机器上登录，用运行时 `grok` 和 provider `grok-login` 建 Agent Profile 并选用。在此之前没有东西跑在 Grok 上。
7. **脚本。** 不要再传 `group=queued`。不要再从 `/api/overview` 读项目并发。用 `review_roles` 代替 `review_role`。把 Manager 新建的定时任务当成停用，直到它被启用；来自聊天的启用和立即运行会等下一条消息。
8. **本地记录里的一把密钥。** 有一把 CPA 密钥曾被写进一份本地会话记录。如果那份记录在你使用的机器上，请轮换这把密钥。Looper 不在本发布里保存该密钥，本正文也不重复它。
9. **检查。** 运行 `looper doctor`；使用服务时再运行 `looper service status`。

```bash
curl -fsSL https://raw.githubusercontent.com/foolzzz/looper/main/install.sh | bash
looper doctor
looper serve
  # 或者使用服务：
looper service restart && looper service status
```

**回退到 v2.7.0。** 停止 Looper（装了服务就运行 `looper service uninstall`），把数据库重建为空库，并恢复首次启动日志里给出的迁移前备份（`pg_restore --no-owner --dbname "$LOOPER_DATABASE_URL" FILE`）。然后安装 v2.7.0 的 wheel，例如 `uv tool install --force "looper @ https://github.com/foolzzz/looper/releases/download/v2.7.0/looper-2.7.0-py3-none-any.whl"`。`install.sh` 总是安装最新 release，不能用来回退。v2.7.0 不认识关卡、agent room、角色模板、任务 worktree 或 Grok Profile。

### 可选能力启用与使用

#### User gates

**启用：**所有未设置 `user_gates` 的项目默认开启（`null` 即开启）。新项目也是开启。在 Project → Settings → Execution 里开关，或用 `PUT /api/projects/PROJECT_ID` 加 `{"user_gates": "on"}`。可选的 `gate_reminder_hours` 为 0 到 168，空为 24，0 表示不提醒。在 dashboard 或网页聊天里发起的任务，要在 Settings → Channels 用 `PUT /api/gate-settings` 把 `user_gates.dashboard_target` 设成渠道白名单已允许的发送者，且该渠道已启用。定时任务发起的任务无论项目如何设置都不会开关卡。

**验证：**`GET /api/projects` 显示 `user_gates` 为开（或 null，即开）。等待中的关卡出现在 Needs you 分组、任务 Overview 和 Pipeline 节点上。`GET /api/tasks/TASK_ID` 列出 `gates`。在飞书或 Telegram 里发起的任务，关卡卡片出现在那个聊天里；卡片下的回复进入关卡讨论，不会变成 Manager 的回合。

**停用 / 回退：**`PUT /api/projects/PROJECT_ID` 加 `{"user_gates": "off"}`。之后的计划不能再加关卡，Planner 契约恢复为没有关卡时的版本。已经开着的关卡继续等到关闭、取消或任务结束。清掉 `dashboard_target` 后，dashboard 上发起的任务不再发到聊天；任务页仍然可用。

**权限边界：**开着的关卡只挡住依赖它的步骤。Planner 编写问题，以及之后的 agent 会读到的结束总结。能在任务页发消息的人，以及关卡所在聊天里的白名单发送者，都可以回答。飞书群里，该线程中下一条 @ 机器人的消息就是回答，不论白名单里的哪一位发送。Manager 的转达以该用户的身份写入关卡。别处的确认仍按聊天计。投递以机器人的身份发出。不新增密钥；聊天 id 是该任务的渠道里本来就有的。

**文档：**https://github.com/foolzzz/looper/blob/v2.8.0/docs/architecture/agent-system.md#user-gates

```bash
curl -s -X PUT http://127.0.0.1:8767/api/projects/PROJECT_ID -H 'Content-Type: application/json' \
  -d '{"user_gates": "on", "gate_reminder_hours": 24}'
curl -s http://127.0.0.1:8767/api/gate-settings
curl -s -X PUT http://127.0.0.1:8767/api/gate-settings -H 'Content-Type: application/json' \
  -d '{"dashboard_target": {"channel": "lark", "chat_id": "CHAT_ID"}}'
curl -s http://127.0.0.1:8767/api/tasks/TASK_ID | python3 -c 'import json,sys; print(json.load(sys.stdin).get("gates"))'
  # 关掉关卡：
curl -s -X PUT http://127.0.0.1:8767/api/projects/PROJECT_ID -H 'Content-Type: application/json' \
  -d '{"user_gates": "off"}'
```

#### Agent room

**启用：**默认开启（`agent_room` 为 null 即开启）。把项目的 `agent_room` 设为 `on` 或保持不设（Project → Settings → Execution，或 `PUT /api/projects/PROJECT_ID`）。可选上限：`room_post_per_minute`（1 到 60，空为 6）、`room_broadcasts_per_run`（0 到 50，空为 5）、`room_message_max_chars`（500 到 20,000，空为 4,000）、`room_messages_per_task`（20 到 5,000，空为 300）、`room_ping_pong_rounds`（2 到 50，空为 6）、`room_wait_max_seconds`（0 到 120，空为 60）。没有单独的安装步骤。room 开启时，问已结束步骤的席位会用该席位最后一次会话做一次只读 consult（[#188](https://github.com/foolzzz/looper/pull/188)）。单次上限默认 0.50 USD（`room_consult_budget_usd`），超时 300 秒（`room_consult_timeout_seconds`），每个任务 10 次（`room_consults_per_task`）。超过上限或没有报价的回答会被丢掉。

**验证：**`GET /api/projects` 显示 `agent_room` 为开或 null。任务跑过之后，`GET /api/tasks/TASK_ID/room` 列出席位和消息，`GET /api/tasks/TASK_ID` 带有 `room` 计数。任务页有 Room 标签。运行的第一回合会写出自己的席位。被拒绝的消息出现在任务活动里。

**停用 / 回退：**把 `agent_room` 设为 `off`。之后的运行回到以前的提示词，且没有 room 工具。已经存下的消息留在任务上，直到从头再来或删除任务。没有要卸载的东西。

**权限边界：**同一任务的 agent 可以互相下指示。工作席位不能游说 Reviewer，除非回答该 Reviewer 自己的问题。评审席位不能广播。Planner 能看到整个 room。令牌按次运行发放，运行结束即作废，不是 Manager 的令牌。本版本里用户和 Manager 不能发消息，但可以读。消息本身不是沙箱：agent 在工作树里仍有其角色的工具。速率上限即上面的项目设置。Consult 只读，且失败即关闭：超过上限或没有报价的回答会被丢掉，没答上的部分交给 Planner（[#188](https://github.com/foolzzz/looper/pull/188)）。OMP 的检出不是沙箱，Claude Code 的 fork 留在 Claude Code 自己的会话存储里；见“已知限制”。

**文档：**https://github.com/foolzzz/looper/blob/v2.8.0/docs/architecture/agent-system.md#a-tasks-agent-room

```bash
curl -s -X PUT http://127.0.0.1:8767/api/projects/PROJECT_ID -H 'Content-Type: application/json' \
  -d '{"agent_room": "on", "room_post_per_minute": 6, "room_messages_per_task": 300}'
curl -s http://127.0.0.1:8767/api/tasks/TASK_ID/room | python3 -m json.tool | head -40
  # 关掉 room：
curl -s -X PUT http://127.0.0.1:8767/api/projects/PROJECT_ID -H 'Content-Type: application/json' \
  -d '{"agent_room": "off"}'
```

#### Grok runtime

**启用：**在有 Profile 使用之前不生效。`grok` 在服务的 `PATH` 上时，`looper serve` 注册运行时 `rt-grok`。在服务所在机器上用 Grok 自己的登录完成登录，用 provider `prov-grok-login` 新建 Agent Profile（Settings → Agent Profiles，或 `POST /api/agent-profiles`），再为某个角色、项目或任务选用。没有选 Grok 的 Profile 不变。

**验证：**CLI 在 `PATH` 上时，Settings → Agent Runtimes 列出 Grok。有 Profile 使用时，`looper doctor` 包含 Grok 登录检查。`GET /api/status` 有 `grok_login` 检查，`GET /api/registry` 有该 provider 的登录状态。运行记录写明 Profile；运行时报告了花费时，记录里就是该花费。

**停用 / 回退：**在该层改选别的 Profile（或 null 以继承），再删除 Grok Profile（仍有地方选用时返回 409）。若某次运行把登录文件换成了副本，Looper 删掉副本、恢复链接，并停用该登录，直到你核对登录后选择 “Use the login again”（`DELETE /api/providers/prov-grok-login/login-problem`）。去掉 `grok` 可执行文件并重启后，检测不到该运行时。

**权限边界：**Grok agent 以你的用户身份运行，带 `--always-approve` 和 `--trust`，家目录由 Looper 拥有。登录留在你的 Grok 登录文件里；每个家目录只链接到它，Looper 不保存令牌。Worker 或 Reviewer 的 shell 会拿回你的家目录，因此能读到你的用户能读的内容。Grok 的 Planner 没有 shell。Grok 不会在单次花费上限处停下；某次运行报告花费之后，任务上限仍会阻止后续运行。花了 token 但花费为 0 表示未知，不是免费。本版本没有 Grok 的 API key provider。

**文档：**https://github.com/foolzzz/looper/blob/v2.8.0/docs/architecture/agent-system.md#runtimes-llm-providers-and-agent-profiles

```bash
grok --version
curl -s -X POST http://127.0.0.1:8767/api/agent-profiles -H 'Content-Type: application/json' \
  -d '{"name": "grok/login", "runtime_id": "rt-grok", "provider_id": "prov-grok-login", "model": "grok-4.7"}'
curl -s -X PUT http://127.0.0.1:8767/api/agent-settings/roles/worker -H 'Content-Type: application/json' \
  -d '{"profile_id": "PROFILE_ID"}'
looper doctor
  # 撤销：
curl -s -X PUT http://127.0.0.1:8767/api/agent-settings/roles/worker -H 'Content-Type: application/json' \
  -d '{"profile_id": null}'
curl -s -X DELETE http://127.0.0.1:8767/api/agent-profiles/PROFILE_ID
```

#### System prompt replace

**启用：**在 Profile 设置之前不生效。每个 Profile 的 `system_prompt_mode` 默认 `append`，包括从 v2.7.0 升级来的。在 Settings → Agent Profiles、`POST` 或 `PUT /api/agent-profiles`、配置导入，或 Manager 的 Profile 工具里把某个 Profile 设为 `replace`。Claude Code、Codex、Grok 和 OMP 接受替换。不能替换的运行时在保存时返回 400 并给出原因，编辑器会禁用该选项。

**验证：**`GET /api/registry` 和 `GET /api/agent-profiles` 显示 `system_prompt_mode`。运行记录保存 `system_prompt_mode`，为 `replace` 时运行页显示 “replaced default” 标记。追加模式保持以前的命令行和生成的家目录文件。

**停用 / 回退：**把 Profile 改回 `append`。下一次运行重新追加。已有的运行记录保留它们当时的模式。没有全局开关。

**权限边界：**替换会丢掉该运行时的默认 system prompt，包括它自带的指导，并把 Looper 的提示词当作全部指令。工具定义保留。Profile 的角色提示词、harness、项目说明和操作者笔记仍像追加模式一样生效。这可能让小模型的契约违约变多（haiku：成功 52/66，追加模式为 53/66；契约违约从 3.7 到 8.3；修复回合能收回）。它不会授予运行时本来没有的工具。只有能编辑该 Profile 的人，或通过 Profile 工具操作的 Manager，可以设置它。

**文档：**https://github.com/foolzzz/looper/blob/v2.8.0/docs/architecture/agent-system.md#runtimes-llm-providers-and-agent-profiles

```bash
curl -s -X PUT http://127.0.0.1:8767/api/agent-profiles/PROFILE_ID -H 'Content-Type: application/json' \
  -d '{"system_prompt_mode": "replace"}'
curl -s http://127.0.0.1:8767/api/registry | python3 -c 'import json,sys; [print(p["name"], p.get("system_prompt_mode")) for p in json.load(sys.stdin)["profiles"]]'
  # 改回追加：
curl -s -X PUT http://127.0.0.1:8767/api/agent-profiles/PROFILE_ID -H 'Content-Type: application/json' \
  -d '{"system_prompt_mode": "append"}'
```

#### Task workspaces

**启用：**新项目的 `task_workspaces` 为 `worktree`（API、任务表单和 Manager）。已有或导入的项目为 null，即就地运行，直到你设为 `worktree`（Project → Settings → Execution，或 `PUT /api/projects/PROJECT_ID`）。任务也可以自己指定模式；任务指定了项目目录以外的目录时，无论项目默认如何都会用 worktree。`operator_notes` 对每个项目默认开启，包括已有项目（`null` 即开启）。`workspace_links` 最多 20 条相对于项目目录的路径，空表示没有。

**验证：**`GET /api/projects` 显示 `task_workspaces` 和 `operator_notes`。`GET /api/workspaces/check` 和创建响应里的 `workspace` 字段说明任务将使用的仓库、分支和基点，并警告 `not_git`、`uncommitted`、`shared` 或 `large_checkout`。活动里写明分支 `looper/<任务 id>/task`。完成时任务页以及飞书或 Telegram 的结束通知会写出该分支。应用了笔记时，运行记录的 prompt layers 里有 `operator_notes`（哈希、文件、被省略的）。

**停用 / 回退：**把 `task_workspaces` 设为 `in_place`，之后没有另行要求的任务在检出里运行。把 `operator_notes` 设为 `off` 即停止注入笔记；已经开始的运行保持当时拿到的提示词。Looper 从不合入任务分支。不想要该分支时在 git 里删除它。停止的任务保留 worktree 以便重启；删除任务会去掉 worktree 并保留分支。该分支上的 git 历史就是任务的提交。

**权限边界：**Looper 在你的仓库里创建 worktree 和分支，任务完成时提交剩余改动（Looper 的身份，不跑钩子，不含链接），不推送、不切换你的检出、不合入。指定目录里未提交的改动不会复制进 worktree；检查会警告。Agent 在 worktree 里以你的用户身份运行，工具与以前相同。操作者笔记是该仓库的 Claude Code 自动记忆的只读片段，注入每一种运行时的提示词，内容就是那份记忆里有的东西。不在 git 里的目录就地运行，并带 `not_git` 警告，包括 worktree 只是默认值的情况。

**文档：**https://github.com/foolzzz/looper/blob/v2.8.0/docs/architecture/agent-system.md#task-workspaces

```bash
curl -s -X PUT http://127.0.0.1:8767/api/projects/PROJECT_ID -H 'Content-Type: application/json' \
  -d '{"task_workspaces": "worktree", "operator_notes": "on"}'
curl -s 'http://127.0.0.1:8767/api/workspaces/check?project_id=PROJECT_ID'
  # 改回在检出里运行，并停止注入笔记：
curl -s -X PUT http://127.0.0.1:8767/api/projects/PROJECT_ID -H 'Content-Type: application/json' \
  -d '{"task_workspaces": "in_place", "operator_notes": "off"}'
```

#### Planner-defined roles

**启用：**在项目把 `planner_roles` 设为 `on` 之前仍然关闭（Project → Settings → Execution，或 `PUT /api/projects/PROJECT_ID`）。开关关闭时也可以写模板；Planner 只在开关打开时复制它们。`PUT /api/projects/PROJECT_ID/role-templates/KEY`，带 `key`、`kind`、`description`、`role_prompt`，以及可选的 `harness`、`profile_id` 和 `items`。可选的 `role_text_max_chars` 为 500 到 20,000，空为 8,000。角色的 Profile 必须在项目的允许列表里。目录条目只有在安装指定了 `task_role` 之后才会为角色加载。

**验证：**`GET /api/projects/PROJECT_ID/role-templates` 列出模板。任务定义了角色之后，`GET /api/tasks/TASK_ID` 列出带版本、`edited_by_user`、`template_key` 和统计的 `roles`，步骤上有 `review_roles`。任务页的 Roles 区块有 Edit。`GET /api/projects/PROJECT_ID/role-stats` 跨任务汇总角色。以角色身份的运行在 Runs 页和 Agent Timeline 上标出角色。

**停用 / 回退：**把 `planner_roles` 设为 `off`。之后不能再定义或指定角色；已经指定了角色的步骤继续按该角色运行。用 `DELETE /api/projects/PROJECT_ID/role-templates/KEY` 删除模板；已经复制出的角色还在。从头再来会删除任务的角色。用户的修改一直是当前版本，直到用户再次修改；Planner 不能覆盖它。

**权限边界：**对于用户还没改过的角色，Planner 仍编写角色提示词，因此 Worker 会遵循模型写的文字，拥有该角色的工具且无需权限确认。安全边界仍位于 Planner 或用户所写的一切之后、契约之前，且只能在共用默认上修改。评审角色只在内置 Reviewer 通过之后运行。仅供参考的评审角色不阻止验收。角色条目仅限于你为 `task_role` 安装的目录条目。配置文件里的模板带有提示词；导入不会打开 `planner_roles`。

**文档：**https://github.com/foolzzz/looper/blob/v2.8.0/docs/architecture/agent-system.md#roles-a-tasks-planner-defines

```bash
curl -s -X PUT http://127.0.0.1:8767/api/projects/PROJECT_ID -H 'Content-Type: application/json' \
  -d '{"planner_roles": "on"}'
curl -s -X PUT http://127.0.0.1:8767/api/projects/PROJECT_ID/role-templates/backend_rd -H 'Content-Type: application/json' \
  -d '{"kind": "work", "description": "Back end", "role_prompt": "You work on the server."}'
curl -s http://127.0.0.1:8767/api/projects/PROJECT_ID/role-templates
  # 关掉角色定义（模板仍保留）：
curl -s -X PUT http://127.0.0.1:8767/api/projects/PROJECT_ID -H 'Content-Type: application/json' \
  -d '{"planner_roles": "off"}'
```

#### Scheduled tasks

**启用：**Dashboard 上的行为与以前相同：新建的定时任务是停用的，启用即表示批准它无人值守发起的任务。本版本增加 Manager 路径。`looper_schedules` 的 `create`（总是停用）、`update` 和 `run`。启用（`action` 为 `enable`）和立即运行（`action` 为 `run`）要等用户在下一条消息里经 `looper_confirm` 确认之后才执行。创建那一回合不能启用或运行。定时任务包含在配置导出和导入里，导入的定时任务是停用的。HTTP API 仍是 v2.7.0 的创建和启用；直接调用它不会插入一次聊天确认。

**验证：**Manager 创建之后，回复里有配置块和接下来的触发时间，`GET /api/schedules/SCHEDULE_ID` 显示 `enabled` 为 false。你确认启用之后，`enabled` 为 true 且设置了 `next_fire_at`。没有确认的立即运行不会建任务。`GET /api/projects/PROJECT_ID/schedules` 列出它们。导出配置，确认定时任务在文件里，且重新导入后是停用的。

**停用 / 回退：**Manager 的停用不再询问。`PUT /api/schedules/SCHEDULE_ID` 加 `{"enabled": false}` 停止后续触发，不停止已经在跑的任务。删除在聊天里仍要询问，API 上是 `DELETE /api/schedules/SCHEDULE_ID`；定时任务已经发起的任务保留。若要回到不能创建定时任务的 Manager，使用 v2.7.0 的构建；行还在，先停用即可。

**权限边界：**确认后的启用批准之后的每一次触发：无人值守的 Planner、Worker 和 Reviewer，带各自的工具且无需权限确认，受定时任务的重叠策略、预算、超时和任务并发限制。立即运行马上建一个任务，花费计入同样的上限。确认的人是该聊天里发送下一条消息的人，且在确认时限内。从已在白名单里的 Telegram 或飞书聊天创建、又没有别的通知对象时，通知发给该发送者。导出文件包含需求和命令，不包含渠道密钥。若设置了前置检查命令，它仍以你的用户身份在每次触发时运行。

**文档：**https://github.com/foolzzz/looper/blob/v2.8.0/docs/architecture/agent-system.md#schedules-tasks-on-a-time-rule

```bash
curl -s -X POST http://127.0.0.1:8767/api/projects/PROJECT_ID/schedules -H 'Content-Type: application/json' \
  -d '{"name": "weekday-deps", "cron": "0 9 * * 1-5", "timezone": "America/Los_Angeles",

curl -s http://127.0.0.1:8767/api/schedules/SCHEDULE_ID | python3 -c 'import json,sys; s=json.load(sys.stdin)["schedule"]; print(s["enabled"], s.get("next_fire_at"))'
  # Dashboard 上的启用是直接的。经 Manager 时，启用和立即运行要等下一条消息。
curl -s -X PUT http://127.0.0.1:8767/api/schedules/SCHEDULE_ID -H 'Content-Type: application/json' \
```

#### Step workspaces

**启用：**按项目设置，默认 `shared`，null 也是。把 `step_workspaces` 设为 `worktree`（Project → Settings → Execution，或 `PUT /api/projects/PROJECT_ID`）。可选的 `workspace_links`：最多 20 条相对于任务目录的路径（不能有 `.` 或 `..`，不能在 `.git` 里，不能重复，不能一条在另一条里面）。仅当任务目录是在某个分支上、至少有一个提交的 git 检出，git 不低于 2.40，没有进行中的 merge、rebase、cherry-pick、revert 或 bisect，`HEAD` 上的文件不超过 1 GiB，且该步骤与本任务的其他步骤同时运行时才生效。关卡步骤从不会得到 worktree。超过 1 GiB，或检出不满足 git 条件时，该轮一步一步跑，活动里写明原因。

**验证：**`GET /api/projects` 显示 `step_workspaces` 和 `workspace_links`。有并行步骤的任务会记下起始提交、每步的 worktree 和分支，以及每次合并。`GET /api/tasks/TASK_ID` 的 `step_workspaces` 包含 `start`、每个 workspace 和 `undo`。任务页列出它们，并在任务不在运行时提供 Discard。git 缺失或低于 2.40 时 `looper doctor` 会警告，并检查默认目录设为 `worktree` 的项目。

**停用 / 回退：**把 `step_workspaces` 改回 `shared`。之后派出的轮次重新共用任务目录。任务不在运行时，用 `POST /api/tasks/TASK_ID/workspaces/WORKSPACE_ID/discard` 丢掉一个残留。`git reset` 到活动里给出的起始提交会撤销任务的提交并保留改动；`git revert -m 1` 撤销一步的合并。已完成任务的 worktree 和分支会被删除；失败、停止或取消的任务保留未合回的，直到从头再来、删除或 Discard。

**权限边界：**Looper 在任务分支上提交：并行一轮开始前的检查点、剩余改动，以及每个验收步骤一个合并提交。这些提交不签名、不跑钩子。Looper 不推送。链接与任务目录共享被忽略的路径（例如依赖目录），且不会作为链接被提交。Worker 用自己的文件替换链接时，那些文件会成为它的提交。合并冲突时任务目录保持不动并交给 Planner。不增加模型花费。1 GiB 上限是为了避免把很大的检出按步骤各复制一份。

**文档：**https://github.com/foolzzz/looper/blob/v2.8.0/docs/architecture/agent-system.md#step-workspaces

```bash
curl -s -X PUT http://127.0.0.1:8767/api/projects/PROJECT_ID -H 'Content-Type: application/json' \
  -d '{"step_workspaces": "worktree", "workspace_links": ["node_modules"]}'
curl -s http://127.0.0.1:8767/api/tasks/TASK_ID | python3 -c 'import json,sys; print(json.load(sys.stdin).get("step_workspaces"))'
  # 关掉步骤 worktree：
curl -s -X PUT http://127.0.0.1:8767/api/projects/PROJECT_ID -H 'Content-Type: application/json' \
  -d '{"step_workspaces": "shared"}'
```

### 已知限制

- **替换模式丢掉每种运行时的默认指导。** 它按 Profile 显式打开。在 haiku 上，替换模式为 52/66，追加模式为 53/66，契约违约从 3.7 升到 8.3。修复回合能收回。运行时的工具定义还在；它自己的指令不在。
- **有一把 CPA 密钥曾被写进一份本地会话记录。** 如果那份记录在你使用的机器上，请轮换这把密钥。本正文不含密钥，也不含记录的路径。
- **Telegram 上重试的帖子可能重复。** 飞书用幂等键去重关卡帖子。Telegram 没有，因此应答丢失后重试的帖子可能到两次。
- **Grok 的 Planner 没有 shell。** 它的只读工具是读、搜索和列目录。它不能跑 git 或其他命令。Claude Code 的 Planner 仍可以跑“只读 Planner”一节里列出的只读 git 命令。Grok 也没有单次花费上限，只在运行结束时报花费。
- **Consult 对来源的钉住没有和席位重启串行化。** 该席位的重启不会被 consult 所读那次运行上的钉住挡住。（[#188](https://github.com/foolzzz/looper/pull/188)）
- **Claude Code 和 OMP 的只读工具名单没有在真实运行里核实。** Consult 要求 Claude Code 只用 `Read`、`Glob` 和 `Grep`，OMP 只用 `read`、`glob` 和 `grep`。这条限制没有对照真实 CLI 检查过。（[#188](https://github.com/foolzzz/looper/pull/188)）
- **OMP 的 consult 检出不是沙箱。** OMP 以你的用户身份在任务分支的一份分离检出里运行，之后删除该检出。检出之外的写入既不会被阻止，也不会被发现。（[#188](https://github.com/foolzzz/looper/pull/188)）
- **Codex 在真实 resume 上的指令优先级没有核实。** Codex 的 consult 只复制留下的那份会话。那份会话被真实续接时哪条指令生效，没有检查过。（[#188](https://github.com/foolzzz/looper/pull/188)）
- **很快退出的 consult 父进程可能留下脱离的子进程。** 启动 consult 的进程先退出时，它已经脱离的子进程可能继续跑。（[#188](https://github.com/foolzzz/looper/pull/188)）
- **超时的 worktree add 可能留下一份不完整的检出。** Consult 的检出在 worktree add 超时后，可能把那份不完整的目录留在磁盘上。（[#188](https://github.com/foolzzz/looper/pull/188)）
- **Claude Code 的 consult fork 留在 Claude 的会话存储里。** Claude Code 像保存每一次会话那样保存这份 fork，Looper 不删除 Claude Code 自己目录里的条目。（[#188](https://github.com/foolzzz/looper/pull/188)）
- 超过 1 GiB 的检出不会按步骤建 worktree，该轮一步一步跑。不在 git 里的目录不会得到任务 worktree，就地运行。
- 除了 agent 自己的工具路由，HTTP API 仍没有认证。请保持默认的 `127.0.0.1` 绑定。
- Grok 登录刷新后如何写回尚未核实。若某次运行用副本替换了登录链接，Looper 会收回该登录，直到你再次确认。

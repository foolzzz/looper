# Looper v2.14.56

This is the patch release v2.14.56, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.55: the Manager and the client API now refuse to delete a command schedule that has a running run before they ask the user to confirm ([#1032](https://github.com/foolzzz/looper/pull/1032)).

## Release Decision

**Who should upgrade:** Anyone who deletes command schedules through the Manager (`looper_schedules`) or the client-token API (`/api/v1/schedule_admin/delete`).

**What this release solves:** The service refuses with 409 to delete a command schedule while one of its runs is running, because the runner outlives the server. The Manager and the client API still asked the user to confirm first, and the Manager's text said the running task "goes on and ends normally"; after the user confirmed, the call conflicted and nothing was deleted. [#1032](https://github.com/foolzzz/looper/pull/1032) makes both entry points refuse up front with the service's message (`conflict`: disable the schedule and wait for the run to end). For a command schedule with no running run, the confirmation now says what deleting does to a command schedule: a queued run will not execute, and it has no tasks.

**Breaking changes:** No. No API shape or migration changes; a delete that the service would have refused now fails earlier with the same message.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#1032](https://github.com/foolzzz/looper/pull/1032); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.56
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.55 upgrades directly. This release adds no migration.

## Behavior changes

- **Early refusal ([#1032](https://github.com/foolzzz/looper/pull/1032)).** Deleting a command schedule that has a running run through the Manager's `looper_schedules` `delete` or `POST /api/v1/schedule_admin/delete` (client token) answers `conflict` (HTTP 409) before any confirmation is created, with the message "cannot delete a command schedule while a run is running; disable the schedule and wait for the run to end". The Manager's message names the schedule and project. The service's own check in `schedules.delete_schedule` stays the authority for a run that starts after the question; both now share one predicate (`blocks_delete`) and one message.
- **Command schedule confirmation.** With no running run, the Manager's confirmation no longer says "它建出的任务都保留" (its tasks stay) for a command schedule, and a queued run is reported as "排队中的运行不会再执行" (a queued run will not execute). The client impact text reads "Delete <schedule>, its runs and notifications." plus " The queued run will not execute." when a run is queued, plus " It has no tasks.". The result note for a deleted command schedule is "its run history was deleted with it".
- **Unchanged.** The wording and behavior of agent schedule deletion are unchanged. The dashboard is unchanged: after its inline confirm it still shows the server's 409 message. The schedule is not disabled automatically and the delete does not wait for the run.
- **Model-visible changes:** Yes. The `looper_schedules` tool description now says that an agent schedule's tasks stay, that deleting a command schedule is refused only while its command is running (disable it and wait for the run to end), and that otherwise the delete removes its runs and messages, a queued run will not execute, and a command schedule has no tasks. The refusal is a new `conflict` result the model sees for that case, and the Manager's delete confirmation text differs for command schedules as described above. No tool schema changes.
- **Test and docs changes.** `docs/architecture/agent-system.md` describes the deletion rule and the tool row; one readiness test in `tests/test_api_v1_v1_transport_status.py` now guards only its own `time.sleep` calls.

## 中文摘要

本版本是 patch release v2.14.56（热修线，每个合并的改动立即发布）。自 v2.14.55 以来只合并了一项改动：Manager 和客户端 API 在用户确认之前，就会拒绝删除有运行中任务的命令定时任务（[#1032](https://github.com/foolzzz/looper/pull/1032)）。

### 升级决策

**谁需要升级：**通过 Manager（`looper_schedules`）或客户端令牌 API（`/api/v1/schedule_admin/delete`）删除命令定时任务的用户。

**解决了什么：**命令定时任务有运行中的 run 时，服务会以 409 拒绝删除（runner 的寿命长于服务器）。但 Manager 和客户端 API 仍会先请用户确认，Manager 的文字还说运行中的任务会“照常结束”；用户确认后调用冲突，什么也没删。[#1032](https://github.com/foolzzz/looper/pull/1032) 让两个入口提前拒绝，并使用服务的提示（`conflict`：先停用定时任务，等运行结束）。没有运行中的 run 时，确认文字现在说明删除命令定时任务的影响：排队中的运行不会再执行，且它没有任务。

**是否有破坏性变更：**否。API 形态和迁移不变；服务本来会拒绝的删除现在更早失败，提示相同。

**如何验证：**运行 `looper --version` 核对版本为 2.14.56。

**贡献者：**维护者 @foolzzz 提交 [#1032](https://github.com/foolzzz/looper/pull/1032)；本版本无社区贡献。

```bash
looper --version   # looper 2.14.56
```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.55 上的安装可直接升级。本版本没有新迁移。

### 行为变化与入口

- **提前拒绝（[#1032](https://github.com/foolzzz/looper/pull/1032)）。**通过 Manager 的 `looper_schedules` `delete` 或 `POST /api/v1/schedule_admin/delete`（客户端令牌）删除有运行中 run 的命令定时任务时，在创建任何确认之前就返回 `conflict`（HTTP 409），提示为“cannot delete a command schedule while a run is running; disable the schedule and wait for the run to end”。Manager 的提示会带上定时任务和项目名。服务自身的检查（`schedules.delete_schedule`）仍是提问之后才开始的运行的最终依据；两处现共用同一个判断（`blocks_delete`）和同一条提示。
- **命令定时任务的确认文字。**没有运行中 run 时，Manager 的确认不再对命令定时任务说“它建出的任务都保留”，排队中的运行显示为“排队中的运行不会再执行”。客户端的影响说明为“Delete <schedule>, its runs and notifications.”，有排队 run 时再加“ The queued run will not execute.”，最后加“ It has no tasks.”。删除命令定时任务的结果备注为“its run history was deleted with it”。
- **不变。**agent 定时任务删除的文字和行为不变。仪表盘不变：内联确认后仍显示服务器的 409 提示。不会自动停用定时任务，删除也不会等待运行结束。
- **面向模型的变化：**有。`looper_schedules` 的工具描述现在说明：agent 定时任务的任务保留；命令定时任务仅在命令运行时拒绝删除（先停用并等运行结束），否则删除会移除其 run 和消息，排队中的运行不会执行，且命令定时任务没有任务。模型会看到这种情况下新的 `conflict` 结果，Manager 对命令定时任务的删除确认文字也如上所述不同。工具 schema 不变。
- **测试与文档改动。**`docs/architecture/agent-system.md` 描述了删除规则和工具行；`tests/test_api_v1_v1_transport_status.py` 中一个就绪测试现在只拦截自己的 `time.sleep` 调用。

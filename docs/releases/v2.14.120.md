# Looper v2.14.120

This is the patch release v2.14.120, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.119: process record follow-ups ([#1195](https://github.com/foolzzz/looper/pull/1195)).

## Release Decision

**Who should upgrade:** Operators who run workflows with `phase_notices` and read the delivery result or the process record, and Telegram, Lark or dashboard chat users who follow those tasks. Installations and tasks without a workflow see no change in behavior.

**What this release solves:** [#1195](https://github.com/foolzzz/looper/pull/1195). The delivery result of a completed or failed workflow task now ends with a short code-generated process summary instead of a bare pointer; the reported model of a run is the model the runtime reported; the record's text budget is split per section so review, verification and escalation sections are no longer crowded out; and a dashboard chat task with phase notices no longer also gets the generic plan line.

**Breaking changes:** No. There is no database change, and tasks without a workflow are unchanged.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.14.120
```

**Contributors:** Maintainer @foolzzz authored [#1195](https://github.com/foolzzz/looper/pull/1195); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.119 upgrades directly. This release has no database change: `tasks.process_record` already exists, and its new `delivery_summary` and `Runs` entries are stored inside the existing JSONB value; records stored earlier stay readable.

## Behavior changes

- **Delivery summary.** Only for a workflow task. The result text of a completed or failed task now ends with a code-generated `## Process record` summary of at most 1200 characters: one line each for the actual roles, runtimes and models with fallbacks, the latest review rounds and outcomes, the latest verification outcomes, and escalations, plus a pointer to the task page or `looper_tasks` get. Before, the result ended with the line "Process record: see the task page". The summary is also stored as `process_record.delivery_summary`, computed before detail truncation, so a long verification explanation cannot hide its final outcome.
- **Reported model.** The reported model of a run follows the Runs API rules: an explicit `model_reported` wins (including null), Cursor otherwise uses `model_display`, and the Codex, Grok, Pi, OMP and DSH runtimes, which give no report evidence, no longer show the requested model as reported. The requested model falls back to the Profile's model when the run recorded no model choice.
- **Per-section budgets.** The stored record (60000 JSON characters) and the `looper_tasks` get text view (6000 characters) reserve a separate budget for each section (`Roles`, `Reviews`, `Verification`, `Escalations` and the new `Runs`) and omit whole entries only. The text view always keeps the remote-environment safety line and the omitted-entry count, including omissions made when the record was stored. Distinct actual role, runtime and model combinations lead `Roles`; repeated ordinary runs with the same role, Profile, runtime and models share one counted entry in `Runs` (for example, `12 worker runs on <model>`), and fallback runs stay separate.
- **Dashboard.** The task page shows the new `Runs` section when it has entries; records stored earlier without `Runs` still display.
- **Chat plan line.** For a task with `phase_notices` that was started from dashboard chat, the generic "decomposed into N steps" reply is skipped, because the plan-created phase notice already carries the roles and breakdown; Telegram and Lark already behaved this way.
- **Unchanged:** tasks without a workflow, the review panel and verification rules, the database schema and the channel commands.
- **Model-visible changes:** Yes, small. For workflow tasks the result text that the Planner publishes and the Manager relays now carries the delivery summary, and the `looper_tasks` get view of the process record is budgeted per section and carries the `Runs` section, so the Manager model sees them when it reads a task. The Planner's, Worker's and Reviewer's prompts and contracts are unchanged. Tasks without a workflow see none of this.

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.119 上的安装可直接升级。本版本无数据库变更：`tasks.process_record` 已存在，新增的 `delivery_summary` 与 `Runs` 存放在原有 JSONB 值内；此前存储的记录仍可读取。

### 行为变化与入口

- **交付摘要。**仅对工作流任务生效。已完成或失败任务的结果文本现在以代码生成、最多 1200 字符的 `## Process record` 摘要结尾：实际角色、运行时与模型（含回落）、最近的评审轮次与结论、最近的验证结论、升级各一行，并指向任务页或 `looper_tasks` get。此前结果以“Process record: see the task page”一行结尾。摘要同时存为 `process_record.delivery_summary`，在明细截断之前计算，因此冗长的验证说明不会掩盖其最终结论。
- **报告模型。**运行的报告模型遵循 Runs API 规则：显式的 `model_reported` 优先（包括 null）；Cursor 在没有它时用 `model_display`；Codex、Grok、Pi、OMP、DSH 这些不提供报告证据的运行时，不再把请求的模型显示为已报告。运行未记录模型选择时，请求模型回退为 Profile 的模型。
- **按部分的预算。**存储的记录（60000 JSON 字符）和 `looper_tasks` get 的文本视图（6000 字符）为各部分（`Roles`、`Reviews`、`Verification`、`Escalations` 和新增的 `Runs`）各自预留预算，只整条省略。文本视图始终保留远程环境安全说明和省略条数，包括存储时已省略的条目。实际使用的角色、运行时和模型组合排在 `Roles` 前面；角色、Profile、运行时和模型相同的普通重复运行合并为 `Runs` 中一条带计数的记录（例如 `12 worker runs on <model>`），回落运行保持单独。
- **仪表盘。**任务页在 `Runs` 有内容时显示该部分；此前存储、没有 `Runs` 的记录仍可显示。
- **聊天计划行。**对从仪表盘聊天发起且带 `phase_notices` 的任务，不再回复通用的“已分解为 N 个步骤”，因为计划创建的阶段通知已含角色和步骤分解；Telegram 与 Lark 此前已是如此。
- **不变：**没有工作流的任务、评审小组与验证规则、数据库结构和渠道命令。
- **面向模型的变化：**有，较小。对工作流任务，Planner 发布、Manager 转述的结果文本现在带有交付摘要，`looper_tasks` get 的过程记录视图按部分预算并包含 `Runs` 部分，Manager 模型读取任务时会看到。Planner、Worker 和 Reviewer 的提示词与契约不变。没有工作流的任务不受影响。

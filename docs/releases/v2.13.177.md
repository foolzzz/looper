# Looper v2.13.177

## Release Decision

**Who should upgrade:** Operators who change a Manager's installed skills while its session is running, who delete Managers, or who read Manager installations in the catalog. It is a hotfix that ships the change merged since v2.13.176.

**What this release solves:** [#773](https://github.com/foolzzz/looper/pull/773) tells the Manager when a saved capability change is waiting for `/new`, counts Manager-only installations in the catalog's usage and delete confirmation, and refuses to delete a Manager that has active or admitted work, so an in-flight tool is not cancelled and then replayed.

**Breaking changes:** No. No command, configuration format or schema changed. Deleting a Manager that is active now returns a 409 where it used to proceed; the catalog item payload gains a field.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#773](https://github.com/foolzzz/looper/pull/773); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.177
```

## Behavior changes

- **Pending capability notice ([#773](https://github.com/foolzzz/looper/pull/773)):** `_run_prepared` in `looper/agents/tiers/manager.py` keeps the running launch when the library changed but `try_stop_if_idle` could not close the resident process, and then adds a notice block to that turn. A resume retry removes the block first and recomputes it. `ResidentClaude` in `looper/agents/claude_cli.py` exposes `idle`, which `try_stop_if_idle` now uses.
- **Deletion refused while active ([#773](https://github.com/foolzzz/looper/pull/773)):** `ManagerFleet.delete_manager` in `looper/agents/managers.py` returns `busy` when the agent's new `deletion_blocked` is true, when its ops have an execution admitted, or when the bus has pending messages for it. `delete_manager` in `looper/agents/managers_api.py` turns that into a 409 asking to retry after the work finishes. `deletion_blocked` covers preparation, queued messages, resets and a runtime that is not provably idle. The new `idle` property exists on `ApiSession`, `PerTurnSession` and `AcpGrok`; `AcpGrok` reports idle only in its legacy fallback, because ACP cannot acknowledge that its background work finished.
- **Tool admission ([#773](https://github.com/foolzzz/looper/pull/773)):** `ManagerOps._run_tool` in `looper/agents/ops/service.py` runs a tool, including a confirmed one, only after taking the fleet's cleanup guard, checking that the Manager is running and that the turn is still answering, and counting the execution. A retiring Manager returns `UNAVAILABLE` with "this operation did not run".
- **Catalog readback ([#773](https://github.com/foolzzz/looper/pull/773)):** `item_view` in `looper/agents/catalog.py` takes `manager_install_count`; the catalog, import, update and project views fill it from `manager_installs.item_use_counts()`. The v1 schema (`looper/agents/v1_domains/catalog.py`) lists the field. In the dashboard, the catalog card shows `Managers: N`, counts such items as installed, and its delete confirmation names the Manager installations.
- **Model-visible changes:** when the notice applies, the turn's prompt gains the line `能力变更待应用：已保存的 skills 将在 /new 后生效；当前会话继续使用原有能力。` No tool description, tool schema or system prompt text changed. A tool call that is refused during retirement returns an error result to the model.

## Upgrade and rollback

Re-run `install.sh` once v2.13.177 is published. There is no schema change, so rolling back to v2.13.176 needs nothing else.

## 中文摘要

### 升级决策

**谁需要升级：**在 Manager 会话运行时修改其已安装 skills、删除 Manager，或在目录中查看 Manager 安装情况的运维人员。本版本是随合并即发布的 hotfix。

**解决了什么：**[#773](https://github.com/foolzzz/looper/pull/773) 在已保存的能力变更等待 `/new` 时告知 Manager；目录的使用情况与删除确认计入仅 Manager 安装的条目；并拒绝删除有活动或已受理工作的 Manager，避免进行中的工具被取消后又重放。

**是否有破坏性变更：**无。命令、配置格式和 schema 均未改变。删除处于活动状态的 Manager 现在返回 409，此前会继续执行；目录条目的返回多一个字段。

**如何验证：**运行 `looper --version` 核对版本为 2.13.177。

**贡献者：**维护者 @foolzzz 提交 [#773](https://github.com/foolzzz/looper/pull/773)；本次 patch release 无社区贡献。

```bash
looper --version   # looper 2.13.177
```

### 行为变化与入口

- **能力变更提示（#773）：**库已变化但 `try_stop_if_idle` 无法关闭常驻进程时，`tiers/manager.py` 的 `_run_prepared` 沿用正在运行的启动配置，并在该回合加入提示块；resume 重试会先移除再重新计算。`ResidentClaude` 新增 `idle`，`try_stop_if_idle` 改用它。
- **活动时拒绝删除（#773）：**`ManagerFleet.delete_manager` 在 agent 的 `deletion_blocked` 为真、ops 有已受理的执行或总线上有该 Manager 的待处理消息时返回 `busy`；`managers_api.py` 将其转为 409，提示工作结束后重试。`deletion_blocked` 覆盖准备阶段、排队消息、重置，以及无法证明空闲的运行时。`ApiSession`、`PerTurnSession`、`AcpGrok` 新增 `idle`；ACP 无法确认后台工作已结束，因此 `AcpGrok` 仅在旧版回退模式下报告空闲。
- **工具受理（#773）：**`ops/service.py` 的 `ManagerOps._run_tool`（含已确认的工具）先获取 fleet 的清理锁，检查 Manager 在运行且回合仍在应答，并计入执行数后才运行。正在退役的 Manager 返回 `UNAVAILABLE`，提示该操作未运行。
- **目录回读（#773）：**`catalog.py` 的 `item_view` 新增 `manager_install_count`，目录、导入、更新和项目视图用 `manager_installs.item_use_counts()` 填充；v1 schema 列出该字段。仪表盘目录卡片显示 `Managers: N`，将此类条目计为已安装，删除确认会提到 Manager 安装。
- **面向模型的变化：**提示适用时，该回合 prompt 新增一行 `能力变更待应用：已保存的 skills 将在 /new 后生效；当前会话继续使用原有能力。` 没有工具描述、工具 schema 或系统 prompt 文本改动。退役期间被拒绝的工具调用会向模型返回错误结果。

### 升级与回退

v2.13.177 发布后重新运行 `install.sh`。无 schema 变更，回退到 v2.13.176 无需其他操作。

本版本未新增可选能力启用入口。

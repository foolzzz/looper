# Looper v2.14.153

This is the patch release v2.14.153, a hotfix line in which each merged change ships at once. It documents one change: [#1273](https://github.com/foolzzz/looper/pull/1273) (a control-plane upgrade can wait for non-keepable runs before it drains, and a failed upgrade reports its blockers).

## Release Decision

**Who should upgrade:** Operators who run `looper service upgrade` with `--no-force` on a host that has long non-keepable runs in flight. Everyone else gets no change in normal use.

**What this release solves:** [#1273](https://github.com/foolzzz/looper/pull/1273) adds `--preflight-wait SECONDS`, so a `--no-force` control-plane upgrade waits, with the service still serving, for non-keepable runs to finish before it pauses admission. When the wait ends or the drain deadline passes, the error and the report name what blocks the upgrade. Drain-status polls and the status probe after a failure no longer time out early and report a false "not serving".

**Breaking changes:** No. There is no migration and no API removal. The new option defaults to 0 (disabled). The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.14.153
```

**Contributors:** Maintainer @foolzzz authored [#1273](https://github.com/foolzzz/looper/pull/1273); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.152 upgrades directly. There is no schema change.

## Behavior changes

- **Preflight wait** ([#1273](https://github.com/foolzzz/looper/pull/1273), `looper/cli.py`, `looper/agents/service.py`). `looper service upgrade --preflight-wait SECONDS` (default 0, disabled; must be a non-negative finite number) applies only to a control-plane upgrade with `--no-force`. Before draining, the upgrade reads the drain status every 15 s while the service keeps serving, and starts the drain as soon as no non-keepable run is left. If the service is no longer serving, it stops with "the service is already draining; deployment stopped". If non-keepable runs remain when the wait ends, it refuses with the count and a blocker summary, nothing having been drained, and the report has `blockers`. The elapsed wait is the new report field `preflight_wait_seconds` (0.0 when unused).
- **Blockers in cancellations** (`looper/agents/service.py`). When the drain deadline passes under `--no-force`, the error and `report["blockers"]` list the non-keepable runs with `age_seconds` (null if the start time cannot be read), the Manager and Planner turns, and the counts of gates, waits, consults and starting runs; a non-control-plane drain also lists keepable runs. While draining, a summary line `drain waiting (Ns): ...` goes to stderr every 60 s.
- **Longer reads, retried** (`looper/agents/service.py`). Drain-status polls (including the lease renewals) and the status probe after a failure use the upgrade read timeout (15 s) instead of 3 s. A drain-status read that times out is retried twice; other errors are raised at once. The caller still checks the phase, in case the controller lease expired. The probe change avoids reporting a busy but serving service as not serving.
- **Runtime in the drain status** (`looper/agents/tiers/worker.py`, `looper/agents/v1_domains/drain.py`). Each run in the drain status's `waiting.runs` has nullable `runtime_id` and `runtime_type`, set when the run is launched or adopted; both are optional in the schema, so older rows still validate.
- **Unchanged:** no frontend change; the dashboard, Telegram and Lark still use the shared admission barrier. The PR also corrects timing assumptions in regression tests (tests only).
- **Documentation:** the PR description says it documents the option and report fields, but its diff has no documentation file; the option's help text in `looper service upgrade --help` is the only description.
- **Model-visible changes:** None. The change touches the service CLI, its report and the drain-status payload only; no prompt, tool, tool result or Manager scope text changed.

### 升级决策

**谁需要升级：**在有长时间不可保留（non-keepable）运行的主机上使用 `looper service upgrade --no-force` 的运维者。其他人在正常使用中没有变化。

**解决了什么：**[#1273](https://github.com/foolzzz/looper/pull/1273) 新增 `--preflight-wait SECONDS`，使 `--no-force` 的控制面升级在服务仍提供服务时等待不可保留的运行结束，再暂停接收。等待结束或排空期限已过时，错误和报告会指出阻塞项。排空状态轮询和失败后的状态探测不再过早超时而误报“未在服务”。

**是否有破坏性变更：**否。没有迁移，没有移除 API。新选项默认 0（关闭）。桥接边界不变：早于 v2.13.165 的安装须先升级到 v2.13.165。

**如何验证：**核对版本为 2.14.153。

**贡献者：**维护者 @foolzzz 提交 [#1273](https://github.com/foolzzz/looper/pull/1273)；本版本无社区贡献。

```bash
looper --version   # looper 2.14.153
```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.152 上的安装可直接升级。没有结构变更。

### 行为变化与入口

- **预检等待**（[#1273](https://github.com/foolzzz/looper/pull/1273)，`looper/cli.py`、`looper/agents/service.py`）。`looper service upgrade --preflight-wait SECONDS`（默认 0，关闭；须为非负有限数）只对带 `--no-force` 的控制面升级生效。排空前，升级每 15 秒读取一次排空状态（服务继续提供服务），一旦没有不可保留的运行就开始排空。若服务已不在 serving 状态，则以“the service is already draining; deployment stopped”停止。等待结束时仍有不可保留的运行，则在未排空的前提下拒绝，给出数量和阻塞摘要，报告含 `blockers`。已等待时间写入新的报告字段 `preflight_wait_seconds`（未使用时为 0.0）。
- **取消时附带阻塞项**（`looper/agents/service.py`）。`--no-force` 下排空期限已过时，错误和 `report["blockers"]` 列出不可保留的运行及其 `age_seconds`（无法读取开始时间时为 null）、Manager 与 Planner 的回合，以及 gates、waits、consults、starting 的数量；非控制面排空还列出可保留的运行。排空期间每 60 秒向 stderr 输出一行 `drain waiting (Ns): ...` 摘要。
- **更长的读取超时并重试**（`looper/agents/service.py`）。排空状态轮询（含租约续期）和失败后的状态探测使用升级读取超时（15 秒），而不是 3 秒。排空状态读取超时会重试两次，其他错误立即抛出。调用方仍检查阶段，以防控制器租约已过期。状态探测的改动避免把繁忙但仍在服务的实例误报为未在服务。
- **排空状态中的运行时信息**（`looper/agents/tiers/worker.py`、`looper/agents/v1_domains/drain.py`）。`waiting.runs` 中每个运行新增可为空的 `runtime_id` 和 `runtime_type`，在运行启动或接管时设置；两者在 schema 中可选，旧数据仍有效。
- **不变：**前端无改动；控制台、Telegram 和 Lark 仍使用共享的准入屏障。PR 还修正了回归测试中的时序假设（仅测试）。
- **文档：**PR 描述称已记录该选项和报告字段，但其 diff 不含文档文件；该选项只有 `looper service upgrade --help` 中的帮助文本。
- **面向模型的变化：**无。改动只涉及服务 CLI、其报告和排空状态载荷；没有改动提示词、工具、工具结果或 Manager 范围文本。

# Looper v2.14.75

This is the patch release v2.14.75, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.74: moving a project's directory together with its files ([#1075](https://github.com/foolzzz/looper/pull/1075)).

## Release Decision

**Who should upgrade:** Operators who want to relocate a project's directory (for example under the projects root) without moving the files by hand and fixing every schedule afterwards. Nobody else needs it: nothing changes unless a move is requested.

**What this release solves:** Changing a project's directory used to change only the stored path, so the files had to be moved first. [#1075](https://github.com/foolzzz/looper/pull/1075) adds a move that renames the directory, keeps the old path working and updates what pointed at it.

**Breaking changes:** No. The change adds an operation, an action, a dashboard section and one additive table; changing a project's directory through `update` behaves as before.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#1075](https://github.com/foolzzz/looper/pull/1075); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.75
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.74 upgrades directly. This release carries a one-time additive schema upgrade (see below) that runs when the service starts.

## Behavior changes

- **Operation.** `project_admin.preview_move_dir` (read) and `project_admin.move_dir` (high risk) take `{project, to?, link_old?}` (`looper/agents/project_move.py`, `looper/agents/v1_domains/projects.py`). With `to` omitted and `[projects] root` set, the target is the first free `<root>/<name>`, `<root>/<name>-2`, … (the name is the same safe directory name project creation uses). API clients get `needs_confirmation` first; the confirmation lists the old and new directory, the number of files and their size (counting stops at a limit and says so), the schedules whose directory moves along, whether the old path is kept as a link, and states that nothing running is interrupted. The confirmation is bound to a `move_version` that covers the project, the schedules and the source directory; if any of them changed, the move is refused and must be confirmed again. The confirmation text itself is written in Chinese.
- **Refusals, before anything is touched.** The project has no directory or it does not exist; the target already exists (an empty directory included); the target is relative, inside the current directory, has no writable parent or is on another filesystem (there is no cross-device copy); the project directory is a symbolic link or a git submodule checkout; the project has an in-progress task, step, running model call, running command schedule run, schedule run gating or open user gate. When `link_old` is false, a move is also refused if a task, workspace, template, schedule or another project depends on the directory. Only one move or delete per project runs at a time. Through the Manager, a project that is also used outside that Manager cannot be moved.
- **Move.** `os.rename` on the same filesystem, then a symbolic link at the old path unless `link_old` is false. `git worktree repair` runs for the moved repositories and for Looper's task and step worktrees, and the result lists each repository's outcome; submodules are left alone. One transaction, under table locks, rewrites the project's directory, every command and agent schedule whose directory is at or under the old one, and the recorded task worktree paths, and adds a `directory_moved` line to a new per-project activity history.
- **Failure handling.** If the transaction fails or is cancelled before the commit, the directory is renamed back and the link removed. Once it has committed, a later cancellation never undoes the move (a missing old-path link is logged).
- **Operator notes.** When notes are enabled and the notes belong to the moved checkout, the notes directory is renamed to the new key after the commit. When they belong to a checkout that stays, the new name is taken, the key is unchanged or the notes do not exist, they stay and the result says why. Notes are never merged or deleted.
- **Dispatch during a move.** The scheduler's project barrier now distinguishes a delete from a move. While a move runs, a task start, restart, schedule gate completion and a Planner's ready-step dispatch wait for it and then continue, instead of being lost or failed; during a delete they are still refused. A restart reads the task row again after waiting. Waits happen before database locks are taken.
- **Schema.** A new table `project_activity` (project id, kind, summary, time). An existing database gets it once (migration `project_activity`) under the schema lock; a fresh database already has it. `schema_change_pending` reports it, so the backup step before a schema change covers it. A downgrade ignores the table.
- **API errors.** For the two move operations the refusal message of the server is returned to the client instead of the generic "the operation was refused".
- **Dashboard.** Project → Settings has a directory move with a preview, a confirmation and the result (including the notes outcome); a refusal shows the server's reason.
- **Evals.** The Manager dialogs `project_move_dir` (move under the projects root after confirmation) and `project_dir_plain` (changing the stored path only, at once).
- **Size:** per the changed files of the pull request, about 2,600 added lines in total, of which about 1,700 are tests.
- **Model-visible changes:** The `looper_projects` tool description and schema gain the `move` action and the `to` and `link_old` arguments, and the tool's confirmation text for a move is new. No built-in role text or prompt changes. Changing a directory with `update` is unchanged.

## Optional Capability Activation & Use

### Project directory move

**Activation:** Nothing to enable. In Project → Settings choose the directory move, or ask the Manager to move the project; with `[projects] root` set the target can be left out. The Manager and API clients confirm before anything moves.

```bash
looper --version   # looper 2.14.75
```

**Validation:** After a move, Project → Settings shows the new directory and the result lists the git repairs and the notes outcome; the old path is a symbolic link to the new directory unless `link_old` was false, and the project's schedules point under the new directory.

**Disable / rollback:** Nothing to disable: no move happens unless requested. A completed move is undone by moving the project back to a path that does not exist (remove the old-path link first). The new table is not removed by a downgrade.

**Authority boundary:** A move is high risk and needs the user's confirmation. It only renames within one filesystem, never copies or deletes files, never interrupts a running task, command or gate (it refuses instead), and never merges notes.

**Docs:** [evals/README.md](https://github.com/foolzzz/looper/blob/main/evals/README.md).

## 中文摘要

本版本是 patch release v2.14.75（热修线，每个合并的改动立即发布）。自 v2.14.74 以来只合并了一项改动：连同文件一起移动项目目录（[#1075](https://github.com/foolzzz/looper/pull/1075)）。

### 升级决策

**谁需要升级：**希望把项目目录迁移（例如迁到 projects 根目录下），又不想手动搬文件、事后逐个修正定时任务的运维人员。其他人无需升级：不发起移动就没有任何变化。

**解决了什么：**此前修改项目目录只改存储的路径，必须先手动搬文件。[#1075](https://github.com/foolzzz/looper/pull/1075) 增加移动操作：重命名目录、保持旧路径可用，并更新引用它的内容。

**是否有破坏性变更：**否。本改动增加操作、动作、控制台区块和一张只增不改的表；通过 `update` 修改项目目录的行为不变。

**如何验证：**运行 `looper --version` 核对版本为 2.14.75。

**贡献者：**维护者 @foolzzz 提交 [#1075](https://github.com/foolzzz/looper/pull/1075)；本版本无社区贡献。

```bash
looper --version   # looper 2.14.75
```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.74 上的安装可直接升级。本版本带有一次性的增量数据库升级（见下），在服务启动时执行。

### 行为变化与入口

- **操作。**`project_admin.preview_move_dir`（只读）和 `project_admin.move_dir`（高风险）接收 `{project, to?, link_old?}`（`looper/agents/project_move.py`、`looper/agents/v1_domains/projects.py`）。省略 `to` 且设置了 `[projects] root` 时，目标为第一个空闲的 `<root>/<name>`、`<root>/<name>-2` ……（名称与创建项目时使用的安全目录名相同）。API 客户端先得到 `needs_confirmation`；确认内容列出旧目录和新目录、文件数量与大小（计数到上限即停止并注明）、目录随之移动的定时任务、是否保留旧路径链接，并说明不会中断任何运行。确认绑定到 `move_version`，它覆盖项目、定时任务和源目录；任何一项变化都会拒绝移动并需重新确认。确认文本本身为中文。
- **拒绝条件（在改动任何内容之前）。**项目没有目录或目录不存在；目标已存在（含空目录）；目标为相对路径、位于当前目录之内、父目录不可写或在另一个文件系统上（不做跨设备复制）；项目目录是符号链接或 git 子模块检出；项目有进行中的任务、步骤、运行中的模型调用、运行中的命令定时任务、处于 gating 的定时任务运行或未关闭的用户 gate。`link_old` 为 false 时，若有任务、工作区、模板、定时任务或其他项目依赖该目录，也会拒绝。每个项目同一时间只运行一个移动或删除。通过 Manager 时，也被 Manager 之外使用的项目不能移动。
- **移动。**同一文件系统内 `os.rename`，随后在旧路径放置符号链接（`link_old` 为 false 时不放）。对移动后的仓库以及 Looper 的任务和步骤 worktree 运行 `git worktree repair`，结果列出每个仓库的情况；子模块不处理。一个事务在表锁下改写项目目录、目录位于旧目录处或其下的每个命令和 Agent 定时任务、已记录的任务 worktree 路径，并向新的项目活动历史写入一条 `directory_moved`。
- **失败处理。**事务在提交前失败或被取消时，目录改回原名并移除链接。提交之后的取消不会撤销移动（缺少旧路径链接会记录日志）。
- **操作员笔记。**笔记启用且属于被移动的检出时，提交后将笔记目录重命名为新键。若属于保持原位的检出、新名称已被占用、键未变化或笔记不存在，则笔记不动，结果会说明原因。笔记从不合并或删除。
- **移动期间的派发。**调度器的项目屏障现在区分删除与移动。移动期间，任务启动、重启、定时任务 gate 完成以及 Planner 的就绪步骤派发会等待移动结束再继续，不会丢失或失败；删除期间仍被拒绝。重启在等待后重新读取任务行。等待发生在获取数据库锁之前。
- **数据库结构。**新增表 `project_activity`（项目 id、类型、摘要、时间）。已有数据库在 schema 锁下一次性获得它（迁移 `project_activity`）；新数据库已包含。`schema_change_pending` 会报告该变更，因此 schema 变更前的备份步骤涵盖它。降级会忽略该表。
- **API 错误。**对这两个移动操作，服务器返回具体的拒绝原因，而不是通用的「the operation was refused」。
- **控制台。**项目 → 设置提供目录移动：预览、确认和结果（含笔记结果）；被拒绝时显示服务器给出的原因。
- **评测。**Manager 对话 `project_move_dir`（确认后移动到 projects 根目录下）和 `project_dir_plain`（只改存储路径，立即执行）。
- **规模：**据 PR 的改动文件，共新增约 2,600 行，其中约 1,700 行为测试。
- **面向模型的变化：**`looper_projects` 工具说明和 schema 增加 `move` 动作及 `to`、`link_old` 参数，移动的确认文本为新增。无内置角色文本或提示词变化。通过 `update` 修改目录不变。

### 可选能力启用与使用

#### Project directory move

**启用：**无需开启。在项目 → 设置中选择目录移动，或让 Manager 移动该项目；设置了 `[projects] root` 时可省略目标。Manager 和 API 客户端会在移动前确认。

```bash
looper --version   # looper 2.14.75
```

**验证：**移动后，项目 → 设置显示新目录，结果列出 git 修复和笔记结果；除非 `link_old` 为 false，旧路径是指向新目录的符号链接，且项目的定时任务指向新目录之下。

**停用 / 回退：**无需停用：不请求就不会移动。已完成的移动可通过把项目移回一个不存在的路径来撤销（先移除旧路径链接）。降级不会删除新表。

**权限边界：**移动属于高风险，需要用户确认。它只在一个文件系统内重命名，从不复制或删除文件，从不中断运行中的任务、命令或 gate（而是拒绝），也从不合并笔记。

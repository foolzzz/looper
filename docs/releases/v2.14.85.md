# Looper v2.14.85

This is the patch release v2.14.85, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.84: a scenario Manager can now own a set of projects and act on every task of those projects, whoever created it ([#1103](https://github.com/foolzzz/looper/pull/1103)).

## Release Decision

**Who should upgrade:** Operators who run scenario Managers and want a Manager to follow the tasks of chosen projects, including tasks created by schedules, the API or other Managers. Everyone else can stay.

**What this release solves:** A Manager saw either every task (`all`) or only the tasks it created (`own`), so a Manager meant to follow a project's tasks could not reach tasks it did not create without also reaching every other project. [#1103](https://github.com/foolzzz/looper/pull/1103) adds the task scope `projects`.

**Breaking changes:** No. No setting, operation or field is removed. Managers with `all` or `own` behave as before. There is an additive database change, applied at start (see Upgrading).

**How to verify:** Check the installed version. In Settings → Managers, the task scope editor offers "Projects" with a project picker; a Manager with `tools = tasks` and that scope lists and instructs tasks of its projects only, and a task of another project is refused as `forbidden`.

**Contributors:** Maintainer @foolzzz authored [#1103](https://github.com/foolzzz/looper/pull/1103); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.85
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.84 upgrades directly. The database gains the column `managers.scope_project_ids` and two constraints through the named upgrade `manager_scope_projects`, applied once at start; the `task_scope` check also admits `projects`. A fresh schema already contains them.

## Behavior changes

- **New task scope `projects`** (`looper/agents/managers_api.py`, `looper/db/schema.sql`, `looper/db/connection.py`). A Manager's `task_scope` may be `projects` with `scope_project_ids`, 1 to 20 project ids that must exist. The scope requires `tools = tasks`: the API refuses other combinations with 400, and a database CHECK keeps it so. A scope that is not `projects` holds no project ids; changing away from `projects` clears them.
- **What the Manager may do with it.** `ManagerOps` lists, reads, supplements, instructs, controls and cancels only tasks of those projects, whoever created them, and creates tasks only there. A template of such a Manager must name one of its projects: saving a template elsewhere, or choosing a scope that leaves a template outside it, is refused (the latter with 409). Anything outside the scope answers `forbidden`.
- **Per-turn context and gates** (`looper/agents/tiers/manager.py`, `looper/agents/gate_commands.py`). For `projects`, the `Projects`, `Ready tasks` and `Open gates` sections and the `/gates` list follow the same project filter. If the scope cannot be read, those sections say "(could not be read)" instead of listing.
- **Project deletion** (`looper/agents/projects.py`). Deleting a project removes it from every scope and bumps the revision of each affected Manager. A Manager left with no project stays `projects` with an empty list: it sees and creates nothing and says so in the dashboard, the `Projects` section and tool errors, until the operator chooses projects. The delete confirmation names the affected Managers.
- **Dashboard.** The scope editor in Settings → Managers offers "Projects" with a project picker.
- **Config export and import** carry the scope by project name (`scope_projects`).
- **Unchanged:** Managers with `all` or `own`, the default Manager, wheel and source upgrades, and the rest of the API.
- **Documentation and tests.** `docs/architecture/agent-system.md` describes the scope and the `managers` columns. The pull request adds PostgreSQL and unit tests for the scope rules, tools, prompt sections, gates, project deletion, the schema upgrade and config transfer, a headless-browser test of the scope editor, and the eval dialog `project_scope_manager`.
- **Model-visible changes:** A Manager with the `projects` scope receives a short scope contract in its instructions, its per-turn sections are filtered by project, and its tool results can be `forbidden` outside its projects. With `all` or `own` every prompt and tool text is unchanged.

## 中文摘要

本版本是 patch release v2.14.85（热修线，每个合并的改动立即发布）。自 v2.14.84 以来只合并了一项改动：场景管家现在可以拥有一组项目，并处理这些项目的所有任务，不论任务由谁创建（[#1103](https://github.com/foolzzz/looper/pull/1103)）。

### 升级决策

**谁需要升级：**使用场景管家、希望某个管家跟进所选项目的任务（包括定时任务、API 或其他管家创建的任务）的运维人员。其他人可不升级。

**解决了什么：**管家要么看到全部任务（`all`），要么只看到自己创建的任务（`own`），想跟进某个项目任务的管家若不同时触及所有其他项目，就够不到非自己创建的任务。[#1103](https://github.com/foolzzz/looper/pull/1103) 新增任务范围 `projects`。

**是否有破坏性变更：**否。没有移除设置、操作或字段。`all` 或 `own` 的管家行为不变。有一项新增的数据库变更，启动时自动应用（见升级一节）。

**如何验证：**核对版本为 2.14.85。在 设置 → 管家 中，任务范围编辑器提供"项目"及项目选择器；`tools = tasks` 且使用该范围的管家只列出并操作其项目的任务，其他项目的任务会被拒绝（`forbidden`）。

**贡献者：**维护者 @foolzzz 提交 [#1103](https://github.com/foolzzz/looper/pull/1103)；本版本无社区贡献。

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.84 上的安装可直接升级。数据库通过命名升级 `manager_scope_projects` 新增列 `managers.scope_project_ids` 和两个约束，启动时应用一次；`task_scope` 检查同时接受 `projects`。全新的库结构已包含这些内容。

### 行为变化与入口

- **新增任务范围 `projects`**（`looper/agents/managers_api.py`、`looper/db/schema.sql`、`looper/db/connection.py`）。管家的 `task_scope` 可设为 `projects`，并带 `scope_project_ids`：1 到 20 个必须存在的项目 id。该范围要求 `tools = tasks`：其他组合 API 返回 400，数据库 CHECK 约束也保证这一点。非 `projects` 范围不保存项目 id；从 `projects` 改成其他范围会清空它们。
- **该范围下管家能做什么。**`ManagerOps` 只列出、读取、补充、指示、控制和取消这些项目的任务，不论创建者，也只在这些项目中创建任务。这类管家的模板必须指向其项目之一：把模板存到其他项目，或选择了让模板落到范围之外的范围，都会被拒绝（后者返回 409）。范围之外一律返回 `forbidden`。
- **每轮上下文与关卡**（`looper/agents/tiers/manager.py`、`looper/agents/gate_commands.py`）。对 `projects`，`Projects`、`Ready tasks`、`Open gates` 各节和 `/gates` 列表按同样的项目过滤。读不到范围时，这些节显示"(could not be read)"而不列出内容。
- **删除项目**（`looper/agents/projects.py`）。删除项目会把它从所有范围中移除，并提升每个受影响管家的 revision。没有任何项目的管家仍为 `projects` 且列表为空：什么也看不到、也不能创建，并在仪表盘、`Projects` 节和工具错误中说明，直到运维人员重新选择项目。删除确认会列出受影响的管家。
- **仪表盘。**设置 → 管家 的范围编辑器提供"项目"及项目选择器。
- **配置导出与导入**按项目名称携带该范围（`scope_projects`）。
- **不变：**`all` 或 `own` 的管家、默认管家、wheel 与源码升级，以及 API 的其余部分。
- **文档与测试。**`docs/architecture/agent-system.md` 描述了该范围和 `managers` 的列。该 PR 新增了覆盖范围规则、工具、提示各节、关卡、项目删除、结构升级和配置迁移的 PostgreSQL 与单元测试，范围编辑器的无头浏览器测试，以及评测对话 `project_scope_manager`。
- **面向模型的变化：**使用 `projects` 范围的管家会在指令中收到一段简短的范围约定，每轮各节按项目过滤，范围之外的工具结果可能是 `forbidden`。`all` 或 `own` 的提示和工具文本均不变。

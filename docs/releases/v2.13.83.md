# Looper v2.13.83

## Release Decision

**Who should upgrade:** Anyone who chats with the Manager or a running task's Planner from the dashboard, or who calls `POST /api/chat/send` or `GET /api/chat/events` from a script. Everyone else gets no change.

**What this release solves:** [#524](https://github.com/foolzzz/looper/pull/524) moves dashboard chat sending and both reply streams onto three operator-only operations in the versioned API, and removes the two legacy routes.

**Breaking changes:** Yes. `POST /api/chat/send` and `GET /api/chat/events` (by `?cid=` or `?session=`) are removed; a script that calls them must use `POST /api/v1/operator_chat/send`, `reply_events` or `thread_events`. The send result no longer carries `events_url`. The dashboard shipped in this release already uses the new operations. Client-owned conversations (`/api/v1/chat/...`) are not touched.

**How to verify:** Check the installed version.

**Contributors:** Maintainer @foolzzz authored [#524](https://github.com/foolzzz/looper/pull/524); no community contribution was included in this patch release.

```bash
looper --version   # looper 2.13.83
```

## Behavior changes

- **Three operations on v1 ([#524](https://github.com/foolzzz/looper/pull/524)):** the new `looper/agents/v1_domains/operator_chat_streams.py` registers `operator_chat.send` (risk `write`), `operator_chat.reply_events` and `operator_chat.thread_events` (risk `read`, streams), all `POST` at `/api/v1/operator_chat/<action>` and all `operator_only`, so an API client credential cannot reach them. Requests are closed objects.
- **Send:** takes `text` (1 to 32000 characters), and optionally `session_id`, `message_id`, `target` (the Manager, default, or `{kind: planner, task_id}`), `new_session_profile_id`, `language` (`zh` or `en`), `goal_id` and `attachments`. It returns `{correlation_id}`. It runs the same target resolution, `/new` profile check, thread-owner check and `_deliver_chat` as the old route; Planner messages still use the shared durable supplement dispatch. Errors are v1 errors: a thread owned by another Manager, or a Planner target without a running Planner, is `conflict`; a bad `new_session_profile_id` or empty text is `invalid`. The old 400/409 JSON bodies are gone.
- **Streams:** `reply_events` takes `correlation_id` and follows one reply until its final answer or timeout; an unknown correlation ends at once. `thread_events` takes `session_id` and optional `manager`, checks the thread's Manager owner before sending headers, and follows saved answers and autonomous messages. Events keep their dashboard names and payloads (`answer.delta`, `answer.final`, `agent.phase`, `chat.message`, `heartbeat`, `system.event`). Leaving the connection closes the subscription (the server closes the reply stream in a `finally`). The server routes these two paths with the same disconnect watcher as `tasks.activity_stream`.
- **Removed routes:** `POST /api/chat/send`, `GET /api/chat/events` and their handlers (`_handle_chat_send`, `_handle_sse_events`, `_handle_chat_session_events`, `_foreign_thread`) are removed from `looper/agents/http_server.py`. The web channel adapter no longer returns `events_url`.
- **Dashboard:** `sendChat` in `web/src/lib/api.ts` calls `operator_chat.send`; `streamSSE` is replaced by `streamChatReply` and `streamChatThread` over the v1 stream helper; `chat.tsx` follows `correlation_id`. A confirmation answer is surfaced as an error. The prompt regression evals, `evals/stop_realpath.py`, `examples/dsh/validate.py` and `examples/pi/isolated-smoke.py` were moved to the new operations.
- **Pattern check start-up (same PR, unrelated to chat):** `looper/agents/task_templates.py` now has the pattern-matching subprocess print `ready` first and waits up to 10 seconds (`PATTERN_STARTUP_TIMEOUT_SEC`) for it, so slow interpreter start-up under load no longer eats the 2 second matching budget. If the subprocess is not ready in time or prints something else, the check fails with a `TemplateError`.
- **Docs:** `README.md`, `README.zh-CN.md`, `docs/architecture/agent-system.md` and `docs/design.md` name the new operations.
- **Tests:** `tests/test_api_v1_operator_chat_streams.py` and `web/src/lib/operator-chat-streams.test.ts` were added; existing chat, manager-session, scenario, DSH, prompt-eval, stop-realpath, task-template and dashboard tests were moved to the new operations.
- **Model-visible changes:** One. The error text of a failed pattern check is now "Looper could not check the input's pattern now; tell the user and try again later" when the checker is not ready, and it is returned to the model that fills a task template. Manager, Planner, Worker and Reviewer prompts, role recommended prompts and Tool declarations are unchanged; the new operations declare no Tool. The operations appear in the v1 operation catalog that API clients read.
- **Not confirmed in code:** this draft did not run any test, and did not trace delivery of a Planner supplement or the stream timeout.

## Upgrade and rollback

Re-run `install.sh` once v2.13.83 is published. No data migration. Update any script that used the removed routes. Rolling back to v2.13.82 restores them together with the old dashboard.

### 行为变化与入口

- **三个 v1 操作（[#524](https://github.com/foolzzz/looper/pull/524)）：**新增 `looper/agents/v1_domains/operator_chat_streams.py`，注册 `operator_chat.send`（风险 `write`）、`operator_chat.reply_events` 与 `operator_chat.thread_events`（风险 `read`，流式），均为 `POST /api/v1/operator_chat/<action>` 且 `operator_only`，API 客户端凭据无法访问。请求为封闭对象。
- **发送：**接收 `text`（1 至 32000 字符），可选 `session_id`、`message_id`、`target`（默认 Manager，或 `{kind: planner, task_id}`）、`new_session_profile_id`、`language`（`zh`/`en`）、`goal_id`、`attachments`，返回 `{correlation_id}`。目标解析、`/new` 配置检查、会话归属检查和 `_deliver_chat` 与旧路由相同；发给 Planner 的消息仍走共享的持久化补充消息分发。错误改为 v1 错误：会话属于另一个 Manager，或 Planner 目标没有运行中的 Planner，为 `conflict`；`new_session_profile_id` 不合法或文本为空，为 `invalid`。旧的 400/409 JSON 正文不再出现。
- **流：**`reply_events` 接收 `correlation_id`，跟随一次回复直到最终答案或超时；未知的 correlation 立即结束。`thread_events` 接收 `session_id` 和可选 `manager`，在发送响应头之前检查会话的 Manager 归属，并跟随已保存的回答与自主消息。事件保留仪表盘原有的名称与负载（`answer.delta`、`answer.final`、`agent.phase`、`chat.message`、`heartbeat`、`system.event`）。连接断开会关闭订阅（服务器在 `finally` 中关闭回复流）。这两个路径与 `tasks.activity_stream` 共用同一个断开监视。
- **移除的路由：**`POST /api/chat/send`、`GET /api/chat/events` 及其处理函数（`_handle_chat_send`、`_handle_sse_events`、`_handle_chat_session_events`、`_foreign_thread`）已从 `looper/agents/http_server.py` 移除。Web 渠道适配器不再返回 `events_url`。
- **仪表盘：**`web/src/lib/api.ts` 的 `sendChat` 调用 `operator_chat.send`；`streamSSE` 被基于 v1 流辅助函数的 `streamChatReply` 与 `streamChatThread` 取代；`chat.tsx` 跟随 `correlation_id`。确认应答会作为错误抛出。prompt 回归评测、`evals/stop_realpath.py`、`examples/dsh/validate.py`、`examples/pi/isolated-smoke.py` 已改用新操作。
- **模式检查启动（同一 PR，与聊天无关）：**`looper/agents/task_templates.py` 让模式匹配子进程先输出 `ready`，并最多等待 10 秒（`PATTERN_STARTUP_TIMEOUT_SEC`），负载高时解释器启动慢不再占用 2 秒的匹配预算。子进程未及时就绪或输出其他内容时，检查以 `TemplateError` 失败。
- **文档：**`README.md`、`README.zh-CN.md`、`docs/architecture/agent-system.md`、`docs/design.md` 已写明新操作。
- **测试：**新增 `tests/test_api_v1_operator_chat_streams.py` 与 `web/src/lib/operator-chat-streams.test.ts`；现有的聊天、Manager 会话、场景、DSH、prompt 评测、stop-realpath、任务模板和仪表盘测试已改用新操作。
- **面向模型的变化：**有一处。模式检查器未就绪时，错误文本变为 “Looper could not check the input's pattern now; tell the user and try again later”，并返回给填写任务模板的模型。Manager、Planner、Worker、Reviewer 的 prompt、角色推荐 prompt 以及 Tool 声明均未改动；新操作未声明 Tool。这些操作会出现在 API 客户端读取的 v1 操作目录中。
- **代码中未确认：**本草稿未运行任何测试，也未追踪 Planner 补充消息的投递和流超时。

# Looper v2.14.83

This is the patch release v2.14.83, a hotfix line in which each merged change ships at once. It ships the one change merged since v2.14.82: `looper serve` starts listening sooner because runtime probes and advisory checks no longer run one after another before it listens ([#1093](https://github.com/foolzzz/looper/pull/1093)).

## Release Decision

**Who should upgrade:** Operators whose `looper serve` takes tens of seconds to start answering (many runtime CLIs installed), for example because deploys stay down too long or a test server misses its startup window. Everyone else can stay.

**What this release solves:** Startup had grown to about 45-55 s before the HTTP server listened, because every runtime CLI was probed one after another and the advisory startup checks ran one after another before listening, although they only warn. [#1093](https://github.com/foolzzz/looper/pull/1093) probes the runtimes concurrently and runs the advisory checks in the background after the server listens.

**Breaking changes:** No. No setting, operation or field is removed and there is no schema change. The registered runtime rows are the same as before for the same probe answers.

**How to verify:** Check the installed version. In the log, the line `HTTP server listening on` now ends with the seconds since process start, and a `probed runtime` line appears for each probed runtime at startup.

**Contributors:** Maintainer @foolzzz authored [#1093](https://github.com/foolzzz/looper/pull/1093); no community contribution was included in this release.

```bash
looper --version   # looper 2.14.83
```

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.82 upgrades directly. There is no database change.

## Behavior changes

- **Concurrent runtime probes** (`looper/agents/profile_registry.py`). `register_found_runtimes` probes every runtime type and launcher pair at the same time, then writes the rows in adapter/launcher order, so the rows are the same as before for the same probe answers. No outer timeout is added: each adapter bounds its own subprocesses, because an outer timeout would also count executor queue time and drop the real result. It logs `probed runtime <type> in <s> s` for each probe and `probed runtimes in <s> s total`.
- **Advisory checks after listening** (`looper/agents/serve.py`). The Claude, Codex, Grok and Cursor login, TTADK, lark-cli, git and projects-root checks run concurrently in a background task started right after the HTTP server listens, and log their problems as before. A check that raises is logged and skipped; it never stops serving. The task is cancelled on shutdown. The database check still runs before serving.
- **The server answers while checks run.** Warnings from the advisory checks appear in the log a few seconds after listening. Until they finish, `system/status` reports only the database check under `checks`; once they finish it reports all of them, in the original order.
- **Startup log** (`looper/__init__.py`, `looper/agents/http_server.py`). The listening line gives the seconds since process start.
- **Documentation and tests.** The module docstring of `looper/agents/self_check.py` describes the new order. New tests cover concurrent probes (same rows, about the time of the slowest probe) and a slow advisory check not delaying readiness (PostgreSQL); existing tests are adjusted.
- **Unchanged:** the set of checks and probes, the runtime rows, the database check and its failure to start, Manager start after HTTP readiness, and the API.
- **Model-visible changes:** None. No tool schema, instruction or prompt a model receives changes.

## 中文摘要

本版本是 patch release v2.14.83（热修线，每个合并的改动立即发布）。自 v2.14.82 以来只合并了一项改动：`looper serve` 不再在监听前依次执行运行时探测和建议性检查，因此更早开始监听（[#1093](https://github.com/foolzzz/looper/pull/1093)）。

### 升级决策

**谁需要升级：**`looper serve` 需要数十秒才开始响应的运维人员（安装了很多运行时 CLI），例如部署停机过久或测试服务器错过启动窗口。其他人可不升级。

**解决了什么：**启动在 HTTP 服务监听前曾长达约 45-55 秒，因为每个运行时 CLI 依次探测，建议性启动检查也在监听前依次执行，尽管它们只发出警告。[#1093](https://github.com/foolzzz/looper/pull/1093) 并发探测运行时，并在服务监听后于后台运行建议性检查。

**是否有破坏性变更：**否。没有移除设置、操作或字段，也没有数据库结构变更。相同探测结果下，注册的运行时行与以前相同。

**如何验证：**核对版本为 2.14.83。日志中 `HTTP server listening on` 一行现在以自进程启动以来的秒数结尾，启动时每个被探测的运行时出现一行 `probed runtime` 日志。

**贡献者：**维护者 @foolzzz 提交 [#1093](https://github.com/foolzzz/looper/pull/1093)；本版本无社区贡献。

```bash
looper --version   # looper 2.14.83
```

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.82 上的安装可直接升级。没有数据库变更。

### 行为变化与入口

- **并发运行时探测**（`looper/agents/profile_registry.py`）。`register_found_runtimes` 同时探测所有运行时类型与启动器组合，之后按适配器/启动器顺序写入，因此相同探测结果下行与以前相同。没有增加外层超时：每个适配器自行限制其子进程，外层超时还会计入线程池排队时间并丢弃真实结果。每次探测记录 `probed runtime <type> in <s> s`，并记录总耗时 `probed runtimes in <s> s total`。
- **监听后的建议性检查**（`looper/agents/serve.py`）。Claude、Codex、Grok、Cursor 登录、TTADK、lark-cli、git 和项目根目录检查在 HTTP 服务监听后立即以后台任务并发运行，问题照常记入日志。抛出异常的检查会被记录并跳过，不会中止服务。关闭时该任务被取消。数据库检查仍在服务前运行。
- **检查进行时服务器已可响应。**建议性检查的警告在监听后几秒出现在日志中。在它们完成之前，`system/status` 的 `checks` 只包含数据库检查；完成后按原顺序包含全部检查。
- **启动日志**（`looper/__init__.py`、`looper/agents/http_server.py`）。监听日志行给出自进程启动以来的秒数。
- **文档与测试。**`looper/agents/self_check.py` 的模块文档描述了新的顺序。新增测试覆盖并发探测（行相同，耗时约等于最慢一次探测）以及慢的建议性检查不延迟就绪（PostgreSQL）；现有测试已调整。
- **不变：**检查与探测的集合、运行时行、数据库检查及其失败时不启动、Manager 在 HTTP 就绪后启动，以及 API。
- **面向模型的变化：**无。模型收到的工具模式、指令和提示均不变。

# Looper v2.14.130

This is the patch release v2.14.130, a hotfix line in which each merged change ships at once. It documents one change: [#1218](https://github.com/foolzzz/looper/pull/1218) (the dashboard shows the `coco` runtime as "Coco (TRAE CLI)", explains its login and places model refusals beside the Model input).

## Release Decision

**Who should upgrade:** Operators who use or want to use Coco (TRAE CLI) from the dashboard; anyone who creates Agent Profiles through the dashboard, the HTTP v1 API, Telegram, Lark or the CLI and wants an unknown coco model refused at the first save. Everyone else gets no change.

**What this release solves:** [#1218](https://github.com/foolzzz/looper/pull/1218) completes the dashboard side of the `coco` runtime: the runtime cards, the Agent Profile selections and the `coco login` row. A model refusal now appears at the Model input, and a usable coco login warms the model catalog during runtime discovery or probing so that the first profile save can already refuse an unknown model.

**Breaking changes:** No. There is no migration and no API removal; the v1 error envelope gains an optional field. The bridge boundary is unchanged: upgrade to v2.13.165 first if the installation is older.

**How to verify:** Check the installed version.

```bash
looper --version   # looper 2.14.130
```

**Contributors:** Maintainer @foolzzz authored [#1218](https://github.com/foolzzz/looper/pull/1218); no community contribution was included in this release.

## Upgrading

The bridge boundary is unchanged: an installation older than v2.13.165 must upgrade to v2.13.165 first (upgrade to v2.13.165 first) and be started once; see the Upgrading section of the v2.14.0 release for the steps and rollback. An installation on v2.14.0 to v2.14.129 upgrades directly. There is no schema change.

## Behavior changes

- **Coco in the dashboard** ([#1218](https://github.com/foolzzz/looper/pull/1218)). Runtime cards identify `coco` as "Coco (TRAE CLI)" with no install command. Settings lists its detected version and supported roles, Agent Profiles select registered models from the `coco-login` provider, and the provider's login row shows `coco login status` and `coco login` when the login cannot be used. `coco_login` joins the login checks that the startup banner shows when they fail. The "Check ...; run ..." sign-in wording applies to coco only; Codex and Cursor keep their wording.
- **Model refusals carry a field.** Registry and operation errors (`RegistryError`, `RuntimeUnsupported`, `OpError`) take an optional `field`. The v1 error envelope and the OpenAPI `OpError` schema gain an optional `error.field`, and API-client errors carry it too. It is omitted when unset and for credential-writing operations. Coco's catalog refusals (unknown model) set `field: "model"`. The profile form shows only a server error with that field at the Model input, with `aria-invalid="true"`; choosing another model, provider or runtime clears it. Other errors, including duplicate names and effort refusals, stay in the form's bottom error.
- **The model catalog is warmed.** During first registration of the coco runtime, startup with an existing registration, and re-detection or probing, Looper checks for a usable coco login and, if there is one, reads `coco models` in a worker thread into the process-local catalog. Pairing checks only read that cache. With a logged-out or unknown login, or a failed catalog read, the earlier deferred validation at launch is kept.
- **Telegram, Lark and the CLI** share the registry validation and receive the optional v1 field; their interaction flow is unchanged.
- **Unchanged:** all other runtimes, run behavior of coco itself, and the HTTP v1 errors without a field.
- **Model-visible changes:** None. No Planner, Worker, Reviewer or Manager prompt or contract text changes, and no run `AGENTS.md` text changes. The change touches the dashboard, the v1 error envelope and the registry's validation timing only.

### 升级

桥接边界不变：早于 v2.13.165 的安装必须先升级到 v2.13.165 并启动一次（upgrade to v2.13.165 first 即先升级到 v2.13.165），步骤与回退见 v2.14.0 发布说明的升级一节。v2.14.0 至 v2.14.129 上的安装可直接升级。没有结构变更。

### 行为变化与入口

- **仪表盘中的 Coco**（[#1218](https://github.com/foolzzz/looper/pull/1218)）。运行时卡片把 `coco` 标为 “Coco (TRAE CLI)”，不显示安装命令。设置页列出其检测到的版本和支持的角色，Agent Profile 从 `coco-login` 提供方选择已注册的模型，登录无法使用时提供方的登录行显示 `coco login status` 和 `coco login`。`coco_login` 加入启动横幅在失败时显示的登录检查。“Check ...; run ...” 的登录提示仅用于 coco；Codex 和 Cursor 保持原有措辞。
- **模型拒绝信息带字段。**注册表和操作错误（`RegistryError`、`RuntimeUnsupported`、`OpError`）可带可选的 `field`。v1 错误信封和 OpenAPI 的 `OpError` 模式新增可选的 `error.field`，API 客户端的错误也带它；未设置时以及写入凭据的操作中省略。Coco 的目录拒绝（未知模型）设置 `field: "model"`。Profile 表单只把带该字段的服务器错误显示在 Model 输入框处，并设置 `aria-invalid="true"`；换模型、提供方或运行时后清除。其他错误，包括重名和 effort 拒绝，仍显示在表单底部。
- **预热模型目录。**coco 运行时首次注册、带已有注册的启动、重新检测或探测时，Looper 检查 coco 登录是否可用，可用则在工作线程中读取 `coco models` 到进程内目录。配对检查只读该缓存。登录未登录或未知、目录读取失败时，保持此前在启动运行时才验证的行为。
- **Telegram、Lark 和 CLI** 共用注册表验证并获得可选的 v1 字段，交互流程不变。
- **不变：**所有其他运行时、coco 本身的运行行为，以及不带字段的 HTTP v1 错误。
- **面向模型的变化：**无。Planner、Worker、Reviewer 和 Manager 的提示词与契约文本无变化，运行的 `AGENTS.md` 文本也无变化。改动只涉及仪表盘、v1 错误信封和注册表的验证时机。
